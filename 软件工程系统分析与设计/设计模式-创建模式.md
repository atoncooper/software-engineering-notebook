## 设计模式 —— 创建型模式（Creational Patterns）

创建型模式关注**对象的创建过程**：把"对象如何被创建、组合、表示"这件事从业务代码中剥离出来，让系统不依赖具体类的构造方式。

涉及的模式：**单例（Singleton）、工厂方法（Factory Method）、抽象工厂（Abstract Factory）、建造者（Builder）、原型（Prototype）** 五种（GoF 23 种之一类）。

> 面试提示：创建型模式的面试题几乎一定围绕"什么时候用 X 而不用 Y"展开。每节末尾的"面试速答"是高密度考点。

---

## 一、单例模式（Singleton）

### 1.1 意图

保证一个类**只有一个实例**，并提供一个全局访问点。

### 1.2 适用场景

- 全局配置读取器。
- 日志器、缓存、线程池、数据库连接池。
- 硬件设备访问器（如串口、打印机）。

### 1.3 结构

```
   ┌────────────────────┐
   │   Singleton        │
   ├────────────────────┤
   │ - instance: Singleton  │  ← 类持有唯一实例
   ├────────────────────┤
   │ - Singleton()       │  ← 私有构造，禁止外部 new
   │ + Instance(): Singleton │  ← 全局访问点
   └────────────────────┘
```

### 1.4 难点：线程安全 + 懒加载 + 性能

单例的关键在于处理三件事的平衡：**懒加载（用到才创建）、线程安全（多线程下只创建一次）、性能（不要每次访问都加锁）**。

### 1.5 Java 版（五种写法 + 推荐方案）

#### 写法 1：饿汉式（线程安全，非懒加载）

```java
public class Singleton1 {
    private static final Singleton1 INSTANCE = new Singleton1();
    private Singleton1() {}
    public static Singleton1 getInstance() { return INSTANCE; }
}
```
- 优点：JVM 类加载机制保证线程安全，简单。
- 缺点：类加载即初始化，未用到也占内存；无法处理构造时的异常重试。

#### 写法 2：懒汉式（非线程安全）

```java
public class Singleton2 {
    private static Singleton2 instance;
    private Singleton2() {}
    public static Singleton2 getInstance() {
        if (instance == null) instance = new Singleton2();
        return instance;
    }
}
```
- 严禁在多线程环境使用。

#### 写法 3：同步方法（线程安全，性能差）

```java
public synchronized static Singleton3 getInstance() {
    if (instance == null) instance = new Singleton3();
    return instance;
}
```
- 每次访问都加锁，热点路径性能不可接受。

#### 写法 4：双重检查锁（DCL）—— 推荐

```java
public class Singleton4 {
    private static volatile Singleton4 instance;   // volatile 必须！
    private Singleton4() {}

    public static Singleton4 getInstance() {
        if (instance == null) {                     // 第一次检查：避免无谓加锁
            synchronized (Singleton4.class) {
                if (instance == null) {             // 第二次检查：防止重复创建
                    instance = new Singleton4();
                }
            }
        }
        return instance;
    }
}
```

**关键考点：为什么 `volatile` 不能少？**
> `new Singleton4()` 在 JVM 中是三步：①分配内存 ②初始化对象 ③把引用指向内存。JIT 可能重排为 ①→③→②，导致其它线程拿到"未初始化完的对象"。`volatile` 通过内存屏障禁止重排。

#### 写法 5：静态内部类（推荐）—— 懒加载 + 线程安全 + 无锁

```java
public class Singleton5 {
    private Singleton5() {}

    private static class Holder {
        private static final Singleton5 INSTANCE = new Singleton5();
    }

    public static Singleton5 getInstance() {
        return Holder.INSTANCE;   // 用到才触发 Holder 类的加载
    }
}
```
- JVM 类加载机制保证线程安全；用到 Holder 时才加载，实现懒加载；无锁高性能。
- **Java 单例首选**。

#### 写法 6：枚举（Effective Java 推荐）

```java
public enum Singleton6 {
    INSTANCE;
    public void doWork() { /* ... */ }
}
// 使用：Singleton6.INSTANCE.doWork();
```
- 天然防反射攻击、防反序列化破坏，最简洁。
- 缺点：枚举不能延迟初始化，也不能继承其它类。

### 1.6 Go 版

Go 没有 private 构造函数的概念，靠"包外不可见小写结构体 + 大写访问函数"实现单例。Go 用 `sync.Once` 保证只执行一次。

```go
package singleton

import "sync"

type singleton struct {
    Config map[string]string
}

var (
    instance *singleton
    once     sync.Once
)

// 全局访问点
func GetInstance() *singleton {
    once.Do(func() {
        instance = &singleton{
            Config: loadConfig(),  // 懒加载：只有第一次调用才执行
        }
    })
    return instance
}

func loadConfig() map[string]string {
    return map[string]string{"env": "prod"}
}
```

**`sync.Once` 原理**：
- 内部用 `atomic` + Mutex 实现双重检查，开销极小。
- 即使有多个 goroutine 同时调用 `GetInstance`，`loadConfig()` 也只执行一次。

> Go 单例的常见坑：把 `instance` 字段设为大写（导出），其它包就能直接 `singleton.Instance.Config = ...` 修改，单例语义被破坏。务必小写字段 + 大写访问函数。

### 1.7 单例的反模式与陷阱

| 陷阱 | 说明 | 解决 |
|------|------|------|
| 反射破坏 | Java 反射可调用 private 构造函数 | 枚举单例免疫 |
| 反序列化破坏 | `readObject` 会新建实例 | 实现 `readResolve()` 或用枚举 |
| 全局可变状态 | 单例持有可变状态导致测试不可控 | 优先用依赖注入替代 |
| 隐式依赖 | 业务代码直接 `Singleton.getInstance()`，违反 DIP | 通过构造注入传入 |

### 1.8 面试速答

- **Q：单例有几种写法？** A：饿汉、懒汉、同步方法、DCL、静态内部类、枚举。推荐静态内部类或枚举。
- **Q：DCL 为什么要 volatile？** A：禁止 new 对象时的指令重排，避免拿到未初始化对象。
- **Q：枚举单例为什么防反射？** A：JVM 规定不能通过反射创建枚举对象，构造时会抛异常。
- **Q：Go 怎么实现单例？** A：`sync.Once` + 包级私有结构体 + 大写访问函数。
- **Q：单例 vs 全局变量？** A：单例是"受控的全局变量"，构造时机受控、唯一性受控、可加访问钩子。

## 二、工厂方法模式（Factory Method）

### 2.1 意图

定义一个创建对象的接口，但由子类决定实例化哪个类。工厂方法让类的实例化延迟到子类。

### 2.2 适用场景

- 创建对象时不想指定确切类（面向接口编程）。
- 希望把"使用对象"和"创建对象"解耦。
- 后续可能新增产品类型，希望扩展时不动调用方。

### 2.3 结构

```
   ┌──────────────┐         creates        ┌──────────────┐
   │   Creator    │ ─────────────────────▶ │   Product    │  (接口)
   └──────┬───────┘                         └──────┬───────┘
          │                                        │
   ┌──────┴───────┐                         ┌──────┴───────┐
   │ ConcreteCreator│ creates               │ ConcreteProduct│
   └──────────────┘ ─────────────────────▶ └──────────────┘
```

### 2.4 Java 版

```java
// 产品接口
public interface Logger {
    void log(String msg);
}

// 具体产品
public class FileLogger implements Logger {
    public void log(String msg) { System.out.println("[FILE] " + msg); }
}
public class ConsoleLogger implements Logger {
    public void log(String msg) { System.out.println("[CONSOLE] " + msg); }
}

// 工厂接口
public interface LoggerFactory {
    Logger createLogger();   // 工厂方法
}

// 具体工厂
public class FileLoggerFactory implements LoggerFactory {
    public Logger createLogger() { return new FileLogger(); }
}
public class ConsoleLoggerFactory implements LoggerFactory {
    public Logger createLogger() { return new ConsoleLogger(); }
}

// 客户端：面向工厂接口，不 new 具体产品
public class App {
    private final LoggerFactory factory;
    public App(LoggerFactory factory) { this.factory = factory; }

    public void run() {
        Logger logger = factory.createLogger();
        logger.log("hello");
    }
}
```

新增 `DBLogger` 时，只需新增 `DBLogger` + `DBLoggerFactory` 两个类，客户端 `App` 代码不动 —— 符合 OCP。

### 2.5 Go 版

Go 没有抽象类/继承，工厂方法通常用**函数 + 接口**实现。两种风格：工厂函数 / 接口工厂。

#### 风格 1：工厂函数（简单场景）

```go
package logger

type Logger interface {
    Log(msg string)
}

type fileLogger struct{}
func (fileLogger) Log(msg string) { fmt.Println("[FILE]", msg) }

type consoleLogger struct{}
func (consoleLogger) Log(msg string) { fmt.Println("[CONSOLE]", msg) }

// 工厂函数
func NewLogger(kind string) Logger {
    switch kind {
    case "file":
        return fileLogger{}
    case "console":
        return consoleLogger{}
    default:
        panic("unknown logger: " + kind)
    }
}
```

#### 风格 2：接口工厂（对齐 Java 的工厂方法）

```go
type LoggerFactory interface {
    CreateLogger() Logger
}

type FileLoggerFactory struct{}
func (FileLoggerFactory) CreateLogger() Logger { return fileLogger{} }

type ConsoleLoggerFactory struct{}
func (ConsoleLoggerFactory) CreateLogger() Logger { return consoleLogger{} }

// 客户端
type App struct{ factory LoggerFactory }
func NewApp(f LoggerFactory) *App { return &App{factory: f} }
func (a *App) Run() {
    l := a.factory.CreateLogger()
    l.Log("hello")
}
```

> Go 实践：能用函数就别上接口。只有当"工厂本身需要多态"（比如框架要按配置注入不同工厂）时才用接口工厂。

### 2.6 工厂方法 vs 简单工厂

很多人把"工厂函数 + switch"叫简单工厂，它不是 GoF 模式但很常用。

| 对比项 | 简单工厂 | 工厂方法 |
|--------|---------|---------|
| 结构 | 一个工厂类 + switch | 抽象工厂 + 多个具体工厂 |
| 扩展 | 改 switch，违反 OCP | 新增工厂类，符合 OCP |
| 复杂度 | 低 | 高 |
| 适用 | 产品少、变化少 | 产品多、扩展频繁 |

### 2.7 面试速答

- **Q：工厂方法解决什么问题？** A：把对象创建和使用解耦，新增产品类型不改老代码（OCP）。
- **Q：简单工厂和工厂方法的区别？** A：简单工厂用 switch 集中创建，扩展要改工厂；工厂方法把创建延迟到子类，扩展加新类即可。
- **Q：什么时候不用工厂？** A：对象构造简单、类型稳定、无复杂依赖时，直接 new 更清晰。滥用工厂是过度设计。

## 三、抽象工厂模式（Abstract Factory）

### 3.1 意图

提供一个接口，用于创建**一系列相关或相互依赖的对象**，而无需指定具体类。

### 3.2 与工厂方法的区别

| 对比项 | 工厂方法 | 抽象工厂 |
|--------|---------|---------|
| 创建对象数 | 单个产品 | 一族产品 |
| 扩展方向 | 新增产品类型（加新工厂类） | 新增产品族（加新工厂类） |
| 典型场景 | 创建一个 Logger | 同时创建 UI 控件（Button + Input + Dialog）的整套风格 |

> 一句话：**工厂方法针对"产品等级结构"（同一产品的不同实现），抽象工厂针对"产品族"（一组相关产品的不同实现）**。

### 3.3 结构

```
           ┌─────────────────────┐
           │  GUIFactory (接口)   │
           │  + createButton()   │
           │  + createInput()    │
           └──────────┬──────────┘
        ┌─────────────┴─────────────┐
        ▼                            ▼
   ┌──────────┐                ┌──────────┐
   │MacFactory│                │WinFactory│
   └────┬─────┘                └─────┬────┘
        │ creates                     │ creates
        ▼                             ▼
   [MacButton, MacInput]        [WinButton, WinInput]

   产品族1：Mac 风格                  产品族2：Win 风格
```

### 3.4 Java 版

```java
// 产品族 1：Button
public interface Button { void render(); }
public class MacButton implements Button { public void render() { System.out.println("Mac button"); } }
public class WinButton implements Button { public void render() { System.out.println("Win button"); } }

// 产品族 2：Input
public interface Input { void render(); }
public class MacInput implements Input { public void render() { System.out.println("Mac input"); } }
public class WinInput implements Input { public void render() { System.out.println("Win input"); } }

// 抽象工厂
public interface GUIFactory {
    Button createButton();
    Input createInput();
}

// 具体工厂1：Mac 全家桶
public class MacFactory implements GUIFactory {
    public Button createButton() { return new MacButton(); }
    public Input createInput()   { return new MacInput(); }
}

// 具体工厂2：Win 全家桶
public class WinFactory implements GUIFactory {
    public Button createButton() { return new WinButton(); }
    public Input createInput()   { return new WinInput(); }
}

// 客户端：拿到一个工厂，就拿到了整套风格一致的产品
public class App {
    private final GUIFactory factory;
    public App(GUIFactory f) { this.factory = f; }

    public void render() {
        factory.createButton().render();
        factory.createInput().render();
    }
}
```

### 3.5 Go 版

```go
package gui

// 产品族 1
type Button interface { Render() }
type macButton struct{}
func (macButton) Render() { fmt.Println("Mac button") }
type winButton struct{}
func (winButton) Render() { fmt.Println("Win button") }

// 产品族 2
type Input interface { Render() }
type macInput struct{}
func (macInput) Render() { fmt.Println("Mac input") }
type winInput struct{}
func (winInput) Render() { fmt.Println("Win input") }

// 抽象工厂
type GUIFactory interface {
    CreateButton() Button
    CreateInput()  Input
}

type MacFactory struct{}
func (MacFactory) CreateButton() Button { return macButton{} }
func (MacFactory) CreateInput()  Input  { return macInput{} }

type WinFactory struct{}
func (WinFactory) CreateButton() Button { return winButton{} }
func (WinFactory) CreateInput()  Input  { return winInput{} }

// 客户端
type App struct{ factory GUIFactory }
func NewApp(f GUIFactory) *App { return &App{factory: f} }
func (a *App) Render() {
    a.factory.CreateButton().Render()
    a.factory.CreateInput().Render()
}
```

### 3.6 抽象工厂的"开闭方向"

抽象工厂在**增加产品族**时符合 OCP（加新工厂类），但**增加新产品类型**时违反 OCP（要改抽象工厂接口 + 所有具体工厂）。这是抽象工厂的固有局限。

```
现状：MacFactory、WinFactory 都生产 Button、Input
新增产品族 LinuxFactory：✅ 只加新类
新增产品类型 Checkbox：❌ 要改 GUIFactory 接口 + 三个工厂全要改
```

### 3.7 面试速答

- **Q：抽象工厂和工厂方法区别？** A：工厂方法创建单个产品；抽象工厂创建一族相关产品。
- **Q：抽象工厂什么时候用？** A：产品需要成套出现（如跨平台 UI、数据库方言套件：连接 + 命令 + 事务）。
- **Q：抽象工厂的缺点？** A：新增产品类型时需要修改接口和所有具体工厂，违反 OCP。

## 四、建造者模式（Builder）

### 4.1 意图

将一个复杂对象的**构造过程**与它的**表示**分离，使得同样的构造过程可以创建不同的表示。

通俗说：当一个对象有**很多可选参数**时，避免写一堆重载构造函数。

### 4.2 适用场景

- 构造函数参数多（>=4）且部分可选。
- 需要分步骤构造对象（如 SQL 查询、HTTP 请求、HTML 文档）。
- 希望构造出的对象是不可变的。

### 4.3 结构

```
   ┌─────────────┐  build  ┌──────────────┐
   │  Director   │────────▶│   Builder    │ (接口)
   └─────────────┘         └──────┬───────┘
                                  │
                           ┌──────┴───────┐
                           │ConcreteBuilder│
                           └──────┬───────┘
                                  │ produces
                                  ▼
                           ┌──────────────┐
                           │   Product    │
                           └──────────────┘
```

实际工程中 Director 经常被省略，Builder 链式调用即可。

### 4.4 难点：解决"构造函数参数爆炸"

```java
// 反例：构造函数爆炸
class HttpRequest {
    public HttpRequest(String url) { ... }
    public HttpRequest(String url, String method) { ... }
    public HttpRequest(String url, String method, Map<String,String> headers) { ... }
    public HttpRequest(String url, String method, Map<String,String> headers, int timeout) { ... }
    public HttpRequest(String url, String method, Map<String,String> headers, int timeout, String body) { ... }
}
```

### 4.5 Java 版（链式 Builder）

```java
public class HttpRequest {
    private final String url;
    private final String method;
    private final Map<String, String> headers;
    private final int timeout;
    private final String body;

    private HttpRequest(Builder b) {
        this.url     = b.url;
        this.method  = b.method;
        this.headers = b.headers;
        this.timeout = b.timeout;
        this.body    = b.body;
    }

    // 静态内部类 Builder
    public static class Builder {
        private String url;
        private String method = "GET";
        private Map<String, String> headers = new HashMap<>();
        private int timeout = 30_000;
        private String body = "";

        public Builder url(String url)            { this.url = url; return this; }
        public Builder method(String method)      { this.method = method; return this; }
        public Builder header(String k, String v) { this.headers.put(k, v); return this; }
        public Builder timeout(int ms)            { this.timeout = ms; return this; }
        public Builder body(String body)          { this.body = body; return this; }

        public HttpRequest build() {
            if (url == null) throw new IllegalStateException("url required");
            return new HttpRequest(this);
        }
    }
}

// 使用：可读、可变、构造后不可变
HttpRequest req = new HttpRequest.Builder()
        .url("https://api.example.com")
        .method("POST")
        .header("Content-Type", "application/json")
        .body("{\"k\":1}")
        .timeout(5000)
        .build();
```

Lombok 的 `@Builder` 注解可自动生成以上代码。

### 4.6 Go 版

Go 没有构造函数重载问题，但参数过多仍推荐 Builder 提升可读性。链式 Builder 需要**每个方法返回接收者指针**。

```go
package http

type Request struct {
    url     string
    method  string
    headers map[string]string
    timeout int
    body    string
}

type RequestBuilder struct {
    r *Request
}

func NewBuilder() *RequestBuilder {
    return &RequestBuilder{r: &Request{
        method:  "GET",
        headers: map[string]string{},
        timeout: 30000,
        body:    "",
    }}
}

func (b *RequestBuilder) URL(u string) *RequestBuilder       { b.r.url = u; return b }
func (b *RequestBuilder) Method(m string) *RequestBuilder    { b.r.method = m; return b }
func (b *RequestBuilder) Header(k, v string) *RequestBuilder { b.r.headers[k] = v; return b }
func (b *RequestBuilder) Timeout(ms int) *RequestBuilder     { b.r.timeout = ms; return b }
func (b *RequestBuilder) Body(s string) *RequestBuilder      { b.r.body = s; return b }

func (b *RequestBuilder) Build() (*Request, error) {
    if b.r.url == "" {
        return nil, errors.New("url required")
    }
    return b.r, nil
}

// 使用
req, err := http.NewBuilder().
    URL("https://api.example.com").
    Method("POST").
    Header("Content-Type", "application/json").
    Body(`{"k":1}`).
    Timeout(5000).
    Build()
```

> Go 替代方案：**函数选项模式（Functional Options）**，更符合 Go 习惯。下节展开。

### 4.7 Go 特有：函数选项模式（Functional Options）

```go
type Request struct {
    url     string
    method  string
    headers map[string]string
    timeout int
    body    string
}

type Option func(*Request)

func WithMethod(m string) Option        { return func(r *Request) { r.method = m } }
func WithHeader(k, v string) Option     { return func(r *Request) { r.headers[k] = v } }
func WithTimeout(ms int) Option         { return func(r *Request) { r.timeout = ms } }
func WithBody(b string) Option          { return func(r *Request) { r.body = b } }

func NewRequest(url string, opts ...Option) (*Request, error) {
    r := &Request{
        url:     url,
        method:  "GET",
        headers: map[string]string{},
        timeout: 30000,
    }
    for _, opt := range opts {
        opt(r)
    }
    return r, nil
}

// 使用：清爽、可扩展、零依赖
req, _ := NewRequest("https://api.example.com",
    WithMethod("POST"),
    WithHeader("Content-Type", "application/json"),
    WithBody(`{"k":1}`),
    WithTimeout(5000),
)
```

> 函数选项模式是 Go 标准库、gRPC、Kubernetes client 等都在用的惯用法。它解决了"可选参数"问题，又避免了 Builder 的链式结构，是 Go 圈最推荐的"创建复杂对象"方式。

### 4.8 面试速答

- **Q：Builder 解决什么问题？** A：构造函数参数爆炸 + 不可变对象的可读构造。
- **Q：Builder 和工厂模式区别？** A：工厂关注"创建哪种"；Builder 关注"如何一步步创建"。
- **Q：Go 里推荐用什么替代 Builder？** A：函数选项模式（Functional Options）。
- **Q：Director 必须吗？** A：不必须。Director 用于复用"构造步骤序列"，简单场景直接链式调用即可。

## 五、原型模式（Prototype）

### 5.1 意图

通过**复制**已有实例来创建新对象，而不是通过 new。

### 5.2 适用场景

- 创建对象代价大（如需要复杂计算、读数据库、调远程接口）。
- 需要保留某些"已初始化好的状态"作为模板。
- 大量相似对象，差异很小。

### 5.3 难点：深拷贝 vs 浅拷贝

```
   浅拷贝：复制基本类型 + 引用指针（共享内部对象）
   深拷贝：递归复制所有引用对象，完全独立
```

绝大多数原型场景需要**深拷贝**，否则修改副本会影响原型。

### 5.4 Java 版

Java 通过实现 `Cloneable` 接口 + 重写 `clone()` 实现原型。但 `clone()` 默认是浅拷贝，深拷贝需手动处理或序列化。

```java
public class Address implements Cloneable {
    String city;
    public Address(String city) { this.city = city; }

    @Override
    protected Address clone() throws CloneNotSupportedException {
        return (Address) super.clone();
    }
}

public class User implements Cloneable {
    String name;
    Address address;   // 引用类型

    public User(String name, Address addr) {
        this.name = name;
        this.address = addr;
    }

    // 深拷贝：手动 clone 引用字段
    @Override
    protected User clone() throws CloneNotSupportedException {
        User copy = (User) super.clone();
        copy.address = address.clone();   // 关键：引用类型也要 clone
        return copy;
    }
}

// 使用
User proto = new User("Alice", new Address("Beijing"));
User copy = proto.clone();
copy.name = "Bob";
copy.address.city = "Shanghai";
System.out.println(proto.address.city);  // Beijing —— 原型不受影响
```

**Effective Java 观点**：`Cloneable` 设计糟糕，推荐用**序列化 / 拷贝构造函数 / 拷贝工厂**替代。

```java
// 拷贝构造函数方式
public class User {
    public User(User other) {
        this.name = other.name;
        this.address = new Address(other.address.city);  // 深拷贝
    }
}
```

### 5.5 Go 版

Go 没有 `clone()` 内置约定，靠手动实现或序列化。常用 JSON 序列化做深拷贝（简单但有性能损失）。

#### 方式 1：手动深拷贝

```go
type Address struct{ City string }
type User struct {
    Name    string
    Address *Address
}

func (u *User) Clone() *User {
    return &User{
        Name:    u.Name,
        Address: &Address{City: u.Address.City},  // 显式深拷贝
    }
}
```

#### 方式 2：JSON 序列化做深拷贝（通用但慢）

```go
import "encoding/json"

func DeepClone[T any](src T) (T, error) {
    var dst T
    b, err := json.Marshal(src)
    if err != nil { return dst, err }
    err = json.Unmarshal(b, &dst)
    return dst, err
}

// 使用
copy, _ := DeepClone(proto)
```

### 5.6 原型注册表（Prototype Registry）

常见配套模式：维护一个"原型字典"，按 key 取原型并克隆。

```java
public class PrototypeRegistry {
    private final Map<String, User> prototypes = new HashMap<>();

    public void register(String key, User proto) { prototypes.put(key, proto); }

    public User create(String key) throws CloneNotSupportedException {
        return prototypes.get(key).clone();
    }
}
```

### 5.7 面试速答

- **Q：原型模式是什么？** A：用复制代替 new，适合创建成本高的对象。
- **Q：浅拷贝和深拷贝区别？** A：浅拷贝共享引用字段，深拷贝递归复制全部字段。
- **Q：Java 的 clone 有什么坑？** A：默认浅拷贝；不调用构造函数；Cloneable 标记接口设计反人类。推荐用拷贝构造函数。
- **Q：Go 怎么做深拷贝？** A：手动复制或 JSON 序列化。性能敏感场景可用 `github.com/jinzhu/copier` 等库。

## 六、五种创建型模式对比

| 模式 | 意图 | 关键词 | 典型场景 |
|------|------|--------|---------|
| 单例 | 全局唯一实例 | 唯一性 | 配置、日志、连接池 |
| 工厂方法 | 单产品创建解耦 | 子类决定 | 多种 Logger、多种支付渠道 |

| 原型 | 复制代替 new | 克隆 | 模板对象、相似对象批量生成 |

## 八、综合实战：用三种模式组合实现一个支付系统

需求：支付系统支持多种支付方式（微信、支付宝、银行卡），每种方式有不同创建逻辑；支付请求参数复杂。

### Java 版

```java
// === Builder 构造支付请求 ===
public class PayRequest {
    private final String userId;
    private final long amount;
    private final String channel;
    private final String callbackUrl;

    private PayRequest(Builder b) {
        this.userId = b.userId; this.amount = b.amount;
        this.channel = b.channel; this.callbackUrl = b.callbackUrl;
    }
    public static class Builder {
        private String userId, channel, callbackUrl;
        private long amount;
        public Builder userId(String u) { this.userId = u; return this; }
        public Builder amount(long a) { this.amount = a; return this; }
        public Builder channel(String c) { this.channel = c; return this; }
        public Builder callback(String u) { this.callbackUrl = u; return this; }
        public PayRequest build() { return new PayRequest(this); }
    }
    public String getChannel() { return channel; }
    public long getAmount() { return amount; }
}

// === 工厂方法：不同渠道不同实现 ===
public interface PayChannel {
    void pay(PayRequest req);
}
public class WechatPay implements PayChannel {
    public void pay(PayRequest r) { System.out.println("Wechat pay " + r.getAmount()); }
}
public class Alipay implements PayChannel {
    public void pay(PayRequest r) { System.out.println("Alipay pay " + r.getAmount()); }
}

public interface PayFactory { PayChannel create(); }
public class WechatFactory implements PayFactory { public PayChannel create() { return new WechatPay(); } }
public class AlipayFactory  implements PayFactory { public PayChannel create() { return new Alipay(); } }

// === 单例：支付配置 ===
public class PayConfig {
    private static final PayConfig INSTANCE = new PayConfig();
    private PayConfig() {}
    public static PayConfig get() { return INSTANCE; }
    public String getMerchantId() { return "M001"; }
}

// === 客户端 ===
public class PayApp {
    public static void main(String[] args) {
        PayRequest req = new PayRequest.Builder()
                .userId("U123").amount(100).channel("wechat")
                .callback("https://cb.com").build();

        PayFactory factory = new WechatFactory();
        PayChannel channel = factory.create();
        System.out.println("merchant: " + PayConfig.get().getMerchantId());
        channel.pay(req);
    }
}
```

### Go 版

```go
package pay

// === Builder（用函数选项）===
type PayRequest struct {
    UserID      string
    Amount      int64
    Channel     string
    CallbackURL string
}

type Option func(*PayRequest)

func WithAmount(a int64) Option       { return func(r *PayRequest) { r.Amount = a } }
func WithCallback(u string) Option    { return func(r *PayRequest) { r.CallbackURL = u } }

func NewPayRequest(userID, channel string, opts ...Option) *PayRequest {
    r := &PayRequest{UserID: userID, Channel: channel}
    for _, o := range opts { o(r) }
    return r
}

// === 工厂方法 ===
type PayChannel interface { Pay(r *PayRequest) }
type wechatPay struct{}
func (wechatPay) Pay(r *PayRequest) { fmt.Println("Wechat pay", r.Amount) }
type alipay struct{}
func (alipay) Pay(r *PayRequest) { fmt.Println("Alipay pay", r.Amount) }

func NewPayFactory(channel string) (PayChannel, error) {
    switch channel {
    case "wechat": return wechatPay{}, nil
    case "alipay":  return alipay{}, nil
    default:        return nil, fmt.Errorf("unknown channel: %s", channel)
    }
}

// === 单例 ===
type payConfig struct{ MerchantID string }
var (
    cfg  *payConfig
    once sync.Once
)
func Config() *payConfig {
    once.Do(func() { cfg = &payConfig{MerchantID: "M001"} })
    return cfg
}

// === 客户端 ===
func ExampleUsage() {
    req := NewPayRequest("U123", "wechat", WithAmount(100), WithCallback("https://cb.com"))
    ch, _ := NewPayFactory(req.Channel)
    fmt.Println("merchant:", Config().MerchantID)
    ch.Pay(req)
}
```
