## 软件设计原则（Software Design Principles）

设计原则是**判断设计好坏的启发式规则**，比设计模式更底层、更抽象。设计模式是"招式"，设计原则是"内功心法"——招式可以照搬，心法决定你能不能自创招式。

> 与 [架构基本原则.md](./架构基本原则.md) 的分工：架构基本原则讲**模块级**（高内聚低耦合、扇入扇出、作用域控制域）；本文讲**类/对象级**（SOLID、DRY、KISS 等）。

涉及的原则：

- **SOLID**（五大核心原则）
  - SRP 单一职责
  - OCP 开闭
  - LSP 里氏替换
  - ISP 接口隔离
  - DIP 依赖倒置
- **DRY**（Don't Repeat Yourself）
- **KISS**（Keep It Simple, Stupid）
- **YAGNI**（You Aren't Gonna Need It）
- **LoD**（Law of Demeter / 迪米特法则 / 最少知道原则）
- **组合优于继承**（Composition over Inheritance）
- **面向接口编程**（Program to Interface）
- **封装变化**（Encapsulate What Varies）
- **好莱坞原则**（Hollywood Principle / IoC）
- **CQS**（Command-Query Separation）
- **Tell, Don't Ask**
- **Fail Fast**

> 面试提示：SOLID 是必考点，每条都要能说出**定义 + 反例 + 重构方案**。其他原则常以"你了解哪些设计原则"开放题出现，能讲清取舍和冲突比背定义重要。

## 一、SOLID 概览

SOLID 是 Robert C. Martin（Uncle Bob）提出的五大面向对象设计原则首字母缩写：

| 缩写 | 全称 | 中文 | 一句话 |
|------|------|------|--------|
| **S** | Single Responsibility Principle | 单一职责原则 | 一个类只有一个引起它变化的原因 |
| **O** | Open-Closed Principle | 开闭原则 | 对扩展开放，对修改关闭 |
| **L** | Liskov Substitution Principle | 里氏替换原则 | 子类必须能替换父类 |
| **I** | Interface Segregation Principle | 接口隔离原则 | 接口要小而专，不要大而全 |
| **D** | Dependency Inversion Principle | 依赖倒置原则 | 依赖抽象，不依赖具体 |

> **核心思想**：SOLID 都是为了应对**变化**——让代码在需求变化时**少改、不改老代码**，从而降低维护成本。

### 原则之间的内在关系

```
                应对变化
                   │
        ┌──────────┼──────────┐
        ▼          ▼          ▼
      扩展       替换       复用
        │          │          │
       OCP        LSP        DRY
        │          │
        ▼          ▼
     DIP ────────► ISP
        │
        ▼
      SRP (基础：职责清晰是一切的前提)
```

- **SRP 是基础**：职责不清，其他原则无从谈起。
- **OCP 是目标**：所有原则最终都是为了"扩展开放、修改关闭"。
- **DIP 是手段**：通过依赖抽象实现 OCP。
- **LSP 是约束**：保证继承体系下 OCP 不被破坏。
- **ISP 是细化**：抽象要精细，避免接口污染。

## 二、单一职责原则（SRP）

### 2.1 定义

一个类应该**只有一个引起它变化的原因**。

> 通俗说：一个类只做一件事。如果一个类承担了多个职责，任何一个职责变化都会修改这个类，导致其他职责受牵连。

### 2.2 难点："职责"的边界

SRP 最难的是**识别职责**。一个类"做几件事"不是看方法数，而是看**变化的轴线**：

- 如果两个职责**总是同时变化**，可能是同一职责。
- 如果两个职责**独立变化**，应该拆分。

> 经典误区：把"一个类只做一个事"理解成"一个类只有一个方法"。SRP 关注的是**变化的原因**，不是方法数。

### 2.3 反例：一个类承担多职责

```java
// Employee 同时承担：业务逻辑 + 持久化 + 报表生成
public class Employee {
    private String name;
    private double salary;

    // 职责 1：业务计算
    public double calculatePay() { return salary * 1.1; }

    // 职责 2：持久化（数据库）
    public void save() { /* INSERT INTO employees ... */ }
    public void load(int id) { /* SELECT ... */ }

    // 职责 3：报表（UI 层关注的事）
    public String formatHtml() { return "<div>" + name + "</div>"; }
    public String formatJson() { return "{\"name\":\"" + name + "\"}"; }
}
```

**问题**：
- 数据库 schema 变化 → 改 `save/load` → 影响业务和报表。
- 报表样式变化 → 改 `formatHtml` → 影响业务和持久化。
- 三个职责在**不同的变化轴线**上，应该拆分。

### 2.4 正例：按变化轴线拆分

```java
// 职责 1：业务模型
public class Employee {
    private String name;
    private double salary;
    public double calculatePay() { return salary * 1.1; }
    public String getName() { return name; }
    public double getSalary() { return salary; }
}

// 职责 2：持久化（Repository）
public interface EmployeeRepository {
    void save(Employee e);
    Employee load(int id);
}
public class JdbcEmployeeRepository implements EmployeeRepository { /* ... */ }

// 职责 3：报表渲染
public interface EmployeeReportFormatter {
    String format(Employee e);
}
public class HtmlFormatter implements EmployeeReportFormatter { /* ... */ }
public class JsonFormatter implements EmployeeReportFormatter { /* ... */ }
```

### 2.5 Go 版

```go
// 反例：一个结构体啥都干
type Employee struct {
    Name   string
    Salary float64
}

func (e *Employee) CalculatePay() float64   { return e.Salary * 1.1 }
func (e *Employee) Save()                   { /* db.Exec(...) */ }
func (e *Employee) Load(id int)             { /* db.Query(...) */ }
func (e *Employee) FormatHTML() string      { return "<div>" + e.Name + "</div>" }

// 正例：按职责拆分
type Employee struct {   // 业务模型：只有数据和业务规则
    Name   string
    Salary float64
}
func (e *Employee) CalculatePay() float64 { return e.Salary * 1.1 }

type EmployeeRepository interface {   // 持久化职责
    Save(*Employee) error
    Load(id int) (*Employee, error)
}

type JdbcRepo struct{ db *sql.DB }
func (r *JdbcRepo) Save(e *Employee) error { /* ... */ return nil }
func (r *JdbcRepo) Load(id int) (*Employee, error) { /* ... */ return nil, nil }

type Formatter interface {   // 报表职责
    Format(*Employee) string
}
type HTMLFormatter struct{}
func (HTMLFormatter) Format(e *Employee) string { return "<div>" + e.Name + "</div>" }
```

> Go 的接口隔离天然鼓励 SRP：把不同职责拆成不同接口，结构体只持有数据，行为分散到接口实现里。

### 2.6 SRP 的代价

过度拆分会导致**类的数量爆炸**、**跳转链变长**。判断标准：

| 信号 | 倾向 |
|------|------|
| 两个职责独立变化 | 拆 |
| 两个职责总是同时变化 | 合并 |
| 修改 A 职责经常导致 B 职责 bug | 必须拆 |
| 团队分工（前端 / 后端 / DBA）对应不同职责 | 按团队边界拆 |

### 2.7 面试速答

- **Q：SRP 的定义？** A：一个类只有一个引起它变化的原因。
- **Q：怎么判断"职责"？** A：看变化轴线，不看方法数。两个独立变化的职责就该拆。
- **Q：SRP 过度拆分有什么坏处？** A：类爆炸、跳转链变长、简单问题复杂化。
- **Q：SRP 和高内聚关系？** A：SRP 是高内聚在类级别的体现——一个类只装一个职责，内部元素高度内聚。

## 三、开闭原则（OCP）

### 3.1 定义

软件实体（类、模块、函数）应该**对扩展开放，对修改关闭**。

> 通俗说：加新功能时，**加新代码**，**不改老代码**。

### 3.2 难点：如何做到"不改老代码"

OCP 的核心是**抽象**——把变化点抽象成接口/抽象类，新需求通过实现新接口或继承新类完成，老代码不动。

```
   需求变化时：
   ❌ 改老代码（违反 OCP）：在 switch 里加 case
   ✅ 加新代码（符合 OCP）：实现新接口/新子类
```

### 3.3 反例：硬编码分支

```java
public class DiscountCalculator {
    public double calc(String type, double price) {
        if ("vip".equals(type)) return price * 0.8;
        else if ("svip".equals(type)) return price * 0.7;
        else if ("new".equals(type)) return price * 0.9;
        else return price;
        // 新增 "employee" 类型 → 必须改这个方法 → 违反 OCP
    }
}
```

### 3.4 正例：用抽象 + 多态实现 OCP

```java
public interface Discount {
    double apply(double price);
}
public class VipDiscount implements Discount {
    public double apply(double p) { return p * 0.8; }
}
public class SvipDiscount implements Discount {
    public double apply(double p) { return p * 0.7; }
}

public class DiscountCalculator {
    private final Discount discount;
    public DiscountCalculator(Discount d) { this.discount = d; }
    public double calc(double price) { return discount.apply(price); }
    // 新增 EmployeeDiscount → 只加新类，Calculator 不动 → 符合 OCP
}
```

> 这就是策略模式。OCP 是目标，**策略、工厂、模板方法、装饰器**等模式都是实现 OCP 的手段。

### 3.5 Go 版

```go
// 反例
func Calc(typ string, price float64) float64 {
    switch typ {
    case "vip":  return price * 0.8
    case "svip": return price * 0.7
    default:     return price
    }
}

// 正例
type Discount interface {
    Apply(price float64) float64
}

type Vip struct{}
func (Vip) Apply(p float64) float64 { return p * 0.8 }

type Calculator struct{ d Discount }
func (c *Calculator) Calc(p float64) float64 { return c.d.Apply(p) }

// 新增 Employee 折扣 → 加新类型即可
type Employee struct{}
func (Employee) Apply(p float64) float64 { return p * 0.5 }
```

### 3.6 OCP 的"不可能三角"

OCP 是理想目标，**100% 做到不可能**——总有一些变化是无法预见的。实际工程：

| 变化频率 | 应对策略 |
|---------|---------|
| 高频变化（业务规则） | 抽象成接口，多态扩展 |
| 中频变化（配置） | 配置文件 / 依赖注入 |
| 低频变化（一次性） | 直接改代码，别过度设计 |

> **YAGNI 提醒**：不要为所有可能的变化都做抽象。只对**确知会变化**且**变化方向明确**的部分做抽象。

### 3.7 面试速答

- **Q：OCP 的定义？** A：对扩展开放，对修改关闭。加新功能不改老代码。
- **Q：如何实现 OCP？** A：通过抽象（接口/抽象类）+ 多态，把变化点封装。
- **Q：OCP 和 SRP 关系？** A：SRP 是 OCP 的基础——职责清晰才能识别变化点。
- **Q：哪些设计模式实现 OCP？** A：策略、工厂方法、模板方法、装饰器、观察者。
- **Q：OCP 能 100% 做到吗？** A：不能。对未预见的变化做不到，需要重构时再抽象（YAGNI）。

## 四、里氏替换原则（LSP）

### 4.1 定义

所有引用基类的地方必须能透明地使用其子类对象，而程序行为不变。

> 通俗说：**子类必须能完全替换父类**，调用方察觉不到差异。这是"继承是否合理"的判据。

### 4.2 难点：LSP 的隐性违反

LSP 比 SRP/OCP 更微妙——很多违反是**隐性的**，编译能过、测试能跑，但行为已经不一致。

**经典违反模式**：

| 违反模式 | 说明 |
|---------|------|
| 子类方法抛出父类不抛的异常 | 调用方未处理，崩溃 |
| 子类方法做了父类不允许的副作用 | 如子类 `add` 拒绝 null，父类允许 |
| 子类削弱了父类的前置条件 | 父类接受任意 int，子类只接受正数 |
| 子类加强了后置条件 | 父类返回 [0,100]，子类返回 [0,50] |
| 子类改变了父类的"语义" | 经典：正方形继承长方形 |

### 4.3 反例：正方形继承长方形

```java
// 长方形
public class Rectangle {
    protected int width, height;
    public void setWidth(int w)  { width = w; }
    public void setHeight(int h) { height = h; }
    public int area() { return width * height; }
}

// 正方形继承长方形——看似合理（正方形 IS-A 长方形）
public class Square extends Rectangle {
    @Override
    public void setWidth(int w)  { width = w; height = w; }   // 强制等边
    @Override
    public void setHeight(int h) { width = h; height = h; }
}

// 调用方依赖 Rectangle 的契约
public class App {
    public static void main(String[] args) {
        Rectangle r = new Square();   // 子类替换父类
        r.setWidth(5);
        r.setHeight(10);
        System.out.println(r.area()); // 期望 50，实际 100 → 行为异常！
    }
}
```

**问题**：`Rectangle` 的契约是"宽高独立"，`Square` 破坏了这个契约。LSP 被违反，调用方代码出错。

**修复**：不要让 Square 继承 Rectangle。引入共同的抽象基类 `Shape`，或者用组合。

```java
public interface Shape { int area(); }
public class Rectangle implements Shape { /* width, height 独立 */ }
public class Square implements Shape { /* side */ }
```

### 4.4 正例：遵守契约的继承

```java
// 基类契约：Bird.canFly() 返回是否能飞
public abstract class Bird {
    public abstract boolean canFly();
    public void fly() {
        if (!canFly()) throw new UnsupportedOperationException();
        System.out.println("flying");
    }
}

// 子类 1：麻雀，能飞——契约一致
public class Sparrow extends Bird {
    public boolean canFly() { return true; }
}

// 子类 2：企鹅，不能飞
public class Penguin extends Bird {
    public boolean canFly() { return false; }
    // 注意：不重写 fly() 抛新异常，而是通过 canFly() 让调用方先检查
}

// 调用方：先检查 canFly 再 fly
void safeFly(Bird b) {
    if (b.canFly()) b.fly();
}
```

### 4.5 Go 版

Go 没有"继承"，但有**结构体嵌入**和**接口实现**。LSP 在 Go 中体现为：**实现同一接口的不同类型，行为契约要一致**。

```go
// 反例：实现同一接口但行为不一致
type ReadWriter interface {
    Read(p []byte) (n int, err error)
    Write(p []byte) (n int, err error)
}

// ReadOnlyWriter 实现 ReadWriter，但 Write 永远返回 error
type ReadOnlyWriter struct{ f *os.File }
func (r *ReadOnlyWriter) Read(p []byte) (int, error)  { return r.f.Read(p) }
func (r *ReadOnlyWriter) Write(p []byte) (int, error) {
    return 0, errors.New("read only")   // 违反 LSP：调用方期望 Write 能写
}

// 正例：拆分接口
type Reader interface { Read(p []byte) (int, error) }
type Writer interface { Write(p []byte) (int, error) }
type ReadWriter interface {
    Reader
    Writer
}
// ReadOnlyWriter 只实现 Reader，不实现 ReadWriter
```

> Go 的接口隔离天然防止 LSP 违反——接口小，实现者无法"半实现"。

### 4.6 LSP 与契约式设计（DbC）

LSP 的理论基础是 Bertrand Meyer 的**契约式设计**：

| 契约类型 | 子类规则 |
|---------|---------|
| 前置条件（方法对入参的要求） | 子类**只能放宽**，不能加强 |
| 后置条件（方法对返回值的承诺） | 子类**只能加强**，不能放宽 |
| 不变式（对象始终满足的条件） | 子类**必须保持** |

> 通俗记忆：**子类不能要求更多，不能承诺更少**。

### 4.7 面试速答

- **Q：LSP 的定义？** A：子类必须能完全替换父类，程序行为不变。
- **Q：LSP 的经典反例？** A：正方形继承长方形——子类破坏了父类"宽高独立"的契约。
- **Q：LSP 和继承关系？** A：LSP 是判断"继承是否合理"的标准。IS-A 关系不够，还要行为一致。
- **Q：子类抛父类不抛的异常算违反 LSP 吗？** A：算。调用方未处理该异常，行为会变。
- **Q：Go 没有 inherit，LSP 还适用吗？** A：适用。体现为"实现同一接口的类型行为契约要一致"。

## 五、接口隔离原则（ISP）

### 5.1 定义

客户端**不应该被迫依赖**它不使用的方法。

> 通俗说：接口要小而专，不要大而全。一个接口里的方法应该都属于同一类客户端。

### 5.2 难点：ISP vs SRP

| 对比项 | SRP | ISP |
|--------|-----|-----|
| 关注点 | 类的职责 | 接口的方法集合 |
| 判据 | 变化轴线 | 客户端使用范围 |
| 修整对象 | 类 | 接口 |

> SRP 是对**实现**的约束，ISP 是对**抽象**的约束。两者经常一起出现。

### 5.3 反例：胖接口

```java
// 胖接口：什么都塞进去
public interface Worker {
    void work();
    void eat();
    void sleep();
}

// 机器人实现 Worker，但不需要 eat/sleep
public class Robot implements Worker {
    public void work()  { /* 工作 */ }
    public void eat()   { throw new UnsupportedOperationException(); }   // 被迫实现
    public void sleep() { throw new UnsupportedOperationException(); }
}
```

**问题**：`Robot` 被迫依赖它不用的方法，违反 ISP。

### 5.4 正例：拆分接口

```java
public interface Workable { void work(); }
public interface Eatable  { void eat(); }
public interface Sleepable { void sleep(); }

public class Human implements Workable, Eatable, Sleepable {
    public void work()  { /* ... */ }
    public void eat()   { /* ... */ }
    public void sleep() { /* ... */ }
}

public class Robot implements Workable {
    public void work() { /* ... */ }   // 只依赖需要的接口
}
```

### 5.5 Go 版

Go 的接口天然小——标准库的 `io.Reader` 只有一个方法 `Read`，`io.Writer` 只有一个 `Write`。这是 ISP 在 Go 中的最佳实践。

```go
// 反例：胖接口
type Worker interface {
    Work()
    Eat()
    Sleep()
}

type Robot struct{}
func (Robot) Work()  {}
func (Robot) Eat()   { panic("robot doesn't eat") }   // 被迫实现
func (Robot) Sleep() { panic("robot doesn't sleep") }

// 正例：拆分
type Worker interface  { Work() }
type Eater interface   { Eat() }
type Sleeper interface { Sleep() }

type Human struct{}
func (Human) Work()  {}
func (Human) Eat()   {}
func (Human) Sleep() {}

type Robot struct{}
func (Robot) Work() {}   // 只实现需要的

// 客户端按需依赖
func RunWork(w Worker) { w.Work() }
func FeedWorker(e Eater) { e.Eat() }
```

> Go 哲学："接口越小越好"。`io.Reader`/`io.Writer` 是黄金标准。Go 鼓励在**使用方**定义接口，而不是**提供方**——这样接口天然只包含调用方需要的方法。

### 5.6 ISP 在 Spring 中的应用

Spring 的 `BeanFactory` 和 `ApplicationContext` 就是 ISP 的典范：

```java
// ListableBeanFactory：列举 Bean
// HierarchicalBeanFactory：父子容器
// AutowireCapableBeanFactory：自动装配
// ApplicationContext 继承所有，但客户端可以只依赖需要的窄接口
void listBeans(ListableBeanFactory f) { /* 只用列举能力 */ }
```

### 5.7 面试速答

- **Q：ISP 的定义？** A：客户端不应被迫依赖它不使用的方法。
- **Q：ISP 和 SRP 区别？** A：SRP 约束类的职责（实现层），ISP 约束接口的方法集（抽象层）。
- **Q：胖接口有什么坏处？** A：实现者被迫实现不需要的方法（抛异常 / 空实现）；客户端被迫依赖不用的方法，接口变更影响范围大。
- **Q：Go 怎么实践 ISP？** A：接口尽量小；在使用方定义接口（消费者驱动）。
- **Q：Java 8 default 方法缓解了 ISP 吗？** A：部分缓解——default 方法提供默认实现，但接口污染问题仍在。

## 六、依赖倒置原则（DIP）

### 6.1 定义

1. 高层模块不应该依赖低层模块，**二者都应该依赖抽象**。
2. 抽象不应该依赖细节，**细节应该依赖抽象**。

> 通俗说：**面向接口编程，不要面向实现编程**。依赖方向从"高层 → 低层"倒置为"高层 → 抽象 ← 低层"。

### 6.2 难点："倒置"在哪

传统分层架构中，依赖方向是**向下**的：

```
   Controller ──依赖──▶ Service ──依赖──▶ DAO ──依赖──▶ DB
```

DIP 把依赖**倒置**：低层也依赖抽象，抽象由高层定义。

```
   Controller ──┐                         ┌── DB
                ▼                         ▲
              IService 抽象            implements
                ▲                         │
   Service ─────┘  (implements IService)
```

> 关键洞察：**抽象属于高层**。高层定义自己需要的接口，低层去实现。这样高层不依赖低层，低层变化不影响高层。

### 6.3 反例：高层依赖低层

```java
// 低层：MySQL 数据访问
public class MySQLUserDao {
    public void insert(User u) { /* INSERT INTO mysql */ }
}

// 高层：业务逻辑直接依赖低层具体类
public class UserService {
    private MySQLUserDao dao = new MySQLUserDao();   // 直接 new 具体类

    public void register(User u) {
        dao.insert(u);
    }
    // 想换 PostgreSQL → 必须改 UserService → 高层被低层变化绑架
}
```

### 6.4 正例：都依赖抽象

```java
// 抽象：由高层定义
public interface UserDao {
    void insert(User u);
}

// 低层实现抽象
public class MySQLUserDao implements UserDao {
    public void insert(User u) { /* INSERT INTO mysql */ }
}
public class PostgresUserDao implements UserDao {
    public void insert(User u) { /* INSERT INTO postgres */ }
}

// 高层依赖抽象，不依赖具体实现
public class UserService {
    private final UserDao dao;   // 依赖接口

    // 通过构造注入，低层从外部注入
    public UserService(UserDao dao) { this.dao = dao; }

    public void register(User u) { dao.insert(u); }
    // 换 PostgreSQL → 只改注入的实例，UserService 不动
}

// 组装（依赖注入）
UserService service = new UserService(new MySQLUserDao());
// 或
UserService service = new UserService(new PostgresUserDao());
```

### 6.5 Go 版

```go
// 反例
type MySQLUserDao struct{}
func (MySQLUserDao) Insert(u *User) { /* mysql */ }

type UserService struct {
    dao MySQLUserDao   // 直接依赖具体类型
}
func (s *UserService) Register(u *User) { s.dao.Insert(u) }

// 正例
type UserDao interface {   // 抽象，由高层定义
    Insert(u *User) error
}

type MySQLUserDao struct{}
func (MySQLUserDao) Insert(u *User) error { /* mysql */ return nil }

type PostgresUserDao struct{}
func (PostgresUserDao) Insert(u *User) error { /* postgres */ return nil }

type UserService struct {
    dao UserDao   // 依赖接口
}

func NewUserService(dao UserDao) *UserService {
    return &UserService{dao: dao}
}
func (s *UserService) Register(u *User) error { return s.dao.Insert(u) }

// 组装
svc := NewUserService(MySQLUserDao{})
// 切换
svc = NewUserService(PostgresUserDao{})
```

> Go 实践：Go 的接口隐式实现（duck typing）让 DIP 极其自然——定义接口在使用方，实现方不需要 `implements` 关键字。这是 Go 相对 Java 的优势。

### 6.6 DIP 与依赖注入（DI）

DIP 是**原则**，依赖注入（DI）是实现 DIP 的**技术**：

| 概念 | 角色 |
|------|------|
| DIP | 设计原则：依赖抽象 |
| DI | 实现手段：把依赖从外部注入 |
| IoC 容器 | 工具：自动管理对象创建和注入（Spring、wire） |

```java
// 手动 DI
new UserService(new MySQLUserDao());

// IoC 容器（Spring）
@Service
public class UserService {
    private final UserDao dao;
    @Autowired  // 容器自动注入
    public UserService(UserDao dao) { this.dao = dao; }
}
```

### 6.7 DIP 与六边形架构 / Clean Architecture

DIP 是现代架构的基石：

- **六边形架构**（端口与适配器）：核心业务定义端口（抽象），外部适配器实现端口。依赖方向向内。
- **Clean Architecture**：内层定义接口，外层实现。依赖方向从外指向内。
- **洋葱架构**：同理。

```
   Clean Architecture 的依赖方向：
   ┌─────────────────────────┐
   │  Frameworks & Drivers   │  ← 外层（DB、Web）
   │  ┌───────────────────┐  │
   │  │  Interface Adapters│  │  ← 控制器、网关
   │  │  ┌──────────────┐ │  │
   │  │  │  Use Cases    │ │  │  ← 业务逻辑（定义接口）
   │  │  │  ┌─────────┐ │ │  │
   │  │  │  │ Entities │ │ │  │  ← 实体（最内层）
   │  │  │  └─────────┘ │ │  │
   │  │  └──────────────┘ │  │
   │  └───────────────────┘  │
   └─────────────────────────┘
   依赖箭头永远向内：外层依赖内层，内层不依赖外层
```

### 6.8 面试速答

- **Q：DIP 的定义？** A：高层低层都依赖抽象；抽象不依赖细节，细节依赖抽象。
- **Q：DIP "倒置"在哪？** A：传统高层依赖低层；DIP 让低层也依赖抽象，依赖方向从"向下"变"向抽象"。
- **Q：DIP 和 DI 关系？** A：DIP 是原则，DI 是实现手段，IoC 容器是工具。
- **Q：Go 实现 DIP 的优势？** A：接口隐式实现，定义在使用方，无需 `implements`，天然符合 DIP。
- **Q：DIP 和 Clean Architecture 关系？** A：DIP 是 Clean Architecture 的基石——依赖方向向内，内层定义接口，外层实现。

## 七、DRY（Don't Repeat Yourself）

### 7.1 定义

> **Every piece of knowledge must have a single, unambiguous, authoritative representation within a system.**
>
> 系统中每一份知识都应该有**唯一、明确、权威**的表示。

DRY 不是简单的"不要复制代码"，而是"**不要重复知识**"。

### 7.2 难点：DRY 的边界

```python
# 看起来是重复，实际是"巧合重复"
class A:
    def foo(self): return 42

class B:
    def foo(self): return 42   # 巧合：两个领域恰好返回 42

# 强行 DRY → 抽出公共方法 → A 和 B 被绑死，未来 A 想返回 43 要改 B
```

**判断标准**：两段代码是否表达**同一份知识/同一业务规则**？
- 是 → 必须合并（真重复）。
- 否 → 不要合并（巧合重复），保持独立。

### 7.3 反例：真重复

```java
// 散落在多处的"VIP 折扣 0.8"
public class OrderService {
    public double calc(Order o) { return o.getAmount() * 0.8; }
}
public class PriceService {
    public double calc(User u) { return u.getAmount() * 0.8; }   // 同一规则
}
public class ReportService {
    public double calc(User u) { return u.getAmount() * 0.8; }   // 第三次重复
}
// 折扣规则变化（0.8 → 0.75）→ 改三处 → 漏改一处就是 bug
```

### 7.4 正例：提取公共逻辑

```java
public class VipDiscount {
    public static final double RATE = 0.8;
    public static double apply(double amount) { return amount * RATE; }
}

public class OrderService {
    public double calc(Order o) { return VipDiscount.apply(o.getAmount()); }
}
// 折扣变化只改 VipDiscount 一处
```

### 7.5 Go 版

```go
// 反例
func calcOrder(o *Order) float64 { return o.Amount * 0.8 }
func calcPrice(u *User) float64  { return u.Amount * 0.8 }

// 正例
var vipRate = 0.8
func applyVipDiscount(amount float64) float64 { return amount * vipRate }

func calcOrder(o *Order) float64 { return applyVipDiscount(o.Amount) }
func calcPrice(u *User) float64  { return applyVipDiscount(u.Amount) }
```

### 7.6 DRY 的反原则：WET/AHA

- **WET**（Write Everything Twice / We Enjoy Typing）：第一次复制没关系，第三次才抽象。规则：**Rule of Three**。
- **AHA**（Avoid Hasty Abstractions）：不要过早抽象。错误的抽象比重复更难维护。

> 实践建议：**容忍前两次重复，第三次出现时再抽象**。这是 DRY 和 YAGNI 的平衡。

### 7.7 DRY 的层级

DRY 不只针对代码，还覆盖：

| 层级 | 重复形式 |
|------|---------|
| 代码 | 复制粘贴的函数 |
| 数据库 | 字段在多张表冗余存储 |
| 配置 | 同一配置在多处硬编码 |
| 文档 | 文档和代码描述不一致 |
| 测试 | 测试数据重复造 |
| 知识 | 业务规则散落多处 |

### 7.8 面试速答

- **Q：DRY 的定义？** A：每一份知识在系统中有唯一权威表示。
- **Q：DRY 只是不要复制代码吗？** A：不是。DRY 关注"知识重复"，包括代码、配置、文档、业务规则。
- **Q：什么是"巧合重复"？** A：两段代码恰好相同但表达不同知识，不应合并。
- **Q：Rule of Three 是什么？** A：前两次重复容忍，第三次才抽象，避免过早抽象。
- **Q：DRY 和 AHA 冲突吗？** A：AHA 是对 DRY 的修正——不要为 DRY 而 DRY，错误的抽象比重复更糟。

## 八、KISS（Keep It Simple, Stupid）

### 8.1 定义

保持简单。大多数系统的复杂度都是**人为制造**的，而非问题本身需要。

> KISS 源自美国海军 1960 年代工程原则："Most systems work best if they are kept simple rather than made complicated."

### 8.2 难点：简单 ≠ 简陋

KISS 不是"能跑就行"，而是"**用最简单的方式正确解决问题**"。

| 维度 | 简陋 | 简单 | 复杂 |
|------|------|------|------|
| 设计 | 无设计 | 直接清晰 | 过度设计 |
| 抽象 | 无 | 必要的抽象 | 无关抽象 |
| 错误处理 | 无 | 边界处理 | 全局 try-catch |
| 可读性 | 差 | 好 | 难懂 |

### 8.3 反例：过度设计

```java
// 简单需求：根据用户类型返回折扣
// 过度设计版
public interface DiscountStrategyFactory {
    DiscountStrategy create(UserType type);
}
public class DiscountStrategyFactoryImpl implements DiscountStrategyFactory {
    private final Map<UserType, DiscountStrategy> registry;
    // ... 注入、配置、Builder ...
}
public abstract class AbstractDiscountStrategy implements DiscountStrategy {
    protected abstract double doApply(double price);
    public double apply(double price) {
        // 模板方法 + 钩子 + 责任链 ...
    }
}
// 实际只有 3 种用户类型，if/else 三行就够了
```

### 8.4 正例：先简单后演进

```java
// 起步：直接 if/else
public double discount(UserType type, double price) {
    return switch (type) {
        case VIP  -> price * 0.8;
        case SVIP -> price * 0.7;
        default   -> price;
    };
}
// 等折扣规则超过 5 种、需要运行时配置时，再重构成策略模式
```

### 8.5 Go 版

```go
// 反例：为简单功能上接口 + 工厂 + 注入
type Greeter interface { Greet(name string) string }
type EnglishGreeter struct{}
func (EnglishGreeter) Greet(name string) string { return "Hello, " + name }

type GreeterFactory interface { Create() Greeter }
// ...

// 正例：一个函数
func Greet(name string) string { return "Hello, " + name }
```

> Go 哲学："A little copying is better than a little dependency."（少量复制优于引入依赖）——这是 KISS 的极致体现。

### 8.6 KISS 与其他原则的关系

- **KISS vs DRY**：DRY 追求消除重复，可能引入抽象；KISS 提醒抽象本身也是复杂度。两者冲突时，**简单优先**。
- **KISS vs YAGNI**：YAGNI 关注"不要做不需要的"，KISS 关注"做的时候要简单"。两者互补。
- **KISS vs SOLID**：SOLID 是"好的复杂"，KISS 是"避免坏的复杂"。SOLID 不应成为过度设计的借口。

### 8.7 面试速答

- **Q：KISS 的定义？** A：保持简单，避免不必要的复杂度。
- **Q：KISS 和"简陋"区别？** A：简陋是无设计；KISS 是用最简单方式正确解决问题。
- **Q：KISS 和 DRY 冲突时怎么办？** A：简单优先。错误的抽象比重复更难维护。
- **Q：什么时候该用设计模式（增加复杂度）？** A：当复杂度来自问题本身（如确知的多种变化）时，用模式管理复杂度；来自人为设计时，简化。

## 九、YAGNI（You Aren't Gonna Need It）

### 9.1 定义

不要实现**当前不需要**的功能，即使你认为将来会需要。

> YAGNI 来自 XP（极限编程）。核心：**永远不要为想象中的未来写代码**。

### 9.2 难点：YAGNI vs 前瞻性设计

工程上常听到"为将来扩展留接口"——这是 YAGNI 还是好的前瞻性？

**判断标准**：

| 情况 | 决策 |
|------|------|
| 需求明确，下个迭代就要做 | 现在可以预留 |
| 需求模糊，"也许将来会..." | 不要做（YAGNI） |
| 抽象成本低，且明显会让未来更顺 | 可以做 |
| 抽象成本高，未来需求不确定 | 不要做（YAGNI） |

### 9.3 反例：为"未来"过度设计

```java
// 当前需求：用户注册
// 反例：为"将来可能的多租户、多语言、多币种"预留一堆配置
public class UserRegistrationService {
    private final MultiTenantManager tenantManager;
    private final I18nManager i18n;
    private final CurrencyConverter currency;
    private final AuditLogger audit;
    // ... 当前只用到了 register 一个方法，其他全是 YAGNI
    public void register(User u) { /* ... */ }
}
```

### 9.4 正例：只做当前需要的

```java
public class UserRegistrationService {
    public void register(User u) { /* ... */ }
}
// 真出现多租户需求时再重构
```

### 9.5 YAGNI 的理由

1. **未来不可预测**：80% 的"将来会需要"永远不会发生。
2. **预测错误**：即使发生，预测的接口/抽象往往不对，还要重做。
3. **维护成本**：无用代码增加阅读、测试、维护负担。
4. **延迟决策**：等到需求明确时决策质量更高。

### 9.6 YAGNI 的例外

YAGNI 不是"拒绝所有前瞻"。以下情况值得提前设计：

- **数据库 schema**：后期改 schema 成本极高，值得前瞻。
- **API 契约**：对外 API 一旦发布难以修改，值得谨慎设计。
- **核心架构**：迁移成本高，值得早期投入。
- **安全 / 性能**：后期补代价大，值得提前考虑。

### 9.7 面试速答

- **Q：YAGNI 的定义？** A：不要实现当前不需要的功能。
- **Q：YAGNI 和 KISS 区别？** A：YAGNI 关注"做什么"（不要做不需要的）；KISS 关注"怎么做"（做的时候要简单）。
- **Q：什么时候不该 YAGNI？** A：数据库 schema、对外 API、核心架构、安全——这些后期改成本高，值得前瞻。
- **Q：为什么"为将来扩展留接口"常是错的？** A：未来需求不可预测，预测的接口往往不对，还要重做；无用代码增加维护负担。

## 十、迪米特法则（Law of Demeter / LoD）

### 10.1 定义

一个对象应该对其他对象有**最少的了解**。一个方法 `m` 只能调用以下对象的方法：

1. 对象自身（`this`）
2. 方法的参数
3. 方法内创建的对象
4. 对象的直接字段

> 简称：**只和直接朋友说话，不要和陌生人说话**。又叫**最少知道原则**（Least Knowledge Principle）。

### 10.2 难点：链式调用是 LoD 违反吗？

```java
// 违反 LoD：a 拿到 b 拿到 c 拿到 d
a.getB().getC().getD().doSomething();

// 问题：a 依赖了 B、C、D 的结构，B/C/D 任一变化都会影响 a
```

但**流式 API**（Stream、Builder）不算违反：

```java
// 这不是违反 LoD：每次返回的是新对象，a 没有跨越对象图
list.stream().filter(...).map(...).collect(...);
```

判断标准：**链式调用返回的是"同一逻辑链条上的中间值"还是"深入对象图的内部引用"**。

### 10.3 反例

```java
// 反例：订单服务深入到顾客的地址的城市
public class OrderService {
    public void ship(Order order) {
        // 跨越了 order → customer → address → city
        String city = order.getCustomer().getAddress().getCity();
        if ("北京".equals(city)) {
            // ...
        }
    }
}
```

### 10.4 正例

```java
// 方式 1：让 Order 暴露"是否需要特殊处理"的方法
public class Order {
    public boolean needsSpecialShipping() {
        return "北京".equals(customer.getAddress().getCity());
    }
}
public class OrderService {
    public void ship(Order order) {
        if (order.needsSpecialShipping()) { /* ... */ }
    }
}

// 方式 2：在 Order 上做"告知"而非"询问"（Tell, Don't Ask）
public class Order {
    public void ship(ShippingPolicy policy) {
        policy.apply(this.customer.getShippingAddress());
    }
}
```

### 10.5 Go 版

```go
// 反例
func Ship(o *Order) {
    city := o.Customer.Address.City   // 跨越三层
    if city == "北京" { /* ... */ }
}

// 正例
func (o *Order) NeedsSpecialShipping() bool {
    return o.customer.address.city == "北京"
}
func Ship(o *Order) {
    if o.NeedsSpecialShipping() { /* ... */ }
}
```

### 10.6 LoD 的代价

过度遵守 LoD 会导致：

- **中转方法爆炸**：每个对象都要为内部字段提供转发方法。
- **上帝对象**：中间对象承担过多转发职责。

> 实践：LoD 是**指导**而非**铁律**。对**深层次对象图**应用 LoD，对**简单数据结构**（DTO/VO）不应用。

### 10.7 面试速答

- **Q：迪米特法则的定义？** A：一个对象只和直接朋友说话，不深入陌生人内部。
- **Q：`a.getB().getC().do()` 违反 LoD 吗？** A：违反——a 跨越了 B 访问 C。除非 B 是流式 API（每次返回新对象）。
- **Q：LoD 和封装关系？** A：LoD 是封装的延伸——不仅隐藏内部数据，还隐藏内部结构。
- **Q：LoD 过度应用的坏处？** A：中转方法爆炸、上帝对象。对 DTO 等纯数据结构不应套用。

## 十一、组合优于继承（Composition over Inheritance）

### 11.1 定义

优先使用**对象组合**而不是**类继承**来达到复用和扩展。

> GoF 原话："Favor object composition over class inheritance."

### 11.2 难点：继承的陷阱

继承的问题：

1. **白盒复用**：子类依赖父类实现细节，父类变化破坏子类。
2. **编译期绑定**：继承关系在编译时固定，运行时不能换。
3. **强耦合**：子类和父类绑定，无法独立变化。
4. **单继承限制**（Java）：继承了一个父类就不能继承其他。
5. **层级过深**：继承链 5+ 层后几乎不可维护。

### 11.3 反例：继承栈爆炸

```java
// 想给 InputStream 加功能：缓冲、解压、加密、计数...
// Java 用继承
class InputStream { /* ... */ }
class BufferedInputStream extends InputStream { /* ... */ }
class GzipInputStream extends InputStream { /* ... */ }
class EncryptedInputStream extends InputStream { /* ... */ }
// 想要"缓冲 + 解压 + 加密"的组合呢？
// 要么写 EncryptedGzipBufferedInputStream（组合爆炸），要么多层继承（深度爆炸）
```

### 11.4 正例：装饰器模式（组合）

```java
// 装饰器：包装现有对象，组合扩展
public abstract class InputStreamDecorator extends InputStream {
    protected final InputStream delegate;
    public InputStreamDecorator(InputStream d) { delegate = d; }
}

public class BufferedInputStream extends InputStreamDecorator { /* ... */ }
public class GzipInputStream extends InputStreamDecorator { /* ... */ }
public class EncryptedInputStream extends InputStreamDecorator { /* ... */ }

// 任意组合：缓冲 + 解压 + 加密
InputStream s = new BufferedInputStream(
    new GzipInputStream(
        new EncryptedInputStream(
            new FileInputStream("file"))));
// 无组合爆炸，运行时可任意搭配
```

### 11.5 Go 版

Go 没有继承，天然只有组合。**嵌入（embedding）**是 Go 的组合语法：

```go
// Go 的"组合优于继承"是语言强制的
type Reader interface { Read(p []byte) (int, error) }
type Writer interface { Write(p []byte) (int, error) }

// 组合接口
type ReadWriter interface {
    Reader
    Writer
}

// 结构体嵌入：复用方法
type Logger struct{}
func (Logger) Log(msg string) { fmt.Println(msg) }

type Service struct {
    Logger   // 嵌入 Logger，Service 自动获得 Log 方法
    name string
}

s := Service{name: "svc"}
s.Log("hello")   // 等价于 s.Logger.Log("hello")
```

> Go 嵌入 vs Java 继承的关键区别：
> - Go 嵌入是**组合**（持有引用 + 方法转发），运行时可替换。
> - Java 继承是**静态绑定**（子类是父类的特化），编译期固定。
> - Go 没有 `super`，嵌入类型的方法不会被子类型"覆盖"成多态。

### 11.6 何时仍可用继承

继承不是绝对禁止。以下场景继承合理：

1. **真正的 IS-A 关系**：`Cat extends Animal`，且 `Cat` 完全遵守 `Animal` 契约（LSP）。
2. **框架要求**：如 Java 的 `RuntimeException` 必须继承才能被 throw。
3. **模板方法模式**：父类定义骨架，子类填步骤——继承的自然用法。
4. **类型层级稳定**：如 GUI 控件 `Widget → Button → IconButton`。

> 判断标准：**"子类是父类的特化"用继承；"对象有某种能力"用组合**。

### 11.7 面试速答

- **Q：为什么组合优于继承？** A：组合松耦合、运行时可换、无单继承限制；继承强耦合、编译期固定、白盒复用。
- **Q：什么时候用继承？** A：真正的 IS-A 关系且满足 LSP；框架要求；模板方法模式；类型层级稳定。
- **Q：Go 怎么实现"继承"？** A：用结构体嵌入（embedding），本质是组合 + 方法转发，不是真继承。
- **Q：装饰器模式是组合优于继承的体现吗？** A：是。装饰器用组合包装对象，避免继承爆炸。

## 十二、面向接口编程（Program to Interface）

### 12.1 定义

代码应该依赖**抽象接口**，而不是**具体实现**。

> GoF 原话："Program to an interface, not an implementation."

### 12.2 与 DIP 的关系

面向接口编程是 DIP 的通俗表达，DIP 是其形式化定义。两者本质相同：**依赖抽象**。

### 12.3 反例

```java
// 依赖具体类
public class App {
    private ArrayList<String> list = new ArrayList<>();   // 依赖具体实现
    public void add(String s) { list.add(s); }
}
// 想换 LinkedList → 改代码
```

### 12.4 正例

```java
public class App {
    private List<String> list;   // 依赖接口
    public App(List<String> list) { this.list = list; }   // 注入
    public void add(String s) { list.add(s); }
}
// 使用：new App(new ArrayList<>()) 或 new App(new LinkedList<>())
```

### 12.5 误区：接口 ≠ Java interface

"接口"是**抽象**的概念，不一定是 Java 的 `interface` 关键字：

| 语言构造 | 是否算"接口" |
|---------|-------------|
| Java `interface` | 是 |
| Java 抽象类 | 是 |
| Go `interface` | 是 |
| Python 鸭子类型协议 | 是 |
| 函数签名（函数式编程） | 是 |
| 具体类（无抽象） | 否 |

> 关键是"**抽象**"，不是语法。一个具体类如果稳定且不需要多态，直接依赖也可以（如 `String`）。

### 12.6 Go 版

```go
// 反例
type App struct {
    list *arraylist.List   // 依赖具体类型
}

// 正例
type App struct {
    list []string   // 依赖内置 slice（抽象稳定）
}

// 更复杂场景
type Repository interface {
    Save(*User) error
}

type App struct {
    repo Repository   // 依赖接口
}

func NewApp(r Repository) *App { return &App{repo: r} }
```

> Go 的接口隐式实现让"面向接口编程"成本极低——定义接口在使用方，实现方无需声明。

### 12.7 面试速答

- **Q：面向接口编程的定义？** A：依赖抽象接口，不依赖具体实现。
- **Q：接口一定要用 interface 关键字吗？** A：不一定。"接口"指抽象，可以是抽象类、鸭子类型、函数签名。
- **Q：所有依赖都要面向接口吗？** A：不是。稳定、不需要多态的具体类（如 `String`）可以直接依赖。
- **Q：和 DIP 关系？** A：面向接口编程是 DIP 的通俗表达，本质相同。

## 十三、封装变化（Encapsulate What Varies）

### 13.1 定义

识别代码中**会变化的部分**，把它**封装**起来，让变化不影响稳定部分。

> 这是设计模式的核心思想——几乎所有模式都是"封装变化"的不同形式。

### 13.2 变化的类型与对应模式

| 变化类型 | 封装方式 | 对应模式 |
|---------|---------|---------|
| 算法变化 | 策略对象 | 策略模式 |
| 状态变化 | 状态对象 | 状态模式 |
| 创建变化 | 工厂对象 | 工厂方法 / 抽象工厂 |
| 步骤变化 | 模板方法钩子 | 模板方法 |
| 通知变化 | 观察者集合 | 观察者 |
| 请求变化 | 命令对象 | 命令模式 |
| 访问变化 | 访问者对象 | 访问者模式 |

### 13.3 反例：变化点散落

```java
public class PaymentService {
    public void pay(String type, double amount) {
        if ("wechat".equals(type)) {
            // 微信支付逻辑散在这里
            callWechatAPI(amount);
        } else if ("alipay".equals(type)) {
            // 支付宝逻辑散在这里
            callAlipayAPI(amount);
        }
        // 新增"银行卡" → 改这个方法 → 变化没封装
    }
}
```

### 13.4 正例：变化点抽成对象

```java
public interface PaymentStrategy {
    void pay(double amount);
}
public class WechatPay implements PaymentStrategy {
    public void pay(double amount) { callWechatAPI(amount); }
}
public class Alipay implements PaymentStrategy {
    public void pay(double amount) { callAlipayAPI(amount); }
}

public class PaymentService {
    private final PaymentStrategy strategy;
    public PaymentService(PaymentStrategy s) { strategy = s; }
    public void pay(double amount) { strategy.pay(amount); }
    // 新增银行卡 → 加新类，PaymentService 不变
}
```

### 13.5 面试速答

- **Q：封装变化是什么意思？** A：把会变化的代码抽出来封装成对象，让稳定代码不受变化影响。
- **Q：设计模式和"封装变化"关系？** A：几乎所有模式都是封装变化的具体形式——策略封装算法变化、状态封装状态变化、工厂封装创建变化等。
- **Q：怎么识别变化点？** A：看 if/else 分支、看频繁修改的代码、看"将来可能扩展"的注释。

## 十四、好莱坞原则（Hollywood Principle / IoC）

### 14.1 定义

> **Don't call us, we'll call you.**
>
> 不要调用我们，我们会调用你。

高层组件决定何时调用低层组件，低层组件**被动等待被调用**。这是**控制反转**（Inversion of Control, IoC）的口语化表达。

### 14.2 与 DIP / 模板方法的关系

- **DIP**：依赖方向倒置（依赖抽象）。
- **IoC**：控制流方向倒置（框架调用代码）。
- **好莱坞原则**：IoC 的形象化表达。

模板方法是好莱坞原则的典型：

```java
// 父类（高层）：控制流程，调用子类
public abstract class Game {
    public final void play() {   // 模板方法：流程固定
        initialize();
        startPlay();
        endPlay();
    }
    abstract void initialize();
    abstract void startPlay();
    abstract void endPlay();
}

// 子类（低层）：被动等待被调用
public class Chess extends Game {
    void initialize() { /* ... */ }
    void startPlay()  { /* ... */ }
    void endPlay()    { /* ... */ }
}
// 子类不主动调 play()，由父类决定何时调子类方法
```

### 14.3 IoC 容器

Spring 等 IoC 容器把"控制反转"做到极致：

```java
// 传统：代码主动 new 对象
UserService svc = new UserService(new MySQLUserDao());

// IoC：容器管理对象生命周期，代码被动接收
@Service
public class App {
    private final UserService svc;
    public App(UserService svc) { this.svc = svc; }   // 容器注入
}
// App 不控制 svc 的创建，由容器决定
```

### 14.4 Go 版

```go
// 反例：代码主动创建依赖
type App struct{}
func (a *App) Run() {
    dao := &MySQLUserDao{}         // 主动创建
    svc := NewUserService(dao)     // 主动创建
    svc.Register(...)
}

// 正例：依赖从外部注入
type App struct {
    svc UserService
}
func NewApp(svc UserService) *App { return &App{svc: svc} }
func (a *App) Run() { a.svc.Register(...) }
// App 不控制 svc 创建，由调用方（main 或 wire/fx）决定
```

> Go 不像 Spring 有重量级 IoC 容器，但 `wire`、`fx` 等依赖注入工具实现了同样的控制反转思想。简单项目直接在 `main` 手动组装也是 IoC——只要"使用方不创建依赖"。

### 14.5 面试速答

- **Q：好莱坞原则是什么？** A：Don't call us, we'll call you——高层决定何时调用低层，低层被动等待。
- **Q：和 IoC 关系？** A：好莱坞原则是 IoC 的形象化表达。
- **Q：和 DIP 区别？** A：DIP 讲依赖方向倒置（结构）；好莱坞/IoC 讲控制流倒置（行为）。
- **Q：模板方法模式体现好莱坞原则吗？** A：是。父类模板方法控制流程，子类方法被父类调用。

## 十五、CQS / CQRS（命令查询分离）

### 15.1 定义

一个方法应该**要么是命令（改变状态），要么是查询（返回值）**，不能两者兼具。

> Bertrand Meyer 提出。目的：让查询无副作用，可任意调用；让命令显式有副作用，调用者警惕。

### 15.2 反例：命令查询混淆

```java
// 这个方法既改状态又返回值
public class Stack<T> {
    public T pop() {   // 改变状态（删除栈顶）+ 返回值（栈顶元素）
        // ...
    }
}
// 问题：调用方难以判断这是只读还是有副作用
//   if (stack.pop() != null) { ... }  // 这里 pop 实际删除了元素！
```

### 15.3 正例：分离命令和查询

```java
public class Stack<T> {
    public T peek() { return top; }   // 查询：不改变状态
    public void pop() { top = top.next; }   // 命令：改变状态，无返回
}
// 调用方：
T x = stack.peek();   // 明确无副作用
if (x != null) stack.pop();   // 明确有副作用
```

> 实际上 Java 的 `Stack.pop()` 是违反 CQS 的历史包袱。`peek()` + `pop()` 分离才是符合 CQS 的设计。

### 15.4 CQRS：架构级的 CQS

CQRS（Command Query Responsibility Segregation）把 CQS 扩展到架构级：

```
   ┌──────────┐         ┌──────────┐
   │  Command │         │  Query   │
   │   Side   │         │   Side   │
   │ (写模型) │         │ (读模型) │
   └────┬─────┘         └────▲─────┘
        │                    │
        ▼                    │
   ┌─────────┐          ┌─────────┐
   │  Write  │──同步──▶  │  Read   │
   │   DB    │          │   DB    │
   └─────────┘          └─────────┘
        │                    ▲
        └─────异步事件──────┘
```

- **写模型**：专注业务一致性，规范化。
- **读模型**：专注查询性能，反范式、缓存、物化视图。
- 写库和读库通过事件最终一致。

### 15.5 何时用 CQRS

| 场景 | 是否适合 CQRS |
|------|--------------|
| 读远多于写（如电商商品页） | 适合 |
| 读写复杂度差异大 | 适合 |
| 需要多视图查询 | 适合 |
| 简单 CRUD | 不适合（过度设计） |
| 强一致性要求 | 不适合（CQRS 通常最终一致） |

### 15.6 面试速答

- **Q：CQS 的定义？** A：方法要么是命令（改状态）要么是查询（返回值），不兼具。
- **Q：为什么 `pop()` 违反 CQS？** A：它既删除元素又返回元素，命令查询混淆。
- **Q：CQRS 是什么？** A：CQS 的架构级扩展，读写模型分离，常通过事件最终一致。
- **Q：CQRS 适合什么场景？** A：读多写少、读写复杂度差异大、需要多视图查询。不适合简单 CRUD。

## 十六、Tell, Don't Ask

### 16.1 定义

**告诉对象做什么**，而不是**问对象状态再决定做什么**。

> 与 LoD、封装思想一脉相承：把行为放到数据所在的对象里，而不是拿出来在外部决策。

### 16.2 反例：Ask 模式

```java
// 询问对象状态，在外部决策
public class OrderProcessor {
    public void process(Order order) {
        if (order.getStatus() == Status.PAID) {
            if (order.getItems().size() > 0) {
                if (order.getTotal() > 100) {
                    order.setStatus(Status.SHIPPED);
                    order.setShipDate(today());
                }
            }
        }
    }
}
// 问题：订单的内部规则散落在 OrderProcessor，Order 被当成数据包
```

### 16.3 正例：Tell 模式

```java
public class Order {
    public void ship() {   // 把规则放回 Order
        if (status != Status.PAID) throw new IllegalStateException();
        if (items.isEmpty()) throw new IllegalStateException();
        if (total <= 100) throw new IllegalStateException();
        this.status = Status.SHIPPED;
        this.shipDate = today();
    }
}
public class OrderProcessor {
    public void process(Order order) {
        order.ship();   // 告诉订单"发货"，让订单自己决定怎么做
    }
}
```

### 16.4 与 OOP 原则的关系

Tell, Don't Ask 是 OOP 的根本——**对象 = 数据 + 行为**。Ask 模式本质上是**贫血模型**（数据和行为分离），是面向过程写法。

| 风格 | 特征 | 评价 |
|------|------|------|
| 贫血模型 | 数据对象 + Service 操作 | 面向过程，简单但违背 OOP |
| 充血模型 | 数据 + 行为在同一对象 | 符合 Tell Don't Ask，更 OOP |

> DDD（领域驱动设计）主张充血模型——把业务规则放回领域对象。

### 16.5 何时仍用贫血模型

- **CRUD 为主**：简单增删改查，充血反而复杂。
- **跨对象协作**：涉及多个对象的复杂流程，放在 Service 更清晰。
- **框架限制**：如 MyBatis 默认要 POJO，JPA 实体受限。

> 取舍：核心业务规则用充血，流程编排用 Service。

### 16.6 面试速答

- **Q：Tell, Don't Ask 是什么？** A：告诉对象做什么，而不是问状态再决策。
- **Q：和贫血模型关系？** A：Ask 模式是贫血模型；Tell 模式是充血模型，更符合 OOP。
- **Q：DDD 推崇什么？** A：充血模型——业务规则放回领域对象。
- **Q：什么时候用贫血模型？** A：CRUD 为主、跨对象编排、框架限制时。

## 十七、Fail Fast

### 17.1 定义

系统遇到错误时**尽快失败**、**尽早暴露**，而不是隐藏错误、推迟报错、最后崩溃。

### 17.2 反例：隐藏错误

```java
// 反例 1：吞掉异常
public void save(User u) {
    try {
        db.insert(u);
    } catch (Exception e) {
        // 啥也不做 → 错误被隐藏，调用方以为成功
    }
}

// 反例 2：返回 null
public User findById(int id) {
    if (notFound) return null;   // 调用方忘检查 → NPE
}

// 反例 3：返回错误码但不检查
public int delete(int id) {
    return -1;   // 调用方忽略 → 数据不一致
}
```

### 17.3 正例：快速失败

```java
// 入参校验：提前失败
public void register(User u) {
    Objects.requireNonNull(u, "user cannot be null");
    if (u.getName() == null || u.getName().isEmpty()) {
        throw new IllegalArgumentException("name required");
    }
    if (u.getAge() < 0 || u.getAge() > 150) {
        throw new IllegalArgumentException("invalid age");
    }
    // 校验通过才执行
    save(u);
}

// 不返回 null，用 Optional
public Optional<User> findById(int id) {
    return Optional.ofNullable(db.get(id));
}

// 抛异常而非返回错误码
public void delete(int id) {
    if (!exists(id)) throw new NotFoundException("user " + id);
    db.delete(id);
}
```

### 17.4 Fail Fast 的多个层级

| 层级 | 做法 |
|------|------|
| 入参校验 | 方法开头校验，不合法立即抛异常 |
| 不可变对象 | 构造函数校验，构造完成即合法 |
| 配置校验 | 启动时校验所有必需配置，缺失则启动失败 |
| 契约校验 | 断言（assert）不变式 |
| 依赖检查 | 启动时检查依赖服务可用，不可用则不启动 |
| 编译期 | 类型系统、`@NonNull` 注解、Lombok 校验 |

### 17.5 Go 版

```go
// 反例：返回 error 但不检查
func Save(u *User) error {
    _, err := db.Exec("INSERT ...")
    return err
}
func main() {
    Save(u)   // 忽略 error → 错误被吞
}

// 正例：fail fast
func Save(u *User) error {
    if u == nil {
        return errors.New("user is nil")   // 入参校验
    }
    if u.Name == "" {
        return errors.New("name required")
    }
    _, err := db.Exec("INSERT ...")
    if err != nil {
        return fmt.Errorf("save user: %w", err)   // 包装错误，不吞
    }
    return nil
}

func main() {
    if err := Save(u); err != nil {
        log.Fatal(err)   // 立即失败，不忽略
    }
}
```

> Go 的 `error` 是显式返回值，编译器不强制检查，但 `errcheck` 等工具会检查未处理的 error。Go 的 fail fast 靠**显式 error 返回 + 工具检查**实现。

### 17.6 Fail Fast vs 容错

Fail Fast 不是"一遇错误就崩"。容错系统也要 fail fast——**快速失败后快速恢复**，比"隐藏错误慢慢腐烂"更好。

| 场景 | 策略 |
|------|------|
| 输入错误 | Fail Fast，立即拒绝 |
| 内部不变式违反 | Fail Fast，崩溃暴露 bug |
| 依赖服务失败 | Fail Fast + 重试 / 熔断 |
| 部分节点失败 | Fail Fast + 降级 |

### 17.7 面试速答

- **Q：Fail Fast 的定义？** A：尽快失败、尽早暴露错误，不隐藏不推迟。
- **Q：吞异常为什么坏？** A：错误被隐藏，调用方误以为成功，问题累积到后期更难定位。
- **Q：返回 null 和 Optional 区别？** A：null 调用方容易忘记检查；Optional 强制调用方处理"无值"情况。
- **Q：Go 怎么实现 Fail Fast？** A：显式 error 返回 + 调用方必须检查（配合 errcheck 工具）+ `panic` 用于不可恢复错误。

## 十八、原则之间的冲突与取舍

设计原则不是铁律，**经常互相冲突**。工程能力体现在**权衡取舍**。

### 18.1 常见冲突

| 冲突 | 表现 | 取舍 |
|------|------|------|
| DRY vs KISS | DRY 抽象消除重复，KISS 反对过度抽象 | 重复 ≤2 次容忍（WET），第 3 次再抽象 |
| DRY vs AHA | DRY 追求唯一表示，AHA 警告过早抽象 | 错误的抽象比重复更糟，宁可不抽象 |
| SOLID vs KISS | SOLID 引入接口/抽象，KISS 反对复杂度 | 只对确知的变化抽象 |
| YAGNI vs 前瞻 | YAGNI 反对预测未来，前瞻反对后期重做 | schema/API/架构前瞻；业务逻辑 YAGNI |
| LoD vs 简洁 | LoD 要求转发方法，导致方法爆炸 | 对深对象图用 LoD，DTO 不用 |
| Tell-Don't-Ask vs Service | 充血模型 vs 贫血模型 | 核心规则充血，编排逻辑 Service |
| Fail Fast vs 容错 | 立即失败 vs 继续运行 | 输入 fail fast，运行时容错 |

### 18.2 取舍的核心原则

**简单优先，按需演进**：

1. **先简单**：用最简单方式实现当前需求。
2. **识别变化**：代码稳定运行一段时间后，识别真实变化点。
3. **按需抽象**：变化出现时，再用对应原则/模式重构。
4. **持续重构**：代码不会一次写好，持续小步重构。

> Uncle Bob: "Make it work, make it right, make it fast." ——先能跑，再正确，最后优化。

### 18.3 反例：原则教条主义

```java
// 一个简单 Hello World，被教条主义魔改
public interface GreetingStrategy { String greet(String name); }
public class EnglishGreetingStrategy implements GreetingStrategy {
    public String greet(String name) { return "Hello, " + name; }
}
public class GreetingStrategyFactory {
    public GreetingStrategy create(Locale locale) {
        return switch (locale.getLanguage()) {
            case "en" -> new EnglishGreetingStrategy();
            // ...
        };
    }
}
public class GreetingService {
    private final GreetingStrategy strategy;
    @Autowired
    public GreetingService(GreetingStrategy strategy) { this.strategy = strategy; }
    public String greet(String name) { return strategy.greet(name); }
}
// SOLID 全占，DRY 满足，但这就是个 Hello World → 过度设计
```

**正确做法**：

```java
public String greet(String name) { return "Hello, " + name; }
// 真出现多语言需求时再重构
```

## 二十、面试综合题

### Q1：SOLID 你最常违反哪一条？怎么改？

> 实话实答：**SRP 最常被违反**。一个 Service 类堆了多个业务方法，看起来都"和用户相关"，但实际有多个变化轴线（业务规则、持久化、通知）。
> 改法：按变化轴线拆分——业务逻辑留 Service，持久化抽 Repository，通知抽 Notifier。

### Q2：什么时候该用设计模式，什么时候不该用？

> 该用：变化点明确且高频、代码稳定后识别出模式、复杂度来自问题本身。
> 不该用：简单 CRUD、未来需求不确定（YAGNI）、为用模式而用模式（KISS）。
> 标准：**模式是为变化服务的，不是为了显得专业**。

### Q3：组合优于继承，但 Java 的 Stream、集合都是继承体系，怎么解释？

> 继承不是绝对禁止。**真正的 IS-A 关系**且**层级稳定**时继承合理（如 `ArrayList extends AbstractList`）。问题是"用继承来做复用"（如为了复用父类方法而继承）——这时该用组合。

### Q4：DRY 和 KISS 冲突怎么办？

> 优先 KISS。重复 ≤2 次容忍，第 3 次再抽象（Rule of Three）。错误的抽象比重复更难维护——重构时拆抽象比合抽象容易。

### Q5：贫血模型和充血模型怎么选？

> 核心业务规则用充血（领域对象封装规则，符合 Tell Don't Ask）；流程编排用 Service（跨对象协调，注入领域对象）；CRUD 用贫血。DDD 推崇充血，但不是所有项目都适合 DDD。

### Q6：Fail Fast 和容错矛盾吗？

> 不矛盾。Fail Fast 是**快速暴露错误**，容错是**错误后继续运行**。两者结合：**快速失败 → 快速恢复**（重试 / 熔断 / 降级）。隐藏错误（吞异常）才是和容错矛盾的——问题累积到不可恢复。

### Q7：Go 怎么实践 SOLID？

> Go 语言特性天然支持 SOLID：
> - SRP：小结构体 + 小接口
> - OCP：接口 + 多态
> - LSP：实现同一接口的行为契约一致
> - ISP：接口尽量小，使用方定义接口
> - DIP：接口隐式实现，定义在使用方
> Go 哲学："接口越小越好"、"少即是多"、"组合优于继承"——与 SOLID 高度一致。
