## 参考范式 —— 分层模式（Layered Pattern）

### 一、定义

将系统划分为若干**水平层次**，每一层承担一类职责，**上层依赖下层**，下层对上层一无所知。层与层之间通过明确的接口通信，禁止跨层调用与反向依赖。

分层模式是软件架构中最古老、最广泛使用的范式，几乎是所有企业应用的"默认骨架"。

---

### 二、经典四层架构

| 层次 | 名称 | 职责 | 典型组件 |
|------|------|------|----------|
| 1 | 表现层（Presentation） | 接收用户输入、渲染输出、协议转换 | Controller、View、API Endpoint、DTO |
| 2 | 业务逻辑层（Business / Service） | 核心领域规则、流程编排 | Service、Domain Model、UseCase |
| 3 | 数据访问层（Data Access / Repository） | 持久化、外部数据交互 | Repository、DAO、Mapper |
| 4 | 数据存储层（Storage） | 数据落地 | MySQL、Redis、文件系统 |

```
┌─────────────────────────────────────┐
│  表现层 Presentation (Controller)    │  ← 接收 HTTP / gRPC 请求
├─────────────────────────────────────┤
│  业务层 Service (Domain Logic)       │  ← 编排业务规则
├─────────────────────────────────────┤
│  数据访问层 Repository (DAO)         │  ← 屏蔽存储细节
├─────────────────────────────────────┤
│  存储层 Storage (MySQL / Redis)      │  ← 数据落地
└─────────────────────────────────────┘
        ▲ 上层依赖下层，下层不感知上层
```

---

### 三、调用规则：严格分层 vs 松散分层

#### 1. 严格分层（Strict Layering）

**第 N 层只能调用第 N-1 层**，不能跨层。

```
Presentation ──▶ Service ──▶ Repository ──▶ Storage
     ✘ 不允许 Presentation 直接调用 Repository
```

- 优点：层间解耦最彻底，替换某一层不影响其它层。
- 缺点：调用链长，简单场景也要逐层透传，"噪音代码"多。

#### 2. 松散分层（Relaxed Layering）

**第 N 层可以调用任意下层**。表现层为追求性能可直接跳过 Service 访问 Repository（只读场景常见）。

```
Presentation ──┬──▶ Service ──▶ Repository ──▶ Storage
               └────────────────────▶
                  （只读查询允许跨层）
```

- 优点：灵活，减少无意义透传。
- 缺点：层间耦合增加，替换中间层时要排查所有跨层调用。

> **实践中常用折中方案**：写操作走严格分层，读操作允许松散分层（CQRS 思想）。

### 四、Golang 伪代码示例

#### 1. 目录结构

```
order-service/
├── internal/
│   ├── handler/        # 表现层
│   │   └── order_handler.go
│   ├── service/        # 业务层
│   │   └── order_service.go
│   ├── repository/     # 数据访问层
│   │   ├── order_repo.go
│   │   └── model.go
│   └── domain/         # 领域模型（纯结构体，无依赖）
│       └── order.go
└── main.go
```

#### 2. 表现层（Handler）

```go
package handler

type OrderHandler struct {
    svc *service.OrderService  // 仅依赖业务层接口
}

// POST /orders
func (h *OrderHandler) Create(w http.ResponseWriter, r *http.Request) {
    var req CreateOrderRequest
    if err := json.NewDecoder(r.Body).Decode(&req); err != nil {
        http.Error(w, "bad request", http.StatusBadRequest)
        return
    }
    order, err := h.svc.Create(r.Context(), req.ToDomain())
    if err != nil {
        http.Error(w, err.Error(), http.StatusInternalServerError)
        return
    }
    json.NewEncoder(w).Encode(order)
}
```

#### 3. 业务层（Service）

```go
package service

type OrderService struct {
    repo   repository.OrderRepository  // 依赖接口，不依赖具体实现
    notify Notifier
}

func (s *OrderService) Create(ctx context.Context, o domain.Order) (domain.Order, error) {
    if err := o.Validate(); err != nil {
        return domain.Order{}, err
    }
    o.ID = uuid.NewString()
    o.Status = domain.StatusCreated
    o.CreatedAt = time.Now()

    if err := s.repo.Save(ctx, o); err != nil {
        return domain.Order{}, fmt.Errorf("save order: %w", err)
    }
    _ = s.notify.OrderCreated(o)  // 通知解耦，可异步
    return o, nil
}
```

#### 4. 数据访问层（Repository）

```go
package repository

type OrderRepository interface {
    Save(ctx context.Context, o domain.Order) error
    FindByID(ctx context.Context, id string) (domain.Order, error)
}

type mysqlOrderRepo struct {
    db *sql.DB
}

func NewMysqlOrderRepo(db *sql.DB) OrderRepository {
    return &mysqlOrderRepo{db: db}
}

func (r *mysqlOrderRepo) Save(ctx context.Context, o domain.Order) error {
    _, err := r.db.ExecContext(ctx,
        `INSERT INTO orders (id, user_id, amount, status, created_at)
         VALUES (?, ?, ?, ?, ?)`,
        o.ID, o.UserID, o.Amount, o.Status, o.CreatedAt)
    return err
}
```

#### 5. 依赖注入（main.go 装配）

```go
func main() {
    db, _ := sql.Open("mysql", os.Getenv("DSN"))

    repo := repository.NewMysqlOrderRepo(db)
    svc  := service.NewOrderService(repo, notify.NewEmailNotifier())
    h    := handler.NewOrderHandler(svc)

    http.Handle("/orders", h)
    http.ListenAndServe(":8080", nil)
}
```

> 关键：依赖关系**单向**从上到下；下层（Repository）通过接口反转依赖；main.go 是唯一知道具体实现的地方。

### 五、分层的价值

| 价值 | 说明 |
|------|------|
| **职责清晰** | 每层只关心本层问题，降低认知负担 |
| **可替换性** | MySQL 换 PostgreSQL 只动 Repository 层 |
| **可测试性** | Service 层可用 Mock Repository 做单元测试 |
| **演进性** | 表现层可同时支持 HTTP / gRPC / GraphQL，业务层复用 |
| **团队协作** | 前端 / 后端 / DBA 按层分工，互不阻塞 |

### 六、分层的代价与反模式

#### 1. 性能损耗

每次跨层调用都有序列化、参数转换开销。对极高性能场景（如高频交易），可能需要扁平化。

#### 2. 转发透传（Passthrough）反模式

```go
// ❌ Service 只是 Repository 的转发器，没有业务价值
func (s *OrderService) FindByID(ctx context.Context, id string) (Order, error) {
    return s.repo.FindByID(ctx, id)  // 纯透传，无任何业务逻辑
}
```

此时应考虑**松散分层**，让 Handler 直接调用 Repository（只读场景），或合并这两层。

#### 3. 跨层泄漏反模式

```go
// ❌ Handler 直接操作 sql.DB，绕过 Service 和 Repository
func (h *OrderHandler) Create(w http.ResponseWriter, r *http.Request) {
    db.Exec("INSERT INTO orders ...")  // 跨层调用！
}
```

表现层一旦直接依赖底层存储，整个分层架构名存实亡。

#### 4. 循环依赖反模式

```go
// ❌ Repository 反过来调用 Service
type mysqlOrderRepo struct {
    svc *OrderService  // 反向依赖，破坏分层
}
```

### 七、分层模式的变体

#### 1. 三层架构（经典 MVC 衍生）

```
Controller (Web) ──▶ Service ──▶ DAO
```

适用于中小型 CRUD 系统，是 Java Spring / Go Gin 项目的默认形态。

#### 2. 六边形架构（Hexagonal / Ports & Adapters）

将领域逻辑置于核心，所有外部交互（DB、HTTP、MQ）通过"端口"适配。是分层架构的**演化版**，进一步解耦了领域与基础设施。

```
                  ┌─────────────┐
   HTTP Adapter ──▶│             │──▶ DB Adapter
                  │  Domain Core │
   MQ Adapter   ──▶│  (业务层)    │──▶ Email Adapter
                  └─────────────┘
```

#### 3. 洋葱架构 / 整洁架构（Clean Architecture）

依赖方向**从外向内**，内层不知道外层存在。本质是分层模式把"水平依赖"改为"同心圆依赖"。

```
   Entities (领域模型)
       ▲
   Use Cases (业务用例)
       ▲
   Interface Adapters (Controller / Repository 实现)
       ▲
   Frameworks & Drivers (Web / DB / 外部库)
```

### 八、与其它架构的关系

| 对比项 | 分层模式 | 微服务 | 事件驱动 |
|--------|---------|--------|---------|
| 切分维度 | 水平（按技术职责） | 垂直（按业务领域） | 按事件流 |
| 通信方式 | 同步函数调用 | 多样（HTTP/RPC/MQ） | 异步消息 |
| 适用场景 | 单体应用 | 大型分布式系统 | 解耦度要求高的系统 |

> 微服务内部通常仍采用分层架构，微服务之间则可采用 REST / 事件驱动。**分层是"单服务内部"的组织方式**。

### 九、速记要点

| 要点 | 记忆 |
|------|------|
| 方向 | 上层依赖下层，依赖单向 |
| 边界 | 层间只通过接口/DTO 通信 |
| 严格 vs 松散 | 写严格、读可松散 |
| 接口反转 | 下层定义接口，上层依赖接口，main 装配实现 |
| 反模式 | 转发透传、跨层调用、循环依赖 |
| 演化 | 六边形 / 整洁架构是分层模式的进阶形态 |
