## 设计模式 —— 行为型模式（Behavioral Patterns）

行为型模式关注**对象之间的职责分配与交互方式**：谁做什么、什么时候做、怎么通信。创建型解决"怎么造"，结构型解决"怎么组合"，行为型解决"怎么协作"。

涉及的模式（GoF 11 种）：

- **责任链（Chain of Responsibility）**
- **命令（Command）**
- **解释器（Interpreter）**
- **迭代器（Iterator）**
- **中介者（Mediator）**
- **备忘录（Memento）**
- **观察者（Observer）**
- **状态（State）**
- **策略（Strategy）**
- **模板方法（Template Method）**
- **访问者（Visitor）**

> 面试提示：行为模式的考点集中在"**何时用 X 而不用 Y**"以及"**用与不用的代价**"。其中 **策略 / 观察者 / 责任链 / 状态 / 模板方法** 是高频考点，**访问者 / 解释器** 出现频率低但能区分候选人深度。

## 一、策略模式（Strategy）

### 1.1 意图

定义一系列算法，把它们各自封装成可互换的类，使得算法可以独立于使用它的客户端变化。

> 通俗说：把"做一件事的不同做法"抽出来，调用方在运行时挑选一种。

### 1.2 适用场景

- 同一业务有多种实现（多种支付、多种排序、多种折扣计算）。
- 需要在运行时切换算法。
- 想消除大量的 `if/else` 分支。
- 算法变更频繁，不希望影响调用方。

### 1.3 结构

```
   ┌──────────────┐  uses   ┌──────────────┐
   │   Context    │────────▶│  Strategy    │ (接口)
   └──────────────┘         └──────┬───────┘
                                   │
                  ┌────────────────┼────────────────┐
                  ▼                ▼                ▼
            ┌──────────┐     ┌──────────┐     ┌──────────┐
            │StrategyA │     │StrategyB │     │StrategyC │
            └──────────┘     └──────────┘     └──────────┘
```

### 1.4 难点：消除 if/else 的关键

```java
// 反例：分支地狱
public double calcPrice(String type, double price) {
    if ("vip".equals(type))       return price * 0.8;
    else if ("svip".equals(type)) return price * 0.7;
    else if ("new".equals(type))  return price * 0.9;
    else                          return price;
}
```

每新增一种用户类型都要改这个方法，违反 OCP。策略模式把每种折扣抽成独立类。

### 1.5 Java 版

```java
// 策略接口
public interface DiscountStrategy {
    double apply(double price);
}

// 具体策略
public class VipDiscount implements DiscountStrategy {
    public double apply(double price) { return price * 0.8; }
}
public class SvipDiscount implements DiscountStrategy {
    public double apply(double price) { return price * 0.7; }
}
public class NewUserDiscount implements DiscountStrategy {
    public double apply(double price) { return price * 0.9; }
}
public class NoDiscount implements DiscountStrategy {
    public double apply(double price) { return price; }
}

// Context：持有策略，可运行时切换
public class Order {
    private DiscountStrategy strategy;

    public Order(DiscountStrategy strategy) { this.strategy = strategy; }
    public void setStrategy(DiscountStrategy s) { this.strategy = s; }

    public double checkout(double price) {
        return strategy.apply(price);
    }
}

// 客户端
Order order = new Order(new VipDiscount());
order.checkout(100);   // 80
order.setStrategy(new SvipDiscount());
order.checkout(100);   // 70
```

#### 进阶：策略注册表（消除工厂的 switch）

```java
public class DiscountRegistry {
    private final Map<String, DiscountStrategy> strategies = new HashMap<>();

    public DiscountRegistry() {
        strategies.put("vip", new VipDiscount());
        strategies.put("svip", new SvipDiscount());
        strategies.put("new", new NewUserDiscount());
        strategies.put("default", new NoDiscount());
    }

    public DiscountStrategy get(String type) {
        return strategies.getOrDefault(type, strategies.get("default"));
    }
}
```

> Spring 中可以用 `Map<String, DiscountStrategy>` + `@Service("vip")` 自动注入所有策略 Bean，完全消除 if/else。

### 1.6 Go 版

Go 的策略模式通常用**接口 + 函数**实现。函数本身就是一等公民，比 Java 更轻量。

```go
package discount

// 策略接口
type Strategy interface {
    Apply(price float64) float64
}

// 具体策略
type Vip struct{}
func (Vip) Apply(p float64) float64 { return p * 0.8 }

type Svip struct{}
func (Svip) Apply(p float64) float64 { return p * 0.7 }

type NewUser struct{}
func (NewUser) Apply(p float64) float64 { return p * 0.9 }

type None struct{}
func (None) Apply(p float64) float64 { return p }

// Context
type Order struct{ strategy Strategy }

func NewOrder(s Strategy) *Order         { return &Order{strategy: s} }
func (o *Order) SetStrategy(s Strategy)  { o.strategy = s }
func (o *Order) Checkout(price float64) float64 { return o.strategy.Apply(price) }
```

#### Go 风格：用函数代替接口（更地道）

```go
type DiscountFunc func(price float64) float64

func VipDiscount(p float64) float64      { return p * 0.8 }
func SvipDiscount(p float64) float64     { return p * 0.7 }
func NewUserDiscount(p float64) float64  { return p * 0.9 }

type Order struct{ strategy DiscountFunc }

func (o *Order) Checkout(price float64) float64 {
    if o.strategy == nil {
        return price
    }
    return o.strategy(price)
}

// 注册表
var registry = map[string]DiscountFunc{
    "vip":  VipDiscount,
    "svip": SvipDiscount,
    "new":  NewUserDiscount,
}

func GetDiscount(kind string) DiscountFunc {
    if fn, ok := registry[kind]; ok {
        return fn
    }
    return func(p float64) float64 { return p }
}
```

> Go 实践：当策略只有一个方法且无状态时，**用函数代替接口**更地道。当策略需要持有多字段或多个方法时，再用接口。

### 1.7 策略 vs 工厂 vs 状态

| 对比项 | 策略 | 工厂 | 状态 |
|--------|------|------|------|
| 关注点 | "怎么做" | "造什么" | "现在处于哪个状态" |
| 客户端是否主动选 | 是 | 是 | 否（状态自动转换） |
| 切换频率 | 业务驱动 | 一次性创建 | 内部驱动 |

### 1.8 面试速答

- **Q：策略模式解决什么？** A：消除条件分支，让算法可独立变化、运行时切换。
- **Q：策略模式和工厂模式区别？** A：工厂关心"创建哪种对象"，策略关心"用哪种算法"。
- **Q：策略模式和状态模式区别？** A：策略由客户端主动选择；状态由对象内部状态驱动自动切换，对客户端透明。
- **Q：策略模式的缺点？** A：策略类数量膨胀；客户端必须了解所有策略差异。

## 二、观察者模式（Observer）

### 2.1 意图

定义对象间**一对多**的依赖：当一个对象状态变化时，所有依赖者自动收到通知。

> 又叫发布-订阅（Publish/Subscribe），但严格意义上 Pub/Sub 中间多一层 Broker，而观察者模式 Subject 直接持有 Observer 引用。

### 2.2 适用场景

- 事件系统（按钮点击、消息总线）。
- 数据变更通知（MVVM 中 Model 变化通知 View）。
- 消息队列的消费者模型（同进程内）。
- Reactor 模式（事件驱动 IO）。

### 2.3 结构

```
                notify()
   ┌──────────────┼──────────────┐
   │              │              │
   ▼              ▼              ▼
┌──────┐      ┌──────┐      ┌──────┐
│Obs A │      │Obs B │      │Obs C │
└──────┘      └──────┘      └──────┘
   ▲              ▲              ▲
   │              │              │
   └──────────────┴──────────────┘
                  │
              ┌───────┐
              │Subject│ attach/detach/notify
              └───────┘
```

### 2.4 难点：推模型 vs 拉模型

- **推模型**：Subject 把变化的数据**主动推给** Observer（参数传完整数据）。简单、耦合高。
- **拉模型**：Subject 只发"我变了"的通知，Observer 自己来 Subject 拉数据。解耦、性能稍低。

### 2.5 Java 版

```java
// 观察者接口
public interface Observer<T> {
    void update(T event);
}

// Subject 基类
public class Subject<T> {
    private final List<Observer<T>> observers = new CopyOnWriteArrayList<>();   // 线程安全

    public void attach(Observer<T> o)  { observers.add(o); }
    public void detach(Observer<T> o)  { observers.remove(o); }

    protected void notifyObservers(T event) {
        for (Observer<T> o : observers) {
            o.update(event);   // 顺序通知
        }
    }
}

// 具体业务：温度传感器
public class TemperatureSensor extends Subject<Double> {
    private double temperature;

    public void setTemperature(double t) {
        if (this.temperature != t) {
            this.temperature = t;
            notifyObservers(t);   // 自动推送
        }
    }

    public double getTemperature() { return temperature; }
}

// 具体观察者：显示屏
public class Display implements Observer<Double> {
    private final String name;
    public Display(String name) { this.name = name; }

    public void update(Double temp) {
        System.out.println(name + " 显示: " + temp + "℃");
    }
}

// 使用
TemperatureSensor sensor = new TemperatureSensor();
sensor.attach(new Display("客厅"));
sensor.attach(new Display("卧室"));
sensor.setTemperature(25.5);
// 客厅 显示: 25.5℃
// 卧室 显示: 25.5℃
```

#### Java 内置工具

- `java.util.Observable`（已废弃，JDK 9+）：设计糟糕，`setChanged` 是 protected，必须继承。
- `java.beans.PropertyChangeListener`：属性变化监听，标准库推荐。
- 现代 Java 用 **Reactor / RxJava / Flow API**（响应式流）。

### 2.6 Go 版

Go 没有"继承基类"的概念，用接口 + 切片即可。Go channel 是观察者模式的天然载体。

#### 方式 1：经典观察者

```go
package observer

type Observer interface {
    Update(event any)
}

type Subject struct {
    observers []Observer
}

func (s *Subject) Attach(o Observer)    { s.observers = append(s.observers, o) }
func (s *Subject) Detach(target Observer) {
    for i, o := range s.observers {
        if o == target {
            s.observers = append(s.observers[:i], s.observers[i+1:]...)
            return
        }
    }
}
func (s *Subject) Notify(event any) {
    for _, o := range s.observers {
        o.Update(event)
    }
}
```

#### 方式 2：用 channel（Go 地道写法）

```go
package eventbus

type EventBus struct {
    subscribers map[string][]chan any
    mu          sync.RWMutex
}

func New() *EventBus {
    return &EventBus{subscribers: make(map[string][]chan any)}
}

func (b *EventBus) Subscribe(topic string) <-chan any {
    b.mu.Lock()
    defer b.mu.Unlock()
    ch := make(chan any, 16)   // 带缓冲，避免慢消费者阻塞发布者
    b.subscribers[topic] = append(b.subscribers[topic], ch)
    return ch
}

func (b *EventBus) Publish(topic string, event any) {
    b.mu.RLock()
    subs := b.subscribers[topic]
    b.mu.RUnlock()
    for _, ch := range subs {
        select {
        case ch <- event:
        default:
            // 慢消费者：丢弃或重试，避免阻塞
        }
    }
}
```

> Go 实践：用 channel 实现的 EventBus 是观察者模式的并发安全版本，特别适合跨 goroutine 通信。注意"慢消费者"问题——`select + default` 丢弃、或用独立 goroutine 异步消费。

### 2.7 陷阱

| 陷阱 | 说明 | 解决 |
|------|------|------|
| 内存泄漏 | Subject 持有 Observer 引用，未 detach 时无法 GC | Java 用 WeakReference；Go 关闭 channel 后从切片移除 |
| 顺序依赖 | Observer 之间隐含执行顺序 | 用并发通知打破顺序依赖 |
| 链式更新 | Observer A 在 update 中又修改 Subject，触发 B → 死循环 | 加 reentrant guard 或禁止在 update 中改 Subject |
| 同步阻塞 | 一个 Observer 慢，全部拖死 | 异步通知（线程池 / channel） |

### 2.8 面试速答

- **Q：观察者模式解决什么？** A：一对多依赖，状态变化时自动通知所有观察者，实现 Subject 和 Observer 解耦。
- **Q：推模型和拉模型？** A：推模型 Subject 主动传数据；拉模型只通知事件，Observer 主动查询。
- **Q：观察者和发布订阅区别？** A：观察者 Subject 直接持有 Observer，耦合高；Pub/Sub 中间有 Broker，发布者订阅者互不感知。
- **Q：观察者模式有哪些坑？** A：内存泄漏（未取消订阅）、循环依赖、慢消费者阻塞、顺序依赖。

## 三、责任链模式（Chain of Responsibility）

### 3.1 意图

将请求沿着一条链传递，每个处理者决定**处理请求**或**传给下一个**。发送者不需要知道哪个处理者最终处理。

### 3.2 适用场景

- HTTP 请求处理（Filter / Interceptor / Middleware）。
- 日志级别（DEBUG → INFO → WARN → ERROR）。
- 审批流程（组长 → 经理 → 总监）。
- 异常处理链。
- Spring `HandlerInterceptor`、Servlet `FilterChain`、Netty `ChannelPipeline`。

### 3.3 结构

```
   Client ──▶ Handler1 ──▶ Handler2 ──▶ Handler3 ──▶ null
                  │            │            │
                  ▼            ▼            ▼
               处理 or 转       处理 or 转    处理 or 转
```

### 3.4 难点：纯与不纯

- **纯责任链**：每个 Handler 要么处理要么传递，不既处理又传递。
- **不纯责任链**：Handler 可以处理后继续传递（如 Filter 修改请求后传给下一个）。

实际工程中**不纯责任链更常见**（Servlet Filter、Spring Interceptor 都是不纯的）。

### 3.5 Java 版

```java
// 抽象处理者
public abstract class Handler {
    protected Handler next;

    public Handler setNext(Handler next) {
        this.next = next;
        return next;   // 链式构建
    }

    public abstract void handle(Request req);

    protected void passToNext(Request req) {
        if (next != null) next.handle(req);
    }
}

// 具体处理者 1：认证
public class AuthHandler extends Handler {
    public void handle(Request req) {
        if (req.getToken() == null) {
            throw new RuntimeException("未认证");
        }
        System.out.println("认证通过");
        passToNext(req);
    }
}

// 具体处理者 2：限流
public class RateLimitHandler extends Handler {
    public void handle(Request req) {
        if (isRateLimited(req)) {
            throw new RuntimeException("限流");
        }
        System.out.println("限流通过");
        passToNext(req);
    }
}

// 具体处理者 3：日志
public class LogHandler extends Handler {
    public void handle(Request req) {
        long start = System.currentTimeMillis();
        try {
            passToNext(req);
        } finally {
            System.out.println("耗时: " + (System.currentTimeMillis() - start) + "ms");
        }
    }
}

// 客户端：链式构建
Handler chain = new AuthHandler();
chain.setNext(new RateLimitHandler()).setNext(new LogHandler());
chain.handle(request);
```

#### Java 函数式风格（推荐）

```java
@FunctionalInterface
public interface Filter {
    void doFilter(Request req, FilterChain chain);
}

public class FilterChain {
    private final List<Filter> filters;
    private int index = 0;

    public FilterChain(List<Filter> filters) { this.filters = filters; }

    public void proceed(Request req) {
        if (index < filters.size()) {
            Filter f = filters.get(index++);
            f.doFilter(req, this);   // 调用方决定是否继续
        }
    }
}

// 使用
List<Filter> filters = List.of(
    (req, chain) -> { System.out.println("auth"); chain.proceed(req); },
    (req, chain) -> { System.out.println("log"); chain.proceed(req); },
    (req, chain) -> { System.out.println("business"); }
);
new FilterChain(filters).proceed(req);
```

> 这就是 Servlet `FilterChain` 的精髓：每个 Filter 自己决定是否调用 `chain.doFilter()`，从而实现"前置处理 / 后置处理"的洋葱模型。

### 3.6 Go 版

Go 没有继承，责任链用**接口 + next 字段**或**中间件函数**实现。后者是 Go Web 框架的标准做法。

#### 方式 1：经典链式 Handler

```go
type Handler interface {
    Handle(req *Request)
    SetNext(Handler) Handler
}

type BaseHandler struct{ next Handler }

func (h *BaseHandler) SetNext(next Handler) Handler {
    h.next = next
    return next
}
func (h *BaseHandler) Next(req *Request) {
    if h.next != nil {
        h.next.Handle(req)
    }
}

type AuthHandler struct{ BaseHandler }
func (h *AuthHandler) Handle(req *Request) {
    if req.Token == "" {
        panic("未认证")
    }
    fmt.Println("认证通过")
    h.Next(req)
}

type LogHandler struct{ BaseHandler }
func (h *LogHandler) Handle(req *Request) {
    start := time.Now()
    h.Next(req)
    fmt.Println("耗时:", time.Since(start))
}

// 构建链
auth := &AuthHandler{}
log := &LogHandler{}
auth.SetNext(log)
auth.Handle(req)
```

#### 方式 2：中间件函数（Go 地道写法）

```go
type HandlerFunc func(req *Request)

type Middleware func(HandlerFunc) HandlerFunc

func AuthMiddleware(next HandlerFunc) HandlerFunc {
    return func(req *Request) {
        if req.Token == "" {
            panic("未认证")
        }
        fmt.Println("认证通过")
        next(req)
    }
}

func LogMiddleware(next HandlerFunc) HandlerFunc {
    return func(req *Request) {
        start := time.Now()
        next(req)
        fmt.Println("耗时:", time.Since(start))
    }
}

// 把多个中间件套到核心 Handler 上
func Chain(h HandlerFunc, mws ...Middleware) HandlerFunc {
    for i := len(mws) - 1; i >= 0; i-- {
        h = mws[i](h)
    }
    return h
}

// 使用
final := Chain(
    func(req *Request) { fmt.Println("业务处理") },
    AuthMiddleware,
    LogMiddleware,
)
final(req)
```

> 这就是 Gin / Echo / Chi 等 Go Web 框架中间件的实现方式。函数式中间件比类继承更轻量、组合更灵活。

### 3.7 陷阱

| 陷阱 | 说明 | 解决 |
|------|------|------|
| 链断裂 | 某个 Handler 忘记调用 `next` | 不纯链用框架封装（FilterChain），纯链用模板方法保证 |
| 链过长 | 链上 Handler 太多，调试困难 | 控制链长度；用图结构（DAG）替代 |
| 循环引用 | A → B → A 死循环 | 加深度限制或访问标记 |
| 性能 | 每次请求遍历整链 | 静态链可以编译期优化；动态链不可避免 |

### 3.8 面试速答

- **Q：责任链解决什么？** A：请求发送者和接收者解耦，多个接收者按顺序尝试处理。
- **Q：纯和不纯责任链？** A：纯链只处理或只传递；不纯链可以既处理又传递（如 Filter 前后置）。
- **Q：Servlet FilterChain 是责任链吗？** A：是，且是不纯责任链，每个 Filter 可以前置+后置处理。
- **Q：Go 怎么实现责任链？** A：经典用接口 + next；地道用中间件函数 `func(Handler) Handler`。

## 四、状态模式（State）

### 4.1 意图

允许一个对象在其**内部状态改变时改变其行为**，仿佛对象本身换了类。

### 4.2 适用场景

- 对象行为随状态变化（订单状态机、流程引擎）。
- 大量 `if (state == X)` 分支判断。
- 游戏 AI（移动 / 攻击 / 死亡 / 复活）。

### 4.3 结构

```
   ┌───────────────┐  delegates to  ┌──────────────┐
   │   Context     │───────────────▶│   State      │ (接口)
   │  state: State │                └──────┬───────┘
   │  request()    │                       │
   └───────────────┘            ┌──────────┼──────────┐
                                ▼          ▼          ▼
                          ┌──────┐    ┌──────┐    ┌──────┐
                          │StateA│    │StateB│    │StateC│
                          └──────┘    └──────┘    └──────┘
```

### 4.4 难点：状态 vs 策略

- **策略模式**：客户端主动选择策略，**策略之间互不感知**。
- **状态模式**：状态自己决定下一个状态，**状态之间互相转换**，对客户端透明。

### 4.5 Java 版

```java
// 状态接口
public interface OrderState {
    void next(Order order);
    void cancel(Order order);
    String name();
}

// Context：订单
public class Order {
    private OrderState state;

    public Order() { this.state = new CreatedState(); }

    public void setState(OrderState s) { this.state = s; }
    public OrderState getState() { return state; }

    public void next()   { state.next(this); }
    public void cancel() { state.cancel(this); }
}

// 具体状态：已创建
public class CreatedState implements OrderState {
    public void next(Order o) {
        System.out.println("创建 → 已支付");
        o.setState(new PaidState());
    }
    public void cancel(Order o) {
        System.out.println("创建 → 已取消");
        o.setState(new CancelledState());
    }
    public String name() { return "CREATED"; }
}

// 具体状态：已支付
public class PaidState implements OrderState {
    public void next(Order o) {
        System.out.println("已支付 → 已发货");
        o.setState(new ShippedState());
    }
    public void cancel(Order o) {
        System.out.println("已支付，需走退款流程");
        o.setState(new CancelledState());
    }
    public String name() { return "PAID"; }
}

// 具体状态：已发货
public class ShippedState implements OrderState {
    public void next(Order o)    { System.out.println("已发货，无法流转"); }
    public void cancel(Order o)  { System.out.println("已发货，无法取消"); }
    public String name() { return "SHIPPED"; }
}

// 具体状态：已取消
public class CancelledState implements OrderState {
    public void next(Order o)    { System.out.println("已取消，终态"); }
    public void cancel(Order o)  { System.out.println("已取消"); }
    public String name() { return "CANCELLED"; }
}

// 使用
Order order = new Order();
order.next();    // 创建 → 已支付
order.next();    // 已支付 → 已发货
order.cancel();  // 已发货，无法取消
```

#### 状态机框架推荐

- **Spring Statemachine**：企业级状态机，支持嵌套状态、并行状态、持久化。
- **Squirrel-Foundation**：轻量级状态机库。
- **Cola-statemachine**（阿里）：基于 DSL 的轻量状态机。

### 4.7 状态模式的替代方案：状态表

当状态多、转换复杂时，可以用**状态表**代替继承体系：

```go
type Transition struct {
    From, Event, To string
    Action          func()
}

var transitions = []Transition{
    {"CREATED", "PAY",    "PAID",      func() { fmt.Println("支付成功") }},
    {"PAID",    "SHIP",   "SHIPPED",   func() { fmt.Println("已发货") }},
    {"SHIPPED", "DELIVER","DELIVERED", func() { fmt.Println("已签收") }},
}

func (o *Order) Fire(event string) {
    for _, t := range transitions {
        if t.From == o.state && t.Event == event {
            t.Action()
            o.state = t.To
            return
        }
    }
    fmt.Println("非法转换")
}
```

> 状态表把"状态机"从代码搬到数据，可配置化、可视化，复杂业务首选。

### 4.8 面试速答

- **Q：状态模式解决什么？** A：对象行为随内部状态变化时，把每种状态封装成独立类，消除 `if (state == X)` 分支。
- **Q：状态模式和策略模式区别？** A：策略由客户端选；状态由对象自身状态驱动自动切换，对客户端透明。
- **Q：状态模式缺点？** A：状态类数量膨胀；状态间转换逻辑分散在各个状态类中，难全局把握。
- **Q：订单状态机用什么实现？** A：简单用状态模式；复杂用状态机框架（Spring Statemachine / 状态表）。

## 五、模板方法模式（Template Method）

### 5.1 意图

定义算法骨架，把某些步骤延迟到子类实现。模板方法让子类在不改变算法结构的前提下重写特定步骤。

### 5.2 适用场景

- 算法骨架固定，但个别步骤可变。
- 框架的"钩子"机制（Spring `JdbcTemplate`、`RestTemplate`）。
- 复用代码：把公共流程抽到父类。

### 5.3 结构

```
   ┌──────────────────────┐
   │  AbstractClass       │
   ├──────────────────────┤
   │ + templateMethod()   │  ← final，定义骨架
   │ # step1()  abstract  │  ← 子类实现
   │ # step2()  abstract  │
   │ # hook()             │  ← 可选钩子（默认空实现）
   └──────────────────────┘
              │
              ▼
   ┌──────────────────────┐
   │  ConcreteClass       │
   ├──────────────────────┤
   │ # step1()            │  ← 实现细节
   │ # step2()            │
   └──────────────────────┘
```

### 5.4 难点：钩子方法

钩子（Hook）是模板方法的关键技巧：父类提供默认空实现，子类按需重写。这样子类可以"插手"算法流程而不破坏骨架。

### 5.5 Java 版

```java
public abstract class HttpRequestTemplate {

    // 模板方法：final 防止子类篡改骨架
    public final void execute(String url) {
        String conn = createConnection(url);
        Map<String, String> headers = buildHeaders();
        String body = doRequest(conn, headers);
        if (shouldLog()) {       // 钩子
            System.out.println("响应: " + body);
        }
        afterRequest(body);      // 钩子
    }

    // 抽象步骤：子类必须实现
    protected abstract String createConnection(String url);
    protected abstract String doRequest(String conn, Map<String, String> headers);

    // 可重写：默认 headers
    protected Map<String, String> buildHeaders() {
        return Map.of("User-Agent", "MyApp/1.0");
    }

    // 钩子：默认不记日志
    protected boolean shouldLog() { return false; }

    // 钩子：默认空实现
    protected void afterRequest(String body) { }
}

public class GetRequest extends HttpRequestTemplate {
    protected String createConnection(String url) { return "GET " + url; }
    protected String doRequest(String conn, Map<String, String> headers) {
        return "200 OK";
    }
    protected boolean shouldLog() { return true; }   // 重写钩子
}

public class PostRequest extends HttpRequestTemplate {
    protected String createConnection(String url) { return "POST " + url; }
    protected String doRequest(String conn, Map<String, String> headers) {
        return "201 Created";
    }
    protected void afterRequest(String body) {
        System.out.println("写入审计日志");
    }
}
```

> Spring 的 `JdbcTemplate`、`RestTemplate`、`TransactionTemplate` 都是模板方法：父类固定"获取连接 → 执行 → 关闭"骨架，子类只实现 `doInTransaction()` 等回调。

#### Java 8+ 函数式模板

```java
public class HttpTemplate {
    public void execute(String url,
                        Function<String, String> requestFn,
                        Consumer<String> afterHook) {
        String conn = "conn:" + url;
        Map<String, String> headers = Map.of("UA", "App");
        String body = requestFn.apply(conn);
        if (afterHook != null) afterHook.accept(body);
    }
}

// 使用
new HttpTemplate().execute("https://api.com",
    conn -> "GET " + conn,
    body -> System.out.println("log: " + body));
```

> Java 8 之后，函数式回调大量替代了模板方法中的抽象方法。骨架仍在，但不需要子类，传 Lambda 即可。

### 5.6 Go 版

Go 没有"继承"和"final 方法"，模板方法靠**组合 + 函数回调**实现。

#### 方式 1：用接口实现"骨架 + 步骤"

```go
type RequestStep interface {
    CreateConnection(url string) string
    DoRequest(conn string, headers map[string]string) string
    ShouldLog() bool
}

type Template struct{ step RequestStep }

func (t *Template) Execute(url string) {
    conn := t.step.CreateConnection(url)
    headers := map[string]string{"UA": "App"}
    body := t.step.DoRequest(conn, headers)
    if t.step.ShouldLog() {
        fmt.Println("响应:", body)
    }
}

// 具体实现
type GetRequest struct{}
func (GetRequest) CreateConnection(url string) string { return "GET " + url }
func (GetRequest) DoRequest(conn string, h map[string]string) string { return "200 OK" }
func (GetRequest) ShouldLog() bool { return true }

// 使用
(&Template{step: GetRequest{}}).Execute("https://api.com")
```

> 问题：Go 接口要求实现所有方法，钩子也得显式实现。可以用**嵌入默认实现结构体**缓解。

#### 方式 2：函数回调（Go 地道写法）

```go
type Template struct {
    createConn func(url string) string
    doRequest  func(conn string, headers map[string]string) string
    shouldLog  func() bool
    afterHook  func(body string)
}

func (t *Template) Execute(url string) {
    conn := t.createConn(url)
    headers := map[string]string{"UA": "App"}
    body := t.doRequest(conn, headers)
    if t.shouldLog != nil && t.shouldLog() {
        fmt.Println("响应:", body)
    }
    if t.afterHook != nil {
        t.afterHook(body)
    }
}

// 使用
(&Template{
    createConn: func(url string) string { return "GET " + url },
    doRequest:  func(conn string, h map[string]string) string { return "200 OK" },
    shouldLog:  func() bool { return true },
    afterHook:  func(body string) { fmt.Println("审计:", body) },
}).Execute("https://api.com")
```

> Go 实践：当"步骤"是单方法时，用函数回调远比接口灵活。模板方法的精髓是"骨架固定 + 步骤可替换"，函数回调完美对应。

### 5.7 钩子 vs 抽象方法

| 对比项 | 抽象方法 | 钩子方法 |
|--------|---------|---------|
| 是否必须实现 | 是 | 否，有默认实现 |
| 是否影响骨架 | 必须执行 | 可选执行 |
| 用途 | 算法的必要步骤 | 扩展点 / 监听点 |

### 5.8 面试速答

- **Q：模板方法解决什么？** A：固定算法骨架，把可变步骤延迟到子类，避免子类重复代码。
- **Q：钩子方法是什么？** A：父类提供默认空实现的方法，子类按需重写，作为扩展点。
- **Q：模板方法和策略模式区别？** A：模板方法用继承改局部步骤；策略用组合替换整个算法。
- **Q：Java 8 之后模板方法还流行吗？** A：骨架仍常见，但抽象步骤大量被 Lambda / 函数式接口替代。

## 六、命令模式（Command）

### 6.1 意图

把"请求"封装成对象，从而可以**参数化客户端、排队请求、记录日志、支持撤销/重做**。

### 6.2 适用场景

- GUI 操作（按钮点击 → 命令对象）。
- 事务系统（一组命令原子执行 / 回滚）。
- 任务队列（命令对象入队，工作线程出队执行）。
- 撤销 / 重做（命令对象保存反向操作）。
- 宏命令（一组命令组合执行）。

### 6.3 结构

```
   ┌────────┐ invokes ┌─────────┐ executes ┌─────────┐
   │ Client │────────▶│ Invoker │─────────▶│ Command │
   └────────┘         └─────────┘          └────┬────┘
        │                                        │
        │ creates                                │ delegates
        ▼                                        ▼
   ┌─────────┐                            ┌──────────┐
   │ Command │◀───────────────────────────│ Receiver │
   └─────────┘                            └──────────┘
```

### 6.4 难点：撤销（Undo）

命令对象除了 `execute()`，还要实现 `undo()`。常见做法是命令在执行前保存"备份状态"，撤销时恢复。

### 6.5 Java 版

```java
// 命令接口
public interface Command {
    void execute();
    void undo();
}

// Receiver：实际干活的
public class Light {
    public void on()  { System.out.println("灯亮"); }
    public void off() { System.out.println("灯灭"); }
}

// 具体命令：开灯
public class LightOnCommand implements Command {
    private final Light light;
    public LightOnCommand(Light light) { this.light = light; }
    public void execute() { light.on(); }
    public void undo()    { light.off(); }
}

// 具体命令：关灯
public class LightOffCommand implements Command {
    private final Light light;
    public LightOffCommand(Light light) { this.light = light; }
    public void execute() { light.off(); }
    public void undo()    { light.on(); }
}

// Invoker：遥控器
public class RemoteControl {
    private final Deque<Command> history = new ArrayDeque<>();

    public void press(Command cmd) {
        cmd.execute();
        history.push(cmd);
    }

    public void undo() {
        if (history.isEmpty()) return;
        history.pop().undo();
    }
}

// 使用
Light light = new Light();
RemoteControl remote = new RemoteControl();
remote.press(new LightOnCommand(light));   // 灯亮
remote.press(new LightOffCommand(light));  // 灯灭
remote.undo();   // 灯亮
remote.undo();   // 灯灭
```

#### 宏命令（组合命令）

```java
public class MacroCommand implements Command {
    private final List<Command> cmds;
    public MacroCommand(List<Command> cmds) { this.cmds = cmds; }
    public void execute() { cmds.forEach(Command::execute); }
    public void undo() {
        // 反向撤销
        for (int i = cmds.size() - 1; i >= 0; i--) cmds.get(i).undo();
    }
}
```

### 6.6 Go 版

```go
package command

type Command interface {
    Execute()
    Undo()
}

// Receiver
type Light struct{}
func (Light) On()  { fmt.Println("灯亮") }
func (Light) Off() { fmt.Println("灯灭") }

// Concrete Command
type LightOnCmd struct{ light *Light }
func (c LightOnCmd) Execute() { c.light.On() }
func (c LightOnCmd) Undo()    { c.light.Off() }

type LightOffCmd struct{ light *Light }
func (c LightOffCmd) Execute() { c.light.Off() }
func (c LightOffCmd) Undo()    { c.light.On() }

// Invoker
type RemoteControl struct{ history []Command }

func (r *RemoteControl) Press(c Command) {
    c.Execute()
    r.history = append(r.history, c)
}
func (r *RemoteControl) Undo() {
    if len(r.history) == 0 { return }
    cmd := r.history[len(r.history)-1]
    r.history = r.history[:len(r.history)-1]
    cmd.Undo()
}

// 使用
light := &Light{}
remote := &RemoteControl{}
remote.Press(LightOnCmd{light})
remote.Press(LightOffCmd{light})
remote.Undo()
remote.Undo()
```

当不需要 Undo 时，命令就是个函数：


### 6.7 应用案例

- **Runnable / Callable**：Java 线程池任务就是命令对象。
- **Spring 的 `TransactionTemplate`**：`execute` 接受 `TransactionCallback`，本质是命令模式。
- **CQRS**：命令（写）和查询（读）分离，命令对象是核心。

### 6.8 面试速答

- **Q：命令模式解决什么？** A：把请求封装成对象，实现调用者与接收者解耦，支持排队、日志、撤销。
- **Q：命令模式和策略模式区别？** A：策略关注"用哪种算法"；命令关注"封装请求 + 可撤销"。
- **Q：Runnable 是命令模式吗？** A：是，`Runnable` 是命令接口，`Thread` 是调用者，业务代码是接收者。
- **Q：如何实现撤销？** A：命令对象在 `execute()` 时保存状态，`undo()` 时恢复；宏命令反向撤销。

## 七、迭代器模式（Iterator）

### 7.1 意图

提供一种方法**顺序访问**聚合对象中的元素，而不暴露其内部表示。

### 7.2 适用场景

- 容器遍历（List、Tree、Graph）。
- 自定义集合需要多种遍历方式（前序 / 中序 / 后序）。
- 流式数据 / 懒加载遍历。

### 7.3 结构

```
   ┌──────────────┐  creates  ┌──────────────┐
   │  Aggregate   │──────────▶│   Iterator   │
   │ +iterator()  │           │ +hasNext()   │
   └──────────────┘           │ +next()      │
                              └──────────────┘
```

### 7.4 难点：fail-fast 与并发修改

Java `ArrayList` 的迭代器是 **fail-fast**：遍历期间被结构性修改（add/remove），下次 `next()` 抛 `ConcurrentModificationException`。靠 `modCount` 实现。

`CopyOnWriteArrayList` 的迭代器是 **fail-safe**：迭代时遍历的是创建时的快照，不抛异常，但也看不到最新修改。

### 7.5 Java 版

```java
// 自定义容器 + 迭代器
public class LinkedList<T> implements Iterable<T> {
    private static class Node<T> {
        T val; Node<T> next;
        Node(T v) { val = v; }
    }
    private Node<T> head;

    public void add(T v) {
        Node<T> n = new Node<>(v);
        if (head == null) head = n;
        else {
            Node<T> cur = head;
            while (cur.next != null) cur = cur.next;
            cur.next = n;
        }
    }

    @Override
    public Iterator<T> iterator() {
        return new Iterator<>() {
            private Node<T> cur = head;
            public boolean hasNext() { return cur != null; }
            public T next() {
                if (!hasNext()) throw new NoSuchElementException();
                T v = cur.val;
                cur = cur.next;
                return v;
            }
        };
    }
}

// 使用：foreach 语法糖
LinkedList<String> list = new LinkedList<>();
list.add("a"); list.add("b");
for (String s : list) {
    System.out.println(s);
}
```

> 实现 `Iterable` 即可用 `for-each`，这是 Java 迭代器模式的标准做法。

### 7.6 Go 版

Go 没有内建迭代器协议，但有约定俗成的"迭代器函数"模式。

#### 方式 1：返回 next 函数

```go
type Iterator[T any] func() (T, bool)

type List[T any] struct {
    head *node[T]
}
type node[T any] struct {
    val  T
    next *node[T]
}

func (l *List[T]) Iter() Iterator[T] {
    cur := l.head
    return func() (T, bool) {
        var zero T
        if cur == nil {
            return zero, false
        }
        v := cur.val
        cur = cur.next
        return v, true
    }
}

// 使用
next := list.Iter()
for {
    v, ok := next()
    if !ok { break }
    fmt.Println(v)
}
```

#### 方式 2：回调式迭代器（Go 1.23 之前的惯用法）

```go
func (l *List[T]) ForEach(fn func(T) bool) {
    for cur := l.head; cur != nil; cur = cur.next {
        if !fn(cur.val) { break }   // 返回 false 提前退出
    }
}

// 使用
list.ForEach(func(v string) bool {
    fmt.Println(v)
    return true   // 继续
})
```

#### 方式 3：Go 1.23+ range over func

Go 1.23 引入了 `range over function` 特性，让迭代器写法变得优雅：

```go
func (l *List[T]) All() func(func(T) bool) {
    return func(yield func(T) bool) {
        for cur := l.head; cur != nil; cur = cur.next {
            if !yield(cur.val) { return }
        }
    }
}

// 使用：和原生 range 一样
for v := range list.All() {
    fmt.Println(v)
    if v == "stop" { break }   // 提前退出
}
```

> Go 1.23 的 `range over func` 是迭代器模式的官方支持，写法简洁、支持 break、和语言原生集成。

### 7.7 面试速答

- **Q：迭代器解决什么？** A：统一遍历接口，不暴露聚合内部结构。
- **Q：fail-fast 和 fail-safe？** A：fail-fast 遍历期间被修改则抛异常（modCount 检查）；fail-safe 遍历快照，不抛异常但看不到最新修改。
- **Q：为什么 foreach 要求实现 Iterable？** A：foreach 是 Iterable.iterator() 的语法糖。
- **Q：Go 怎么实现迭代器？** A：Go 1.23+ 用 `range over func`；旧版本用回调函数或 next 函数闭包。

## 八、中介者模式（Mediator）

### 8.1 意图

用一个**中介对象**来封装一组对象之间的交互，使对象之间不需要显式相互引用，从而降低耦合。

### 8.2 适用场景

- GUI 系统：组件之间通过 Mediator 通信（如按钮点击禁用菜单）。
- 聊天室：用户之间通过聊天室中介通信。
- 机场塔台：飞机之间通过塔台协调起降。
- 事件总线 / Message Broker。

### 8.3 难点：中介者 vs 观察者

| 对比项 | 中介者 | 观察者 |
|--------|--------|--------|
| 通信方向 | 双向（同事 → 中介 → 同事） | 单向（Subject → Observer） |
| 解耦目标 | 同事之间互不知道 | Observer 不知道 Subject |
| 中枢 | Mediator 是显式中枢 | Subject 自身就是中枢 |
| 典型 | 聊天室、塔台 | 事件订阅 |

### 8.4 Java 版

```java
// 中介者接口
public interface ChatMediator {
    void sendMessage(User user, String msg);
    void register(User user);
}

// 同事基类
public abstract class User {
    protected ChatMediator mediator;
    protected String name;
    public User(ChatMediator m, String n) { mediator = m; name = n; }
    public abstract void send(String msg);
    public abstract void receive(String msg);
}

// 具体同事
public class ConcreteUser extends User {
    public ConcreteUser(ChatMediator m, String n) { super(m, n); }
    public void send(String msg) { mediator.sendMessage(this, msg); }
    public void receive(String msg) { System.out.println(name + " 收到: " + msg); }
}

// 具体中介者：聊天室
public class ChatRoom implements ChatMediator {
    private final List<User> users = new ArrayList<>();
    public void register(User u) { users.add(u); }
    public void sendMessage(User sender, String msg) {
        for (User u : users) {
            if (u != sender) u.receive(msg);   // 中介转发，同事之间不直接通信
        }
    }
}

// 使用
ChatMediator room = new ChatRoom();
User alice = new ConcreteUser(room, "Alice");
User bob   = new ConcreteUser(room, "Bob");
room.register(alice);
room.register(bob);
alice.send("Hi");   // Bob 收到: Hi
```

> 中介者模式的代价：Mediator 会变成"上帝对象"，所有交互逻辑堆在它身上。需要小心拆分。

### 8.5 Go 版

```go
package chat

type User struct {
    name    string
    mediator Mediator
}

func NewUser(name string, m Mediator) *User {
    u := &User{name: name, mediator: m}
    m.Register(u)
    return u
}

func (u *User) Send(msg string) { u.mediator.Send(u, msg) }
func (u *User) Receive(msg string) { fmt.Printf("%s 收到: %s\n", u.name, msg) }

type Mediator interface {
    Register(*User)
    Send(sender *User, msg string)
}

type ChatRoom struct{ users []*User }

func (r *ChatRoom) Register(u *User) { r.users = append(r.users, u) }
func (r *ChatRoom) Send(sender *User, msg string) {
    for _, u := range r.users {
        if u != sender {
            u.Receive(msg)
        }
    }
}

// 使用
room := &ChatRoom{}
alice := NewUser("Alice", room)
bob := NewUser("Bob", room)
alice.Send("Hi")
```

### 8.6 中介者 vs 事件总线

事件总线（Event Bus）是中介者模式的**解耦升级版**：同事连中介接口都不依赖，只依赖事件类型。

```java
// 事件总线：中介者的进一步解耦
public class EventBus {
    private final Map<Class<?>, List<Consumer<?>>> handlers = new HashMap<>();

    public <T> void subscribe(Class<T> eventType, Consumer<T> handler) {
        handlers.computeIfAbsent(eventType, k -> new ArrayList<>()).add(handler);
    }

    @SuppressWarnings("unchecked")
    public <T> void publish(T event) {
        List<Consumer<?>> hs = handlers.get(event.getClass());
        if (hs != null) {
            for (Consumer<?> h : hs) {
                ((Consumer<T>) h).accept(event);
            }
        }
    }
}
```

> Guava `EventBus`、Spring `ApplicationEventPublisher` 都是这种实现。

### 8.7 面试速答

- **Q：中介者模式解决什么？** A：把网状的对象交互改造成星型（所有交互通过中介），降低耦合。
- **Q：中介者和观察者区别？** A：观察者单向通知；中介者双向协调，是显式中枢。
- **Q：中介者模式缺点？** A：Mediator 容易变成上帝对象，自身难以维护。
- **Q：MVC 中 Controller 是中介者吗？** A：是，Controller 协调 Model 和 View 的交互，是中介者。

## 九、备忘录模式（Memento）

### 9.1 意图

在不破坏封装的前提下，捕获一个对象的**内部状态**，以便将来恢复。

### 9.2 适用场景

- 撤销 / 重做（编辑器、游戏存档）。
- 事务回滚。
- 状态快照（数据库 mvcc、虚拟机快照）。

### 9.3 结构

```
   ┌──────────────┐  creates  ┌──────────────┐  stores  ┌──────────────┐
   │  Originator  │──────────▶│   Memento    │─────────▶│  Caretaker   │
   │  - state     │           │  - state     │          │              │
   │  +restore()  │◀──────────│              │          │              │
   └──────────────┘  restores └──────────────┘          └──────────────┘
```

三个角色：
- **Originator**：被保存状态的对象。
- **Memento**：状态快照（不可变）。
- **Caretaker**：管理快照的栈 / 列表。

### 9.4 难点：封装性 vs 可恢复性

Memento 应该只让 Originator 访问其内部状态，对 Caretaker 是黑盒。Java 用**内部类 + 包级私有**实现；Go 用**非导出字段 + 同包访问**。

### 9.5 Java 版

```java
// Memento：不可变快照
public final class EditorMemento {
    private final String content;
    private final int cursor;

    EditorMemento(String content, int cursor) {
        this.content = content;
        this.cursor = cursor;
    }
    String getContent() { return content; }   // 包级私有
    int getCursor() { return cursor; }
}

// Originator
public class Editor {
    private String content = "";
    private int cursor = 0;

    public void type(String text) {
        content = content.substring(0, cursor) + text + content.substring(cursor);
        cursor += text.length();
    }

    public EditorMemento save() {
        return new EditorMemento(content, cursor);
    }

    public void restore(EditorMemento m) {
        this.content = m.getContent();
        this.cursor = m.getCursor();
    }

    public String toString() { return "content=" + content + ", cursor=" + cursor; }
}

// Caretaker：管理快照栈
public class History {
    private final Deque<EditorMemento> stack = new ArrayDeque<>();
    public void push(EditorMemento m) { stack.push(m); }
    public EditorMemento pop() { return stack.pop(); }
}

// 使用
Editor editor = new Editor();
History history = new History();

editor.type("Hello");
history.push(editor.save());

editor.type(" World");
history.push(editor.save());

editor.restore(history.pop());   // 回到 "Hello World"
editor.restore(history.pop());   // 回到 "Hello"
```

### 9.6 Go 版

Go 用非导出字段保证封装：Memento 的字段小写，Caretaker 拿不到，但同包的 Originator 可以。

```go
package editor

// Memento：字段非导出
type Memento struct {
    content string
    cursor  int
}

// Originator
type Editor struct {
    content string
    cursor  int
}

func (e *Editor) Type(text string) {
    e.content = e.content[:e.cursor] + text + e.content[e.cursor:]
    e.cursor += len(text)
}

func (e *Editor) Save() *Memento {
    return &Memento{content: e.content, cursor: e.cursor}
}

func (e *Editor) Restore(m *Memento) {
    e.content = m.content
    e.cursor = m.cursor
}

func (e *Editor) String() string {
    return fmt.Sprintf("content=%s, cursor=%d", e.content, e.cursor)
}

// Caretaker
type History struct{ stack []*Memento }

func (h *History) Push(m *Memento) { h.stack = append(h.stack, m) }
func (h *History) Pop() *Memento {
    if len(h.stack) == 0 { return nil }
    m := h.stack[len(h.stack)-1]
    h.stack = h.stack[:len(h.stack)-1]
    return m
}
```

> Go 的封装靠包边界：Memento 字段非导出，跨包的 Caretaker 无法读取，但同包的 Originator 可以自由访问。这是 Go 实现"友元"效果的标准做法。

### 9.7 备忘录 vs 命令的 Undo

- **命令的 Undo**：保存"反向操作"，按操作顺序撤销。
- **备忘录**：保存"完整状态快照"，按时间点回滚。

| 对比项 | 命令 Undo | 备忘录 |
|--------|-----------|--------|
| 存储内容 | 反向操作 | 完整状态 |
| 内存占用 | 小 | 大 |
| 适用 | 操作粒度小、可逆计算 | 状态复杂、需要快照回滚 |

### 9.8 面试速答

- **Q：备忘录模式解决什么？** A：不破坏封装的前提下保存对象状态，支持回滚。
- **Q：备忘录和命令模式 Undo 区别？** A：命令存反向操作；备忘录存状态快照。命令内存占用小，备忘录适用复杂状态。
- **Q：Java 如何保证 Memento 对 Caretaker 不可见？** A：Memento 字段包级私有，Caretaker 跨包访问不到。
- **Q：Go 如何实现"友元"封装？** A：Memento 字段非导出，靠包边界控制可见性。

## 十、访问者模式（Visitor）

### 10.1 意图

在不改变各元素类的前提下，定义作用于这些元素的**新操作**。

### 10.2 适用场景

- 需要对一个**稳定**的对象结构（如 AST、文件系统）频繁**新增操作**。
- 编译器对 AST 的多种 pass（类型检查、代码生成、优化）。
- 导出 / 序列化复杂对象结构。

### 10.3 难点：双重分派（Double Dispatch）

Java / Go 都是**单分派**语言：方法调用由"对象类型 + 方法名"决定，参数类型不影响。

访问者通过**两次方法分派**模拟双分派：
1. `element.accept(visitor)` —— 由 element 类型决定调用哪个 `accept` 重载。
2. `visitor.visit(this)` —— 由 visitor 类型决定调用哪个 `visit` 重载。

### 10.4 结构

```
   ┌──────────────┐  accept(v)   ┌──────────────┐  visit(e)
   │   Element    │─────────────▶│   Visitor    │◀────────────┐
   └──────┬───────┘              └──────┬───────┘             │
          │                             │                     │
   ┌──────┴───────┐             ┌──────┴───────┐              │
   │ ElementA     │ accept:     │ VisitorA     │ visitA(this)─┘
   │ ElementB     │ v.visit(this) VisitorB     │
   └──────────────┘             └──────────────┘
```

### 10.5 Java 版

```java
// Element 接口
public interface Shape {
    void accept(Visitor v);
}

public class Circle implements Shape {
    public double radius;
    public Circle(double r) { radius = r; }
    public void accept(Visitor v) { v.visit(this); }   // 关键：传 this，触发重载
}

public class Rectangle implements Shape {
    public double w, h;
    public Rectangle(double w, double h) { this.w = w; this.h = h; }
    public void accept(Visitor v) { v.visit(this); }
}

// Visitor 接口：每种 Element 对应一个 visit 重载
public interface Visitor {
    void visit(Circle c);
    void visit(Rectangle r);
}

// 具体访问者 1：计算面积
public class AreaVisitor implements Visitor {
    public double total = 0;
    public void visit(Circle c)    { total += Math.PI * c.radius * c.radius; }
    public void visit(Rectangle r) { total += r.w * r.h; }
}

// 具体访问者 2：导出 XML
public class XmlVisitor implements Visitor {
    public StringBuilder sb = new StringBuilder();
    public void visit(Circle c)    { sb.append("<circle r=\"").append(c.radius).append("\"/>\n"); }
    public void visit(Rectangle r) { sb.append("<rect w=\"").append(r.w).append("\" h=\"").append(r.h).append("\"/>\n"); }
}

// 使用：新增操作只加新 Visitor，不改 Shape 类
List<Shape> shapes = List.of(new Circle(2), new Rectangle(3, 4));

AreaVisitor area = new AreaVisitor();
for (Shape s : shapes) s.accept(area);
System.out.println("总面积: " + area.total);

XmlVisitor xml = new XmlVisitor();
for (Shape s : shapes) s.accept(xml);
System.out.println(xml.sb);
```

> 关键点：`s.accept(area)` 时，JVM 根据 `s` 的实际类型（Circle / Rectangle）选择对应的 `accept` 重载；进入 `accept` 后调用 `v.visit(this)`，`this` 是明确的 Circle/Rectangle 类型，再次触发重载。这就是**双重分派**。

### 10.6 Go 版

Go 没有方法重载，访问者模式实现起来比 Java 啰嗦，需要 type switch。

```go
package shape

// Element
type Shape interface {
    Accept(Visitor)
}

type Circle struct{ Radius float64 }
func (c Circle) Accept(v Visitor) { v.VisitCircle(c) }

type Rectangle struct{ W, H float64 }
func (r Rectangle) Accept(v Visitor) { v.VisitRectangle(r) }

// Visitor 接口：每种 Element 一个方法
type Visitor interface {
    VisitCircle(Circle)
    VisitRectangle(Rectangle)
}

// 具体访问者：面积
type AreaVisitor struct{ Total float64 }
func (a *AreaVisitor) VisitCircle(c Circle)    { a.Total += math.Pi * c.Radius * c.Radius }
func (a *AreaVisitor) VisitRectangle(r Rectangle) { a.Total += r.W * r.H }

// 具体访问者：XML
type XmlVisitor struct{ SB strings.Builder }
func (x *XmlVisitor) VisitCircle(c Circle) {
    fmt.Fprintf(&x.SB, "<circle r=\"%v\"/>\n", c.Radius)
}
func (x *XmlVisitor) VisitRectangle(r Rectangle) {
    fmt.Fprintf(&x.SB, "<rect w=\"%v\" h=\"%v\"/>\n", r.W, r.H)
}

// 使用
shapes := []Shape{Circle{Radius: 2}, Rectangle{W: 3, H: 4}}
area := &AreaVisitor{}
for _, s := range shapes { s.Accept(area) }
fmt.Println("总面积:", area.Total)
```

#### Go 简化版：type switch

当不需要"扩展 Element 类型"时，可以直接 type switch，省去 Accept 方法：

```go
type Visitor interface {
    Visit(s Shape)
}

func (a *AreaVisitor) Visit(s Shape) {
    switch v := s.(type) {
    case Circle:
        a.Total += math.Pi * v.Radius * v.Radius
    case Rectangle:
        a.Total += v.W * v.H
    }
}
```

> 这种写法牺牲了"扩展 Element 不改 Visitor"的优势，但代码更简单。当 Element 结构稳定时推荐。

### 10.7 访问者模式的"开闭方向"

访问者模式在**新增操作**时符合 OCP（加新 Visitor 即可），但**新增 Element 类型**时违反 OCP（要改所有 Visitor 接口和实现）。

```
现状：Circle、Rectangle + AreaVisitor、XmlVisitor
新增操作 DrawVisitor：✅ 只加新 Visitor
新增 Element Triangle：❌ 要改 Visitor 接口 + 所有 Visitor 实现
```

> 这与抽象工厂正好相反——抽象工厂扩展产品族 OCP，扩展产品类型违反 OCP。设计模式都有"开闭方向"，没有银弹。

### 10.8 面试速答

- **Q：访问者模式解决什么？** A：在不改 Element 类的前提下新增操作，适合 Element 稳定但操作频繁变化的场景。
- **Q：什么是双重分派？** A：accept 调 visit、visit 又调用具体类型方法，两次分派让"元素类型 × 操作类型"组合都被正确路由。
- **Q：访问者模式缺点？** A：新增 Element 类型要改所有 Visitor，违反 OCP；破坏封装（Visitor 需要访问 Element 内部）。
- **Q：什么时候用访问者？** A：编译器 AST 处理、文件系统遍历、稳定对象结构 + 多种操作。

## 十一、解释器模式（Interpreter）

### 11.1 意图

给定一个语言，定义它的文法的一种表示，并定义一个解释器，用来解释语言中的句子。

### 11.2 适用场景

- DSL（领域特定语言）：SQL 解析、正则表达式、规则引擎。
- 配置表达式：如 Spring SpEL、EL 表达式。
- 简单脚本语言。

### 11.3 难点：文法表示

通常用 **BNF** 表示文法，再为每条规则建一个类。复杂文法用解释器模式会类爆炸，实际工程更推荐**ANTLR / yacc**等工具生成解析器。

### 11.4 Java 版（简单算术表达式）

```java
// 抽象表达式
public interface Expression {
    int interpret(Map<String, Integer> ctx);
}

// 终结符表达式：变量
public class Variable implements Expression {
    private final String name;
    public Variable(String n) { name = n; }
    public int interpret(Map<String, Integer> ctx) {
        if (!ctx.containsKey(name)) throw new RuntimeException("未定义: " + name);
        return ctx.get(name);
    }
}

// 终结符表达式：常量
public class Constant implements Expression {
    private final int value;
    public Constant(int v) { value = v; }
    public int interpret(Map<String, Integer> ctx) { return value; }
}

// 非终结符表达式：加法
public class Add implements Expression {
    private final Expression left, right;
    public Add(Expression l, Expression r) { left = l; right = r; }
    public int interpret(Map<String, Integer> ctx) {
        return left.interpret(ctx) + right.interpret(ctx);
    }
}

// 非终结符表达式：乘法
public class Mul implements Expression {
    private final Expression left, right;
    public Mul(Expression l, Expression r) { left = l; right = r; }
    public int interpret(Map<String, Integer> ctx) {
        return left.interpret(ctx) * right.interpret(ctx);
    }
}

// 使用：(a + 3) * b
Expression expr = new Mul(new Add(new Variable("a"), new Constant(3)), new Variable("b"));
Map<String, Integer> ctx = Map.of("a", 2, "b", 4);
System.out.println(expr.interpret(ctx));   // (2+3)*4 = 20
```

> 现代 Java 中，解释器模式常被 Lambda + Function 替代：

```java
// 用函数式接口简化
interface Expr extends Function<Map<String, Integer>, Integer> {}

Expr var(String n)    { return ctx -> ctx.get(n); }
Expr constant(int v)  { return ctx -> v; }
Expr add(Expr a, Expr b) { return ctx -> a.apply(ctx) + b.apply(ctx); }
Expr mul(Expr a, Expr b) { return ctx -> a.apply(ctx) * b.apply(ctx); }

// 使用
Expr expr = mul(add(var("a"), constant(3)), var("b"));
System.out.println(expr.apply(Map.of("a", 2, "b", 4)));   // 20
```

### 11.5 Go 版

```go
package interp

type Context map[string]int

type Expression interface {
    Interpret(ctx Context) int
}

type Variable struct{ Name string }
func (v Variable) Interpret(ctx Context) int {
    val, ok := ctx[v.Name]
    if !ok { panic("未定义: " + v.Name) }
    return val
}

type Constant struct{ Value int }
func (c Constant) Interpret(_ Context) int { return c.Value }

type Add struct{ Left, Right Expression }
func (a Add) Interpret(ctx Context) int {
    return a.Left.Interpret(ctx) + a.Right.Interpret(ctx)
}

type Mul struct{ Left, Right Expression }
func (m Mul) Interpret(ctx Context) int {
    return m.Left.Interpret(ctx) * m.Right.Interpret(ctx)
}

// 使用：(a + 3) * b
expr := Mul{Add{Variable{"a"}, Constant{3}}, Variable{"b"}}
fmt.Println(expr.Interpret(Context{"a": 2, "b": 4}))   // 20
```

#### Go 函数式简化

```go
type Expr func(Context) int

func Var(name string) Expr     { return func(c Context) int { return c[name] } }
func Const(v int) Expr         { return func(_ Context) int { return v } }
func AddExpr(a, b Expr) Expr   { return func(c Context) int { return a(c) + b(c) } }
func MulExpr(a, b Expr) Expr   { return func(c Context) int { return a(c) * b(c) } }

// 使用
expr := MulExpr(AddExpr(Var("a"), Const(3)), Var("b"))
fmt.Println(expr(Context{"a": 2, "b": 4}))
```

### 11.6 工程实践

解释器模式在工程中**很少手写**，因为：

1. 文法复杂时类数量爆炸。
2. 性能差（递归解释）。
3. 错误恢复困难。

替代方案：

- **ANTLR**：根据文法文件生成解析器（Java/Go/Python 都支持）。
- **participle**（Go）：现代 Go 解析器生成器。
- **表达式引擎**：`govaluate`、`aviator`（Java）、`SpEL`。

### 11.7 面试速答

- **Q：解释器模式解决什么？** A：为简单 DSL 提供文法表示和解释执行。
- **Q：什么时候用解释器？** A：文法简单、变化不频繁、性能要求不高。
- **Q：解释器模式缺点？** A：复杂文法类爆炸；性能差；难以维护。工程上常用 ANTLR 替代。
- **Q：解释器和访问者关系？** A：解释器的"解释"操作常通过访问者模式实现，把不同节点类型的解释逻辑解耦。

需求：模拟一个 Web 框架，包含中间件链、状态管理、事件通知、策略路由。

### Java 版

```java
// === 责任链：中间件 ===
@FunctionalInterface
interface Filter {
    void doFilter(Request req, Response resp, FilterChain chain);
}
class FilterChain {
    private final List<Filter> filters;
    private int idx = 0;
    FilterChain(List<Filter> f) { filters = f; }
    void doFilter(Request req, Response resp) {
        if (idx < filters.size()) filters.get(idx++).doFilter(req, resp, this);
    }
}

// === 观察者：事件总线 ===
interface EventListener { void onEvent(Event e); }
class EventBus {
    private final Map<String, List<EventListener>> listeners = new HashMap<>();
    void subscribe(String topic, EventListener l) {
        listeners.computeIfAbsent(topic, k -> new ArrayList<>()).add(l);
    }
    void publish(String topic, Event e) {
        List<EventListener> ls = listeners.get(topic);
        if (ls != null) ls.forEach(l -> l.onEvent(e));
    }
}

// === 状态：请求生命周期 ===
interface RequestState {
    void handle(Request req, RequestContext ctx);
}
class ReceivedState implements RequestState {
    public void handle(Request req, RequestContext ctx) {
        ctx.publish("request.received", new Event(req));
        ctx.setState(new ProcessingState());
    }
}
class ProcessingState implements RequestState {
    public void handle(Request req, RequestContext ctx) {
        ctx.publish("request.processing", new Event(req));
        ctx.setState(new CompletedState());
    }
}
class CompletedState implements RequestState {
    public void handle(Request req, RequestContext ctx) {
        ctx.publish("request.completed", new Event(req));
    }
}

// === 策略：路由匹配 ===
interface RouteStrategy {
    Handler match(String path, Map<String, Handler> routes);
}
class ExactMatchStrategy implements RouteStrategy {
    public Handler match(String path, Map<String, Handler> routes) {
        return routes.get(path);
    }
}
class PrefixMatchStrategy implements RouteStrategy {
    public Handler match(String path, Map<String, Handler> routes) {
        for (var e : routes.entrySet()) {
            if (path.startsWith(e.getKey())) return e.getValue();
        }
        return null;
    }
}

// === 上下文 ===
class RequestContext {
    private RequestState state;
    private final EventBus bus;
    RequestContext(EventBus bus) { this.bus = bus; this.state = new ReceivedState(); }
    void setState(RequestState s) { this.state = s; }
    void publish(String topic, Event e) { bus.publish(topic, e); }
    void run(Request req) {
        state.handle(req, this);
        state.handle(req, this);
        state.handle(req, this);
    }
}

// === 主程序 ===
public class WebFramework {
    public static void main(String[] args) {
        EventBus bus = new EventBus();
        bus.subscribe("request.received", e -> System.out.println("[日志] 收到请求"));
        bus.subscribe("request.completed", e -> System.out.println("[日志] 请求完成"));

        List<Filter> filters = List.of(
            (req, resp, chain) -> { System.out.println("认证"); chain.doFilter(req, resp); },
            (req, resp, chain) -> { System.out.println("限流"); chain.doFilter(req, resp); }
        );

        Map<String, Handler> routes = new HashMap<>();
        routes.put("/hello", req -> System.out.println("hello"));

        RouteStrategy strategy = new ExactMatchStrategy();

        Request req = new Request("/hello");
        Response resp = new Response();

        new FilterChain(filters).doFilter(req, resp);
        Handler h = strategy.match(req.getPath(), routes);
        if (h != null) h.handle(req);

        new RequestContext(bus).run(req);
    }
}
```

### Go 版

```go
package webfw

// === 责任链：中间件 ===
type HandlerFunc func(req *Request)
type Middleware func(HandlerFunc) HandlerFunc

func Chain(h HandlerFunc, mws ...Middleware) HandlerFunc {
    for i := len(mws) - 1; i >= 0; i-- {
        h = mws[i](h)
    }
    return h
}

func AuthMW(next HandlerFunc) HandlerFunc {
    return func(req *Request) { fmt.Println("认证"); next(req) }
}
func RateLimitMW(next HandlerFunc) HandlerFunc {
    return func(req *Request) { fmt.Println("限流"); next(req) }
}

// === 观察者：事件总线 ===
type EventBus struct {
    listeners map[string][]func(Event)
    mu        sync.RWMutex
}

func NewEventBus() *EventBus {
    return &EventBus{listeners: make(map[string][]func(Event))}
}
func (b *EventBus) Subscribe(topic string, fn func(Event)) {
    b.mu.Lock()
    defer b.mu.Unlock()
    b.listeners[topic] = append(b.listeners[topic], fn)
}
func (b *EventBus) Publish(topic string, e Event) {
    b.mu.RLock()
    defer b.mu.RUnlock()
    for _, fn := range b.listeners[topic] { fn(e) }
}

// === 状态：请求生命周期 ===
type State interface {
    Handle(req *Request, ctx *RequestContext)
}

type ReceivedState struct{}
func (ReceivedState) Handle(req *Request, ctx *RequestContext) {
    ctx.Publish("request.received", Event{Req: req})
    ctx.SetState(ProcessingState{})
}

type ProcessingState struct{}
func (ProcessingState) Handle(req *Request, ctx *RequestContext) {
    ctx.Publish("request.processing", Event{Req: req})
    ctx.SetState(CompletedState{})
}

type CompletedState struct{}
func (CompletedState) Handle(req *Request, ctx *RequestContext) {
    ctx.Publish("request.completed", Event{Req: req})
}

// === 策略：路由匹配 ===
type RouteStrategy interface {
    Match(path string, routes map[string]HandlerFunc) HandlerFunc
}

type ExactMatch struct{}
func (ExactMatch) Match(path string, routes map[string]HandlerFunc) HandlerFunc {
    return routes[path]
}

type PrefixMatch struct{}
func (PrefixMatch) Match(path string, routes map[string]HandlerFunc) HandlerFunc {
    for prefix, h := range routes {
        if strings.HasPrefix(path, prefix) { return h }
    }
    return nil
}

// === 上下文 ===
type RequestContext struct {
    state State
    bus   *EventBus
}

func NewRequestContext(bus *EventBus) *RequestContext {
    return &RequestContext{state: ReceivedState{}, bus: bus}
}
func (c *RequestContext) SetState(s State)      { c.state = s }
func (c *RequestContext) Publish(t string, e Event) { c.bus.Publish(t, e) }
func (c *RequestContext) Run(req *Request) {
    c.state.Handle(req, c)
    c.state.Handle(req, c)
    c.state.Handle(req, c)
}

// === 主程序 ===
func ExampleRun() {
    bus := NewEventBus()
    bus.Subscribe("request.received", func(e Event) { fmt.Println("[日志] 收到请求") })
    bus.Subscribe("request.completed", func(e Event) { fmt.Println("[日志] 请求完成") })

    routes := map[string]HandlerFunc{
        "/hello": func(req *Request) { fmt.Println("hello") },
    }

    strategy := ExactMatch{}
    handler := strategy.Match("/hello", routes)

    final := Chain(handler, AuthMW, RateLimitMW)
    final(&Request{Path: "/hello"})

    NewRequestContext(bus).Run(&Request{Path: "/hello"})
}
```

## 十五、速记要点

| 要点 | 记忆 |
|------|------|
| 行为型关注点 | 对象之间的职责分配与交互 |
| 策略 | 算法可互换，消除 if/else |
| 观察者 | 一对多通知，注意内存泄漏 |
| 责任链 | 链式传递，Go 用中间件函数 |
| 状态 | 行为随状态变，状态自己决定下一步 |
| 模板方法 | 骨架固定 + 钩子扩展 |
| 命令 | 请求封装为对象，支持撤销 |
| 迭代器 | 统一遍历接口，Go 1.23 用 range over func |
| 中介者 | 多对象协调中枢，避免上帝对象 |
| 备忘录 | 状态快照 + 回滚 |
| 访问者 | 双重分派，新增操作不改 Element |
| 解释器 | DSL 文法解释，工程上常用 ANTLR 替代 |
| Java 推荐 | 函数式接口替代策略/命令/模板方法，Spring 生态广泛使用 |
