## 设计模式 —— 结构型模式（Structural Patterns）

结构型模式关注**对象如何组合**：把类或对象组合成更大的结构，同时保持结构的灵活与高效。

涉及七种模式：**适配器（Adapter）、桥接（Bridge）、组合（Composite）、装饰器（Decorator）、外观（Facade）、享元（Flyweight）、代理（Proxy）**。

> 面试主线：意图 → 结构 → 与相邻模式区别 → 实战案例 → 难点。每节末尾"面试速答"是高密度考点。

---

## 一、适配器模式（Adapter）

### 1.1 意图

将一个类的接口**转换**为客户期望的另一个接口，使原本接口不兼容的类可以一起工作。

### 1.2 类比

- 电源适配器：国标插座 ←转换→ 美标插头。
- 读卡器：SD 卡 ←转换→ USB 接口。

### 1.3 适用场景

- 复用已有类，但接口与系统期望的不一致。
- 想统一多个第三方 SDK 的调用方式（如多支付渠道）。
- 不能修改被适配类（旧系统、第三方库）。

### 1.4 结构（两种形态）

```
【对象适配器（推荐，用组合）】

   ┌──────────────┐  uses   ┌──────────────┐
   │   Target     │◀────────│   Adapter    │
   │  (期望接口)   │         └──────┬───────┘
   └──────────────┘                │ has-a
                                   ▼
                            ┌──────────────┐
                            │  Adaptee     │
                            │ (被适配类)    │
                            └──────────────┘

【类适配器（用继承，Java 单继承限制下少用）】

   Adapter ──extends──▶ Adaptee
          ──implements─▶ Target
```

### 1.5 Java 版（对象适配器）

```java
// 系统期望的统一接口
public interface PayTarget {
    void pay(long cents);
}

// 第三方 SDK（接口不兼容）
public class WechatSDK {
    public void doPay(String yuan) {
        System.out.println("Wechat pay: " + yuan + " yuan");
    }
}

// 适配器：把 cents → yuan，把 pay → doPay
public class WechatAdapter implements PayTarget {
    private final WechatSDK sdk;

    public WechatAdapter(WechatSDK sdk) { this.sdk = sdk; }

    @Override
    public void pay(long cents) {
        String yuan = String.valueOf(cents / 100.0);
        sdk.doPay(yuan);   // 转换 + 委托
    }
}

// 客户端只认 PayTarget
public class App {
    public static void main(String[] args) {
        PayTarget pay = new WechatAdapter(new WechatSDK());
        pay.pay(19999);   // 199.99 元
    }
}
```

### 1.6 Go 版

Go 用**嵌入字段 + 实现接口**做对象适配器。

```go
package pay

// 期望接口
type PayTarget interface {
    Pay(cents int64)
}

// 第三方 SDK
type WechatSDK struct{}
func (WechatSDK) DoPay(yuan string) { fmt.Println("Wechat pay:", yuan, "yuan") }

// 适配器
type WechatAdapter struct {
    sdk WechatSDK
}

func NewWechatAdapter(sdk WechatSDK) *WechatAdapter {
    return &WechatAdapter{sdk: sdk}
}

func (a *WechatAdapter) Pay(cents int64) {
    yuan := fmt.Sprintf("%.2f", float64(cents)/100.0)
    a.sdk.DoPay(yuan)
}

// 使用
func Example() {
    var p PayTarget = NewWechatAdapter(WechatSDK{})
    p.Pay(19999)
}
```

### 1.7 适配器 vs 装饰器 vs 代理

| 模式 | 接口关系 | 意图 |
|------|---------|------|
| 适配器 | **改变**接口 | 让不兼容的东西能协作 |
| 装饰器 | **保持**接口 | 增强功能，不改接口 |
| 代理 | **保持**接口 | 控制访问，常带间接性 |

### 1.8 面试速答

- **Q：适配器解决什么问题？** A：让接口不兼容的类协作，常用于复用遗留代码 / 统一第三方 SDK。
- **Q：类适配器和对象适配器区别？** A：类适配器用继承（受单继承限制），对象适配器用组合（推荐）。
- **Q：适配器和装饰器的本质区别？** A：适配器改接口，装饰器不改接口只加功能。

## 二、桥接模式（Bridge）

### 2.1 意图

将**抽象部分**与它的**实现部分**分离，使二者都可以独立变化。

### 2.2 适用场景

- 两个维度同时变化，用继承会导致类爆炸。
- 跨平台（Windows/Linux/Mac）× 多功能（图形/音频/网络）。
- 颜色 × 形状、消息类型 × 发送通道、ORM × 数据库方言。

### 2.3 难点：识别"两个独立变化的维度"

```
反例（继承）：3 形状 × 3 颜色 = 9 个子类
   Shape
   ├── RedCircle
   ├── BlueCircle
   ├── GreenCircle
   ├── RedSquare
   ├── ... (9 个)

正例（桥接）：Shape 持有 Color，各 3 个类
   Shape ──has-a──▶ Color
   ├── Circle              ├── Red
   ├── Square              ├── Blue
   └── Triangle            └── Green
```

### 2.4 结构

```
   ┌──────────────┐  implements   ┌──────────────┐
   │ Abstraction  │──────────────▶│ Implementor  │
   │ (抽象)       │               │ (实现接口)    │
   └──────┬───────┘               └──────┬───────┘
          │ has-a                        │
          ▼                              ▼
   ┌──────────────┐               ┌──────────────┐
   │RefinedAbstrac│               │ ConcreteImpl │
   └──────────────┘               └──────────────┘
```

### 2.5 Java 版

```java
// 实现维度：颜色
public interface Color {
    String apply();
}
public class Red  implements Color { public String apply() { return "red"; } }
public class Blue implements Color { public String apply() { return "blue"; } }

// 抽象维度：形状，持有 Color 引用（桥）
public abstract class Shape {
    protected Color color;   // 桥接点
    public Shape(Color c) { this.color = c; }
    public abstract void draw();
}

public class Circle extends Shape {
    public Circle(Color c) { super(c); }
    public void draw() { System.out.println("draw circle in " + color.apply()); }
}
public class Square extends Shape {
    public Square(Color c) { super(c); }
    public void draw() { System.out.println("draw square in " + color.apply()); }
}

// 客户端：两个维度独立扩展
Shape s1 = new Circle(new Red());
Shape s2 = new Square(new Blue());
s1.draw();   // draw circle in red
s2.draw();   // draw square in blue
// 新增颜色 Green：只加一个类；新增形状 Triangle：只加一个类
```

### 2.6 Go 版

```go
package shape

type Color interface { Apply() string }
type Red struct{}
func (Red) Apply() string { return "red" }
type Blue struct{}
func (Blue) Apply() string { return "blue" }

type Shape interface { Draw() }

type Circle struct{ Color Color }
func (c Circle) Draw() { fmt.Println("draw circle in", c.Color.Apply()) }

type Square struct{ Color Color }
func (s Square) Draw() { fmt.Println("draw square in", s.Color.Apply()) }

// 使用
func Example() {
    var s1 Shape = Circle{Color: Red{}}
    var s2 Shape = Square{Color: Blue{}}
    s1.Draw(); s2.Draw()
}
```

### 2.7 面试速答

- **Q：桥接模式是什么？** A：把"抽象"和"实现"两个独立变化维度分离，用组合代替继承。
- **Q：什么时候用桥接？** A：发现类爆炸且沿两个维度时（如平台 × 功能）。
- **Q：桥接和策略模式区别？** A：桥接是结构型，关注两个维度都独立扩展；策略是行为型，关注一个算法维度的可替换。

## 三、组合模式（Composite）

### 3.1 意图

将对象组合成**树形结构**，使单个对象和组合对象的使用具有一致性。客户端可以统一对待叶子节点和树枝节点。

### 3.2 适用场景

- 树形层级：文件系统（文件 + 文件夹）、UI 控件树、组织架构、菜单。
- 希望客户端忽略组合对象与单个对象的差别。

### 3.3 结构

```
           ┌──────────────┐
           │ Component    │ (统一接口)
           │ + operation()│
           │ + add()      │
           │ + remove()   │
           └──────┬───────┘
                  │
        ┌─────────┴─────────┐
        ▼                    ▼
   ┌─────────┐         ┌──────────────┐
   │  Leaf   │         │   Composite  │
   │ (叶子)   │         │ children[]   │
   └─────────┘         └──────┬───────┘
                              │ has-a (0..n Component)
                              ▼
                         [Component, Component, ...]
```

### 3.4 Java 版

```java
public interface FileSystemNode {
    void display(int indent);
}

// 叶子：文件
public class File implements FileSystemNode {
    private final String name;
    public File(String name) { this.name = name; }
    public void display(int indent) {
        System.out.println(" ".repeat(indent) + "- " + name);
    }
}

// 组合：文件夹
public class Directory implements FileSystemNode {
    private final String name;
    private final List<FileSystemNode> children = new ArrayList<>();

    public Directory(String name) { this.name = name; }
    public Directory add(FileSystemNode node) {
        children.add(node);
        return this;
    }
    public void display(int indent) {
        System.out.println(" ".repeat(indent) + "+ " + name + "/");
        for (FileSystemNode c : children) c.display(indent + 2);
    }
}

// 客户端：叶子与组合用同一个接口
public class App {
    public static void main(String[] args) {
        Directory root = new Directory("root");
        root.add(new File("a.txt"));
        Directory sub = new Directory("sub");
        sub.add(new File("b.txt")).add(new File("c.txt"));
        root.add(sub);
        root.display(0);
    }
}
// 输出：
// + root/
//   - a.txt
//   + sub/
//     - b.txt
//     - c.txt
```

### 3.5 Go 版

```go
package fs

type Node interface {
    Display(indent int)
}

type File struct{ Name string }
func (f File) Display(indent int) {
    fmt.Println(strings.Repeat(" ", indent) + "- " + f.Name)
}

type Directory struct {
    Name     string
    Children []Node
}
func (d *Directory) Add(n Node) { d.Children = append(d.Children, n) }
func (d Directory) Display(indent int) {
    fmt.Println(strings.Repeat(" ", indent) + "+ " + d.Name + "/")
    for _, c := range d.Children {
        c.Display(indent + 2)
    }
}

// 使用
func Example() {
    root := &Directory{Name: "root"}
    root.Add(File{Name: "a.txt"})
    sub := &Directory{Name: "sub"}
    sub.Add(File{Name: "b.txt"})
    sub.Add(File{Name: "c.txt"})
    root.Add(sub)
    root.Display(0)
}
```

### 3.6 透明 vs 安全组合

| 形态 | add/remove 放哪 | 优点 | 缺点 |
|------|----------------|------|------|
| 透明模式 | Component 接口里 | 客户端无需区分类型 | 叶子被迫实现无意义方法 |
| 安全模式 | Composite 自己 | 叶子干净 | 客户端要类型判断才能 add |

Java 上面的例子是**安全模式**（add 只在 Directory）。如果要在 Component 里声明 add，叶子要抛 `UnsupportedOperationException`，就是**透明模式**。

### 3.7 面试速答

- **Q：组合模式解决什么问题？** A：统一处理树形结构中的叶子和容器。
- **Q：透明和安全模式区别？** A：透明把 add 放接口（叶子要抛异常），安全把 add 放 Composite（客户端需类型判断）。
- **Q：哪里见过组合模式？** A：文件系统、UI 控件树、MyBatis SqlNode、AST。

## 四、装饰器模式（Decorator）

### 4.1 意图

**动态**地给一个对象添加额外职责，比生成子类（继承）更灵活。

### 4.2 与继承的对比

- 继承：编译期决定、静态、强耦合、类爆炸。
- 装饰器：运行时组合、可叠加、松耦合、按需装配。

### 4.3 结构

```
   ┌──────────────┐  implements   ┌──────────────┐
   │  Component   │◀──────────────│  Decorator   │
   │  (接口)       │               └──────┬───────┘
   └──────┬───────┘                      │ has-a
          │                              ▼
   ┌──────┴───────┐              ┌──────────────┐
   │ConcreteCompon│              │  Component   │ (被装饰对象)
   └──────────────┘              └──────────────┘
                                          ▲
                                 ┌────────┴────────┐
                                 │ ConcreteDecorator│ (加功能的子类)
                                 └─────────────────┘
```

### 4.4 Java 版：咖啡加料

```java
// 抽象组件
public interface Coffee {
    double cost();
    String desc();
}

// 具体组件
public class SimpleCoffee implements Coffee {
    public double cost() { return 10; }
    public String desc() { return "Coffee"; }
}

// 装饰器抽象（持有一个 Coffee）
public abstract class CoffeeDecorator implements Coffee {
    protected final Coffee inner;
    public CoffeeDecorator(Coffee inner) { this.inner = inner; }
}

// 具体装饰器1：加奶
public class Milk extends CoffeeDecorator {
    public Milk(Coffee inner) { super(inner); }
    public double cost() { return inner.cost() + 2; }
    public String desc() { return inner.desc() + " + Milk"; }
}

// 具体装饰器2：加糖
public class Sugar extends CoffeeDecorator {
    public Sugar(Coffee inner) { super(inner); }
    public double cost() { return inner.cost() + 1; }
    public String desc() { return inner.desc() + " + Sugar"; }
}

// 使用：可任意叠加
Coffee c = new Sugar(new Milk(new SimpleCoffee()));
System.out.println(c.desc() + " = " + c.cost());
// Coffee + Milk + Sugar = 13.0
```

### 4.5 Go 版

Go 没有"抽象类"概念，装饰器直接用**嵌入接口 + 实现同接口**实现。

```go
package coffee

type Coffee interface {
    Cost() float64
    Desc() string
}

type SimpleCoffee struct{}
func (SimpleCoffee) Cost() float64 { return 10 }
func (SimpleCoffee) Desc() string  { return "Coffee" }

// 装饰器：嵌入 Coffee 接口
type Milk struct{ Coffee Coffee }
func (m Milk) Cost() float64 { return m.Coffee.Cost() + 2 }
func (m Milk) Desc() string  { return m.Coffee.Desc() + " + Milk" }

type Sugar struct{ Coffee Coffee }
func (s Sugar) Cost() float64 { return s.Coffee.Cost() + 1 }
func (s Sugar) Desc() string  { return s.Coffee.Desc() + " + Sugar" }

// 使用
func Example() {
    var c Coffee = Sugar{Coffee: Milk{Coffee: SimpleCoffee{}}}
    fmt.Println(c.Desc(), "=", c.Cost())
}
```

### 4.6 Go 函数装饰器（轻量场景）

对于函数场景，Go 习惯用高阶函数做装饰器，比结构体装饰器简洁得多。

```go
// 装饰一个函数：加日志
type HandlerFunc func(req string) error

func WithLog(h HandlerFunc) HandlerFunc {
    return func(req string) error {
        start := time.Now()
        err := h(req)
        log.Printf("call took %v, err=%v", time.Since(start), err)
        return err
    }
}

func WithRetry(h HandlerFunc) HandlerFunc {
    return func(req string) error {
        for i := 0; i < 3; i++ {
            if err := h(req); err == nil { return nil }
        }
        return errors.New("retry exhausted")
    }
}

// 使用：叠加装饰
h := WithRetry(WithLog(myHandler))
h("request")
```

> Go 中 HTTP middleware（`func(http.Handler) http.Handler`）就是函数装饰器，标准库 `http.TimeoutHandler` 也是。

### 4.7 陷阱：装饰器套娃过度

```java
// 反例：10 层装饰器套娃，调试地狱
new A(new B(new C(new D(new E(new F(new G(new H(new I(new J(coffee))))))))));
```

装饰器层数应控制在 2-3 层以内。多层封装时考虑改用职责链或策略。

### 4.8 面试速答

- **Q：装饰器和继承的区别？** A：装饰器运行时动态组合，可叠加；继承编译期静态，类爆炸。
- **Q：装饰器和代理的区别？** A：装饰器强调"加功能"；代理强调"控制访问"。装饰器通常由客户端组装，代理通常对客户端透明。
- **Q：Java IO 哪些是装饰器？** A：`InputStream` 是组件，`FileInputStream` 是具体组件，`BufferedInputStream` / `DataInputStream` 是装饰器。
- **Q：Go 怎么写装饰器？** A：结构体嵌入接口，或用高阶函数（HTTP middleware 风格）。

## 五、外观模式（Facade）

### 5.1 意图

为子系统中的一组接口提供一个**统一的入口**，让子系统更易使用。

### 5.2 类比

- 一键启动按钮：背后涉及电控、燃油、点火多个子系统，用户只看到一个按钮。
- 客服热线：客户只拨一个号，背后转接多个部门。

### 5.3 适用场景

- 子系统复杂，调用方只关心高层流程。
- 想给老系统套个简单接口供新代码用。
- 微服务网关本质是外观模式。

### 5.4 结构

```
   ┌──────────┐  uses   ┌──────────────────────┐
   │  Client  │────────▶│       Facade         │  统一入口
   └──────────┘         └──┬─────┬─────┬───────┘
                           │     │     │
                           ▼     ▼     ▼
                       [SubA] [SubB] [SubC]  复杂子系统
```

### 5.5 Java 版

```java
// 复杂子系统
public class CPU { public void freeze() { System.out.println("CPU freeze"); }
                   public void execute() { System.out.println("CPU execute"); } }
public class Memory { public void load() { System.out.println("Memory load"); } }
public class Disk { public void read() { System.out.println("Disk read"); } }

// 外观：一键启动
public class ComputerFacade {
    private final CPU cpu = new CPU();
    private final Memory memory = new Memory();
    private final Disk disk = new Disk();

    public void start() {
        cpu.freeze();
        memory.load();
        disk.read();
        cpu.execute();
    }
}

// 客户端：不感知子系统细节
new ComputerFacade().start();
```

### 5.6 Go 版

```go
package computer

type CPU struct{}
func (CPU) Freeze()   { fmt.Println("CPU freeze") }
func (CPU) Execute()  { fmt.Println("CPU execute") }

type Memory struct{}
func (Memory) Load() { fmt.Println("Memory load") }

type Disk struct{}
func (Disk) Read() { fmt.Println("Disk read") }

// 外观
type Facade struct {
    cpu    CPU
    memory Memory
    disk   Disk
}

func NewFacade() *Facade { return &Facade{} }
func (f *Facade) Start() {
    f.cpu.Freeze()
    f.memory.Load()
    f.disk.Read()
    f.cpu.Execute()
}

// 使用
func Example() { NewFacade().Start() }
```

### 5.7 外观 vs 适配器

| 模式 | 意图 |
|------|------|
| 外观 | 为复杂子系统提供**简化入口**（new 接口） |
| 适配器 | 把**已有接口**转换为目标接口（改接口） |

外观通常面向"多个对象"做封装，适配器通常面向"一个对象"做转换。

### 5.8 面试速答

- **Q：外观模式解决什么问题？** A：复杂子系统的简化入口，降低调用方学习成本。
- **Q：外观破坏封装吗？** A：不破坏，子系统仍可被直接访问，外观只是提供一条捷径。
- **Q：外观和 API 网关关系？** A：网关是分布式系统的外观，聚合多个后端服务接口。
- **Q：外观和中介者区别？** A：外观是单向（Facade→子系统），中介者是双向多对多协作。

## 六、享元模式（Flyweight）

### 6.1 意图

通过**共享**细粒度对象，减少内存占用与对象创建开销。享元对象的内部状态不变，外部状态由调用方传入。

### 6.2 适用场景

- 大量相似对象（如棋盘上 1000 个棋子、文档中 1 万个字符）。
- 对象大部分状态可外部化。
- 对象池、缓存场景。

### 6.3 关键：内蕴状态 vs 外蕴状态

| 状态类型 | 存放位置 | 是否共享 | 是否可变 |
|---------|---------|---------|---------|
| 内蕴状态（Intrinsic） | 享元对象内部 | 共享 | 不可变 |
| 外蕴状态（Extrinsic） | 调用方传入 | 不共享 | 可变 |

例：围棋棋子
- 内蕴：颜色（黑/白）—— 共享，整盘只有 2 个享元对象。
- 外蕴：位置（x,y）—— 由调用方维护，每步变化。

### 6.4 结构

```
   ┌──────────────┐         ┌──────────────┐
   │  Flyweight   │◀────────│ FlyweightFactory │
   │ (共享对象)    │  共享池  │ + get(key)       │
   └──────────────┘         └──────────────┘
```

### 6.5 Java 版：围棋棋子

```java
// 享元：颜色（内蕴状态）
public class ChessPiece {
    private final String color;   // 不可变
    public ChessPiece(String color) { this.color = color; }
    public void display(int x, int y) {   // x,y 是外蕴状态
        System.out.println(color + " at (" + x + "," + y + ")");
    }
}

// 工厂：缓存享元
public class ChessFactory {
    private static final Map<String, ChessPiece> POOL = new HashMap<>();

    public static ChessPiece get(String color) {
        return POOL.computeIfAbsent(color, ChessPiece::new);
    }
}

// 客户端：1000 步只有 2 个 ChessPiece 实例
ChessPiece b1 = ChessFactory.get("black");
ChessPiece b2 = ChessFactory.get("black");
System.out.println(b1 == b2);   // true，共享同一实例
b1.display(3, 5);
```

### 6.6 Go 版

```go
package chess

type ChessPiece struct {
    Color string   // 不可变
}

func (c ChessPiece) Display(x, y int) {
    fmt.Printf("%s at (%d,%d)\n", c.Color, x, y)
}

type Factory struct {
    pool sync.Map
}

func (f *Factory) Get(color string) ChessPiece {
    if v, ok := f.pool.Load(color); ok {
        return v.(ChessPiece)
    }
    p := ChessPiece{Color: color}
    f.pool.Store(color, p)
    return p
}

// 使用
func Example() {
    f := &Factory{}
    b1 := f.Get("black")
    b2 := f.Get("black")
    fmt.Println(b1 == b2)   // true
}
```

### 6.7 享元 vs 单例 vs 对象池

| 模式 | 共享粒度 | 意图 |
|------|---------|------|
| 单例 | 全局唯一 | 全局唯一实例 |
| 享元 | 按内蕴状态分多类共享 | 减少相似对象内存 |
| 对象池 | 复用可变对象 | 减少创建/销毁开销（如 DB 连接池） |

### 6.8 面试速答

- **Q：享元是什么？** A：共享细粒度对象，分离内蕴（共享不变）与外蕴（外部传入）状态。
- **Q：Java 哪些地方用了享元？** A：`Integer` 缓存 `-128~127`、`String` 常量池、`Boolean.TRUE/FALSE`。
- **Q：享元和单例区别？** A：单例全局唯一；享元按 key 共享多个实例。
- **Q：享元和对象池区别？** A：享元对象不可变；对象池对象可变且独占使用。

## 七、代理模式（Proxy）

### 7.1 意图

为其他对象提供一个**代理**以控制对这个对象的访问。

### 7.2 适用场景

- 远程代理：RPC stub、gRPC client。
- 虚拟代理：延迟创建昂贵对象（如大图懒加载）。
- 保护代理：权限校验。
- 智能引用代理：引用计数、缓存、日志。

### 7.3 与装饰器的区别

| 对比项 | 代理 | 装饰器 |
|-------|------|--------|
| 关注点 | 控制访问 | 增强功能 |
| 客户端感知 | 通常不感知 | 通常主动组装 |
| 生命周期 | 代理常驻 | 装饰器按需创建 |
| 典型场景 | RPC / 权限 / 缓存 | 加日志 / 加校验 / 加流控 |

### 7.4 结构

```
   ┌──────────┐  uses   ┌──────────┐  delegates   ┌──────────────┐
   │  Client  │────────▶│  Proxy   │─────────────▶│ RealSubject  │
   └──────────┘         └──────────┘              └──────────────┘
                          implements                     implements
                                 ▼                              ▼
                          ┌──────────────────┐
                          │    Subject       │ (共同接口)
                          └──────────────────┘
```

### 7.5 Java 版：权限代理

```java
public interface UserService {
    void delete(long userId);
}

public class UserServiceImpl implements UserService {
    public void delete(long userId) {
        System.out.println("deleted user " + userId);
    }
}

// 代理：加权限校验
public class UserServiceProxy implements UserService {
    private final UserService target;
    private final String currentUserRole;

    public UserServiceProxy(UserService target, String role) {
        this.target = target;
        this.currentUserRole = role;
    }

    public void delete(long userId) {
        if (!"admin".equals(currentUserRole)) {
            throw new SecurityException("only admin can delete");
        }
        target.delete(userId);   // 委托给真实对象
    }
}

// 使用：客户端只认 UserService，不知道是代理
UserService svc = new UserServiceProxy(new UserServiceImpl(), "admin");
svc.delete(1L);
```

### 7.6 Java 动态代理（JDK Proxy）

手写代理每个类要写一个代理类，繁琐。Java 提供 JDK 动态代理（基于接口）和 CGLIB（基于继承）。

```java
// JDK 动态代理：任意接口 + InvocationHandler
UserService target = new UserServiceImpl();
UserService proxy = (UserService) Proxy.newProxyInstance(
        target.getClass().getClassLoader(),
        new Class[]{UserService.class},
        (p, method, args) -> {
            if (!"admin".equals(currentRole)) {
                throw new SecurityException("forbidden");
            }
            System.out.println("[before] " + method.getName());
            Object ret = method.invoke(target, args);
            System.out.println("[after] " + method.getName());
            return ret;
        }
);
proxy.delete(1L);
```

> Spring AOP 底层就是动态代理：接口用 JDK Proxy，类用 CGLIB。

### 7.7 Go 版

Go 没有运行时反射代理，但通过接口 + 结构体包装可以非常自然地实现代理，习惯上直接用装饰器风格的结构体嵌入。

```go
package user

type Service interface {
    Delete(userID int64)
}

type Impl struct{}
func (Impl) Delete(id int64) { fmt.Println("deleted user", id) }

// 代理：权限校验
type Proxy struct {
    target Service
    role   string
}

func NewProxy(target Service, role string) *Proxy {
    return &Proxy{target: target, role: role}
}

func (p *Proxy) Delete(id int64) {
    if p.role != "admin" {
        panic("only admin can delete")
    }
    p.target.Delete(id)
}

// 使用
func Example() {
    var svc Service = NewProxy(Impl{}, "admin")
    svc.Delete(1)
}
```

> Go 圈的"代理"和"装饰器"在代码结构上几乎相同，区别只在**意图**：控制访问 = 代理，增强功能 = 装饰器。grpc-go 的 client 就是远程代理的典型。

### 7.8 面试速答

- **Q：代理模式是什么？** A：为对象提供一个替身以控制访问（远程/虚拟/保护/智能引用）。
- **Q：代理和装饰器区别？** A：代理控制访问，装饰器增强功能；代理对客户端常透明，装饰器常由客户端主动组装。
- **Q：Spring AOP 用什么实现？** A：JDK 动态代理（接口）+ CGLIB（类）。
- **Q：Go 怎么做代理？** A：结构体嵌入接口 + 同接口实现，和装饰器结构相同，靠意图区分。

## 八、七种模式对比与选型

| 模式 | 解决的问题 | 关键词 |
|------|----------|--------|
| 适配器 | 接口不兼容 | 转换接口 |
| 桥接 | 两个维度独立变化 | 抽象 + 实现 分离 |
| 组合 | 树形结构统一处理 | 叶子 + 容器同接口 |
| 装饰器 | 动态加功能 | 套娃 + 同接口 |
| 外观 | 简化复杂子系统 | 一键入口 |
| 享元 | 大量相似对象省内存 | 共享内蕴状态 |
| 代理 | 控制对象访问 | 替身 + 控制 |

### 选型决策

```
        你想做什么？
       /      |      \
  接口转换   组合对象   控制访问
     │       /    \         │
  Adapter  单一   多个     Proxy
          接口   一致？
           │      │
       装饰器    组合
        │
   两个维度独立变化 → 桥接
   简化子系统入口 → 外观
   大量相似对象 → 享元
```

## 九、综合实战：日志系统用多种结构模式

需求：日志系统要支持多种存储（文件、DB），多种格式（JSON、Plain），且支持懒加载和缓存。

### Java 版（桥接 + 装饰器 + 代理 + 享元 + 外观）

```java
// === 桥接：Logger 抽象 × Storage 实现 ===
interface LogStorage {
    void write(String formatted);
}
class FileStorage implements LogStorage {
    public void write(String s) { System.out.println("[File] " + s); }
}
class DBStorage implements LogStorage {
    public void write(String s) { System.out.println("[DB] " + s); }
}

abstract class Logger {
    protected LogStorage storage;   // 桥
    public Logger(LogStorage s) { this.storage = s; }
    public abstract void log(String msg);
}
class PlainLogger extends Logger {
    public PlainLogger(LogStorage s) { super(s); }
    public void log(String msg) { storage.write(msg); }
}

// === 装饰器：加格式 ===
abstract class LoggerDecorator extends Logger {
    protected final Logger inner;
    public LoggerDecorator(Logger inner, LogStorage s) { super(s); this.inner = inner; }
}
class JsonDecorator extends LoggerDecorator {
    public JsonDecorator(Logger inner, LogStorage s) { super(inner, s); }
    public void log(String msg) {
        storage.write("{\"msg\":\"" + msg + "\"}");
    }
}

// === 代理：懒加载 + 缓存 ===
class LazyLoggerProxy implements Logger {   // 这里为简化直接实现接口
    private Logger real;
    private final Supplier<Logger> factory;
    public LazyLoggerProxy(Supplier<Logger> f) { this.factory = f; }
    public void log(String msg) {
        if (real == null) real = factory.get();   // 懒加载
        real.log(msg);
    }
}

// === 享元：日志级别对象复用 ===
class Level {
    private final String name;
    private Level(String n) { this.name = n; }
    private static final Map<String, Level> POOL = new HashMap<>();
    public static Level of(String n) { return POOL.computeIfAbsent(n, Level::new); }
}

// === 外观：一键拿一个全功能 Logger ===
class LogFacade {
    public static Logger fileJson() {
        return new LazyLoggerProxy(() ->
            new JsonDecorator(new PlainLogger(new FileStorage()), new FileStorage())
        );
    }
}

// 使用
LogFacade.fileJson().log("hello");
```

### Go 版（精简版：桥接 + 装饰器 + 代理）

```go
package log

// 桥接：Storage 接口
type Storage interface {
    Write(formatted string)
}

type FileStorage struct{}
func (FileStorage) Write(s string) { fmt.Println("[File]", s) }

type DBStorage struct{}
func (DBStorage) Write(s string) { fmt.Println("[DB]", s) }

// Logger 接口（既是抽象也是组件）
type Logger interface {
    Log(msg string)
}

// 基础实现
type PlainLogger struct{ Storage Storage }
func (p PlainLogger) Log(msg string) { p.Storage.Write(msg) }

// 装饰器：JSON 格式
type JsonDecorator struct{ Logger Logger }
func (d JsonDecorator) Log(msg string) {
    d.Logger.Log(fmt.Sprintf(`{"msg":%q}`, msg))
}

// 代理：懒加载
type LazyProxy struct {
    factory func() Logger
    real    Logger
    once    sync.Once
}
func (p *LazyProxy) Log(msg string) {
    p.once.Do(func() { p.real = p.factory() })
    p.real.Log(msg)
}

// 外观
func NewFileJsonLogger() Logger {
    return &LazyProxy{
        factory: func() Logger {
            return JsonDecorator{Logger: PlainLogger{Storage: FileStorage{}}}
        },
    }
}

// 使用
func Example() {
    l := NewFileJsonLogger()
    l.Log("hello")
}
```
