## 参考范式 —— 网络应用架构模式

网络应用架构模式描述的是**应用代码在客户端与服务端之间如何分布**的问题，与具体的分层架构（MVC / 分层）是正交关系。常见的有四种范式：单机版、C/S、B/S、P2P。

---

### 一、模式总览

| 范式 | 代码分布 | 典型代表 | 优点 | 缺点 |
|------|---------|---------|------|------|
| 单机版（Standalone） | 全部在本机 | 桌面记事本、单机游戏 | 零部署成本、离线可用 | 数据孤岛、难协作 |
| C/S（Client/Server） | 客户端 + 服务端，客户端需安装 | QQ、微信桌面、MySQL 客户端 | 性能好、交互流畅 | 安装升级麻烦、跨平台成本高 |
| B/S（Browser/Server） | 浏览器 + 服务端 | 各类 Web 应用、SaaS | 免安装、易升级、跨平台 | 受浏览器沙箱限制、实时性弱 |
| P2P（Peer-to-Peer） | 节点对等、无中心 | BitTorrent、区块链 | 去中心化、可扩展性强 | 治理难、数据一致性差 |

```
            ┌──────────────────────────────────────────────┐
            │            网络应用架构演进                    │
            └──────────────────────────────────────────────┘

   单机版 ──▶ C/S ──▶ B/S ──▶ P2P（并行存在，非完全替代）
   (本地)   (胖客户端)  (瘦客户端)  (无中心)
```

---

### 二、单机版（Standalone）

所有代码、数据、UI 都运行在用户本机一台设备上，不涉及网络通信。

```
   ┌─────────────────────────────┐
   │       本机进程               │
   │  ┌────────┐  ┌──────────┐  │
   │  │   UI   │──│ 业务逻辑  │  │
   │  └────────┘  └────┬─────┘  │
   │                    ▼        │
   │              ┌─────────┐   │
   │              │ 本地文件 │   │
   │              └─────────┘   │
   └─────────────────────────────┘
```

- 典型：VSCode（单机编辑部分）、单机游戏、Windows 计算器。
- 优点：无网络依赖、零部署成本、性能最优。
- 缺点：数据无法共享、升级需用户手动、难以多人协作。

---

### 三、C/S 模式（Client / Server）

客户端为"胖客户端"，承担一部分业务逻辑和 UI；服务端提供数据与核心服务。客户端需要安装到用户机器。

```
   ┌──────────────┐         ┌──────────────┐
   │   Client     │  TCP/UDP │   Server     │
   │ ┌──────────┐ │ ◀──────▶ │ ┌──────────┐ │
   │ │  UI 层   │ │  自定义  │ │ 业务逻辑  │ │
   │ │ 部分业务 │ │  协议    │ │ 数据存储  │ │
   │ └──────────┘ │         │ └──────────┘ │
   └──────────────┘         └──────────────┘
```

#### 1. 特点

- 客户端承担部分业务逻辑，减轻服务端压力。
- 使用自定义协议（TCP/UDP/二进制），性能优于 HTTP。
- 客户端需要安装，升级成本高（虽有热更新方案）。
- 跨平台成本高（Windows/Mac/Linux 各写一份）。

#### 2. 两层 C/S vs 三层 C/S

```
【两层 C/S】                          【三层 C/S】
   Client ──SQL──▶ DBMS                 Client ──▶ AppServer ──▶ DBMS
   客户端直接连数据库                    客户端通过应用服务器访问数据库
   安全性差、耦合高                      安全、可扩展、主流方案
```

> 老的 Delphi / VB 项目常是两层 C/S，客户端直接拼 SQL；现代 C/S（如游戏服务器、IM）都是三层结构。

#### 3. Go 伪代码：自定义协议的 C/S

```go
// server.go
package main

import (
    "encoding/binary"
    "net"
)

func handleConn(conn net.Conn) {
    defer conn.Close()
    var len uint16
    binary.Read(conn, binary.BigEndian, &len)
    buf := make([]byte, len)
    conn.Read(buf)
    // 处理业务 ...
    conn.Write([]byte("OK"))
}

func main() {
    ln, _ := net.Listen("tcp", ":9000")
    for {
        conn, _ := ln.Accept()
        go handleConn(conn)
    }
}

// client.go
func send(msg string) {
    conn, _ := net.Dial("tcp", "server:9000")
    defer conn.Close()
    binary.Write(conn, binary.BigEndian, uint16(len(msg)))
    conn.Write([]byte(msg))
}
```

#### 4. 典型代表

- 即时通讯：QQ、微信桌面版、Discord
- 游戏：所有 MMO 服务端
- 数据库：MySQL/PostgreSQL 客户端协议
- 远程工具：SSH、RDP

### 四、B/S 模式（Browser / Server）

客户端为"瘦客户端"（浏览器），只负责渲染；所有业务逻辑在服务端。通信协议为 HTTP/HTTPS。

```
   ┌──────────────┐         ┌──────────────┐
   │   Browser    │  HTTP(S)│   Server     │
   │ ┌──────────┐ │ ◀──────▶ │ ┌──────────┐ │
   │ │ HTML/JS  │ │ Request │ │ Web框架   │ │
   │ │  渲染    │ │ ──────▶ │ │ 业务逻辑  │ │
   │ │          │ │ Response│ │ 数据库    │ │
   │ └──────────┘ │ ◀────── │ └──────────┘ │
   └──────────────┘         └──────────────┘
   瘦客户端（仅渲染）          厚服务端（全部逻辑）
```

#### 1. 特点

- 客户端免安装，浏览器即用。
- 升级零成本：服务端发布即生效。
- 跨平台天然支持。
- 受浏览器沙箱限制：不能直接访问本地文件、硬件。
- 实时性弱于 C/S，需借助 WebSocket/SSE 补足。

#### 2. B/S 的演化阶段

```
   1. 静态网页时代     服务器返回纯 HTML，无交互
   2. CGI/JSP/PHP     服务端动态拼 HTML
   3. AJAX 时代        局部刷新、异步交互（Gmail）
   4. SPA 时代         前端框架 + REST API，前后端分离
   5. SSR + 同构       Next.js / Nuxt，兼顾 SEO 与体验
```

#### 3. B/S 本质是"特殊 C/S"

浏览器 = 特殊客户端，HTTP = 特殊协议，Web 服务器 = 特殊服务端。B/S 仍是 C/S 架构，只是把客户端标准化为浏览器。

#### 4. Python Flask 示例

```python
from flask import Flask, request, jsonify

app = Flask(__name__)

@app.route("/api/orders/<int:oid>", methods=["GET"])
def get_order(oid):
    order = {"id": oid, "amount": 99.5, "status": "PAID"}
    return jsonify(order)   # 浏览器拿 JSON 自行渲染

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=80)
```

#### 5. 典型代表

- 搜索引擎、电商、SaaS（GitHub、Notion Web）
- 企业内部管理系统（OA、CRM、ERP）
- 所有云原生应用

### 五、P2P 模式（Peer-to-Peer）

所有节点地位对等，既是客户端也是服务端，无中心服务器。节点之间直接通信。

```
        ┌────────┐
        │ Node A │◀────────┐
        └───┬────┘         │
            │              │
            ▼              ▼
        ┌────────┐     ┌────────┐
        │ Node C │◀───▶│ Node B │
        └────────┘     └────────┘
            ▲              ▲
            │              │
        ┌───┴────┘         │
        │ Node D │─────────┘
        └────────┘
        每个节点既是 Client 也是 Server
```

#### 1. 特点

- 去中心化：无单点故障，抗审查。
- 可扩展性强：节点越多总能力越强。
- 数据一致性难：无主节点，共识复杂。
- 安全与治理难：恶意节点、版权、合规问题。

#### 2. 纯 P2P vs 混合 P2P

```
【纯 P2P】              【混合 P2P（带索引服务器）】
  节点对等                  节点对等，但通过中心索引发现彼此
  发现难                    BT Tracker、Skype 超级节点
```

#### 3. Go 伪代码：简易 P2P 节点

```go
package main

import (
    "net"
    "net/rpc"
)

type Node struct {
    Peers []string
}

// 既是服务器，也是客户端
func (n *Node) Serve(port string) {
    rpc.Register(n)
    ln, _ := net.Listen("tcp", ":"+port)
    go rpc.Accept(ln)
}

// 调用其它节点
func (n *Node) Call(peer, method string, args interface{}) {
    client, _ := rpc.Dial("tcp", peer)
    client.Call(method, args, nil)
}
```

#### 4. 典型代表

- 文件共享：BitTorrent、eMule
- 区块链：Bitcoin、Ethereum
- 通信：Skype 早期、Tox
- 流媒体：WebRTC

### 六、四种范式对比

| 对比项 | 单机版 | C/S | B/S | P2P |
|--------|-------|-----|-----|-----|
| 客户端形态 | 无 | 胖客户端 | 瘦客户端（浏览器） | 对等节点 |
| 是否需安装 | 否 | 是 | 否 | 部分 |
| 升级方式 | 手动 | 客户端+服务端 | 仅服务端 | 协议升级 |
| 跨平台 | 易 | 难 | 天然支持 | 中 |
| 网络协议 | 无 | 自定义 | HTTP/HTTPS | 多样 |
| 实时性 | 最强 | 强 | 弱（需 WebSocket） | 强 |
| 数据共享 | 无 | 强 | 强 | 中 |
| 治理难度 | 易 | 中 | 中 | 难 |
| 典型场景 | 工具类 | IM/游戏 | Web 应用 | 文件/区块链 |

### 七、选型决策树

```
                    是否需要联网？
                   /            \
                  否              是
                  │               │
              单机版         是否有中心服务器？
                            /            \
                           是             否
                           │              │
                      客户端形态？         P2P
                      /        \
                  需安装？    不需安装？
                     │          │
                    C/S        B/S
```

实践提示：
- **面向大众消费者 + 跨平台 + 免安装** → B/S 优先
- **强交互 + 高性能 + 可安装**（游戏、IM、IDE） → C/S
- **去中心化 + 抗审查 + 节点协作** → P2P
- **离线工具类** → 单机版

### 八、混合架构（现代主流）

真实系统常是多种范式的组合：

```
   ┌──────────────────────────────────────────────┐
   │  混合架构示例：现代 IM 应用（如微信）          │
   ├──────────────────────────────────────────────┤
   │                                              │
   │  [Web 端]  ──B/S──▶  ┌──────────────┐        │
   │                       │ 接入网关层    │        │
   │  [桌面端] ──C/S──▶    │ (HTTP/WebSocket)│     │
   │                       └──────┬───────┘        │
   │  [手机端] ──C/S──▶           │                │
   │                              ▼                │
   │                       ┌──────────────┐        │
   │                       │ 业务服务集群  │        │
   │                       └──────┬───────┘        │
   │                              ▼                │
   │                       ┌──────────────┐        │
   │                       │ 存储与缓存    │        │
   │                       └──────────────┘        │
   │                                              │
   │  [文件传输] ──P2P──▶ 节点直连                  │
   └──────────────────────────────────────────────┘
```

- 客户端：Web（B/S）+ 桌面/手机（C/S）多端覆盖
- 服务端：分层架构 + 微服务
- 文件传输：节点间走 P2P 减轻服务器带宽

### 九、与分层架构、MVC 的关系

网络应用架构模式回答"**代码部署在哪**"，分层架构和 MVC 回答"**代码如何组织**"，二者正交。

```
              代码部署位置（网络范式）  ×  代码组织方式（结构范式）

              单机 / C/S / B/S / P2P      ×   分层 / MVC / 微服务

   例：B/S + 分层 + MVC = 典型 Spring Boot Web 应用
       C/S + 分层       = 典型游戏客户端 + 服务端
       P2P + 分层       = 区块链节点
```

任何一种网络范式内部，都可以采用分层架构组织代码，表现层都可以用 MVC 细化。

### 十、速记要点

| 要点 | 记忆 |
|------|------|
| 四种范式 | 单机、C/S、B/S、P2P |
| 单机 | 全本地，离线可用 |
| C/S | 胖客户端 + 自定义协议，性能强 |
| B/S | 瘦客户端 + HTTP，免安装易升级 |
| P2P | 节点对等，去中心化 |
| B/S 本质 | 标准化客户端（浏览器）的 C/S |
| 选型口诀 | 大众 Web、强交互 C/S、去中心 P2P、离线单机 |
| 现代趋势 | 多端混合，单一范式已少见 |
| 与分层关系 | 网络范式管部署，分层/MVC 管组织，二者正交 |
