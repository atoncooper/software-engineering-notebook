## 设计基本原则

> 架构基本原则是**模块级**的设计准则，关注"模块边界划得对不对"。它们比设计模式更底层、比 SOLID 更宏观——SOLID 管类内/类间关系，本原则管模块/子系统之间的关系。

涉及的原则：

- 高内聚低耦合（Cohesion / Coupling）—— 母原则
- 模块规模适中
- 单入单出（Single Entry Single Exit）
- 合适的宽度、深度、扇入、扇出
- 作用域 ⊆ 控制域
- 模块功能可预测
- **无环依赖原则**（ADP，Acyclic Dependencies Principle）
- **稳定依赖原则**（SDP，Stable Dependencies Principle）
- **稳定抽象原则**（SAP，Stable Abstractions Principle）
- **共同复用原则**（CRP，Common Reuse Principle）
- **共同闭包原则**（CCP，Common Closure Principle）
- **康威定律**（Conway's Law）

> 面试提示：高内聚低耦合、扇入扇出、作用域控制域是软考/中级岗位高频考点；ADP/SDP/SAP 是 Robert Martin 在《敏捷软件开发》提出的组件级原则，中高级面试加分项。

### 速览

- 高内聚低耦合作为基本原则
- 模块规模应该适中
- 单入单出 — 应用设计单入、单出的模块
- 架构应该具备合适的宽度、深度、扇入、和扇出
- 模块的作用域应该在控制域以内
- 模块功能可以预测

## 一、高内聚低耦合

**内聚（Cohesion）** 指的是一个模块内部各个元素（代码、函数、类）彼此结合的紧密程度。
**耦合（Coupling）** 指的是不同模块之间相互依赖、相互影响的程度。

这是最根本的原则，是其它原则（单入单出、扇入扇出等）的"母原则"。

### 1.1 内聚的级别

内聚从低到高一般分为以下几级（重点记住最高 3 级，前几级属于反模式）：

| 级别 | 名称 | 含义 |
|------|------|------|
| 低 | 偶然内聚 | 元素之间毫无关系，只是被放在一起 |
| 中 | 逻辑内聚 | 完成逻辑上相似的功能，由参数决定执行哪个 |
| 中 | 时间内聚 | 在同一时间段内执行（如 init 函数） |
| 高 | 通信内聚 | 操作同一数据集的多个功能 |
| 高 | 顺序内聚 | 前一个功能的输出是后一个的输入 |
| **最高** | **功能内聚** | **所有元素共同完成一个单一、明确的功能** |

**目标：追求功能内聚**。一个模块只做一件事，且所有元素都为这件事服务。

### 1.2 耦合的级别

耦合从低到高：

| 级别 | 名称 | 含义 |
|------|------|------|
| **低** | **非直接耦合** | 模块间无直接调用，通过主模块或事件交互 |
| **低** | **数据耦合** | 模块间仅通过参数传递简单数据 |
| 中 | 标记耦合 | 传递复杂的数据结构（如 struct） |
| 中 | 控制耦合 | 传递控制标志（如 flag、mode）来决定对方行为 |
| 高 | 公共耦合 | 共享全局变量、公共数据区 |
| **最高** | **内容耦合** | 一个模块直接访问另一模块的内部数据 / 代码 |

**目标：追求数据耦合，避免控制耦合及以上的强耦合**。

### 1.3 架构图对比

```
【低内聚高耦合（反模式）】                【高内聚低耦合（推荐）】

  ┌──────┐   ┌──────┐   ┌──────┐         ┌────────────┐
  │ Mod A │──▶│ Mod B │──▶│ Mod C │         │ OrderService│
  └──┬───┘   └──┬───┘   └──┬───┘         │  - Create() │
     │          │          │              │  - Pay()    │   ┌─────────┐
     └──────────┴──────────┘              │  - Ship()   │──▶│NotifySvc│
        互相直接访问内部状态                └────────────┘   └─────────┘
        共享全局变量                         仅通过接口/参数
```

### 1.4 Golang 伪代码示例

```go
// ❌ 反模式：低内聚（一个模块干三件事）+ 控制耦合（传 mode 控制）
func ProcessOrder(order Order, mode string) error {
    switch mode {
    case "create":
        // 创建订单逻辑
    case "pay":
        // 支付逻辑
    case "ship":
        // 发货逻辑
    }
    return nil
}

//  推荐：功能内聚 + 数据耦合
// 每个函数只做一件事，模块间仅通过参数（数据）交互
type OrderService struct {
    repo    OrderRepository  // 依赖接口，不依赖具体实现 —— 解耦的关键
    notify  Notifier
}

func (s *OrderService) Create(o Order) (OrderID, error) { /* ... */ }
func (s *OrderService) Pay(id OrderID) error            { /* ... */ }
func (s *OrderService) Ship(id OrderID) error           { /* ... */ }

type OrderRepository interface {
    Save(o Order) error
    Find(id OrderID) (Order, error)
}
```

## 二、单入单出

一个模块（或函数、方法）在执行时，**只有一个合法的进入点和一个合法的退出点**。

- **单入**：模块只能通过其公开的入口被调用，不能从中间跳入。
- **单出**：模块执行完毕后只能从一个出口返回，不能有多个 return / throw / goto 分散在各处。

### 2.1 微服务架构中的"单入单出"——网关收口

如果允许前端（App/Web）绕过网关，直接去调用后端的各个微服务，系统马上就会陷入混乱。将所有接口的访问权集中在网关这一个组件上（单入口），是为了解决以下核心痛点：

#### 统一鉴权与限流（防止漏做安全检查）

- **反面教材**：如果用户服务和订单服务都能被外部直接访问。某天安全升级，要求所有请求必须携带最新的 Token。由于接口分散在不同组件，你需要在用户服务写一遍验证逻辑，在订单服务也写一遍。只要有一个新来的开发人员漏写了，就会造成巨大的安全漏洞。
- **网关收口**：所有请求统一走网关。网关作为唯一的入口，**统一拦截、统一做身份认证（Authentication）、统一做流量控制**。后面的微服务甚至不需要关心用户是谁、Token 是真是假，因为"网关既然放它进来了，它就一定是合法的"。

#### 避免客户端维护复杂的逻辑

- **反面教材**：如果接口不集中，前端 App 需要记录：用户服务的 IP、订单服务的 IP、支付服务的 IP。一旦后端服务器换了域名或做了重构，前端 App 必须跟着发版更新，用户体验极差。
- **网关收口**：前端只认网关的地址（如 `https://api.company.com`）。网关内部通过路由表，把 `/user/*` 转发给用户服务，把 `/order/*` 转发给订单服务。后端组件怎么变，前端完全感知不到。

既然所有的请求都是从网关进来的，那么当后端微服务发生各种奇葩的错误时，异常也必须遵循"单出口"的原则——由网关进行统一的截获、包装和输出。

```
              【单入单出：网关收口】

   Client ──────▶ ┌──────────┐ ─────▶ /user/*  ──▶ UserService
   (App/Web)      │  Gateway │ ─────▶ /order/* ──▶ OrderService
                  │ (唯一入口)│ ─────▶ /pay/*   ──▶ PayService
                  └────┬─────┘
                       │ 统一鉴权 / 限流 / 日志 / 错误包装
                       ▼
                 【所有出口由网关统一返回】
```

### 2.2 函数级单入单出

```go
// ❌ 反例：多出口（散弹式 return），难以追踪资源释放
func checkStatus(code int) string {
    if code == 1 {
        return "active"      // 出口1
    } else if code == 2 {
        return "inactive"    // 出口2
    }
    return "unknown"         // 出口3
}

// ✅ 正例：单入单出 —— 入口唯一，出口唯一
func checkStatus(code int) string {
    var result string        // 用局部变量承载中间结果
    switch code {
    case 1:
        result = "active"
    case 2:
        result = "inactive"
    default:
        result = "unknown"
    }
    return result            // 唯一出口
}
```

### 2.3 Go 中 `defer` 是单出的天然盟友

```go
// 单入单出 + defer：资源释放逻辑只写一次，保证退出时执行
func ReadConfig(path string) (Config, error) {
    f, err := os.Open(path)
    if err != nil {
        return Config{}, err   // 注：错误提前返回是 Go 惯用法
    }
    defer f.Close()            // 无论走哪条路径，Close 都会执行

    var cfg Config
    decoder := json.NewDecoder(f)
    if err := decoder.Decode(&cfg); err != nil {
        return Config{}, err
    }
    return cfg, nil
}
```

> **实践提示**：现代语言（Go / Rust）中，"错误提前返回"是惯用法，严格意义的多出口已被业界接受。单入单出的核心精神是 **"主流程只有一个正常出口，错误用统一机制处理"**，而非机械地只写一个 return。

## 三、模块结构的度量指标：宽度、深度、扇入、扇出

这四个指标用来**量化**一个软件架构的"形状"是否健康。

### 3.1 结构图示意

```
                  ┌──────────┐
                  │ Module A │  ← 深度 = 1（顶层）
                  └────┬─────┘
            ┌──────────┼──────────┐       宽度（第2层）= 3
       ┌────▼───┐ ┌────▼───┐ ┌────▼───┐
       │ Mod B  │ │ Mod C  │ │ Mod D  │  ← 深度 = 2
       └────┬───┘ └────────┘ └────┬───┘
            │                      │
       ┌────▼───┐             ┌────▼───┐
       │ Mod E  │             │ Mod F  │     ← 深度 = 3
       └────────┘             └────────┘

  扇出 (Fan-out)：A 扇出 = 3（调用 B/C/D）
  扇入 (Fan-in)：E 扇入 = 1（只被 B 调用）
                 F 扇入 = 1（只被 D 调用）
```

### 3.2 四个指标定义

| 指标 | 定义 | 健康范围 |
|------|------|----------|
| **深度（Depth）** | 从顶层模块到最底层模块的层数 | 一般 ≤ 7 层；过深说明抽象堆叠过度 |
| **宽度（Width）** | 同一层次的模块总数 | 适中，避免某一层"爆炸" |
| **扇出（Fan-out）** | 一个模块直接调用的下级模块数 | 建议 ≤ 7；过大说明该模块职责过重 |
| **扇入（Fan-in）** | 一个模块被多少个上级模块调用 | **越大越好**，说明复用性高 |

### 3.3 经验法则

- **扇出过大**（>7）：模块做了"调度中心"的事，违反单一职责，应拆分或引入中间层。
- **扇入越大越好**：底层公共模块（工具函数、领域服务）应被多处复用。
- **深度过深**（>7）：调用链太长，可读性差、调试困难，通常说明中间层抽象不当。
- **顶层模块扇出大、底层模块扇入大**：这是健康的"金字塔"形态。

### 3.4 健康形态 vs 病态形态

```
【健康：金字塔形】                  【病态：倒三角 / 雪茄形】

       ┌──┐                              ┌──┐
       │A │ 扇出=3                        │A │ 扇出=1
       └┬─┘                              └┬─┘
     ┌──┼──┐                              ┌┼┐
     │B │C │D│ 扇出=2                     │B│ 扇出=1
     └┬─┘└─┘└┬                            └┬┘
       │     │                             ┌┼┐
       ▼     ▼                             │C│ 扇出=8 ← 过大！
     ┌──┐ ┌──┐                             └┬┘
     │E │ │F │ 扇入=3 (被多处复用)         ...深度=9 ← 过深！
     └──┘ └──┘
```

### 3.5 Golang 伪代码：扇出过大的拆分

```go
// ❌ 扇出过大：OrderHandler 直接依赖 8 个下游
type OrderHandler struct {
    userRepo    UserRepo
    orderRepo   OrderRepo
    stockRepo   StockRepo
    couponRepo  CouponRepo
    paySvc      PayService
    notifySvc   NotifyService
    auditSvc    AuditService
    logSvc      LogService
}
func (h *OrderHandler) PlaceOrder(o Order) error {
    // 调用 8 个下游 —— 调度逻辑全堆在这里
    return nil
}

// ✅ 引入中间聚合层，把扇出从 8 降到 2
type OrderHandler struct {
    orderService *OrderService  // 只扇出到 1 个领域服务
    audit        *AuditService  // +1 个横切关注点
}
type OrderService struct {
    userRepo   UserRepo
    orderRepo  OrderRepo
    stockRepo  StockRepo
    couponRepo CouponRepo
    paySvc     PayService
}
// 扇出从 Handler 的 8 降到 Service 的 5，层级清晰
```

## 四、作用域与控制域（Scope of Effect vs Scope of Control）

这是判断**模块划分是否合理**的重要准则，由 Constantine 提出。

### 4.1 定义

- **作用域（Scope of Effect / 影响域）**：一个模块的**判断语句（if/switch）所影响的全部模块**集合 —— 即这个判断结果会传导到哪些模块。
- **控制域（Scope of Control / 控制域）**：一个模块及其**所有下属模块**（直接或间接被它调用的模块）的集合。

### 4.2 核心准则

> **一个模块的作用域，必须是其控制域的子集。**
> 即：受某个判断影响的模块，必须在该模块的可控制范围（下属模块）之内。

违反此准则会导致：**上层模块不得不"知道"下层模块的内部判断结果，从而出现控制耦合和反向依赖**。

### 4.3 反例与正例图示

```
【违反准则：作用域 ⊄ 控制域】

              ┌──────┐
              │  A   │  ← A 里有判断 if(flag)
              └──┬───┘
          ┌──────┼──────┐
          ▼      ▼      ▼
        ┌──┐  ┌──┐  ┌──┐
        │ B │  │ C │  │ D │  ← A 的控制域 = {A, B, C, D}
        └──┘  └─┬┘  └──┘
                ▼
              ┌──┐
              │ E │   ← E 是 C 的下属，但 A 的判断 flag 影响到了 E
              └──┘     而 E 不在 A 的"直接"判断下，A 却通过参数传 flag 给 C 再传给 E
                       问题：A 必须知道 C 的内部细节（E 的存在）→ 控制耦合

【符合准则：把判断下推到 C 内部】

              ┌──────┐
              │  A   │  ← A 不再判断 flag
              └──┬───┘
          ┌──────┼──────┐
          ▼      ▼      ▼
        ┌──┐  ┌──┐  ┌──┐
        │ B │  │ C │  │ D │
        └──┘  └─┬┘  └──┘
                ▼
              ┌──┐
              │ E │   ← flag 的判断放在 C 里
              └──┘     C 的作用域 = {C, E}，控制域 = {C, E}，子集关系成立 ✓
```

### 4.4 Golang 伪代码

```go
// ❌ 违反：A 的判断影响到了下层 E，但 E 不受 A 直接控制
//         A 被迫把 mode 透传给 C，C 再传给 E —— 控制耦合 + 透传坏味道
func (a *ModuleA) DoSomething(mode string) {
    a.c.Do(mode)   // A 在判断模式，但实际行为发生在 E
}
func (c *ModuleC) Do(mode string) {
    c.e.Do(mode)   // 只做透传
}
func (e *ModuleE) Do(mode string) {
    if mode == "fast" { /* 快速路径 */ } else { /* 慢速路径 */ }
}

// ✅ 正确：把判断下放到真正执行的地方
func (a *ModuleA) DoSomething() {
    a.c.Do()        // A 不需要知道任何模式
}
func (c *ModuleC) Do() {
    c.e.Do()        // C 也不需要知道
}
func (e *ModuleE) Do() {
    if e.shouldFast() {   // 判断与行为同处一个模块
        e.fastPath()
    } else {
        e.slowPath()
    }
}
// 此时 E 的作用域 = 控制域 = {E}，判断与行为紧邻，符合准则
```

## 五、总结速记表

| 原则 | 一句话记忆 |
|------|-----------|
| 高内聚低耦合 | 内部抱团做一件事，外部只通过数据交谈 |
| 单入单出 | 一个门进、一个门出（架构层 = 网关；函数层 = 唯一 return） |
| 模块规模适中 | 函数 < 50 行，文件 < 800 行 |
| 深度 ≤ 7、宽度适中 | 调用链别太长，同层模块别爆炸 |
| 扇出 ≤ 7、扇入越大越好 | 上层少调度，底层多复用 |
| 作用域 ⊆ 控制域 | 谁判断谁负责执行，别让上层替下层操心 |

四者从不同角度共同回答同一个问题：**模块边界划得对不对**。

## 六、模块规模与可预测性

### 6.1 模块规模适中

模块（类、函数、包）过大或过小都是坏味道：

| 维度 | 经验阈值 | 超出意味着 |
|------|---------|-----------|
| 函数行数 | < 50 行 | 过长说明职责不清，应拆分 |
| 类行数 | < 800 行 | 上帝类，违反 SRP |
| 包内文件数 | 适中（10-30） | 过多应拆子包 |
| 圈复杂度 | < 10 | 过高说明分支太多，难测难维护 |
| 参数个数 | < 4 | 过多应封装为对象 |
| 嵌套深度 | < 4 层 | 过深用提前 return / 抽函数 |

> **圈复杂度**（Cyclomatic Complexity）：McCabe 提出，衡量线性独立路径数。`CC = 边数 - 节点数 + 2`，等价于 `if/for/while/case/&&/||` 数 + 1。CC 越高测试用例越多。

### 6.2 模块功能可预测

> **一个模块的输出应该可以从输入完全推断**——给定相同输入，得到相同输出和副作用。

**违反可预测性的常见形态**：

- 依赖全局状态（单例、全局变量、配置文件）。
- 隐式依赖时间（`new Date()`、`System.currentTimeMillis()`）。
- 隐式依赖随机数（`Math.random()`）。
- 隐式依赖网络 / DB / 外部服务（不通过依赖注入）。
- 副作用扩散（修改入参、写文件、发请求）。

```go
// ❌ 不可预测：依赖全局时间
func IsExpired(t time.Time) bool {
    return t.Before(time.Now())   // 调用时机不同结果不同
}

// ✅ 可预测：时间从外部注入
type Clock interface { Now() time.Time }
func IsExpired(t time.Time, now time.Time) bool {
    return t.Before(now)
}
```

> 可预测性是**可测试性**的前提——不可预测的模块无法写确定性测试。函数式编程强调"纯函数"本质就是追求可预测。

## 七、组件级原则（Robert Martin）

> Robert C. Martin 在《Agile Software Development》提出组件级六大原则，是高内聚低耦合在**包/模块/组件**层面的精细化。REP/CCP/CRP 是内聚原则，ADP/SDP/SAP 是耦合原则。

### 7.1 三组内聚原则（REP / CCP / CRP）

#### 7.1.1 复用发布等价原则（REP, Reuse-Release Equivalence）

> **可复用的单元必须同时是可发布的单元**。

一个包/组件要么整体复用、要么整体不复用，不能"复用其中一半"。如果两个类总是被不同项目分开复用，它们不应放在同一个包。

```
   ❌ 把 StringUtil 和 OrderService 放一个包
      → 复用 StringUtil 的人被迫引入 OrderService
   ✅ 分到 utils 包和 order 包
```

#### 7.1.2 共同闭包原则（CCP, Common Closure Principle）

> **一起变化的类放在同一个包**。

把因为同一业务原因需要修改的类聚到一起——这样一次需求变更只改一个包，而不是散落在多个包。这是**SRP 在包级别**的体现。

```
   修改"订单折扣规则"时，Order、DiscountPolicy、Coupon 都要改
   → 它们应该放一个包 order
```

#### 7.1.3 共同复用原则（CRP, Common Reuse Principle）

> **一起被复用的类放在同一个包**。

如果两个类总是被一起使用，放一起；如果只是偶尔一起用，分开。避免"为一个类引入整个包"。

> **CCP 和 CRP 的张力**：CCP 倾向"聚集"（一起改的放一起），CRP 倾向"分散"（不一起用的分开）。实际权衡：**把强相关（同时满足 CCP 和 CRP）的放一起**。

### 7.2 三组耦合原则（ADP / SDP / SAP）

#### 7.2.1 无环依赖原则（ADP, Acyclic Dependencies Principle）

> **组件依赖图必须是无环图（DAG）**。

```
   ❌ 循环依赖：A → B → C → A
      问题：A 改了影响 C，C 改了影响 A，无法独立编译/发布/测试

   ✅ 无环：用依赖倒置打破环
      A → B → C
      A ← Interface ← C  （C 依赖抽象，A 实现抽象）
```

**打破循环依赖的方法**：
1. **依赖倒置（DIP）**：引入接口，让双方依赖接口。
2. **新建中间组件**：把共同依赖的部分抽出来。
3. **观察者模式**：用事件解耦。

> Maven 的 `mvn dependency:tree`、Go 的循环导入检测都是 ADP 的工具化。Go 编译器直接拒绝循环导入——语言级强制 ADP。

#### 7.2.2 稳定依赖原则（SDP, Stable Dependencies Principle）

> **依赖方向必须指向稳定方向**。

"稳定"指"难于修改"——被很多组件依赖的组件稳定（改它影响大）；不依赖别人的组件稳定（不受别人变化影响）。

```
   ❌ 稳定组件依赖不稳定组件
      Stable (被10个组件依赖) → Unstable (依赖5个组件)
      Unstable 一变，Stable 被迫变 → 稳定性被破坏

   ✅ 不稳定组件依赖稳定组件
      Unstable → Stable
      Stable 不依赖任何人，可以稳定存在
```

**稳定性度量**（不稳定度 I）：

```
   I = 扇出 / (扇入 + 扇出)

   I = 0：完全稳定（不依赖任何人）
   I = 1：完全不稳定（不被任何人依赖）
```

> 依赖方向应从 I 大的指向 I 小的。

#### 7.2.3 稳定抽象原则（SAP, Stable Abstractions Principle）

> **越稳定的组件应该越抽象**。

稳定的组件（被很多人依赖）一旦变化影响巨大，所以应该抽象（接口/抽象类），抽象不变则实现可换。

```
   稳定 + 抽象 = 健康核心（如 Domain 层接口）
   不稳定 + 具体 = 健康外围（如 Infrastructure 层实现）
   
   ❌ 稳定 + 具体：改不动又必须改 → 僵化
   ❌ 不稳定 + 抽象：白抽象，没人用
```

**抽象度 A** = 抽象类/接口数 / 总类数。SAP 要求：稳定性 I 和抽象度 A 应正相关（I 小则 A 大）。

### 7.3 主序列（Main Sequence）

把 I（不稳定度）和 A（抽象度）画在二维图上：

```
   A (抽象度)
   1 ┌─────────────────┐
     │  抽象但没人用    │
     │  (Zone of Useless)│
     │                 │
     │      主序列      │
     │      ╱          │
     │    ╱            │
     │  ╱              │
   0 └─┴───────────────┐ 0
     0                 1  I (不稳定度)
       痛苦区          主序列 = I + A = 1
       (具体又稳定)
```

- **主序列**（`I + A = 1`）：稳定↔抽象、不稳定↔具体的平衡线，最健康。
- **痛苦区**（I=0, A=0）：又稳定又具体——僵化，改不动。
- **无用区**（I=1, A=1）：又抽象又不稳定——没人用的过度设计。

> 软件架构的目标是让所有组件靠近主序列。

## 八、康威定律（Conway's Law）

> "Any organization that designs a system will produce a design whose structure is a copy of the organization's communication structure."
>
> **任何设计系统的组织，其产出的系统结构都会复制该组织的沟通结构。**

### 8.1 核心含义

Melvin Conway 1967 年提出。简单说：**系统架构 = 组织架构**。

- 4 个团队开发编译器，会得到 4 段编译器。
- 前端 + 后端 + DBA 团队，会得到前后端分离 + 独立 DB 的三层架构。
- 跨地域团队，会得到松耦合的微服务。

### 8.2 反向康威定律（Inverse Conway Maneuver）

> 不要让组织结构决定架构，而要**按目标架构调整组织结构**。

如果你想微服务架构，就要拆分小团队（每个团队 owning 几个服务）；如果组织是按"前端/后端/DB"垂直分层，强行做微服务会失败——团队沟通模式还是分层的。

### 8.3 微服务与康威定律

微服务架构的成功前提是**组织结构匹配**：

| 组织形态 | 适合的架构 |
|---------|-----------|
| 垂直分层（前端/后端/DB 团队） | 单体分层 |
| 跨功能小团队（端到端 owning） | 微服务 |
| 跨地域大团队 | 松耦合服务 |

> 这就是为什么很多公司"上微服务失败"——组织没改，硬上架构，团队间沟通成本反而上升。

### 8.4 团队拓扑（Team Topologies）

Matthew Skelton 提出四种团队类型：

| 团队类型 | 职责 |
|---------|------|
| **Stream-Aligned**（业务流团队） | 端到端交付一个业务领域 |
| **Platform**（平台团队） | 提供内部平台让业务团队自助 |
| **Enabling**（赋能团队） | 临时帮业务团队掌握新技术 |
| **Complicated Subsystem**（复杂子系统团队） | 维护高专业度子系统 |

> 康威定律的现代应用：**先设计团队拓扑，再设计系统架构**。

## 九、架构坏味道（Architecture Smells）

> 类似代码坏味道，架构层也有常见反模式。识别它们是重构的起点。

### 9.1 上帝模块（God Module / God Object）

一个模块承担过多职责，知道得太多，被所有人依赖。

```
   ❌ UserManager：用户增删改查 + 权限 + 通知 + 日志 + 缓存
   问题：扇出大、扇入大、改动频繁、所有人改动它导致冲突
   解法：按职责拆分（UserRepo / AuthService / NotifyService）
```

### 9.2 散弹手术（Shotgun Surgery）

一次需求变更要改十几个文件——违反 CCP（共同闭包原则）。

```
   ❌ "修改订单折扣"要改：Order.java + DiscountService.java + CouponUtil.java + ...
   解法：把一起变化的聚到同一个包
```

### 9.3 依恋情结（Feature Envy）

一个模块对另一个模块的内部细节异常感兴趣，大量调用对方的 getter。

```
   ❌ OrderService 大量调用 order.getUser().getAddress().getCity()
   问题：OrderService 依赖 User 的内部结构（违反 LoD）
   解法：让 User 暴露行为（getShippingCity()），或把逻辑挪到 User
```

### 9.4 循环依赖（Cyclic Dependency）

A 依赖 B，B 依赖 A。违反 ADP。

```
   ❌ OrderService 依赖 UserService，UserService 依赖 OrderService
   解法：引入接口（DIP）或抽公共子模块
```

### 9.5 不当依赖方向（依赖指向不稳定）

违反 SDP——稳定的核心依赖了不稳定的外围。

```
   ❌ Domain 层依赖 Infrastructure 层（DB 实现）
   解法：Domain 定义接口，Infrastructure 实现（DIP）
```

### 9.6 数据泥团（Data Clumps）

多个地方重复出现相同的一组字段。

```
   ❌ 多个方法签名都有 (userId, userName, userPhone)
   解法：封装为 User 对象
```

### 9.7 基本类型偏执（Primitive Obsession）

用基本类型表达领域概念。

```
   ❌ 用 String 表达 Email、PhoneNumber、UserId
   问题：无法约束格式、类型混淆（UserId 和 OrderId 都是 String）
   解法：值对象（Value Object）
```

## 十、内聚与耦合的判定技巧

> 面试常问"怎么判断内聚高低、耦合强弱"。这里给实用技巧。

### 10.1 判定内聚（自问）

| 问题 | 高内聚 | 低内聚 |
|------|--------|--------|
| 能用一句话描述模块做什么吗？ | 能 | 不能（"做用户相关的事"） |
| 模块内所有元素都为同一目标服务吗？ | 是 | 否（顺手做的事） |
| 删掉某个元素，模块核心功能还完整吗？ | 不完整 | 完整（元素不属于这里） |
| 模块改名困难吗？ | 不困难（名字精准） | 困难（叫啥都不对） |

### 10.2 判定耦合（自问）

| 信号 | 耦合强度 |
|------|---------|
| 只通过参数传递简单数据 | 弱（数据耦合） |
| 传递复杂对象 | 中（标记耦合） |
| 传递 flag / mode 控制对方 | 中强（控制耦合） |
| 共享全局变量 | 强（公共耦合） |
| 直接访问对方内部字段 | 极强（内容耦合） |
| 修改对方后必须改我 | 强 |
| 我能脱离对方独立测试吗 | 否 → 强 |

### 10.3 解耦手段

| 手段 | 适用 |
|------|------|
| 接口抽象（DIP） | 消除对具体实现的依赖 |
| 事件驱动 | 消除调用方对被调方的直接依赖 |
| 依赖注入 | 消除 new 的硬编码依赖 |
| 中介者 / Facade | 消除多对多的网状依赖 |
| 数据契约（DTO） | 消除内部结构泄露 |
| 服务发现 | 消除地址硬编码 |

## 十一、架构原则之间的冲突与权衡

### 11.1 CCP vs CRP

- CCP：一起改的放一起（聚集）。
- CRP：不一起用的分开（分散）。

**权衡**：强相关的（同时满足 CCP 和 CRP）放一起；只满足 CCP 不满足 CRP 的，倾向 CCP（修改成本 > 复用成本）；只满足 CRP 的，倾向 CRP。

### 11.2 SDP vs SAP

- SDP：依赖指向稳定。
- SAP：稳定 = 抽象。

两者协同：**稳定的组件必须抽象**，否则别人依赖它会僵化。

### 11.3 高内聚 vs 低耦合

有时冲突：把强相关的东西聚到一起（高内聚），可能让模块变大、依赖变多（高耦合）。

**权衡**：优先内聚，然后用接口 / 事件降低耦合。内聚是基础，低耦合通过抽象达成。

### 11.4 康威定律 vs 理想架构

理想架构按业务领域切分，但组织可能按技术分层（前端/后端/DB）。

**权衡**：要么改组织（反向康威），要么接受架构被组织塑形——不要幻想"组织不动但架构理想"。

## 十二、综合面试题

### Q1：高内聚低耦合怎么判断？

> 内聚看模块内部：能否一句话描述？元素是否都为同一目标服务？删掉某元素是否破坏核心？
> 耦合看模块之间：传什么（数据 vs 控制标志）？能否独立测试？改对方要不要改我？
> 目标：功能内聚 + 数据耦合。

### Q2：扇入扇出怎么量化健康度？

> 扇出 = 直接调用的下级模块数，建议 ≤ 7，过大说明职责过重。
> 扇入 = 被多少上级调用，越大越好，说明复用高。
> 健康形态：金字塔——顶层扇出大、底层扇入大；病态：倒三角、雪茄形（深且窄）。

### Q3：作用域 ⊆ 控制域怎么理解？

> 作用域是判断语句影响到的模块集合，控制域是模块及其下属集合。准则要求"判断影响的范围"必须 ≤ "能控制的范围"。
> 违反的典型：A 判断 flag 后透传给 C，C 传给 E，E 真正用——A 必须知道 E 的存在，控制耦合 + 透传坏味道。
> 修复：把判断下推到真正执行的地方。

### Q4：循环依赖怎么破？

> 三种方法：① 依赖倒置——引入接口，双方依赖接口；② 抽公共子模块——把共同部分抽出来；③ 事件解耦——用观察者模式。
> Go 编译器直接拒绝循环导入，是语言级强制 ADP。

### Q5：稳定依赖原则怎么用？

> 依赖方向必须指向稳定方向。稳定性 I = 扇出 / (扇入 + 扇出)，I=0 完全稳定，I=1 完全不稳定。
> 健康架构：外围（I 大）依赖核心（I 小）。如果发现核心依赖外围，用 DIP 反转——核心定义接口，外围实现。

### Q6：康威定律对架构设计有什么影响？

> 系统架构会复制组织沟通结构。如果想做微服务，必须先拆小团队（端到端 owning）；如果组织是垂直分层，强行微服务会失败。反向康威：先设计团队拓扑，再设计架构。

### Q7：高内聚低耦合和 SOLID 是什么关系？

> 高内聚低耦合是母原则，SOLID 是它在类级别的细化。SRP 对应高内聚，DIP/LSP/ISP 对应低耦合。组件级原则（ADP/SDP/SAP）是它在包级别的细化。三者是同一思想在不同粒度的体现。

### Q8：单入单出在微服务架构里怎么体现？

> 单入：所有外部请求走 API 网关，统一鉴权/限流/路由，后端服务不直接对外暴露。
> 单出：所有响应由网关统一封装格式（成功/失败契约），后端服务的异常被网关截获转为标准错误。这避免了前端维护多个地址、漏做安全检查。

### Q9：模块功能可预测为什么重要？

> 可预测是可测的前提——不可预测（依赖全局状态/时间/随机）的模块无法写确定性测试。也是并发安全的前提——可预测的纯函数天然线程安全。函数式编程强调纯函数本质就是追求可预测。

### Q10：发现架构坏味道后怎么重构？

> 先识别（上帝模块/散弹手术/循环依赖等），再按原则重构：上帝模块按 SRP 拆分；散弹手术按 CCP 聚集；循环依赖按 ADP 破环；不当依赖方向按 SDP/DIP 反转。**重构必须有小步、有测试保护、有回归验证**——大爆炸式重构必败。
