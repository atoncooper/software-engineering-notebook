## 设计模式 —— 面向对象基础知识

面向对象（Object-Oriented, OO）是一种以"对象"为核心组织程序的范式。对象 = **数据（状态）+ 行为（方法）** 的封装体。本章系统梳理 OO 的核心概念、三大（四大）特性、设计原则（SOLID）以及 Java / Go 双语言实现对照，为后续设计模式章节打基础。

---

## 一、核心概念

### 1.1 对象（Object）

对象是系统中用来描述客观事物的实体，由**状态**和**行为**两部分构成：

- 状态：用字段/属性表示，是对象内部的数据。
- 行为：用方法表示，是对象对外提供的能力。

### 1.2 类（Class）

类是对象的"蓝图"或"模板"，定义了同类对象共有的属性和方法。对象是类的实例（instance）。

```
   类 (Class)  ──实例化──▶  对象 (Object)
   ┌────────┐              ┌────────┐
   │ 字段定义│              │ 字段值  │
   │ 方法定义│              │ 方法引用│
   └────────┘              └────────┘
   抽象模板                 具体实例
```

### 1.3 消息（Message）

对象之间通过**发送消息**（调用方法）协作。一个对象不知道另一个对象内部如何实现，只知道它提供了什么方法。

### 1.4 接口（Interface）

接口是对象对外暴露的行为契约，只声明"做什么"，不规定"怎么做"。接口是多态的基础。

### 1.5 抽象类（Abstract Class）

介于"类"和"接口"之间：可以包含已实现的方法（提供默认行为），也可以包含抽象方法（强制子类实现）。抽象类不能被直接实例化。

## 二、面向对象的三大特性

### 2.1 封装（Encapsulation）

**定义**：将对象的状态隐藏在内部，对外只暴露受控的访问接口。

**价值**：
- 防止外部代码随意修改内部状态，保证数据完整性。
- 内部实现可自由变化，不影响调用方。
- 降低耦合，提升可维护性。

**实现要点**：
- 字段设为 private，通过 getter/setter 暴露。
- 内部方法可设为 private / protected。
- 只暴露必要的方法，遵循"最小知识原则"。

#### Java 版

```java
public class BankAccount {
    private String owner;        // 字段私有
    private long balance;        // 内部状态不直接暴露

    public BankAccount(String owner, long initial) {
        this.owner = owner;
        if (initial < 0) throw new IllegalArgumentException("initial < 0");
        this.balance = initial;
    }

    // 行为公开：通过方法受控访问
    public long getBalance() { return balance; }

    public void deposit(long amount) {
        if (amount <= 0) throw new IllegalArgumentException("amount <= 0");
        balance += amount;
    }

    public void withdraw(long amount) {
        if (amount <= 0) throw new IllegalArgumentException("amount <= 0");
        if (amount > balance) throw new IllegalStateException("insufficient");
        balance -= amount;
    }
}
```

#### Go 版

Go 没有 class 关键字，用 struct + 方法实现。Go 的封装基于**包**：小写字母开头的字段/方法包外不可见。

```go
package account

type BankAccount struct {
    owner   string  // 小写：包外不可见
    balance int64   // 小写：包外不可见
}

// 构造函数（Go 惯例：NewXxx）
func NewBankAccount(owner string, initial int64) *BankAccount {
    if initial < 0 {
        panic("initial < 0")
    }
    return &BankAccount{owner: owner, balance: initial}
}

// 大写方法：包外可见，是受控访问入口
func (a *BankAccount) Balance() int64 { return a.balance }

func (a *BankAccount) Deposit(amount int64) {
    if amount <= 0 {
        panic("amount <= 0")
    }
    a.balance += amount
}

func (a *BankAccount) Withdraw(amount int64) {
    if amount <= 0 {
        panic("amount <= 0")
    }
    if amount > a.balance {
        panic("insufficient")
    }
    a.balance -= amount
}
```

> Java 的封装粒度是"类/字段级"，Go 是"包级"。这是两种语言哲学的核心差异之一。

---

### 2.2 继承（Inheritance）

**定义**：子类继承父类的字段和方法，可复用、扩展或覆盖父类行为，体现 **is-a** 关系。

**价值**：
- 代码复用。
- 建立类型层次，支持多态。
- 通过方法覆盖实现"同一接口，不同表现"。

**代价**：
- 强耦合：父类变化直接影响子类。
- 继承层次过深时难以维护。
- 违反"组合优于继承"的现代原则。

#### Java 版

```java
// 父类
public class Animal {
    protected String name;   // protected：子类可见

    public Animal(String name) { this.name = name; }

    public void eat() {
        System.out.println(name + " is eating");
    }

    // 可被覆盖的方法
    public String sound() {
        return "...";
    }
}

// 子类：继承 + 覆盖
public class Dog extends Animal {
    public Dog(String name) { super(name); }

    @Override
    public String sound() { return "Woof"; }

    // 扩展：子类新增方法
    public void fetch() {
        System.out.println(name + " fetches the ball");
    }
}
```

#### Go 版

**Go 没有继承**，只有"组合"。通过**嵌套字段（embedding）**模拟继承语义，通过**接口**实现多态。这是 Go 的有意设计 —— 强制"组合优于继承"。

```go
package main

import "fmt"

// "父类"
type Animal struct {
    Name string
}

func (a *Animal) Eat() {
    fmt.Printf("%s is eating\n", a.Name)
}

func (a *Animal) Sound() string {
    return "..."
}

// "子类"：通过嵌套字段组合
type Dog struct {
    Animal  // 匿名嵌套，Dog "拥有" Animal 的所有字段和方法
}

// 覆盖 Sound
func (d *Dog) Sound() string {
    return "Woof"
}

// 扩展
func (d *Dog) Fetch() {
    fmt.Printf("%s fetches the ball\n", d.Name)  // 直接访问 d.Name
}

func main() {
    d := &Dog{Animal: Animal{Name: "Rex"}}
    d.Eat()         // 调用嵌入字段的方法
    fmt.Println(d.Sound())  // Woof —— 自身覆盖版本
    d.Fetch()
}
```

> Go 的嵌入会"提升"嵌入字段的方法到外层结构体，看起来像继承，但本质是组合。外层覆盖同名方法时，内层方法仍可通过 `d.Animal.Sound()` 访问，不构成真正的虚函数分发。

### 2.3 多态（Polymorphism）

**定义**：同一接口，不同实现。调用方针对接口编程，运行时根据实际类型调用对应方法。

**价值**：
- 解耦：调用方不依赖具体类型。
- 可扩展：新增实现不改调用方代码（开闭原则）。
- 是策略模式、工厂模式、观察者模式等设计模式的基石。

**三种形式**：
1. **编译时多态**：方法重载（Overload），同名方法不同参数。
2. **运行时多态**：方法覆盖（Override）+ 向上转型。
3. **参数化多态**：泛型（Generic）。

#### Java 版

```java
// 接口
public interface Shape {
    double area();
}

// 实现1
public class Circle implements Shape {
    private final double r;
    public Circle(double r) { this.r = r; }
    @Override public double area() { return Math.PI * r * r; }
}

// 实现2
public class Rectangle implements Shape {
    private final double w, h;
    public Rectangle(double w, double h) { this.w = w; this.h = h; }
    @Override public double area() { return w * h; }
}

// 调用方：面向接口编程，不关心具体类型
public class AreaPrinter {
    public static void print(Shape s) {   // 多态：s 可以是 Circle / Rectangle
        System.out.printf("area = %.2f%n", s.area());
    }
}

// 使用
Shape s1 = new Circle(2);
Shape s2 = new Rectangle(3, 4);
AreaPrinter.print(s1);  // 12.57
AreaPrinter.print(s2);  // 12.00
```

#### Go 版

Go 的多态基于**接口的隐式实现**：结构体只要实现了接口定义的全部方法，就自动满足该接口，无需 `implements` 关键字（鸭子类型）。

```go
package main

import "fmt"

// 接口
type Shape interface {
    Area() float64
}

// 实现1
type Circle struct{ R float64 }
func (c Circle) Area() float64 { return 3.14159 * c.R * c.R }

// 实现2
type Rectangle struct{ W, H float64 }
func (r Rectangle) Area() float64 { return r.W * r.H }

// 调用方：面向接口
func PrintArea(s Shape) {
    fmt.Printf("area = %.2f\n", s.Area())
}

func main() {
    var s1 Shape = Circle{R: 2}
    var s2 Shape = Rectangle{W: 3, H: 4}
    PrintArea(s1)
    PrintArea(s2)
}
```

> Java 的多态显式（implements），Go 的多态隐式（鸭子类型）。隐式更灵活但牺牲了编译期检查的严格性（Go 通过 `var _ Shape = Circle{}` 做编译期断言）。

## 三、面向对象的"第四特性"：抽象（Abstraction）

抽象有时被独立列为第四特性，但本质上是封装 + 继承的延伸。

**定义**：抓住事物核心特征，忽略非本质细节，建立问题域到代码域的映射。

**两种载体**：
- **抽象类**：定义部分实现 + 部分抽象方法，子类补全。
- **接口**：完全抽象，只定义契约。

### Java 版

```java
// 抽象类：模板方法模式的基础
public abstract class Vehicle {
    protected final String name;
    protected Vehicle(String name) { this.name = name; }

    // 模板方法：定义骨架，子类填充
    public final void start() {
        checkFuel();
        ignite();
        System.out.println(name + " started");
    }

    private void checkFuel() { System.out.println("fuel checked"); }

    // 抽象方法：子类必须实现
    protected abstract void ignite();
}

public class Car extends Vehicle {
    public Car() { super("Car"); }
    @Override protected void ignite() { System.out.println("spark plug ignited"); }
}
```

### Go 版

Go 没有抽象类，用接口 + 默认结构体组合模拟。

```go
package main

import "fmt"

type Vehicle interface {
    Start()
}

// 用一个"基类"提供默认实现
type vehicleBase struct {
    Name string
}

func (v *vehicleBase) CheckFuel() { fmt.Println("fuel checked") }

// Car 嵌入 vehicleBase 并实现自己的 ignite
type Car struct {
    vehicleBase
}

func (c *Car) ignite() { fmt.Println("spark plug ignited") }

func (c *Car) Start() {
    c.CheckFuel()
    c.ignite()
    fmt.Println(c.Name + " started")
}

func NewCar() *Car {
    return &Car{vehicleBase: vehicleBase{Name: "Car"}}
}

func main() {
    var v Vehicle = NewCar()
    v.Start()
}
```

## 四、OO 设计原则（SOLID）

设计模式是原则的具体落地，原则是模式的"道"。

### 4.1 SRP —— 单一职责原则（Single Responsibility）

**一个类应该只有一个引起它变化的原因。**

```
反例：一个 Order 类既负责业务规则、又负责持久化、又负责发邮件
       → 业务规则变 / 存储方案变 / 邮件模板变 都会改这个类
正例：拆分为 OrderService / OrderRepository / OrderNotifier
```

#### Java

```java
// 反例
class Order {
    void calculate() { /* ... */ }
    void saveToDb() { /* ... */ }
    void sendEmail() { /* ... */ }
}

// 正例
class OrderService { void calculate(Order o) { /* ... */ } }
class OrderRepository { void save(Order o) { /* ... */ } }
class OrderNotifier { void notify(Order o) { /* ... */ } }
```

#### Go

```go
// 正例：按职责拆分为不同的 struct / 接口
type OrderService struct{}
func (s *OrderService) Calculate(o *Order) { }

type OrderRepository struct{ db *sql.DB }
func (r *OrderRepository) Save(o *Order) error { return nil }

type OrderNotifier struct{}
func (n *OrderNotifier) Notify(o *Order) { }
```

---

### 4.2 OCP —— 开闭原则（Open-Closed）

**对扩展开放，对修改关闭。** 新增功能时通过新增代码（新类 / 新实现）扩展，不修改老代码。

#### Java：通过接口 + 实现扩展

```java
// 折扣策略
interface DiscountStrategy {
    double apply(double price);
}

class NoDiscount implements DiscountStrategy {
    public double apply(double price) { return price; }
}

class PercentageDiscount implements DiscountStrategy {
    private final double pct;
    public PercentageDiscount(double pct) { this.pct = pct; }
    public double apply(double price) { return price * (1 - pct); }
}

// 新增"满减策略"时：只新增类，不改老代码
class FullCutDiscount implements DiscountStrategy {
    public double apply(double price) {
        return price >= 100 ? price - 20 : price;
    }
}

class Checkout {
    private final DiscountStrategy strategy;
    public Checkout(DiscountStrategy s) { this.strategy = s; }
    public double total(Order o) { return strategy.apply(o.amount()); }
}
```

#### Go

```go
type DiscountStrategy interface {
    Apply(price float64) float64
}

type NoDiscount struct{}
func (NoDiscount) Apply(p float64) float64 { return p }

type PercentageDiscount struct{ Pct float64 }
func (d PercentageDiscount) Apply(p float64) float64 { return p * (1 - d.Pct) }

// 新增策略只加文件
type FullCutDiscount struct{}
func (FullCutDiscount) Apply(p float64) float64 {
    if p >= 100 { return p - 20 }
    return p
}

type Checkout struct{ strategy DiscountStrategy }
func (c *Checkout) Total(o *Order) float64 { return c.strategy.Apply(o.Amount) }
```

### 4.3 LSP —— 里氏替换原则（Liskov Substitution）

**子类必须能替换父类而不破坏程序正确性。** 即：子类不能加强前置条件，不能削弱后置条件，不能抛出新的受检异常。

经典反例：正方形继承长方形 —— 长方形有独立的 width/height，正方形强制相等，替换后 `setWidth` 行为破坏。

#### Java 反例

```java
class Rectangle {
    protected int w, h;
    public void setWidth(int w) { this.w = w; }
    public void setHeight(int h) { this.h = h; }
    public int area() { return w * h; }
}

// 反例：正方形继承长方形，破坏了 setWidth/setHeight 的语义
class Square extends Rectangle {
    @Override public void setWidth(int w)  { this.w = w; this.h = w; }
    @Override public void setHeight(int h) { this.w = h; this.h = h; }
}

// 调用方期待 Rectangle 的行为，传 Square 出 bug
void test(Rectangle r) {
    r.setWidth(3);
    r.setHeight(4);
    assert r.area() == 12;   // Square 时 area = 16，违反 LSP
}
```

**正解**：不建立继承关系，改为共同的抽象基类（如 Shape）。

---

### 4.4 ISP —— 接口隔离原则（Interface Segregation）

**客户端不应被迫依赖它不使用的方法。** 接口要小而专，不要做成"胖接口"。

#### Java

```java
// 反例：胖接口
interface Worker {
    void work();
    void eat();
    void sleep();
}

// 机器人实现 Worker，被迫实现 eat/sleep（无意义）
class Robot implements Worker {
    public void work() { }
    public void eat() { throw new UnsupportedOperationException(); }
    public void sleep() { throw new UnsupportedOperationException(); }
}

// 正例：拆分为小接口
interface Workable { void work(); }
interface Eatable  { void eat(); }
interface Sleepable{ void sleep(); }

class Robot implements Workable {
    public void work() { }
}
```

#### Go

Go 的接口天然鼓励小而专，标准库很多接口只有 1-2 个方法（如 `Reader.Read`、`Writer.Write`）。

```go
// 小接口
type Worker interface { Work() }
type Eater interface { Eat() }

type Robot struct{}
func (Robot) Work() {}

type Human struct{}
func (Human) Work() {}
func (Human) Eat()  {}
```

---

### 4.5 DIP —— 依赖倒置原则（Dependency Inversion）

**高层模块不应依赖低层模块，二者都依赖抽象。** 抽象不依赖细节，细节依赖抽象。

#### Java

```java
// 反例：高层直接依赖低层具体类
class OrderService {
    private MySQLOrderRepo repo = new MySQLOrderRepo();  // 强耦合
}

// 正例：依赖接口
interface OrderRepository {
    void save(Order o);
}

class MySQLOrderRepo implements OrderRepository {
    public void save(Order o) { /* ... */ }
}

class OrderService {
    private final OrderRepository repo;
    public OrderService(OrderRepository repo) {  // 构造注入
        this.repo = repo;
    }
}
```

#### Go

```go
type OrderRepository interface {
    Save(o *Order) error
}

type MySQLOrderRepo struct{ db *sql.DB }
func (r *MySQLOrderRepo) Save(o *Order) error { return nil }

type OrderService struct {
    repo OrderRepository   // 依赖接口
}

func NewOrderService(repo OrderRepository) *OrderService {
    return &OrderService{repo: repo}
}

// main.go 装配
func main() {
    db, _ := sql.Open("mysql", "dsn")
    repo := &MySQLOrderRepo{db: db}
    svc := NewOrderService(repo)
    _ = svc
}
```

## 五、组合与继承的取舍

**现代 OO 设计的金科玉律："组合优于继承"（Favor composition over inheritance）。**

| 对比项 | 继承 | 组合 |
|--------|------|------|
| 关系 | is-a | has-a |
| 耦合 | 强（编译期绑定） | 弱（运行时可换） |
| 灵活性 | 受类层次限制 | 任意组合 |
| 复用维度 | 静态 | 动态 |
| 推荐 | 框架/抽象层级少时用 | 优先选择 |

### Java 示例

```java
// 继承：紧耦合
class Stack<E> extends ArrayList<E> {
    public void push(E e) { add(e); }
    public E pop() { return remove(size() - 1); }
}
// 问题：Stack 暴露了 ArrayList 的所有方法，破坏栈语义

// 组合：暴露受控接口
class Stack<E> {
    private final List<E> items = new ArrayList<>();
    public void push(E e) { items.add(e); }
    public E pop() { return items.remove(items.size() - 1); }
    // 不暴露 size/insert/... 等
}
```

### Go 示例

```go
// 组合天然
type Stack[T any] struct {
    items []T
}

func (s *Stack[T]) Push(v T) { s.items = append(s.items, v) }
func (s *Stack[T]) Pop() T {
    n := len(s.items)
    v := s.items[n-1]
    s.items = s.items[:n-1]
    return v
}
```

## 六、Java 与 Go 的 OO 对比

| 对比项 | Java | Go |
|--------|------|-----|
| 类 | `class` | `struct` + 方法 |
| 继承 | 单继承 + 接口多实现 | 无继承，仅组合（嵌入） |
| 多态 | 显式 `implements` | 隐式鸭子类型 |
| 封装粒度 | 类/字段级（private/protected/public） | 包级（大小写） |
| 抽象类 | 有（`abstract`） | 无，用接口 + 默认结构体模拟 |
| 泛型 | 类型擦除式泛型 | 1.18+ 引入参数化类型 |
| 方法重载 | 支持 | 不支持（函数名相同会编译错误） |
| 构造函数 | 类同名方法 | 约定 `NewXxx` 工厂函数 |
| 异常 | 受检 + 非受检异常 | `error` 返回值 |
| this/self | `this` | 接收者参数（`func (r *T) Method()`） |

### 同一需求的双语言实现对照

需求：定义一个 `Animal` 抽象，`Dog` 和 `Cat` 是其实现，都有 `Sound()` 行为。

#### Java

```java
interface Animal {
    String sound();
}

class Dog implements Animal {
    public String sound() { return "Woof"; }
}

class Cat implements Animal {
    public String sound() { return "Meow"; }
}

public class Main {
    public static void main(String[] args) {
        List<Animal> zoo = List.of(new Dog(), new Cat());
        for (Animal a : zoo) {
            System.out.println(a.getClass().getSimpleName() + ": " + a.sound());
        }
    }
}
```

#### Go

```go
package main

import "fmt"

type Animal interface {
    Sound() string
}

type Dog struct{}
func (Dog) Sound() string { return "Woof" }

type Cat struct{}
func (Cat) Sound() string { return "Meow" }

func main() {
    zoo := []Animal{Dog{}, Cat{}}
    for _, a := range zoo {
        fmt.Printf("%T: %s\n", a, a.Sound())
    }
}
```

## 七、OO 设计的常见反模式

### 7.1 贫血模型（Anemic Domain Model）

只有 getter/setter 的对象，业务逻辑全在 Service。本质是把面向过程写成 OO 的壳。

```java
// 反例：贫血
class Order {
    private double amount;
    public double getAmount() { return amount; }
    public void setAmount(double a) { this.amount = a; }
}
class OrderService {
    public double applyDiscount(Order o) {
        return o.getAmount() * 0.9;   // 业务规则在 Service 里
    }
}

// 正例：充血模型，规则回到 Model
class Order {
    private double amount;
    public Order(double amount) { this.amount = amount; }
    public double applyDiscount() { return amount * 0.9; }
}
```

### 7.2 上帝对象（God Object）

一个类无所不知、无所不能，承担太多职责，违反 SRP。

### 7.3 深继承塔

继承层次超过 3-4 层，可读性、可维护性急剧下降。应改用组合。

### 7.4 标签接口滥用

`interface Marker {}` 无方法，仅用于 `instanceof` 判断，破坏多态价值。

## 八、OO 与设计模式的关系

设计模式是 OO 原则在特定场景下的**经验性方案**：

| 设计原则 | 对应模式举例 |
|---------|------------|
| OCP（开闭） | 策略、工厂、观察者、装饰器 |
| SRP（单一职责） | 外观、命令 |
| LSP（里氏替换） | 模板方法 |
| ISP（接口隔离） | 适配器 |
| DIP（依赖倒置） | 依赖注入、抽象工厂 |

掌握 OO 基础 = 掌握设计模式的前置条件。后续模式章节每一条都对应到本节的某条原则。

## 九、速记要点

| 要点 | 记忆 |
|------|------|
| 三大特性 | 封装、继承、多态 |
| 第四特性 | 抽象（封装+继承的延伸） |
| 封装 | 隐藏状态，暴露行为 |
| 继承 | is-a，复用 + 类型层次 |
| 多态 | 同一接口，不同实现 |
| 组合优于继承 | has-a 优于 is-a |
| SOLID | SRP / OCP / LSP / ISP / DIP |
| Java vs Go | 显式 vs 隐式；类级 vs 包级；有继承 vs 无继承 |
| 贫血模型 | 反模式，业务规则要回到 Model |
| 模式本质 | OO 原则在具体场景的落地 |
