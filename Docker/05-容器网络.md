# 05 - 容器网络

> 容器网络是 Docker 最复杂、最容易踩坑的部分。本章把四种网络模型、端口映射、DNS、overlay 跨主机通信讲到生产级。

---

## 1. 问题定义与边界

### 1.1 本章解决什么

- 把 Docker 的 **四种网络模型**(bridge / host / none / container)讲透
- 把 **自定义 bridge** 与默认 bridge 的差异说清(为什么生产必须用自定义)
- 把 **端口映射** 的机制与陷阱说透(iptables DNAT、ipvlan)
- 把 **DNS 解析** 的内置机制说清(为什么自定义 bridge 能用容器名通信)
- 把 **overlay 跨主机网络** 讲到能落地(VXLAN、Swarm / K8s)

### 1.2 本章不解决什么

- 不讲 network namespace 内核机制(见 [08-底层原理-namespaces](./08-底层原理-namespaces.md))
- 不讲 K8s CNI 网络(Calico / Cilium / Flannel,见 [19-容器生态对比](./19-容器生态对比.md))
- 不讲服务网格(Istio / Linkerd,见 [infra开发](../infra开发/))
- 不讲存储网络(见 [06-数据存储与卷](./06-数据存储与卷.md))

> **关键认知**:Docker 网络本质是 **Linux 网络虚拟化**——veth pair、bridge、iptables、netns、VXLAN 的组合。理解 Linux 网络,就理解 Docker 网络。

## 2. 直觉解释

### 2.1 网络模型类比

```
   bridge(默认)         host              none            container
   ─────────────         ────              ────            ──────────
   容器有独立 netns       容器共享宿主       容器有 netns     容器共享另一容器
   通过 docker0 桥接     网络栈             但只有 lo        的 netns
   端口映射到宿主        无需映射           完全隔离         子容器模式
   
   ┌──────┐             ┌──────┐          ┌──────┐        ┌──────┐
   │ 容器  │             │ 容器  │          │ 容器  │        │ 容器B │
   │  ↓   │             │  =   │          │  lo  │        │ ↗    │
   │docker0│             │ 宿主  │          │      │        │容器A │
   │  ↓   │             │  eth │          └──────┘        └──────┘
   │ 宿主  │             └──────┘                             
   │  eth │                                                  
   └──────┘                                                  
```

### 2.2 为什么默认 bridge 不够用

```bash
# 默认 bridge:容器间只能用 IP 通信
docker run -d --name c1 alpine sleep 3600
docker run -d --name c2 alpine sleep 3600
docker exec c2 ping c1   # ❌ 失败,unknown host

# 自定义 bridge:自动 DNS,容器间用容器名通信
docker network create mynet
docker run -d --name c1 --network mynet alpine sleep 3600
docker run -d --name c2 --network mynet alpine sleep 3600
docker exec c2 ping c1   # ✓ 成功
```

> **生产基线**:永远用自定义 bridge,不用默认 bridge。

## 3. 核心概念与架构

### 3.1 默认 bridge 网络架构

```
┌─────────────────────────────────────────────────┐
│                宿主机                            │
│                                                 │
│   ┌─────────┐  ┌─────────┐  ┌─────────┐        │
│   │ 容器 A  │  │ 容器 B  │  │ 容器 C  │        │
│   │eth0@if12│  │eth0@if13│  │eth0@if14│        │
│   │172.17.0.│  │172.17.0.│  │172.17.0.│        │
│   └────┬────┘  └────┬────┘  └────┬────┘        │
│        │            │            │              │
│   ┌────┴────┐  ┌────┴────┐  ┌────┴────┐         │
│   │veth@if11│  │veth@if10│  │veth@if9 │  veth   │
│   └────┬────┘  └────┬────┘  └────┬────┘  pair   │
│        │            │            │              │
│        └────────────┼────────────┘              │
│                  ┌──┴──┐                        │
│                  │docker0│  ← Linux bridge      │
│                  │172.17│     网段 172.17.0.0/16│
│                  └──┬──┘                        │
│                     │                           │
│   ┌─────────────────┴────────────────┐          │
│   │  iptables NAT                    │          │
│   │  -A POSTROUTING -s 172.17.0.0/16 │          │
│   │    -j MASQUERADE                 │          │
│   │  -A DOCKER -p tcp --dport 8080   │          │
│   │    -j DNAT --to 172.17.0.2:80    │          │
│   └─────────────────┬────────────────┘          │
│                     │                           │
│                  ┌──┴──┐                        │
│                  │ eth0│  ← 宿主机物理网卡      │
│                  │10.0.│                        │
│                  └─────┘                        │
└─────────────────────────────────────────────────┘
```

### 3.2 veth pair 工作原理

```
veth pair:虚拟以太网线,两端各一个接口

  容器 netns            宿主 netns
  ┌──────────┐         ┌──────────┐
  │ eth0@if12│ <=====> │veth@if11 │
  │          │   虚拟   │          │
  │ 172.17..│   线缆   │          │
  └──────────┘         └──────────┘
       ↑                    ↑
       │                    │
       └── 一端在容器netns   └── 一端在宿主netns
           另一端接 docker0 bridge
```

**关键性质**:
- veth pair 总是成对,一端发包,另一端收包
- 容器内的 `eth0@if12` 与宿主机的 `veth@if11` 是同一对
- 容器发包 → eth0 → veth → docker0 → 路由到宿主机或同桥容器

### 3.3 iptables NAT 链

```
入站流量(外部 → 容器):
  eth0 → PREROUTING → DNAT(8080→172.17.0.2:80) → FORWARD → docker0 → veth → 容器

出站流量(容器 → 外部):
  容器 → veth → docker0 → FORWARD → POSTROUTING → MASQUERADE(SNAT) → eth0 → 外部

容器间(同 bridge):
  容器A → vethA → docker0 → vethB → 容器B
  (不经过 iptables,直接 bridge 转发)
```

### 3.4 四种网络模型对比

| 维度 | bridge(默认) | host | none | container |
|------|---------------|------|------|-----------|
| 网络栈 | 独立 netns | 共享宿主 | 独立 netns,只有 lo | 共享另一容器 |
| IP | 容器自有(172.17.0.x) | 宿主机 IP | 无 | 另一容器 IP |
| 端口映射 | 需要 | 不需要 | N/A | 不需要 |
| 隔离 | 强 | 弱 | 极强 | 弱(共享) |
| 性能 | 中(经过 docker0) | 高(原生) | N/A | 高(共享) |
| DNS | 默认无(自定义有) | 用宿主 | 无 | 用宿主 |
| 适用场景 | 通用 | 高性能 | 自定义网络 | Sidecar |

## 4. 操作流程与命令

### 4.1 网络管理命令

```bash
# 列出所有网络
docker network ls
# NETWORK ID     NAME      DRIVER    SCOPE
# a1b2c3d4e5f6   bridge    bridge    local
# b2c3d4e5f6a1   host      host      local
# c3d4e5f6a1b2   none      null      local

# 查看网络详情
docker network inspect bridge

# 创建自定义网络
docker network create mynet
docker network create --driver bridge --subnet 172.20.0.0/16 mynet
docker network create --driver bridge --subnet 172.20.0.0/16 --gateway 172.20.0.1 mynet

# 删除网络
docker network rm mynet

# 清理未使用网络
docker network prune

# 容器接入/退出网络
docker network connect mynet web
docker network disconnect mynet web
```

### 4.2 端口映射

```bash
# 默认随机映射到宿主高端口
docker run -d -P nginx

# 指定映射
docker run -d -p 8080:80 nginx         # 0.0.0.0:8080 -> 80
docker run -d -p 127.0.0.1:8080:80 nginx  # 只监听本地
docker run -d -p 8080:80/tcp nginx     # 显式 TCP
docker run -d -p 8080:80/udp nginx     # UDP
docker run -d -p 8080-8090:80 nginx    # 端口范围

# 查看端口映射
docker port web
# 80/tcp -> 0.0.0.0:8080
```

### 4.3 host 模式

```bash
# 共享宿主网络栈,无需端口映射
docker run -d --network host nginx

# 此时 nginx 直接监听宿主机 80 端口
# 容器内 ifconfig 看到的是宿主机网卡
```

> **注意**:host 模式在 macOS / Windows 上无效(因为容器跑在 VM 内,共享 VM 网络而非宿主机)。

### 4.4 container 模式(Sidecar)

```bash
# 容器 B 共享容器 A 的网络栈
docker run -d --name app --network mynet myapp
docker run -d --name sidecar --network container:app busybox sleep 3600

# sidecar 内 localhost:8080 即 app 的 8080
docker exec sidecar wget -qO- http://localhost:8080
```

> **用途**:Sidecar 模式,如 Envoy 代理、日志收集器,与应用共享网络栈。

## 5. 底层原理(简略)

### 5.1 容器创建时网络栈的初始化

```
docker run --network bridge --name web nginx
                ↓
1. 调用 CNI / libnetwork 创建网络接口
2. 创建 veth pair(vethA, vethB)
3. vethA 移到容器 netns,重命名为 eth0
4. vethB 接到 docker0 bridge
5. 给容器 eth0 分配 IP(172.17.0.2)
6. 设置默认路由(via 172.17.0.1)
7. 设置 /etc/resolv.conf(默认用宿主机 DNS)
8. iptables 配置:
   - 出站:MASQUERADE(SNAT)
   - 入站(有 -p):DNAT
```

### 5.2 DNS 解析机制

```
默认 bridge:
  - /etc/resolv.conf 复制宿主机
  - 没有 Docker 内置 DNS
  - 容器间只能用 IP

自定义 bridge:
  - 内置 DNS(127.0.0.11)
  - 容器名 → IP 自动解析
  - --link 也工作(但已不推荐)
  - 外部域名转发到宿主机 DNS
```

```bash
# 容器内查看 DNS 配置
docker run --rm --network mynet alpine cat /etc/resolv.conf
# nameserver 127.0.0.11
# options ndots:0
```

> **关键**:127.0.0.11 是 Docker 内嵌 DNS,监听容器 netns 内。容器名解析通过它完成。

### 5.3 overlay 网络架构

```
   节点 A (10.0.0.1)                  节点 B (10.0.0.2)
   ┌──────────────────┐              ┌──────────────────┐
   │ 容器 172.21.0.2  │              │ 容器 172.21.0.3  │
   │   ↓              │              │   ↓              │
   │ veth             │              │ veth             │
   │   ↓              │              │   ↓              │
   │ br-<id>(overlay) │              │ br-<id>(overlay) │
   │   ↓              │              │   ↓              │
   │ vxlan0           │              │ vxlan0           │
   │   ↓ ─────────────┼──────────────┼─── ↓            │
   │                  │  VXLAN 隧道   │                  │
   │                  │  (UDP 4789)  │                  │
   │ eth0 (10.0.0.1)  │ <──────────> │ eth0 (10.0.0.2) │
   └──────────────────┘              └──────────────────┘
```

**VXLAN**:把二层帧封装在 UDP 包里,跨主机传输。容器看起来像在同一个二层网络。

> **要求**:overlay 需要 Swarm 模式或 K8s,普通 `docker network create --driver overlay` 需先 `docker swarm init`。

## 6. 代码与配置示例

### 6.1 生产级自定义网络

```bash
# 创建带子网与网关的网络
docker network create \
  --driver bridge \
  --subnet 172.20.0.0/16 \
  --gateway 172.20.0.1 \
  --ip-range 172.20.0.0/24 \
  --label env=production \
  prod-net

# 容器使用静态 IP
docker run -d --name web --network prod-net --ip 172.20.0.10 nginx

# 内置 DNS 解析
docker run -d --name api --network prod-net --ip 172.20.0.20 myapi
docker exec web curl http://api:8000/health   # 用容器名访问
```

### 6.2 多网络接入

```bash
# 容器接入多个网络(前端 + 后端)
docker run -d --name api \
  --network frontend \
  --network backend \
  myapi

# 不同网络中,容器名解析都生效
docker exec frontend-container ping api   # ✓
docker exec backend-container ping api    # ✓
```

### 6.3 Compose 中的网络

```yaml
# docker-compose.yml
services:
  web:
    image: nginx:1.25
    networks:
      - frontend
    ports:
      - "8080:80"

  api:
    image: myapi:v1
    networks:
      - frontend
      - backend
    environment:
      DB_HOST: db   # 用服务名访问

  db:
    image: postgres:16
    networks:
      - backend
    volumes:
      - db-data:/var/lib/postgresql/data

networks:
  frontend:
    driver: bridge
  backend:
    driver: bridge
    internal: true   # 内部网络,不能访问外网

volumes:
  db-data:
```

### 6.4 macvlan(容器直连物理网络)

```bash
# 创建 macvlan 网络(容器获得与宿主同网段 IP)
docker network create -d macvlan \
  --subnet=192.168.1.0/24 \
  --gateway=192.168.1.1 \
  -o parent=eth0 \
  macvlan-net

# 容器使用
docker run -d --network macvlan-net --ip 192.168.1.100 nginx

# 注意:容器与宿主机不能直接通信(默认)
# 需在宿主机创建 macvlan 接口做路由
```

> **用途**:IoT 设备、需要广播的传统应用(如 mDNS)。生产慎用,网络策略难管理。

## 7. 常见陷阱与调优

### 7.1 陷阱:默认 bridge 无 DNS

```bash
# ❌ 用默认 bridge
docker run -d --name api nginx
docker run -d --name web nginx
docker exec web curl http://api/   # 失败

# ✓ 用自定义 bridge
docker network create mynet
docker run -d --name api --network mynet nginx
docker run -d --name web --network mynet nginx
docker exec web curl http://api/   # 成功
```

### 7.2 陷阱:端口冲突

```bash
# 容器 A 占了 8080
docker run -d -p 8080:80 --name a nginx
# 容器 B 也想用 8080
docker run -d -p 8080:80 --name b nginx
# ❌ Bind for 0.0.0.0:8080 failed: port is already allocated
```

**修复**:用不同宿主端口 `-p 8081:80`,或用 Traefik/Nginx 反向代理。

### 7.3 陷阱:`-p` 监听所有接口

```bash
# ❌ 默认监听 0.0.0.0,外网可访问
docker run -d -p 8080:80 nginx

# ✓ 只监听本地
docker run -d -p 127.0.0.1:8080:80 nginx
```

> **生产基线**:数据库等内部服务只绑 127.0.0.1,前面加反向代理。

### 7.4 陷阱:host 模式端口冲突

```bash
# 宿主机已有 nginx 监听 80
docker run -d --network host nginx
# ❌ nginx: [emerg] bind() to 0.0.0.0:80 failed (98: Address already in use)
```

### 7.5 陷阱:overlay 网络跨主机不通

**可能原因**:
- 防火墙挡了 VXLAN UDP 4789
- 节点间时间不同步(导致 TLS 握手失败)
- Swarm 没正确初始化
- MTU 不匹配(物理网络 MTU 1400,overlay 默认 1450)

**修复**:
```bash
# 检查 VXLAN 端口
sudo iptables -L -n | grep 4789

# 创建时指定 MTU
docker network create -d overlay --opt com.docker.network.driver.mtu=1400 mynet
```

### 7.6 陷阱:容器 DNS 解析慢

**原因**:默认用宿主机 `/etc/resolv.conf`,如果宿主机 DNS 慢,容器也慢。

**修复**:
```bash
# 创建网络时指定 DNS
docker network create --dns 8.8.8.8 --dns 8.8.4.4 mynet

# 或 daemon.json 全局
{
  "dns": ["8.8.8.8", "8.8.4.4"]
}
```

### 7.7 陷阱:容器访问外网慢

**原因**:MASQUERADE 性能瓶颈,或 conntrack 表满。

**修复**:
```bash
# 调大 conntrack 表
sudo sysctl -w net.netfilter.nf_conntrack_max=1048576

# 监控
sudo cat /proc/net/nf_conntrack_count
```

## 8. 工业案例与基准数据

### 8.1 网络性能对比

**测试条件**:iperf3 测吞吐,容器到容器同主机。

| 网络模式 | 吞吐 | 延迟 | CPU 占用 |
|----------|------|------|----------|
| host | 40 Gbps | 0.05 ms | 低 |
| bridge(默认) | 35 Gbps | 0.08 ms | 中 |
| bridge + 自定义 | 35 Gbps | 0.08 ms | 中 |
| macvlan | 38 Gbps | 0.06 ms | 低 |
| overlay(VXLAN) | 3 Gbps | 0.3 ms | 高 |

**结论**:
- 同主机:bridge 性能接近 host(差距 < 15%)
- 跨主机:overlay 有显著开销(VXLAN 封装 + CPU)
- 高性能场景:用 host 或 macvlan

### 8.2 大规模集群的网络方案

| 公司 | 网络方案 | 模式 | 备注 |
|------|----------|------|------|
| 阿里 | Terway + ENI | underlay | 弹性网卡直通,性能最优 |
| 字节 | 自研 + BGP | underlay | 自研 CNI,EBGP 大规模组网 |
| 腾讯 | VPC-CNI | underlay | 与 VPC 网络集成 |
| Netflix | Titus + VPC | underlay | AWS VPC 直连 |
| Google | VPC-native | underlay | GKE 默认 alias IP |

> **趋势**:大厂用 **underlay**(VPC 直连),不用 overlay。性能更好,但 IP 管理复杂。

### 8.3 conntrack 表爆炸案例

**场景**:某公司 1000 节点集群,每个节点 500 容器,每容器 1000 连接,共 50 万条 conntrack。

**问题**:
- 默认 `nf_conntrack_max=262144`(26 万)
- 表满后新连接被丢
- 表现为服务间歇性不通

**修复**:
```bash
# 调大 conntrack
sudo sysctl -w net.netfilter.nf_conntrack_max=2097152
sudo sysctl -w net.netfilter.nf_conntrack_buckets=524288

# 持久化
echo "net.netfilter.nf_conntrack_max=2097152" | sudo tee -a /etc/sysctl.conf
```

### 8.4 Service Mesh 与 Docker 网络

**对比**:
| 方案 | 网络层 | 服务发现 | 熔断 | 链路追踪 |
|------|--------|----------|------|----------|
| Docker Compose | bridge | DNS | 无 | 无 |
| K8s + Service | CNI | kube-dns | 无 | 无 |
| K8s + Istio | CNI + Envoy | kube-dns + Pilot | 有 | 有 |
| K8s + Linkerd | CNI + proxy | kube-dns | 有 | 有 |

> 详见 [infra开发](../infra开发/) 的服务网格章节。

## 9. 与其他方案的关系

### 9.1 Docker bridge vs K8s Service

| 维度 | Docker bridge | K8s Service |
|------|---------------|-------------|
| 跨主机 | 否(默认) | 是 |
| 服务发现 | DNS(同网络) | kube-dns |
| 负载均衡 | 无 | kube-proxy(iptables / IPVS) |
| 类型 | 单一 | ClusterIP / NodePort / LoadBalancer |

### 9.2 Docker overlay vs K8s CNI(Calico / Flannel)

| 维度 | Docker overlay | Calico | Flannel |
|------|---------------|--------|---------|
| 封装 | VXLAN | BGP / VXLAN | VXLAN / Host-GW |
| 性能 | 中 | 高(BGP) | 中 |
| 网络策略 | 无 | 有 | 需 Calico 补充 |
| K8s 集成 | 否(仅 Swarm) | 是 | 是 |

### 9.3 macvlan vs ipvlan

| 维度 | macvlan | ipvlan |
|------|---------|--------|
| MAC 地址 | 每容器独立 MAC | 共享宿主 MAC |
| 交换机 | 需要支持 MAC 学习 | 不需要 |
| 兼容性 | 部分云平台不支持 | 更兼容 |
| 性能 | 高 | 高 |

## 10. 面试速答

| 问题 | 一句话答案 |
|------|-----------|
| Docker 四种网络模式? | bridge(默认,独立 netns)、host(共享宿主)、none(只有 lo)、container(共享另一容器)。 |
| 默认 bridge 与自定义 bridge 区别? | 默认无 DNS、需 --link;自定义有内置 DNS(127.0.0.11),容器名直接解析。 |
| 容器如何访问外网? | 通过 iptables MASQUERADE(SNAT),把容器 IP 改成宿主机 IP。 |
| 端口映射如何实现? | iptables DNAT,把宿主端口流量转发到容器 IP:port。 |
| veth pair 是什么? | 虚拟以太网线,两端各一个接口,一端在容器 netns,一端接 docker0 bridge。 |
| overlay 网络用什么封装? | VXLAN,把二层帧封装在 UDP 4789。 |
| host 模式在 macOS 上有效吗? | 无效,容器跑在 VM 内,host 共享的是 VM 网络,不是 Mac 宿主。 |
| 为什么默认 bridge 容器间不能用容器名通信? | 默认 bridge 没有 Docker 内置 DNS,需用 --link 或自定义网络。 |
| conntrack 表满了会怎样? | 新连接被丢,服务间歇性不通;dmesg 看到 `nf_conntrack: table full`。 |
| 容器 DNS 慢怎么排查? | 看 /etc/resolv.conf 是否用 127.0.0.11,宿主机 DNS 是否慢,ndots 是否过高。 |

## 11. 综合面试题

### 题 1(原理)
**问**:解释 `docker run -p 8080:80` 在内核里发生了什么。

**答题要点**:
- 创建容器,分配 IP(如 172.17.0.2)
- 创建 veth pair,一端到容器 eth0,一端到 docker0
- iptables 加规则:
  - `DOCKER` 链:`-p tcp --dport 8080 -j DNAT --to 172.17.0.2:80`
  - `POSTROUTING`:`-s 172.17.0.0/16 -j MASQUERADE`
- 用户态 docker-proxy 监听 8080(可选,兼容性)
- 流量路径:客户端 → eth0 → PREROUTING → DNAT → docker0 → veth → 容器

### 题 2(对比)
**问**:什么时候用 host 模式,什么时候用 bridge?

**答题要点**:
- host:高性能、无需隔离(如本机监控 agent)、需要监听宿主原生端口
- bridge:需要隔离、多容器端口不冲突、生产标准
- host 风险:容器崩溃影响宿主网络、端口冲突、安全隔离弱
- 工业实践:99% 用 bridge,host 仅限特定场景

### 题 3(故障)
**问**:容器间能 ping 通,但 HTTP 访问失败,可能原因?

**答题要点**:
- 应用监听的是 127.0.0.1 而非 0.0.0.0(容器内 lo 才能访问)
- 端口不对(检查 `docker port` 或容器内 `ss -tlnp`)
- 防火墙(iptables FORWARD 链 DROP)
- 应用本身有问题(看容器日志)
- DNS 解析错(用容器名而非 IP)

### 题 4(性能)
**问**:跨主机容器网络延迟高,如何优化?

**答题要点**:
- 用 underlay(VPC-CNI / Terway)替代 overlay
- 调大 MTU(避免分片)
- 关闭 iptables conntrack(用 eBPF 替代,如 Cilium)
- 用 SR-IOV / DPDK(极致性能)
- 应用层:连接池、长连接、批处理

### 题 5(架构)
**问**:设计一个跨 3 个数据中心的容器网络方案。

**答题要点**:
- 子网规划:每数据中心独立 /16,避免冲突
- 跨中心:VPC peering / 物理专线 / VPN
- 网络方案:Calico BGP(跨中心路由)或 Submariner(K8s 跨集群)
- 服务发现:全局 DNS + 本地缓存
- 安全:跨中心流量加密(WireGuard / IPSec)
- 容灾:多活 + 流量切换

### 题 6(工业)
**问**:大厂为什么不用 Docker overlay,而用 VPC-CNI?

**答题要点**:
- overlay 有 VXLAN 封装开销(CPU、延迟)
- VPC-CNI 直连 VPC 网络,性能接近原生
- 与云厂商 VPC 集成,网络策略、流日志可用
- IP 管理更精细(每容器一个 VPC IP)
- 缺点:IP 数量受 VPC 限制,管理复杂

### 题 7(深度)
**问**:容器内 `curl localhost:8080` 访问的是谁?

**答题要点**:
- 容器有自己的 netns,localhost 是容器内 lo 接口
- 访问的是容器内 8080 端口的进程
- 不是宿主机的 8080,也不是其他容器的
- host 模式例外:localhost 是宿主机的

### 题 8(安全)
**问**:`-p 8080:80` 把端口暴露到外网,有什么风险?

**答题要点**:
- 默认监听 0.0.0.0,公网可访问
- 风险:扫描、攻击、未授权访问
- 修复:`-p 127.0.0.1:8080:80` 只监听本地
- 或:前置反向代理 + WAF
- 或:用 internal 网络,不暴露端口
- 工业基线:仅 Web 入口暴露,内部服务不暴露

### 题 9(故障)
**问**:`docker run` 报 `No chain/target/match by that name`,如何排查?

**答题要点**:
- iptables 规则被外部清空(firewalld 重启)
- 重启 dockerd:`systemctl restart docker`
- 检查 `iptables -L -n` 是否有 DOCKER 链
- 检查 `iptables -t nat -L -n` 是否有 DOCKER 链
- 永久禁用 firewalld 或配置信任

### 题 10(综合)
**问**:设计一个生产级容器网络方案,要求:多主机、服务发现、网络策略、可观测。

**答题要点**:
- 网络方案:Calico(BGP 模式,无 overlay)
- 服务发现:CoreDNS + kube-dns
- 网络策略:Calico NetworkPolicy(命名空间 / 标签维度)
- 负载均衡: metallb(L2/BGP)+ nginx-ingress
- 可观测:Cilium Hubble(流量拓扑)+ Prometheus + Loki
- 安全:NetworkPolicy 默认拒绝,显式放行
- IPAM:Calico ipip 模式或 VPC-CNI
- 多集群:Submariner 跨集群通信

## 12. 故障复盘

### 案例 1:容器访问外网间歇性失败

**现象**:某集群容器间歇性无法访问外网,`curl` 偶尔超时。

**根因**:
- 节点 conntrack 表满(默认 26 万,实际 50 万连接)
- 表满后新连接被丢
- 表现为间歇性不通

**修复**:
```bash
sudo sysctl -w net.netfilter.nf_conntrack_max=2097152
sudo sysctl -w net.netfilter.nf_conntrack_buckets=524288
```

**防范**:
- 节点初始化时调大 conntrack
- 监控 conntrack 使用率
- 应用层用连接池,减少连接数

### 案例 2:容器间 DNS 解析失败

**现象**:自定义 bridge 网络,容器名偶尔解析失败。

**根因**:
- 内置 DNS(127.0.0.11)的并发上限低
- 高并发查询时排队,超时

**修复**:
```bash
# 容器内本地缓存(nscd / dnsmasq)
# 或调 ndots(减少查询次数)
```

**防范**:
- 应用层加 DNS 缓存
- 监控 DNS 查询延迟
- 大规模用 CoreDNS + 缓存

### 案例 3:overlay 跨主机不通

**现象**:Swarm 集群,跨节点容器 ping 不通。

**根因**:
- 云厂商安全组挡了 UDP 4789(VXLAN)
- 节点间无法建立 VXLAN 隧道

**修复**:
```
安全组规则:入站 UDP 4789 + 7946 放行
```

**防范**:
- 文档化 Swarm / overlay 端口要求
- 节点初始化脚本检查防火墙

### 案例 4:MTU 不匹配导致大包丢失

**现象**:容器间小包(ping)通,大包(1 MB 文件)丢。

**根因**:
- 物理网络 MTU 1400(云厂商 GRE 隧道)
- overlay 默认 MTU 1450
- 大包分片或被丢

**修复**:
```bash
# 创建网络时指定 MTU
docker network create -d overlay --opt com.docker.network.driver.mtu=1400 mynet
```

**防范**:
- 节点初始化检测物理 MTU
- Docker daemon.json 设默认 MTU

### 案例 5:容器内 localhost 访问不到宿主机服务

**现象**:宿主机跑了 MySQL,容器内 `mysql -h 127.0.0.1` 连不上。

**根因**:
- 容器有独立 netns,localhost 是容器内 lo
- 不是宿主机的 localhost

**修复**:
```bash
# 方案 1:用宿主机网关 IP
docker exec -it web sh -c "ip route | grep default"
# default via 172.17.0.1
mysql -h 172.17.0.1

# 方案 2:host 模式
docker run --network host ...

# 方案 3:host.docker.internal(Docker Desktop)
mysql -h host.docker.internal
```
