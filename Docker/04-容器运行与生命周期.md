# 04 - 容器运行与生命周期

> `docker run` 是 Docker 最常用也最容易踩坑的命令。本章把它的全部参数、容器状态机、资源限制、信号处理讲到生产级。

---

## 1. 问题定义与边界

### 1.1 本章解决什么

- 把 `docker run` 几十个常用参数讲到能写出生产级启动命令
- 把容器从创建到死亡的 **状态机** 画清楚
- 把 **资源限制**(CPU / 内存 / IO / PID)的语义与陷阱说透
- 把 **重启策略** 与 **健康检查** 配置到生产可用
- 把 **PID 1 与信号处理** 讲到能避免"容器无法优雅停止"这一最常见生产事故

### 1.2 本章不解决什么

- 不讲网络配置细节(见 [05-容器网络](./05-容器网络.md))
- 不讲存储挂载细节(见 [06-数据存储与卷](./06-数据存储与卷.md))
- 不讲 cgroup 内核机制(见 [09-底层原理-cgroups](./09-底层原理-cgroups.md))
- 不讲 Compose 多容器编排(见 [07-Docker-Compose](./07-Docker-Compose.md))

> **关键认知**:容器就是被隔离的进程。理解进程,就理解容器;理解信号,就理解优雅停止。

## 2. 直觉解释

### 2.1 容器生命周期类比:剧场演出

```
   created  →  running  →  paused  →  stopped  →  deleted
   ───────     ───────     ───────     ───────     ───────
   装台完毕    演出中      暂停(冻     谢幕(进     拆台(资源
   演员就位                结进程)     程退出)     回收)
```

- **created**:容器已创建,文件系统已挂载,但进程未启动
- **running**:PID 1 进程已启动,正在执行
- **paused**:cgroup freezer 冻结所有进程,CPU 0%,内存保留
- **stopped/exited**:PID 1 退出,文件系统还在,可重启
- **deleted**:容器对象删除,卷按策略保留

### 2.2 优雅停止类比:关电视 vs 拔插头

```
   SIGTERM(15)              SIGKILL(9)
   ───────────              ──────────
   "请关闭"                  "立刻死"
   应用可处理:               无法处理:
   - 保存数据                - 数据可能丢失
   - 释放连接                - 文件可能损坏
   - 通知下游                - 连接被强制 RST
   默认 10s 后无效则         立即生效
   升级为 SIGKILL
```

## 3. 核心概念与架构

### 3.1 容器状态机

```
            docker create
                  │
                  ▼
            ┌──────────┐
            │ created  │
            └────┬─────┘
                 │ docker start
                 ▼
   docker pause ┌──────────┐ docker unpause
        ┌───────│ running  │────────┐
        │       └────┬─────┘        │
        ▼            │              │
   ┌──────────┐      │              │
   │ paused   │◀─────┘              │
   └──────────┘                     │
                  docker stop /     │
                  PID 1 退出        │
                       │            │
                       ▼            │
                  ┌──────────┐      │
                  │ exited   │      │
                  └────┬─────┘      │
                       │ docker start
                       └────────────┘
                       │
                       │ docker rm
                       ▼
                  ┌──────────┐
                  │ deleted  │
                  └──────────┘
```

### 3.2 PID 1 的特殊地位

```
容器内进程树:
PID 1: nginx(主进程)        ← docker 启动的进程
  ├─ PID 7: nginx worker
  ├─ PID 8: nginx worker
  └─ PID 9: nginx worker

宿主机进程树(同一进程,不同 PID):
PID 4567: containerd-shim     ← 容器父进程
  └─ PID 4568: nginx          ← 容器内 PID 1
     ├─ PID 4569: nginx worker
     └─ ...
```

**PID 1 的特殊职责**:
1. **接收信号**:`docker stop` 发的 SIGTERM 先到 PID 1
2. **收割僵尸进程**(reap zombie):孤儿进程的父变 PID 1,需 `wait` 回收
3. **容器生命周期**:PID 1 退出 → 容器退出

> **关键陷阱**:如果 PID 1 不处理 SIGTERM(如 shell 形式 CMD),`docker stop` 等 10 秒后 SIGKILL,数据丢失。

### 3.3 资源限制三层

```
┌─────────────────────────────────────┐
│  docker run 参数                     │
│  --cpus / --cpu-shares              │
│  --memory / --memory-swap           │
│  --pids-limit                       │
├─────────────────────────────────────┤
│  cgroup(内核机制)                  │
│  /sys/fs/cgroup/cpu/.../docker/<id> │
│  /sys/fs/cgroup/memory/.../         │
│  /sys/fs/cgroup/pids/.../           │
├─────────────────────────────────────┤
│  内核调度器 / OOM Killer             │
└─────────────────────────────────────┘
```

## 4. 操作流程与命令

### 4.1 `docker run` 全参数(生产常用)

```bash
docker run \
  # ── 命名与后台 ──
  -d                              # 后台运行
  --name web                      # 容器名
  --hostname web-01               # 容器内 hostname

  # ── 镜像与标签 ──
  nginx:1.25                      # 镜像

  # ── 网络 ──
  -p 8080:80                      # 端口映射(宿主:容器)
  -p 127.0.0.1:8080:80            # 只监听本地
  --network mynet                 # 接入自定义网络
  --ip 172.18.0.10                # 指定 IP
  --dns 8.8.8.8                   # 自定义 DNS
  --add-host api.corp.com:10.0.0.5  # /etc/hosts 注入

  # ── 存储 ──
  -v /data/web:/usr/share/nginx/html:ro  # 绑定挂载(只读)
  -v nginx-conf:/etc/nginx         # 命名卷
  --tmpfs /tmp                    # tmpfs 挂载
  --read-only                     # 根文件系统只读

  # ── 资源限制 ──
  --cpus="2.0"                    # CPU 配额(核数)
  --cpu-shares=512                # CPU 权重(相对,默认 1024)
  --cpuset-cpus="0,1"             # 绑定到 CPU 0 和 1
  --memory="1g"                   # 内存上限
  --memory-swap="2g"              # 内存 + swap 上限
  --memory-reservation="512m"     # 内存软限(低水位)
  --pids-limit="200"              # 最大进程数
  --ulimit nofile=65535:65535     # 文件描述符上限
  --ulimit nproc=65535:65535      # 进程数上限

  # ── 重启策略 ──
  --restart=unless-stopped        # 总是重启(除非手动 stop)

  # ── 健康检查 ──
  --health-cmd="curl -f http://localhost/ || exit 1"
  --health-interval=10s
  --health-timeout=3s
  --health-retries=3
  --health-start-period=30s       # 启动期不计失败

  # ── 环境与配置 ──
  -e ENV=production               # 环境变量
  --env-file /etc/web.env         # 环境变量文件
  --label team=platform           # 标签
  --label severity=critical

  # ── 用户与权限 ──
  -u 10001:10001                  # 以非 root 用户运行
  --cap-drop ALL                  # 删除所有 capabilities
  --cap-add NET_BIND_SERVICE      # 加回需要的
  --no-new-privileges             # 禁止子进程提权
  --security-opt no-new-privileges:true

  # ── 日志 ──
  --log-driver json-file          # 日志驱动
  --log-opt max-size=100m
  --log-opt max-file=10

  # ── 信号与停止 ──
  --stop-signal=SIGTERM           # 停止信号
  --stop-timeout=30               # 停止超时(秒)
  --init                          # 用 tini 作 PID 1(处理信号与 reap)

  # ── 运行命令(覆盖 CMD) ──
  nginx -g 'daemon off;'
```

### 4.2 容器生命周期命令

```bash
# 创建(不启动)
docker create --name web nginx:1.25

# 启动已创建的
docker start web

# 停止(优雅,默认 10s 超时后 SIGKILL)
docker stop web
docker stop -t 30 web          # 30s 超时

# 强制停止(直接 SIGKILL)
docker kill web
docker kill -s SIGINT web      # 发特定信号

# 重启
docker restart web
docker restart -t 30 web

# 暂停(冻结进程,不占 CPU,内存保留)
docker pause web

# 取消暂停
docker unpause web

# 查看状态
docker ps                      # 运行中
docker ps -a                   # 包括已停止
docker inspect web             # 详细元数据
docker stats                   # 资源占用
docker top web                 # 容器内进程

# 重命名
docker rename web web-old

# 删除(需先停止)
docker rm web
docker rm -f web               # 强制(运行中也删)

# 删除所有已停止容器
docker container prune
```

### 4.3 进入容器

```bash
# exec:在运行的容器内启动新进程
docker exec -it web sh         # 进入交互 shell
docker exec -it web bash
docker exec web ls /app        # 执行单条命令
docker exec -u root web sh     # 以 root 进入

# attach:连到容器 PID 1 的 stdin/stdout/stderr
docker attach web
# Ctrl+P, Ctrl+Q 脱离(不停止容器)
```

> **区别**:`exec` 是新进程,`attach` 是连主进程。生产环境 99% 用 exec。

## 5. 底层原理(简略)

### 5.1 资源限制的内核映射

```bash
docker run --cpus=2 --memory=1g --pids-limit=200 web
```

对应 cgroup v2:

```
/sys/fs/cgroup/docker/<container-id>/
├── cpu.max              # "200000 100000"(2 核,周期 100ms)
├── cpu.weight           # "100"(相对权重)
├── memory.max           # "1073741824"(1 GB)
├── memory.high          # 软限
├── pids.max             # "200"
├── cgroup.procs         # 容器内所有 PID
└── cgroup.controllers   # "cpu memory io pids"
```

### 5.2 CPU 限制机制:CFS quota

```
CFS(完全公平调度器)周期:100ms(default)

--cpus=2.0  →  cpu.max = "200000 100000"
含义:每 100ms 周期内,容器可用 200ms CPU 时间(2 核满载)

容器内进程突发用满 2 核,100ms 内用完 200ms quota
→ 被 throttle,等下一个 100ms 周期
→ 表现:CPU throttling 延迟毛刺
```

> 详见 [09-底层原理-cgroups](./09-底层原理-cgroups.md) 与 [25-故障复盘集](./25-工业实战-故障复盘集.md) 的 throttling 案例。

### 5.3 OOM Killer

```
容器内存超过 memory.max:
1. cgroup OOM Killer 触发(优先杀容器内进程)
2. 杀掉 PID 1 → 容器退出(exited 137)
3. --restart 策略决定是否重启

宿主机内存不足(系统级 OOM):
1. 全局 OOM Killer 触发
2. 按 oom_score 排序,杀分数高的进程
3. 容器进程 oom_score 通常高(占内存多)
4. 可能杀掉容器,也可能杀宿主机进程
```


### 6.2 重启策略对比

```bash
# 1. no(默认):退出不重启
docker run --restart=no nginx

# 2. always:总是重启(包括手动 stop 后 daemon 重启)
docker run --restart=always nginx
# 注意:手动 stop 后,daemon 重启时容器会跟着启动

# 3. unless-stopped:总是重启,但手动 stop 后不自动启动
docker run --restart=unless-stopped nginx
# 推荐:生产环境用这个

# 4. on-failure:仅非 0 退出码重启,可设上限
docker run --restart=on-failure:5 nginx
# 退出码 0 不重启;退出码非 0 重启,最多 5 次
```

| 策略 | 退出 0 | 退出非 0 | 手动 stop 后 daemon 重启 |
|------|-------|---------|------------------------|
| no | 不重启 | 不重启 | 不启动 |
| always | 重启 | 重启 | 启动 |
| **unless-stopped** | 重启 | 重启 | 不启动 |
| on-failure:N | 不重启 | 重启(≤N) | 不启动 |

### 6.3 健康检查

```bash
# 命令行
docker run -d \
  --name web \
  --health-cmd="curl -fsS http://localhost/ || exit 1" \
  --health-interval=10s \
  --health-timeout=3s \
  --health-retries=3 \
  --health-start-period=30s \
  nginx:1.25

# 查看健康状态
docker inspect --format='{{.State.Health.Status}}' web
# healthy / unhealthy / starting

docker inspect web | jq '.[0].State.Health'
# {
#   "Status": "healthy",
#   "FailingStreak": 0,
#   "Log": [
#     { "Start": "...", "ExitCode": 0, "Output": "..." }
#   ]
# }
```

```dockerfile
# Dockerfile 内置健康检查
HEALTHCHECK --interval=10s --timeout=3s --retries=3 --start-period=30s \
  CMD curl -fsS http://localhost/ || exit 1
```

> **关键**:健康检查失败不会自动重启容器,需要配合 `--restart` 或外部监控(如 K8s liveness probe)。

## 7. 常见陷阱与调优

### 7.1 陷阱:PID 1 不处理 SIGTERM

**症状**:`docker stop` 等 10 秒才停止,日志出现 `SIGKILL`。

**原因**:
```dockerfile
# shell 形式,PID 1 是 /bin/sh,不转发信号给应用
CMD python main.py
```

**修复**:
```dockerfile
# exec 形式,PID 1 是 python,直接接收信号
CMD ["python", "main.py"]

# 或用 init
docker run --init ...
```

### 7.2 陷阱:容器内跑僵尸进程

**症状**:容器内 `ps aux` 看到大量 `[defunct]` 进程,内存涨。

**原因**:PID 1 不收割僵尸进程(没有 `wait`),子进程退出后变 zombie。

**修复**:
```bash
# 用 tini / dumb-init 作 PID 1
docker run --init ...   # 自动用 tini

# 或 Dockerfile
ENTRYPOINT ["tini", "--"]
CMD ["python", "main.py"]
```

### 7.3 陷阱:`--memory` 设过小

**症状**:Java 应用启动时直接 OOM。

**原因**:JVM 看到的是宿主机内存,堆设得过大,超过 `--memory` 触发 OOM。

**修复**:
- JDK 8u191+ 自动感知 cgroup:`-XX:+UseContainerSupport`(默认开)
- 显式限制堆:`-XX:MaxRAMPercentage=75`
- 不要用 `-Xms` / `-Xmx` 写死

### 7.4 陷阱:CPU throttling 毛刺

**症状**:P99 延迟周期性飙高,`cpu.stat` 里 `nr_throttled` 增长。

**原因**:`--cpus=2` 设得过低,突发流量在 100ms 内用完 quota。

**修复**:
- 调高 `--cpus`(如 2 → 2.5)
- 关键服务只设 CPU request,不设 limit(K8s 模式)
- 升级 cgroup v2,`cpu.max` 更平滑

> 详见 [25-故障复盘集](./25-工业实战-故障复盘集.md)。

### 7.5 陷阱:`--restart=always` 配合健康检查不生效

**症状**:容器 unhealthy 但不重启。

**原因**:`--restart` 只在容器退出时生效,unhealthy 不会触发退出。

**修复**:
```bash
# 方案 1:外部脚本监控 unhealthy 后 kill
docker events --filter event=health_status:unhealthy | while read; do
  docker kill <name>
done

# 方案 2:K8s livenessProbe(推荐)
# K8s 自动重启 unhealthy 容器
```

### 7.6 陷阱:`--read-only` 但应用要写文件

**症状**:容器启动报 `Read-only file system`。

**修复**:
```bash
# 根文件系统只读,但 tmpfs / volume 可写
docker run --read-only \
  --tmpfs /tmp \
  -v /data/app:/var/log/app \
  myapp
```

### 7.7 陷阱:`docker exec` 改了容器状态,重启丢失

**症状**:`docker exec` 装了包,容器重启后没了。

**原因**:exec 是新进程,改的是容器层;容器删除后,容器层也删除。

**修复**:在 Dockerfile 里装,不要靠 exec。

## 8. 工业案例与基准数据

### 8.1 优雅停止时间对比

**测试条件**:Spring Boot 应用,需要保存 100 MB 内存数据到数据库。

| 方案 | 停止时间 | 数据完整性 |
|------|----------|-----------|
| 默认(SIGTERM 10s 超时) | 10s + SIGKILL | 可能丢失 |
| `--stop-timeout=60` + 应用处理 SIGTERM | 8s | 完整 |
| `--init` + tini + 应用处理 | 8s | 完整 |
| 无信号处理(SIGKILL) | <1s | 丢失 |

### 8.2 CPU throttling 对延迟的影响

**测试条件**:Python FastAPI,`--cpus=1`,QPS 500。

| 指标 | 无 throttling | throttling(nr_throttled/s=10) |
|------|--------------|------------------------------|
| P50 延迟 | 5 ms | 8 ms |
| P95 延迟 | 20 ms | **180 ms** |
| P99 延迟 | 50 ms | **450 ms** |
| 错误率 | 0% | 0.1% |

**结论**:throttling 对 P99 影响巨大,生产关键服务应避免设过低的 CPU limit。

### 8.3 Netflix Titus 的容器规范(公开)

```yaml
# Titus 容器规格(简化)
container:
  cpu: 1.0              # 1 核
  memory: 1GB
  disk: 10GB
  network: 100Mbps
  
  restart: always
  
  healthcheck:
    type: http
    endpoint: /health
    interval: 10s
    timeout: 5s
    
  security:
    user: 10001
    capabilities: [NET_BIND_SERVICE]
    read_only_rootfs: true
    
  logging:
    driver: json-file
    max_size: 100MB
    max_files: 5
```

### 8.4 大厂容器密度与资源限制

| 公司 | 单容器典型规格 | 单机容器数 | 备注 |
|------|----------------|-----------|------|
| Netflix | 1C1G-2C4G | 50-100 | 在线为主 |
| 阿里 Sigma | 0.5C-4C | 200-500 | 在线+离线混部 |
| 字节 Kamino | 0.25C-2C | 150-300 | 微服务为主 |
| AWS Fargate | 0.25C-16C | N/A(托管) | 按需付费 |

> **趋势**:容器越来越小(0.25C 起步),密度越来越高(混部),资源利用率从 15% → 40%+。

## 9. 与其他方案的关系

### 9.1 Docker restart vs K8s livenessProbe

| 维度 | Docker --restart | K8s livenessProbe |
|------|------------------|-------------------|
| 触发条件 | 容器退出 | 健康检查失败 |
| 健康检查 | 不自动重启 | 自动重启 |
| 重启位置 | 同一节点 | 可能调度到其他节点 |
| 适合场景 | 单机 / 简单场景 | 生产集群 |

### 9.2 Docker run vs systemd

| 维度 | docker run | systemd |
|------|-----------|---------|
| 隔离 | namespace + cgroup | 无 |
| 资源限制 | 内置 | 需配合 cgroup |
| 日志 | docker logs | journald |
| 依赖管理 | --link(已废弃) / Compose | After= / Requires= |
| 适合场景 | 容器化应用 | 系统服务 |

> **实践**:在 systemd 里管理 docker 容器,用 `Type=oneshot` + `ExecStart=docker run`。

## 10. 面试速答

| 问题 | 一句话答案 |
|------|-----------|
| `docker stop` 与 `docker kill` 区别? | stop 发 SIGTERM 优雅停止(10s 超时后 SIGKILL);kill 直接发 SIGKILL(默认)。 |
| 容器为什么 PID 1 退出就死? | 容器本质是 PID 1 的进程树,PID 1 退出,进程树空,容器退出。 |
| `--cpus=2` 是什么意思? | CFS quota 2 核,每 100ms 周期内可用 200ms CPU 时间。 |
| `--memory` 与 `--memory-swap` 区别? | memory 是物理内存上限;memory-swap 是 memory+swap 上限,大于 memory 才允许用 swap。 |
| `--restart=always` 与 `unless-stopped` 区别? | always 在 daemon 重启时也启动手动 stop 的容器;unless-stopped 不会。 |
| `--init` 干什么? | 用 tini 作 PID 1,处理信号转发与僵尸进程收割。 |
| 健康检查 unhealthy 会自动重启吗? | 不会,只标 unhealthy,需配合外部监控或 K8s livenessProbe。 |
| 为什么 `CMD python main.py` 优雅停止失败? | shell 形式 PID 1 是 /bin/sh,不转发 SIGTERM 给 python。 |
| 容器退出码 137 是什么? | 128 + 9(SIGKILL),通常是 OOM 或 stop 超时后被 KILL。 |
| 容器退出码 143 是什么? | 128 + 15(SIGTERM),正常优雅停止。 |

## 11. 综合面试题

### 题 1(原理)
**问**:容器内 PID 1 退出码与容器退出码的关系?PID 1 是 shell 时有什么问题?

**答题要点**:
- 容器退出码 = PID 1 退出码
- PID 1 是 shell(/bin/sh -c):不转发 SIGTERM 给子进程,优雅停止失效
- shell 不 reap zombie,子进程退出后变僵尸
- 修复:exec 形式 CMD / ENTRYPOINT,或 `--init`

### 题 2(资源)
**问**:`--cpus=2` 与 `--cpu-shares=1024` 的区别?

**答题要点**:
- `--cpus`:绝对配额,2 核 = 每 100ms 用 200ms
- `--cpu-shares`:相对权重,默认 1024,空闲时可用全部,争抢时按比例
- 配额是硬限制,shares 是软限制
- 生产:limits 用 cpus,request 用 cpu-shares(K8s 模式)

### 题 3(故障)
**问**:容器频繁 OOM(exited 137),但应用日志无异常,如何排查?

**答题要点**:
- 看 `docker inspect` 的 `OOMKilled` 字段
- `docker stats` 看内存增长曲线(是否泄漏)
- 容器内 `cat /proc/1/status` 看 VmRSS
- cgroup `memory.max` 设得过低?
- JVM / Node 是否感知容器?(JDK 8u191+ 自动)
- 是否被宿主机全局 OOM Killer 杀?看 dmesg
- 修复:调大 limit、修复泄漏、用容器感知运行时

### 题 4(信号)
**问**:`docker stop` 后容器 10 秒才停,如何让它在 3 秒内停?

**答题要点**:
- 应用必须处理 SIGTERM(优雅关闭连接、保存数据)
- `--stop-timeout=3` 设短超时(但应用没处理就 SIGKILL,数据丢失)
- 真正解决:应用注册 SIGTERM handler
- `--init` 确保信号正确转发
- 检查 Dockerfile 是不是 exec 形式

### 题 5(健康检查)
**问**:健康检查 healthy → unhealthy 后,容器会怎样?

**答题要点**:
- Docker 本身不会重启,只标 unhealthy
- 配合 `--restart` 无效(restart 只看退出)
- 需要:外部脚本监听 `docker events` + 手动 kill
- 或:K8s livenessProbe(自动重启)
- 或:Docker Swarm `--update-failure-action`

### 题 6(工业)
**问**:关键在线服务(支付网关)的容器如何设置资源限制?

**答题要点**:
- CPU:request 设典型用量(如 1 核),**不设 limit** 或 limit ≥ 2× request
  - 原因:CPU throttling 影响 P99,支付不能慢
- 内存:request = limit(避免 OOM 后被调度到其他节点重新启动)
- 关闭 swap:`--memory-swap=0`(禁止 swap,避免延迟)
- `--pids-limit` 设大(避免连接风暴时打不开线程)
- `--ulimit nofile=65535`(支付需要大量连接)
- 健康检查:HTTP /health,间隔 5s,失败 3 次
- 重启:unless-stopped

### 题 7(架构)
**问**:容器为什么不能像 VM 一样跑 systemd?

**答题要点**:
- 容器设计哲学:一容器一进程
- systemd 需要 PID 1,与容器 PID 1 冲突
- systemd 依赖 systemctl / dbus,容器内不一定有
- 容器内多服务应:拆成多个容器(Compose)
- 例外:LXC 系统容器可以跑 systemd(但不是 Docker 设计目标)

### 题 8(深度)
**问**:解释 `--memory-reservation` 与 `--memory` 的关系。

**答题要点**:
- `--memory`:硬限制,超过触发 OOM
- `--memory-reservation`:软限制(低水位)
- 内核内存紧张时,优先回收超过 reservation 的容器
- reservation < memory
- 适用:突发流量场景,平时用 reservation,峰值用 memory

### 题 9(安全)
**问**:`--cap-drop ALL --cap-add NET_BIND_SERVICE` 解决什么?

**答题要点**:
- 默认容器有 14 个 capabilities(如 CHOWN, DAC_OVERRIDE)
- 攻击面大:容器逃逸后能做很多事
- drop ALL:删所有,最小权限
- add NET_BIND_SERVICE:仅加回绑定 80/443 端口的能力
- 配合 `--security-opt no-new-privileges` 防止子进程提权
- 工业基线:所有生产容器必须 drop ALL

### 题 10(综合)
**问**:设计一个支付服务的容器启动命令,需要考虑:高可用、优雅停止、安全、可观测。

**答题要点**:
```bash
docker run -d \
  --name payment \
  --network payment-net \
  -p 8443:8443 \
  \
  --cpus="2" \
  --memory="2g" \
  --memory-reservation="1g" \
  --memory-swap="0" \
  --pids-limit="1000" \
  --ulimit nofile=65535:65535 \
  \
  --restart=unless-stopped \
  --stop-timeout=30 \
  --stop-signal=SIGTERM \
  --init \
  \
  --health-cmd="curl -fsS https://localhost:8443/health || exit 1" \
  --health-interval=5s \
  --health-timeout=3s \
  --health-retries=3 \
  \
  -u 10001:10001 \
  --cap-drop ALL \
  --cap-add NET_BIND_SERVICE \
  --security-opt no-new-privileges:true \
  --read-only \
  --tmpfs /tmp \
  \
  --log-driver json-file \
  --log-opt max-size=100m \
  --log-opt max-file=10 \
  \
  payment:v1.2.3
```

## 12. 故障复盘

### 案例 1:Java 应用 OOM,堆设置过小

**现象**:某公司 Spring Boot 容器化后,启动 30 秒就 OOM,日志 `java.lang.OutOfMemoryError: Java heap space`。

**根因**:
- `--memory=2g`,但 JVM 用的是 `-Xmx1g`(老配置)
- JDK 8u191 之前不感知 cgroup,JVM 看到宿主机 64 GB,堆算到 16 GB
- 容器 limit 2 GB,堆 16 GB,启动即 OOM

**修复**:
```bash
# JDK 8u191+ 自动感知
-XX:+UseContainerSupport -XX:MaxRAMPercentage=75

# 或显式
-Xmx1.5g -Xms1.5g
```

**防范**:
- JDK 升级到 8u191+ 或 JDK 11+
- 用 `MaxRAMPercentage` 而非 `-Xmx`
- CI 跑容器化启动测试

### 案例 2:容器频繁重启,业务中断

**现象**:某服务每 10 分钟重启一次,用户投诉。

**根因**:
- `--restart=always`,容器内进程内存泄漏,每天涨 10 GB
- 超过 `--memory=4g` → OOM → 退出 137 → restart
- 业务中断 5 秒/次

**修复**:
- 修复内存泄漏(根本)
- 加内存监控告警
- 用 K8s 的 livenessProbe + readinessProbe,优雅重启

**防范**:
- 监控 `docker stats` 内存增长趋势
- 设置合理的 restart 上限(`on-failure:5`)
- 关键服务多副本 + 负载均衡

### 案例 3:容器停止时数据库连接未释放

**现象**:滚动更新时,数据库连接数飙升到上限,新连接失败。

**根因**:
- 应用没处理 SIGTERM
- `docker stop` 10s 后 SIGKILL,连接被强制 RST
- 数据库侧连接还在等待 timeout(默认 8 小时)

**修复**:
- 应用注册 SIGTERM handler:关闭 HTTP server → 关闭 DB 连接池 → 退出
- `--stop-timeout=30` 给足时间
- 数据库连接池设 `maxLifetime=30min`(强制回收)

**防范**:
- 所有服务必须处理 SIGTERM
- CI 跑优雅停止测试(发 SIGTERM 后看是否在 N 秒内干净退出)
- 数据库监控空闲连接

### 案例 4:`--read-only` 导致应用崩溃

**现象**:某团队上 `--read-only` 加固安全,容器启动报 `Read-only file system`。

**根因**:
- 应用要写 `/tmp`(临时文件)和 `/var/log/app`(日志)
- 根文件系统只读,这两个目录不可写

**修复**:
```bash
docker run --read-only \
  --tmpfs /tmp:rw,size=64m \
  -v app-logs:/var/log/app \
  myapp
```

**防范**:
- 应用遵循 12-factor:日志写 stdout/stderr,不写文件
- 临时文件用 /tmp(挂 tmpfs)
- 持久数据用 volume

### 案例 5:健康检查脚本错误导致容器一直 unhealthy

**现象**:某团队所有容器 unhealthy,但服务实际正常。

**根因**:
- 健康检查命令 `curl http://localhost/health`,但容器内没装 curl(用 distroless)
- curl 不存在 → exit 127 → unhealthy

**修复**:
```dockerfile
# 用 Python / Node 等运行时自带工具
HEALTHCHECK CMD python -c "import urllib.request; urllib.request.urlopen('http://localhost:8000/health')"
```

或在外部检查:
```bash
# 不在容器内检查,从外部
curl http://localhost:8080/health
```

**防范**:
- 健康检查命令用容器内一定有的工具
- distroless 镜像用 `:debug` 变种验证
- CI 测试健康检查命令是否能执行
