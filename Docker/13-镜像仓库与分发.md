## 3. 核心概念与架构

### 3.1 镜像仓库的核心 API(OCI Distribution Spec)

```
POST   /v2/<name>/blobs/uploads/         # 开始上传层
PATCH  /v2/<name>/blobs/uploads/<uuid>   # 上传层数据
PUT    /v2/<name>/blobs/uploads/<uuid>   # 完成上传
HEAD   /v2/<name>/blobs/<digest>         # 检查层是否存在
GET    /v2/<name>/blobs/<digest>         # 下载层
GET    /v2/<name>/manifests/<tag>        # 获取 manifest
PUT    /v2/<name>/manifests/<tag>        # 上传 manifest
DELETE /v2/<name>/manifests/<tag>        # 删除 manifest
GET    /v2/_catalog                      # 列出所有仓库
GET    /v2/<name>/tags/list              # 列出 tag
```

### 3.2 镜像 push 流程

```
docker push myrepo/myapp:v1

1. 检查本地镜像,分解为 manifest + config + layers
2. 对每层:
   a. HEAD /v2/myapp/blobs/<digest> 检查是否已存在
   b. 不存在:POST uploads/ → PATCH 数据 → PUT 完成
   c. 已存在:跳过(节省带宽)
3. 上传 config(同样流程)
4. 上传 manifest(PUT /manifests/v1)
5. 完成
```

### 3.3 镜像 pull 流程

```
docker pull myrepo/myapp:v1

1. GET /v2/myapp/manifests/v1 → 获取 manifest
2. 解析 manifest,得到 config + layers 的 digest 列表
3. 对每层:
   a. 检查本地是否已有(根据 digest)
   b. 不存在:GET /v2/myapp/blobs/<digest> 下载
4. 下载 config
5. 组装镜像,写入 /var/lib/docker/overlay2/
```

## 5. 底层原理

### 5.1 镜像存储模型

```
Harbor 用 registry:2 作为存储后端,支持:

- filesystem:本地磁盘(默认)
  /data/harbor/registry/docker/registry/v2/
  ├── blobs/sha256/<first-2-chars>/<digest>/data
  └── repositories/<name>/_manifests/
      └── revisions/sha256/<digest>/

- s3:AWS S3 / 阿里 OSS
  镜像层存对象存储,无限扩展

- azure:Azure Blob Storage

- gcs:Google Cloud Storage

- swift:OpenStack Swift
```

### 5.2 GC 机制

```
registry GC 流程:

1. 标记(Mark):
   - 遍历所有 manifest
   - 标记被引用的 layer

2. 清除(Sweep):
   - 删除未被标记的 blob
   - 释放磁盘空间

问题:
- 在线 GC 不停服务,但有窗口期(可能删正在用的)
- 离线 GC 需停服务,但安全

Harbor 改进:
- 在线 GC:基于引用计数,安全
- 离线 GC:停 registry,彻底
```

### 5.3 镜像复制机制

```
Harbor 复制流程:

1. 触发:push 镜像 / 定时 / 手动
2. 源 Harbor 查询要复制的镜像
3. 对每个镜像:
   a. 检查目标是否已有(manifest digest)
   b. 不存在:复制 manifest + layers
   c. 已存在:跳过(去重)
4. 记录复制状态
```

## 7. 常见陷阱与调优

### 7.1 陷阱:Docker Hub 限速

**问题**:匿名拉取 100/6h,登录 200/6h,大集群很快用完。

**修复**:
- 用付费账号(提高限额)
- 用国内镜像源
- 用 Harbor 做代理缓存(proxy cache)

### 7.2 陷阱:Harbor 磁盘满

**原因**:
- 镜像只 push 不 delete
- GC 没配置

**修复**:
```yaml
# 定时 GC
garbage_collection:
  schedule: "0 3 * * *"
  enabled: true

# 保留策略:自动删旧 tag
# Web UI: 项目 → 配置 → 标签保留
# 保留最近 10 个 tag
```

### 7.3 陷阱:镜像层重复上传

**原因**:不同镜像共享层,但每次 push 都 HEAD 检查。

**修复**:
- Harbor 自动去重(基于 digest)
- 共享 base image(推送一次)

### 7.4 陷阱:跨地域复制延迟

**原因**:
- 大镜像(1 GB)跨地域传输慢
- 复制串行

**修复**:
- 预复制(pre-warm):关键镜像提前复制
- 多区域 Harbor + 本地拉取
- 用 P2P 分发(Dragonfly)

### 7.5 调优:Harbor 性能

```yaml
# 数据库连接池
database:
  max_idle_conns: 50
  max_open_conns: 1000

# JobService 并发
jobservice:
  max_job_workers: 20  # 默认 10

# Redis 缓存
external_redis:
  max_idle: 100
  max_active: 500

# 存储:用 S3 而非本地(扩展性)
```

### 7.6 调优:镜像拉取并发

```toml
# containerd
max_concurrent_downloads = 20  # 默认 3
```

### 7.7 调优:镜像分层优化

- 基础镜像统一(共享底层)
- 多阶段构建(减少层数)
- 用 `--squash` 合并层(实验性)

| 维度 | Harbor(自建) | ACR / ECR(托管) |

| 高可用 | 自行 | 内置 |
| 适合 | 多云 / 私有 | 单云 |

| 维度 | Docker Hub | GHCR |
|------|-----------|------|
| 免费 | 有限 | 与 GitHub 集成 |
| 私有仓库 | 收费 | 免费 |

| 适合 | 通用 | GitHub 项目 |

## 11. 综合面试题

### 题 1(原理)
**问**:解释 `docker push` 的完整流程。

**答题要点**:
- 分解镜像为 manifest + config + layers
- 对每层:HEAD 检查是否存在,不存在则上传
- 上传 config(同样 HEAD + 上传)
- 上传 manifest(PUT)
- 仓库返回 digest
- 共享层不重复上传(基于 digest)

### 题 2(架构)
**问**:设计一个支持万级镜像、千节点拉取的企业仓库。

**答题要点**:
- 仓库:Harbor 高可用(多实例 + PostgreSQL 主从 + S3)
- 分发:Dragonfly P2P
- 缓存:边缘节点 registry 缓存
- 多地域:Harbor 复制
- 安全:扫描(Trivy)+ 签名(Cosign)
- RBAC:项目隔离 + 机器人账号
- GC:定时 + 保留策略
- 监控:拉取延迟、成功率、带宽

### 题 3(故障)
**问**:Harbor 磁盘 95%,如何处理?

**答题要点**:
- 看哪些项目占大头(Web UI 统计)
- 配置保留策略(保留最近 10 个 tag)
- 触发 GC
- 检查 GC 历史(是否失败)
- 长期:扩容 / 迁移到 S3
- 紧急:删大镜像(谨慎)
- 监控:磁盘 80% 报警

### 题 4(深度)
**问**:为什么镜像层用 content-addressable(digest)?

**答题要点**:
- digest = SHA256(层内容)
- 内容相同 → digest 相同 → 去重
- 内容变 → digest 变 → 不冲突
- 验证完整性(下载后比对 digest)
- 安全(防篡改)
- 全局唯一(跨仓库)

### 题 5(工业)
**问**:大厂如何保证镜像分发的高可用?

**答题要点**:
- 多地域 Harbor(同城双活 / 异地多活)
- P2P 分发(Dragonfly / Kraken)
- 边缘缓存(节点本地 registry cache)
- 按需加载(Nydus / Stargz)
- 镜像预热(发布前预复制到所有区域)
- 监控:拉取延迟、成功率、带宽
- 容量规划:带宽 × 节点数

### 题 6(安全)
**问**:如何防止未授权镜像被部署?

**答题要点**:
- 仓库:Harbor RBAC + 项目隔离
- 签名:Cosign 签名
- 准入:K8s Admission Controller(Kyverno / OPA)
- 扫描:Trivy CRITICAL 拒绝
- 网络:NetworkPolicy 限制拉取
- 审计:所有 pull 记录
- 案例:未签名镜像拒绝部署

### 题 7(故障)
**问**:某节点拉镜像超时,如何排查?

**答题要点**:
- 看 kubelet / containerd 日志
- 网络:ping / traceroute 到 Harbor
- DNS:nslookup harbor.corp.com
- 证书:openssl s_client
- Harbor 状态:健康检查
- 带宽:是否打满
- 镜像大小:是否过大
- 重试:配 imagePullPolicy

### 题 8(优化)
**问**:镜像拉取慢,如何优化?

**答题要点**:
- 镜像瘦身(多阶段 + distroless)
- 共享基础镜像(缓存命中)
- P2P 分发(Dragonfly)
- 按需加载(Nydus / Stargz)
- 镜像预热
- 多区域 Harbor
- containerd max_concurrent_downloads 调大
- 镜像源优化

### 题 9(架构)
**问**:Harbor 高可用怎么部署?

**答题要点**:
- 多实例(3+ Harbor Core)
- 负载均衡(nginx / F5)
- PostgreSQL 主从(或云托管)
- Redis 主从(任务队列)
- 共享存储(S3 / OSS)
- 共享证书
- 跨地域复制(灾备)
- 监控:Prometheus + Grafana

### 题 10(综合)
**问**:设计一个生产级镜像仓库方案。

**答题要点**:
- 仓库:Harbor 高可用(3 节点 + PG 主从 + S3)
- 网络:VPC 内网 + 公网 LB(限速)
- 认证:LDAP / OAuth + 机器人账号
- RBAC:项目隔离 + 角色(开发/访客/维护)

- 签名:Cosign + 准入控制
- 复制:多地域同步 + 灾备
- GC:定时 + 保留策略
- 监控:Prometheus + 告警
- 容量:存储 10 TB+ 起步,可扩 S3
- 成本:自建 ~$2000/月,云托管按量

## 12. 故障复盘

### 案例 1:Docker Hub 限速导致部署失败

**现象**:某公司凌晨扩容,500 节点同时拉镜像,大部分超时。

**根因**:
- 用 Docker Hub 公共镜像
- 匿名拉取限速,500 节点秒级耗尽

**修复**:
- 镜像同步到 Harbor
- 节点配置 Harbor 为镜像源
- 用 P2P 分发

**防范**:
- 生产不依赖公共仓库
- 镜像预热

### 案例 2:Harbor GC 误删正在用的镜像

**现象**:某 Harbor 执行 GC 后,部分 Pod 拉镜像失败,报 layer not found。

**根因**:
- 在线 GC 窗口期,正在 push 的镜像被误标
- GC 删除了被引用的 layer

**修复**:
- 改用离线 GC(停服务)
- 或升级 Harbor(改进 GC 算法)

**防范**:
- GC 在低峰期(凌晨)
- 监控 GC 后镜像完整性

### 案例 3:跨地域复制延迟

**现象**:某公司北京 push 镜像,杭州 K8s 5 分钟后还拉不到。

**根因**:
- Harbor 复制是异步
- 大镜像(1 GB)传输慢
- 复制串行

**修复**:
- 关键镜像预复制
- 多区域 Harbor + 本地拉取
- 用 P2P 分发

### 案例 4:证书过期导致拉取失败

**现象**:某 Harbor 证书过期,所有节点拉镜像失败。

**根因**:
- 自签证书 1 年有效期
- 没有监控证书过期

**修复**:
- 更新证书
- 节点更新 CA

**防范**:
- 证书监控(提前 30 天告警)
- 用 Let's Encrypt 自动续签
- 或用云厂商托管证书

### 案例 5:镜像层损坏

**现象**:某节点拉镜像报 `digest mismatch`,layer 内容与 digest 不符。

**根因**:
- 磁盘坏块
- 或网络传输错误(罕见,TLS 校验)

**修复**:
- 删除本地损坏层
- 重新拉取
- 检查磁盘健康
