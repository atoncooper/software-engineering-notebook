## 22.2 章节简介

集群密度是容器化成本控制的核心杠杆。单节点从默认 30 容器提升到 200+,意味着同样的业务用 1/7 的机器,成本降 85%。

本章系统讲解集群密度优化的完整路径:
1. **镜像瘦身**: 1GB → 50MB,减少存储/网络/启动开销
2. **资源调优**: request/limit + CPU manager + 巨页
3. **调度优化**: 反亲和 + 拓扑分布 + 在线/离线混部
4. **内核优化**: cgroup v2 + 网络栈 + IO 调度
5. **运行时优化**: containerd + runc + 共享镜像

每节包含工业实测数据,所有优化均经大厂验证。

**本章工业焦点**:
- 字节跳动: 单节点 30 → 200+ 容器
- Google Borg: 单节点 50+ 任务,利用率 70%+
- 阿里双11: 10万节点支撑千万容器
- 在线/离线混部: 利用率 30% → 70%

## 22.3 镜像瘦身(密度优化的基石)

### 22.3.1 镜像对密度的影响

```
单节点存储: 100GB(可用)
单镜像: 1GB
最大镜像数: 100(理论值)
实际(考虑 layer 共享): 50-80

镜像瘦身到 50MB:
最大镜像数: 2000
实际: 500-1000
```

**镜像瘦身优先级**(参考 [15 章](./15-Dockerfile生产模板.md)):

| 优化项 | 体积变化 | 收益 |
|-------|---------|------|
| 多阶段构建 | 1GB → 200MB | 节省 80% |
| distroless/alpine | 200MB → 50MB | 节省 75% |
| 静态编译 + scratch | 50MB → 20MB | 节省 60% |
| 二进制 strip | 20MB → 12MB | 节省 40% |
| upx 压缩 | 12MB → 6MB | 节省 50% |

### 22.3.2 共享 base image

```
不同应用共享 base:
┌──────────────────────────────────┐
│ Distroless base(20MB)           │  ← 共享层
├──────────────────────────────────┤
│ App1(2MB)  App2(3MB)  App3(5MB)│  ← 各自应用层
└──────────────────────────────────┘

节点存储:
- 100 应用,不共享: 100 × 50MB = 5GB
- 100 应用,共享: 20MB + 100 × 5MB = 520MB
节省 90%
```

**实践**: 公司统一 base image,所有应用基于它构建。

### 22.3.3 镜像层复用

```dockerfile
# 所有 Java 应用用同一 base
FROM eclipse-temurin:17-jre-alpine AS base
# 共享 JRE 层(~150MB)

# 应用层仅含业务代码(~5MB)
COPY app.jar /app/app.jar
```

**节点镜像统计**:
```
$ docker images | wc -l
50 个镜像

$ docker system df
Images: 50
Storage: 800MB(而非 50 × 200MB = 10GB)
节省: 92%(层复用)
```

## 22.4 资源调优

### 22.4.1 request/limit 精细化

**问题**: 默认配置浪费严重。

```yaml
# 错误: 浪费
resources:
  requests: { cpu: 1, memory: 1Gi }
  limits:   { cpu: 1, memory: 1Gi }
# 实际使用: cpu 100m, memory 200Mi
# 浪费: 90% CPU, 80% 内存
```

**解决**: 基于 metric server 历史数据调优。

```yaml
# 正确: 精准配置
resources:
  requests:
    cpu: 200m        # 实际使用 × 1.5
    memory: 256Mi
  limits:
    cpu: 500m        # 峰值 × 1.5
    memory: 512Mi
```

**容量计算**:
```
节点: 32C / 64GB
- 系统/K8s 预留: 4C / 8GB
- 可用: 28C / 56GB

应用(0.5C/0.5Gi request):
- CPU 限制: 28 / 0.5 = 56 Pod
- 内存限制: 56 / 0.5 = 112 Pod
- 实际调度: 56 Pod(CPU 瓶颈)

应用(0.2C/0.25Gi request):
- CPU: 28 / 0.2 = 140 Pod
- 内存: 56 / 0.25 = 224 Pod
- 实际: 140 Pod
```

### 22.4.2 CPU manager static 模式

**默认 CFS 配额模式**:
- 时间片轮转,有上下文切换
- 适合共享,但延迟波动

**static 模式**:
- 整数 CPU 独占核心
- 无上下文切换,性能稳定
- 适合延迟敏感应用

```yaml
# K8s 配置
apiVersion: kubelet.config.k8s.io/v1beta1
kind: KubeletConfiguration
cpuManagerPolicy: static
reservedSystemCPUs: "0,1"   # 系统预留
```

```yaml
# Pod 使用(整数 CPU)
resources:
  requests:
    cpu: 4   # 必须整数
  limits:
    cpu: 4
```

**性能对比**:

| 模式 | 延迟 P99 | CPU 利用率 | 上下文切换 |
|------|---------|-----------|-----------|
| CFS(默认) | 5ms | 70% | 5000/s |
| static | 1ms | 80% | 100/s |

### 22.4.3 巨页(HugePages)

```
普通页: 4KB
巨页: 2MB(512 倍)

优势:
- TLB 命中率高(页表项少 512 倍)
- 内存访问快 5-15%
- 适合大内存应用(JVM/DPDK)

劣势:
- 预留内存(不可被普通应用用)
- 配置复杂
```

**配置**:
```bash
# 节点预留巨页
echo 1024 > /proc/sys/vm/nr_hugepages  # 1024 × 2MB = 2GB
```

```yaml
# Pod 使用
spec:
  containers:
  - name: app
    resources:
      requests:
        memory: 4Gi
        hugepages-2Mi: 2Gi
      volumes:
      - name: hugepage
        emptyDir:
          medium: HugePages-2Mi
      volumeMounts:
      - mountPath: /hugepages
        name: hugepage
```

**JVM 使用巨页**:
```bash
java -XX:+UseLargePages -Xms2G -Xmx2G -jar app.jar
```

### 22.4.4 内存回收优化

**cgroup v2 内存回收**:
```bash
# 优先回收非活跃页
memory.swap.max=0          # 禁用 swap
memory.high=80%             # 软限制,触发回收
memory.max=100%             # 硬限制,OOM
```

**K8s 配置**:
```yaml
resources:
  requests:
    memory: 1Gi
  limits:
    memory: 2Gi
# K8s 自动设置 cgroup
```

## 22.5 调度优化

### 22.5.1 反亲和与拓扑分布

**问题**: 默认调度可能把 Pod 集中在少数节点。

**解决**: topologySpreadConstraints。

```yaml
spec:
  topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: kubernetes.io/hostname
    whenUnsatisfiable: ScheduleAnyway  # 尽量均匀
    labelSelector:
      matchLabels:
        app: myapp
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule   # 强制跨 AZ
    labelSelector:
      matchLabels:
        app: myapp
```

**效果**:
```
6 副本,3 节点:
  - 不配置: 可能 4/1/1
  - 配置后: 2/2/2(均匀)
```

### 22.5.2 优先级与抢占

**PriorityClass**:
```yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: online-critical
value: 1000000
globalDefault: false
---
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: batch
value: 100000
preemptionPolicy: PreemptLowerPriority
---
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: free
value: 10000
preemptionPolicy: Never   # 不抢占,等
```

**抢占逻辑**:
```
节点满,新 Pod 调度:
1. 找到能调度的节点(可能需驱逐低优)
2. 驱逐最低优 Pod
3. 调度高优 Pod
```

### 22.5.3 在线/离线混部

**核心思想**:
```
节点资源(64C):
┌──────────────────────────────────┐
│ 在线服务(高优,40C)              │  ← 保障
├──────────────────────────────────┤
│ 离线任务(低优,24C)              │  ← 抢占式
└──────────────────────────────────┘

在线峰值时:
- 在线需求 50C
- 离线被驱逐,让出 10C
- 在线获得 50C

在线低谷时:
- 在线需求 20C
- 离线获得 44C
- 利用率 100%
```

**实现机制**:

**1. cgroup CPU shares**:
```bash
# 在线: shares 1024(高)
# 离线: shares 256(低)
# CPU 紧张时,在线获得 4/5 CPU
```

**2. cpuset 独占**:
```yaml
# 在线独占核心
spec:
  containers:
  - resources:
      requests:
        cpu: 4
  # cpu manager static 模式
```

**3. 内存优先级**:
```bash
# 离线内存优先被回收
echo 1 > /sys/fs/cgroup/.../memory.swappiness
```

**4. IO 调度**:
```bash
# 在线 IO 优先
echo "online" > /sys/block/sda/queue/io_priority
```

### 22.5.4 节点污点与容忍

```yaml
# 节点打污点(专用节点)
kubectl taint nodes node-1 dedicated=online:NoSchedule

# Pod 容忍
spec:
  tolerations:
  - key: dedicated
    value: online
    effect: NoSchedule
```

**场景**:
- 在线专用节点(高优)
- 离线专用节点(Spot,可被驱逐)
- GPU 节点
- 高内存节点

## 22.6 内核与运行时优化

### 22.6.1 cgroup v2

**v1 vs v2**:

| 维度 | v1 | v2 |
|------|----|----|
| 层级 | 每子系统独立 | 统一层级 |
| 性能 | 慢(多文件) | 快(统一) |
| 内存 | usage 含 cache | 区分 |
| 调度 | CFS | CFS + 改进 |

**K8s 启用 v2**:
```bash
# 内核启动参数
grub-set-default --kernel-args="systemd.unified_cgroup_hierarchy=1"

# 验证
mount | grep cgroup
# cgroup2 on /sys/fs/cgroup type cgroup2
```

### 22.6.2 网络优化

**内核参数**:
```bash
# /etc/sysctl.d/99-container.conf

# 高并发连接
net.ipv4.tcp_max_syn_backlog = 65535
net.core.somaxconn = 65535
net.ipv4.tcp_tw_reuse = 1
net.netfilter.nf_conntrack_max = 1048576

# 缓冲区
net.core.rmem_max = 16777216
net.core.wmem_max = 16777216

# 文件描述符
fs.file-max = 2097152
fs.nr_open = 2097152

# inotify(容器多文件)
fs.inotify.max_user_watches = 1048576
```

**网络模式选型**:

| 模式 | 延迟 | 性能 | 隔离 | 适用 |
|------|------|------|------|------|
| bridge | 1-2ms | 中 | ✓ | 默认 |
| macvlan | 0.5ms | 高 | ✓ | 高性能 |
| ipvlan | 0.5ms | 高 | ✓ | 高性能 |
| host | 0.1ms | 极高 | ✗ | 极致性能 |

**CNI 选型**:
- Calico: BGP,性能好
- Cilium: eBPF,性能最佳
- Flannel: 简单,性能一般

### 22.6.3 存储优化

**overlay2 优化**:
```json
// /etc/docker/daemon.json
{
  "storage-driver": "overlay2",
  "storage-opts": [
    "overlay2.override_kernel_check=true"
  ]
}
```

**containerd 配置**:
```toml
# /etc/containerd/config.toml
[plugins."io.containerd.grpc.v1.cri".containerd]
  snapshotter = "overlayfs"

  # 定期 GC
  [plugins."io.containerd.grpc.v1.cri".containerd.snapshotter]
    gc_enabled = true
```

**IO 调度器**:
```bash
# SSD 推荐 none(直通)
echo none > /sys/block/nvme0n1/queue/scheduler

# 机械盘 mq-deadline
echo mq-deadline > /sys/block/sda/queue/scheduler
```

### 22.6.4 containerd 优化

**禁用不需要的功能**:
```toml
[plugins."io.containerd.grpc.v1.cri"]
  # 禁用 image GC(手动管理)
  disable_image_gc = false
  image_gc_interval = "5m"

  # 限制镜像数
  max_container_log_line_size = 16384
```

**镜像拉取优化**:
```toml
[plugins."io.containerd.grpc.v1.cri".registry]
  # 镜像加速
  [plugins."io.containerd.grpc.v1.cri".registry.mirrors."docker.io"]
    endpoint = ["https://mirror.registry.aliyuncs.com"]

  # 并发拉取
  [plugins."io.containerd.grpc.v1.cri".image_decryption]
    key_model = "node"
```

## 22.8 故障复盘

### 22.8.1 故障 1: 密度过高导致雪崩

**背景**: 2024-03,某公司单节点 200 容器,高峰期节点 CPU 100%,所有容器响应慢。

**根因**:
- request 设过低(50m),实际 200m
- 超卖 4 倍
- 单节点故障影响 200 个服务

**修复**:
1. 基于 metric 调 request
2. 限制单节点 maxPods=110
3. HPA 自动扩容

**预防**: request 必须基于历史数据,超卖不超过 1.5x。

### 22.8.2 故障 2: CPU static 模式资源浪费

**背景**: 2024-05,某公司启用 CPU static 后,部分节点 CPU 利用率反而下降。

**根因**:
- static 模式独占核心
- 应用实际使用仅 30% 独占核心
- 70% 核心资源浪费

**修复**:
1. 仅延迟敏感应用用 static
2. 其他应用用 CFS(可共享)
3. 监控 CPU 利用率

**预防**: static 模式慎用,仅适合数据库/中间件等。

### 22.8.3 故障 3: 巨页配置不当导致 OOM

**背景**: 2024-06,某公司配置巨页后,部分应用 OOM。

**根因**:
- 节点预留 50GB 巨页
- 普通应用可用内存减少 50GB
- 部分应用 OOM

**修复**:
1. 仅 JVM 应用用巨页
2. 节点专用(JVM 节点 + 普通节点)
3. 监控巨页使用

**预防**: 巨页专用节点,不全局配置。

### 22.8.4 故障 4: 混部导致在线延迟升高

**背景**: 2024-07,某公司混部后,在线服务 P99 延迟升 20%。

**根因**:
- 离线任务 IO 密集
- 在线 IO 被影响
- cgroup IO 隔离不完整

**修复**:
1. 离线任务限速
2. 在线用专用磁盘
3. IO 调度器配置

**预防**: 混部需测试,IO 隔离关键。

### 22.8.5 故障 5: 镜像层冲突

**背景**: 2024-08,某公司不同应用共享 base,但运行时行为不一致。

**根因**:
- 共享 base 含旧版 lib
- 应用 A 依赖新功能
- 应用 B 兼容旧版

**修复**:
1. base image 版本化
2. 应用显式声明依赖
3. 定期升级 base

**预防**: base image 版本管理,定期升级。

## 22.10 常见陷阱

### 22.10.1 陷阱 1: 过度超卖

**问题**: request 远低于实际,导致节点超载。

**解决**: 超卖不超过 1.5x,基于 metric 数据。

### 22.10.2 陷阱 2: 忽视 IO

**问题**: 只关注 CPU/内存,IO 成为瓶颈。

**解决**: 监控 IO,离线任务限速。

### 22.10.3 陷阱 3: 混部影响在线

**问题**: 离线任务影响在线延迟。

**解决**: IO/网络隔离,优先级保障。

### 22.10.4 陷阱 4: 镜像不一致

**问题**: 共享 base 但版本不同。

**解决**: base 版本化,定期升级。

### 22.10.5 陷阱 5: 静态绑核浪费

**问题**: 应用使用低,独占核心浪费。

**解决**: 仅高使用率应用用 static。

### 22.10.6 陷阱 6: 巨页预留过多

**问题**: 巨页占满内存,普通应用 OOM。

**解决**: 巨页专用节点。

## 22.11 面试题

### Q1: 怎么提升单节点容器密度?

**答**:
5 大优化:
1. **镜像瘦身**: 1GB → 50MB,减少存储
2. **request 调优**: 基于历史数据,合理超卖
3. **CPU static**: 整数核独占,无切换
4. **巨页**: TLB 命中率 +30%
5. **混部**: 在线/离线共享,利用率 70%+

实测: 30 → 200+ Pod,成本降 85%。

### Q2: 在线/离线混部怎么实现?

**答**:
**原理**: 在线峰值驱逐离线,低谷复用资源。

**实现**:
1. PriorityClass 区分优先级
2. cgroup CPU shares 在线高
3. cpuset 在线独占核心
4. 内存离线优先回收
5. IO 在线优先

**收益**: 利用率 30% → 70%+,成本降 50%+。

### Q3: CPU static 模式和 CFS 区别?

**答**:
- **CFS(默认)**: 时间片轮转,可共享,有上下文切换
- **static**: 整数核独占,无切换,性能稳定

| 模式 | 延迟 P99 | 上下文切换 | 适用 |
|------|---------|-----------|------|
| CFS | 5ms | 5000/s | 通用 |
| static | 1ms | 100/s | 延迟敏感 |

### Q4: 巨页有什么用?

**答**:
- 普通 4KB,巨页 2MB/1GB
- TLB 命中率高(页表项少)
- 内存访问快 5-15%
- 适合大内存应用(JVM/DPDK)

**配置**: 节点预留,Pod 显式请求。

### Q5: 怎么避免混部影响在线?

**答**:
1. **PriorityClass**: 在线高优,离线低优
2. **cpuset**: 在线独占核心
3. **IO 隔离**: 在线专用磁盘/限速离线
4. **网络隔离**: 在线优先
5. **监控**: 在线延迟异常立即驱逐离线

### Q6: 镜像瘦身对密度有什么影响?

**答**:
- 镜像小 → 节点存储更多镜像
- 拉取快 → 部署快
- 共享 base → 层复用,节省 90% 存储

实测: 1GB → 50MB,单节点镜像数 50 → 500。

### Q7: topologySpreadConstraints 有什么用?

**答**:
- 控制 Pod 跨节点/AZ 均匀分布
- maxSkew=1 保证最多差 1 个
- 防止集中导致单点故障

### Q8: cgroup v2 比 v1 好在哪?

**答**:
1. 统一层级(简化)
2. 性能更好(少文件操作)
3. 内存统计更准(区分 cache)
4. 改进的 CPU 调度

### Q9: 单节点最大能跑多少 Pod?

**答**:
- K8s 默认 maxPods=110
- 调到 250(需测试)
- 实际受资源/网络/IP 限制
- 大厂实测 200+ Pod(混部)

### Q10: 怎么监控密度是否合理?

**答**:
**指标**:
- 节点 CPU/内存利用率(60-80% 合理)
- Pod throttle 比例(< 5%)
- 调度失败率(< 1%)
- 单节点 Pod 数

**告警**:
- 利用率 > 85% → 扩容
- 利用率 < 30% 持续 7 天 → 缩容
- Pod 数 > 80% maxPods → 接近上限

### 22.12.1 核心要点
