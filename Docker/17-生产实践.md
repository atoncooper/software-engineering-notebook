## 17.3 核心概念

### 17.3.1 容量规划

**4 步法**:

```
1. 需求预测
   ├─ 历史数据(过去 30/90 天)
   ├─ 业务增长(年同比)
   └─ 突发场景(大促/活动)

2. 资源估算
   ├─ CPU: QPS × 单请求 CPU = 总 CPU
   ├─ 内存: 实例数 × 单实例内存
   ├─ 网络: QPS × 平均响应大小
   └─ 存储: 数据量 + 增长率 × 保留期

3. 弹性预留
   ├─ Headroom: 30-50%(应对突发)
   ├─ 多可用区: 跨 AZ 容灾
   └─ 灾备: 1.5x ~ 2x 容量

4. 持续校准
   ├─ 月度容量 review
   ├─ 压测验证极限
   └─ 弹性扩缩容
```

**容量公式**(Web 服务):

```
总 CPU = (QPS × 单请求 CPU_秒) / (目标 CPU 利用率 × 单核性能)
       + 副本数 × 系统开销

例: 10000 QPS,单请求 10ms CPU,目标 70%,4 核机器
   需要 CPU = 10000 × 0.01 / 0.7 = 143 核
   副本数 = 143 / 4 ≈ 36 副本
   预留 30% headroom → 47 副本
```

### 17.3.2 性能调优三层模型

```
┌─────────────────────────────────────┐
│  L1: 应用层调优                      │
│  - 算法/数据结构                     │
│  - 缓存策略                          │
│  - 连接池                            │
│  - 并发模型                          │
├─────────────────────────────────────┤
│  L2: 容器层调优                      │
│  - CPU/memory request/limit         │
│  - CPU manager(static/policy)       │
│  - NUMA 绑定                        │
│  - 巨页(hugepages)                  │
├─────────────────────────────────────┤
│  L3: 内核/系统调优                   │
│  - 内核参数(net.ipv4.tcp_*)         │
│  - 文件描述符限制                    │
│  - 磁盘 IO 调度                      │
│  - 网络栈(net.core.somaxconn)      │
└─────────────────────────────────────┘
```

### 17.3.3 高可用设计

**3 层容错**:

```
L1: 实例级(单 Pod)
  - 健康检查 + 自动重启
  - 资源限制防雪崩

L2: 节点级(单 Node)
  - 多副本 + 反亲和
  - PodDisruptionBudget
  - 节点自愈(自动替换)

L3: 机房级(单 Region)
  - 多可用区部署
  - 跨区流量分发
  - 数据多副本

L4: 地域级(多 Region)
  - 全球负载均衡
  - 数据异地复制
  - 灾难恢复(DR)
```

**SLA 计算**:

```
单实例 SLA = 99% (年宕机 87.6h)
+ 多副本(3 副本,需同时故障) = 99.99% (52.6min)
+ 多可用区 = 99.999% (5.26min)
+ 多地域 = 99.9999% (31.5s)

实际 K8s 生产 SLA 目标: 99.9% ~ 99.95%
```

### 17.3.4 RTO 与 RPO

```
故障发生                 数据恢复
   │                        │
   │←── RTO(恢复时间)──→│
   │                        │
   │←── RPO(数据丢失)──→│
   │  (上次备份到故障点)
```

| 业务等级 | RTO 目标 | RPO 目标 | 备份策略 |
|---------|---------|---------|---------|
| P0(核心) | < 5min | 0 | 同步复制 |
| P1(重要) | < 30min | < 5min | 异步复制 |
| P2(一般) | < 4h | < 1h | 定期备份 |
| P3(边缘) | < 24h | < 24h | 每日备份 |

### 17.3.5 成本治理

```
单实例成本 = (CPU + 内存 + 存储 + 网络) / 实例数

优化方向:
1. 镜像瘦身 → 存储降
2. 资源利用率提升 → 单位算力降
3. 弹性伸缩 → 低谷缩减
4. Spot/抢占式实例 → 降 70%
5. Reserved Instance → 长期降 30-50%
6. 多租户共享 → 复用资源
```

**利用率提升路径**:
```
当前 30% → 50%: request/limit 调优
50% → 70%: 弹性伸缩 + 超卖
70% → 80%: 在线/离线混部
80%+: 极致优化(需冒风险)
```

## 17.4 底层原理

### 17.4.1 CPU manager 与 NUMA

```yaml
# K8s static CPU manager
spec:
  containers:
  - name: app
    resources:
      requests:
        cpu: 4          # 整数核
      limits:
        cpu: 4
```

**static 策略**:
- 整数 CPU request → 独占核心
- 无上下文切换,性能稳定
- 适合延迟敏感型(数据库/中间件)

**NUMA 绑定**:
```
Node 0: CPU 0-15, 内存 0-64GB
Node 1: CPU 16-31, 内存 64-128GB

CPU 0 访问 Node 0 内存: 快(本地)
CPU 0 访问 Node 1 内存: 慢(跨 NUMA,延迟 +50%)
```

**Topology Manager**:
```yaml
spec:
  topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: kubernetes.io/hostname
```

### 17.4.2 内存巨页(HugePages)

```
普通页: 4KB
巨页: 2MB / 1GB

优势:
- TLB 命中率高(页表项少)
- 内存访问快 5-15%
- 适合大内存应用(JVM/DPDK)

劣势:
- 预留内存(不可被普通应用用)
- 配置复杂
```

```yaml
# K8s 使用巨页
spec:
  containers:
  - name: app
    resources:
      requests:
        memory: 4Gi
        hugepages-2Mi: 2Gi
      volumes:
      - name: hugepage
        emptyDir:
          medium: HugePages-2Mi
      volumeMounts:
      - mountPath: /hugepages
        name: hugepage
```

### 17.4.3 网络性能优化

**内核参数调优**:

```bash
# /etc/sysctl.d/99-container.conf

# TCP 连接优化
net.ipv4.tcp_max_syn_backlog = 65535
net.core.somaxconn = 65535
net.ipv4.tcp_tw_reuse = 1
net.ipv4.tcp_fin_timeout = 15

# 缓冲区
net.core.rmem_max = 16777216
net.core.wmem_max = 16777216
net.ipv4.tcp_rmem = 4096 87380 16777216
net.ipv4.tcp_wmem = 4096 65536 16777216

# 连接跟踪(高并发必调)
net.netfilter.nf_conntrack_max = 1048576
net.ipv4.tcp_max_tw_buckets = 1048576

# 文件描述符
fs.file-max = 2097152
fs.nr_open = 2097152

# inotify(容器多文件场景)
fs.inotify.max_user_watches = 1048576
fs.inotify.max_user_instances = 8192
```

**容器内 ulimit**:
```yaml
spec:
  containers:
  - name: app
    resources:
      limits:
        # K8s 1.20+ 支持容器级 ulimit
    securityContext:
      capabilities:
        add: ["SYS_RESOURCE"]
```

### 17.4.4 磁盘 IO 优化

**IO 调度器**:
```bash
# 查看
$ cat /sys/block/sda/queue/scheduler
mq-deadline kyber [bfq] none

# 容器场景推荐: none(SSD) / mq-deadline(机械)
echo none > /sys/block/nvme0n1/queue/scheduler
```

**overlay2 性能优化**:
```bash
# daemon.json
{
  "storage-opts": [
    "overlay2.override_kernel_check=true",
    "overlay2.size=100G"     # 限制 xfs 配额
  ]
}
```

**容器 IO 限制**:
```yaml
# cgroup v2 IO 限制
resources:
  limits:
    cpu: 1
    memory: 1Gi
# K8s 1.29+ 支持
#   devices.io: "100MiB/s"
```

### 17.4.5 在线/离线混部

```
节点资源利用:
┌──────────────────────────────────┐
│ 在线服务(高优)                  │  ← 保障 CPU/memory
│   web/api 等延迟敏感             │
├──────────────────────────────────┤
│ 离线任务(低优)                  │  ← 抢占式,可被驱逐
│   批处理/训练/分析               │
└──────────────────────────────────┘

实现:
- cgroup CPU shares: 在线高,离线低
- cpuset: 在线独占核心,离线用空闲
- 内存回收: 离线优先被回收
- IO 调度: 在线优先
```

```yaml
# K8s PriorityClass
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: online
value: 1000
globalDefault: false
---
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: batch
value: 100
preemptionPolicy: PreemptLowerPriority
globalDefault: false
```

## 17.5 代码实现

### 17.5.1 生产 K8s 部署清单

```yaml
# deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
  namespace: prod
  labels:
    app: myapp
    version: v1
spec:
  replicas: 6
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0   # 永不减少可用
  selector:
    matchLabels:
      app: myapp
  template:
    metadata:
      labels:
        app: myapp
        version: v1
    spec:
      # 1. 优雅退出
      terminationGracePeriodSeconds: 60

      # 2. 反亲和(分散到不同节点)
      affinity:
        podAntiAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 100
            podAffinityTerm:
              labelSelector:
                matchLabels:
                  app: myapp
              topologyKey: kubernetes.io/hostname
        # 跨可用区
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: topology.kubernetes.io/zone
                operator: In
                values: [zone-a, zone-b, zone-c]

      # 3. 资源配置
      containers:
      - name: app
        image: myapp:v1.2.3
        imagePullPolicy: IfNotPresent

        # 资源 request/limit
        resources:
          requests:
            cpu: 500m
            memory: 512Mi
          limits:
            cpu: 1000m
            memory: 1Gi

        # 4. 健康检查
        startupProbe:
          httpGet:
            path: /health
            port: 8080
          failureThreshold: 30
          periodSeconds: 10
        livenessProbe:
          httpGet:
            path: /health
            port: 8080
          periodSeconds: 10
          failureThreshold: 3
          timeoutSeconds: 3
        readinessProbe:
          httpGet:
            path: /ready
            port: 8080
          periodSeconds: 5
          failureThreshold: 3

        # 5. 优雅退出 hook
        lifecycle:
          preStop:
            exec:
              command:
              - sh
              - -c
              - "sleep 10 && /app -shutdown"

        # 6. 安全上下文
        securityContext:
          runAsNonRoot: true
          runAsUser: 65532
          runAsGroup: 65532
          readOnlyRootFilesystem: true
          allowPrivilegeEscalation: false
          capabilities:
            drop: [ALL]
            add: [NET_BIND_SERVICE]

        # 7. 环境变量
        env:
        - name: APP_ENV
          value: production
        - name: LOG_LEVEL
          value: info
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef:
              name: db-secret
              key: password

        # 8. 卷挂载
        volumeMounts:
        - name: tmp
          mountPath: /tmp
        - name: config
          mountPath: /etc/app
          readOnly: true

      # 9. 卷定义
      volumes:
      - name: tmp
        emptyDir:
          medium: Memory    # tmpfs
          sizeLimit: 100Mi
      - name: config
        configMap:
          name: app-config

      # 10. 优先级
      priorityClassName: online-critical

      # 11. 容忍度(可调度到污点节点)
      tolerations:
      - key: dedicated
        value: online
        effect: NoSchedule
```

### 17.5.2 PodDisruptionBudget

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: myapp-pdb
  namespace: prod
spec:
  minAvailable: 4          # 或 maxUnavailable: 1
  selector:
    matchLabels:
      app: myapp
```

**作用**:
- 自愿驱逐(节点维护/升级)时保证最少 4 副本可用
- 防止 K8s 同时驱逐过多 Pod

### 17.5.3 HPA 自动扩缩

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: myapp-hpa
  namespace: prod
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: myapp
  minReplicas: 6
  maxReplicas: 50
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
  - type: Resource
    resource:
      name: memory
      target:
        type: Utilization
        averageUtilization: 80
  # 自定义指标(QPS)
  - type: Pods
    pods:
      metric:
        name: http_requests_per_second
      target:
        type: AverageValue
        averageValue: "1000"
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 30
      policies:
      - type: Percent
        value: 100          # 一次性最多翻倍
        periodSeconds: 30
      - type: Pods
        value: 10
        periodSeconds: 30
      selectPolicy: Max
    scaleDown:
      stabilizationWindowSeconds: 300  # 5min 才缩
      policies:
      - type: Percent
        value: 10          # 一次最多缩 10%
        periodSeconds: 60
```

### 17.5.4 VPA 垂直扩缩

```yaml
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: myapp-vpa
spec:
  targetRef:
    apiVersion: "apps/v1"
    kind: Deployment
    name: myapp
  updatePolicy:
    updateMode: "Auto"     # Off / Initial / Auto
  resourcePolicy:
    containerPolicies:
    - containerName: app
      minAllowed:
        cpu: 100m
        memory: 128Mi
      maxAllowed:
        cpu: 2
        memory: 4Gi
      controlledResources: ["cpu", "memory"]
```

**注意**: VPA Auto 模式会重启 Pod 调整资源,慎用于生产关键服务。

**数据库备份**:

```yaml
# CronJob 备份 MySQL
apiVersion: batch/v1
kind: CronJob
metadata:
  name: mysql-backup
spec:
  schedule: "0 2 * * *"
  jobTemplate:
    spec:
      template:
        spec:
          containers:
          - name: backup
            image: mysql:8
            env:
            - name: MYSQL_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: mysql-secret
                  key: password
            command:
            - sh
            - -c
            - |
              mysqldump -h mysql -u root -p$MYSQL_PASSWORD \
                --all-databases --single-transaction \
                --routines --triggers | gzip > /backup/db-$(date +%Y%m%d).sql.gz
              # 上传 S3
              aws s3 cp /backup/db-$(date +%Y%m%d).sql.gz s3://my-bucket/mysql/
              # 清理 7 天前
              find /backup -name "*.sql.gz" -mtime +7 -delete
          volumeMounts:
          - name: backup
            mountPath: /backup
          volumes:
          - name: backup
            emptyDir: {}
          restartPolicy: OnFailure
```

**原则**:

- **内存 limit 设**: OOM 风险,但不超卖
- **数据库/中间件 limit = 不限**: 性能优先

## 17.8 故障复盘

### 17.8.1 故障 1: 容器密度过高导致雪崩

**背景**: 2024-03,某公司单节点 200 容器,业务高峰期节点 CPU 100%,所有容器响应慢。

**现象**:
- 单节点 200 容器,所有容器 CPU throttling
- 业务 P99 延迟从 50ms 飙到 5s
- 节点 load average > 100
- K8s 调度新 Pod 失败

**根因**:
- request 设过低(50m),实际使用 200m
- 超卖 4 倍,CPU 总需求 > 节点容量
- 单节点故障,影响 200 个服务

**修复过程**:
1. **临时**: 驱逐部分 Pod 到其他节点
2. **彻底**:
   - 基于 metric server 历史数据调整 request
   - 限制单节点最大 Pod 数(maxPods=110)
   - HPA 自动扩容,减少单节点压力
3. **监控**:
   - 节点 CPU > 70% 告警
   - Pod throttle 比例 > 5% 告警

**预防措施**:
- **request 必须基于历史数据**(P0)
- **超卖不超过 1.5x**(CPU)
- **节点 Pod 数限制**(maxPods)
- **HPA + Cluster Autoscaler 配合**

### 17.8.2 故障 2: 跨可用区流量集中

**背景**: 2024-04,某公司某 AZ 故障,50% 流量受影响。

**现象**:
- 3 个 AZ,理论上单 AZ 故障影响 33%
- 实际某 AZ 故障,50% 流量异常
- 排查发现 Pod 集中在某 2 个 AZ

**根因**:
- 部署未配置 topologySpreadConstraints
- K8s 调度器为省资源,集中在资源充足的 AZ
- 某 AZ 故障时影响超出预期

**修复过程**:
```yaml
spec:
  topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule   # 强制
    labelSelector:
      matchLabels:
        app: myapp
  - maxSkew: 1
    topologyKey: kubernetes.io/hostname
    whenUnsatisfiable: ScheduleAnyway  # 尽量
    labelSelector:
      matchLabels:
        app: myapp
```

**预防措施**:
- **必配 topologySpreadConstraints**(P0)
- **跨 AZ 副本数均匀**: maxSkew=1
- **定期演练**: 模拟单 AZ 故障
- **DNS 健康检查**: 故障 AZ 自动摘除

### 17.8.3 故障 3: 内存 limit 过低导致 OOM

**背景**: 2024-05,某公司 Java 应用频繁 OOM,业务告警。

**现象**:
- Java 应用 OOMKilled
- 实际堆使用仅 1GB,limit 4GB
- JVM 未识别容器 limit

**根因**:
```
# 老版本 JVM(< 8u191)
JVM 看主机内存(64GB)
  → 默认堆 = 主机内存 / 4 = 16GB
  → 但容器 limit = 4GB
  → 堆超过 limit → OOM

# 新版本 JVM(8u191+)
JVM 看容器 limit
  → 默认堆 = limit / 4 = 1GB
```

应用用了 JDK 8u131,未识别容器 limit。

**修复过程**:
1. **升级 JVM**: 8u191+ 或 JDK 11+
2. **显式指定堆**:
   ```dockerfile
   ENV JAVA_OPTS="-XX:+UseContainerSupport \
                  -XX:MaxRAMPercentage=75 \
                  -XX:InitialRAMPercentage=50"
   CMD ["java", "-XX:MaxRAMPercentage=75", "-jar", "app.jar"]
   ```
3. **监控**: JVM 堆使用率 + GC 频率

**预防措施**:
- **JVM 必须 8u191+**(P0)
- **显式 MaxRAMPercentage**(75% 留余量)
- **JVM 监控**: 堆/GC/线程
- **压测验证**: 模拟流量峰值

### 17.8.4 故障 4: DNS 解析慢导致请求超时

**背景**: 2024-06,某公司微服务调用偶发超时,业务异常。

**现象**:
- 服务间调用偶发 5s 超时
- 应用日志: `DNS lookup timed out`
- CoreDNS 日志: 大量 SERVFAIL

**根因**:
- 集群 5000+ 服务,DNS 查询量大
- CoreDNS 默认 cache 容量 1000,不足
- ndots:5 导致每次查询多次

**修复过程**:
1. **CoreDNS 调优**:
   ```yaml
   # CoreDNS ConfigMap
   .:53 {
     cache {
       success 4096 300
       denial 4096 60
       prefetch 5 30s 20%
     }
   }
   ```
2. **Pod DNS 配置**:
   ```yaml
   spec:
     dnsConfig:
       options:
       - name: ndots
         value: "2"           # 默认 5,改 2 减少查询
       - name: single-request-reopen
       - name: timeout
         value: "2"
     dnsPolicy: ClusterFirst
   ```
3. **应用层 DNS cache**: JVM/Go 缓存 DNS

**预防措施**:
- **CoreDNS 资源充足**(CPU/memory)
- **CoreDNS cache 调优**(根据集群规模)
- **ndots 调整**(2 通常够)
- **应用 DNS 缓存**: 减少查询频率

### 17.8.5 故障 5: 镜像仓库故障导致无法扩容

**背景**: 2024-07,某公司突发流量需要扩容,但镜像拉取失败,无法扩容。

**现象**:
- HPA 触发扩容,新 Pod 一直 ContainerCreating
- 日志: `ImagePullBackOff`
- 镜像仓库 Harbor 宕机

**根因**:
- 所有镜像在 Harbor,无备份
- 节点本地无镜像缓存
- Harbor 单点故障,无法拉取

**修复过程**:
1. **临时**: 紧急恢复 Harbor
2. **多 registry 镜像**:
   - 主 Harbor + 备 Harbor(实时同步)
   - 关键镜像同时推到 ACR/ECR
3. **节点预拉取**: 关键镜像 cron 拉到所有节点
4. **P2P 分发**: Dragonfly,registry 故障也能从 Peer 拉

**预防措施**:
- **registry 高可用**(P0): 多副本 + 多区域
- **关键镜像多源**: 不同 registry 备份
- **节点镜像缓存**: daemon.json 配置
- **P2P 分发**: 单点故障可降级
- **定期 DR 演练**: 模拟 registry 故障

## 17.10 常见陷阱

### 17.10.1 陷阱 1: request = limit

**问题**:
```yaml
resources:
  requests: { cpu: 1, memory: 1Gi }
  limits:   { cpu: 1, memory: 1Gi }
```

- CPU 突发被限制(无 burst)
- 内存稍超即 OOM

**建议**:
- CPU: request < limit(允许突发)
- 内存: request = limit(避免 OOM 影响其他)

### 17.10.2 陷阱 2: 忽略 startupProbe

**问题**:
```yaml
livenessProbe:
  httpGet:
    path: /health
  initialDelaySeconds: 60   # 等 60s 才检查
```

- 慢启动应用(Java)可能 90s 才 ready
- 60s 时检查失败,Pod 重启
- 进入无限重启循环

**解决**:
```yaml
startupProbe:
  httpGet:
    path: /health
  failureThreshold: 30
  periodSeconds: 10   # 5min 启动期
livenessProbe: ...    # 启动后才开始
```

### 17.10.3 陷阱 3: 缺少 PDB

**问题**: 节点维护时,所有副本被同时驱逐。

**解决**:
```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
spec:
  minAvailable: 2     # 或 maxUnavailable: 1
  selector:
    matchLabels:
      app: myapp
```

### 17.10.4 陷阱 4: ConfigMap 热更新未生效

**问题**: 更新 ConfigMap,但 Pod 未重新加载。

**原因**:
- ConfigMap 是 volumeMount 的,Pod 内文件已更新
- 但应用未监听文件变化,未重新加载

**解决**:
1. **应用监听文件变化**: inotify + 热加载
2. **Reloader 工具**: 自动滚动更新
   ```yaml
   metadata:
     annotations:
       reloader.stakater.com/auto: "true"
   ```
3. **手动滚动**: `kubectl rollout restart`

### 17.10.5 陷阱 5: 单点 namespace

**问题**: 所有服务都在 default namespace,无法隔离。

**建议**:
- 不同业务不同 namespace
- 用 NetworkPolicy 隔离
- RBAC 按 namespace 授权
- ResourceQuota 限制单 namespace 资源

### 17.10.6 陷阱 6: 节点 maxPods 过低

**问题**: 默认 maxPods=110,某些场景不够。

**调优**:
```yaml
# kubelet 配置
maxPods: 250

# 同时调 ENI(aws)
--max-pods=250
```

**注意**: maxPods 过大会增加 K8s 控制面压力,建议 110-250 之间。

## 17.11 面试题

### Q1: 怎么做容器化应用的容量规划?

**答**:
4 步法:
1. **需求预测**: 历史数据 + 业务增长 + 突发场景
2. **资源估算**: QPS × 单请求资源 = 总资源
3. **弹性预留**: 30% headroom + 跨 AZ + 灾备
4. **持续校准**: 月度 review + 压测 + 弹性

**公式**:
- 总 CPU = QPS × 单请求 CPU / (目标利用率 × 单核性能)
- 副本数 = 总 CPU / 单副本 CPU × 1.3(headroom)

### Q2: K8s 生产环境资源 request/limit 怎么设?

**答**:
**CPU**:
- request = 平均使用 × 1.2
- limit = 峰值 × 1.5(允许突发)

**内存**:
- request = 平均使用 × 1.2
- limit = 峰值 × 1.5(OOM 风险,谨慎超卖)

**原则**:
- 数据库/中间件 limit 不限(性能优先)
- 在线服务 CPU limit 设(防突发影响)
- 离线任务 request 低(可被驱逐)

### Q3: 怎么保证 K8s 高可用?

**答**:
4 层容错:
1. **Pod 级**: 健康检查 + 自动重启
2. **节点级**: 多副本 + 反亲和 + PDB
3. **AZ 级**: topologySpreadConstraints + 跨 AZ
4. **区域级**: 多区域部署 + 全球负载均衡

**关键配置**:
- replicas >= 3,跨 3 AZ
- PDB minAvailable >= 2
- 反亲和到不同节点
- 健康检查(startup/liveness/readiness)
- HPA 自动扩缩
- Cluster Autoscaler 节点扩缩

### Q4: 在线/离线混部怎么做?

**答**:
**原理**: 在线峰值时驱逐离线,低谷时复用资源。

**实现**:
1. **PriorityClass**: 在线高优,离线低优
2. **cgroup**: 在线高 shares,离线低
3. **cpuset**: 在线独占核心,离线用空闲
4. **内存**: 离线优先被回收
5. **驱逐**: 节点压力大时驱逐离线

**收益**:
- 节点容器数 30 → 200+
- 利用率 30% → 70%+
- 成本降 50%+

### Q5: 怎么做容器化应用的灾备?

**答**:
**3 层灾备**:

1. **单集群**:
   - 多副本 + 跨 AZ
   - PDB 防驱逐
   - HPA 自动扩缩

2. **多集群**(同城):
   - 双活/主备
   - 数据同步(Cassandra/MySQL 主从)
   - 流量切换(全局 LB)

3. **多区域**(异地):
   - 全球 DNS 切流
   - 数据异步复制
   - DR 演练(年度)

**RTO/RPO 目标**:
- 同城双活: RTO < 5min, RPO = 0
- 异地灾备: RTO < 30min, RPO < 5min

### Q6: 怎么提升节点资源利用率?

**答**:
6 大杠杆:
1. **镜像瘦身**: 减少存储/网络
2. **request 调优**: 基于历史数据,合理超卖
3. **HPA + VPA**: 弹性扩缩
4. **混部**: 在线/离线共享节点
5. **Spot 实例**: 离线任务用,降 70%
6. **Reserved**: 长期容量,降 30-50%

**目标**: 利用率 30% → 70%+,成本降 50%+。

### Q7: K8s 滚动更新怎么避免中断?

**答**:
5 个关键点:
1. **maxUnavailable=0**: 永不减少可用副本
2. **readinessProbe**: 新 Pod ready 才加入
3. **preStop hook**: 给旧 Pod 处理存量请求时间
4. **应用优雅退出**: 处理 SIGTERM
5. **terminationGracePeriodSeconds**: 留足退出时间

```yaml
strategy:
  rollingUpdate:
    maxSurge: 1
    maxUnavailable: 0
template:
  spec:
    terminationGracePeriodSeconds: 60
    containers:
    - name: app
      lifecycle:
        preStop:
          exec:
            command: ["sh", "-c", "sleep 10"]
```

### Q8: 怎么做容器化应用的监控?

**答**:
4 层监控(参考 [14 章](./14-监控与日志.md)):
1. **业务指标**: RED(QPS/错误/延迟)
2. **应用指标**: JVM/连接池/线程池
3. **容器指标**: CPU/内存/IO(cAdvisor)
4. **节点指标**: 主机 CPU/磁盘(node-exporter)

**告警分级**:
- P0: 业务全停(电话)
- P1: 部分功能异常(短信)
- P2: 指标异常(IM)
- P3: 容量预警(邮件)

### Q9: 怎么控制容器化成本?

**答**:
6 板斧:
1. **镜像瘦身**: 1GB → 50MB
2. **request 调优**: 避免 over-provision
3. **HPA**: 低谷缩减,峰值扩容
4. **Cluster Autoscaler**: 节点动态
5. **Spot/抢占式**: 离线任务降 70%
6. **混部**: 在线/离线共享

**关键指标**:
- 资源利用率 60-80%
- 单实例成本持续下降
- 部署频率高(快速迭代)

### Q10: 怎么做混沌工程?

**答**:
**目标**: 主动注入故障,验证系统韧性。

**工具**: Chaos Mesh / Litmus / Gremlin

**场景**:
1. **Pod 故障**: 随机 kill Pod
2. **网络故障**: 延迟/丢包/分区
3. **节点故障**: not-ready / drain
4. **IO 故障**: 慢盘/错误
5. **DNS 故障**: 解析失败/延迟

**实施**:
- 测试环境: 每周
- 预发环境: 每月
- 生产环境: 谨慎(小范围)

**收益**:
- 提前发现隐患
- 验证容错机制
- 提升团队应急能力
