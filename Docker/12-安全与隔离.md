# 12 - 安全与隔离

> 容器不是安全沙箱。本章把容器隔离边界、capability、seccomp、AppArmor、镜像签名、rootless 讲到安全工程师水平。

---

## 1. 问题定义与边界

### 1.1 本章解决什么

- 把 **容器隔离边界** 讲清:哪里弱、为什么弱、怎么补

- 把 **镜像安全**(签名、扫描、SBOM)讲到生产级
- 把 **rootless 容器** 讲到能落地
- 把 **大厂容器安全实践** 讲到能复用

### 1.2 本章不解决什么

- 不讲 K8s RBAC / NetworkPolicy(见 [19-容器生态对比](./19-容器生态对比.md))
- 不讲供应链安全流水线(见 [24-工业实战-供应链安全](./24-工业实战-供应链安全.md))

> **关键认知**:容器安全是 **纵深防御**——单层都不够,多层叠加才安全。默认配置只是起点,生产必须加固。

## 2. 直觉解释

### 2.1 容器安全类比:银行金库

```
   银行金库的多层防御              容器的多层防御
   ────────────────                ────────────
   1. 围墙(物理边界)              1. namespace(视图隔离)
   2. 门禁(身份验证)              2. cgroup(资源限制)
   3. 摄像头(监控)                3. capability(权限裁剪)
   4. 保险柜(物理防护)            4. seccomp(syscall 过滤)
   5. 报警系统(响应)              5. AppArmor/SELinux(强制访问控制)
   6. 巡逻(主动检查)              6. 漏洞扫描 + 签名验证
   7. 独立房间(强隔离)            7. gVisor / Kata(VM 级)
```

**核心思想**:任何单层都可能被攻破,多层叠加提升攻击成本。

### 2.2 容器 vs VM 隔离强度

```
   VM(硬件隔离)                  容器(进程隔离)
   ──────────────                  ─────────────
   独立内核                       共享内核 ← 根本弱点
   Hypervisor 隔离                namespace 隔离
   逃逸需 Hypervisor 漏洞         逃逸需内核漏洞
   
   攻击面:小                      攻击面:大(整个内核)
   密度:低                        密度:高
   性能:有开销                    性能:接近原生
```

## 3. 核心概念与架构

### 3.1 容器安全六层防御

```
┌─────────────────────────────────────────────────┐
│  Layer 6: 强隔离运行时                          │
│  gVisor / Kata / Firecracker                    │
├─────────────────────────────────────────────────┤
│  Layer 5: 镜像安全                              │
│  签名(Cosign) + 扫描(Trivy) + SBOM           │
├─────────────────────────────────────────────────┤
│  Layer 4: 强制访问控制                          │
│  AppArmor / SELinux                             │
├─────────────────────────────────────────────────┤
│  Layer 3: syscall 过滤                          │
│  seccomp profile                                │
├─────────────────────────────────────────────────┤
│  Layer 2: 权限裁剪                              │
│  capabilities drop / no-new-privileges          │
├─────────────────────────────────────────────────┤
│  Layer 1: 隔离与限制                            │
│  namespace + cgroup + rootless                  │
├─────────────────────────────────────────────────┤
│  Layer 0: 基础设施                              │
│  内核版本 / 补丁 / 节点加固                     │
└─────────────────────────────────────────────────┘
```

### 3.2 Linux Capabilities

传统 Unix 只有 root / non-root 二分。Capabilities 把 root 权限拆成 40+ 个细粒度权限。

| capability | 能力 | 默认 |
|------------|------|------|
| CAP_CHOWN | 改文件属主 | ✓ |
| CAP_DAC_OVERRIDE | 忽略文件权限 | ✓ |
| CAP_FOWNER | 忽略属主限制 | ✓ |
| CAP_KILL | 发信号给任意进程 | ✓ |
| CAP_SETGID | 改 GID | ✓ |
| CAP_SETUID | 改 UID | ✓ |
| CAP_NET_BIND_SERVICE | 绑定 < 1024 端口 | ✓ |
| CAP_NET_RAW | 原始套接字(ping) | ✓ |
| CAP_SYS_CHROOT | chroot | ✓ |
| CAP_SYS_PTRACE | ptrace(调试) | ✓ |
| CAP_SYS_ADMIN | 几乎所有管理操作 | ✓(危险) |
| CAP_SYS_MODULE | 加载内核模块 | ✗ |
| CAP_SYS_TIME | 改系统时间 | ✗ |

> **关键**:默认容器有 14 个 capabilities,但很多不需要。`--cap-drop ALL --cap-add <needed>` 是生产基线。

### 3.3 seccomp

seccomp(secure computing mode)过滤进程能调用的 syscall。

```json
// /etc/docker/seccomp/default.json(简化)
{
  "defaultAction": "SCMP_ACT_ERRNO",
  "syscalls": [
    {
      "names": ["accept", "bind", "brk", "chdir", ...],
      "action": "SCMP_ACT_ALLOW"
    },
    {
      "names": ["keyctl", "mount", "reboot", "swapon", ...],
      "action": "SCMP_ACT_ERRNO"
    }
  ]
}
```

Docker 默认 seccomp profile 阻止约 60 个危险 syscall(如 `keyctl`、`mount`、`reboot`)。

### 3.4 AppArmor vs SELinux

| 维度 | AppArmor | SELinux |
|------|----------|---------|
| 模型 | 路径-based | 标签-based |
| 配置 | 简单(profile 文件) | 复杂(policy 模块) |
| 发行版 | Ubuntu / Debian | RHEL / CentOS |
| 启用 | `--security-opt apparmor=profile` | `--security-opt label=user:role:type` |
| 学习曲线 | 低 | 高 |

## 4. 操作流程与命令

### 4.1 查看与裁剪 capabilities

```bash
# 查看当前容器 capabilities
docker run --rm alpine cat /proc/1/status | grep Cap
# CapInh: 0000000000000000
# CapPrm: 00000000a80425fb
# CapEff: 00000000a80425fb
# CapBnd: 00000000a80425fb
# CapAmb: 0000000000000000

# 解码
docker run --rm alpine cat /proc/1/status | grep CapEff | \
  awk '{print $2}' | capsh --decode

# 默认 14 个 capabilities
```

```bash
# 裁剪:删除所有,加回必需
docker run -d \
  --cap-drop ALL \
  --cap-add NET_BIND_SERVICE \
  nginx

# 验证
docker exec <id> cat /proc/1/status | grep Cap
```

### 4.2 启用 seccomp

```bash
# 用默认 profile(已默认启用)
docker run --security-opt seccomp=default.json nginx

# 完全禁用(不推荐)
docker run --security-opt seccomp=unconfined nginx

# 自定义 profile
docker run --security-opt seccomp=/etc/docker/seccomp/strict.json nginx
```

### 4.3 启用 AppArmor

```bash
# Ubuntu 默认装了 AppArmor
# 查看 profile
sudo apparmor_status

# 加载 profile
sudo apparmor_parser -r /etc/apparmor.d/docker-nginx

# 容器使用
docker run --security-opt apparmor=docker-nginx nginx
```

### 4.4 no-new-privileges

```bash
# 防止子进程提权(setuid 等)
docker run --security-opt no-new-privileges nginx
```

> **关键**:`no-new-privileges` 防止容器内通过 setuid 程序(如 sudo)提权。

### 4.5 rootless 容器

```bash
# 安装 rootless Docker
curl -fsSL https://get.docker.com/rootless | sh

# 启动
systemctl --user start docker-rootless

# 用法与普通 Docker 一样
docker run -d -p 8080:80 nginx
# 容器内 root,宿主机普通用户
```

```bash
# Podman 默认 rootless
podman run -d -p 8080:80 nginx
```

### 4.6 只读根文件系统

```bash
docker run -d \
  --read-only \
  --tmpfs /tmp \
  -v app-logs:/var/log/app \
  nginx
```

### 4.7 镜像扫描

```bash
# Trivy 扫描
trivy image nginx:1.25

# Grype 扫描
grype nginx:1.25

# Docker Scout(Docker 官方)
docker scout cves nginx:1.25
```

### 4.8 镜像签名

```bash
# Cosign 签名
cosign sign --key cosign.key myrepo/myapp:v1

# 验证
cosign verify --key cosign.pub myrepo/myapp:v1

# K8s 准入控制(用 Kyverno)
# 拒绝未签名镜像
```

## 5. 底层原理

### 5.1 容器逃逸的常见路径

```
路径 1:内核漏洞
  Dirty COW(CVE-2016-5195)
  → 容器内写宿主文件
  → 逃逸

路径 2:runc 漏洞
  CVE-2019-5736
  → 容器内覆盖宿主 runc 二进制
  → 下次 docker exec 时执行恶意 runc
  → 逃逸

路径 3:危险挂载
  docker run -v /:/host ...
  → 容器内 chroot /host
  → 直接宿主 root

路径 4:CAP_SYS_ADMIN
  → mount /proc
  → 访问宿主进程
  → 逃逸

路径 5:Docker socket
  docker run -v /var/run/docker.sock:/var/run/docker.sock ...
  → 容器内控制 dockerd
  → 创建特权容器
  → 逃逸

路径 6:特权容器
  docker run --privileged ...
  → 所有 capabilities + 所有设备访问
  → 直接逃逸
```

### 5.2 capability 在内核中的实现

```c
// 内核 task_struct
struct task_struct {
    kernel_cap_t cap_effective;   // 当前有效权限
    kernel_cap_t cap_inheritable; // 可继承
    kernel_cap_t cap_permitted;   // 允许的
    kernel_cap_t cap_bounding;    // 边界
    kernel_cap_t cap_ambient;     // 环境变量
};

// 检查权限时
if (capable(CAP_NET_BIND_SERVICE)) {
    // 允许绑定 < 1024 端口
}
```

### 5.3 seccomp-BPF

```
seccomp 用 BPF 过滤 syscall:

应用 → syscall
         ↓
       BPF filter(seccomp profile)
         ↓
       ALLOW / ERRNO / KILL

例:禁止 mount syscall
  BPF 规则:if (syscall == __NR_mount) return ERRNO(EPERM);
```

## 6. 代码与配置示例

### 6.1 生产级安全配置

```bash
docker run -d \
  --name web \
  \
  # ── Layer 1: 隔离 ──
  --network mynet \              # 不用 host
  --cgroupns private \          # 私有 cgroup ns
  \
  # ── Layer 2: 权限裁剪 ──
  -u 10001:10001 \              # 非 root
  --cap-drop ALL \              # 删所有
  --cap-add NET_BIND_SERVICE \  # 加回必需
  --security-opt no-new-privileges:true \
  \
  # ── Layer 3: syscall 过滤 ──
  --security-opt seccomp=/etc/docker/seccomp/strict.json \
  \
  # ── Layer 4: 强制访问控制 ──
  --security-opt apparmor=docker-strict \
  \
  # ── Layer 5: 文件系统 ──
  --read-only \                 # 根只读
  --tmpfs /tmp:rw,size=64m \   # 临时文件
  --tmpfs /var/run \           # PID 等
  -v nginx-conf:/etc/nginx:ro \ # 配置只读
  \
  # ── 资源限制 ──
  --cpus="2" \
  --memory="1g" \
  --pids-limit="100" \
  --ulimit nofile=65535:65535 \
  \
  # ── 日志 ──
  --log-driver json-file \
  --log-opt max-size=100m \
  --log-opt max-file=10 \
  \
  nginx:1.25@sha256:abc123...
```

### 6.3 AppArmor profile

```
#include <tunables/global>

profile docker-strict flags=(attach_disconnected,mediate_deleted) {
  #include <abstractions/base>

  network inet tcp,
  network inet udp,
  network inet icmp,

  deny network raw,
  deny network packet,

  deny mount,
  deny umount,

  deny /sys/[^f]*/** wklx,
  deny /sys/f[^s]*/** wklx,
  deny /sys/fs/[^c]*/** wklx,
  deny /sys/fs/c[^g]*/** wklx,
  deny /sys/fs/cg[^r]*/** wklx,

  deny @{PROC}/* w,
  deny @{PROC}/sys/kernel/[^s][^h][^m]* wklx,
  deny @{PROC}/sys/kernel/shm* wklx,

  deny /var/lib/docker/** wklx,
}
```

## 7. 常见陷阱与调优

### 7.1 陷阱:`--privileged` 滥用

```bash
# ❌ 危险:特权容器,所有 capabilities + 所有设备
docker run --privileged ...

# ✓ 仅加必需权限
docker run --cap-add NET_ADMIN ...
```

> **规则**:永不使用 `--privileged`。特殊情况(如容器内跑 Docker)用 rootless 或 Kata。

### 7.2 陷阱:挂载 Docker socket

```bash
# ❌ 等同 root
docker run -v /var/run/docker.sock:/var/run/docker.sock ...

# 攻击:
docker run -v /:/host alpine chroot /host
```

### 7.3 陷阱:挂载宿主敏感路径

```bash
# ❌ 危险
docker run -v /:/host ...
docker run -v /etc:/etc ...
docker run -v /root:/root ...
```

### 7.4 陷阱:root 用户运行

```dockerfile
# ❌ 默认 root
FROM nginx
CMD ["nginx"]

# ✓ 显式非 root
FROM nginx
RUN useradd -m -u 10001 app
USER 10001:10001
```

### 7.5 陷阱:不验证镜像来源

```bash
# ❌ 拉任意镜像
docker pull unknownrepo/myapp:latest

# ✓ 验证签名 + 扫描
cosign verify --key cosign.pub myrepo/myapp:v1
trivy image myrepo/myapp:v1
```

### 7.6 调优:镜像扫描策略

```bash
# CI 中嵌入
trivy image --exit-code 1 --severity CRITICAL myrepo/myapp:v1
# CRITICAL 漏洞不通过

# 忽略已知误报
trivy image --ignorefile .trivyignore --severity HIGH,CRITICAL myrepo/myapp:v1
```

### 7.7 调优:定期重扫

```bash
# 已部署镜像每 7 天重扫
0 3 * * * /opt/scan-running-images.sh
```

## 9. 与其他方案的关系

### 9.1 Docker vs Podman(安全维度)

| 维度 | Docker | Podman |
|------|--------|--------|
| 默认 root | 是 | 否(rootless) |
| daemon | root 守护进程 | 无 |
| socket | /var/run/docker.sock | per-user |
| 逃逸影响 | 整个宿主 | 用户级 |
| 适用 | 通用 | 安全敏感 |

### 9.2 runc vs gVisor vs Kata

| 维度 | runc | gVisor | Kata |
|------|------|--------|------|
| 隔离 | namespace | 用户态内核 | microVM |
| 内核 | 共享 | 应用→gVisor→内核 | 独立 VM 内核 |
| 性能 | 1× | 0.2-0.5× | 0.5-0.8× |
| 兼容 | 100% | 部分 syscall | 100% |
| 启动 | < 1s | 2-5s | 1-3s |
| 适用 | 通用 | 多租户、不可信 | 强隔离、合规 |

### 9.3 镜像签名:Cosign vs Notary

| 维度 | Cosign | Notary v1 | Notary v2 |
|------|--------|-----------|-----------|
| 来源 | Sigstore | Docker | Docker |
| 透明日志 | Rekor | 无 | 有 |
| 密钥 | KMS / HSM | 自管 | KMS |
| 生态 | 主流 | 旧 | 新 |
| 现状 | 活跃 | 维护 | 活跃 |

> **趋势**:Cosign 是事实标准。

## 11. 综合面试题

### 题 1(原理)
**问**:为什么容器不能像 VM 一样当作安全沙箱?

**答题要点**:
- 共享内核,内核漏洞可逃逸(Dirty COW 等)
- namespace 是视图隔离,不是权限隔离
- 容器内 root 默认有 14 个 capabilities
- 攻击面大:整个内核 + 内核模块
- 强隔离需 gVisor / Kata / Firecracker

### 题 2(实战)
**问**:如何把一个 nginx 容器加固到生产级?

**答题要点**:
- 非 root 用户(-u 10001:10001)
- cap-drop ALL + cap-add NET_BIND_SERVICE
- seccomp profile
- AppArmor profile
- no-new-privileges
- read-only rootfs + tmpfs
- 资源限制(cpu/memory/pids)
- 镜像扫描 + 签名
- 网络隔离(自定义网络)
- 日志限制

### 题 3(故障)
**问**:容器内被植入挖矿程序,如何排查是否逃逸到宿主?

**答题要点**:
- 宿主 `ps aux | grep -i miner`
- 宿主 `netstat -tlnp` 看异常端口
- 宿主 `last` 看异常登录
- 检查 `/etc/passwd`、`/etc/crontab`
- 容器日志:`docker logs`
- 审计:`auditd` 日志
- 内核:`dmesg`
- 隔离:立即下线节点,镜像取证
- 修复:升级内核、runc,改密码

### 题 4(深度)
**问**:解释 CVE-2019-5736 runc 逃逸的原理与防御。

**答题要点**:
- 原理:容器内进程可打开 `/proc/self/exe`(runc 二进制)的文件描述符
- 攻击:容器内覆盖 runc 二进制为恶意代码
- 触发:下次 `docker exec` 执行被覆盖的 runc
- 逃逸:恶意 runc 以 root 在宿主执行
- 防御:升级 runc ≥ 1.0-rc6,用只读 runc 二进制

### 题 5(架构)
**问**:设计一个多租户容器平台的安全方案。

**答题要点**:
- 运行时:Kata Containers(VM 级隔离)
- 网络:NetworkPolicy + VPC 隔离
- 存储:每租户独立卷,加密
- 镜像:签名 + 扫描 + 准入控制
- RBAC:K8s namespace + RBAC
- 审计:所有 API 调用记录
- 监控:Falco 实时检测
- 容器逃逸检测:Falco + Tracee
- 数据隔离:每租户独立 namespace + etcd 加密
- 合规:等保 / SOC 2

### 题 6(工业)
**问**:大厂如何做镜像供应链安全?

**答题要点**:
- CI 嵌入:Trivy / Grype 扫描
- 签名:Cosign + Rekor 透明日志
- SBOM:syft 生成物料清单
- 准入:K8s Admission Controller 拦截未签名
- 运行时:Falco 检测异常
- 基础镜像:统一公司维护,定期更新
- 漏洞响应:Log4Shell 后 24 小时内全集群扫描
- 详见 [24-工业实战-供应链安全](./24-工业实战-供应链安全.md)

### 题 7(深度)
**问**:rootless 容器的局限是什么?

**答题要点**:
- 性能:USER ns 有 5-10% 开销
- 端口:不能绑 < 1024(需 sysctl 调整)
- 网络:slirp4netns 性能不如原生
- 存储:overlay 在用户态实现(fuse-overlayfs)
- 兼容:部分镜像不兼容(需 /proc 等)
- K8s:1.25 才开始支持
- 监控:cAdvisor 需适配

### 题 8(安全)
**问**:如何防止容器内 fork bomb?

**答题要点**:
- `--pids-limit=200`(限制进程数)
- `--ulimit nproc=65535:65535`
- seccomp 限制 clone(激进)
- cgroup v2 + pids.max
- 监控:容器进程数告警
- 应用:限制线程池大小

### 题 9(故障)
**问**:Docker socket 被挂载到容器,如何评估风险?

**答题要点**:
- 等同 root:容器可控制 dockerd
- 攻击:docker run -v /:/host alpine chroot /host
- 检测:容器内是否有 docker CLI
- 修复:不挂载 docker.sock
- 替代:用 Docker API + TLS + RBAC
- 监控:auditd 记录 docker.sock 访问
- 案例:Jenkins 容器常用 docker.sock,需严格隔离

### 题 10(综合)
**问**:设计一个生产级容器安全方案,涵盖构建、部署、运行。

**答题要点**:
- 构建:
  - 基础镜像统一(公司维护)
  - 多阶段构建 + distroless
  - 非 root + read-only
  - Trivy / Grype 扫描
  - Cosign 签名 + SBOM
- 部署:
  - 镜像仓库:Harbor + 签名验证
  - 准入控制:Kyverno / OPA Gatekeeper
  - 网络策略:Calico / Cilium
  - RBAC:K8s namespace + Role
- 运行:
  - 容器:cap-drop ALL + seccomp + AppArmor
  - 资源限制:cpu/memory/pids
  - 监控:Falco + Prometheus
  - 日志:Loki + 审计
  - 升级:定期重扫,滚动升级
- 强隔离:Kata(敏感租户)
- 容器逃逸:Falco + 节点隔离 + 自动响应

## 12. 故障复盘

### 案例 1:`--privileged` 导致挖矿逃逸

**现象**:某团队跑了一个不可信镜像,用 `--privileged`,几小时后宿主被挖矿。

**根因**:
- `--privileged` 给所有 capabilities + 所有设备
- 容器内可挂载宿主磁盘
- 直接逃逸

**修复**:
- 不用 `--privileged`
- cap-drop ALL + 必需权限
- 用 Kata 跑不可信镜像

**防范**:
- 禁止 `--privileged`(K8s PSA restricted)
- 准入控制拦截
- 镜像扫描

### 案例 2:Docker socket 挂载导致逃逸

**现象**:某 Jenkins 容器挂载 docker.sock 用于构建,被攻击者利用逃逸。

**根因**:
- Jenkins 有 RCE 漏洞
- 攻击者通过 docker.sock 控制 dockerd
- docker run -v /:/host alpine chroot /host

**修复**:
- Jenkins 不直接挂 docker.sock
- 用 Docker-in-Docker(独立 daemon)
- 或用 Kaniko(无特权构建)
- 严格 RBAC + 审计

### 案例 3:Log4Shell 漏洞响应

**现象**:2021 年 12 月 Log4Shell(CVE-2021-44228)爆发,影响所有用 Log4j 的容器。

**响应**:
- 24 小时内全集群扫描(Trivy)
- 找出所有含漏洞镜像
- 紧急升级 Log4j
- 重新构建 + 推送 + 滚动更新
- WAF 加规则拦截 JNDI 注入

**教训**:
- 必须有 SBOM(知道用了哪个版本的 Log4j)
- 必须有镜像扫描 + 定期重扫
- 必须有应急响应流程
- 详见 [24-工业实战-供应链安全](./24-工业实战-供应链安全.md)

### 案例 4:容器内 sudo 提权

**现象**:某容器以非 root 运行,但镜像内有 sudo,被攻击者提权。

**根因**:
- 镜像内有 sudo(基础镜像带)
- sudo 是 setuid root
- 攻击者通过应用漏洞执行 sudo

**修复**:
- Dockerfile 删除 sudo:`RUN apt remove -y sudo`
- `--security-opt no-new-privileges:true`(禁止 setuid 提权)
- 用 distroless(无 shell、无 sudo)

### 案例 5:镜像含敏感信息泄漏

**现象**:某团队把 AWS key 写进 Dockerfile ENV,镜像推到公开 Docker Hub,被爬虫扫到。

**根因**:
- Dockerfile 写明文密码
- `docker history` 能看到所有层
- 公开仓库被爬

**修复**:
- 立即吊销 AWS key
- 重新构建(不含 secret)
- 用 BuildKit `--mount=type=secret`
- 运行时注入(K8s Secret)
- CI 加 secret 扫描(gitleaks)
