## 19.3 核心概念

### 19.3.1 容器生态演进时间线

```
2013: Docker 发布(容器化普及)
   │
2014: Kubernetes 发布(Google 开源 Borg 经验)
   │
2015: CNCF 成立(K8s 捐赠)
      OCI 成立(开放容器标准)
      Docker Swarm 发布(独立工具)
   │
2016: Docker 1.12 集成 Swarm(swarm mode)
      containerd 捐赠给 CNCF
   │
2017: CRI 接口标准化
      K8s 1.8 默认容器运行时切换到 containerd
      Mesos 衰落
   │
2018: K8s 1.11 GA(生产就绪)
      Podman/Buildah 发布(Red Hat)
   │
2020: Docker 企业版卖 Mirantis
      dockershim 弃用预告
   │
2022: K8s 1.24 移除 dockershim
      K8s 100% CRI(containerd/CRI-O)
   │
2024: K8s 占容器编排 95%+
      containerd 占运行时 80%+
      BuildKit 成默认构建器
```

### 19.3.2 OCI 标准(参考 [11 章](./11-OCI规范与运行时.md))

```
OCI 标准
   │
   ├─ Image Spec(镜像规范)
   │  └─ 镜像格式/manifest/config/layer
   │
   └─ Runtime Spec(运行时规范)
      └─ 容器生命周期/namespace/cgroup

实现:
- Image Spec: Docker 镜像 / OCI 镜像
- Runtime Spec: runc / crun / runsc / kata
```

### 19.3.3 CRI 接口

```
K8s kubelet
    │
    │ CRI(Container Runtime Interface)
    ▼
┌─────────────┐
│ CRI Shim    │
├─────────────┤
│ containerd  │  ← 主流
│ CRI-O       │  ← Red Hat 主推
│ dockershim  │  ← 已移除(K8s 1.24)
└─────────────┘
    │
    │ OCI Runtime
    ▼
┌─────────────┐
│ runc        │  ← 默认
│ crun        │  ← C 实现,更轻量
│ gVisor      │  ← 沙箱(用户态内核)
│ Kata        │  ← 轻量 VM
└─────────────┘
```

## 19.4 底层原理

### 19.4.1 K8s vs Swarm 架构对比

**K8s 架构**:

```
┌──────────────────────────────────────────┐
│            Control Plane                  │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ │
│  │ API      │ │ Scheduler│ │ CM       │ │
│  │ Server   │ │          │ │          │ │
│  └──────────┘ └──────────┘ └──────────┘ │
│  ┌──────────┐ ┌──────────┐               │
│  │ etcd     │ │ CC-Manager│              │
│  │ (KV DB)  │ │          │              │
│  └──────────┘ └──────────┘               │
└──────────────────────────────────────────┘
        │
        ▼ watch
┌──────────────────────────────────────────┐
│              Worker Nodes                 │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ │
│  │ kubelet  │ │ kube-prox│ │ container│ │
│  │          │ │ y        │ │ runtime  │ │
│  └──────────┘ └──────────┘ └──────────┘ │
└──────────────────────────────────────────┘
```

**Swarm 架构**:

```
┌──────────────────────────────────────────┐
│            Manager Nodes                  │
│  ┌──────────┐ ┌──────────┐               │
│  │ Swarm    │ │ Raft     │               │
│  │ Manager  │ │ Consensus│               │
│  └──────────┘ └──────────┘               │
└──────────────────────────────────────────┘
        │
        ▼ gRPC
┌──────────────────────────────────────────┐
│              Worker Nodes                 │
│  ┌──────────┐ ┌──────────┐               │
│  │ Swarm    │ │ Docker   │               │
│  │ Worker   │ │ Engine   │               │
│  └──────────┘ └──────────┘               │
└──────────────────────────────────────────┘
```

**关键差异**:

| 维度 | K8s | Swarm |
|------|-----|-------|
| 状态存储 | etcd(独立 KV) | Raft(内置) |
| API | REST + watch | gRPC |
| 组件 | 多组件(API/Sched/CM/CC) | 单一 Manager |
| 扩展 | CRD/operator | 无 |
| 复杂度 | 高 | 低 |

### 19.4.2 containerd vs CRI-O

**containerd 架构**:

```
kubelet
   │ CRI
   ▼
containerd
   ├─ containerd-shim(每个容器一个)
   │   └─ runc
   ├─ image pull/push
   ├─ snapshotter(overlay2)
   └─ CNI(网络)
```

**CRI-O 架构**:

```
kubelet
   │ CRI
   ▼
CRI-O
   ├─ conmon(监控容器)
   │   └─ runc
   ├─ image pull/push(用 containers/storage)
   └─ CNI(网络)
```

**对比**:

| 维度 | containerd | CRI-O |
|------|-----------|-------|
| 来源 | Docker 抽离 | Red Hat 专为 K8s |
| 复杂度 | 中 | 低 |
| 功能 | 丰富(含非 K8s) | 仅 K8s |
| 默认 | K8s 主流 | OpenShift |
| 生态 | 大 | 小 |

### 19.4.3 runc vs gVisor vs Kata

```
┌─────────────────────────────────────┐
│ 容器进程                            │
├─────────────────────────────────────┤
│ runc: 共享内核                       │
│   ├─ namespace + cgroup             │
│   ├─ 内核: 主机内核                  │
│   ├─ 性能: 接近原生                  │
│   └─ 隔离: 弱(内核漏洞可逃逸)       │
├─────────────────────────────────────┤
│ gVisor: 用户态内核                  │
│   ├─ 拦截系统调用                    │
│   ├─ 内核: 用户态实现(_go)          │
│   ├─ 性能: 慢 10-50%(syscall 拦截) │
│   └─ 隔离: 强(无内核共享)           │
├─────────────────────────────────────┤
│ Kata: 轻量 VM                       │
│   ├─ 每容器一个 VM                  │
│   ├─ 内核: 独立 guest kernel        │
│   ├─ 性能: 慢 5-20%(VM 开销)       │
│   └─ 隔离: 极强(硬件级)            │
└─────────────────────────────────────┘
```

**性能对比**(nginx QPS):

| 运行时 | QPS | 延迟 P99 | 启动时间 |
|--------|-----|---------|---------|
| runc | 50000 | 5ms | 0.1s |
| gVisor | 30000 | 15ms | 0.5s |
| Kata | 45000 | 8ms | 2s |
| VM(传统) | 45000 | 8ms | 30s |

### 19.4.4 BuildKit vs Buildah vs Kaniko

| 工具 | 来源 | 特点 | 适用 |
|------|------|------|------|
| Dockerfile + BuildKit | Docker/Moby | 默认,功能强 | 通用 |
| Buildah | Red Hat | 无 daemon,脚本化 | K8s CI |
| Kaniko | Google | K8s 内构建,无 daemon | K8s CI |
| img |Jessie Frazelle | 无 daemon,客户端 | 本地 |
| makisu | Uber | 分布式构建 | 大规模 |

**Kaniko 工作原理**:

```
K8s Pod
  ├─ Kaniko container
  │   ├─ 解析 Dockerfile
  │   ├─ 逐条执行(无 docker daemon)
  │   ├─ snapshot 每层
  │   └─ 推送 registry
  └─ workspace emptyDir
```

**为什么需要无 daemon 构建**:
- K8s Pod 内无 docker daemon
- Docker-in-Docker(dind)需要特权,安全风险
- Kaniko/Buildah 无需特权,适合 K8s

### 19.5.2 containerd 配置

`/etc/containerd/config.toml`:

```toml
version = 2

[plugins."io.containerd.grpc.v1.cri"]
  # 沙箱镜像(替换 pause)
  sandbox_image = "registry.k8s.io/pause:3.9"

  # 容器运行时
  [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runc]
    runtime_type = "io.containerd.runc.v2"
    [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runc.options]
      SystemdCgroup = true   # 用 systemd cgroup

  # gVisor 沙箱
  [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.gvisor]
    runtime_type = "io.containerd.runsc.v1"

  # Kata 容器
  [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.kata]
    runtime_type = "io.containerd.kata.v2"

  # 镜像仓库镜像
  [plugins."io.containerd.grpc.v1.cri".registry.mirrors."docker.io"]
    endpoint = ["https://mirror.registry.aliyuncs.com"]

# 镜像拉取
[plugins."io.containerd.grpc.v1.cri".image_decryption]
  key_model = "node"
```

**K8s RuntimeClass**:

```yaml
# gVisor
apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata:
  name: gvisor
handler: gvisor
---
# Kata
apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata:
  name: kata
handler: kata
---
# 使用
apiVersion: apps/v1
kind: Deployment

  template:
    spec:
      runtimeClassName: gvisor   # 用 gVisor 隔离

      - name: app
        image: myapp
```

### 19.5.4 Buildah 脚本化构建

```bash
#!/bin/bash
# build.sh - Buildah 构建

# 1. 拉基础镜像
container=$(buildah from golang:1.21-alpine)

# 2. 复制代码
buildah copy $container go.mod go.sum /app/
buildah copy $container . /app/

# 3. 运行构建
buildah run $container -- sh -c "cd /app && go mod download"
buildah run $container -- sh -c "cd /app && CGO_ENABLED=0 go build -o /out/app"

# 4. 创建最终镜像(基于 distroless)
final=$(buildah from gcr.io/distroless/static-debian12:nonroot)
buildah copy $final /out/app /app   # 注意:从主机复制,需要先 mount

# 5. 配置
buildah config --entrypoint '["/app"]' $final
buildah config --user 65532:65532 $final
buildah config --port 8080 $final

# 6. 提交镜像
buildah commit $final myapp:v1

# 7. 推送
buildah push myapp:v1 docker://registry/myapp:v1
```

### 19.6.1 K8s vs Swarm 部署对比

**K8s 部署 MySQL**:

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mysql
spec:
  serviceName: mysql
  replicas: 3
  selector:
    matchLabels:
      app: mysql

    metadata:
      labels:
        app: mysql

      containers:
      - name: mysql

        - name: MYSQL_ROOT_PASSWORD

            secretKeyRef:
              name: mysql-secret

  - metadata:
      name: data
    spec:
      accessModes: ["ReadWriteOnce"]
      resources:
        requests:
          storage: 100Gi
```

**Swarm 部署 MySQL**:

```yaml
# docker-compose.yml(Swarm 模式)
version: "3.9"
services:
  mysql:
    image: mysql:8
    environment:
      MYSQL_ROOT_PASSWORD_FILE: /run/secrets/db_password
    secrets:
      - db_password
    volumes:
      - mysql-data:/var/lib/mysql
    deploy:
      replicas: 1
      placement:
        constraints:
          - node.role == manager

secrets:
  db_password:
    external: true

  mysql-data:
```

**对比**:
- K8s: YAML 多,但功能强(StatefulSet/PVC)
- Swarm: 简洁,但功能有限(无 StatefulSet)

## 19.7 工业案例与基准数据

### 19.7.1 案例 1: K8s 击败 Swarm 的关键节点

**时间线**:
- 2015: K8s 1.0 发布,Swarm 独立工具
- 2016: Swarm 集成 Docker,Docker 公司强力推广
- 2017: 关键转折 — Google/AWS/Azure 联合支持 K8s
- 2018: K8s 1.11 GA,生产就绪
- 2020: Docker 企业版卖 Mirantis
- 2022: dockershim 移除,K8s 完全脱离 Docker

**K8s 胜出的关键因素**:
1. **生态**: CNCF 推动,云厂商共建
2. **扩展性**: CRD/operator 生态丰富
3. **Google 背书**: Borg 经验,可信度高
4. **云厂商力推**: AWS EKS / Azure AKS / GCP GKE
5. **社区**: 贡献者数远超 Swarm

**经验教训**:
- 技术好不等于赢,生态是关键
- 标准化(open)击败私有(closed)
- 云厂商支持至关重要

### 19.7.2 案例 2: 阿里 ACK vs 自研

**演进**:
- 2014: 自研容器平台(基于 LXC)
- 2016: 引入 K8s(ACK 前身)
- 2018: 全栈 K8s(ACK 1.0)
- 2020: Serverless K8s(ASK)
- 2024: ACK 单集群 1万节点

**为何选 K8s**:
- 规模大(双11)
- 需要生态(Prometheus/Grafana/...)
- 自定义需求(CRD/operator)
- 多云/混合云

### 19.7.3 案例 3: Netflix Titus 演进

**演进**:
- 2015: 自研 Titus(基于 Mesos)
- 2018: 迁移到 K8s
- 2020: 完全 K8s

**为何转 K8s**:
- Mesos 社区衰落
- K8s 生态成熟
- 与 AWS EKS 集成

## 19.8 故障复盘

### 19.8.1 故障 1: dockershim 移除导致集群不可用

**背景**: 2022 年 K8s 1.24 移除 dockershim,某公司未及时迁移,集群升级后所有 Pod 创建失败。

**现象**:
- K8s 1.24 升级后,新 Pod 一直 ContainerCreating
- kubelet 日志: `Failed to create pod: no container runtime found`
- 节点仍有 docker,但 K8s 不识别

**根因**:
- K8s 1.24 移除 dockershim
- 节点仍用 docker 作为运行时
- K8s 无法通过 CRI 与 docker 通信

**修复过程**:
1. 紧急回退到 K8s 1.23
2. 节点迁移到 containerd
   ```bash
   # 安装 containerd
   apt-get install containerd
   # 配置
   cat > /etc/containerd/config.toml <<EOF
   version = 2
   [plugins."io.containerd.grpc.v1.cri"]
     sandbox_image = "registry.k8s.io/pause:3.9"
   EOF
   # 启动
   systemctl enable containerd
   systemctl start containerd
   ```
3. Kubelet 配置改用 containerd
   ```yaml
   # /etc/kubernetes/kubelet.conf
   kind: KubeletConfiguration
   containerRuntime: remote
   containerRuntimeEndpoint: unix:///run/containerd/containerd.sock
   ```
4. 重新加入集群

**预防措施**:
- **及时关注 K8s deprecation**(P0)
- **新集群直接用 containerd**
- **升级前充分测试**
- **Mirantis Containerd 兼容方案**(若必须用 docker CLI)

### 19.8.2 故障 2: gVisor 兼容性问题

**背景**: 2024-04,某公司尝试用 gVisor 增强安全,部分应用异常。

**现象**:
- 部分容器启动失败
- 应用日志: `syscall not permitted`
- 性能下降 30%

**根因**:
- gVisor 拦截系统调用,部分 syscall 不支持
- 应用依赖特定内核功能(如某些 ioctl)
- gVisor 用户态内核实现有限

**修复过程**:
1. 识别不兼容应用
   ```bash
   # 查看 gVisor 失败日志
   journalctl -u containerd | grep runsc
   ```
2. 改用 Kata(更兼容)
   ```yaml
   runtimeClassName: kata
   ```
3. 性能敏感应用回到 runc
4. 建立兼容性测试集

**预防措施**:
- **gVisor 需测试兼容性**(P0)
- **性能敏感应用不用 gVisor**
- **强隔离用 Kata**(更兼容)
- **建立运行时选型决策树**

### 19.8.3 故障 3: BuildKit 缓存膨胀

**背景**: 2024-05,某公司 CI runner 磁盘频繁告警,排查发现 BuildKit 缓存膨胀。

**现象**:
- CI runner 磁盘 80%+
- 缓存目录 /var/lib/buildkit 占 100GB+
- 构建变慢

**根因**:
- BuildKit 缓存无自动清理
- 每次构建都新增层,旧层未删
- 没有配置 GC

**修复过程**:
1. 配置 BuildKit GC
   ```toml
   # /etc/buildkit/buildkitd.toml
   [worker.oci]
     gc = true
     gckeepstorage = "10GB"

     [[worker.oci.gcpolicy]]
       keepDuration = "168h"      # 保留 7 天
       keepBytes = "10GB"
       all = true

     [[worker.oci.gcpolicy]]
       keepBytes = "5GB"
       all = false                # 仅保留必要层
   ```
2. 定期清理 cron
3. 监控缓存大小

**预防措施**:
- **配置 GC 策略**(P0)
- **监控缓存大小**
- **定期清理**
- **CI runner 用临时盘**

## 19.10 常见陷阱

### 19.10.1 陷阱 1: 过度依赖 Docker CLI

**问题**: 团队习惯 docker 命令,K8s 转 containerd 后不适应。

**解决**:
- 用 `nerdctl`(containerd 的 docker 兼容 CLI)
- 或 `crictl`(K8s 标准 CLI)
- 逐步过渡到 kubectl

### 19.10.2 陷阱 2: 混用编排器

**问题**: 一个公司同时用 K8s + Swarm + Nomad,运维复杂。

**解决**: 统一到 K8s(或 K3s)。

### 19.10.3 陷阱 3: 轻量 K8s 用错场景

**问题**: K3s 用于大规模生产(> 100 节点),出现性能问题。

**解决**:
- K3s 适合 < 50 节点
- 大规模用 K8s
- K3s 也可外接 etcd 支持更大规模

### 19.10.4 陷阱 4: gVisor 性能盲点

**问题**: 用 gVisor 后,IO 密集应用性能降 50%。

**解决**:
- 测试 gVisor 兼容性
- 性能敏感用 runc
- 强隔离用 Kata

### 19.10.5 陷阱 5: Kaniko 慢

**问题**: Kaniko 构建比 Docker 慢 2 倍。

**解决**:
- 启用 Kaniko 缓存
- 用 BuildKit(更快)
- 或 Buildah

### 19.10.6 陷阱 6: 跨集群通信复杂

**问题**: 多 K8s 集群互通,网络配置复杂。

**解决**:
- 用 Submariner / Cilium 集群互联
- 或服务网格(Istio multi-cluster)
- 或 KubeFed(已弃用)/ Karmada

## 19.11 面试题

### Q1: K8s 为什么击败 Swarm?

**答**:
5 大原因:
1. **生态**: CNCF 推动,云厂商共建
2. **扩展性**: CRD/operator 生态
3. **Google 背书**: Borg 经验
4. **云厂商力推**: EKS/AKS/GKE
5. **社区贡献**: 远超 Swarm

**核心**: 技术好不够,生态是关键。

### Q2: dockershim 是什么?为什么移除?

**答**:
- dockershim: K8s 早期支持 Docker 的适配层
- Docker 不直接兼容 CRI 接口
- dockershim 是临时方案

**移除原因**:
- 维护负担重
- Docker = containerd + runc,直接用 containerd 更高效
- 推动 CRI 标准化

**影响**:
- K8s 1.24+ 不再支持 Docker
- 节点改用 containerd/CRI-O
- 镜像仍兼容(OCI 标准)

### Q3: containerd 和 docker 区别?

**答**:
- **Docker**: 完整容器平台(含 CLI + daemon + containerd + runc + buildkit + compose)
- **containerd**: 仅容器运行时(Docker 的子集)

**关系**: Docker 内部用 containerd。

**K8s 选 containerd 原因**:
- 轻量(无 Docker daemon)
- CRI 原生支持
- 性能更好

### Q4: gVisor 和 Kata 区别?

**答**:
| 维度 | gVisor | Kata |
|------|--------|------|
| 实现 | 用户态内核 | 轻量 VM |
| 隔离 | syscall 拦截 | 硬件虚拟化 |
| 性能 | 慢 30-50% | 慢 5-20% |
| 兼容性 | 弱(部分 syscall) | 强(完整内核) |
| 启动 | 0.5s | 2s |
| 适用 | 不可信代码 | 强隔离需求 |

### Q5: K3s 和 K8s 区别?

**答**:
- **K3s**: 轻量 K8s,单二进制
- **K8s**: 完整组件,多二进制

**K3s 优化**:
- 内置 containerd
- SQLite 替代 etcd(< 5 节点)
- 内置 Traefik
- 单二进制 < 100MB

**适用**:
- K3s: 边缘/IoT/小规模
- K8s: 大规模生产

### Q6: Nomad 和 K8s 区别?

**答**:
| 维度 | Nomad | K8s |
|------|-------|-----|
| 来源 | HashiCorp | Google/CNCF |
| 复杂度 | 低 | 高 |
| 多负载 | ✓(Java/原生/qemu) | 仅容器 |
| 生态 | 小 | 大 |
| 适用 | 简单/多负载 | 容器化 |

### Q7: BuildKit 比 Docker build 好在哪?

**答**:
1. **并行构建**: 多阶段并行
2. **缓存挂载**: `--mount=type=cache`
3. **secret mount**: 安全传递密钥
4. **SSH mount**: 拉私有仓库
5. **更快**: 5-10x

### Q8: Kaniko 为什么适合 K8s?

**答**:
- 无需 docker daemon
- 无需特权(dind 需要)
- 在 K8s Pod 内运行
- 安全性好

**劣势**: 比 BuildKit 慢 2x。

### Q9: Podman 和 Docker 区别?

**答**:
- **Docker**: C/S 架构,需 daemon
- **Podman**: 无 daemon,直接运行

**Podman 优势**:
- 无 daemon,更安全
- Rootless 默认
- 兼容 docker CLI
- systemd 集成

**劣势**: 生态弱,部分工具不兼容。

### Q10: 怎么选编排器?

**答**:
决策树:
```
规模 > 50 节点? → K8s
├─ 资源受限? → K3s
├─ 多负载? → Nomad
├─ 简单场景? → Swarm(谨慎)
└─ 本地开发 → kind/k3d
```

**通用建议**: 99% 选 K8s(或 K3s)。

## 19.12 总结

### 19.12.1 核心要点

1. **K8s 一统天下**: 95%+ 市场份额
2. **containerd 主流运行时**: 80%+ 份额
3. **BuildKit 成默认构建器**: 替代 docker build

6. **Nomad 适合多负载**: 容器 + 非容器
7. **OCI 标准统一**: 镜像/运行时互通

### 19.12.2 工业定位

- **大厂**: K8s + containerd + runc(安全用 gVisor/Kata)
- **边缘**: K3s
- **多负载**: Nomad
- **历史**: Mesos/Swarm 逐渐退出

### 19.12.3 选型决策

```
编排器:
├─ 大规模生产 → K8s
├─ 边缘/小规模 → K3s

└─ 本地 → kind/k3d

运行时:
├─ 通用 → runc
├─ 不可信 → gVisor
└─ 强隔离 → Kata

构建:
├─ 通用 → BuildKit
├─ K8s CI → Kaniko
└─ 脚本化 → Buildah

仓库:
├─ 公开 → Docker Hub
├─ 私有 → Harbor
└─ 云上 → ACR/ECR/GCR
```
