## 26.2 章节简介

容器化并不天然省钱。事实上,如果没有系统化的成本治理,容器化往往让成本**上升 30-50%**。原因:

1. **资源浪费隐蔽** — 开发者填 `request: 1, limit: 4`,实际只用 0.1
2. **超卖雪崩风险** — 节点超卖但突发时雪崩,被迫多买节点
3. **存储爆炸** — 镜像版本爆炸、日志无限制、PV 不清理
4. **网络费用高** — 跨 AZ 流量、公网回源、NAT 网关
5. **工具链开销** — Prometheus、ELK、Jaeger 自身就吃资源
6. **人力成本** — K8s 工程师薪资高于传统运维

本章基于 **FinOps (Financial Operations)** 框架,给出容器化成本的系统化分析方法:

- **成本结构拆解** — 计算/存储/网络/软件/人力
- **可见性建设** — 标签体系 + 成本归因
- **优化手段** — 资源调优/调度优化/Spot/混部
- **治理机制** — 配额 + 预算 + 告警 + 工单审批
- **大厂实践** — 阿里/字节/Netflix/Google 的成本治理路径

**核心理念:** 容器化降本不是"减少资源",而是"提高利用率"。从平均 10-20% 利用率提升到 50-60%,等于成本砍 60%。

**Inform 阶段** — 知道钱花在哪了
- 标签体系 (label)
- 成本归因到团队/产品/环境
- 实时成本看板

**Optimize 阶段** — 减少浪费
- 资源配比优化 (request/limit 调整)
- Spot/Preemptible 实例
- 混部 (在线+离线)
- 镜像瘦身/存储清理

**Operate 阶段** — 制度化
- 配额 + 预算
- 异常告警 + 工单审批
- Showback/Chargeback (成本回流业务)
- 成本 KPI

### 26.3.3 资源利用率指标

| 指标 | 定义 | 健康范围 |
|------|------|----------|
| **CPU Utilization** | 实际 CPU / 节点 CPU | 40-70% (生产) |
| **Memory Utilization** | 实际内存 / 节点内存 | 50-80% |
| **Pod Density** | Pod 数 / 节点 | 30-100 (取决于应用) |
| **Resource Efficiency** | 实际使用 / request | 60-100% |
| **Over-provisioning Rate** | (limit - 实际) / 实际 | < 50% |
| **Stranded Resources** | 已分配未使用资源 | < 10% |

**典型问题数据：**
- 大部分集群 CPU 利用率 **5-15%**
- 内存利用率 **20-40%**
- 60% Pod 资源 request 远高于实际使用
- 30% PV 创建后从未使用

## 26.4 底层原理

### 26.4.1 K8s 调度与成本的关系

```
传统部署:
  物理机 → 应用 A (4核8GB, 实际用 1核2GB)
                  浪费 3核6GB,利用率 25%

容器化部署 (理想):
  物理机 → 4个 Pod (各 1核2GB, 实际用 1核2GB)
                  利用率 100%

容器化部署 (现实):
  物理机 → 4个 Pod (各 request 1核2GB limit 4核8GB, 实际用 0.5核1GB)
                  调度基于 request,节点装满 4个 Pod
                  但 limit 是 4核8GB,节点超卖 4x
                  突发时雪崩,被迫加节点
                  实际利用率 25%, 但买了 4 倍机器
```

**核心矛盾：** 调度基于 request,但用户习惯把 limit 设很高 "以防万一",导致:
- request 低 → 节点超卖 → 突发雪崩
- limit 高 → 应用无法实际使用 → 资源闲置

**解决思路：**
- 用 VPA (Vertical Pod Autoscaler) 自动调整 request 基于历史使用
- 关键服务 request = limit (Guaranteed QoS)
- 用 HPA 基于实际负载扩容,而非靠 limit 留余地

### 26.4.3 成本归因模型

```
节点成本 (EC2 + EBS + 网络)
         │
         ▼
按 Pod 资源 request 比例分摊
         │
         ├─ Pod A (request 1核2GB) → 25% 节点成本
         ├─ Pod B (request 2核4GB) → 50% 节点成本
         ├─ Pod C (request 1核2GB) → 25% 节点成本
         └─ 系统组件 (kubelet/proxy) → 10% 不可分摊
         
         ▼
按 Pod 标签归因到团队/项目
         │
         ├─ Pod A (team=payment) → payment 团队
         ├─ Pod B (team=order)   → order 团队
         └─ Pod C (team=payment) → payment 团队
         
         ▼
Showback 报表: payment 团队用了 $5000, order 团队用了 $10000
Chargeback 报表: 这部分成本从业务预算中扣除
```

```yaml
# cost-alerts.yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: cost-alerts
  namespace: kubecost
spec:
  groups:
  - name: cost-management
    interval: 1h
    rules:

    # 1. 节点成本突增 (>20%)
    - alert: CostSpikeDetected
      expr: |
        avg_over_time(kubecost_cluster_management_cost[1h]) >
        1.2 * avg_over_time(kubecost_cluster_management_cost[7d])
      for: 1h
      labels:
        severity: warning
      annotations:
        summary: "集群成本突增 20%+"

    # 2. 资源利用率低
    - alert: LowCPUUtilization
      expr: |
        avg_over_time(container_cpu_usage_seconds_total:sum_rate[1h]) /
        kube_node_status_allocatable{resource="cpu"} < 0.2
      for: 6h
      labels:
        severity: info
      annotations:
        summary: "节点 CPU 利用率 < 20%,可考虑缩容"

    # 3. 资源浪费严重
    - alert: HighResourceWaste
      expr: |
        kubecost_pod_network_egress_bytes_total:sum_rate >
        0.8 * kube_pod_container_resource_limits{resource="cpu"}
      for: 1h
      labels:
        severity: warning
      annotations:
        summary: "Pod request 远超实际使用 (>80% 浪费)"

    # 4. 团队成本超预算
    - alert: TeamBudgetExceeded
      expr: |
        sum by (team) (kubecost_namespace_allocation) > 10000
      for: 1d
      labels:
        severity: warning
      annotations:
        summary: "团队 {{ $labels.team }} 日成本超 $10K"

    # 5. PV 闲置
    - alert: IdlePersistentVolume
      expr: |

        severity: info
```

### 26.5.3 资源优化建议生成器

```python
# scripts/resource_optimizer.py
"""分析 Pod 资源使用,生成优化建议"""
import subprocess
import json
from typing import List, Dict


def get_pod_metrics() -> List[Dict]:
    """从 Prometheus 获取过去 7 天的 Pod 资源使用"""
    query = """
      sum by (namespace, pod, container) (
        rate(container_cpu_usage_seconds_total[7d])
      ),
      max by (namespace, pod, container) (
        container_memory_working_set_bytes
      )
    """
    # 简化:实际用 prometheus-api-client
    cmd = ["kubectl", "top", "pods", "-A", "-o", "json"]
    out = subprocess.check_output(cmd, text=True)
    return json.loads(out).get("items", [])


def get_pod_resources() -> Dict:
    """获取所有 Pod 的 request/limit"""
    cmd = ["kubectl", "get", "pods", "-A", "-o", "json"]
    out = subprocess.check_output(cmd, text=True)
    pods = json.loads(out)["items"]

    result = {}
    for pod in pods:
        name = pod["metadata"]["name"]
        ns = pod["metadata"]["namespace"]
        for c in pod["spec"].get("containers", []):
            resources = c.get("resources", {})
            result[(ns, name, c["name"])] = {
                "requests": resources.get("requests", {}),
                "limits": resources.get("limits", {}),
            }
    return result


def generate_recommendations(metrics: List, resources: Dict) -> List[str]:
    recs = []
    for m in metrics:
        name = m["metadata"]["name"]
        ns = m["metadata"]["namespace"]
        containers = m.get("containers", [])

        for c in containers:
            cname = c["name"]
            actual_cpu = c.get("cpu", "0m")
            actual_mem = c.get("memory", "0Mi")

            key = (ns, name, cname)
            if key not in resources:
                continue

            req = resources[key]["requests"]
            req_cpu = req.get("cpu", "0m")
            req_mem = req.get("memory", "0Mi")

            # 如果实际使用 < request 的 30%,建议降低 request
            if parse_cpu(actual_cpu) < parse_cpu(req_cpu) * 0.3:
                recs.append(
                    f"[{ns}/{name}/{cname}] CPU 实际 {actual_cpu} 远低于 request {req_cpu},"
                    f"建议降到 {actual_cpu}"
                )

            if parse_mem(actual_mem) < parse_mem(req_mem) * 0.3:
                recs.append(
                    f"[{ns}/{name}/{cname}] 内存实际 {actual_mem} 远低于 request {req_mem},"
                    f"建议降到 {actual_mem}"
                )

    return recs


def parse_cpu(s: str) -> int:
    """解析 '100m' / '1' 等为毫核"""
    if s.endswith("m"):
        return int(s[:-1])
    return int(float(s) * 1000)


def parse_mem(s: str) -> int:
    """解析 '256Mi' / '1Gi' 等为 Mi"""
    if s.endswith("Mi"):
        return int(s[:-2])
    if s.endswith("Gi"):
        return int(s[:-2]) * 1024
    if s.endswith("Ki"):
        return int(s[:-2]) // 1024
    return int(s) // (1024 * 1024)


def main():
    metrics = get_pod_metrics()
    resources = get_pod_resources()
    recs = generate_recommendations(metrics, resources)

    print(f"=== 资源优化建议 ({len(recs)} 条) ===\n")
    for r in recs[:50]:
        print(f"  - {r}")


if __name__ == "__main__":
    main()
```

### 26.5.5 HPA + Cluster Autoscaler 联动

```yaml
# hpa-with-ca.yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: myapp-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: myapp
  minReplicas: 3
  maxReplicas: 100   # 上限由预算决定
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 60   # 60% 时扩容 (而非默认 80%)
  - type: Resource
    resource:
      name: memory
      target:
        type: Utilization
        averageUtilization: 70
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 30   # 快速扩容
      policies:
      - type: Percent
        value: 100   # 每次最多翻倍
        periodSeconds: 30
    scaleDown:
      stabilizationWindowSeconds: 600   # 慢缩容,避免抖动
      policies:
      - type: Percent
        value: 10   # 每次最多缩 10%
        periodSeconds: 60
---
# Cluster Autoscaler
apiVersion: apps/v1
kind: Deployment
metadata:
  name: cluster-autoscaler
  namespace: kube-system
spec:
  template:
    spec:
      containers:
      - name: cluster-autoscaler
        image: k8s.gcr.io/autoscaling/cluster-autoscaler:v1.27.3
        command:
        - ./cluster-autoscaler
        - --balance-similar-node-groups=true
        - --expander=least-waste   # 选择浪费最少的节点组
```

## 26.8 故障复盘

### 26.8.1 复盘 Case 1: Spot 大规模回收导致雪崩

**事件经过：**
- 某公司 60% 节点用 Spot
- AWS 某区域容量紧张,5 分钟内回收 200+ Spot 节点
- 业务 Pod 大规模重新调度,但 On-Demand 节点不足
- 服务降级 30 分钟

**根因：**
1. Spot 比例过高 (60%),无足够 On-Demand 缓冲
2. 应用启动慢 (Java 90s),无法快速恢复
3. 没有多 AZ 分布,某 AZ 集中回收

**修复方案：**
1. Spot 比例降到 40-50%,关键服务用 On-Demand
2. PDB (PodDisruptionBudget) 防 Spot 回收导致同时驱逐
3. 多 AZ 分布,降低单 AZ 影响
4. 应用层优化启动速度 (Spring Boot LazyInit)
5. Spot 中断通知 + 提前迁移 (Karpenter interruption handler)

### 26.8.2 复盘 Case 2: HPA 抖动导致成本暴增

**事件经过：**
- 某服务 HPA 配置 `targetCPU: 50%`
- 流量轻微波动,HPA 频繁扩容
- 缩容 `stabilizationWindow` 设的 60s,过短
- 节点频繁加减,月成本暴增 30%

**根因：**
- HPA 抖动 (thrashing)
- 缩容窗口过短,刚加的节点又删
- Cluster Autoscaler 反复加减节点

**修复方案：**
1. HPA `targetCPU` 调到 65% (留余地)
2. `scaleDown.stabilizationWindowSeconds: 600` (10 分钟)
3. `scaleDown.policy: max 10% per minute` (慢缩容)
4. 用 KEDA 基于 Prometheus 自定义指标,而非纯 CPU

### 26.8.3 复盘 Case 3: PV 闲置成本累积

**事件经过：**
- 团队习惯创建 PVC 但不删除
- 一年后集群有 500+ PVC,实际使用 200
- 闲置 PV 占 100TB,月成本 $8000

**根因：**
- 缺乏生命周期管理
- reclaimPolicy: Retain (删除 PVC 后 PV 保留)
- 没有定期清理流程

**修复方案：**
1. StorageClass `reclaimPolicy: Delete`
2. CronJob 定期扫描未绑定 PVC
3. 工单系统提醒团队清理
4. Kubecost 报告闲置 PV 成本

### 26.8.4 复盘 Case 4: 日志成本失控

**事件经过：**
- 业务上线后日志量从 1TB/天涨到 50TB/天
- ELK 集群需要不断扩容,月成本 $20K
- 90% 是 DEBUG/INFO 日志,无人查看

**根因：**
- 应用日志级别配错 (生产用 DEBUG)
- 没有采样和过滤
- 日志保留期过长 (90 天)

**修复方案：**
1. 生产环境改 INFO 级别
2. Promtail 采集时丢弃 DEBUG
3. 高频日志采样 (10%)
4. 日志保留期改 7 天
5. 长期日志归档到 S3 (便宜 4 倍)

**优化后: 月成本 $3K (节省 85%)**

### 26.8.5 复盘 Case 5: 跨 AZ 流量费用暴增

**事件经过：**
- 某业务从单 AZ 迁移到多 AZ
- 月度账单中跨 AZ 流量费 $15K
- 占总成本 25%

**根因：**
- 服务调用未做同 AZ 亲和
- 数据库跨 AZ 复制流量大
- 监控数据采集跨 AZ

**修复方案：**
1. K8s Service 启用 topology-aware routing
2. Pod 跨 AZ 反亲和 + ScheduleAnyway
3. 数据库主从在同 AZ
4. Prometheus 分区采集 (每 AZ 一个)

**优化后: 跨 AZ 流量费 $3K (节省 80%)**

## 26.10 常见陷阱

### 26.10.1 陷阱 1: 只看账单不看利用率

**问题：** 财务只关心月账单金额,但账单降了不等于真省钱 (可能是业务缩水)。

**修复：** 关注"单位业务成本":
- 每订单成本
- 每用户成本
- 每请求成本

### 26.10.2 陷阱 2: Spot 比例过高

**问题：** 80%+ Spot 省钱,但回收时雪崩。

**修复：** 关键服务用 On-Demand,Spot 比例 40-60%。

### 26.10.3 陷阱 3: HPA 抖动

**问题：** HPA 频繁扩缩,Cluster Autoscaler 频繁加减节点。

**修复：** `stabilizationWindowSeconds` 设大 (10 分钟),`scaleDown.policy: 10%/min`。

### 26.10.4 陷阱 4: 监控自身吃资源

**问题：** Prometheus + ELK + Jaeger 自身占 10-20% 集群资源。

**修复：**
- Prometheus 采样 (非全量)
- 日志采样 (丢弃 DEBUG)
- Trace 比例采样 (1%)
- 长期数据归档到对象存储

### 26.10.5 陷阱 5: 镜像版本爆炸

**问题：** 每次发布都 push 新镜像,旧镜像不清理,仓库存储爆炸。

**修复：**
- Harbor 生命周期策略 (保留 30/90 天)
- 自动清理 untagged 镜像
- 配额限制团队存储

### 26.10.6 陷阱 6: 跨 AZ 流量被忽视

**问题：** 业务不感知 AZ,所有调用跨 AZ,流量费 $0.01/GB 累积惊人。

**修复：**
- K8s topology-aware routing
- Pod 跨 AZ 反亲和
- 数据库同 AZ 主从

### 26.10.7 陷阱 7: 用 limit 而非 request 留余地

**问题：** 业务把 limit 设很高 "以防万一",但调度基于 request,节点超卖雪崩。

**修复：**
- 关键服务 request = limit
- 用 HPA 扩容,而非靠 limit 留余地
- VPA 自动调整 request 基于历史使用

### 26.10.8 陷阱 8: 测试环境配置等同生产

**问题：** 测试环境副本数和资源都和 prod 一样,成本高。

**修复：**
- 测试环境用 Spot
- 非工作时间自动缩容 (CronJob)
- 资源配比减半
- 测试环境日志保留 1 天

## 26.11 面试题

### Q1: 容器化一定省钱吗?

**答：** 不一定。容器化的本质是"提高资源利用率",而非"减少资源"。如果配置不当,反而更贵:

- 资源浪费隐蔽 (request 远高于实际)
- 超卖雪崩 (被迫加节点)
- 工具链开销 (Prometheus/ELK 自身吃 10-20%)
- 镜像存储爆炸
- 网络/跨 AZ 费用增加

**关键：** 容器化 + FinOps 才省钱,无治理的容器化反而贵 30%。

### Q2: 如何归因 K8s 集群成本到团队?

**答：** 三步:

1. **节点成本计算** — EC2/ECS + EBS + 网络费用汇总
2. **按 Pod 分摊** — 按 Pod 的 request 比例分摊 (CPU request + memory request 加权)
3. **按标签归因** — Pod 的 `team` 标签归因到团队

**开源工具：** Kubecost, Cloud Custodian, OpenCost。

**精度：** 一般 ±10%,因为系统组件 (kubelet/proxy) 占 5-10% 不可分摊。

### Q3: Spot 实例适合什么场景?

**答：** Spot 适合:
- 无状态服务 (可重新调度)
- 批处理任务 (可中断)
- CI/CD 流水线
- 开发测试环境

不适合:
- 数据库 (有状态,中断丢数据)
- 核心 API (中断影响业务)
- 单点服务 (无副本)

**比例：** 总节点 40-60%,关键服务用 On-Demand。

### Q4: 在线/离线混部如何避免干扰?

**答：** 多层隔离:

1. **cgroup 隔离** — 在线用 cpu shares,离线用 cpu quota
2. **cpuset 独占** — 在线业务独占 CPU 核心
3. **内存优先级** — 在线内存高优,离线低优 (触发 OOM 先杀离线)
4. **网络 QoS** — 离线流量限速
5. **磁盘 IO 限速** — 离线 IO 限速,避免影响在线
6. **动态调度** — 实时感知在线负载,离线任务让路

### Q5: VPA 和 HPA 怎么选?

**答：**

| 维度 | VPA | HPA |
|------|-----|-----|
| 调整对象 | request/limit | 副本数 |
| 适用场景 | 资源配置不准 | 流量波动大 |
| 重启 Pod | 是 (推荐模式) | 否 |
| 与 Cluster Autoscaler | 间接 (改 request 影响调度) | 直接 (副本多需更多节点) |

**最佳实践：** VPA 用于"修正配置",HPA 用于"应对流量"。两者可以共存,VPA 调整单 Pod 资源,HPA 调整副本数。

### Q6: 跨 AZ 流量费怎么优化?

**答：**

1. **Service topology-aware routing** — K8s 1.21+ 内置,优先同 AZ 后端
2. **Pod 跨 AZ 反亲和** — 每个副本在不同 AZ,流量均衡
3. **数据库同 AZ** — 主从在同 AZ,避免复制流量
4. **VPC Endpoint** — S3/ECR/CloudWatch 走 VPC 端点,免 NAT
5. **Prometheus 分区** — 每 AZ 一个 Prometheus,避免跨 AZ 抓取
6. **业务改造** — 服务间调用尽量在同 AZ (用 Service short name)

### Q7: 集群 CPU 利用率从 15% 提到 50% 难吗?

**答：** 难,需要系统化工作:

1. **VPA 调整 request** — 把虚高的 request 降下来 (单 Pod 利用率从 30% 提到 60%)
2. **HPA 扩缩容** — 流量低时缩容,节点少但利用率高
3. **混部** — 在线 + 离线任务同节点
4. **Pod density 优化** — 单节点放更多 Pod (30 → 80)
5. **干扰隔离** — 避免高优业务被低优影响

**典型路径：** 15% → 30% (1-2 个月,VPA + HPA) → 45% (3-6 个月,混部) → 55%+ (6-12 个月,深度优化)。

### Q8: Chargeback 和 Showback 区别?

**答：**

- **Showback** — 给业务团队看成本报表,但不实际扣钱。"你们团队上月用了 $10K"。
- **Chargeback** — 实际从业务预算中扣除。"你们团队上月用了 $10K,已从你们的预算中扣除"。

**Showback 价值低,Chargeback 才有约束力。** 但 Chargeback 需要财务流程支持,实施难度大。

### Q9: 容器化降本的天花板在哪?

**答：** 理论极限:

- CPU 利用率 80%+ (Google Borg 水平)
- 内存利用率 80%+
- Pod density 100+/节点
- Spot 比例 80%
- 业务流量零跨 AZ

**现实天花板:**
- CPU 利用率 60-70% (考虑突发)
- 内存利用率 70-80%
- Pod density 50-100 (考虑隔离)
- Spot 比例 40-60% (考虑稳定性)

**典型节省:** 相对传统部署 50-70%,相对无治理容器化 30-50%。

### Q10: 如何衡量 FinOps 成熟度?

**答：** FinOps 基金会定义 5 个级别:

| 级别 | 特征 |
|------|------|
| Crawl (爬行) | 知道总成本,无归因 |
| Walk (行走) | 团队级成本可见,无优化 |
| Run (跑步) | 团队级优化,Spot + HPA |
| Sprint (冲刺) | 自动化优化 + Chargeback |
| Sprint+ (高阶) | AI 驱动 + 业务 KPI 挂钩 |

**业界平均: Walk 级别。** 头部公司 (Google/Netflix) 在 Sprint+ 级别。

## 26.12 总结

容器化成本治理是云原生时代的核心工程能力。本章核心要点:

1. **FinOps 三阶段: Inform → Optimize → Operate** — 没有可见性就没有优化,没有治理就没有持续
2. **成本归因是基础** — 标签 + Kubecost + Chargeback 是三件套
3. **资源利用率是核心指标** — 从 15% 提到 50% 等于成本砍 70%
4. **Spot + 混部是降本大头** — 占节省的 50-70%
5. **HPA/VPA 是标配** — 但需注意抖动和重启风险
6. **网络/存储成本容易被忽视** — 跨 AZ 流量费可达 25%
7. **治理机制是保障** — 配额 + 预算 + 告警 + 审批 + 回流
8. **降本是持续过程** — 不是一次优化完事,需要月度评审
9. **业务参与是关键** — 工程师 + 财务 + 业务三方协作
10. **天花板有限** — 现实节省 30-50%,极限 50-70%

**与上一章的关系:** 第 25 章解决"故障发生时如何快速恢复",本章解决"如何让集群运行得更经济"。两者是生产环境的两个长期课题: **稳定性 + 经济性**。

**全书总结:** 至此,Docker 学习笔记 26 章全部完成。从基础概念 (1-3 章) → 核心技术 (4-9 章) → 实战编排 (10-14 章) → 生产实践 (15-17 章) → 生态对比 (18-20 章) → 工业实战 (21-26 章),覆盖了容器技术从入门到大厂实战的完整路径。
