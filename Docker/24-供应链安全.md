## 24.2 章节简介

容器供应链安全是云原生安全体系中最关键的一环。一个 Docker 镜像从源代码到生产运行，需要经过数十个环节：依赖下载、编译构建、镜像打包、仓库推送、节点拉取、kubelet 启动。任何一个环节被攻击者入侵，都可能导致恶意代码进入生产环境。

**真实威胁时间线：**

| 时间 | 事件 | 影响范围 |
|------|------|----------|
| 2020-12 | SolarWinds 攻击 | 18000+ 企业客户被植入后门 |
| 2021-12 | Log4Shell (CVE-2021-44228) | 全球数百万应用受影响 |
| 2021-11 | npm `coa`/`rc` 包被劫持 | 11M+ 周下载量被植入恶意代码 |
| 2022-01 | npm `ua-parser-js` 后门 | 800万+ 周下载被植入挖矿+窃密 |
| 2024-03 | `xz-utils` 后门 (CVE-2024-3094) | 几乎进入 Debian/Ubuntu 主线 |

**核心问题：** 你运行的镜像真的来自你信任的源吗？构建过程真的没被篡改吗？运行时的镜像和构建时一样吗？

本章围绕 **SLSA 框架** 给出系统化的供应链安全方案，从 SBOM、签名、出处 (Provenance)、透明日志 (Rekor) 到运行时准入 (Kyverno)，覆盖完整生命周期。

## 24.3 核心概念

### 24.3.1 SLSA 框架

**SLSA (Supply Chain Levels for Software Artifacts)** 是 Google 主导、Linux 基金会托管的供应链安全分级框架，2021 年发布 1.0。

| 级别 | 要求 | 关键控制 |
|------|------|----------|
| **L1** | 构建过程有文档 | 自动生成构建出处 (provenance) |
| **L2** | 托管构建服务 | 构建在隔离环境运行，防篡改 |
| **L3** | 构建隔离可验证 | 构建源不可变，来源可信 |
| **L4** | 双人审核 + 可重现构建 | 任何修改需两人同意，构建可独立验证 |

```
SLSA 各级别防护的攻击:

L1: 防止"无文档构建" - 知道镜像从哪来
L2: 防止"构建机被入侵" - 托管隔离环境
L3: 防止"源代码被篡改" - 源不可变 + 出处可验
L4: 防止"内部人员作恶" - 双人审核 + 可重现
```

### 24.3.2 SBOM (Software Bill of Materials)

**SBOM = 软件物料清单**，类似食品的成分表。一份 SBOM 记录镜像中所有组件（OS 包、语言依赖、共享库）及其版本、来源、许可证。

**两大标准：**

| 标准 | 主导方 | 格式 | 用途 |
|------|--------|------|------|
| **SPDX** | Linux 基金会 | JSON/YAML/RDF/Tag-Value | 企业合规、许可证审计 |
| **CycloneDX** | OWASP | JSON/XML | 安全研究、漏洞关联 |

**SPDX 关键字段示例：**

```json
{
  "SPDXVersion": "SPDX-2.3",
  "DataLicense": "CC0-1.0",
  "SPDXID": "SPDXRef-DOCUMENT",
  "DocumentName": "myapp:1.2.3",
  "Creator": "Tool: syft-0.84.0",
  "Created": "2026-07-04T10:30:00Z",
  "Packages": [
    {
      "SPDXID": "SPDXRef-Package-1",
      "Name": "openssl",
      "VersionInfo": "1.1.1n-0+deb11u5",
      "Supplier": "Organization: Debian",
      "LicenseConcluded": "OpenSSL",
      "ExternalRefs": [
        { "Type": "cpe23Type", "Reference": "cpe:2.3:a:openssl:openssl:1.1.1n:*:*:*:*:*:*:*" },
        { "Type": "purl", "Reference": "pkg:deb/debian/openssl@1.1.1n-0+deb11u5" }
      ]
    }
  ]
}
```

### 24.3.3 制品签名 (Cosign)

**Cosign** 是 Sigstore 项目提供的镜像签名工具，2021 年发布 1.0。支持三种签名模式：

| 模式 | 私钥 | 公钥分发 | 适用场景 |
|------|------|----------|----------|
| **Key-based** | 自管 | 手动分发公钥 | 内部机房、强合规 |
| **Keyless (OIDC)** | 无 (Fulcio 短期证书) | OIDC issuer (GitHub/Google) | 开源、CI/CD |
| **KMS** | AWS KMS/Azure KV/GCP KMS | KMS 公钥 | 云上生产 |

**Keyless 签名流程：**

```
   ┌─────────┐   1. OIDC token    ┌────────┐
   │ GitHub  │ ─────────────────► │ Cosign │
   │ Actions │                    └───┬────┘
   └─────────┘                        │ 2. 签名请求
                                      ▼
                                 ┌─────────┐
                                 │ Fulcio  │  ← 颁发短期证书
                                 │ (CA)    │
                                 └────┬────┘
                                      │ 3. 证书 + 签名
                                      ▼
                                 ┌─────────┐
                                 │  Rekor  │  ← 透明日志
                                 │ (log)   │
                                 └────┬────┘
                                      │ 4. 记录
                                      ▼
                                 ┌─────────┐
                                 │ Registry│ ← 签名作为 manifest 附件
                                 └─────────┘
```

### 24.3.4 Provenance (出处)

**Provenance = 构建过程的"产地证"**，记录：
- 构建源代码的 git commit SHA
- 构建用的 Dockerfile 路径
- 构建时的环境（builder 版本、构建参数）
- 构建产物的 SHA256
- 构建步骤

**SLSA Provenance 标准** 通过 in-toto 格式表达：

```json
{
  "_type": "https://in-toto.io/Statement/v0.1",
  "subject": [
    { "name": "myapp:1.2.3",
      "digest": { "sha256": "a1b2c3..." } }
  ],
  "predicateType": "https://slsa.dev/provenance/v0.2",
  "predicate": {
    "builder": { "id": "pkg:github/actions/buildx-docker@v3" },
    "buildType": "https://github.com/buildkit/buildkit",
    "source": {
      "uri": "git+https://github.com/myorg/myapp",
      "digest": { "sha1": "abc123..." }
    },
    "materials": [
      { "uri": "pkg:docker/alpine@3.18", "digest": { "sha256": "..." } }
    ],
    "buildConfig": { "args": { "VERSION": "1.2.3" } }
  }
}
```

### 24.3.5 透明日志 (Rekor)

**Rekor** 是 Sigstore 的不可篡改透明日志，所有签名都记录在 Merkle 树上。任何人都可以查询：

- 镜像 X 何时被谁签名？
- 在时间 T，是否存在签名 Y？
- 签名者的证书是否当时有效？

**为什么需要透明日志？** 防止"撤销隐藏" — 如果签名者作恶，可以查询历史所有签名；防止"伪造来源" — 没有出现在 Rekor 的签名视为可疑。

## 24.4 底层原理

### 24.4.1 镜像签名在 OCI 规范中的位置

OCI Image Spec v1.1 引入 **Reference Manifest**，签名作为附件 (referrer) 而非镜像层：

```
   ┌─────────────────────────────────┐
   │   Image Manifest (artifactType) │
   │   - config: sha256:abc          │
   │   - layers: [sha256:def, ...]   │
   └────────────┬────────────────────┘
                │
                ▼ Subject 链接
   ┌─────────────────────────────────┐
   │   Signature Manifest (附件)     │
   │   - artifactType:               │
   │     application/vnd.oci.image.  │
   │     signature.v1+json           │
   │   - blobs: [签名 payload]       │
   └─────────────────────────────────┘

   查询: ORAS / Cosign 通过 referrers API 查询
   GET /v2/<repo>/referrers/<digest>
```

**对比旧方案 (Docker Content Trust)：**

| 维度 | DCT (Notary v1) | Cosign (Notation / OCI Referrers) |
|------|------------------|-----------------------------------|
| 签名位置 | 独立 Notary 仓库 | 同一 Registry (附件) |
| 密钥管理 | 单一私钥 | KMS/OIDC/双钥 |
| 透明日志 | 无 | Rekor |
| 多签名 | 困难 | 原生支持 |
| 在用情况 | 弃用中 | 主流 |

### 24.4.2 Cosign 签名验证流程

```
kubelet 拉取镜像 myapp:1.2.3
         │
         ▼
1. 拉取镜像 manifest + config + layers
         │
         ▼
2. 计算 manifest digest = sha256(...)
         │
         ▼
3. 查询 referrers API: /v2/myapp/referrers/<digest>
         │
         ▼
4. 拿到签名附件列表,逐个验证:
   ┌─ a. 提取签名 payload (含 manifest digest + 时间戳)
   ├─ b. 用公钥/Fulcio 证书验签
   ├─ c. 查 Rekor: 此签名是否在透明日志中
   ├─ d. 检查 OIDC issuer 是否在白名单
   └─ e. 检查证书是否已过期
         │
         ▼
5. 全部通过 → kubelet 允许运行
   任一失败 → webhook 拒绝
```

### 24.4.3 Kyverno 准入控制原理

**Kyverno** 是 Kubernetes 原生策略引擎，作为 Admission Webhook 运行：

```
kubectl apply / Pod 创建请求
         │
         ▼
   ┌──────────────┐
   │ API Server   │
   └──────┬───────┘
          │ Admission Webhook 调用
          ▼
   ┌──────────────┐  1. 验证镜像签名
   │  Kyverno     │  2. 检查 SBOM 存在
   │              │  3. 验证 CVE 扫描通过
   └──────┬───────┘  4. 验证 SLSA 等级
          │ 允许 / 拒绝
          ▼
   ┌──────────────┐
   │   Pod 运行   │
   └──────────────┘
```

**Kyverno vs OPA Gatekeeper 对比：**

| 维度 | Kyverno | OPA Gatekeeper |
|------|---------|----------------|
| 策略语言 | YAML (K8s 原生) | Rego |
| 学习曲线 | 低 | 高 |
| 镜像签名验证 | 内置 verifyImages | 需要外部调用 |
| 生成/变异 (Mutate) | 强 | 弱 |
| 性能 | 中等 | 较快 |

### 24.4.4 漏洞扫描的工作机制

**Trivy** 等扫描器的工作流程：

```
   输入: 镜像 myapp:1.2.3
              │
              ▼
1. 解压镜像 layers (tar.gz)
              │
              ▼
2. 识别包管理器元数据:
   ├─ Debian/Ubuntu: /var/lib/dpkg/status
   ├─ Alpine: /lib/apk/db/installed
   ├─ Python: site-packages/*.dist-info/METADATA
   ├─ Node: node_modules/*/package.json
   ├─ Java: META-INF/MANIFEST.MF
   └─ Go: 二进制嵌入的 buildinfo
              │
              ▼
3. 对每个包查询漏洞数据库:
   - OSV / NVD / GHSA / vendor advisories
              │
              ▼
4. 输出: 漏洞列表 (CVE, 严重度, 修复版本)
```

**关键挑战：**
- **误报**：包被安装但应用未使用其漏洞函数
- **延迟**：CVE 数据库更新滞后于上游披露
- **CPE 匹配**：包名与 CVE 数据库的 CPE 命名差异

## 24.5 代码实现

### 24.5.1 完整 CI/CD 供应链安全流水线

```yaml
# .github/workflows/secure-supply-chain.yml
name: Secure Supply Chain

on:
  push:
    branches: [main]
    tags: ['v*']
  pull_request:

permissions:
  contents: read
  packages: write
  id-token: write   # OIDC token for keyless signing

env:
  IMAGE: ghcr.io/${{ github.repository_owner }}/myapp

jobs:
  # 阶段 1: 依赖审计
  dependency-review:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/dependency-review-action@v4
        with:
          fail-on-severity: high
          # 拒绝高风险新引入的依赖

  # 阶段 2: 构建并生成 SBOM
  build-and-sbom:
    runs-on: ubuntu-latest
    needs: dependency-review
    outputs:
      digest: ${{ steps.build.outputs.digest }}
      sbom-path: ${{ steps.sbom.outputs.path }}
    steps:
      - uses: actions/checkout@v4

      - uses: docker/setup-buildx-action@v3

      # 登录 GHCR
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      # 构建镜像 (推送后得到 digest)
      - name: Build and push
        id: build
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: ${{ env.IMAGE }}:${{ github.sha }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
          provenance: true   # 启用 SLSA provenance
          sbom: true         # 启用 SBOM 生成

      # 用 Syft 单独生成更详细的 SBOM
      - name: Generate SBOM (Syft)
        id: sbom
        run: |
          curl -sSfL https://raw.githubusercontent.com/anchore/syft/main/install.sh | sh
          syft ${{ env.IMAGE }}:${{ github.sha }} -o spdx-json > sbom.spdx.json
          echo "path=sbom.spdx.json" >> $GITHUB_OUTPUT

      # 上传 SBOM 作为 artifact
      - uses: actions/upload-artifact@v4
        with:
          name: sbom-spdx
          path: sbom.spdx.json

  # 阶段 3: 漏洞扫描
  vuln-scan:
    runs-on: ubuntu-latest
    needs: build-and-sbom
    steps:
      - uses: actions/checkout@v4

      - name: Download SBOM
        uses: actions/download-artifact@v4
        with:
          name: sbom-spdx

      # 用 Grype 扫描 SBOM (无需拉取镜像)
      - name: Scan SBOM with Grype
        run: |
          curl -sSfL https://raw.githubusercontent.com/anchore/grype/main/install.sh | sh
          grype sbom:sbom.spdx.json \
            --fail-on high \
            --only-fixed \
            -o json > grype-report.json || exit 1

      # 上传扫描报告
      - uses: actions/upload-artifact@v4
        with:
          name: vuln-report
          path: grype-report.json

  # 阶段 4: 镜像签名 (Keyless)
  sign:
    runs-on: ubuntu-latest
    needs: [build-and-sbom, vuln-scan]
    steps:
      - uses: actions/checkout@v4
      - uses: sigstore/cosign-installer@v3

      # Keyless 签名 (用 GitHub OIDC)
      - name: Sign image (keyless)
        env:
          COSIGN_EXPERIMENTAL: 1
        run: |
          cosign sign --yes \
            ${{ env.IMAGE }}@${{ needs.build-and-sbom.outputs.digest }}

      # 附加 SBOM 作为证明 (attestation)
      - name: Attest SBOM
        env:
          COSIGN_EXPERIMENTAL: 1
        run: |
          cosign attest --yes \
            --predicate sbom.spdx.json \
            --type spdxjson \
            ${{ env.IMAGE }}@${{ needs.build-and-sbom.outputs.digest }}

      # 附加漏洞扫描结果
      - name: Attest vuln scan
        env:
          COSIGN_EXPERIMENTAL: 1
        run: |
          cosign attest --yes \
            --predicate grype-report.json \
            --type vuln \
            ${{ env.IMAGE }}@${{ needs.build-and-sbom.outputs.digest }}

  # 阶段 5: 部署 (带签名验证)
  deploy:
    runs-on: ubuntu-latest
    needs: sign
    environment: production
    steps:
      - uses: actions/checkout@v4

      - name: Deploy to K8s
        run: |
          echo "Deploying ${{ env.IMAGE }}@${{ needs.build-and-sbom.outputs.digest }}"
          # 部署 yaml 中已通过 Kyverno 验证签名
          kubectl set image deployment/myapp \
            myapp=${{ env.IMAGE }}@${{ needs.build-and-sbom.outputs.digest }}
```

### 24.5.2 Kyverno 镜像签名验证策略

```yaml
# kyverno-verify-signature.yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: verify-image-signatures
spec:
  validationFailureAction: Enforce
  background: false  # 签名验证需要运行时拉取,关闭后台扫描
  rules:
  - name: verify-cosign-keyless
    match:
      any:
      - resources:
          kinds:
          - Pod
    verifyImages:
    - imageReferences:
      - "ghcr.io/myorg/*"
      mutateDigest: true   # 把 tag 替换为 digest,防止 tag 复用攻击
      attestors:
      - entries:
        - keyless:
            subject: "https://github.com/myorg/*/.github/workflows/*@refs/heads/main"
            issuer: "https://token.actions.githubusercontent.com"
            rekor:
              url: https://rekor.sigstore.dev
      attestations:
      - type: spdxjson
        attestors:
        - entries:
          - keyless:
              subject: "https://github.com/myorg/*/.github/workflows/*@refs/heads/main"
              issuer: "https://token.actions.githubusercontent.com"
      - type: vuln
        attestors:
        - entries:
          - keyless:
              subject: "https://github.com/myorg/*/.github/workflows/*@refs/heads/main"
              issuer: "https://token.actions.githubusercontent.com"
        conditions:
        - all:
          - key: "{{ matches.*.vulnerabilities.*.severity }}"
            operator: AnyNotIn
            value:
            - Critical
            - High
```

### 24.5.3 SBOM 生成与比较脚本

```python
# scripts/sbom_diff.py
"""比较两个 SBOM,识别新增/移除/升级的依赖"""
import json
import sys
from pathlib import Path
from typing import Dict, Tuple


def load_sbom(path: Path) -> Dict[str, str]:
    """解析 SPDX JSON,返回 {包名: 版本} 字典"""
    data = json.loads(path.read_text())
    packages = {}
    for pkg in data.get("packages", []):
        name = pkg["name"].lower()
        version = pkg.get("versionInfo", "unknown")
        packages[name] = version
    return packages


def diff_sbom(old: Dict[str, str], new: Dict[str, str]) -> Tuple[set, set, dict]:
    added = set(new) - set(old)
    removed = set(old) - set(new)
    changed = {
        n: (old[n], new[n])
        for n in set(old) & set(new)
        if old[n] != new[n]
    }
    return added, removed, changed


def main(old_path: str, new_path: str) -> int:
    old = load_sbom(Path(old_path))
    new = load_sbom(Path(new_path))

    added, removed, changed = diff_sbom(old, new)

    print(f"=== SBOM Diff ===")
    print(f"Old: {len(old)} packages")
    print(f"New: {len(new)} packages")
    print(f"\n[+] Added ({len(added)}):")
    for n in sorted(added):
        print(f"    {n}@{new[n]}")

    print(f"\n[-] Removed ({len(removed)}):")
    for n in sorted(removed):
        print(f"    {n}@{old[n]}")

    print(f"\n[~] Changed ({len(changed)}):")
    for n, (ov, nv) in sorted(changed.items()):
        print(f"    {n}: {ov} -> {nv}")

    # 高危模式: 移除已知依赖可能表示供应链攻击
    if removed:
        print(f"\n[!] WARNING: {len(removed)} packages removed - verify this is intentional")

    return 0 if not removed else 1


if __name__ == "__main__":
    sys.exit(main(sys.argv[1], sys.argv[2]))
```

### 24.5.4 Rekor 透明日志查询

```python
# scripts/verify_rekor.py
"""查询 Rekor 透明日志,验证签名历史"""
import requests
import hashlib
from base64 import b64encode


REKOR_URL = "https://rekor.sigstore.dev"


def search_by_digest(image: str, digest: str) -> list:
    """查询某镜像 digest 的所有签名记录"""
    payload = {
        "entries": [{
            "kind": "hashedrekord",
            "apiVersion": "0.0.1",
            "spec": {
                "signature": {
                    "publicKey": {"content": ""},
                    "content": ""
                },
                "data": {
                    "hash": {"algorithm": "sha256", "value": digest}
                }
            }
        }]
    }
    r = requests.post(
        f"{REKOR_URL}/api/v1/index/retrieve",
        json=payload,
        timeout=10
    )
    r.raise_for_status()
    return r.json()


def get_entry(uuid: str) -> dict:
    """获取单条 Rekor 记录的完整内容"""
    r = requests.get(
        f"{REKOR_URL}/api/v1/log/entries/{uuid}",
        timeout=10
    )
    r.raise_for_status()
    return r.json()


def main(image: str, digest: str):
    print(f"Searching Rekor for {image}@{digest[:12]}...")
    uuids = search_by_digest(image, digest)

    if not uuids:
        print("[!] No signature records found - image may be unsigned")
        return

    print(f"[+] Found {len(uuids)} signature records:")
    for uuid in uuids:
        entry = get_entry(uuid)
        for eid, body in entry.items():
            integrated = body.get("integratedTime")
            print(f"  UUID: {eid}")
            print(f"  Time: {integrated}")
            print(f"  Body: {body.get('body', '')[:80]}...")


if __name__ == "__main__":
    import sys
    main(sys.argv[1], sys.argv[2])
```

## 24.6 配置示例

### 24.6.1 Cosign 签名 (Key-based 模式)

```bash
# 1. 生成密钥对 (cosign-key.pub / cosign-key.key)
COSIGN_PASSWORD=$(openssl rand -base64 32) cosign generate-key-pair

# 2. 用环境变量保护私钥 (生产中应该用 KMS)
export COSIGN_PASSWORD="..."

# 3. 签名镜像
cosign sign --key cosign.key myregistry.com/myapp:1.2.3

# 4. 验证签名
cosign verify --key cosign.pub myregistry.com/myapp:1.2.3

# 5. 附加证明 (SBOM)
cosign attest --key cosign.key \
  --predicate sbom.spdx.json \
  --type spdxjson \
  myregistry.com/myapp:1.2.3

# 6. 验证证明
cosign verify-attestation --key cosign.pub \
  --type spdxjson \
  myregistry.com/myapp:1.2.3
```

### 24.6.5 Kyverno 完整策略集

```yaml
# kyverno-required-labels.yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: require-image-signature-and-sbom
spec:
  validationFailureAction: Enforce
  background: false
  rules:
  # 规则 1: 必须用 digest 而非 tag
  - name: require-digest
    match:
      any:
      - resources:
          kinds: [Pod]
    validate:
      message: "镜像必须使用 digest (@sha256:...) 而非 tag"
      pattern:
        spec:
          containers:
          - image: "*@sha256:*"

  # 规则 2: 禁止 latest tag
  - name: disallow-latest-tag
    match:
      any:
      - resources:
          kinds: [Pod]
    validate:
      message: "禁止使用 latest tag"
      pattern:
        spec:
          containers:
          - image: "!*:latest"

  # 规则 3: 必须来自受信 registry
  - name: trusted-registry-only
    match:
      any:
      - resources:
          kinds: [Pod]
    validate:
      message: "镜像必须来自受信 registry"
      pattern:
        spec:
          containers:
          - image: "ghcr.io/myorg/* | docker.io/library/*"

  # 规则 4: 必须有 SBOM attestation
  - name: require-sbom-attestation
    match:
      any:
      - resources:
          kinds: [Pod]
    verifyImages:
    - imageReferences: ["ghcr.io/myorg/*"]
      attestations:
      - type: spdxjson
        attestors:
        - entries:
          - keyless:
              subject: "https://github.com/myorg/*"
              issuer: "https://token.actions.githubusercontent.com"
```

## 24.7 工业案例与基准数据

### 24.7.1 Google 内部供应链安全 (SLSA 起源)

Google 内部早在 2013-2014 年就建立了 **Binary Authorization for Borg (BAA)** 系统，要求所有部署到 Borg 的二进制都必须：

1. 通过受控 CI 构建 (不允许开发者直接上传二进制)
2. 构建过程不可篡改 (构建日志 + 出处)
3. 部署前验证签名

**关键数据 (Google 2021 SLSA 白皮书)：**
- 2014-2019 年内部统计：通过 BAA 阻止了 **数千次** 供应链攻击尝试
- 内部构建系统每天处理 **5000 万+** 构建
- Binary Authorization 拒绝率：**~0.1%** (主要因配置错误)

**SLSA 是 Google 把 BAA 经验抽象出来的开源版本。**

### 24.7.2 阿里云 ACR + TEE 构建链

阿里云容器镜像服务 ACR 企业版提供 **云原生制品沙箱构建**：

```
开发者 push 代码
     │
     ▼
ACR 构建机 (基于 Intel SGX TEE 可信执行环境)
     │
     ├─ 1. 代码在飞地 (enclave) 内编译
     ├─ 2. 构建产物在飞地内签名
     ├─ 3. 生成 SLSA L3 出处证明
     └─ 4. 推送到 ACR + 上传证明
     │
     ▼
ACK 集群准入 (Kyverno 验证签名 + 出处)
     │
     ▼
Pod 运行
```

**性能数据 (2024 公开演讲)：**
- TEE 构建开销：**~15-25%** CPU 时间
- 单镜像构建时间：**+30-60 秒** (主要是远程证明)
- 准入延迟：**P99 < 50ms**

### 24.7.3 字节跳动 ARSC 依赖审计平台

字节内部 **ARSC (Artifact Risk & Supply Chain)** 平台 (2023 公开演讲)：

| 功能 | 实现 |
|------|------|
| 依赖扫描 | 所有 Pom/package.json/requirements.txt 进库前扫描 |
| 漏洞情报 | 整合 OSV/NVD/采购商业情报 (Snyk/Black Duck) |
| 自动升级 | PR 机器人提补丁 PR |
| 准入拦截 | 高危依赖不允许合并 PR |
| 历史追溯 | 每个镜像的 SBOM 永久存储 (5 年) |

**关键指标：**
- 拦截高危依赖引入：**8000+ 次/年**
- Log4Shell 响应：**4 小时**内盘点所有受影响服务 (vs 业界平均 3 天)
- 误报率：**<5%** (通过精准 CPE 匹配)

## 24.8 故障复盘

### 24.8.1 Case 1: npm `ua-parser-js` 后门 (2021-10)

**事件：** npm 上 `ua-parser-js` 包被作者账号被盗后植入恶意代码 (版本 0.7.29, 0.8.0, 0.8.1)，包含挖矿和密码窃取代码。

**影响：**
- 周下载量 **800 万+**
- 数千个项目传递依赖
- 包括大型项目如 React Native、Vue CLI

**根因：**
- 作者账号被钓鱼 (Email 伪装成 npm 管理员)
- 无 2FA (后来 npm 强制要求)
- 无发布前代码审查

**容器层启示：**
- 用户的 Docker 镜像通过 `npm install` 拉取了 `ua-parser-js@0.7.29`
- Trivy 当时未识别此漏洞 (因为不是 CVE 而是恶意代码)

**修复方案：**
1. 在 CI 加 `npm audit --audit-level=high`
2. 锁定 `package-lock.json` 的 integrity hash
3. 用 Cosign 签名构建产物 — 即使 npm 包被改，构建时的 lock 文件指纹可验证

**预防：**
- 用 Renovate/Dependabot 自动升级
- 在生产 CI 强制使用 `npm ci` (不允许 `npm install` 改 lock)
- SBOM 永久存档，便于事后追溯

### 24.8.2 Case 2: codecov bash uploader 被篡改 (2021-01)

**事件：** codecov 的 bash uploader 脚本 (用户在 CI 中 `curl | bash` 下载) 被 GitHub Gist 替换，泄露 CI 中的环境变量 (包括 AWS 密钥、数据库密码、Token)。

**影响：**
- 受害组织数百个 (包括快速扩张中的独角兽)
- 大量凭证泄露被滥用
- 后续多次勒索和挖矿攻击

**容器层启示：** CI 中 `curl | bash` 是极度危险的模式：
- 下载内容不签名
- 下载时间不同 = 内容不同
- 中间人可以替换

**修复方案：**
1. 锁定 URL + 校验 SHA256：`curl -o script.sh <url> && echo "<expected-sha>" | sha256sum -c -`
2. 把脚本作为版本化依赖放仓库
3. 用 SLSA 验证构建工具来源

**预防：**
- 禁止 CI 中 `curl | bash` 模式
- 任何外部资源必须固定版本 + 校验
- 关键 CI 镜像自身用 Cosign 签名

### 24.8.3 Case 3: 内部 Registry 被植入后门镜像 (某金融公司)

**事件：** 某金融公司内部 Harbor Registry 被入侵，攻击者把 `myorg/payment-service:1.4.2` 替换为带后门版本，开发者在不知情下部署。

**根因：**
- Harbor 没启用签名验证
- 镜像用 tag 而非 digest 拉取
- 没有审计日志告警

**攻击路径：**
```
1. 攻击者通过钓鱼获取 Harbor 管理员账号
2. 重新 push 同名 tag (覆盖原镜像)
3. 开发者 kubectl apply → kubelet 用 tag 拉取到后门镜像
4. 后门启动,外连 C2 服务器
```

**修复方案：**
1. 部署 Cosign 签名 — K8s 用 Kyverno 验证
2. 镜像引用强制用 digest (`myorg/payment-service@sha256:abc...`)
3. Harbor 启用 immutable tags (一旦 push 不允许覆盖)
4. Harbor 启用详细审计日志 + 异常告警
5. CI/CD 凭证与生产部署凭证分离

**预防：**
- 所有生产镜像必须签名
- Kyverno 策略 `mutateDigest: true` 自动把 tag 转 digest
- Harbor 启用签名策略 (只允许已签名镜像 push 到生产 namespace)
- 定期审计 Harbor 用户权限

### 24.8.4 Case 4: Trivy 漏报 CVE (2023-09)

**事件：** 某公司用 Trivy 扫描 `python:3.11-slim` 镜像通过，但上线后发现 CVE-2023-XXXX 漏洞被利用。

**根因：**
- Trivy 用的 OSV 数据库滞后 CVE 披露 7 天
- 该 CVE 在 NVD 已公开，但 OSV 还未同步
- 公司 CI 只用 Trivy 一个扫描器

**修复方案：**
1. 多扫描器交叉验证 (Trivy + Grype + Snyk)
2. 订阅 CVE 邮件列表，关键 CVE 手动核对
3. 上线后持续扫描 (CronJob 每天扫集群中的镜像)
4. 升级 OSV 数据库频率 (从每日改每小时)

**预防：**
- 不要相信单一漏洞源
- 关键 CVE 走人工审核流程
- 上线后漏洞扫描 ≠ 上线前扫描，需要持续

### 24.8.5 Case 5: Kyverno 误拦生产部署 (2023-11)

**事件：** 某公司部署时 Kyverno 拦截镜像，提示签名验证失败，导致 4 小时生产部署延迟。

**根因：**
- 之前的 keyless 证书已过期 (90 天有效期)
- Rekor 当时网络抖动访问超时
- Kyverno 配置为 `fail-closed` (Rekor 不可达就拒绝)

**修复方案：**
1. 配置 Kyverno `fail-open` (Rekor 不可达时放行 + 告警)
2. Rekor 多副本 + 本地缓存
3. CI 中提前更新签名 (避免证书过期)

**预防：**
- 准入控制要考虑"控制平面自身故障"场景
- 关键安全控制要做故障模式分析 (FMEA)
- Rekor 不可达时不能完全阻断业务

## 24.9 最佳实践

### 24.9.1 SLSA 实施路线图 (推荐 4 阶段)

```
阶段 1 (1 个月): SLSA L1
- 所有镜像生成 SBOM (Syft)
- 镜像 digest 锁定 (禁用 latest tag)
- 启用基础漏洞扫描

阶段 2 (3 个月): SLSA L2
- CI 改为托管构建服务 (GitHub Actions/GitLab CI)
- Cosign Keyless 签名
- Kyverno 签名验证

阶段 3 (6 个月): SLSA L3
- 构建源不可变 (git tag + commit SHA)
- 生成 SLSA Provenance
- 多 attestation (SBOM + 漏洞扫描结果 + 测试报告)

阶段 4 (12 个月): SLSA L4
- 可重现构建 (Bazel/Nix)
- 双人审核关键镜像
- 强制 KMS 签名
```

### 24.9.2 关键策略清单

| 类别 | 策略 | 工具 |
|------|------|------|
| 源代码 | 依赖审计 + 锁文件 | Dependabot/Renovate |
| 源代码 | 静态分析 | Semgrep/CodeQL |
| 构建 | 托管构建 + 出处 | GitHub Actions/GitLab CI |
| 制品 | SBOM 生成 | Syft |
| 制品 | 漏洞扫描 | Trivy/Grype |
| 制品 | 签名 | Cosign |
| 制品 | 透明日志 | Rekor |
| 制品 | 不可变 tag | Harbor/ACR |
| 分发 | 仓库审计 | Harbor 漏洞策略 |
| 运行时 | 准入控制 | Kyverno/Connaisseur |
| 运行时 | 运行时检测 | Falco/Tetragon |
| 运行时 | 持续扫描 | Trivy CronJob |

### 24.9.3 SBOM 治理最佳实践

1. **每个镜像生成 SBOM** (构建时)
2. **SBOM 永久存档** (>= 5 年，便于追溯)
3. **SBOM 与镜像 digest 绑定** (cosign attest)
4. **SBOM 比对工具** (升级前 diff)
5. **SBOM 查询接口** (漏洞披露后秒级查询受影响服务)

### 24.9.4 漏洞响应流程

```

     │
     ▼
1. 镜像 SBOM 库查询受影响服务 (5 分钟)
     │
     ▼
2. 评估严重度 (CVSS + 利用条件 + 业务影响)
     │
     ├─ CRITICAL ──► 24h 内修复
     ├─ HIGH      ──► 7 天内修复
     └─ MEDIUM    ──► 下个迭代
     │
     ▼
3. 升级依赖 + 重新构建镜像 + 签名 + 扫描
     │
     ▼
4. 部署到 staging 验证 + 滚动到生产
     │
     ▼
5. 复盘 + 更新 .trivyignore / Kyverno 策略
```

## 24.10 常见陷阱

### 24.10.1 陷阱 1: 用 tag 签名而非 digest

**错误：**
```bash
cosign sign myregistry.com/myapp:1.2.3
```

签名是签 tag 的，但 tag 可被覆盖 → 签名失效。

**正确：**
```bash
cosign sign myregistry.com/myapp@sha256:abc123...
```

Kyverno 配置 `mutateDigest: true` 自动把 tag 替换为 digest。

### 24.10.2 陷阱 2: 私钥泄露在 CI 日志

**错误：** 把 cosign 私钥作为 base64 字符串直接放 GitHub Actions env。

```yaml
env:
  COSIGN_KEY: ${{ secrets.COSIGN_KEY }}  # 如果日志 echo 出来就泄露
```

**正确：** 用 KMS 或 OIDC keyless。

### 24.10.3 陷阱 3: SBOM 不完整

**问题：** Syft 默认扫描 OS 包 + 主语言依赖，但忽略：
- 静态链接的 C 库 (Go 二进制中的 netgo)
- Dockerfile `COPY` 进来的二进制
- 容器启动时下载的依赖

**修复：**
- Go 项目用 `go version -m binary` 提取依赖
- 用 `syft scope` 指定深层扫描
- Dockerfile 中显式声明 COPY 来源

### 24.10.4 陷阱 4: 漏洞扫描误报噪声

**问题：** Trivy 报告 1000 个 CVE，开发者麻木，所有都加 .trivyignore。

**修复：**
- 用 `--only-fixed` 只报有修复版本的
- 用 VEX (Vulnerability Exploitability eXchange) 文档声明哪些不影响
- 用 grype 的 `--by-cve` 按漏洞聚合

### 24.10.5 陷阱 5: 准入控制策略过严

**问题：** Kyverno 拦截所有未签名镜像，包括 `kindest/node`、`registry:2` 这类系统镜像。

**修复：**
```yaml
# 排除 kube-system 命名空间
match:
  any:
  - resources:
      kinds: [Pod]
      namespaces: ["!kube-system", "!kyverno", "!monitoring"]
```

### 24.10.6 陷阱 6: 透明日志延迟

**问题：** Rekor 写入有 5-30 秒延迟，验证时可能查不到最新签名。

**修复：**
- CI 中签名后 sleep 30s 再部署
- 用 `cosign attach` 强制刷新
- 本地 Rekor 镜像同步

### 24.10.7 陷阱 7: 签名验证跳过系统镜像

**问题：** 为了方便，对 `kindest/*`、`registry:2` 等系统镜像跳过验证，攻击者可注入恶意系统镜像。

**修复：**
- 系统镜像也用 Cosign 签名 (kindnode 已签名)
- 维护受信镜像白名单 + digest
- 离线环境用本地镜像 + 手动签名

## 24.11 面试题

### Q1: 什么是 SLSA？各级别防护什么攻击？

**答：** SLSA (Supply Chain Levels for Software Artifacts) 是 Google 主导的供应链安全分级框架：

- **L1**：构建过程有出处文档 — 防止"无文档构建"，知道镜像来源
- **L2**：托管构建服务 — 防止"构建机被入侵"，构建在隔离环境
- **L3**：构建隔离可验证 — 防止"源代码被篡改"，源不可变 + 出处可验
- **L4**：双人审核 + 可重现构建 — 防止"内部作恶"，任何修改需两人同意

**关键点：** SLSA 是渐进的，不是 L4 才有意义。L2 已能挡住 90% 的供应链攻击。

### Q2: Cosign Keyless 签名原理？为什么不需要私钥？

**答：**
1. CI 通过 OIDC 拿到短期 token (如 GitHub Actions)
2. Cosign 把 token 发给 Fulcio (Sigstore CA)
3. Fulcio 验证 token，颁发 10 分钟有效期的短期证书
4. Cosign 用证书私钥签名镜像，证书公钥写入 Rekor
5. 验证者查 Rekor + 检查 OIDC issuer/subject

**为什么不需要私钥：** 证书本身有效期极短，且与 OIDC 身份绑定，泄露后影响有限。每次签名都用新证书，无需管理长期密钥。

### Q3: SBOM 是什么？为什么必须存档？

**答：** SBOM = Software Bill of Materials = 软件物料清单，列出镜像中所有组件 (OS 包/语言依赖/库) 及版本、来源、许可证。

**存档价值：**
1. **漏洞响应**：新 CVE 披露后，秒级查询受影响服务 (vs 不存档需重新扫描所有镜像)
2. **合规审计**：监管要求提供软件成分 (FDA/NIST/EU CRA)
3. **历史追溯**：3 年后发现某版本有漏洞，能查到当时部署了什么
4. **许可证合规**：避免无意使用 GPL/AGPL 商业风险

### Q4: Rekor 透明日志解决什么问题？

**答：** Rekor 是 Merkle 树结构的不可篡改日志，所有签名都记录其中。解决三个问题：

1. **撤销隐藏** — 签名者无法"撤销并隐藏"过往签名，所有签名历史可查
2. **伪造来源** — 没有出现在 Rekor 的签名视为可疑
3. **证书有效性** — 验证签名时证书是否当时有效 (短期证书过期后仍可验)

### Q5: Kyverno 验证镜像签名时，性能瓶颈在哪？

**答：** 主要三个瓶颈：

1. **Rekor 查询**：每次验证需查 Rekor (P99 250ms)
2. **拉取签名 manifest**：从 registry 拉 referrers (P99 200ms)
3. **证书链验证**：Fulcio 证书 + OIDC issuer 验证 (P99 100ms)

**优化：**
- Kyverno 内置缓存 (TTL 5 分钟)
- 用 `fail-open` 模式，Rekor 故障时放行
- 对系统镜像排除验证

### Q6: xz-utils 后门事件给供应链安全的启示？

**答：**
1. **代码审查不是银弹** — 后门经数月审查未发现
2. **构建产物 ≠ 源代码** — 后门藏在构建脚本里
3. **可重现构建是底线** — 任何人能用源代码构建出相同字节码
4. **社会工程攻击** — 攻击者花 3 年获取信任
5. **SLSA L4 双人审核** — 防止单人提交后门

### Q7: 如何防止镜像被 tag 覆盖攻击？

**答：**
1. **用 digest 而非 tag** (`myapp@sha256:abc...`)
2. **Kyverno `mutateDigest: true`** — 自动把 tag 转 digest
3. **Harbor 启用 immutable tags** — push 后不允许覆盖
4. **Cosign 签名** — 签名验证 digest 完整性
5. **CI 强制 push 新 tag** — 不允许复用已存在 tag

### Q8: 漏洞扫描器为什么会有误报？

**答：**
1. **CPE 匹配差异** — 包名 vs CVE 数据库的命名规则不同
2. **版本范围误判** — CVE 影响 1.0-1.5，但实际补丁版本 1.0-1.4 (1.5 已修)
3. **编译时禁用** — 包被安装但应用未使用漏洞函数
4. **静态链接差异** — Go 静态链接的库版本与系统包不同
5. **数据库滞后** — OSV 滞后 NVD 数天

**应对：** 用 VEX (Vulnerability Exploitability eXchange) 文档声明哪些不影响。

### Q9: Cosign Keyless 模式 vs KMS 模式，如何选？

**答：**

| 维度 | Keyless | KMS |
|------|---------|-----|
| 适用场景 | 开源、CI/CD | 企业内部、生产 |
| 密钥管理 | 无 (Fulcio 证书) | KMS (AWS/GCP/Azure) |
| 身份绑定 | OIDC issuer | KMS 策略 |
| 验证速度 | 慢 (查 Rekor) | 快 (无 Rekor) |
| 离线验证 | 困难 (需 Rekor) | 简单 (公钥即可) |
| 单点故障 | Fulcio/Rekor | KMS |

**推荐：** 开源项目用 Keyless；企业内部用 KMS；混合模式 (生产 KMS + 开发 Keyless)。

### Q10: 如何在 K8s 中实现"只运行已签名镜像"？

**答：**
1. **Cosign 签名** — CI 中所有镜像签名
2. **Kyverno ClusterPolicy** — `verifyImages` 规则
3. **`validationFailureAction: Enforce`** — 拒绝未签名
4. **`mutateDigest: true`** — 自动 tag 转 digest
5. **`background: false`** — 签名验证需运行时拉取
6. **配置 attestation** — SBOM/漏洞扫描作为额外证明
7. **`exclude` 系统命名空间** — kube-system/kyverno 排除

## 24.12 总结

容器供应链安全是云原生安全的核心战场。本章核心要点：

1. **SLSA 是渐进式框架**：从 L1 到 L4，逐级提升防护。L2 已能挡住 90% 攻击，是当前业界主流目标。

2. **SBOM 是基础**：每个镜像都必须生成 SBOM 并存档。漏洞响应、合规审计、历史追溯都依赖 SBOM。

3. **Cosign Keyless 是趋势**：用 OIDC 替代长期密钥，降低密钥管理负担。开源生态首选。

4. **Kyverno 是 K8s 原生方案**：YAML 配置简单，与 K8s API 深度集成，但需注意性能开销。

5. **透明日志是必备**：Rekor 让签名历史不可篡改，是 SLSA L3+ 的关键组件。

6. **多扫描器交叉验证**：单一漏洞源会滞后和误报。生产环境至少 2 个扫描器。

7. **可重现构建是终极防线**：xz-utils 事件证明，只有可重现构建才能彻底防住源码层后门。

8. **供应链安全是持续过程**：不是一次部署完事，需要持续监控、漏洞响应、策略迭代。

**与上一章的关系：** 第 23 章解决"镜像如何高效分发到节点"，本章解决"分发到节点的镜像是否可信"。两者结合形成完整的镜像交付链：**构建→签名→扫描→分发→验证→运行**。
