## 25.2 章节简介

容器在生产环境的故障模式与裸机/虚拟机时代截然不同。本章系统化梳理容器在生产环境中最常见的 6 类故障：

1. **启动失败** — ImagePullBackOff / ErrImagePull / OOMKill 早夭
2. **资源耗尽** — CPU 节流 / 内存 OOM / 文件句柄 / PID
3. **网络异常** — DNS 解析慢 / 连接重置 / 跨节点延迟突增
4. **存储故障** — 磁盘满 / IO 高 / Volume 无法挂载
5. **调度异常** — Pending 卡住 / 不断 Evicted / Affinity 失败
6. **运行时崩溃** — CrashLoopBackOff / Exit Code 异常 / 僵尸进程

每类故障给出：
- **典型现象** — 监控指标 + 日志特征
- **根因分析** — 从底层 (内核/容器运行时) 到上层 (K8s 调度)
- **排查方法论** — 标准化排查步骤 (SOP)
- **真实工业案例** — 大厂故障复盘 + 损失数据
- **预防方案** — 监控告警 + 自动恢复

**核心理念：** 容器故障排查的关键在于"分层定位" — 先判断是基础设施问题、K8s 控制平面问题、容器运行时问题，还是应用本身问题。本章提供一套系统化的 SOP。

## 25.3 核心概念

### 25.3.1 容器故障的分层模型

```
应用层           ← CrashLoop, Exit 1, 启动慢, 内存泄漏
   │
容器运行时层     ← OOMKill, CPU throttling, 信号丢失
   │
K8s 控制平面层   ← Pending, Evicted, 调度失败, webhook 阻塞
   │
存储/网络层      ← Volume 挂载失败, DNS 解析慢, CNI 故障
   │
宿主机/内核层    ← 内核 panic, 文件系统满, 网卡丢包, CPU 抢占
```

### 25.3.2 Pod 状态机

```
   Pending ──────► Running ──────► Succeeded
       │              │
       │              ▼
       │          Failed
       │              │
       ▼              ▼
   ImagePull      CrashLoopBackOff
   BackOff         (重启策略指数退避)
       │              │
       └──────────────┘
              │
              ▼
       (Reach max retries → fail permanently)
```

**Pod Phase 与状态：**

| Phase | 含义 | 关键状态 |
|-------|------|----------|
| Pending | 已提交但未运行 | ImagePullBackOff, ErrImagePull, ContainerCreating |
| Running | 至少一个容器运行中 | (无特殊状态) |
| Succeeded | 所有容器正常退出 | (仅 Job/CronJob) |
| Failed | 所有容器退出且至少一个失败 | OOMKilled, Error |
| Unknown | 通常因节点失联 | NodeLost |

### 25.3.3 Exit Code 速查表

| Exit Code | 含义 | 容器层典型原因 |
|-----------|------|----------------|
| 0 | 正常退出 | Job 完成任务 |
| 1 | 应用错误 | 应用异常退出 |
| 125 | docker run 失败 | 容器启动参数错误 |
| 126 | 命令不可执行 | 权限问题或 ENTRYPOINT 错误 |
| 127 | 命令未找到 | 镜像中缺少二进制 |
| 137 | SIGKILL (128+9) | OOMKill 或手动 kill -9 |
| 139 | SIGSEGV (128+11) | 段错误,通常 C/C++ 应用 |
| 143 | SIGTERM (128+15) | 优雅退出 (kubelet 发送) |

**137 vs 143 关键区别：**
- **137 (SIGKILL)** — 强制杀死,无法捕获,常见于 OOMKill 或 `preStop` 超时
- **143 (SIGTERM)** — 优雅退出,应用应捕获 SIGTERM 做清理

### 25.3.4 OOMKill 的工作机制

```
内核维护每个 cgroup 的内存计数
         │
         ▼
cgroup.memory.usage_in_bytes > limit
         │
         ▼
内核 OOM killer 选中此 cgroup 中内存最大的进程
         │
         ▼
发送 SIGKILL (signal 9)
         │
         ▼
容器内进程死亡,容器退出 (Exit 137)
         │
         ▼
kubelet 检测容器退出
         │
         ├─ Last State: Terminated
         ├─ Reason: OOMKilled
         └─ Exit Code: 137
         │
         ▼
根据 restartPolicy 决定是否重启
```

**关键细节：**
- **OOMKill 不是 docker kill** — 是内核 cgroup OOM killer 触发
- **`working_set` 接近 limit 不等于 OOM** — 但 K8s 报告的内存用量是 working_set
- **JVM Heap OOM 不是 cgroup OOM** — JVM 抛 OutOfMemoryError 但容器不退出
- **Java 8 默认不识别 cgroup** — JVM 看到的是宿主机内存 (Bug,JDK-8146115,11+ 已修)

## 25.4 底层原理

### 25.4.1 ImagePullBackOff 的触发链

```
kubelet 同步 Pod (每 10s 一次)
         │
         ▼
调用 CRI: PullImage(imageRef)
         │
         ▼
containerd/docker 拉取镜像
         │
         ├─ 1. 解析镜像名 → registry/repo:tag
         ├─ 2. 拉取 manifest
         ├─ 3. 拉取每一层 layer
         └─ 4. 解压到 overlayfs
         │
         ▼
失败 (网络/认证/镜像不存在/磁盘满)
         │
         ▼
kubelet 记录事件: Failed → ImagePullBackOff
         │
         ▼
指数退避重试: 10s, 20s, 40s, 80s, 160s, 300s (上限 5 分钟)
         │
         ▼
达到上限后停止重试,Pod 卡在 ImagePullBackOff
```

**常见根因：**
- Registry 不可达 (DNS/网络)
- 认证失败 (imagePullSecret 过期或权限不足)
- 镜像不存在 (tag 拼错或被删)
- 节点磁盘满 (无法解压 layer)
- 镜像 layer 损坏 (网络中断导致)
- 速率限制 (Docker Hub 限流)

### 25.4.2 CrashLoopBackOff 的触发链

```
kubelet 启动容器
         │
         ▼
容器进程启动
         │
         ├─ 失败 (配置错误/依赖缺失/权限不足)
         ├─ 立即退出 (Exit != 0)
         └─ 启动后崩溃 (OOMKill/Segfault)
         │
         ▼
kubelet 检测容器退出
         │
         ▼
根据 restartPolicy:
- Always: 总是重启 (默认)
- OnFailure: 仅异常退出时重启
- Never: 不重启
         │
         ▼
指数退避: 10s, 20s, 40s, 80s, 160s, 300s (上限 5 分钟)
         │
         ▼
状态: CrashLoopBackOff
         │
         ▼
持续重启 + 退避,直到容器稳定运行或人为干预
```

**CrashLoop vs 容器反复重启的区别：**
- CrashLoopBackOff 是 kubelet 主动延迟重试的状态
- 单纯反复重启可能还在 Running 短暂停留

### 25.4.3 CPU 节流 (CFS Throttling) 原理

Linux CFS (Completely Fair Scheduler) 用两个参数控制 CPU：
- **cpu.cfs_quota_us** — 周期内可用 CPU 时间 (微秒)
- **cpu.cfs_period_us** — 周期长度 (默认 100ms)

K8s `resources.limits.cpu: 1` 翻译为 `quota=100000, period=100000`，即每 100ms 可用 100ms CPU。

**节流场景：**
```
cpu.limits = 1 core (100ms / 100ms)
         │
         ▼
应用突发使用 200ms CPU (在 50ms 内用完 100ms 配额)
         │
         ▼
CFS 检测到超额,本周期剩余 50ms 强制睡眠
         │
         ▼
应用看似"卡顿" 50ms
         │
         ▼
下个周期恢复,继续 100ms
```

**关键问题：**
- **P99 延迟暴增** — 即使平均 CPU 低,突发也会被节流
- **GC 暂停触发节流** — JVM GC 突发 CPU 需求被节流 → STW 时间变长
- **检测方法** — `/sys/fs/cgroup/cpu/cpu.stat` 中 `nr_throttled` 和 `throttled_time`

### 25.4.4 DNS 解析慢的根因

容器中 DNS 慢的典型原因：

```
1. /etc/resolv.conf 配置:
   - options timeout:1   (超时 1s,但 5s 才失败)
   - options attempts:2   (重试 2 次 = 最多 5s)
   - options ndots:5      (默认 5,任何含 5 个以下 . 的名字都会先尝试 search domain)

2. conntrack 表满:
   - DNS 用 UDP,内核为每个 UDP 流创建 conntrack 项
   - 高并发 Pod + 高 QPS DNS → conntrack 表满 → 包丢弃
   - dmesg 看到: "nf_conntrack: table full, dropping packet"

3. CoreDNS 副本不足:
   - 默认 2 个 CoreDNS Pod
   - 上千 Pod 集群时 CoreDNS CPU 满载 → 解析超时

4. ndots:5 的隐性开销:
   - 解析 "redis" 时实际查询:
     redis.default.svc.cluster.local
     redis.svc.cluster.local
     redis.cluster.local
     redis.localdomain
     redis
   - 4 次失败查询后才查到 (每次 1s = 4s)
```

### 25.4.5 节点驱逐 (Eviction) 机制

```
kubelet 周期性检查节点资源 (每 10s)
         │
         ▼
比较实际压力与 eviction thresholds:
- memory.available < 100Mi
- nodefs.available < 10%
- nodefs.inodesFree < 5%
- imagefs.available < 15%
         │
         ▼
超过 Soft threshold → 标记 node under pressure
超过 Hard threshold → 立即驱逐
         │
         ▼
kubelet 按 QoS 等级排序 Pod,从低到高驱逐:
1. BestEffort (无 request/limit)
2. Burstable (有 request 但 < limit)
3. Guaranteed (request == limit)
         │
         ▼
同 QoS 内按优先级排序,PriorityClass 低的先驱逐
         │
         ▼
Pod 状态: Terminated (reason: Evicted)
节点状态: MemoryPressure / DiskPressure
```

**关键细节：**
- **Eviction 不是 Preemption** — Preemption 是为了调度高优先级 Pod 主动抢占；Eviction 是节点资源压力下被动驱逐
- **QoS 决定被驱逐顺序** — 生产 Pod 必须配置 Guaranteed
- **节点驱逐后不会自动恢复** — 需要 Pod 重新调度到其他节点

### 25.5.1 故障排查 SOP 脚本

```bash
#!/bin/bash
# scripts/pod-troubleshoot.sh
# Pod 故障排查一键脚本

set -e

POD_NAME=${1:?"Usage: $0 <pod-name> [namespace]"}
NAMESPACE=${2:-default}

echo "==================== Pod 基本信息 ===================="
kubectl get pod "$POD_NAME" -n "$NAMESPACE" -o wide

echo ""
echo "==================== Pod 状态详情 ===================="
kubectl describe pod "$POD_NAME" -n "$NAMESPACE" | tail -60

echo ""
echo "==================== 容器状态 ===================="
kubectl get pod "$POD_NAME" -n "$NAMESPACE" -o jsonpath='{range .status.containerStatuses[*]}{.name}{"\t"}{.state}{"\n"}{end}'

echo ""
echo "==================== 最近事件 (按时间倒序) ===================="
kubectl get events -n "$NAMESPACE" \
  --field-selector involvedObject.name="$POD_NAME" \
  --sort-by='.lastTimestamp'

echo ""
echo "==================== 容器日志 (上次崩溃) ===================="
for c in $(kubectl get pod "$POD_NAME" -n "$NAMESPACE" -o jsonpath='{.spec.containers[*].name}'); do
  echo "--- Container: $c ---"
  kubectl logs "$POD_NAME" -n "$NAMESPACE" -c "$c" --previous --tail=50 2>/dev/null || echo "(无上次崩溃日志)"
done

echo ""
echo "==================== 节点信息 ===================="
NODE=$(kubectl get pod "$POD_NAME" -n "$NAMESPACE" -o jsonpath='{.spec.nodeName}')
echo "Node: $NODE"
kubectl describe node "$NODE" | grep -A 5 -E "Conditions|Allocated|Memory|CPU"

echo ""
echo "==================== Exit Code 解读 ===================="
EXIT_CODE=$(kubectl get pod "$POD_NAME" -n "$NAMESPACE" -o jsonpath='{.status.containerStatuses[0].lastState.terminated.exitCode}' 2>/dev/null)
REASON=$(kubectl get pod "$POD_NAME" -n "$NAMESPACE" -o jsonpath='{.status.containerStatuses[0].lastState.terminated.reason}' 2>/dev/null)

if [ -n "$EXIT_CODE" ]; then
  echo "Exit Code: $EXIT_CODE, Reason: $REASON"
  case "$EXIT_CODE" in
    137) echo "  → OOMKill 或 SIGKILL. 检查内存限制和应用内存使用." ;;
    143) echo "  → SIGTERM 优雅退出. 检查应用是否在 preStop 中正常清理." ;;
    139) echo "  → 段错误. 检查应用是否有内存越界." ;;
    127) echo "  → 命令未找到. 检查镜像中 ENTRYPOINT/CMD 是否正确." ;;
    126) echo "  → 命令不可执行. 检查权限或文件格式." ;;
    1)   echo "  → 应用错误. 查看应用日志." ;;
  esac
fi
```

### 25.5.2 OOM 根因分析脚本

```python
# scripts/oom_analyzer.py
"""分析 Pod 是否会触发 OOMKill"""
import subprocess
import json
import sys


def get_pod_resources(pod_name: str, namespace: str = "default") -> dict:
    cmd = [
        "kubectl", "get", "pod", pod_name,
        "-n", namespace,
        "-o", "json"
    ]
    out = subprocess.check_output(cmd)
    return json.loads(out)


def analyze_oom_risk(pod: dict) -> list:
    risks = []
    spec = pod["spec"]
    containers = spec.get("containers", [])

    for c in containers:
        name = c["name"]
        resources = c.get("resources", {})
        requests = resources.get("requests", {})
        limits = resources.get("limits", {})

        # 风险 1: 没有 memory limit → BestEffort,易被驱逐
        if "memory" not in limits:
            risks.append(f"[{name}] 无 memory limit (BestEffort QoS,易被驱逐)")

        # 风险 2: request < limit 太多 → Burstable,易被节流
        req_mem = requests.get("memory")
        lim_mem = limits.get("memory")
        if req_mem and lim_mem:
            # 简化:假设都是 Mi/Gi
            req_num = parse_memory(req_mem)
            lim_num = parse_memory(lim_mem)
            if lim_num > req_num * 2:
                risks.append(
                    f"[{name}] memory request ({req_mem}) 远小于 limit ({lim_mem}),"
                    f"Burstable QoS,突发内存可能触发 OOM"
                )

        # 风险 3: Java 应用没有设 -XX:MaxRAMPercentage
        if "java" in str(c.get("command", []) + c.get("args", [])):
            if "MaxRAMPercentage" not in str(c.get("args", [])):
                risks.append(
                    f"[{name}] Java 应用未设置 MaxRAMPercentage,"
                    f"JVM Heap 可能超出 cgroup limit 触发 OOM"
                )

        # 风险 4: 没有设 livenessProbe → 进程 hang 不重启
        if "livenessProbe" not in c:
            risks.append(f"[{name}] 无 livenessProbe,进程 hang 住不会被重启")

    return risks


def parse_memory(s: str) -> int:
    """解析 '256Mi' / '1Gi' 等为字节数"""
    if s.endswith("Mi"):
        return int(s[:-2]) * 1024 * 1024
    if s.endswith("Gi"):
        return int(s[:-2]) * 1024 * 1024 * 1024
    if s.endswith("Ki"):
        return int(s[:-2]) * 1024
    return int(s)


def main():
    pod_name = sys.argv[1]
    namespace = sys.argv[2] if len(sys.argv) > 2 else "default"

    pod = get_pod_resources(pod_name, namespace)
    risks = analyze_oom_risk(pod)

    if not risks:
        print(f"✓ Pod {pod_name} 资源配置合理,无明显 OOM 风险")
    else:
        print(f"⚠ Pod {pod_name} 发现 {len(risks)} 个风险:")
        for r in risks:
            print(f"  - {r}")


if __name__ == "__main__":
    main()
```

### 25.5.3 CPU 节流检测

```python
# scripts/cpu_throttle_detector.py
"""检测节点上所有 Pod 的 CPU 节流情况"""
import subprocess
import json


def get_throttled_pods(node: str) -> list:
    """通过 ssh 到节点读取 cgroup cpu.stat"""
    cmd = [
        "ssh", node,
        "find /sys/fs/cgroup/cpu/kubepods -name cpu.stat -exec grep -H throttled {} +"
    ]
    out = subprocess.check_output(cmd, text=True)

    throttled = []
    for line in out.strip().split("\n"):
        if "nr_throttled 0" in line:
            continue
        # 提取 pod UID
        parts = line.split("/")
        pod_uid = next((p for p in parts if "pod" in p), "unknown")
        throttled.append({"pod_uid": pod_uid, "stat": line})

    return throttled


def main():
    import sys
    node = sys.argv[1]
    pods = get_throttled_pods(node)
    print(f"节点 {node} 上发现 {len(pods)} 个被节流的 Pod:")
    for p in pods[:20]:
        print(f"  {p['pod_uid']}")
        print(f"    {p['stat']}")


if __name__ == "__main__":
    main()
```

### 25.5.5 完整的 K8s Pod 故障自愈

```yaml
# auto-heal.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  replicas: 3
  template:
    spec:
      containers:
      - name: app
        image: myapp:1.2.3
        # 1. 资源配置 (Guaranteed QoS,避免被驱逐)
        resources:
          requests: {cpu: 500m, memory: 512Mi}
          limits:   {cpu: 500m, memory: 512Mi}

        # 2. 启动探针 (失败 600s 才重启,避免大应用被误杀)
        startupProbe:
          httpGet: {path: /health/startup, port: 8080}
          failureThreshold: 30
          periodSeconds: 20

        # 3. 存活探针 (失败 5 次重启,避免频繁重启)
        livenessProbe:
          httpGet: {path: /health/live, port: 8080}
          failureThreshold: 5
          periodSeconds: 10
          timeoutSeconds: 3

        # 4. 就绪探子 (失败立即下线,不重启)
        readinessProbe:
          httpGet: {path: /health/ready, port: 8080}
          failureThreshold: 3
          periodSeconds: 5
          timeoutSeconds: 2

        # 5. 优雅退出配置
        lifecycle:
          preStop:
            exec:
              command: ["/bin/sh", "-c", "sleep 15 && curl -X POST localhost:8080/shutdown"]

        # 6. 安全上下文 (non-root)
        securityContext:
          runAsNonRoot: true
          runAsUser: 1000
          readOnlyRootFilesystem: true
          allowPrivilegeEscalation: false
          capabilities:
            drop: [ALL]

      # 7. 优雅终止宽限期
      terminationGracePeriodSeconds: 60

      # 8. 优先级 (高优先级避免被驱逐)

      topologySpreadConstraints:
      - maxSkew: 1
        topologyKey: topology.kubernetes.io/zone
        whenUnsatisfiable: DoNotSchedule
        labelSelector:
          matchLabels:
            app: myapp

      # 10. 容忍短期节点压力
      tolerations:
      - key: node.kubernetes.io/memory-pressure
        operator: Exists
        effect: NoSchedule
```

```yaml

kind: DaemonSet
metadata:
  name: node-pressure-recover
  namespace: kube-system
spec:
  selector:
    matchLabels:
      app: node-pressure-recover

    spec:
      hostPID: true
      hostNetwork: true
      nodeSelector:
        node-role.kubernetes.io/worker: ""

        image: alpine:3.18

          privileged: true

        - /bin/sh
        - -c
        - |
          while true; do
            # 检查磁盘
            USAGE=$(df /var | tail -1 | awk '{print $5}' | tr -d '%')
            if [ "$USAGE" -gt 85 ]; then
              echo "$(date) Disk usage ${USAGE}%, cleaning docker logs"
              # 清理 docker 容器日志
              find /var/lib/docker/containers -name "*-json.log*" -mtime +3 -delete
              # 清理未使用镜像
              crictl rmi --prune
            fi

            # 检查内存
            MEM_AVAIL=$(grep MemAvailable /proc/meminfo | awk '{print $2}')
            MEM_TOTAL=$(grep MemTotal /proc/meminfo | awk '{print $2}')
            MEM_PCT=$((MEM_AVAIL * 100 / MEM_TOTAL))
            if [ "$MEM_PCT" -lt 10 ]; then
              echo "$(date) Memory available ${MEM_PCT}%, drop caches"
              echo 3 > /proc/sys/vm/drop_caches
            fi

            sleep 60
          done
        volumeMounts:
        - name: docker
          mountPath: /var/lib/docker
        - name: containers
          mountPath: /var/lib/containers
        - name: proc

      - name: proc
        hostPath: {path: /proc}
```

## 25.7 工业案例与基准数据

### 25.7.1 案例一: 某电商 OOM 雪崩 (2023-11)

**事件经过：**
- 双 11 大促,流量是平时 5 倍
- 订单服务 Pod 频繁 OOMKill (Exit 137)
- Pod 不断重启,服务雪崩
- 用户下单失败,持续 35 分钟

**根因分析：**
1. Java 11 服务,JVM Heap 设的 2GB,Pod memory limit 设的 2.5GB
2. 大促期间 GC 频繁,Heap 占用接近 2GB,加上 Metaspace + DirectBuffer + Stack
3. 实际内存超过 2.5GB → cgroup OOMKill
4. JVM 没收到 SIGTERM (因为 SIGKILL 不能捕获),未做清理
5. 重启后再次 OOM,形成 CrashLoop

**损失：** 估算 1500 万订单失败,直接损失 2000 万。

**修复方案：**
1. Pod memory limit 调到 4GB,JVM Heap 设 2GB (Heap:Limit = 50%)
2. JVM 加 `-XX:MaxRAMPercentage=50 -XX:+UseG1GC`
3. 加 startupProbe (大促期间启动慢,避免误杀)
4. 加 memory request = limit (Guaranteed QoS)
5. 加 HPA 基于内存使用率提前扩容

**预防：**
- JVM 容器内存配比规范:Heap:Limit = 50%,留 50% 给非堆
- 压测时模拟 2x 流量验证内存
- Prometheus 监控 JVM Heap 趋势,提前告警

### 25.7.2 案例二: 字节 DNS 雪崩 (2022-08)

**事件经过：**
- 某业务升级后,Pod 数量从 5000 涨到 20000
- 集群内 DNS 解析延迟从 5ms 涨到 5s+
- 大量服务超时,业务受影响 25 分钟

**根因分析：**
1. CoreDNS 默认 2 副本,CPU 100m,无法支撑 20000 Pod
2. conntrack 表满 (`nf_conntrack: table full, dropping packet`)
3. `ndots:5` 导致每次解析发起 5 次查询
4. Pod 用 UDP 解析,UDP 包被 conntrack 丢弃

**修复方案：**
1. CoreDNS 横向扩到 10 副本,CPU 1 core
2. CoreDNS 启用 NodeLocal DNSCache (DaemonSet)
3. 调高节点 `nf_conntrack_max` 到 524288
4. 业务侧:Service 之间用短名直接访问 (跳过 search domain)
5. 关键 Pod 用静态 hosts (跨 Service 直连 IP)

**性能数据 (修复后)：**
- DNS P99 延迟: 5s → 8ms
- CoreDNS CPU: 100m × 2 → 200m × 10 (吞吐 5x,延迟 1/600)

### 25.7.3 案例三: Netflix 容器僵尸进程 (2021)

**事件经过：**
- Titus (Netflix 容器平台) 上某 Java 服务 Pod 内存持续增长
- 容器内 RSS 已超 limit 但未触发 OOM
- 节点内存压力,影响其他 Pod

**根因分析：**
- 容器 ENTRYPOINT 用 shell 脚本启动 Java (`sh -c "java ..."`)
- shell 脚本是 PID 1,Java 是 PID 2
- shell 不转发信号 → kubelet 发 SIGTERM 给 shell,Java 进程未收到
- Java 进程变成僵尸 (zombie),内存不释放

**修复方案：**
1. ENTRYPOINT 直接用 `["java", "-jar", ...]` (exec 形式)
2. 用 `tini` 作为 PID 1 init 进程
3. 监控 Pod 内僵尸进程数

**Dockerfile 修复：**
```dockerfile
# 安装 tini
RUN apk add --no-cache tini

# 用 tini 作为 entrypoint
ENTRYPOINT ["/sbin/tini", "--"]

# Java 命令作为参数
CMD ["java", "-jar", "/app/app.jar"]
```

### 25.7.4 案例四: 阿里 ImagePull 风暴 (2020)

**事件经过：**
- 某 ACK 集群 1000 节点,部署某业务需要拉 2GB 镜像
- 一次滚动更新触发 1000 节点同时拉取
- 内网 Harbor 实例被打满,带宽 10Gbps 全占
- 部署延迟 1.5 小时,部分节点拉取失败

**根因分析：**
- 没有镜像预热
- 没有 P2P 分发
- Harbor 单点 + 带宽有限

**修复方案：**
1. 引入 Dragonfly P2P 分发 (P2P 比例 95%+)
2. 镜像预热 DaemonSet (新版本 push 后预拉)
3. Harbor 多副本 + 阿里云 OSS 后端
4. 滚动更新 batch size 限制 (一次更新 100 节点)

**性能数据 (修复后)：**
- 1000 节点拉 2GB 镜像: 90 分钟 → 5 分钟
- Harbor 带宽占用: 10Gbps → 200Mbps

### 25.7.5 案例五: 节点磁盘满导致 Pod 驱逐 (某游戏公司)

**事件经过：**
- 游戏节点 50 个 Pod,每个 4GB 日志
- 日志轮转配置不当,旧日志未删除
- 节点磁盘使用率 95% → kubelet 触发 DiskPressure
- 50 个 Pod 同时被驱逐,游戏掉线

**根因分析：**
1. Pod 日志写入本地 (emptyDir),无大小限制
2. 应用日志没轮转,Docker json-file 日志没限制大小
3. 节点磁盘 100GB,Pod 日志占 80GB

**修复方案：**
1. Docker daemon.json 配置 `log-opts: {max-size: "100m", max-file: "3"}`
2. Pod emptyDir 加 `sizeLimit`
3. 日志收集到 ELK,本地只保留最近 1 小时
4. Prometheus 监控节点磁盘,80% 告警

**daemon.json 配置：**
```json
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "100m",
    "max-file": "3"
  }
}
```

## 25.8 故障复盘

### 25.8.1 复盘 Case 1: 容器启动慢被 liveness 误杀

**事件：** Java Spring Boot 应用启动需要 90 秒,但 livenessProbe `initialDelaySeconds: 30` + `failureThreshold: 3` + `periodSeconds: 10` = 60 秒后开始失败,Pod 不断重启。

**根因：** 没用 startupProbe 区分"启动"和"存活"。

**修复：**
```yaml
startupProbe:
  httpGet: {path: /health, port: 8080}
  failureThreshold: 30
  periodSeconds: 5    # 150 秒启动时间
livenessProbe:
  httpGet: {path: /health, port: 8080}
  failureThreshold: 3
  periodSeconds: 10   # 启动后才生效
```

**教训：**
- K8s 1.16+ 必用 startupProbe
- Java 应用启动时间应单独评估
- livenessProbe 失败次数不要设太低

### 25.8.2 复盘 Case 2: SIGTERM 没收到导致数据丢失

**事件：** 滚动更新时,某 Java 应用收到 SIGTERM 但未优雅关闭,正在处理的请求被中断,数据库连接未释放,部分订单数据丢失。

**根因：**
1. ENTRYPOINT 用 shell 形式 (`ENTRYPOINT java -jar app.jar`),shell 不转发信号
2. JVM 默认不响应 SIGTERM 做优雅关闭
3. terminationGracePeriodSeconds 设的 30s,但 JVM 强制退出

**修复：**
1. Dockerfile 改为 exec 形式 (`ENTRYPOINT ["java", "-jar", "/app/app.jar"]`)
2. Spring Boot 启用优雅关闭: `server.shutdown=graceful`
3. preStop 加 sleep 让负载均衡摘除流量
4. terminationGracePeriodSeconds 设 60s

```yaml
lifecycle:
  preStop:
    exec:
      command: ["/bin/sh", "-c", "sleep 15"]
terminationGracePeriodSeconds: 60
```

### 25.8.3 复盘 Case 3: limit 设太高导致节点超卖

**事件：** 节点 32 核 64GB,部署 10 个 Pod 每个 limit 8 核 16GB。理论上 80 核 160GB,远超节点容量。正常运行没问题,但所有 Pod 同时高负载时,节点 CPU 100%,所有服务延迟暴增。

**根因：**
- K8s 调度基于 request 不基于 limit
- request 设的 1 核 2GB,limit 设的 8 核 16GB
- 节点超卖 8x,平时没事,突发时雪崩

**修复：**
1. 关键服务 request = limit (Guaranteed QoS)
2. 非关键服务 request << limit,但加 limit 比例控制
3. 监控节点实际 CPU/内存使用,告警阈值 70%
4. 用 VPA 自动调整 request

### 25.8.4 复盘 Case 4: ConfigMap 更新导致 Pod 读取旧配置

**事件：** 修改 ConfigMap 后,部分 Pod 读到新配置,部分读到旧配置,行为不一致,引发故障 1 小时。

**根因：**
- ConfigMap 以 Volume 形式挂载时,kubelet 同步是异步的 (默认 60s-120s)
- 用环境变量读取 ConfigMap 时,Pod 重启才会更新
- 部分业务读 cached 配置,不感知文件变化

**修复方案：**
1. 滚动重启 Pod 让所有 Pod 重新读 ConfigMap
2. 用 Reloader 等 operator 自动重启
3. 应用层监听文件变化 (inotify) 热加载
4. 关键配置变更走 PR + CI/CD 流程,不直接 kubectl

### 25.8.5 复盘 Case 5: CoreDNS ConfigMap 误删

**事件：** 运维误删 kube-system 下 CoreDNS ConfigMap,集群内所有 DNS 解析失败,持续 8 分钟。

**根因：**
- ConfigMap 没有版本控制
- 没有 GitOps,直接 kubectl 操作
- CoreDNS 没有备份

**修复方案：**
1. 集群配置全部 GitOps (ArgoCD/Flux)
2. CoreDNS ConfigMap 加 RBAC 限制 (只读)
3. 关键 ConfigMap 加 `argocd.argoproj.io/sync-options: Delete=false`
4. 定期备份 etcd (Velero)

## 25.10 常见陷阱

### 25.10.1 陷阱 1: shell 形式 ENTRYPOINT 不转发信号

**错误：**
```dockerfile
ENTRYPOINT java -jar app.jar
```

shell 进程是 PID 1,不转发 SIGTERM 给 Java → 优雅退出失败。

**正确：**
```dockerfile
ENTRYPOINT ["java", "-jar", "/app/app.jar"]
```

或用 tini:
```dockerfile
RUN apk add --no-cache tini
ENTRYPOINT ["/sbin/tini", "--"]
CMD ["java", "-jar", "/app/app.jar"]
```

### 25.10.2 陷阱 2: livenessProbe 检查依赖服务

**错误：**
```yaml
livenessProbe:
  httpGet: {path: /health/live, port: 8080}
  # /health/live 检查数据库连接,数据库挂了 → liveness 失败 → Pod 重启
```

数据库故障导致 Pod 重启,加剧雪崩。

**正确：** livenessProbe 只检查进程本身存活;依赖检查用 readinessProbe。

### 25.10.3 陷阱 3: emptyDir 没设 sizeLimit

**问题：** Pod 写大量日志到 emptyDir,占用节点磁盘,触发节点 DiskPressure。

**修复：**
```yaml
volumes:
- name: logs
  emptyDir:
    sizeLimit: 1Gi   # 超过后 Pod 被驱逐
```

### 25.10.4 陷阱 4: ConfigMap 修改后 Pod 没生效

**问题：** ConfigMap 以 Volume 挂载,修改后业务仍读旧值。

**原因：**
- kubelet 同步 ConfigMap 是异步的 (60-120s)
- 应用启动时一次性读取,不感知文件变化

**修复：**
- 滚动重启 Pod (`kubectl rollout restart deployment/xxx`)
- 用 inotify 监听文件变化热加载
- 用 Reloader operator 自动重启

### 25.10.5 陷阱 5: limit 远大于 request 导致超卖

**问题：** `request: 100m, limit: 4` → 节点调度 40 个 Pod (基于 request),但每个 Pod 突发可到 4 核,节点 16 核被严重超卖。

**修复：**
- 关键服务 request = limit
- 用 HPA 基于实际负载扩容,而非靠 limit
- 监控节点 CPU 实际使用率

### 25.10.6 陷阱 6: terminationGracePeriodSeconds 太短

**问题：** 设的 10s,但应用需要 30s 优雅关闭,被 SIGKILL 强杀。

**修复：**
- 默认 30s,关键服务设 60s+
- preStop hook 加 sleep 让 LB 摘除流量
- 测量应用实际优雅关闭时间

### 25.10.7 陷阱 7: Pod 用 latest tag

**问题：** `image: myapp:latest` → kubelet 每次都尝试拉取,且 latest 被覆盖后行为不一致。

**修复：**
- 用具体版本号或 git SHA
- `imagePullPolicy: IfNotPresent` (用 digest 时必配)
- Kyverno 禁止 latest tag

## 25.11 面试题

### Q1: Pod 一直 Pending,如何排查?

**答：** Pending 表示 Pod 未调度或镜像拉取失败。按顺序排查:

1. **调度失败**: `kubectl describe pod` 看 Events,是否有 `FailedScheduling`
   - 资源不足: 节点 CPU/内存不够
   - NodeSelector/Affinity 不匹配
   - Taint/Toleration 不匹配
   - PriorityClass 抢占失败

2. **镜像拉取失败**: 状态 `ImagePullBackOff` 或 `ErrImagePull`
   - 镜像名拼错
   - 认证失败 (imagePullSecret)
   - Registry 不可达
   - 节点磁盘满

3. **Volume 挂载失败**: 状态 `ContainerCreating`
   - PVC 不存在或 Pending
   - StorageClass 不存在
   - 节点无法挂载 (NFS/ISCSI 故障)

4. **Webhook 阻塞**: 状态 `ContainerCreating`
   - Kyverno/OPA 拦截
   - webhook 服务不可达

### Q2: Pod CrashLoopBackOff,如何排查?

**答：**

1. **看上次崩溃日志**:
   ```
   kubectl logs <pod> --previous
   ```

2. **看 Exit Code**:
   ```
   kubectl get pod <pod> -o jsonpath='{.status.containerStatuses[0].lastState.terminated.exitCode}'
   ```
   - 137: OOMKill 或 SIGKILL
   - 143: SIGTERM (可能 preStop 超时)
   - 1: 应用错误
   - 127: 命令未找到

3. **看 Events**:
   ```
   kubectl describe pod <pod>
   ```

4. **常见原因**:
   - 配置错误 (ConfigMap/Secret 不存在)
   - 依赖服务不可达 (数据库/DNS)
   - 应用启动失败 (端口冲突/权限问题)
   - 资源不足 (OOMKill)
   - 命令错误 (ENTRYPOINT 拼错)

### Q3: Pod OOMKilled 但应用监控显示内存不高,为什么?

**答：** 几种可能:

1. **JVM 非堆内存**: Heap 不高,但 Metaspace + DirectBuffer + Stack 超过 limit
2. **off-heap 内存**: C/C++ 应用 malloc 不释放,Netty DirectBuffer
3. **内存短暂峰值**: GC 前的瞬时高峰,监控采样没抓到
4. **子进程内存**: fork 出来的子进程内存也算 cgroup
5. **内存碎片**: 实际 RSS 不高但 working_set 高 (内核统计差异)

**排查方法：**
- 看 cgroup memory.stat 详细分项
- 用 jcmd / jmap 看 JVM 内存分布
- 用 pmap 看进程内存映射
- 用 strace 看内存分配

### Q4: 容器 CPU 节流,但 CPU 使用率不高,为什么?

**答：** 这是 CFS 配额机制导致的:

- K8s `limits.cpu: 1` 翻译为 `cpu.cfs_quota_us=100000, cpu.cfs_period_us=100000`
- 每 100ms 周期可用 100ms CPU
- 应用突发在 50ms 内用完 100ms 配额 → 剩 50ms 强制睡眠
- 监控显示平均 CPU 50%,但实际 P99 延迟暴增

**修复：**
- 提高 limit (但浪费资源)
- 改用 CPU Manager static policy (独占 CPU)
- 应用层降低突发 (限流/队列)
- 改用 `cpuShares` (Burstable QoS)

### Q5: DNS 解析慢,如何排查?

**答：**

1. **看 CoreDNS 状态**:
   ```
   kubectl get pods -n kube-system -l k8s-app=kube-dns
   kubectl top pods -n kube-system -l k8s-app=kube-dns
   ```

2. **看 Pod 内 DNS 配置**:
   ```
   kubectl exec <pod> -- cat /etc/resolv.conf
   ```
   关注 `ndots` (默认 5) 和 `search` 列表

3. **测试解析延迟**:
   ```
   kubectl exec <pod> -- dig kubernetes.default +stats
   ```

4. **看 conntrack**:
   ```
   dmesg | grep conntrack
   cat /proc/sys/net/netfilter/nf_conntrack_count
   cat /proc/sys/net/netfilter/nf_conntrack_max
   ```

5. **修复方案**:
   - 扩 CoreDNS 副本
   - 部署 NodeLocal DNSCache
   - 调高 `nf_conntrack_max`
   - 业务用 FQDN (`redis.default.svc.cluster.local.`) 跳过 search

### Q6: 节点频繁 Evicted,怎么办?

**答：**

1. **看节点压力**:
   ```
   kubectl describe node <node>
   ```
   关注 Conditions: MemoryPressure / DiskPressure / PIDPressure

2. **看资源使用**:
   ```
   kubectl describe node <node> | grep -A 5 "Allocated"
   ```

3. **看磁盘占用**:
   ```
   df -h
   du -sh /var/lib/docker/*
   du -sh /var/lib/kubelet/*
   ```

4. **常见原因**:
   - Pod 日志未轮转
   - 镜像未清理
   - emptyDir 过大
   - 内存超卖

5. **修复**:
   - docker daemon.json 配置 log-opts 限制
   - crictl rmi --prune 清理镜像
   - Pod emptyDir 加 sizeLimit
   - 关键 Pod 配 Guaranteed QoS

### Q7: 滚动更新时有请求失败,如何修复?

**答：**

1. **SIGTERM 没收到**: 用 exec 形式 ENTRYPOINT
2. **LB 未摘除**: preStop hook sleep + readinessProbe
3. **连接未排空**: terminationGracePeriodSeconds 加大
4. **新 Pod 启动慢**: maxSurge 控制滚动速度
5. **客户端连接保持**: 用 Service + Endpoints,避免直连 Pod IP

**配置示例：**
```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1
    maxUnavailable: 0   # 不允许减少可用副本
lifecycle:
  preStop:
    exec:
      command: ["/bin/sh", "-c", "sleep 15"]  # 让 LB 摘除
terminationGracePeriodSeconds: 60
```

### Q8: Pod Exit 137 但不是 OOMKill,可能是什么原因?

**答：** Exit 137 = 128 + 9 = SIGKILL,可能原因:

1. **OOMKill** (最常见)
2. **kubelet 主动杀**: preStop 超过 terminationGracePeriodSeconds
3. **docker kill**: 手动或 daemon 重启
4. **内核 OOM killer**: 宿主机内存不足,杀掉容器进程 (不是 cgroup OOM)
5. **OOM killer 误判**: /proc/<pid>/oom_score 高的进程
6. **kubelet 健康检查**: livenessProbe 失败 + 重启策略

**区分方法：**
- `kubectl describe pod` 看 `Last State: Reason`
- `dmesg | grep -i "killed process"` 看内核日志
- 看 `/var/log/messages` 宿主机 OOM 记录

### Q9: Pod 启动很慢,如何优化?

**答：**

1. **镜像层优化**: 多阶段构建 + distroless
2. **镜像预热**: DaemonSet 提前拉取
3. **JVM 优化**: TieredStopAtLevel=1, CDS, AppCDS
4. **依赖懒加载**: Spring Boot LazyInit
5. **缓存挂载**: BuildKit cache mount
6. **HPA 提前扩容**: 不要等到流量来了才扩
7. **保留 Pod**: `spec.scaleSubresourcePolicy` 或 warm pool

### Q10: 节点 NotReady,业务如何自动恢复?

**答：** K8s 内置机制:

1. **node-monitor-grace-period** (默认 40s): kubelet 40s 没上报,节点标记 NotReady
2. **pod-eviction-timeout** (默认 5m): NotReady 5 分钟后,Pod 被驱逐
3. **Pod 重新调度**: 到其他健康节点

**优化：**
- 关键 Pod 配 PodDisruptionBudget
- 跨 AZ 部署 (topologySpreadConstraints)
- PriorityClass 确保高优 Pod 优先调度
- 节点自愈 (DaemonSet 监控 + 自动恢复脚本)

## 25.12 总结

容器生产故障排查是 SRE 的核心能力。本章核心要点:

1. **分层定位是关键** — 先判断是基础设施、K8s 控制平面、容器运行时还是应用层问题
2. **Exit Code 是入口** — 137/143/127 等代码指向不同根因
3. **OOMKill 不是应用 OOM** — 是 cgroup 内存超限,内核强制杀
4. **CPU 节流是隐形杀手** — 平均 CPU 不高但 P99 延迟暴增,常见于 GC 突发
5. **DNS 是高发故障** — CoreDNS 扩容 + NodeLocal DNSCache 是标配
6. **优雅退出必须配置** — exec ENTRYPOINT + preStop + terminationGracePeriodSeconds
7. **资源配比规范** — Guaranteed QoS + request=limit 是生产标配
8. **监控告警是基础** — 没监控就是裸奔,Prometheus + Grafana 必备
9. **故障复盘要写文档** — 每次故障都形成 SOP,组织级学习

**与上一章的关系：** 第 24 章解决"如何防止恶意镜像进入",本章解决"合法镜像运行后出问题怎么办"。两者构成生产环境的两道防线: **入口防御 (供应链) + 运行时防御 (故障自愈)**。
