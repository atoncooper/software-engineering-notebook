# 01 - 基础与核心概念

> 一切的起点：Docker 是什么、不是什么、为什么这样设计、在大厂生产里它扮演什么角色。

---

## 1. 问题定义与边界

### 1.1 Docker 解决的问题

软件交付长期被三个问题折磨：

| 问题 | 前 Docker 时代 | Docker 之后 |
|------|----------------|-------------|
| **环境一致性** | "在我机器上能跑" | 镜像打包整个运行时,处处一致 |
| **依赖冲突** | 多个应用共享 OS,Python 2 / 3 互踩 | 每个容器独立文件系统,隔离依赖 |
| **资源利用率** | 一台机器跑一个应用,VM 开销大 | 单机可跑数百容器,共享内核 |
| **部署速度** | VM 启动分钟级,镜像几十 GB | 容器启动秒级,镜像 MB 级 |
| **运维标准化** | 每种语言一套打包规范 | `docker run` 是统一接口 |

### 1.2 Docker 不解决什么(边界)

- **不是完整虚拟机**:共享宿主机内核,无法在 Linux 上跑 Windows 容器(除非用 LCOW / Hyper-V 隔离)
- **不是安全沙箱**:默认 namespace + cgroup 隔离边界比 VM 弱,内核漏洞可逃逸。强隔离需 gVisor / Kata / Firecracker
- **不是编排系统**:Docker 本身只管单机,多机编排需要 Swarm / Kubernetes / Nomad
- **不是 GUI 桌面虚拟化**:容器面向后端服务,不是桌面虚拟化
- **不是数据库 / 中间件**:它是打包与运行载体,不是被运行的应用本身

> **关键认知**:Docker 是"应用容器"的代表,**不是"系统容器"**(LXC / LXD 才是)。理解这一区别能避免 80% 的误用。

## 2. 直觉解释

### 2.1 集装箱类比(官方比喻)

> Docker 的 logo 是一只鲸鱼背着集装箱——这是核心隐喻。

- **传统运输**:货物(应用)形状各异,船运公司(运维)要为每种货物定制容器 → 混乱
- **集装箱化**:所有货物装进标准 20/40 英尺集装箱 → 船、卡车、火车只需适配集装箱接口
- **软件集装箱**:应用 + 依赖 + 文件系统打包成标准镜像 → 任何 Linux 内核都能运行

```
   传统部署                    容器化部署
┌─────────────┐            ┌─────────────┐
│  物理机      │            │  物理机      │
│  ┌────────┐ │            │  ┌────────┐ │
│  │ App A  │ │            │  │ Container│ │
│  │ 依赖X  │ │            │  │ App A   │ │
│  │ 依赖Y  │ │            │  └────────┘ │
│  └────────┘ │            │  ┌────────┐ │
│  单应用     │            │  │ Container│ │
│             │            │  │ App B   │ │
└─────────────┘            │  └────────┘ │
                           │  共享内核   │
                           └─────────────┘
```

### 2.2 "Build Once, Run Anywhere"

这是 Docker 的核心承诺,但有个隐藏前提:**目标机器的内核必须兼容**。

- Linux 容器镜像 → 任意 Linux 内核(同架构) ✓
- Linux 容器镜像 → macOS / Windows ✗(需要 Linux VM)
- x86 镜像 → ARM 机器 ✗(需要 multi-arch build)

## 3. 核心概念与架构

### 3.1 C/S 架构总览

```
┌──────────────────────────────────────────────────┐
│                  用户侧                          │
│   docker CLI / Docker Desktop GUI / SDK          │
└──────────────────┬───────────────────────────────┘
                   │ REST API (unix socket / tcp)
                   ▼
┌──────────────────────────────────────────────────┐
│              Docker daemon (dockerd)             │
│  - 镜像管理  - 卷管理  - 网络管理  - API 服务   │
└──────┬───────────────────────────────────┬───────┘
       │                                   │
       ▼                                   ▼
┌──────────────┐                ┌──────────────────┐
│ containerd   │                │  network / volume│
│ (高级运行时) │                │  plugin          │
│  └── runc    │                └──────────────────┘
│  (低级运行时)│
│      │       │
│      ▼       │
│  Linux kernel│
│  namespaces  │
│  cgroups     │
│  overlayfs   │
└──────────────┘
```

### 3.2 核心术语对照

| 术语 | 类比 | 说明 |
|------|------|------|
| **Image(镜像)** | 可执行程序 | 分层只读模板,包含应用 + 依赖 + 文件系统 |
| **Container(容器)** | 进程 | 镜像的运行实例,可读写层 + 隔离环境 |
| **Registry(仓库)** | 应用商店 | 存储 / 分发镜像(Docker Hub / Harbor / ACR) |
| **Repository(仓库组)** | GitHub repo | 同名不同 tag 的镜像集合,如 `nginx:1.25` |
| **Tag(标签)** | 版本号 | 同一镜像的不同版本,如 `latest` / `1.25-alpine` |
| **Dockerfile** | 源代码 | 构建镜像的指令脚本 |
| **Volume(卷)** | 外接硬盘 | 持久化数据,独立于容器生命周期 |
| **Network(网络)** | 虚拟交换机 | 容器间通信的虚拟网络 |
| **Engine(引擎)** | 操作系统 | dockerd + containerd + runc 的总称 |
| **Runtime(运行时)** | 加载器 | containerd(高级) + runc(低级) |

### 3.3 镜像分层结构

```
┌──────────────────────────┐  ← 可读写层(容器层)
│  Container Layer (R/W)   │     docker run 时创建
├──────────────────────────┤
│  Layer 5: CMD nginx      │  ← 启动命令
├──────────────────────────┤
│  Layer 4: COPY app /app  │  ← 应用代码
├──────────────────────────┤
│  Layer 3: RUN npm install│  ← 依赖安装
├──────────────────────────┤
│  Layer 2: FROM node:20   │  ← 基础镜像
├──────────────────────────┤
│  Layer 1: debian:bookworm│  ← 基础 OS
└──────────────────────────┘
        ↓ UnionFS (overlay2)
   统一视图:/app, /usr, /etc ...
```

**关键性质**:
- 每层都是只读的,多个镜像可共享底层(节省存储)
- 容器启动时在最上层加一个可读写层(写时复制 CoW)
- 修改文件时,从下层复制到容器层再修改,下层不变

### 3.4 容器与镜像的关系

```
   镜像(Image)                    容器(Container)
┌──────────────┐                ┌──────────────┐
│  只读模板    │  ──docker run──>│  运行实例    │
│  分层存储    │                 │  +R/W 层     │
│  不可变      │  <─docker commit─│  临时存在    │
└──────────────┘                └──────────────┘
   持久化在磁盘                    随生命周期消亡
   可推送到 Registry               数据默认不持久
```

### 3.5 三大支柱:namespace / cgroup / UnionFS

| 技术 | 解决问题 | 类比 |
|------|----------|------|
| **namespaces** | 隔离(让容器看不见宿主机) | 单人房,互不干扰 |
| **cgroups** | 限制(让容器用不了全部资源) | 限电限水 |
| **UnionFS** | 分层存储(镜像可叠加) | 透明硫酸纸叠加 |

> 详见 [08-底层原理-namespaces](./08-底层原理-namespaces.md) / [09-底层原理-cgroups](./09-底层原理-cgroups.md) / [10-底层原理-UnionFS](./10-底层原理-UnionFS.md)。

```bash
# 后台运行 nginx,映射端口 8080 -> 80

# 查看运行中的容器
docker ps

# <html>...Welcome to nginx!...</html>

# 进入容器
docker exec -it web sh

# 查看日志
docker logs -f web

# 停止 / 删除
docker stop web
docker rm web
```

## 5. 底层原理(简略)

> 完整版见 [08-11 章](./08-底层原理-namespaces.md)。

### 5.1 一个容器是怎么被创建出来的

```bash
docker run -d --name web -p 8080:80 nginx:1.25
```

发生的事情:

```
1. CLI 通过 REST API 把请求发给 dockerd
2. dockerd 检查本地是否有 nginx:1.25 镜像
   ├─ 有:跳过
   └─ 无:从 Registry 拉取,存到 /var/lib/docker/overlay2/
3. dockerd 调用 containerd 创建容器
4. containerd 调用 runc
5. runc 做了实际工作:
   ├─ clone() + CLONE_NEWPID  → 创建 PID namespace
   ├─ clone() + CLONE_NEWNET  → 创建 NET namespace
   ├─ clone() + CLONE_NEWNS   → 创建 MNT namespace
   ├─ ... 其他 5 个 namespace
   ├─ 设置 cgroup 限制 (CPU / memory / blkio)
   ├─ mount overlayfs (lowerdir + upperdir + workdir)
   ├─ chroot 到新根文件系统
   ├─ exec nginx 进程(PID 1)
   └─ 容器开始运行
6. runc 退出,containerd-shim 接管,作为容器父进程
```

### 5.2 容器 = namespace + cgroup + rootfs

```
┌─────────────────────────────────────┐
│            Linux Kernel             │
│  (宿主机与所有容器共享)             │
└────┬──────────┬──────────┬──────────┘
     │          │          │
     ▼          ▼          ▼
┌─────────┐ ┌─────────┐ ┌─────────┐
│ 容器 A  │ │ 容器 B  │ │ 容器 C  │
│ PID ns  │ │ PID ns  │ │ PID ns  │
│ NET ns  │ │ NET ns  │ │ NET ns  │
│ MNT ns  │ │ MNT ns  │ │ MNT ns  │
│ cgroup  │ │ cgroup  │ │ cgroup  │
│ rootfs  │ │ rootfs  │ │ rootfs  │
└─────────┘ └─────────┘ └─────────┘
```

> **本质**:容器就是一组被 namespace 隔离、被 cgroup 限制、拥有独立 rootfs 的 Linux 进程。**没有虚拟化,没有 hypervisor,共享内核**。

```dockerfile
# Dockerfile

```

## 7. 常见陷阱与调优

### 7.1 把 Docker 当 VM 用

| 误区 | 正确做法 |
|------|----------|
| 一台容器跑 SSH + Nginx + MySQL + Redis | 一容器一进程,用 Compose 编排 |
| 容器里 `apt install` 装东西 | 在 Dockerfile 里装,重新 build |
| 容器里手动改配置后没保存 | 改 Dockerfile,不靠 `docker exec` 改文件 |
| 把容器当长久运行的环境 | 容器随时可销毁重建,数据放 volume |

### 7.2 用 `latest` tag

```bash
docker pull nginx:latest    # ❌ 不可重现,今天和明天可能不一样
docker pull nginx:1.25.3    # ✓ 锁定版本
```

工业实践:在镜像签名 / 准入控制里**禁止 `latest`**,强制语义化版本 + commit SHA。

### 7.3 容器里跑 systemd

容器 PID 1 必须是应用进程本身,不是 init 系统。如果应用不处理 SIGTERM,容器无法优雅停止。详见 [25-故障复盘集](./25-工业实战-故障复盘集.md) 的"PID 1 不处理 SIGTERM"案例。

### 7.4 镜像没清理

```bash
# 看看磁盘占用
docker system df
# TYPE            TOTAL   ACTIVE   SIZE      RECLAIMABLE
# Images          56      12       18.5GB    12.3GB (66%)
# Containers      38      5        800MB     600MB (75%)
# Local Volumes   12      8        5.2GB     1.1GB (21%)

# 清理
docker system prune -a --volumes
```

工业实践:CI 流水线每天定时清理构建机,否则磁盘一周就爆。

### 7.5 其他高频陷阱

- **时区**:容器默认 UTC,日志时间与本地差 8 小时 → 设 `TZ=Asia/Shanghai`
- **文件权限**:Dockerfile 里 `COPY` 进去的文件属主变 root → 用 `--chown=user:group`
- **日志撑爆磁盘**:`docker logs` 默认 json-file 无大小限制 → 设 `max-size` + `max-file`
- **DNS 解析慢**:默认用宿主机 `/etc/resolv.conf` → 用自定义网络启用 embedded DNS

## 9. 与其他方案的关系

### 9.1 Docker vs 虚拟机

| 维度 | 虚拟机 | Docker 容器 |
|------|--------|-------------|
| 隔离级别 | 硬件级(独立内核) | 操作系统级(共享内核) |
| 启动时间 | 30-90 秒 | 0.1-2 秒 |
| 资源开销 | 大(hypervisor + 完整 OS) | 小(共享内核) |
| 单机密度 | 10-30 | 100-500 |
| 镜像大小 | GB 级 | MB 级 |
| 安全性 | 强(硬件隔离) | 中(内核逃逸风险) |
| 跨平台 | 强(可跨 OS) | 弱(同内核) |
| 典型代表 | KVM / VMware / Hyper-V | Docker / containerd / Podman |

### 9.2 Docker vs Podman

| 维度 | Docker | Podman |
|------|--------|--------|
| 架构 | C/S,dockerd 守护进程 | daemonless,直接调用 |
| Root | 默认 root 守护进程 | 默认 rootless |
| 镜像兼容 | 原生 | 完全兼容 OCI |
| Compose | 原生支持 | podman-compose(兼容) |
| K8s 集成 | 间接 | podman generate kube |
| 适用场景 | 通用,生态成熟 | 安全敏感、单机开发 |

### 9.3 Docker vs LXC/LXD(系统容器)

| 维度 | Docker(应用容器) | LXC(系统容器) |
|------|-------------------|-----------------|
| 设计目标 | 跑单个应用 | 跑完整 OS(init + 多进程) |
| 启动进程 | 应用本身 | /sbin/init |
| 类比 | 一次性餐具 | 一整套厨房 |
| 使用场景 | 微服务、CI | 轻量 VM 替代 |

### 9.4 Docker vs Kubernetes

```
Docker:单机容器运行时
    ↓ 提供基础
Kubernetes:多机容器编排
    ↓ 使用
containerd / CRI-O:K8s 的容器运行时
    ↓ 调用
runc:实际创建容器
```

> Docker 是"如何跑一个容器",Kubernetes 是"如何在 1000 台机器上跑 1 万个容器并管理它们的生命周期"。详见 [19-容器生态对比](./19-容器生态对比.md)。

## 10. 面试速答

| 问题 | 一句话答案 |
|------|-----------|
| Docker 是什么? | 基于 Linux namespace/cgroup/UnionFS 的应用容器引擎,把应用与依赖打包成镜像,实现"Build Once, Run Anywhere"。 |
| Docker 和 VM 区别? | VM 虚拟硬件跑完整 OS,Docker 共享宿主机内核只隔离进程;容器启动快、密度高、开销小,但隔离性弱。 |
| Docker 如何实现隔离? | 通过 Linux namespace(PID/NET/MNT/UTS/IPC/USER)让容器有独立的进程视图、网络栈、文件系统。 |
| Docker 如何限制资源? | 通过 cgroups 限制 CPU、内存、IO、PID 数量。 |
| Docker 镜像如何存储? | 通过 UnionFS(overlay2)分层存储,多层只读 + 一层可读写,共享底层节省空间。 |
| 容器是轻量 VM 吗? | 不是。容器共享内核,本质是被隔离的进程;VM 有独立内核,是真正的虚拟机。 |
| 为什么容器启动比 VM 快? | 容器不需要启动内核、init 系统、加载驱动,只是 fork 一个被隔离的进程。 |
| Docker 是 C/S 架构吗? | 是。dockerd 是服务端,CLI 是客户端,通过 REST API 通信。 |
| Docker 的运行时是什么? | containerd(高级运行时) + runc(低级运行时,OCI 规范实现)。 |
| 容器能跨 OS 运行吗? | Linux 容器只能在 Linux 内核上跑;Windows 容器只能在 Windows 上跑;不能交叉。 |

## 11. 综合面试题

### 题 1(基础)
**问**:为什么说"容器就是特殊的进程"?请从内核视角解释。

**答题要点**:
- 容器内进程在宿主机上仍是普通进程(`ps aux` 能看到)
- 只是被加上了 namespace 隔离视图(看不见宿主机其他进程)
- 被 cgroup 限制资源(用不了全部 CPU / 内存)
- 拥有独立 rootfs(chroot / pivot_root)
- 没有虚拟化,没有 hypervisor,共享内核

### 题 2(原理)
**问**:Docker 镜像如何实现分层与共享?

**答题要点**:
- 每条 Dockerfile 指令生成一层
- 层是只读的,通过 UnionFS(overlay2)叠加成统一视图
- 多个镜像共享底层(如都基于 `debian:bookworm`),磁盘只存一份
- 容器启动时加一层可读写层(CoW)
- 修改文件时从下层复制到容器层,下层不变

### 题 3(实战)
**问**:线上容器频繁被 OOM Kill,但宿主机内存充足,可能原因是什么?

**答题要点**:
- 容器自身的 cgroup memory limit 设得过低
- 应用内存泄漏,超过 limit 触发 OOM Killer
- cgroup v1 的 memory.kmem(内核内存)未单独限制,被 slab 占满
- JVM 容器化常见坑:JVM 看到的是宿主机内存,堆设得过大 → 用 `-XX:+UseContainerSupport`(JDK 8u191+)
- 修复:调高 limit、修复泄漏、升级 cgroup v2、JVM 加容器感知参数

### 题 4(对比)
**问**:为什么 K8s 最终选择 containerd 而不是 Docker 作为运行时?

**答题要点**:
- Docker 包含了 K8s 不需要的功能(网络/卷/构建),臃肿
- containerd 是 Docker 的子集,只保留运行时核心,CRI 兼容
- Docker 的 CRI 实现(dockershim)在 K8s 1.24 被移除
- containerd 性能更好、攻击面更小、资源占用更低
- 镜像完全兼容(都是 OCI 标准)

### 题 5(深度)
**问**:容器能否完全替代虚拟机?为什么?

**答题要点**:
- 不能完全替代,因为隔离性差异
- 容器共享内核,内核漏洞可逃逸(如 Dirty COW)
- 强隔离场景(多租户、不可信代码)需要 microVM(gVisor / Kata / Firecracker)
- VM 仍适合:跑不同 OS、跑遗留系统、强合规要求
- 趋势:VM + 容器融合(如 Kata Containers = VM 级隔离 + 容器接口)

### 题 6(工业)
**问**:大厂为什么要把容器密度从 50 提到 200+?瓶颈在哪?

**答题要点**:
- 动机:机器成本,利用率每提 10%,千万级节省
- 瓶颈:内核参数(inotify / conntrack / PID 上限)、网络栈性能、镜像 IO、调度延迟
- 解法:内核调优、cgroup v2、混部(在线 + 离线)、网络加速(Cilium / eBPF)
- 副作用:故障爆炸半径大,需更细粒度隔离

### 题 7(故障)
**问**:`docker run` 后容器立刻 Exited(0),可能原因?

**答题要点**:
- CMD / ENTRYPOINT 是后台进程(如 `service nginx start`),PID 1 退出 → 容器退出
- 改为前台进程(`nginx -g 'daemon off;'`)
- 或者用 `tail -f /var/log/nginx/access.log` 保持前台
- 容器设计哲学:PID 1 必须是前台进程

### 题 8(架构)
**问**:dockerd、containerd、containerd-shim、runc 各自职责?

**答题要点**:
- **dockerd**:面向用户,管理镜像、卷、网络、API
- **containerd**:高级运行时,管理容器生命周期、镜像拉取
- **containerd-shim**:每个容器的父进程,即使 containerd 重启容器不受影响
- **runc**:低级运行时,实际调用 namespace/cgroup 创建容器,OCI 规范实现

### 题 9(安全)
**问**:容器隔离边界比 VM 弱,具体弱在哪?

**答题要点**:
- 共享内核:内核 0day 可逃逸(Dirty COW / CVE-2019-5736 runc 逃逸)
- 共享文件系统:配置不当可挂载宿主机根目录
- 共享设备: `/dev` 默认不隔离
- 共享资源:DoS 风险(CPU / 内存 / PID 耗尽)
- 缓解:capability 裁剪、seccomp、AppArmor、rootless、gVisor / Kata

### 题 10(综合)
**问**:从零设计一个支持 1000 节点的容器平台,会考虑哪些问题?

**答题要点**:
- 镜像分发:P2P(Dragonfly / Kraken)、镜像预热、按需加载(Nydus)
- 调度:bin-packing、亲和性、跨可用区
- 网络:overlay vs underlay、CNI 选择、网络策略
- 存储:CSI、分布式块存储 vs 本地盘
- 监控:Prometheus + cAdvisor、日志 Loki / ELK
- 安全:镜像签名、运行时检测(Falco)、准入控制
- 高可用:多 cluster、故障域隔离、优雅停止
- 成本:混部、弹性、FinOps

## 12. 故障复盘

### 案例 1:CPU throttling 导致延迟毛刺

**现象**:某互联网公司迁移到 Docker 后,P99 延迟从 50ms 飙到 200ms,业务方投诉。

**排查过程**:
1. 看应用日志,无明显错误
2. `docker stats` 显示 CPU 用量 80%,看似没满
3. 但 `cat /sys/fs/cgroup/cpu/cpu.stat` 显示 `nr_throttled` 持续增长
4. **根因**:cgroup v1 CFS quota 设为 `--cpus=2`(200ms/100ms),突发流量在 100ms 窗口内用完 quota,被 throttled 到下一个周期

**修复**:
- 调高 quota(`--cpus=2.5`)
- 升级到 cgroup v2,使用 `cpu.max` 更平滑
- 应用层:降低单请求 CPU 占用(连接池、异步化)

**防范**:
- 监控 `nr_throttled`,> 0 报警
- CPU limit 设为 request 的 1.5-2 倍
- 关键路径服务不设 CPU limit(只设 request)

> 类似案例:Netflix 在 Titus 上观察到 Java 应用因 CPU throttling STW 时间变长。

### 案例 2:容器时区错乱导致定时任务错乱

**现象**:某公司容器化的 cron 任务每天凌晨 8 点跑,实际在 16 点跑,数据延迟 8 小时。

**根因**:
- 容器默认时区 UTC(+00:00)
- 宿主机 / 跳板机时区 `Asia/Shanghai`(+08:00)
- 应用日志时间戳是 UTC,但 cron 解析按 UTC,导致看起来"延迟 8 小时"

**修复**:
```dockerfile
ENV TZ=Asia/Shanghai
RUN ln -snf /usr/share/zoneinfo/$TZ /etc/localtime && echo $TZ > /etc/timezone
```

**防范**:
- Dockerfile 基础镜像统一设时区
- 所有时间存储用 UTC,展示时转本地
- 监控:对比容器与 NTP 时间差

### 案例 3:镜像 `latest` tag 导致回滚困难

**现象**:某团队 `docker pull myapp:latest` 后容器启动失败,无法快速回滚到上一版本。

**根因**:
- `latest` 被覆盖,旧版本已被 GC
- 没有版本号,不知道回滚到哪个 commit

**修复**:
- 改用 `myapp:v1.2.3` + commit SHA(`myapp:git-a1b2c3d`)
- 镜像仓库保留最近 100 个版本

**防范**:
- 准入控制禁止 `latest`
- CI 必须打两个 tag:语义版本 + git SHA
- 镜像仓库 GC 策略保留 N 个最近版本
