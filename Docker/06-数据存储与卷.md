# 06 - 数据存储与卷

> 容器是无状态的,数据是有状态的。理解 volume / bind mount / tmpfs 的差异,才能避免"容器删除数据丢失"的生产事故。

---

## 1. 问题定义与边界

### 1.1 本章解决什么

- 把 **三种存储方式**(volume / bind mount / tmpfs)的适用场景说清
- 把 **数据持久化** 的最佳实践讲到生产级
- 把 **备份 / 迁移 / 灾难恢复** 流程化
- 把 **性能差异** 量化(不同存储方式的 IO 基准)
- 把 **跨主机存储**(NFS / 分布式卷)讲到能落地

### 1.2 本章不解决什么

- 不讲分布式文件系统设计(见 [分布式系统](../分布式系统/) 的存储章节)
- 不讲数据库存储引擎(见 [数据库](../数据库/))
- 不讲 CSI(Container Storage Interface,见 [11-OCI规范与运行时](./11-OCI规范与运行时.md))
- 不讲 K8s PV / PVC(见 [19-容器生态对比](./19-容器生态对比.md))

> **关键认知**:容器设计哲学是 **无状态**——容器随时可销毁重建,数据必须放在容器外的持久化存储里。

## 2. 直觉解释

### 2.1 三种存储类比

```
   volume                  bind mount              tmpfs
   ───────                 ──────────              ─────
   Docker 管理的卷          直接挂载宿主目录         内存盘
   独立于容器生命周期        独立于容器生命周期        容器停就消失
   
   ┌──────────┐            ┌──────────┐            ┌──────────┐
   │  容器     │            │  容器     │            │  容器     │
   │  /data   │            │  /data   │            │  /tmp    │
   └────┬─────┘            └────┬─────┘            └────┬─────┘
        │                       │                       │
   ┌────▼─────────┐        ┌────▼─────┐          ┌────▼─────┐
   │/var/lib/docker│        │/home/me/ │          │   RAM    │
   │/volumes/xxx  │        │  data    │          │ (内存)   │
   └──────────────┘        └──────────┘          └──────────┘
   Docker 管理              宿主机任意路径          不持久
```

### 2.2 容器层 vs 卷:生命周期

```
   容器层(R/W)              Volume
   ────────────              ──────
   容器启动创建              docker volume create 创建
   容器删除消失              容器删除仍存在
   
   ┌──────────┐            ┌──────────┐
   │ 容器层    │            │  Volume  │
   │ (临时)   │            │ (持久)   │
   └──────────┘            └──────────┘
        ↑                       ↑
   docker rm 删除          docker volume rm 删除
```

> **关键**:写日志、临时文件 → 容器层(或 tmpfs);写数据库、用户上传 → volume。

## 3. 核心概念与架构

### 3.1 容器存储分层

```
┌─────────────────────────────────────────────────┐
│              应用视角                             │
│   /app/data  /var/log  /tmp  /etc/config        │
└────┬──────────────┬──────────────┬──────────────┘
     │              │              │
     ▼              ▼              ▼
┌─────────┐  ┌─────────────┐  ┌─────────┐
│ volume  │  │ bind mount  │  │ tmpfs   │
│ (持久) │  │ (宿主路径)  │  │ (内存)  │
└────┬────┘  └──────┬──────┘  └─────────┘
     │              │
     ▼              ▼
┌──────────────────────────────────────┐
│  宿主机文件系统                        │
│  /var/lib/docker/volumes/  (volume)  │
│  /home/me/data            (bind)     │
└──────────────────────────────────────┘
```

### 3.2 volume 的存储路径

```
/var/lib/docker/volumes/
├── myvolume/
│   └── _data/           # 卷数据
│       ├── file1.txt
│       └── subdir/
├── anothervolume/
│   └── _data/
└── metadata.db          # 卷元数据
```

### 3.3 三种存储对比

| 维度 | volume | bind mount | tmpfs |
|------|--------|------------|-------|
| 管理方 | Docker | 用户 | 内核 |
| 路径 | /var/lib/docker/volumes | 宿主任意路径 | 内存 |
| 持久 | 是 | 是 | 否 |
| 跨主机 | 是(NFS / 分布式) | 否 | 否 |
| 性能 | 接近原生 | 接近原生 | 极快(内存) |
| 安全 | 好(Docker 隔离) | 差(可访问宿主) | 好 |
| 备份 | docker volume 标准 | 直接拷贝 | 不需要 |
| 适用 | 数据库 / 应用数据 | 开发挂载源码 | 临时文件 / 缓存 |

## 4. 操作流程与命令

### 4.1 volume 管理

```bash
# 创建
docker volume create mydata

# 列出
docker volume ls
# DRIVER    VOLUME NAME
# local     mydata

# 查看
docker volume inspect mydata
# [
#   {
#     "CreatedAt": "2024-01-01T00:00:00Z",
#     "Driver": "local",
#     "Labels": {},
#     "Mountpoint": "/var/lib/docker/volumes/mydata/_data",
#     "Name": "mydata",
#     "Options": {},
#     "Scope": "local"
#   }
# ]

# 删除
docker volume rm mydata

# 清理未使用
docker volume prune
```

### 4.2 挂载 volume

```bash
# 命名卷
docker run -d -v mydata:/data nginx

# 匿名卷(自动生成名字)
docker run -d -v /data nginx

# 只读挂载
docker run -d -v mydata:/data:ro nginx

# 多卷
docker run -d \
  -v mydata:/data \
  -v myconfig:/etc/nginx/conf.d:ro \
  nginx
```

### 4.3 bind mount

```bash
# 挂载宿主目录
docker run -d -v /home/me/app:/app nginx

# 只读
docker run -d -v /home/me/app:/app:ro nginx

# 用 --mount(更明确)
docker run -d --mount type=bind,source=/home/me/app,target=/app nginx
```

### 4.4 tmpfs

```bash
# 临时内存盘
docker run -d --tmpfs /tmp nginx

# 限制大小
docker run -d --tmpfs /tmp:rw,size=64m nginx

# --mount 形式
docker run -d --mount type=tmpfs,destination=/tmp,tmpfs-size=64m nginx
```

### 4.5 --mount vs -v

```bash
# -v / --volume:简短形式
docker run -v mydata:/data nginx

# --mount:详细形式(推荐)
docker run --mount type=volume,source=mydata,target=/data nginx

# bind
docker run --mount type=bind,source=/home/me/app,target=/app nginx

# tmpfs
docker run --mount type=tmpfs,destination=/tmp nginx
```

> **推荐**:生产用 `--mount`,更明确,不易出错。

## 5. 底层原理(简略)

### 5.1 volume 的挂载机制

```
docker run -v mydata:/data nginx

1. dockerd 检查 mydata 卷是否存在
   ├─ 不存在:在 /var/lib/docker/volumes/mydata/_data 创建
   └─ 存在:跳过
2. 调用 containerd → runc
3. runc 在容器 netns 内:
   - mount --bind /var/lib/docker/volumes/mydata/_data /data
   - /data 在容器内可读写
4. 容器进程看到 /data 是独立目录,实际是宿主机路径的 bind mount
```

### 5.2 tmpfs 的挂载

```
docker run --tmpfs /tmp nginx

1. runc 在容器 netns 内:
   - mount -t tmpfs none /tmp
   - /tmp 在内存中,容器停止释放
2. 不经过宿主机文件系统
```

### 5.3 NFS volume driver

```bash
# 创建 NFS 卷
docker volume create \
  --driver local \
  --opt type=nfs \
  --opt o=addr=10.0.0.10,rw \
  --opt device=:/data/shared \
  nfs-volume

# 容器使用
docker run -d -v nfs-volume:/data nginx

# 底层:runc 执行 mount -t nfs 10.0.0.10:/data/shared /data
```

## 6. 代码与配置示例

### 6.1 数据库持久化

```bash
# PostgreSQL 数据持久化
docker run -d \
  --name postgres \
  -e POSTGRES_PASSWORD=secret \
  -v pg-data:/var/lib/postgresql/data \
  -v pg-init:/docker-entrypoint-initdb.d:ro \
  --restart=unless-stopped \
  postgres:16

# 备份
docker run --rm \
  -v pg-data:/data:ro \
  -v /backup:/backup \
  alpine tar czf /backup/pg-$(date +%Y%m%d).tar.gz -C /data .

# 恢复
docker run --rm \
  -v pg-data:/data \
  -v /backup:/backup:ro \
  alpine sh -c "rm -rf /data/* && tar xzf /backup/pg-20240101.tar.gz -C /data"
```

### 6.2 应用配置文件

```bash
# 配置文件用只读 bind mount
docker run -d \
  --name nginx \
  -v /etc/nginx/nginx.conf:/etc/nginx/nginx.conf:ro \
  -v /etc/nginx/conf.d:/etc/nginx/conf.d:ro \
  -v nginx-cache:/var/cache/nginx \
  -v nginx-logs:/var/log/nginx \
  -p 80:80 -p 443:443 \
  nginx:1.25
```

### 6.3 开发环境源码挂载

```bash
# 开发:源码挂载,代码改即生效
docker run -d \
  --name dev \
  -v $(pwd):/app \
  -v node-modules:/app/node_modules \
  -p 3000:3000 \
  node:20 npm run dev
```

> **关键**:`node_modules` 用命名卷,避免宿主无 node_modules 覆盖容器内安装的。

### 6.4 跨主机共享存储(NFS)

```bash
# 在所有节点创建 NFS 卷
docker volume create \
  --driver local \
  --opt type=nfs \
  --opt o=addr=nfs.internal.corp.com,rw,noatime,rsize=1048576,wsize=1048576 \
  --opt device=:/data/shared \
  shared-data

# 容器使用,跨主机共享
docker run -d -v shared-data:/data myapp
```

### 6.5 Compose 中的卷

```yaml
services:
  db:
    image: postgres:16
    volumes:
      - db-data:/var/lib/postgresql/data
      - ./init.sql:/docker-entrypoint-initdb.d/init.sql:ro
    environment:
      POSTGRES_PASSWORD: ${DB_PASSWORD}

  app:
    image: myapp:v1
    volumes:
      - app-logs:/var/log/app
    tmpfs:
      - /tmp
    depends_on:
      - db

volumes:
  db-data:
    driver: local
  app-logs:
    driver: local
    driver_opts:
      type: nfs
      o: addr=nfs.corp.com,rw
      device::/data/logs
```

## 7. 常见陷阱与调优

### 7.1 陷阱:容器删除后数据丢失

```bash
# ❌ 数据写在容器层
docker run -d --name db postgres
# 写入数据...
docker rm -f db    # 数据没了!

# ✓ 数据写在 volume
docker run -d --name db -v pg-data:/var/lib/postgresql/data postgres
docker rm -f db    # 数据在 pg-data 卷里,还在
```

### 7.2 陷阱:bind mount 权限问题

```bash
# 容器内 UID 1000 写 /app,但宿主 /home/me/app 属主是 1001
docker run -v /home/me/app:/app myapp
# ❌ Permission denied

# 修复 1:调整宿主目录权限
chmod -R 777 /home/me/app   # 不安全

# 修复 2:容器内用对应用户
docker run -u 1001:1001 -v /home/me/app:/app myapp

# 修复 3:Dockerfile 里设 USER 与宿主一致
```

### 7.3 陷阱:macOS bind mount 慢

```bash
# Mac 上 bind mount IO 慢 5-10 倍
docker run -v $(pwd):/app node:20 npm run build   # 慢

# 优化:
# 1. 升级 Docker Desktop 4.6+(VirtioFS)
# 2. 把 node_modules 放命名卷
docker run -v $(pwd):/app -v node-modules:/app/node_modules node:20 npm run build
```

### 7.4 陷阱:volume 未清理导致磁盘满

```bash
# 看卷占用
docker system df
# VOLUME NAME       SIZE
# orphan-volume     5GB

# 清理未使用卷(慎用,会删数据)
docker volume prune

# 安全清理:只删超过 7 天未用的
docker volume prune --filter "until=168h"
```

### 7.5 陷阱:容器内挂载点覆盖

```bash
# 镜像内 /etc/nginx 已有配置,挂载会覆盖
docker run -v /my/nginx.conf:/etc/nginx/nginx.conf:ro nginx
# /etc/nginx/nginx.conf 变成宿主机的版本,其他文件还在

# 但如果挂载目录
docker run -v /my/dir:/etc/nginx nginx
# /etc/nginx 整个被宿主 dir 覆盖,镜像内配置消失!
```

### 7.6 陷阱:NFS 挂载失败导致容器起不来

```bash
# NFS 服务器不可达,容器启动卡住
docker run -v nfs-volume:/data myapp
# 卡在 mount 阶段

# 修复:soft 模式 + timeout
docker volume create \
  --opt type=nfs \
  --opt o=addr=nfs.corp.com,soft,timeo=10,retrans=2 \
  --opt device=:/data/shared \
  nfs-volume
```

### 7.7 陷阱:用 bind mount 挂 secret

```bash
# ❌ secret 文件在宿主,容易被 git 提交
docker run -v /home/me/.aws/credentials:/root/.aws/credentials:ro myapp

# ✓ 用 K8s Secret / Docker Secret
# ✓ 用 Vault / 云 KMS 运行时注入
```

## 8. 工业案例与基准数据

### 8.1 存储性能对比

**测试条件**:fio 顺序写 4KB,容器内测试。

| 存储方式 | IOPS | 吞吐 | 延迟 |
|----------|------|------|------|
| 容器层(overlay2) | 9500 | 38 MB/s | 0.1 ms |
| volume(local) | 10500 | 42 MB/s | 0.09 ms |
| bind mount(local) | 10400 | 41 MB/s | 0.09 ms |
| tmpfs | 85000 | 340 MB/s | 0.01 ms |
| NFS volume | 1200 | 8 MB/s | 0.8 ms |
| EBS(EFS) | 3000 | 12 MB/s | 1.5 ms |

**结论**:
- 本地 volume / bind mount 性能接近原生(overlay2 开销小)
- tmpfs 极快(内存),适合缓存
- NFS / 网络存储性能下降 5-10 倍,适合冷数据

### 8.2 数据库存储选型

| 数据库 | 推荐存储 | 原因 |
|--------|----------|------|
| MySQL / PostgreSQL | 本地 volume(SSD) | 高 IOPS,低延迟 |
| Redis | 本地 volume / tmpfs | 内存数据库,持久化辅助 |
| MongoDB | 本地 volume(SSD) | 高 IOPS |
| Elasticsearch | 本地 volume(SSD) | 高 IOPS |
| Kafka | 本地 volume(NVMe) | 顺序写,高吞吐 |
| 备份归档 | NFS / S3 | 冷数据,低成本 |

> **工业基线**:数据库不用 NFS、不用 overlay2,必须本地 volume。

### 8.3 大厂容器存储实践

**阿里 ACK**:
- 数据库:本地盘(神龙裸金属)+ ESSD
- 应用:emptyDir(tmpfs)
- 共享:NAS(NFS 协议)
- 备份:OSS(对象存储)

**AWS EKS**:
- 数据库:EBS(io2 / gp3)
- 应用:emptyDir
- 共享:EFS(NFS)
- 备份:S3

**Netflix Titus**:
- 数据库:EBS + RDS
- 应用:local scratch
- 共享:EFS
- 备份:S3

### 8.4 备份策略对比

| 策略 | 频率 | 保留 | 恢复时间 | 成本 |
|------|------|------|----------|------|
| 全量备份 | 每天 | 30 天 | 1-4 小时 | 高 |
| 增量备份 | 每小时 | 7 天 | 2-6 小时 | 中 |
| 快照(EBS) | 每小时 | 24 个 | 5-30 分钟 | 中 |
| PITR(持续) | 实时 | N/A | 几秒 | 低 |
| 复制(主从) | 实时 | N/A | 秒级 | 高(双倍资源) |

> **工业实践**:关键数据库 = 全量每日 + 增量每小时 + 主从复制 + 异地备份。

## 9. 与其他方案的关系

### 9.1 Docker volume vs K8s PV/PVC

| 维度 | Docker volume | K8s PV/PVC |
|------|---------------|------------|
| 抽象 | 直接挂载 | 持久卷申请(声明式) |
| 跨主机 | NFS / 分布式 driver | CSI 标准 |
| 动态供给 | 否 | 是(StorageClass) |
| 快照 | 手动 | VolumeSnapshot |
| 适用 | 单机 / Compose | 集群 |

### 9.2 Docker volume vs CSI

CSI(Container Storage Interface)是 K8s 标准,Docker 不原生支持 CSI。第三方工具(如 docker-csi-driver)可桥接。

### 9.3 本地存储 vs 分布式存储

| 维度 | 本地 volume | 分布式存储(Ceph / Gluster) |
|------|-------------|------------------------------|
| 性能 | 高(本地 IO) | 中(网络开销) |
| 可用性 | 单点(节点故障数据不可访问) | 高(多副本) |
| 跨主机 | 否 | 是 |
| 成本 | 低 | 高(需额外集群) |
| 适用 | 数据库 / 高性能 | 共享数据 / 多副本 |

## 10. 面试速答

| 问题 | 一句话答案 |
|------|-----------|
| volume / bind mount / tmpfs 区别? | volume 是 Docker 管理(/var/lib/docker/volumes),bind mount 是宿主路径,tmpfs 是内存。 |
| 容器删除后数据还在吗? | 容器层不在,volume 在;bind mount 在(tmpfs 不在)。 |
| 为什么数据库不用 NFS? | NFS 延迟高、IOPS 低、锁机制弱,数据库性能差。 |
| macOS bind mount 为什么慢? | 文件从 macOS 通过 VirtioFS 跨 VM 边界,Linux 上原生无此问题。 |
| `docker volume prune` 安全吗? | 不安全,会删所有未挂载卷(含备份)。用 `--filter until=168h` 限制。 |
| 容器内挂载点覆盖是什么意思? | 挂载目录时,镜像内该目录的内容被宿主目录覆盖,看不见原内容。 |
| 跨主机共享存储怎么实现? | NFS volume driver,或分布式存储(Ceph / Gluster),或云 NAS。 |
| tmpfs 适合存什么? | 临时文件、缓存、密钥(不持久)。不适合数据库。 |
| 容器内 UID 与宿主权限冲突? | 容器内进程 UID 与宿主 UID 是同一套,需对齐或调宿主目录权限。 |
| K8s PV/PVC 与 Docker volume 区别? | PV/PVC 是声明式 + 动态供给,Docker volume 是直接挂载。 |

## 11. 综合面试题

### 题 1(原理)
**问**:解释 `docker run -v mydata:/data` 的挂载过程。

**答题要点**:
- 检查 mydata 卷是否存在,不存在则在 /var/lib/docker/volumes/mydata/_data 创建
- runc 在容器 netns 内执行 `mount --bind`
- 宿主 _data 目录与容器 /data 关联
- 容器进程看到 /data 是普通目录
- 容器删除,volume 保留

### 题 2(实战)
**问**:PostgreSQL 容器化,如何保证数据安全?

**答题要点**:
- 数据目录用本地 volume(SSD):`-v pg-data:/var/lib/postgresql/data`
- 启用 WAL 归档
- 每日全量备份(pg_dump / 物理备份)
- 每小时增量备份(WAL)
- 主从复制(流复制)
- 异地备份(S3)
- 定期恢复演练

### 题 3(故障)
**问**:容器启动报 `permission denied`,如何排查?

**答题要点**:
- 看挂载点权限:`ls -l /var/lib/docker/volumes/xxx/_data`
- 看容器内 USER:是不是非 root 用户写 root 目录
- 看 SELinux / AppArmor:是不是安全策略挡了
- 看 mount 选项:是不是 ro 挂载
- 修复:对齐 UID、调权限、改 USER

### 题 4(性能)
**问**:容器内数据库 IO 慢,如何优化?

**答题要点**:
- 用 volume 而非容器层(overlay2 有 CoW 开销)
- 用本地 volume 而非 NFS(网络开销)
- 用 SSD / NVMe
- 调内核 IO 调度器(deadline / noop)
- 数据库配置:WAL、shared_buffers
- 监控 iostat:`await`、`%util`

### 题 5(架构)
**问**:设计一个跨主机共享文件方案,要求高可用、高性能。

**答题要点**:
- 选项 1:NFS(简单,单点)
- 选项 2:NAS(云厂商托管 NFS,高可用)
- 选项 3:Ceph / GlusterFS(自建分布式,复杂但灵活)
- 选项 4:对象存储(S3 / OSS,适合冷数据)
- 选型:小规模 NFS,中规模 NAS,大规模 Ceph
- 配置:soft mount + timeout,避免 NFS 挂死容器

### 题 6(工业)
**问**:大厂如何备份容器化数据库?

**答题要点**:
- 主从复制:从库实时同步
- 物理备份:pgBackRest / Percona XtraBackup
- 增量备份:WAL / binlog
- 快照:EBS 快照(秒级)
- 异地:跨 region 复制
- 验证:定期恢复演练
- 保留:7 天日志 + 30 天全量 + 1 年归档
- 监控:备份成功率、恢复时间

### 题 7(深度)
**问**:为什么 overlay2 上跑数据库有性能损失?

**答题要点**:
- overlay2 有 CoW 机制,第一次写要复制
- 大文件(数据文件)修改触发整文件复制
- metadata 操作有额外开销(lookup)
- fsync 性能下降(写屏障)
- 解决:数据目录用 volume(本地 ext4 / xfs),不用 overlay2

### 题 8(安全)
**问**:如何安全地在容器里挂载 secret?

**答题要点**:
- 不用 bind mount 挂 secret 文件(宿主上明文)
- Docker Secret(Swarm 模式)
- K8s Secret(etcd 加密)
- Vault 运行时注入(sidecar 拉取)
- 云 KMS / SSM Parameter Store
- tmpfs 挂载(内存,不持久)

### 题 9(故障)
**问**:NFS 挂载失败导致所有容器起不来,如何应急?

**答题要点**:
- 短期:NFS 改 soft + timeout,挂失败快速返回
- 应急:临时去掉 NFS 依赖,容器用 emptyDir 启动
- 排查:NFS 服务器状态、网络、防火墙
- 长期:依赖解耦,关键服务不依赖 NFS
- 监控:NFS 健康检查,挂了告警

### 题 10(综合)
**问**:设计一个生产级存储方案,涵盖数据库、应用、备份。

**答题要点**:
- 数据库:本地 NVMe volume(主)+ EBS(从)
- 应用日志:emptyDir(tmpfs,滚动)
- 配置:ConfigMap + 只读挂载
- Secret:K8s Secret + tmpfs
- 共享:NAS(NFS)
- 备份:每日全量 + 每小时增量 + WAL
- 异地:S3 跨 region
- 监控:磁盘使用、IOPS、延迟
- 容量规划:每月增长预测 + 告警阈值
- 灾难恢复:RTO 30 分钟,RPO 5 分钟

## 12. 故障复盘

### 案例 1:容器删除导致数据库数据丢失

**现象**:某团队开发环境,`docker rm -f postgres` 后所有数据消失。

**根因**:
- 没用 volume,数据写在容器层
- 容器删除,容器层也删除

**修复**:
```bash
# 用 volume
docker run -v pg-data:/var/lib/postgresql/data postgres
```

**防范**:
- 团队规范:数据库必须用 volume
- Docker Compose 模板统一
- 定期备份

### 案例 2:bind mount 权限冲突

**现象**:容器内应用报 `Permission denied`,无法写挂载目录。

**根因**:
- 容器内 USER 1000
- 宿主目录属主 1001
- UID 不匹配

**修复**:
```bash
# 调宿主目录属主
sudo chown -R 1000:1000 /home/me/app

# 或容器内用对应 UID
docker run -u 1001:1001 -v /home/me/app:/app myapp
```

**防范**:
- Dockerfile 设固定 UID
- 部署脚本检查宿主目录权限
- 文档说明 UID 要求

### 案例 3:NFS 挂载卡死导致节点不可用

**现象**:某集群节点 NotReady,所有容器卡在挂载 NFS。

**根因**:
- NFS hard mount,服务器宕机时挂载操作无限等待
- 容器卡在 mount 阶段
- 节点上所有依赖 NFS 的容器都卡

**修复**:
```bash
# 改 soft mount + timeout
docker volume create \
  --opt type=nfs \
  --opt o=addr=nfs.corp.com,soft,timeo=30,retrans=2 \
  --opt device=:/data/shared \
  nfs-volume
```

**防范**:
- NFS 用 soft + timeout
- 关键服务不依赖 NFS
- 监控 NFS 健康

### 案例 4:macOS 开发环境慢

**现象**:某开发者 Mac 上 `npm run dev` 慢,Webpack 热更新延迟 30 秒。

**根因**:
- bind mount 通过 VirtioFS 转发,文件 IO 慢
- Webpack 监听大量文件,IO 频繁

**修复**:
- 升级 Docker Desktop 4.6+(VirtioFS 默认)
- node_modules 用命名卷(不挂载)
- 用 WSL 2(Windows)或原生 Linux(开发服务器)

**防范**:
- Mac 开发用 Docker Desktop 最新版
- 大型项目考虑 dev container + 远程开发

### 案例 5:volume 占满磁盘

**现象**:某节点 `/var/lib/docker/volumes` 占 200 GB,磁盘 95%。

**根因**:
- 测试环境创建大量卷,未清理
- 数据库测试数据累积

**修复**:
```bash
# 看哪些卷占用
docker system df -v

# 清理未使用卷
docker volume prune --filter "until=168h"

# 长期:定时清理脚本
```

**防范**:
- 监控卷占用
- 测试环境定时清理
- 生产环境严格审批创建卷
