## 14.2 章节简介

容器化带来的最大运维挑战是**可观测性碎片化**: 一个 K8s 集群可能有数千个短生命周期 Pod,传统基于主机的监控/日志体系完全失效。本章从三个层次系统讲解容器监控与日志:

1. **Docker 原生能力**: `docker stats` / `docker logs` / docker events
2. **指标体系**: cAdvisor + node-exporter + Prometheus + Grafana
3. **日志体系**: docker log-driver + Fluent Bit/Loki + ELK

工业实践表明,**监控告警延迟每降低 1 分钟,P0 故障平均恢复时间(MTTR)可缩短 30%**。Netflix 在 Titus 平台公开数据:完善的可观测性使其容器平台 MTTR 从 45min 降至 12min。

**本章工业焦点**:
- 阿里 SLS(日志服务)日均 50PB 数据接入
- 字节跳动 BMQ 日志采集峰值 800M条/秒
- Netflix Titus 单集群 50万容器指标采集架构
- 大厂日志成本治理(采样/降级/冷热分离)

## 14.3 核心概念

### 14.3.1 可观测性三支柱

**定义**: 系统的内部状态可以从外部输出推断的程度。

```
        可观测性 ≠ 监控
            │
   ┌────────┴────────┐
   │                 │
  监控              可观测性
  (Monitoring)    (Observability)
   │                 │
 预定义指标        任意维度查询
 已知问题告警      未知问题排查
 被动响应          主动探索
```

**三支柱协作模式**:

```
告警触发                    根因定位
   │                          │
   ▼                          ▼
Metrics ────────────────► Logs ──────────────► Traces
(发现异常)              (定位事件)            (还原路径)

例: CPU > 90% (Metrics)
   → 某容器 OOM 日志 (Logs)
   → 该请求调用链慢在 DB (Traces)
```

### 14.3.2 容器指标分层

```
┌─────────────────────────────────────────┐
│  业务指标 (Business)                    │  ← QPS/转化率/订单数
│  例: 订单成功率、API P99 延迟            │
├─────────────────────────────────────────┤
│  应用指标 (Application)                 │  ← Micrometer/Prom client
│  例: JVM 堆、HTTP 状态码、连接池         │
├─────────────────────────────────────────┤
│  容器指标 (Container)                   │  ← cAdvisor
│  例: CPU/内存/网络/IO(按容器维度)        │
├─────────────────────────────────────────┤
│  节点指标 (Node/Host)                   │  ← node-exporter
│  例: 节点 CPU/磁盘/内核参数              │
├─────────────────────────────────────────┤
│  基础设施 (Infrastructure)              │  ← 云厂商
│  例: 物理机、网络设备、存储               │
└─────────────────────────────────────────┘
```

**USE 方法**(Utilization / Saturation / Errors):
- CPU: 使用率 % / 运行队列长度 / 上下文切换错误
- 内存: 使用率 % / swap 频度 / OOM 次数
- 磁盘 IO: 使用率 % / IO 等待时间 / IO 错误
- 网络: 带宽使用 % / 重传率 / 丢包率

**RED 方法**(Rate / Errors / Duration):
- 服务入口指标标准: QPS / 错误率 / 延迟分布

### 14.3.3 容器日志分类

| 日志类型 | 来源 | 体积 | 价值 | 保留期 |
|---------|------|-----|-----|-------|
| 业务日志 | 应用 stdout/stderr | 大 | 高 | 7-30天 |
| 访问日志 | Nginx/网关 | 极大 | 中 | 3-7天 |
| 审计日志 | 鉴权/操作 | 中 | 极高 | 90天-1年 |
| 错误日志 | 应用 error | 小 | 极高 | 30-90天 |
| 调试日志 | debug 级别 | 极大 | 低 | 1-3天 |

**容器日志三大坑**:
1. 日志写到容器内文件,容器删除即丢失
2. 日志未限制大小,撑爆磁盘
3. 多容器日志混在一起,无法区分来源

正确姿势: **stdout/stderr + log-driver 集中采集**

### 14.3.4 docker stats 实时指标

```bash
$ docker stats

CONTAINER ID   NAME       CPU %     MEM USAGE / LIMIT   MEM %    NET I/O         BLOCK I/O        PIDS
a1b2c3d4       web        1.50%     256MiB / 1GiB       25.00%   12MB / 8MB      45MB / 12MB      87
e5f6g7h8       redis      0.30%     64MiB / 512MiB      12.50%   3MB / 5MB       8MB / 2MB        12
...
```

**底层实现**: `docker stats` 通过 containerd 的 CRI 接口读取 cgroup 数据,默认每 1s 刷新。

```go
// 伪代码: docker stats 数据来源
func getContainerStats(containerID string) Stats {
    // 1. 读取 cgroup v2 文件
    cpu := readCgroupFile(containerID, "cpu.stat")
    mem := readCgroupFile(containerID, "memory.current")
    io  := readCgroupFile(containerID, "io.stat")

    // 2. 计算差值(累计值 → 瞬时值)
    cpuPercent := (cpuNow - cpuPrev) / interval

    // 3. 读取网络命名空间统计
    net := readNetDev("/proc/net/dev")

    return Stats{CPU: cpuPercent, Mem: mem, IO: io, Net: net}
}
```

**注意事项**:
- `docker stats` 显示的是**容器相对主机**的 CPU %,多核机器可能超过 100%
- 内存统计包含 page cache,应用实际使用看 `RSS` 而非 `USAGE`
- 无 cgroup v2 支持的老版本 docker 可能统计不准

### 14.3.5 docker logs 与日志驱动

```bash
# 基础用法
docker logs web
docker logs -f web                 # 实时跟随
docker logs --tail 100 web         # 最后 100 行
docker logs --since 30m web        # 最近 30 分钟
docker logs -t web                 # 显示时间戳

# 多容器
docker compose logs -f --tail=50 web redis
```

**关键限制**: `docker logs` 仅能查看 **json-file / journald / local** 驱动输出的日志,如果用 fluentd/gelf 则不可用。

## 14.4 底层原理

### 14.4.1 cAdvisor 工作原理

**cAdvisor**(Container Advisor)是 Google 开源的容器指标采集器,K8s 内置为 kubelet 的一部分。

```
┌──────────────────────────────────────────────┐
│                cAdvisor                       │
│                                               │
│  ┌─────────────┐    ┌─────────────────────┐  │
│  │ Discovery    │───►│ Container Handler   │  │
│  │ (容器发现)   │    │ (按容器注册)         │  │
│  └─────────────┘    └─────────────────────┘  │
│                            │                  │
│  ┌─────────────────────────▼──────────────┐ │
│  │ Stats Collector(采集器)                │ │
│  │  ├─ CPU: cgroup cpu.stat               │ │
│  │  ├─ Mem: cgroup memory.current         │ │
│  │  ├─ IO:  cgroup io.stat                │ │
│  │  ├─ Net: /proc/<pid>/net/dev           │ │
│  │  └─ FS:  overlay2 上层目录大小          │ │
│  └─────────────────────────┬──────────────┘ │
│                            │                  │
│  ┌─────────────────────────▼──────────────┐ │
│  │ Storage Backend(存储后端)              │ │
│  │  ├─ In-memory(默认,1分钟数据)         │ │
│  │  ├─ Prometheus(/metrics 端点)         │ │
│  │  ├─ InfluxDB                            │ │
│  │  └─ BigQuery                            │ │
│  └────────────────────────────────────────┘ │
└──────────────────────────────────────────────┘
```

**关键指标**:

```
# CPU(累计 ns)
container_cpu_usage_seconds_total{container="web"} 1234.56

# 内存(byte)
container_memory_usage_bytes{container="web"}      # 含 cache
container_memory_rss{container="web"}              # 实际使用
container_memory_working_set_bytes{container="web"} # OOM 判定依据

# IO(累计 byte)
container_fs_reads_bytes_total{container="web"}
container_fs_writes_bytes_total{container="web"}

# 网络(累计 byte)
container_network_receive_bytes_total{container="web"}
container_network_transmit_bytes_total{container="web"}
```

**为什么 OOM 看的是 working_set 而不是 rss**?

```
memory.usage = rss + page_cache + swap

memory.working_set = usage - inactive_file (非活跃文件页)

内核 OOM 判定依据: working_set_bytes > memory.limit
理由: inactive_file 可被回收,不应计入"必死"判定
```

### 14.4.2 docker logs 实现机制

```
┌────────────────────────────────────────────────┐
│ 容器进程 (PID 1)                                │
│   │                                            │
│   ▼ write()                                    │
│ /dev/pts/0 (TTY) 或 pipe                       │
│   │                                            │
└───┼────────────────────────────────────────────┘
    │
    ▼ containerd-shim 读取
┌────────────────────────────────────────────────┐
│ Log Driver(日志驱动)                          │
│   ├─ json-file: 写入 JSON 行格式文件           │
│   ├─ journald: 写入 systemd journal            │
│   ├─ fluentd:  发送到 fluentd socket           │
│   ├─ gelf:     发送 GELF 协议                  │
│   ├─ awslogs:  发送到 CloudWatch               │
│   └─ none:     丢弃                            │
└────────────────────────────────────────────────┘
    │
    ▼ json-file 默认路径
/var/lib/docker/containers/<id>/<id>-json.log
```

**json-file 格式**:

```json
{"log":"2026-07-04 10:00:00 INFO Starting...\n","stream":"stdout","time":"2026-07-04T10:00:00.123456789Z"}
{"log":"Error: connection refused\n","stream":"stderr","time":"2026-07-04T10:00:01.234567890Z"}
```

**日志驱动对比**:

| 驱动 | docker logs 可读 | 性能 | 可靠性 | 适用场景 |
|------|-----------------|------|-------|---------|
| json-file | ✓ | 中(本地写盘) | 中(磁盘满丢) | 单机/开发 |
| local | ✓ | 高(二进制) | 高(轮转内置) | 生产单机 |
| journald | ✓ | 中 | 高(索引) | systemd 集成 |
| fluentd | ✗ | 高(直发) | 中(网络) | 集群采集 |
| gelf | ✗ | 中 | 中 | Graylog |
| awslogs | ✗ | 中 | 高 | AWS 云上 |
| none | - | 最高 | - | 不需日志 |
| syslog | ✗ | 中 | 中 | 系统日志集成 |

### 14.4.3 Prometheus 拉取模型

```
       Pull 模型(默认 15s 抓取)
            │
            ▼
┌───────────────────────────────────┐
│  Prometheus Server                │
│  ┌──────────────────────────┐    │
│  │ TSDB(时序数据库)         │    │
│  │  └─ block(2h 一块)        │    │
│  └──────────────────────────┘    │
│  ┌──────────────────────────┐    │
│  │ PromQL 查询引擎           │    │
│  └──────────────────────────┘    │
│  ┌──────────────────────────┐    │
│  │ Alertmanager 告警         │    │
│  └──────────────────────────┘    │
└───────────────────────────────────┘
            ▲
            │ /metrics
   ┌────────┴────────┐
   │                 │
node-exporter    cAdvisor    应用 /metrics
(主机指标)       (容器指标)   (业务指标)
```

**Prometheus vs 日志系统对比**:

| 维度 | Prometheus | ELK |
|------|-----------|-----|
| 数据模型 | 时序(数值) | 文档(全文) |
| 查询语言 | PromQL | Lucene/DSL |
| 写入路径 | Pull | Push |
| 采样 | 必采样(15s) | 全量 |
| 成本 | 低(降采样) | 高(全量) |
| 适用 | 告警/趋势 | 排查/审计 |

### 14.4.4 日志采集两种模式

```
模式 A: DaemonSet 模式(节点级)
┌─────────────────────────────────┐
│ Node                            │
│  ┌─────────┐ ┌─────────┐       │
│  │ Pod1    │ │ Pod2    │       │
│  │ stdout  │ │ stdout  │       │
│  └────┬────┘ └────┬────┘       │
│       │           │            │
│  ┌────▼───────────▼────┐       │
│  │ /var/log/containers │       │
│  └─────────┬───────────┘       │
│            │                   │
│  ┌─────────▼───────────┐       │
│  │ Fluent Bit(DS)      │───────┼──► Loki/ES
│  └─────────────────────┘       │
└─────────────────────────────────┘

模式 B: Sidecar 模式(容器级)
┌─────────────────────────────────┐
│ Pod                              │
│  ┌─────────┐  ┌──────────────┐ │
│  │ App     │─►│ Sidecar      │ │
│  │ 写文件  │  │ Fluentd      │─┼──► Loki/ES
│  └─────────┘  └──────────────┘ │
└─────────────────────────────────┘
```

**选型决策**:

| 维度 | DaemonSet | Sidecar |
|------|----------|---------|
| 资源开销 | 低(1/N) | 高(N倍) |
| 隔离性 | 弱 | 强 |
| 配置灵活 | 低 | 高 |
| 适用 | 通用场景 | 多输出/特殊解析 |

**工业现状**: 90% 场景用 DaemonSet,Sidecar 用于以下特殊场景:
- 业务日志写本地文件(非 stdout)
- 多日志格式需要不同解析
- 不同 Pod 日志需隔离传输

### 14.5.3 告警规则

`monitoring/rules/container.yml`:

```yaml
groups:
  - name: container.rules
    rules:
      # 1. 容器 CPU 持续高
      - alert: ContainerHighCPU
        expr: |
          sum(rate(container_cpu_usage_seconds_total{name!=""}[5m])) by (name)
          /
          sum(container_spec_cpu_quota{name!=""} / container_spec_cpu_period{name!=""}) by (name)
          > 0.85
        for: 10m
        labels:
          severity: warning
        annotations:
          summary: "容器 {{ $labels.name }} CPU > 85% 持续 10min"
          description: "当前值: {{ $value | humanizePercentage }}"

      # 2. 容器内存接近限制
      - alert: ContainerMemoryNearLimit
        expr: |
          container_memory_working_set_bytes / container_spec_memory_limit_bytes > 0.9
        for: 5m
        labels:
          severity: critical
        annotations:
          summary: "容器 {{ $labels.name }} 内存 > 90% limit"

      # 3. 容器重启
      - alert: ContainerRestarted
        expr: |
          increase(kube_pod_container_status_restarts_total[1h]) > 0
        labels:
          severity: warning
        annotations:
          summary: "容器 {{ $labels.container }} 1h 内重启"

      # 4. 节点磁盘将满
      - alert: NodeDiskWillFill
        expr: |
          predict_linear(node_filesystem_avail_bytes[1h], 24 * 3600) < 0
        labels:
          severity: critical
        annotations:
          summary: "节点 {{ $labels.instance }} 24h 内磁盘将满"

      # 5. 容器 OOM
      - alert: ContainerOOMKilled
        expr: |
          increase(container_memory_failcnt[5m]) > 0
        labels:
          severity: critical
        annotations:
          summary: "容器 {{ $labels.name }} 触发 OOM"
```

## 14.8 故障复盘

### 14.8.1 故障 1: 日志撑爆磁盘导致节点 NotReady

**背景**: 2024-03,某公司 K8s 集群 30% 节点突然 NotReady,业务告警疯狂。

**现象**:
- 节点日志盘 `/var/lib/docker` 100% 占满
- kubelet 无法写镜像,docker daemon 响应慢
- Pod 状态变为 ContainerCreating 失败

**根因分析**:
```bash
# 检查磁盘占用
$ du -sh /var/lib/docker/containers/*/*.log | sort -h | tail -5
120G  /var/lib/docker/containers/abc123/abc123-json.log
85G   /var/lib/docker/containers/def456/def456-json.log

# 检查日志驱动配置
$ cat /etc/docker/daemon.json
{
  "log-driver": "json-file"
  # ❌ 没有配置 max-size / max-file
}
```

某应用 Nginx access_log 默认全开,QPS 1万,单日产生 120GB 日志。

**修复过程**:
1. **临时**: `truncate -s 0 abc123-json.log` 清空日志(避免删文件,fd 还在)
2. **配置**: 修改 `/etc/docker/daemon.json`
   ```json
   {
     "log-driver": "json-file",
     "log-opts": {
       "max-size": "100m",
       "max-file": "5"
     }
   }
   ```
3. **重启**: `systemctl restart docker`(注意: 重启会断开容器,需提前 drain)
4. **存量**: 对已运行容器无法生效,需重建

**预防措施**:
- **daemon.json 强制配置 max-size/max-file**(P0)
- **Prometheus 告警**: 节点磁盘 > 80% / 90% 双告警
- **日志标准化**: 应用层只用 stdout,关闭非必要 access_log
- **定期巡检**: cron 每天检查大日志文件

### 14.8.2 故障 2: Prometheus 拉取超时导致告警丢失

**背景**: 2024-05,某公司 P0 故障期间告警未触发,损失扩大。

**现象**:
- 业务 P99 延迟从 50ms 飙到 5s
- Prometheus dashboard 显示数据缺失
- 告警状态: pending(未触发 alert)
- Prometheus 日志: `Error scraping target: context deadline exceeded`

**根因**:
```
故障期间业务 Pod 大量重启
  → Pod 指标暴露端点 /metrics 响应慢(>30s)
  → Prometheus 默认 scrape_timeout=10s 超时
  → 数据缺失 → 告警条件不满足 → 不触发
```

**修复过程**:
1. **临时**: 手动触发告警,通知 SRE
2. **配置调整**:
   ```yaml
   scrape_configs:
     - job_name: "app"
       scrape_interval: 15s
       scrape_timeout: 30s      # ← 调大
       scheme: http
   ```
3. **关键告警双路径**:
   - 业务指标告警(Prometheus)
   - 黑盒探测告警(blackbox-exporter,独立路径)
4. **告警兜底**: 添加 `absent()` 规则
   ```yaml
   - alert: MetricsMissing
     expr: absent(up{job="app"})
     for: 2m
     labels:
       severity: critical
   ```

**预防措施**:
- **关键告警必须有兜底**: 数据缺失本身也是告警
- **scrape_timeout 不能等于 scrape_interval**(留出余量)
- **多源验证**: 业务指标 + 黑盒探测 + 用户侧拨测
- **告警演练**: 定期验证告警链路通畅

### 14.8.3 故障 3: Fluentd 阻塞导致业务卡死

**背景**: 2024-06,某公司应用日志写入卡住,所有请求超时。

**现象**:
- 应用日志写 stdout 突然阻塞
- HTTP 请求全部超时
- 容器 CPU/内存正常,但服务无响应

**根因**:
```
应用 stdout ─► docker json-file driver
                     │
                     ▼
              Fluentd(采集) ─► ES(下游)
                                │
                                ▼ 网络抖动 → ES 拒绝写入
                     ▲
                     │ Fluentd 内存满 → 阻塞 socket
                     │
              Docker log driver 阻塞
                     ▲
                     │
              应用 stdout write() 阻塞
```

**Fluentd 默认行为**:
- `buffer_queue_limit` 默认 256
- 队列满后**阻塞**写入端
- 导致 docker log driver 写入阻塞
- 最终应用 stdout write() 阻塞

**修复过程**:
1. **临时**: 重启 Fluentd,清空队列
2. **配置调整**:
   ```xml
   <match **>
     @type elasticsearch
     buffer_type file
     buffer_path /var/log/fluentd/buffer
     buffer_chunk_limit 64m
     buffer_queue_limit 1024         # ← 调大
     flush_interval 5s
     # 关键: 队列满时丢弃日志,不阻塞业务
     overflow_action drop_oldest_log
     retry_limit 5
     retry_wait 1s
     retry_max_interval 30s
   </match>
   ```
3. **架构调整**:
   - 应用日志改为非阻塞写入(独立线程/缓冲区)
   - 关键日志双写: stdout(本地) + 异步上报

**预防措施**:
- **日志采集器必须配置 overflow_action**(P0)
- **应用层日志异步化**: 不让日志拖慢业务线程
- **下游降级方案**: ES 不可用时落本地盘
- **混沌测试**: 模拟 ES 故障验证日志链路

### 14.8.4 故障 4: cAdvisor 指标不准导致误判

**背景**: 2024-04,某公司基于 Prometheus 告警扩容,但实际负载正常,造成资源浪费。

**现象**:
- 告警显示容器 CPU > 95%
- 实际应用内部监控显示 CPU 仅 30%
- 扩容 3 倍后告警仍然持续

**根因**:
```
cAdvisor 报告的 container_cpu_usage_seconds_total
  ├─ 包含 cgroup throttling 等待时间 ❌
  └─ CPU limit 越小,throttle 越严重,数值越虚高

公式: cpu% = cpu_usage / (cpu_quota / cpu_period)
       = (实际 + 等待) / 限制
```

某 Java 应用 CPU limit=500m,实际使用 150m,但因 GC 短峰触发 throttle,cAdvisor 报告 480m(96%),触发告警。

**修复过程**:
1. **改用正确公式**:
   ```promql
   # 错误(包含 throttle)
   rate(container_cpu_usage_seconds_total[5m])

   # 正确(实际使用)
   rate(container_cpu_usage_seconds_total[5m])
     / on(container) ignoring(mode)
   sum(rate(container_cpu_cfs_periods_total[5m])) by (container)
   ```
2. **监控 throttle**:
   ```yaml
   - alert: ContainerCPUThrottling
     expr: |
       rate(container_cpu_cfs_throttled_periods_total[5m])
       / rate(container_cpu_cfs_periods_total[5m]) > 0.3
     for: 5m
   ```
3. **应用优化**: Java 调大 CPU limit(避免 GC throttle)

**预防措施**:
- **理解指标含义**: 看 cgroup 源文件而非简单用
- **多源对比**: 应用 JMX/Prometheus client 与 cAdvisor 对比
- **CPU throttle 单独监控**: 不混在 CPU 使用率里
- **limit 设置留余量**: CPU limit = 应用均值的 2-3 倍

### 14.8.5 故障 5: 日志泄露敏感信息

**背景**: 2024-02,某公司安全审计发现生产日志中含用户密码、API token。

**现象**:
- Loki/ES 中可搜索到 `password=xxx` `token=Bearer xxx`
- 日志保留期 30 天,数据可能已泄露
- 部分日志被同步到第三方监控平台

**根因**:
- 应用直接 `log.info("received request: " + request)`
- 框架默认打印完整请求体,包含敏感字段
- 未配置脱敏规则

**修复过程**:
1. **代码修复**:
   ```java
   // 错误
   log.info("login request: {}", request);

   // 正确
   log.info("login request: user={}, password=***", request.getUsername());
   ```
2. **日志采集层脱敏**(Fluentd):
   ```ruby
   <filter **>
     @type record_transformer
     enable_ruby true
     <record>
       message ${record["message"].gsub(/password=\S+/, "password=***")}
     </record>
   </filter>
   ```
3. **历史数据清理**:
   ```bash
   # Loki 删除指定日志
   curl -X POST http://loki:3100/loki/api/v1/delete \
     -d 'query={app="auth"}&start=1706745600000000000'
   ```
4. **审计与合规**:
   - 全量扫描历史日志,统计泄露范围
   - 评估是否需上报监管(个人信息保护法)

**预防措施**:
- **代码规范**: 严禁日志直接打印请求对象
- **采集层脱敏**: Fluentd/Logstash 配置敏感字段规则
- **Loki/ES 字段加密**: 高敏字段单独加密存储
- **定期扫描**: 用 TruffleHog 等工具扫描日志库

## 14.9 最佳实践

### 14.9.1 监控分层实践

```
┌─────────────────────────────────────────────────┐
│  L0: 黑盒探测(独立路径)                         │
│  - HTTP 拨测 / TCP 探活 / DNS 解析              │
│  - 用途: 兜底告警,业务是否真的可用             │
├─────────────────────────────────────────────────┤
│  L1: 业务指标(应用自暴露)                      │
│  - RED: Rate / Errors / Duration                │
│  - USE: Utilization / Saturation / Errors       │
│  - 用途: 业务健康度,告警主路径                 │
├─────────────────────────────────────────────────┤
│  L2: 容器指标(cAdvisor)                        │
│  - CPU / 内存 / IO / 网络                       │
│  - 用途: 容量规划,资源告警                     │
├─────────────────────────────────────────────────┤
│  L3: 节点指标(node-exporter)                   │
│  - 主机 CPU / 磁盘 / 内核                       │
│  - 用途: 节点级故障定位                         │
├─────────────────────────────────────────────────┤
│  L4: 基础设施(云厂商)                          │
│  - 物理机 / 网络 / 存储                         │
│  - 用途: 底层故障排查                           │
└─────────────────────────────────────────────────┘
```

### 14.9.2 日志规范

**6 条铁律**:

1. **只用 stdout/stderr**(不写文件,不用文件 appender)
2. **结构化 JSON**(不用字符串拼接,便于解析)
3. **必须包含 trace_id**(关联请求链路)
4. **敏感字段脱敏**(password/token/身份证)
5. **分级合理**(INFO 业务事件,WARN 异常可恢复,ERROR 需人工)
6. **限流保护**(单实例日志速率上限,防止日志风暴)

**标准日志字段**:

```json
{
  "@timestamp": "2026-07-04T10:00:00.123Z",
  "level": "INFO",
  "service": "order-service",
  "env": "prod",
  "trace_id": "abc123",
  "span_id": "def456",
  "user_id": "u_12345",
  "message": "order_created",
  "duration_ms": 123,
  "status": "success"
}
```

### 14.9.3 告警分级

| 级别 | 触发条件 | 响应时间 | 通知方式 | 示例 |
|------|---------|---------|---------|------|
| P0(致命) | 业务全停/数据丢失 | < 5min | 电话+短信+IM | API 5xx > 50% |
| P1(严重) | 部分功能不可用 | < 15min | 短信+IM | 单机房故障 |
| P2(警告) | 指标异常但可用 | < 1h | IM | CPU > 80% |
| P3(提示) | 容量/趋势问题 | 工作日 | 邮件 | 磁盘 3 天将满 |

**告警黄金法则**:
- **每个告警必须可执行**(收到能知道做什么)
- **避免告警风暴**(同一问题聚合,最多 3 条)
- **告警去重**(基于 (alertname, labels) hash)
- **定期 review 告警有效性**(噪音率 > 30% 必须改)

### 14.9.4 日志采样策略

```
全量日志 ─► 采样 ─► 存储
              │
              ├─ 业务关键(订单/支付): 100%
              ├─ 错误日志(ERROR):    100%
              ├─ 普通访问日志:        10%-50%
              └─ 调试日志(DEBUG):     1% 或不存
```

**Fluentd 采样配置**:

```xml
<filter access.log>
  @type sampler
  sample_rate 0.1
  # 错误日志不采样
  <filter access.log>
    @type grep
    <regexp>
      key level
      pattern ERROR
    </regexp>
  </filter>
</filter>
```

### 14.9.5 日志成本治理

**4 板斧**:

1. **冷热分离**: 7 天热数据 SSD,30 天温数据 HDD,1 年冷数据 OSS
2. **降采样**: 1min → 5min → 1h 多级降采样
3. **采样**: 高频低价值日志按比例采样
4. **索引裁剪**: 仅关键字段建索引,文本用 doc_values

**成本对比**(1TB/天日志,保留 90 天):

| 方案 | 存储成本 | 查询性能 |
|------|---------|---------|
| ES 全量索引 | 90 TB | 100ms |
| ES + 冷热分离 | 30 TB | 100ms(热) / 5s(冷) |
| Loki + 全冷存 | 3 TB | 5-30s |
| ES + 采样 10% | 9 TB | 100ms |

## 14.10 常见陷阱

### 14.10.1 陷阱 1: docker logs 看不到日志

**错误现象**:
```bash
$ docker logs web
# 无输出,但应用确实在打日志
```

**原因排查**:

| 原因 | 验证方法 | 解决方案 |
|------|---------|---------|
| 日志写到文件非 stdout | 进容器 `ls /app/logs` | 改应用配置输出到 stdout |
| log-driver 不是 json-file/journald | `docker inspect web` 看 LogConfig | 改 log-driver |
| 应用日志缓冲未刷新 | 日志无 \n 结尾 | 配置日志即时 flush |
| stdout 被重定向 | 检查启动命令 `> file.log` | 改为 stdout |

### 14.10.2 陷阱 2: Prometheus 抓不到 cAdvisor 指标

**排查清单**:

```bash
# 1. cAdvisor 是否运行
$ curl http://cadvisor:8080/healthz

# 2. /metrics 是否可访问
$ curl http://cadvisor:8080/metrics | head

# 3. Prometheus target 状态
$ curl http://prometheus:9090/api/v1/targets

# 4. 检查 scrape 配置
$ kubectl get secret prometheus-config -o yaml

# 5. 防火墙/网络策略
$ telnet cadvisor 8080
```

### 14.10.3 陷阱 3: 指标标签基数爆炸

**问题**:
```promql
# 危险: 按 user_id 标签
http_requests_total{user_id="u1"}
http_requests_total{user_id="u2"}
...
http_requests_total{user_id="u10000000"}  # 1000万时序!
```

**后果**:
- Prometheus 内存爆掉
- 查询超时
- 磁盘膨胀 10 倍以上

**解决**:
- **高基数字段不能做 label**(user_id/request_id/trace_id)
- 改放日志或追踪系统
- 必要时用 `histogram_quantile` + bucket 替代

### 14.10.4 陷阱 4: 时区不一致

**现象**: Grafana 看到的时间和实际差 8 小时。

**根因**: 容器默认 UTC,应用 / 日志 / Prometheus 各自时区不一致。

**解决**:
```dockerfile
# Dockerfile 设置时区
ENV TZ=Asia/Shanghai
RUN ln -snf /usr/share/zoneinfo/$TZ /etc/localtime && echo $TZ > /etc/timezone
```

```yaml
# docker-compose.yml
services:
  app:
    environment:
      TZ: Asia/Shanghai
```

**注意**: 推荐做法是**全程 UTC**,仅在前端展示时转本地时区。

### 14.10.5 陷阱 5: 日志格式不统一

**问题**: 不同应用日志格式各异,难以统一查询。

```
应用A: 2026-07-04 10:00:00 INFO order received
应用B: [INFO] 2026/07/04 10:00:00.123 order received
应用C: {"level":"INFO","time":"2026-07-04T10:00:00Z","msg":"order received"}
```

**解决**:
- **强制结构化 JSON**(所有应用必须)
- **统一字段名**(level / time / msg / trace_id)
- **采集层解析**: 不同格式用不同 pipeline_stages
- **日志接入检查**: CI 中验证日志格式

### 14.10.6 陷阱 6: 告警风暴

**现象**: 一次故障收到 200+ 条告警,反而找不到根因。

**解决**:
- **告警分组**: 同类告警用 `group_by: [alertname, cluster]`
- **抑制规则**: P0 触发时抑制 P1/P2
  ```yaml
  inhibit_rules:
    - source_match: { severity: critical }
      target_match: { severity: warning }
      equal: ['cluster', 'service']
  ```
- **根因告警优先**: 上游故障时不下游重复告警
- **告警静默**: 维护期间静默非关键告警

## 14.11 面试题

### Q1: docker logs 命令底层是怎么工作的?

**答**:
docker logs 通过 containerd-shim 读取容器的 stdout/stderr 流,根据配置的 log-driver 写入对应后端:
- **json-file**: 写入 `/var/lib/docker/containers/<id>/<id>-json.log`,JSON 行格式
- **journald**: 写入 systemd journal
- **fluentd**: 通过 socket 发送到 fluentd
- 等

docker logs 仅对**有本地存储**的驱动(json-file / journald / local)生效,对 fluentd/gelf 等远程驱动不可用。

### Q2: 容器 CPU 使用率怎么算?

**答**:
```promql
# 单核百分比(0-100% × 核数)
rate(container_cpu_usage_seconds_total[5m]) * 100

# 占 limit 比例
sum(rate(container_cpu_usage_seconds_total{name="web"}[5m]))
  /
sum(container_spec_cpu_quota{name="web"} / container_spec_cpu_period{name="web"})
```

**注意**:
- `container_cpu_usage_seconds_total` 包含 throttle 时间,实际使用应扣除
- CPU quota = -1 表示不限制,需特殊处理
- 多核机器单容器 CPU 可能 > 100%

### Q3: 容器内存看哪个指标?为什么不是 usage?

**答**:
看 **container_memory_working_set_bytes**,不是 container_memory_usage_bytes。

原因:
- `usage` 包含 page cache,应用实际未占用
- `working_set` = usage - inactive_file(可回收的文件页)
- **内核 OOM 判定依据是 working_set > limit**,而非 usage

```promql
# 正确的内存使用率
container_memory_working_set_bytes / container_spec_memory_limit_bytes
```

### Q4: Prometheus vs ELK 区别?分别适用什么场景?

**答**:
| 维度 | Prometheus | ELK |
|------|-----------|-----|
| 数据模型 | 时序数值 | 文档全文 |
| 采集方式 | Pull | Push |
| 查询语言 | PromQL | Lucene DSL |
| 采样 | 必采样(15s) | 全量 |
| 成本 | 低 | 高(15x) |
| 适用 | 告警/趋势 | 排查/审计 |

**选型**:
- 指标告警 → Prometheus
- 全文检索/复杂日志查询 → ES
- 仅按 label 查日志 → Loki(成本最低)
- 大规模指标 → VictoriaMetrics / Thanos

### Q5: 容器日志为什么必须用 stdout 而不是写文件?

**答**:
4 个原因:
1. **生命周期一致**: 容器删除日志可被采集器完整收走,不会丢
2. **采集标准**: docker logs / kubectl logs / Fluentd 标准接口
3. **自动轮转**: log-driver 配置 max-size/max-file 自动轮转
4. **12-factor 兼容**: 日志作为事件流,不关心存储

写文件的问题:
- 容器删除日志丢
- 多副本无法聚合
- 大小不可控
- 需进容器才能看

### Q6: 日志采集器(Fluentd/Fluent Bit)如何避免拖慢业务?

**答**:
3 个关键点:
1. **配置 overflow_action**: 队列满时丢弃日志(`drop_oldest_log`),不阻塞上游
2. **缓冲队列**: 文件 buffer 而非内存,容量大且宕机不丢
3. **应用层异步**: 业务线程不直接写 stdout,通过异步队列缓冲

```xml
<!-- Fluentd 关键配置 -->
buffer_queue_limit 1024
overflow_action drop_oldest_log
flush_interval 5s
retry_limit 5
```

### Q7: 如何防止 Prometheus 标签基数爆炸?

**答**:
**原则**: 高基数字段(user_id / request_id / trace_id / IP)不能做 label。

**原因**:
- Prometheus 时序 = (指标名, label_set) 组合
- 1000万 user_id × 1 指标 = 1000万时序
- 内存爆炸,查询超时,磁盘膨胀

**解决**:
- 高基数放日志或追踪系统
- 用 histogram bucket 替代精确值
- 用 `metric_relabel_configs` 删除高基数 label
  ```yaml
  metric_relabel_configs:
    - source_labels: [user_id]
      action: labeldrop
  ```

### Q8: 容器 OOM 怎么排查?

**答**:
**步骤**:
1. 确认是否 OOM: `docker inspect <id>` 看 OOMKilled 字段
2. 查时间点: `dmesg | grep -i "killed process"`
3. 看内存增长: Grafana 查 `container_memory_working_set_bytes`
4. 应用级分析: JVM dump / Go pprof / Python tracemalloc
5. 调整 limit 或修内存泄漏

**常见原因**:
- limit 设置过小
- 内存泄漏
- 大对象一次性加载
- GC 配置不当(JVM 堆未适配容器)
- 临时文件加载到内存

### Q9: docker stats 显示的 CPU 100% 是什么意思?

**答**:
- **单核**: 100% = 1 核打满
- **多核机器**: 100% = 1 核打满,400% = 4 核打满
- **容器 CPU limit**: limit=2 时 200% 才是限制

```bash
# 查看 limit
$ docker inspect web | grep CpuQuota
"CpuQuota": 200000   # 2 核 = 200000/100000
```

### Q10: 如何设计一个高可用的日志采集系统?

**答**:
**架构**:
```
App ─stdout─► Docker(json-file)
                  │
                  ▼
         Fluent Bit(DS, 节点级)
                  │
                  ▼
         Kafka(缓冲, 3副本)
                  │
       ┌──────────┴──────────┐
       │                     │
   Flink(实时)           ES(检索)
       │                     │
   告警/大盘              Kibana
```

**关键设计**:
1. **采集层**: DaemonSet,节点故障不影响其他节点
2. **缓冲层**: Kafka 解耦上下游,3 副本保证可靠
3. **存储层**: 冷热分离 + 副本
4. **降级方案**: ES 故障时 Flunentd 落本地盘待恢复
5. **限流保护**: 每个应用日志速率上限,防止打爆
6. **多机房部署**: 独立采集 + 中心聚合

## 14.12 总结

### 14.12.1 核心要点

1. **可观测性三支柱**: Metrics(指标)/Logs(日志)/Traces(追踪),各自定位不同
2. **容器指标分层**: 业务 → 应用 → 容器 → 节点 → 基础设施
3. **USE/RED 方法**: 资源类看 USE,服务类看 RED
4. **日志必须 stdout**: 不写文件,12-factor 兼容
5. **结构化 JSON**: 便于解析、查询、关联
6. **采集器 DaemonSet 优先**: 资源开销最低
7. **告警分层 + 兜底**: P0-P3 分级,关键告警必须有 absent 兜底
8. **成本治理**: 冷热分离 + 降采样 + 采样 + 索引裁剪

### 14.12.2 工业实践要点

1. **阿里 SLS**: 50PB/天,冷热分离 + 列存,成本降 70%
2. **Netflix Atlas**: 50万容器/集群,自研替代 Prometheus
3. **字节 BMQ**: 800M条/秒,三级存储 + 索引裁剪
4. **VictoriaMetrics**: 比 Prometheus 省 4 倍内存,适合超大规模
5. **Loki**: 比 ES 省 15 倍存储,label 查询场景首选

### 14.12.3 决策树

```
监控选型:
├─ 单机/小规模 → Prometheus + Grafana + Loki
├─ K8s 集群 → Prometheus + cAdvisor + node-exporter + Grafana
├─ 大规模 K8s(>500节点) → VictoriaMetrics / Thanos
├─ 超大规模(>1万节点) → 自研(参考 Netflix Atlas)

日志选型:
├─ 仅按 label 查 → Loki(成本最低)
├─ 全文检索 → ES
├─ 超大规模 → 自研(参考阿里 SLS / 字节 BMQ)
└─ 简单场景 → docker logs + ELK 单机
```
