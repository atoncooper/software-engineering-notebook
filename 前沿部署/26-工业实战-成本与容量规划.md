## 二、问题定义与边界

### 2.1 解决什么

- **成本结构拆解**: GPU、网络、存储、软件、运维各占多少
- **利用率提升路径**: 从均值 30% 到 70% 的工程方法
- **计费模型设计**: per-token / per-request / 混合
- **容量规划方法**: 预留 / 按需 / Spot 的配比
- **跨地域成本优化**: 带宽、副本、同步开销
- **冷热分层策略**: 模型分级管理
- **真实成本基准**: 千万 QPS 平台年度预算

### 2.2 不解决什么

- 不深入推理引擎内部（03-08 章）
- 不重复分布式并行原理（07 章）
- 不覆盖模型训练成本（仅推理侧）
- 不讨论自建数据中心硬件采购（聚焦云上 / 混合云）

### 2.3 核心矛盾

```
   成本 ←────矛盾────→ 质量
     │                  │
     │                  │
     ▼                  ▼
   延迟 ←────权衡────→ 吞吐
     │                  │
     │                  │
     ▼                  ▼
   弹性 ←────取舍────→ 稳定
```

容量规划本质是这五个维度的多目标优化, 没有"最优解", 只有"当前业务最合适的解"。

## 三、GPU 利用率: 从 30% 到 70% 的路径

### 3.1 为什么均值只有 30%?

LLM 推理 GPU 利用率低下的根本原因:

| 原因 | 说明 | 利用率损失 |
|------|------|-----------|
| Prefill/Decode 不均衡 | Prefill 计算密集 (高 util), Decode 内存密集 (低 util) | 混部时 Decode 拖累 |
| 请求到达不均 | 高峰 vs 低谷, 低谷时 GPU 空转 | 30-50% |
| batch 不饱满 | 队列浅时 batch=1, GPU 算力闲置 | 50-70% |
| 模型加载开销 | 冷启动 / 切换模型时 GPU 闲置 | 突发场景明显 |
| KV Cache 浪费 | 显存碎片, 实际可批处理请求数少 | 20-30% |
| 单请求阻塞 | 长 Decode 占用 GPU, 新请求等待 | 20-40% |

**实测基准** (Llama-70B, 8×H100, vLLM 0.5):
- 单租户、低 QPS: GPU util 平均 15-25%
- 单租户、高 QPS: GPU util 平均 40-50%
- 多租户、continuous batching: GPU util 平均 50-60%
- 多租户、PD 分离 + continuous batching: GPU util 平均 60-70%

### 3.2 利用率提升路径

#### 路径 1: Continuous Batching（+15-20%）

**原理**: 传统 static batching 等齐 batch_size 才执行, 队头阻塞严重。Continuous batching 让请求在 token 级别动态加入/退出 batch, GPU 始终满载。

**配置** (vLLM):
```python
# vLLM 默认已启用 continuous batching
from vllm import LLM, SamplingParams

llm = LLM(
    model="meta-llama/Llama-2-70b-chat-hf",
    tensor_parallel_size=8,
    # 关键参数
    max_num_seqs=256,           # 同时处理的请求序列数
    max_num_batched_tokens=8192, # 单步 batch 的最大 token 数
    gpu_memory_utilization=0.9,  # GPU 显存利用率上限
    enable_prefix_caching=True,  # 前缀缓存
    swap_space=8,                # KV Cache swap 到 CPU 的空间 (GB)
)

# 监控
# vllm expose metrics at :8000/metrics
# 关键指标:
#   vllm:num_requests_running    - 运行中请求数
#   vllm:num_requests_waiting    - 等待中请求数
#   vllm:gpu_cache_usage_perc    - KV Cache 使用率
#   vllm:num_preemption           - 抢占次数
```

**收益**: GPU util 从 25% → 45%, 吞吐 +60%。

#### 路径 2: PD 分离（+10-15%）

**原理**: Prefill (计算密集, 高 util) 与 Decode (内存密集, 低 util) 分到不同集群, 各自优化。

```
            传统单集群
        ┌──────────────────┐
        │   Prefill + Decode│  GPU util 45%
        │   混部            │
        └──────────────────┘

            PD 分离
    ┌──────────────┐  ┌──────────────┐
    │  Prefill 集群 │  │ Decode 集群   │
    │  GPU util 85%│  │ GPU util 65% │
    │  (计算密集)   │  │ (内存密集)   │
    └──────┬───────┘  └──────▲───────┘
           │                   │
           └─ KV Cache 传输 ──┘
              (RDMA / NVLink)
```

**收益**: 整体 GPU util 从 45% → 60%, 但需付出 KV 传输开销 (详见 [25 章 PD 分离 TTFT 退化案例](25-工业实战-故障复盘集.md#22-案例-2-pd-分离后-ttft-飙升))。

#### 路径 3: Speculative Decoding（+5-10%）

**原理**: 用小模型 (draft model) 预测多个 token, 大模型 (target model) 一次性验证多个 token, 减少 Decode 步数。

```python
# vLLM 0.6+ 支持 speculative decoding
llm = LLM(
    model="meta-llama/Llama-2-70b-chat-hf",
    tensor_parallel_size=8,
    speculative_model="meta-llama/Llama-2-7b-chat-hf",  # draft model
    num_speculative_tokens=5,                            # 每步预测 5 个
    speculative_draft_tensor_parallel_size=1,            # draft 单卡
)
```

**收益**: Decode 步数减少 30-50% (取决于接受率), 整体吞吐 +20-30%, 但 draft model 也占 GPU。

#### 路径 4: LoRA 多租户（+10-15%）

**原理**: 多个 LoRA adapter 共享同一个 base model, 一张 GPU 服务多个客户/任务, 利用率叠加。

```python
# vLLM LoRA 多租户
llm = LLM(
    model="meta-llama/Llama-2-70b-chat-hf",
    enable_lora=True,
    max_loras_per_gpu=8,              # 单 GPU 同时 8 个 LoRA
    max_lora_rank=64,
    max_cpu_loras=32,                 # CPU 缓存 32 个
)

# 加载多个 LoRA
llm.load_lora_adapter("loras/customer_a_v1")
llm.load_lora_adapter("loras/customer_b_v1")
llm.load_lora_adapter("loras/customer_c_v1")

# 请求时指定 LoRA
sampling_params = SamplingParams(temperature=0.7, max_tokens=100)
outputs = llm.generate(
    prompts,
    sampling_params,
    lora_request=LoRARequest("customer_a_v1", 1, "loras/customer_a_v1"),
)
```

**收益**: 单卡服务 8 个客户 (而非 1 个), GPU util 从 50% → 65%, 单客户成本降低 8 倍。

#### 路径 5: Spot/Interruptible（成本 -60%, util 不变）

**原理**: 利用云厂商闲置 GPU (Spot/竞价实例), 成本仅为按需的 30-40%, 但可能被中断。

**适用场景**:
- 离线批处理 (LLM 训练数据生成、批量推理)
- 非实时 Agent 任务
- 异步 AIGC 任务 (Midjourney、Suno 模式)

**不适用场景**:
- 实时对话 (ChatGPT 模式)
- SLA 严格的 API
- 流式输出

**配置** (Karpenter + AWS Spot):
```yaml
# karpenter provisioner with spot
apiVersion: karpenter.sh/v1alpha5
kind: Provisioner
metadata:
  name: gpu-spot
spec:
  requirements:
    - key: karpenter.sh/capacity-type
      operator: In
      values: ["spot"]
    - key: node.kubernetes.io/instance-type
      operator: In
      values: ["p4d.24xlarge", "p4de.24xlarge", "g5.48xlarge"]
  limits:
    resources:
      nvidia.com/gpu: 100
  provider:
    instanceProfile: KarpenterNodeInstanceProfile
  ttlSecondsAfterEmpty: 30
```

### 3.3 综合提升路径

```
  30% ──→ Continuous Batching ──→ 45%
   │
       ──→ PD 分离 ──→ 60%
   │
       ──→ LoRA 多租户 ──→ 65%
   │
       ──→ Speculative Decoding ──→ 70%
   │
       ──→ Spot (成本侧 -60%) ──→ 综合成本下降 50%
```

**实测** (某公司 Llama-70B 推理服务, 8×H100):
- 优化前 (vLLM 0.5 默认): GPU util 28%, 月成本 $96K
- Continuous Batching: GPU util 45%, 月成本 $60K (-38%)
- + PD 分离: GPU util 60%, 月成本 $48K (-50%)
- + LoRA 多租户 (8 客户): GPU util 65%, 单客户月成本 $6K (-94%)
- + Spot (离线部分): 综合月成本 $36K (-63%)

## 四、FinOps for AI: 计费模型

### 4.1 计费维度

LLM 推理的计费比传统服务复杂, 涉及多个维度:

| 计费维度 | 单位 | 说明 | 适用场景 |
|---------|------|------|---------|
| **per-token** | $/1K tokens | 区分 input/output | OpenAI、Anthropic |
| **per-request** | $/request | 不区分 token 数 | 简单 API、限流场景 |
| **per-second** | $/GPU-second | 按 GPU 使用时长 | Modal、Replicate |
| **per-hour** | $/GPU-hour | 长时租用 | 传统云 GPU |
| **混合** | 订阅 + 超额 | 月费 + 超量计费 | ChatGPT Plus、Claude Pro |

### 4.3 per-token 计费实现

```python
# 简化的 per-token 计费实现
from dataclasses import dataclass
from typing import Dict
import time

@dataclass
class PricingConfig:
    """计费配置"""
    input_price_per_1m: float    # $/1M input tokens
    output_price_per_1m: float   # $/1M output tokens
    cached_input_price_per_1m: float = None  # 缓存命中价 (可选)

class TokenMeter:
    """Token 计量器"""
    def __init__(self, pricing: PricingConfig):
        self.pricing = pricing
        self.usage_records = []

    def record_request(
        self,
        user_id: str,
        input_tokens: int,
        output_tokens: int,
        cached_input_tokens: int = 0,
    ):
        """记录一次请求的 token 使用"""
        non_cached_input = input_tokens - cached_input_tokens

        # 计算费用
        cost = 0.0
        if self.pricing.cached_input_price_per_1m and cached_input_tokens > 0:
            cost += (cached_input_tokens / 1_000_000) * self.pricing.cached_input_price_per_1m
        cost += (non_cached_input / 1_000_000) * self.pricing.input_price_per_1m
        cost += (output_tokens / 1_000_000) * self.pricing.output_price_per_1m

        self.usage_records.append({
            "user_id": user_id,
            "input_tokens": input_tokens,
            "output_tokens": output_tokens,
            "cached_input_tokens": cached_input_tokens,
            "cost_usd": cost,
            "timestamp": time.time(),
        })
        return cost

    def get_user_usage(self, user_id: str, start: float, end: float) -> Dict:
        """查询用户在时间段的用量"""
        user_records = [
            r for r in self.usage_records
            if r["user_id"] == user_id and start <= r["timestamp"] <= end
        ]
        return {
            "total_requests": len(user_records),
            "total_input_tokens": sum(r["input_tokens"] for r in user_records),
            "total_output_tokens": sum(r["output_tokens"] for r in user_records),
            "total_cost_usd": sum(r["cost_usd"] for r in user_records),
        }

# 使用示例
pricing = PricingConfig(
    input_price_per_1m=5.0,     # GPT-4o 价格
    output_price_per_1m=15.0,
    cached_input_price_per_1m=2.5,
)
meter = TokenMeter(pricing)

# 记录请求
cost = meter.record_request(
    user_id="user_123",
    input_tokens=2000,
    output_tokens=500,
    cached_input_tokens=1500,  # 1500 命中缓存
)
print(f"本次请求费用: ${cost:.4f}")  # $0.01375
```

### 4.4 混合计费模型

**模式**: 订阅 (月费) + 超额按量

```python
@dataclass
class SubscriptionPlan:
    """订阅计划"""
    name: str
    monthly_fee: float              # 月费 ($)
    included_input_tokens: int      # 包含的 input tokens / 月
    included_output_tokens: int     # 包含的 output tokens / 月
    overage_input_price_per_1m: float   # 超额单价
    overage_output_price_per_1m: float

class HybridBilling:
    """混合计费引擎"""
    def __init__(self, plan: SubscriptionPlan):
        self.plan = plan
        self.user_usage = {}  # user_id -> {input_tokens, output_tokens, billing_cycle_start}

    def _get_current_usage(self, user_id: str):
        if user_id not in self.user_usage:
            self.user_usage[user_id] = {
                "input_tokens": 0,
                "output_tokens": 0,
                "billing_cycle_start": time.time(),
            }
        return self.user_usage[user_id]

    def charge(self, user_id: str, input_tokens: int, output_tokens: int) -> dict:
        """计费: 优先扣套餐, 超额按量"""
        usage = self._get_current_usage(user_id)

        # 套餐内剩余
        remaining_input = max(0, self.plan.included_input_tokens - usage["input_tokens"])
        remaining_output = max(0, self.plan.included_output_tokens - usage["output_tokens"])

        # 套餐内扣减
        in_plan_input = min(remaining_input, input_tokens)
        in_plan_output = min(remaining_output, output_tokens)

        # 超额部分
        overage_input = input_tokens - in_plan_input
        overage_output = output_tokens - in_plan_output

        # 超额费用
        overage_cost = (
            (overage_input / 1_000_000) * self.plan.overage_input_price_per_1m
            + (overage_output / 1_000_000) * self.plan.overage_output_price_per_1m
        )

        # 更新用量
        usage["input_tokens"] += input_tokens
        usage["output_tokens"] += output_tokens

        return {
            "in_plan": overage_cost == 0,
            "overage_cost_usd": overage_cost,
            "remaining_input_tokens": self.plan.included_input_tokens - usage["input_tokens"],
            "remaining_output_tokens": self.plan.included_output_tokens - usage["output_tokens"],
        }

# 示例: ChatGPT Plus 类似计划
plus_plan = SubscriptionPlan(
    name="Plus",
    monthly_fee=20.0,
    included_input_tokens=2_000_000,    # 2M input / 月
    included_output_tokens=500_000,     # 0.5M output / 月
    overage_input_price_per_1m=5.0,
    overage_output_price_per_1m=15.0,
)
billing = HybridBilling(plus_plan)
```

### 4.5 成本归因 (Cost Attribution)

多租户平台必须能精确归因每个用户的成本:

```python
class CostAttribution:
    """成本归因系统"""
    def __init__(self):
        # user_id -> list of {resource, cost, timestamp}
        self.attribution = {}

    def attribute(
        self,
        user_id: str,
        resource_type: str,    # gpu / network / storage
        cost_usd: float,
        metadata: dict = None,
    ):
        if user_id not in self.attribution:
            self.attribution[user_id] = []
        self.attribution[user_id].append({
            "resource_type": resource_type,
            "cost_usd": cost_usd,
            "metadata": metadata or {},
            "timestamp": time.time(),
        })

    def showback_report(self, user_id: str) -> dict:
        """生成 showback 报告 (展示给用户)"""
        records = self.attribution.get(user_id, [])
        by_resource = {}
        for r in records:
            t = r["resource_type"]
            by_resource[t] = by_resource.get(t, 0) + r["cost_usd"]
        return {
            "user_id": user_id,
            "total_cost_usd": sum(r["cost_usd"] for r in records),
            "by_resource": by_resource,
            "period": "current_month",
        }
```

## 五、预留 vs 按需 vs Spot

### 5.1 三种计费模式对比

| 模式 | 折扣 | 保障 | 提前期 | 适用场景 |
|------|------|------|--------|---------|
| **按需 (On-Demand)** | 1x (基准) | 100% | 0 | 突发、短期、测试 |
| **预留 (Reserved)** | 0.4-0.7x | 100% | 1-3 年 | 长期稳定负载 |
| **Spot (竞价)** | 0.1-0.3x | 0% (可中断) | 0 | 批处理、容错任务 |

|------|-----|-----------|----------------|----------------|-----------|
| p4d.24xlarge | 8× A100 40GB | $32.77 | $19.57 (-40%) | $13.10 (-60%) | $9.83 (-70%) |
| p4de.24xlarge | 8× A100 80GB | $40.97 | $24.46 (-40%) | $16.39 (-60%) | $12.29 (-70%) |
| p5.48xlarge | 8× H100 80GB | $98.32 | $58.99 (-40%) | $39.33 (-60%) | $29.50 (-70%) |
| g5.48xlarge | 8× A10G 24GB | $8.00 | $4.78 (-40%) | $3.19 (-60%) | $2.40 (-70%) |

### 5.2 混合策略

```
            流量负载曲线
   QPS │
       │              ┌───┐ 突发 (按需)
       │            ┌─┘   └─┐
       │           ┌┘       └──┐
       │      ┌────┘            └────┐ 基线+常态波动 (预留)
       │ ┌────┘                      └─┐
       │─┘                             └── 低谷 (Spot 可用于离线)
       └──────────────────────────────────→ 时间
```

**配比建议** (基于流量模式):

| 流量模式 | 预留 | 按需 | Spot |
|---------|------|------|------|
| 稳定 (web API) | 70% | 20% | 10% |
| 周期波动 (办公时段) | 50% | 30% | 20% |
| 突发 (社交媒体) | 40% | 50% | 10% |
| 批处理为主 (离线推理) | 20% | 10% | 70% |
| 混合 (实时 + 异步) | 50% | 20% | 30% |

### 5.3 容量规划模型

```python
import numpy as np
from dataclasses import dataclass
from typing import List

@dataclass
class TrafficPattern:
    """流量模式: 24 小时 QPS 分布"""
    hourly_qps: List[float]   # 24 个值, 每小时平均 QPS

@dataclass
class GPUCapacity:
    """GPU 容量配置"""
    reserved_gpus: int       # 预留 GPU 数
    on_demand_max: int       # 按需上限
    spot_max: int            # Spot 上限

class CapacityPlanner:
    """容量规划器"""
    def __init__(
        self,
        gpu_throughput_qps: float,    # 单 GPU 吞吐 (QPS)
        price_on_demand: float,       # $/GPU/hour
        price_reserved_3yr: float,    # $/GPU/hour
        price_spot: float,            # $/GPU/hour
    ):
        self.gpu_qps = gpu_throughput_qps
        self.prices = {
            "on_demand": price_on_demand,
            "reserved": price_reserved_3yr,
            "spot": price_spot,
        }

    def plan(self, traffic: TrafficPattern, strategy: str = "balanced") -> dict:
        """规划容量"""
        # 1. 计算每小时的 GPU 需求
        hourly_gpus_needed = [np.ceil(qps / self.gpu_qps) for qps in traffic.hourly_qps]

        # 2. 基线 (P50)
        baseline_gpus = int(np.percentile(hourly_gpus_needed, 50))
        # 3. 高峰 (P95)
        peak_gpus = int(np.percentile(hourly_gpus_needed, 95))

        # 4. 根据策略分配
        if strategy == "stable":        # 稳定优先
            reserved = peak_gpus
            on_demand_max = int(peak_gpus * 0.2)
            spot_max = int(peak_gpus * 0.1)
        elif strategy == "balanced":    # 平衡
            reserved = baseline_gpus
            on_demand_max = peak_gpus - baseline_gpus
            spot_max = int(peak_gpus * 0.3)
        elif strategy == "cost_first":  # 成本优先
            reserved = int(baseline_gpus * 0.7)
            on_demand_max = peak_gpus - reserved
            spot_max = int(peak_gpus * 0.5)
        else:
            raise ValueError(f"Unknown strategy: {strategy}")

        # 5. 计算月成本
        monthly_cost = self._calculate_monthly_cost(
            hourly_gpus_needed, reserved, on_demand_max, spot_max
        )

        return {
            "strategy": strategy,
            "baseline_gpus": baseline_gpus,
            "peak_gpus": peak_gpus,
            "reserved_gpus": reserved,
            "on_demand_max": on_demand_max,
            "spot_max": spot_max,
            "monthly_cost_usd": monthly_cost,
            "cost_breakdown": self._cost_breakdown(hourly_gpus_needed, reserved, on_demand_max, spot_max),
        }

    def _calculate_monthly_cost(self, hourly_gpus, reserved, od_max, spot_max):
        """计算月成本 (720 小时)"""
        total = 0.0
        for hour_gpus in hourly_gpus:
            # 复制 30 天
            for _ in range(30):
                # 预留部分 (固定费用)
                total += reserved * self.prices["reserved"]
                remaining = max(0, hour_gpus - reserved)
                # 按需部分
                od_used = min(remaining, od_max)
                total += od_used * self.prices["on_demand"]
                remaining -= od_used
                # Spot 部分
                spot_used = min(remaining, spot_max)
                total += spot_used * self.prices["spot"]
        return total

    def _cost_breakdown(self, hourly_gpus, reserved, od_max, spot_max):
        reserved_cost = reserved * self.prices["reserved"] * 720
        od_cost = 0
        spot_cost = 0
        for hour_gpus in hourly_gpus:
            for _ in range(30):
                remaining = max(0, hour_gpus - reserved)
                od_cost += min(remaining, od_max) * self.prices["on_demand"]
                remaining -= min(remaining, od_max)
                spot_cost += min(remaining, spot_max) * self.prices["spot"]
        return {
            "reserved": reserved_cost,
            "on_demand": od_cost,
            "spot": spot_cost,
        }
```

### 6.1 成本来源

```
        ┌─────────────────────────────────────┐
        │           跨地域成本来源             │
        └─────────────────────────────────────┘
                          │
        ┌─────────────────┼─────────────────┐
        ▼                 ▼                 ▼
   ┌─────────┐     ┌──────────┐     ┌──────────┐
   │ 带宽费用 │     │ 副本存储 │     │ 同步开销 │
   │ Egress  │     │ 多份模型 │     │ 跨区一致 │
   │ 跨区流量 │     │ 多份 KV  │     │ 数据复制 │
   └─────────┘     └──────────┘     └──────────┘
```

### 6.2 带宽定价 (AWS 跨区, 2024 年公开)

**Egress (出站)**: 数据从某区域传出

| 源区域 → 目标区域 | $/GB |
|------------------|------|
| us-east-1 → us-west-2 | $0.02 |
| us-east-1 → eu-west-1 | $0.02 |
| us-east-1 → ap-northeast-1 | $0.09 |
| us-east-1 → 互联网 | $0.09 (前 100TB) |

**跨区推理调用的带宽成本**:

假设 GPT-4o 请求: input 2K tokens (≈8KB), output 500 tokens (≈2KB)
- 单请求总流量 ≈ 10KB
- 100 万次请求 ≈ 10GB
- 跨区成本 (us → ap): 10GB × $0.09 = $0.9

看似不多, 但**KV Cache 跨区同步**才是大头:

假设 PD 分离, KV Cache = 32K context × 7B 模型 ≈ 1GB / 请求
- 1 次跨区 KV 同步 = 1GB × $0.09 = $0.09
- 100 万次 PD 分离请求 = $90,000 仅带宽!

**优化策略**:
1. **同区域内 PD 分离**: Prefill 与 Decode 同 AZ, KV 走 NVLink/RDMA
2. **跨区只传结果, 不传 KV**: 用户请求路由到就近区域, 全程本地
3. **KV 压缩**: MLA (Multi-head Latent Attention) 4x 压缩
4. **KV 量化**: FP8 2x 压缩

### 6.3 副本存储成本

多地域部署意味着每个区域都有模型副本:

| 模型 | 单副本大小 | 3 区域副本 | 月存储成本 (S3 $0.023/GB) |
|------|-----------|-----------|--------------------------|
| Llama-7B FP16 | 14GB | 42GB | $0.97/月 |
| Llama-70B FP16 | 140GB | 420GB | $9.66/月 |
| Llama-405B FP16 | 810GB | 2.43TB | $55.89/月 |
| GPT-3 175B FP16 | 350GB | 1.05TB | $24.15/月 |

**优化**: 模型权重存储用 S3 Standard, 计算节点本地 NVMe 缓存。副本本身不贵, 贵的是每个区域都要 GPU 集群。

### 6.4 跨区同步成本

数据库跨区同步 (如 DynamoDB Global Table):

| 数据类型 | 跨区同步成本 |
|---------|-------------|
| 用户会话 | $0.02/GB (写) × 副本数 |
| 计费记录 | $0.02/GB (写) × 副本数 |
| KV Cache (不推荐跨区) | 太贵, 应本地化 |

**优化原则**:
- 用户请求**就近处理**, 不跨区
- **会话粘性** (session stickiness): 同一用户路由到同区域
- 跨区只同步**元数据** (用户配置、计费), 不同步推理数据

### 7.3 实现: 模型路由 + 自动升降级

```python
import time
from collections import OrderedDict
from dataclasses import dataclass
from typing import Optional

@dataclass
class ModelEntry:
    name: str
    size_gb: float
    last_access: float
    access_count: int
    location: str       # "gpu" / "cpu" / "ssd" / "s3"
    loaded: bool = False

class ModelTieredCache:
    """模型冷热分层管理"""
    def __init__(
        self,
        gpu_capacity_gb: float,
        cpu_capacity_gb: float,
        ssd_capacity_gb: float,
        gpu_models_limit: int = 5,
    ):
        self.tiers = {
            "gpu": {"capacity": gpu_capacity_gb, "used": 0, "models": OrderedDict()},
            "cpu": {"capacity": cpu_capacity_gb, "used": 0, "models": OrderedDict()},
            "ssd": {"capacity": ssd_capacity_gb, "used": 0, "models": OrderedDict()},
            "s3": {"capacity": float("inf"), "used": 0, "models": {}},
        }
        self.gpu_models_limit = gpu_models_limit

    def access(self, model_name: str) -> str:
        """访问模型, 返回所在层级"""
        for tier_name, tier in self.tiers.items():
            if model_name in tier["models"]:
                model = tier["models"][model_name]
                model.last_access = time.time()
                model.access_count += 1
                # 移到末尾 (LRU)
                if tier_name != "s3":
                    tier["models"].move_to_end(model_name)
                # 检查是否需要升级
                self._maybe_promote(model_name, tier_name)
                return tier_name
        # 模型不在任何层, 从 S3 加载
        return self._load_from_s3(model_name)

    def _maybe_promote(self, model_name: str, current_tier: str):
        """根据访问频率升级模型"""
        model = self.tiers[current_tier]["models"][model_name]
        if current_tier == "gpu":
            return
        # 升级条件: 1 分钟内访问 5 次以上
        recent_accesses = model.access_count
        if recent_accesses > 5 and (time.time() - model.last_access) < 60:
            target = "gpu" if current_tier in ("cpu", "ssd") else "cpu"
            if current_tier == "cpu":
                target = "gpu"
            elif current_tier == "ssd" and recent_accesses > 10:
                target = "gpu"
            self._move_model(model_name, current_tier, target)

    def _move_model(self, model_name: str, from_tier: str, to_tier: str):
        """移动模型到新层级"""
        if from_tier == to_tier:
            return
        from_t = self.tiers[from_tier]
        to_t = self.tiers[to_tier]
        model = from_t["models"][model_name]
        # 检查目标容量
        while to_t["used"] + model.size_gb > to_t["capacity"] and to_t["models"]:
            # LRU 淘汰
            evicted_name, evicted = to_t["models"].popitem(last=False)
            to_t["used"] -= evicted.size_gb
            # 降级
            lower_tier = "ssd" if to_tier == "gpu" else "s3"
            if lower_tier == "ssd" and self.tiers[lower_tier]["used"] + evicted.size_gb > self.tiers[lower_tier]["capacity"]:
                lower_tier = "s3"
            self.tiers[lower_tier]["models"][evicted_name] = evicted
            self.tiers[lower_tier]["used"] += evicted.size_gb
            evicted.location = lower_tier
            print(f"  [降级] {evicted_name}: {to_tier} → {lower_tier}")
        # 移动
        from_t["models"].pop(model_name)
        from_t["used"] -= model.size_gb
        to_t["models"][model_name] = model
        to_t["used"] += model.size_gb
        model.location = to_tier
        print(f"  [升级] {model_name}: {from_tier} → {to_tier}")

    def _load_from_s3(self, model_name: str) -> str:
        """从 S3 加载模型 (默认到 SSD)"""
        # 模拟: 模型大小
        size_gb = 140.0  # Llama-70B
        model = ModelEntry(
            name=model_name,
            size_gb=size_gb,
            last_access=time.time(),
            access_count=1,
            location="ssd",
        )
        # 放到 SSD
        while self.tiers["ssd"]["used"] + size_gb > self.tiers["ssd"]["capacity"]:
            evicted_name, evicted = self.tiers["ssd"]["models"].popitem(last=False)
            self.tiers["ssd"]["used"] -= evicted.size_gb
            self.tiers["s3"]["models"][evicted_name] = evicted
            self.tiers["s3"]["used"] += evicted.size_gb
            evicted.location = "s3"
        self.tiers["ssd"]["models"][model_name] = model
        self.tiers["ssd"]["used"] += size_gb
        return "ssd"

# 使用示例

    gpu_capacity_gb=640,    # 8× H100 80GB
    cpu_capacity_gb=1000,   # 1TB DRAM
    ssd_capacity_gb=4000,   # 4TB NVMe
)
```

```python
# 启动 Spot 监控线程
import threading
def spot_loop():
    monitor = AWSSpotMonitor(handler)
    while True:
        monitor.check_interrupt()
        time.sleep(5)
threading.Thread(target=spot_loop, daemon=True).start()
```

## 十一、面试速答

### Q1: 如何把 GPU 利用率从 30% 提升到 70%?

**答**: 四板斧:
1. **Continuous Batching** (vLLM 默认开启): token 级动态 batch, +15-20%
2. **PD 分离**: Prefill/Decode 分集群, 各自优化, +10-15%
3. **LoRA 多租户**: 多 adapter 共享 base model, +10-15%
4. **Speculative Decoding**: 小模型预测, 大模型验证, +5-10%
综合可达 60-70% util。

### Q2: 预留、按需、Spot 怎么配比?

**答**: 看流量模式:
- **稳定流量**: 70% 预留 + 20% 按需 + 10% Spot
- **突发流量**: 40% 预留 + 50% 按需 + 10% Spot
- **批处理为主**: 20% 预留 + 10% 按需 + 70% Spot
核心原则: 预留覆盖基线, 按需处理突发, Spot 吃离线。

### Q3: 千万 QPS 推理平台年成本多少?

**答**: 大约 $50M-$100M。GPU 占 60-80%, 网络 5-10%, 存储 3-5%, 软件 3-5%, 人力 3-5%。单 token 成本约 $1-3/M, 取决于模型规模与优化程度。DeepSeek-V3 把单 token 成本压到 $0.27/M, 是 GPT-4o 的 1/14。

### Q4: 跨地域部署最大成本是什么?

**答**: **跨区带宽**, 尤其是KV Cache 同步。1GB KV 跨区传输 (us → ap) 就要 $0.09, 100 万次 PD 分离请求带宽成本 $90K。优化: 同区域内 PD 分离, KV 走 NVLink/RDMA; 跨区只传结果不传 KV, 用户请求就近处理。

### Q5: 冷热分层怎么设计?

**答**: 四级: Hot (GPU 显存, Top 5 模型) / Warm (CPU DRAM) / Cold (NVMe SSD) / Frozen (S3)。基于访问频率自动升降级 (LRU + 访问计数)。Hot 模型常驻, Cold 模型按需加载。加载时间: Hot 0s, Warm 1-5s, Cold 5-15s, Frozen 15-30s。

### Q6: Spot 中断怎么处理?

**答**: 三层防御:
1. **检测**: 监听 IMDS metadata (AWS 2 分钟预告) 或 K8s termination signal
2. **Drain**: 收到信号后从 LB 摘除, 等待 inflight 请求完成 (最多 120s)
3. **恢复**: KV Cache checkpoint 保存, 控制平面重新调度, 实例恢复后重新加载状态
**禁止**: Spot 用于实时 SLA 严格的场景。

### Q7: per-token 计费怎么实现?

**答**: 区分 input/output/cached-input 三档价格。请求结束时记录 token 数, 写入计费系统。关键: cache hit 检测 (prompt caching), 命中部分按 cached 价格计费 (OpenAI 0.5x, Anthropic 0.1x)。还要处理: 超时重试不重复计费、流式断连按已生成 token 计费、批量请求折扣。

### Q8: 如何评估一个推理平台的成本效率?

**答**: 核心指标: **$ / 1M output tokens**。辅助指标:
- GPU 平均利用率 (目标 60%+)
- 单卡吞吐 (tokens/s)
- 单 token 成本分解 (GPU / 网络 / 存储)
- 冷启动占比 (低 = 好)
- Spot 占比 (高 = 成本低, 但需评估 SLA 影响)
对比 OpenAI / DeepSeek 价格, 衡量自身竞争力。

### Q9: 为什么 LLM 推理 GPU 利用率比训练低这么多?

**答**: 训练是 **计算密集 + 大 batch + 持续运行**, GPU 始终满载。推理是 **内存密集 (Decode) + 小 batch + 请求驱动**, Decode 阶段 GPU 等内存, 自然低 util。PD 分离就是把这个矛盾拆开: Prefill 集群计算密集 (高 util), Decode 集群内存密集 (低 util 但批处理大)。

### Q10: 模型量化对成本的影响?

**答**: 量化直接降低显存占用, 间接提升吞吐:
- FP16 → FP8: 显存 -50%, 吞吐 +30-50%
- FP16 → INT8: 显存 -50%, 吞吐 +50-100% (需硬件支持)
- FP16 → INT4: 显存 -75%, 吞吐 +100%+, 但精度损失明显
关键: 必须评估 perplexity 与下游任务精度, 不能盲目量化。H100 原生支持 FP8, 是当前最优选择。

**题目**: 一张 H100 ($3/hour) 跑 Llama-7B, 平均吞吐 200 QPS, 平均请求 input 500 tokens + output 200 tokens。求单 token 成本。

### 题 2 (中级): 容量规划

**题目**: 设计一个 LLM 推理平台, 日均 1 亿请求, 平均 input 1000 tokens + output 300 tokens, P99 TTFT < 800ms。模型 Llama-70B, 单卡 (H100) 吞吐 50 QPS。求 GPU 数量与月成本。

**答案**:

- 假设高峰 3x = 3471 QPS
- GPU 数 = 3471 / 50 = 70 张 (高峰)
- 基线 GPU = 1157 / 50 = 24 张
- **配比** (balanced): 24 预留 + 46 按需上限
- 月成本:
  - 预留: 24 × $39.33 × 720 = $679K
  - 按需 (按实际高峰时段算, 假设 8h/天高峰): 46 × $98.32 × 240 = $1.08M
  - 合计: ~$1.76M / 月

**追问**: 如何降到 $1M 以下?

**答**:
1. **PD 分离**: 吞吐 +30%, GPU 数量 -23% → 54 张高峰
2. **Spot 吃低峰**: 夜间 Spot 处理 30% 流量
3. **prompt caching**: input 命中 50%, 实际 input 减半
4. 综合可降到 ~$0.8M / 月

### 题 3 (中级): 跨地域成本优化

**题目**: 全球 3 区域部署 LLM 推理, 模型 Llama-70B (140GB), 每区域 8 张 H100。用户请求均匀分布, 平均请求 2KB。求月成本 (网络 + 存储)。

**答案**:
- 模型存储: 3 区域 × 140GB = 420GB, S3 = $9.66/月 (可忽略)
- 跨区流量: 假设 1000 万请求/天, 2KB/请求
  - 如果**请求就近处理**: 跨区流量 ≈ 0
  - 如果**跨区路由** (如美区用户打到欧区): 1000万 × 2KB × 30天 × $0.09/GB = 600GB × $0.09 = $54/月 (可忽略)
- **关键**: KV Cache 同步才是大头
  - 假设 10% 请求跨区 PD 分离, KV Cache 1GB/请求
  - 跨区 KV: 100万 × 1GB × $0.09 = $90K / 月
- **结论**: 必须同区域 PD 分离, 跨区只传结果

### 题 5 (高级): Spot 中断恢复设计

**题目**: 实时 LLM 推理服务使用 30% Spot 实例, 如何保证 SLA (P99 TTFT < 1s)?

**答案** (要点):

**核心矛盾**: Spot 可被中断 (AWS 2 分钟预告), 但实时 SLA 严格。

**策略**:
1. **Spot 仅用于 Decode**: Decode 阶段 KV Cache 已建立, 中断后可恢复; Prefill 严格用预留
2. **冗余部署**: Spot 实例 + 5% 预留冗余, Spot 中断时预留接管
3. **快速检测**: 监听 IMDS metadata, 2 分钟前预警
4. **Drain 机制**: 收到预警 → 从 LB 摘除 → 等待 inflight 完成 (≤90s) → KV checkpoint 保存 → 退出
5. **快速恢复**: Karpenter 立即申请新 Spot, 加载 KV checkpoint, 加入 LB
6. **请求级重试**: 客户端断连后, 路由到其他实例, 用 KV checkpoint 续传
7. **熔断**: Spot 中断频率 > 阈值时, 自动切换到按需

**SLA 保障**:
- Spot 中断概率 < 5%/小时
- 30% Spot × 5% 中断 = 1.5% 实例任意时刻不可用
- 5% 预留冗余覆盖
- P99 TTFT 影响可控

### 题 6 (系统设计): Token 计费系统

**题目**: 设计 OpenAI 风格的 per-token 计费系统, 日均 10 亿请求, 要求: 计费准确、低延迟、可追溯。

**答案** (要点):

**架构**:
```
请求 ──→ API Gateway ──→ 推理引擎 ──→ Token 计数 ──→ 计费事件
              │                              │
              ▼                              ▼
          用量配额检查                   Kafka (计费事件流)
              │                              │
              ▼                              ▼
          Redis (实时余额)            Flink (流式聚合)
                                             │
                                             ▼
                                       ClickHouse (明细)
                                             │
                                             ▼
                                       账单生成 (月度)
```

**关键设计**:
1. **Token 计数**: 推理引擎返回 input/output token 数 (含 cached input)
2. **实时配额**: Redis 存用户余额, API Gateway 前置检查
3. **事件流**: 计费事件写 Kafka, 解耦推理与计费
4. **流式聚合**: Flink 实时聚合用户级用量, 写 ClickHouse
5. **明细查询**: ClickHouse 存全量明细, 支持用户查询
6. **对账**: 每日对账, 推理日志 vs 计费事件
7. **幂等**: 请求 ID 去重, 重试不重复计费
8. **降级**: 计费系统故障时, 推理继续, 事件堆积在 Kafka, 恢复后补处理

**性能**:
- 计费事件延迟 < 100ms (Kafka 写入)
- 用户查询 < 1s (ClickHouse)
- 日处理 10 亿事件, 单 Flink 集群足够

### 题 7 (开放题): 如何评估是否该自建 GPU 集群 vs 用云?

**答案** (要点):

**自建考量**:
- **优势**: 长期成本低 (3 年摊销 vs 云按需), 数据完全可控, 可定制硬件
- **劣势**: 巨额前期投入 ($100M+), 弹性差, 运维重, GPU 折旧快 (3-5 年淘汰)

**云上考量**:
- **优势**: 弹性, 无前期投入, 全球部署, 运维轻
- **劣势**: 长期成本高, 数据锁定, 厂商绑定

**决策框架**:
1. **利用率**: 长期 > 70% → 自建划算; < 50% → 云上
2. **规模**: 1000+ GPU → 自建议价能力强; < 100 → 云上
3. **弹性需求**: 流量波动大 → 云上; 稳定 → 自建
4. **数据敏感**: 极敏感 → 自建; 一般 → 云上 + 加密
5. **团队**: 有运维能力 → 自建; 无 → 云上

**典型选择**: 大厂混合云
- 自建 60% 基线 (3 年摊销, 单卡 $0.5/h)
- 云预留 20% (跨区域容灾)
- 云 Spot 20% (弹性突发)

## 十三、故障复盘: 容量规划相关

### 13.1 案例: 容量规划不足导致高峰雪崩

**背景**: 某 LLM 推理服务, 日均 500 万请求, 高峰 5 万 QPS。

**现象**:
- 营销活动带来 10x 流量, QPS 飙到 50 万
- GPU 集群饱和, 请求堆积
- KV Cache OOM, 全雪崩
- 持续 4 小时不可用

**根因**:
1. 容量规划只考虑 3x 高峰, 实际 10x
2. 无自动扩缩容 (依赖人工)
3. 无限流, 请求无脑接收
4. KV Cache OOM 后无降级, 直接雪崩

**修复**:
1. **流量预测**: 接入营销日历, 提前扩容
2. **自动扩缩**: KEDA 基于 QPS + 队列长度
3. **多层限流**: API Gateway / 服务层 / GPU 层
4. **降级策略**: 高峰时关闭长请求 (>8K context), 只服务短请求
5. **预算保护**: 单用户 QPS 限制, 防滥用

**经验**: 容量规划必须考虑**极端场景** (10x), 自动化扩缩容 + 多层限流 + 降级策略是三道防线。

### 13.2 案例: Spot 比例过高导致 SLA 翻车

**背景**: 为降成本, Spot 比例从 10% 提到 50%。

**现象**:
- 某区域 Spot 价格上涨, 大量实例被中断
- 50% Spot 中断 → 50% 流量无服务
- P99 TTFT 从 800ms 飙到 8s
- 持续 30 分钟

**根因**:
1. Spot 比例过高 (50%), 中断时无足够冗余
2. 同区域 Spot 同时被中断 (价格联动)
3. Drain 超时不足, inflight 请求丢失
4. 无快速切换到按需的机制

**修复**:
1. **Spot 比例上限 30%**: 实时推理不超过此比例
2. **多区域 Spot 分散**: 不同区域 Spot 价格独立
3. **快速切换**: Spot 中断率 > 阈值, 自动切按需
4. **Drain 优化**: 90s drain + KV checkpoint 保存

**经验**: Spot 是**成本优化**, 不是**容量保障**。SLA 严格的实时服务, Spot 比例不超过 30%。

### 13.3 案例: 跨区带宽账单失控

**背景**: PD 分离架构, Prefill 在 us-east, Decode 在 ap-northeast。

**现象**:
- 月账单 $200K, 其中跨区带宽 $80K (40%)
- KV Cache 跨区传输占绝大部分

**根因**:
1. PD 跨区部署, KV Cache 1GB/请求跨区
2. 100 万请求/天 × 1GB × $0.09/GB = $9K/天
3. 月度 $270K (账单显示 $80K, 因为部分流量在同区)

**修复**:
1. **同区 PD**: Prefill 与 Decode 同 AZ, KV 走 NVLink
2. **KV 压缩**: MLA 4x 压缩
3. **KV 量化**: FP8 2x 压缩
4. **请求就近**: 用户路由到就近区域, 全程本地

**经验**: 跨区只传结果 (KB 级), 不传 KV (GB 级)。跨区带宽成本可能超过 GPU 成本。

### 13.4 案例: 冷模型加载耗尽预算

**背景**: 平台支持 1000+ LoRA adapter, 全部常驻 GPU。

**现象**:
- GPU 显存不够, 大量 H100 用于存 LoRA
- 实际 90% LoRA 一周访问 < 1 次
- GPU 利用率 30%, 但成本高

**根因**:
1. 无冷热分层, 所有 LoRA 平等对待
2. LoRA 加载到 GPU 后不卸载
3. 无访问频率统计

**修复**:
1. **冷热分层**: Hot (GPU) / Warm (CPU) / Cold (SSD)
2. **LRU 淘汰**: GPU 满时淘汰最久未用的 LoRA
3. **访问统计**: 记录每个 LoRA 的访问频率
4. **自动升降级**: 频率高的升级, 低的降级

**结果**: GPU 数量减少 60%, 单 LoRA 服务延迟 P99 < 5s (Warm 加载)。

**经验**: 不是所有模型都该常驻 GPU。冷热分层是成本与延迟的平衡。
