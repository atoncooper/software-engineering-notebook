## 三、OpenAI GPT 部署（推测架构）

### 3.1 背景

OpenAI 是 LLM 推理工程的标杆, GPT-4 推理架构虽未公开, 但从博客/招聘信息/学术论文可推测。

### 3.2 推测架构

```
┌─────────────────────────────────────────────┐
│            Global Frontend                  │
│  - GeoDNS (全球接入)                         │
│  - Cloudflare CDN                           │
└─────────────────┬───────────────────────────┘
                  │
                  ▼
┌─────────────────────────────────────────────┐
│         API Gateway                         │
│  - 鉴权 (API Key)                            │
│  - 限流 (per user)                           │
│  - 路由 (按模型/地域)                         │
└─────────────────┬───────────────────────────┘
                  │
        ┌─────────┴─────────┐
        ▼                   ▼
┌──────────────┐    ┌──────────────┐
│  Prefill     │    │  Decode      │
│  Cluster     │    │  Cluster     │
│  (CPU/H100)  │    │  (H100)      │
│              │    │              │
│  - 大 batch  │    │  - 小 batch  │
│  - 算力密集  │    │  - 内存密集  │
│  - PD 分离   │    │              │
└──────┬───────┘    └───────▲──────┘
       │                    │
       └─── KV Cache ───────┘
           (RDMA/InfiniBand)
```

### 3.3 关键技术推测

```
1. PD 分离 (Prefill-Decode Disaggregation)
   - Prefill 与 Decode 解耦到不同集群
   - Prefill: 大 batch, 算力密集, 用满 GPU
   - Decode: 小 batch, 内存密集, 高吞吐
   - KV Cache 跨节点传输 (RDMA, InfiniBand)

2. KV Cache 复用
   - 系统 prompt 的 KV Cache 预计算并缓存
   - 多用户共享相同 system prompt, 复用 KV
   - 节省 prefill 算力 50%+

3. 专家并行 (MoE)
   - GPT-4 推测为 MoE 架构 (8 专家, 2 激活)
   - EP (Expert Parallel) 部署
   - All-to-All 通信

4. 量化
   - FP8 (H100 原生支持)
   - INT8 (部分模型)
   - 推测: GPT-4o 用 FP8, 比 FP16 快 2x

5. 多地域部署
   - 美西/美东/欧洲/亚洲
   - 用户就近接入
   - 模型权重多地域副本
   - 会话保持 (KV Cache 不跨地域)

6. 流式输出
   - SSE (Server-Sent Events)
   - 首 token 优先 (TTFT 优化)
   - 增量解码
```

### 3.4 性能基准（推测）

| 指标 | GPT-4 Turbo | GPT-4o |
|------|-------------|--------|
| TTFT P50 | 500ms | 300ms |
| TTFT P99 | 1.5s | 800ms |
| 吞吐 (tokens/s) | 50 | 100 |
| 上下文长度 | 128K | 128K |
| GPU 利用率 | ~70% | ~75% |

### 3.5 可借鉴经验

1. **PD 分离**: 大规模集群的关键架构
2. **KV Cache 复用**: 系统 prompt 复用节省算力
3. **多地域**: 全球低延迟
4. **量化**: FP8 在 H100 上是杀手锏
5. **流式**: 用户感知优于吞吐

## 四、Anthropic Claude 部署

### 4.1 背景

Anthropic Claude 以长上下文 (200K) 和安全 (Constitutional AI) 著称, 推理架构有独特设计。

### 4.2 架构推测

```
┌─────────────────────────────────────────────┐
│            Claude.ai / API                  │
└─────────────────┬───────────────────────────┘
                  │
                  ▼
┌─────────────────────────────────────────────┐
│         Safety Layer                        │
│  - Input filtering                          │
│  - Output filtering                         │
│  - Constitutional AI                        │
└─────────────────┬───────────────────────────┘
                  │
                  ▼
┌─────────────────────────────────────────────┐
│         Long Context Engine                 │
│  - 200K context                             │
│  - KV Cache 压缩                            │
│  - Sliding window attention                 │
│  - Ring attention (推测)                    │
└─────────────────┬───────────────────────────┘
                  │
                  ▼
┌─────────────────────────────────────────────┐
│         Inference Cluster                   │
│  - 多卡 TP (Tensor Parallel)                │
│  - 长 prompt 优化                            │
│  - 安全沙箱 (代码执行)                       │
└─────────────────────────────────────────────┘
```

### 4.3 关键技术

```
1. 长上下文优化
   - 200K token context
   - KV Cache 内存: 200K × 8KB = 1.6GB (单请求)
   - 优化:
     - Sliding window attention (注意力局部化)
     - Ring attention (跨卡分布式 attention)
     - KV Cache 量化 (FP8/INT4)
     - Flash Attention 2/3

2. 安全沙箱
   - Claude 能执行代码
   - 沙箱: Firecracker (推测)
   - 网络隔离: 仅必要 endpoint
   - 资源限制: CPU/内存/时间

3. Constitutional AI
   - 输入安全过滤
   - 输出审核
   - 拒答机制
   - 红队评估

4. 流式输出
   - SSE
   - 长流式 (200K 输出)
   - 增量 token
```

### 4.4 性能基准

| 指标 | Claude 3.5 Sonnet | Claude 3 Opus |
|------|-------------------|---------------|
| TTFT P50 | 600ms | 1.2s |
| 吞吐 (tokens/s) | 80 | 40 |
| 上下文 | 200K | 200K |
| 拒答率 | ~3% | ~5% |

### 4.5 可借鉴经验

1. **长上下文**: KV Cache 管理是关键
2. **安全**: 沙箱 + 多层过滤
3. **流式**: 长输出不能阻塞
4. **质量**: 拒答率与质量平衡

## 五、DeepSeek-V3 部署（开源标杆）

### 5.1 背景

DeepSeek-V3 (2024) 是 671B MoE 模型, 256 专家, 37B 激活, 部署架构公开在技术报告。

### 5.2 架构

```
┌─────────────────────────────────────────────┐
│              DeepSeek-V3 (671B)             │
│  - 256 experts (8 routed + 1 shared)        │
│  - 37B active params per token              │
│  - MLA (Multi-head Latent Attention)        │
│  - Context: 128K                            │
└─────────────────┬───────────────────────────┘
                  │
                  ▼
┌─────────────────────────────────────────────┐
│         PD 分离架构                          │
│  ┌──────────────┐    ┌──────────────┐       │
│  │ Prefill      │    │ Decode       │       │
│  │ (32 Experts/ │    │ (8 Experts/  │       │
│  │  GPU)        │    │  GPU)        │       │
│  │              │    │              │       │
│  │ 大 batch     │    │ 小 batch     │       │
│  │ EP=32        │    │ EP=8         │       │
│  └──────┬───────┘    └───────▲──────┘       │
│         │                    │               │
│         └─── KV (MLA) ───────┘               │
│             RDMA                            │
└─────────────────────────────────────────────┘

关键:
  - EP (Expert Parallel): 32/8
  - MLA: KV Cache 压缩到 1/4
  - MTP (Multi-Token Prediction): 加速
  - FP8 量化
```

### 5.3 关键技术

```
1. MLA (Multi-head Latent Attention)
   - KV Cache 压缩
   - 4 倍压缩 (相比 MHA)
   - 200K context 仍可服务

2. PD 分离
   - Prefill: 32 GPU, 大 batch
   - Decode: 8 GPU, 高吞吐
   - KV Cache 跨节点传输

3. 专家负载均衡
   - 动态路由
   - 防 expert 退化 (有的过载, 有的闲置)
   - Expert Affinity (请求亲和到同一 GPU)

4. FP8 量化
   - H100 原生支持
   - 比 BF16 快 2x
   - 精度损失 < 1%

5. MTP (Multi-Token Prediction)
   - 一次预测多 token
   - 推理加速 1.5-2x
```

### 5.4 性能基准

| 指标 | 数值 |
|------|------|
| 总参数 | 671B |
| 激活参数 | 37B |
| 上下文 | 128K |
| FP8 显存 | ~350GB |
| 推理速度 (tokens/s) | 60+ (8×H100) |
| 成本 ($/M tokens) | $0.27 (input), $1.10 (output) |

### 5.5 可借鉴经验

1. **MoE**: 激活参数远小于总参数, 推理便宜
2. **MLA**: KV Cache 压缩是长上下文关键
3. **PD 分离**: MoE 部署的标准操作
4. **FP8**: H100 时代的标配
5. **开源**: DeepSeek 把工程细节都公开了, 难得

│  - 全球接入 (CN/SG/US)                       │

└─────────────────┬───────────────────────────┘
                  │
                  ▼
┌─────────────────────────────────────────────┐
│       VeRLm 推理平台                        │
│  - 自研调度器                                │
│  - TP + PP 混合并行                          │
│  - 万卡集群                                  │
└─────────────────┬───────────────────────────┘
                  │
                  ▼
┌─────────────────────────────────────────────┐
│         推理集群                             │
│  ┌──────────────────────────────────────┐   │
│  │  TP=8 (单机 8 卡) + PP=4 (4 节点)    │   │
│  │  共 32 H100 跑豆包 175B              │   │

## 九、技术趋势

### 9.1 PD 分离成为标配

```
传统 (单集群):
  Prefill + Decode 混合, GPU 利用率 30%

PD 分离:
  Prefill 集群: 算力密集, 大 batch, 利用率 70%+
  Decode 集群: 内存密集, 高吞吐
  KV Cache RDMA 传输
  整体利用率 60-80%
```

### 9.2 MoE 是大模型未来

```
Dense vs MoE:
  Dense 70B: 70B 激活, 推理慢
  MoE 671B (37B 激活): 推理与 70B 接近, 效果更好

趋势:
  - 大模型普遍 MoE
  - 专家数 8→64→256
  - 激活参数比例 1/4 → 1/8
  - 部署: EP (Expert Parallel)
```

### 9.3 KV Cache 优化

```
KV Cache 内存 (70B 模型, 32K context):
  MHA: 2.62MB × 32K = 84GB
  MLA (DeepSeek): 84GB / 4 = 21GB
  GQA (Llama): 84GB / 8 = 10GB

优化:
  - MLA: 4 倍压缩
  - KV 量化: FP8/INT4
  - PagedAttention: 显存复用
  - RadixTree: prefix cache
```

### 9.4 多模态融合

```
趋势:
  - VLM (Vision-Language Model)
  - Audio 模态
  - Video 模态
  - 任意模态输入输出

部署挑战:
  - 跨模态 batch
  - 变长输入
  - 视觉编码器优化
```

### 9.5 端云协同普及

```
趋势:
  - 端侧小模型 (1-7B)
  - 云端大模型 (70B+)
  - 智能路由 (复杂度/隐私)

案例:
  - Apple Intelligence (端 70% + 云 30%)
  - Google Gemini Nano
  - 字节豆包 Lite
  - 微软 Copilot+PC
```

## 十、面试速答

**Q1: OpenAI 推理架构推测?**

A: 1) PD 分离 (Prefill/Decode 解耦到不同集群); 2) KV Cache 复用 (system prompt 共享); 3) FP8 量化 (H100 原生); 4) 多地域部署 (美西/美东/欧洲); 5) 流式 SSE; 6) GPT-4 推测为 MoE 架构, EP 部署。

**Q2: DeepSeek-V3 部署的关键?**

A: 1) MoE 671B 总参/37B 激活, 推理便宜; 2) MLA (Multi-head Latent Attention) KV Cache 压缩 4 倍; 3) PD 分离, EP=32 (prefill) / EP=8 (decode); 4) FP8 量化; 5) MTP (Multi-Token Prediction) 加速 1.5-2x。开源工程细节是标杆。

**Q3: 阿里 PAI-EAS 的特点?**

A: 1) 平台化 (PAI-EAS 推理平台); 2) PD 分离 (DistServe 思路); 3) 多模型路由 (Qwen-7B/72B/VL 按复杂度路由); 4) Serverless GPU (KEDA 弹性); 5) 多地域 (国内+海外); 6) 与阿里云生态集成 (OSS/SLB/RDS)。

**Q4: 字节豆包部署规模?**

A: 万卡集群, 豆包 175B 部署: TP=8 (单机 8 卡) + PP=4 (4 节点), 共 32 卡/实例。多租户 (火山引擎外部 + 抖音/今日头条内部), 端云协同 (抖音 APP 端侧小模型 + 云端豆包大模型)。

**Q5: 大厂 LLM 部署的共同点?**

A: 1) PD 分离 (利用率 30% → 70%+); 2) FP8 量化 (H100 时代标配); 3) 多地域 (全球低延迟); 4) 流式 SSE (用户感知); 5) KV Cache 优化 (PagedAttention/MLA); 6) 弹性 (Serverless GPU); 7) 多模型路由 (按复杂度); 8) 安全沙箱 (代码执行)。

### 题 1（中级）：从大厂案例看 LLM 部署演进

**答题要点**：

   - 主要优化: KV Cache (PagedAttention), Continuous Batching

2. **第二阶段 (2023-2024)**:
   - PD 分离 (DistServe/Splitwise)
   - FP8 量化 (H100)
   - GPU 利用率 50-70%

3. **第三阶段 (2024+)**:
   - MoE 普及 (DeepSeek/Mixtral)
   - MLA (KV 压缩)
   - 多地域多活
   - GPU 利用率 70%+

4. **未来趋势**:
   - 端云协同 (Apple Intelligence)
   - 多模态 (VLM/Audio/Video)
   - Agent 系统 (长任务)
   - 推理 ASIC (Inferentia/TPU)

5. **可借鉴**:
   - PD 分离: 利用率提升关键
   - FP8: H100 必用
   - KV 优化: 长上下文基础
   - 多地域: 全球服务

   - 调度器: K8s + 自研 GPU 调度
   - 路由: 按模型/复杂度/地域
   - 弹性: KEDA + Serverless GPU

   - PagedAttention + Continuous Batching
   - FP8/INT8 量化
   - KV Cache 优化 (prefix cache, MLA)
   - 多地域部署
   - 流式 SSE

4. **多租户**:
   - 命名空间隔离
   - 资源池化 + 优先级
   - 配额管理
   - 计费 (按 token)

5. **可靠性**:
   - 多地域多活
   - 故障切换自动
   - 混沌工程验证
   - 红黑演练

6. **成本**:
   - Spot 实例 (备地域)
   - PD 分离 (利用率 70%+)
   - 模型路由 (简单请求小模型)
   - 端云协同 (端侧分流)

   - MoE 支持
