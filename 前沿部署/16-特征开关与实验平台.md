## 二、问题定义与边界

### 2.1 解决什么

- **解耦发布与上线**：代码先部署, 功能后开启
- **灰度路由**：按用户/地域/时间开关功能
- **紧急降级**：出问题不回滚代码, 关开关
- **A/B 实验**：量化版本优劣, 数据驱动决策
- **权限控制**：Beta 功能白名单

### 2.2 不解决什么

- 不覆盖渐进式发布（15 章, 部署层面）
- 不覆盖监控告警（infra开发 模块）
- 不深入统计理论（机器学习 模块）

## 三、直觉解释

### 3.1 为什么需要特征开关

```
传统发布:
  代码合并 → 部署 → 上线
  ↓
  出问题: 必须回滚代码 (5-10 min)
  ↓
  影响: 所有用户

特征开关:
  代码合并 → 部署 (开关关) → 开开关 (灰度) → 全量
  ↓                ↓                ↓
  出问题: 关开关 (秒级)  灰度验证    全量验证
  ↓
  影响: 仅灰度用户

价值:
  - 降低风险: 紧急降级秒级
  - 加速迭代: 代码先合并, 功能后开启
  - 灵活控制: 按用户/地域/时间
  - 数据驱动: A/B 实验量化
```

### 3.2 特征开关类型

| 类型 | 生命周期 | 变更频率 | 典型场景 |
|------|---------|---------|---------|
| Release | 天-周 | 低 | 控制发布节奏 |
| Ops | 分钟-小时 | 高 | 紧急降级 (熔断) |
| Config | 持久 | 中 | 业务参数 (限额/阈值) |
| Permission | 持久 | 低 | 白名单/Beta |

### 3.3 开关粒度

```
全局开关:
  - 所有用户统一开关
  - 简单粗暴, 适合紧急降级

百分比开关:
  - 5% / 25% / 50% / 100%
  - 一致性哈希保证同一用户始终同一组

用户分桶:
  - 按用户 ID 哈希分桶
  - 同一用户始终进同一组 (避免体验跳变)

属性规则:
  - 按地域/语言/设备/会员等级
  - 例如: 仅北京+VIP 用户

白名单:
  - 内部用户优先
  - 指定 user_id 列表
```

## 五、A/B 实验统计学

### 5.1 实验设计基础

```
假设检验:
  H0 (原假设): 新版本无效果 (差异=0)
  H1 (备择假设): 新版本有效果 (差异≠0)

两类错误:
  Type I (α): 假阳性, H0 真但拒绝 (默认 α=5%)
  Type II (β): 假阴性, H1 真但接受 (默认 β=20%, power=80%)

样本量计算:
  n = (Z_{α/2} + Z_β)^2 × 2σ^2 / Δ^2
  
  Z_{α/2}=1.96 (95% 置信)
  Z_β=0.84 (80% power)
  σ: 指标标准差
  Δ: 最小可检测差异

例: 转化率从 5% 提升到 5.5% (Δ=0.5%)
  n = (1.96 + 0.84)^2 × 2 × 0.218^2 / 0.005^2
  n ≈ 30000 per group
```

### 5.2 显著性检验

```python
import numpy as np
from scipy import stats

def ab_test(control: list, treatment: list, alpha=0.05):
    """A/B 实验显著性检验."""
    # 均值
    c_mean, t_mean = np.mean(control), np.mean(treatment)
    # 标准差
    c_std, t_std = np.std(control, ddof=1), np.std(treatment, ddof=1)
    # 样本量
    n_c, n_t = len(control), len(treatment)

    # t 检验 (Welch's t-test, 不假设等方差)
    t_stat, p_value = stats.ttest_ind(control, treatment, equal_var=False)

    # 置信区间
    diff = t_mean - c_mean
    se = np.sqrt(c_std**2/n_c + t_std**2/n_t)
    ci_low = diff - 1.96 * se
    ci_high = diff + 1.96 * se

    # 提升幅度
    lift = (t_mean - c_mean) / c_mean * 100

    # 结论
    significant = p_value < alpha

    return {
        'control_mean': c_mean,
        'treatment_mean': t_mean,
        'lift_percent': lift,
        'p_value': p_value,
        'ci_95': (ci_low, ci_high),
        'significant': significant,
    }

# 示例: LLM 推理服务 A/B
# Control: 旧版本, 1000 请求, 平均 TTFT 850ms, std 120ms
# Treatment: 新版本, 1000 请求, 平均 TTFT 780ms, std 110ms
control = np.random.normal(850, 120, 1000)
treatment = np.random.normal(780, 110, 1000)
result = ab_test(control, treatment)
# lift: -8.2%, p < 0.001, significant: True
# 结论: 新版本 TTFT 显著下降 8.2%
```

### 5.3 分层实验与互斥分组

```
问题: 多个实验并行, 互相干扰
  实验 A: 新模型 vs 旧模型 (影响延迟)
  实验 B: 新 UI vs 旧 UI (影响点击率)
  ↓
  同一用户同时在 A.treatment 和 B.treatment, 无法独立归因

方案 1: 互斥分组 (Mutex)
  用户先分到实验 A 或实验 B (互斥)
  再在实验内分 treatment/control
  缺点: 实验数受限, 流量不够

方案 2: 分层实验 (Layered)
  Layer 1 (UI 层): 实验 A
  Layer 2 (模型层): 实验 B
  同一用户在每层独立分桶
  Layer 1 的分桶不影响 Layer 2 (正交)
  优点: 实验数不受限, 流量复用

实现: 正交分层 (Hash(user_id, layer_id) % 100)
```

### 5.4 正交分桶实现

```python
import hashlib

def bucket(user_id: str, layer: str, num_buckets: int = 1000) -> int:
    """正交分桶: 同一用户在不同 layer 独立分桶."""
    key = f"{layer}:{user_id}"
    h = hashlib.md5(key.encode()).hexdigest()
    return int(h, 16) % num_buckets

# Layer 1 (UI): 实验 A
# buckets 0-499: treatment, 500-999: control
# Layer 2 (Model): 实验 B
# buckets 0-199: treatment, 200-999: control

def assign(user_id: str):
    ui_bucket = bucket(user_id, "ui_layer")
    model_bucket = bucket(user_id, "model_layer")

    return {
        'ui_variant': 'treatment' if ui_bucket < 500 else 'control',
        'model_variant': 'treatment' if model_bucket < 200 else 'control',
    }
# 同一用户: ui_variant 与 model_variant 独立
# 互不干扰, 可独立归因
```

### 6.3 LLM 推理服务的特征开关实践

```python
# llm_service.py
from openfeature import api as openfeature

class LLMService:
    def __init__(self):
        self.flag_client = openfeature.get_client("llm-service")

    def generate(self, user_id: str, prompt: str, **kwargs):
        ctx = {
            'user_id': user_id,
            'user_tier': self._get_tier(user_id),
            'region': self._get_region(user_id),
        }

        # 1. 选择模型 (开关控制)
        model = self.flag_client.get_string_value(
            "llm_model",
            default="llama-3.1-70b",
            evaluation_context=ctx
        )

        # 2. 选择路由策略 (灰度新路由)
        use_new_router = self.flag_client.get_boolean_value(
            "new_router_enabled",
            default=False,
            evaluation_context=ctx
        )

        # 3. 限流配置 (动态调整)
        rate_limit = self.flag_client.get_integer_value(
            "rate_limit_per_minute",
            default=60,
            evaluation_context=ctx
        )

        # 4. 安全检查 (紧急降级开关)
        safety_check_enabled = self.flag_client.get_boolean_value(
            "safety_check_enabled",
            default=True,
            evaluation_context=ctx
        )

        if safety_check_enabled:
            self._safety_check(prompt)

        if not self._rate_limit(user_id, rate_limit):
            raise RateLimitError()

        if use_new_router:
            return self._new_route(model, prompt, **kwargs)
        else:
            return self._old_route(model, prompt, **kwargs)
```

## 七、底层原理

### 7.1 求值性能与缓存

```
问题: 每次请求都查开关, 网络往返 50ms, 不可接受

方案: 本地缓存 + 流式更新
  1. SDK 启动时拉取全部开关配置 (JSON)
  2. 本地内存缓存, 求值在本地 (< 1ms)
  3. SSE/WebSocket 流式接收变更
  4. 心跳保活 (30s)
  5. 网络中断时用本地缓存 (降级)

性能:
  - 求值延迟: < 1ms (本地)
  - 配置更新: < 1s (流式)
  - 网络中断: 仍可用 (本地缓存)

OpenFeature 标准:
  - InMemoryProvider: 本地缓存
  - StreamingProvider: 流式更新
```

### 7.2 一致性哈希分桶

```
目标: 同一用户始终进入同一组 (避免体验跳变)

方案: hash(user_id) % 100
  - 用户 u123: 始终分到桶 67
  - 桶 0-4: canary (5%)
  - 桶 5-99: stable

特性:
  - 一致性: 同一用户始终同组
  - 均匀性: 用户均匀分布
  - 可调: 改变桶范围即可改变比例

陷阱:
  - hash 算法选择: MD5/SHA1 (分布均匀), 不用 CRC32 (分布不均)
  - hash 输入: user_id 而非 IP (NAT 后多人共享)
  - 跨实验正交: hash(user_id + experiment_id) 保证独立
```

### 7.3 实验指标体系

```
指标层次:
  1. 护栏指标 (Guardrail)
     - 不能恶化的指标
     - 例: 错误率, P99 延迟, 留存
     - 任一恶化即终止实验

  2. 核心指标 (Primary)
     - 实验目标
     - 例: 转化率, 点击率, 人均收入
     - 决定实验结论

  3. 辅助指标 (Secondary)
     - 解释核心指标变化
     - 例: 各页面转化, 各用户群体

  4. 数据质量指标 (Data Quality)
     - 实验可信度
     - 例: 样本量, 分桶比例, SRM 检验

LLM 推理实验指标:
  - 护栏: TTFT P99, 错误率, 拒答率
  - 核心: 用户满意度 (点赞率), 留存
  - 辅助: 平均对话长度, 多轮率, 模型选择率
```

### 7.4 SRM 检验（样本比例失衡）

```
Sample Ratio Mismatch (SRM):
  实验设计: 50/50 分流
  实际观察: 49.5/50.5
  ↓
  说明分流失衡, 实验不可信

检测: 卡方检验
  expected = [total/2, total/2]
  observed = [n_control, n_treatment]
  chi2 = sum((obs - exp)^2 / exp)
  p_value = 1 - chi2.cdf(chi2, df=1)
  p < 0.001 → SRM 警报

常见原因:
  - 跟踪丢失 (部分请求未上报)
  - 重定向 (treatment 用户被重定向到 control)
  - 缓存 (CDN 缓存导致同一用户看到不同版本)
  - Bot 流量过滤不均
  - 灰度切流逻辑 bug

LLM 场景:
  - 长请求超时, treatment 失败率更高 (报告少)
  - 不同模型延迟不同, 上报时机不同
```

## 八、代码与配置示例

### 8.1 完整 A/B 实验闭环

```python
# experiment_platform.py
import pandas as pd
import numpy as np
from scipy import stats
from dataclasses import dataclass
from typing import List

@dataclass
class ExperimentConfig:
    name: str
    description: str
    variants: List[str]                  # ['control', 'treatment']
    primary_metric: str                  # 'retention_d7'
    guardrail_metrics: List[str]         # ['error_rate', 'p99_latency']
    alpha: float = 0.05
    power: float = 0.8
    mde: float = 0.01                    # 最小可检测效应

class ExperimentAnalyzer:
    def __init__(self, config: ExperimentConfig):
        self.config = config

    def analyze(self, df: pd.DataFrame) -> dict:
        """分析实验结果."""
        results = {}

        # 1. SRM 检验
        srm = self._check_srm(df)
        results['srm'] = srm
        if not srm['passed']:
            results['conclusion'] = 'SRM 失败, 实验不可信'
            return results

        # 2. 护栏指标
        results['guardrails'] = {}
        for metric in self.config.guardrail_metrics:
            g = self._test_metric(df, metric)
            results['guardrails'][metric] = g
            if g['degraded']:
                results['conclusion'] = f'护栏指标 {metric} 恶化, 终止实验'
                return results

        # 3. 核心指标
        primary = self._test_metric(df, self.config.primary_metric)
        results['primary'] = primary

        # 4. 结论
        if primary['significant'] and primary['lift'] > 0:
            results['conclusion'] = 'treatment 显著正向, 推荐全量'
        elif primary['significant'] and primary['lift'] < 0:
            results['conclusion'] = 'treatment 显著负向, 不全量'
        else:
            results['conclusion'] = '无显著差异, 建议延长实验或调整 MDE'

        return results

    def _check_srm(self, df: pd.DataFrame) -> dict:
        """SRM 检验."""
        observed = df['variant'].value_counts().sort_index().values
        expected = [len(df) / len(self.config.variants)] * len(self.config.variants)
        chi2, p = stats.chisquare(observed, expected)
        return {
            'observed': observed.tolist(),
            'expected': expected,
            'p_value': p,
            'passed': p > 0.001
        }

    def _test_metric(self, df: pd.DataFrame, metric: str) -> dict:
        """单指标检验."""
        control = df[df['variant'] == 'control'][metric].dropna()
        treatment = df[df['variant'] == 'treatment'][metric].dropna()

        t_stat, p_value = stats.ttest_ind(control, treatment, equal_var=False)

        c_mean, t_mean = control.mean(), treatment.mean()
        lift = (t_mean - c_mean) / c_mean if c_mean != 0 else 0

        # 置信区间
        diff = t_mean - c_mean
        se = np.sqrt(control.var()/len(control) + treatment.var()/len(treatment))
        ci = (diff - 1.96*se, diff + 1.96*se)

        # 护栏指标: 检测是否恶化
        degraded = lift > 0 and metric in self.config.guardrail_metrics and 'rate' in metric and lift > 0.05

        return {
            'control_mean': c_mean,
            'treatment_mean': t_mean,
            'lift_percent': lift * 100,
            'p_value': p_value,
            'ci_95': ci,
            'significant': p_value < self.config.alpha,
            'degraded': degraded
        }

# 使用
config = ExperimentConfig(
    name="new_llm_router_v2",
    description="测试新版本 LLM 路由器",
    variants=['control', 'treatment'],
    primary_metric='retention_d7',
    guardrail_metrics=['error_rate', 'ttft_p99', 'csat_score'],
    mde=0.005
)

analyzer = ExperimentAnalyzer(config)
df = pd.read_csv('experiment_data.csv')  # 包含 user_id, variant, metrics
results = analyzer.analyze(df)
print(results)
```

```python
# experiment_tracking.py
from typing import Dict, Any
import json
import time

class ExperimentTracker:
    """上报实验事件, 用于后续分析."""

    def __init__(self, kafka_producer):
        self.producer = kafka_producer

    def track_exposure(self, user_id: str, experiment: str, variant: str, **ctx):
        """用户暴露于实验."""
        event = {
            'event_type': 'exposure',
            'user_id': user_id,
            'experiment': experiment,
            'variant': variant,
            'timestamp': int(time.time() * 1000),
            'context': ctx
        }
        self.producer.send('experiment_events', event)

    def track_outcome(self, user_id: str, experiment: str, metric: str, value: float):
        """实验结果指标."""
        event = {
            'event_type': 'outcome',
            'user_id': user_id,
            'experiment': experiment,
            'metric': metric,
            'value': value,
            'timestamp': int(time.time() * 1000)
        }
        self.producer.send('experiment_events', event)

# 在推理服务中
class LLMService:
    def __init__(self, tracker: ExperimentTracker):
        self.tracker = tracker

    def route_request(self, user_id: str, prompt: str):
        # 分桶
        variant = self._get_variant(user_id, "new_router_v2")

        # 上报 exposure (仅一次)
        self.tracker.track_exposure(
            user_id=user_id,
            experiment="new_router_v2",
            variant=variant,
            user_tier=self._get_tier(user_id)
        )

        # 路由
        start = time.time()
        if variant == 'treatment':
            result = self._new_route(prompt)
        else:
            result = self._old_route(prompt)
        latency = time.time() - start

        # 上报 outcome
        self.tracker.track_outcome(
            user_id=user_id,
            experiment="new_router_v2",
            metric="latency_ms",
            value=latency * 1000
        )

        return result
```

## 九、常见陷阱与调优

### 9.1 陷阱 1：开关债务

**症状**：旧开关永远不删, 代码充斥 `if flag.enabled()` 分支, 难以维护。

**修复**：
- 开关命名带版本号 (`new_router_v2`), 旧版本删除后清理开关
- 设置开关过期时间, 自动提醒清理
- 季度清理计划, 移除已完成实验的开关

### 9.2 陷阱 2：实验交叉污染

**症状**：多个实验同时跑, 同一用户在多个 treatment, 无法独立归因。

**修复**：
- 分层实验 (Layered): UI 层 / 模型层 / 推荐层独立
- 互斥分组 (Mutex): 关键实验用互斥分组, 不与其他实验并行
- 正交分桶: hash(user_id + layer_id) 保证独立

### 9.3 陷阱 3：样本比例失衡（SRM）

**症状**：实验设计 50/50, 实际 49/50, 结论不可信。

**修复**：
- 实时监控分桶比例
- SRM 卡方检验, p<0.001 立即告警
- 排查: 跟踪丢失, 重定向, 缓存, Bot 过滤

### 9.4 陷阱 4：过早停止实验

**症状**：实验 3 天就出显著结果, 提前停止, 实际是假阳性。

**修复**：
- 实验前计算所需样本量, 跑够再分析
- sequential testing (序贯检验) 控制多次比较的 α
- 至少跑一个完整周期 (7 天/14 天), 覆盖周末与工作日

### 9.5 陷阱 5：长期实验累积效应

**症状**：短期实验有效, 长期反而有害 (用户疲劳, 新奇效应消退)。

**修复**：
- 短期 + 长期双实验: 先 1 周看效果, 再 4 周看持续
- 留存指标: 7日/14日/30日留存
- 反转实验: treatment 切回 control, 看是否有"撤回效应"

### 9.6 调优 Checklist

- [ ] 开关命名规范 (版本号 + 描述)
- [ ] 开关过期机制 (自动提醒清理)
- [ ] SDK 本地缓存 + 流式更新
- [ ] 实验前计算样本量
- [ ] 分层实验 + 正交分桶
- [ ] SRM 实时监控
- [ ] 护栏指标 + 核心指标
- [ ] 实验至少跑 7 天 (覆盖周末)
- [ ] 灰度发布配合 (15 章)
- [ ] 紧急降级开关演练

## 十一、与其他方案的关系

### 11.1 特征开关 vs 渐进式发布

```
渐进式发布 (15 章):
  - 部署层面: 按流量比例切分 (5%→25%→100%)
  - 工具: Argo Rollouts / Flagger
  - 适合: 新版本整体灰度

特征开关:
  - 代码层面: 功能维度开关
  - 工具: OpenFeature / LaunchDarkly
  - 适合: 单功能灰度, 紧急降级

配合:
  - 部署用 Argo Rollouts 灰度新版本
  - 功能用特征开关控制开启
  - 出问题: 关开关 (秒级) > 回滚代码 (分钟级)
```

### 11.2 特征开关 vs 配置中心

| 维度 | 特征开关 | 配置中心 (Apollo/Nacos) |
|------|---------|------------------------|
| 目的 | 功能开关 + 实验 | 配置管理 |
| 求值 | 布尔/枚举 (开关决策) | 任意配置值 |
| 灰度 | 内置 (规则+分桶) | 弱 (需自实现) |
| 实验 | 内置 (A/B 统计) | 无 |
| SDK | 专用 (本地缓存+流式) | 通用 (轮询/监听) |
| 适用 | 功能灰度/实验 | 配置热更新 |

## 十二、面试速答

**Q1: 特征开关解决了什么问题?**

A: 1) 解耦发布与上线 (代码先部署, 功能后开启); 2) 紧急降级 (出问题秒级关开关, 不回滚代码); 3) 灰度路由 (按用户/地域/时间); 4) A/B 实验 (量化版本优劣); 5) 白名单 (Beta 功能控制)。

**Q2: OpenFeature 是什么? 为什么重要?**

A: OpenFeature 是厂商中立的特征开关 API 标准, 任意后端 (LaunchDarkly/Unleash/Flagsmith) 都可实现。重要性: 1) 避免厂商锁定; 2) 统一 SDK API; 3) 跨语言一致; 4) 可平滑迁移。

**Q3: A/B 实验的样本量怎么算?**

A: n = (Z_{α/2} + Z_β)^2 × 2σ^2 / Δ^2, 其中 Z_{α/2}=1.96 (95%置信), Z_β=0.84 (80% power), σ 是指标标准差, Δ 是最小可检测差异。例: 转化率从 5% 提升到 5.5%, 需 ~30000 样本/组。

**Q4: 分层实验为什么需要正交分桶?**

A: 多个实验并行时, 同一用户在多个 treatment 会导致交叉污染, 无法独立归因。正交分桶 hash(user_id + layer_id) 保证同一用户在不同 layer 独立分桶, 实验间互不干扰。

**Q5: SRM 是什么? 怎么检测?**

A: Sample Ratio Mismatch, 实验设计 50/50 但实际比例失衡, 说明分流失衡, 实验不可信。检测: 卡方检验, p<0.001 报警。原因: 跟踪丢失, 重定向, 缓存, Bot 过滤不均, 灰度切流 bug。

## 十三、综合面试题

### 题 1（中级）：设计 LLM 推理服务的 A/B 实验

**答题要点**：

1. **实验设计**:
   - 假设: 新路由器降低 TTFT 10%
   - 变体: control (旧) / treatment (新)
   - 分桶: hash(user_id) % 100, 50/50
   - 周期: 14 天 (覆盖两个周末)

2. **指标体系**:
   - 护栏: 错误率 (<1%), TTFT P99 (<800ms), 拒答率 (<5%)
   - 核心: 用户满意度 (点赞率), 7日留存
   - 辅助: 平均对话长度, 多轮率, 模型选择率

3. **样本量**:
   - 假设当前点赞率 60%, MDE 1%
   - n ≈ 96000 per group
   - 日活 1M, 跑 1 天够

4. **数据质量**:
   - SRM 实时监控
   - 分桶比例校验
   - 异常流量过滤 (Bot)

5. **决策规则**:
   - 护栏不恶化 + 核心显著正向 → 全量
   - 护栏恶化 → 终止实验
   - 无显著差异 → 延长或调整 MDE

6. **降级方案**:
   - 特征开关秒级关停
   - Argo Rollouts 配合, 流量回退

### 题 2（高级）：实验平台在 LLM 应用的工程挑战

**答题要点**：

1. **挑战**:
   - LLM 输出非数值, 难以定义指标
   - 长对话流式输出, exposure 难定义
   - 用户多轮交互, 难独立归因
   - 模型版本迭代快, 实验周期短

2. **方案**:
   - 输出评估: 自动化指标 (perplexity, BERTScore) + 人工评分
   - exposure: 首次请求即暴露, 后续多轮不再重复计
   - 多轮归因: 用户级别聚合 (per-user outcome)
   - 快迭代: 短期 (3天) + 长期 (14天) 双实验

3. **指标创新**:
   - 用户满意度: 点赞/踩, 重写率, 多轮率
   - 输出质量: 长度分布, 拒答率, 安全性
   - 业务指标: 留存, 付费转化, ARPU

4. **统计方法**:
   - 长尾分布: 用 median 而非 mean
   - 异常值: winsorize 处理
   - 多重比较: Bonferroni 校正

5. **工程实现**:
   - 事件上报: Kafka + Flink 实时管道
   - 离线分析: Spark + Jupyter
   - 报告自动化: 每日推送 Slack

## 十四、故障复盘

### 14.1 案例 1：开关债务导致代码混乱

**背景**：2024 年某公司 LLM 服务累计 200+ 开关, 代码充斥 if-else 分支, 维护困难。

**根因**：实验结束未清理开关, 旧分支永久保留。

**修复**：
- 季度清理: 移除 100+ 旧开关
- 开关命名带版本号 (`new_router_v2`)
- 设置过期时间, 自动提醒
- 代码合并后 PR 自动检查开关清理

**防范**：开关生命周期管理, 实验结束必须清理。

### 14.2 案例 2：SRM 导致错误决策

**背景**：2025 年某公司 LLM 路由实验, 报告显示 treatment 提升 15%, 全量后反而下降。

**根因**：treatment 用户因超时未上报, 实际分桶 47/53, SRM 失败但未检测。

**修复**：
- 实时 SRM 检测告警
- 排查: 长请求超时导致上报丢失
- 修复上报逻辑后重新实验

**防范**：SRM 必须实时监控, p<0.001 立即终止实验。

### 14.3 案例 3：实验交叉污染

**背景**：2024 年某公司同时跑 UI 实验 + 模型实验, 同一用户在两个 treatment, 结论混乱。

**根因**：未分层, 用户在两实验间非正交。

**修复**：
- 引入分层实验: UI 层 + 模型层
- hash(user_id + layer_id) 正交分桶
- 验证: 检查两实验分桶独立性

**防范**：所有并行实验必须分层, 正交分桶。

### 14.4 案例 4：开关故障引发全局不可用

**背景**：2025 年某公司特征开关平台故障, SDK 拿不到配置, 全部返回默认值 (关闭), LLM 服务不可用。

**根因**：默认值设置不合理 (关键开关默认 false), 平台故障导致连锁降级。

**修复**：
- 关键开关默认值改为"安全态" (服务可用)
- SDK 本地持久化缓存, 平台故障时用最近配置
- 熔断: 平台故障超过 30s, 用本地缓存

**防范**：默认值设计必须考虑故障场景, 本地缓存 + 降级策略。

### 14.5 案例 5：长期实验累积效应未发现

**背景**：2024 年某公司新推荐算法短期提升 5%, 全量后 30 天留存下降。

**根因**：短期新奇效应, 长期用户疲劳。

**修复**：
- 短期 + 长期双实验: 1 周看效果, 4 周看持续
- 留存指标: 7日/14日/30日
- 反转实验: 切回旧版本看撤回效应

**防范**：关键实验必须长期跟踪, 不能仅看短期指标。
