# 02 - 前沿部署的核心矛盾与权衡

> 前沿部署不是"最优技术"的堆砌，而是一组永恒矛盾的权衡。理解这些矛盾，才能在具体场景做出合理决策；不理解矛盾，就会陷入"为什么用了最新技术反而不 work"的困惑。
>
> 本章梳理五大核心矛盾，每个矛盾给出量化分析、典型场景、工业权衡案例。

## 二、问题定义与边界

### 2.1 解决什么

- **识别矛盾**：当前沿部署出现问题时，能定位到是哪个矛盾的权衡失误
- **量化权衡**：用具体数据（成本、延迟、利用率）支撑决策，不靠经验直觉
- **建立决策框架**：在具体场景下，如何选择矛盾的一方
- **工业案例参考**：大厂在相同矛盾下做了什么选择

### 2.2 不解决什么

- 不讨论具体技术实现（后续章节展开）
- 不做哲学层面的"trade-off 理论"
- 不覆盖小众矛盾（如能耗 vs 性能）

### 2.3 矛盾的本质

矛盾不是"问题"，而是"物理规律"：

- **延迟 vs 吞吐**：源于 Little's Law，是排队论的基本约束
- **成本 vs 弹性**：源于资源时间粒度，预留必然比按需便宜
- **可靠性 vs 复杂度**：源于故障域理论，多副本引入一致性复杂度
- **隐私 vs 性能**：源于数据局部性，本地数据传云端必然慢
- **迭代速度 vs 稳定性**：源于变更风险，每次发布都是一次风险事件

理解矛盾的物理本质，就不会试图"用技术消除矛盾"，而是"在约束下找最优解"。

## 三、直觉解释

### 3.1 矛盾 1：延迟 vs 吞吐

**直觉**：处理一个请求快（低延迟）和处理很多请求快（高吞吐）往往是矛盾的。

**经典例子**：超市收银台
- 单个收银台：顾客等待时间短（低延迟），但整体处理速度有限（低吞吐）
- 批量收银（10 人一批）：整体处理速度高（高吞吐），但单顾客等待时间长（高延迟）

**LLM 推理中的体现**：
- `batch_size=1`：每个请求立即处理，TTFT 最低，但 GPU 利用率 5%
- `batch_size=256`：等够 256 个请求再处理，吞吐最高，但 TTFT 高（等批凑齐）

**Little's Law**：`L = λ × W`
- L：系统中平均请求数
- λ：到达率（QPS）
- W：平均等待时间

约束：如果想保持低 W（延迟），要么降低 λ（吞吐），要么增加并发能力（成本）。

### 3.2 矛盾 2：成本 vs 弹性

**直觉**：资源可以随时用随时还（弹性）必然比长期占着（预留）贵。

**经典例子**：租车 vs 买车
- 买车（预留）：固定成本高，但单次使用边际成本为 0
- 租车（按需）：固定成本低，但单次使用成本高

**LLM 推理中的体现**：
- 预留 H100：$2/小时（长租），24×7 在线
- Serverless H100：$5/小时（按需），用完释放
- Spot H100：$0.8/小时（中断风险），适合离线

**核心权衡**：稳态流量用预留（便宜），突发流量用按需（弹性）。

### 3.3 矛盾 3：可靠性 vs 复杂度

**直觉**：系统越可靠，需要的冗余越多，复杂度越高，而复杂度本身引入新故障。

**经典例子**：单机 vs 集群
- 单机：简单，但宕机就全挂
- 集群：高可用，但引入一致性、脑裂、网络分区问题

**LLM 推理中的体现**：
- 单点 vLLM：简单，但宕机影响所有请求
- 多副本 + 负载均衡：高可用，但 KV Cache 跨节点同步复杂
- 多地域多活：极高可用，但数据一致性、跨区延迟、成本暴增

**CAP 约束**：分布式系统在 C（一致性）和 A（可用性）之间必选其一（分区容忍 P 是必选）。

### 3.4 矛盾 4：隐私 vs 性能

**直觉**：数据留在本地（隐私）vs 数据传到云端高性能机器（性能），不可兼得。

**经典例子**：本地文档 vs 云盘
- 本地：私密，但访问慢、容量小
- 云盘：快、容量大，但隐私风险

**LLM 推理中的体现**：
- 端侧推理（手机 NPU）：隐私好，但模型小、慢
- 云端推理（H100 集群）：性能好，但数据上传
- 端云协同：端侧小模型 + 云端大模型，复杂但平衡

**GDPR / 数据安全法**约束：敏感数据（医疗、金融）必须本地处理。

### 3.5 矛盾 5：迭代速度 vs 稳定性

**直觉**：发布越快，新功能越快上线，但故障也越多。

**经典例子**：瀑布开发 vs 敏捷开发
- 瀑布：稳定但慢
- 敏捷：快但可能不稳定

**LLM 推理中的体现**：
- 月度发布：稳定，但跟不上竞争
- 每日发布：快，但需要灰度、回滚、监控全套
- 模型版本切换：每次切换都是风险（输出风格变化、用户感知）

**关键工具**：渐进式发布（Canary/Shadow）、特征开关、A/B 实验。

## 四、核心概念与架构

### 4.1 矛盾 1：延迟 vs 吞吐的量化

#### LLM 推理的延迟分解

```
TTFT (Time To First Token)
├── Queue Time (排队等待)
├── Prefill Time (prefill 计算)
└── First Token Generation

TPOT (Time Per Output Token)
├── Decode Time (单 token 生成)
├── Batch Interference (batch 内其他请求影响)
└── Memory Bandwidth Contention (显存带宽竞争)
```

#### batch_size 对延迟与吞吐的影响（Llama-70B，A100 80GB）

| batch_size | TTFT (ms) | TPOT (ms) | 吞吐 (tokens/s) | GPU 利用率 |
|------------|-----------|-----------|-----------------|------------|
| 1 | 120 | 25 | 40 | 8% |
| 4 | 180 | 28 | 143 | 25% |
| 16 | 280 | 35 | 457 | 55% |
| 64 | 450 | 50 | 1280 | 75% |
| 128 | 800 | 75 | 1700 | 85% |
| 256 | 1500 | 120 | 2130 | 90% |

观察：
- batch_size 1→256，吞吐 53x，但 TTFT 12.5x
- 最优 batch_size 取决于 SLA：TTFT < 500ms 选 batch ≤ 64

#### continuous batching 的破局

传统 static batching：等批凑齐 → 高延迟
continuous batching（Inflight Batching）：请求动态加入/退出 → 低延迟 + 高吞吐

```
Static Batching:
  t=0: 等待 8 个请求到齐 (300ms)
  t=300ms: 开始处理 batch (2000ms)
  t=2300ms: 全部完成

Continuous Batching:
  t=0: 请求1 到达，立即处理
  t=50ms: 请求2 到达，加入 batch
  t=100ms: 请求3 到达，加入 batch
  ...
  t=2300ms: 全部完成
```

效果：吞吐相同，但 TTFT 从 300ms → 50ms。

### 4.2 矛盾 2：成本 vs 弹性的量化

#### GPU 计费模型对比

| 模式 | H100 单价 | 适用场景 | 风险 |
|------|-----------|----------|------|
| 包年（预留） | $1.8/小时 | 24×7 稳态 | 闲置浪费 |
| 按需（on-demand） | $3.5/小时 | 突发 | 单价高 |
| Spot | $0.9/小时 | 离线/可中断 | 中断风险 |
| Serverless（Modal） | $5/小时（按秒） | 极突发 | 冷启动 |

#### 流量特征决定选型

```
流量模式:
  - 稳态（24×7 高负载）: 预留最优
  - 昼夜波动（白天高夜间低）: 预留 base + 按需 peak
  - 突发（少量高峰）: 全按需
  - 离线 batch: Spot
```

#### 混合部署的成本模型

假设日均 1 亿 token，峰值 5x：

| 方案 | 配置 | 月成本 |
|------|------|--------|
| 全预留 | 200×H100 24×7 | $259K |
| 全按需 | 200×H100 on-demand | $504K |
| base+peak | 150 预留 + 50 按需 | $227K |
| base+Spot | 150 预留 + 50 Spot（peak） | $216K（有中断风险） |

base+peak 比 base+Spot 贵 5%，但 SLA 兑现率高。

### 4.3 矛盾 3：可靠性 vs 复杂度的量化

#### 可靠性等级与成本

| 等级 | SLA | 架构 | 月成本（亿 token） |
|------|-----|------|-------------------|
| L1 | 99% | 单点 | $80K |
| L2 | 99.9% | 多副本 + LB | $120K |
| L3 | 99.99% | 多可用区 | $180K |
| L4 | 99.999% | 多地域多活 | $400K+ |

每多一个 9，成本翻倍。

#### 故障域与爆炸半径

```
单点: 爆炸半径 = 全部
多副本: 爆炸半径 = 1/N (N 副本)
多可用区: 爆炸半径 = 单 AZ
多地域: 爆炸半径 = 单地域
单元化: 爆炸半径 = 单元 (用户子集)
```

单元化（蚂蚁 LDC、字节 Dorado）的精髓：把爆炸半径从"全局"降到"单元"，5% 用户故障 vs 100% 用户故障。

### 4.4 矛盾 4：隐私 vs 性能的量化

#### 端云协同的延迟对比

| 方案 | 模型 | 延迟 | 隐私 | 适用 |
|------|------|------|------|------|
| 全云端 | Llama-70B | 300ms TTFT | 数据上传 | 通用 |
| 端侧 | Llama-1B Q4 | 800ms TTFT | 完全本地 | 隐私敏感 |
| 端云协同 | 端 1B + 云 70B | 端 200ms / 云 300ms | 部分上传 | 平衡 |
| cascade | 端 1B 优先 + 云 fallback | 简单请求 200ms / 复杂 300ms | 简单不上传 | 性能优化 |

#### 级联推理（cascade）的成本

```
端侧小模型 (1B): 处理 70% 简单请求, 延迟 200ms, 成本 $0
云端大模型 (70B): 处理 30% 复杂请求, 延迟 300ms, 成本 $0.5/M token

混合成本 = 0.7×0 + 0.3×$0.5 = $0.15/M token
全云端成本 = $0.5/M token
节省 70%
```

### 4.5 矛盾 5：迭代速度 vs 稳定性的量化

#### 发布策略与故障率

| 策略 | 发布频率 | 故障率 | MTTR | 适合 |
|------|----------|--------|------|------|
| 月度发布 | 1/月 | 5% | 4 小时 | 传统企业 |
| 周度发布 | 1/周 | 3% | 1 小时 | 一般互联网 |
| 日级发布 | 1/天 | 1.5% | 30 分钟 | 互联网大厂 |
| 持续部署 | 100+/天 | 0.5% | 5 分钟 | Netflix/GitHub |

观察：发布频率越高，故障率反而越低（每次发布变更少、回滚快、监控细）。

#### 渐进式发布的风险曲线

```
全量发布 (Big Bang):
  t=0: 100% 流量到新版本
  t=10min: 发现 bug, 已影响全部用户
  损失: 100% × 10min

Canary 10%:
  t=0: 10% 流量到新版本
  t=10min: 发现 bug, 影响 10% 用户
  t=15min: 回滚
  损失: 10% × 15min
```

Canary 把损失降到 1/10。

## 五、操作流程与配置

### 5.1 矛盾权衡决策框架

针对每个矛盾，提供决策框架：

#### 延迟 vs 吞吐决策

```
1. 定义 SLA:
   - TTFT 上限 (例: 500ms P99)
   - TPOT 上限 (例: 50ms P99)
   - 吞吐目标 (例: 10000 tokens/s)

2. 测试基线:
   - benchmark 不同 batch_size 下的延迟/吞吐
   - 找到满足 SLA 的最大 batch_size

3. 选 continuous batching:
   - 总是优于 static batching
   - 配合 --max-num-seqs 调优

4. PD 分离:
   - prefill 集群优化 TTFT
   - decode 集群优化吞吐
```

#### 成本 vs 弹性决策

```
1. 分析流量:
   - 日均 QPS / token
   - 峰值倍数 (峰值/均值)
   - 时间分布 (昼夜/工作日)

2. 资源配比:
   - 稳态 (80% 时间) → 预留 (base)
   - 突发 (20% 时间) → 按需 (peak)
   - 离线 → Spot

3. 混合策略:
   - K8s 预留 70% + Serverless 30%
   - KEDA 监控队列长度触发 Serverless
```

#### 可靠性 vs 复杂度决策

```
1. 定义 SLA:
   - 可用性目标 (99.9% / 99.99% / 99.999%)
   - RTO (恢复时间)
   - RPO (数据丢失)

2. 架构选型:
   - 99.9%: 多副本 + 跨 AZ
   - 99.99%: 多 AZ + 单元化
   - 99.999%: 多地域多活

3. 故障演练:
   - ChaosMesh 定期注入故障
   - 红黑演练
```

#### 隐私 vs 性能决策

```
1. 数据分级:
   - 公开: 全云端
   - 内部: 私有云
   - 敏感: 端侧 / 私有云
   - 机密: 端侧 + 加密

2. 模型选择:
   - 端侧: 1B-7B 量化
   - 私有云: 7B-70B
   - 公有云: 70B+

3. 级联策略:
   - 端侧处理简单 (70%)
   - 云端处理复杂 (30%)
```

#### 迭代速度 vs 稳定性决策

```
1. 发布策略:
   - Canary 10% → 50% → 100%
   - 每阶段观察 1 小时
   - 自动回滚 (错误率 > 阈值)

2. 特征开关:
   - 新功能默认关闭
   - 灰度开启 1% → 10% → 100%
   - 可随时关闭

3. 模型版本:
   - 蓝绿部署 (双版本并行)
   - A/B 实验 (流量切分)
   - 影子流量 (新版本不影响用户)
```

## 六、底层原理

### 6.1 矛盾 1 的底层原理：Little's Law 与排队论

**Little's Law**：`L = λ × W`
- L：系统中平均请求数
- λ：到达率（QPS）
- W：平均等待时间

**推论**：如果想保持 W 低（低延迟），要么降低 λ（吞吐），要么增加 L（并发能力，即成本）。

**M/M/c 排队模型**（c 个服务台）：
- 利用率 ρ = λ / (c × μ)，μ 是单服务台速率
- ρ > 0.8 时，等待时间急剧上升（指数增长）
- 经验值：保持 ρ < 0.7 以确保低延迟

**LLM 推理应用**：
- 单 GPU QPS 上限 = 1 / TTFT
- 想保持 TTFT < 500ms，单 GPU QPS < 2
- 10K QPS 需要 5000 GPU（理论值），实际通过 batching 降到 500 GPU

### 6.2 矛盾 2 的底层原理：资源时间粒度

**资源粒度越细，单价越高**：
- 包年：资源"锁"1 年，供应商可长期规划，单价低
- 按需：资源随时释放，供应商需要冗余，单价高
- Spot：用供应商的冗余资源，可能被回收，单价最低

**价格曲线**（H100 80GB，2026 市场价）：
- 包年：$1.8/小时
- 按需：$3.5/小时（1.94x）
- Spot：$0.9/小时（0.5x）
- Serverless：$5/小时（2.78x，按秒计费）

**核心权衡**：
- 利用率 > 70%：预留便宜
- 利用率 30-70%：按需便宜
- 利用率 < 30%：Serverless 便宜

### 6.3 矛盾 3 的底层原理：CAP 与故障域

**CAP 定理**：分布式系统在 C（一致性）、A（可用性）、P（分区容忍）中三选二。
- 网络分区（P）必然发生，所以实际是 C vs A
- 选 C：分区时拒绝服务（保证一致）
- 选 A：分区时继续服务（可能不一致）

**故障域理论**：
- 故障域 = 一个故障能影响的范围
- 单点 = 全局故障域
- 多副本 = 故障域 = 1/N
- 单元化 = 故障域 = 单元（用户子集）

**复杂度来源**：
- 多副本：数据同步、一致性协议（Raft/Paxos）
- 多 AZ：跨 AZ 网络延迟（1-2ms）、数据复制
- 多地域：跨地域延迟（50-200ms）、全局路由、数据主权

**经验法则**：每增加一个 9 的可用性，系统复杂度翻倍，成本翻倍。

### 6.4 矛盾 4 的底层原理：数据局部性与带宽

**数据局部性原理**：处理数据离存储越近，性能越好。
- L1 cache：1ns
- L2 cache：4ns
- L3 cache：12ns
- 内存：100ns
- SSD：16μs
- 网络（同 AZ）：500μs
- 网络（跨地域）：50ms

**LLM 推理的局部性**：
- KV Cache 在 GPU 显存（HBM）：3TB/s
- KV Cache 在 CPU 内存：100GB/s（30x 慢）
- KV Cache 跨节点传输：50GB/s（60x 慢）
- KV Cache 跨地域传输：10GB/s（300x 慢）

**结论**：KV Cache 必须留本地，导致推理有状态，破坏无状态假设。

**端云协同的延迟数学**：
- 端侧 1B 模型：800ms TTFT（手机 NPU）
- 云端 70B 模型：300ms TTFT（H100）+ 100ms 网络延迟 = 400ms
- cascade：简单 800ms 端侧（无网络）+ 复杂 400ms 云端

端侧反而比云端慢（无网络优势被算力劣势抵消），但隐私好。

### 6.5 矛盾 5 的底层原理：变更风险与回滚成本

**变更风险公式**：
```
故障概率 = 变更行数 × 单行 bug 率 × 监控盲区率
MTTR = 检测时间 + 决策时间 + 回滚时间
```

**经验数据**（Google SRE）：
- 单次变更 < 100 行：故障率 0.5%
- 单次变更 100-1000 行：故障率 3%
- 单次变更 > 1000 行：故障率 10%

**结论**：小步快跑（持续部署）比大步慢跑（月度发布）故障率低。

**LLM 推理的特殊性**：
- 模型版本切换是"语义变更"（输出风格变化）
- 不能简单回滚（已生成的输出无法撤回）
- 需要"语义灰度"：新版本处理 10% 流量，对比输出质量

class CascadeInference:
    def __init__(self):
        self.edge_model = load_edge_model("llama-1b-q4")  # 端侧 1B
        self.cloud_client = CloudLLMClient("llama-70b")   # 云端 70B

    def infer(self, prompt, complexity_threshold=0.5):
        # 1. 端侧先试
        edge_output, confidence = self.edge_model.generate(prompt)

        if confidence > complexity_threshold:
            # 简单请求, 端侧返回
            return edge_output, "edge"
        else:
            # 复杂请求, 云端处理
            cloud_output = self.cloud_client.generate(prompt)
            return cloud_output, "cloud"

# 隐私分级
class PrivacyAwareRouter:
    def __init__(self):
        self.classifier = load_classifier()  # 敏感数据分类器

    def route(self, prompt):
        sensitivity = self.classifier(prompt)
        if sensitivity == "public":
            return "cloud-70b"
        elif sensitivity == "internal":
            return "private-cloud-13b"
        elif sensitivity == "sensitive":
            return "edge-7b"
        else:  # confidential
            return "edge-1b-q4"

## 八、常见陷阱与调优

### 8.1 陷阱 1：盲目追求高吞吐

**症状**：把 batch_size 调到 512，吞吐上去了，但用户反馈慢。

**根因**：TTFT 随 batch_size 线性增长，512 batch 的 TTFT 可能 1.5s+，用户体验差。

**修复**：先定 SLA（TTFT < 500ms），再反推最大 batch_size。

### 8.2 陷阱 2：全预留导致成本失控

**症状**：为了应对峰值，预留 100 张 H100，但均值只用 30 张。

**根因**：没有分析流量特征，盲目预留。

**修复**：base + peak 模式，预留 70%，按需 30%。

### 8.3 陷阱 3：过度追求多活

**症状**：业务还没起来就上多地域多活，运维复杂度爆炸。

**根因**：多活是为 99.999% 设计的，99.9% 用多副本 + 跨 AZ 就够。

**修复**：根据 SLA 选架构，不要 over-engineer。

### 8.4 陷阱 4：cascade 路由错误

**症状**：cascade 推理效果差，复杂请求也被端侧处理。

**根因**：confidence 阈值设错，或分类器不准。

**修复**：用 LLM judge 标注数据训练分类器，定期评估。

### 8.5 陷阱 5：渐进式发布观察期太短

**症状**：Canary 10% 观察 10 分钟就全量，结果 2 小时后才发现 bug。

**根因**：有些 bug 需要长时间才能暴露（内存泄漏、状态累积）。

**修复**：每阶段至少观察 1 小时，关键指标自动监控。

## 十一、面试速答

**Q1: 延迟 vs 吞吐的矛盾如何在 LLM 推理中体现？**

A: 大 batch 提升吞吐但增加 TTFT，小 batch 降低 TTFT 但牺牲吞吐。破局是 continuous batching，让请求动态加入/退出，避免等批凑齐。Little's Law 是底层约束：L = λ × W。

**Q2: 成本 vs 弹性的核心权衡？**

A: 资源粒度越细单价越高。预留（包年）便宜但浪费，按需贵但弹性，Spot 最便宜但有中断风险。混合部署最优：base 预留 70% + peak 按需 30%。

**Q3: 多活值得吗？**

A: 取决于 SLA。99.9% 用多副本 + 跨 AZ 就够，99.99% 才需要单元化，99.999% 才需要多地域多活。每多一个 9，成本和复杂度翻倍。

**Q4: 端云协同的核心思想？**

A: cascade 推理。端侧小模型处理简单请求（70%），云端大模型处理复杂请求（30%）。降低延迟（无网络）+ 隐私保护 + 成本节省（70% 免费额度）。

**Q5: 持续部署为什么故障率反而低？**

A: 每次变更小（< 100 行故障率 0.5%，> 1000 行 10%）。回滚快（5 分钟 vs 4 小时）。监控细（每次部署都监控指标）。

**Q6: PD 分离解决什么矛盾？**

A: 延迟 vs 吞吐。Prefill 算力密集（影响 TTFT），Decode 显存密集（影响吞吐）。拆到不同集群分别优化，Prefill 用 H100 高算力卡，Decode 用 A10 高显存密度卡。

**Q7: CAP 在 LLM 推理中的体现？**

A: 多副本 KV Cache 同步是 C vs A 取舍。强一致（C）需要跨节点同步，延迟高；最终一致（A）各副本独立，可能输出不一致。多数实践选 A（KV Cache 不强一致）。

**Q8: 如何权衡矛盾？**

A: 1) 定义 SLA（量化目标） 2) 测试基线（不同配置的延迟/吞吐/成本） 3) 找到满足 SLA 的最低成本配置 4) 渐进式优化（不要一次到位）。

## 十三、故障复盘

### 13.1 案例 1：盲目追求吞吐导致 TTFT 1.5s

**背景**：2024 年某公司 LLM 推理，batch_size=512，吞吐高但 TTFT 1.5s。

**现象**：
- 吞吐 2000 tokens/s（看似好）
- TTFT 1.5s（用户抱怨）
- 用户流失率 30%

**根因**：
- 没定义 SLA，盲目调优吞吐
- batch_size 太大导致排队等待

**修复**：
- 定义 SLA：TTFT < 500ms
- 测试 batch_size 32/64/128/256 下的 TTFT
- 选 batch_size=64（TTFT 280ms，吞吐 457 tokens/s）
- 配合 continuous batching 弥补吞吐

**效果**：
- TTFT 1.5s → 280ms（5x）
- 吞吐 2000 → 1400 tokens/s（牺牲 30%）
- 用户留存恢复

**教训**：先定 SLA 再调优，不要盲目追求单一指标。

### 13.2 案例 2：全预留导致成本超预算 2x

**背景**：2025 年某公司为了 SLA，预留 200 张 H100，但均值只用 50 张。

**现象**：
- SLA 兑现 99.95%
- 但月成本 $518K，预算 $250K
- GPU 利用率均值 25%

**根因**：
- 没做流量分析
- 盲目预留应对峰值
- 峰值 200 张但均值 50 张

**修复**：
- 分析流量：均值 50 张，峰值 150 张，P99 200 张
- 配置：预留 70（base） + 按需 80（peak） + Spot 50（离线）
- 月成本：70×$1.8×24×30 + 80×$3.5×8×30 + 50×$0.9×8×30 = $90K + $67K + $11K = $168K

**效果**：
- 月成本 $518K → $168K（降 67%）
- SLA 仍 99.9%（峰值有按需兜底）

**教训**：base + peak 模式，预留只覆盖稳态。

### 13.3 案例 3：过度多活导致运维爆炸

**背景**：2024 年某创业公司，业务刚起步就上多地域多活。

**现象**：
- 6 个月后运维复杂度爆炸
- 跨地域数据同步 bug 频发
- 团队 30% 时间在处理多活问题

**根因**：
- SLA 实际只要 99.9%
- 多活是为 99.999% 设计的
- over-engineering

**修复**：
- 退回单地域 + 多 AZ
- 月成本降 60%
- 运维复杂度大幅下降
- SLA 仍 99.9%

**教训**：根据 SLA 选架构，不要 over-engineer。

### 13.4 案例 4：cascade 路由错误导致质量下降

**背景**：2025 年某公司 cascade 推理，端侧处理 70%，但用户反馈质量下降。

**现象**：
- 延迟降 30%（看似好）
- 但用户满意度下降
- 复杂请求被端侧处理

**根因**：
- confidence 阈值设错（0.5 太低）
- 分类器在长 prompt 上不准
- 复杂请求被误判为简单

**修复**：
- 用 LLM judge 标注 10000 条数据
- 训练专门的复杂度分类器
- 阈值从 0.5 调到 0.7
- 端侧处理比例从 70% 降到 50%

**效果**：
- 用户满意度恢复
- 延迟略升（50% 端侧 vs 70% 端侧）

**教训**：cascade 的关键在路由分类器，需要持续评估。

### 13.5 案例 5：渐进式发布观察期太短

**背景**：2025 年某公司 Canary 10% 观察 10 分钟就全量，2 小时后内存泄漏。

**现象**：
- 前 10 分钟指标正常
- 全量后 2 小时 OOM
- 影响全部用户

**根因**：
- 观察期太短
- 内存泄漏需要长时间暴露
- 没有长时间监控

**修复**：
- 每阶段至少观察 1 小时
- 内存指标单独监控
- 自动回滚（内存增长 > 阈值）

**效果**：
- 类似 bug 在 Canary 阶段就被发现
- 不再影响全量用户

**教训**：观察期要够长，关键指标要细。
