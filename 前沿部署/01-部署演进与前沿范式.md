# 01 - 部署演进与前沿范式

> 理解"前沿部署"必须先理解部署范式演进。本章梳理从物理机到 AI 原生部署的五次范式跃迁，每次跃迁的驱动力、技术底座、引入的新矛盾，以及当前"前沿"的真实含义。
>
> 本章是全书的概念地基，后续 25 章都在此之上展开。

## 三、直觉解释

### 3.1 一句话概括演进驱动力

> **部署演进的驱动力：在更细的时间粒度上分配更精确的资源。**

每一代范式都比上一代在两个维度上更精细：

| 维度 | 物理机 | 虚拟机 | 容器 | Serverless | AI 原生 |
|------|--------|--------|------|------------|---------|
| 时间粒度 | 年/月 | 小时 | 秒 | 毫秒 | token |
| 资源粒度 | 整机 | vCPU/GB | 毫核/MB | 单请求 | 显存页/token |

### 3.2 五代范式的核心矛盾

每代范式都解决上一代的核心矛盾，但引入新的矛盾：

```
物理机 ── 矛盾: 利用率低 ──→ 虚拟机
   VM ── 矛盾: hypervisor 开销 ──→ 容器
  容器 ── 矛盾: 隔离弱、运维重 ──→ Serverless
Serverless ── 矛盾: 冷启动、无状态 ──→ AI 原生
AI 原生 ── 矛盾: GPU 调度复杂、有状态、成本高 ──→ ???
```

**AI 原生范式的根本矛盾**（截至 2026）：
- GPU 资源调度粒度粗（一张卡不能多模型共享，但单模型又用不满）
- 推理有状态（KV Cache 让请求间有共享状态，破坏了无状态假设）
- 流式输出（SSE 替代一次性响应，连接保持时间长）
- 长尾延迟敏感（首 token 延迟比平均延迟更重要）

### 3.3 为什么 AI 原生是新范式（不是容器的延伸）

很多人误以为 LLM 推理服务"就是 K8s + GPU Pod"，这是范式错配。关键差异：

| 维度 | 传统 Web 服务（容器范式） | LLM 推理服务（AI 原生范式） |
|------|--------------------------|----------------------------|
| 资源 | CPU/内存为主 | GPU 显存为主（一级资源） |
| 状态 | 无状态（任何 Pod 处理任何请求） | 有状态（KV Cache 复用需要亲和性） |
| 响应 | 一次性 JSON | 流式 SSE/WebSocket |
| 延迟指标 | P99 整体延迟 | TTFT（首 token）+ TPOT（每 token） |
| 批处理 | 一般不批 | continuous batching 是核心 |
| 调度 | round-robin / least-connections | prefix-aware / KV-aware |
| 弹性 | HPA on CPU/QPS | HPA on token/s + GPU util |
| 冷启动 | 容器镜像秒级 | 模型权重 GB 级，分钟级 |

后文反复出现的"范式错配"，根源都是把容器范式套到 AI 原生场景。

## 四、核心概念与架构

### 4.1 五范式对比矩阵

| 维度 | 物理机 | 虚拟机 | 容器 | Serverless | AI 原生 |
|------|--------|--------|------|------------|---------|
| 隔离边界 | 硬件 | hypervisor | namespace + cgroup | MicroVM | GPU + namespace |
| 资源粒度 | 整机 | vCPU/GB | 毫核/MB | 单请求 | 显存页/token |
| 启动时间 | 分钟-小时 | 秒-分钟 | 毫秒-秒 | 毫秒-秒（冷启动秒级） | 秒-分钟（权重加载） |
| 计费粒度 | 月 | 小时 | 秒 | 毫秒/请求 | token |
| 状态模型 | 有状态 | 有状态 | 无状态首选 | 强制无状态 | 有状态（KV Cache） |
| 利用率 | 10-15% | 30-40% | 50-60% | 70%+ | 30-70%（GPU 难） |
| 运维边界 | 全栈 | guest OS 以下 | 容器以下 | 运行时以下 | 模型以下 |
| 典型代表 | IDC 裸机 | VMware ESXi | Docker/K8s | Lambda/Fargate | vLLM/Modal/PAI-EAS |

### 4.2 每代范式的技术底座

#### 物理机（1990s-）

技术底座：
- BIOS + bootloader
- 操作系统直接装硬件
- 网络栈：TCP/IP over 物理/虚拟网卡

核心限制：
- 资源无法共享（一台机器一个 OS）
- 部署周期长（采购到上线周/月）
- 利用率低（IDC 实测均值 10-15%，参考 Google 2015 Borg 论文）

#### 虚拟机（2000s-）

技术底座：
- **Hypervisor（VMM）**：Type 1（ESXi/Xen/Hyper-V）直接装硬件，Type 2（KVM/VirtualBox）跑在 OS 上
- **虚拟硬件**：vCPU/vNIC/vDisk 抽象
- **硬件辅助虚拟化**：Intel VT-x / AMD-V 指令集

核心限制：
- hypervisor 开销（CPU 5-10%、内存 5-10%、IO 10-30%）
- VM 镜像大（GB 级），迁移慢
- guest OS 维护成本

#### 容器（2013-）

技术底座：
- **namespace**（PID/NET/MNT/UTS/IPC/USER/CGROUP）：进程级隔离
- **cgroup**（v1/v2）：资源限制
- **UnionFS**（OverlayFS）：分层镜像
- **OCI 规范**：image spec + runtime spec

核心限制：
- 共享内核（隔离弱于 VM）
- 网络性能损耗（veth bridge 转发）
- 调度依赖 K8s（运维复杂度高）

#### Serverless（2018-）

技术底座：
- **MicroVM**：Firecracker（Lambda/Fargate 底座）
- **事件驱动**：API Gateway → Function → 自动伸缩
- **Scale-to-Zero**：KEDA/Knative 触发器
- **快照恢复**：CRIU、Firecracker snapshot

核心限制：
- 冷启动（毫秒-秒级，但模型加载是分钟级）
- 强制无状态（KV Cache 难以 Scale-to-Zero）
- 请求级计费但长任务贵
- 调试困难

#### AI 原生（2023-）

技术底座：
- **GPU 调度**：NVIDIA MIG、time-slicing、MPS
- **KV Cache 管理**：PagedAttention、prefix cache
- **continuous batching**：Inflight Batching
- **PD 分离**：Prefill/Decode 解耦到不同集群
- **流式协议**：SSE/WebSocket
- **token 计费**：按输入/输出 token 分别计价

核心限制：
- GPU 资源粒度粗（一张 H100 80GB，无法 0.1 张卡分配）
- 有状态推理破坏无状态假设
- 流式连接保持时间长（连接数成为瓶颈）
- 成本极高（H100 单卡 $3-4/小时，推理成本是 CPU 服务的 100x）

### 4.3 AI 原生部署的五个根本差异

#### 差异 1：GPU 优先调度

传统 K8s 调度以 CPU/内存为核心资源，GPU 是 extended resource（一张卡一个整数）。AI 原生调度必须考虑：

- **显存（VRAM）**：模型权重 + KV Cache，是真正的瓶颈
- **GPU 算力**：TFLOPS（FP16/FP8/INT8）
- **NVLink/PCIe 拓扑**：TP 并行需要 NVLink
- **GPU 健康状态**：ECC 错误、降频、XID 错误

实践：NVIDIA GPU Operator + Volcano/KubeFlow + 自研 GPU 调度器（阿里 cnao、字节 VecGPU）。

#### 差异 2：有状态推理

传统 Web 服务无状态，任何 Pod 处理任何请求。LLM 推理中 KV Cache 让请求间有共享状态：

- **prefix caching**：相同 system prompt 的 KV Cache 复用
- **session affinity**：同一会话路由到同一 GPU
- **抢占式调度**：高优请求抢占低优的 KV Cache

破坏无状态假设后，K8s Service 的 round-robin 不再适用，需要 prefix-aware router（vLLM 0.6+ 的分散路由、SGLang 的 radix tree）。

#### 差异 3：流式输出

传统 HTTP 请求-响应是一次性 JSON。LLM 推理是流式输出：

- **SSE（Server-Sent Events）**：单向流，OpenAI 兼容
- **WebSocket**：双向流，多模态交互
- **gRPC streaming**：内部 RPC 高效

流式连接保持时间长（一次推理 30s-5min），连接数成为瓶颈。Nginx 默认 60s 超时不够，需要调到 600s+。负载均衡需要支持流式（Envoy、HAProxy 支持，传统 Nginx 需配置）。

#### 差异 4：长尾延迟敏感

传统服务关注 P99 整体延迟。LLM 推理关注两个指标：

- **TTFT（Time To First Token）**：首 token 延迟，用户感知最强
- **TPOT（Time Per Output Token）**：每 token 延迟，决定生成速度

TTFT 主要由 prefill 阶段决定（与 prompt 长度相关），TPOT 由 decode 阶段决定。PD 分离架构（DistServe、Splitwise）就是把这两个阶段拆到不同集群优化。

#### 差异 5：token 计费

传统服务按 QPS 计费。LLM 推理按 token 计费：

- **input token**：prefill 阶段，计算密集
- **output token**：decode 阶段，显存密集
- **cache hit token**：prefix cache 命中的部分，几乎免费

OpenAI、Anthropic 的定价已经按 input/output 分开（output 比 input 贵 3-5x）。内部成本核算也必须按 token 拆解，否则预算失控。

### 4.4 范式跃迁的工程信号

如何判断"该换范式了"？三个工程信号：

1. **利用率天花板**：当前范式优化到极限仍无法满足需求
   - 例：容器范式在 GPU 利用率 30-40% 触顶，需要 AI 原生范式

2. **新指标出现**：旧范式无法表达新指标
   - 例：TTFT/TPOT 无法用 P99/QPS 表达，需要 AI 原生范式

3. **成本曲线失控**：旧范式下成本随规模线性增长
   - 例：Serverless GPU 冷启动成本失控，需要 AI 原生的预热策略

## 五、操作流程与配置

### 5.1 范式选型决策树

```
                ┌──────────────────────────┐
                │ 是否需要 GPU 推理?       │
                └────────────┬─────────────┘
                             │
              ┌──────────────┴──────────────┐
              ▼                             ▼
        [需要 GPU]                       [不需要]
              │                             │
   ┌──────────┴──────────┐         ┌───────┴────────┐
   ▼                     ▼         ▼                ▼
[长时稳定]           [突发弹性]  [有状态]         [无状态]
   │                     │         │                │
   ▼                     ▼         ▼                ▼
K8s + GPU Operator   Serverless   K8s +        Serverless
+ vLLM/SGLang        GPU(Modal)  StatefulSet    (Lambda/KNative)
+ PD 分离            + 快照恢复   (Redis/MySQL)
```

### 5.2 从传统到 AI 原生的迁移路径

企业从容器范式迁移到 AI 原生范式的典型四阶段：

#### 阶段 1：共存（Coexist）

容器平台（K8s）继续跑传统服务，新增 GPU 集群跑 LLM 推理。两套调度器并行。

```yaml
# K8s GPU Pod 基础形态（阶段 1）
apiVersion: v1
kind: Pod
metadata:
  name: vllm-llama70b
spec:
  containers:
  - name: vllm
    image: vllm/vllm-openai:v0.6.0
    resources:
      limits:
        nvidia.com/gpu: 4  # 整卡分配，粒度粗
    env:
    - name: MODEL
      value: meta-llama/Llama-3.1-70B
    volumeMounts:
    - name: dshm
      mountPath: /dev/shm
  volumes:
  - name: dshm
    emptyDir:
      medium: Memory
      sizeLimit: 16Gi
```

问题：整卡分配粒度粗、KV Cache 无法跨 Pod 共享、流式连接超时。

#### 阶段 2：GPU 调度优化

引入 Volcano/YuniKorn 做 GPU 调度，启用 MIG/MPS 实现细粒度共享。

```yaml
# MIG 切分（H100 可切 7 个实例）
apiVersion: v1
kind: Pod
metadata:
  name: vllm-mig
spec:
  containers:
  - name: vllm
    image: vllm/vllm-openai:v0.6.0
    resources:
      limits:
        nvidia.com/mig-1g.10gb: 1  # 1g.10gb MIG 实例
```

#### 阶段 3：PD 分离

Prefill 与 Decode 拆到不同集群，分别优化。需要自研路由层。

```
[Client] → [Router] → [Prefill Cluster] ──KV Cache──→ [Decode Cluster]
                       (A100 高算力)                    (A10 高显存)
```

#### 阶段 4：AI 原生平台

统一调度 GPU/CPU/显存，内置 KV Cache 共享、PD 分离、continuous batching。代表：阿里 PAI-EAS、字节 VeRLm、Modal。

### 5.3 范式选型的量化对比

以"Llama-3.1-70B 推理、P50 50 tokens/s、日均 1 亿 token"为例：

| 方案 | 月成本（估） | P99 TTFT | 运维复杂度 |
|------|--------------|----------|------------|
| 物理机 + 自研 | $200K+ | 500ms | 高 |
| K8s + vLLM | $80K | 800ms | 中 |
| K8s + vLLM + PD 分离 | $50K | 300ms | 中高 |
| Modal Serverless | $120K | 1.2s（冷启动） | 低 |
| 阿里 PAI-EAS | $60K | 400ms | 低 |

成本/延迟/复杂度的三角取舍，是范式选型的核心。

## 六、底层原理

### 6.1 隔离机制演进

```
物理机: 硬件隔离（不同机器）
   ↓
虚拟机: hypervisor 拦截敏感指令（Intel VT-x）
   ↓
容器: namespace（进程可见性）+ cgroup（资源限制）
   ↓ 共享内核 = 隔离弱
MicroVM: 轻量级 VM（Firecracker 5MB 镜像，125ms 启动）
   ↓ 兼顾隔离与速度
AI 原生: GPU MIG（硬件级切分）+ namespace（进程隔离）
```

#### 隔离强度对比

| 机制 | 隔离强度 | 性能开销 | 启动时间 |
|------|----------|----------|----------|
| 物理机 | 最强 | 0 | 分钟 |
| hypervisor（VM） | 强 | 5-15% | 秒 |
| MicroVM（Firecracker） | 强 | 1-5% | 125ms |
| gVisor（用户态内核） | 中强 | 10-30%（syscall 密集型更慢） | 秒 |
| 容器（namespace） | 弱（共享内核） | <1% | 毫秒 |
| WASM | 中（沙箱） | <5% | 毫秒 |

AI 原生场景的隔离需求：
- **多租户推理**：不同客户的请求互不可见 → MicroVM 或 gVisor
- **Agent 代码执行**：用户代码不可信 → Firecracker / E2B
- **单租户多模型**：模型互不影响 → MIG + 容器

### 6.2 资源调度模型演进

#### 物理机调度

```
采购 → 上架 → 装系统 → 部署应用
周期: 周/月
粒度: 整机
```

#### VM 调度

```
VM 镜像模板 → 克隆 → 启动 → 分配 vCPU/vNIC
周期: 分钟
粒度: vCPU/GB
调度器: vCenter/OpenStack Nova
```

#### 容器调度（K8s）

```
Pod Spec → Scheduler 选节点 → kubelet 拉镜像 → 启动容器
周期: 秒
粒度: 毫核/MB
调度算法: predicates + priorities（1.27+ 默认 Scheduling Framework）
关键资源: cpu/memory/ephemeral-storage + extended resources
```

#### Serverless 调度

```
事件触发 → 控制面启动实例 → 加载函数 → 执行 → 销毁/保活
周期: 毫秒（热）/ 秒（冷）
粒度: 单请求
调度器: AWS Lambda Frontend、Knative Activator
关键问题: 冷启动
```

#### AI 原生调度

```
请求到达 → Router 选 GPU（基于 prefix 亲和性）→ 推理 → 流式返回
周期: token 级
粒度: 显存页/token
调度器: vLLM Router、SGLang Router、自研
关键问题: KV Cache 局部性、GPU 利用率、PD 分离
```

### 6.3 状态管理演进

```
物理机: 状态在本地磁盘（强一致但难迁移）
   ↓
VM: 状态在虚拟磁盘（可迁移但慢）
   ↓
容器: 状态外置（Volume + 外部存储）→ 无状态应用
   ↓
Serverless: 强制无状态 → 状态全部外置（Redis/DynamoDB）
   ↓
AI 原生: 状态回归（KV Cache 在 GPU 显存）→ 有状态推理
```

**AI 原生范式的状态回归**是反直觉的：Serverless 时代把状态全部外置，AI 原生又把状态（KV Cache）放回 GPU 显存。原因：

- KV Cache 大（Llama-70B 单请求 4K context ≈ 1.6GB）
- 显存带宽高（H100 3TB/s vs DDR5 100GB/s）
- 跨节点传输 KV Cache 慢（400Gbps IB 也只能传 50GB/s）

所以 AI 原生部署不能像 Serverless 那样"状态全外置"，必须考虑：
- **KV Cache 局部性**：同一会话路由到同一 GPU
- **KV Cache 复用**：prefix cache 跨请求共享
- **KV Cache 抢占**：高优请求抢占低优的 KV Cache
- **KV Cache 卸载**：低优请求的 KV Cache 卸载到 CPU 内存/磁盘

### 6.4 网络模型演进

| 范式 | 网络模型 | 典型延迟 |
|------|----------|----------|
| 物理机 | 物理网卡 + VLAN | 10-100μs |
| VM | vNIC + 虚拟交换机（OVS） | 50-200μs |
| 容器 | veth pair + bridge / CNI | 50-500μs（bridge） |
| Serverless | 共享网关 + MicroVM 网络 | 1-10ms（冷启动更高） |
| AI 原生 | RDMA（GPU Direct）+ NVLink | 1-10μs（节点内 NVLink） |

AI 原生场景的特殊网络需求：
- **GPU Direct RDMA**：GPU 显存直接网卡传输，绕过 CPU
- **NVLink**：节点内 GPU 互联，TP 并行必需
- **InfiniBand 400Gbps**：跨节点 TP 并行
- **流式连接长保持**：SSE/WebSocket 连接 30s-5min

## 八、常见陷阱与调优

### 8.1 陷阱 1：用容器思维做 AI 原生部署

**症状**：LLM 推理服务 QPS 上不去，P99 延迟波动大。

**根因**：
- 用 K8s Service round-robin 路由请求 → KV Cache 无法复用
- HPA on CPU → CPU 没满但 GPU 显存满了，不扩容
- 没开 continuous batching → 单请求串行 decode

**修复**：
```yaml
# 1. 用 vLLM Router 替代 K8s Service
# 2. HPA 指标改用 GPU 显存利用率
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: vllm-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: vllm
  minReplicas: 4
  maxReplicas: 32
  metrics:
  - type: Pods
    pods:
      metric:
        name: gpu_memory_utilization  # 自定义指标
      target:
        type: AverageValue
        averageValue: "85"
```

### 8.2 陷阱 2：Serverless GPU 冷启动失控

**症状**：Modal/Replicate 部署的 LLM 推理，首次请求 30s+。

**根因**：模型权重 GB 级，每次冷启动都从镜像仓库拉取。

**修复**：
- 启用快照恢复（Modal 的 `@app.function` 默认会缓存模型）
- 配置最小温热实例（Knative min-scale=1）
- 模型权重放本地 SSD（vLLM 的 `--model-path`）

### 8.3 陷阱 3：流式连接被负载均衡切断

**症状**：SSE 流式响应在 60s 后被 Nginx 切断。

**根因**：Nginx 默认 `proxy_read_timeout 60s`，流式推理超过 60s 就断。

**修复**：
```nginx
location /v1/chat/completions {
    proxy_pass http://vllm;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_buffering off;  # 关键：禁用缓冲
    proxy_read_timeout 600s;
    proxy_send_timeout 600s;
    # SSE 必须禁用 chunked encoding 缓冲
    chunked_transfer_encoding on;
}
```

### 8.4 陷阱 4：PD 分离后 KV Cache 传输成为瓶颈

**症状**：PD 分离后 TTFT 反而升高。

**根因**：Prefill 节点的 KV Cache 传到 Decode 节点，400Gbps IB 也只能传 50GB/s，单请求 KV Cache 1.6GB 传输 30ms+。

**修复**：
- 用 NVLink over NVSwitch（节点内 900GB/s）
- 用 GPU Direct RDMA（绕过 CPU）
- 局部性优先：同会话路由到同节点，避免传输

### 8.5 陷阱 5：范式错配的成本失控

**症状**：用 Serverless GPU 跑长稳态推理，成本是 K8s 的 3x。

**根因**：Serverless GPU 适合突发，长稳态用预留更便宜。

**修复**：
- 突发流量用 Serverless
- 稳态流量用 K8s + 预留实例
- 混合部署：base 用 K8s，peak 用 Serverless（Knative + KEDA）

### 8.6 调优 Checklist

- [ ] GPU 资源粒度（MIG/MPS vs 整卡）
- [ ] KV Cache 是否启用 prefix cache
- [ ] continuous batching 是否开启
- [ ] 流式连接超时是否足够（600s+）
- [ ] HPA 指标是否用 GPU 利用率
- [ ] PD 分离是否值得（小模型不必）
- [ ] 冷启动是否优化（快照/预热）
- [ ] 成本核算是否按 token 拆解

## 十一、面试速答

> 高频问题的一句话答案，便于面试快速响应。

**Q1: 什么是 AI 原生部署？和容器部署有什么本质区别？**

A: AI 原生部署以 GPU/显存为一级资源、KV Cache 为核心状态、token 为调度粒度、流式输出为协议。容器部署以 CPU/内存为资源、无状态、QPS 为调度粒度、一次性响应为协议。把容器范式套到 LLM 推理会导致 GPU 利用率低、KV Cache 无法复用、流式连接被切断。

**Q2: 部署范式演进的驱动力是什么？**

A: 在更细的时间粒度上分配更精确的资源。从物理机（年/整机）→ VM（小时/vCPU）→ 容器（秒/毫核）→ Serverless（毫秒/请求）→ AI 原生（token/显存页）。

**Q3: 为什么 LLM 推理是有状态的？KV Cache 为什么不能外置？**

A: KV Cache 是 prefill 阶段计算的注意力中间结果，单请求可达 1.6GB。显存带宽 3TB/s 远高于 DDR5 100GB/s，跨节点传输慢（400Gbps IB = 50GB/s）。所以 KV Cache 必须留在 GPU 显存，导致推理有状态，破坏无状态假设。

**Q4: PD 分离是什么？为什么需要？**

A: Prefill（首 token 计算）和 Decode（后续 token 生成）资源特征不同：Prefill 算力密集，Decode 显存密集。拆到不同集群分别优化，Prefill 用高算力卡（H100），Decode 用高显存密度卡（A10）。DistServe 论文证明 PD 分离可提升 goodput 4-7x。

**Q5: Serverless GPU 为什么不适合长稳态推理？**

A: Serverless GPU 按秒计费，单价是预留的 3-5x。长稳态推理用预留更便宜。Serverless GPU 适合突发流量（白天高、夜间零）。

**Q6: 什么是范式错配？举例。**

A: 用旧范式的思维做新范式部署。例：用 K8s Service round-robin 路由 LLM 请求，导致 KV Cache 无法复用；用 HPA on CPU 监控 GPU 推理，CPU 没满但 GPU 显存满了不扩容。

**Q7: 五代范式各自的隔离机制？**

A: 物理机（硬件隔离）、VM（hypervisor）、容器（namespace + cgroup，共享内核隔离弱）、Serverless（MicroVM 如 Firecracker）、AI 原生（GPU MIG + namespace）。

**Q8: TTFT 和 TPOT 分别是什么？为什么 LLM 关注两个延迟指标？**

A: TTFT（Time To First Token）首 token 延迟，由 prefill 决定；TPOT（Time Per Output Token）每 token 延迟，由 decode 决定。传统服务只有 P99 整体延迟，LLM 推理流式输出，用户感知首 token，所以 TTFT 单独优化。

**Q9: AI 原生部署的五个根本差异？**

A: 1) GPU 优先调度 2) 有状态推理（KV Cache）3) 流式输出 4) 长尾延迟敏感（TTFT/TPOT）5) token 计费。

**Q10: 部署演进中状态管理的反直觉现象？**

A: Serverless 时代把状态全部外置（Redis/DynamoDB），AI 原生又把状态（KV Cache）放回 GPU 显存。原因是 KV Cache 大、显存带宽高、跨节点传输慢，必须留在本地 GPU。

**答题要点**：
1. 分析流量特征：日均 1 亿 token ≈ 1157 token/s 平均，峰值假设 5x = 5800 token/s
2. 选 Llama-70B：单卡 25 token/s（vLLM 优化后），需要 230 张 H100（峰值）
3. 范式选型：
   - 稳态用 K8s + vLLM + PD 分离（利用率最优）
   - 突发用 Serverless GPU（弹性）
   - 混合：base 70% K8s，peak 30% Serverless
4. 成本估算：
   - K8s 预留 200 张 H100：$200K/月
   - Serverless 突发 30 张：$30K/月
   - 总 $230K/月
5. 备选：阿里 PAI-EAS / 字节 VeRLm 托管，省运维但锁定供应商

**加分项**：提成本/延迟/复杂度三角取舍，提具体厂商报价。

### 题 4（高级）：PD 分离架构的工程挑战与解决方案

**考点**：PD 分离的深度理解

**答题要点**：
1. **挑战 1：KV Cache 传输**
   - 单请求 KV Cache 1.6GB，400Gbps IB 传 30ms+
   - 解决：GPU Direct RDMA（绕过 CPU）、NVLink（节点内 900GB/s）
2. **挑战 2：负载均衡**
   - Prefill 短时高算力，Decode 长时低算力
   - 解决：独立伸缩、共享队列
3. **挑战 3：故障恢复**
   - Decode 节点宕机，KV Cache 丢失
   - 解决：KV Cache 持久化到 CPU 内存 / 跨节点副本
4. **挑战 4：路由决策**
   - 哪个 Prefill 节点配哪个 Decode 节点
   - 解决：基于 KV Cache 局部性 + 负载
5. **挑战 5：小模型不必**
   - 7B 以下模型 PD 分离开销大于收益
   - 解决：阈值判断（一般 70B+ 才值得 PD 分离）

**加分项**：提 DistServe / Splitwise 论文，提 DeepSeek 的 MoE + PD 分离实践。

### 题 5（高级）：设计一个支持多租户的 LLM 推理平台

**考点**：综合架构能力

**答题要点**：
1. **隔离**：每租户独立 MicroVM（Firecracker）跑 vLLM
2. **调度**：GPU MIG 切分（H100 切 7 个 1g.10gb 实例）
3. **路由**：prefix-aware router，KV Cache 跨请求复用
4. **配额**：每租户 token/s 限流，超额排队
5. **计费**：按 input/output token 分别计价
6. **监控**：每租户独立 dashboard，TTFT/TPOT/GPU 利用率
7. **弹性**：每租户独立 HPA，base + peak 混合
8. **安全**：模型权重不下载，Agent 代码执行隔离
9. **成本**：混部（在线 + 离线），夜间跑 batch 推理

**加分项**：提阿里 PAI-EAS / Modal / Replicate 的架构参考，提具体技术选型（Volcano + GPU Operator + 自研 Router）。

## 十三、故障复盘

### 13.1 案例 1：范式错配导致 GPU 利用率仅 15%

**事故背景**：2024 年某公司用 K8s + vLLM 部署 Llama-70B，GPU 利用率仅 15%，P99 TTFT 1.2s。

**现象**：
- QPS 上不去（单卡 3 token/s）
- GPU 利用率 15%
- 显存利用率 40%
- CPU 利用率 30%

**根因分析**：
1. 用 K8s Service round-robin 路由 → KV Cache 无法复用
2. HPA on CPU → CPU 30% 不扩容，但 GPU 显存已满
3. 没开 continuous batching → 单请求串行 decode
4. `--max-num-seqs=1` → 实际只批 1 个请求

**修复**：
```yaml
# 1. 开启 continuous batching
args:
- --max-num-seqs
- "256"
- --enable-prefix-caching
- --gpu-memory-utilization
- "0.9"

# 2. HPA 改用 GPU 显存利用率
metrics:
- type: Pods
  pods:
    metric: {name: gpu_memory_utilization}
    target: {type: AverageValue, averageValue: "85"}

# 3. 用 vLLM Router 替代 K8s Service（prefix-aware）
```

**效果**：
- GPU 利用率 15% → 65%
- 单卡 QPS 3 → 25 token/s
- P99 TTFT 1.2s → 350ms

**防范**：
- LLM 推理上线 checklist（continuous batching / prefix cache / 路由策略）
- 监控 GPU 利用率而非 CPU
- 性能基线测试（vLLM benchmark 脚本）

### 13.2 案例 2：Serverless GPU 冷启动导致 SLA 违约

**事故背景**：2024 年某创业公司用 Modal 部署 LLM 推理，夜间无流量 Scale-to-Zero，早晨流量来时冷启动 30s+，SLA 违约。

**现象**：
- 早晨 9 点流量高峰，首请求 30s+
- Modal 自动扩容，但模型加载耗时
- 用户大量超时投诉

**根因**：
1. Llama-70B 权重 140GB，从镜像仓库拉取慢
2. Modal 容器冷启动快（毫秒），但模型加载慢（分钟）
3. 没有预热策略

**修复**：
```python
# 1. 配置最小温热实例
@app.function(
    image=image,
    gpu="A100",
    min_containers=2,  # 至少保持 2 个温热实例
)
def infer(...):
    ...

# 2. 模型权重放本地 SSD（Modal Volume）
vol = modal.Volume.from_name("llama-weights")
@app.function(image=image, volumes={"/models": vol})
def infer(...):
    model = load_model("/models/llama-70b")

# 3. 定时预热
@modal.Cron("0 8 * * *")
def warmup():
    infer.remote("warmup")
```

**效果**：
- 冷启动 30s → 200ms（温热实例）
- 成本增加 30%（夜间保持 2 实例），但 SLA 兑现

**防范**：
- Serverless GPU 慎用 Scale-to-Zero
- 模型权重必须本地缓存
- 流量预测 + 定时预热

### 13.3 案例 3：PD 分离后 KV Cache 传输瓶颈

**事故背景**：2024 年某公司实施 PD 分离，TTFT 反而从 400ms 升到 600ms。

**现象**：
- Prefill 集群算力充足
- Decode 集群显存充足
- 但 TTFT 升高 50%

**根因**：
1. Prefill 节点 KV Cache 1.6GB 传到 Decode 节点
2. 用普通 TCP over 100Gbps 以太网，传输 30ms+
3. 加上 RDMA 配置错误，实际只有 10Gbps

**修复**：
```bash
# 1. 启用 GPU Direct RDMA
# /etc/modprobe.d/nvidia.conf
options nvidia NVreg_OpenRmEnableUnsupportedGpus=1

# 2. 验证 RDMA 拓扑
ibstat
nvidia-smi topo -m

# 3. vLLM 配置 KV Transfer
args:
- --kv-transfer-config
- '{"role": "producer", "kv_role": "producer", "kv_connector_module": "PyNcclConnector"}'
```

**效果**：
- KV Cache 传输 30ms → 5ms（GPU Direct RDMA）
- TTFT 600ms → 250ms

**防范**：
- PD 分离前先验证网络拓扑
- RDMA 配置 checklist
- 小模型不必 PD 分离（7B 以下开销大于收益）

### 13.4 案例 4：流式连接被 Nginx 切断

**事故背景**：2024 年某公司 LLM 推理服务，用户反馈"回复到一半就断了"。

**现象**：
- 短回复正常
- 长回复（>60s）在 60s 处被切断
- 客户端收到不完整流

**根因**：
1. Nginx `proxy_read_timeout 60s` 默认
2. SSE 流式响应超过 60s 被切断
3. Nginx `proxy_buffering on` 缓冲流式响应

**修复**：
```nginx
location /v1/chat/completions {
    proxy_pass http://vllm;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_buffering off;  # 关键
    proxy_read_timeout 600s;
    proxy_send_timeout 600s;
    chunked_transfer_encoding on;
}
```

**效果**：
- 长回复正常完成
- 用户投诉消失

**防范**：
- 流式服务 Nginx 配置 checklist
- 监控 SSE 连接断开率
- 客户端断线重连机制

### 13.5 案例 5：范式迁移导致预算超支 3x

**事故背景**：2025 年某公司从 K8s 迁移到 Serverless GPU，月成本从 $50K 涨到 $150K。

**现象**：
- 迁移后功能正常
- 但月账单翻 3 倍

**根因**：
1. 长稳态流量用 Serverless（按秒计费贵 3-5x）
2. 冷启动频繁（min-scale=0）
3. 没做流量分析就迁范式

**修复**：
- 稳态流量迁回 K8s（base 70%）
- 突发流量保留 Serverless（peak 30%）
- Knative + KEDA 实现混合伸缩

**效果**：
- 月成本 $150K → $60K
- SLA 不变

**防范**：
- 范式迁移前做流量特征分析
- 稳态 vs 突发分别选范式
- 成本监控告警
