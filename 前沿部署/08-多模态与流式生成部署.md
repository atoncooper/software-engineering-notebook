# 08 - 多模态与流式生成部署

> 多模态（VLM、Audio、Video）部署与纯文本 LLM 有显著差异：变长输入、跨模态 batch、流式输出。本章梳理多模态推理的特殊性、流式协议、batch 优化、生产实践。

## 三、直觉解释

### 3.1 多模态推理的挑战

```
文本 LLM:
  输入: token ids (固定维度)
  batch: 容易 (padding)

VLM (Vision-Language):
  输入: 图片 (变长) + 文本
  batch: 难 (图片大小不同, 视觉编码器输出变长)

Audio:
  输入: 音频帧 (流式) + 文本
  batch: 难 (音频长度不同)

Video:
  输入: 视频帧序列 (大量) + 文本
  batch: 极难 (视频长度差异大, 内存爆炸)
```

### 3.2 流式协议对比

```
SSE (Server-Sent Events):
  单向 (服务器 → 客户端)
  HTTP/1.1 chunked
  简单, OpenAI 兼容
  适合: LLM 文本流式

WebSocket:
  双向
  长连接
  复杂, 但灵活
  适合: 多模态交互, 实时反馈

gRPC streaming:
  双向流
  HTTP/2
  高效, 内部 RPC
  适合: 服务间通信
```

### 3.3 视频/音频的特殊性

```
视频推理:
  1 个视频 = N 帧 (每帧 1 张图)
  N 可能 100-1000+
  显存: N × 视觉编码器激活

  例: 1 分钟视频 (30fps) = 1800 帧
  每帧视觉编码: 1GB 激活
  总: 1.8TB (无法装下)

  方案:
  - 帧采样 (每秒 1 帧而非 30)
  - 分块处理 (chunked video)
  - 流式输出 (边处理边返回)
```

## 四、核心概念与架构

### 4.1 VLM 架构

```
VLM 推理流程:
  1. 图片 → 视觉编码器 (CLIP/SigLIP) → 视觉 token 序列
  2. 视觉 token + 文本 token → LLM → 输出

  例: LLaVA
    图片 (224×224) → CLIP → 576 视觉 token
    视觉 token + 文本 token → Llama → 回答

显存:
  视觉编码器: ~1GB (CLIP ViT-L)
  LLM: 标准权重
  视觉 token KV Cache: 576 × 2.62MB = 1.5GB (Llama-70B)
```

### 4.2 跨模态 batch

```
问题:
  请求1: 1 张图 + "描述图片"
  请求2: 4 张图 + "对比这些图"
  请求3: 0 张图 + "写首诗"

  视觉 token 数: 576, 2304, 0
  文本 token 数: 10, 20, 5

  难以 batch (视觉 token 数差异大)

方案 1: padding 到最大
  浪费显存 (请求3 padding 2304 个 0)

方案 2: 桶式 batch (按视觉 token 数分组)
  请求1 + 请求3 一组 (视觉 token ≤ 576)
  请求2 单独一组

方案 3: sequence parallelism
  视觉 token 切到多卡
```

### 4.3 SSE 流式实现

```python
# vLLM SSE 流式
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
import json

app = FastAPI()

@app.post("/v1/chat/completions")
async def chat(req: dict):
    if req.get("stream"):
        return StreamingResponse(
            stream_response(req),
            media_type="text/event-stream"
        )

async def stream_response(req):
    # 调用 vLLM 流式生成
    async for chunk in vllm_stream(req):
        data = {
            "choices": [{
                "delta": {"content": chunk},
                "finish_reason": None
            }]
        }
        yield f"data: {json.dumps(data)}\n\n"

    # 结束
    yield f"data: {json.dumps({'choices': [{'delta': {}, 'finish_reason': 'stop'}]})}\n\n"
    yield "data: [DONE]\n\n"
```

### 4.4 WebSocket 流式

```python
# WebSocket 双向流 (用于实时语音对话)
from fastapi import WebSocket

@app.websocket("/ws/chat")
async def ws_chat(ws: WebSocket):
    await ws.accept()
    try:
        while True:
            # 接收客户端消息 (可能是音频帧)
            msg = await ws.receive_json()

            if msg["type"] == "audio":
                # 流式接收音频
                audio_buffer.append(msg["data"])
            elif msg["type"] == "end":
                # 处理完整音频, 生成回复
                response = await process_audio(audio_buffer)

                # 流式返回文本
                async for chunk in stream_text(response):
                    await ws.send_json({
                        "type": "text_chunk",
                        "data": chunk
                    })

                # 流式返回音频 (TTS)
                async for audio_chunk in stream_tts(response):
                    await ws.send_json({
                        "type": "audio_chunk",
                        "data": audio_chunk
                    })

                await ws.send_json({"type": "end"})
    except WebSocketDisconnect:
        pass
```

### 4.5 视频流式处理

```python
# 视频分块处理
class VideoStreamer:
    def __init__(self, chunk_size=30):  # 每块 30 帧 (1 秒)
        self.chunk_size = chunk_size

    async def process_video(self, video_stream):
        chunk = []
        async for frame in video_stream:
            chunk.append(frame)
            if len(chunk) >= self.chunk_size:
                # 处理一块
                result = await self.process_chunk(chunk)
                yield result  # 流式返回
                chunk = []

        if chunk:  # 处理剩余
            yield await self.process_chunk(chunk)

    async def process_chunk(self, frames):
        # 视觉编码
        visual_tokens = self.vision_encoder(frames)
        # LLM 推理
        response = self.llm.generate(visual_tokens)
        return response
```

## 六、底层原理

### 6.1 视觉编码器瓶颈

```
CLIP ViT-L 处理 1 张 224×224 图:
  - patch embedding: 224/14 = 16, 16×16 = 256 patches
  - transformer: 24 层
  - 输出: 256 × 1024 token

LLaVA 把 256 视觉 token 投影到 LLM 空间:
  - 576 token (LLaVA-1.5)
  - 2880 token (LLaVA-1.6 高分辨率)

显存:
  视觉编码器激活: 1-2GB/图
  视觉 token KV Cache: 576 × 2.62MB = 1.5GB (Llama-70B)

batch 多图:
  4 张图 = 6GB 视觉 token KV Cache
  16 张图 = 24GB (单卡显存大半)
```

### 6.2 流式延迟分解

```
VLM 流式响应延迟:
  1. 图片上传: 100ms (1MB 图)
  2. 视觉编码: 200ms
  3. Prefill (视觉 + 文本): 300ms
  4. 首 token 生成: 50ms
  TTFT = 100 + 200 + 300 + 50 = 650ms

  5. 后续 token: 25ms each
  100 token: 2500ms

  总: 650 + 2500 = 3150ms
```

### 6.3 视频 token 压缩

```
1 分钟视频 (30fps) = 1800 帧
每帧 CLIP: 256 token
总: 1800 × 256 = 460K token

LLM 上下文: 460K (远超 32K 限制)

压缩方案:
  1. 帧采样: 1fps 而非 30fps → 60 帧 → 15K token
  2. token 池化: 4 frame → 1 token → 3.75K token
  3. 关键帧提取: 10 帧 → 2.5K token
  4. 长视频分块: 5 个 12 秒块, 各 3K token
```

# OpenAI 兼容 VLM 调用
import openai
import base64

client = openai.OpenAI(base_url="http://vllm-vlm:8000/v1", api_key="dummy")

# 编码图片
def encode_image(path):
    with open(path, "rb") as f:
        return base64.b64encode(f.read()).decode()

# 多模态流式
stream = client.chat.completions.create(
    model="llava-v1.6-mistral-7b-hf",
    messages=[{
        "role": "user",
        "content": [
            {"type": "text", "text": "描述这张图"},
            {"type": "image_url", "image_url": {
                "url": f"data:image/jpeg;base64,{encode_image('test.jpg')}"
            }}
        ]
    }],
    stream=True,
    max_tokens=500
)

for chunk in stream:
    delta = chunk.choices[0].delta
    if delta.content:
        print(delta.content, end="", flush=True)

## 八、常见陷阱与调优

### 8.1 陷阱 1：图片上传慢

**症状**：VLM 推理 TTFT 高。

**根因**：base64 编码 + 大图上传慢。

**修复**：
- 客户端压缩图片（resize 到 1024×1024）
- 用 multipart/form-data 而非 base64
- CDN 加速图片上传

### 8.2 陷阱 2：多图 batch 显存爆炸

**症状**：4 图请求 OOM。

**根因**：视觉 token KV Cache 占用大。

**修复**：
- `--limit-mm-per-prompt image=4` 限制
- 降 max-num-seqs

### 8.3 陷阱 3：WebSocket 连接超时

**症状**：长对话 WebSocket 断开。

**根因**：Nginx `proxy_read_timeout 60s`。

**修复**：调到 3600s。

### 8.4 陷阱 4：视频超长 context

**症状**：视频 token 超 max-model-len。

**根因**：1 分钟视频原始 token 460K。

**修复**：帧采样 + token 压缩。

### 8.5 调优 Checklist

- [ ] 图片压缩（客户端）
- [ ] limit-mm-per-prompt 限制
- [ ] max-num-seqs 适配多图
- [ ] Nginx 流式 + WebSocket 配置
- [ ] 视频帧采样
- [ ] 监控视觉编码器耗时

### 10.1 多模态 vs 纯文本

| 维度 | 纯文本 LLM | VLM | 视频 LLM |
|------|------------|-----|----------|
| 输入 | token | token + 图片 | token + 视频 |

## 十一、面试速答

**Q1: VLM 推理的瓶颈？**

A: 视觉编码器（图片→token）+ 视觉 token 的 prefill。1 张图 576 视觉 token，相当于 576 文本 token 的 prefill 开销。

**Q2: SSE vs WebSocket？**

A: SSE 单向（服务器→客户端），HTTP/1.1 chunked，简单，OpenAI 兼容。WebSocket 双向，长连接，复杂但灵活。LLM 文本流式用 SSE，多模态实时交互用 WebSocket。

**Q3: 多图 batch 怎么做？**

A: 桶式分组（按视觉 token 数分组）。`--limit-mm-per-prompt image=4` 限制单请求图数。

**Q4: 视频推理如何控制显存？**

A: 帧采样（1fps 而非 30fps）+ token 池化（4 frame→1 token）+ 分块处理（30 秒一块）+ 流式输出。

**Q5: VLM 流式 TTFT 分解？**

A: 图片上传 100ms + 视觉编码 200ms + prefill 300ms + 首 token 50ms = 650ms。
