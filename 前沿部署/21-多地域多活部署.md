# 21 - 多地域多活部署

> 单集群是 SPOD, 单地域是 SPOF, 单云是 SPOC。多地域多活是规模与可靠性的终极形态: 蚂蚁 LDC 单元化、字节 Dorado 全局路由、Google Borg 多区域调度。本章梳理多活层次、单元化架构、全局流量调度、数据一致性、故障切换, 以及大厂 LLM 推理平台的跨地域部署实践。

## 二、问题定义与边界

### 2.1 解决什么

- **可用性**: 单地域故障不影响服务
- **低延迟**: 用户就近接入
- **容量**: 单地域装不下, 多地域分担
- **合规**: 数据驻留 (GDPR/数据出境)
- **容灾**: 自然灾害/大规模故障

### 2.2 不解决什么

- 不覆盖单集群高可用（k8s 模块）
- 不深入分布式一致性（分布式系统 模块）
- 不覆盖混沌工程（22 章）

## 三、直觉解释

### 3.1 多活层次

```
冷备 (Cold Standby):
  - 备地域无流量, 仅备份数据
  - RPO: 小时级 (备份周期)
  - RTO: 小时-天级 (拉起服务)
  - 成本: 低 (仅数据存储)
  - 适用: 非核心业务

温备 (Warm Standby):
  - 备地域有服务, 无流量
  - 数据准实时同步
  - RPO: 分钟级
  - RTO: 分钟级 (切流量)
  - 成本: 中 (服务待命)
  - 适用: 中等业务

热备 (Hot Standby):
  - 备地域有服务, 部分流量
  - 数据实时同步
  - RPO: 秒级
  - RTO: 秒级
  - 成本: 高
  - 适用: 核心业务

双活 (Active-Active):
  - 两地域同时服务
  - 数据双向同步
  - RPO: 接近 0
  - RTO: 接近 0
  - 成本: 极高
  - 适用: 关键业务

多活 (Multi-Active):
  - 多地域同时服务
  - 单元化隔离
  - RPO: 0 (单元内)
  - RTO: 0 (单元内)
  - 成本: 极高
  - 适用: 超大规模 (蚂蚁/字节/阿里)
```

### 3.2 RPO/RTO 概念

```
RPO (Recovery Point Objective):
  - 数据丢失容忍度
  - RPO=0: 不丢任何数据
  - RPO=1h: 最多丢 1 小时数据

RTO (Recovery Time Objective):
  - 服务恢复时间
  - RTO=0: 不中断
  - RTO=5min: 5 分钟内恢复

SLA 等级:
  - 99.9%: 年停机 8.76h
  - 99.99%: 年停机 52.6min
  - 99.999%: 年停机 5.26min (5个9)
  - 99.9999%: 年停机 31.5s (6个9)

金融级: RPO=0, RTO<1min (5个9)
互联网级: RPO<1min, RTO<5min (4个9)
一般业务: RPO<1h, RTO<1h (3个9)
```

### 3.3 多活的核心矛盾

```
CAP 定理 (分布式系统):
  - C (一致性): 所有节点同时看到相同数据
  - A (可用性): 每个请求都得到响应
  - P (分区容错): 网络分区时仍工作

多活场景:
  - 必须保证 P (网络分区不可避免)
  - 在 C 与 A 之间取舍
  
  强一致多活 (CP): 跨地域事务, 高延迟
  最终一致多活 (AP): 本地写, 异步同步, 短期不一致
  单元化多活: 数据按用户分片, 单元内强一致, 跨单元最终一致

LLM 推理场景:
  - 推理无状态, 易多活
  - 模型权重: 跨地域分发
  - 用户会话: 跨地域难 (KV Cache 不共享)
  - 解决: 会话保持 (sticky) 或会话重建
```

## 四、核心概念与架构

### 4.1 单元化架构（LDC）

```
LDC (Logic Data Center):
  蚂蚁金服自研, 把业务拆分为多个"单元"
  
核心思想:
  - 用户按 ID 分片 (e.g. user_id % 100)
  - 每个单元服务一部分用户
  - 单元内: 完整服务 + 完整数据 (该分片)
  - 跨单元: 异步消息, 最终一致

架构:
  ┌────────────────────────────────────────┐
  │           全局路由 (Gateway)            │
  │  按 user_id 路由到对应单元              │
  └────────────────┬───────────────────────┘
                   │
        ┌──────────┼──────────┐
        ▼          ▼          ▼
  ┌─────────┐ ┌─────────┐ ┌─────────┐
  │ Unit A  │ │ Unit B  │ │ Unit C  │
  │ (0-33)  │ │ (34-66) │ │ (67-99) │
  │ 服务+DB │ │ 服务+DB │ │ 服务+DB │
  └─────────┘ └─────────┘ └─────────┘
  
单元内:
  - 强一致 (单机事务)
  - 完整服务栈
  - 独立部署
  
跨单元:
  - 异步消息 (MQ)
  - 最终一致
  - 跨单元调用避免

优势:
  - 单元故障仅影响部分用户
  - 单元内强一致 (无需跨地域事务)
  - 横向扩展: 加单元即可
  - 故障隔离: 爆炸半径小

挑战:
  - 跨单元数据同步复杂
  - 全局查询困难
  - 单元规划需精细
```

### 4.2 字节 Dorado 全局路由

```
Dorado (字节自研多活):
  - 全球多活
  - 按用户路由
  - 数据双向同步

架构:
  ┌──────────────────────────────────────┐
  │        Global Traffic Manager        │
  │  - 智能路由 (延迟/容量/故障)          │
  │  - DNS / HTTP DNS                    │
  └────────────────┬─────────────────────┘
                   │
        ┌──────────┼──────────┐
        ▼          ▼          ▼
  ┌─────────┐ ┌─────────┐ ┌─────────┐
  │ 北京    │ │ 新加坡  │ │ 美西    │
  │ Region  │ │ Region  │ │ Region  │
  │         │ │         │ │         │
  │ Pod×N   │ │ Pod×N   │ │ Pod×N   │
  │ DB主    │ │ DB主    │ │ DB主    │
  │  (CN)  │ │  (SG)   │ │  (US)   │
  └─────────┘ └─────────┘ └─────────┘
        │          │          │
        └──────────┼──────────┘
                   │
              数据同步层
              (DTS / Binlog)
```

### 4.3 全局流量调度

```
流量入口层次:

L1: DNS (Global Traffic Manager)
  - 基于 GeoDNS / HTTP DNS
  - 按地域/运营商路由
  - 故障切换 (地域级)
  
L2: Anycast (BGP)
  - 同一 IP 多地域宣告
  - BGP 自动选路
  - 全球负载均衡
  - Cloudflare/AWS Route53 支持

L3: 全局 LB (应用层)
  - 按延迟/容量/健康路由
  - 跨地域流量切分
  - 适合 LLM 推理 (按模型/用户)

L4: Service Mesh
  - 跨集群流量管理
  - 金丝雀 (地域级)
  - 故障转移
```

### 4.4 数据一致性方案

```
方案 1: 强一致 (CP)
  - 跨地域事务 (2PC / 3PC)
  - 高延迟 (跨地域 RTT 100-300ms)
  - 适用: 金融交易
  - 工具: Spanner / TiDB (跨地域)

方案 2: 最终一致 (AP)
  - 本地写, 异步同步
  - 短期不一致
  - 冲突解决 (LWW / CRDT / 业务逻辑)
  - 适用: 用户内容, 评论

方案 3: 单元化 (分片)
  - 数据按用户分片
  - 单元内强一致
  - 跨单元异步
  - 适用: 大规模用户数据

方案 4: 读写分离
  - 主地域写, 备地域读
  - 异步复制
  - 切换: 提升备地域为主
  - 适用: 读多写少

LLM 推理场景:
  - 推理无状态: 易多活
  - 模型权重: 多地域分发 (对象存储)
  - 用户数据 (历史): 主从同步, 读就近
  - 会话 (KV Cache): 单地域内, 不跨地域
```

### 4.5 CRDT（Conflict-free Replicated Data Type）

```
CRDT (无冲突复制数据类型):
  - 多地域并发写, 自动解决冲突
  - 数学保证最终一致
  - 无需协调 (无锁)

类型:
  - G-Counter (单调递增): 各节点累加, 合并取 max
  - PN-Counter (可增可减): 两个 G-Counter (增/减)
  - LWW-Register (Last-Write-Wins): 时间戳最新者胜
  - OR-Set (Set): 添加/删除, 添加优先
  - RGA (Replicated Growable Array): 协同编辑

应用:
  - 协同文档: Yjs, Automerge
  - Redis CRDT: 跨地域 Redis
  - Riak: NoSQL 数据库

LLM 场景:
  - 用户配置: CRDT (多地域并发改)
  - 模型路由表: CRDT
  - 计数器 (请求数): G-Counter
```

## 六、底层原理

### 6.1 跨地域网络延迟

```
跨地域 RTT (Round Trip Time):
  北京-上海: 30ms
  北京-新加坡: 70ms
  北京-美西: 150ms
  北京-欧洲: 200ms
  美西-欧洲: 100ms

对系统设计影响:
  - 强一致事务: 跨地域 + 2PC, 高延迟
  - 异步同步: 不阻塞本地写
  - 读写分离: 读本地, 写主地域

LLM 推理场景:
  - 用户接入: 就近地域 (低 TTFT)
  - 模型权重: 多地域副本 (对象存储 + CDN)
  - 推理日志: 异步同步到中心 (不阻塞)
  - 用户历史: 主从复制 (读本地, 写主)
```

### 6.2 一致性模型

```
Linearizability (线性一致):
  - 所有操作按某全局顺序执行
  - 强一致, 跨地域高延迟
  - Spanner: TrueTime + 2PC

Sequential Consistency (顺序一致):
  - 所有节点看到相同顺序
  - 不要求实时
  - 比 Linearizability 弱

Causal Consistency (因果一致):
  - 因果相关的操作有序
  - 无因果的可并发
  - Cassandra 用版本向量

Eventual Consistency (最终一致):
  - 短期不一致, 最终趋同
  - 跨地域最优
  - Dynamo / Riak

LLM 推理选型:
  - 推理本身: 强一致 (单地域)
  - 用户配置: 最终一致 (跨地域)
  - 计数器: CRDT (G-Counter)
  - 会话: 单地域 (不跨)
```

### 6.3 故障切换（Failover）

```
故障切换流程:

阶段 1: 故障检测 (Detection)
  - 健康检查 (HTTP/TCP)
  - 心跳超时 (3-5 次)
  - 检测时间: 10-30s

阶段 2: 决策 (Decision)
  - 人工确认 / 自动切换
  - 评估影响范围
  - 选目标地域 (容量/延迟)

阶段 3: 流量切换 (Traffic Switch)
  - DNS TTL 降低 (60s)
  - GTM 切换权重
  - 客户端重连

阶段 4: 数据切换 (Data Switch)
  - 提升备地域为主
  - 数据校验
  - 反向同步准备

阶段 5: 恢复 (Recovery)
  - 故障地域修复
  - 数据回补
  - 流量回切

故障切换 RTO:
  - 自动: 30s-5min
  - 人工: 5-30min
  - 数据校验: 1-24h

LLM 推理切换:
  - 推理无状态, 切换快
  - 模型权重已多地域, 无需迁移
  - KV Cache 丢失, 用户重连
```

### 6.4 容量规划

```
多活容量规划:
  - 单地域容量: N
  - 多活 N+1: 总容量 N×(地域数-1), 任一地域故障仍够
  - 多活 N+M: M 个备份地域, 容错更强

LLM 推理容量:
  - 单地域: 1000 H100, 100K QPS
  - 双活: 2 × 1000 = 2000 H100, 任一故障剩 100K QPS
  - 三活: 3 × 500 = 1500 H100, 任一故障剩 100K QPS (省 25%)

成本权衡:
  - 多活: 总成本高, 但利用率高
  - N+1: 成本中, 利用率中
  - 冷备: 成本低, 利用率低 (备地域闲置)

LLM 场景:
  - 备地域: 可跑训练/批量推理 (不浪费)
  - Spot 实例: 备地域用 Spot 降本
  - 模型权重: 多地域对象存储 (便宜)
```

### 7.2 全局路由（GeoDNS + 智能路由）

```python
# global_router.py
from fastapi import FastAPI, Request
from typing import Dict
import hashlib

app = FastAPI()

REGIONS = {
    'cn-east-1': { 'endpoint': 'https://cn.llm.example.com', 'capacity': 100 },
    'cn-north-1': { 'endpoint': 'https://cn.llm.example.com', 'capacity': 100 },
    'us-west-1': { 'endpoint': 'https://us.llm.example.com', 'capacity': 80 },
    'sg-1': { 'endpoint': 'https://sg.llm.example.com', 'capacity': 60 },
}

@app.get("/route")
def route(request: Request, user_id: str):
    """智能路由: 综合地域/容量/延迟."""
    client_region = request.headers.get('x-client-region', 'cn-east-1')

    # 1. 优先就近
    candidates = [client_region]

    # 2. 同地域备选
    same_geo = {
        'cn': ['cn-east-1', 'cn-north-1'],
        'us': ['us-west-1'],
        'asia': ['sg-1', 'cn-east-1']
    }
    for geo, regions in same_geo.items():
        if client_region.startswith(geo):
            candidates.extend(regions)

    # 3. 全局备选
    candidates.extend(list(REGIONS.keys()))

    # 4. 过滤健康 + 容量
    healthy = [r for r in candidates if is_healthy(r) and get_capacity(r) > 0]
    if not healthy:
        raise HTTPException(503, "All regions unavailable")

    # 5. 选最优 (延迟 + 容量)
    best = min(healthy, key=lambda r: latency(client_region, r) - capacity(r) * 0.1)

    return {
        'endpoint': REGIONS[best]['endpoint'],
        'region': best
    }

def is_healthy(region: str) -> bool:
    # 健康检查
    return True

def get_capacity(region: str) -> int:
    return REGIONS[region]['capacity']

def latency(from_r: str, to_r: str) -> int:
    # 跨地域延迟 (ms)
    matrix = {
        ('cn-east-1', 'cn-east-1'): 1,
        ('cn-east-1', 'cn-north-1'): 30,
        ('cn-east-1', 'us-west-1'): 150,
        # ...
    }
    return matrix.get((from_r, to_r), 100)
```

## 八、常见陷阱与调优

### 8.1 陷阱 1：跨地域事务慢

**症状**：跨地域事务 200ms+, 用户体验差。

**修复**：
- 避免跨地域事务, 数据按用户分片
- 单元化: 数据就近, 跨单元异步
- 用最终一致替代强一致

### 8.2 陷阱 2：DNS 切换慢

**症状**：故障切换后, 客户端仍访问故障地域 (DNS 缓存)。

**修复**：
- DNS TTL 降到 60s
- 用 HTTP DNS (绕过运营商 DNS)
- 客户端定期刷新 DNS
- 长连接: 切换时主动断开

### 8.3 陷阱 3：数据冲突

**症状**：双写双活, 同一记录在两地域并发改, 同步时冲突。

**修复**：
- CRDT: 数学保证无冲突
- 单元化: 数据按用户分片, 单元内强一致
- LWW: 时间戳最新者胜
- 业务规则解决 (如转账: 借贷平衡)

### 8.4 陷阱 4：KV Cache 丢失

**症状**：用户跨地域路由, KV Cache 丢失, 重算贵。

**修复**：
- 会话保持 (Sticky): 同一用户始终同地域
- KV Cache 同步 (RDMA, 实验)
- 接受重算 (短会话影响小)

### 8.5 陷阱 5：故障切换误判

**症状**：网络抖动误判故障, 切换后原地域实际正常, 双主冲突。

**修复**：
- 多数派决策 (3 地域投票)
- 切换前确认 (健康检查 + 人工)
- 切换后只读模式 (避免双写)
- Fencing (原主隔离)

### 8.6 调优 Checklist

- [ ] 数据按用户分片 (单元化)
- [ ] 跨地域异步同步 (非事务)
- [ ] DNS TTL < 60s
- [ ] HTTP DNS 绕过运营商
- [ ] 会话保持 (KV Cache)
- [ ] 容量 N+1 (任一地域故障仍够)
- [ ] 备地域跑批量 (不闲置)
- [ ] 故障切换演练 (定期)
- [ ] 数据校验 (切换前后)
- [ ] 监控跨地域延迟/同步延迟

### 9.1 案例 1：蚂蚁 LDC 单元化

**背景**：蚂蚁金服双十一, 单集群不够, 多活单元化。

**背景**：TikTok 全球用户, 多活架构。

**方案**：
- 全球 30+ 地域
- 用户就近接入
- 数据双向同步 (DTS)
- 智能路由 (容量/延迟)

**规模**：
- 日活: 1B+
- 跨地域同步: PB 级/天
- 故障切换: 自动, 分钟级

### 9.3 案例 3：Google Spanner 全球数据库

**背景**：Google 全球数据库, 强一致。

**方案**：
- TrueTime (原子钟)
- 跨地域 2PC
- Paxos 多副本
- 全球强一致

**特点**：
- 跨地域事务: ~100ms
- 全球任何位置读一致
- 可用性: 99.999%

### 9.4 案例 4：阿里云多活架构

**背景**：阿里云 ECS/SLB/OSS 多地域多可用区。

**方案**：
- 多地域: 北京/上海/深圳/新加坡/美西
- 多可用区: 每地域 3+ AZ
- 数据库: RDS 主备 + 跨地域只读
- 对象存储: OSS 跨地域复制

**适用**：企业上云的多活方案。

### 9.5 案例 5：OpenAI 推理多地域

**背景**：OpenAI ChatGPT 全球服务 (推测)。

**推测方案**：
- 多地域部署: 美西/美东/欧洲
- 用户就近接入 (低延迟)
- 模型权重多地域副本
- 流量调度: 按容量 + 延迟

**特点**：
- 推理无状态, 易多活
- KV Cache: 单地域, 会话保持
- 全球 P99 TTFT: < 1s

## 十一、面试速答

**Q1: 多活的层次?**

A: 冷备 (无流量, RPO 小时)、温备 (有服务无流量, RPO 分钟)、热备 (部分流量, RPO 秒)、双活 (双地域同时服务, RPO 0)、多活 (多地域多单元, RPO 0 单元内)。成本与可用性递增。

**Q2: 单元化架构 (LDC) 是什么?**

A: 蚂蚁自研, 把用户按 ID 分片到多个"单元", 单元内完整服务+数据 (该分片), 单元内强一致 (单机事务), 跨单元异步 (最终一致)。优势: 单元故障仅影响部分用户, 横向扩展加单元, 爆炸半径小。挑战: 跨单元同步复杂, 全局查询困难。

**Q3: 跨地域数据一致性怎么解决?**

A: 1) 强一致 (Spanner, 跨地域 2PC, 高延迟); 2) 最终一致 (本地写, 异步同步, CRDT 解决冲突); 3) 单元化 (数据按用户分片, 单元内强一致); 4) 读写分离 (主地域写, 备地域读)。LLM 场景: 推理无状态易多活, 用户配置 CRDT, 会话单地域。

**Q4: 故障切换流程?**

A: 1) 检测 (健康检查, 10-30s); 2) 决策 (人工/自动, 选目标地域); 3) 流量切换 (DNS TTL 60s, GTM 权重); 4) 数据切换 (备升主, 校验); 5) 恢复 (修复原主, 数据回补, 回切)。RTO: 自动 30s-5min, 人工 5-30min。

**Q5: LLM 推理怎么多活?**

A: 1) 推理无状态, 易多活; 2) 模型权重多地域副本 (对象存储); 3) 用户就近接入 (低 TTFT); 4) 会话保持 (Sticky, KV Cache 不跨地域); 5) 用户历史主从同步 (读本地); 6) 智能路由 (容量+延迟); 7) 故障切换自动 (推理无状态, 切换快)。

## 十二、综合面试题

### 题 1（中级）：设计 LLM 推理双活方案

**答题要点**：

1. **架构**:
   - 双地域: 北京 + 美西
   - 每地域: K8s 集群 + vLLM 推理
   - 模型权重: OSS 跨地域复制

2. **流量路由**:
   - GeoDNS: 中国用户 → 北京, 美国用户 → 美西
   - 故障切换: DNS TTL 60s, 切权重

3. **数据同步**:
   - 用户历史: TiDB 跨地域主从
   - 实时日志: Kafka 跨地域异步
   - 配置: CRDT (多地域并发改)

4. **会话保持**:
   - 同一用户固定地域 (避免 KV Cache 丢失)
   - JWT token 内嵌 region

5. **故障切换**:
   - 健康检查: HTTP /health, 30s 内 3 次失败
   - 自动切: DNS 权重 100% 到备地域
   - RTO: < 1min

6. **容量**:
   - 单地域: 1000 H100, 100K QPS
   - 双活: 2 × 1000 = 2000 H100, 任一故障仍 100K QPS
   - 利用率: 70% (备地域跑批量)

### 题 2（高级）：单元化 LLM 推理平台

**答题要点**：

1. **挑战**:
   - 全球用户: 100M+
   - 单地域装不下
   - 跨地域延迟: 100-200ms
   - KV Cache 不跨地域

2. **单元化方案**:
   - 用户按 ID 分片: hash(user_id) % 100
   - 单元: 服务一组用户分片
   - 单元内: 完整推理服务 + 用户数据
   - 跨单元: 仅异步消息

3. **单元规划**:
   - 单元大小: 1M 用户 / 单元
   - 单元数: 100 (覆盖 100M 用户)
   - 地域分布: 全球 10+ 地域, 每地域 5-10 单元

4. **路由**:
   - GTM: 按用户 ID 路由到单元所在地域
   - 本地路由: 单元选择
   - 故障切换: 单元级 (仅影响 1M 用户)

5. **数据**:
   - 用户历史: 单元内 TiDB
   - 跨单元: 异步消息 (会话历史共享)
   - 模型权重: 多地域对象存储

6. **运营**:
   - 单元扩容: 加 Pod
   - 加单元: 新地域 + 数据迁移
   - 故障演练: 单元级注入

7. **收益**:
   - 爆炸半径: 1M 用户 (vs 全局故障)
   - RTO: 0 (单元内自洽)
   - 横向扩展: 加单元

## 十三、故障复盘

### 13.1 案例 1：AWS S3 美东大故障 (2017)

**背景**：2017 年 AWS S3 美东大故障, 大量互联网服务受影响。

**根因**：运维误执行命令, 删除过多服务器, 主地域不可用。

**影响**：Slack/Trello/Quora 等数小时不可用。

**修复**：
- AWS 加强操作流程
- 客户反思多地域/多云
- 跨地域备份成标准

**防范**：关键服务必须多地域部署, 不能依赖单一地域。

### 13.2 案例 2：Cloudflare BGP 路由故障 (2020)

**背景**：2020 年 Cloudflare BGP 配置错误, 全球流量异常。

**根因**：BGP 路由表配置错误, 部分流量黑洞。

**影响**：全球 50% 互联网受影响 27 分钟。

**修复**：回滚 BGP 配置。

**防范**：BGP 配置变更需自动化校验 + 灰度。

### 13.3 案例 3：某公司双活数据冲突

**背景**：2024 年某公司双活数据库, 同一记录两地并发改, 同步时冲突。

**根因**：未做单元化, 双写双活导致冲突。

**修复**：
- 改单元化: 数据按用户分片, 单元内强一致
- 或 CRDT: 数学保证无冲突
- 紧急: 人工解决冲突数据

**防范**：双活必须单元化或 CRDT, 避免双写冲突。

### 13.4 案例 4：故障切换误判双主

**背景**：2025 年某公司网络抖动, 备地域误判主故障, 自动切换, 形成双主。

**根因**：未做多数派决策, 单方面切换。

**修复**：
- 多数派决策 (3 地域投票)
- Fencing: 原主强制只读
- 数据校验后合并

**防范**：故障切换必须多数派决策 + Fencing 防双主。

### 13.5 案例 5：KV Cache 跨地域丢失

**背景**：2024 年某公司 LLM 推理多活, 用户跨地域路由, KV Cache 丢失, TTFT 飙升。

**根因**：未做会话保持, 用户每次路由到最近地域。

**修复**：
- 会话保持: JWT 内嵌 region
- 同一会话始终同地域
- 接受首次跨地域 (冷启动)

**防范**：LLM 推理多活必须会话保持, 避免 KV Cache 跨地域。
