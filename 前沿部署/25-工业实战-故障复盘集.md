## 二、LLM 推理故障复盘

### 2.1 案例 1: KV Cache OOM 雪崩

**时间**: 2024 年某公司

**背景**:
- LLM 推理服务 (Llama-70B), 8×H100 集群
- 高峰期 10K QPS, 平均请求 4K context
- 部分用户使用 32K context 长请求

**现象**:
- 高峰期所有 vLLM 实例 OOM, 服务全不可用
- 重启后再次 OOM, 雪崩

**根因分析**:
1. 长请求 (32K context) 单请求 KV Cache 占 84GB
2. vLLM 默认抢占式调度, 但抢占开销大
3. 多个长请求并发, KV Cache 总量超显存
4. vLLM OOM, 触发 Pod 重启
5. 重启后流量回来, 再次 OOM

**修复**:
1. **请求长度限制**: 单请求 max_context_length=16K
2. **抢占式调度优化**: 启用 `--preemption-mode=swap` (KV Cache 换 CPU)
3. **流量优先级**: 付费用户优先, 免费用户长请求限流
4. **监控**: KV Cache 使用率 > 80% 告警, 主动限流

**防范**:
- 容量规划: 显存 = (模型权重 + KV Cache 上限)
- 压测: 模拟长请求场景
- 熔断: KV Cache 满时拒绝新长请求

**经验**: KV Cache 是 LLM 推理的核心资源, 必须显式管理。

### 2.2 案例 2: PD 分离后 TTFT 飙升

**时间**: 2025 年某公司

**背景**:
- 推理服务从单集群迁 PD 分离架构
- Prefill 集群 (32 卡) + Decode 集群 (8 卡)
- KV Cache 跨节点 RDMA 传输

**现象**:
- 迁移后 TTFT P99 从 500ms → 1.5s (3x 退化)
- 用户投诉首字延迟明显

**根因分析**:
1. KV Cache 跨节点传输耗时 200-500ms
2. RDMA 配置未优化 (默认参数)
3. Prefill 与 Decode 集群网络跨交换机
4. 大 batch 时 KV Cache 传输量大 (batch × KV size)

**修复**:
1. **网络优化**: Prefill 与 Decode 同交换机 (低延迟)
2. **RDMA 调优**: GPU Direct RDMA (绕过 CPU)
3. **KV Cache 压缩**: MLA 或量化 (FP8) 减少传输量
4. **本地复用**: 部分 Decode 在 Prefill 节点本地 (短请求)

**防范**:
- PD 分离架构需评估 KV 传输开销
- 同交换机部署 (网络拓扑感知)
- 监控 KV 传输延迟

**经验**: PD 分离不是银弹, KV 传输开销可能抵消收益。

### 2.3 案例 3: GPU ECC 错误导致输出乱码

**时间**: 2024 年某公司

**背景**:
- LLM 推理服务, 8×H100 集群
- 部分请求返回乱码 (token 完全无意义)

**现象**:
- 0.1% 请求乱码
- 同一 prompt 多次推理结果不同
- 错误率与特定 GPU 关联

**根因分析**:
1. GPU 出现 ECC 错误 (硬件故障)
2. H100 自动纠正单 bit 错误, 双 bit 错误未隔离
3. GPU 持续运行, 输出错误结果
4. 推理服务未检测 GPU 健康

**修复**:
1. **GPU 健康检查**: 启动时跑诊断 (DCGM)
2. **运行时监控**: ECC 错误率 > 阈值自动隔离
3. **GPU 隔离**: 故障 GPU 标记 unschedulable
4. **结果校验**: 推理输出 perplexity 异常检测

**防范**:
- 部署前 GPU 诊断 (DCGM diagnose)
- 运行时 ECC 监控 + 自动隔离
- 输出质量校验 (perplexity / 语义相似度)
- 多副本冗余 (不同 GPU)

**经验**: GPU 硬件故障会导致静默错误, 必须主动检测。

### 2.4 案例 4: 流式断连引发用户重连风暴

**时间**: 2024 年某公司

**背景**:
- LLM 推理服务, 流式 SSE 输出
- 网络抖动, 部分连接断开

**现象**:
- 网络抖动后 5 分钟内 QPS 翻 5 倍
- 服务过载, 错误率飙升

**根因分析**:
1. 客户端默认重试策略: 立即重连, 最多 10 次
2. 网络抖动导致大量连接断开
3. 客户端同时重连, QPS 飙升
4. 服务过载, 又导致新连接断开, 雪崩

**修复**:
1. **客户端规范**: 指数退避 + 抖动 (jitter)
2. **服务端 429**: 过载时拒绝, 客户端退避
3. **重连限流**: per-user 重连频率限制
4. **WebSocket 替代 SSE**: 自动重连 + 心跳

**防范**:
- 客户端 SDK 规范 (指数退避)
- 服务端过载保护 (429 + Retry-After)
- 重连限流
- 流式协议选择 (WebSocket vs SSE)

**经验**: 流式服务的重连风暴比普通 API 更危险。

### 2.5 案例 5: 模型加载失败导致冷启动失控

**时间**: 2025 年某公司

**背景**:
- Serverless GPU 推理, Scale-to-Zero
- 流量来时启动新实例

**现象**:
- 早晨流量高峰, 100+ 实例同时冷启动
- 模型仓库过载, 加载失败
- 冷启动雪崩, 服务不可用 30 分钟

**根因分析**:
1. 模型仓库 (HuggingFace Hub) 速率限制
2. 100+ 实例同时下载 70B 模型 (140GB)
3. 模型仓库返回 429, 下载失败
4. 实例启动失败, 流量堆积, 更多实例启动

**修复**:
1. **模型权重本地缓存**: 每节点预下载 + Volume 挂载
2. **模型仓库镜像**: 内部 OSS 镜像, 无速率限制
3. **预热**: 早晨流量前预启动实例
4. **限流**: 冷启动并发数限制

**防范**:
- 模型权重不依赖外部仓库 (本地缓存)
- Scale-to-Zero 谨慎 (关键服务保持温热)
- 预热策略 (流量预测)
- 冷启动限流 (避免雪崩)

**经验**: Serverless LLM 必须解决模型加载问题, 不能依赖外部仓库。

## 三、Agent 系统故障复盘

### 3.1 案例 6: 多 Agent 死锁

**时间**: 2024 年某公司

**背景**:
- Agent 系统, 多 Agent 协作 (Planner + Executor + Reviewer)
- 工具调用: web_search, code_exec, db_query

**现象**:
- 部分 Agent 任务无限等待
- 日志显示工具调用循环依赖
- 用户请求超时

**根因分析**:
1. Planner 调用 Executor, Executor 调用 web_search
2. web_search 失败, Executor 重试
3. Reviewer 等待 Executor 完成, 持有锁
4. Planner 等待 Reviewer, 形成循环依赖
5. 死锁, 无限等待

**修复**:
1. **超时机制**: 每工具调用 30s 超时, Agent 链路 5min 超时
2. **环检测**: Agent 调用图检测环, 中断
3. **失败快速返回**: 工具失败不重试, 上层决策
4. **资源释放**: 超时后强制释放锁

**防范**:
- 所有工具调用必须超时
- Agent 拓扑校验 (无环)
- 链路级超时 + 死锁检测
- 监控 Agent 等待时间

**经验**: Agent 系统的死锁比传统并发更复杂, 必须主动检测。

### 3.2 案例 7: 沙箱逃逸 (Firecracker 配置错误)

**时间**: 2025 年某公司

**背景**:
- AI Agent 代码执行沙箱 (Firecracker)
- 用户提交 Python 代码, 沙箱内执行

**现象**:
- 红队测试发现可读取宿主 /etc/passwd
- 进一步可获取宿主 root

**根因分析**:
1. Firecracker rootfs 配置错误, 挂载了宿主 /etc
2. 沙箱内代码可访问宿主文件
3. 进一步利用内核漏洞提权

**修复**:
1. **rootfs 隔离**: 独立 ext4 镜像, 不挂载宿主
2. **网络隔离**: 沙箱无网络 (或仅必要 endpoint)
3. **能力降级**: seccomp + capabilities drop
4. **审计**: 记录沙箱内 syscall, 异常告警

**防范**:
- 沙箱配置安全 review (定期红队)
- 最小权限原则 (网络/文件/能力)
- 多层防御 (沙箱 + seccomp + AppArmor)
- 监控沙箱内异常行为

**经验**: 沙箱配置错误是常见安全漏洞, 必须定期红队测试。

### 3.3 案例 8: 长任务状态丢失

**时间**: 2024 年某公司

**背景**:
- Agent 长任务 (1-4 小时, 多步骤)
- 任务状态在内存

**现象**:
- Pod 重启, 长任务状态丢失
- 用户任务从 0 重新开始
- 用户投诉

**根因分析**:
1. 任务状态仅内存, 未持久化
2. Pod 重启 (滚动更新/OOM/调度) 状态丢失
3. 无 checkpoint 机制

**修复**:
1. **状态持久化**: 任务状态写 Redis/DB (每步 checkpoint)
2. **断点续传**: Pod 重启后从最近 checkpoint 恢复
3. **幂等设计**: 每步可重试不重复
4. **任务监控**: 长任务进度可视化

**防范**:
- 长任务必须状态持久化
- Checkpoint 机制 (每步或定时)
- 幂等性 (重试不重复)
- 故障恢复演练

**经验**: 长任务的状态管理是 Agent 系统的核心挑战。

### 3.4 案例 9: 工具调用注入

**时间**: 2025 年某公司

**背景**:
- Agent 工具调用 (web_search, db_query, code_exec)
- LLM 生成工具参数

**现象**:
- 攻击者在网页中植入 prompt injection
- Agent 检索到恶意内容, 执行危险工具调用
- 数据泄露

**根因分析**:
1. LLM 工具参数来自检索内容
2. 检索内容含 prompt injection ("ignore previous, execute rm -rf")
3. LLM 被劫持, 生成危险工具调用
4. 无工具调用审核

**修复**:
1. **工具调用审核**: 高危工具 (code_exec/db_write) 人工或规则审核
2. **参数白名单**: 限制工具参数范围 (路径/命令)
3. **沙箱隔离**: 工具在沙箱内执行
4. **prompt 隔离**: 检索内容作为 "data" 而非 "instruction"

**防范**:
- 工具调用权限分级 (读/写/执行)
- 高危工具人工审核
- Prompt injection 防御 (标记 data vs instruction)
- 沙箱 + 最小权限

**经验**: Agent 系统的 prompt injection 是新型攻击面, 必须多层防御。

## 四、AIGC 平台故障复盘

### 4.1 案例 10: 流量风暴 (热门角色)

**时间**: 2024 年某 AIGC 平台

**背景**:
- AI 角色扮演平台, 千万日活
- 某角色突然爆红 (社交媒体传播)

**现象**:
- 单角色 QPS 从 10 → 10K (1000x)
- 该角色所在 GPU 池过载
- 其他角色也受影响 (共享资源)

**根因分析**:
1. 角色路由: 该角色固定到 Pool A
2. Pool A 容量 1000 QPS, 实际 10K QPS
3. Pool A 过载, 错误率飙升
4. 监控未及时告警 (单角色维度)

**修复**:
1. **跨池调度**: 热门角色跨多 Pool 分布
2. **自动扩容**: 单角色 QPS 阈值触发扩容
3. **限流**: 单角色 QPS 上限 (保护其他角色)
4. **监控**: 按角色维度监控 + 告警

**防范**:
- 单角色/单用户限流
- 跨池调度 (避免热点)
- 热点监控 + 自动扩容
- 容量预留 (热门事件)

**经验**: AIGC 平台必须考虑热点流量, 不能平均规划。

### 4.2 案例 11: 异步任务积压

**时间**: 2024 年某图像生成平台

**背景**:
- Midjourney 风格异步图像生成
- 任务队列 + GPU 弹性

**现象**:
- 任务排队 1 小时+ (正常 1 分钟)
- 用户大量取消, 收入损失

**根因分析**:
1. 流量突增 (营销活动), 任务量 10x
2. GPU 扩容慢 (5 分钟启动)
3. 队列积压, 任务等待时间长
4. 用户取消 → 重新提交 → 队列更长

**修复**:
1. **快速扩容**: 预启动池 (温热实例)
2. **任务优先级**: 付费 > 免费, 短任务 > 长任务
3. **队列监控**: 积压 > 阈值告警
4. **流量预测**: 营销活动前预扩容

**防范**:
- 预启动实例池 (降低扩容延迟)
- 任务优先级 + 公平调度
- 队列积压监控 + 告警
- 流量预测 + 预扩容
- 用户通知 (排队时间预估)

**经验**: 异步任务平台的扩容延迟是核心痛点, 必须预热池化。

### 4.3 案例 12: 冷启动失控

**时间**: 2025 年某 Serverless AIGC 平台

**背景**:
- Serverless GPU + Scale-to-Zero
- 多模型路由 (按 prompt 类型)

**现象**:
- 模型切换频繁, 冷启动雪崩
- 单实例冷启动 30s, 用户超时

**根因分析**:
1. 多模型路由: 不同 prompt 路由到不同模型
2. 每模型独立 Scale-to-Zero
3. 模型切换 = 冷启动
4. 用户连续请求不同模型, 反复冷启动

**修复**:
1. **模型合并**: 多模型共享权重 (LoRA)
2. **多模型实例**: 单实例加载多模型
3. **预测路由**: 历史用户模型偏好, 预加载
4. **保持温热**: 高频模型常驻

**防范**:
- 多模型路由需评估冷启动
- LoRA 共享权重 (切换 < 1s)
- 模型偏好预测 + 预加载
- 高频模型常驻

**经验**: 多模型 Serverless 必须解决冷启动, LoRA 是关键。

### 4.4 案例 13: 流式断连 + 重新生成

**时间**: 2024 年某 LLM 应用

**背景**:
- 流式 SSE 输出
- 网络抖动, 连接断开

**现象**:
- 用户重新提交相同 prompt
- 服务重新生成 (KV Cache 未命中)
- 成本翻倍

**根因分析**:
1. 流式断开后, 已生成内容未保存
2. 用户重新提交, 服务从 0 生成
3. KV Cache 已释放, 重新计算

**修复**:
1. **结果缓存**: 已生成内容缓存 (按 prompt hash)
2. **断点续传**: 用户重连后从断点继续
3. **KV Cache 持久化**: 短期内重连复用 KV
4. **客户端缓冲**: 已接收内容保留

**防范**:
- 流式结果缓存
- 断点续传机制
- KV Cache 短期持久化 (5min)
- 客户端断线重连策略

**经验**: 流式断连不能让用户重新生成, 必须断点续传。

### 4.5 案例 14: 多模态 batch 不均衡

**时间**: 2025 年某多模态平台

**背景**:
- 多模态推理 (文字 + 图像)
- 跨模态 batch

**现象**:
- 文字请求快, 图像请求慢
- 同 batch 内文字请求等待图像, 吞吐下降

**根因分析**:
1. 跨模态 batch: 文字 + 图像混合
2. 图像 token 多 (1000+), 文字 token 少 (100+)
3. batch 内最长请求决定耗时
4. 文字请求被图像拖慢

**修复**:
1. **按模态分桶**: 文字 batch + 图像 batch 分开
2. **长度分桶**: 同 batch 内 token 数接近
3. **动态 batch**: 连续 batching + 动态调整
4. **超时切分**: 长等待时强制切分

**防范**:
- 多模态 batch 策略 (分桶)
- 长度分桶 (减少最长等待)
- 动态 batch (continuous batching)
- 监控 batch 利用率

**经验**: 多模态推理的 batch 优化比纯文本复杂, 必须分桶。

## 五、基础设施故障复盘

### 5.1 案例 15: 网络分区导致多活失效

**时间**: 2024 年某公司

**背景**:
- 双活架构 (北京 + 美西)
- 数据库主从同步

**现象**:
- 网络分区, 双地域失联
- 各自升主, 形成双主
- 数据冲突

**根因分析**:
1. 网络分区, 北京与美西失联
2. 两地都认为对方故障, 各自升主
3. 双主期间各自接受写请求
4. 网络恢复后, 数据冲突

**修复**:
1. **多数派决策**: 3 地域投票 (避免单方面升主)
2. **Fencing**: 原主强制只读
3. **数据校验**: 网络恢复后冲突检测 + 修复
4. **CRDT**: 关键数据用 CRDT (无冲突)

**防范**:
- 多活必须多数派决策 (3 地域)
- Fencing 防双主
- 数据冲突检测 + 修复机制
- CRDT 解决双写冲突

**经验**: 多活的双主问题比单主故障更严重, 必须多数派。

### 5.2 案例 16: GitOps 漂移导致配置不一致

**时间**: 2025 年某公司

**背景**:
- ArgoCD GitOps 管理 1000+ 应用
- selfHeal=false (手动 Sync)

**现象**:
- 部分集群配置与 Git 不一致
- 故障时找不到真实配置

**根因分析**:
1. 工程师 kubectl edit 直改集群
2. selfHeal=false, ArgoCD 不自动纠正
3. 长期积累, 漂移严重
4. 紧急时按 Git 配置操作, 实际集群不同

**修复**:
1. **selfHeal=true**: 自动纠正漂移
2. **禁止 kubectl edit**: OPA 策略禁止
3. **定期审计**: 对比 Git vs 集群
4. **文化**: 任何变更必须经 Git

**防范**:
- GitOps 必须 selfHeal=true
- 禁止手动改集群 (OPA)
- 定期漂移审计
- 团队培训 (Git 唯一可信源)

**经验**: GitOps 的价值在于"Git 即真相", 漂移是灾难。

### 5.3 案例 17: 混沌实验失控

**时间**: 2024 年某公司

**背景**:
- ChaosMesh 混沌实验
- 实验: 杀 50% Pod

**现象**:
- 实验期间服务不可用 10 分钟
- 影响真实用户

**根因分析**:
1. 实验设计: 直接 50% (未渐进)
2. 稳态监控未配置, 无自动终止
3. 业务时段实验, 影响用户

**修复**:
1. **渐进实验**: 1% → 5% → 25% → 50%
2. **稳态监控**: 错误率 > 5% 自动终止
3. **业务时段**: 仅低峰期首次
4. **爆炸半径**: 仅测试命名空间

**防范**:
- 混沌实验必须渐进
- 稳态假设 + 自动终止
- 低峰期首次, 灰度放大
- 爆炸半径控制

**经验**: 混沌工程的价值在于"可控故障", 失控就是事故。

## 六、故障复盘通用模式

### 6.1 常见根因分类

```
1. 容量规划不足 (30%)
   - KV Cache OOM
   - GPU 资源不足
   - 队列积压

2. 网络问题 (20%)
   - 网络分区
   - 延迟飙升
   - 带宽不足

3. 配置错误 (20%)
   - 沙箱配置
   - GitOps 漂移
   - 限流阈值

4. 硬件故障 (10%)
   - GPU ECC 错误
   - 磁盘故障
   - 内存故障

5. 软件缺陷 (10%)
   - 死锁
   - 内存泄漏
   - 算法错误

6. 人为操作 (10%)
   - 误操作
   - 流程缺失
   - 培训不足
```

### 6.2 修复模式

```
紧急修复 (灭火):
  - 回滚
  - 限流/降级
  - 重启
  - 切换备地域

根因修复 (根治):
  - 代码 fix
  - 配置调整
  - 容量扩容
  - 架构优化

防范 (避免重复):
  - 监控告警
  - 自动化测试
  - 流程规范
  - 团队培训
  - 混沌演练
```

### 6.3 复盘文化

```
复盘原则:
  - 对事不对人 (blameless)
  - 找根因, 不止于表面
  - 改进项追踪到完成
  - 知识沉淀 (文档/培训)

复盘流程:
  1. 24h 内初评 (紧急)
  2. 1 周内详细复盘
  3. 改进项 + 责任人 + 截止日期
  4. 月度 review 进度
  5. 季度总结 (避免重复)

输出:
  - 故障报告 (时间线/根因/修复/防范)
  - 改进项追踪表
  - 知识库更新
  - 培训材料
```

## 七、面试速答

**Q1: 踩过最严重的 LLM 推理故障?**

A: KV Cache OOM 雪崩。高峰期长请求 (32K context) 挤占 KV Cache, vLLM OOM, Pod 重启, 流量回来再次 OOM。修复: 请求长度限制 + 抢占式调度优化 (swap to CPU) + 流量优先级 + KV 监控告警。防范: 容量规划显式管理 KV, 压测长请求场景。

**Q2: Agent 系统的故障特点?**

A: 1) 死锁 (多 Agent 循环依赖); 2) 沙箱逃逸 (配置错误); 3) 长任务状态丢失 (未持久化); 4) Prompt injection (工具调用劫持)。比传统系统更复杂, 必须超时 + 环检测 + 状态持久化 + 工具调用审核。

**Q3: 流式断连怎么处理?**

A: 1) 客户端指数退避 (避免重连风暴); 2) 服务端 429 + Retry-After; 3) 结果缓存 (断点续传); 4) KV Cache 短期持久化 (重连复用); 5) WebSocket 替代 SSE (自动重连 + 心跳); 6) 重连限流。

**Q4: 多活的双主问题怎么避免?**

A: 1) 多数派决策 (3 地域投票, 避免单方面升主); 2) Fencing (原主强制只读); 3) CRDT (关键数据无冲突); 4) 数据冲突检测 + 修复; 5) 网络恢复后校验。比单主故障更严重, 必须多数派。

**Q5: 怎么避免故障重复发生?**

A: 1) 复盘 (blameless, 找根因); 2) 改进项追踪到完成; 3) 监控告警覆盖; 4) 自动化测试 (含混沌); 5) 流程规范; 6) 团队培训; 7) 季度总结避免重复。复盘文化是 SRE 的核心。

## 八、综合面试题

### 题 1（中级）：LLM 推理服务的故障应急预案

**答题要点**：

1. **监控告警**:
   - TTFT P99 > 1s
   - 错误率 > 1%
   - KV Cache 使用率 > 80%
   - GPU 利用率 > 95%
   - 队列长度 > 100

2. **应急分级**:
   - P0 (全员): 服务不可用
   - P1 (核心团队): 错误率 > 5%
   - P2 (值班): 单实例异常

3. **应急措施**:
   - 限流 (per user / global)
   - 降级 (大模型 → 小模型)
   - 扩容 (HPA + 预热池)
   - 切换 (备地域)
   - 回滚 (模型版本)

4. **沟通**:
   - 内部: Slack #incident
   - 用户: 状态页 + 邮件
   - 升级: 30 分钟无缓解升级 P0

5. **复盘**:
   - 24h 初评
   - 1 周详细复盘
   - 改进项追踪

### 题 2（高级）：从故障复盘看 LLM 平台架构演进

**答题要点**：

1. **第一阶段 (单集群)**:
   - 故障: KV OOM, 单点故障
   - 改进: 多副本 + 容量规划

2. **第二阶段 (PD 分离)**:
   - 故障: KV 传输开销, 网络依赖
   - 改进: 网络拓扑感知, KV 压缩

3. **第三阶段 (多地域)**:
   - 故障: 双主冲突, 流量切换慢
   - 改进: 多数派决策, 自动切换

4. **第四阶段 (端云协同)**:
   - 故障: 端侧 OOM, 路由错误
   - 改进: 智能路由, 降级机制

5. **演进原则**:
   - 故障驱动架构演进
   - 每次故障后改进架构
   - 混沌工程验证
   - 持续优化
