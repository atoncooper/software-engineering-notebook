# 06 - 模型量化与压缩部署

> 量化是 LLM 推理降本增效的核心技术。从 FP16 到 FP8/INT8/INT4，显存减半乃至 1/4，吞吐提升 1.5-2x。但量化伴随精度损失，如何选型是工程关键。
>
> 本章梳理量化算法谱系（GPTQ/AWQ/SmoothQuant/GGUF/EXL2）、硬件支持（H100 FP8/AMD MI300/Intel AMX）、精度评估、生产实践。

## 三、直觉解释

### 3.1 为什么需要量化

**问题**：Llama-70B FP16 需要 140GB 显存，单卡装不下。

```
Llama-70B 显存需求:
- FP32: 280GB (4 卡 H100)
- FP16: 140GB (2 卡 H100)
- BF16: 140GB (2 卡 H100)
- FP8:  70GB  (1 卡 H100)
- INT8: 70GB  (1 卡 H100)
- INT4: 35GB  (1 卡 H100, 显存富余)
```

**量化收益**：
1. 显存减半乃至 1/4，单卡可装大模型
2. 显存带宽减半，decode 速度提升 1.5-2x
3. 成本下降 50-75%

### 3.2 量化的本质

把浮点数（FP16）映射到低精度整数（INT8/INT4）。

```
FP16 范围: [-65504, 65504]
INT8 范围: [-128, 127]
INT4 范围: [-8, 7]

量化公式 (对称):
  q = round(x / scale)
  scale = max(abs(x)) / 127 (INT8)

反量化:
  x_dequant = q × scale
```

**精度损失来源**：
1. 舍入误差（round）
2. 截断误差（超出范围）
3. 离散化（连续值变离散）

### 3.3 量化粒度

```
per-tensor: 全张量一个 scale
  优点: 简单, 开销小
  缺点: 精度差 (不同 channel 分布不同)

per-channel: 每个通道一个 scale
  优点: 精度好
  缺点: 开销大

per-group: 每 N 个连续元素一个 scale (如 N=128)
  优点: 精度与开销平衡
  缺点: 实现复杂
```

### 3.4 量化时机

```
PTQ (Post-Training Quantization):
  训练后量化, 不需要重训
  简单, 但精度可能损失

QAT (Quantization-Aware Training):
  训练时模拟量化, 微调
  精度好, 但需要训练资源
```

LLM 量化基本都用 PTQ（模型太大，QAT 代价高）。

## 四、核心概念与架构

### 4.1 量化算法谱系

| 算法 | 开发方 | 核心思想 | 优势 | 劣势 |
|------|--------|----------|------|------|
| GPTQ | ICLR 2023 | Hessian-based 逐层量化 | 精度好 | 量化慢（小时级） |
| AWQ | MIT | 激活感知, 保护重要权重 | 精度好, 量化快 | 仅支持 INT4 |
| SmoothQuant | MIT | 激活平滑, 减小权重方差 | INT8 优秀 | 不支持 INT4 |
| GGUF | llama.cpp | 自定义格式, 多精度 | CPU 友好 | 性能不如专用 |
| EXL2 | ExLlamaV2 | 混合精度, 2-8 bit | 灵活 | 兼容性差 |
| FP8 | NVIDIA | 硬件原生 FP8 | 速度最快 | 仅 H100+ |

### 4.2 GPTQ 原理

**核心**：基于 Hessian 矩阵的逐层量化，最小化量化误差。

```
1. 选一层 (如 Linear)
2. 计算该层的 Hessian (二阶导数)
3. 逐列量化权重:
   - 选当前列
   - 量化为 INT4
   - 用 Hessian 信息更新未量化列, 补偿误差
4. 重复直到全层量化
```

**特点**：
- 精度好（perplexity +0.5%）
- 量化慢（70B 模型 2 小时）
- 主流支持（vLLM、TRT-LLM、LMDeploy）

### 4.3 AWQ 原理

**核心**：激活感知量化，保护"重要"权重。

```
观察: 不是所有权重同等重要
  - 激活值大的 channel 对应的权重重要
  - 量化这些权重会损失精度

方案:
  1. 分析校准数据, 找激活值大的 channel
  2. 对这些 channel 的权重缩放 (放大)
  3. 量化 (缩放后的权重占 INT4 更多范围)
  4. 反量化时缩放回来
```

**特点**：
- 精度好（与 GPTQ 相当）
- 量化快（70B 模型 10 分钟）
- 仅支持 INT4
- 主流支持

### 4.4 SmoothQuant 原理

**核心**：激活平滑，减小权重方差。

```
问题: 激活值范围大 (有的 0.01, 有的 100)
      权重范围小 (基本 [-1, 1])
      per-tensor INT8 量化激活损失大

方案: 把激活的"难度"转移到权重
  1. 找激活值大的 channel
  2. 除以平滑因子 s (缩小激活)
  3. 权重乘以 s (放大权重, 但权重范围小, 影响小)
  4. 量化平滑后的激活和权重

效果: 激活和权重都适合 INT8 量化
```

**特点**：
- INT8 量化最优
- 不支持 INT4
- 量化快
- 主流支持

### 4.5 FP8 量化

**核心**：H100 原生支持 FP8（E4M3/E5M2），硬件加速。

```
FP8 格式:
  E4M3: 1 符号 + 4 指数 + 3 尾数 (范围小, 精度高)
  E5M2: 1 符号 + 5 指数 + 2 尾数 (范围大, 精度低)

LLM 推理用 E4M3 (前向, 精度重要)

优势:
  - H100 原生支持, 硬件加速 2x
  - 比 INT8 精度好 (浮点 vs 定点)
  - 量化简单 (无需 calibration)

劣势:
  - 仅 H100+ 支持 (A100 不支持)
  - 显存只减半 (vs INT4 的 1/4)
```

### 4.6 GGUF 格式

**核心**：llama.cpp 自定义格式，支持多精度（Q2_K 到 F16）。

```
GGUF 量化等级:
  F16: 全精度
  Q8_0: 8 bit (per-block)
  Q4_0: 4 bit (per-block)
  Q4_K: 4 bit 混合 (重要层用 6 bit)
  Q2_K: 2 bit (极低精度)

优势:
  - CPU 推理友好 (SIMD 优化)
  - 内存映射加载 (mmap)
  - 多平台 (x86/ARM/Apple Silicon)

劣势:
  - 性能不如专用 (vLLM/TRT-LLM)
  - 适合本地/边缘, 不适合生产 GPU
```

### 4.7 精度对比表

| 精度 | 显存 (Llama-70B) | 硬件要求 | 精度损失 | 速度 |
|------|------------------|----------|----------|------|
| FP32 | 280GB | 任意 | 0% | 1x |
| FP16 | 140GB | 任意 GPU | 0% | 2x |
| BF16 | 140GB | A100+ | 0% | 2x |
| FP8 | 70GB | H100+ | <1% | 3x |
| INT8 | 70GB | 任意 GPU | 1-3% | 3x |
| INT4 | 35GB | 任意 GPU | 3-10% | 4x |

### 5.4 精度评估

```python
# Perplexity 评估
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer

def evaluate_perplexity(model_path, dataset="wikitext"):
    model = AutoModelForCausalLM.from_pretrained(model_path, torch_dtype=torch.float16, device_map="auto")
    tokenizer = AutoTokenizer.from_pretrained(model_path)

    # 加载测试集
    from datasets import load_dataset
    test = load_dataset("wikitext", "wikitext-2-raw-v1", split="test")
    encodings = tokenizer("\n\n".join(test["text"]), return_tensors="pt")

    # 计算 perplexity
    import torch.nn.functional as F
    max_length = 2048
    stride = 512
    nlls = []
    for i in range(0, encodings.input_ids.size(1), stride):
        begin_loc = max(i + stride - max_length, 0)
        end_loc = min(i + stride, encodings.input_ids.size(1))
        trg_len = i + stride - begin_loc
        input_ids = encodings.input_ids[:, begin_loc:end_loc].to(model.device)
        with torch.no_grad():
            outputs = model(input_ids, labels=input_ids)
            nlls.append(outputs.loss * trg_len)

    ppl = torch.exp(torch.stack(nlls).sum() / end_loc)
    return ppl.item()

# 对比
print("FP16:", evaluate_perplexity("meta-llama/Llama-3.1-70B"))      # 5.32
print("FP8:", evaluate_perplexity("Llama-3.1-70B-FP8"))               # 5.35
print("INT8:", evaluate_perplexity("Llama-3.1-70B-SmoothQuant"))      # 5.42
print("INT4 AWQ:", evaluate_perplexity("Llama-3.1-70B-AWQ"))          # 5.48
print("INT4 GPTQ:", evaluate_perplexity("Llama-3.1-70B-GPTQ"))        # 5.50
```

## 六、底层原理

### 6.1 量化的数学

**对称量化**：
```
q = round(x / scale)
scale = max(abs(x)) / (2^(bits-1) - 1)

例: x = [1.2, -0.5, 3.8, -2.1], INT8
  max(abs) = 3.8
  scale = 3.8 / 127 = 0.03
  q = [40, -17, 127, -70]
```

**非对称量化**：
```
q = round((x - zero_point) / scale)
scale = (max(x) - min(x)) / (2^bits - 1)
zero_point = min(x)

例: x = [1.2, 0.5, 3.8, 2.1], INT8
  min=0.5, max=3.8
  scale = (3.8-0.5)/255 = 0.0129
  zero_point = 0.5
  q = [54, 0, 255, 124]
```

### 6.2 GPTQ 的 Hessian

```
目标: 最小化量化误差
  min ||WX - QX||^2
  W: 权重, X: 输入, Q: 量化权重

GPTQ 用 Hessian 矩阵 H = X X^T 引导量化顺序:
  1. 计算 H
  2. 选 H 最小的列先量化 (误差小)
  3. 量化后, 更新剩余列补偿误差
  4. 逐列进行
```

### 6.3 AWQ 的激活感知

```
观察: 不同 channel 的激活值差异大
  channel 1: 激活值 [0.1, 0.2, 0.15]  (小)
  channel 2: 激活值 [50, 80, 60]      (大)

量化 channel 2 误差大 (相对激活值)

方案: 缩放 channel 2 的权重
  W' = W * s  (s > 1)
  量化 W' (相对误差小)
  反量化: W = W' / s

  但前向时:
  y = W * x
  y = (W' / s) * x = W' * (x / s)
  → 也缩放激活 x / s

  实际: 对应激活值大的 channel, 缩小激活, 放大权重
```

### 6.4 FP8 的硬件实现

H100 FP8 单元：
- Tensor Core 支持 FP8 矩阵乘法
- 比 FP16 快 2x（理论 1979 TFLOPS vs 989 TFLOPS）
- 自动转换（FP8 ↔ FP16/BF16）

```
H100 算力:
  FP32: 67 TFLOPS
  TF32: 495 TFLOPS
  BF16: 989 TFLOPS
  FP8:  1979 TFLOPS (2x BF16)
  INT8: 1979 TOPS
  INT4: 3958 TOPS
```

### 6.5 量化对推理速度的影响

```
Llama-70B 单卡 H100 (TP=4):

FP16:
  权重 35GB/卡
  decode 1 token 读 35GB
  H100 带宽 3TB/s
  理论: 35/3000 = 11.7ms/token
  实际: 25ms (含 attention 等开销)

FP8:
  权重 17.5GB/卡
  理论: 17.5/3000 = 5.8ms/token
  实际: 15ms (1.67x 加速)

INT8 (SmoothQuant):
  权重 17.5GB/卡
  理论: 5.8ms
  实际: 16ms (1.56x, 比 FP8 略慢, 因 dequant 开销)

INT4 (AWQ):
  权重 8.75GB/卡
  理论: 2.9ms
  实际: 10ms (2.5x, 但精度损失)
```

## 八、常见陷阱与调优

### 8.1 陷阱 1：小模型量化精度差

**症状**：7B 模型 INT4 量化后输出乱码。

**根因**：小模型容量小，量化损失相对大。

**修复**：7B 用 FP16/INT8，70B+ 才用 INT4。

### 8.2 陷阱 2：FP8 在 A100 不支持

**症状**：A100 上启用 FP8 报错。

**根因**：FP8 是 H100+ 才有的硬件特性。

**修复**：A100 用 INT8（SmoothQuant）。

### 8.3 陷阱 3：校准数据不当

**症状**：AWQ 量化后 perplexity 暴涨。

**根因**：校准数据与目标领域不匹配。

**修复**：用目标领域的文本做校准（如代码模型用代码）。

### 8.4 陷阱 4：KV Cache 量化与权重不匹配

**症状**：FP8 权重 + FP16 KV Cache，显存没省多少。

**根因**：KV Cache 占显存比例大（长 context 场景）。

**修复**：权重和 KV Cache 同时量化（`--quantization fp8 --kv-cache-dtype fp8`）。

### 8.5 调优 Checklist

- [ ] 大模型（70B+）用 FP8/INT4
- [ ] 小模型（7B 以下）用 FP16/INT8
- [ ] H100 用 FP8，A100 用 INT8
- [ ] 校准数据匹配目标领域
- [ ] 量化后 perplexity 评估
- [ ] 下游任务评估
- [ ] KV Cache 同步量化
- [ ] 性能对比（量化 vs 非量化）

**结论**：
- H100 用 FP8（精度损失 < 1%，速度 +56%）
- A100 用 INT8 SmoothQuant
- 显存极度紧张用 INT4 AWQ

### 9.2 案例 1：DeepSeek V3 的 FP8 量化

**背景**：DeepSeek-V3 671B，FP16 需要 1.3TB 显存（16 卡 H100）。

**方案**：
- FP8 量化（权重 + KV Cache）
- 单节点 8×H100 80GB = 640GB
- FP8 后 671B 需要 ~700GB（含 KV Cache），刚好

**效果**：
- 单节点推理 V3
- 吞吐 60K tokens/s
- 成本 $0.27/M token

### 9.3 案例 2：Llama-405B 量化部署

**背景**：Llama-405B 太大，单卡装不下。

**方案**：
- FP8 量化：200GB（3 卡 H100）
- INT4 AWQ：100GB（2 卡 H100）
- TP=4 单机部署

**效果**：
- FP8：精度损失 0.5%，吞吐 800 tokens/s
- INT4：精度损失 3%，吞吐 1500 tokens/s

### 9.4 案例 3：阿里通义 INT4 部署

**背景**：通义千问部署到边缘节点（A10 24GB）。

**方案**：
- Qwen-72B INT4 AWQ：36GB
- 2 卡 A10（48GB）部署
- KV Cache INT8

**效果**：
- 单节点边缘部署
- 吞吐 200 tokens/s
- 精度损失 2%

### 10.1 量化与其他优化

| 优化 | 与量化的关系 |
|------|--------------|
| Continuous batching | 协同（量化减显存，batching 提并发） |
| Prefix cache | 协同（KV Cache 量化让 prefix cache 更省） |

| PD 分离 | 协同（量化让 prefill 更快） |
| Speculative decoding | 协同（target + draft 都可量化） |

### 10.2 量化 vs 蒸馏

| 方法 | 思路 | 优势 | 劣势 |
|------|------|------|------|
| 量化 | 大模型压缩到低精度 | 简单，无需训练 | 精度损失 |
| 蒸馏 | 大模型教小模型 | 小模型独立部署 | 需要训练，能力下降 |

## 十一、面试速答

**Q1: FP8 vs INT8 哪个好？**

A: H100 用 FP8（硬件原生，精度更好），A100 用 INT8（FP8 不支持）。FP8 是浮点，INT8 是定点，FP8 精度更高。

**Q2: GPTQ vs AWQ 怎么选？**

A: 精度差不多。AWQ 量化快（10 分钟 vs 2 小时），仅支持 INT4。GPTQ 历史更长，支持更广。生产推荐 AWQ（INT4）+ SmoothQuant（INT8）。

**Q3: 量化后精度损失多少可接受？**

A: Perplexity +5% 以内可接受。MMLU 等下游任务 -2% 以内可接受。小模型（7B 以下）量化损失大，建议用 FP16。

**Q4: 量化为什么能加速？**

A: 显存带宽减半。decode 阶段每 token 读模型权重，FP16 140GB，FP8 70GB。H100 带宽 3TB/s，FP8 速度 1.5-2x。

**Q5: 校准数据怎么选？**

A: 匹配目标领域。通用模型用 wikitext + c4。代码模型用代码。对话模型用 ShareGPT。100-1000 条多样文本。

**Q6: KV Cache 量化和权重量化独立吗？**

A: 独立。可单独量化（`--kv-cache-dtype fp8`）。建议同步量化，否则显存节省有限。

**Q7: 量化对长 context 影响大吗？**

A: 大。KV Cache 随 context 增长（4K 10GB，32K 80GB）。INT4 KV Cache 可让 32K context 单卡可装。

**Q8: 量化会损失工具调用能力吗？**

A: 会略有影响。INT4 量化后工具调用准确率 -3-5%。生产场景建议 INT8 或 FP8。

## 十二、综合面试题

### 题 1（中级）：对比 FP8、INT8、INT4 量化

**答题要点**：
1. **FP8**：H100 原生，浮点，精度 < 1% 损失，速度 1.5-2x，显存减半
2. **INT8**：通用，定点，1-3% 损失，速度 1.5x，显存减半。SmoothQuant 最优
3. **INT4**：通用，定点，3-10% 损失，速度 2-3x，显存 1/4。AWQ/GPTQ
4. **选型**：
   - H100 + 大模型：FP8
   - A100 + 大模型：INT8
   - 显存紧张：INT4
   - 小模型：FP16（量化损失大）

### 题 2（中级）：AWQ 的原理

**答题要点**：
1. **观察**：激活值大的 channel 对应权重重要
2. **方案**：
   - 用校准数据找激活值大的 channel
   - 缩放这些 channel 的权重（放大）
   - 量化缩放后的权重
   - 反量化时缩放回来
3. **效果**：与 GPTQ 精度相当，但量化快 10x
4. **配置**：per-group 128，INT4

### 题 3（高级）：设计量化部署流程

**答题要点**：
1. **评估必要性**：
   - 显存够：不必量化
   - 显存不够：先 FP8/INT8
   - 仍不够：INT4
2. **选算法**：
   - H100：FP8（在线）
   - A100 INT8：SmoothQuant
   - INT4：AWQ
3. **校准**：目标领域 100-1000 条文本
4. **评估**：
   - Perplexity +5% 内
   - MMLU -2% 内
   - 工具调用准确率 -5% 内
5. **部署**：
   - vLLM 加载量化模型
   - KV Cache 同步量化
   - 性能 benchmark
6. **监控**：
   - 推理质量（用户反馈）
   - 性能（吞吐/延迟）
   - 异常检测（输出乱码告警）

### 题 4（高级）：FP8 在 PD 分离中的应用

**答题要点**：
1. **权重 FP8**：Prefill 和 Decode 节点都用 FP8 权重
2. **KV Cache FP8**：跨节点传输量减半（5.25GB vs 10.5GB）
3. **传输加速**：RDMA 传输时间减半（105ms vs 210ms）
4. **精度**：FP8 几乎无损，PD 分离 + FP8 是 H100 部署最优组合
5. **DeepSeek V3 案例**：FP8 + PD 分离，单节点 8×H100 推理 671B MoE

### 题 5（高级）：量化对推理质量的影响评估

**答题要点**：
1. **指标**：
   - Perplexity（语言建模）
   - MMLU（多任务理解）
   - GSM8K（数学推理）
   - HumanEval（代码生成）
   - 工具调用准确率
2. **方法**：
   - 量化前后对比
   - 多指标综合评估
   - 真实流量 A/B 测试
3. **阈值**：
   - Perplexity +5% 内
   - MMLU -2% 内
   - 工具调用 -5% 内
4. **不可接受时的措施**：
   - 升级精度（INT4 → INT8）
   - 用更优算法（GPTQ → AWQ）
   - 改善校准数据
   - 放弃量化

## 十三、故障复盘

### 13.1 案例 1：INT4 量化导致工具调用失败

**背景**：2024 年某公司 Llama-70B INT4 量化后，工具调用准确率从 95% 降到 80%。

**根因**：INT4 对工具调用这种精确任务损失大。

**修复**：换 INT8 SmoothQuant，工具调用 92%。

### 13.2 案例 2：FP8 在 A100 报错

**背景**：2024 年某公司在 A100 上启用 FP8，报错。

**根因**：FP8 是 H100+ 才有的硬件特性。

**修复**：A100 用 INT8 SmoothQuant。

### 13.3 案例 3：校准数据不当导致精度差

**背景**：2025 年某公司代码模型用通用文本校准，量化后代码生成质量差。

**根因**：校准数据与目标领域不匹配。

**修复**：用代码数据校准，精度恢复。

### 13.4 案例 4：KV Cache 没量化导致显存不够

**背景**：2024 年某公司权重 INT4 但 KV Cache FP16，长 context 显存不够。

**根因**：长 context 场景 KV Cache 占比大。

**修复**：`--kv-cache-dtype fp8` 同步量化。

### 13.5 案例 5：量化后输出乱码

**背景**：2025 年某公司 7B 模型 INT4 量化，部分输出乱码。

**根因**：小模型容量小，INT4 损失大。

**修复**：7B 用 FP16，70B+ 才用 INT4。
