# 22 - 混沌工程与稳定性验证

> 混沌工程不是"破坏", 而是"主动发现": 在故障发现你之前, 你先发现故障。Netflix Chaos Monkey 起源, ChaosMesh/Gremlin/Litmus 工具谱系, 在 LLM 推理集群注入 GPU 故障/KV Cache OOM/网络分区, 验证系统的真实韧性。本章梳理混沌工程原则、实验设计、工具对比、AI 场景实践, 以及大厂红黑演练文化。

## 二、问题定义与边界

### 2.1 解决什么

- **发现隐藏故障**: 主动注入, 提前发现
- **验证韧性**: 系统是否真能扛住故障
- **演练应急**: 团队故障响应能力
- **提升架构**: 反思改进, 持续优化

### 2.2 不解决什么

- 不覆盖监控告警（infra开发 模块）
- 不覆盖多活架构（21 章, 但混沌验证多活）
- 不深入 SRE 流程（推荐 SRE 书）

## 三、直觉解释

### 3.1 为什么需要混沌工程

```
传统测试:
  - 单元测试: 函数级
  - 集成测试: 接口级
  - E2E 测试: 用户路径
  - 但: 都是"正常路径"
  
  生产现实:
    - 网络抖动 (100ms → 5s)
    - 节点故障 (硬件/内核)
    - 依赖服务慢
    - 流量突增
    - 配置错误
    - 人为操作失误

混沌工程:
  - 在生产或预发主动注入故障
  - 观察系统行为
  - 验证监控告警
  - 发现隐藏 bug

价值:
  - 提前发现: 故障率下降 50%+
  - 缩短 MTTR: 团队熟练应急
  - 提升架构: 反思改进
  - 文化: 拥抱故障, 不恐惧
```

### 3.2 混沌工程四原则

```
1. 稳态假设 (Steady State Hypothesis)
   - 定义系统"正常"指标 (QPS, P99, 错误率)
   - 注入故障, 验证指标是否仍稳态
   - 例: 注入 Pod 故障, P99 仍 < 500ms

2. 真实事件 (Real World Events)
   - 注入生产可能发生的故障
   - 节点宕机, 网络分区, 磁盘满
   - 避免不切实际的注入

3. 在生产实验 (Run Experiments in Production)
   - 测试环境无法暴露真实问题
   - 生产流量 + 真实依赖
   - 控制爆炸半径, 渐进放大

4. 自动化连续运行 (Automate and Run Continuously)
   - 手动一次性实验价值有限
   - 自动化: 每日/每周运行
   - 持续验证系统韧性
```

### 3.3 故障注入谱系

```
网络层:
  - 延迟 (latency)
  - 丢包 (loss)
  - 分区 (partition)
  - 带宽限制 (bandwidth)

节点层:
  - Pod 杀死 (pod-kill)
  - CPU 打满 (cpu-burn)
  - 内存打满 (memory-burn)
  - 磁盘 IO (disk-IO)
  - 磁盘满 (disk-fill)
  - 时钟漂移 (clock-skew)

应用层:
  - 依赖故障 (dependency-failure)
  - 返回错误 (HTTP 5xx)
  - 慢响应 (timeout)
  - 异常抛出

AI 特殊:
  - GPU 故障 (ECC 错误, 驱动崩溃)
  - KV Cache OOM
  - 模型加载失败
  - 推理超时
  - Agent 死锁
```

### 5.4 自动化混沌（CI 集成）

```python
# chaos_ci.py - CI 集成混沌实验
import yaml
import subprocess
import requests
import time
from kubernetes import client, config

class ChaosExperiment:
    def __init__(self, manifest_path: str):
        self.manifest = yaml.safe_load(open(manifest_path))
        config.load_kube_config()
        self.api = client.CustomObjectsApi()
        self.metrics_url = "http://prometheus:9090/api/v1/query"

    def run(self) -> dict:
        """运行混沌实验, 验证稳态."""
        # 1. 记录基线
        baseline = self._collect_metrics()
        
        # 2. 注入故障
        self._inject_chaos()
        
        # 3. 等待实验完成
        time.sleep(self._get_duration())
        
        # 4. 收集实验期间指标
        during = self._collect_metrics()
        
        # 5. 清理故障
        self._cleanup()
        
        # 6. 等待恢复
        time.sleep(60)
        
        # 7. 收集恢复后指标
        after = self._collect_metrics()
        
        # 8. 验证稳态
        result = self._verify_steady(baseline, during, after)
        return result

    def _collect_metrics(self) -> dict:
        """收集稳态指标."""
        queries = {
            'qps': 'sum(rate(http_requests_total[2m]))',
            'p99_latency': 'histogram_quantile(0.99, sum(rate(http_request_duration_seconds_bucket[2m])) by (le))',
            'error_rate': 'sum(rate(http_requests_total{code=~"5.."}[2m])) / sum(rate(http_requests_total[2m]))',
            'pod_count': 'kube_deployment_status_replicas_available{deployment="vllm"}'
        }
        return {k: self._query(v) for k, v in queries.items()}

    def _query(self, promql: str):
        resp = requests.get(self.metrics_url, params={'query': promql})
        return float(resp.json()['data']['result'][0]['value'][1])

    def _verify_steady(self, baseline, during, after) -> dict:
        """验证稳态假设."""
        return {
            'baseline': baseline,
            'during': during,
            'after': after,
            'passed': (
                during['error_rate'] < 0.05 and  # 错误率 < 5%
                after['error_rate'] < 0.01 and   # 恢复后 < 1%
                after['p99_latency'] < baseline['p99_latency'] * 1.2  # 延迟恢复
            )
        }


# CI 中调用
exp = ChaosExperiment('experiments/pod-kill.yaml')
result = exp.run()
if not result['passed']:
    print(f"混沌实验失败: {result}")
    exit(1)
```

## 六、底层原理

### 6.1 网络故障注入

```
tc (Traffic Control) - Linux 内核流量控制:

  ChaosMesh 用 tc 注入网络故障:
  - delay: tc qdisc add dev eth0 root netem delay 100ms
  - loss: tc qdisc add dev eth0 root netem loss 10%
  - bandwidth: tc qdisc add dev eth0 root tbf rate 1mbit

  原理:
    - qdisc (queueing discipline) 拦截网络包
    - netem (network emulator) 模拟延迟/丢包
    - tbf (token bucket filter) 限速

  作用域:
    - Pod 级 (NetworkChaos + selector)
    - 命名空间级
    - 节点级 (hostNetwork)

  限制:
    - 仅影响 egress (出站)
    - TCP/UDP/ICMP 都受影响
    - 不影响同 Pod 内容器间
```

### 6.2 Pod 故障注入

```
Pod 杀死:
  - kubectl delete pod (ChaosMesh 内部)
  - 模拟 Pod 异常退出
  - K8s 自动重启

容器内进程杀死:
  - kill -9 <pid>
  - 模拟进程崩溃

container kill:
  - docker kill / crictl stop
  - 容器级别故障
  - Pod 仍存活

区别:
  - pod-kill: Pod 重新调度 (可能换节点)
  - container-kill: 同 Pod 重启容器
  - process-kill: 仅杀进程, 容器仍存活
```

### 6.3 资源压力注入

```
stress-ng - 资源压力工具:

CPU:
  - stress-ng --cpu 4 --cpu-load 80
  - 多个 worker 跑 while 循环
  - 占用 CPU

内存:
  - stress-ng --vm 1 --vm-bytes 4G
  - 分配并占用内存
  - 触发 OOM

磁盘 IO:
  - stress-ng --io 4
  - syncfs/sync 写盘

网络:
  - stress-ng --sock 4
  - 大量 socket

混沌实验:
  - 在目标 Pod 内启动 stress-ng sidecar
  - 注入到容器 namespace
  - 影响该 Pod 的资源
```

### 6.4 实验设计原则

```
1. 爆炸半径控制
   - 从最小爆炸半径开始 (1% Pod)
   - 渐进放大 (5% → 25% → 50%)
   - 任一阶段失败立即停止

2. 稳态假设明确
   - 实验前定义 "正常" 指标
   - 实验中持续监控
   - 失败立即终止 + 告警

3. 业务时段选择
   - 初期: 低峰期 (凌晨)
   - 成熟: 业务时段 (验证真实流量)
   - 严禁: 大促/关键节点

4. 自动化
   - CI 集成: 每次发布跑
   - 定时: 每日/每周
   - 持续验证

5. 团队准备
   - 应急预案
   - 回滚方案
   - 通讯渠道

6. 文档化
   - 实验目的
   - 注入故障
   - 预期结果
   - 实际结果
   - 改进措施
```

- [ ] 杀 5 个 Pod (50%)
- [ ] 注入 GPU 故障
- [ ] 验证: 流量切到备地域
- [ ] 验证: RTO < 5min

### 阶段 5: 恢复 (30 min)
- [ ] 清理所有故障
- [ ] 验证: 完全恢复
- [ ] 数据一致性校验

## 应急预案
- 任一阶段失败, 立即停止
- 错误率 > 5% 持续 1min, 终止演练

## 复盘
- 演练后 24h 内复盘会议
- 输出改进项 + 责任人 + 截止日期
- 改进项追踪到完成

## 八、常见陷阱与调优

### 8.1 陷阱 1：爆炸半径失控

**症状**：混沌实验影响生产用户, 引发故障。

**修复**：
- 从 1% Pod 开始
- 渐进放大
- 任一异常立即停止
- 仅低峰期首次实验

### 8.2 陷阱 2：稳态假设缺失

**症状**：注入故障后, 不知道系统是否正常。

**修复**：
- 实验前定义稳态指标 (QPS, P99, 错误率)
- 持续监控
- 异常立即终止 + 告警

### 8.3 陷阱 3：实验未清理

**症状**：实验结束, 故障未清理, 持续影响。

**修复**：
- 设置 duration
- 实验后验证清理
- ChaosMesh 自动 GC

### 8.4 陷阱 4：仅在测试环境

**症状**：测试环境通过, 生产仍故障。

**修复**：
- 测试环境验证实验设计
- 生产环境跑 (控制爆炸半径)
- 持续集成

### 8.5 陷阱 5：缺乏复盘

**症状**：发现问题但不改进, 重复发生。

**修复**：
- 每次实验必复盘
- 改进项追踪到完成
- 文化: 拥抱故障, 不甩锅

### 8.6 调优 Checklist

- [ ] 稳态指标定义清晰
- [ ] 爆炸半径从 1% 起
- [ ] 实验自动清理
- [ ] 监控告警就位
- [ ] 应急回滚方案
- [ ] 团队培训 (红黑演练)
- [ ] CI 集成 (持续验证)
- [ ] 复盘文化 (改进追踪)

## 十、与其他方案的关系

### 10.1 混沌工程 vs 测试

| 维度 | 测试 | 混沌工程 |
|------|------|---------|
| 目的 | 验证功能正确 | 验证系统韧性 |
| 环境 | 测试环境 | 生产/预发 |
| 故障 | 模拟预期 | 注入意外 |
| 频率 | 一次性 | 持续 |
| 价值 | 防止 bug | 防止故障 |

### 10.2 混沌工程与 SRE

```
SRE (Site Reliability Engineering):
  - SLI/SLO/SLA 定义
  - 错误预算
  - 故障复盘
  - 自动化运维

混沌工程:
  - 主动验证 SLI/SLO
  - 消耗错误预算 (可控)
  - 故障复盘素材
  - 自动化实验

关系: 混沌工程是 SRE 的工具, 验证 SRE 目标
```

## 十一、面试速答

**Q1: 混沌工程四原则?**

A: 1) 稳态假设 (定义正常指标); 2) 真实事件 (注入生产可能故障); 3) 在生产实验 (测试环境无法暴露真实问题); 4) 自动化连续运行 (手动一次性价值有限)。

**Q2: ChaosMesh 与 Gremlin 区别?**

A: ChaosMesh 开源 (CNCF), K8s 原生 (CRD), 免费, 适合自建。Gremlin 商用, 跨平台 (VM/容器/K8s), 有完整 SaaS 平台 + 团队培训, 适合企业付费。

**Q3: 混沌实验怎么控制爆炸半径?**

A: 1) 从 1% Pod 开始; 2) 渐进放大 (5% → 25% → 50%); 3) 任一阶段失败立即停止; 4) 稳态监控告警; 5) 仅低峰期首次实验; 6) 团队 ready, 应急预案就位。

**Q4: LLM 推理混沌实验做什么?**

A: 1) Pod 故障 (验证自动恢复); 2) 网络延迟/分区 (验证重试/降级); 3) GPU 故障 (ECC 错误, 驱动崩溃); 4) KV Cache OOM (内存打满, 验证抢占式调度); 5) 模型加载失败 (验证缓存); 6) Agent 死锁 (超时 + 环检测)。

**Q5: 红黑演练是什么?**

A: Netflix 起源, 红 = 故障注入团队, 黑 = 应急响应团队。生产环境注入故障, 验证团队应急能力 + 系统韧性。季度演练, 24h 内复盘, 改进项追踪到完成。

## 十二、综合面试题

### 题 1（中级）：设计 LLM 推理混沌实验

**答题要点**：

1. **稳态指标**:
   - QPS: 1000+
   - TTFT P99: < 800ms
   - 错误率: < 1%
   - Pod 数: >= 6 (共 8)

2. **实验设计**:
   - 阶段 1: 杀 1 Pod, 验证 30s 内恢复
   - 阶段 2: 注入 100ms 网络延迟, 验证 P99 < 1.5s
   - 阶段 3: 杀 2 Pod (25%), 验证 HPA 扩容
   - 阶段 4: 模型仓库分区, 验证本地缓存

3. **爆炸半径**:
   - 仅 vllm-prod 命名空间
   - 仅 1%-25% Pod
   - 低峰期 (凌晨 2-4 点)

4. **监控**:
   - Prometheus 实时指标
   - 异常告警 (< 1min)
   - 自动终止 (错误率 > 5%)

5. **复盘**:
   - 24h 内复盘
   - 改进项 + 责任人
   - 追踪到完成

### 题 2（高级）：多活架构的混沌验证

**答题要点**：

1. **多活场景**:
   - 双地域: 北京 + 美西
   - 用户就近接入
   - 故障自动切换

2. **混沌实验**:
   - 整地域故障 (DNS 黑洞)
   - 跨地域网络分区
   - 数据库主从切换
   - KV Cache 丢失

3. **验证目标**:
   - RTO < 5min
   - RPO < 1min
   - 用户感知 < 30s

4. **挑战**:
   - 整地域故障难注入
   - 数据一致性验证
   - 用户重连风暴

5. **方案**:
   - 流量染色 (仅实验用户)
   - DNS TTL 60s
   - 灰度切换 (10% → 50% → 100%)
   - 数据校验 (实时 + 离线)

6. **红黑演练**:
   - 季度演练
   - 多团队协作
   - 完整应急预案

## 十三、故障复盘

### 13.1 案例 1：混沌实验失控引发生产故障

**背景**：2024 年某公司混沌实验爆炸半径失控, 50% Pod 被杀, 生产不可用。

**根因**：未从 1% 渐进, 直接 50%, 且无自动终止。

**修复**：
- 严格按 1% → 5% → 25% → 50% 渐进
- 自动终止机制 (错误率 > 5% 立即停止)
- 低峰期 + 灰度

**防范**：混沌实验必须爆炸半径控制 + 自动终止 + 灰度。

### 13.2 案例 2：稳态假设缺失导致误判

**背景**：2025 年某公司混沌实验无稳态指标, 实验后不知道是否通过。

**根因**：未定义稳态假设, 无法判定。

**修复**：
- 实验前定义 QPS/P99/错误率阈值
- 持续监控
- 异常立即终止

**防范**：每次实验必须有明确稳态假设。

### 13.3 案例 3：实验未清理持续影响

**背景**：2024 年某公司混沌实验结束, 网络故障未清理, 持续 2 小时影响。

**根因**：duration 配置错误, 实验未自动结束。

**修复**：
- 设置 duration
- 实验后验证清理
- ChaosMesh GC

**防范**：实验必须 duration + 自动清理。

### 13.4 案例 4：仅在测试环境无效

**背景**：2025 年某公司混沌仅在测试环境, 生产仍频繁故障。

**根因**：测试环境无真实流量, 无法暴露问题。

**修复**：
- 生产环境跑 (控制爆炸半径)
- 真实流量验证
- 持续集成

**防范**：混沌必须在生产环境 (控制范围)。

### 13.5 案例 5：发现问题不改进

**背景**：2024 年某公司混沌发现 10+ 问题, 但未改进, 半年后重复故障。

**根因**：无复盘机制, 改进不追踪。

**修复**：
- 每次实验必复盘
- 改进项 + 责任人 + 截止日期
- 月度 review

**防范**：混沌价值在改进, 不在实验本身。
