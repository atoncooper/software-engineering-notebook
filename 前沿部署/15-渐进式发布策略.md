# 15 - 渐进式发布策略

> 渐进式发布（Progressive Delivery）是 GitOps 之后的安全网：从 Rolling → Blue-Green → Canary → Shadow → Traffic Mirroring，逐级放大爆炸半径。本章梳理发布策略谱系、Argo Rollouts vs Flagger、流量切分粒度、自动化分析（Kayenta/Flagger 分析器），以及大厂 LLM 推理服务的灰度实战。

## 二、问题定义与边界

### 2.1 解决什么

- **降低发布风险**：小流量验证, 出问题快速回滚
- **业务无感发布**：用户不感知, SLA 不掉
- **A/B 验证**：新版本是否真的更好
- **流量镜像**：实流量回放, 不影响用户

### 2.2 不解决什么

- 不覆盖 GitOps 流水线（14 章）
- 不深入特征开关（16 章）
- 不覆盖混沌工程（22 章）

## 三、直觉解释

### 3.1 发布策略谱系

```
风险 ←─────────────────────────────────→ 安全

Rolling → Blue-Green → Canary → Shadow → Traffic Mirror
  │           │           │          │           │
  │           │           │          │           └─ 镜像流量, 不影响用户
  │           │           │          └─ 影子版本, 双写双读
  │           │           └─ 按比例放量, 渐进
  │           └─ 两套环境, 切流量
  └─ 滚动替换, 默认策略
```

### 3.2 各策略核心特征

| 策略 | 资源倍数 | 切流量粒度 | 回滚速度 | 用户影响 | 适用 |
|------|---------|-----------|---------|---------|------|
| Rolling | 1x | 无 (按 Pod) | 慢 (重启) | 有 (混合) | 常规迭代 |
| Blue-Green | 2x | 100% 切换 | 快 (切回) | 无 (切换瞬间) | 数据库/有状态 |
| Canary | 1.1-1.5x | 1%→5%→25%→100% | 快 (减流量) | 部分 (灰度用户) | 高风险变更 |
| Shadow | 2x | 0% (镜像) | 无需回滚 | 无 (仅观测) | 正确性验证 |
| Traffic Mirror | 1.1x | 0% (镜像) | 无需回滚 | 无 | 性能验证 |

### 3.3 为什么需要 Canary

```
全量发布 (kubernetes RollingUpdate):
  - 出问题: P1 故障, 30% 用户受影响
  - 发现: 5-10 min (监控报警)
  - 回滚: 5 min (重新拉镜像)
  - 总停机: 10-15 min

Canary 1% → 5% → 25% → 100%:
  - 1% 阶段出问题: 1% 用户, 1 min 内自动回滚
  - 5% 阶段: 5% 用户, 2 min 内回滚
  - 25% 阶段: 25% 用户, 3 min 内回滚
  - 100% 阶段: 极少出问题 (前面已验证)
  - 总停机: 1-3 min, 影响范围 < 5%
```

## 四、核心概念与架构

### 4.1 Argo Rollouts 架构

```
┌─────────────────────────────────────────────┐
│              Rollout CRD                    │
│  (替代 Deployment, 增加 strategy)           │
└──────────────────┬──────────────────────────┘
                   │
                   ▼
┌─────────────────────────────────────────────┐
│           Rollout Controller                │
│  ┌────────────────────────────────────┐     │
│  │ 1. 创建 ReplicaSet (新版本)        │     │
│  │ 2. 按 strategy 配置切流量          │     │
│  │ 3. 等待 AnalysisPhase              │     │
│  │ 4. 失败则回滚, 成功则放大          │     │
│  └────────────────────────────────────┘     │
└──────────────────┬──────────────────────────┘
                   │
       ┌───────────┼───────────┐
       ▼                       ▼
┌──────────────┐         ┌──────────────┐
│ Traffic      │         │ Analysis     │
│ Routing      │         │ Template     │
│ (Istio/NGINX)│         │ (PromQL/     │
│              │         │  Datadog/Webhook) │
└──────────────┘         └──────────────┘
```

### 4.2 Argo Rollouts Canary 基础

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: vllm-canary
spec:
  replicas: 10
  selector:
    matchLabels:
      app: vllm
  template:
    metadata:
      labels:
        app: vllm
    spec:
      containers:
        - name: vllm
          image: vllm/vllm-openai:v0.6.1
          resources:
            limits:
              nvidia.com/gpu: 8
  strategy:
    canary:
      canaryService: vllm-canary      # Canary Service
      stableService: vllm-stable      # Stable Service
      trafficRouting:
        istio:
          virtualService:
            name: vllm-vs
            routes:
              - primary
      steps:
        - setWeight: 5                # 5% 流量到 canary
        - pause: { duration: 5m }     # 观察 5 分钟
        - analysis:                   # 自动化分析
            templates:
              - templateName: success-rate
            args:
              - name: service-name
                value: vllm-canary
        - setWeight: 25
        - pause: { duration: 10m }
        - analysis:
            templates:
              - templateName: latency-p99
        - setWeight: 50
        - pause: { duration: 10m }
        - setWeight: 100
```

### 4.5 Argo Rollouts vs Flagger

| 维度 | Argo Rollouts | Flagger |
|------|--------------|---------|
| CRD | Rollout (替代 Deployment) | Canary (独立控制) |
| 工作方式 | Rollout 接管 Deployment | 监控 Deployment, 创建 clone |
| 流量路由 | Istio/NGINX/ALB/SMI | Istio/NGINX/Linkerd/App Mesh |
| 分析 | AnalysisTemplate (PromQL/Webhook/Datadog) | metric + webhook |
| 与 GitOps | 与 ArgoCD 原生集成 | 与 Flux 原生集成 |
| 学习曲线 | 中 | 低 |
| 灵活性 | 高 (复杂 step) | 中 (配置驱动) |
| 适用 | 复杂发布流程 | 标准化灰度 |

## 六、底层原理

### 6.1 Rollout 状态机

```
Rollout 状态:
  Healthy        ─→ Paused (手动 pause)
  ↓
  Progressing    ─→ Healthy (全量完成)
  ↓ (analysis 失败)
  Degraded       ─→ 自动回滚到 stable
  ↓
  Paused         ─→ 可手动 promote/abort

阶段:
  1. 创建 ReplicaSet (canary)
  2. 等待 Pod Ready
  3. 切流量 (按 step 配置)
  4. 等待 pause 时长
  5. 跑 AnalysisTemplate
     ├── 成功: 进入下一个 step
     └── 失败: failureLimit 次后回滚
  6. 全量后, 旧 ReplicaSet 缩容
```

### 6.2 流量切分实现

```
Istio 模式:
  Argo Rollouts 修改 VirtualService 的 weight
  Istio 控制面下发配置到 Envoy
  Envoy 按权重路由请求

NGINX Ingress 模式:
  Argo Rollouts 修改 Ingress 的 canary-weight annotation
  NGINX Ingress Controller 重载配置
  按 weight 切分到 canary/stable upstream

权重精度:
  - Istio: 0.01% 精度
  - NGINX: 1% 精度
  - ALB: 1% 精度

切分维度:
  - 按权重 (5%, 25%, 50%)
  - 按 Header (x-canary: true)
  - 按 Cookie (canary=true)
  - 按用户分桶 (hash(user_id) % 100 < 5)
```

### 6.3 Kayenta 自动化分析（Netflix）

```
Kayenta (Canary Analysis):
  1. 采集 stable 与 canary 的 metric
  2. 按时间窗口对齐
  3. 计算 Mann-Whitney U 检验 (非参数)
  4. 输出 canary score (0-100)
  5. score > threshold: 通过
  6. score < threshold: 失败回滚

metric 举例:
  - 延迟: P50/P95/P99
  - 错误率: 5xx, 4xx
  - 业务: 转化率, 留存
  - 资源: CPU, 内存, GPU

Argo Rollouts 集成 Kayenta:
  AnalysisTemplate 中 provider.kayenta
```

### 6.4 流量镜像的注意点

```
镜像场景:
  - 100% 镜像, 不影响用户
  - 验证新版本: 延迟, 错误率, 资源占用
  - 不影响用户: 镜像响应被丢弃

注意:
  1. 镜像请求仍消耗资源 (GPU/CPU/内存)
  2. 写操作要谨慎 (镜像到 DB 会污染数据)
     - 用 mock DB 或 dry-run 模式
  3. 镜像请求的 Host header 已修改, 注意路由
  4. 镜像流量可能放大 N 倍 (每个请求都镜像)
  5. LLM 推理镜像: 镜像请求也消耗 KV Cache, 影响生产性能

LLM 镜像实践:
  - 仅镜像 GET /v1/embeddings (无副作用)
  - 不镜像 POST /v1/chat/completions (写 KV Cache)
  - 或镜像到独立集群 (避免资源竞争)
```

### 7.2 按用户分桶（特征开关配合）

```python
# app/router.py
from fastapi import FastAPI, Request
import hashlib

app = FastAPI()

CANARY_PERCENT = 5  # 从 feature flag 读取

@app.middleware("http")
async def route_to_canary(request: Request, call_next):
    user_id = request.headers.get("x-user-id", "")
    if not user_id:
        return await call_next(request)

    bucket = int(hashlib.md5(user_id.encode()).hexdigest(), 16) % 100
    if bucket < CANARY_PERCENT:
        # 转发到 canary service
        request.scope["headers"].append((b"x-canary", b"true"))

    return await call_next(request)
```

# 对比 stable 与 shadow 的响应, 检测正确性
import asyncio
import httpx

async def compare(stable_resp, shadow_resp):
    """对比两版本响应."""
    if stable_resp.status_code != shadow_resp.status_code:
        return False
    # LLM 输出可能有 token-level 差异, 用语义相似度
    sim = await semantic_similarity(stable_resp.json(), shadow_resp.json())
    return sim > 0.95

async def shadow_test(prompt: str):
    async with httpx.AsyncClient() as client:
        stable, shadow = await asyncio.gather(
            client.post("http://vllm-stable/generate", json={"prompt": prompt}),
            client.post("http://vllm-shadow/generate", json={"prompt": prompt}),
        )
    ok = await compare(stable, shadow)
    if not ok:
        alert(f"Shadow 测试失败: prompt={prompt}")

## 八、常见陷阱与调优

### 8.1 陷阱 1：Canary 与 HPA 冲突

**症状**：Canary 阶段 HPA 误判, 扩缩容影响灰度。

**修复**：Canary 期间暂停 HPA, 或使用 KEDA 基于 vLLM 排队数扩缩。

### 8.2 陷阱 2：数据库 Schema 不兼容

**症状**：新版本 Schema 改了, 旧版本写的数据读不出。

**修复**：
- Schema 变更遵循"扩展而非修改"原则
- 双写过渡: 新版本同时写新旧字段
- 灰度期间两套 Schema 共存

### 8.3 陷阱 3：Sticky Session 破坏灰度

**症状**：用户会话粘在 stable, 永远进不了 canary。

**修复**：
- 灰度版本用独立域名 (canary.example.com)
- 或按用户 ID 一致性哈希分桶
- 避免基于 IP 的 sticky (NAT 后多人共享)

### 8.4 陷阱 4：Analysis 误判

**症状**：监控抖动导致正常版本被回滚。

**修复**：
- `failureLimit: 3` 连续 3 次失败才回滚
- `interval: 30s` 间隔够长, 避免瞬时抖动
- 多 metric 取交集 (error-rate + latency + throughput)

### 8.5 陷阱 5：流量镜像放大效应

**症状**：镜像 100% 流量, 实际请求量翻倍, 集群过载。

**修复**：
- 镜像流量比例从 10% 起步
- 镜像集群独立, 不影响生产
- 限制镜像请求并发 (Envoy rate limit)

### 8.6 调优 Checklist

- [ ] Canary 步骤: 5% → 25% → 50% → 100% (而非 50% → 100%)
- [ ] 每步 pause 时长 > 5min (留监控告警时间)
- [ ] AnalysisTemplate 多 metric 交叉验证
- [ ] failureLimit ≥ 3 避免抖动误判
- [ ] 数据库 Schema 兼容性预演
- [ ] 灰度用户分桶一致性 (同一用户同一版本)
- [ ] 流量镜像独立集群, 避免资源竞争
- [ ] Slack/钉钉通知, 人工可 abort
- [ ] 回滚演练: 从 100% 回到 0 在 1 分钟内

## 十一、面试速答

**Q1: Canary 与 Blue-Green 区别?**

A: Blue-Green 是 100% 切换 (两套环境, 切流量), 适合数据库/有状态变更, 资源 2x。Canary 是按比例渐进 (5%→25%→50%→100%), 适合高风险变更, 资源 1.1-1.5x, 出问题影响小。

**Q2: Argo Rollouts 与 Flagger 怎么选?**

A: Argo Rollouts 用 Rollout CRD 替代 Deployment, 灵活度高, 与 ArgoCD 原生集成; Flagger 监控 Deployment 创建 clone, 配置驱动简单, 与 Flux 原生集成。ArgoCD 用户选 Rollouts, Flux 用户选 Flagger。

**Q3: 流量镜像的注意点?**

A: 1) 镜像请求仍消耗资源 (GPU/CPU); 2) 写操作要谨慎 (镜像到 DB 污染数据), 用 mock 或 dry-run; 3) LLM 镜像会写 KV Cache, 影响生产性能; 4) 镜像流量可能放大 N 倍; 5) 镜像集群建议独立, 避免资源竞争。

**Q4: 如何避免 Canary 误判?**

A: 1) `failureLimit >= 3` 连续失败才回滚; 2) `interval >= 30s` 避免瞬时抖动; 3) 多 metric 交叉验证 (error-rate + latency + throughput); 4) 业务 metric (转化率/留存) 加权; 5) 灰度用户分桶一致性, 避免用户在 stable/canary 间跳变。

**Q5: LLM 推理服务的灰度指标?**

A: 1) TTFT P99 (首 token 延迟); 2) 吞吐 (tokens/s); 3) 错误率 (5xx + OOM); 4) 拒答率 (safety filter); 5) 用户负反馈率; 6) 输出质量 (perplexity / 人工评分); 7) GPU 利用率与显存。

## 十二、综合面试题

### 题 1（中级）：设计 LLM 推理服务的 Canary 发布

**答题要点**：

1. **流量切分**：Istio VirtualService, 5%→25%→50%→100%

2. **分析指标**:
   - error-rate < 1%
   - TTFT P99 < 800ms
   - 吞吐 > 1000 tokens/s
   - 拒答率 < 5%

3. **步骤**:
   - setWeight 5%, pause 5min, analysis
   - setWeight 25%, pause 10min, analysis
   - setWeight 50%, pause 10min, analysis
   - setWeight 100%

4. **失败处理**: failureLimit=3, 自动回滚到 stable

5. **回滚时间**: 1 分钟内 (调权重到 0%)

6. **配合特征开关**: 内部用户先灰度, Beta 用户次之, 普通用户最后

7. **通知**: Slack 推送进度, 人工可 abort

### 题 2（高级）：流量镜像在 LLM 推理的工程挑战

**答题要点**：

1. **挑战**:
   - LLM 推理有状态 (KV Cache), 镜像请求污染缓存
   - 镜像 100% 流量, GPU 资源翻倍
   - 镜像请求的响应不返回, 难以对比正确性

2. **方案**:
   - 镜像集群独立, 不共享 KV Cache
   - 镜像比例从 10% 起步, 逐步放大
   - 离线对比: 镜像响应落库, 离线计算语义相似度
   - 仅镜像 GET (无副作用), POST 用 dry-run 模式

3. **正确性验证**:
   - 语义相似度 (BERTScore)
   - 拒答率对比
   - 长度分布对比
   - token-level diff

4. **性能验证**:
   - 镜像集群的 TTFT/吞吐
   - GPU 利用率
   - 显存占用

5. **决策**:
   - 正确性 > 95% + 性能不退化 → 进入 Canary
   - 否则 → 修复后重镜像

## 十三、故障复盘

### 13.1 案例 1：Canary 误判导致正常版本被回滚

**背景**：2024 年某公司 LLM 推理服务 Canary, 监控抖动导致 3 次连续失败, 正常版本被回滚。

**根因**：`failureLimit=1` 过于敏感, 监控瞬时抖动被误判。

**修复**：
- `failureLimit=3` 连续 3 次失败才回滚
- `interval=30s` 间隔拉长
- 多 metric 取交集 (单 metric 抖动不致命)

**防范**：分析模板上线前先用历史数据回放, 验证阈值合理性。

### 13.2 案例 2：数据库 Schema 不兼容

**背景**：2025 年某公司新版本改了 prompt 模板表 Schema, 灰度期间旧版本写的数据新版本读不出。

**根因**：Schema 变更不兼容, 未遵循"扩展而非修改"。

**修复**：
- 立即回滚到旧版本
- 重新设计 Schema: 新增字段而非修改
- 双写过渡: 新版本同时写新旧字段
- 全量升级后再删除旧字段

**防范**：所有 Schema 变更必须经过兼容性评审, 优先扩展不修改。

### 13.3 案例 3：流量镜像放大故障

**背景**：2024 年某公司镜像 100% 流量, 镜像集群过载, 反向影响生产集群网络。

**根因**：镜像集群与生产集群共用网络, 镜像流量放大导致网络拥塞。

**修复**：
- 镜像集群独立网络
- 镜像比例限制 10% 起步
- 镜像集群独立 HPA, 自动扩容

**防范**：镜像集群必须独立, 资源/网络/数据库不共享。

### 13.4 案例 4：Sticky Session 破坏灰度

**背景**：2025 年某公司基于 IP 的 sticky session, NAT 后多人共享 IP, 灰度比例失真。

**根因**：sticky 基于 IP, 企业内网 NAT 后大量用户共享同一 IP, 全部进 stable 或全部进 canary。

**修复**：
- 改用用户 ID 一致性哈希分桶
- 或 JWT token 中的 user_id 分桶

**防范**：灰度分桶必须基于稳定用户标识, 不用 IP。

### 13.5 案例 5：Shadow 流量引发数据库污染

**背景**：2024 年某公司影子版本镜像了写流量, 数据库被写入测试数据。

**根因**：影子版本未隔离写操作, 直接写生产 DB。

**修复**：
- 影子版本配置 dry-run 模式, 不实际写
- 或写入独立 shadow DB
- 紧急清理被污染数据

**防范**：影子版本必须显式隔离写操作, 配置 review 检查。
