# 07 - 分布式推理并行策略

> 当单卡装不下大模型，分布式推理成为必选项。Tensor Parallelism（TP）、Pipeline Parallelism（PP）、Expert Parallelism（EP）、Prefill-Decode Disaggregation（PD 分离）是四大核心策略。
>
> 本章剖析每种策略的原理、适用场景、工程实现，以及混合并行的工业实践。

## 二、问题定义与边界

### 2.1 解决什么

- **单卡装不下**：Llama-405B FP16 810GB，单卡 80GB 远不够
- **延迟太高**：单卡 decode 慢，需要多卡并行加速
- **MoE 部署**：DeepSeek-V3 671B MoE，专家分布到多卡
- **资源利用**：prefill 算力密集 vs decode 显存密集，分离部署

### 2.2 不解决什么

- 不深入 NCCL/RDMA 协议细节
- 不覆盖训练并行（参考 LLM 训练模块）
- 不讨论 DP（数据并行，推理用得少）

## 三、直觉解释

### 3.1 为什么需要分布式推理

**问题 1：显存不够**

```
Llama-405B FP16: 810GB
H100 80GB: 需要 11 卡 (单机不够)
Llama-405B FP8: 405GB
H100 80GB: 需要 6 卡 (单机 8 卡够)
```

**问题 2：延迟高**

```
Llama-70B 单卡 decode:
- 每 token 读 140GB 权重
- H100 带宽 3TB/s
- 理论 47ms/token
- TP=4: 每 token 35GB, 12ms (4x 加速)
```

### 3.2 四种并行策略对比

| 策略 | 切分维度 | 通信 | 适合 | 代表 |
|------|----------|------|------|------|
| TP | 单层内 | AllReduce（每层 2 次） | 单机多卡（NVLink） | Megatron-LM |
| PP | 层间 | pipeline bubble | 跨机（IB） | GPipe、PipeDream |
| EP | MoE 专家 | All-to-All（路由） | MoE 模型 | DeepSpeed-MoE |
| PD 分离 | 阶段（prefill/decode） | KV Cache 传输 | 大模型生产 | DistServe |

### 3.3 TP 的直觉

```
单层 Linear: Y = X × W
W: [in_dim, out_dim] = [8192, 8192]

TP=4 切分 W:
  GPU 0: W[:, 0:2048]
  GPU 1: W[:, 2048:4096]
  GPU 2: W[:, 4096:6144]
  GPU 3: W[:, 6144:8192]

每 GPU 算部分 Y:
  GPU i: Y_i = X × W[:, i*2048:(i+1)*2048]

合并 Y (AllReduce):
  Y = [Y_0, Y_1, Y_2, Y_3] (concat) 或 sum (按配置)
```

**通信**：每层 2 次 AllReduce（Q/K/V 投影 + MLP）。

**关键**：TP 需要 NVLink（900GB/s），跨机 IB（50GB/s）通信开销大。

### 3.4 PP 的直觉

```
Llama-70B 有 80 层
PP=4 切分:
  GPU 0: layer 0-19
  GPU 1: layer 20-39
  GPU 2: layer 40-59
  GPU 3: layer 60-79

micro-batch 流水:
  t=0: micro-batch 1 进入 GPU 0
  t=1: micro-batch 1 进入 GPU 1, micro-batch 2 进入 GPU 0
  t=2: micro-batch 1 进入 GPU 2, micro-batch 2 进入 GPU 1, micro-batch 3 进入 GPU 0
  ...
```

**问题**：pipeline bubble（流水线气泡）。

```
PP=4, 4 micro-batch:
  GPU 0: [1][2][3][4][_][_][_][_][_][_][_][_]
  GPU 1: [_][_][_][_][1][2][3][4][_][_][_][_]
  GPU 2: [_][_][_][_][_][_][_][_][1][2][3][4]
  GPU 3: [_][_][_][_][_][_][_][_][_][_][_][1][2][3][4]
  
  bubble = (PP-1) / (PP-1+micro_batch) = 3/7 = 43%
```

**改进**：1F1B、Interleaved 1F1B 减少 bubble。

### 3.5 EP 的直觉（MoE 专用）

```
DeepSeek-V3: 671B MoE, 256 个专家, 每 token 激活 8 个

EP=8 切分:
  GPU 0: expert 0-31
  GPU 1: expert 32-63
  ...
  GPU 7: expert 224-255

每 token:
  1. 路由器决定激活哪 8 个专家
  2. token 发送到对应 GPU (All-to-All)
  3. 各 GPU 计算自己负责的专家
  4. 结果送回 (All-to-All 反向)
```

**挑战**：专家负载不均（某些专家被频繁激活，其他闲置）。

### 3.6 PD 分离的直觉

```
传统 (PD 一体):
  单卡同时做 prefill 和 decode
  prefill 占满算力, decode 被阻塞

PD 分离:
  Prefill 集群 (高算力 H100):
    专注 prefill, 算力满载
  
  Decode 集群 (高显存密度 A10):
    专注 decode, 显存满载
  
  KV Cache 跨节点传输 (RDMA)
```

**效果**：goodput（有效吞吐）提升 4-7x（DistServe 论文）。

## 四、核心概念与架构

### 4.1 Tensor Parallelism（TP）详解

#### 切分方式

```
Column Parallel (列切分):
  W = [W_1, W_2, ..., W_n]  (按列切)
  Y = X × W = [X×W_1, X×W_2, ..., X×W_n]
  无需通信 (各 GPU 独立算部分)
  用于 Q/K/V 投影

Row Parallel (行切分):
  W = [W_1; W_2; ...; W_n]  (按行切)
  Y = X × W = X×W_1 + X×W_2 + ... + X×W_n
  需要 AllReduce (求和)
  用于 MLP 的 down projection
```

#### Transformer 层的 TP

```
标准 Transformer 层:
  1. LayerNorm
  2. Q = X × W_q, K = X × W_k, V = X × W_v
  3. Attention(Q, K, V)
  4. LayerNorm
  5. MLP: X × W_up → GELU → X × W_down

TP 实现 (Megatron):
  Step 1-2: Q/K/V 用 column parallel (无需通信)
  Step 3:   Attention 各 GPU 独立 (每个 GPU 处理部分 head)
  Step 5:   W_up 用 column parallel, W_down 用 row parallel
            W_down 后 AllReduce (1 次通信)

每层通信: 2 次 AllReduce (attention 后 + MLP 后)
```

#### 通信开销

```
AllReduce 数据量:
  batch_size × seq_len × hidden_dim × dtype_size

Llama-70B, batch=64, seq=2048, FP16:
  64 × 2048 × 8192 × 2 = 2.1GB (单次 AllReduce)

NVLink (节点内): 900GB/s
  2.1GB / 900GB/s = 2.3ms (可忽略)

IB 400Gbps (跨节点): 50GB/s
  2.1GB / 50GB/s = 42ms (占总延迟 30%+)

结论: TP 优先单机内 (NVLink)
```

### 4.2 Pipeline Parallelism（PP）详解

#### 切分方式

```
Llama-70B, 80 层, PP=4:
  Stage 0: layer 0-19
  Stage 1: layer 20-39
  Stage 2: layer 40-59
  Stage 3: layer 60-79

每个 stage 在一个 GPU (或一组 GPU)
```

#### 调度策略

```
GPipe (朴素):
  micro-batch 1, 2, 3, 4 依次流水
  bubble 大

1F1B (One Forward One Backward):
  前向 + 反向交错, 减少显存
  bubble 仍存在

Interleaved 1F1B:
  每个 stage 切多段, 减小 bubble
  bubble = (PP-1) / (PP-1 + micro_batch × chunks)
  PP=4, micro=8, chunks=4: bubble = 3/35 = 8.6%
```

#### PP 在推理的特殊性

推理只有前向，没有反向。PP 的 bubble 问题在推理中：
- micro-batch 流水填满 pipeline
- 但单请求 decode 是逐 token，难以流水

**实际**：推理 PP 用得少，主要用于显存不够时（如 Llama-405B 单机装不下）。

### 4.3 Expert Parallelism（EP）详解

#### MoE 架构

```
DeepSeek-V3 MoE 层:
  输入 X → 路由器 (gate) → 选 top-2 专家 → 专家计算 → 加权求和

每 token 激活 2-8 个专家 (out of 256)
总参数 671B, 激活 37B
```

#### EP 切分

```
EP=8, 256 专家:
  GPU 0: expert 0-31
  GPU 1: expert 32-63
  ...
  GPU 7: expert 224-255

每 token:
  1. 路由器输出 top-2 专家 ID
  2. All-to-All: 把 token 发送到对应 GPU
  3. 各 GPU 用自己的专家计算
  4. All-to-All 反向: 把结果送回
  5. 加权求和
```

#### 负载均衡

```
问题: 某些专家被频繁激活 (hot experts), 其他闲置

  GPU 0 (expert 0-31): 处理 80% token (热门)
  GPU 1 (expert 32-63): 处理 5% token (冷门)
  → GPU 0 成为瓶颈

方案:
  1. 训练时负载均衡 loss (让 token 均匀路由)
  2. 推理时 expert duplication (复制热门专家)
  3. Dynamic EP (动态调整专家分布)
```

#### DeepSeek-V3 的 EP 实践

```
DeepSeek-V3:
  - 256 专家, 每 token 激活 8
  - EP=64 (8 节点 × 8 卡)
  - 每卡 4 专家
  - PD 分离: prefill 用全部专家, decode 用 hot experts
  - 专家路由缓存 (热专家优先)
```

### 4.4 Prefill-Decode Disaggregation（PD 分离）

#### 架构

```
[Client] → [Router]
              │
              ├──→ [Prefill Cluster] (H100, 高算力)
              │       │
              │       └──KV Cache──→ (RDMA)
              │                          │
              └──→ [Decode Cluster] (A10, 高显存密度)
                                          │
                                          └──→ [Client] (流式)
```

#### 工作流程

```
1. 请求到达 Router
2. Router 选 Prefill 节点 (基于负载 + KV Cache 局部性)
3. Prefill 节点计算 KV Cache
4. KV Cache 通过 RDMA 传到 Decode 节点
5. Decode 节点流式生成 token
6. 客户端通过 Decode 节点获取流式响应
```

#### KV Cache 传输

```
单请求 KV Cache (4K context, FP8): 5.25GB

传输方式:
- TCP over 100Gbps: 420ms (太慢)
- RDMA over 400Gbps IB: 105ms (可接受)
- GPU Direct RDMA: 105ms (CPU 不参与, 更高效)
- NVLink (节点内): 5.8ms (最快, 但仅同节点)
```

#### 优势

1. **资源专业化**：Prefill 用高算力卡（H100），Decode 用高显存密度卡（A10）
2. **独立伸缩**：Prefill/Decode 集群独立扩缩容
3. **batching 优化**：Prefill 集中批处理，Decode 连续 batching
4. **goodput 提升**：DistServe 论文证明 4-7x

#### 劣势

1. **架构复杂**：需要 Router、KV Cache 传输、故障恢复
2. **传输开销**：KV Cache 跨节点传输
3. **小模型不必**：7B 以下 PD 分离开销大于收益
4. **故障恢复**：Decode 节点宕机，KV Cache 丢失

### 4.5 混合并行

生产实践常组合多种并行：

```
Llama-405B 部署 (8 机 × 8 卡 = 64 H100):
  - TP=8 (单机内, NVLink)
  - PP=8 (跨机, IB)
  - 总: 8×8 = 64 卡

DeepSeek-V3 部署 (8 机 × 8 卡 = 64 H100):
  - EP=64 (256 专家分布到 64 卡, 每卡 4 专家)
  - TP=8 (单机内非 MoE 层)
  - PD 分离 (prefill/decode 独立集群)
```

## 六、底层原理

### 6.1 TP 通信模式

```
AllReduce (Ring 算法):
  GPU 0 → GPU 1 → GPU 2 → GPU 3 → GPU 0 (ring)
  
  每步: GPU i 把部分结果发给 GPU (i+1) mod n
  n-1 步完成
  
  数据量: 2 × (n-1)/n × data_size (Ring 特性)
  延迟: 2 × (n-1) × latency + 2 × (n-1)/n × data_size / bandwidth
```

### 6.2 PP bubble 分析

```
GPipe bubble:
  PP stages = p
  micro-batches = m
  bubble fraction = (p-1) / (m + p - 1)

例:
  p=4, m=1: bubble = 3/4 = 75% (差)
  p=4, m=4: bubble = 3/7 = 43% (一般)
  p=4, m=16: bubble = 3/19 = 16% (好)
  p=4, m=64: bubble = 3/67 = 4.5% (很好)
```

**结论**：micro-batch 越多，bubble 越小。推理场景 micro-batch 来自不同请求，足够多。

### 6.3 EP 通信

```
All-to-All:
  每个 GPU 给其他 GPU 发送不同数据
  数据量: (n-1) × per_gpu_data

DeepSeek-V3 EP=64:
  每 token 路由到 8 专家, 跨 GPU
  All-to-All 数据量: 8 × token_size = 8 × hidden_dim × dtype
  256 experts, 每 token 激活 8
  实际通信: 2 × 8 × hidden_dim × dtype (前向 + 反向, 但推理只前向)

  hidden=8192, FP16:
  2 × 8 × 8192 × 2 = 256KB / token

  batch=64, 64 token 通信:
  256KB × 64 = 16MB

  NVLink: 16MB / 900GB/s = 0.018ms (可忽略)
  IB: 16MB / 50GB/s = 0.32ms (可接受)
```

### 6.4 PD 分离的 goodput 模型

```
传统 (PD 一体):
  单卡同时 prefill + decode
  prefill 阻塞 decode
  
  goodput = 1 / (T_prefill + T_decode)
  例: T_prefill=200ms, T_decode=2000ms (100 token × 20ms)
  goodput = 1/2.2 = 0.45 req/s

PD 分离:
  prefill 集群: 专注 prefill, T_prefill=200ms
  decode 集群: 专注 decode, T_decode=2000ms
  
  prefill goodput = 1/0.2 = 5 req/s
  decode goodput = 1/2 = 0.5 req/s (但 batch=64 时, 32 req/s)
  
  整体 goodput (batch=64):
  传统: 64 / 2.2 = 29 req/s
  PD 分离: min(5×64, 32) = 32 req/s (略好)
  
  但 prefill 集群可以更大 batch:
  prefill batch=256: goodput = 256/0.2 = 1280 req/s
  decode batch=64: goodput = 32 req/s
  
  真正优势: 资源专业化 + 独立 batching
  DistServe 论文: 4-7x goodput 提升
```

## 八、常见陷阱与调优

### 8.1 陷阱 1：TP 跨机性能差

**症状**：TP=8 跨机比单机慢 3x。

**根因**：跨机无 NVLink，AllReduce 走 IB 慢 18x。

**修复**：TP 单机内（≤8），跨机用 PP。

### 8.2 陷阱 2：PP bubble 严重

**症状**：PP=4 吞吐只有理论值 60%。

**根因**：micro-batch 不够。

**修复**：增加并发请求（提高 micro-batch），或用 Interleaved 1F1B。

### 8.3 陷阱 3：EP 负载不均

**症状**：部分 GPU 满载，其他闲置。

**根因**：热门专家集中。

**修复**：
- 训练时负载均衡 loss
- 推理时 expert duplication
- Dynamic EP

### 8.4 陷阱 4：PD 分离 KV Cache 传输慢

**症状**：PD 分离后 TTFT 反而升高。

**根因**：KV Cache 传输走 TCP，慢。

**修复**：启用 GPU Direct RDMA。

### 8.5 陷阱 5：小模型用 PD 分离

**症状**：7B 模型 PD 分离后性能没提升。

**根因**：小模型 prefill/decode 资源特征差异小，分离开销大于收益。

**修复**：70B+ 才用 PD 分离。

### 8.6 调优 Checklist

- [ ] TP 单机内（NVLink）
- [ ] PP 跨机（IB）
- [ ] EP 用于 MoE
- [ ] PD 分离用于大模型（70B+）
- [ ] KV Cache 传输用 RDMA
- [ ] 监控 TP 通信时间
- [ ] 监控 EP 负载均衡
- [ ] 监控 PD 分离 KV 传输

## 九、工业案例与基准数据

### 9.1 Llama-70B 不同并行策略对比

环境：8×H100，ShareGPT。

| 策略 | 吞吐 (tokens/s) | P99 TTFT | 备注 |

## 十一、面试速答

**Q1: TP 和 PP 的区别？**

A: TP 切单层内权重（按列/行），每层 AllReduce 通信，需要 NVLink，适合单机。PP 切层间（layer 分组），pipeline bubble，通信量少，适合跨机。

**Q2: 为什么 TP 优先单机？**

A: TP 通信是 AllReduce（每层 2 次），单机 NVLink 900GB/s，跨机 IB 50GB/s（18x 慢）。跨机 TP 通信开销占 30%+。

**Q3: EP 是什么？为什么 MoE 需要？**

A: Expert Parallelism，把 MoE 的专家分布到多卡。每 token 路由到 top-K 专家，All-to-All 通信。MoE 模型总参数大（671B）但激活小（37B），EP 让每卡只装部分专家。

**Q4: PD 分离解决什么问题？**

A: prefill 算力密集，decode 显存密集，资源特征不同。分离后 Prefill 用高算力卡（H100），Decode 用高显存密度卡（A10），独立优化。goodput 提升 4-7x。

**Q5: PD 分离的 KV Cache 怎么传？**

A: GPU Direct RDMA，400Gbps IB 50GB/s。单请求 5.25GB（FP8）传输 105ms。节点内 NVLink 900GB/s，5.8ms。

**Q6: PP 的 bubble 怎么减小？**

A: 1) 增加 micro-batch（更多并发请求）；2) Interleaved 1F1B（每 stage 切多段）。PP=4, micro=64 时 bubble 仅 4.5%。

**Q7: EP 负载不均怎么办？**

A: 1) 训练时负载均衡 loss；2) 推理时 hot expert duplication（复制热门专家到多卡）；3) Dynamic EP（动态调整专家分布）。

**Q8: 7B 模型需要分布式吗？**

A: 单卡够（FP16 14GB）就不需要。TP=2 可加速 1.5x，但成本翻倍。PD 分离对小模型不划算（开销大于收益）。

## 十二、综合面试题

### 题 1（中级）：TP 的通信开销分析

**答题要点**：
1. **通信量**：每层 2 次 AllReduce，每次 batch × seq × hidden × dtype
2. **Llama-70B**：batch=64, seq=2048, hidden=8192, FP16，单次 2.1GB
3. **NVLink**（单机）：900GB/s，2.3ms（可忽略）
4. **IB 400Gbps**（跨机）：50GB/s，42ms（占 30%+）
5. **结论**：TP 优先单机，跨机用 PP

### 题 2（中级）：PD 分离的工程挑战

**答题要点**：
1. **KV Cache 传输**：单请求 5.25GB，需要 RDMA
2. **路由决策**：选 Prefill 节点 + Decode 节点
3. **故障恢复**：Decode 节点宕机，KV Cache 丢失
4. **小模型不必**：7B 以下分离开销大于收益
5. **架构复杂**：需要自研 Router

### 题 3（高级）：设计 DeepSeek-V3 的部署架构

**答题要点**：
1. **模型规模**：671B MoE, 256 专家, FP8
2. **单节点部署**（目标）：
   - 8×H100 80GB = 640GB
   - FP8 后 V3 约 700GB（含 KV Cache），不够
3. **方案**：
   - EP=8（单机 8 卡，每卡 32 专家）
   - 专家分片 + 共享
   - KV Cache FP8
   - MLA 压缩 KV Cache 1/4
4. **PD 分离**：
   - Prefill 用全专家
   - Decode 用 hot experts
5. **效果**：单节点 8×H100 推理 V3，60K tokens/s

### 题 4（高级）：混合并行的选型

**答题要点**：
1. **7B 模型**：
   - 单卡 FP16
   - TP=2 提速（可选）
2. **70B 模型**：
   - TP=4 单机（FP16）
   - TP=8 + PD 分离（高吞吐）
   - TP=4 + FP8（单机 4 卡）
3. **405B 模型**：
   - TP=8 + PP=2（跨 2 机，FP8）
   - TP=8 + PD 分离
4. **MoE 模型**：
   - EP + TP（非 MoE 层）
   - + PD 分离
5. **选型原则**：
   - TP 优先单机（NVLink）
   - PP 用于跨机
   - EP 用于 MoE
   - PD 分离用于大模型生产

### 题 5（高级）：PD 分离的故障恢复

**答题要点**：
1. **故障场景**：
   - Prefill 节点宕机：请求重新调度
   - Decode 节点宕机：KV Cache 丢失
   - 网络故障：KV Cache 传输失败
2. **恢复策略**：
   - Prefill 重试（其他节点）
   - KV Cache 持久化（CPU 内存 / 跨节点副本）
   - 客户端断线重连（重新 prefill）
3. **监控**：
   - 节点健康检查
   - KV Cache 传输成功率
   - 请求超时率
4. **权衡**：
   - 持久化开销 vs 恢复速度
   - 副本数 vs 成本

## 十三、故障复盘

### 13.1 案例 1：TP 跨机性能差 3x

**背景**：2024 年某公司 TP=8 跨 2 机，比单机 TP=8 慢 3x。

**根因**：跨机无 NVLink，AllReduce 走 IB 慢。

**修复**：改 TP=4 + PP=2，TP 单机内。

**效果**：性能恢复。

### 13.2 案例 2：PP bubble 严重

**背景**：2024 年某公司 PP=4，吞吐只有 60%。

**根因**：micro-batch 不够（并发低）。

**修复**：增加 max-num-seqs，提高并发。

### 13.3 案例 3：EP 负载不均

**背景**：2025 年某公司 MoE 部署，部分 GPU 满载其他闲置。

**根因**：热门专家集中。

**修复**：hot expert duplication + Dynamic EP。

### 13.4 案例 4：PD 分离 KV Cache 传输慢

**背景**：2024 年某公司 PD 分离后 TTFT 升高。

**根因**：KV Cache 走 TCP，420ms。

**修复**：启用 GPU Direct RDMA，105ms。

### 13.5 案例 5：小模型 PD 分离无收益

**背景**：2025 年某公司 7B 模型 PD 分离，性能没提升。

**根因**：小模型 prefill/decode 资源特征差异小。

**修复**：取消 PD 分离，单集群 TP=2。
