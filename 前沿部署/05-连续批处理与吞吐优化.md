> 本章剖析 batching 演进、continuous batching 原理、chunked prefill、speculative decoding 及其他吞吐优化技术。

## 三、直觉解释

### 3.1 三种 batching 对比

#### Static Batching（静态批处理）

```
t=0: 等 8 个请求到齐 (300ms)
t=300ms: 开始处理 batch
  请求1: 100 token
  请求2: 200 token
  请求3: 50 token
  ...
  请求8: 150 token

t=300ms+50ms=350ms: 请求3 完成, 但要等最慢的
t=300ms+200ms=500ms: 全部完成

问题:
  - 请求3 等了 150ms 才返回 (实际 50ms 就够)
  - 凑批 300ms 浪费
  - GPU 在 t=0 到 300ms 空闲
```

#### Dynamic Batching（动态批处理）

```
t=0: 3 个请求到, 立即开始 (不等凑齐)
t=100ms: 又来 2 个, 加入下一批
t=200ms: 第一批完成, 第二批开始
...

问题:
  - 每批仍是 static (一旦开始, 不再加新请求)
  - 仍有"等最慢"问题
```

#### Continuous Batching（连续批处理）

```
t=0: 请求1 到, 立即处理 (batch=[1])
t=50ms: 请求2 到, 加入 batch (batch=[1,2])
t=100ms: 请求3 到, 加入 (batch=[1,2,3])
t=150ms: 请求1 完成, 退出 (batch=[2,3])
t=200ms: 请求4 到, 加入 (batch=[2,3,4])
...

每个 step (token 生成) 都重新评估:
  - 哪些请求加入
  - 哪些请求退出
  - 哪些请求继续
```

**关键差异**：continuous batching 在每个 decode step 都可以动态调整 batch，不需要等整个 batch 完成。

### 3.2 为什么 continuous batching 快

**GPU 视角**：
- Static: 100 个 token 串行生成，GPU 大部分时间空闲
- Continuous: 100 个 token 并行生成（不同请求），GPU 满载

**延迟视角**：
- Static: TTFT 高（等批凑齐）
- Continuous: TTFT 低（立即开始）

**吞吐视角**：
- Static: GPU 利用率 10%
- Continuous: GPU 利用率 70%+

### 3.3 Chunked Prefill 的直觉

**问题**：prefill（首 token 计算）和 decode（后续 token）资源特征不同。

```
Prefill: 处理 1024 token prompt
  - 算力密集 (1024 × 70B FLOPS)
  - 时间长 (200ms)
  - GPU 满载

Decode: 生成 256 token
  - 显存密集 (每 token 读 70B 权重)
  - 时间短 (每 token 25ms)
  - GPU 利用率低 (5-20%)
```

**冲突**：batch 中如果同时有 prefill 和 decode 请求：
- prefill 占满 GPU 算力
- decode 请求被阻塞
- 整体吞吐下降

**Chunked Prefill 方案**：把长 prefill 切成小块，与 decode 交错执行。

```
传统 (无 chunked prefill):
  step 1: prefill 请求A (1024 token) - 200ms
  step 2: decode 所有请求 - 25ms
  step 3: decode 所有请求 - 25ms
  ...
  问题: step 1 时, decode 请求等待 200ms

Chunked Prefill:
  step 1: prefill 请求A 前 256 token + decode 所有 - 50ms
  step 2: prefill 请求A 中 256 token + decode 所有 - 50ms
  step 3: prefill 请求A 后 512 token + decode 所有 - 100ms
  step 4: decode 所有 - 25ms
  ...
  优势: decode 请求不阻塞
```

### 3.4 Speculative Decoding 的直觉

**问题**：大模型 decode 慢（25ms/token），但生成有"可预测性"（如 "Hello, how are" 后面大概率 "you"）。

**方案**：用小模型猜，大模型验证。

```
传统 (大模型自回归):
  t=0: 大模型生成 "Hello"
  t=25ms: 大模型生成 ","
  t=50ms: 大模型生成 "how"
  t=75ms: 大模型生成 "are"
  t=100ms: 大模型生成 "you"
  总耗时: 125ms (5 token × 25ms)

Speculative (小模型猜 + 大模型验证):
  t=0: 小模型生成 ["Hello", ",", "how", "are", "you"] (5ms, 5 token 并行)
  t=5ms: 大模型验证 5 token (25ms, 一次 forward)
  t=30ms: 全部接受
  总耗时: 30ms (4x 加速)
```

**核心**：
- 小模型 draft model（如 1B）
- 大模型 target model（如 70B）
- 小模型一次猜 k 个 token
- 大模型一次 forward 验证 k 个 token
- 接受小模型猜对的部分

## 四、核心概念与架构

### 4.1 Continuous Batching 调度算法

```python
# 简化伪代码
class ContinuousBatchingScheduler:
    def __init__(self, max_batch_size=256):
        self.max_batch_size = max_batch_size
        self.waiting = []  # 等待队列
        self.running = []  # 运行中

    def schedule(self):
        # 1. 移出已完成的
        self.running = [r for r in self.running if not r.finished]

        # 2. 加入新请求 (如果 batch 未满)
        while len(self.running) < self.max_batch_size and self.waiting:
            self.running.append(self.waiting.pop(0))

        # 3. 抢占低优 (显存不够时)
        if self.kv_cache_full():
            self.preempt_low_priority()

        # 4. 执行一个 step
        batch = self.prepare_batch(self.running)
        outputs = self.model.forward(batch)
        self.update_requests(outputs)

    def preempt_low_priority(self):
        # 找最低优先级请求, 卸载 KV Cache 到 CPU
        victim = min(self.running, key=lambda r: r.priority)
        self.swap_out(victim)
        self.waiting.append(victim)
        self.running.remove(victim)
```

### 4.2 Iteration-Level Scheduling

**关键**：调度粒度是"iteration"（每个 token 生成），不是"request"。

```
传统 request-level:
  调度 = 选哪些请求组成 batch
  一旦选定, 等所有完成

iteration-level (continuous batching):
  调度 = 每个迭代 (token) 重新评估
  请求可动态加入/退出
```

### 4.3 Chunked Prefill 调度

```python
class ChunkedPrefillScheduler:
    def __init__(self, chunk_size=512):
        self.chunk_size = chunk_size

    def schedule(self):
        # 分两类: prefill 请求 (新) 和 decode 请求 (进行中)
        prefill_reqs = [r for r in self.waiting if not r.prefilled]
        decode_reqs = [r for r in self.running if r.prefilled]

        # 选一个 prefill 请求, 切块
        if prefill_reqs:
            req = prefill_reqs[0]
            chunk = req.prompt[:self.chunk_size]
            req.prompt = req.prompt[self.chunk_size:]
            if not req.prompt:
                req.prefilled = True

        # batch = [prefill chunk] + [decode reqs]
        batch = self.prepare_mixed_batch(chunk, decode_reqs)
        return self.model.forward(batch)
```


### 4.4 Speculative Decoding

#### 标准实现

```python
class SpeculativeDecoder:
    def __init__(self, target_model, draft_model, num_spec_tokens=5):
        self.target = target_model
        self.draft = draft_model
        self.k = num_spec_tokens

    def generate(self, prompt, max_tokens):
        tokens = tokenize(prompt)
        while len(tokens) < max_tokens:
            # 1. draft 生成 k 个候选
            draft_tokens = self.draft.generate(tokens, num_tokens=self.k)

            # 2. target 验证 (一次 forward)
            target_logits = self.target.forward(tokens + draft_tokens)

            # 3. 接受 draft 猜对的部分
            accepted = 0
            for i, dt in enumerate(draft_tokens):
                target_token = argmax(target_logits[len(tokens) + i - 1])
                if dt == target_token:
                    accepted += 1
                else:
                    break

            # 4. 加入接受的 token + 1 个 target 生成的 token
            tokens.extend(draft_tokens[:accepted])
            if accepted < self.k:
                # draft 猜错的位置, 用 target 的
                tokens.append(argmax(target_logits[len(tokens) + accepted - 1]))
            else:
                # 全部猜对, 再用 target 生成 1 个
                tokens.append(argmax(target_logits[-1]))

        return detokenize(tokens)
```

#### 加速比分析

```
假设:
- 大模型 25ms/token
- 小模型 5ms/token (并行 k 个)
- 接受率 p (draft 猜对的概率)

无 speculative:
  k+1 token 耗时 = (k+1) × 25ms

有 speculative (k 个 draft):
  - draft 生成: 5ms
  - target 验证: 25ms (一次 forward)
  - 总: 30ms
  - 期望产出: 1 + k×p token

加速比 = (k+1) × 25 / 30, 期望产出 1+k×p
当 p=0.7, k=5:
  产出 = 1 + 3.5 = 4.5 token
  无 spec: 4.5 × 25 = 112.5ms
  有 spec: 30ms
  加速比 = 3.75x
```

#### 变种

1. **Self-Speculative**：用同一模型的早期层做 draft（如 LayerSkip）
2. **Medusa**：多个 head 并行猜多个候选
3. **EAGLE**：用 LM head 而非完整模型做 draft
4. **Lookahead**：用 n-gram 匹配做 draft（无需小模型）

### 4.5 其他吞吐优化技术

#### 1. Prefix Cache（04 章）

复用相同 prefix 的 KV Cache，TTFT 降 70%。

#### 2. TP/PP 并行（07 章）

多卡并行，吞吐线性提升。

#### 3. 量化（06 章）

FP8/INT8 减半显存，提升 batch 容量。

#### 4. CUDA Graph

捕获 GPU 操作序列，减少 kernel launch 开销。


#### 5. Flash Attention

## 六、底层原理

### 6.1 Continuous Batching 的性能模型

**Little's Law 应用**：
```
L = λ × W
L: 系统中平均请求数 (并发)
λ: 到达率 (QPS)
W: 平均处理时间

LLM 推理:
  W = TTFT + tokens × TPOT
  假设 TTFT=300ms, TPOT=25ms, 200 token
  W = 300 + 200×25 = 5300ms = 5.3s

  单卡 L = max_num_seqs = 256
  单卡 λ = L / W = 256 / 5.3 = 48 QPS
  单卡吞吐 = 48 × 200 = 9600 tokens/s
```

### 6.2 Chunked Prefill 的资源利用

```
无 chunked prefill:
  step 1: prefill (GPU 100%) - 200ms
  step 2-256: decode (GPU 15%) - 25ms each
  平均 GPU 利用率: (100% + 15%×255) / 256 = 16%

有 chunked prefill:
  step 1: prefill 256 token + decode 100 reqs (GPU 80%) - 30ms
  step 2-4: 继续 prefill + decode (GPU 80%) - 30ms each
  step 5-256: decode (GPU 50%) - 25ms each
  平均 GPU 利用率: (80%×4 + 50%×252) / 256 = 50%
```

**结论**：chunked prefill 提升 GPU 利用率 3x。

### 6.3 Speculative Decoding 的数学

**接受率模型**：
```
draft 接受率 p (单 token)
k 个 token 全部接受: p^k
k 个 token 接受 j 个: C(k,j) × p^j × (1-p)^(k-j)

期望接受 token 数:
E[accepted] = sum_{j=0}^{k} j × C(k,j) × p^j × (1-p)^(k-j)
            = k × p (二项分布期望)

加上 1 个 target 生成的 token:
E[total] = 1 + k×p

加速比 (理论):
speedup = (1 + k×p) × T_target / (T_draft + T_target)
       = (1 + k×p) / (1 + T_draft/T_target)

当 T_draft/T_target = 0.2 (draft 模型 5x 快):
  p=0.5, k=5: speedup = 3.5 / 1.2 = 2.92x
  p=0.7, k=5: speedup = 4.5 / 1.2 = 3.75x
  p=0.8, k=8: speedup = 7.4 / 1.2 = 6.17x
```

### 6.4 batching 与延迟的权衡

```
batch_size = 1: TTFT 最低, GPU 利用率 5%
batch_size = 256: TTFT 高 (排队), GPU 利用率 70%

最优 batch_size:
  定义 SLA: TTFT < 500ms, TPOT < 50ms
  测试不同 batch 下的 TTFT/TPOT
  找满足 SLA 的最大 batch
```

## 八、常见陷阱与调优

### 8.1 陷阱 1：max-num-seqs 太小

**症状**：吞吐只有理论值 1/10。

**根因**：默认 max-num-seqs=1，没开 continuous batching。

**修复**：`--max-num-seqs 256`。

### 8.2 陷阱 2：没开 chunked prefill

**症状**：prefill 请求阻塞 decode。

**根因**：长 prompt prefill 占满 GPU。

**修复**：`--enable-chunked-prefill`。

### 8.3 陷阱 3：speculative 接受率低

**症状**：speculative decoding 加速不明显。

**根因**：draft model 与 target model 差距大，接受率低。

**修复**：
- 用同系列的 draft（Llama-70B + Llama-1B）
- 降低 num-speculative-tokens（5→3）
- 用 EAGLE / Medusa 等高级方法

### 8.4 陷阱 4：CUDA Graph 编译失败

**症状**：vLLM 启动报 CUDA Graph 错误。

**根因**：模型动态 shape 与 CUDA Graph 不兼容。

**修复**：`--enforce-eager`（牺牲 10% 性能）。

### 8.5 调优 Checklist

- [ ] continuous batching（max-num-seqs ≥ 64）
- [ ] chunked prefill
- [ ] prefix caching
- [ ] FP8 KV Cache（大模型）
- [ ] CUDA Graph（生产开启）
- [ ] TP 单机内
- [ ] speculative decoding（可选，需评估接受率）
- [ ] 监控 TTFT/TPOT/吞吐/GPU 利用率

## 十一、面试速答

**Q1: continuous batching vs dynamic batching？**

A: dynamic batching 定时刷新 batch，但每个 batch 仍是 static（开始后不加新请求）。continuous batching 在每个 decode step 都可以动态加入/退出请求，不需要等 batch 完成。后者吞吐高 3-5x。

**Q2: chunked prefill 解决什么问题？**

A: 长 prompt prefill 占满 GPU 算力，阻塞 decode 请求。chunked prefill 把长 prefill 切成小块，与 decode 交错执行，让 decode 请求不被阻塞。GPU 利用率提升 3x。

**Q3: speculative decoding 的原理？**

A: 用小模型（draft）猜 k 个 token，大模型（target）一次 forward 验证。接受猜对的部分。期望加速比 = (1+k×p) / (1+T_draft/T_target)。当 p=0.7, k=5，加速 3.75x。

**Q4: speculative decoding 接受率低怎么办？**

A: 1) 用同系列 draft（同 tokenizer）；2) 降低 k（5→3）；3) 用 EAGLE/Medusa 等高级方法；4) 评估是否值得（接受率 < 0.5 不推荐）。

**Q5: continuous batching 的调度粒度？**

A: iteration-level（每个 token 生成）。每个 step 重新评估 batch，请求动态加入/退出。这是与 request-level 调度的根本差异。

**Q6: CUDA Graph 的作用？**

A: 捕获 GPU 操作序列，减少 kernel launch 开销。LLM 推理每 step 数百 kernel launch，CUDA Graph 可省 10% 时间。生产开启，调试时关闭（--enforce-eager）。

**Q7: 如何评估 batching 效果？**

A: 1) 吞吐（tokens/s）；2) TTFT P50/P99；3) TPOT P50/P99；4) GPU 利用率；5) KV Cache 使用率。用 vLLM benchmark_serving.py 测试。

**Q8: batching 的极限在哪？**

A: 显存带宽。decode 阶段每 token 读 70B 权重，H100 带宽 3TB/s，理论最低 47ms/token（单卡）。TP=4 12ms/token。这是物理下限，再优化只能靠 PD 分离、speculative 等架构创新。

## 十二、综合面试题

### 题 1（中级）：对比三种 batching，为什么 continuous 最优

**答题要点**：
1. **Static**：等批凑齐，TTFT 高，GPU 空闲
2. **Dynamic**：定时刷新，但每批仍是 static
3. **Continuous**：iteration-level 调度，每 step 动态进出
4. **关键差异**：调度粒度。request-level vs iteration-level
5. **效果**：vLLM 比 HF transformers 吞吐 24x
6. **依赖**：PagedAttention（动态 KV Cache 分配）

### 题 2（中级）：speculative decoding 的数学

**答题要点**：
```
设: draft 接受率 p, 猜 k 个 token
  T_target (大模型单 token), T_draft (小模型单 token)

无 spec: k+1 token 耗时 = (k+1) × T_target

有 spec:
  draft 生成 k token: T_draft (并行)
  target 验证: T_target (一次 forward)
  期望产出: 1 + k×p token

加速比 = (1+k×p) × T_target / (T_draft + T_target)
       = (1+k×p) / (1 + T_draft/T_target)

例: p=0.7, k=5, T_draft/T_target=0.2
  speedup = 4.5 / 1.2 = 3.75x
```

### 题 3（高级）：设计一个支持 10K QPS 的 LLM 推理服务

**答题要点**：
1. **流量分析**：
   - 10K QPS × 200 token = 2M tokens/s
   - 假设 Llama-70B，单卡 25 token/s（vLLM 优化）
   - 需要 80K 张 H100（不可行）
   - 优化后单卡 1800 token/s，需要 1100 张
2. **优化**：
   - continuous batching + chunked prefill + prefix cache
   - FP8 量化
   - PD 分离
   - speculative decoding
   - 优化后单卡 3500 token/s，需 570 张
3. **架构**：
   - K8s + GPU Operator
   - Volcano 调度
   - vLLM Router（prefix-aware）
   - HPA on 排队数
4. **成本**：
   - 570 × $1.8 × 24 × 30 = $740K/月（预留）
   - 混合（base + peak）：$500K/月
5. **可靠性**：
   - 多 AZ + 单元化
   - 99.95% SLA

### 题 4（高级）：chunked prefill 的实现细节

**答题要点**：
1. **问题**：长 prefill 占满 GPU，阻塞 decode
2. **方案**：切长 prefill 为 chunk，与 decode 交错
3. **实现**：
   - 每步选一个 prefill 请求，处理 chunk_size 个 token
   - 同步执行所有 decode 请求
   - batch = [prefill chunk] + [decode reqs]
4. **配置**：vLLM `--enable-chunked-prefill --max-num-batched-tokens 8192`
5. **效果**：GPU 利用率 16% → 50%，吞吐 +20%
6. **注意**：chunk 太小（如 64）会让 prefill 慢；太大（如 4096）失去交错效果。512 是经验值。

### 题 5（高级）：speculative decoding 的工程挑战

**答题要点**：
1. **draft model 选择**：
   - 同系列（同 tokenizer）
   - 5-10x 快于 target
   - 例：Llama-1B draft + Llama-70B target
2. **接受率优化**：
   - num-speculative-tokens 调优（3-8）
   - 用 EAGLE（LM head 做 draft）
   - 用 Medusa（多 head 并行）
3. **资源开销**：
   - draft model 占额外显存
   - target forward 计算量增加（验证 k token）
4. **实现复杂度**：
   - tree attention（Medusa）
   - 修改 attention kernel
   - vLLM 0.6+ 支持
5. **效果评估**：
   - 接受率监控
   - 实际加速比
   - 不值得就关闭

## 十三、故障复盘

### 13.1 案例 1：没开 chunked prefill 导致 decode 抖动

**背景**：2024 年某公司长 prompt 请求导致 decode 延迟飙升。

**根因**：长 prefill 占满 GPU，decode 请求等待。

**修复**：开启 chunked prefill。

**效果**：decode 延迟稳定，P99 降 50%。

### 13.2 案例 2：speculative decoding 接受率 0.3

**背景**：2025 年某公司用 GPT-2 做 Llama-70B 的 draft，接受率 0.3。

**根因**：不同 tokenizer，draft 猜的 token 与 target 不对齐。

**修复**：换成 Llama-1B draft，接受率 0.7。

### 13.3 案例 3：CUDA Graph 编译失败

**背景**：2024 年某公司 vLLM 启动报 CUDA Graph 错误。

**根因**：模型有动态 shape（如变长 prompt）。

**修复**：`--enforce-eager`（牺牲 10% 性能）。

### 13.4 案例 4：max-num-seqs 过大导致抢占频繁

**背景**：2024 年某公司 max-num-seqs=512，高峰期抢占频繁。

**根因**：KV Cache 不够，低优请求被抢占重算。

**修复**：max-num-seqs 降到 256，配合 swap_space。

### 13.5 案例 5：speculative decoding 反而更慢

**背景**：2025 年某公司 speculative decoding 后吞吐下降。

**根因**：draft model 太大（7B），T_draft/T_target=0.5，加上验证开销，反而慢。

**修复**：换 1B draft，T_draft/T_target=0.2。
