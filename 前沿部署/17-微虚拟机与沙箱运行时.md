# 17 - 微虚拟机与沙箱运行时

> 容器的隔离边界一直是它的阿喀琉斯之踵: 共享内核意味着逃逸漏洞链直达宿主。MicroVM 把虚拟机级别的隔离与容器的启动速度合并: Firecracker 125ms 启动, gVisor 用户态内核, Kata QEMU 轻量化, Cloud Hypervisor Rust 实现。本章梳理沙箱运行时谱系、隔离原理、性能开销, 以及在 AI Agent 代码执行/Serverless 函数/CI Runner 的工业实践。

## 二、问题定义与边界

### 2.1 解决什么

- **强隔离**: 容器逃逸不直达宿主
- **多租户安全**: Serverless/Agent 代码执行的信任边界
- **快速启动**: VM 级隔离 + 容器级启动速度
- **资源开销低**: 比传统 VM 内存/CPU 开销小一个数量级

### 2.2 不解决什么

- 不覆盖容器基础（Docker 模块）
- 不覆盖 K8s 调度（k8s 模块）
- 不覆盖 Service Mesh（20 章）

## 三、直觉解释

### 3.1 为什么需要 MicroVM

```
容器 (runc):
  - 共享宿主内核
  - 隔离: namespaces + cgroups
  - 启动: ~50ms
  - 隔离强度: 弱 (内核漏洞即逃逸)
  - 历史: CVE-2019-5736 (runc 逃逸), CVE-2022-0185 (cgroup 逃逸)

传统 VM:
  - 完整内核
  - 隔离: 硬件虚拟化 (VT-x/AMD-V)
  - 启动: 5-30s
  - 隔离强度: 强 (需突破 hypervisor)
  - 内存开销: 256MB+ per VM

MicroVM (Firecracker):
  - 精简内核 (裁剪)
  - 隔离: 硬件虚拟化
  - 启动: 125ms
  - 隔离强度: 强
  - 内存开销: 5MB per VM
```

### 3.2 沙箱谱系

| 方案 | 隔离机制 | 启动时间 | 内存开销 | IO 性能 | 兼容性 |
|------|---------|---------|---------|---------|--------|
| runc (默认) | namespaces+cgroups | 50ms | 1MB | 原生 | 100% |
| gVisor | 用户态内核 | 200ms | 50MB | 慢 (拦截) | 95% |
| Kata Containers | QEMU/KVM | 1-2s | 100MB | 中 (virtio) | 99% |
| Firecracker | KVM (精简) | 125ms | 5MB | 中 (virtio) | 90% |
| Cloud Hypervisor | KVM (Rust) | 100ms | 10MB | 中 (virtio) | 95% |

### 3.3 隔离边界对比

```
攻击面:
  runc:
    - 内核 syscall 接口 (~400 syscalls)
    - 内核漏洞直接逃逸
    
  gVisor:
    - 用户态内核拦截 syscall (~50 syscalls 实现完整 TCP/IP/fs)
    - 攻击面缩小到 gVisor 实现
    
  Kata/Firecracker:
    - 完整独立内核
    - 攻击面缩小到 hypervisor (KVM)
    - 需突破 hypervisor 才能逃逸
    
逃逸路径:
  runc → 宿主: 1 个内核漏洞
  gVisor → 宿主: 1 个 gVisor 漏洞 + 1 个内核漏洞
  Kata/Firecracker → 宿主: 1 个 hypervisor 漏洞
```

## 四、核心概念与架构

### 4.1 Firecracker 架构

```
┌─────────────────────────────────────────────┐
│              Host Linux + KVM               │
│  ┌──────────────────────────────────────┐   │
│  │      Firecracker VMM (Rust)          │   │
│  │  ┌────────────┐  ┌────────────────┐  │   │
│  │  │ vCPU 线程  │  │ IO 处理线程    │  │   │
│  │  │ (KVM)      │  │ (virtio)       │  │   │
│  │  └────────────┘  └────────────────┘  │   │
│  │  ┌────────────────────────────────┐  │   │
│  │  │ Mini Kernel (裁剪)             │  │   │
│  │  │ - 不支持 PCI/USB/VGA           │  │   │
│  │  │ - 仅 virtio-net/block/serial   │  │   │
│  │  └────────────────────────────────┘  │   │
│  └──────────────────────────────────────┘   │
└─────────────────────────────────────────────┘

精简设计:
  - 仅 4 个设备: virtio-net, virtio-block, serial, keyboard
  - 无 BIOS, 无 PCI, 无 USB, 无 VGA
  - 启动直接加载内核 (跳过 bootloader)
  - 125ms 从 0 到 ready
```

### 4.2 Firecracker 启动流程

```
1. host: firecracker --api-sock /tmp/firecracker.sock
   ↓ (10ms)
2. 配置: API 调用设置 kernel/rootfs/cmdline
   ↓ (5ms)
3. 启动 VM: KVM_CREATE_VM + KVM_CREATE_VCPU
   ↓ (60ms)
4. 加载内核: 从内存加载 kernel image
   ↓ (40ms)
5. 内核初始化: 裁剪内核, 跳过 PCI/USB
   ↓ (10ms)
6. 用户空间 init: 启动应用
   ↓ (10ms)
7. 应用 ready

总耗时: ~125ms (Lambda 实测)
```

### 4.3 gVisor 架构

```
┌─────────────────────────────────────────────┐
│              Host Kernel                    │
│  ┌──────────────────────────────────────┐   │
│  │  Host syscalls (受限 subset)         │   │
│  └──────────────────────────────────────┘   │
└─────────────────▲───────────────────────────┘
                  │ ~50 syscalls (过滤后)
┌─────────────────┴───────────────────────────┐
│         gVisor Sentry (用户态内核)          │
│  ┌────────────┐  ┌────────────┐             │
│  │ TCP/IP 栈  │  │ VFS        │             │
│  │ (用户态)   │  │ (用户态)   │             │
│  └────────────┘  └────────────┘             │
│  ┌────────────────────────────────────┐     │
│  │ Syscall 拦截 + 实现                │     │
│  │ - open/read/write: 重定向到 Gofer  │     │
│  │ - socket: 用户态 TCP 栈            │     │
│  │ - mmap: 用户态实现                 │     │
│  └────────────────────────────────────┘     │
└─────────────────▲───────────────────────────┘
                  │ 9p 协议
┌─────────────────┴───────────────────────────┐
│              Gofer (文件代理)               │
│  - 沙箱内文件操作经 Gofer 转发到宿主         │
└─────────────────────────────────────────────┘
```

### 4.4 Kata Containers 架构

```
┌─────────────────────────────────────────────┐
│              Host + KVM                     │
│  ┌──────────────────────────────────────┐   │
│  │  QEMU (轻量化)                       │   │
│  │  ┌────────────────────────────────┐  │   │
│  │  │ Guest Kernel (完整 Linux)      │  │   │
│  │  │ ┌──────────────────────────┐   │  │   │
│  │  │ │ Pod 级容器 (runc)        │   │  │   │
│  │  │ │ ┌────────┐ ┌────────┐    │   │  │   │
│  │  │ │ │cont-1  │ │cont-2  │    │   │  │   │
│  │  │ │ └────────┘ └────────┘    │   │  │   │
│  │  │ └──────────────────────────┘   │  │   │
│  │  └────────────────────────────────┘  │   │
│  └──────────────────────────────────────┘   │
└─────────────────────────────────────────────┘

特点:
  - 一个 Pod 一个轻量 VM (QEMU + KVM)
  - VM 内部用 runc 跑容器
  - 完整 Linux 内核, 兼容性最好
  - 启动: 1-2s (QEMU 开销)
  - 内存: ~100MB (QEMU + guest kernel)
```

### 4.5 Cloud Hypervisor

```
Cloud Hypervisor (Intel 主导, Rust 实现):
  - 与 Firecracker 类似但功能更丰富
  - 支持 PCI, VFIO (GPU 直通), hotplug
  - 适合: AI 推理 (GPU 直通), 容器运行时
  - 启动: ~100ms
  - 内存: ~10MB

与 Firecracker 区别:
  - Firecracker: 极致精简 (Lambda/Fargate)
  - Cloud Hypervisor: 平衡 (Kata 后端, GPU 直通)
```

## 六、底层原理

### 6.1 KVM 硬件虚拟化

```
KVM (Kernel-based Virtual Machine):
  - Linux 内核模块 (/dev/kvm)
  - 利用 CPU 虚拟化指令 (Intel VT-x, AMD-V)
  - 提供 /dev/kvm 字符设备

主要 ioctl:
  KVM_CREATE_VM: 创建虚拟机
  KVM_CREATE_VCPU: 创建虚拟 CPU
  KVM_RUN: 运行 vCPU
  KVM_SET_USER_MEMORY_REGION: 设置内存映射

Firecracker 使用 KVM 流程:
  1. open("/dev/kvm") 得到 fd
  2. ioctl(KVM_CREATE_VM) 创建 VM
  3. ioctl(KVM_SET_USER_MEMORY_REGION) 设置 guest 内存
  4. ioctl(KVM_CREATE_VCPU) 创建 vCPU
  5. ioctl(KVM_RUN) 运行 (陷入 guest 模式)
  6. guest 退出 (IO/异常) → host 处理 → 重新 KVM_RUN
```

### 6.2 virtio 设备模型

```
virtio (半虚拟化):
  - guest 知道自己在虚拟化环境
  - guest 与 host 通过共享内存 + 队列通信
  - 比 full emulation 快 10-100x

virtio-net 数据路径:
  Guest: write socket → virtio-net driver → virtqueue (共享内存)
  Host: VMM 线程读 virtqueue → tap fd → host kernel → 物理网卡

virtio-block 数据路径:
  Guest: write() → virtio-blk driver → virtqueue
  Host: VMM 读 virtqueue → read/write 文件 → 返回

Firecracker 仅支持:
  - virtio-net (网络)
  - virtio-block (块设备)
  - serial (串口)
  - keyboard (仅键盘输入, 用于交互)
```

### 6.3 gVisor syscall 拦截

```
gVisor (runsc) 工作流:
  1. 容器进程通过 seccomp 拦截 syscall
  2. seccomp BPF 过滤器把 syscall 重定向到 Sentry
  3. Sentry (用户态内核) 处理 syscall:
     - open(): 通过 9p 协议请求 Gofer
     - read/write(): 转发到 Gofer 或本地缓存
     - socket(): 用户态 TCP/IP 栈
     - mmap(): 用户态实现
  4. 仅必要 syscall 透传到 host kernel

性能影响:
  - 文件 IO: 慢 2-10x (经 Gofer 中转)
  - 网络: 中等开销 (用户态 TCP 栈)
  - 计算密集: 几乎无影响 (CPU 指令不拦截)
  - 系统调用密集: 显著变慢

适用:
  - 不可信代码 (CI/Agent)
  - 网络服务 (中等开销可接受)
不适用:
  - 文件 IO 密集 (数据库, 大数据处理)
```

### 6.4 启动时间分析

```
Firecracker 启动分解 (125ms):
  - VMM 进程启动: 5ms
  - KVM_CREATE_VM: 10ms
  - 加载内核镜像到内存: 30ms
  - KVM_CREATE_VCPU: 5ms
  - 内核解压+初始化: 60ms (裁剪内核, 跳过 PCI/USB)
  - 用户空间 init: 15ms

Kata Containers 启动分解 (1.5s):
  - QEMU 进程启动: 100ms
  - QEMU 设备初始化 (PCI/USB): 200ms
  - 内核加载: 100ms
  - 完整 Linux 内核初始化: 800ms
  - containerd-shim + runc: 200ms
  - 容器 init: 100ms

差异来源:
  - Firecracker 裁剪内核 (5MB), Kata 完整内核 (50MB+)
  - Firecracker 无 PCI/USB, Kata 有
  - Firecracker 直接加载内核, Kata 经 QEMU bootloader
```

### 6.5 内存开销对比

```
runc (默认):
  - 共享宿主内核: 0 额外
  - 进程开销: ~1MB
  - 总: 1MB

Firecracker:
  - VMM 进程: 3MB
  - Guest kernel: 5MB (裁剪)
  - 用户空间: 取决于应用
  - 总: ~8MB (空载)

Kata (QEMU):
  - QEMU 进程: 50MB
  - Guest kernel: 50MB (完整)
  - containerd-shim: 10MB
  - runc: 1MB
  - 总: ~110MB (空载)

gVisor:
  - Sentry 进程: 30MB
  - Gofer 进程: 20MB
  - 总: ~50MB (空载)

密度对比 (256GB 内存宿主, 留 50GB 给系统):
  - runc: 200K 容器 (理论, 实际受其他限制)
  - Firecracker: 30K VM
  - Kata: 1.8K VM
  - gVisor: 4K 容器

Serverless 密度:
  - AWS Lambda 用 Firecracker, 单机万级并发函数
  - 若用 QEMU, 单机百级, 成本高 100x
```

## 七、代码与配置示例

### 7.1 AI Agent 代码沙箱（Firecracker）

```python
# agent_sandbox.py
import subprocess
import json
import os
import tempfile
import time
from pathlib import Path

class FirecrackerSandbox:
    """AI Agent 代码执行沙箱, 用 Firecracker 强隔离."""

    def __init__(self, kernel_path: str, rootfs_path: str):
        self.kernel = kernel_path
        self.rootfs = rootfs_path
        self.socket = None
        self.vmm_pid = None

    def start(self):
        """启动 MicroVM."""
        self.socket = f"/tmp/fc-{os.getpid()}.sock"
        if os.path.exists(self.socket):
            os.remove(self.socket)

        # 启动 firecracker
        self.vmm_pid = subprocess.Popen(
            ["firecracker", "--api-sock", self.socket],
            stdout=subprocess.PIPE,
            stderr=subprocess.PIPE
        )

        # 等待 socket 就绪
        for _ in range(50):
            if os.path.exists(self.socket):
                break
            time.sleep(0.01)

        # 配置
        self._api_put("/boot-source", {
            "kernel_image_path": self.kernel,
            "boot_args": "console=ttyS0 reboot=k panic=1 pci=off"
        })

        self._api_put("/drives/rootfs", {
            "drive_id": "rootfs",
            "path_on_host": self.rootfs,
            "is_root_device": True,
            "is_read_only": False
        })

        # 网络 (可选, 默认无网络更安全)
        # self._setup_network()

        # 启动
        self._api_put("/actions", {"action_type": "InstanceStart"})

    def _api_put(self, path: str, data: dict):
        """调用 Firecracker API."""
        subprocess.run([
            "curl", "--unix-socket", self.socket,
            "-X", "PUT", f"http://localhost{path}",
            "-H", "Content-Type: application/json",
            "-d", json.dumps(data)
        ], check=True)

    def execute_code(self, code: str, timeout: int = 30) -> dict:
        """在沙箱内执行代码 (通过 serial 注入)."""
        # 1. 把代码写入 rootfs (宿主操作)
        self._inject_code(code)
        # 2. 启动 VM 执行
        # 3. 等待输出
        # 4. 收集结果
        return {
            "stdout": "...",
            "stderr": "...",
            "exit_code": 0
        }

    def stop(self):
        """销毁沙箱."""
        if self.vmm_pid:
            self.vmm_pid.kill()
            self.vmm_pid.wait()
        if self.socket and os.path.exists(self.socket):
            os.remove(self.socket)


# 使用
sandbox = FirecrackerSandbox(
    kernel_path="/var/lib/firecracker/vmlinux-5.10",
    rootfs_path="/var/lib/firecracker/rootfs.ext4"
)
sandbox.start()
result = sandbox.execute_code("print('hello from sandbox')")
sandbox.stop()
```

### 7.2 Serverless 函数平台（Firecracker 模型）

```python
# serverless_platform.py
import asyncio
from typing import Dict
from dataclasses import dataclass

@dataclass
class FunctionInstance:
    vm_id: str
    socket: str
    status: str  # 'cold', 'warming', 'ready', 'busy'
    last_used: float

class FirecrackerPool:
    """Firecracker 函数池, 复用温热实例."""

    def __init__(self, max_pool: int = 1000):
        self.pool: Dict[str, FunctionInstance] = {}
        self.max_pool = max_pool

    async def invoke(self, function_id: str, payload: dict) -> dict:
        """调用函数, 优先用温热实例."""
        # 1. 找温热实例
        instance = self._get_warm(function_id)
        if not instance:
            # 2. 冷启动
            instance = await self._start_cold(function_id)

        # 3. 调用
        instance.status = 'busy'
        try:
            result = await self._invoke_instance(instance, payload)
        finally:
            instance.status = 'ready'
            instance.last_used = asyncio.get_event_loop().time()

        return result

    async def _start_cold(self, function_id: str) -> FunctionInstance:
        """冷启动一个新 MicroVM."""
        vm_id = f"vm-{function_id}-{int(time.time()*1000)}"
        socket = f"/tmp/{vm_id}.sock"

        # 异步启动 firecracker
        proc = await asyncio.create_subprocess_exec(
            "firecracker", "--api-sock", socket,
            stdout=asyncio.subprocess.PIPE,
            stderr=asyncio.subprocess.PIPE
        )

        # 等待 ready
        await asyncio.sleep(0.125)  # 125ms

        instance = FunctionInstance(
            vm_id=vm_id,
            socket=socket,
            status='ready',
            last_used=asyncio.get_event_loop().time()
        )
        self.pool[vm_id] = instance
        return instance

    async def cleanup_idle(self, idle_seconds: int = 300):
        """清理空闲实例 (Scale-to-Zero)."""
        now = asyncio.get_event_loop().time()
        for vm_id, instance in list(self.pool.items()):
            if instance.status == 'ready' and now - instance.last_used > idle_seconds:
                await self._destroy(vm_id)

    async def _destroy(self, vm_id: str):
        """销毁 MicroVM."""
        # 优雅关闭
        instance = self.pool.pop(vm_id)
        # 通过 API 发送 CtrlAltDel
        # ...
```

## 八、常见陷阱与调优

### 8.1 陷阱 1：IO 性能瓶颈

**症状**：gVisor 跑数据库, 文件 IO 慢 10x。

**修复**：
- gVisor 不适合 IO 密集场景
- 改用 Kata (virtio-blk 性能更好)
- 或用 runc + 加固 (seccomp + AppArmor)

### 8.2 陷阱 2：GPU 直通困难

**症状**：Kata 跑 LLM 推理, GPU 用不上。

**修复**：
- Kata + Cloud Hypervisor 支持 VFIO GPU 直通
- 或用 NVIDIA vGPU (商业方案)
- 配置 Kata: `enable_gpu = true`

### 8.3 陷阱 3：启动慢导致冷启动超时

**症状**：Kata 启动 2s, Serverless 函数冷启动超时。

**修复**：
- Serverless 用 Firecracker (125ms)
- 预启动实例池, 保持温热
- 快照恢复 (snapshot restore)

### 8.4 陷阱 4：网络性能差

**症状**：Firecracker virtio-net 性能不及宿主 50%。

**修复**：
- 用 vhost-user (DPDK 加速)
- SR-IOV 直通 (硬件虚拟化网卡)
- 大批量场景用宿主网络 + 仅控制面进 VM

### 8.5 陷阱 5：监控盲区

**症状**：MicroVM 内进程异常, 宿主监控看不到。

**修复**：
- VM 内部署 agent, 通过 API 上报
- 或从 virtio-serial 收集日志
- Prometheus + VM 内 node_exporter

### 8.6 调优 Checklist

- [ ] 按敏感度选 RuntimeClass (高→Kata, 中→gVisor, 低→runc)
- [ ] GPU 场景用 Kata + Cloud Hypervisor + VFIO
- [ ] Serverless 用 Firecracker + 实例池
- [ ] 监控进 VM 内, 不依赖宿主观察
- [ ] IO 密集用 Kata, 避免 gVisor
- [ ] 快照恢复降低冷启动 (Firecracker snapshot)
- [ ] OPA Gatekeeper 强制 RuntimeClass 策略
- [ ] 网络性能用 vhost-user / SR-IOV

## 九、工业案例与基准数据

### 9.1 案例 1：AWS Lambda + Firecracker

**背景**：AWS Lambda Serverless 函数平台。

**方案**：
- Firecracker 由 AWS 2018 开源, 专为 Lambda 设计
- 每个函数实例一个 Firecracker VM
- 函数复用: 同一 VM 内多次调用 (温热)
- 实例池: 预启动 VM, 降低冷启动

**规模**：
- 单机并发: 1000+ Firecracker VM
- 冷启动: 125ms (代码小), 1-2s (大代码)
- 内存密度: 5MB/VM 空载
- ARM/Intel 双架构

**效果**：密度比传统 VM 提升 100x, 成本下降 90%。

### 9.2 案例 2：AWS Fargate

**背景**：AWS Fargate Serverless 容器。

**方案**：
- 每个 Task (Pod) 一个 Firecracker VM
- 客户无 EC2 管理, 按资源计费
- 与 ECS/EKS 集成

**效果**：客户无需运维 EC2, 安全隔离达 VM 级别。

### 9.3 案例 3：Fly.io

**背景**：边缘 Serverless 平台 Fly.io。

**方案**：
- Firecracker 跑用户容器
- 全球 30+ 边缘节点
- 每个用户 App 一个 MicroVM
- 启动: 100-300ms

**效果**：边缘部署密度高, 全球低延迟。

### 9.4 案例 4：Modal (Serverless GPU)

**背景**：Modal Serverless GPU 平台 (10 章)。

**方案**：
- Firecracker + GPU 直通
- 每个函数实例一个 MicroVM + GPU
- 冷启动: 1-30s (含模型加载)

**效果**：GPU Serverless 隔离与密度兼得。

### 9.5 案例 5：Kata Containers 在生产 K8s

**背景**：阿里云 ACK 沙箱容器, 字节火山引擎 VKE。

**方案**：
- Kata Containers + 自研 QEMU 优化
- GPU 直通 (VFIO)
- 启动优化: 1.5s → 600ms (内核裁剪 + 快照)

**适用**：金融/政务/医疗等高安全场景, 多租户强隔离。

## 十、与其他方案的关系

### 10.1 与 WASM 沙箱对比

| 维度 | MicroVM | WASM |
|------|---------|------|
| 隔离 | 硬件虚拟化 | 内存安全 (语言级) |
| 启动 | 100-1500ms | < 1ms |
| 内存 | 5-110MB | < 1MB |
| 性能 | 接近原生 | 接近原生 (JIT) |
| 兼容性 | 完整 Linux | WASM 生态 |
| 适合 | 不可信容器/Serverless | 边缘函数/Plugin |

详见 [18-WebAssembly部署](./18-WebAssembly部署.md)。

### 10.2 与容器加固对比

```
容器加固 (runc 上):
  - seccomp: 限制 syscall
  - AppArmor/SELinux: MAC 策略
  - capabilities drop: 移除特权能力
  - user namespace: 容器内 root ≠ 宿主 root
  - readOnlyRootFilesystem: 只读根文件系统

强度: 中 (仍共享内核)
开销: 极小

MicroVM:
  - 完整内核隔离
  - 强度: 高
  - 开销: 5-110MB + 启动延迟

选型:
  - 内部可信集群: runc + 加固
  - 多租户/不可信: MicroVM
  - 极致安全: MicroVM + 加固
```

## 十一、面试速答

**Q1: Firecracker 为什么快?**

A: 1) 极简设计: 仅 4 个 virtio 设备, 无 PCI/USB/VGA; 2) 裁剪内核: 跳过 bootloader, 直接加载内核; 3) Rust 实现: 无 GC, 内存安全; 4) KVM 直通: 硬件虚拟化, 无模拟开销。125ms 启动, 5MB 内存。

**Q2: gVisor 与 Kata 区别?**

A: gVisor 用户态内核 (Sentry) 拦截 syscall, 仅必要 syscall 透传宿主, 隔离强度中, 文件 IO 慢 2-10x。Kata 用 QEMU+KVM 跑完整 Linux 内核, 隔离强度高, 兼容性好, 但启动慢 (1-2s), 内存大 (~100MB)。

**Q3: 容器逃逸怎么防范?**

A: 1) runc 加固: seccomp + AppArmor + capabilities drop + user namespace; 2) 高敏感用 Kata/Firecracker (硬件隔离); 3) 不可信代码用 gVisor/MicroVM; 4) 内核及时升级 (CVE 修复); 5) 最小权限原则。

**Q4: Serverless 函数用什么沙箱?**

A: AWS Lambda 用 Firecracker (自研, 开源), 启动 125ms, 内存 5MB, 单机万级并发。Fargate 用 Firecracker 跑容器。Modal 用 Firecracker + GPU 直通跑 Serverless GPU。Kata 启动太慢不适合 Serverless。

**Q5: AI Agent 代码执行沙箱怎么选?**

A: 1) Firecracker: 强隔离 + 快启动, 推荐 (E2B/Modal 都用); 2) gVisor: 中等隔离, 性能更好; 3) Docker: 弱隔离, 不推荐生产; 4) WASM: 最轻量, 适合简单代码 (18 章)。

## 十二、综合面试题

### 题 1（中级）：设计多租户 LLM 推理平台隔离方案

**答题要点**：

1. **租户分级**:
   - 高敏感 (金融/医疗): Kata Containers
   - 中敏感 (企业): gVisor
   - 低敏感 (公开 API): runc + 加固

2. **网络隔离**:
   - 每租户独立 namespace
   - NetworkPolicy 限制
   - 出站仅允许必要 endpoint

3. **存储隔离**:
   - 每租户独立 PVC
   - 加密 at-rest
   - 不共享 KV Cache (每租户独立实例或 namespace 隔离)

4. **GPU 隔离**:
   - 时间分片 (MPS) 或 vGPU
   - Kata + VFIO 直通 (高敏感)
   - 监控 GPU 利用率, 防止侧信道

5. **OPA 策略**:
   - 强制 RuntimeClass 与租户标签匹配
   - 强制 NetworkPolicy 存在
   - 强制 Pod Security Standards (restricted)

6. **监控**:
   - VM 内 agent 上报
   - 异常检测: 跨租户流量, 资源越界

### 题 2（高级）：Serverless GPU 平台的 MicroVM 架构

**答题要点**：

1. **挑战**:
   - GPU 启动慢 (CUDA 上下文, 模型加载)
   - GPU 资源稀缺, 不能像 CPU 那样高密度
   - 多租户共享 GPU 的安全

2. **方案**:
   - Firecracker + NVIDIA vGPU (时间分片)
   - 或 Kata + VFIO 直通 (独占 GPU)
   - 模型权重 Volume 共享 (不重复加载)
   - 快照恢复: 保存已加载模型的 VM 状态

3. **冷启动优化**:
   - 预启动池: 保持 N 个温热 VM (含模型)
   - 快照恢复: VM 状态 + GPU 状态恢复
   - CUDA 上下文池: 避免每次初始化

4. **隔离**:
   - 每函数独占 VM (强隔离)
   - GPU 直通或 vGPU (硬件隔离)
   - 网络: 仅控制面通信

5. **成本**:
   - 单 GPU 单机 8 卡
   - vGPU 分时: 8 卡 → 32 并发函数
   - 利用率: 30% → 70%

## 十三、故障复盘

### 13.1 案例 1：runc 逃逸 CVE-2019-5736

**背景**：2019 年 runc 容器逃逸漏洞, 攻击者通过容器内 `/proc/self/exe` 覆盖宿主 runc 二进制, 获取宿主 root。

**根因**：runc 进程在容器内可被覆盖, 后续 K8s 操作触发宿主执行被污染的 runc。

**修复**:
- runc 升级到 1.0-rc6+, 用 `/proc/self/exe` 不可写
- 容器用只读 rootfs
- user namespace (容器内 root ≠ 宿主 root)

**防范**：高威胁场景用 Kata/Firecracker, 容器逃逸不直达宿主。

### 13.2 案例 2：gVisor 性能引发投诉

**背景**：2024 年某公司对所有 Pod 强制 gVisor, 数据库 IO 慢 5x, 业务投诉。

**根因**：未按场景选 RuntimeClass, IO 密集用 gVisor 是灾难。

**修复**：
- 数据库用 runc + 加固
- 不可信代码用 gVisor
- 按业务域配置 RuntimeClass

**防范**：RuntimeClass 选型按场景, 不能一刀切。

### 13.3 案例 3：Kata 启动慢导致 Pod 调度超时

**背景**：2025 年某公司 Kata 容器启动 2s, 高峰期 Pod 调度超时。

**根因**：Kata QEMU 启动慢, 大规模并发调度时 API server 超时。

**修复**：
- 切换到 Cloud Hypervisor (启动 100ms)
- 内核裁剪 + 快照恢复
- 预启动 VM 池

**防范**：高并发场景评估 RuntimeClass 启动延迟。

### 13.4 案例 4：Firecracker 函数 OOM 雪崩

**背景**：2024 年某公司 Firecracker 池过大, 单机内存耗尽, 雪崩。

**根因**：未限制 pool size, 函数实例无限增长。

**修复**：
- pool size 上限 (按内存计算)
- LRU 淘汰空闲实例
- 监控内存使用率, 高水位拒绝新实例

**防范**：实例池必须配额管理, 否则单机不可控。

### 13.5 案例 5：GPU 直通导致宿主崩溃

**背景**：2025 年某公司 Kata + GPU 直通, 客户 GPU 驱动 bug 触发宿主 panic。

**根因**：GPU 直通绕过 hypervisor, guest GPU bug 直接影响宿主。

**修复**：
- 用 vGPU (虚拟化 GPU) 替代直通
- GPU 厂商驱动及时升级
- 监控 GPU ECC 错误, 自动隔离

**防范**：GPU 直通有风险, 评估后再用; 关键场景用 vGPU。
