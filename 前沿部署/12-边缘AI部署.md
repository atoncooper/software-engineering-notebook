# 12 - 边缘 AI 部署

> 边缘 AI 部署将推理从云端下沉到设备端：手机、车机、IoT、边缘服务器。本章梳理边缘推理运行时（ONNX Runtime/TFLite/Core ML/OpenVINO）、硬件适配、模型转换、性能基准。

## 二、问题定义与边界

### 2.1 解决什么

- **边缘推理运行时**：ONNX/TFLite/Core ML/OpenVINO 选型
- **硬件适配**：Jetson/Apple/手机/TPU
- **模型转换与压缩**：PyTorch → 边缘格式 + 量化
- **性能基准**：不同硬件的延迟与功耗

### 2.2 不解决什么

- 不深入模型压缩算法（06 章 + 13 章）
- 不覆盖端云协同（13 章）

## 三、直觉解释

### 3.1 为什么需要边缘 AI

```
云端推理:
  - 数据上传 (隐私风险)
  - 网络延迟 (100-500ms)
  - 持续成本 (按 token 计费)

边缘推理:
  - 数据本地 (隐私好)
  - 无网络延迟
  - 一次硬件成本
  - 但: 算力受限, 模型小
```

### 3.2 边缘硬件谱系

| 硬件 | 算力 (TOPS) | 功耗 | 典型延迟 (7B INT4) | 适用 |
|------|-------------|------|---------------------|------|
| Jetson Orin | 275 | 60W | 500ms | 机器人/车 |
| Apple M3 NPU | 18 | 5W | 200ms | Mac/iPad |
| iPhone 15 Pro | 35 | 3W | 800ms | 手机 |
| 高通 8 Gen 3 | 73 | 5W | 400ms | 安卓旗舰 |
| 边缘 TPU (Coral) | 4 | 2W | 不支持 7B | IoT |
| Intel NUC + NPU | 13 | 15W | 2s | 边缘服务器 |

### 3.3 边缘运行时对比

| 运行时 | 平台 | 模型格式 | 优势 |
|--------|------|----------|------|
| ONNX Runtime | 跨平台 | ONNX | 通用, 性能好 |
| TFLite | Android/IoT | TFLite | 移动优化 |
| Core ML | Apple | mlmodel | Apple NPU 加速 |
| OpenVINO | Intel | IR | Intel 硬件优化 |
| NCNN | 腾讯 | param | 移动优化, 开源 |
| MNN | 阿里 | mnn | 移动 + 边缘 |
| llama.cpp | 跨平台 | GGUF | LLM 专用, CPU 友好 |

## 四、核心概念与架构

### 4.1 ONNX Runtime 部署

```python
# PyTorch → ONNX → ONNX Runtime
import torch
import onnxruntime as ort

# 1. 导出 ONNX
model = load_pytorch_model()
dummy_input = torch.randn(1, 3, 224, 224)
torch.onnx.export(
    model, dummy_input, "model.onnx",
    input_names=["input"], output_names=["output"],
    dynamic_axes={"input": {0: "batch"}, "output": {0: "batch"}},
    opset_version=17,
)

# 2. 量化 (INT8)
from onnxruntime.quantization import quantize_dynamic, QuantType
quantize_dynamic("model.onnx", "model_int8.onnx", weight_type=QuantType.QInt8)

# 3. 推理
sess = ort.InferenceSession("model_int8.onnx", providers=["CUDAExecutionProvider"])
output = sess.run(None, {"input": input_data})
```

### 4.2 TFLite Android 部署

```kotlin
// Android Kotlin
val interpreter = Interpreter(loadModelFile("model.tflite"))
val input = Array(1) { Array(224) { FloatArray(224) } }
val output = Array(1) { FloatArray(1000) }
interpreter.run(input, output)
```

### 4.3 Core ML iOS 部署

```swift
// iOS Swift
import CoreML

let model = try MyModel(configuration: MLModelConfiguration())
let input = MyInput(input: pixelBuffer)
let output = try model.prediction(input: input)
```

### 4.4 llama.cpp LLM 边缘部署

```bash
# 1. 下载 GGUF 模型
wget https://huggingface.co/TheBloke/Llama-7B-GGUF/resolve/main/llama-7b-q4_k_m.gguf

# 2. 运行
./main -m llama-7b-q4_k_m.gguf -p "Hello" -n 100

# 3. 服务化
./server -m llama-7b-q4_k_m.gguf --port 8080
```

### 4.5 模型转换流程

```
PyTorch 模型
    ↓
ONNX (通用中间格式)
    ↓
量化 (INT8/INT4)
    ↓
硬件特定格式
  - ONNX Runtime: .onnx
  - TFLite: .tflite
  - Core ML: .mlmodel
  - OpenVINO: .xml + .bin
  - GGUF (llama.cpp): .gguf
```

## 六、底层原理

### 6.1 边缘推理的性能瓶颈

```
7B INT4 模型, 单 token:
- 加载权重: 3.5GB (INT4)
- Jetson 内存带宽: 102GB/s
- 理论最低: 3.5/102 = 34ms
- 实际: 33ms (接近理论)

iPhone 15 Pro:
- 内存带宽: 51GB/s
- 理论: 68ms
- 实际: 65ms

Apple M3:
- 内存带宽: 150GB/s
- 理论: 23ms
- 实际: 20ms
```

**结论**：边缘推理瓶颈是内存带宽，不是算力。

### 6.2 量化对边缘的影响

```
7B 模型不同精度:
- FP16: 14GB → 手机装不下
- INT8: 7GB → 旗舰手机勉强
- INT4: 3.5GB → 旗舰手机可装
- Q2_K: 2GB → 牺牲精度

边缘必量化 (INT4 起步)
```

### 6.3 NPU 加速

```
NPU (Neural Processing Unit):
  - 专为矩阵运算设计
  - 功耗远低于 GPU
  - 算力: 5-100 TOPS

Apple Neural Engine:
  - M3: 18 TOPS
  - A17 Pro: 35 TOPS
  - 自动 Core ML 加速

高通 Hexagon NPU:
  - 8 Gen 3: 73 TOPS
  - 自动 Qualcomm AI Engine 加速

挑战:
  - LLM 的动态 shape 与 NPU 优化冲突
  - NPU 对 attention 等复杂算子支持有限
  - 多用 GPU/CPU, NPU 用于视觉模型
```

## 七、代码与配置示例

### 7.1 边缘 LLM 服务（Jetson）

```python
# jetson_llm_server.py
from fastapi import FastAPI
from llama_cpp import Llama

app = FastAPI()
llm = Llama(
    model_path="/models/llama-3.2-3b-q4.gguf",
    n_ctx=4096,
    n_gpu_layers=-1,  # 全部 GPU
    n_threads=4,
)

@app.post("/generate")
def generate(prompt: str, max_tokens: int = 100):
    output = llm(prompt, max_tokens=max_tokens)
    return {"text": output["choices"][0]["text"]}
```

## 八、常见陷阱与调优

### 8.1 陷阱 1：模型太大装不下

**症状**：7B FP16 手机装不下。

**修复**：INT4 量化（3.5GB）。

### 8.2 陷阱 2：NPU 不支持 LLM

**症状**：Core ML 部署 LLM 性能差。

**修复**：用 llama.cpp 或 MLX，走 GPU/CPU 而非 NPU。

### 8.3 陷阱 3：内存不足

**症状**：3B 模型 4GB 手机 OOM。

**修复**：用 1B 模型或 Q2_K 量化。

### 8.4 陷阱 4：电池消耗快

**症状**：持续推理手机发烫。

**修复**：限制推理频率，降温节流。

### 8.5 调优 Checklist

- [ ] INT4 量化（边缘必做）
- [ ] 模型大小适配设备内存
- [ ] 用合适运行时（llama.cpp for LLM）
- [ ] 监控功耗与温度
- [ ] 降级机制（边缘跑不动转云端）

## 十一、面试速答

**Q1: 边缘 LLM 部署的瓶颈？**

A: 内存带宽。7B INT4 模型 3.5GB，单 token 加载 3.5GB，Jetson 带宽 102GB/s，理论 34ms。实际接近理论。

**Q2: 边缘 LLM 量化必做？**

A: 是。FP16 7B 模型 14GB，手机装不下。INT4 后 3.5GB，旗舰手机可装。

**Q3: NPU 适合 LLM 吗？**

A: 不太适合。NPU 适合视觉模型（固定 shape）。LLM 动态 shape 与 NPU 优化冲突，且 attention 等复杂算子 NPU 支持有限。LLM 多用 GPU/CPU。

**Q4: 边缘 LLM 运行时选型？**

A: LLM 用 llama.cpp（GGUF，跨平台，CPU 友好）或 MLX（Apple）。视觉模型用 ONNX Runtime / TFLite / Core ML。

**Q5: Apple Intelligence 如何部署？**

A: 3B 端侧模型 + Apple Silicon NPU/GPU + INT4 + 端云协同（端侧 70%，私有云 30%）。

## 十二、综合面试题

### 题 1（中级）：在 Jetson 上部署 Llama-3.2-3B

**答题要点**：
1. 量化：INT4 Q4_K_M（GGUF 格式）
2. 运行时：llama.cpp（CUDA 编译）
3. 配置：n_gpu_layers=-1, n_threads=4
4. 性能：30 tokens/s, 25W
5. 服务化：FastAPI + llama-cpp-python

### 题 2（高级）：设计手机端 LLM 应用

**答题要点**：
1. 模型：1B 或 3B INT4
2. 运行时：iOS 用 MLX/Core ML，Android 用 MNN/llama.cpp
3. 内存：限制 < 4GB
4. 功耗：限制推理频率，降温节流
5. 降级：边缘跑不动转云端
6. 隐私：默认端侧，敏感请求强制端侧
7. 体验：流式输出，UI 不阻塞
