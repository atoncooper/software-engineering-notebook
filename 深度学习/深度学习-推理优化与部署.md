## 1. 问题定义

### 1.1 推理 vs 训练的根本差异

| 维度 | 训练 | 推理 |
|------|------|------|
| 目标 | 收敛、泛化 | 低延迟、高吞吐、低成本 |
| 显存瓶颈 | 激活 + 优化器状态 | KV Cache + 权重 |
| 算力分布 | 前向 + 反向 (≈ 3×) | 仅前向 (1×) |
| Batch Size | 大 (32-2048) | 动态 (1-256) |
| 精度 | BF16/FP32 | INT8/INT4/FP8 |
| 通信 | AllReduce 梯度 | 无 (单卡) / KV 传输 (PD 分离) |

### 1.2 推理服务的关键 SLA

- **TTFT (Time To First Token)**: 首 token 延迟,影响交互体验。目标 < 200ms。
- **TPOT (Time Per Output Token)**: 单 token 生成时间。目标 < 30ms。
- **E2E Latency**: 端到端延迟 = TTFT + TPOT × (N-1)。
- **Throughput**: tokens/s/GPU,影响单位成本。
- **Goodput**: 满足 SLA 的吞吐,扣除慢请求。
- **P99 Latency**: 99 分位延迟,SLA 红线。

### 1.3 推理成本的冰山模型

```
可见成本 (25%)
├── GPU 折旧
├── 电费
└── 机架

隐藏成本 (75%)
├── 推理框架开销 (30%)
├── 量化精度损失返工 (15%)
├── 流量低估导致的过配 (15%)
└── 长尾请求慢拖垮整体吞吐 (15%)
```

## 2. 直觉解释

### 2.1 为什么推理优化比训练优化更复杂?

**训练是"批量优化"**:Batch Size 大,GPU 利用率高,优化方向明确(更快的 AllReduce、更大的 Batch)。

**推理是"流式优化"**:
- 用户请求长度不同(64-8192 tokens),动态批处理复杂
- Prefill 阶段 compute-bound(算力瓶颈),Decode 阶段 memory-bound(显存带宽瓶颈)
- KV Cache 随序列长度线性增长,长上下文场景显存爆炸
- 多用户并发,显存碎片化严重

### 2.2 Prefill vs Decode 的二象性

```
Prefill 阶段 (Prompt 处理):
- 并行计算所有 prompt token
- 算力密集 (GPU 利用率 60-80%)
- 生成初始 KV Cache
- 时间 ≈ O(L² × d) 但高度并行

Decode 阶段 (逐 token 生成):
- 自回归,每次 1 token
- 显存带宽密集 (GPU 利用率 5-15%)
- 读 KV Cache,写 1 行新 KV
- 时间 ≈ O(L × d),串行执行
```

**核心矛盾**: Prefill 吃算力,Decode 吃带宽。混合调度是关键。

### 2.3 Batch Size 的甜蜜点

```
Batch Size = 1 (单用户):
- GPU 利用率 < 10%
- 延迟最低,成本最高

Batch Size = N (多用户批处理):
- 利用率提升,但延迟增加
- KV Cache 显存线性增长

Continuous Batching (动态批处理):
- 每个迭代步可加入/移除请求
- 吞吐 8-15× 提升,延迟仅增 20%
```

## 3. 形式化推导 🎓

### 3.1 推理延迟数学模型

对于自回归 Transformer,L 个层,d_model 维度:

$$
T_{\text{prefill}} = \frac{2 \cdot L \cdot s^2 \cdot d}{\text{FLOPs/s}} + \frac{L \cdot s \cdot d \cdot b}{\text{BW}}
$$

其中 s = 序列长度,b = batch size。第一项为计算时间(attention 是 O(s²d)),第二项为访存时间。

$$
T_{\text{decode}} = \frac{2 \cdot L \cdot s \cdot d \cdot b}{\text{BW}} + \frac{L \cdot d \cdot b}{\text{FLOPs/s}}
$$

Decode 阶段每个 token 只需 O(s·d) 计算(attention 一次乘法),但需读取全部 KV Cache,所以是**访存密集**。

### 3.2 Roofline 模型

定义算力强度 $I = \text{FLOPs} / \text{Bytes}$,峰值算力 $\pi$,带宽 $\beta$:

$$
\text{Perf} = \min(\pi, \beta \cdot I)
$$

- 若 $I > \pi/\beta$:计算瓶颈,需量化或剪枝降低 FLOPs
- 若 $I < \pi/\beta$:访存瓶颈,需量化 KV Cache 或增大 Batch

**A100 数据**:
- $\pi$ = 312 TFLOPs (FP16)
- $\beta$ = 2.0 TB/s (HBM)
- 转折点 $I^* = 156$ FLOPs/Byte

Decode 阶段 $I \approx 2 \cdot d / d = 2$ FLOPs/Byte ≪ 156,**严重访存瓶颈**,所以 KV Cache 量化收益巨大。

### 3.3 KV Cache 显存公式

对于 L 层、d_model 维、b batch、s 序列长、k_v 多头 KV 数:

$$
M_{\text{KV}} = 2 \cdot L \cdot b \cdot s \cdot d_{\text{kv}} \cdot h_{\text{kv}} \cdot \text{dtype}
$$

**LLaMA-2 70B 例子** (L=80, d=8192, h_kv=8, d_kv=128, FP16):
- 单序列 s=4096: M_KV = 2 × 80 × 1 × 4096 × 128 × 8 × 2 = **640 MB**
- b=64 并发: M_KV = **40 GB** (超过权重本身)

### 3.4 量化误差传播

均匀量化到 INT8:

$$
x_q = \text{round}(x / s) \cdot s, \quad s = \frac{\max(|x|)}{127}
$$

量化误差 $\epsilon = x - x_q \in [-s/2, s/2]$。

经 LayerNorm 后误差被归一化抑制,但经 Softmax 后异常值(outlier)会放大误差,**SmoothQuant 的核心思想**就是把激活的异常值"smooth"到权重上。

## 4. 算法流程

### 4.1 量化算法 (PTQ - Post Training Quantization)

#### 4.1.1 GPTQ (Generalized Post-Training Quantization)

**核心思想**: 基于 OBQ (Optimal Brain Quantization),逐层用二阶信息(Hessian)最小化量化误差。

```
Input: 预训练模型 W, 校准集 D
Output: 量化模型 W_q

1. for each layer L:
    1.1 收集校准集激活 X = W @ X_input
    1.2 计算 Hessian H = X @ X^T
    1.3 for each column j of W (逆序):
        - 量化: q_j = quant(W[:, j])
        - 误差: e = (W[:, j] - q_j) / H[j,j]
        - 更新剩余列: W[:, j+1:] -= e @ H[j, j+1:]
2. 返回 W_q
```

#### 4.1.2 AWQ (Activation-aware Weight Quantization)

**核心思想**: 不是所有权重同等重要,激活幅度大的通道对应权重更敏感。

```
1. 在校准集上统计每通道激活幅度 s
2. 引入缩放因子 Δ,放大敏感通道权重:
   W' = W * Δ,  X' = X / Δ
3. 量化 W' 到 INT4
4. 推理时反量化: W * X = (W' / Δ) * (X' * Δ) = W' * X' / Δ * Δ
```

#### 4.1.3 SmoothQuant

**核心思想**: 激活异常值难以量化,迁移到权重上。

$$
Y = (X \cdot \text{diag}(s)^{-1}) \cdot (\text{diag}(s) \cdot W) = X' \cdot W'
$$

选择 s 使得 $X' = X/s$ 与 $W' = W \cdot s$ 的最大值相近。

### 4.2 知识蒸馏算法

#### 4.2.1 经典 Logit 蒸馏 (Hinton 2015)

```
Loss = α * CE(y, student_logits) + (1-α) * KL(softmax(teacher/T) || softmax(student/T)) * T²
```

温度 T 软化分布,捕捉 teacher 的"暗知识"(类间相似度)。

#### 4.2.2 LLM 时代的蒸馏 (Black-box)

- **数据蒸馏**: 用 GPT-4 生成 52K 指令数据,小模型 (Vicuna/Alpaca) SFT
- **行为克隆**: 模仿 teacher 的逐步推理 (Chain-of-Thought)
- **过程奖励**: teacher 评判 student 中间步骤

### 4.3 PagedAttention 算法 (vLLM)

**核心思想**: 借鉴 OS 虚拟内存,把 KV Cache 分成固定大小 block,消除碎片化。

```
传统 KV Cache:
请求 A (s=100): [..............................]  连续
请求 B (s=200): [........................................]  连续
碎片: 空间利用率 ~60%

PagedAttention:
Block 0: [A_0..A_15]
Block 1: [A_16..A_31, B_0..B_15]   <- 物理共享
Block 2: [B_16..B_31]
请求 A 映射: Block 0, Block 1 (前半)
请求 B 映射: Block 1 (后半), Block 2

每个请求维护 block table (类似页表)
```

**收益**:
- 显存碎片从 60% → 4%
- 吞吐 2-4× 提升
- 支持变长请求无缝批处理

### 4.4 Speculative Decoding

**核心思想**: 小模型 (draft) 先快速生成 k 个 token,大模型 (target) 一次性并行验证,接受/拒绝。

```
1. Draft 模型生成 k 个 token: x_1, x_2, ..., x_k (低成本)
2. Target 模型并行计算 P_target(x_1..x_k | context)
3. for i in 1..k:
       r = random()
       if r < P_target(x_i) / P_draft(x_i):
           accept x_i
       else:
           reject, 从 P_target - P_draft 重新采样
           break
4. 接受率 ρ 越高,加速越大 (理论加速 ≈ k × ρ / (1 + (k-1) × (1-ρ)))
```

**实际效果**:
- LLaMA-2 70B + 7B draft: 2-3× 加速,精度无损
- Medusa: 多头并行预测,1.5-2× 加速

### 4.5 Continuous Batching

```
传统 Static Batching:
  Batch [A, B, C] 同时开始
  A 生成 20 token 完成,B 生成 100 token,C 生成 50 token
  必须等 B 完成才能加入新请求 -> 长尾拖累

Continuous Batching:
  每个迭代步:
    1. 检查哪些请求已完成,移出 batch
    2. 从队列中拉新请求加入
    3. 全 batch 并行计算 1 token
  长短请求互不阻塞,吞吐 8-15× 提升
```

## 5. PyTorch 实现

### 5.1 从零实现:INT8 量化推理

```python
import torch
import torch.nn as nn

class LinearINT8(nn.Module):
    """对称量化 Linear 层,推理时反量化计算"""
    def __init__(self, in_features, out_features):
        super().__init__()
        self.in_features = in_features
        self.out_features = out_features
        # 量化参数
        self.register_buffer('weight_scale', torch.zeros(1))
        # INT8 权重存储为 int8
        self.register_buffer('weight_int8', torch.zeros(out_features, in_features, dtype=torch.int8))
        # FP16 偏置
        self.register_buffer('bias_fp16', torch.zeros(out_features, dtype=torch.float16))

    def quantize(self, weight_fp16):
        """校准时调用: 对称量化到 INT8"""
        max_abs = weight_fp16.abs().max()
        scale = max_abs / 127.0
        # 量化 + 反量化计算 scale
        w_int8 = (weight_fp16 / scale).round().clamp(-127, 127).to(torch.int8)
        self.weight_int8.copy_(w_int8)
        self.weight_scale.copy_(scale)

    def forward(self, x):
        # 反量化 weight 到 FP16 计算 (实际引擎用 INT8 内核)
        w_fp16 = self.weight_int8.to(torch.float16) * self.weight_scale
        return torch.nn.functional.linear(x, w_fp16, self.bias_fp16)


def calibrate_quantize(model, calibration_loader, device='cuda'):
    """PTQ 校准: 收集激活统计,逐层量化"""
    model.eval()
    # 注册 hook 收集输入统计
    activation_stats = {}
    def hook_fn(name):
        def hook(module, inp, out):
            if name not in activation_stats:
                activation_stats[name] = {'max': 0.0, 'count': 0, 'sum': 0.0}
            x = inp[0]
            activation_stats[name]['max'] = max(
                activation_stats[name]['max'],
                x.abs().max().item()
            )
            activation_stats[name]['count'] += 1
            activation_stats[name]['sum'] += x.sum().item()
        return hook

    hooks = []
    for name, module in model.named_modules():
        if isinstance(module, nn.Linear):
            hooks.append(module.register_forward_hook(hook_fn(name)))

    # 校准前向
    with torch.no_grad():
        for batch in calibration_loader:
            batch = batch.to(device)
            model(batch)

    for h in hooks:
        h.remove()

    # 量化每个 Linear
    for name, module in model.named_modules():
        if isinstance(module, nn.Linear) and name in activation_stats:
            quant_layer = LinearINT8(module.in_features, module.out_features).to(device)
            quant_layer.quantize(module.weight.data)
            quant_layer.bias_fp16.copy_(module.bias.data if module.bias is not None else 0)
            # 替换原层
            parent_name, _, child_name = name.rpartition('.')
            parent = model.get_submodule(parent_name) if parent_name else model
            setattr(parent, child_name, quant_layer)

    return model
```

### 5.2 从零实现:Speculative Decoding

```python
import torch
import torch.nn.functional as F

def speculative_decode(target_model, draft_model, prompt, max_new_tokens,
                       k=4, temperature=1.0):
    """
    target_model: 大模型 (target)
    draft_model: 小模型 (draft)
    k: draft 每次生成 token 数
    """
    input_ids = prompt.clone()
    finished = False
    generated = 0

    while not finished and generated < max_new_tokens:
        # 1. Draft 模型自回归生成 k 个 token
        draft_tokens = []
        draft_probs = []
        cur = input_ids
        for _ in range(k):
            with torch.no_grad():
                out = draft_model(cur)
            logits = out[:, -1, :] / temperature
            p = F.softmax(logits, dim=-1)
            next_tok = torch.multinomial(p, num_samples=1)
            draft_tokens.append(next_tok)
            draft_probs.append(p)
            cur = torch.cat([cur, next_tok], dim=1)

        draft_tokens = torch.cat(draft_tokens, dim=1)  # [1, k]
        draft_probs = torch.stack(draft_probs, dim=1)  # [1, k, V]

        # 2. Target 模型并行验证 (一次前向)
        verify_input = torch.cat([input_ids, draft_tokens], dim=1)
        with torch.no_grad():
            target_out = target_model(verify_input)
        # 取每个 draft token 位置的预测分布
        target_logits = target_out[:, input_ids.shape[1]-1:-1, :] / temperature
        target_probs = F.softmax(target_logits, dim=-1)

        # 3. 接受/拒绝
        accepted = 0
        for i in range(k):
            x = draft_tokens[0, i]
            p_target = target_probs[0, i, x].item()
            p_draft = draft_probs[0, i, x].item()
            r = torch.rand(1).item()
            if r < p_target / max(p_draft, 1e-10):
                accepted += 1
            else:
                # 拒绝,从 (target - draft) 重新采样
                adjusted = (target_probs[0, i] - draft_probs[0, i]).clamp(min=0)
                adjusted = adjusted / adjusted.sum()
                resampled = torch.multinomial(adjusted, num_samples=1)
                input_ids = torch.cat([input_ids, draft_tokens[:, :i], resampled.unsqueeze(0)], dim=1)
                break
        else:
            # 全部接受,bonus token (target 预测下一个)
            input_ids = torch.cat([input_ids, draft_tokens], dim=1)
            # target 最后一个位置的预测
            bonus = torch.multinomial(target_out[:, -1, :] / temperature, num_samples=1)
            input_ids = torch.cat([input_ids, bonus], dim=1)
            accepted += 1  # bonus

        generated += accepted
        if input_ids[0, -1].item() == eos_token_id:
            finished = True

    return input_ids
```

```python
"""
生产级 LLM 服务 - FastAPI + vLLM + Prometheus
"""
from fastapi import FastAPI, HTTPException
from fastapi.responses import StreamingResponse
from pydantic import BaseModel, Field
from vllm import LLM, SamplingParams
from prometheus_client import Counter, Histogram, generate_latest
import time
import asyncio
from typing import AsyncGenerator

app = FastAPI(title="LLM Inference Service")

# 指标
REQUEST_COUNT = Counter('llm_requests_total', 'Total requests', ['status'])
REQUEST_LATENCY = Histogram('llm_request_latency_seconds', 'Request latency',
                            buckets=[0.1, 0.5, 1, 2, 5, 10, 30, 60])
TOKENS_GENERATED = Counter('llm_tokens_generated_total', 'Tokens generated')

# 单例 LLM
llm = LLM(
    model="meta-llama/Llama-2-70b-hf",
    quant_config=QuantConfig(method="awq", bits=4),
    tensor_parallel_size=4,
    gpu_memory_utilization=0.9,
    max_model_len=4096,
    enable_prefix_caching=True,
)

class GenerateRequest(BaseModel):
    prompt: str = Field(..., max_length=8000)
    max_tokens: int = Field(512, ge=1, le=2048)
    temperature: float = Field(0.7, ge=0, le=2)
    top_p: float = Field(0.9, ge=0, le=1)
    stream: bool = False

    def validate_prompt(self):
        if not self.prompt.strip():
            raise ValueError("Prompt cannot be empty")
        # 简单的安全过滤
        if any(w in self.prompt.lower() for w in ['<script', 'javascript:']):
            raise ValueError("Unsafe content detected")

@app.post("/v1/generate")
async def generate(req: GenerateRequest):
    start = time.time()
    try:
        req.validate_prompt()
        sampling = SamplingParams(
            temperature=req.temperature,
            top_p=req.top_p,
            max_tokens=req.max_tokens,
        )
        outputs = llm.generate([req.prompt], sampling)
        text = outputs[0].outputs[0].text
        tokens = len(outputs[0].outputs[0].token_ids)

        REQUEST_COUNT.labels(status='success').inc()
        TOKENS_GENERATED.inc(tokens)
        REQUEST_LATENCY.observe(time.time() - start)
        return {"text": text, "tokens": tokens,
                "latency_ms": (time.time() - start) * 1000}
    except Exception as e:
        REQUEST_COUNT.labels(status='error').inc()
        raise HTTPException(status_code=500, detail=str(e))

@app.post("/v1/stream")
async def stream(req: GenerateRequest):
    """流式输出"""
    async def gen() -> AsyncGenerator[bytes, None]:
        sampling = SamplingParams(temperature=req.temperature, top_p=req.top_p,
                                  max_tokens=req.max_tokens)
        for output in llm.generate([req.prompt], sampling, use_tqdm=False):
            for tok in output.outputs[0].token_ids:
                chunk = tokenizer.decode([tok])
                yield f"data: {chunk}\n\n".encode()
        yield b"data: [DONE]\n\n"
    return StreamingResponse(gen(), media_type="text/event-stream")

@app.get("/metrics")
def metrics():
    return generate_latest()

# 启动: uvicorn server:app --host 0.0.0.0 --port 8000 --workers 1
```

## 6. 常见陷阱 ⚠️

| # | 陷阱 | 后果 | 解决方案 |
|---|------|------|----------|
| 1 | INT4 量化所有层 | 模型能力崩塌 (尤其 70B+ 上某些敏感层) | 混合精度,前几层和最后几层保留 FP16 |
| 2 | KV Cache 用 FP16 | 长 context 显存爆炸 | INT8/FP8 KV Cache,精度损失 < 1% |
| 3 | Static Batching | 长尾请求拖垮吞吐 | 用 Continuous Batching (vLLM/TGI) |
| 4 | 量化后不评估 | 线上业务质量回退 | 全套 benchmark: MMLU/HumanEval/MT-Bench |
| 5 | Tokenizer 与训练不一致 | 输出乱码 | 序列化 tokenizer 一并部署 |
| 6 | max_model_len 设置过大 | KV Cache 预分配挤占权重显存 | 按业务 P99 长度设,留 10% buffer |
| 7 | Prefix Caching 失效 | 重复 prompt 仍重算 | 保证 prompt 末尾对齐 + 一致 hash |
| 8 | LoRA 不合并 | 推理多一次 adapter forward | 服务化前 merge_and_unload() |
| 9 | Speculative 接受率低 | 加速反而变慢 | draft 模型与 target 同源,微调 draft |
| 10 | gpu_memory_utilization=1.0 | OOM 频繁 | 设 0.85-0.9,留 KV 增长空间 |
| 11 | Triton 动态 batching 队列过长 | P99 延迟超 SLA | max_queue_delay + preferred_batch_size |
| 12 | 未启用 CUDA Graph | decode 阶段 launch 开销大 | enforce_eager=False,固定 shape |
| 13 | 蒸馏只用 logit | student 学到 teacher 偏见 | 加 feature distillation + 多 teacher |
| 14 | 剪枝后不微调 | 精度暴跌 | 剪枝 → 微调 → 迭代 (Lottery Ticket) |
| 15 | 量化敏感层未识别 | 全局量化精度损失大 | 用 SensitivityScan 找敏感层,FP16 保留 |
| 16 | 流式输出 SSE 未设 keepalive | 长生成中断连接 | 加心跳 ping 每 10s |
| 17 | 多租户共享 model 无隔离 | 互推 prompt 串扰 | 系统 prompt 隔离 + rate limit |

## 7. 与其他方法关系

### 7.1 推理优化技术栈层次

```
┌──────────────────────────────────────────┐
│   应用层 (A/B test, Canary, RAG)          │  业务级
├──────────────────────────────────────────┤
│   服务层 (Triton, vLLM, TGI)              │  部署级
├──────────────────────────────────────────┤
│   解码层 (Speculative, Medusa)            │  算法级
├──────────────────────────────────────────┤
│   引擎层 (PagedAttention, FlashAttn)      │  系统级
├──────────────────────────────────────────┤
│   模型层 (LoRA, MoE, 蒸馏)                │  模型级
├──────────────────────────────────────────┤
│   算子层 (Tensor Core, INT8/FP8)          │  硬件级
└──────────────────────────────────────────┘
```

### 7.2 与训练优化的互补性

- **训练侧** (见 [[深度学习-分布式训练]]): 用 BF16 + ZeRO-3 训出大模型
- **推理侧** (本文): 用 INT4 + PagedAttention 部署上线
- **关键差异**: 训练吃算子精度,推理可更激进量化 (用校准集补精度)

### 7.3 与 Transformer 的关系

- 推理优化主要针对 [[深度学习-Transformer与注意力]] 中的注意力机制
- KV Cache 源于自回归特性
- PagedAttention 是对 KV Cache 的虚拟化管理
- FlashAttention 是对 Attention kernel 的 IO 优化

### 7.4 与生成模型的关系

- Diffusion 模型推理优化方向不同: **步数减少** (DDIM, DPM-Solver, Consistency Model)
- GAN 推理: 一次前向,优化重点在 batch
- LLM 推理: 自回归,优化重点在 KV Cache + 解码

### 7.5 推理引擎对比

| 引擎 | 强项 | 弱项 | 适用场景 |
|------|------|------|----------|
| **vLLM** | PagedAttention, 吞吐最高 | 仅支持主流模型 | 通用 LLM 服务 |
| **TGI** | HuggingFace 生态,易部署 | 性能略低 vLLM | 中小团队 |
| **TensorRT-LLM** | NVIDIA 极致优化,FP8 支持 | 编译复杂,版本绑定 | 大规模生产 |
| **llama.cpp** | CPU/Mac 友好,GGUF 格式 | 性能远低于 GPU | 边缘/个人 |
| **ONNX Runtime** | 跨平台,小模型最优 | LLM 优化少 | CV/小 NLP |
| **SGLang** | RadixAttention,结构化输出 | 社区较小 | 函数调用/JSON 输出 |
| **MLC-LLM** | 移动端/浏览器 | 大模型支持弱 | 端侧部署 |

## 8. 面试速答 ⭐

**Q1: 为什么 LLM 推理是 memory-bound?**

A: Decode 阶段每生成 1 token 需读取全部 KV Cache (L×2×d×s 字节),但仅做 1 次 attention + MLP (≈ L×d² FLOPs)。算力强度 I ≈ d/L ≈ 5-15 FLOPs/Byte,远低于 A100 转折点 156。GPU 利用率仅 5-15%。**优化方向**: 量化 KV Cache、增大 batch、PagedAttention。

**Q2: PagedAttention 解决什么问题?**

A: 解决 KV Cache 内存碎片化。传统连续分配下,变长请求导致内部+外部碎片,空间利用率 60%。PagedAttention 借鉴 OS 虚拟内存,把 KV Cache 分为固定 block (如 16 token/block),用 block table 映射逻辑-物理,碎片降至 4%,吞吐 2-4× 提升。还支持 Copy-on-Write 实现共享前缀 (Beam Search, Multi-sample)。

**Q3: INT4 量化 vs INT8 量化的取舍?**

A:
- INT8: 几乎无损 (< 1% MMLU 下降),显存减半,所有层可量化
- INT4: 1-3% 精度损失,显存 1/4,但需要校准 + 敏感层保留 FP16
- **关键**: 70B+ 模型 INT4 表现优秀,小模型 (7B-) INT4 损失大
- **方案**: 大模型用 AWQ INT4,小模型用 GPTQ INT8 或 BF16

**Q4: Speculative Decoding 的数学原理?**

A: Draft 模型生成 k 个 token,Target 模型一次前向并行验证。对每个 draft token x_i,以概率 min(1, P_target(x_i)/P_draft(x_i)) 接受。拒绝时从 (P_target - P_draft)+ 重新采样。**理论保证**: 最终分布严格等于 target 分布 (零偏差)。**加速比**: 取决于接受率 ρ,k 个 token 全接受概率 ρ^k,期望加速 ≈ (1-ρ^k)/(1-ρ)。

**Q5: LoRA 的本质是什么?为什么有效?**

A: LoRA 假设微调的权重更新 ΔW 是低秩的,ΔW = A·B (r<<d)。只训练 A、B,r=8 时参数降低 1000×。**有效原因**: 预训练大模型本就存在低秩"内在维度",微调不需改变全部参数。**QLoRA** 进一步把基模 4-bit 量化 + LoRA FP16 训练,70B 模型可在单 48G 显存微调。

**Q6: 推理服务的 P99 延迟如何优化?**

A:
1. **预填充与生成分离** (Prefill-Decode Disaggregation): 重计算用算力机器,生成用带宽机器
2. **优先级队列**: 交互请求优先,后台批处理低优先级
3. **缓存预热**: 常用 system prompt 预填充 KV
4. **限流降级**: 超过 SLA 时拒绝或返回简化结果
5. **GPU 亲和性**: 请求路由到缓存有该 prompt 的 GPU

**Q7: Prefill 和 Decode 为什么用不同策略?**

A: Prefill 算力密集 (s² d FLOPs),用大 batch + 高精度 (BF16) + FlashAttention;Decode 访存密集,用 INT4 权重 + INT8 KV + Continuous Batching + 小 batch 但多并发。**趋势**: Prefill-Decode 解耦 (PD disaggregation),两种阶段不同 GPU 池,各自最优配置。

**Q8: 如何评估量化质量?**

A: 多层次评估:
1. ** perplexity**: WikiText-2/C4 困惑度,1-3% 增加可接受
2. **下游任务**: MMLU (57 任务), HumanEval (代码), GSM8K (数学)
3. **指令跟随**: MT-Bench (GPT-4 评判), AlpacaEval
4. **长上下文**: LongBench, Needleshark
5. **生成质量**: 人工评估 + 偏好对比 (Arena Elo)
6. **公平性**: 性别/种族偏差指标

**Q9: Continuous Batching 的核心实现挑战?**

A:
1. **变长处理**: batch 内请求长度不同,padding 浪费
2. **KV Cache 管理**: 请求加入/退出时动态分配/释放
3. **同步**: 每个迭代步都要 sync 所有请求,慢请求拖累快请求
4. **调度策略**: 哪些请求组合到一起? (长度相近优先)
vLLM 用 PagedAttention + 迭代器模式优雅解决,每步可独立增减请求。

**Q10: 知识蒸馏在大模型时代的新形态?**

A: 传统 logit 蒸馏需要 teacher 参数,大模型不可行 (GPT-4 不开源)。新形态:
1. **黑盒蒸馏**: 调用 API 收集 5万-50万 instruction → SFT (Alpaca, Vicuna)
2. **行为蒸馏**: 模仿 CoT 推理轨迹 (phi 系列, Orca)
3. **过程奖励**: Teacher 评判 student 中间步骤 (PRM)
4. **合成数据**: GPT-4 生成多样化训练数据 (Evol-Instruct)
**关键**: 小模型 (7B) 可逼近 GPT-3.5 80% 性能,成本 1/100。

## 10. 工业案例

### 10.1 OpenAI GPT-4 推理架构 (推测)

**背景**: GPT-4 (MoE 1.8T 参数,8 expert × 220B),推理成本是 GPT-3.5 的 30×。

**关键技术** (基于公开信息推测):
- **MoE 路由**: top-2 expert,每 token 激活 280B
- **量化**: FP8 推理 (NVIDIA H100 原生支持)
- **Speculative Decoding**: 小 GPT-4 (推测 13B) 作 draft,加速 2-3×
- **PD 分离**: Prefill 用 H100 集群,Decode 用 A100 集群
- **路由**: 用户级别亲和 (history KV cache 命中)
- **成本**: \$0.03/1K input, \$0.06/1K output,毛利率 70%+

### 10.2 Anthropic Claude 3 推理

**架构特点** (基于 Anthropic 工程博客):
- **Long context**: 200K context,PagedAttention + Sliding Window Attention 混合
- ** Constitutional AI**: 服务层加 safety filter + red-team model
- **动态精度**: 短 prompt FP16,长 prompt INT8 KV
- **缓存层**: 系统 prompt + 用户 history 全局缓存
- **成本**: Haiku (\$0.25/M), Sonnet (\$3/M), Opus (\$15/M),梯度定价

### 10.3 字节豆包推理优化

**挑战**: 日活 6000 万,峰值 QPS 50K,成本控制严格。

**方案**:
- **自研引擎**: ByteInfer (类 vLLM),原生支持 MoE
- **量化**: 自研 PixelQueue INT4 + INT8 KV
- **PD 分离**: 国内首批大规模应用
  - Prefill: H800 集群 (4 卡)
  - Decode: A800 集群 (8 卡)
  - KV 通过 RDMA 传输,延迟 < 5ms
- **路由策略**: 用户 history 哈希到固定 GPU
- **弹性**: KEDA 基于 QPS 自动伸缩,峰谷 10×
- **成本**: \$0.002/千 tokens (国内最低)

### 10.4 阿里通义千问推理

**架构**:
- **ModelScope 推理**: 自研 EasyInfer
- **量化**: GPTQ INT4,模型库提供多版本
- **多模态**: Qwen-VL 流式视觉特征缓存
- **部署**: 阿里云 PAI-EAS,弹性 GPU
- **生态**: 开源 + 商业双轨,7B-72B 全谱系

### 10.5 Meta LLaMA 推理 (PyTorch + TensorRT)

**官方推荐**:
- **小规模**: PyTorch + flash-attention + BF16
- **大规模**: TensorRT-LLM + INT4 AWQ
- **代码生成**: Code Llama 用 FIM (Fill-in-the-Middle) 加速 IDE
- **开源**: 模型权重 + 推理代码全开源,推动生态

### 10.6 故障复盘: 某大厂线上 OOM 事件

**事件**: 70B 模型上线第 3 天,OOM 率从 0.1% 飙到 8%。

**排查**:
1. 监控显示 GPU 显存从 80G → 92G (超过 90% 阈值)
2. 日志显示部分请求 max_seq_len = 3900 (接近上限 4096)
3. PagedAttention block table 持续增长不释放

**根因**:
- 用户发现 prompt 注入 system 指令可改变输出 → 部分用户塞 4000 token 的"魔法 prompt"
- 没有请求长度限制 + KV Cache 没有定时清理

**修复**:
1. 加请求级限流: 单用户 100 req/min, prompt < 3500 token
2. KV Cache LRU 淘汰: 超 5 分钟未活跃请求强制释放
3. 显存水位监控: > 85% 触发拒绝新请求
4. P99 延迟从 8s → 2s,OOM 归零

### 10.7 vLLM vs TGI vs TensorRT-LLM Benchmark

**测试条件**: LLaMA-2 70B, 4×A100 80G, INT4 量化, 1024 input + 256 output

| 引擎 | Throughput (tok/s) | TTFT (ms) | TPOT (ms) | 显存利用率 |
|------|---------------------|-----------|-----------|------------|
| vLLM 0.6 | 4200 | 280 | 22 | 89% |
| TGI 1.4 | 3500 | 320 | 28 | 85% |
| TensorRT-LLM | 5800 | 220 | 18 | 92% |
| llama.cpp | 800 | 1200 | 80 | 70% |

**结论**:
- TensorRT-LLM 性能最优 (35%↑ vLLM),但编译复杂
- vLLM 综合最优,易用性 + 性能 + 社区
- TGI 适合 HF 生态深度用户
- llama.cpp 仅适合 CPU/边缘场景
