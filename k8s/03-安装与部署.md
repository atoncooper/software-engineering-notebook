# 03 - 安装与部署

> 从零搭建一个 K8s 集群有 5 条路径:kubeadm / kind / k3s / 云厂商托管 / 二进制。本章对比每种方案的适用场景、生产配置、踩坑经验,并给出工业级部署模板。

---

## 1. 问题定义与边界

### 1.1 本章解决什么

- 5 种主流安装方式的**适用场景**与**取舍**
- 生产级 kubeadm 集群的**完整步骤**(含 etcd HA / CNI / CCM)
- 二进制部署的**坑**(为什么生产不推荐)
- 托管 K8s(ACK / EKS / GKE / TKE)的**选型维度**
- k3s / kind 在**开发与边缘**的角色

### 1.2 不解决什么

- 不讲具体网络插件配置(见第 5、15 章)
- 不讲 Operator / Helm 部署(见第 04 章及后续)
- 不讲多集群联邦(见第 30 章)

## 3. 五种部署方案详解

### 3.1 kubeadm:生产自建首选

#### 3.1.1 定位

- CNCF 官方维护的 K8s 集群引导工具
- **不**做基础设施(机器、网络、OS)管理
- 只负责:K8s 控制平面初始化、节点加入、证书管理、升级

#### 3.1.2 生产级 HA 集群架构

```
       ┌─────────────────────────────────────┐
       │      External LB (HAProxy/Keepalived)│
       │       VIP: 10.0.0.100:6443           │
       └────┬──────────┬──────────┬──────────┘
            │          │          │
       ┌────▼───┐ ┌────▼───┐ ┌────▼───┐
       │master1 │ │master2 │ │master3 │
       │apisrv  │ │apisrv  │ │apisrv  │
       │sched   │ │sched   │ │sched   │
       │cm      │ │cm      │ │cm      │
       │etcd    │ │etcd    │ │etcd    │  ← 内嵌 etcd,堆叠模式
       └────┬───┘ └────┬───┘ └────┬───┘
            │          │          │
            └──────────┼──────────┘
                       │
       ┌───────────────┼───────────────┐
       │               │               │
   ┌───▼───┐      ┌────▼───┐      ┌────▼───┐
   │worker1│      │worker2 │      │worker3 │
   │kubelet│      │kubelet │      │kubelet │
   │proxy  │      │proxy   │      │proxy   │
   └───────┘      └────────┘      └────────┘
```

#### 3.1.3 部署前准备

**所有节点(3 master + N worker)**:

```bash
# 1. 关闭 swap(K8s 1.24+ 可选,但仍推荐关)
sudo swapoff -a
sudo sed -i '/swap/d' /etc/fstab

# 2. 内核模块
cat <<EOF | sudo tee /etc/modules-load.d/k8s.conf
overlay
br_netfilter
EOF
sudo modprobe overlay
sudo modprobe br_netfilter

# 3. sysctl
cat <<EOF | sudo tee /etc/sysctl.d/k8s.conf
net.bridge.bridge-nf-call-iptables  = 1
net.bridge.bridge-nf-call-ip6tables = 1
net.ipv4.ip_forward                 = 1
EOF
sudo sysctl --system

# 4. 容器运行时 (containerd)
sudo apt-get update && sudo apt-get install -y containerd
sudo mkdir -p /etc/containerd
containerd config default | sudo tee /etc/containerd/config.toml
# 修改 SystemdCgroup = true
sudo sed -i 's/SystemdCgroup = false/SystemdCgroup = true/' /etc/containerd/config.toml
sudo systemctl restart containerd
sudo systemctl enable containerd

# 5. 安装 kubeadm / kubelet / kubectl
sudo apt-get install -y apt-transport-https ca-certificates curl
curl -fsSL https://pkgs.k8s.io/core:/stable:/v1.30/deb/Release.key | \
  sudo gpg --dearmor -o /etc/apt/keyrings/kubernetes-apt-keyring.gpg
echo 'deb [signed-by=/etc/apt/keyrings/kubernetes-apt-keyring.gpg] https://pkgs.k8s.io/core:/stable:/v1.30/deb/ /' | \
  sudo tee /etc/apt/sources.list.d/kubernetes.list
sudo apt-get update
sudo apt-get install -y kubelet kubeadm kubectl
sudo apt-mark hold kubelet kubeadm kubectl
```

### 3.2 kind:本地开发与 CI 神器

#### 3.2.1 定位

- Kubernetes IN Docker —— 用 Docker 容器模拟 Node
- 单机启动多节点集群(含多 master)
- 主要用于:**本地开发 / CI 流水线 / K8s 自身 e2e 测试**

#### 3.2.2 安装

```bash
# Go 安装
go install sigs.k8s.io/kind@v0.23.0

# 或下载二进制
curl -Lo ./kind https://kind.sigs.k8s.io/dl/v0.23.0/kind-linux-amd64
chmod +x ./kind
sudo mv ./kind /usr/local/bin/
```

#### 3.2.3 多 master 集群配置

```yaml
# kind-config.yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
- role: control-plane
- role: control-plane
- role: control-plane
- role: worker
- role: worker
- role: worker
networking:
  podSubnet: "10.244.0.0/16"
  serviceSubnet: "10.96.0.0/12"
  disableDefaultCNI: true
  apiServerAddress: "127.0.0.1"
  apiServerPort: 6443
featureGates:
  EphemeralContainers: true
kubeadmConfigPatches:
- |-
  apiVersion: kubeadm.k8s.io/v1beta3
  kind: ClusterConfiguration
  metadata:
    name: config
  imageRepository: registry.k8s.io
  kubernetesVersion: v1.30.2
containerdConfigPatches:
- |-
  [plugins."io.containerd.grpc.v1.cri".registry.mirrors."docker.io"]
    endpoint = ["https://registry-mirror.example.com"]
```

```bash
kind create cluster --config kind-config.yaml --name my-cluster
kind load docker-image my-app:v1.0 --name my-cluster
kubectl get nodes
```

#### 3.2.4 使用场景

- **CI**:GitHub Actions / GitLab CI 中跑 K8s e2e 测试
- **开发**:本地写 Operator,在真 K8s(非 mock)上验证
- **测试**:版本兼容性测试(1.25 → 1.30 多版本并行)

### 3.3 k3s:边缘与轻量场景

#### 3.3.1 定位

- Rancher 出品,单二进制(< 70MB)
- 内嵌 sqlite 替代 etcd(可选 MySQL/Postgres/etcd)
- 内嵌 containerd + flannel + CoreDNS + metrics-server
- **去掉**云厂商特定代码、alpha API、StorageClass 等非核心
- 适合:**边缘 / IoT / 资源受限 / 单机生产**

#### 3.3.2 部署 server

```bash
curl -sfL https://get.k3s.io | sh -

# 查看状态
sudo k3s kubectl get nodes
sudo cat /etc/rancher/k3s/k3s.yaml   # kubeconfig
```

#### 3.3.3 多 master HA(需要外部数据库)

```bash
# master1
curl -sfL https://get.k3s.io | sh -s - server \
  --cluster-init \
  --tls-san 10.0.0.100

# master2 / master3
curl -sfL https://get.k3s.io | sh -s - server \
  --server https://10.0.0.10:6443 \
  --token <token>

# worker
curl -sfL https://get.k3s.io | K3S_URL=https://10.0.0.100:6443 \
  K3S_TOKEN=<token> sh -
```

#### 3.3.4 适合场景

- 边缘节点(树莓派 / 工控机)
- CI/CD 临时集群
- 个人本地 K8s(比 minikube 轻)
- 小规模生产(< 50 节点)

#### 3.3.5 与 K8s 差异

| 项 | k3s | k8s |
|----|-----|-----|
| 二进制大小 | ~70MB | ~500MB |
| etcd | sqlite 默认 | etcd 必须 |
| CNI | 内嵌 flannel | 需手动装 |
| Ingress | 内嵌 traefik | 需手动装 |
| 资源占用 | 512MB 起 | 2GB 起 |
| API 兼容 | 完全兼容 | - |

### 3.4 云厂商托管 K8s

#### 3.4.1 阿里云 ACK(阿里云容器服务)

**版本**:
- **ACK 托管版**:Control Plane 阿里托管,免费;worker 自管
- **ACK 专有版**:全集群自管,适合强合规
- **ACK Serverless**:无节点,按 Pod 计费,适合突发流量
- **ACK Edge**:边缘场景

**创建**:

```bash
  "region_id": "cn-hangzhou",
  "zoneid": "cn-hangzhou-h,cn-hangzhou-i,cn-hangzhou-j",
  "num_of_nodes": 3,
  "master_instance_type": "ecs.g6.large",
  "worker_instance_type": "ecs.g6.xlarge",
  "vpcid": "vpc-xxx",
  "container_cidr": "10.244.0.0/16",
  "service_cidr": "10.96.0.0/12",
  "pod_vswitch_ids": ["vsw-xxx"],
  "kubernetes_version": "1.30.2-aliyun.1",
  "snat_entry": true,
  "proxy_mode": "ipvs",
  "endpoint_public_access": true,
  "timezone": "Asia/Shanghai"
}'
```

**特色**:
- Terway(阿里自研 CNI,基于 ENI)
- Cloud Controller Manager 集成 CLB / ESS / EIP
- ACK Pro 版:Control Plane 监控告警
- 与日志服务 / 监控服务 / ACR 容器镜像深度集成

#### 3.4.2 AWS EKS

**创建**:
```bash
# 用 eksctl(官方推荐)
cat <<EOF > cluster.yaml
apiVersion: eksctl.io/v1alpha5
kind: ClusterConfig
metadata:
  name: prod-cluster
  region: ap-northeast-1
  version: "1.30"

- name: system
  instanceType: m6i.xlarge
  minSize: 3
  maxSize: 10
  desiredCapacity: 3
  volumeSize: 100
  ssh:
    allow: true
  iam:
    withAddonPolicies:
      autoScaler: true
      cloudWatch: true
      ebs: true
      fsx: true
      efs: true
  labels:
    role: system
  taints:
  - key: dedicated
    value: system
    effect: NoSchedule
vpc:
  clusterEndpoints:
    publicAccess:  true
    privateAccess: true
  subnets:
    private:
```

**特色**:
- IRSA(IAM Roles for Service Accounts):Pod 级 IAM 权限

- 与 CloudWatch / X-Ray / Fargate 集成

### 3.5 二进制部署

#### 3.5.1 为什么不推荐生产

- **复杂度高**:每个组件单独 systemd unit,证书手动签
- **升级困难**:逐组件停服升级
- **HA 配置繁琐**:LB / Keepalived / etcd 全手动
- **社区基本不维护**:K8s 1.20 后官方文档已弱化

#### 3.5.2 适合场景

- 学习理解 K8s 内部组件交互
- 极端定制(如内网完全隔离,无法用 kubeadm)
- 历史遗留集群

#### 3.5.3 步骤概览

```
1. 准备机器 + 证书(PKI)
2. 部署 etcd 集群(3 节点,Raft)
3. 部署 apiserver(2+ 副本,前置 LB)
4. 部署 controller-manager + scheduler(leader election)
5. 配置 kubeconfig(管理员 / 各组件)
6. 部署 kubelet(各 Node)
7. 部署 kube-proxy(各 Node)
8. 部署 CNI / CoreDNS
9. 验证
```

每个步骤都需手动管理证书、配置文件、systemd unit,且容易出错。**生产请用 kubeadm**。

## 4. 操作流程与命令

### 4.1 kubeadm 升级流程

```bash
# 1. 升级 kubeadm
sudo apt-get update
sudo apt-get install -y kubeadm=1.30.2-00
sudo kubeadm version

# 2. 验证升级计划
sudo kubeadm upgrade plan

# 3. 应用升级(在 master1 上)
sudo kubeadm upgrade apply v1.30.2

# 4. 升级其他 master
sudo kubeadm upgrade node

# 5. 升级 kubelet / kubectl(所有节点)
sudo apt-get install -y kubelet=1.30.2-00 kubectl=1.30.2-00
sudo systemctl restart kubelet

# 6. 驱逐 + 排水 worker(逐个)
kubectl cordon worker1
kubectl drain worker1 --ignore-daemonsets --delete-emptydir-data
# 在 worker1 上:升级 kubeadm + kubelet
sudo kubeadm upgrade node
sudo apt-get install -y kubelet=1.30.2-00
sudo systemctl restart kubelet
kubectl uncordon worker1
```

### 4.2 etcd 备份与恢复

```bash
# 备份
ETCDCTL_API=3 etcdctl snapshot save /backup/etcd-$(date +%Y%m%d).db \
  --endpoints=https://10.0.0.10:2379 \
  --cacert=/etc/etcd/ca.crt \
  --cert=/etc/etcd/peer.crt \
  --key=/etc/etcd/peer.key

# 验证备份
ETCDCTL_API=3 etcdctl snapshot status /backup/etcd-20260705.db --write-out=table

# 恢复(灾难恢复)
# 1. 停止所有 etcd
sudo systemctl stop etcd
sudo rm -rf /var/lib/etcd

# 2. 在每个 etcd 节点上恢复
ETCDCTL_API=3 etcdctl snapshot restore /backup/etcd-20260705.db \
  --data-dir=/var/lib/etcd \
  --name=etcd-01 \
  --initial-cluster=etcd-01=https://10.0.0.10:2380,etcd-02=https://10.0.0.11:2380 \
  --initial-cluster-token=etcd-cluster-prod \
  --initial-advertise-peer-urls=https://10.0.0.10:2380

# 3. 启动 etcd
sudo chown -R etcd:etcd /var/lib/etcd
sudo systemctl start etcd
```

### 4.3 证书管理

```bash
# 检查证书过期
sudo kubeadm certs check-expiration

# 续期所有证书(在控制平面节点)
sudo kubeadm certs renew all

# 重启控制平面组件(静态 Pod 自动重启)
sudo docker ps | grep -E "apiserver|controller|scheduler" | awk '{print $1}' | xargs sudo docker kill

# 续期 kubelet 证书(自动)
# kubelet 默认开启证书轮换,在过期前自动续期
```

### 4.4 Node 上下线

```bash
# 上线新 Node
sudo kubeadm join 10.0.0.100:6443 \
  --token <token> \
  --discovery-token-ca-cert-hash sha256:<hash>

# 离线 Node(优雅)

kubectl delete node node1
```

## 5. 底层原理:K8s 集群初始化的关键点

### 5.1 kubeadm init 做了什么

```
1. preflight checks
   ├─ 检查 OS 版本
   ├─ 检查 swap 关闭
   ├─ 检查端口(6443, 10250, 10257, 10259, 2379-2380)
   └─ 检查容器运行时

2. 生成 PKI
   ├─ CA (ca.crt / ca.key) - 10 年
   ├─ apiserver (apiserver.crt) - 1 年
   ├─ apiserver-kubelet-client
   ├─ front-proxy-ca / front-proxy-client
   ├─ etcd CA + server / peer / healthcheck
   ├─ service account (sa.key / sa.pub)
   └─ scheduler / controller-manager kubeconfig

3. 写 kubeconfig
   ├─ /etc/kubernetes/admin.conf
   ├─ /etc/kubernetes/kubelet.conf
   ├─ /etc/kubernetes/controller-manager.conf
   └─ /etc/kubernetes/scheduler.conf

4. 启动静态 Pod
   ├─ /etc/kubernetes/manifests/kube-apiserver.yaml
   ├─ /etc/kubernetes/manifests/kube-controller-manager.yaml
   ├─ /etc/kubernetes/manifests/kube-scheduler.yaml
   └─ /etc/kubernetes/manifests/etcd.yaml

5. 启动 kubelet(它负责拉起静态 Pod)

6. 配置 RBAC
   ├─ system:masters 组
   ├─ system:nodes 组
   ├─ Node authorizer
   └─ kubelet bootstrap token

7. 等待控制平面 Ready
   ├─ 等 apiserver /healthz 200
   ├─ 等 etcd quorum
   └─ 等 controller-manager / scheduler leader

8. 配置 cluster-info ConfigMap(用于 node bootstrap)

9. 上传证书到集群(用 secret,kubeadm cert)
```

### 5.2 kubeadm join 做了什么

```
1. preflight checks
2. 用 bootstrap token 发现 cluster-info
   ├─ GET https://api:6443/api/v1/namespaces/kube-public/configmaps/cluster-info
   └─ 验证 CA cert hash
3. TLS bootstrap
   ├─ 用 token 拿到临时 kubeconfig
   ├─ 创建 CSR (Certificate Signing Request)
   ├─ controller-manager 自动签发
   └─ 拿到正式证书
4. 写入 kubelet kubeconfig
5. 启动 kubelet
6. kubelet 上报 Node 信息
7. (control-plane join 额外)下载 control plane 证书 + 启动静态 Pod
```

### 5.3 kubeadm upgrade 的策略

```
1. 升级 kubeadm 工具本身
2. kubeadm upgrade apply(在 master1)
   ├─ 升级 PKI(必要时)
   ├─ 升级静态 Pod 镜像
   ├─ 升级 RBAC 规则
   └─ 升级 cluster-config
3. 其他 master:kubeadm upgrade node
4. 各 Node:升级 kubelet + kubectl
5. cordon + drain + upgrade + uncordon(逐 Node)
```

## 7. 常见陷阱与调优 ⚠️

### 7.1 部署阶段陷阱

| 陷阱 | 现象 | 根因 | 解决 |
|------|------|------|------|
| **swap 未关** | kubelet 启动失败 | K8s 默认禁用 swap | `swapoff -a`,改 /etc/fstab |
| **cgroup driver 不一致** | kubelet 报错 | containerd 用 cgroupfs,kubelet 用 systemd | 统一为 SystemdCgroup=true |
| **CNI 未装** | Pod 卡 ContainerCreating | kubeadm 不装 CNI | 装 Calico / Flannel / Cilium |
| **端口冲突** | apiserver 启动失败 | 6443 / 10250 被占 | netstat 检查,kill 占用进程 |
| **镜像拉不下来** | init 失败 | registry.k8s.io 国内访问慢 | 改用国内镜像源 |

### 7.2 网络陷阱

| 陷阱 | 现象 | 根因 | 解决 |
|------|------|------|------|
| **Pod 子网冲突** | Pod 无法通信 | podSubnet 与 Node 物理网段重叠 | 规划独立网段(10.244/16) |
| **Service IP 冲突** | Service 不通 | serviceSubnet 与已有 IP 冲突 | 改 10.96/12 |
| **DNS 不通** | Pod 解析失败 | CoreDNS 未就绪 / coredns ConfigMap 错 | 检查 CoreDNS Pod 状态 |
| **跨节点 Pod 不通** | 同集群不同 Node Pod 不通 | CNI 模式错(VXLAN vs BGP)/ 防火墙 | 检查 CNI 模式与 iptables |

### 7.3 证书陷阱

| 陷阱 | 现象 | 根因 | 解决 |
|------|------|------|------|
| **apiserver 证书过期** | kubectl 报 x509 expired | 默认 1 年过期 | kubeadm certs renew all |
| **证书 SAN 缺失** | 通过 VIP 连接失败 | certSANs 没加 VIP/域名 | 重新生成证书 |
| **kubelet 证书未轮换** | 节点失联 | 未启用 rotation | `--rotate-certificates=true` |

### 7.4 升级陷阱

| 陷阱 | 现象 | 根因 | 解决 |
|------|------|------|------|
| **跨版本升级** | apiserver 启动失败 | K8s 只能逐版本升级(1.28→1.29→1.30) | 严格逐版本 |
| **kubelet 版本超前** | kubelet 启动失败 | kubelet 不能比 apiserver 新 | 先升 apiserver,再 kubelet |
| **etcd 版本不兼容** | etcd 数据丢失 | 跨大版本未备份 | 升级前 snapshot save |

### 8.1 阿里 ACK 托管版生产实践

**场景**:某中型公司,从自建 K8s 迁移到 ACK。

**迁移前(自建)**:
- 3 master + 30 worker,3 运维 7×24 待命
- 每周 1-2 次故障(证书过期 / etcd 抖动 / 网络问题)

- 运维成本降低 70%(只管 worker)
- 升级一键,5 分钟完成
- 月成本约 ¥8k(托管费 + worker 节点)

**经验**:
1. **托管版的真正价值不是省钱,是省精力**
2. worker 节点用spot实例 + on-demand 混合,降本 40%
3. 监控用阿里云 ARMS(Prometheus 兼容),省自建监控集群

**部署经验**:

## 9. 与其他方案的关系

### 9.1 kubeadm vs Rancher vs Kubespray

| 工具 | 定位 | 优势 | 劣势 |
|------|------|------|------|
| **kubeadm** | 官方引导工具 | 官方维护,纯净 | 不做机器/网络管理 |
| **Rancher** | 多集群管理平台 | UI 友好,支持多 K8s 发行版 | 中心化 Rancher Server 是单点 |
| **Kubespray** | Ansible playbook | 自动化部署多节点 | 慢,改起来复杂 |
| **Cluster API** | 声明式集群管理 | K8s 管 K8s,生态新 | 学习曲线陡 |

### 9.2 自建 vs 托管

| 维度 | 自建 | 托管 |
|------|------|------|
| 初始成本 | 低(只机器) | 高(托管费) |
| 长期成本 | 高(运维人力) | 中(托管费 + 节点) |
| 控制力 | 完全 | 受限(Control Plane) |
| 升级 | 手动 + 风险 | 一键 + 厂商保证 |
| SLA | 自负 | 厂商背书 |
| 合规 | 完全可控 | 部分依赖厂商 |
| 故障恢复 | 自处理 | 厂商处理 |

**选型经验**:
- < 100 节点 + 上云:托管(ACK/EKS/GKE)
- 100-1000 节点 + 上云:托管 + 自管节点池
- > 1000 节点 + 强合规:自建 kubeadm
- 边缘 / IoT:k3s
- 开发 / CI:kind

## 11. 综合面试题

### 11.1 基础题

**Q1**: 描述 kubeadm init 的执行流程。

**答题要点**:
1. preflight checks(端口、OS、容器运行时、swap)
2. 生成 PKI(CA、apiserver、etcd 等)
3. 生成 kubeconfig(admin / kubelet / controller-manager / scheduler)
4. 写静态 Pod 清单到 /etc/kubernetes/manifests/
5. 启动 kubelet,kubelet 拉起静态 Pod(apiserver/controller/scheduler/etcd)
6. 配置 RBAC(Node authorizer + bootstrap token)
7. 等待控制平面就绪(apiserver /healthz + etcd quorum)
8. 上传 cluster-info ConfigMap(供 node join)

**Q2**: kubeadm join 的 TLS bootstrap 怎么工作?

**答题要点**:
- Node 用 bootstrap token 找到 apiserver
- 从 cluster-info ConfigMap 拿到 CA(验证 ca-cert-hash)
- 用 token 拿到临时 kubeconfig
- 创建 CSR(证书签名请求)
- controller-manager 自动签发(配置了 signing RBAC)
- Node 拿到正式证书,写入 kubelet.conf
- kubelet 启动,上报 Node 对象

### 11.2 进阶题

**Q3**: 生产级 K8s HA 集群怎么部署?需要哪些组件?

**答题要点**:
- 3+ master,跨可用区部署
- 外部 LB(HAProxy + Keepalived)给 apiserver 提供 VIP
- etcd 3/5 节点,Raft 多数派,同 AZ 部署优先
- apiserver 多副本,无状态
- scheduler / controller-manager 通过 leader election 单活
- worker 节点 ≥ 3,跨 AZ
- CNI(Calico / Cilium)+ CoreDNS + metrics-server
- 监控:Prometheus + Grafana
- 日志:Fluent Bit + Loki/ELK

**Q4**: kubeadm 升级 1.28 到 1.30 怎么做?

**答题要点**:
- 不能跨版本,必须 1.28 → 1.29 → 1.30 两次升级
- 步骤:
  1. 备份 etcd(snapshot save)
  2. apt install kubeadm=1.29
  3. kubeadm upgrade plan
  4. kubeadm upgrade apply v1.29(在 master1)
  5. 其他 master:kubeadm upgrade node
  6. 各 Node:apt install kubelet=1.29 kubectl=1.29
  7. cordon + drain + restart kubelet + uncordon(逐 Node)
  8. 验证集群健康
  9. 重复 1-8 升 1.30

**Q5**: 一个新集群装好后,Pod 之间不通,你怎么排查?

**答题要点**:
1. 检查 CNI 是否安装:`kubectl get pods -n kube-system | grep -E "calico|flannel|cilium"`
2. 检查 CNI Pod 是否 Running
3. 检查 Pod 是否拿到 IP:`kubectl get pod -o wide`
4. 在 Pod 内 ping 同 Node Pod:
   - 不通:检查 CNI 接口 + iptables
5. 在 Pod 内 ping 跨 Node Pod:
   - 不通:检查 CNI 跨节点模式(VXLAN/BGP)、防火墙
6. 检查 Service:
   - `kubectl get svc + endpoints`,endpoints 应有 Pod IP
   - 不通:检查 kube-proxy iptables/IPVS
7. 检查 DNS:
   - `kubectl exec -it pod -- nslookup kubernetes.default`
   - 不通:检查 CoreDNS

### 11.3 高级题

**Q6**: 设计一个跨 3 Region 的 K8s 多集群方案,要求 RTO < 5min。

**答题要点**:
- 每 Region 一个 K8s 集群(自建或托管),Control Plane 独立
- 全局 DNS(Route53 / 阿里云 GTM)按权重 / 延迟路由,健康检查 5s
- 跨集群 Pod 通信:Cilium ClusterMesh / Submariner / Istio Multi-Primary
- 全局 Service(同名 LB 跨集群)
- 数据库跨 Region 异步复制(TiDB / Spanner / Aurora Global Database)
- 应用层:无状态,任意集群可服务
- 配置同步:Argo CD ApplicationSet 推同一 Git 仓库
- 监控:Thanos Query 跨集群聚合
- 灾备:RTO 5min → DNS 切换 30s + 集群拉起 4min

**Q7**: 集群规模从 100 节点扩到 5000 节点,你会做哪些优化?

**答题要点**:
- **etcd**:
  - 升级到 5/7 节点 + local SSD
  - 启用 auto-compaction + 定期 defrag
  - 监控 fsync P99 < 10ms
- **apiserver**:
  - 多副本 + APF(优先级与公平性)
  - 增大 max-requests-inflight + watch cache
  - 监控 P99 < 100ms
- **kube-proxy**:
  - 切 IPVS 模式(必切,iptables 撑不住)
- **scheduler**:
  - 启用调度器多副本(leader)+ 调度框架优化
- **kubelet**:
  - max-pods 调到 250
  - image GC 阈值合理
- **网络**:
  - 节点子网规划 / Pod IP 池
  - CNI 模式:Calico BGP / Cilium eBPF
- **监控**:
  - Prometheus 分片 + Thanos
  - Pod 级 + Node 级 + 集群级
- **运维**:
  - 节点池(规格 + 用途)
  - 自动伸缩(Cluster Autoscaler)
  - 灰度发布(Argo Rollouts)

### 11.4 设计题

**Q8**: 设计一个 K8s 集群的灾备方案。

**答题要点**:
- **etcd 备份**:
  - 每日全量 + 每小时增量
  - 异地保存(S3 / OSS)
  - 定期恢复演练
- **控制平面**:
  - 多 master + 跨 AZ
  - 静态 Pod 配置备份(版本控制)
  - 证书自动轮换(cert-manager)
- **业务层**:
  - Deployment 跨集群部署(主备 / 双活)
  - 数据库主从 / 多活
  - 配置 GitOps(Argo CD)
- **恢复流程**:
  1. 评估故障范围(单集群 / 单 Region)
  2. DNS 切换到备用集群
  3. 数据库切主
  4. 应用层验证
  5. 故障集群恢复后切回
- **演练**:
  - 季度灾难恢复演练
  - 模拟 etcd 损坏 / master 全挂 / Region 失联
  - RTO / RPO 度量

## 12. 故障复盘

### 12.1 案例 1:kubeadm 升级导致 etcd 数据不一致

**业务影响**:2023 年某公司从 1.27 升级到 1.28,etcd 升级到 3.5.10,升级后部分 Pod 状态丢失,apiserver 报错 `etcdserver: mvcc: required revision has been compacted`。

**根因**:
- 升级前未做 etcd 快照
- etcd 新版本默认 compaction 间隔不同
- 升级过程中 etcd 重启,部分 Watch 连接断开,Informer 缓存与 etcd 不一致

**修复过程**:
1. 紧急:回退 apiserver 到 1.27(快)
2. 验证:etcd 数据完整(`etcdctl get --prefix / --keys-only | head`)
3. 重启所有 controller 的 Informer(重启 controller-manager)
4. 业务 Pod 重新同步

**防范**:
- 升级前必做 etcd snapshot
- 升级窗口选低峰
- 准备好回滚方案(版本回退 + etcd 恢复)
- 升级后验证:Pod 数 / Service 数 / Deployment 数与升级前一致

### 12.2 案例 2:Calico CNI 安装错版本导致 Pod 网络不通

**业务影响**:2022 年某公司,K8s 1.26 + Calico v3.21(版本不匹配),Pod 拿到 IP 但跨 Node 不通,持续 6 小时。

**根因**:
- Calico v3.21 不支持 K8s 1.26 的某些 API
- Calico Pod Running 但 IPAM 模块报错
- 跨 Node Pod IP 在 IPAM 中重复分配

**修复过程**:
1. 紧急:删除所有 Calico Pod,清空 IPAM 数据
2. 升级 Calico 到 v3.27(匹配 K8s 1.26)
3. 重新分配 Pod IP
4. 业务逐个重启

**防范**:
- 安装前查阅组件版本兼容矩阵
- 测试环境验证后上生产
- 监控 CNI Pod 日志(`kubectl logs -n kube-system -l k8s-app=calico-node`)

### 12.3 案例 3:托管 K8s 升级失败导致业务中断

**业务影响**:2024 年某公司用阿里云 ACK 托管版,自动升级到 1.30,因 PodDisruptionBudget 配置错,导致滚动升级中 worker 节点 drain 失败,部分 Pod 卡 Pending,业务 5xx 错误率上升。

**根因**:
- PDB minAvailable=100%(写错,本意 50%)
- ACK 升级 worker 时,drain 节点要求 PDB 满足,PDB 不允许任何 Pod 不可用
- 节点无法 drain,升级卡死,部分节点已是新版本,部分是旧版本
- 调度器在新版本节点调度失败(CNI 版本不一致)

**修复过程**:
1. 紧急:取消升级(无法,部分节点已升)
2. 手动修复 PDB:minAvailable=50%
3. 逐节点 cordon + drain + uncordon
4. 验证业务

**防范**:
- PDB 配置严格 review
- 升级前预演(在测试集群)
- 关键业务预留 50% 余量
- 监控升级过程,异常立即中止
