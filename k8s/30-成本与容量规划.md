# 30. 成本与容量规划

> 关键词:FinOps、资源利用率、混部(Co-location)、HPA + CA + Spot、Request/Limit、超卖、Koordinator、Kubecost、OpenCost、Karpenter、Showback/Chargeback、Serverless 容器、GPU 共享

## 30.1 问题定义与边界

### 30.1.1 核心问题

K8s 集群在规模化运行后,会暴露三类「钱的问题」:

1. **资源利用率低**:大部分企业集群平均 CPU 利用率 15-25%,内存 30-40%,意味着 70%+ 的钱在「烧闲置」。
2. **成本不可见**:业务方不知道自己用的 Pod 每月花多少钱,平台方不知道哪些租户在亏钱。
3. **弹性不可控**:流量来了扩不出节点,流量走了节点不释放,要么宕机要么烧钱。

> **核心问题**:如何让 K8s 集群在 **保证 SLO** 的前提下,把资源利用率从 20% 推到 60%+,同时让每一块钱的成本可追溯、可分摊、可优化?

### 30.1.2 容量规划的边界

容量规划要回答四个问题:

| 问题 | 时间尺度 | 决策 |
|------|---------|------|
| 现在够不够 | 小时级 | HPA / VPA / CA 弹性 |
| 下个月够不够 | 周级 | 节点池预留、Reserved Instance 续约 |
| 下个季度够不够 | 月级 | 集群扩容、机房上架 |
| 下一年够不够 | 季级 | 多云规划、自建 vs 云上 |

**本章边界**:
- 解决:K8s 集群内的资源利用率、成本核算、弹性策略、混部
- 不解决:跨云采购谈判、IDC 选址、硬件采购周期
- 关联:与 [10-HPA-VPA-CA](./10-HPA-VPA-CA.md)、[08-调度器](./08-调度器.md)、[25-大厂K8s平台](./25-大厂K8s平台.md)、[26-大规模集群优化](./26-大规模集群优化.md) 紧密耦合

### 30.1.3 成本爆炸的典型场景

```
场景 1:Request 过高
  Pod Request CPU = 4 core,实际只用 0.3 core
  100 个 Pod → 申请 400 core,实际用 30 core
  浪费 370 core × 0.5元/h × 24h × 30d = 13.3万/月

场景 2:Limit 过高导致超卖失效
  节点 64 core,超卖比 3:1,理论可调度 192 core Request
  但 Limit 都设为 8 core,实际峰值时 8×8=64 core 满载,只剩 8 个 Pod 抢 CPU
  → 业务延迟飙升,实际密度和理论密度差 3 倍

场景 3:Spot 雪崩
  集群 80% 节点是 Spot,某云厂商 Spot 大规模回收
  5 分钟内 200 个节点被驱逐,3000 个 Pod 重新调度
  → 业务大面积 504, fallback 到 On-Demand 又涨成本 3 倍

场景 4:网络成本爆炸
  跨可用区流量 0.5元/GB,某业务每天同步 2TB 数据
  月网络费 = 2TB × 30 × 0.5 = 3万/月,比节点费还贵
  → 没人发现,因为网络费在云账单里被节点费淹没
```

### 30.1.4 FinOps 的三个阶段

FinOps 基金会定义了三个阶段:

```
Inform(告知)
  - 看到成本:账单接入、标签完整、分摊到租户
  - 工具:Kubecost / OpenCost / 云厂商成本管家
  - 产出:租户级成本报表

Optimize(优化)
  - 降低成本:Right-size、Reserved、Spot、混部
  - 工具:VPA、Karpenter、Koordinator
  - 产出:利用率提升、单 Pod 成本下降

Operate(运营)
  - 持续闭环:告警、预算、Anomaly Detection
  - 工具:Prometheus + AlertManager + 自建预算系统
  - 产出:成本 SLO、预算审批流程
```

## 30.2 直觉解释

### 30.2.1 成本公式

把 K8s 成本拆成最简形式:

```
月度成本 = 节点成本 + 存储成本 + 网络成本 + License 成本 + 管理费

节点成本 = Sigma(实例类型单价 × 数量 × 时长)
  - On-Demand:0.5元/vCPU·h(标准)
  - Reserved(1年):0.3元/vCPU·h(6折)
  - Spot:0.1-0.2元/vCPU·h(2-4折)
  - 自建:0.2-0.3元/vCPU·h(摊销)

存储成本 = Sigma(GB × 单价 × 时长)
  - SSD:0.5元/GB·月
  - HDD:0.1元/GB·月
  - 对象存储:0.12元/GB·月
  - 快照:0.15元/GB·月

网络成本 = 跨可用区流量 + 跨区域流量 + 公网出口
  - 跨 AZ:0.5元/GB
  - 跨 Region:0.8元/GB
  - 公网出口:0.5元/GB

License 成本 = 商业镜像 + 商业 Operator + 商业监控
  - RHEL 镜像:0.2元/vCPU·h
  - 商业 Istio:按 Pod 数
  - Datadog:15元/主机/月
```

### 30.2.2 资源利用率提升路径

把利用率提升想象成「挤地铁」:

```
阶段 1(20%):所有人各自打车
  - 每个业务独占节点
  - Request = Limit = 实际峰值
  - 浪费大,但稳定

阶段 2(40%):拼车
  - 多个业务共享节点
  - Request < Limit,允许超卖
  - CPU 超卖 1.5:1,内存 1.2:1

阶段 3(60%):高峰+平峰混跑
  - 在线业务(白天高峰)+ 离线任务(夜间跑)
  - CPU 超卖 3:1,内存 1.5:1
  - 用 Koordinator / BatchScheduler 调度

阶段 4(70%+):Borg 级别
  - 严格优先级 + 抢占
  - 在线业务随时抢占离线
  - 离线任务用「碎片资源」
  - 全自动 Right-size
```

### 30.2.3 FinOps 直觉:让业务方看到钱

> 「业务方看不到钱,就不会省钱。」

```
传统模式(黑盒):
  业务方提需求 → 平台方扩节点 → 云账单爆炸 → 老板骂平台方

FinOps 模式(白盒):
  业务方提需求 → 平台方报价 → 业务方确认预算 → Showback 报表
  → 业务方主动 Right-size → 成本下降 30%+
```

### 30.2.4 弹性策略组合的直觉

```
流量稳定型(数据库):
  Reserved Instance + 固定 Pod → 成本最低

流量波动型(Web/API):
  HPA + On-Demand → 自动扩缩
  + Spot → 低成本兜底

突发型(秒杀/AI 训练):
  KEDA 事件驱动 + Karpenter 秒级扩节点 + Spot
  → 突发容量 + 低成本

离线型(批处理/ETL):
  Koordinator 混部 + Spot + Volcano 批调度
  → 用碎片资源,几乎免费
```

### 30.3.2 资源对象模型

K8s 中所有可计费的资源:

```
计算资源:
  - CPU:单位 millicore(m),1 core = 1000m
  - Memory:单位 Byte,常用 Mi/Gi
  - GPU:单位(card),nvidia.com/gpu
  - GPU 共享:aliyun.com/gpu-mem(阿里)、volcano.sh/gpu-memory

存储资源:
  - ephemeral-storage:本地临时存储(emptyDir、hostPath)
  - persistent-volume:持久化存储(PV/PVC)
  - 对象存储:S3/OSS(不进 K8s 调度,但算钱)

网络资源:
  - 网络带宽(节点级):通常不限制
  - 网络流量(跨 AZ/Region):云厂商计费
  - Pod 级带宽:Cilium Bandwidth Manager
```

### 30.3.3 Request 与 Limit 的双重含义

```
Request:
  - 调度依据:scheduler 按 Request 选节点
  - 计费依据:Kubecost 按 Request 算成本
  - QoS 依据:Guaranteed/Burstable/BestEffort

Limit:
  - 运行时上限:cgroup 限制
  - 超过 Limit:CPU 节流 / Memory OOM
  - 不参与调度,但影响实际密度

三档 QoS:
  Guaranteed:Request == Limit(最高优先级,最稳定)
  Burstable:Request < Limit(常见,允许突发)
  BestEffort:无 Request/Limit(最低优先级,先被驱逐)
```

### 30.3.5 Showback vs Chargeback

| 模式 | 含义 | 适用阶段 |
|------|------|---------|
| Showback | 显示成本,但不真扣钱 | FinOps 早期,培养意识 |
| Chargeback | 真扣钱,从业务方预算扣除 | FinOps 成熟期,强制优化 |

```
Showback 报表示例:
  租户:订单团队
  月份:2026-06
  Pod 数:120
  CPU 申请:480 core
  CPU 实际使用:180 core(37%)
  内存申请:960 GB
  内存实际使用:520 GB(54%)
  应付成本:86,400元
  优化建议:CPU Request 可下调至 240 core(省 21,600元/月)
```

### 30.3.7 混部(Co-location)架构

```
┌──────────────────────────────────────────────┐
│              混部节点(单机视角)              │
├──────────────────────────────────────────────┤
│                                              │
│   在线业务(LS, Latency-Sensitive)          │
│   ┌────────────────────────────────────┐     │
│   │ Pod A:API Server(QoS Guaranteed) │     │
│   │ Pod B:Web Server (QoS Guaranteed) │     │
│   │ Pod C:DB          (QoS Guaranteed)│     │
│   └────────────────────────────────────┘     │
│   ▲ 高优先级,绝对优先调度                    │
│   │                                          │
│   │ CPU Manager static pinning              │
│   │ Memory Manager hugepages                │
│   │                                          │
│   ▼ 离线任务(BE, Best-Effort)              │
│   ┌────────────────────────────────────┐     │
│   │ Pod X:Spark Executor(QoS BE)      │     │
│   │ Pod Y:Tensorflow  (QoS BE)        │     │
│   │ Pod Z:ETL Job     (QoS BE)        │     │
│   └────────────────────────────────────┘     │
│   ▲ 低优先级,用碎片资源                      │
│   │                                          │
│   │ cgroup cpu.shares = 2(在线=1024)       │
│   │ 网络优先级 = best-effort                  │
│   │ I/O 优先级 = best-effort                  │
│                                              │
└──────────────────────────────────────────────┘

混部核心思想:
  在线业务优先,离线任务用「边角料」
  在线突发时,抢占离线资源
  离线任务能容忍中断,可被驱逐
```

### 30.3.8 Spot 实例模型

```
Spot 实例生命周期:
  申请 → 运行 → 中断通知(2分钟)→ 回收

中断原因:
  1. 容量不足:云厂商容量回收
  2. 价格高于 On-Demand:Spot 价格随供需浮动
  3. 用户主动释放

中断处理:
  - Pod Disruption Budget:限制同时驱逐数
  - Node Termination Handler:监听中断,优雅排水
  - Karpenter:自动用其他实例类型补充
  - Multi-AZ:分散风险,避免单 AZ 集中驱逐
```

### 30.3.10 GPU 成本模型

```
GPU 是 K8s 中最贵的资源,单价参考:
  - NVIDIA A100 80GB:~15,000元/月(云上按需)
  - NVIDIA H100 80GB:~30,000元/月(云上按需)
  - NVIDIA T4 16GB:~2,500元/月
  - 自购 A100:~80,000元/张(一次性)

GPU 调度模式:
  1. 独占(Exclusive):1 Pod 占 1 GPU,利用率低(20-30%)
  2. MPS(Multi-Process Service):多 Pod 共享 1 GPU,内核级隔离
  3. MIG(Multi-Instance GPU):A100/H100 硬件分区,最多 7 实例
  4. vGPU(时间片):NVIDIA vGPU 软件,硬件虚拟化
  5. 池化(GPU Pooling):阿里 GPU Pooling,动态切分

GPU 共享的 K8s 集成:
  - nvidia.com/gpu(原生,独占)
  - nvidia.com/mig-1g.10gb(MIG 切分)
  - aliyun.com/gpu-mem(阿里云按显存切分)
  - volcano.sh/gpu-memory(Volcano 批调度)
```

## 30.4 操作流程与命令

### 30.4.1 资源使用查询

```bash
# 1. 查看节点资源
kubectl top nodes
kubectl describe node <node-name> | grep -A 10 "Allocated resources"

# 2. 查看 Pod 资源
kubectl top pods --all-namespaces
kubectl top pods -n default --sort-by=cpu

# 3. 查看集群整体分配
kubectl get nodes -o json | jq '.items[] | {
  name: .metadata.name,
  cpu_alloc: .status.allocatable.cpu,
  mem_alloc: .status.allocatable.memory,
  cpu_cap: .status.capacity.cpu
}'

# 4. metrics-server 检查
kubectl get apiservice v1beta1.metrics.k8s.io -o yaml
kubectl get deployment metrics-server -n kube-system
```

### 30.4.2 Prometheus 资源查询

```promql
# 1. 集群 CPU 利用率
sum(rate(container_cpu_usage_seconds_total{container!="POD",container!=""}[5m])) by (node)
/
sum(kube_pod_container_resource_limits{resource="cpu"}) by (node)

# 2. Pod CPU 使用率(相对 Request)
sum(rate(container_cpu_usage_seconds_total{namespace="prod"}[5m])) by (pod)
/
sum(kube_pod_container_resource_requests{namespace="prod", resource="cpu"}) by (pod)

# 3. 内存使用率
sum(container_memory_working_set_bytes{container!="POD",container!=""}) by (node)
/
sum(kube_node_status_allocatable{resource="memory"}) by (node)

# 4. 找出 CPU 使用率低于 10% 的 Pod(可 Right-size)
sum(rate(container_cpu_usage_seconds_total[1h])) by (namespace, pod) < 0.1

# 5. 找出 Request 远高于使用的 Pod(浪费)
(
  sum(kube_pod_container_resource_requests{resource="cpu"}) by (namespace, pod)
  -
  sum(rate(container_cpu_usage_seconds_total[1h])) by (namespace, pod)
) > 1

# 6. 节点超卖比
sum(kube_pod_container_resource_requests{resource="cpu"}) by (node)
/
kube_node_status_allocatable{resource="cpu"}

# 7. Pending Pod(资源不足)
kube_pod_status_unschedulable

# 8. HPA 接近扩容阈值
hpa_status_current_metrics_average_utilization > 80
```

### 30.4.3 Kubecost 部署与查询

```bash

helm repo update

helm install kubecost kubecost/cost-analyzer --namespace kubecost --create-namespace --set kubecostToken="..." --set prometheus.server.persistentVolume.size=200Gi --set persistentVolume.size=32Gi --version 1.108.0
```

### 30.4.4 OpenCost 部署

OpenCost 是 Kubecost 的开源核心,完全 CNCF 项目:


## 30.5 底层原理

### 30.5.1 Request/Limit 与调度的关系

K8s 调度器只看 Request,不看 Limit:

```
节点状态:
  Capacity(物理容量):64 CPU, 256 GB
  Allocatable(可分配):63 CPU, 250 GB(扣系统预留)

调度决策:
  scheduler.Filter:node.Request + pod.Request <= node.Allocatable
  scheduler.Score:Bin Packing / Spread

cgroup 设置(kubelet):
  cpu.shares = Request.cpu * 1024(权重)
  cpu.cfs_quota_us = Limit.cpu * 100000(限流)
  cpu.cfs_period_us = 100000
  memory.limit_in_bytes = Limit.memory(硬限制)

举例:
  Pod A: Request=2 core, Limit=4 core
  -> cpu.shares = 2048(相对权重)
  -> cpu.cfs_quota_us = 400000(每 100ms 最多用 40ms CPU)
  -> 实际能用 4 core(如果有空闲)
  -> 调度时按 2 core 算
```

### 30.5.2 CPU Manager static 模式

```
CPU Manager 策略:
  - none(默认):不绑核,cgroup shares 调度
  - static:Guaranteed Pod 整核绑定

static 模式工作原理:
  1. Pod 必须是 Guaranteed(Request == Limit,且都是整数核)
  2. kubelet 从 cpuset.cpus 分配独占核
  3. 该核不参与 CFS 调度,不被其他 Pod 抢占
  4. 适合低延迟、CPU 敏感业务(数据库、网关)

kubelet 配置:
  /var/lib/kubelet/config.yaml:
    cpuManagerPolicy: static
    reservedSystemCPUs: "0,1"  # 系统保留核

cpuset 文件:
  /sys/fs/cgroup/cpuset/kubepods/pod<pod-id>/<container-id>/cpuset.cpus
  例:0-3 (绑定 0,1,2,3 四个核)
```

### 30.5.3 Memory Manager

K8s 1.21+ 引入 Memory Manager,为 Guaranteed Pod 提供 hugepages 支持:

```
Memory Manager 工作原理:
  1. Pod 申请 hugepages-2Mi 或 hugepages-1Gi
  2. kubelet 从节点预留的 hugepages 池中分配
  3. 与 CPU Manager 协同(NUMA 亲和)

kubelet 配置:
  memoryManagerPolicy: Static
  reservedMemory:
  - numaNode: 0
    limits:
      memory: 1Gi
      hugepages-2Mi: 500Mi

适用场景:
  - DPDK(数据面网络)
  - 大内存数据库(Oracle、SAP HANA)
  - ML 推理(避免 TLB miss)
```

### 30.5.4 ResourceQuota 与 LimitRange

```
ResourceQuota(命名空间级配额):
  - 限制 ns 总 Request/Limit
  - 限制 Pod/Service/PVC 数量
  - 强制 ns 内每个 Pod 必须设 Request

LimitRange(默认值与上下限):
  - 给没设 Request 的 Pod 自动填默认值
  - 限制单 Pod 的 Request 范围
```

### 30.5.5 超卖(Oversubscription)原理

```
超卖的本质:
  节点 Allocatable CPU = 64 core
  调度的 Request 总和 = 64 x 超卖比

  超卖比 1:1 -> 调度 64 core Request(无超卖)
  超卖比 2:1 -> 调度 128 core Request
  超卖比 3:1 -> 调度 192 core Request(常见)
  超卖比 5:1 -> 调度 320 core Request(激进)

CPU 超卖安全(可压缩资源):
  - 过载时 CPU 节流(throttling),不崩溃
  - 通过 cfs_quota_us 控制
  - 风险:延迟敏感业务被拖慢

内存超卖危险(不可压缩):
  - 过载时 OOM Kill
  - 内存超卖比一般不超过 1.5:1
  - 建议 Request = Limit(Guaranteed),用 QoS 保护

kubelet Eviction 阈值:
  memory.available < 100Mi  -> 触发驱逐
  nodefs.available < 10%    -> 触发驱逐
  nodefs.inodesFree < 5%    -> 触发驱逐

驱逐顺序(QoS):
  1. BestEffort(无 Request/Limit)
  2. Burstable(超过 Request 的部分)
  3. Guaranteed(最后才驱逐)
```


### 30.5.6 混部架构深度剖析

```
混部节点资源模型:
  节点总容量:64 CPU, 256 GB
  
  在线业务区(LS):
    Reserved: 32 CPU, 128 GB
    实际使用:10-20 CPU, 60 GB
    -> 留出 12-22 CPU 给离线任务

  离线任务区(BE):
    可用:22 CPU, 80 GB
    实际使用:15-20 CPU, 50 GB

  总实际使用:30-40 CPU(利用率 47-62%)
```

混部的关键技术:

```
1. cgroup cpu.shares:
   在线 Pod:cpu.shares = 1024
   离线 Pod:cpu.shares = 2(或 1)
   
   当在线突发时,内核 CFS 自动给在线 1024/(1024+2) = 99.8% CPU
   离线只拿到 0.2% CPU

2. CPU Set 隔离:
   在线绑独占核(static CPU Manager)
   离线用「剩余核」(cpu.shares 模式)

Koordinator 进一步分级:
   LSE(Latency-Sensitive Exclusive):独占核 + L3 Cache
   LSR(Latency-Sensitive Reserved):预留核
   LS(Latency-Sensitive):普通在线
   BE(Best-Effort):离线

3. Memory 隔离:
   在线:memory.min(硬预留,不可被回收)
   离线:memory.low(可被回收)
   
   OOM 时:离线 Pod 先被杀(oom_score 调高)

4. Network 隔离:
   在线:高优先级 TC class
   离线:best-effort TC class
   
   带宽限制:离线 Pod 限速(避免打满网卡)

5. I/O 隔离:
   在线:io.high
   离线:io.low(限速)
   
   CFQ / BFQ 调度器按 cgroup 权重分配 I/O

6. 抢占(Preemption):
   在线突发 -> kubelet 驱逐离线 Pod
   优先级:online PriorityClass > BE PriorityClass
   抢占延迟:< 1s(Koordinator 优化)
```

### 30.5.7 Spot 实例中断模型

```
Spot 中断信号链:

  云厂商决定回收 -> 队列发出中断事件(IMDS)
       |
  Node Termination Handler(DaemonSet) 轮询 IMDS
       |
  收到中断通知(2 分钟倒计时)
       |
  NTH 调用 kubectl drain(node)
       |
  kubelet 进入 Graceful Shutdown
       |
  Pod 收到 SIGTERM -> preStop hook -> 优雅关闭
       |
  Pod 删除,调度器重新调度
       |
  Karpenter 看到节点减少 -> 启动新节点
       |
  新节点加入 -> Pending Pod 重新调度

端到端恢复时间:
  - 检测:10-30s
  - 排水:30s-2min(看 preStop)
  - 新节点启动:30-60s(Karpenter)
  - Pod 启动:30s-2min
  - 总计:2-5 分钟

关键优化:
  - 多 AZ 分散:避免单 AZ Spot 集中回收
  - 多实例类型:某类型回收,其他类型补充
  - Spot Block:1-6 小时锁定(部分云支持)
  - 容量预留:Capacity Reservation + Spot 混合
```

### 30.5.8 Karpenter 调度模型

Karpenter vs Cluster Autoscaler 的根本差异:

```
Cluster Autoscaler(CA):
  - 基于 NodeGroup/ASG 扩容
  - 先 Pending Pod -> 触发 ASG 扩容 -> 等待节点
  - 节点类型固定(预定义)
  - 响应时间:2-5 分钟
  - 缩容保守(怕影响业务)

Karpenter:
  - 无 NodeGroup,直接调度 EC2 实例
  - 直接看 Pending Pod 的 Request -> 选最便宜的实例
  - 实例类型灵活(从 1500+ 类型中选)
  - 响应时间:30-60 秒
  - 主动缩容(Consolidation)

Karpenter 调度算法:
  1. 收集所有 Pending Pod
  2. 按 Request 求和(Taint/Toleration 分组)
  3. 从实例池选最便宜的类型:
     - On-Demand / Spot
     - 满足 Resource Request
     - 满足 NodeAffinity
     - 满足 Topology Spread
  4. 启动 EC2 实例(直接 API,不走 ASG)
  5. 节点 Ready -> kubelet 注册 -> Pod 调度

Consolidation(缩容):
  周期性扫描所有节点
  找出「可被合并」的节点(利用率低)
  驱逐 Pod -> 缩容节点 -> Pod 重新调度到其他节点
```

### 30.5.9 HPA 算法原理

```
HPA 控制循环(默认 15s):

desiredReplicas = ceil(currentReplicas x (currentMetric / targetMetric))

举例:
  当前:10 副本,CPU 利用率 80%,目标 50%
  期望 = ceil(10 x 80/50) = 16 副本

容差(tolerance):默认 10%
  |current - target| / target < 0.1 -> 不扩缩(避免抖动)

冷却(downscale stabilization):默认 5 分钟
  缩容时取过去 5 分钟的最大副本数(防止抖动)

HPA v2 支持:
  - Resource(CPU/Memory)
  - Pods 自定义指标(每 Pod 一个指标,如 QPS)
  - Object 外部指标(如 SQS 队列长度)
  - External(全局指标)
  - Container metrics(按容器指标,不是 Pod 总和)
```

### 30.5.10 VPA 与 HPA 的冲突

```
VPA(Vertical Pod Autoscaler):
  - 调整 Pod 的 Request(纵向)
  - 需要重启 Pod 才能应用新 Request
  - 适合「无法水平扩展」的工作负载(如 DB)

VPA 与 HPA 冲突:
  - 同时调整 CPU Request -> 互相覆盖
  - 不能同时用 CPU 指标

解决方案:
  1. HPA 用自定义指标(QPS),VPA 调 CPU/Memory
  2. VPA 仅 Recommendation 模式,不自动应用
  3. 使用 KEDA 替代 HPA(更灵活)

VPA 模式:
  - Auto:自动调整 + 重启 Pod
  - Recreate:同 Auto,但明确重启
  - Initial:仅创建时应用推荐
  - Recommendation:只给建议,不应用(观察)
```

### 30.5.11 成本核算的底层模型

Kubecost / OpenCost 的成本核算公式:

```
节点成本分摊:
  节点月成本 = 云账单 / 30 / 24(每小时成本)
  
  某 Pod 节点成本 = 节点时成本 x (Pod Request CPU / 节点 Allocatable CPU)
                  + 节点时成本 x (Pod Request Mem / 节点 Allocatable Mem)
                  (按 CPU 和 Memory 加权,默认 50:50)

存储成本分摊:
  PVC 月成本 = PVC 容量 x 单价
  Pod 挂载的 PVC 成本算到 Pod

网络成本分摊:
  跨 AZ 流量 x 单价
  网络成本难以精确归因到 Pod(需要 Network Cost DaemonSet)

GPU 成本分摊:
  GPU 时成本 x (Pod 申请 GPU 数 / 节点 GPU 数)

闲置成本(Idle):
  节点 Allocatable - 所有 Pod Request = Idle
  Idle 成本分摊到所有 Pod(按比例)或算到命名空间

效率指标:
  Efficiency = 实际使用 / Request
  utilization = 实际使用 / Allocatable
```

### 30.5.12 Koordinator 调度框架

Koordinator 在 K8s 调度框架基础上扩展:

```
Koordinator 调度器扩展点(Scheduler Framework):

  QueueSort:按优先级排序(在线 > 离线)
      |
  Filter:节点过滤(混部节点专用 predicate)
      |
  Score:打分(NodeNUMAResource / LoadAware)
      |
  Reserve:预留资源(在线预留,离线可超卖)
      |
  Permit:延迟绑定(等待 GPU 共享确认)
      |
  PreBind:绑定前校验

Koordinator CRD:
  - PodMigrationJob:优雅迁移(抢占时)
  - Reservation:资源预留(为未来 Pod 占位)
  - Device:GPU/网卡设备分配
  - NodeMetric:节点级指标
  - ColocationProfile:混部策略

Koordinator QoS:
  LSE(Latency-Sensitive Exclusive):
    - CPU 独占 + L3 Cache 隔离
    - 用于核心数据库、网关
    
  LSR(Latency-Sensitive Reserved):
    - CPU 预留(不独占,但优先)
    - 用于在线业务
    
  LS(Latency-Sensitive):
    - 普通 Burstable
    - 用于一般在线
    
  BE(Best-Effort):
    - cpu.shares = 2
    - 用于离线任务
```

### 30.6.9 Karpenter NodePool 配置

```yaml
apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: default
spec:
  template:
    metadata:
      labels:
        nodepool: default
    spec:
      requirements:
      - key: kubernetes.io/arch
        operator: In
        values: ["amd64"]
      - key: karpenter.sh/capacity-type
        operator: In
        values: ["spot", "on-demand"]
      - key: node.kubernetes.io/instance-type
        operator: In
        values: ["m5.large", "m5.xlarge", "m5.2xlarge", "m5.4xlarge",
                 "c5.large", "c5.xlarge", "c5.2xlarge", "c5.4xlarge"]
      - key: topology.kubernetes.io/zone
        operator: In
        values: ["us-east-1a", "us-east-1b", "us-east-1c"]
      nodeClassRef:
        group: karpenter.k8s.aws
        kind: EC2NodeClass
        name: default
  limits:
    cpu: 1000
    memory: 1000Gi
  disruption:
    consolidationPolicy: WhenEmptyOrUnderutilized
    consolidateAfter: 30s
    budgets:
    - nodes: "10%"
```

### 30.6.13 预算告警(Prometheus AlertRule)

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: cost-alerts
  namespace: kubecost
spec:
  groups:
  - name: cost.rules
    rules:
    - alert: MonthlyCostOverBudget
      expr: |
        sum(kubecost_cluster_management_cost{cluster=~"prod.*"} * 24 * 30) > 100000
      for: 1h
      labels:
        severity: warning
      annotations:
        summary: "集群月成本超过 10 万"

    - alert: TenantCostAnomaly
      expr: |
        avg_over_time(kubecost_namespace_total_cost{namespace=~"team-.*"}[1h])
        > 2 * avg_over_time(kubecost_namespace_total_cost{namespace=~"team-.*"}[7d])
      for: 30m
      labels:
        severity: warning
      annotations:
        summary: "租户成本异常增长"

    - alert: NodeUnderutilized
      expr: |
        avg_over_time(rate(node_cpu_seconds_total{mode="idle"}[5m])[1h:5m]) > 0.8
      for: 6h
      labels:
        severity: info
      annotations:
        summary: "节点利用率低,可合并"

    - alert: SpotRatioTooHigh
      expr: |
        count(kube_node_labels{label_karpenter_sh_capacity_type="spot"})
        / count(kube_node_labels) > 0.7
      for: 10m
      labels:
        severity: warning
      annotations:
        summary: "Spot 节点比例 > 70%,风险过高"
```
