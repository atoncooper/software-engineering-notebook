## 2. 直觉解释

### 2.1 "公司组织架构"类比

把 K8s 集群想象成一家公司:

| K8s 组件 | 公司角色 | 干什么 |
|---------|---------|--------|
| **apiserver** | 前台+秘书室 | 所有进出请求必经,认证授权,登记入册 |
| **etcd** | 档案室 | 唯一真相源,所有状态最终归档于此 |
| **kube-scheduler** | HR | 决定员工(Pod)坐哪个工位(Node) |
| **kube-controller-manager** | 各部门经理 | 监控本部门状态,缺人就招,多就裁 |
| **cloud-controller-manager** | 外包联络官 | 跟云厂商 LB / Storage / Network 对接 |
| **kubelet** | 工位助理 | 确保员工到岗、健康、按时下班 |
| **kube-proxy** | 内线电话总机 | 服务发现 + 流量转接 |
| **容器运行时 (containerd)** | 员工本人 | 真正干活的人 |
| **Pod** | 工位 | 共享办公资源(网络/卷)的一组员工 |

### 2.2 关键认知:Control Plane = 大脑,Node = 四肢

```
              ┌─────────────────────────────────────┐
              │          Control Plane               │
              │  (大脑:决策、记忆、调度)            │
              │                                      │
              │  ┌──────────┐  ┌──────────────┐     │
              │  │ apiserver│  │     etcd     │     │
              │  └────┬─────┘  └──────▲───────┘     │
              │       │               │              │
              │  ┌────▼─────┐  ┌──────┴───────┐     │
              │  │scheduler │  │controller-mgr│     │
              │  └──────────┘  └──────────────┘     │
              └─────────────────┬───────────────────┘
                                │ List-Watch
              ┌─────────────────▼───────────────────┐
              │            Node × N                  │
              │  (四肢:执行、汇报)                 │
              │                                      │
              │  ┌─────────┐  ┌─────────┐           │
              │  │ kubelet │  │kube-proxy│          │
              │  └────┬────┘  └────┬─────┘          │
              │       │            │                 │
              │  ┌────▼────┐  ┌────▼─────┐          │
              │  │containerd│ │ iptables │          │
              │  └────┬────┘  └──────────┘          │
              │       │                              │
              │  ┌────▼────┐                         │
              │  │  Pods   │                         │
              │  └─────────┘                         │
              └──────────────────────────────────────┘
```

**核心不变量**:
1. apiserver 是**唯一**写 etcd 的入口,任何组件要改状态都得通过它
2. Node 上的组件不直接读 etcd,通过 apiserver 的 List-Watch 拿数据
3. Control Plane 挂了,已运行 Pod **继续跑**(kubelet 与运行时不依赖大脑),但**不能新建/改**
4. Node 挂了,Pod 重新调度到其他 Node(Control Plane 检测到 Node NotReady,标记 Pod 失败)

## 3. 核心架构与组件职责

### 3.1 Control Plane 组件详解

#### 3.1.1 kube-apiserver

**角色**:集群网关 + 状态守门人

**职责**:
- 接收所有 REST 请求(kubectl / kubelet / scheduler / controller / 外部 API)
- 认证 (Authentication):客户端证书 / Token / OIDC / Webhook
- 授权 (Authorization):RBAC / ABAC / Node / Webhook
- 准入控制 (Admission):Mutating → Validating → (1.26+ 准入完成)
- 序列化写入 etcd
- 提供 Watch (HTTP/2 长连接,分块推送)

**关键设计**:
- **无状态**:多副本部署,共享同一 etcd
- **唯一写 etcd 的组件**:其他组件通过 apiserver 改状态
- **请求流水线**:
  ```
  HTTP Request → Authn → Authz → Mutating → Validation → etcd → Watch 推送
  ```
- **etcd 直连**:apiserver 是 etcd 的"代理客户端",内部用 `client-go` 的 `cacher` 缓存热点对象降低 etcd 压力

**生产配置要点**:
- 至少 3 副本(配合 etcd 多副本,达到 HA)
- `--max-requests-inflight=400` (默认 400,大集群需调高)
- `--max-mutating-requests-inflight=200`
- 启用 watch cache (`--default-watch-cache-size=100`)
- 启用 Priority and Fairness (APF,1.20+) 防止单一客户端打满 apiserver

#### 3.1.2 etcd

**角色**:集群的"唯一真相源" (Single Source of Truth)

**职责**:
- 存储 K8s 所有对象 (Pod / Service / Deployment / Secret / ConfigMap ...)
- 强一致性 (Raft 协议)
- 提供 Watch 机制 (订阅式)
- MVCC 多版本并发控制 (支持 resourceVersion 乐观锁)

**关键设计**:
- **Raft 协议**:Leader 写,Followers 复制,多数派确认才返回成功
  - 选 Leader:随机超时 + 任期 (Term)
  - 写流程:Client → Leader → Append Log → 复制到多数派 → Commit → Apply
  - 脑裂防护:多数派机制保证最多一个 Leader
- **为什么不是 Paxos**:Raft 易理解、易实现、强 Leader 模型适合 K8s 写少读多
- **数据模型**:扁平 key-value,key 形如 `/registry/pods/default/my-pod`
- **压缩 (Compaction)**:保留历史版本一段时间后清理,否则磁盘爆炸

**生产配置要点**:
- **奇数节点**(3 或 5),跨可用区部署
- **SSD + 独占磁盘**:etcd 对 fsync 延迟极敏感,P99 < 10ms
- `--quota-backend-bytes=8GB` (默认 2GB)
- `--auto-compaction-retention=1h` (按小时压缩)
- `--heartbeat-interval=100ms --election-timeout=1000ms`(跨机房需调高)
- **不要**与其他服务混部,CPU 与磁盘 IO 会被抢

**etcd 性能基线**(工业数据):

| 集群规模 | 节点数 | QPS | P99 延迟 | 磁盘占用 |
|---------|--------|-----|---------|---------|
| 小型 | 3 | 1k | < 10ms | 1-3 GB |
| 中型 | 5 | 5k | < 20ms | 5-15 GB |
| 大型(阿里 ACK) | 5+SSD | 15k | < 50ms | 20-50 GB |
| 超大(GKE) | 7+local SSD | 30k+ | < 100ms | 50-100 GB |

#### 3.1.3 kube-scheduler

**角色**:Pod 的"HR",决定 Pod 落到哪个 Node

**职责**:
- Watch 待调度 Pod (`.spec.nodeName == ""`)
- 两阶段调度:**过滤 (Filter)** → **打分 (Score)**
- 输出调度决策,写回 Pod 的 `.spec.nodeName`(通过 apiserver)
- 不直接操作 Node,只更新 Pod 对象

**调度阶段**:
1. **Filter**:过滤不满足条件的 Node(资源不足、污点不容忍、亲和性不符)
2. **Score**:对剩余 Node 打分(0-100),按策略排序
3. **Reserve**:预留资源(防止下一个 Pod 抢占)
4. **Permit**:插件可延迟绑定(如 Coscheduling 等批调度)
5. **PreBind / PostBind**:绑定前后钩子(如 PreBind 写 PV)

**内置插件**(1.30):
- 过滤:`NodeUnschedulable` / `TaintToleration` / `NodeAffinity` / `PodTopologySpread` / `NodeResourcesFit`
- 打分:`NodeResourcesFit` (LeastAllocated/MostAllocated) / `InterPodAffinity` / `ImageLocality` / `PodTopologySpread`

**调度延迟**:
- 默认串行:每 Pod 10-100ms
- 启用 `--profile`:并行调度可降至 < 10ms/Pod
- 大厂扩展:Volcano (批调度)、KubeEdge (边缘)、YuniKorn (分层)

> 详见第 08 章调度器专章。

#### 3.1.4 kube-controller-manager

**角色**:运行内置控制器的"集合体"

**职责**:运行一组 Reconcile Loop,持续观察集群状态并驱动收敛

**内置控制器**:
- **Node Controller**:节点失联 40s 标记 NotReady,5min 后驱逐 Pod
- **ReplicaSet Controller**(被 Deployment 调用):维持副本数
- **Deployment Controller**:滚动更新、回滚
- **StatefulSet Controller**:有序创建/删除、稳定网络标识
- **DaemonSet Controller**:每个 Node 一个副本
- **Job / CronJob Controller**:批处理任务
- **EndpointSlice Controller**:维护 Service 后端 Pod 列表
- **ServiceAccount / Token Controller**:为 Pod 挂载默认 SA Token
- **PV / PVC Controller**:存储绑定
- **garbagecollector**:级联删除依赖对象
- **namespace-controller**:删除 Namespace 时清理资源

**关键设计**:
- 每个控制器是**独立 goroutine**,通过 Informer 监听资源
- 优先级:Node > Endpoint > ReplicaSet > ...
- 失败重试:指数退避 + 速率限制 (BucketRateLimiter)

#### 3.1.5 cloud-controller-manager

**角色**:云厂商集成的"外包联络官"

**职责**:把 K8s 的 Service / PV / Node 概念映射到云厂商的 LB / Disk / VM

**三大控制器**:
- **Node Controller**:向云厂商查询 Node 信息,标注 zone/instance-type
- **Route Controller**:配置云厂商 VPC 路由,使 Pod 跨节点通信
- **Service Controller**:为 `type=LoadBalancer` 的 Service 创建云厂商 LB

**意义**:K8s 主代码不依赖具体云厂商,云厂商通过 CCM 插件接入(AWS / Azure / GCP / 阿里 / 华为均有官方 CCM)。

### 3.2 Node 组件详解

#### 3.2.1 kubelet

**角色**:Node 上的"工位助理",Pod 的全生命周期管家

**职责**:
- 注册 Node 对象到 apiserver(启动时上报 hostname / IP / capacity)
- Watch 分配到本 Node 的 Pod(`.spec.nodeName == 本机`)
- 调用 CRI (containerd) 拉镜像、启容器
- 挂载 Volume (调用 CSI)
- 执行探针 (liveness / readiness / startup)
- 上报 Pod 与 Node 状态
- 执行 Pod 优雅终止 (preStop + SIGTERM + grace period)

**核心循环:syncLoop**
```
   ┌─────────────────────────────────────┐
   │            syncLoop                 │
   │                                     │
   │  ┌──────┐  ┌──────┐  ┌──────────┐  │
   │  │PLEG  │  │sync  │  │housekeeping│ │
   │  │事件  │  │Pod   │  │清理容器    │  │
   │  └──┬───┘  └──┬───┘  └────┬─────┘  │
   │     │         │            │        │
   │     └─────────┴────────────┘        │
   │               ▼                     │
   │       CRI / CSI / CNI 调用          │
   │               ▼                     │
   │           状态写回 apiserver        │
   └─────────────────────────────────────┘
```

**PLEG (Pod Lifecycle Event Generator)**:每秒轮询容器运行时,产生 Pod 状态变化事件,触发 syncPod。

**生产配置要点**:
- `--max-pods=110` (默认 110,大集群可调到 250-500,需 Node 资源够)
- `--pod-pids-limit=4096` (单 Pod 进程数限制)
- `--image-gc-high-threshold=85 --image-gc-low-threshold=80` (镜像 GC)
- `--eviction-hard` (硬驱逐阈值,如 `memory.available<100Mi`)

> 详见第 13 章 kubelet 专章。

#### 3.2.2 kube-proxy

**角色**:Node 上的"内线总机",Service → Pod 的流量转发

**职责**:
- Watch Service 与 EndpointSlice 对象
- 在本 Node 配置转发规则(iptables / IPVS / eBPF)
- 实现负载均衡(轮询 / 随机 / 最少连接)

**三种模式**:
- **iptables**(默认):规则链 `KUBE-SERVICES → KUBE-SVC-XXX → KUBE-SEP-XXX`,随机转发
- **IPVS**:基于内核 IPVS,支持 rr/lc/dh/sed 等调度算法,大集群性能优
- **ebpf**(Cilium 替代):绕过 iptables,直接 XDP/TC,延迟最低

**性能对比**(1000 Service × 10 Pod):

| 模式 | 规则数 | 同步延迟 | 转发延迟 | 内存 |
|------|--------|---------|---------|------|
| iptables | ~30k 条 | 5-10s | 50-200μs | 100MB |
| IPVS | ~1k 条 | 1-2s | 20-50μs | 50MB |
| eBPF(Cilium) | 无规则 | < 500ms | 5-20μs | 80MB |

> 详见第 14 章 kube-proxy 专章。

#### 3.2.3 容器运行时 (Container Runtime)

**角色**:真正跑容器的人

**职责**:实现 CRI (Container Runtime Interface) gRPC 接口

**主流运行时**:
- **containerd**:CNCF 毕业项目,Docker 内部使用的核心,CNCF 主推
- **CRI-O**:Red Hat 主导,专为 K8s 设计,轻量
- **Docker Engine**(1.24 后已废弃支持,通过 cri-dockerd 适配)
- **Kata Containers**:强隔离,VM 级别,适合多租户
- **gVisor**:用户态内核,沙箱级隔离

**containerd 架构**:
```
   ┌─────────────────────────────────┐
   │           kubelet               │
   └────────────┬────────────────────┘
                │ CRI gRPC
   ┌────────────▼────────────────────┐
   │     CRI Plugin (containerd)     │
   │  ┌──────────────────────────┐   │
   │  │ image service            │   │
   │  │ runtime service          │   │
   │  └──────────────────────────┘   │
   └────────────┬────────────────────┘
                │ OCI runtime (runc)
   ┌────────────▼────────────────────┐
   │         Linux Kernel            │
   │  namespace + cgroup + UnionFS   │
   └─────────────────────────────────┘
```

## 4. 数据流:一个 `kubectl apply` 的完整旅程

### 4.1 创建 Deployment 的端到端流程

```bash
kubectl apply -f deployment.yaml
```

**步骤分解**:

```
┌──────────┐
│ kubectl  │ 1. 读 KUBECONFIG,提取证书/Token
└────┬─────┘
     │ HTTPS POST /apis/apps/v1/namespaces/default/deployments
     ▼
┌──────────────────┐
│  apiserver       │ 2. 认证(客户端证书)
│                  │ 3. 授权(RBAC: user → create deployments)
│                  │ 4. Mutating Admission (DefaultNamespace 等)
│                  │ 5. Validating Admission (检查字段、镜像策略等)
│                  │ 6. 序列化为 protobuf,写 etcd
└────┬─────────────┘
     │ etcd Put /registry/deployments/default/my-app
     ▼
┌──────────────────┐
│     etcd         │ 7. Raft 复制到多数派,Commit
└────┬─────────────┘
     │
     ▼
┌──────────────────────────────┐
│ apiserver Watch              │ 8. 推送给所有 Watcher
│   - Deployment Controller    │
│   - ReplicaSet Controller    │
└────┬─────────────────────────┘
     │
     ▼
┌──────────────────────────────┐
│ Deployment Controller        │ 9. 收到新增 Deployment
│ (kube-controller-manager)    │ 10. 创建 ReplicaSet (子资源)
└────┬─────────────────────────┘
     │ apiserver POST .../replicasets
     ▼
┌──────────────────────────────┐
│ ReplicaSet Controller        │ 11. 收到新增 ReplicaSet
│                              │ 12. 计算缺几个 Pod,创建 N 个 Pod
└────┬─────────────────────────┘
     │ apiserver POST .../pods (spec.nodeName="")
     ▼
┌──────────────────────────────┐
│ kube-scheduler               │ 13. Watch 到待调度 Pod
│                              │ 14. Filter → Score → Bind
│                              │ 15. 写 Pod .spec.nodeName=node-X
└────┬─────────────────────────┘
     │ apiserver PUT .../pods/my-app-xxx (更新 nodeName)
     ▼
┌──────────────────────────────┐
│ kubelet (node-X)             │ 16. Watch 到 nodeName=本机的 Pod
│                              │ 17. CRI 拉镜像、启容器
│                              │ 18. CSI 挂卷、CNI 配置网络
│                              │ 19. Pod 状态 Running 写回 apiserver
└────┬─────────────────────────┘
     │
     ▼
┌──────────────────────────────┐
│ EndpointSlice Controller     │ 20. Watch Pod Ready
│ kube-proxy (各 Node)         │ 21. 更新本机 iptables/IPVS 规则
│                              │ 22. Service 流量可路由到新 Pod
└──────────────────────────────┘
```

**总耗时**(单 Pod):
- apiserver → etcd 写入:< 50ms
- Deployment → ReplicaSet → Pod 创建:< 200ms(异步,通过 Watch)
- 调度决策:< 100ms
- kubelet 拉镜像启动容器:**镜像已缓存** 1-3s,**镜像未缓存** 30s-数分钟(看镜像大小与带宽)
- kube-proxy 同步规则:< 5s(iptables 大集群可能 10s+)

**关键认知**:K8s 是**最终一致性**系统,没有"同步等待所有组件"的概念。`kubectl apply` 返回成功只代表"apiserver 写入 etcd 成功",不代表 Pod 已 Running。

### 4.2 数据流的关键特性

#### 4.2.1 List-Watch 是 K8s 的灵魂

- **List**:首次全量拉取
- **Watch**:增量推送(基于 `resourceVersion`),HTTP/2 长连接
- **Informer**:client-go 封装,本地缓存 + 事件分发
- **为什么不用轮询**:1k 节点 × 每秒 List = apiserver 雪崩

#### 4.2.2 乐观锁 (resourceVersion)

- 每次写 etcd,对象 `resourceVersion` 自增
- 写请求需带 `resourceVersion`,冲突时返回 409,客户端重试
- 防止 ABA 问题与并发覆盖

#### 4.2.3 所有组件都是 apiserver 的客户端

- kubelet / scheduler / controller / kube-proxy 全用 client-go
- 共享 Informer 机制,本地缓存 + Watch 增量
- 一致性保证:apiserver 是**唯一**写 etcd 的,所有读走 apiserver 或本地缓存

## 5. 底层原理与组件协作

### 5.1 Control Plane 的 HA 实现

```
              ┌─────────────────────────────┐
              │      Load Balancer          │
              │   (云厂商 CLB / HAProxy)    │
              └────┬─────────┬─────────┬───┘
                   │         │         │
              ┌────▼───┐ ┌───▼────┐ ┌──▼─────┐
              │api-1   │ │api-2   │ │api-3   │
              └────┬───┘ └───┬────┘ └───┬────┘
                   │         │         │
              ┌────▼─────────▼─────────▼────┐
              │          etcd cluster        │
              │   ┌─────┐  ┌─────┐  ┌─────┐ │
              │   │etcd1│◄─┤etcd2│◄─┤etcd3│ │  ← Raft 多数派
              │   └─────┘  └─────┘  └─────┘ │
              └─────────────────────────────┘
```

**HA 关键点**:
- apiserver 无状态,可水平扩展
- etcd 用 Raft 保证一致性,**奇数节点**(3 或 5)
- scheduler 与 controller-manager 通过 leader election,同时只有一个工作
- kubelet / kube-proxy 通过 LB 连 apiserver,失败自动重试

#### 5.1.1 Leader Election 实现

```yaml
# kube-controller-manager 配置
--leader-elect=true
--leader-elect-lease-duration=15s
--leader-elect-renew-deadline=10s
--leader-elect-retry-period=2s
```

**机制**:
- 用 `coordination.k8s.io/Lease` 对象,谁先创建谁当 Leader
- Leader 每 10s 续约,15s 不续约视为失联
- 其他副本每 2s 重试抢锁

### 5.2 组件协作时序图:Pod 故障自愈

```
   T=0s   Pod 容器崩溃 (exit 1)
          │
   T=1s   ▼
          kubelet PLEG 检测到容器状态变化
          │
   T=1s   ▼
          kubelet syncPod 重启容器(默认 restartPolicy=Always)
          │
   T=1s   ▼
          liveness probe 失败(若配置)
          │
   T=30s  ▼
          kubelet 标记 Pod .status.containerStatuses.ready=false
          │
   T=30s  ▼
          EndpointSlice Controller Watch 到 Pod NotReady
          │
   T=31s  ▼
          从 EndpointSlice 移除该 Pod
          │
   T=31s  ▼
          kube-proxy (各 Node) Watch EndpointSlice 变化
          │
   T=33s  ▼
          更新本机 iptables/IPVS 规则,流量不再转给该 Pod
          │
   T=33s  ▼
          kubelet 多次重启失败 (CrashLoopBackOff)
          │
   T=5min ▼
          若 Node 整体失联,Node Controller 标记 Node NotReady
          │
   T=5min ▼
          (默认 5min) Pod 被标记 terminating,触发重新调度
          │
   T=5min ▼
          ReplicaSet Controller 检测副本数不足,创建新 Pod
          │
   T=5.1s ▼
          scheduler 调度新 Pod 到健康 Node
          │
   T=10s  ▼
          新 Pod Running,Service 流量恢复
```

**关键参数**:
- `--node-monitor-period=5s` (Node Controller 检查间隔)
- `--node-monitor-grace-period=40s` (多久没收到 Node 心跳标记 NotReady)
- `--pod-eviction-timeout=5m` (NotReady 多久后驱逐 Pod)
- `--default-not-ready-toleration-seconds=300` (默认污点容忍时间)

## 7. 常见陷阱与调优 ⚠️

### 7.1 etcd 相关陷阱

| 陷阱 | 现象 | 根因 | 解决 |
|------|------|------|------|
| **etcd 磁盘满** | 集群全挂,无法创建任何资源 | etcd 数据目录无上限,历史版本不压缩 | 启用 `--auto-compaction-retention=1h`,加监控 |
| **etcd 脑裂** | Leader 频繁切换,apiserver 超时 | 跨机房网络抖动,heartbeat 超时 | 同机房部署,跨机房用 etcd proxy |
| **fsync 延迟高** | etcd 写入 P99 > 100ms | 共享磁盘 IO 争抢 | etcd 独占 SSD,关闭其他 IO 密集服务 |
| **大对象写入** | `kubectl apply` 失败,etcd 报错 | ConfigMap > 1MB(默认 quota) | 拆分 ConfigMap,或用 OCI 镜像存配置 |
| **etcd defrag 卡死** | 集群不可写 | defrag 阻塞主线程 | 在线 defrag 用 v3.5+,先逐节点 evict leader |

### 7.2 apiserver 陷阱

| 陷阱 | 现象 | 根因 | 解决 |
|------|------|------|------|
| **Watch 断连** | kubectl 偶尔卡 1 分钟 | apiserver LB 不支持 HTTP/2 长连接超时 | LB 配置 idle timeout >= 1h |
| **请求被限流** | 409 Too Many Requests | 单客户端打满 max-requests-inflight | 启用 APF,按 priority 分流 |
| **慢查询** | List Pods 延迟 > 5s | 不带 fieldSelector 全量拉 | 用 labelSelector + 分页 |
| **admission webhook 超时** | 创建 Pod 慢 / 失败 | webhook 服务不可达 | webhook 设置 timeout=10s + failurePolicy=Ignore(慎用) |
| **证书过期** | 集群突然不可用 | apiserver 证书 1 年过期,未轮换 | 启用 cert-manager + 自动轮换 |

### 7.3 kubelet 陷阱

| 陷阱 | 现象 | 根因 | 解决 |
|------|------|------|------|
| **PLEG 不可达** | Pod 状态卡 Pending | 容器运行时卡死,docker daemon 不响应 | 重启 containerd,排查死锁 |
| **镜像 GC 过激** | Pod 拉不到镜像 | 频繁 GC 删了还在用的镜像层 | 调高 `image-gc-high-threshold` 到 85 |
| **Pod 卡 Terminating** | Pod 删不掉 | kubelet 卡死,或 finalizer 未移除 | 检查 finalizer,必要时重启 kubelet |
| **容器 OOM 但 kubelet 不重启** | Pod 状态 Running 但应用死了 | OOMKill 后容器退出,但 restartPolicy=Never | 改 restartPolicy=Always 或用 Job |

### 7.4 kube-proxy 陷阱

| 陷阱 | 现象 | 根因 | 解决 |
|------|------|------|------|
| **iptables 同步慢** | Service 创建后 10s 才生效 | iptables 模式,大集群规则爆炸 | 切 IPVS 模式 |
| **Pod IP 残留** | 流量到已删除 Pod | kube-proxy 同步延迟 + conntrack 缓存 | 启用 `--conntrack-tcp-timeout-est=300s` |
| **会话保持失效** | 同客户端被分到不同 Pod | Service `sessionAffinity=None` | 设置 `sessionAffinity=ClientIP`,timeout=10800 |
| **conntrack 表满** | 新连接失败 | 大流量 + 表容量不足 | `sysctl net.netfilter.nf_conntrack_max=1048576` |

### 7.5 调度器陷阱

| 陷阱 | 现象 | 根因 | 解决 |
|------|------|------|------|
| **Pod 卡 Pending** | 调度失败 | 资源不足 / 污点 / 亲和性 | `kubectl describe pod` 看 Events |
| **调度不均** | 部分 Node 满载,部分空闲 | 默认 LeastAllocated 策略堆积 | 吁 PodTopologySpread + 自定义打分 |
| **节点资源超卖** | Node 内存满,触发 eviction | requests 设置过低,limits 不限制 | 合理设置 requests/limits,启用 LimitRanger |

## 8. 工业案例与基准数据

### 8.1 阿里巴巴 ACK(阿里云容器服务 K8s)

**集群规模**(2024 公开数据):
- 单集群最大 5000 节点
- etcd 7 副本 + local SSD,P99 写延迟 < 30ms
- apiserver 5 副本 + APF,支撑 5000 QPS
- 单 Node 跑 250 Pod(高密度)

**优化经验**:
1. **etcd 分片**:超大规模用"多 etcd 集群"按资源类型分片,Pods/ConfigMap 单独 etcd
2. **apiserver cache**:增大 watch cache,降低 etcd 读压力
3. **kube-proxy IPVS**:必启,否则 iptables 规则数爆炸(单 Node 30k+ 规则)
4. **节点池**:按规格分池(CPU 密集 / 内存密集 / GPU),调度器走 NodePool 路由
5. **CCM 集成**:CLB / ESS / EIP 全打通,Service type=LB 自动建云 LB

**故障案例**:
- 2021 年某次 etcd 集群网络抖动,Leader 切换 3 次,集群 30s 不可写
- 根因:跨 AZ 网络抖动 + heartbeat 超时过短
- 修复:`--election-timeout=3000`,etcd 同 AZ 部署,跨 AZ 用 etcd proxy

### 8.2 字节跳动 ByteKube

**集群规模**:
- 单集群 8000+ 节点(自研扩展)
- Pod 总数 100k+
- 每日调度量 1M+ 次

**深度优化**:
1. **自研调度器**:基于 K8s scheduler framework,加 Coscheduling / Gang 调度,支持离线批
2. **kube-proxy 替换**:自研基于 eBPF 的 KubeProxy,延迟从 200μs 降至 30μs
3. **apiserver 分级**:核心控制平面 / 业务平面分离,不同租户走不同 apiserver
4. **etcd 分片**:按 namespace 分片,大 namespace 单独 etcd 集群
5. **CRD 限流**:对所有 CRD 控制 List 速率,防止客户端拉爆 apiserver

**生产数据**:
- apiserver P99 延迟 < 100ms(单 namespace)
- etcd P99 写延迟 < 20ms
- Pod 创建到 Running:P50 3s,P99 8s(不含拉镜像)

### 8.3 Google GKE(Google Kubernetes Engine)

**集群规模**:
- 单集群最大 15000 节点
- 跨 Region 多集群联邦
- etcd 用 local SSD + Bigtable 备份

**特色**:
1. **GKE Autopilot**:Google 托管 Control Plane,用户只关心应用
2. **multi-cluster mesh**:Anthos Service Mesh 跨集群通信
3. **Vertical Pod Autoscaler**:生产可用,自动调 requests
4. **节点自动修复**:Node Problem Detector + auto-repair

**性能数据**:
- apiserver P99 < 200ms(15000 节点)
- etcd 写入 QPS 30k+
- Pod 调度延迟 < 500ms

### 8.4 AWS EKS

**架构特点**:
- Control Plane 托管,跨 3 AZ 部署
- etcd 多副本,自动备份到 S3
- 与 AWS VPC / IAM / ALB / EBS 深度集成

**性能基线**:
- 单集群 1000 节点(官方推荐上限)
- apiserver QPS 3000+
- Pod 启动延迟(已缓存镜像)2-4s

**典型问题**:
- VPC CNI IP 不足:节点子网 IP 耗尽,改用 Prefix Delegation
- ALB Ingress Controller:大量 Ingress 同步慢,改用 ALB Ingress 控制器 + TargetType=IP
- EBS CSI:跨 AZ 挂载失败,PV 不跨 AZ,Pod 调度需拓扑约束

## 9. 与其他方案的关系

### 9.1 K8s vs Docker Swarm

| 维度 | K8s | Docker Swarm |
|------|-----|--------------|
| 复杂度 | 高(20+ 组件) | 低(docker daemon 内嵌) |
| 单集群规模 | 5000-15000 节点 | < 1000 节点 |
| 网络模型 | CNI 插件(扁平) | overlay driver |
| 服务发现 | Service + DNS | 内置 DNS |
| 滚动更新 | Deployment 原生支持 | docker service update |
| 存储编排 | CSI + PV/PVC | volume plugin |
| 多租户 | Namespace + RBAC | 弱 |
| 适合场景 | 大规模生产 | 小规模简单场景 |

### 9.2 K8s vs Nomad

| 维度 | K8s | Nomad |
|------|-----|-------|
| 厂商 | CNCF | HashiCorp |
| 工作负载 | 容器为主 | 容器 + 进程 + Java + 任意二进制 |
| 调度器 | 内置 + 可扩展 | 单二进制 + 简单调度 |
| 生态 | 极丰富(CNI/CSI/Operator) | 简洁,与 Consul/Vault 集成 |
| 学习曲线 | 陡峭 | 平缓 |
| 适合场景 | 云原生应用 | 混合工作负载、传统应用 |

### 9.3 K8s vs Apache Mesos

| 维度 | K8s | Mesos |
|------|-----|-------|
| 调度模型 | 两级调度(scheduler + kubelet) | 两级调度(FW + Executor) |
| 工作负载 | 容器 | 容器 + 进程 + 大数据(Spark/Chronos) |
| 资源隔离 | cgroup + namespace | cgroup + namespace |
| 生态 | 云原生 | 大数据 + 容器 |
| 现状 | 主流 | 衰退(Twitter 改用 K8s) |

### 9.4 K8s vs Google Borg/Omega

| 维度 | K8s | Borg | Omega |
|------|-----|------|-------|
| API 风格 | 声明式 + Reconcile | 命令式 + 作业 | 声明式 + 事务 |
| 资源模型 | Pod + Service | Job + Task | 同 Borg |
| 多租户 | Namespace + RBAC | Cell + ACL | 同 Borg |
| 历史 | 2014+ Borg 开源版 | 2003+ Google 内部 | Borg 后继实验 |
| 关系 | K8s 借鉴 Borg 但重写 | K8s 之父 | Borg/Omega → K8s |

**Borg 对 K8s 的关键影响**:
- 声明式 API(从 Omega)
- 控制循环(从 Borg)
- 标签 + 选择器(从 Borg)
- Pod(Borg 的 task group 简化)
- Service(Borg 没有,K8s 新增)

## 11. 综合面试题

### 11.1 基础题

**Q1**: 描述 K8s 的整体架构,并说明 Control Plane 与 Node 各自的核心组件。

**答题要点**:
- Control Plane: apiserver(网关)/ etcd(存储)/ scheduler(调度)/ controller-manager(控制器集合)/ cloud-controller-manager(云集成)
- Node: kubelet(Pod 管家)/ kube-proxy(网络转发)/ 容器运行时(containerd/CRI-O)
- 数据流: kubectl → apiserver → etcd → Watch 推给 controller/scheduler/kubelet
- 关键特性: apiserver 是唯一写 etcd 的入口,所有组件通过 List-Watch 获取状态

**Q2**: 解释 etcd 在 K8s 中的作用,为什么用 Raft?

**答题要点**:
- etcd 是 K8s 的"唯一真相源",所有对象(Pod/Service/Deployment...)最终存于此
- Raft:强 Leader、易理解、多数派写、写少读多场景下性能优
- vs Paxos:Raft 工程实现简单,Paxos 通用但难懂
- vs ZK:etcd 用 gRPC + HTTP/2,Watch 机制原生,Paxos 变种 ZAB
- 生产配置:奇数节点、SSD 独占、跨可用区、定期压缩与 defrag

**Q3**: 解释 `kubectl apply -f deployment.yaml` 后,集群内部发生了什么。

**答题要点**:
1. kubectl 读 KUBECONFIG,向 apiserver 发 HTTPS POST
2. apiserver: Authn → Authz → Mutating Admission → Validation → Validating Admission → etcd
3. etcd Raft 复制,Commit
4. Deployment Controller 通过 Watch 收到新对象,创建 ReplicaSet
5. ReplicaSet Controller 创建 Pod(spec.nodeName="")
6. scheduler Watch 到待调度 Pod,Filter+Score,写 Pod.nodeName
7. 目标 Node 的 kubelet Watch 到 Pod,CRI 拉镜像启容器,CSI 挂卷,CNI 配网络
8. kubelet 上报 Pod Running
9. EndpointSlice Controller 收到 Pod Ready,更新 EndpointSlice
10. 各 Node kube-proxy Watch EndpointSlice,更新 iptables/IPVS

### 11.2 进阶题

**Q4**: Control Plane 的 HA 怎么实现?Leader Election 详细机制?

**答题要点**:
- apiserver 无状态,水平扩展 + LB
- etcd 多副本 + Raft(奇数节点,多数派可用)
- scheduler / controller-manager 通过 Lease 对象抢锁
  - `--leader-elect=true`
  - Lease duration 15s, renew 10s, retry 2s
  - Leader 续约失败 15s 后,其他副本抢
- kubelet / kube-proxy 通过 LB 连 apiserver,失败重试
- 生产:跨 3 AZ 部署,任一 AZ 挂仍可用

**Q5**: apiserver 的请求流水线有哪些阶段?Admission Controller 干什么?

**答题要点**:
- 流水线: HTTP → Authn → Authz → Mutating Admission → Object Validation → Validating Admission → etcd Write → Watch Push
- Mutating: 可修改对象(DefaultNamespace、DefaultToleration、MutatingWebhook)
- Validating: 只能通过/拒绝(LimitRanger、ResourceQuota、ValidatingWebhook)
- 顺序: Mutating 必须在 Validating 前,否则修改无效
- Webhook: 业务自定义(如 OPA Gatekeeper、Istio Sidecar 注入)

**Q6**: 一个 Pod 卡 Pending,你怎么排查?

**答题要点**:
1. `kubectl describe pod <name>` 看 Events
2. 检查 scheduler 是否调度过(nodeName 是否空)
3. 常见原因:
   - Insufficient cpu/memory:资源不够
   - node(s) had taints:污点不容忍
   - node(s) didn't match node selector:亲和性
   - FailedScheduling:镜像太大 / 端口冲突 / volume 不可用
4. 解决:
   - 加节点 / 降 requests
   - 加 tolerations
   - 改 nodeSelector / nodeAffinity
   - 提前预热镜像

**Q7**: kube-proxy IPVS vs iptables,什么时候必须切 IPVS?

**答题要点**:
- iptables:规则数与 Service × Pod 数线性增长,O(n) 查找
- IPVS:基于 hash,O(1) 查找,适合大集群
- 切换阈值:
  - 单 Node Service > 1000,Pod > 5000 → 必切 IPVS
  - 否则 iptables 同步可能 > 30s,新 Pod 流量切换不及时
- 切换方法: `kubectl -n kube-system edit cm kube-proxy` 改 mode: "ipvs",重启 kube-proxy
- 注意: IPVS 不支持 iptables 部分高级特性(如 Service Mesh 的精细流量控制)

### 11.3 高级题

**Q8**: 大规模集群(> 5000 节点)etcd 怎么优化?

**答题要点**:
- **分片**:按资源类型分到不同 etcd 集群(Pods/ConfigMap 单独 etcd)
- **本地 SSD**:etcd 独占 local NVMe,fsync P99 < 5ms
- **压缩**:`--auto-compaction-retention=1h`,定期 defrag
- **空间配额**:`--quota-backend-bytes=8GB`,防止磁盘满
- **请求大小**:`--max-request-bytes=1MB`,大对象拆分
- **客户端优化**:apiserver watch cache 增大,降低 etcd 读
- **跨机房**:同机房多副本 + 跨机房 etcd proxy(只读)
- **监控**:etcd_disk_wal_fsync_duration / etcd_server_proposals_failed_total

**Q9**: 描述 K8s 的最终一致性模型,以及为什么不能强一致?

**答题要点**:
- etcd 强一致(线性一致),但 K8s 整体是最终一致
- 原因:
  1. 多个控制器异步 Watch,处理延迟
  2. kubelet 异步上报状态
  3. 调度器异步决策
  4. Service 转发规则异步同步
- 强一致代价太高:每个请求等所有组件确认,延迟爆炸
- 设计取舍:可用性 > 一致性(类似 BASE)
- 业务影响:
  - 创建 Pod 后流量不会立刻打到它(kube-proxy 同步延迟)
  - 删除 Pod 后流量可能持续几秒(conntrack 缓存)
  - 解决:readiness probe + preStop + termination grace period

**Q10**: 如何设计一个 K8s 集群的容量规划?

**答题要点**:
- **业务侧**:
  - Pod 总数 = 业务副本数总和
  - 单 Pod 资源 = requests.cpu/memory
  - 峰值系数 1.5-3x
- **集群侧**:
  - 节点数 = Pod 总数 / 单节点 Pod 密度(110/250)
  - Control Plane 配置按节点数:500 节点 → apiserver 4C8G × 3 + etcd 4C16G × 3 + local SSD
- **etcd 容量**:
  - 每 Pod 在 etcd ~1-3KB,1M Pod → 1-3GB
  - 配额 8GB,留 50% 余量
- **网络**:
  - Service IP 段 / Pod IP 段 / Node IP 段互不重叠
  - 跨节点流量评估(Bandwidth)
- **灾备**:
  - 跨 AZ 部署
  - etcd 定期快照
  - 多集群联邦(关键业务)
- **预留**:
  - 节点资源预留(kubeReserved + systemReserved)
  - 突发流量缓冲(HPA + Cluster Autoscaler)

### 11.4 设计题

**Q11**: 设计一个跨地域多集群 K8s 方案,要求支持灰度发布和故障切换。

**答题要点**:
- **集群层**:每 Region 一个 K8s 集群,Control Plane 独立
- **网络层**:
  - Pod 互通:Cilium ClusterMesh / Submariner / Istio Multi-Primary
  - Service 互通:Global Service(同名 LB 跨集群)
- **流量入口**:
  - 全局 DNS(Route53 / 阿里云 GTM)按权重 / 延迟路由
  - 边缘 Ingress(Istio IngressGateway / Envoy)
- **应用层**:
  - 灰度:Argo Rollouts + ClusterDecision(按集群权重)
  - 故障切换:Global LB 健康检查 + 自动摘除
- **数据层**:
  - 数据库跨 Region 主从(MySQL MGR / TiDB / Spanner)
  - 缓存跨集群同步(Redis Cluster / 多副本)
- **治理**:
  - GitOps:Argo CD + 多集群 ApplicationSet
  - 配置:Karmada / Cluster API
  - 监控:Thanos / Mimir 跨集群查询
- **成本**:
  - 同 Region 多集群(主备)成本低,跨 Region 高
  - 按 RTO/RPO 选:同 Region(RTO 分钟级)/ 跨 Region(RTO 小时级)

## 12. 故障复盘

### 12.1 案例 1:etcd 磁盘满导致全集群不可写

**业务影响**:2023 年某中型公司 K8s 集群,夜间 etcd 磁盘使用率 100%,所有 `kubectl` 命令失败,Pod 无法创建,业务受影响 2 小时。

**根因**:
- etcd 启用 `--auto-compaction-retention=5`(保留 5 小时历史)
- ConfigMap 数量从 1k 增长到 50k(应用日志配置爆增)
- 历史版本累积,3TB 数据盘 90% 满
- 触发 `quota-backend-bytes` 限制,etcd 报 `mvcc: database space exceeded`

**修复过程**:
1. 紧急:`etcdctl compact <rev>` + `etcdctl defrag`(逐节点 evict leader)
2. 临时:提高 `--quota-backend-bytes` 到 16GB
3. 根治:
   - 启用 `--auto-compaction-mode=periodic --auto-compaction-retention=1h`
   - 定期 cron defrag
   - ConfigMap 拆分,大配置迁 OCI 镜像
   - 加监控告警:磁盘使用率 > 70%

**防范**:
- 监控指标:`etcd_mvcc_db_total_size_in_bytes` / `etcd_server_quota_backend_bytes`
- 告警阈值:磁盘使用率 > 70%(P1)/ 80%(P0)
- 巡检脚本:每日检查 etcd 压缩状态与碎片率
- 容量规划:按 Pod 数估算 etcd 大小(Pod 1-3KB × N × 5h)

### 12.2 案例 2:apiserver 证书过期导致集群不可用

**业务影响**:2022 年某公司,K8s 集群运行 1 年后,apiserver 证书过期,所有 kubectl 命令报 `x509: certificate has expired`,kubelet 上报状态失败,但已运行 Pod 不受影响。

**根因**:
- 集群用 kubeadm 初始化,默认证书 1 年有效期
- 没启用证书自动轮换
- 没监控证书过期时间

**修复过程**:
1. 备份 etcd(防止操作失误)
2. 在 master 上:`kubeadm certs renew all`
3. 重启 apiserver / controller-manager / scheduler 静态 Pod
4. 重启 kubelet(重新加载证书)
5. 更新 kubeconfig:`~/.kube/config` 用新证书

**防范**:
- 启用 cert-manager + 自动轮换
- 监控指标:`kube-apiserver certificate expiry`(Prometheus)
- 告警阈值:证书剩余 < 30 天(P1)/ 7 天(P0)
- 巡检脚本:`kubeadm certs check-expiration` 每月检查
- 升级到 K8s 1.22+:kubeadm 默认 10 年证书

### 12.3 案例 3:kube-proxy IPVS 模式下 Pod IP 残留

**业务影响**:2023 年某公司,Service 后端 Pod 滚动更新,新 Pod Ready 但流量仍打到旧 Pod,导致 5xx 错误率突增 30%,持续 3 分钟。

**根因**:
- kube-proxy IPVS 模式,但 conntrack 表保留旧连接
- 旧 Pod 已删除,但 conntrack 缓存的连接 5 分钟不释放
- 客户端长连接(WebSocket)持续发送到旧 Pod IP

**修复过程**:
1. 紧急:重置 conntrack `conntrack -D -p tcp --orig-port 80`
2. 临时:增加 Pod 优雅终止时间到 60s + preStop hook 等待 30s
3. 根治:
   - 启用 `--conntrack-tcp-timeout-est=300s`(默认 5 天)
   - kube-proxy 启用 `--conntrack-max-per-core=0`(禁用 per-core 限制)
   - 应用层支持重连 + 优雅终止通知

**防范**:
- 长连接应用:preStop hook 主动通知 + grace period 足够长
- conntrack 表监控:`nf_conntrack_count` / `nf_conntrack_max`
- 滚动更新:maxSurge=1, maxUnavailable=0, readiness probe 严格
- 切换到 eBPF 模式(Cilium):绕过 conntrack,无此问题
