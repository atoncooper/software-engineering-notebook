# 01 - 基础与核心概念

> 一切的起点:K8s 是什么、不是什么、为什么这样设计、在大厂生产里它扮演什么角色。

---

## 1. 问题定义与边界

### 1.1 Kubernetes 解决的问题

容器化之后,生产环境面临 5 个新问题:

| 问题 | 前 K8s 时代 | K8s 之后 |
|------|-------------|----------|
| **多机编排** | Docker 单机、Swarm 弱 | 跨千节点调度 Pod |
| **故障自愈** | 容器挂了靠人重启 | 探针 + ReplicaSet 自动重建 |
| **服务发现** | 手写 nginx upstream | Service + DNS 自动注册 |
| **滚动发布** | 停机部署或脚本化 | Deployment 滚动更新 + 回滚 |
| **资源调度** | 手动分配机器 | scheduler 按资源/亲和/污点自动选节点 |

### 1.2 Kubernetes 不解决什么(边界)

- **不是 PaaS**:不提供应用市场、不打包业务逻辑、不绑定语言
- **不是配置管理工具**:Ansible / Puppet 的替代品是 Helm / Argo CD,但 K8s 本身只接收声明
- **不是日志系统**:只暴露日志接口,聚合要靠 Fluent Bit + Loki/ELK
- **不是数据库**:etcd 是元数据存储,不是业务数据库
- **不是负载均衡器**:Service 是抽象,真正的 LB 在云厂商 (CLB/NLB) 或 kube-proxy/iptables
- **不保证零停机**:零停机靠探针 + 滚动更新 + preStop 配合,K8s 只提供机制

> **关键认知**:K8s 是"编排平台",不是"应用平台"。它给机制不给策略,给原语不给业务。理解这一点能避免 80% 的误用与抱怨。

### 1.3 K8s vs Docker 的根本差异

| 维度 | Docker | Kubernetes |
|------|--------|------------|
| 作用域 | 单机 | 多机集群 |
| 单元 | 容器 | Pod(可含多容器) |
| API 风格 | 命令式 (docker run) | 声明式 (kubectl apply YAML) |
| 状态管理 | 无状态 | Reconcile Loop 持续收敛 |
| 网络模型 | 单机 bridge/overlay | 集群扁平网络 + Service |
| 故障恢复 | 需 restart 策略 + 外部监控 | 探针 + ReplicaSet 自愈 |
| 学习曲线 | 1 周 | 3-6 月 |

## 2. 直觉解释

### 2.1 "交响乐团指挥"类比

- **容器 (Container)**:乐手,单独能演奏,但不知何时入场
- **Pod**:乐谱架,把协奏的乐手放一起 (sidecar / main container 共享网络与卷)
- **Deployment**:曲目单,规定这首曲子需要几个乐手、版本如何
- **Service**:广播系统,听众无需关心哪个乐手在演奏,只听"小提琴声部"的输出
- **kube-scheduler**:舞台经理,根据乐手需求 (乐器大小、电源) 分配座位
- **kubelet**:每个座位的助理,确保乐手按时到场、健康演奏
- **etcd**:总谱,所有人按这份总谱演奏,任何变更先入总谱

```
        ┌──────────────────────────────────┐
        │       指挥 (Control Plane)        │
        │  apiserver / scheduler / cm      │
        │       etcd (总谱)                │
        └────┬──────┬──────┬──────┬────────┘
             │      │      │      │
        ┌────▼─┐ ┌─▼──┐ ┌─▼──┐ ┌─▼──┐
        │Node 1│ │Node2│ │Node3│ │Node4│   ← 乐手席
        │kubelet│ │kubelet│ │kubelet│ │kubelet│
        │Pods  │ │Pods │ │Pods │ │Pods │
        └──────┘ └─────┘ └─────┘ └─────┘
```

### 2.2 声明式 = "订购 vs 命令"

**命令式 (Docker)**:
```bash
docker run -d --name web -p 80:80 nginx
docker stop web
docker rm web
```
你关心"怎么做",每一步都要发号施令。

**声明式 (K8s)**:
```yaml
apiVersion: apps/v1
kind: Deployment
metadata: {name: web}
spec:
  replicas: 3
  selector: {matchLabels: {app: web}}
  template:
    metadata: {labels: {app: web}}
    spec:
      containers:
      - name: nginx
        image: nginx:1.25
        ports: [{containerPort: 80}]
```
你只声明"想要 3 个 nginx 副本",K8s 自己决定怎么达到、怎么维持。

**关键差异**:声明式让系统具备"自愈"能力——容器挂了、节点宕了、网络断了,K8s 都能自动把状态拉回声明值。

### 2.3 Reconcile Loop:K8s 的灵魂

```
期望状态 (YAML)                实际状态 (集群)
   │                              │
   └──────► 控制器 ◄──────────────┘
              │
              ▼
        差异 = 期望 - 实际
              │
              ▼
        调谐动作 (创建/删除/更新 Pod)
              │
              ▼
        实际状态 → 期望状态
              │
              ▼
          循环继续
```

**举例**:你声明 `replicas: 3`,某 Pod 因 OOM 挂掉,实际变成 2。Deployment 控制器发现差异,触发 ReplicaSet 创建新 Pod,实际回到 3。整个过程无需人工干预。

## 3. 核心概念与架构

### 3.1 双层架构总览

```
┌──────────────────────────────────────────────────────────────────┐
│                    Control Plane (Master)                        │
│  ┌──────────────┐ ┌──────────────┐ ┌──────────────────────┐      │
│  │ kube-        │ │ kube-        │ │ kube-controller-     │      │
│  │ apiserver    │ │ scheduler    │ │ manager              │      │
│  └──────┬───────┘ └──────────────┘ │ (Deployment/Replica  │      │
│         │                          │  Set/Node/Endpoint)  │      │
│         │                          └──────────────────────┘      │
│         │                                                         │
│         │           ┌──────────────────────┐                     │
│         └──────────►│       etcd           │                     │
│                     │ (集群状态总存储)     │                     │
│                     └──────────────────────┘                     │
└──────────────────────────────────────────────────────────────────┘
                              │
        ┌─────────────────────┼─────────────────────┐
        ▼                     ▼                     ▼
┌──────────────┐      ┌──────────────┐      ┌──────────────┐
│   Node 1     │      │   Node 2     │      │   Node 3     │
│  (Worker)    │      │  (Worker)    │      │  (Worker)    │
├──────────────┤      ├──────────────┤      ├──────────────┤
│ kubelet      │      │ kubelet      │      │ kubelet      │
│ kube-proxy   │      │ kube-proxy   │      │ kube-proxy   │
│ containerd   │      │ containerd   │      │ containerd   │
│  └─ runc     │      │  └─ runc     │      │  └─ runc     │
│              │      │              │      │              │
│ Pods (×N)    │      │ Pods (×N)    │      │ Pods (×N)    │
└──────────────┘      └──────────────┘      └──────────────┘
```

### 3.2 Control Plane 组件职责

| 组件 | 作用 | 关键点 |
|------|------|--------|
| **kube-apiserver** | 唯一入口,所有组件通过它通信 | REST API + Watch、水平扩展、认证授权 |
| **etcd** | 强一致 KV 存储,集群大脑 | Raft 共识、quorum N/2+1、备份命脉 |
| **kube-scheduler** | 决定 Pod 跑哪个节点 | Filter → Score → Bind、调度框架 |
| **kube-controller-manager** | 跑内置控制器的进程 | Deployment/ReplicaSet/Node/Endpoint/Job 控制器 |
| **cloud-controller-manager** | 与云厂商 API 交互 | 节点/路由/服务/卷控制器,云中立 |

### 3.3 Node 组件职责

| 组件 | 作用 | 关键点 |
|------|------|--------|
| **kubelet** | 节点上的"Pod 大使" | syncLoop + PLEG、CRI 调用、探针执行 |
| **kube-proxy** | Service 转发规则维护 | iptables / IPVS / eBPF 三种模式 |
| **container runtime** | 真正跑容器 | containerd (默认) / CRI-O / dockershim (已弃) |

### 3.4 核心术语对照

| 术语 | 定义 | 类比 |
|------|------|------|
| **Cluster** | 一组机器 + Control Plane | 一支乐团 |
| **Node** | 集群中的机器 | 一个座位 |
| **Pod** | 最小调度单元,1+ 容器共享网络/卷 | 一个乐谱架 |
| **Container** | 容器实例 | 一个乐手 |
| **Deployment** | 声明副本数与发布策略 | 曲目单 |
| **Service** | 一组 Pod 的稳定访问入口 | 广播系统 |
| **Ingress** | 七层流量入口 | 剧院大门 |
| **ConfigMap** | 配置数据 | 演出说明 |
| **Secret** | 加密配置 | 锁着的储物柜 |
| **Volume** | 持久化或共享存储 | 乐谱夹 |
| **Namespace** | 资源逻辑分组 | 不同声部 |
| **Label / Annotation** | 标签/注解 | 名牌 / 便签 |
| **CRD** | 自定义资源 | 自定义曲目类型 |

### 3.5 资源对象层级

```
Cluster
  └─ Namespace
      ├─ Pod (原子单元)
      ├─ ReplicaSet (Pod 副本管理)
      │   └─ Pod × N
      ├─ Deployment (发布策略,管理 ReplicaSet)
      │   └─ ReplicaSet × N (历史版本)
      ├─ StatefulSet (有状态应用)
      │   └─ Pod × N (有序、稳定网络标识)
      ├─ DaemonSet (每节点一个)
      ├─ Job / CronJob (批处理)
      ├─ Service (Pod 访问入口)
      ├─ Ingress (HTTP 入口)
      ├─ ConfigMap / Secret (配置)
      ├─ PersistentVolume / PersistentVolumeClaim (存储)
      └─ CustomResourceDefinition (自定义)
```

## 4. 操作流程与命令

### 4.1 kubectl 速查

```bash
# 集群信息
kubectl cluster-info                       # 集群入口
kubectl get nodes                          # 节点列表
kubectl get cs                             # 组件状态 (etcd/scheduler/cm)
kubectl top nodes                          # 节点资源使用

# 资源查看
kubectl get pods -A                        # 所有命名空间的 Pod
kubectl get pods -n default -o wide        # 详细信息(节点/IP)
kubectl get pods --show-labels             # 标签
kubectl describe pod <name>                # 事件/探针/容器状态

# 资源创建/更新
kubectl apply -f deploy.yaml               # 声明式应用
kubectl create deployment web --image=nginx  # 命令式创建
kubectl scale deployment web --replicas=5  # 扩缩容
kubectl set image deploy/web nginx=nginx:1.26  # 更新镜像

# 故障排查
kubectl logs <pod> -c <container>          # 日志
kubectl logs -f <pod> --tail=100           # 跟踪最后 100 行
kubectl exec -it <pod> -- bash             # 进入容器
kubectl debug node/<node> -it --image=busybox  # 调试节点
kubectl port-forward svc/web 8080:80       # 本地转发

# 删除
kubectl delete -f deploy.yaml              # 删除资源
kubectl delete pod <name> --force          # 强制删除 (慎用)
```

## 5. 底层原理

### 5.1 声明式 API 的实现机制

```
用户 kubectl apply
    │
    ▼
┌─────────────┐
│ apiserver   │  1. 认证 (TLS 客户端证书/Token/OIDC)
│             │  2. 授权 (RBAC/ABAC/Node)
│             │  3. 准入控制 (Mutating → Validating Webhook)
│             │  4. Schema 校验 (OpenAPI)
│             │  5. 持久化到 etcd (乐观并发 via resourceVersion)
└──────┬──────┘
       │
       ▼
┌─────────────┐
│ etcd        │  强一致 KV (Raft),版本号 + Watch 通知
└──────┬──────┘
       │ Watch (List-Watch)
       ▼
┌─────────────────────────────────────┐
│ controller-manager 内的控制器        │
│  - Deployment Controller             │
│  - ReplicaSet Controller             │
│  - Endpoint Controller               │
│  每个控制器 Informer + Reconcile    │
└──────┬──────────────────────────────┘
       │ 创建 Pod (写 etcd)
       ▼
┌─────────────┐
│ scheduler   │  Filter → Score → Bind
└──────┬──────┘
       │ Bind 到 node-X
       ▼
┌─────────────────────────────────┐
│ node-X kubelet                  │
│  Watch 到本节点新 Pod           │
│  → CRI: 创建容器                │
│  → CNI: 分配 IP                 │
│  → CSI: 挂载卷                  │
│  → 执行探针                     │
│  → 上报状态到 apiserver         │
└─────────────────────────────────┘
```

### 5.2 List-Watch 机制

**问题**:控制器如何知道集群状态变化?轮询 apiserver 太低效。

**解决**:etcd 原生支持 Watch,apiserver 转发给客户端。

```
1. List: 控制器启动,拉全量资源 (例: 所有 Pod)
   GET /api/v1/pods?resourceVersion=
2. Watch: 监听后续变更
   GET /api/v1/pods?watch=true&resourceVersion=12345
3. 收到事件: ADDED / MODIFIED / DELETED
4. 触发 Reconcile
```

**Informer**: client-go 提供的高层封装,带本地缓存 + 工作队列。

```go
// 伪代码
informer := cache.NewInformer(
    &cache.ListWatch{...},
    &v1.Pod{},
    resyncPeriod,
    cache.ResourceEventHandlerFuncs{
        AddFunc:    func(obj) { enqueue(obj) },
        UpdateFunc: func(old, new) { enqueue(new) },
        DeleteFunc: func(obj) { enqueue(obj) },
    },
)
informer.Run(stop)
```

### 5.3 etcd 的角色

```
所有 K8s 状态都存 etcd:
  /registry/pods/default/web-xxx
  /registry/services/default/web
  /registry/deployments/default/web
  /registry/clusterroles/...
  /registry/configmaps/default/...
```

**关键属性**:
- **强一致**:Raft 共识,quorum 写入
- **Watch 机制**:变更推送给 apiserver
- **乐观并发**:resourceVersion 字段防冲突
- **压缩**:历史版本定期压缩,防膨胀

**生产建议**:
- 至少 3 节点 (容忍 1 故障),5 节点 (容忍 2 故障)
- SSD 磁盘 + mlock (内存锁定)
- 配额 (quota) 默认 2GB,超出拒绝写入
- 定期备份 (velero / etcdctl snapshot)

## 6. 代码与配置示例

### 6.1 生产级 Deployment 完整模板

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: prod
  labels:
    app: web
    tier: frontend
    env: prod
spec:
  replicas: 3
  revisionHistoryLimit: 10           # 保留 10 个旧版本
  selector:
    matchLabels:
      app: web
      env: prod
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 25%
      maxUnavailable: 0
  template:
    metadata:
      labels:
        app: web
        env: prod
        tier: frontend
      annotations:
        prometheus.io/scrape: "true"
        prometheus.io/port: "8080"
    spec:
      serviceAccountName: web-sa
      securityContext:
        runAsNonRoot: true
        runAsUser: 1000
        fsGroup: 2000
      affinity:
        podAntiAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 100
            podAffinityTerm:
              labelSelector:
                matchLabels: {app: web, env: prod}
              topologyKey: kubernetes.io/hostname
      containers:
      - name: web
        image: registry.example.com/web:v1.2.3
        imagePullPolicy: IfNotPresent
        ports:
        - name: http
          containerPort: 8080
        env:
        - name: ENV
          valueFrom: {fieldRef: {fieldPath: metadata.namespace}}
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef: {name: db-secret, key: password}
        resources:
          requests: {cpu: 250m, memory: 256Mi}
          limits:   {cpu: 1000m, memory: 1Gi}
        livenessProbe:
          httpGet: {path: /healthz, port: http}
          initialDelaySeconds: 30
          periodSeconds: 10
          timeoutSeconds: 5
          failureThreshold: 3
        readinessProbe:
          httpGet: {path: /ready, port: http}
          initialDelaySeconds: 5
          periodSeconds: 3
        startupProbe:
          httpGet: {path: /startup, port: http}
          failureThreshold: 30
          periodSeconds: 10
        securityContext:
          allowPrivilegeEscalation: false
          readOnlyRootFilesystem: true
          capabilities: {drop: [ALL]}
          seccompProfile: {type: RuntimeDefault}
        volumeMounts:
        - name: tmp
          mountPath: /tmp
        - name: config
          mountPath: /etc/web
          readOnly: true
      volumes:
      - name: tmp
        emptyDir: {medium: Memory, sizeLimit: 100Mi}
      - name: config
        configMap: {name: web-config}
      terminationGracePeriodSeconds: 60
      nodeSelector:
        workload: general
      tolerations:
      - key: spot
        operator: Equal
        value: "true"
        effect: NoSchedule
```

## 7. 常见陷阱与调优

| # | 陷阱 | 后果 | 解决 |
|---|------|------|------|
| 1 | 不设 resources.requests | 调度器无法决策、节点超卖 | 必须设 requests,limits 谨慎设 |
| 2 | 只设 limits 不设 requests | requests 默认等于 limits,资源浪费 | 显式设 requests |
| 3 | livenessProbe 与 readinessProbe 用同一接口 | 启动期死循环重启 | 用 startupProbe 或分开探针 |
| 4 | 不配 terminationGracePeriod | 优雅停止 30s 后 SIGKILL,请求丢 | 设 60s+ 配 preStop hook |
| 5 | latest 标签 | 滚动更新行为不可控 | 用不可变 tag (v1.2.3) |
| 6 | 单 Pod 多无关容器 | 耦合,扩缩容不灵活 | 1 Pod 1 主容器 + 必要 sidecar |
| 7 | 不设 PodAntiAffinity | 滚动更新或节点宕机全挂 | 跨节点反亲和 |
| 8 | ConfigMap 改了不重启 | 配置不生效 | 用 Reloader / 滚动重启 |
| 9 | Namespace 滥用 | 资源配额混乱 | 按团队/环境/租户划分 |
| 10 | etcd 不备份 | 灾难不可恢复 | velero 每日备份 + 异地存 |
| 11 | RBAC 给 cluster-admin | 安全风险大 | 最小权限 + audit log |
| 12 | readinessProbe 过严 | 滚动更新卡死 | 检查探针失败阈值 |
| 13 | Pod 用 hostNetwork | 端口冲突、网络隔离失效 | 仅特殊场景用 (Calico/NodeLocalDNS) |
| 14 | 不设 priorityClass | 关键 Pod 抢不到资源 | 系统组件 high,业务 normal |
| 15 | Container 没处理 SIGTERM | 优雅停止失效,504 风暴 | preStop + sleep + 信号处理 |

## 10. 面试速答 ⭐

**Q1: 为什么 K8s 用声明式 API?**

A: 三大理由:
1. **自愈**:控制器持续 Reconcile,故障自动恢复
2. **可重复**:YAML 可版本化,多次 apply 结果一致
3. **水平扩展**:多个控制器并行 Reconcile,无状态

**Q2: Pod 和容器的区别?为什么 Pod 是最小调度单元?**

A: Pod = 1+ 容器 + 共享网络/卷。Pod 是最小调度单元的原因:
1. **共享网络**:同 Pod 容器共享 network namespace,localhost 互通
2. **共享卷**:数据共享无需网络
3. **原子调度**:同 Pod 容器必须同节点,避免跨节点通信
4. **生命周期一致**:同生共死,适合 sidecar 模式

**Q3: K8s 的核心组件有哪些?它们如何通信?**

A:
- **Control Plane**: apiserver / etcd / scheduler / controller-manager / cloud-controller-manager
- **Node**: kubelet / kube-proxy / container runtime

**通信**:
- 所有组件 → apiserver (REST + Watch)
- apiserver → etcd (gRPC + Raft)
- kubelet → container runtime (CRI gRPC)
- kube-proxy → iptables/IPVS (规则维护)
- 组件间不直接通信,都通过 apiserver 中转

**Q4: 什么是 Reconcile Loop?为什么是 K8s 灵魂?**

A: Reconcile Loop = "期望状态 vs 实际状态" 持续比较并收敛的循环。
- **声明式**:用户只声明期望
- **自愈**:故障/漂移自动恢复
- **幂等**:多次循环结果一致
- **最终一致**:不强求即时一致

**Q5: kubectl apply 的全流程?**

A:
1. kubectl 本地 schema 校验
2. POST/PUT 到 apiserver
3. apiserver 认证 (TLS)
4. 授权 (RBAC)
5. 准入控制 (Mutating → Validating Webhook)
6. Schema 二次校验
7. 写入 etcd (乐观并发,resourceVersion)
8. etcd Watch 通知 controller-manager
9. Deployment Controller 创建 ReplicaSet
10. ReplicaSet Controller 创建 Pod
11. Scheduler Watch 到新 Pod,过滤打分,Bind 到节点
12. 节点 kubelet Watch 到 Pod
13. kubelet 调 CRI 创建容器、CNI 分配 IP、CSI 挂卷
14. 容器启动,探针通过,Pod Ready

**Q6: 为什么 K8s 不直接用 MySQL/PostgreSQL 存状态?**

A:
1. **Watch 机制**:etcd 原生支持 Watch,DB 要轮询
2. **强一致**:Raft 共识,适合元数据
3. **低延迟**:内存索引,微秒级
4. **资源版本**:resourceVersion 乐观并发天然支持
5. **不适合大数据量**:配额 2GB,只存元数据

## 12. 故障复盘

### 12.1 案例:etcd 磁盘满导致全集群不可用

**现象**:
- apiserver 大量 5xx
- kubectl get 全部超时
- 所有控制器停止工作

**根因**:
- etcd 配额 2GB 满,拒绝写入
- 历史版本未压缩,占用空间
- 备份脚本失效一周未发现

**修复**:
1. `etcdctl compact <rev>` 压缩历史版本
2. `etcdctl defrag` 在线碎片整理
3. 临时调高配额到 8GB
4. 验证集群状态恢复

**防范**:
- etcd 磁盘水位告警 (70% / 85% / 95%)
- 自动压缩 + defrag 定时任务
- velero 每日备份到对象存储
- 备份有效性验证 (定期恢复测试)
- etcd 监控:keys 数、空间、raft term

### 12.2 案例:滚动更新雪崩

**现象**:
- 滚动更新 Deployment,服务出现 5xx
- 持续 5 分钟后自愈

**根因**:
- `maxUnavailable: 50%`,一次性下线一半 Pod
- preStop hook 未配置,SIGTERM 即杀进程
- 进程内长连接未排空,请求丢

**修复**:
1. 改 `maxUnavailable: 0`,确保最小可用副本
2. 加 preStop hook: `sleep 15` 等连接排空
3. readinessProbe 失败阈值调小,快速从 Endpoints 摘除

**防范**:
- 滚动更新策略模板: maxUnavailable=0, maxSurge=25%
- preStop sleep + 优雅停止标配
- 发布期监控 error rate,超阈值自动暂停

### 12.3 案例:Namespace 资源配额耗尽

**现象**:
- 某命名空间新 Pod 创建失败
- 错误: "exceeded quota"

**根因**:
- ResourceQuota 设了 Pod 数 100
- 业务方创建了大量 Job,未及时清理
- 失败 Job 累积到 100

**修复**:
1. 清理已完成 Job (`kubectl delete jobs -l completed=true`)
2. 调高 ResourceQuota 限制
3. 加 TTL 控制器: `ttlSecondsAfterFinished: 3600`

**防范**:
- Job 必设 TTL after finished
- CronJob 加 historyLimit
- ResourceQuota 告警 80%
- 定期审计 Namespace 资源占用
