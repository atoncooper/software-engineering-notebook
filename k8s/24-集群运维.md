# 24. 集群运维

> 关键词:版本升级、kubeadm upgrade、蓝绿集群、etcd 备份恢复、Velero、灾难恢复、RTO/RPO、多集群管理、Cluster API、Karmada、KubeFed、OCM、配置管理、Kustomize、Helm、Argo CD ApplicationSet、节点池、Spot 实例

## 24.1 问题定义与边界

K8s 集群从上线那一刻起,就进入 **不停变更** 的状态:K8s 版本每 4 个月一个 minor,容器运行时、CNI、CSI 持续迭代,节点系统内核需要打补丁,证书 1 年到期,etcd 数据需要保护,集群可能整个 Region 失联。集群运维要解决:

- 怎么把 **1000 节点的集群** 从 1.29 升到 1.30 而业务零感知?
- etcd 挂了怎么从备份恢复?RTO 能做到多少?
- 整个 Region 故障,怎么在另一个 Region 拉起一套等价集群?
- 5 个集群分散在不同云上,怎么统一管理应用部署?
- 节点池里的 Spot 实例被回收了,怎么不影响业务?
- 几百个团队的 Helm values 怎么治理,环境间怎么差异化?

**集群运维要解决**:

> 用 **可重复的升级路径 + 可验证的备份恢复 + 跨集群统一控制面 + 声明式配置交付** 的方式,让 K8s 集群像牲口一样可替换,而不像宠物一样需要精心呵护。

**解决**:

- K8s 版本升级(kubeadm / 托管 / 蓝绿)
- API 弃用与兼容性管理
- etcd 备份与恢复(snapshot / restore)
- 应用级备份与恢复(Velero / Kasten K10)
- 灾难恢复(DR)与跨区域多活
- 多集群管理(Cluster API / Karmada / OCM / Clusternet)
- 配置管理(Kustomize / Helm / Argo CD ApplicationSet)
- 节点池管理与滚动节点替换
- Spot 实例处理与优雅中断

**不解决**:

- **应用发布策略** → 见 [11-滚动更新与发布策略](./11-滚动更新与发布策略.md)(RollingUpdate / BlueGreen / Canary)
- **监控告警** → 见 [21-监控与指标](./21-监控与指标.md)
- **日志聚合与追踪** → 见 [22-日志与追踪](./22-日志与追踪.md)
- **故障定位** → 见 [23-故障排查与诊断](./23-故障排查与诊断.md)
- **大规模集群性能调优** → 见 [26-大规模集群优化](./26-大规模集群优化.md)
- **成本核算** → 见 [30-成本与容量规划](./30-成本与容量规划.md)

## 24.2 直觉解释

把集群运维想象成 **城市的市政养护**:

| 城市 | K8s 集群 |
|------|----------|
| 道路翻新 | K8s 版本升级 |
| 道路封闭通知 | 维护窗口 |
| 夜间施工减少影响 | 滚动升级 + PDB |
| 备用发电车 | 蓝绿集群切换 |
| 城市档案室 | etcd 备份 |
| 灾难应急中心 | DR 方案 |
| 区域联动(多城) | 多集群联邦 |
| 区块统一规划 | 配置管理 |
| 临时工管理 | Spot 实例 |
| 街道办 | 节点池 |

关键直觉:

1. **运维 = 不间断变更 + 不间断恢复**:集群永远在变(升级/扩缩/打补丁),也永远可能出故障(节点挂/etcd 损坏/Region 失联)。运维的核心是让变更和恢复都 **可重复、可验证、可回滚**。
2. **升级的本质是"换零件不停机"**:控制面滚动换、kubelet 逐节点换、API 版本逐个迁。任何一步都要保证兼容性(version skew policy)。
3. **备份不等于能恢复**:备份只有 **恢复过** 才算数。Velero backup 做了 1 年,真到恢复时才发现 PV 跨 AZ 不可用,这种故事太多。
4. **多集群 ≠ 高可用**:多集群只是提供了 **隔离边界**,要不要做 HA/DR,取决于业务流量怎么路由、数据怎么同步。多集群用错了就是 2 倍成本 + 1 倍复杂度。
5. **配置管理是配置漂移的死敌**:几百个团队的 values.yaml,只要人手改,就一定漂移。GitOps + 模板化(Kustomize/Helm)是唯一出路。
6. **节点池是滚动升级的最小单元**:不要试图一次升级 1000 个节点。按节点池分批,每批先 drain 一个节点验证,再扩大。
7. **Spot 实例省钱但不能省运维**:Spot 中断率 5-10%,如果没有 PodDisruptionBudget + Node Termination Handler + 多 AZ 分布,业务一定出事。

**3 种升级模式对比**:

| 维度 | 原地滚动 (in-place) | 蓝绿集群 (blue-green) | 托管自动 (managed) |
|------|---------------------|----------------------|---------------------|
| 代表 | kubeadm upgrade | 自建蓝绿 | EKS/GKE/AKS |
| 停机风险 | 中(逐节点 drain) | 低(流量切换) | 低(平台托管) |
| 成本 | 1x | 2x(蓝绿并存) | 1x + 平台费 |
| 复杂度 | 高(版本 skew) | 中(流量切换 + 数据迁移) | 低 |
| 回滚 | 难(版本回退) | 易(切回蓝) | 平台决定 |
| 适合 | 自建、传统 IDC | 强一致、监管要求 | 云上、DevOps 小队 |
| 1000 节点时长 | 3-5 小时 | 1-2 小时(建集群) + 切流 | 2-4 小时 |

## 24.3 核心概念与架构

### 24.3.1 K8s 版本升级全景

```
K8s 版本升级 3 层:
  +-------------------------------------------------+
  |  Control Plane(apiserver/etcd/cm/scheduler)    |
  |  kubeadm upgrade apply                          |
  |  滚动:逐个 master 节点                          |
  +-----------------------+-------------------------+
                          |
  +-----------------------v-------------------------+
  |  Worker Node(kubelet / kube-proxy)             |
  |  kubeadm upgrade node                           |
  |  滚动:逐个 worker drain + upgrade + uncordon    |
  +-----------------------+-------------------------+
                          |
  +-----------------------v-------------------------+
  |  Addons(CNI/CSI/CoreDNS/kube-proxy)            |
  |  helm upgrade / kubectl apply                  |
  |  独立升级,需匹配 K8s 版本                      |
  +-------------------------------------------------+

版本兼容性(version skew):
  - kubelet 不能比 apiserver 新
  - kubelet 可以比 apiserver 低最多 3 个 minor(1.30+)
  - kube-proxy 与 kubelet 版本应一致
  - kubectl 可以比 apiserver 高/低最多 +/- 1 minor
```

### 24.3.2 升级路径决策树

```
                  +----------------------------+
                  |  当前集群 K8s 版本?       |
                  +-------------+--------------+
                                |
              +-----------------+-----------------+
              v                 v                 v
        自建 kubeadm      云上托管 EKS/GKE    传统 IDC
              |                 |                 |
              v                 v                 v
       原地滚动升级      托管自动升级       蓝绿集群切换
              |                 |                 |
              v                 v                 v
       kubeadm upgrade    控制台/API 触发   建新集群 + 迁移
       逐 master          平台自动滚动      流量切换 + 下线旧
       逐 worker

跨 minor 跳跃:
  - 官方支持:每次最多跳 1 个 minor(1.28 -> 1.30 需先 1.29)
  - 实际操作:1.28 -> 1.29 -> 1.30(分 2 次)
  - 托管集群:平台可能支持跳跃(GKE rapid channel)

EOL(End of Life):
  - 每个 minor 支持约 14 个月
  - 1.30 EOL:2025-06 左右
  - 超过 EOL 无安全补丁,必须升级
```

### 24.3.3 etcd 备份恢复模型

```
etcd 备份 3 种方式:

方式 1:etcdctl snapshot(原生)
  +--------------+     +--------------+
  |  etcd cluster| --> |  snapshot.db | --> S3/OSS
  |  3 节点      |     |  (单文件)   |
  +--------------+     +--------------+
  优点:官方原生、轻量
  缺点:集群级备份(不能选命名空间)、恢复需停 apiserver

方式 2:Velero(应用级)
  +--------------+     +--------------+     +--------------+
  |  K8s API     | --> |  Velero      | --> |  S3 + PV     |
  |  资源对象     |     |  backup      |     |  snapshot    |
  +--------------+     +--------------+     +--------------+
  优点:应用级(可选 ns)、PV 快照、跨集群恢复
  缺点:依赖 K8s API(集群挂了可能取不到)、备份慢

方式 3:存储级快照(EBS 快照 / RBD 快照)
  +--------------+     +--------------+
  |  etcd PV     | --> |  EBS/RBD     |
  |              |     |  snapshot    |
  +--------------+     +--------------+
  优点:崩溃一致性、快
  缺点:只能整盘恢复、etcd 多副本需各自快照
```

### 24.3.4 灾难恢复(DR)拓扑

```
DR 拓扑 4 种:

拓扑 1:同 Region 跨 AZ(主备)
  +---- AZ-a ----+         +---- AZ-b ----+
  |  Cluster A   |  DNS    |  Cluster B   |
  |  (Active)    | ------> |  (Standby)   |
  |  etcd 3 节点 |  Route53|  etcd 3 节点 |
  +--------------+         +--------------+
  RPO:5 分钟(数据同步)
  RTO:15 分钟(切换 DNS + 拉起)

拓扑 2:跨 Region 主备(Active-Passive)
  +-- Region A --+         +-- Region B --+
  |  Cluster A   | Velero  |  Cluster B   |
  |  (Active)    | backup  |  (Standby)   |
  |              | ------> |              |
  |              |   S3    |              |
  +--------------+         +--------------+
  RPO:1 小时(Velero schedule)
  RTO:1-2 小时(恢复 + 切流)

拓扑 3:跨 Region 双活(Active-Active)
  +-- Region A --+         +-- Region B --+
  |  Cluster A   | <-----> |  Cluster B   |
  |  (Active)    | 数据同步 |  (Active)    |
  |              |         |              |
  +------+-------+         +------+-------+
         |                        |
         +----- Global LB --------+
  RPO:接近 0(数据实时同步)
  RTO:接近 0(双活流量)
  代价:数据一致性复杂(需分布式 DB 支持)

拓扑 4:多集群联邦(Karmada)
  +----------------------------------+
  |  Karmada Control Plane           |
  |  (PropagationPolicy + Override)  |
  +----+---------+---------+---------+
       |         |         |
       v         v         v
   Cluster A  Cluster B  Cluster C
   (北京)    (上海)    (新加坡)
   调度策略:权重 / 亲和 / 故障转移
```

### 24.3.5 多集群管理 4 种模式

```
模式 1:Hub-Spoke(集中管理)
              +--------------+
              |  Hub Cluster |
              |  (管理面)   |
              +--+---+---+---+
                 |   |   |
          +------+   |   +------+
          v          v          v
       Spoke-1    Spoke-2    Spoke-3

  代表:Cluster API、Azure Arc、OCM
  特点:管理面统一,工作负载在 spoke
  适合:集团统一管理多子公司集群

模式 2:联邦调度(应用分发)
              +--------------+
              |  Karmada     |
              |  Control Plane|
              +--+---+---+---+
                 |   |   |
          +------+   |   +------+
          v          v          v
       Cluster-1  Cluster-2  Cluster-3
       (调度权重 30) (40) (30)

  代表:Karmada、KubeFed(已存档)
  特点:应用按策略分发到多集群
  适合:多活、容灾、地理就近

模式 3:Service Mesh 多集群(服务互通)
   Cluster A --mTLS-- Cluster B
       |                  |
     Service            Service
       |                  |
       +--- 全局服务发现 -+

  代表:Istio Multi-Cluster、Linkerd
  特点:服务跨集群通信透明
  适合:跨集群服务调用、灰度跨集群

模式 4:GitOps 多集群(配置同步)
              +--------------+
              |  Git Repo    |
              |  (单一真源) |
              +--+---+---+---+
                 |   |   |
          +------+   |   +------+
          v          v          v
       Argo CD    Argo CD    Argo CD
       (Cluster A)(Cluster B)(Cluster C)

  代表:Argo CD ApplicationSet、FluxCD
  特点:Git 是唯一真源,各集群 Argo CD 拉取
  适合:配置一致性、多环境部署
```

### 24.3.6 配置管理工具栈

```
配置管理 4 层:

Layer 1:模板(Kustomize / Helm)
  - Kustomize:覆盖叠加(无模板,纯 YAML patch)
  - Helm:模板引擎({{ .Values }})+ 包管理

Layer 2:发布(GitOps)
  - Argo CD:Pull 模型,集群里跑 agent
  - Flux CD:Pull 模型,与 Argo 类似

Layer 3:多集群分发(ApplicationSet)
  - Argo CD ApplicationSet:按 cluster generator 生成 Application
  - Karmada PropagationPolicy:按调度策略分发

Layer 4:密钥管理(External Secrets)
  - External Secrets Operator:从 Vault/AWS SM 拉密钥
  - Sealed Secrets:加密后可存 Git
  - SOPS:加密 K8s YAML

工具选型矩阵:
  +--------------+-------------+-------------+
  |              |  Kustomize  |  Helm       |
  +--------------+-------------+-------------+
  |  学习曲线    |  平         |  中         |
  |  灵活度      |  中         |  高         |
  |  包管理      |  无         |  有         |
  |  适合        |  内部应用   |  公开 chart |
  +--------------+-------------+-------------+
```

### 24.3.7 节点池与 Spot 实例

```
节点池(NodePool / ManagedNodeGroup):
  +-------------------------------------+
  |  Cluster                            |
  |  +------------+  +------------+     |
  |  | NodePool-A |  | NodePool-B |     |
  |  | spot x100  |  | on-demand  |     |
  |  | (批处理)   |  | x50(核心) |     |
  |  +------------+  +------------+     |
  |  +------------+  +------------+     |
  |  | NodePool-C |  | NodePool-D |     |
  |  | GPU x20    |  | arm64 x30  |     |
  |  | (训练)     |  | (日志)     |     |
  |  +------------+  +------------+     |
  +-------------------------------------+

Spot 实例处理:
  1. AWS Node Termination Handler(ATH)
     - 监听 Spot 中断通知(2 分钟)
     - drain 节点 + 通知应用
  2. PodDisruptionBudget
     - 保证 drain 时不破坏 quorum
  3. 多 AZ 分布
     - 不让所有 Spot 在同一 AZ
  4. 优先级抢占
     - Spot 被回收时,低优先级 Pod 先让位
  5. Cluster Autoscaler
     - Spot 节点丢失时,自动补 on-demand
```

## 24.4 操作流程与命令

### 24.4.1 kubeadm 升级完整流程(1.29 → 1.30)

```bash
# ============================================================
# 阶段 0:升级前检查(Pre-flight)
# ============================================================

# 0.1 检查当前版本
kubectl get nodes
# NAME           STATUS   VERSION
# master-01      Ready    v1.29.6
# master-02      Ready    v1.29.6
# worker-01      Ready    v1.29.6

# 0.2 检查 API 弃用(关键!)
kubectl get --raw /metrics | grep apiserver_requested_deprecated_apis
# 或用 pluto / kubent 工具
pluto detect-files --target-version v1.30.0
kubent

# 0.3 检查所有节点 Ready
kubectl get nodes -o wide | grep -v Ready

# 0.4 检查 PDB 是否就绪(防 drain 卡死)
kubectl get poddisruptionbudget -A

# 0.5 备份 etcd(必做!)
ETCDCTL_API=3 etcdctl snapshot save /backup/etcd-pre-upgrade.db \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/peer.crt \
  --key=/etc/kubernetes/pki/etcd/peer.key

# 0.6 备份 K8s 配置
cp -r /etc/kubernetes /backup/etc-kubernetes-$(date +%Y%m%d)
cp /root/.kube/config /backup/kube-config-$(date +%Y%m%d)

# 0.7 升级 kubeadm 工具(第一个 master)
apt-mark unhold kubeadm
apt-get update && apt-get install -y kubeadm=1.30.0-00
apt-mark hold kubeadm
kubeadm version

# ============================================================
# 阶段 1:升级第一个 master 节点
# ============================================================

# 1.1 升级计划检查
kubeadm upgrade plan
# 输出:COMPONENT   CURRENT    TARGET
#       kube-apiserver v1.29.6   v1.30.0
#       ...

# 1.2 应用升级
kubeadm upgrade apply v1.30.0
# 这一步会:
#   - 升级 kube-apiserver / controller-manager / scheduler / kube-proxy
#   - 升级 etcd(若需)
#   - 更新 kubeadm-config / kube-proxy-config ConfigMap
#   - 重新签发证书(若快过期)

# 1.3 升级 kubelet / kubectl
apt-mark unhold kubelet kubectl
apt-get update && apt-get install -y kubelet=1.30.0-00 kubectl=1.30.0-00
apt-mark hold kubelet kubectl

# 1.4 重启 kubelet
systemctl daemon-reload
systemctl restart kubelet

# 1.5 验证
kubectl get nodes
# master-01   Ready    v1.30.0  ← 已升级
# master-02   Ready    v1.29.6  ← 待升级
# worker-01   Ready    v1.29.6  ← 待升级

# ============================================================
# 阶段 2:升级其他 master 节点(逐个)
# ============================================================

# 2.1 SSH 到 master-02
ssh master-02

# 2.2 升级 kubeadm(同上)
apt-mark unhold kubeadm
apt-get update && apt-get install -y kubeadm=1.30.0-00
apt-mark hold kubeadm

# 2.3 应用升级(注意:其他 master 用 node,不用 apply)
kubeadm upgrade node

# 2.4 升级 kubelet / kubectl + 重启
apt-mark unhold kubelet kubectl
apt-get install -y kubelet=1.30.0-00 kubectl=1.30.0-00
apt-mark hold kubelet kubectl
systemctl daemon-reload && systemctl restart kubelet

# 2.5 退出,验证
exit
kubectl get nodes
# master-01   Ready    v1.30.0
# master-02   Ready    v1.30.0  ← 已升级
# worker-01   Ready    v1.29.6  ← 待升级

# ============================================================
# 阶段 3:升级 worker 节点(逐个,带 drain)
# ============================================================

# 3.1 drain worker-01(驱逐 Pod)
kubectl drain worker-01 --ignore-daemonsets --delete-emptydir-data \
  --force --timeout=120s
# 注意:
#   - --ignore-daemonsets:DaemonSet Pod 不驱逐
#   - --delete-emptydir-data:emptyDir 数据丢弃
#   - --force:裸 Pod(无 controller)也驱逐
#   - PDB 会阻止驱逐,需先确保 PDB 允许

# 3.2 SSH 到 worker-01
ssh worker-01

# 3.3 升级 kubeadm / kubelet / kubectl
apt-mark unhold kubeadm kubelet kubectl
apt-get update && apt-get install -y \
  kubeadm=1.30.0-00 kubelet=1.30.0-00 kubectl=1.30.0-00
apt-mark hold kubeadm kubelet kubectl

# 3.4 应用升级
kubeadm upgrade node

# 3.5 重启 kubelet
systemctl daemon-reload && systemctl restart kubelet

# 3.6 退出
exit

# 3.7 uncordon worker-01(恢复调度)
kubectl uncordon worker-01

# 3.8 验证
kubectl get nodes
# worker-01   Ready    v1.30.0  ← 已升级

# 3.9 重复 3.1-3.8 升级其他 worker

# ============================================================
# 阶段 4:升级后验证
# ============================================================

# 4.1 所有节点版本一致
kubectl get nodes
# 全部 v1.30.0

# 4.2 系统组件健康
kubectl get componentstatuses
# scheduler            Healthy
# controller-manager   Healthy
# etcd-0               Healthy
# etcd-1               Healthy
# etcd-2               Healthy

# 4.3 所有 Pod Running
kubectl get pods -A | grep -v Running | grep -v Completed

# 4.4 验证 API 弃用已清理
```

## 24.5 底层原理

### 24.5.1 K8s 版本偏差策略(Version Skew Policy)

K8s 各组件之间允许存在 **有限的版本差异**,这是滚动升级可行的基础。

```
组件版本关系(以升级到 1.30 为例):

  kube-apiserver: 1.30
       |
       +-- kubelet:        1.30 / 1.29 / 1.28(低最多 3)
       +-- kube-proxy:     1.30 / 1.29 / 1.28(与 kubelet 一致)
       +-- kubectl:        1.31 / 1.30 / 1.29(±1)

源码: kubernetes/component-base/version/skew.go
       skewPolicyMax(kubelet, apiserver) = 3 minor(1.30+)
       skewPolicyMax(kubectl, apiserver) = 1 minor

为什么允许 skew:
  1. 滚动升级需要时间(1000 节点数小时)
  2. API 兼容性靠 API 版本号(v1, apps/v1, networking.k8s.io/v1)
  3. etcd 数据 schema 兼容(protobuf 字段可选)

为什么限制 skew:
  1. 新 apiserver 可能写老 kubelet 不认识的字段
  2. 老 kubelet 的 status 可能丢新 apiserver 期望的字段
  3. 3 个 minor 后 API 可能已弃用
```

### 24.5.2 API 弃用机制(Deprecation Policy)

K8s API 遵循严格的弃用规则,这是集群升级能平滑的关键。

```
K8s API 弃用规则(官方 policy):

  GA(stable,v1):     至少 12 个月 / 2 个 release 后删除
  Beta(v1betaX):     至少 9 个月 / 3 个 release 后删除
  Alpha(v1alphaX):   任意时刻可删除

弃用流程:
  1. 标记 deprecated(API 响应带 warning header)
  2. 文档公告(deprecation guide)
  3. 等待宽限期
  4. 删除 API + 提供 migration guide

源码: kubernetes/api/*/registration.go
       stanza "deprecated" 标记

历史弃用案例:
  - extensions/v1beta1 (Deployment/Ingress 等) → 1.16 删除
  - networking.k8s.io/v1beta1 (Ingress) → 1.22 删除
  - policy/v1beta1 (PodSecurityPolicy) → 1.25 删除
  - batch/v1beta1 (CronJob) → 1.25 删除
  - autoscaling/v2beta2 (HPA) → 1.26 删除

升级前必查:
  $ kubectl get --raw /metrics | grep deprecated
  $ pluto detect-files --target-version v1.30.0
  $ kubent(https://github.com/doitintl/kube-no-trouble)

API Server 弃用 warning 源码:
  kubernetes/staging/src/k8s.io/apiserver/pkg/endpoints/handlers/
    response.go - addDeprecationHeader()
```

### 24.5.3 etcd 快照一致性原理

```
etcd 快照一致性保证:

  1. MVCC 多版本并发控制
     - etcd 每次写都生成新 revision
     - 快照取一个 revision 的所有 key
     - 快照期间不阻塞写(读 revision 一致视图)

  2. 快照流程:
     a. etcdctl 调用 Maintenance.ScheduleSnapshot
     b. etcd server 触发 raft snapshot
     c. 持久化当前 applied index
     d. 后台 goroutine 定期 snapshot
     e. snapshot.db 写入文件

  3. 快照内容:
     - 所有 key-value(revision 视图)
     - cluster 信息(members)
     - raft 状态(term/index)
     - 旧 revision 可压缩(compact)

  4. 恢复时:
     - etcdctl snapshot restore
     - 重建 raft 集群(用 --initial-cluster)
     - 加载快照数据
     - 重新选举 leader
     - 接受新写

源码: etcd/etcdserver/server.go - Snapshot()
       etcd/mvcc/backend/batch_tx.go - Commit()

注意:
  - 快照是 **单个 revision 的视图**,不是"按时间点"
  - 快照恢复后,从快照 revision 开始接受新写
  - 快照不可跨大版本恢复(etcd 3.4 快照不能在 3.5 直接恢复,需 etcdctl migrate)
```

### 24.5.4 Velero 备份模型

```
Velero 备份 6 阶段:

  1. 触发(velero backup create)
     - 用户/CronJob 调用
     - 创建 Backup CR

  2. 收集(Backup Controller)
     - 读 Backup CR
     - 通过 K8s API list 所有匹配资源
     - 序列化为 JSON

  3. 快照(Volume Snapshot)
     - 调 CSI driver 的 snapshot 接口
     - 或云厂商 snapshot API(EBS/CBS)
     - 记录 snapshot ID

  4. 打包(tar)
     - 资源 JSON + snapshot 元数据
     - 打包为 tar.gz

  5. 上传(Object Storage)
     - 上传到 S3/OSS/MinIO
     - 上传到 backup location

  6. 状态(Backup CR status)
     - 完成/失败/部分成功
     - 记录 warnings/errors

恢复 4 阶段:
  1. 下载 tar.gz
  2. 解析资源 JSON
  3. 按 namespace 恢复(可改名)
  4. 从 snapshot 恢复 PV(若支持)

源码: velero/pkg/backup/backup.go
       velero/pkg/restore/restore.go

关键限制:
  - 备份依赖 K8s API(apiserver 挂了无法备份)
  - PV 快照依赖 CSI driver(部分 driver 不支持)
  - 跨集群恢复需 backup location 共享
  - 不备份持久化的 etcd(只备份 K8s 资源对象)
```

### 24.5.5 Karmada 联邦调度原理

```
Karmada 调度流程:

  1. 用户在 Karmada 控制面创建 Deployment
     - 此时 **没有实际 Pod 创建**
     - 只在 Karmada etcd 存 Deployment 对象

  2. Karmada scheduler 监听 Deployment
     - 读取 PropagationPolicy
     - 按策略分发到成员集群

  3. ResourceBinding 生成
     - Karmada 为每个工作负载创建 ResourceBinding
     - 记录:目标集群列表 + 每集群副本数

  4. Execution Controller
     - 监听 ResourceBinding
     - 把 Deployment "翻译"到成员集群
     - 实际在成员集群创建 Deployment

  5. 成员集群运行
     - 成员集群的 kube-scheduler 调度 Pod
     - 成员集群的 kubelet 启动容器

  6. 状态回传
     - Karmada 把成员集群的 Deployment status 汇总
     - 写回 Karmada 控制面的 Deployment status

调度策略类型:
  - clusterAffinity:按 label 选中集群
  - replicaScheduling:副本分配(总分/权重/静态)
  - spreadConstraints:分散约束(类似 Pod topologySpread)
  - taints/tolerations:集群污点容忍

源码: karmada/pkg/scheduler/scheduler.go
       karmada/pkg/controllers/execution/execution_controller.go

与 KubeFed 区别:
  - KubeFed 已存档(2021)
  - Karmada 重写了调度器(更高效)
  - Karmada 支持故障转移(成员集群挂自动迁)
  - Karmada 支持 Override Policy(差异化配置)
```

### 24.5.6 Cluster API 工作模型

```
Cluster API(CAPI)核心概念:

  Cluster:逻辑集群对象
    +-- MachineDeployment(类似 Deployment,管 Machine)
          +-- MachineTemplate(模板,spec 而非 status)
          +-- Machine(类似 Pod,一个虚拟机/物理机)
                +-- BootstrapConfig(kubeadm 等)
                +-- InfrastructureMachine(云厂商 VM)

  Cluster API 控制器:
  1. Cluster Controller:管 Cluster 生命周期
  2. Machine Controller:管 Machine 生命周期
  3. Bootstrap Controller:kubeadm 配置生成
  4. Infrastructure Controller:云资源创建(AWS/GCP/vSphere)

工作流(创建集群):
  1. 用户 apply Cluster + MachineDeployment YAML
  2. Cluster Controller 创建 namespace、network 等
  3. Infrastructure Controller 创建 VM(调云 API)
  4. Bootstrap Controller 生成 kubeadm 配置(云 init 注入)
  5. VM 启动后 kubeadm init/join
  6. Machine Controller 标记 Ready

升级流程:
  1. 修改 MachineDeployment 的 version 字段
  2. MachineDeployment 滚动替换 Machine(类似 Deployment 替换 Pod)
  3. 旧 Machine drain + 删除
  4. 新 Machine 创建 + 加入集群
  5. 完成

源码: cluster-api/api/v1beta1/*_types.go
       cluster-api/controllers/machine_controller.go

优势:
  - 集群生命周期声明式
  - 升级 = 改 YAML(GitOps 友好)
  - 跨云厂商统一 API
```

### 24.5.7 节点 drain 与 PDB 协作

```
kubectl drain 工作流:

  1. cordon 节点(设为 Unschedulable)
     - kubectl patch node xxx -p '{"spec":{"unschedulable":true}}'

  2. 驱逐(evict)Pod
     - 调 Eviction API(/api/v1/namespaces/<ns>/pods/<pod>/eviction)
     - 不是直接 delete pod
     - Eviction 会尊重 PDB

  3. PDB 检查
     - PodDisruptionBudget:
       spec.minAvailable: 2  (至少 2 个可用)
       spec.selector: matchLabels: app: web
     - 若驱逐此 Pod 会破坏 PDB → 拒绝(返回 429)
     - 等 Pod 重新调度后再驱逐

  4. 优雅终止
     - kubelet 收到 delete → 触发 preStop hook
     - 发 SIGTERM 给容器
     - 等待 terminationGracePeriodSeconds(默认 30s)
     - 强制 SIGKILL

  5. 超时
     - --timeout=120s 超时后 drain 失败
     - 留下 Pod 未驱逐

源码: kubernetes/staging/src/k8s.io/api/policy/v1/types.go
       kubernetes/pkg/quota/eviction/eviction.go - DisruptionBudget

PDB 关键点:
  - PDB 只保护 voluntary disruption(主动驱逐)
  - 不保护 involuntary disruption(节点硬件故障)
  - minAvailable 和 maxUnavailable 互斥
  - 没有 controller 的裸 Pod 不受 PDB 保护
```

## 24.6 代码与配置示例

### 24.6.1 生产级升级 Runbook(脚本)

```bash
#!/bin/bash
# ============================================================
# k8s-upgrade.sh - K8s 集群升级脚本(1.29 → 1.30)
# 使用:./k8s-upgrade.sh <target-version> [master|worker|all]
# ============================================================
set -euo pipefail

TARGET_VERSION="${1:-1.30.0}"
SCOPE="${2:-all}"
LOG_FILE="/var/log/k8s-upgrade-$(date +%Y%m%d-%H%M%S).log"
BACKUP_DIR="/backup/k8s-upgrade-$(date +%Y%m%d-%H%M%S)"

log() { echo "[$(date +'%F %T')] $*" | tee -a "$LOG_FILE"; }
err() { echo "[$(date +'%F %T')] ERROR: $*" | tee -a "$LOG_FILE" >&2; exit 1; }

# 1. 预检查
preflight() {
  log "=== 预检查 ==="
  kubectl get nodes -o wide | tee -a "$LOG_FILE"
  kubectl get componentstatuses | tee -a "$LOG_FILE"

  # 1.1 所有节点 Ready
  NOT_READY=$(kubectl get nodes -o jsonpath='{.items[?(@.status.conditions[?(@.type=="Ready")].status!="True")].metadata.name}')
  [[ -z "$NOT_READY" ]] || err "存在 NotReady 节点:$NOT_READY"

  # 1.2 PDB 检查
  kubectl get poddisruptionbudget -A -o wide | tee -a "$LOG_FILE"

  # 1.3 API 弃用检查
  command -v pluto >/dev/null && pluto detect-files --target-version "v$TARGET_VERSION" || log "pluto 未安装,跳过弃用检查"

  # 1.4 备份 etcd
  mkdir -p "$BACKUP_DIR"
  log "备份 etcd 到 $BACKUP_DIR/etcd.db"
  ETCDCTL_API=3 etcdctl snapshot save "$BACKUP_DIR/etcd.db" \
    --endpoints=https://127.0.0.1:2379 \
    --cacert=/etc/kubernetes/pki/etcd/ca.crt \
    --cert=/etc/kubernetes/pki/etcd/peer.crt \
    --key=/etc/kubernetes/pki/etcd/peer.key

  # 1.5 备份 K8s 配置
  cp -r /etc/kubernetes "$BACKUP_DIR/"
  log "预检查完成"
}

# 2. 升级 master
upgrade_master() {
  log "=== 升级 master 节点 ==="
  MASTERS=$(kubectl get nodes -l node-role.kubernetes.io/control-plane -o name)

  for master in $MASTERS; do
    NAME=${master#node/}
    log "升级 master: $NAME"

    # 升级 kubeadm
    ssh "$NAME" "
      apt-mark unhold kubeadm && \
      apt-get update && \
      apt-get install -y kubeadm=$TARGET_VERSION-00 && \
      apt-mark hold kubeadm
    "

    # 第一个 master 用 apply,其他用 node
    if [[ "$NAME" == "$(echo $MASTERS | head -1 | sed 's|node/||')" ]]; then
      ssh "$NAME" "kubeadm upgrade apply v$TARGET_VERSION -y"
    else
      ssh "$NAME" "kubeadm upgrade node"
    fi

    # 升级 kubelet / kubectl
    ssh "$NAME" "
      apt-mark unhold kubelet kubectl && \
      apt-get install -y kubelet=$TARGET_VERSION-00 kubectl=$TARGET_VERSION-00 && \
      apt-mark hold kubelet kubectl && \
      systemctl daemon-reload && \
      systemctl restart kubelet
    "

    # 等待 Ready
    log "等待 $NAME Ready..."
    kubectl wait --for=condition=Ready "node/$NAME" --timeout=300s
    log "$NAME 升级完成"
  done
}

# 3. 升级 worker
upgrade_worker() {
  log "=== 升级 worker 节点(逐个)==="
  WORKERS=$(kubectl get nodes -l '!node-role.kubernetes.io/control-plane' -o name)

  for worker in $WORKERS; do
    NAME=${worker#node/}
    log "升级 worker: $NAME"

    # drain
    log "drain $NAME"
    kubectl drain "$NAME" --ignore-daemonsets --delete-emptydir-data \
      --force --timeout=300s || err "drain $NAME 失败"

    # 升级
    ssh "$NAME" "
      apt-mark unhold kubeadm kubelet kubectl && \
      apt-get update && \
      apt-get install -y kubeadm=$TARGET_VERSION-00 kubelet=$TARGET_VERSION-00 kubectl=$TARGET_VERSION-00 && \
      apt-mark hold kubeadm kubelet kubectl && \
      kubeadm upgrade node && \
      systemctl daemon-reload && \
      systemctl restart kubelet
    "

    # uncordon
    kubectl uncordon "$NAME"
    log "等待 $NAME Ready..."
    kubectl wait --for=condition=Ready "node/$NAME" --timeout=300s

    # 验证业务健康
    log "验证业务(30s 观察期)"
    sleep 30
    UNHEALTHY=$(kubectl get pods -A --field-selector=status.phase!=Running,status.phase!=Succeeded --no-headers | wc -l)
    [[ "$UNHEALTHY" -lt 5 ]] || err "$NAME 升级后异常 Pod 数:$UNHEALTHY"
    log "$NAME 升级完成"
  done
}

# 4. 验证
verify() {
  log "=== 升级后验证 ==="
  kubectl get nodes -o wide | tee -a "$LOG_FILE"
  kubectl get componentstatuses | tee -a "$LOG_FILE"

  # 版本一致
  VERSIONS=$(kubectl get nodes -o jsonpath='{.items[*].status.nodeInfo.kubeletVersion}' | tr ' ' '\n' | sort -u)
  COUNT=$(echo "$VERSIONS" | wc -l)
  [[ "$COUNT" -eq 1 ]] || err "节点版本不一致:$VERSIONS"

  log "=== 升级完成 ==="
}

# 主流程
case "$SCOPE" in
  preflight) preflight ;;
  master) preflight; upgrade_master; verify ;;
  worker) preflight; upgrade_worker; verify ;;
  all) preflight; upgrade_master; upgrade_worker; verify ;;
  *) err "未知 scope: $SCOPE";; 
esac
```

### 24.6.3 etcd 备份脚本(定时任务)

```bash
#!/bin/bash
# ============================================================
# etcd-backup.sh - etcd 定时备份(每 3 小时,保留 7 天)
# ============================================================
set -euo pipefail

BACKUP_DIR="/backup/etcd"
S3_BUCKET="k8s-etcd-backup"
RETENTION_DAYS=7
DATE=$(date +%Y%m%d-%H%M)
BACKUP_FILE="$BACKUP_DIR/etcd-$DATE.db"
ENDPOINTS="https://etcd-01:2379,https://etcd-02:2379,https://etcd-03:2379"

mkdir -p "$BACKUP_DIR"

# 1. 备份
ETCDCTL_API=3 etcdctl snapshot save "$BACKUP_FILE" \
  --endpoints="$ENDPOINTS" \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/peer.crt \
  --key=/etc/kubernetes/pki/etcd/peer.key

# 2. 校验
ETCDCTL_API=3 etcdctl snapshot status "$BACKUP_FILE" --write-out=json > "$BACKUP_FILE.status"

# 3. 加密(可选)
gpg --batch --yes --passphrase "$GPG_PASSPHRASE" \
  --symmetric "$BACKUP_FILE"
mv "$BACKUP_FILE.gpg" "$BACKUP_FILE"

# 4. 上传 S3
aws s3 cp "$BACKUP_FILE" "s3://$S3_BUCKET/$(date +%Y)/$(date +%m)/"

# 5. 清理本地旧备份
find "$BACKUP_DIR" -name "etcd-*.db" -mtime +$RETENTION_DAYS -delete

# 6. 清理 S3 旧备份(S3 lifecycle 也可)
aws s3api list-objects-v2 --bucket "$S3_BUCKET" --query "Contents[?LastModified<='$(date -d '-30 days' +%Y-%m-%d)'].Key" --output text | \
  xargs -I {} aws s3api delete-object --bucket "$S3_BUCKET" --key {}

# 7. 健康检查
SIZE=$(stat -c%s "$BACKUP_FILE")
[[ $SIZE -gt 1000000 ]] || { echo "备份异常,文件 < 1MB"; exit 1; }

echo "etcd 备份成功:$BACKUP_FILE ($(numfmt --to=iec $SIZE))"
```

## 24.7 常见陷阱与调优

| # | 陷阱 | 后果 | 解决 |
|---|------|------|------|
| 1 | 跨 minor 跳跃升级(1.28 → 1.30) | API 弃用导致资源不可用 | 每次只跳 1 个 minor,先 1.28 → 1.29 → 1.30 |
| 2 | 升级前不查 API 弃用 | apps/v1beta1 等资源消失 | pluto / kubent / deprecation check |
| 3 | kubeadm upgrade 跳过 master 直接 worker | kubelet 比 apiserver 新,版本 skew 报错 | 严格顺序:master 1 → master N → worker |
| 4 | drain 不带 --ignore-daemonsets | drain 卡死(DaemonSet Pod 无法驱逐) | drain 必带 --ignore-daemonsets --delete-emptydir-data |
| 5 | drain 没等业务健康就升下一个 | 滚动雪崩(多个节点同时驱逐) | 每个节点升级后观察 5 分钟,核心业务 P99 延迟正常再升下一个 |
| 6 | PDB 配置过严(minAvailable=100%) | drain 永远失败,升级卡死 | 单实例应用用 maxUnavailable:1,多实例用 minAvailable:N-1 |
| 7 | 没做 PDB | drain 一次赶光所有副本 | 核心业务全部配 PDB |
| 8 | etcd 备份从未恢复过 | 真到恢复时发现快照损坏 / API 失效 | 每月做 1 次 DR 演练,从备份恢复到测试集群 |
| 9 | etcd 备份只存本地 | 节点故障备份一起丢 | 备份必须上对象存储(S3/OSS)+ 跨区域复制 |
| 10 | Velero 备份未验证 PV 恢复 | PV 跨 AZ 不可用,恢复失败 | 测试集群定期 restore,验证 PV 数据完整 |
| 11 | Velero schedule 太频繁 | 对象存储成本飙升 + APIServer list 压力 | 按重要性分级:核心 ns 每小时,普通 ns 每天 |
| 12 | 多集群配置漂移 | 集群间行为不一致 | GitOps + ApplicationSet,杜绝人手 kubectl apply |
| 13 | Karmada 调度策略未配故障转移 | 单集群挂整体不工作 | PropagationPolicy 配 clusterTolerations + replicaScheduling |
| 14 | Cluster API 升级未配 MachineHealthCheck | 节点卡死无人换 | 配 MachineHealthCheck, unhealthy 自动重建 |
| 15 | Spot 实例无 Node Termination Handler | Spot 被回收 Pod 直接丢 | 装 ATH + PDB + 多 AZ 分布 |
| 16 | Spot 比例过高(>60%) | 中断潮业务大范围抖动 | Spot:OnDemand = 3:7 或 4:6,核心业务不上 Spot |
| 17 | 升级窗口选错(业务高峰) | 升级失败影响大 | 选业务低峰(凌晨 2-5 点),预先通告 |
| 18 | 证书到期未提前续 | 集群全挂 | kubeadm certs check-expiration 提前 30 天告警 |
| 19 | CoreDNS 升级跳过 | DNS 解析异常 | CoreDNS 跟 K8s 版本匹配,见 compatibility matrix |
| 20 | 升级后 addon 未升级(CNI/CSI) | 网络挂 / 卷挂 | 升级 checklist 包含 addon 版本兼容矩阵 |
| 21 | 蓝绿集群数据不一致 | 切流后业务异常 | 双写 + 数据校验,切流前最后 1 次对账 |
| 22 | 多集群权限未统一 | 集群间 RBAC 不一致 | 用 OCM/GitHub Teams 统一权限,OIDC 集成 |
| 23 | etcd 恢复后未等集群稳定就上业务 | 选主抖动 + 写丢失 | 恢复后等 5 分钟,验证 componentstatuses 再放流量 |
| 24 | Helm values 跨环境硬编码 | 环境差异难管理 | values-dev.yaml / values-prod.yaml 分层 |
| 25 | 不做升级演练 | 真升级时出意外 | 季度升级演练(测试集群 → 预发 → 生产) |

**核心调优建议**:

```
升级调优 6 条:

1. 升级前 1 周:全量 etcd 备份 + Velero 备份 + DR 演练
2. 升级前 1 天:pluto / kubent 检查 API 弃用,修复所有弃用 API
3. 升级当天:小流量集群先升级(预发),验证 2 小时再升生产
4. 升级中:每节点升级后观察 5-10 分钟,核心指标正常再升下一个
5. 升级后:全量业务健康检查 + 24 小时观察期
6. 升级后 1 周:复盘 + 文档更新

etcd 调优 4 条:

1. etcd 数据盘用 NVMe SSD(fsync < 10ms)
2. 定期 compact + defrag(避免 db 膨胀)
3. quota-backend-bytes = 8GB(超 8GB 告警)
4. 多副本跨 AZ(3 节点放 3 个 AZ)

多集群调优 3 条:

1. Karmada 控制面独立集群(不与业务集群混部)
2. PropagationPolicy 必配故障转移
3. 跨集群服务调用走 Service Mesh(Istio Multi-Cluster)
```

## 24.8 工业案例与基准数据

### 24.8.1 阿里 ACK:千节点集群零停机升级

**场景**:某金融客户 ACK Pro 集群 1000+ 节点,业务 7x24,升级窗口 2 小时。

**方案**:

1. **升级前 1 周**
   - 用 pluto / kubent 全量扫描弃用 API
   - 用 ACK 智能运维平台模拟升级(预演)
   - etcd 全量备份 + Velero 应用级备份

2. **升级策略**
   - 控制面:ACK 托管(自动滚动,15 分钟)
   - worker 节点:节点池分批(每池 100 节点,4 批)
   - 每批先 drain 1 节点验证,再扩大

3. **节点池滚动**
   ```
   批次 1:NodePool-A 100 节点(0:00-0:30)
   批次 2:NodePool-B 100 节点(0:30-1:00)
   批次 3:NodePool-C 100 节点(1:00-1:30)
   批次 4:NodePool-D 100 节点(1:30-2:00)
   ```
   - 每节点 drain 5 分钟,upgrade 3 分钟,uncordon 1 分钟,观察 5 分钟

4. **业务保障**
   - PDB:minAvailable=70%(允许 30% 抖动)
   - 多 AZ 分布(每池跨 3 AZ)
   - HPA 缩容延迟 10 分钟(避免 drain 期间震荡)

5. **监控**
   - 业务 P99 延迟告警(>100ms)
   - 错误率告警(>0.1%)
   - Pod Pending 告警(>30s)

**结果**:升级耗时 1 小时 45 分,业务零感知,P99 延迟峰值 65ms(<100ms 阈值)。

### 24.8.2 字节跳动:1000 节点升级 0 停机

**场景**:ByteKube 内部平台,1000+ 节点自建集群,K8s 1.26 → 1.28。

**方案**:

1. **升级路径**:1.26 → 1.27 → 1.28(分两次,间隔 1 周)
2. **API 弃用治理**
   - 自研工具扫描全集群 CRD 用了弃用 API
   - 提前 3 个月推动业务方迁移
3. **蓝绿集群切换**(关键业务)
   - 建新集群(1.28)+ 流量灰度
   - 业务自检 → 灰度 5% → 50% → 100%
   - 旧集群保留 1 周下线
4. **原地升级**(普通业务)
   - kubeadm 滚动升级
   - 节点池分批,每批 50 节点

## 24.10 面试速答

**Q1: K8s 升级有几种模式?**

3 种:原地滚动(kubeadm upgrade 逐节点 drain + upgrade)、蓝绿集群(建新集群 + 切流 + 下线旧)、托管自动(EKS/GKE 平台自动)。自建用原地,云上用托管,强一致业务用蓝绿。

**Q2: kubeadm upgrade 的流程?**

先升级第一个 master(kubeadm upgrade apply),再升级其他 master(kubeadm upgrade node),最后升级 worker(drain + kubeadm upgrade node + uncordon)。kubelet/kubectl 用 apt 升级,重启 kubelet。

**Q3: K8s 版本偏差策略(version skew)?**

kubelet 不能比 apiserver 新;kubelet 可以比 apiserver 低最多 3 个 minor(1.30+);kube-proxy 与 kubelet 一致;kubectl ±1 minor。

**Q4: API 弃用怎么检查?**

用 pluto / kubent(kube-no-trouble)工具扫描,或 kubectl get --raw /metrics | grep deprecated。升级前必查,1.28 升 1.30 可能有 batch/v1beta1(CronJob)、policy/v1beta1(PSP)等已删除 API。

**Q5: etcd 备份怎么做的?**

ETCDCTL_API=3 etcdctl snapshot save,3 节点 etcd 任一节点备份即可(数据一致)。每 3 小时一次,上传 S3 + 跨区域复制。每月做 1 次 DR 演练(恢复到测试集群验证)。

**Q6: etcd 恢复怎么做?**

停 apiserver → 在每个 etcd 节点 etcdctl snapshot restore(用同一快照,不同 --name) → 替换数据目录 → 启动 etcd → 验证 → 启 apiserver。注意:恢复时用 --initial-cluster 重建集群。

**Q7: Velero 备份的原理?**

Velero controller 调 K8s API list 资源 → 序列化为 JSON → CSI snapshot 备份 PV → 打包 tar.gz → 上传 S3。恢复时反向:下载 → 解析 → 创建资源 → 从 snapshot 恢复 PV。

**Q8: Velero 与 etcd 备份区别?**

etcd 备份是集群级(全量 K8s 资源,无 PV),恢复需停 apiserver;Velero 是应用级(可选 ns,含 PV 快照),不停 apiserver。生产两者都做:etcd 用于集群级 DR,Velero 用于应用级 DR。

**Q9: DR 的 RTO 和 RPO 怎么定?**

RTO(Recovery Time Objective):恢复时长目标,业务能容忍多久不可用。RPO(Recovery Point Objective):数据丢失目标,业务能容忍丢失多少时间的数据。金融业务 RTO < 15min、RPO < 5min;普通业务 RTO < 4h、RPO < 1h。

**Q10: 多集群管理有几种模式?**

4 种:Hub-Spoke(Cluster API / OCM,集中管理)、联邦调度(Karmada,应用分发)、Service Mesh 多集群(Istio,服务互通)、GitOps 多集群(Argo CD ApplicationSet,配置同步)。

**Q11: Karmada 与 KubeFed 区别?**

KubeFed 已存档(2021);Karmada 重写了调度器,支持故障转移、Override Policy(差异化配置)、spreadConstraints。Karmada 是 KubeFed 的精神继承者。

**Q12: Cluster API 解决什么问题?**

集群生命周期声明式管理(创建/升级/销毁)。把"集群"变成 K8s 资源(Cluster/MachineDeployment),升级 = 改 version 字段,GitOps 友好。跨云厂商统一 API。

**Q13: 蓝绿集群怎么处理数据?**

蓝绿主要解决无状态服务;有状态服务需要数据同步(Cassandra 多副本、Kafka MirrorMaker、DB 双写)。切流前做数据对账,切流后双写一段时间避免丢数据。

**Q14: Spot 实例怎么保证业务稳定?**

3 件套:Node Termination Handler(监听中断通知 + drain)、PDB(保证 quorum)、多 AZ 分布(避免同时被回收)。Spot 比例不超过 60%,核心业务不上 Spot。

**Q15: 配置管理 Kustomize 与 Helm 怎么选?**

内部应用用 Kustomize(覆盖叠加,无模板,易理解);公开 chart 用 Helm(包管理 + 模板)。两者可组合:Helm chart + Kustomize overlay。

### 题 2:etcd 集群全挂,如何恢复?

```
场景:3 节点 etcd 全部故障(磁盘损坏),apiserver 不可用

恢复步骤:

1. 紧急响应
   a. 确认故障范围
      - kubectl get nodes → 超时
      - 直连 etcd → 连接拒绝
      - 检查 etcd 节点:磁盘满 / 数据损坏 / 进程挂
   
   b. 通告
      - 通知业务方集群不可用
      - 启动 DR 预案
      - 切流量到备用集群(若有)

2. 恢复 etcd
   a. 停 apiserver(所有 master)
      systemctl stop kube-apiserver
   
   b. 取最近备份
      - 从 S3 下载 etcd-snapshot.db
      - 验证:snapshot status
   
   c. 在每台 etcd 节点恢复
      ETCDCTL_API=3 etcdctl snapshot restore /backup/etcd.db \
        --name=etcd-01 \
        --initial-cluster=etcd-01=https://etcd-01:2380,... \
        --initial-cluster-token=new-cluster \
        --initial-advertise-peer-urls=https://etcd-01:2380 \
        --data-dir=/var/lib/etcd-new
      
      # 节点 2、3 类似(改 --name 和 peer-urls)
   
   d. 替换数据目录
      mv /var/lib/etcd /var/lib/etcd-broken
      mv /var/lib/etcd-new /var/lib/etcd
   
   e. 启动 etcd
      systemctl start etcd
   
   f. 验证
      etcdctl endpoint health
      etcdctl member list

3. 启动控制面
   systemctl start kube-apiserver
   kubectl get nodes
   kubectl get componentstatuses

4. 业务恢复
   a. 检查所有 Pod Running
   b. 检查核心服务健康
   c. 灰度恢复流量(若已切走)
   d. 24 小时观察

5. 数据丢失评估
   - RPO = 备份间隔(3 小时)
   - 丢失 0-3 小时的 K8s 资源变更
   - 业务数据(PV)未丢,只丢 K8s 元数据
   - 重新 apply 丢失的资源(从 GitOps repo)

6. 复盘
   - etcd 为什么全挂?(磁盘 / 网络 / 配置)
   - 备份是否正常?(最近一次备份时间)
   - 监控是否提前告警?
   - 改进:多 AZ 部署 + 备份频率 + 监控

关键点:
  - 备份必须异地(S3),不能与 etcd 同机
  - 备份必须定期演练(否则真到用时发现不可用)
  - etcd 多副本跨 AZ(避免同 AZ 故障全挂)
```

### 题 4:Spot 实例大规模使用如何保证业务稳定?

```
场景:集群 Spot 比例 60%(600/1000 节点),业务错误率 < 0.1%

设计:

1. Spot 策略
   - 核心业务(DB/Cache/网关):On-Demand
   - 普通业务(Web/API):Spot 60% + On-Demand 40%
   - 批处理(ETL/训练):全 Spot(可中断)

2. 多 AZ 分布
   - 每个节点池跨 3 AZ
   - Spot 中断通常按 AZ(不会同时全 AZ)
   - PDB:每 AZ 至少 1 副本

3. Node Termination Handler
   - 监听 Spot 中断通知(2 分钟)
   - drain 节点 + 通知应用
   - preStop hook:优雅停止

4. 优雅停止
   - 应用:SIGTERM 处理 + 连接 drain
   - terminationGracePeriodSeconds:120(给足时间)
   - preStop hook:sleep 10(等 endpoint 摘除)

5. 调度策略
   - podAntiAffinity:同 Deployment Pod 分散
   - topologySpreadConstraints:跨 AZ 均衡
   - 优先级:Spot Pod 优先级低,被抢占先死

6. 自动伸缩
   - Cluster Autoscaler:Spot 丢失自动补
   - 混合节点池:Spot 池 + On-Demand 池
   - 优先级:优先填 Spot,溢出到 On-Demand

7. 监控
   - Spot 中断率(每日)
   - Pod 重调度时长(<90s)
   - 业务错误率(中断期间)
   - 节点池 Spot 比例

8. 应急
   - Spot 大规模中断(>10% 同时):自动切 On-Demand
   - 紧急扩容 On-Demand 池
   - 流量降级(非核心业务限流)

成本核算:
  - Spot 节省 60-70%
  - 600 Spot + 400 On-Demand vs 1000 On-Demand
  - 月省 $50K+(以 m5.2xlarge 计)
  - 但运维复杂度 +30%
```

### 题 5:多集群 GitOps 怎么设计?

```
需求:30+ 集群,几百个应用,配置一致性 + 差异化

方案:

1. Git 仓库结构
   gitops-repo/
   ├── apps/
   │   ├── web-app/
   │   │   ├── base/           # 公共配置
   │   │   ├── overlays/
   │   │   │   ├── dev/        # 开发
   │   │   │   ├── staging/    # 预发
   │   │   │   ├── prod-beijing/
   │   │   │   ├── prod-shanghai/
   │   │   │   └── prod-singapore/
   │   │   └── Chart.yaml
   │   └── api-service/
   ├── clusters/
   │   ├── cluster-beijing.yaml
   │   ├── cluster-shanghai.yaml
   │   └── cluster-singapore.yaml
   └── projects/

2. Argo CD ApplicationSet
   - 生成器:list(显式集群列表)
   - 或 git(directory 结构自动发现)
   - 或 cluster(注册的集群自动生成)

3. 差异化策略
   a. Kustomize overlay
      base/    → 公共 K8s 资源
      overlays/prod-beijing/ → 北京特有 patch(DB endpoint / 副本数)
   
   b. Helm values
      values.yaml          → 公共
      values-prod.yaml     → 生产
      values-beijing.yaml  → 北京
   
   c. Karmada OverridePolicy
      跨集群差异化(更细粒度)

4. 权限
   - Git 仓库:GitHub Teams 按目录授权
   - Argo CD:RBAC 按项目授权
   - 集群:OIDC + RBAC,SSO 单点登录

5. 流程
   a. 开发提 PR(改 values)
   b. CI 自动测试(kubeval / kubeconform)
   c. 多人审核
   d. 合并 → Argo CD 自动 sync
   e. 灰度:先 sync 到 dev,验证 → staging → prod
   f. 回滚:Git revert

6. 漂移检测
   - Argo CD 自带 diff(Git vs 集群)
   - 告警:漂移超过 5 分钟
   - 自动 sync(selfHeal)

7. 多集群分发
   - ApplicationSet 按 cluster generator 生成
   - 或 Karmada PropagationPolicy
   - 跨集群状态汇总

8. 密钥管理
   - Sealed Secrets(加密存 Git)
   - 或 External Secrets(Vault / AWS SM)

关键收益:
  - 配置一致性(Git 唯一真源)
  - 审计(Git history)
  - 回滚(Git revert)
  - 多人协作(PR + Review)
```

### 题 6:解释 Cluster API 的工作模型

```
Cluster API 核心思想:把集群本身也变成 K8s 资源

1. CRD 定义
   - Cluster:逻辑集群
   - Machine:一台节点(VM/物理机)
   - MachineDeployment:Machine 的 Deployment(滚动升级)
   - MachineSet:Machine 的 ReplicaSet
   - MachineHealthCheck:节点健康检查 + 自愈

2. Provider 分层
   - Core Provider:Cluster API 核心(管理 Cluster/Machine)
   - Bootstrap Provider:kubeadm 配置生成
   - Infrastructure Provider:云资源创建(AWS/GCP/vSphere)

3. 工作流(创建集群)
   a. 用户 apply Cluster + MachineDeployment YAML
   b. Cluster Controller 创建 namespace / 网络等
   c. Infrastructure Controller 调云 API 创建 VM
   d. Bootstrap Controller 生成 kubeadm 配置(注入 cloud-init)
   e. VM 启动 → kubeadm init / join
   f. Machine Controller 标记 Ready

4. 升级流程
   a. 修改 MachineDeployment.spec.template.spec.version: v1.30.0
   b. MachineDeployment 滚动替换 Machine(类似 Deployment 替换 Pod)
   c. 旧 Machine:drain + 删除(VM 销毁)
   d. 新 Machine:创建 VM + kubeadm join
   e. 完成

5. 自愈
   - MachineHealthCheck 监控节点 NotReady
   - 超时(如 5 分钟)自动重建 Machine
   - 旧 VM 销毁,新 VM 创建

6. 优势
   - 集群生命周期声明式(GitOps 友好)
   - 跨云厂商统一 API
   - 升级 = 改 YAML
   - 自愈(节点故障自动换)
   - 适合大规模多集群

7. 局限
   - 学习曲线陡
   - Provider 成熟度不一(AWS 最成熟)
   - 老集群迁移难(已用 kubeadm 装的不易迁到 CAPI)

8. 与 Karmada 区别
   - Cluster API:管集群生命周期(创建/升级/销毁)
   - Karmada:管集群内应用分发
   - 两者互补:CAPI 创建集群,Karmada 分发应用
```

### 题 7:K8s 集群证书过期怎么处理?

```
K8s 证书 1 年过期,过期后集群不可用

1. 检查证书过期
   kubeadm certs check-expiration
   # 输出:CERTIFICATE                EXPIRES
   #       apiserver                 Jan 05, 2026 12:00 UTC
   #       apiserver-kubelet-client  Jan 05, 2026 12:00 UTC
   #       ...

2. 提前告警
   - Prometheus 采集证书过期时间
   - 30 天前告警 P2
   - 7 天前告警 P1

3. 续期(kubeadm 集群)
   # 在每台 master 执行
   kubeadm certs renew all
   
   # 重启控制面
   systemctl restart kube-apiserver
   systemctl restart kube-controller-manager
   systemctl restart kube-scheduler
   systemctl restart etcd
   
   # 更新 kubeconfig
   cp /etc/kubernetes/admin.conf ~/.kube/config

4. 自动续期(1.20+)
   - kubeadm 默认不自动续期
   - 但可配 cron 定期 renew
   - 或用 cert-manager 管理证书(自定义 CA)

5. 托管集群(EKS/GKE)
   - 平台自动管理,用户无感知
   - 证书过期是平台问题,平台负责

6. 应急(证书已过期)
   a. 用备份的 admin.conf(若证书未过期)
   b. 或重新生成:
      kubeadm init phase certs all
      kubeadm init phase kubeconfig all
   c. 重启控制面

7. 注意
   - etcd 证书独立(/etc/kubernetes/pki/etcd/)
   - kubelet 证书自动轮换(--rotate-certificates=true,默认开)
   - 服务账号(SA)证书 10 年,不过期但建议轮换

8. 监控
   - 证书过期时间 Prometheus 告警
   - 自动续期 cron 任务监控
   - 每月人工 check-expiration
```

## 24.12 故障复盘

### 案例 1:升级触发 API 弃用,业务批量报错

**故障时间**:2024-03-15

**故障现象**:
- K8s 1.25 升级到 1.26 后
- 多个业务的 CronJob 创建失败
- 错误: no matches for kind "CronJob" in version "batch/v1beta1"

**根因**:
- K8s 1.25 已弃用 batch/v1beta1(CronJob),1.26 删除
- 升级前未做 API 弃用扫描
- 业务方仍用 batch/v1beta1 创建 CronJob

**修复**:
1. 紧急:业务方改 batch/v1beta1 → batch/v1
2. 监控:扫描所有 ns 的 batch/v1beta1 资源
3. 长期:升级前必跑 pluto / kubent

**经验**:**升级前 API 弃用检查是硬性流程,不可省略**。

### 案例 2:etcd 备份从未成功,真到恢复时发现

**故障时间**:2023-11-08

**故障现象**:
- etcd 集群 2/3 节点磁盘故障,quorum 丢失
- 紧急从备份恢复,发现最近 3 个月的备份都是 0 字节
- 集群不可用 6 小时

**根因**:
- 备份脚本权限错误(etcdctl 无读权限)
- cron 任务一直在跑,但每次失败(脚本 set -e 未生效)
- 监控只看"备份任务跑了没",没看"备份文件有效不"

**修复**:
1. 紧急:用 3 个月前的备份恢复(数据丢失 3 个月)
2. 业务方重新 apply 丢失的 K8s 资源(从 GitOps repo)
3. 修复备份脚本 + 验证逻辑

**经验**:**备份必须定期恢复演练,否则不算真备份**。监控要看备份文件大小 + snapshot status 验证。

### 案例 3:Velero PV 恢复跨 AZ 失败

**故障时间**:2024-06-20

**故障现象**:
- 跨集群 DR 演练
- Velero backup 成功,restore 失败
- 错误:VolumeSnapshotContent creation failed

**根因**:
- 集群 A(us-east-1a)的 EBS 快照
- 集群 B(us-west-2)的 EBS 不认跨区快照
- Velero 默认不支持跨区快照恢复

**修复**:
1. 用 Velero File System Backup(替代 CSI snapshot)
2. 或用 AWS Backup 跨区复制快照
3. 或改用对象存储存数据(S3 + 工具备份)

**经验**:**Velero PV 跨区恢复有局限,需提前验证 + 备用方案**。

### 案例 4:Spot 中断潮,业务大规模抖动

**故障时间**:2024-08-12

**故障现象**:
- AWS us-east-1a Spot 大规模回收(>50% 同时)
- 业务错误率飙到 30%
- Pod 重调度雪崩(scheduler 卡)

**根因**:
- Spot 比例过高(80%)
- 单 AZ 集中(NodePool-A 全在 us-east-1a)
- 无 Node Termination Handler(Spot 中断无预警)
- PDB 配置过严(minAvailable=90%),drain 卡死

**修复**:
1. 紧急扩容 On-Demand 池
2. 临时改 Spot 比例 80% → 50%
3. 装 ATH + 配 PDB(minAvailable=70%)
4. 多 AZ 分布

**经验**:**Spot 比例不超 60%,必须跨 AZ,必须有 NTH + PDB**。

### 案例 5:多集群配置漂移,行为不一致

**故障时间**:2024-09-05

**故障现象**:
- 北京集群业务正常,上海集群业务异常
- 排查发现 Deployment 副本数不一致(北京 10,上海 5)
- ConfigMap 内容也不一致

**根因**:
- 没有 GitOps,运维人手 kubectl apply
- 上海集群运维忘了同步最新配置
- 无漂移检测

**修复**:
1. 紧急:同步配置到上海集群
2. 引入 Argo CD ApplicationSet
3. 全部配置存 Git,禁止人手 apply
4. 漂移检测告警

**经验**:**多集群必须 GitOps,人手 apply 必漂移**。

### 案例 6:kubeadm upgrade 跳过 master 直接 worker

**故障时间**:2024-04-22

**故障现象**:
- 升级 worker 节点 kubelet 到 1.30
- kubelet 启动失败,错误:version skew too large
- worker 节点全部 NotReady

**根因**:
- 运维跳过 master 升级,直接升级 worker
- master apiserver 还是 1.28
- kubelet 1.30 vs apiserver 1.28,skew 2 minor(超限)

**修复**:
1. 回滚 worker kubelet 到 1.28
2. 按 master → worker 顺序重新升级

**经验**:**kubeadm upgrade 必须严格按顺序:master 1 → master N → worker**。

### 案例 7:Karmada 故障转移未生效

**故障时间**:2024-10-18

**故障现象**:
- cluster-beijing 故障
- 预期:副本自动迁到 cluster-shanghai
- 实际:副本未迁,业务中断

**根因**:
- PropagationPolicy 未配 replicaScheduling
- 默认策略不故障转移
- Karmada 把集群标 NotReady 但不重调度

**修复**:
1. 紧急手动迁副本
2. 配 PropagationPolicy.replicaScheduling + clusterTolerations
3. 演练故障转移

**经验**:**多集群联邦必须配故障转移策略,否则只是"多集群部署"不是"多集群 HA"**。
