# 23. 故障排查与诊断

> 关键词:kubectl debug、ephemeral container、crictl、ctr、节点诊断 SOS、故障树、Pod Pending、CrashLoopBackOff、ImagePullBackOff、OOMKilled、PLEG、tcpdump、strace、bcc、bpftrace、eBPF

------

## 23.1 问题定义与边界

### 23.1.1 解决什么

K8s 集群在生产环境运行一段时间后,不可避免会出现各类故障:Pod 起不来、节点 NotReady、网络不通、存储挂载失败、CPU 飙高、DNS 解析慢、服务间歇性 5xx。这些问题跨越 **应用层 / 容器运行时层 / 内核层 / 网络层 / 存储层 / 控制面层** 多个维度,单靠 `kubectl describe` 与 `kubectl logs` 无法覆盖深层次根因。本章系统化解决:

- **故障定位方法论**:从症状到根因的分治法,避免「凭感觉重启」
- **Pod 状态机诊断**:20+ 异常状态(Scheduled/Waiting/ContainerCreating/CrashLoopBackOff/ImagePullBackOff/ErrImagePull/InvalidImageName/CreateContainerError/RunContainerError/OOMKilled/Evicted/Terminating/Succeeded/Failed/ImageInspectError/CreateContainerConfigError/PostStartHookError/PreStopHookError/DockerError)的根因与定位
- **节点诊断**:NotReady 节点的内核级排查(journalctl / dmesg / ss / ip / conntrack / systemctl)
- **容器运行时诊断**:crictl / ctr / nerdctl 三件套,绕过 K8s 直接与 CRI 交互
- **临时容器诊断**:kubectl debug / ephemeral container 在 distroless / scratch 镜像中注入调试工具
- **网络抓包**:tcpdump / iperf3 / mtr / conntrack 在 Pod、节点、Service 多点抓包定位丢包
- **系统调用追踪**:strace / ltrace 追踪进程系统调用,bcc / bpftrace 用 eBPF 在内核态追踪
- **存储诊断**:lsblk / mount / findmnt / xfs_info / ceph status 定位 PV/PVC 挂载异常
- **控制面诊断**:apiserver audit log、etcd mvcc、scheduler trace、controller-manager event

### 23.1.2 不解决什么

- **指标采集与告警**:由 Prometheus 负责(见 [21-监控与指标](./21-监控与指标.md))
- **日志聚合与查询**:由 Loki / ELK 负责(见 [22-日志与追踪](./22-日志与追踪.md))
- **分布式追踪**:由 Jaeger / OpenTelemetry 负责(见 [22-日志与追踪](./22-日志与追踪.md))
- **生产事故根因深度复盘**:跨章节事故集归集到 [29-故障复盘集](./29-故障复盘集.md),本章只给方法学与单点故障的排查过程
- **集群升级与备份恢复运维**:由 [24-集群运维](./24-集群运维.md) 负责
- **容量规划与成本优化**:由 [30-成本与容量规划](./30-成本与容量规划.md) 负责

### 23.1.3 核心矛盾

```
故障域广度 vs 工具链碎片化:
  故障可能位于 Application / Container Runtime / Kernel / CNI / CSI / CRI / Control Plane 6 层
  每层有独立工具链,排查需要跨层跳转

时效性 vs 完整性:
  生产事故 MTTR 要求 < 30 分钟,但完整诊断可能要求数小时
  临时容器、热重启、log rotation 可能冲掉关键现场

侵入性 vs 安全性:
  tcpdump / strace / eBPF 需要特权,生产环境受 PSA / PodSecurityPolicy 限制
  ephemeral container 需要 RBAC 与节点 SSH 权限

黑盒 vs 白盒:
  托管 K8s (EKS/GKE/AKS) 控制面不可见,只能通过 apiserver log 与 cloud audit
  自建 K8s 可登 master,但需保护 etcd / signer key
```

## 23.2 直觉解释

把故障排查想象成 **急诊医学的诊断流程**:

| 急诊流程 | K8s 故障排查 |
|---------|-------------|
| 病人主诉(症状) | 告警 / 用户反馈(Pod Failed / 5xx / 慢) |
| 生命体征监测(心率/血压/血氧) | 黄金信号(延迟/流量/错误/饱和度) |
| 分诊(轻/中/重) | 故障域定位(Pod / Node / Cluster / Region) |
| 问诊(病史 / 诱因) | 时间线对齐(发布 / 配置变更 / 流量突增) |
| 听诊 / 叩诊(快速体检) | kubectl get/describe/logs/events |
| 验血 / 影像(深入检查) | crictl / tcpdump / strace / eBPF |
| 鉴别诊断(列可能病因) | 故障树(20+ Pod 异常状态根因表) |
| 确诊(找到根因) | dmesg / journalctl / etcd log 给出明确证据 |
| 治疗(止血 + 对因) | 重启 Pod / 扩容 / 回滚 / 修复配置 |
| 随访(防复发) | 加监控 / 加告警 / 加 runbook |

关键直觉:

1. **分层定位**:从上到下(Application → Pod → Container → Runtime → Kernel → Hardware),每层有专属工具
2. **分治法**:把大问题切成小问题,「Pod 起不来」切成「调度失败 / 镜像拉取失败 / 启动失败 / 探针失败」
3. **时间线对齐**:用 `kubectl get events --sort-by='.lastTimestamp'` 还原事件顺序
4. **假设-验证**:每个假设必须有命令输出作为证据,避免「我觉得是 XX」
5. **保留现场**:Pod 删除前先 `kubectl describe` + `kubectl logs --previous` + `crictl inspect` 抓快照
6. **二分法**:大规模集群故障,先按节点池/命名空间/Service 切分,定位爆炸半径

排查方法论经典三问:

```
Q1: 这个故障是「预期内」还是「预期外」?
    - 预期内:发布、扩容、配置变更引发的回归 → 回滚优先
    - 预期外:底层故障、依赖异常、流量突增 → 止血 + 定位

Q2: 这个故障的影响半径有多大?
    - 单 Pod:重启 / 重建即可
    - 单 Node:Drain + 修复节点
    - 多 Node / 全集群:控制面或基础设施故障,优先恢复控制面
    - 多集群:依赖服务(DNS / Registry / Storage / Cloud Provider)故障

Q3: 这个故障是「持续性」还是「间歇性」?
    - 持续性:好定位,直接看现场
    - 间歇性:难定位,需要长抓包 / eBPF trace / Chaos Engineering 复现
```

## 23.3 核心概念与架构

### 23.3.1 K8s 故障域分层

K8s 故障域自上而下 7 层,每层有独立故障模式与诊断工具:

```
┌─────────────────────────────────────────────────────────────────────┐
│ L7: Application Layer                                              │
│   故障: 业务逻辑 bug、依赖超时、缓存击穿、死锁                       │
│   工具: kubectl logs、app metrics、trace、pprof                    │
├─────────────────────────────────────────────────────────────────────┤
│ L6: Pod / Workload Layer                                           │
│   故障: Probe 失败、资源不足、ConfigMap/Secret 缺失、Init 失败      │
│   工具: kubectl describe pod、events、kubectl debug                │
├─────────────────────────────────────────────────────────────────────┤
│ L5: Container Runtime Layer (CRI)                                  │
│   故障: 镜像拉取失败、容器启动失败、运行时 hang、OOM                │
│   工具: crictl、ctr、nerdctl、journalctl -u containerd             │
├─────────────────────────────────────────────────────────────────────┤
│ L4: Kubelet / Node Layer                                           │
│   故障: PLEG 卡死、kubelet NotReady、节点资源耗尽、磁盘压力         │
│   工具: journalctl -u kubelet、dmesg、systemctl、node stats        │
├─────────────────────────────────────────────────────────────────────┤
│ L3: Network Layer (CNI / kube-proxy)                               │
│   故障: Pod 网络、Service 转发、DNS、conntrack 满、MTU 不匹配       │
│   工具: tcpdump、iperf3、mtr、conntrack、ipvsadm -L、ss、dig       │
├─────────────────────────────────────────────────────────────────────┤
│ L2: Storage Layer (CSI / Volume)                                   │
│   故障: PV 挂载失败、IO 卡顿、Volume Unmount 残留、快照失败         │
│   工具: lsblk、mount、findmnt、xfs_info、ceph status、iostat       │
├─────────────────────────────────────────────────────────────────────┤
│ L1: Control Plane Layer                                            │
│   故障: apiserver 超时、etcd 慢、scheduler 卡、controller-manager   │
│   工具: apiserver audit log、etcdctl、scheduler trace、metrics     │
├─────────────────────────────────────────────────────────────────────┤
│ L0: Kernel / Hardware Layer                                        │
│   故障: CPU 软死锁、内存泄漏、磁盘坏道、网卡掉线、内核 panic        │
│   工具: dmesg、sysctl、/proc、bcc、bpftrace、perf                  │
└─────────────────────────────────────────────────────────────────────┘
```

### 23.3.2 Pod 状态机

Pod 状态机是故障排查的核心地图。一个 Pod 从创建到终止,经历多个阶段(phase)与状态(condition):

```
                            ┌──────────────┐
                            │   Pending    │ ← 调度中 / 镜像拉取中 / 卷挂载中
                            └──────┬───────┘
                                   │
                  ┌────────────────┼────────────────┐
                  │                │                │
                  ▼                ▼                ▼
            (调度失败)       (镜像拉取失败)    (卷挂载失败)
                  │                │                │
                  ▼                ▼                ▼
            ┌─────────┐     ┌──────────────┐  ┌──────────────┐
            │  Failed │     │ImagePullBackOff│ │  Evicted    │
            └─────────┘     └──────────────┘  └──────────────┘
                                   │
                                   ▼ (镜像就绪)
                            ┌──────────────┐
                            │   Running    │ ← 容器启动 + 探针通过
                            └──────┬───────┘
                                   │
                  ┌────────────────┼────────────────┐
                  │                │                │
                  ▼                ▼                ▼
            (主进程退出)      (探针失败)        (OOM)
                  │                │                │
                  ▼                ▼                ▼
            ┌─────────┐     ┌──────────────┐  ┌──────────────┐
            │Succeeded│     │CrashLoopBackOff│ │  OOMKilled  │
            │ (exit 0)│     │  (重启指数退避) │ │ └→ Restart  │
            └─────────┘     └──────────────┘  └──────────────┘
                                   │
                                   ▼ (达到 backoff 上限)
                            ┌──────────────┐
                            │   Failed     │ ← 退出码非 0 + restartPolicy
                            └──────────────┘
```

Pod phase 五个值:

| Phase | 含义 | 常见根因 |
|-------|------|---------|
| Pending | 已写入 etcd,等待调度/拉镜像/挂卷 | 资源不足、镜像大、CSI 慢 |
| Running | 至少一个容器运行中 | (正常状态) |
| Succeeded | 所有容器退出码 0 | Job/CronJob 完成 |
| Failed | 所有容器退出,至少一个非 0 | 应用崩溃、OOM |
| Unknown | apiserver 无法获取 Pod 状态 | kubelet 失联、节点 NotReady |

Pod condition 五种:

```
PodScheduled     : 是否已调度到节点
Initialized      : 所有 init container 是否完成
Ready            : 是否就绪接流量(就绪探针通过)
ContainersReady  : 所有业务容器是否就绪
DisruptionTarget : 是否正在被驱逐(API 1.22+)
```

### 23.3.3 Container 状态机

Container 状态机比 Pod 更细粒度:

```
┌────────────┐
│  Waiting   │ ← 镜像拉取 / CreateContainer 中
└─────┬──────┘
      │
      ▼
┌────────────┐
│  Running   │ ← 主进程运行中
└─────┬──────┘
      │
      ├─→ (exit 0) ─→ Terminated (Completed)
      ├─→ (exit !=0)─→ Terminated (Error) ─→ Restart (restartPolicy)
      ├─→ (OOM)     ─→ Terminated (OOMKilled) ─→ Restart
      ├─→ (Signal)  ─→ Terminated (Signal) ─→ Restart (取决于信号)
      └─→ (probe fail) ─→ Terminated (killed by kubelet) ─→ Restart
```

Container 状态三态:

| State | 含义 |
|-------|------|
| Waiting | 已创建但未运行,Reason 给出原因(ImagePullBackOff / ErrImagePull / CreateContainerError / InvalidImageName) |
| Running | 主进程运行中,StartedAt / PID 可查 |
| Terminated | 已终止,Reason / ExitCode / Signal 可查 |

Container 重启策略与 backoff:

```
restartPolicy: Always (默认) / OnFailure / Never

backoff 机制:
  第 1 次重启: 立即
  第 2 次:     10s
  第 3 次:     20s
  第 4 次:     40s
  第 5 次:     80s
  第 6 次:     160s
  第 7 次:     300s (上限 5 分钟)

backoff 在容器成功运行 10 分钟后重置。
```

### 23.3.4 故障树(20+ Pod 异常状态)

```
Pod 异常状态根因树:

┌─ Pending
│  ├─ Unschedulable (调度失败)
│  │  ├─ 0/5 nodes available: Insufficient cpu
│  │  ├─ 0/5 nodes available: Insufficient memory
│  │  ├─ 0/5 nodes available: node(s) had taint {dedicated: }, pod didn't tolerate
│  │  ├─ 0/5 nodes available: node(s) didn't match Pod's node affinity
│  │  ├─ 0/5 nodes available: node(s) had volume node affinity conflict
│  │  └─ 0/5 nodes available: PodToleratesNodeTaints 计算错误
│  │
│  ├─ ContainerCreating (已调度,容器创建中)
│  │  ├─ 镜像拉取慢 (ImagePullSlow)
│  │  ├─ CSI 卷挂载慢 (MountVolume.SetUp 失败)
│  │  ├─ CNI 网络分配失败
│  │  ├─ Secret/ConfigMap 不存在
│  │  └─ ServiceAccount 不存在
│  │
│  └─ FailedScheduling (调度器拒绝)
│     └─ 优先级与抢占触发,等待高优 Pod 抢占
│
├─ ImagePullBackOff / ErrImagePull
│  ├─ registry 不可达 (DNS / 网络 / 证书)
│  ├─ 镜像名拼写错误 (InvalidImageName)
│  ├─ 镜像不存在 (manifest unknown)
│  ├─ 认证失败 (401/403, imagePullSecret 缺失或过期)
│  ├─ rate limit (Docker Hub 限流)
│  └─ 镜像超大 (Layer 下载超时)
│
├─ CrashLoopBackOff
│  ├─ 应用启动崩溃 (exit 1, 看 logs)
│  ├─ 配置错误 (env 缺失、文件不存在)
│  ├─ 依赖服务不可达 (DB / Redis / 下游)
│  ├─ 命令错误 (command / args 拼错)
│  ├─ 权限不足 (文件不可执行)
│  ├─ livenessProbe 太激进 (启动还没完就被杀)
│  └─ postStart hook 失败
│
├─ CreateContainerError
│  ├─ 镜像 OCI 规范错误 (manifest schema 不支持)
│  ├─ entrypoint 不存在
│  ├─ volume mount 路径冲突
│  ├─ seccomp / AppArmor profile 不存在
│  └─ user UID/GID 不合法
│
├─ RunContainerError
│  ├─ runtime handler 错误 (containerd / CRI-O 内部错)
│  ├─ image 长度超限
│  ├─ Namespace 创建失败 (PID namespace 耗尽)
│  └─ cgroup 创建失败 (磁盘满)
│
├─ OOMKilled
│  ├─ 内存 limits 太低 (exit 137)
│  ├─ 内存泄漏 (long-running 进程)
│  ├─ 突发流量导致 JVM heap 膨胀
│  └─ cgroup memory.max 触发 (containerd 1.7+)
│
├─ Evicted
│  ├─ DiskPressure (节点磁盘 < 10%)
│  ├─ MemoryPressure (节点可用内存低)
│  ├─ PIDPressure (节点 PID 耗尽)
│  └─ NodePressure (自定义条件)
│
├─ Terminating (卡住)
│  ├─ finalizer 未移除
│  ├─ preStop hook 卡住 (默认 30s,可调)
│  ├─ 容器不响应 SIGTERM
│  ├─ endpoint 从 kube-proxy 移除慢
│  └─ volume unmount 慢 (CSI 卡住)
│
├─ Completed / Succeeded (Job)
│  └─ 正常完成 (exit 0)
│
└─ Unknown
   ├─ kubelet NotReady
   ├─ 节点失联 (网络分区)
   └─ 节点重启中
```

### 23.3.5 Kubelet PLEG 与 Pod 状态采集

PLEG (Pod Lifecycle Event Generator) 是 kubelet 的核心子模块,负责把容器运行时的状态变化推送给 kubelet 主循环:

```
kubelet syncLoop 主循环
    ↑
    │ (PLEG 事件)
    ├──→ PodUpdates channel
    │
PLEG:
    1. relist: 每秒调用 CRI Status() 获取所有 Pod 状态
    2. 对比上一次状态,生成 PodLifecycleEvent
    3. 推送到 PodUpdates channel

    事件类型:
      - ContainerStarted
      - ContainerDied
      - ContainerRemoved
      - NetworkSetupCompleted
      - SandboxChanged

PLEG 卡死症状:
    - relist 超过 3 秒 (PLEG is healthy if relist < 3s)
    - kubelet log: "PLEG is not healthy" warning
    - 节点 status.conditions: Ready=False, reason=PLEG is not healthy
    - Pod 状态长时间不更新

根因:
    - containerd / dockerd 卡死
    - 内核 cgroup 卡死
    - 大量容器(> 200)同时 relist
    - 慢磁盘导致容器状态读写慢

诊断:
    journalctl -u kubelet | grep PLEG
    grep -c "PLEG is not healthy" /var/log/kubelet.log
```

### 23.3.6 CRI 调用链

容器运行时接口(CRI)是 kubelet 与容器运行时之间的 gRPC 接口,理解 CRI 调用链有助于诊断容器级故障:

```
kubectl apply → apiserver → etcd
                              ↓
                          scheduler 调度
                              ↓
                          kubelet syncPod
                              ↓
                    ┌─────────────────────┐
                    │ CRI gRPC calls      │
                    ├─────────────────────┤
                    │ 1. RunPodSandbox    │ (创建网络命名空间、cgroup)
                    │ 2. CreateContainer  │ (创建容器)
                    │ 3. StartContainer   │ (启动容器)
                    │ 4. Status           │ (查询状态,PLEG 调用)
                    │ 5. StopContainer    │ (停止)
                    │ 6. RemoveContainer  │ (删除)
                    │ 7. RemovePodSandbox │ (清理)
                    └─────────────────────┘
                              ↓
                    containerd / CRI-O / dockerd
                              ↓
                          runc / crun (OCI runtime)
                              ↓
                          Linux namespaces + cgroups
                              ↓
                          应用进程
```

CRI 故障点:

```
1. RunPodSandbox 失败:
   - CNI 插件失败 (IPAM 分配不到 IP)
   - netns 创建失败 (内核 PID namespace 满)
   - cgroup 创建失败 (磁盘满)

2. CreateContainer 失败:
   - 镜像在本地但 manifest 损坏
   - volume mount 路径冲突
   - SELinux / AppArmor profile 加载失败

3. StartContainer 失败:
   - entrypoint 不存在
   - exec format error (架构不匹配,amd64 vs arm64)
   - OCI runtime 错误

4. Status 失败:
   - 容器进程不存在 (PID 复用)
   - cgroup 已被清理
```

## 23.4 操作流程与命令

### 23.4.1 kubectl 排查基础命令矩阵

```
┌──────────────────────────────────────────────────────────────────┐
│ 命令                       │ 用途                                │
├───────────────────────────┼─────────────────────────────────────┤
│ kubectl get pods          │ 列出 Pod,看 STATUS / RESTARTS      │
│ kubectl get pods -o wide  │ 看 NODE / IP                        │
│ kubectl get pods -o yaml  │ 看 full spec / status               │
│ kubectl describe pod      │ 看 Events + Conditions + Container  │
│ kubectl logs              │ 看当前 stdout/stderr                │
│ kubectl logs --previous   │ 看上一容器实例日志(崩溃前)        │
│ kubectl logs --tail=100   │ 看最后 100 行                       │
│ kubectl logs -f           │ 跟踪日志                            │
```

### 23.4.2 Pod 故障排查标准流程

```
步骤 1: 看 Pod 状态
   kubectl get pod <pod-name> -o wide
   → 关注 STATUS / RESTARTS / NODE

步骤 2: describe 看 Events
   kubectl describe pod <pod-name>
   → 关注:
     - Status / Phase
     - Conditions (PodScheduled / Ready / Initialized)
     - Containers.State (Waiting/Running/Terminated + Reason)
     - Events (按时间顺序)

步骤 3: 看当前日志
   kubectl logs <pod-name>
   kubectl logs <pod-name> -c <container-name>  # 多容器

步骤 4: 看上一容器崩溃前日志(关键!)
   kubectl logs <pod-name> --previous
   kubectl logs <pod-name> --previous -c <container-name>

步骤 5: 看事件流
   kubectl get events --field-selector involvedObject.name=<pod-name> \
     --sort-by='.lastTimestamp'

步骤 6: 看 Pod YAML
   kubectl get pod <pod-name> -o yaml
   → 关注:
     - spec.containers[].resources
     - spec.containers[].livenessProbe / readinessProbe
     - spec.containers[].volumeMounts
     - status.containerStatuses[].state
     - status.containerStatuses[].lastState (上次崩溃信息)

步骤 7: 进入容器(若 Running)
   kubectl exec -it <pod-name> -- sh

步骤 8: 看节点状态
   kubectl describe node <node-name>
   → 关注:
     - Conditions (MemoryPressure / DiskPressure / PIDPressure)
     - Allocated resources
     - Events
```

### 23.4.3 kubectl debug 四种模式

K8s 1.18+ 引入 ephemeral container(临时容器),1.25+ GA。kubectl debug 提供四种模式:

#### 模式 1: 给 Pod 注入 ephemeral container(无 distroless 调试)

```bash
kubectl debug -it <pod-name> --image=busybox:1.36 --target=<container-name>
```

```
原理:
  - 在已有 Pod 中注入一个临时容器
  - 共享 Pod 的 network / IPC / PID namespace
  - 可访问主容器的进程与文件(/proc 通过 target 共享)
  - 适合 distroless / scratch 镜像(主容器没 shell)

限制:
  - ephemeral container 不会重启
  - 不能加 volume / port / resources
  - 需 K8s 1.25+ (GA)
```

#### 模式 2: 复制 Pod 加调试容器

```bash
kubectl debug -it <pod-name> --image=busybox:1.36 \
  --copy-to=<pod-name>-debug --container=debugger \
  --share-processes=true
```

```
原理:
  - 复制 Pod spec,新建一个 Pod
  - 在新 Pod 中加入调试容器
  - share-processes=true 启用 PID namespace 共享
  - 原 Pod 不受影响

适合:
  - 不能修改原 Pod
  - 需要修改原容器 command (例如覆盖为 sleep infinity)
```

#### 模式 3: 节点调试(Node-shell)

```bash
kubectl debug node/<node-name> -it --image=ubuntu:22.04
```

```
原理:
  - 在节点上启动一个 privileged Pod
  - 挂载节点文件系统到 /host
  - 等价于 SSH 进节点,但通过 K8s API
  - 适合节点级诊断(dmesg / journalctl / iptables)

进入后:
  chroot /host           # 切到节点根
  journalctl -u kubelet  # 看 kubelet 日志
  crictl ps              # 看节点上容器
  iptables -L -n         # 看节点 iptables
```

#### 模式 4: Profile-only(调试 profile)

```bash
kubectl debug -it <pod-name> --profile=sysadmin
```

```
profile 预设权限:
  - legacy: 旧版,等同 unrestricted
  - general: 默认,大多数调试场景
  - baseline: 类似 PSA baseline
  - restricted: 类似 PSA restricted
  - sysadmin: 高特权(dmesg / kernel module)
```

## 23.5 底层原理

### 23.5.1 Pod 创建全链路时序

理解 Pod 创建的完整时序有助于定位「卡在哪一步」:

```
T0   kubectl apply -f pod.yaml
     ↓
T1   apiserver 收到请求 (1-5ms)
     - Authn: 验证 client cert / token
     - Authz: RBAC 检查
     - Admission: Mutating → Validating Webhook
     - 写入 etcd
     ↓
T2   etcd 持久化 (5-20ms)
     - Raft 提交
     - MVCC 写入
     ↓
T3   scheduler Watch 到新 Pod (10-50ms)
     - Filter: 过滤不满足条件的节点
     - Score: 对候选节点打分
     - Reserve: 预占资源
     - Bind: 写回 Pod.spec.nodeName
     ↓
T4   kubelet Watch 到调度结果 (10-100ms)
     - syncPod 主循环触发
     - 生成 PodWorkers goroutine
     ↓
T5   kubelet 调用 CRI: RunPodSandbox (50-200ms)
     - 创建 netns
     - 调用 CNI 分配 IP
     - 创建 cgroup
     ↓
T6   kubelet 挂载卷: MountVolume (100-2000ms,取决于 CSI)
     - 调用 CSI Driver NodeStageVolume
     - 调用 CSI Driver NodePublishVolume
     ↓
T7   kubelet 拉取镜像: PullImage (500ms-5min,取决于镜像大小)
     - CRI 调用 containerd
     - containerd 调用 registry
     - 解压 layer 到 snapshotter
     ↓
T8   kubelet 调用 CRI: CreateContainer (50-200ms)
     - 生成 OCI spec
     - 调用 containerd CreateContainer
     - containerd 调用 runc create
     ↓
T9   kubelet 调用 CRI: StartContainer (50-500ms)
     - runc start 启动容器进程
     - 容器进程 exec 应用 entrypoint
     ↓
T10  应用启动 (1s-10min,取决于应用)
     - Init container 执行
     - 主容器 entrypoint
     - readinessProbe 通过
     ↓
T11  kube-proxy 更新 Service endpoint (1-5s)
     - Watch 到 Pod Ready
     - 更新 iptables / IPVS 规则
     ↓
T12  Pod 可接流量
```

每一步都可能卡住,排查时按时间戳定位:

```
卡在 T3 之前: 调度器问题,看 scheduler log
卡在 T5:     CNI 问题,看 CNI plugin log + journalctl
卡在 T6:     CSI 问题,看 CSI driver log
卡在 T7:     镜像拉取问题,看 crictl + containerd log
卡在 T8-T9:  容器运行时问题,看 crictl inspect + journalctl -u containerd
卡在 T10:    应用问题,看 kubectl logs
卡在 T11:    kube-proxy 问题,看 kube-proxy log + iptables -L
```

### 23.5.2 kubelet syncPod 状态机

kubelet 主循环 syncPod 是 Pod 生命周期管理的核心:

```go
// kubelet syncPod 伪代码(基于 kubernetes/pkg/kubelet/kubelet.go)
func (kl *Kubelet) syncPod(o syncPodOptions) error {
    pod := o.pod
    mirrorPod := o.mirrorPod
    podStatus := o.podStatus

    // 1. 计算 Pod 实际状态(从 PLEG 缓存)
    apiPodStatus := kl.generateAPIPodStatus(pod, podStatus)

    // 2. 判断 Pod 是否需要删除(RunOnce 模式 + 已完成)
    if kl.canBeDeleted(pod, podStatus) {
        kl.killPod(pod, ...)
        return nil
    }

    // 3. 检查 cgroup 配额
    if !kl.podAdmitHandlers.Admit(pod, ...) {
        return fmt.Errorf("pod rejected")
    }

    // 4. 创建 / 更新 Pod 的 cgroup
    kl.podContainerManager.EnsureExists(pod)

    // 5. 创建 Pod 的镜像目录 /var/lib/kubelet/pods/<uid>/
    os.MkdirAll(podDir, 0750)

    // 6. 挂载卷(kubelet volume manager)
    kl.volumeManager.WaitForAttachAndMount(pod)

    // 7. 拉取镜像(secret 从 API 获取)
    kl.imageManager.PullImage(...)

    // 8. 调用 CRI 创建 PodSandbox
    kl.runtimeService.RunPodSandbox(...)

    // 9. 启动 init container 与主容器
    kl.containerRuntime.SyncPod(pod, podStatus, ...)

    return nil
}
```

关键子模块:

```
PLEG                : 监听容器状态变化
PodAdmitHandlers    : 准入检查(资源、PSA、节点选择)
VolumeManager       : 卷的 Attach / Mount
ImageManager        : 镜像拉取与 GC
ContainerRuntime    : CRI 调用封装
PodWorkers          : 每个 Pod 一个 goroutine
StatusManager       : 把 Pod 状态上报 apiserver
EvictionManager     : 节点压力时驱逐 Pod
```

### 23.5.3 PLEG relist 实现

PLEG 通过定期调用 CRI Status 获取所有 Pod 状态,对比上一次状态生成事件:

```go
// kubernetes/pkg/kubelet/pleg/generic.go
func (g *GenericPLEG) relist() {
    // 1. 获取所有 PodSandbox 与容器状态
    pods, err := g.runtime.GetPods(true)  // 调用 CRI Status
    if err != nil {
        return
    }

    // 2. 对比上一次状态,生成事件
    g.podRecords.setCurrent(pods)
    for podID := range allPods {
        old := g.podRecords.getOld(podID)
        cur := g.podRecords.getCurrent(podID)
        events := computeEvents(old, cur)
        for _, e := range events {
            g.eventChannel <- e  // 推送到 kubelet 主循环
        }
    }

    // 3. 更新 cache
    g.cache.Set(pods)
}
```

PLEG 卡死的核心原因:

```
1. GetPods (CRI Status) 慢
   - containerd 卡死
   - runc list 慢 (大量容器)
   - cgroup 文件系统慢 (磁盘满)

2. eventChannel 满
   - kubelet syncPod 慢
   - 阻塞 PLEG relist
   - 形成恶性循环

3. relist 间隔过长
   - 默认 1s
   - 长时间 relist > 3s 触发 PLEG not healthy
   - 影响 Pod 状态更新
```

### 23.5.4 容器退出码与信号

容器退出码是诊断的关键信息:

```
┌─────────────────────────────────────────────────────────────────────┐
│ 退出码 │ 含义                       │ 常见根因                     │
├────────┼────────────────────────────┼───────────────────────────────┤
│ 0      │ 正常退出                   │ Job 完成 / 主进程主动退出    │
│ 1      │ 通用错误                   │ 应用 bug / 配置错误          │
│ 2      │ shell 误用                 │ shell 脚本语法错             │
│ 126    │ 命令不可执行               │ 文件无执行权限               │
│ 127    │ 命令未找到                 │ entrypoint 不存在            │
│ 128    │ 无效参数                   │ exit 参数 > 255              │
│ 128+N  │ 被信号 N 杀死              │                              │
│ 130    │ SIGINT (Ctrl+C)            │                              │
│ 137    │ SIGKILL (128+9)            │ OOMKilled / 强制杀           │
│ 139    │ SIGSEGV (128+11)           │ 段错误                       │
│ 143    │ SIGTERM (128+15)           │ 优雅停止                     │
│ 255    │ 超出范围                   │ exit -1                      │
└─────────────────────────────────────────────────────────────────────┘

退出码 137 = OOMKilled 的判定:
  - container status.lastState.terminated.reason == "OOMKilled"
  - 退出码 137 (SIGKILL)
  - dmesg | grep "Out of memory"
  - cgroup memory.oom_control

区分 SIGKILL 来源:
  - OOMKiller: cgroup 触发,日志在 dmesg
  - kubelet livenessProbe: SIGTERM 后 SIGKILL
  - manual kill: kubectl exec kill
  - runtime kill: crictl stop
```

### 23.5.5 CNI 调用链与故障点

CNI 插件在 Pod 创建时被调用,负责网络配置:

```
kubelet RunPodSandbox
    ↓
CRI: RunPodSandbox
    ↓
containerd: 调用 CNI plugin
    ↓
/opt/cni/bin/<plugin>  (Calico / Cilium / Flannel)
    ↓
    ┌──────────────────────────────────┐
    │ 1. ADD 命令                       │
    │   - 分配 IP (IPAM)                │
    │   - 配置 veth pair                │
    │   - 配置路由                      │
    │   - 配置 iptables / eBPF          │
    │ 2. CHECK 命令(可选)              │
    │ 3. DEL 命令(Pod 删除时)         │
    │   - 释放 IP                       │
    │   - 删除 veth                     │
    │   - 清理规则                      │
    └──────────────────────────────────┘
```

CNI 故障点:

```
1. IPAM 分配失败:
   - IP 池耗尽 (Calico IPPool 满)
   - etcd 不可达 (Calico 后端)
   - 子网重叠

2. veth 创建失败:
   - 内核接口数达到上限
   - 网卡命名冲突

3. 路由配置失败:
   - BGP 邻居未建立
   - 跨子网路由缺失

4. iptables / eBPF 规则失败:
   - iptables 链缺失
   - eBPF 程序加载失败

诊断:
  - CNI 日志: /var/log/calico/ (Calico)
  - Cilium: cilium status, cilium monitor
  - 节点上的 /etc/cni/net.d/*.conf
```

### 23.5.6 CSI 调用链与故障点

CSI Driver 在 Pod 创建时负责卷的 Attach 与 Mount:

```
kubelet VolumeManager
    ↓
    ┌────────────────────────────────────┐
    │ 1. WaitForAttach (Controller)      │
    │    - CSI ControllerPublishVolume   │
    │    - 把卷 attach 到节点            │
    │ 2. MountDevice (Node)              │
    │    - CSI NodeStageVolume           │
    │    - 格式化 + 挂载到 staging 路径  │
    │ 3. SetUpAt (Node)                  │
    │    - CSI NodePublishVolume         │
    │    - bind mount 到 Pod 路径        │
    └────────────────────────────────────┘
```

CSI 故障点:

```
1. ControllerPublish 失败:
   - 云厂商 API 限流 (EBS / PD)
   - 卷配额耗尽
   - 卷已被其他节点 attach

2. NodeStage 失败:
   - 节点不识别块设备
   - 文件系统格式化失败
   - 已有文件系统签名冲突

3. NodePublish 失败:
   - 挂载路径冲突
   - 权限不足
   - readonly mount 选项错误

诊断:
  - CSI driver pod 日志: kube-system csi-xxx
  - 节点上的 mount / findmnt
  - lsblk 看块设备
  - journalctl -u kubelet | grep Volume
```

### 23.5.7 容器运行时 OOM 与 cgroup

容器内存限制通过 cgroup memory 子系统实现:

```
cgroup v2 (K8s 1.25+ 默认):
  /sys/fs/cgroup/kubepods.slice/<pod-id>/<container-id>/
    - memory.max          ← 容器内存上限(K8s resources.limits.memory)
    - memory.current      ← 当前内存使用
    - memory.peak         ← 历史峰值
    - memory.events       ← OOM 事件计数
    - memory.swap.max     ← swap 限制
    - cpu.max             ← CPU 限制
    - cpu.weight          ← CPU 权重

OOM 触发流程:
  1. 容器内存使用达到 memory.max
  2. 内核触发 cgroup OOM killer
  3. OOM killer 选择容器内内存最大的进程杀掉
  4. 若整个 cgroup 仍超限,杀掉所有进程
  5. cgroup memory.events 中 oom_kill 计数 +1
  6. kubelet PLEG 检测到容器死亡
  7. 上报 Pod status: OOMKilled, exit 137

诊断:
  cat /sys/fs/cgroup/.../memory.events
  → oom_kill 1
  → oom 5

  dmesg | grep -i "out of memory"
  → Memory cgroup out of memory: Killed process ... (mysqld)

节点级 OOM vs 容器级 OOM:
  节点 OOM: 整个节点内存耗尽,内核 panic 或杀进程
            监控: node_memory_MemAvailable_bytes
  容器 OOM: cgroup 触发,只杀容器
            监控: container_oom_events
```

## 23.7 常见陷阱与调优

### 23.7.1 CrashLoopBackOff 完整排查指南

CrashLoopBackOff 是最常见的 Pod 异常,本质是容器反复崩溃重启,达到 backoff 上限:

```
诊断流程:
  1. kubectl logs <pod> --previous              ← 关键!崩溃前日志
  2. kubectl describe pod <pod> | grep -A 5 "Last State"
  3. kubectl get pod <pod> -o jsonpath='{.status.containerStatuses[0].lastState}'
  4. 看 Exit Code / Reason / Message
```

常见根因与修复:

| 退出码 | Reason | 根因 | 修复 |
|--------|--------|------|------|
| 1 | Error | 应用异常 | 看 logs 修代码 |
| 127 | ContainerCannotRun | command not found | 检查 command/args 拼写 |
| 137 | OOMKilled | 内存超限 | 调高 limits.memory 或修内存泄漏 |
| 139 | SIGSEGV | 段错误 | 检查指针 / 库版本 |
| 143 | SIGTERM | 被外部杀 | 检查 preStop / probe |
| 255 | Unknown | exit -1 | 看应用代码 |

排查示例:

```bash
# 案例:应用启动崩溃
$ kubectl logs api-server --previous
Error: database connection refused: dial tcp 10.0.0.5:3306: connect: connection refused
exit status 1

# 根因:DB 不可达 → 修 DB

# 案例:配置缺失
$ kubectl logs web --previous
panic: env var "REDIS_URL" not set
goroutine 1 [running]:
main.main()
    /app/main.go:23 +0x2a0

# 根因:env 缺失 → 检查 ConfigMap/Secret

# 案例:命令错误
$ kubectl describe pod web
Last State: Terminated
  Reason: ContainerCannotRun
  Message: exec: "/app/star.sh": stat /app/star.sh: no such file or directory
  Exit Code: 127

# 根因:start.sh 拼成 star.sh → 修 command

# 案例:postStart 失败
$ kubectl describe pod web
Events:
  Warning  FailedPostStartHook  ...  Exec lifecycle hook ([/bin/sh -c sleep 10]) for Container "web" in Pod "web" failed

# 根因:postStart 超时或非 0 退出 → 修 hook
```

### 23.7.2 ImagePullBackOff 完整排查

```
诊断流程:
  1. kubectl describe pod <pod> | grep -A 5 "Reason"
     → Failed (Error: ErrImagePull / ImagePullBackOff)
     → 详细信息在 Message 字段
  2. 在节点上手动拉取:
     ssh <node>
     crictl pull <image>
  3. 测试 registry 连通:
     curl -v https://registry.example.com/v2/
```

常见根因:

| Message | 根因 | 修复 |
|---------|------|------|
| manifest unknown | 镜像不存在 | 检查 tag 是否拼写正确 |
| unauthorized / 401 | 认证失败 | 检查 imagePullSecret |
| forbidden / 403 | 权限不足 | 检查 ServiceAccount + RBAC |
| toomanyrequests | rate limit | 配置镜像缓存 / 换 registry |
| dial tcp: i/o timeout | registry 不可达 | 检查 DNS / 网络 / proxy |
| x509: certificate signed by unknown authority | 证书不受信 | 节点配置 ca-cert |
| InvalidImageName | 镜像名非法 | 检查拼写,大写字母、特殊字符 |

排查示例:

```bash
# 案例:Docker Hub 限流
$ kubectl describe pod web
Warning  Failed  ...  Error: ErrImagePull
Warning  Failed  ...  Error: ImagePullBackOff
Failed to pull image "nginx:latest": rpc error: code = Unknown
  desc = failed to pull and unpack image "docker.io/library/nginx:latest":
  failed to resolve reference "docker.io/library/nginx:latest":
  pulling from host docker.io failed with status code [manifests latest]:
  429 Too Many Requests

# 根因:Docker Hub rate limit → 换私有 registry 或配镜像缓存

# 案例:imagePullSecret 缺失
$ kubectl describe pod web
Failed to pull image "private-registry/app:1.0": rpc error:
  code = Unknown desc = failed to authorize: failed to fetch oauth token:
  unexpected status: 401 Unauthorized

# 修复:
kubectl create secret docker-registry regcred \
  --docker-server=private-registry \
  --docker-username=user \
  --docker-password=pwd \
  --docker-email=dev@example.com

# 在 Pod spec 中加:
spec:
  imagePullSecrets:
  - name: regcred
```

### 23.7.3 Pending 完整排查

Pending = Pod 已写入 etcd,但无法调度或容器创建中:

```
诊断流程:
  1. kubectl describe pod <pod> | tail -20
     → Events 中:
       - 0/N nodes available: ... (调度失败)
       - Successfully assigned ... (已调度,卡在创建)
  2. 看具体 Reason
```

常见根因与修复:

| Reason | 根因 | 修复 |
|--------|------|------|
| Insufficient cpu | CPU 资源不足 | 加节点 / 调低 requests / 加节点 CPU |
| Insufficient memory | 内存不足 | 同上 |
| node(s) had taint, pod didn't tolerate | 污点不匹配 | 加 toleration 或去掉 taint |
| node(s) didn't match node affinity | 亲和性不匹配 | 修 nodeSelector / affinity |
| node(s) had volume node affinity conflict | 卷与节点不匹配 | PV 拓扑与 Pod 调度冲突 |
| pod didn't match PodAntiAffinity | 反亲和性导致无处调度 | 调整反亲和性 |
| Insufficient plugins | 调度器扩展插件拒绝 | 看 scheduler log |

排查示例:

```bash
# 案例:CPU 不足
$ kubectl describe pod batch
Events:
  Warning  FailedScheduling  ...  0/5 nodes available: 5 Insufficient cpu.

# 修复:加节点 / 调低 requests.cpu / 改 best-effort

# 案例:污点不匹配
$ kubectl describe pod web
Events:
  Warning  FailedScheduling  ...  0/5 nodes available: 5 node(s) had taint {gpu: true}, that the pod didn't tolerate.

# 修复:加 tolerations
spec:
  tolerations:
  - key: "gpu"
    value: "true"
    effect: "NoSchedule"

# 案例:CSI 挂载慢导致 Pending
$ kubectl describe pod db
Events:
  Normal  Scheduled         ...  Successfully assigned default/db to node-1
  Warning  FailedMount       ...  Unable to attach or mount volumes: unmounted volumes=[data], unattached volumes=[data]: timed out waiting for the condition
  Normal  VolumeMounted      ...  (5min later) MountVolume.SetUp succeeded for volume "data"

# 根因:CSI driver 慢 → 优化 CSI / 换存储类型
```

### 23.7.4 Evicted 排查

Pod 被 kubelet 驱逐,通常因为节点压力:

```bash
$ kubectl get pod web
NAME   READY   STATUS    RESTARTS  AGE
web    0/1     Evicted   0         5m

$ kubectl describe pod web
Status:  Failed
Reason:  Evicted
Message: The node was low on resource: memory. Container web was using 8056Ki, which exceeds its request of 0.
```

驱逐触发条件:

```
节点条件 → 驱逐信号 → 阈值:
  MemoryPressure  → memory.available < 100Mi (硬驱逐)
  DiskPressure    → nodefs.available < 10%
                  → nodefs.inodesFree < 5%
                  → imagefs.available < 15%
  PIDPressure     → pid.available < 100

软驱逐(soft eviction):
  --eviction-soft=memory.available<1.5Gi
  --eviction-soft-grace-period=memory.available=1m30s
  (达到阈值后等 grace period,再不恢复才驱逐)

硬驱逐(hard eviction):
  --eviction-hard=memory.available<100Mi
  (立即驱逐)
```

排查:

```bash
# 1. 看节点条件
kubectl describe node <node> | grep -A 10 Conditions

# 2. 看节点内存
kubectl top node <node>
free -h

# 3. 看磁盘
df -h /var/lib/kubelet /var/lib/containerd

# 4. 看 PID
ls /proc | wc -l

# 5. 看 kubelet 驱逐日志
journalctl -u kubelet | grep -i evict
```

### 23.7.5 OOMKilled 排查

```bash
$ kubectl describe pod web
Containers:
  web:
    Last State: Terminated
      Reason:   OOMKilled
      Exit Code: 137
      Started:   ...
      Finished:  ...

# 节点 dmesg
$ dmesg | grep -i "out of memory"
[12345.678] Memory cgroup out of memory: Killed process 1234 (java) total-vm:5g, anon-rss:2g

# cgroup memory.events
$ cat /sys/fs/cgroup/kubepods/.../memory.events
oom 5
oom_kill 1
```

排查路径:

```
1. 容器 OOM 还是节点 OOM?
   - 容器 OOM: container status.reason = OOMKilled, exit 137
   - 节点 OOM:  节点 dmesg 显示 "Out of memory: Killed process"
                kubelet 也可能被杀,导致 NotReady

2. 内存使用峰值是什么?
   - Prometheus: container_memory_working_set_bytes / container_spec_memory_limit_bytes
   - cAdvisor: container memory peak

3. 根因:
   a. limits.memory 太低 → 调高
   b. 内存泄漏 → pprof 分析
   c. 突发流量 → 扩容 + 限流
   d. JVM heap 设置不当 → 设 -Xmx
   e. 子进程内存不计 → 看 cgroup memory.usage
```

### 23.7.7 DNS 解析失败

K8s DNS 解析失败是高频问题:

```bash
# 在 Pod 内测试
kubectl exec -it <pod> -- sh
/ # nslookup kubernetes.default
;; connection timed out; no servers could be reached

# 排查路径
1. 看 CoreDNS Pod 状态
   kubectl get pods -n kube-system -l k8s-app=kube-dns

2. 看 CoreDNS 日志
   kubectl logs -n kube-system <coredns-pod>

3. 看 Pod 的 /etc/resolv.conf
   kubectl exec <pod> -- cat /etc/resolv.conf
   # 应该指向 kube-dns service IP

4. 看 CoreDNS 配置
   kubectl get configmap coredns -n kube-system -o yaml

5. 看 NodeLocalDNS(若部署)
   kubectl get ds node-local-dns -n kube-system

6. conntrack 是否爆满
   ssh <node>; conntrack -S | grep -i "insert_failed"
```

常见根因:

| 现象 | 根因 | 修复 |
|------|------|------|
| nslookup 超时 | CoreDNS Pod 不健康 | 重启 CoreDNS |
| 解析慢(2-5s) | UDP conntrack 满 | 部署 NodeLocalDNS |
| 短名解析失败(如 svc1) | search domain 缺失 | 检查 resolv.conf |
| 仅特定 ns 解析失败 | NetworkPolicy 拦截 | 加 DNS egress 规则 |
| ndots:5 导致多次查询 | FQDN 也走 search | 用 FQDN 或调 ndots |

### 23.7.8 Pod 卡在 Terminating

```bash
$ kubectl delete pod web
pod "web" deleted

$ kubectl get pod web
NAME   READY   STATUS        RESTARTS  AGE
web    1/1     Terminating   0         5m   ← 一直卡着
```

根因与修复:

```
1. finalizer 未移除:
   kubectl get pod web -o jsonpath='{.metadata.finalizers}'
   # ["kubernetes.io/pvc-protection"]

   强制移除:
   kubectl patch pod web --type=json -p='[{"op":"remove","path":"/metadata/finalizers"}]'

2. preStop hook 卡住:
   kubectl describe pod web | grep -A 3 "preStop"
   # 默认 terminationGracePeriodSeconds=30

   解决:加大 grace period 或修 preStop 脚本
   kubectl delete pod web --grace-period=0 --force  # 强制(慎用)

3. 容器不响应 SIGTERM:
   应用没处理 SIGTERM → 等 grace period 后 SIGKILL

4. volume unmount 卡住(CSI):
   看 kubelet log: journalctl -u kubelet | grep "Unmount"
   看 CSI driver log

5. 节点 NotReady,kubelet 无法处理:
   修复节点 → kubelet 恢复后自动清理
   或强制: kubectl delete pod web --grace-period=0 --force
```

### 23.7.9 节点 NotReady 排查

```
kubectl get nodes
NAME       STATUS                     ROLES    AGE   VERSION
node-1     Ready                      worker   30d   v1.30.0
node-2     NotReady                   worker   30d   v1.30.0  ← 异常
```

排查:

```bash
# 1. 看节点 conditions
kubectl describe node node-2 | grep -A 10 Conditions
# 关注: Ready / MemoryPressure / DiskPressure / PIDPressure

# 2. SSH 到节点(或 kubectl debug node/node-2)
journalctl -u kubelet --since "30 min ago" | tail -100

# 3. 看节点资源
free -h
df -h
top

# 4. 看进程
ps aux | grep -E "kubelet|containerd"

# 5. 看 dmesg
dmesg | tail -50  # 内核 panic / OOM

# 6. 看 PLEG
journalctl -u kubelet | grep PLEG | tail -20
```

常见根因:

| 现象 | 根因 | 修复 |
|------|------|------|
| Ready=False, KubeletNotReady | kubelet 进程挂了 | systemctl restart kubelet |
| Ready=False, PLEGNotHealthy | PLEG 卡死 | 重启 containerd + kubelet |
| MemoryPressure | 节点内存压力 | 清理或加内存 |
| DiskPressure | 节点磁盘满 | 清理镜像/日志 |
| PIDPressure | PID 耗尽 | 修内存泄漏进程 |
| 节点失联 | 网络分区 / 内核 panic | 重启节点 |

### 23.7.10 5xx 间歇性错误排查

间歇性 5xx 是最难定位的故障:

```
排查思路:
  1. 收集错误样本(时间戳 + URL + client IP)
  2. 关联指标:Pod CPU / Memory / 连接数 / GC
  3. 关联日志:应用 log + ingress log
  4. 关联 trace:OpenTelemetry trace
  5. 抓包确认是否到达 Pod

常见根因:
  a. Pod readinessProbe 失败但还在接流量 → 调严 probe
  b. Kube-proxy iptables 规则更新慢 → 用 IPVS 或 endpoint slices
  c. conntrack 表满 → 调大 max_conntrack
  d. Keep-alive 超时配置不当 → client/server 超时不一致
  e. JVM GC 暂停 → 调 GC
  f. 网络抖动 → 抓包确认
  g. Pod 被驱逐前流量未切走 → 加 preStop + terminationGracePeriod
```

### 23.8.4 Netflix Chaos Engineering 故障排查哲学

Netflix 的混沌工程(Chaos Engineering)不是「制造故障」,而是「持续验证故障恢复能力」:

```
核心原则:
  1. 假设:系统在故障下应能正常服务
  2. 实验:主动注入故障(Chaos Monkey / Chaos Kong)
  3. 度量:SLO 是否达标
  4. 改进:发现薄弱点,加固

工具链:
  - Chaos Monkey: 随机杀 instance
  - Latency Monkey: 注入网络延迟
  - Conformity Monkey: 发现不合规范的实例
  - Security Monkey: 安全合规检查
  - Doctor Monkey: 检查节点健康
  - Janitor Monkey: 清理无用资源

应用在 K8s:
  - Chaos Mesh(开源):注入 Pod / Network / IO 故障
  - Litmus(开源):K8s 原生混沌工程
  - Gremlin: 商业化混沌工程

排查价值:
  - 提前发现隐患,主动修复
  - 训练 SRE 故障排查能力
  - 验证 runbook 有效性
  - 度量系统韧性
```

### 23.8.5 Google Borgmon 故障排查哲学

Google Borgmon(K8s Prometheus 的灵感来源)的故障排查哲学:

```
1. 白盒监控优先:
   - 暴露内部状态(requests / errors / latency)
   - 故障可预测,而非事后发现

2. 故障域隔离:
   - Borg cell(类 K8s cluster)独立
   - 跨 cell 冗余部署
   - 故障影响半径可控

3. Borgmon 规则:
   - alert: 基于多维度组合(expr)
   - 严重度分级: page(电话叫醒) / ticket(工单) / logging
   - actionable: 每个 alert 都有 runbook

4. 排查 SOP:
   - 接到 alert → 看 dashboard
   - 看 alert 关联的 runbook
   - 按 runbook 步骤执行
   - 若 runbook 不全 → 补充

5. 故障复盘(postmortem):
   - blameless(不追责,修流程)
   - root cause(根因,不是症状)
   - action items(改进项,带 owner + deadline)
```

## 23.9 与其他方案的关系

### 23.9.1 kubectl debug vs nsenter

| 维度 | kubectl debug | nsenter |
|------|---------------|---------|
| 实现方式 | ephemeral container(共享 namespace) | 直接进入已有进程的 namespace |
| 需要 SSH | 否(走 K8s API) | 是(需登节点) |
| 镜像工具 | 自带(在 ephemeral container 中) | 节点上的工具 |
| 适合场景 | distroless 容器 / K8s 原生 | 节点级诊断 / 不需新容器 |
| 权限 | ephemeralContainers RBAC | 节点 root / sudo |
| 历史 | K8s 1.18+ | 早就存在 |
| 隔离 | ephemeral container 独立进程树 | 进入主容器进程树 |

```
nsenter 用法:
  # 找到容器主进程 PID
  crictl inspect <container-id> | jq '.info.pid'
  # 或 docker inspect <id> | jq '.State.Pid'

  # nsenter 进入容器命名空间
  nsenter -t <pid> -m -u -i -n -p -- sh

  # 在节点上进入 Pod 的网络命名空间
  PID=$(crictl inspect <id> | jq '.info.pid')
  nsenter -t $PID -n -- tcpdump -i eth0
```

### 23.9.2 crictl vs ctr vs docker CLI

| 维度 | crictl | ctr | docker CLI |
|------|--------|-----|------------|
| 维护方 | K8s SIG | containerd | Docker |
| 接口 | CRI gRPC | containerd gRPC | Docker API |
| 兼容运行时 | 全部 CRI(containerd/CRI-O/dockerd) | 仅 containerd | 仅 dockerd |
| 抽象层 | PodSandbox + Container(高) | namespace + snapshot(低) | image + container(中) |
| 主要场景 | K8s 故障排查 | containerd 故障排查 | 老版本 K8s(已弃用) |
| K8s 1.24+ | 推荐 | 节点上备用 | 不可用(dockershim 移除) |

```
等价命令对照:

  docker ps        ↔ crictl ps / ctr -n k8s.io containers list
  docker images    ↔ crictl images / ctr -n k8s.io images list
  docker logs      ↔ crictl logs / kubectl logs
  docker exec      ↔ crictl exec / kubectl exec
  docker inspect   ↔ crictl inspect / ctr containers info
  docker pull      ↔ crictl pull / ctr -n k8s.io images pull
  docker rm        ↔ crictl rm / ctr -n k8s.io containers delete
  docker rmi       ↔ crictl rmi / ctr -n k8s.io images rm
  docker stats     ↔ crictl stats
```

### 23.9.3 bcc-tools vs bpftrace vs systemtap

| 维度 | bcc-tools | bpftrace | systemtap |
|------|-----------|----------|-----------|
| 语言 | Python + C + BPF | bpftrace(DSL) | SystemTap(DSL) |
| 内核要求 | Linux 4.1+ | Linux 4.9+ | Linux 2.6+ |
| 学习曲线 | 中(需懂 C/BPF) | 平(单行命令) | 陡 |
| 性能开销 | 低 | 极低 | 中 |
| 工具丰富度 | 高(80+ 工具) | 中 | 高 |
| K8s 集成 | 容器化镜像 | 容器化 | 节点级 |
| 社区活跃 | 高(BCC + BPF) | 高 | 中 |

```
等价工具对照:

  跟踪 syscall:
    bcc:     execsnoop-bpfcc / opensnoop-bpfcc
    bpftrace: bpftrace -e 'tracepoint:syscalls:sys_enter_* { @[probe] = count() }'
    systemtap: stap -e 'probe syscall.* { @[name] = count() }'

  跟踪 IO:
    bcc:     biolatency-bpfcc
    bpftrace: bpftrace -e 'tracepoint:block:block_rq_issue { @start[arg->dev] = nsecs } ...'

  跟踪 TCP:
    bcc:     tcptracer-bpfcc
    bpftrace: bpftrace -e 'tracepoint:sock:inet_sock_set_state { ... }'
    systemtap: stap -e 'probe tcp.* { ... }'

  推荐:日常用 bcc(开箱即用);复杂场景用 bpftrace;systemtap 仅老内核用
```

## 23.10 面试速答

1. **Q: Pod 一直 Pending 怎么排查?**
   A: `kubectl describe pod <pod>` 看 Events。FailedScheduling 是调度失败(资源不足/污点不匹配/亲和性);ContainerCreating 是容器创建中(镜像/卷/CNI 慢)。对应修复:加节点/调资源、加 toleration、改 storage 类型。

2. **Q: CrashLoopBackOff 怎么定位?**
   A: 关键命令 `kubectl logs <pod> --previous` 看崩溃前日志。退出码 1=应用错误,127=command not found,137=OOMKilled,139=SIGSEGV。再看 describe 的 LastState.Reason / Message。

3. **Q: OOMKilled 但 limits 没动过,为什么突然出现?**
   A: 可能是流量突增导致 JVM heap 膨胀,或内存泄漏,或子进程内存计入 cgroup。用 `cat /sys/fs/cgroup/.../memory.events` 看 oom_kill 计数,dmesg 看哪个进程被杀,Prometheus 看 container_memory_working_set_bytes 历史曲线。

4. **Q: kubectl debug 的 4 种模式?**
   A: (1) 给 Pod 注入 ephemeral container(共享 namespace);(2) copy-to 复制 Pod 加调试容器;(3) node/<node> 节点级调试(类似 node-shell);(4) profile 预设权限(sysadmin / restricted)。

5. **Q: Pod 卡在 Terminating 怎么办?**
   A: 看 finalizer / preStop hook / volume unmount / 节点 NotReady。先 `kubectl describe` 看 Events,确认为何卡住。若是 finalizer 卡住,可强制 patch 移除;若是 preStop 卡住,加大 terminationGracePeriodSeconds 或修 preStop 脚本;紧急用 `kubectl delete --grace-period=0 --force`(慎用,可能丢数据)。

6. **Q: crictl 和 ctr 区别?**
   A: crictl 走 CRI gRPC,兼容所有 CRI 运行时(containerd/CRI-O),抽象层高,只看到 PodSandbox + Container;ctr 走 containerd gRPC,只支持 containerd,抽象层低,可看到 namespace/snapshot/content。日常用 crictl,看 containerd 细节才用 ctr。

7. **Q: 节点 NotReady 怎么排查?**
   A: `kubectl describe node` 看 Conditions(Ready / MemoryPressure / DiskPressure / PIDPressure)。SSH 进节点 `journalctl -u kubelet` 看日志,`dmesg` 看内核,`free -h` / `df -h` 看资源,`systemctl status kubelet containerd` 看进程。常见根因:kubelet 进程挂、PLEG 卡死、磁盘满、内核 panic。

8. **Q: PLEG is not healthy 是什么?**
   A: PLEG(Pod Lifecycle Event Generator)每秒调用 CRI Status 获取所有 Pod 状态,relist 超过 3 秒就告警。根因:容器太多、containerd 卡死、慢磁盘、cgroup 卡。修复:重启 containerd / kubelet,或减少节点 Pod 密度。

9. **Q: 5xx 间歇性错误怎么排查?**
   A: 收集错误样本(时间戳+URL+client IP)→ 关联应用 log + ingress log + trace → 看节点指标(CPU/GC/conntrack)→ 抓包确认是否到达 Pod。常见根因:readinessProbe 配置过宽、kube-proxy iptables 更新慢、conntrack 满、keep-alive 超时不一致、JVM GC 暂停。

10. **Q: ephemeral container 和普通 container 区别?**
    A: ephemeral container (1) 不能加 resources / ports / volume;(2) 不会 restart;(3) 不会触发 Probe;(4) 共享目标容器 namespace(PID/Network);(5) 通过 ephemeralContainers 子资源追加,不修改原 Pod spec.template;(6) K8s 1.25+ GA。

11. **Q: 容器退出码 137 一定是 OOMKilled 吗?**
    A: 不一定。137 = 128 + 9 (SIGKILL),可能是 (a) OOMKilled 看 dmesg;(b) kubelet livenessProbe 失败后 SIGKILL;(c) `kubectl delete` grace period 后强制 kill;(d) 父进程主动 kill。要看 `kubectl describe` 的 LastState.Reason 是否为 OOMKilled,以及 dmesg 是否有 OOM 日志。

12. **Q: Pod 内的 /etc/resolv.conf 是哪来的?**
    A: kubelet 根据 cluster DNS 配置(`--cluster-dns`)和 `dnsPolicy`(ClusterFirst / Default / None)生成。ClusterFirst 模式下,nameserver 是 kube-dns service IP,search domain 包含 `<ns>.svc.cluster.local svc.cluster.local cluster.local`,ndots 默认 5。

13. **Q: tcpdump 在 Pod 内抓不到包?**
    A: Pod 内默认无 tcpdump,且非特权容器无法抓 raw socket。两种方案:(1) kubectl debug 注入 ephemeral container(特权);(2) 在节点上 `nsenter -t <pid> -n -- tcpdump -i eth0`,PID 来自 `crictl inspect`。后者更轻量。

14. **Q: bpftrace 和 bcc 区别?**
    A: bcc 是工具集(Python+C+BPF),开箱即用 80+ 工具(biolatency / tcptracer / execsnoop),适合日常排查;bpftrace 是 DSL,用单行命令快速写 trace,灵活但需要懂内核 tracepoint。复杂追踪用 bpftrace,标准操作用 bcc。

15. **Q: 镜像拉取失败 ImagePullBackOff 怎么排查?**
    A: `kubectl describe pod` 看 Events 中的具体错误。manifest unknown=镜像不存在;unauthorized/401=imagePullSecret 缺失或过期;toomanyrequests=registry 限流;timeout=网络/DNS。在节点上 `crictl pull <image>` 复现,`curl -v https://registry/v2/` 测试连通。

16. **Q: Pod 间网络不通怎么排查?**
    A: 分层定位:(1) Pod 内 `ip addr` 看是否有 eth0;(2) `ping` 同节点 Pod 测二层;(3) `ping` 跨节点 Pod 测三层(看 CNI 路由);(4) `dig` 测 DNS;(5) `curl` 测 Service;(6) tcpdump 多点抓包确认丢包位置;(7) `iptables -L -n` 看 kube-proxy 规则;(8) `conntrack -L` 看连接跟踪表。

17. **Q: PV 挂载失败怎么排查?**
    A: (1) `kubectl get pvc` 看 STATUS 是否 Bound;(2) `kubectl describe pvc` 看 Events;(3) `kubectl describe pv` 看 CSI 状态;(4) 节点上 `lsblk` / `mount` / `findmnt` 看块设备与挂载点;(5) 看 CSI driver pod 日志;(6) `kubectl get csidriver` 看驱动注册。常见根因:云厂商 API 限流、卷配额满、卷拓扑冲突、节点文件系统签名冲突。

18. **Q: 容器内看到的主机名是哪来的?**
    A: 来自 Pod spec.hostname(默认是 metadata.name)。会写到容器的 /etc/hostname 和 utS namespace。Pod 内 `hostname` 命令读取的就是这个。

19. **Q: kubelet 日志在哪?**
    A: 取决于部署方式。systemd 部署:`journalctl -u kubelet`;静态 Pod:`kubectl logs -n kube-system kubelet-<node>`;二进制 + log 文件:`/var/log/kubelet.log`。日志级别 `-v=2` 默认,排障时可临时调高 `-v=4` 或 `--v=6`(debug)。

20. **Q: 一个 Pod 的 5 个 container,其中一个 OOM,Pod 还活着吗?**
    A: 看 restartPolicy。Always(默认):该容器会被重启,Pod 仍 Running;OnFailure:同样重启;Never:不重启,但其他容器仍运行,Pod phase 仍 Running 直到所有容器终止。restartPolicy 不影响 Pod 内其他容器。

## 23.11 综合面试题

### 题 1:Pod 创建 5 分钟还没 Running,怎么定位?

```
思路:分层定位 + 时间线对齐

1. 看 phase:
   kubectl get pod <pod> -o wide
   → Pending / ContainerCreating / Running / Failed

2. 看 Events:
   kubectl describe pod <pod> | tail -30
   → FailedScheduling: 调度问题
   → Pulling image: 拉镜像中(可能慢)
   → Successfully pulled: 镜像好了,下一步
   → Created container: 容器创建好
   → Started container: 启动
   → Liveness probe failed: 探针失败
   → Readiness probe failed: Ready=False

3. 看 Container Statuses:
   kubectl get pod <pod> -o jsonpath='{.status.containerStatuses}' | jq .
   → state: Waiting / Running / Terminated
   → reason: ImagePullBackOff / CrashLoopBackOff / CreateContainerError / OOMKilled

4. 看节点:
   kubectl describe node <node>
   → Conditions (MemoryPressure / DiskPressure)
   → Events (kubelet 驱逐、containerd 卡死)

5. 看 PLEG:
   journalctl -u kubelet | grep PLEG
   → PLEG is not healthy → 重启 kubelet / containerd

6. 看 CSI:
   kubectl describe pod <pod> | grep -A 3 Volume
   → Mounted / FailedMount / WaitForAttach

7. 看应用:
   kubectl logs <pod>
   kubectl logs <pod> --previous
   → 应用错误 / DB 连不上 / 配置缺失

按时间线还原:
  T0  kubectl apply
  T1  Scheduled (10-100ms)
  T2  Image pull (1s - 5min)
  T3  Volume mount (100ms - 5min,CSI 慢)
  T4  Container create (100ms)
  T5  Container start (100ms)
  T6  App init (1s - 10min)
  T7  Probe pass (1-60s)

卡在哪一步,直接定位
```

### 题 2:大流量导致服务 5xx,Pod 状态都正常,怎么排查?

```
思路:Pod 正常 → 不是 Pod 自身崩溃,是流量层面问题

1. 看指标:
   - Pod CPU / Memory 是否飙高
   - Pod 网络入带宽 / 包速率
   - kube-proxy iptables sync 延迟
   - conntrack 表使用率
   - 客户端到 Service 的延迟分布

2. 看日志:
   - 应用 log(超时、连接被拒)
   - ingress log(503 / 502 / 499)
   - kube-proxy log(endpoint 更新慢)

3. 抓包:
   - 在 client Pod 抓:看请求是否发出
   - 在 server Pod 抓:看请求是否到达
   - 在节点抓:看 conntrack 是否丢
   - 用 cilium monitor / eBPF 看内核丢包

4. 常见根因:
   a. conntrack 表满:
      conntrack -S | grep insert_failed
      → 调大 nf_conntrack_max

   b. kube-proxy iptables 更新慢:
      kube-proxy log: "syncing rules took 30s"
      → 切 IPVS / 缩小 endpoint 范围

   c. Keep-alive 不一致:
      client keep-alive 60s,server 30s
      → server 端在 31s 关闭,但 client 仍发请求

   d. JVM GC 暂停:
      jstat -gcutil,看 Full GC 时间
      → 调 GC 参数 / 加内存

   e. Pod 即将 OOM 但还没被杀:
      memory.usage 接近 limits
      → 调高 limits / 扩容

   f. readinessProbe 失败但 endpoint 没及时移除:
      kube-proxy endpoint slice 同步慢
      → 调小 publishNotReadyAddresses / 用 endpoint slice

5. 修复:
   - 短期:扩容(HPA)+ 限流
   - 中期:调参(conntrack / kube-proxy / GC)
   - 长期:重构(异步 / 缓存 / 分库)
```

### 题 3:某节点上所有 Pod 都 OOMKilled,但节点内存还有,什么原因?

```
思路:全局性 OOM,但不是节点内存压力

1. 看 cgroup 限制:
   cat /sys/fs/cgroup/kubepods.slice/memory.max
   → 可能 kubepods 父 cgroup 被限制

   或 systemd 配置:
   systemctl show kubelet | grep MemoryLimit

2. 看是否 system OOM:
   dmesg | grep "Out of memory"
   → 内核 OOM killer 选择容器杀

3. 看 kubelet eviction:
   journalctl -u kubelet | grep -i evict
   → Hard eviction 触发,但 Pod 状态显示 OOMKilled?

4. 看是否 cgroup v2 + memory.high:
   cat /sys/fs/cgroup/.../memory.high
   → 触发 memory.high 后内核会主动回收,导致 OOM

5. 看是否 Pod QoS 不对:
   kubectl get pod <pod> -o jsonpath='{.status.qosClass}'
   → Guaranteed / Burstable / BestEffort

6. 看是否 KubeletCPUManagerPolicy 影响:
   kubelet 配置 --cpu-manager-policy=static
   → 可能 cgroup 配置不当

修复:
   - 调整节点 kubepods.slice cgroup 限制
   - 检查 systemd / kubelet 配置
   - 升级内核 / kubelet 版本
```

### 题 4:CoreDNS 解析慢,怎么定位?

```
1. 现象:
   - Pod 内 nslookup 慢(2-5s)
   - 间歇性失败

2. 测量:
   kubectl exec <pod> -- dig @10.96.0.10 kubernetes.default +stats
   → query time

3. 看 CoreDNS Pod:
   kubectl get pod -n kube-system -l k8s-app=kube-dns
   → CPU / 内存是否饱和
   kubectl top pod -n kube-system -l k8s-app=kube-dns

4. 看 CoreDNS 日志:
   kubectl logs -n kube-system <coredns-pod>
   → 是否有 timeout / SERVFAIL

5. 看 conntrack:
   conntrack -S | grep insert_failed
   → UDP conntrack 满,导致 DNS 包丢

6. 看 Pod 数量:
   kubectl get pods -A | wc -l
   → 5K+ Pod 后 DNS QPS 过载

解决方案:
  a. 部署 NodeLocalDNS:
     - DaemonSet 在每节点
     - 监听 node-local-dns 的 169.254.20.10
     - 缓存 + 转发到 CoreDNS
     - 减少跨节点 UDP 流量
     - 减少 conntrack 表项

  b. CoreDNS 横向扩容:
     kubectl scale deploy/coredns -n kube-system --replicas=10
     → 但单节点 UDP 反而拥塞,需 NodeLocalDNS

  c. 调优 CoreDNS:
     - 启用 autopath 插件(减少 search domain 查询)
     - 调 cache TTL
     - 调 pod_zone / fallthrough

  d. 调大 conntrack:
     sysctl -w net.netfilter.nf_conntrack_max=1048576

  e. 应用层:
     - 用 FQDN(避免 ndots 触发 search)
     - 调 resolv.conf options(ndots:1)
     - 加 DNS 缓存(libc / JVM)
```

### 题 5:etcd 慢导致 apiserver 超时,怎么定位?

```
1. 现象:
   - kubectl get pods 慢(5-30s)
   - apiserver log: "etcdserver: request timed out"
   - Pod 创建卡在 etcd 写入

2. 看 etcd metrics:
   curl -k https://etcd:2379/metrics | grep -E "etcd_disk|etcd_server"
   → etcd_disk_wal_fsync_duration_seconds
   → etcd_server_proposals_failed_total
   → etcd_mvcc_db_total_size_in_bytes

3. 看 etcd log:
   journalctl -u etcd | grep -E "slow|timeout|fail"
   → "apply request took too long"
   → "failed to publish"
   → "leader changed"

4. 看磁盘:
   iostat -x 1 5
   → %util 接近 100%
   → await > 10ms

5. 看 DB 大小:
   etcdctl endpoint status -w table
   → DB SIZE 是否接近 2GB / 8GB

6. 看 network:
   etcdctl endpoint health --cluster -w table

7. 根因:
   a. 磁盘 IO 慢:
      - 共享磁盘(不推荐)
      - HDD 而非 SSD
      - 文件系统满
      - IO 竞争(其他服务)

   b. DB 过大:
      - 历史事件未清理
      - lease 未回收
      - compaction 没跑

   c. 网络分区:
      - etcd 节点间延迟 > 50ms
      - 跨可用区部署不当

   d. 大量 Watch:
      - 监听整个 /api/v1/pods
      - 每次 Pod 变化推送全量

8. 修复:
   a. 紧急:
      - 切到备用 etcd
      - 限流 apiserver(API Priority and Fairness)

   b. 短期:
      - 跑 compaction: etcdctl compact $(etcdctl endpoint status -w json | jq -r '.[].Status.header.revision')
      - 跑 defrag: etcdctl defrag --cluster
      - 清理旧事件: kubectl delete events --all

   c. 中期:
      - 换 SSD
      - etcd 独占节点
      - 调大 quota (--quota-backend-bytes=8GB)

   d. 长期:
      - 拆分 etcd(按资源类型)
      - 加 etcd 节点(5/7/9 奇数)
      - 跨可用区部署
```

### 题 6:节点上 kubelet 报 PLEG not healthy,Pod 全部 Evicted,怎么救?

```
1. 紧急止损:
   - 标记节点不可调度: kubectl cordon <node>
   - 不 drain(可能卡住),让 Pod 在其他节点重建

2. SSH 进节点(或 kubectl debug node/<node>):
   journalctl -u kubelet --since "30 min ago" | grep PLEG
   → 看 PLEG 卡了多久

   systemctl status containerd
   → containerd 是否还在

   ps aux | grep -E "kubelet|containerd"
   → 进程状态

   ls /var/lib/containerd/io.containerd.snapshotter
   → 快照数是否过多

   df -h /var/lib/containerd /var/lib/kubelet
   → 磁盘是否满

3. 根因分析:
   a. containerd 卡死:
      重启: systemctl restart containerd
      (会重启所有 Pod,但通常能恢复)

   b. 大量容器:
      节点 > 200 Pod,relist 慢
      → 减少节点密度,加节点

   c. 慢磁盘:
      IO 排队 → containerd 读写慢
      → 换 SSD / 优化文件系统

   d. cgroup 卡死:
      内核 bug → 重启节点

4. 恢复:
   - 重启 containerd / kubelet
   - 等节点 Ready
   - kubectl uncordon <node>
   - 验证 Pod 重新调度

5. 防范:
   - 加 PLEG 监控: relist > 3s 告警
   - 加节点密度监控: Pod 数 > 150 告警
   - 加节点自愈: PLEG 不健康持续 5min 自动 drain
```

### 题 7:应用发布后 Pod 全部 CrashLoopBackOff,怎么紧急回滚?

```
1. 紧急回滚(优先止血):
   # 如果用 Deployment
   kubectl rollout undo deploy/<name> --to-revision=<last>

   # 看 revision 历史
   kubectl rollout history deploy/<name>

   # 紧急暂停滚动
   kubectl rollout pause deploy/<name>

2. 保留现场:
   # 不要删 Pod!先抓诊断信息
   for pod in $(kubectl get pods -l app=<name> -o name); do
     kubectl describe $pod > /tmp/describe-$(basename $pod).txt
     kubectl logs $pod --previous > /tmp/logs-prev-$(basename $pod).txt
     kubectl logs $pod > /tmp/logs-$(basename $pod).txt
     kubectl get $pod -o yaml > /tmp/yaml-$(basename $pod).txt
   done

3. 分析根因:
   kubectl logs <pod> --previous | head -50
   → 应用错误 / 配置缺失 / 依赖不可达

4. 修复 + 重新发布:
   - 修代码 / 配置 / 镜像
   - 灰度发布(canary),小流量验证
   - 全量发布

5. 复盘:
   - 为什么 CI 没拦住?
   - 加 staging 验证
   - 加金丝雀发布流程
   - 加自动回滚(readinessProbe 失败率 > 阈值)
```

### 题 8:多集群跨 region 网络延迟 200ms,Pod 间通信慢,怎么排查?

```
1. 现象:
   - 集群 A 的 Pod 访问集群 B 的 Service,延迟 200ms+
   - 同 region 内访问正常(<5ms)

2. 排查路径:
   a. Pod 内测量:
      kubectl exec <pod> -- ping <clusterB-pod-ip>
      kubectl exec <pod> -- mtr -n <clusterB-pod-ip>
      → 看 mtr 路径,确认跨 region 路由

   b. 抓包:
      kubectl exec <pod> -- tcpdump -i eth0 -nn host <clusterB-pod-ip>
      → 看是否有重传

   c. 看 CNI 配置:
      - Calico: 跨 region 是否走 BGP over WAN
      - Cilium: 跨 region 是否走 tunnel / direct
      - Submariner: 跨集群连通方案

   d. 看 conntrack:
      conntrack -L | grep <ip>
      → 长连接是否被复用

   e. 看 kube-proxy:
      - 跨集群 Service 用 ExternalName / Headless / Egress NAT
      - iptables / IPVS 模式影响

3. 根因:
   a. 物理距离远(无法改)
      → 用 Submariner / Cilium ClusterMesh 跨集群直连 Pod
      → 同 region 部署热数据

   b. 路由不当
      → 走公网(慢 + 不安全)
      → 走 VPN(可能拥塞)
      → 应走专线 / VPC peering

   c. TCP keep-alive 不当
      → 长连接 idle 后被 NAT 清,重建慢
      → 调 keep-alive < NAT timeout

   d. TLS handshake
      → 每次 TLS 握手多 1-2 RTT
      → 用 session resumption / mTLS

4. 修复:
   a. 跨 region 服务:
      - 同 region 优先(就近路由)
      - 跨 region 用 CDN 缓存
      - 异步消息替代同步调用

   b. 网络:
      - 专线 / VPC peering
      - 跨集群 mesh(Istio multi-cluster)
      - Cilium ClusterMesh

   c. 协议:
      - HTTP/2 / gRPC(多路复用)
      - Connection pool
      - Protocol buffer(二进制)
```

## 23.12 故障复盘

### 案例 1:CrashLoopBackOff 误判为应用 bug 导致 4 小时排查

**故障时间**:2023-06-15

**故障现象**:
- 业务 Pod 频繁 CrashLoopBackOff
- 应用 log 显示 DB 连接失败
- SRE 误判为应用配置错误,反复修配置

**根因**:
- 实际是 CoreDNS 故障导致 DB 域名解析失败
- 应用代码在 DNS 失败时直接 panic(exit 1)
- CrashLoopBackOff 表象掩盖了 DNS 根因

**修复**:
1. 排查时未先验证 DNS:`kubectl exec <pod> -- nslookup <db>`
2. 修复 CoreDNS(NodeLocalDNS + 扩容)
3. 改应用:DNS 失败重试而非 panic
4. 加监控:DNS 解析失败率告警

**经验**:
- CrashLoopBackOff 看到 logs 报错前,先验证依赖(DNS / DB / Registry)
- 排障 SOP 第一步:确认基础设施健康(DNS / 网络 / API)

### 案例 2:ImagePullBackOff 拖垮集群发布

**故障时间**:2023-08-20

**故障现象**:
- 集群升级,所有节点同时拉新镜像
- registry 带宽打满,大量 ImagePullBackOff
- 升级卡住 6 小时

**根因**:
- 镜像 1.5GB,500 节点同时拉
- registry 单点,无 P2P 加速
- 没有镜像预热(pre-pull)

**修复**:
1. 紧急:分批升级,每批 50 节点
2. 部署 Dragonfly / Kraken P2P 镜像分发
3. 镜像瘦身(用 distroless / 多阶段构建)
4. 加 registry 横向扩容 + 多区域副本

**经验**:
- 大规模发布必须镜像预热
- 镜像大小直接关联发布速度,瘦身优先
- P2P 镜像分发是万节点集群标配

### 案例 3:PLEG not healthy 全节点 Pod 重启

**故障时间**:2023-10-05

**故障现象**:
- 节点 Ready=False,PLEG is not healthy
- 节点上所有 Pod 状态 Unknown
- Pod 被重新调度,但旧 Pod 残留

**根因**:
- containerd 1.6 bug,在大量容器(300+)时 relist 卡死
- 节点 Pod 密度过高(180/200 上限)
- 慢磁盘(IO 排队)加剧 relist 延迟

**修复**:
1. 紧急:`kubectl drain <node> --ignore-daemonsets --force`
2. 节点上 `systemctl restart containerd kubelet`
3. 等节点 Ready,uncordon
4. 升级 containerd 到 1.7+ (修复 PLEG bug)
5. 限制节点 Pod 密度(maxPods=110)

**经验**:
- 节点 Pod 密度有上限,超过 110 需评估
- containerd 版本与 K8s 版本要对齐
- 加 PLEG 监控:relist > 3s 告警

### 案例 4:Conntrack 爆满导致全集群网络抖动

**故障时间**:2023-11-12

**故障现象**:
- 大量 SYN 包被丢,服务间歇性 5xx
- conntrack -S 显示 insert_failed 持续增长
- DNS 解析也慢(UDP 也走 conntrack)

**根因**:
- 节点 conntrack 表大小 262144(默认)
- 集群规模 3000 Pod,长连接 + 短连接混合
- conntrack 表接近满,新连接无法建立

**修复**:
1. 紧急:重启受影响节点(清空 conntrack)
2. 调大 conntrack:`sysctl -w net.netfilter.nf_conntrack_max=1048576`
3. 永久:`/etc/sysctl.d/99-k8s-conntrack.conf`
4. 部署 NodeLocalDNS 减少 UDP conntrack
5. 应用层连接池(减少新建连接)

**经验**:
- conntrack 是 K8s 网络的隐形瓶颈
- 节点初始化脚本必须调 conntrack
- UDP 也走 conntrack,DNS 流量大时受影响

### 案例 5:CSI Driver 卡死导致 PVC 挂载失败

**故障时间**:2024-01-20

**故障现象**:
- 大量 Pod Pending,FailedMount
- 错误:"rpc error: code = DeadlineExceeded"
- CSI driver pod 不响应

**根因**:
- 云厂商 EBS API 限流(>1000 QPS)
- CSI driver 没有重试机制
- 大量 Pod 同时创建,触发限流

**修复**:
1. 紧急:重启 CSI driver pod
2. 限流:限制同时创建带 PVC 的 Pod 数
3. 分批发布,平滑挂载
4. CSI driver 升级(支持重试 + 限流)
5. 用本地存储(emptyDir / hostPath)减少 CSI 依赖

**经验**:
- CSI driver 是 K8s 与云厂商的桥梁,云 API 限流会传导
- 大规模挂载需分批
- 监控 CSI driver 延迟

### 案例 6:节点磁盘满导致 Kubelet 不可用

**故障时间**:2024-03-08

**故障现象**:
- 节点 NotReady
- kubelet log: "failed to write log" / "no space left on device"
- Pod 创建失败,日志写不进

**根因**:
- 应用日志写到本地文件(未走 stdout)
- 容器日志未 rotation,堆积 50GB
- 节点根分区 100GB 满

**修复**:
1. 紧急:`kubectl drain <node>` + 清理日志
2. 改应用:日志走 stdout / stderr
3. 加 log rotation Policy
4. 节点配 LVM / 单独日志分区
5. 加监控:节点磁盘水位告警(>80%)

**经验**:
- 应用日志必须走 stdout,K8s 自动 rotation
- 节点磁盘监控要分层(根 / data / log)
- 容器内文件写要用 emptyDir + sizeLimit

### 案例 7:eBPF 程序加载失败导致 Cilium 节点 NotReady

**故障时间**:2024-04-25

**故障现象**:
- 部分 Pod 跨节点不通
- Cilium pod 报 "bpf load failed: Out of memory"
- 节点上 bpftool prog list 不全

**根因**:
- 内核版本 5.4(旧),BPF 程序内存上限低
- Cilium 1.15 加载大量 BPF 程序(>200)
- 老内核 BPF 内存限制触发

**修复**:
1. 紧急:重启 Cilium pod
2. 升级内核到 5.10+ (BPF 内存上限提高)
3. 临时:`sysctl -w net.core.bpf_jit_limit=2000000000`
4. Cilium 调优:减少 BPF 程序(关不需要的特性)

**经验**:
- Cilium / eBPF 强依赖内核版本(5.10+ 推荐)
- BPF 内存限制是隐藏瓶颈
- 节点内核版本要统一并定期升级

### 案例 8:apiserver 限流(APF)误配导致 Controller 写不动

**故障时间**:2024-06-10

**故障现象**:
- 集群 Pod 创建慢(20s+)
- apiserver log: "failed to write to etcd: context deadline exceeded"
- 但 etcd 健康

**根因**:
- API Priority and Fairness(APF)配置不当
- system 卷宗被一个慢请求占满
- controller-manager 写 status 被排队

**修复**:
1. 看限流指标:apiserver_flowcontrol_dispatched_requests / apiserver_flowcontrol_rejected_requests
2. 调 APF:加大 system 优先级
3. 重启 apiserver 让排队清空
4. 长期:优化 controller 写入频率(informer resync)

**经验**:
- APF 是 1.20+ 的隐性限流,易被忽略
- 大集群需要专门调优 APF
- 监控 apiserver_flowcontrol_* 指标

### 排障 SOP 模板

```
故障排障 SOP(Standard Operating Procedure)模板:

1. 故障发现:
   - 告警来源(Prometheus / 用户反馈)
   - 影响范围(用户数 / 服务数)
   - 严重度(P0/P1/P2)

2. 紧急止损(< 5min):
   - 标记故障时间线
   - 评估是否回滚 / 切流 / 扩容
   - 通知干系人

3. 现场采集(< 15min):
   - kubectl describe / logs
   - crictl ps / inspect
   - journalctl -u kubelet / containerd
   - 节点 SOS 报告

4. 根因定位(< 30min):
   - 列假设(3-5 个)
   - 逐个验证(命令 + 输出)
   - 排除法收敛

5. 修复验证(< 60min):
   - 修复(回滚 / 调参 / 重启)
   - 验证(SLO 恢复 / 用户反馈消失)
   - 全量恢复

6. 复盘(< 7d):
   - 时间线(发现 → 止血 → 修复 → 恢复)
   - 根因(技术 + 流程)
   - 改进项(监控 / 告警 / SOP / 自动化)
   - blameless(不追责,修流程)
```
