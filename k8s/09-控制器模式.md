# 09 - 控制器模式

> K8s 的灵魂是 Reconcile Loop(收敛循环):声明期望状态,控制器不断把实际状态拉向期望。本章讲透 List-Watch / Informer / Reconcile / Finalizer / OwnerReferences,以及如何写自定义控制器。

## 2. 直觉解释

### 2.1 "恒温空调"类比

```
   设定温度 = 25°C  (期望状态,Declared State)
   实际温度 = 30°C  (实际状态,Actual State)
   
   控制器逻辑:
   while True:
     actual = read_sensor()
     if actual > 25:
       cool_down()
     elif actual < 25:
       heat_up()
     sleep(1s)
```

- 不关心"为什么"温度变了,只关心"现在"是不是 25°C
- 不记录"之前"做了什么,每次重新判断
- 持续运行,直到达到目标

这就是 **Reconcile Loop**:声明期望 → 持续观察 → 拉向期望。

### 2.2 K8s 控制器的核心模式

```
   ┌─────────────────────────────────────────┐
   │ Controller                              │
   │                                          │
   │  while True:                             │
   │    desired = read_from_apiserver()       │
   │    actual = read_from_world()            │
   │    if actual != desired:                 │
   │      take_action_to_match(desired)       │
   └─────────────────────────────────────────┘
```

**关键**:
- desired 来自 K8s API(用户声明的 YAML)
- actual 来自"真实世界"(cloud / kubelet / Pod 状态)
- action 通过 K8s API 写回(创建 Pod / 更新状态)
- 持续循环,直到收敛

### 2.3 Level-Triggered vs Edge-Triggered

| 触发方式 | 含义 | 例子 |
|---------|------|------|
| **Edge-Triggered** | 状态变化时触发 | 监控告警(CPU 从 50% 跳到 90%) |
| **Level-Triggered** | 状态本身触发,持续判断 | 恒温空调(只要温度 > 25 就制冷) |

K8s 用 **Level-Triggered**:
- 不管 ReplicaSet 是否变,持续检查 Pod 数
- 即使错过事件,下次循环仍能发现
- 容错性强(事件丢失不致命)

## 3. 核心概念

### 3.1 List-Watch 机制

```
   ┌─────────────────────────────────────────┐
   │ Client (Controller)                     │
   │                                          │
   │ 1. List:全量拉取对象                     │
   │ 2. Watch:增量推送(基于 resourceVersion)│
   │ 3. 失败重连:用最新 resourceVersion 重新 List │
   └─────────────────────────────────────────┘
```

**为什么不用轮询**:
- 1000 个客户端 × 每秒 List = apiserver 雪崩
- Watch 用 HTTP/2 长连接,资源占用低
- 增量推送(只发变化的对象)

**resourceVersion**:
- 每个对象每次更新自增
- Watch 时携带 rv,apiserver 推送该 rv 之后的变化
- rv 失效(被压缩)→ 重新 List

### 3.2 Informer 框架

client-go 的 Informer 封装 List-Watch,提供:

```
   ┌─────────────────────────────────────────┐
   │ Informer                                │
   │                                          │
   │ ┌─────────────────────────────────────┐ │
   │ │ Reflector                           │ │
   │ │  - List + Watch                     │ │
   │ │  - 写入 Delta FIFO Queue            │ │
   │ └─────────────────────────────────────┘ │
   │                                          │
   │ ┌─────────────────────────────────────┐ │
   │ │ Delta FIFO Queue                    │ │
   │ │  - 增量事件(Added/Updated/Deleted)│ │
   │ └─────────────────────────────────────┘ │
   │                                          │
   │ ┌─────────────────────────────────────┐ │
   │ │ Indexer (本地缓存)                  │ │
   │ │  - 索引(按 namespace / labels)     │ │
   │ │  - 类似本地 etcd                    │ │
   │ └─────────────────────────────────────┘ │
   │                                          │
   │ ┌─────────────────────────────────────┐ │
   │ │ Handlers (用户回调)                 │ │
   │ │  - OnAdd / OnUpdate / OnDelete      │ │
   │ └─────────────────────────────────────┘ │
   └─────────────────────────────────────────┘
```

**核心特性**:
- **本地缓存**:Controller 不需每次访问 apiserver,降低压力
- **Delta FIFO**:事件去重 + 顺序保证
- **Indexer**:多维度索引,快速查询

### 3.3 WorkQueue 与 Reconcile

```
   ┌─────────────────────────────────────────┐
   │ Controller                              │
   │                                          │
   │  Informer Handler:                      │
   │    on_add(obj)  → workqueue.Add(key)    │
   │    on_update(obj) → workqueue.Add(key)  │
   │    on_delete(obj) → workqueue.Add(key)  │
   │                                          │
   │  Worker (N 个并发):                     │
   │    while True:                           │
   │      key = workqueue.Get()               │
   │      reconcile(key)                      │
   │      workqueue.Done(key)                 │
   └─────────────────────────────────────────┘
```

**为什么用 WorkQueue**:
- **去重**:同一对象短时间多次变更,只处理一次
- **限流**:RateLimiter,防止 requeue 风暴
- **失败重试**:处理失败自动重新入队,指数退避

### 3.4 Reconcile 函数

```go
// 伪代码
func Reconcile(key string) error {
    namespace, name := splitKey(key)
    
    // 1. 从 Informer 缓存读期望状态
    desired, err := indexer.Get(namespace, name)
    if errors.IsNotFound(err) {
        // 对象被删,清理资源
        return cleanup(name)
    }
    
    // 2. 读实际状态(从 world)
    actual, err := readFromWorld(name)
    
    // 3. 计算 diff
    if actual.replicas != desired.replicas {
        // 4. 采取行动,拉向期望
        updatePods(desired.replicas)
    }
    
    // 5. 写回状态(更新 Status)
    updateStatus(actual)
    
    // 6. 失败 → 返回 err,自动重试
    return nil
}
```

**关键**:
- 幂等:同一输入多次执行结果一致
- 不依赖事件:每次都重新判断完整状态
- 失败安全:返回 err 自动重试,不丢事件

### 3.5 Finalizer(终结器)

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
  finalizers:
  - example.com/cleanup       # 自定义 finalizer
spec:
  replicas: 3
```

**作用**:
- 防止对象被误删
- 删除时,先标记 `deletionTimestamp`,但**不真正删除**
- 等 finalizer 清理完后,移除 finalizer,对象才删

**典型场景**:
- PVC 删除前,先从 Node unmount
- Service 删除前,先释放云厂商 LB
- CRD 删除前,先清理外部资源(如数据库)

**实现**:
```go
func Reconcile(obj) error {
    if obj.DeletionTimestamp != nil && contains(obj.Finalizers, "example.com/cleanup") {
        // 执行清理
        cleanupExternalResources(obj)
        // 移除 finalizer
        obj.Finalizers = remove(obj.Finalizers, "example.com/cleanup")
        apiserver.Update(obj)
        return nil
    }
    // 正常逻辑
}
```

### 3.6 OwnerReferences(级联删除)

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-app-xxx
  ownerReferences:
  - apiVersion: apps/v1
    kind: ReplicaSet
    name: my-app-xxx
    uid: xxx-xxx-xxx
    controller: true        # 是直接控制器
    blockOwnerDeletion: true
```

**作用**:
- 标记对象的所有者
- 所有者删除时,级联删除依赖对象
- garbage collector 自动清理

**级联策略**:
- **Foreground**:先删依赖对象,再删所有者(用户看到所有者最后消失)
- **Background**:先删所有者,后台 GC 清理依赖
- **Orphan**:删所有者,保留依赖(依赖变成孤儿)

### 3.7 Status 子资源

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 3                # 期望状态
status:
  replicas: 3                # 实际状态
  readyReplicas: 3
  availableReplicas: 3
  conditions:
  - type: Progressing
    status: "True"
  - type: Available
    status: "True"
```

**Spec vs Status**:
- **Spec**:用户声明的期望状态
- **Status**:控制器上报的实际状态
- 分离:用户改 Spec,控制器改 Status,各管一摊

## 5. 底层原理

### 5.1 Informer 完整工作流

```
   1. Reflector 调用 List,拿到所有对象 + resourceVersion
   2. 用 resourceVersion 启动 Watch
   3. Watch 收到事件,写入 Delta FIFO Queue
   4. Informer 从 Delta FIFO 取出:
      a. 更新本地 Indexer
      b. 触发 Handlers
   5. Handler 把 key 放入 WorkQueue
   6. Worker 从 WorkQueue 取 key,调 Reconcile
   7. Reconcile 读 Indexer(本地缓存),无需访问 apiserver
   8. Reconcile 通过 apiserver 修改其他对象
   9. 失败 → Reconcile 返回 err,WorkQueue 重试(指数退避)
```

### 5.2 List-Watch 的可靠性

```
   场景:Watch 连接断开
   
   1. Reflector 检测到 Watch 失败
   2. 用最后已知的 resourceVersion 重新 Watch
      - 如果 rv 仍有效:继续从这里 Watch
      - 如果 rv 已过期(被压缩):List 全量,从头开始
   3. 重新 List + Watch,保证不丢事件
```

**关键**:
- 事件可能重复(去重)
- 但不会丢失

### 5.3 sharedInformers 共享

```
   多个控制器监听同一资源:
   
   传统方式:
     Controller A → Informer A → List-Watch Pod
     Controller B → Informer B → List-Watch Pod
     Controller C → Informer C → List-Watch Pod
   问题:3 倍 apiserver 压力
   
   SharedInformer:
     Controller A ─┐
     Controller B ─┼→ SharedInformer → List-Watch Pod
     Controller C ─┘
   优势:1 倍 apiserver 压力,3 个 Controller 共享缓存
```

### 5.4 Reconcile 的幂等性

```go
// 非幂等(错误)
counter := 0
func Reconcile() {
    counter++
    createPod(counter)        // 每次创建不同 Pod
}

// 幂等(正确)
func Reconcile(rs *ReplicaSet) {
    pods := listPods(rs.Selector)
    if len(pods) < rs.Spec.Replicas {
        createPod(generateName(rs))   // 名字基于 RS,重复调用安全
    }
}
```

**关键**:
- 每次都重新读完整状态
- 不依赖"之前调用过几次"
- 操作可重入(创建用 generateName,更新用 resourceVersion 乐观锁)

### 5.5 Status 更新的乐观锁

```go
// 伪代码:控制器更新 Status
for {
    obj := getFromApiserver(name)         // 拿最新版本
    obj.Status.Replicas = currentReplicas
    err := updateStatus(obj)              // 用最新版本更新
    if errors.IsConflict(err) {
        continue                          // 冲突,重试
    }
    break
}
```

**resourceVersion**:
- apiserver 每次更新对象,rv 自增
- 客户端带 rv 更新,服务端校验,冲突返回 409
- 客户端重试(乐观锁)

### 6.2 控制器主循环(伪代码)

```go
package main

import (
    "context"
    "fmt"
    "time"
    
    "k8s.io/apimachinery/pkg/api/errors"
    "k8s.io/apimachinery/pkg/util/runtime"
    "k8s.io/apimachinery/pkg/util/wait"
    "k8s.io/client-go/tools/cache"
    "k8s.io/client-go/util/workqueue"
    "k8s.io/klog/v2"
)

type Controller struct {
    informer    cache.SharedIndexInformer
    queue       workqueue.RateLimitingInterface
    appClient   appsv1client.AppsV1Interface
    kubeClient  kubernetes.Interface
}

func NewController(...) *Controller {
    c := &Controller{...}
    
    // 注册 Informer Handler
    c.informer.AddEventHandler(cache.ResourceEventHandlerFuncs{
        AddFunc:    c.enqueue,
        UpdateFunc: func(old, new interface{}) { c.enqueue(new) },
        DeleteFunc: c.enqueue,
    })
    return c
}

func (c *Controller) enqueue(obj interface{}) {
    key, err := cache.MetaNamespaceKeyFunc(obj)
    if err != nil {
        runtime.HandleError(err)
        return
    }
    c.queue.Add(key)
}

func (c *Controller) Run(workers int, stopCh <-chan struct{}) {
    defer c.queue.ShutDown()
    
    // 启动 Informer
    go c.informer.Run(stopCh)
    
    // 等缓存同步
    if !cache.WaitForCacheSync(stopCh, c.informer.HasSynced) {
        runtime.HandleError(fmt.Errorf("timed out waiting for caches to sync"))
        return
    }
    
    // 启动 N 个 worker
    for i := 0; i < workers; i++ {
        go wait.Until(c.worker, time.Second, stopCh)
    }
    
    <-stopCh
}

func (c *Controller) worker() {
    for c.processNextWorkItem() {
    }
}

func (c *Controller) processNextWorkItem() bool {
    key, quit := c.queue.Get()
    if quit {
        return false
    }
    defer c.queue.Done(key)
    
    err := c.reconcile(key.(string))
    if err != nil {
        c.queue.AddRateLimited(key)    // 失败重试(指数退避)
        return true
    }
    c.queue.Forget(key)
    return true
}

func (c *Controller) reconcile(key string) error {
    namespace, name, _ := cache.SplitMetaNamespaceKey(key)
    
    // 1. 读期望状态
    app, err := c.appClient.Apps(namespace).Get(name)
    if errors.IsNotFound(err) {
        // 对象被删,清理(本例无外部资源)
        return nil
    }
    if err != nil {
        return err
    }
    
    // 2. 读实际状态(查关联的 Deployment)
    deploy, err := c.kubeClient.AppsV1().Deployments(namespace).Get(name)
    
    // 3. 计算行动
    if errors.IsNotFound(err) {
        // Deployment 不存在,创建
        deploy = buildDeployment(app)
        _, err = c.kubeClient.AppsV1().Deployments(namespace).Create(deploy)
        return err
    }
    
    // 4. Deployment 存在,检查是否需要更新
    if deploy.Spec.Replicas != app.Spec.Replicas ||
       deploy.Spec.Template.Spec.Containers[0].Image != app.Spec.Image {
        deploy.Spec.Replicas = app.Spec.Replicas
        deploy.Spec.Template.Spec.Containers[0].Image = app.Spec.Image
        _, err = c.kubeClient.AppsV1().Deployments(namespace).Update(deploy)
        return err
    }
    
    // 5. 更新 App 的 Status
    if app.Status.ReadyReplicas != deploy.Status.ReadyReplicas {
        app.Status.ReadyReplicas = deploy.Status.ReadyReplicas
        app.Status.Phase = calculatePhase(deploy)
        _, err = c.appClient.Apps(namespace).UpdateStatus(app)
        return err
    }
    
    return nil
}

func buildDeployment(app *App) *appsv1.Deployment {
    return &appsv1.Deployment{
        ObjectMeta: metav1.ObjectMeta{
            Name: app.Name,
            OwnerReferences: []metav1.OwnerReference{
                {
                    APIVersion: "example.com/v1",
                    Kind:       "App",
                    Name:       app.Name,
                    UID:        app.UID,
                    Controller: ptr(true),
                },
            },
        },
        Spec: appsv1.DeploymentSpec{
            Replicas: &app.Spec.Replicas,
            Selector: &metav1.LabelSelector{
                MatchLabels: map[string]string{"app": app.Name},
            },
            Template: corev1.PodTemplateSpec{
                ObjectMeta: metav1.ObjectMeta{
                    Labels: map[string]string{"app": app.Name},
                },
                Spec: corev1.PodSpec{
                    Containers: []corev1.Container{
                        {
                            Name:  "app",
                            Image: app.Spec.Image,
                            Ports: []corev1.ContainerPort{{ContainerPort: app.Spec.Port}},
                        },
                    },
                },
            },
        },
    }
}
```

## 7. 常见陷阱与调优 ⚠️

### 7.1 Informer 陷阱

| 陷阱 | 现象 | 根因 | 解决 |
|------|------|------|------|
| **Watch 断连频繁** | Informer 重启 | apiserver LB idle timeout 短 | LB 配置 ≥ 1h |
| **cache 不同步** | 控制器看到旧数据 | cache 未及时同步 | 等待 HasSynced |
| **内存占用高** | OOM | 监听大量对象 | 分 namespace / 分片 |

### 7.2 Reconcile 陷阱

| 陷阱 | 现象 | 根因 | 解决 |
|------|------|------|------|
| **死循环** | CPU 100% | Reconcile 一直返回 err | 排查根因,加 backoff |
| **状态不一致** | 实际与期望不符 | Reconcile 漏写状态 | 状态完全报告 |
| **非幂等** | 多次执行结果不同 | 用 generateName 而非固定名 | 用确定性命名 |

### 7.3 Finalizer 陷阱

| 陷阱 | 现象 | 根因 | 解决 |
|------|------|------|------|
| **Pod 卡 Terminating** | 删不掉 | finalizer 未移除 | 检查控制器是否运行 |
| **资源泄漏** | 外部资源未清理 | 强制移除 finalizer | 先手动清理再移除 |
| **finalizer 死锁** | 一直 Terminating | 控制器逻辑错 | 加超时 + 手动恢复 |

### 7.4 性能陷阱

| 陷阱 | 现象 | 根因 | 解决 |
|------|------|------|------|
| **Reconcile 慢** | 状态更新延迟 | 调用外部 API 慢 | 加缓存 + 异步 |
| **apiserver 压力大** | QPS 超限 | 直接 List-Watch 大对象 | 用 Informer cache |
| **workqueue 堆积** | 事件处理不及时 | worker 太少 | 增加 worker 数 |

## 8. 工业案例与基准数据

### 8.1 阿里:ACK Controller 性能优化

**场景**:单集群 5k 节点,100k Pod,Controller 性能瓶颈。

**优化**:
1. **SharedInformer**:所有控制器共享 cache,降低 apiserver 压力
2. **分片**:大 namespace 单独 Informer
3. **异步 Reconcile**:外部 API 调用异步,避免阻塞 workqueue
4. **批量更新**:状态批量更新,降低 apiserver QPS

**效果**:
- apiserver QPS 从 30k 降到 5k
- Reconcile 延迟 P99 从 5s 降到 1s

### 8.2 字节:Operator 大规模实践

**场景**:Kafka Operator 管理 100+ Kafka 集群。

**架构**:
- Operator 用 kubebuilder 生成
- 每个 Kafka 集群一个 CR
- Operator Reconcile:滚动升级 / 故障切换 / 扩缩容

**经验**:
1. **Reconcile 幂等**:外部 API 失败重试,不创建重复资源
2. **Finalizer**:CR 删除前清理外部 Kafka 集群
3. **OwnerReferences**:Kafka 集群的 Pod/PVC 自动级联删除
4. **Status 完整**:用户能从 Status 看到集群健康度

### 8.3 Google:GKE Autopilot 的控制器

**场景**:GKE Autopilot 全托管,内部大量控制器。

**特色**:
1. **多租户隔离**:每个 namespace 独立控制器实例
2. **资源配额**:控制器自身资源限制
3. **自动扩缩**:控制器根据负载扩缩
4. **零停机升级**:控制器自身滚动更新

| 适合 | 复杂运维(数据库) | 简单部署 |

## 11. 综合面试题

### 11.1 基础题

**Q1**: 描述 K8s 控制器的 Reconcile Loop 模式。

**答题要点**:
- 声明期望状态(Spec)
- 持续观察实际状态(从 world)
- 计算 diff,采取行动拉向期望
- 上报 Status
- 失败重试,幂等
- Level-Triggered:不依赖事件,每次重新判断

**Q2**: Informer 的工作流程?

**答题要点**:
1. Reflector 调用 List 全量拉取
2. 用 resourceVersion 启动 Watch
3. 事件写入 Delta FIFO
4. 更新本地 Indexer(缓存)
5. 触发 Handlers(用户回调)
6. Handler 把 key 放入 WorkQueue
7. Worker 取 key 调 Reconcile
8. Watch 断开 → 用 rv 重新 Watch / 失效则重新 List

### 11.2 进阶题

**Q3**: 为什么 K8s 用 Level-Triggered 而不是 Edge-Triggered?

**答题要点**:
- Edge-Triggered:依赖事件,丢失事件可能永久不一致
- Level-Triggered:看状态本身,即使错过事件,下次循环仍能发现
- 容错性:Level > Edge
- 复杂度:Level 简单(每次重新判断)
- K8s 设计哲学:状态最终一致,容忍短暂不一致

**Q4**: Finalizer 怎么工作?写一个用 finalizer 的场景。

**答题要点**:
- 对象加 finalizer 后,DELETE 标记 deletionTimestamp,但**不真正删除**
- 控制器 Watch 到 deletionTimestamp,执行清理
- 清理完移除 finalizer,对象才真正删除
- 场景:
  - Service type=LB 删除前,先释放云厂商 LB(避免 LB 残留计费)
  - PVC 删除前,先从 Node unmount
  - CRD 删除前,清理外部数据库 / 队列

**Q5**: 怎么写一个自定义控制器?

**答题要点**:
1. 定义 CRD(类型 + Spec + Status)
2. 用 kubebuilder 生成骨架
3. 实现 Reconcile:
   - 读 CR 期望状态
   - 读关联资源(Deployment / Pod)
   - 计算 diff
   - 创建 / 更新 / 删除关联资源
   - 更新 Status
4. 注册 Informer + Handler
5. 启动 worker 处理 workqueue
6. 错误处理:失败重试,指数退避
7. 测试:单元 + 集成 + e2e

### 11.3 高级题

**Q6**: 设计一个 MySQL Operator,要求支持自动备份和故障切换。

**答题要点**:
- **CRD**:MySQLCluster(spec: replicas / version / backupSchedule;status: readyReplicas / phase)
- **Reconcile**:
  - 创建 StatefulSet(MySQL 主从)
  - 创建 Service(读写分离)
  - 创建 ConfigMap(配置)
  - 监控 Pod 健康
- **备份**:
  - CronJob 触发,定期 xtrabackup 到 S3
  - Status 记录最后备份时间
- **故障切换**:
  - 主挂 → 选新主(从副本数最多的)
  - 提升新主,改 Service 指向
  - 重新配置其他从
- **Finalizer**:
  - 删除 CR 前关闭集群
  - 可选保留 PVC(数据安全)
- **OwnerReferences**:
  - StatefulSet/Pod/PVC 都属 CR
  - 删 CR 自动级联清理
- **升级**:
  - 滚动升级 StatefulSet
  - 主最后升级
- **监控**:
  - 复制延迟 / TPS / 慢查询
  - Operator 自身健康

**Q7**: 一个控制器 Reconcile 一直失败,死循环,怎么排查?

**答题要点**:
1. 看控制器日志
2. 看 Reconcile 错误信息
3. 常见原因:
   - apiserver 限流(409 Too Many Requests)
   - 外部依赖故障(DB / API)
   - 资源冲突(resourceVersion mismatch)
   - RBAC 权限不足
   - 代码 bug(空指针 / 类型断言)
4. 排查:
   - 加日志,打印关键步骤
   - 看事件流(kubectl get events)
   - 看 metrics(workqueue_depth / reconcile_errors)
5. 修复:
   - 限流:加 backoff
   - 依赖故障:超时 + 重试
   - 冲突:乐观锁重试
   - 权限:补 RBAC
6. 临时缓解:暂停控制器,手动修复

### 11.4 设计题

**Q8**: 设计一个 K8s 多租户控制器,隔离不同租户的资源。

**答题要点**:
- **租户模型**:每个租户一个 namespace
- **CRD**:Tenant(spec: resourceQuota / networkPolicy;status: usage)
- **Reconcile**:
  - 创建 namespace
  - 应用 ResourceQuota(限制 CPU / 内存 / Pod 数)
  - 应用 NetworkPolicy(隔离网络)
  - 应用 LimitRange(限制 Pod 资源)
  - 创建 RoleBinding(管理员权限)
- **隔离**:
  - 资源隔离:ResourceQuota
  - 网络隔离:NetworkPolicy(默认拒绝,允许同 namespace)
  - 权限隔离:RBAC(各 namespace 独立 SA)
  - 存储隔离:StorageClass + PVC 限制
- **监控**:
  - 各租户资源使用
  - 超额告警
- **Finalizer**:
  - 删除 CR 前清理 namespace(慎用,删 namespace 不可逆)
- **OwnerReferences**:
  - namespace 不属 CR(避免级联删除意外)

## 12. 故障复盘

### 12.1 案例 1:Finalizer 死锁导致资源删不掉

**业务影响**:2023 年某公司,自定义 Operator 升级后,旧 CR 删不掉,卡 Terminating 持续数天。

**根因**:
- 新版 Operator 改了 finalizer 名字
- 旧 CR 的 finalizer 新 Operator 不识别
- 资源一直卡 Terminating

**修复过程**:
1. 紧急:手动 patch 移除 finalizer(`kubectl patch -p '{"metadata":{"finalizers":[]}}'`)
2. 修复 Operator:兼容旧 finalizer(读取时同时识别新旧)
3. 升级流程:先升级 Operator,再删 CR

**防范**:
- finalizer 名字加版本号
- 升级时做兼容处理
- 文档化 finalizer 命名规范

### 12.2 案例 2:Informer cache 不一致

**业务影响**:2022 年某公司,Controller 看到的 Pod 数与实际不符,导致 Reconcile 错乱。

**根因**:
- Informer Watch 断连
- 重新 List 失败(apiserver 限流)
- cache 长时间未同步
- Controller 用旧数据决策

**修复过程**:
1. 紧急:重启 Controller,强制重新 List
2. 监控 Informer 同步状态(`HasSynced`)
3. cache 不一致时拒绝 Reconcile

**防范**:
- 监控 Informer 同步状态
- 启动时等待 HasSynced
- Watch 断连告警

### 12.3 案例 3:Reconcile 死循环导致 CPU 100%

**业务影响**:2024 年某公司,Operator Reconcile 一直返回 err,workqueue 不断重试,CPU 100%。

**根因**:
- Reconcile 调用外部 API,API 一直失败
- workqueue 指数退避但 max backoff 太短(1min)
- 失败事件堆积,CPU 满

**修复过程**:
1. 紧急:停 Operator
2. 修复:外部 API 失败时,Reconcile 返回特殊错误,跳过重试
3. 加 max backoff(30min)+ 失败计数,超阈值告警

**防范**:
- Reconcile 区分可重试 / 不可重试错误
- 失败计数 + 告警
- 外部依赖降级
