# 20. 策略与治理

> 关键词:OPA、Gatekeeper、Kyverno、Admission Webhook、CIS Benchmark、Cosign、SBOM、多租户、vCluster

------

## 20.1 问题定义

K8s 原生机制(RBAC/PSA/NetworkPolicy)解决 **基础安全**,但企业还需:

- 镜像必须来自可信仓库
- 资源必须设 requests/limits
- 标签必须符合规范(团队/产品/合规)
- 命名空间必须有 ResourceQuota
- 禁止 latest 标签
- 必须有 livenessProbe
- 必须从指定 registry 拉镜像
- 跨命名空间引用必须审批

**核心问题**:

> 如何用 **策略即代码(Policy as Code)** 实现比 PSA 更灵活的治理,覆盖合规、安全、运维多个维度?

------

## 20.2 直觉解释

把策略治理想象成 **公司的合规审核流程**:

| 合规审核 | K8s 策略 |
|---------|---------|
| 提交申请 → 审核 | kubectl apply → 准入 |
| 审核员检查规则 | OPA/Kyverno 校验策略 |
| 不合规拒绝 | 准入拒绝 |
| 修复后重新提交 | 修改后重新 apply |
| 高管豁免 | exception |
| 审计日志 | audit log |
| 定期合规报告 | CIS Benchmark 报告 |

关键点:策略 **代码化**(GitOps),**自动化**(准入控制),**可审计**(全 log)。

## 20.3 核心概念

### 20.3.1 K8s 准入控制回顾

```
请求 → Authn → Authz → 准入 → etcd
                      ↓
              Mutating(可改对象)
                      ↓
              Validation(校验)
                      ↓
              Validating(可拒绝)
                      ↓
              etcd

准入 Webhook 类型:
  - MutatingWebhookConfiguration:可修改对象
  - ValidatingWebhookConfiguration:仅校验,不修改

执行顺序:
  1. 内置 Mutating(默认值填充)
  2. 自定义 Mutating Webhook
  3. 内置 Validating(ResourceQuota 等)
  4. 自定义 Validating Webhook
  
K8s 1.30+: ValidatingAdmissionPolicy(VAP,声明式策略)
```

### 20.3.2 OPA(Open Policy Agent)与 Gatekeeper

```
OPA:通用策略引擎
  - 用 Rego 语言写策略
  - decoupled:任意应用嵌入
  - 决策:输入 JSON → 输出 true/false

Gatekeeper:OPA 的 K8s 集成
  - 准入 Webhook
  - CRD 定义策略(Constraint)
  - CRD 定义策略模板(ConstraintTemplate)
  - 支持审计(已存在的违规资源)
  - 支持复制数据(同步资源到 OPA cache)
```

### 20.3.3 Kyverno

```
Kyverno:K8s 原生策略引擎
  - YAML 写策略(无需 Rego)
  - 4 种动作:
    * validate: 校验
    * mutate:  修改
    * generate: 生成资源
    * verifyImages: 镜像签名验证
  - 命名空间级 + 集群级
  - 与 K8s API 完全兼容
```

### 20.3.4 OPA vs Kyverno 对比

| 维度 | OPA Gatekeeper | Kyverno |
|------|----------------|---------|
| 策略语言 | Rego(强大但陡) | YAML(简单) |
| 学习曲线 | 陡 | 平 |
| 灵活度 | 高(通用语言) | 中(K8s 场景) |
| 修改能力 | 弱(Mutating 复杂) | 强(mutate 内置) |
| 资源生成 | 弱 | 强(generate) |
| 镜像签名 | 弱 | 强(verifyImages) |
| 性能 | 好 | 好 |
| 社区 | CNCF 毕业项目 | CNCF 毕业项目 |
| 推荐场景 | 复杂策略、跨场景 | K8s 专用、易上手 |

### 20.3.5 CIS Kubernetes Benchmark

CIS(Center for Internet Security)发布 K8s 安全基线:

```
主要章节:
  1. Master Node 安全配置
  2. Worker Node 安全配置
  3. Control Plane 配置
  4. Policies(PSP/PSA/NetworkPolicy)
  5. RBAC
  6. Pod 安全
  7. 网络策略
  8. 审计日志

检查项示例:
  - 1.1.1 确保 API Server 不允许匿名访问
  - 1.2.1 确保 --anonymous-auth=false
  - 2.1.1 确保 --allow-privileged=true(应禁)
  - 4.1.1 确保 PSP/PSA 启用
```

### 20.3.6 镜像供应链

```
供应链安全:
  Source → Build → Registry → Deploy → Runtime
  
每步安全:
  1. Source:
     - 代码签名
     - 依赖锁定
     - SAST 扫描
     
  2. Build:
     - 构建者身份(Build Provenance)
     - SBOM 物料清单
     - 镜像签名(Cosign)
     
  3. Registry:
     - 漏洞扫描(Trivy)
     - 签名验证
     - 私有仓库访问控制
     
  4. Deploy:
     - Binary Authorization
     - 准入校验签名
     - 策略拦截
     
  5. Runtime:
     - 行为监控(Falco)
     - 异常告警
```

### 20.3.7 多租户隔离方案

```
方案 1:Namespace 隔离(弱)
  - 同集群共享控制面
  - NetworkPolicy + RBAC + PSA
  - 风险:控制面故障全影响

方案 2:vCluster(虚拟集群)
  - 每租户独立 K8s 控制面(在 Pod 内)
  - 共享底层集群
  - 强隔离 + 资源高效

方案 3:Karmada/KubeFed 多集群
  - 每租户独立集群
  - 跨集群管理
  - 强隔离但运维复杂

方案 4:Cluster API 多集群
  - 自动集群生命周期
  - 每租户独立
  - 适合大规模
```

## 20.4 操作流程

### 20.4.1 Gatekeeper 工作流程

```
1. 安装 Gatekeeper:
   helm install gatekeeper gatekeeper/gatekeeper

2. 定义 ConstraintTemplate:
   - 包含 Rego 策略代码
   - 定义 schema(参数)

3. 创建 Constraint:
   - 引用 ConstraintTemplate
   - 提供具体参数
   - 指定 enforcementAction(deny/audit/warn)

4. 资源创建时:
   a. APIServer 收到请求
   b. 准入阶段触发 ValidatingWebhook
   c. Gatekeeper 接收请求
   d. 加载 Constraint + 模板
   e. 运行 Rego 评估
   f. 返回 allow/deny

5. 审计:
   - Gatekeeper 周期性扫描所有资源
   - 标记违规(写入 status)
   - kubectl get constraint 查看违规
```

### 20.4.2 Kyverno 工作流程

```
1. 安装 Kyverno:
   helm install kyverno kyverno/kyverno

2. 创建 ClusterPolicy:
   - YAML 定义规则
   - match: 匹配资源
   - validate/mutate/generate: 动作

3. 资源创建时:
   a. APIServer 收到请求
   b. 触发 Admission Webhook
   c. Kyverno 接收
   d. 按策略评估
   e. validate 失败 → 拒绝
   f. mutate → 修改对象
   g. generate → 创建新资源

4. 策略报告:
   - kyverno 自动生成 PolicyReport
   - 命名空间级 + 集群级
   - 接 Prometheus/Grafana
```

### 20.4.3 镜像签名验证流程

```
1. 构建时签名:
   cosign sign --key cosign.key my-registry/app:v1.0
   # 签名存到 OCI registry

2. K8s 准入验证(Kyverno):
   apiVersion: kyverno.io/v1
   kind: ClusterPolicy
   metadata:
     name: verify-image-signature
   spec:
     rules:
     - name: verify-signature
       match:
         resources:
           kinds: [Pod]
       verifyImages:
       - imageReferences:
         - "my-registry/*"
         attestors:
         - entries:
           - keys:
               publicKeys: |
                 -----BEGIN PUBLIC KEY-----
                 ...
                 -----END PUBLIC KEY-----

3. 流程:
   a. Pod 创建请求
   b. Kyverno 拦截
   c. 提取 image
   d. 调 cosign verify
   e. 验证签名 + 公钥
   f. 通过 → 准入
   g. 失败 → 拒绝
```

## 20.5 底层原理

### 20.5.1 Admission Webhook 实现细节

```
Webhook 配置:
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingWebhookConfiguration
metadata:
  name: my-webhook
webhooks:
- name: validate.example.com
  clientConfig:
    service:
      name: webhook-svc
      namespace: webhook-ns
      path: /validate
    caBundle: <base64-ca>
  rules:
  - apiGroups: [""]
    apiVersions: [v1]
    resources: [pods]
    operations: [CREATE, UPDATE]
  failurePolicy: Fail    # Fail/Ignore
  timeoutSeconds: 10
  namespaceSelector:
    matchExpressions:
    - key: kubernetes.io/metadata.name
      operator: NotIn
      values: [kube-system]

Webhook 接收的 AdmissionReview:
{
  "apiVersion": "admission.k8s.io/v1",
  "kind": "AdmissionReview",
  "request": {
    "uid": "...",
    "kind": {group: "", version: "v1", kind: "Pod"},
    "resource": {...},
    "name": "my-pod",
    "namespace": "production",
    "operation": "CREATE",
    "userInfo": {username: "alice"},
    "object": <完整 Pod 对象>,
    "oldObject": null
  }
}

Webhook 返回:
{
  "apiVersion": "admission.k8s.io/v1",
  "kind": "AdmissionReview",
  "response": {
    "uid": "...",
    "allowed": false,
    "status": {
      "code": 403,
      "message": "image signature verification failed"
    }
  }
}

Mutating Webhook 还可返回 patch(JSON Patch):
{
  "response": {
    "allowed": true,
    "patchType": "JSONPatch",
    "patch": <base64-json-patch>
  }
}
```

### 20.5.2 OPA Rego 语言

```rego
# 检查所有 Pod 必须有 resource limits
package k8srequiredlimits

violation[{"msg": msg}] {
  container := input.review.object.spec.containers[_]
  not container.resources.limits.cpu
  msg := sprintf("container %s must have CPU limit", [container.name])
}

violation[{"msg": msg}] {
  container := input.review.object.spec.containers[_]
  not container.resources.limits.memory
  msg := sprintf("container %s must have memory limit", [container.name])
}

# 检查 image 不能用 latest 标签
violation[{"msg": msg}] {
  container := input.review.object.spec.containers[_]
  endswith(container.image, ":latest")
  msg := sprintf("container %s uses :latest tag, not allowed", [container.name])
}

# 检查必须来自可信 registry
violation[{"msg": msg}] {
  container := input.review.object.spec.containers[_]
  not startswith(container.image, "my-registry.com/")
  msg := sprintf("container %s image must be from my-registry.com", [container.name])
}
```

### 20.5.3 Kyverno 策略语法

```yaml
# 1. validate:校验
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: require-labels
spec:
  rules:
  - name: require-team-label
    match:
      resources:
        kinds: [Pod]
    validate:
      message: "Pod must have team label"
      pattern:
        metadata:
          labels:
            team: "?*"   # 必须存在且非空

# 2. mutate:修改
spec:
  rules:
  - name: add-default-resources
    match:
      resources:
        kinds: [Pod]
    mutate:
      patchStrategicMerge:
        spec:
          containers:
          - (name): "*"
            resources:
              requests:
                cpu: "100m"
                memory: "128Mi"
              limits:
                cpu: "500m"
                memory: "256Mi"

# 3. generate:生成
spec:
  rules:
  - name: generate-networkpolicy
    match:
      resources:
        kinds: [Namespace]
    generate:
      apiVersion: networking.k8s.io/v1
      kind: NetworkPolicy
      name: default-deny
      namespace: "{{request.object.metadata.name}}"
      data:
        spec:
          podSelector: {}
          policyTypes: [Ingress, Egress]

# 4. verifyImages:镜像签名
spec:
  rules:
  - name: verify-signature
    match:
      resources:
        kinds: [Pod]
    verifyImages:
    - imageReferences:
      - "*"
      attestors:
      - entries:
        - keys:
            publicKeys: |
              -----BEGIN PUBLIC KEY-----
              ...
```

### 20.5.4 ValidatingAdmissionPolicy(K8s 1.30+)

```yaml
# 声明式策略(无需 Webhook)
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata:
  name: require-labels
spec:
  failurePolicy: Fail
  matchConstraints:
    resourceRules:
    - apiGroups: [""]
      apiVersions: [v1]
      operations: [CREATE, UPDATE]
      resources: [pods]
  validations:
  - expression: "has(object.metadata.labels) && has(object.metadata.labels.team)"
    message: "Pod must have team label"
---
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicyBinding
metadata:
  name: require-labels-binding
spec:
  policyName: require-labels
  validationActions: [Deny, Audit]   # 1.27+ 支持
```

**优势**:
- 无需 Webhook 服务
- 性能高(在 APIServer 内评估)
- 用 CEL(Common Expression Language)
- K8s 原生

```
1. Namespace 多租户:
```

## 20.6 配置示例

### 20.6.1 Gatekeeper 策略示例

```yaml
# 1. ConstraintTemplate(模板 + Rego 代码)
apiVersion: templates.gatekeeper.sh/v1
kind: ConstraintTemplate
metadata:
  name: k8srequiredlabels
spec:
  crd:
    spec:
      names:
        kind: K8sRequiredLabels
      validation:
        openAPIV3Schema:
          type: object
          properties:
            labels:
              type: array
              items:
                type: string
  targets:
  - target: admission.k8s.gatekeeper.sh
    rego: |
      package k8srequiredlabels

      violation[{"msg": msg, "details": {"missing_labels": missing}}] {
        provided := {label | input.review.object.metadata.labels[label]}
        required := {label | label := input.parameters.labels[_]}
        missing := required - provided
        count(missing) > 0
        msg := sprintf("you must provide labels: %v", [missing])
      }
---
# 2. Constraint(具体策略)
apiVersion: constraints.gatekeeper.sh/v1beta1
kind: K8sRequiredLabels
metadata:
  name: require-team-label
spec:
  enforcementAction: deny    # deny/audit/warn
  match:
    kinds:
    - apiGroups: [""]
      kinds: [Pod]
    namespaces: ["production"]
  parameters:
    labels: [team, owner]
```

### 20.6.3 ValidatingAdmissionPolicy 示例

```yaml
# 1. 策略定义
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata:
  name: require-resources
spec:
  failurePolicy: Fail
  matchConstraints:
    resourceRules:
    - apiGroups: [""]
      apiVersions: [v1]
      operations: [CREATE]
      resources: [pods]
  validations:
  - expression: >
      object.spec.containers.all(c, 
        has(c.resources) && 
        has(c.resources.requests) && 
        has(c.resources.limits))
    message: "All containers must have resources.requests and limits"
---
# 2. 绑定
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicyBinding
metadata:
  name: require-resources-binding
spec:
  policyName: require-resources
  validationActions: [Deny]
  matchResources:
    namespaceSelector:
      matchLabels:
        environment: production
```

## 20.7 常见陷阱

| # | 陷阱 | 后果 | 解决 |
|---|------|------|------|
| 1 | Webhook failurePolicy=Fail | Webhook 故障集群不可用 | 关键 webhook 用 Ignore + 监控 |
| 2 | Webhook 超时 30s | APIServer 阻塞 | timeoutSeconds: 10 + 优化 |
| 3 | Webhook 拦截 kube-system | 集群故障 | namespaceSelector 排除 |
| 4 | OPA Rego 学习陡 | 策略难写 | 用 Kyverno(简单)或模板 |
| 5 | 策略未审计 | 已存在资源违规 | Gatekeeper Audit/Kyverno Report |
| 6 | enforcementAction=deny 直接上 | 已有资源被删 | 先 audit,逐步 enforce |
| 7 | 镜像签名验证无 fallback | 紧急部署被卡 | break-glass 例外 |
| 8 | 策略 GitOps 未做 | 策略漂移 | 策略存 Git,自动 sync |
| 9 | 多策略冲突 | 行为不可预期 | 统一策略管理 + 测试 |
| 10 | 准入 Webhook 不支持 HA | 单点故障 | 多副本 + 跨可用区 |
| 11 | VAP 不支持 mutate | 仅校验 | mutate 用 Kyverno |
| 12 | Cosign 密钥泄露 | 任意镜像可签名 | KMS/HSM 管理 |
| 13 | vCluster 网络默认通 | 隔离不够 | + NetworkPolicy |
| 14 | 合规扫描未定期 | 漂移 | CronJob 定期扫描 |
| 15 | OPA cache 失效慢 | 策略生效延迟 | 等 5 分钟或重启 |

## 20.10 面试速答

**Q1: 策略引擎 OPA 与 Kyverno 区别?**

OPA 用 Rego 语言写策略(强大但陡),Kyverno 用 YAML(简单)。Kyverno K8s 原生、易上手,适合 K8s 场景;OPA 通用,适合跨场景统一策略。

**Q2: Admission Webhook 工作原理?**

请求经 Authn/Authz 后到准入阶段,MutatingWebhook 可修改对象,ValidatingWebhook 校验。Webhook 接收 AdmissionReview,返回 allow/deny + 可选 patch。

**Q3: Gatekeeper 与 Kyverno 选型?**

简单 K8s 策略用 Kyverno(YAML 易写);复杂策略或跨场景(网关/CI)用 OPA Gatekeeper(Rego 强大);大型组织常两者都用。

**Q4: ValidatingAdmissionPolicy 是什么?**

K8s 1.30+ 声明式策略,APIServer 内评估(无需 Webhook),用 CEL 语言。性能高但仅校验,不支持 mutate。

**Q5: 镜像签名验证怎么做?**

构建时用 Cosign 签名(密钥在 KMS),部署时 Kyverno verifyImages 校验签名 + 公钥。验证失败拒绝部署。

**Q6: 多租户方案怎么选?**

- 同组织内:Namespace + NetworkPolicy + RBAC
- SaaS 多租户:vCluster(强隔离 + 高效)
- 强合规:独立集群(Karmada/Cluster API)

**Q7: CIS Benchmark 是什么?**

CIS 发布的 K8s 安全基线,200+ 检查项(Master/Worker/Policies/RBAC 等)。kube-bench 工具自动扫描。

**Q8: Webhook failurePolicy=Fail 风险?**

Webhook 故障时所有匹配请求被拒绝,集群可能不可用。关键系统应用应排除或用 Ignore(谨慎)。

**Q9: 策略 GitOps 怎么做?**

策略存 Git,通过 ArgoCD/FluxCD 同步到集群,变更走 PR + 审核。回滚即 Git revert。

**Q10: Pod Security Standards 与 OPA/Kyverno 关系?**

PSA 是 K8s 内置(三级别),OPA/Kyverno 是扩展(任意策略)。PSA 解决常见安全,OPA/Kyverno 解决更复杂治理。

```
     matchExpressions:
     - key: kubernetes.io/metadata.name
       operator: NotIn
       values: [kube-system, kube-public]
   - failurePolicy: Ignore(关键 webhook)
   - timeoutSeconds: 10(避免长阻塞)
   
5. 监控:
   - webhook 健康检查
   - webhook 延迟告警
   - 关键系统故障自动降级
```

### 题 6:解释 OPA Rego 评估模型

```
Rego 评估:

输入:JSON(AdmissionReview)
策略:Rego 代码
输出:JSON(decision)

评估流程:
1. OPA 加载 Rego 模块(策略)
2. 接收 input JSON
3. 规则匹配(逻辑编程)
4. 输出决策

Rego 特性:
1. 声明式(描述"是什么")
2. 逻辑编程(规则匹配)
3. 集合操作(set/list)
4. 递归(图查询)
5. 内置函数(strings/regex/json)

示例:
  package k8s
  
  # 默认拒绝
  default allow = false
  
  # 允许管理员
  allow {
    input.user == "admin"
  }
  
  # 允许特定操作
  allow {
    input.method == "GET"
  }
  
  # 拒绝删除命名空间
  deny[msg] {
    input.kind.kind == "Namespace"
    input.method == "DELETE"
    msg := "namespace deletion not allowed"
  }

K8s 集成:
  - input.review.object = K8s 资源
  - input.review.userInfo = 调用者
  - 输出 violation 列表
  - Gatekeeper 转换为 admission 响应
```

### 题 7:策略上线如何避免故障?

```
1. 策略测试:
   - 单元测试(Rego/Kyverno 单测)
   - 集成测试(测试集群验证)
   - 干运行(dry-run)
   
2. 渐进式上线:
   a. audit 模式(仅记录,不拒绝)
   b. 分析违规
   c. 修复已存在资源
   d. warn 模式(警告但不拒绝)
   e. enforce 模式(拒绝)
   
3. 例外机制:
   - 紧急情况 break-glass
   - 双人审批
   - 时间限制(自动失效)
   
4. 监控:
   - 策略触发率
   - 拒绝率
   - 关键资源违规告警
   - 策略性能(评估延迟)
   
5. 回滚:
   - 策略 GitOps(回滚 = git revert)
   - 紧急 disable webhook
   - 灾备方案
   
6. 文档:
   - 策略说明
   - 修复指南
   - 例外申请流程
   - FAQ
```

## 20.12 故障复盘

### 案例 1:Webhook 拦截 coredns 升级

**故障时间**:2023-09-12

**故障现象**:
- coredns 升级失败
- DNS 解析全部异常
- 集群大范围服务不可用

**根因**:
- Kyverno 策略要求 resources.limits
- coredns 升级模板未配 limits
- Webhook 拒绝,升级卡住

**修复**:
1. 紧急给 coredns 加 limits
2. 修复 Kyverno 策略,排除 kube-system
3. 加监控:Webhook 拒绝告警

**经验**:Webhook 必须排除系统命名空间。

### 案例 2:OPA 策略语法错全集群不可用

**故障时间**:2023-12-20

**故障现象**:
- 所有 Pod 创建失败
- 错误:webhook timeout

**根因**:
- OPA Rego 策略有语法错误
- 但通过 CI(测试不充分)
- 部署后 Rego 编译失败
- Webhook 持续超时

**修复**:
1. 紧急回滚策略
2. 加 Rego 单元测试
3. Staging 环境先验证

**经验**:策略变更必须 CI 测试 + Staging 验证。

### 案例 3:Cosign 验证阻塞紧急部署

**故障时间**:2024-02-25

**故障现象**:
- 紧急 hotfix 无法部署
- Cosign 验证失败(KMS 不可达)
- 业务中断 30 分钟

**根因**:
- KMS 服务故障
- Kyverno verifyImages 严格校验
- 无 fallback 机制

**修复**:
1. 紧急 KMS 恢复
2. 加 break-glass 机制(例外审批)
3. KMS 多区域备份

**经验**:严格策略必须有应急通道。

### 案例 4:vCluster 网络默认通导致隔离失败

**故障时间**:2024-05-10

**故障现象**:
- 多租户 vCluster 间流量互通
- 租户 A 能访问租户 B 的 Pod

**根因**:
- vCluster 默认共享底层网络
- 未配置 NetworkPolicy
- vCluster Pod 看到所有 Pod

**修复**:
1. 给每个 vCluster 独立 CIDR
2. 配置 NetworkPolicy 隔离
3. vCluster 同步策略到宿主集群

**经验**:vCluster 隔离不彻底,需配合网络策略。

### 案例 5:策略冲突导致资源创建失败

**故障时间**:2024-08-30

**故障现象**:
- Pod 创建失败
- 错误:多个 webhook 拒绝

**根因**:
- Kyverno 与 Gatekeeper 并存
- 两者策略冲突
- 一个允许另一个拒绝

**修复**:
1. 统一策略引擎(选 Kyverno)
2. 移除 Gatekeeper 重复策略
3. 策略清单集中管理

**经验**:多策略引擎需明确分工,避免冲突。
