# 06 - 存储

> 容器是无状态的,但业务有状态。K8s 用 PV / PVC / StorageClass / CSI 把存储抽象出来,让 Pod 与存储解耦。本章从 Volume 类型到 CSI 全流程,含生产级有状态应用模板。

## 2. 直觉解释

### 2.1 "仓库 vs 工位"类比

```
   ┌─────────────────────────────────────┐
   │  StorageClass(仓库类型)             │
   │  - ssd / hdd / nfs / oss            │
   └────────────┬────────────────────────┘
                │ 申请
                ▼
   ┌─────────────────────────────────────┐
   │  PV (Persistent Volume, 仓库)        │
   │  - 实际存储资源                       │
   └────────────┬────────────────────────┘
                │ 绑定
                ▼
   ┌─────────────────────────────────────┐
   │  PVC (Persistent Volume Claim, 工位) │
   │  - Pod 申请存储的"票据"              │
   └────────────┬────────────────────────┘
                │ 挂载
                ▼
   ┌─────────────────────────────────────┐
   │  Pod (业务容器)                      │
   │  mount /data → PVC → PV → 真实存储  │
   └─────────────────────────────────────┘
```

- **StorageClass**:仓库类型(SSD / HDD / NFS / OSS)
- **PV**:实际仓库(管理员创建,或 StorageClass 自动创建)
- **PVC**:申请单("我要 100GB SSD")
- **Pod**:使用方(把 PVC 挂载到容器路径)

### 2.2 为什么需要 PV / PVC 分离

```
传统方式:
  Pod → 直接挂 /dev/sdb1
  问题:Pod 删了,数据还在哪?换 Node 还能挂吗?容量怎么扩?

K8s 方式:
  Pod → PVC → PV → 实际存储
  优势:
   - Pod 与存储解耦(Pod 删了 PVC 还在,PV 还在)
   - 跨 Node 调度,数据自动跟随
   - 动态供给(申请即创建)
   - 容量管理(PVC 限容量)
```

## 3. 核心概念

### 3.1 Volume 类型(13 种)

#### 3.1.1 临时存储

| 类型 | 用途 | 生命周期 |
|------|------|---------|
| **emptyDir** | Pod 内共享数据,临时 | Pod 删除时清空 |
| **hostPath** | 挂载 Node 路径(慎用) | 与 Node 共存 |
| **configMap** | 配置注入 | 跟 ConfigMap 同步 |
| **secret** | 密钥注入 | 跟 Secret 同步 |
| **downwardAPI** | 元数据注入 | 跟 Pod 同步 |
| **projected** | 多源投射(整合上面几个) | 同上 |

#### 3.1.2 持久存储

| 类型 | 用途 |
|------|------|
| **persistentVolumeClaim** | 持久存储(主要方式) |
| **csi** | CSI 直接挂载(高级) |
| **nfs** | NFS 挂载 |
| **iscsi** | iSCSI 块存储 |
| **fc** | Fibre Channel |
| **cephfs / rbd / glusterfs** | 分布式存储 |

#### 3.1.3 云厂商特殊

| 类型 | 用途 |
|------|------|
| **awsElasticBlockStore** | AWS EBS(已废弃,用 CSI) |
| **gcePersistentDisk** | GCE PD(已废弃,用 CSI) |
| **azureDisk / azureFile** | Azure(已废弃,用 CSI) |
| **alicloud-disk** | 阿里云盘(已废弃,用 CSI) |

### 3.2 emptyDir 详解

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: app-with-emptydir
spec:
  containers:
  - name: app
    image: app
    volumeMounts:
    - name: data
      mountPath: /data
  - name: sidecar
    image: log-forwarder
    volumeMounts:
    - name: data
      mountPath: /logs
      readOnly: true
  volumes:
  - name: data
    emptyDir:
      sizeLimit: 1Gi           # 容量限制
      medium: Memory           # 用 tmpfs(内存),性能高但易丢
```

**用途**:
- Sidecar 共享数据
- 临时缓存
- 计算中间结果

**注意**:
- Pod 删除 → 数据丢失
- 默认在 Node 磁盘上,medium=Memory 时在内存(tmpfs)

### 3.3 hostPath 详解

```yaml
volumes:
- name: host-logs
  hostPath:
    path: /var/log/myapp
    type: DirectoryOrCreate    # 不存在则创建
```

**type 取值**:
- "":不校验
- Directory:必须存在且为目录
- DirectoryOrCreate:不存在则创建
- File:必须存在且为文件
- FileOrCreate:不存在则创建
- Socket / CharDevice / BlockDevice

**风险**:
- Pod 可访问 Node 文件系统 → 安全风险
- 调度到其他 Node 数据不一致
- **生产慎用**,仅 DaemonSet(节点级守护进程)用

### 3.4 PV / PVC / StorageClass

#### 3.4.1 PV(Persistent Volume)

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-ssd-100g-1
spec:
  capacity:
    storage: 100Gi
  accessModes:
  - ReadWriteOnce
  persistentVolumeReclaimPolicy: Retain    # 删 PVC 后 PV 保留
  storageClassName: ssd
  mountOptions:
  - hard
  - nfsvers=4.1
  csi:
    driver: disk.csi.azure.com
    volumeHandle: /subscriptions/xxx/resourceGroups/yyy/providers/Microsoft.Compute/disks/disk-1
    volumeAttributes:
      skuName: Premium_LRS
```

#### 3.4.2 accessModes(3 种)

| 模式 | 缩写 | 含义 |
|------|-----|------|
| ReadWriteOnce | RWO | 单 Node 读写 |
| ReadOnlyMany | ROX | 多 Node 只读 |
| ReadWriteMany | RWX | 多 Node 读写 |

**注意**:
- 块存储(EBS / 阿里云盘)仅 RWO
- 文件存储(NFS / CephFS / 阿里 NAS)支持 RWX
- RWX 适合多 Pod 共享(如 Web 服务器共享静态资源)

#### 3.4.3 PVC(Persistent Volume Claim)

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: pvc-data
  namespace: production
spec:
  accessModes:
  - ReadWriteOnce
  storageClassName: ssd
  resources:
    requests:
      storage: 100Gi
  selector:                    # 可选,匹配特定 PV
    matchLabels:
      tier: ssd
```

#### 3.4.4 StorageClass(动态供给)

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: ssd
provisioner: disk.csi.azure.com
parameters:
  skuName: Premium_LRS          # SSD
  cachingMode: ReadOnly
  kind: Managed
reclaimPolicy: Delete           # 删 PVC 自动删 PV + 真实存储
volumeBindingMode: WaitForFirstConsumer    # 延迟绑定(等 Pod 调度)
allowVolumeExpansion: true      # 允许扩容
mountOptions:
  - discard
```

#### 3.4.5 三者关系

```
   Pod (使用 PVC)
    │
    │ mount
    ▼
   PVC (申请单)
    │
    │ 1. 静态绑定:从已有 PV 中选
    │ 2. 动态供给:StorageClass 调用 provisioner 创建
    ▼
   PV (持久卷)
    │
    │ CSI / NFS / iSCSI
    ▼
   真实存储(EBS / 阿里云盘 / Ceph)
```

### 3.5 动态供给流程

```
   1. 用户创建 PVC(storageClassName=ssd)
   2. PVC Pending(等待绑定)
   3. StorageClass 的 provisioner(CSI Driver)Watch 到 PVC
   4. CSI Driver 调用云厂商 API 创建 EBS / 云盘
   5. CSI Driver 创建 PV(指向新创建的存储)
   6. PV 与 PVC 绑定
   7. Pod 调度,WaitForFirstConsumer 模式下等到 Pod 调度后才绑定
   8. kubelet 通过 CSI 挂载到 Pod
```

### 3.6 CSI(Container Storage Interface)

#### 3.6.1 为什么有 CSI

- K8s 早期:存储驱动 in-tree(在 K8s 源码里)
  - 问题:K8s 升级要带驱动,驱动 bug 阻塞 K8s 发版
  - 厂商繁多,代码膨胀
- K8s 1.13+:CSI out-of-tree,驱动独立发布
  - K8s 仅提供接口,厂商实现

#### 3.6.2 CSI 三大组件

```
   ┌──────────────────────────────────┐
   │    K8s (kubelet + ctrl-mgr)      │
   └────────────┬─────────────────────┘
                │ gRPC
                ▼
   ┌──────────────────────────────────┐
   │  CSI Driver (3 组件)              │
   │                                   │
   │  ┌─────────────────────────────┐ │
   │  │ Identity Service            │ │  ← 驱动信息
   │  │ - GetPluginInfo             │ │
   │  │ - GetPluginCapabilities     │ │
   │  └─────────────────────────────┘ │
   │                                   │
   │  ┌─────────────────────────────┐ │
   │  │ Controller Service          │ │  ← 控制平面
   │  │ - CreateVolume              │ │
   │  │ - DeleteVolume              │ │
   │  │ - ControllerPublishVolume   │ │  (Attach)
   │  │ - ControllerUnpublishVolume │ │  (Detach)
   │  │ - CreateSnapshot            │ │
   │  └─────────────────────────────┘ │
   │                                   │
   │  ┌─────────────────────────────┐ │
   │  │ Node Service                │ │  ← 数据平面
   │  │ - NodeStageVolume           │ │  (全局挂载)
   │  │ - NodePublishVolume         │ │  (Pod 挂载)
   │  │ - NodeUnpublishVolume       │ │
   │  │ - NodeUnstageVolume         │ │
   │  └─────────────────────────────┘ │
   └───────────────────────────────────┘
```

#### 3.6.3 CSI 工作流程

```
   1. 用户创建 PVC
   2. external-provisioner Watch 到 PVC
   3. 调用 CSI Controller.CreateVolume → 云厂商创建盘
   4. 创建 PV 关联到新盘
   5. PVC 与 PV 绑定
   6. Pod 调度到 Node-A
   7. kubelet 调用 CSI Node.NodeStageVolume(全局挂载到 /var/lib/kubelet/plugins/xxx/)
   8. kubelet 调用 CSI Node.NodePublishVolume(挂载到 Pod 路径)
   9. Pod 启动,可读写
   10. Pod 删除 → NodeUnpublishVolume → NodeUnstageVolume
   11. PVC 删除 → ControllerUnpublishVolume(Detach)→ DeleteVolume(删盘)
```

### 3.7 主流存储方案对比

| 类型 | 例子 | accessModes | 性能 | 成本 | 适合 |
|------|------|------------|------|------|------|
| 块存储 | EBS / 阿里云盘 / GCE PD | RWO | 高 IOPS | 中 | 数据库 / 单 Pod |
| 文件存储 | NFS / CephFS / 阿里 NAS | RWX | 中 | 低 | 共享文件 / Web |
| 对象存储 | S3 / OSS / GCS | N/A | 高吞吐 | 极低 | 备份 / 大文件 |
| 分布式块 | Portworx / Longhorn / Rook-Ceph | RWO/RWX | 中-高 | 中 | 自建存储 |
| 本地存储 | local-path / OpenEBS Local | RWO | 极高 | 低 | 高性能 / 临时 |

## 4. 操作流程与命令

### 4.1 创建动态供给 PVC

```bash
# 创建 PVC
kubectl apply -f - <<EOF
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: my-data
spec:
  accessModes: [ReadWriteOnce]
  storageClassName: ssd
  resources:
    requests:
      storage: 50Gi
EOF

# 查看 PVC 状态
kubectl get pvc my-data
# NAME      STATUS   VOLUME                CAPACITY   STORAGECLASS
# my-data   Bound    pvc-abc123            50Gi       ssd

# 查看 PV
kubectl get pv pvc-abc123
```

### 4.2 PVC 扩容

```bash
# 修改 PVC 大小
kubectl patch pvc my-data -p '{"spec":{"resources":{"requests":{"storage":"100Gi"}}}}'

# 查看(状态会变 Resizing → Bound)
kubectl get pvc my-data
```

**前提**:
- StorageClass `allowVolumeExpansion: true`
- 仅支持扩容,不支持缩容
- 块存储在线扩容(EBS / 云盘)

### 4.3 快照

```bash
# 创建 VolumeSnapshotClass
kubectl apply -f - <<EOF
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshotClass
metadata:
  name: ssd-snapshot
driver: disk.csi.azure.com
deletionPolicy: Delete
parameters:
  incremental: "true"      # 增量快照
EOF

# 创建快照
kubectl apply -f - <<EOF
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
metadata:
  name: my-data-snap-1
spec:
  volumeSnapshotClassName: ssd-snapshot
  source:
    persistentVolumeClaimName: my-data
EOF

# 查看快照
kubectl get volumesnapshot
kubectl get volumesnapshotcontent

# 从快照恢复
kubectl apply -f - <<EOF
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: my-data-restored
spec:
  accessModes: [ReadWriteOnce]
  storageClassName: ssd
  resources:
    requests:
      storage: 50Gi
  dataSource:
    name: my-data-snap-1
    kind: VolumeSnapshot
    apiGroup: snapshot.storage.k8s.io
EOF
```

## 5. 底层原理

### 5.1 PV 的状态机

```
   Available ──── PVC 绑定 ──→ Bound ──── PVC 删除 ──→ Released ──── reclaim ──→ Available/Delete
       │                                                           │
       └───────────────────────────────────────────────────────────┘
                             (Retain 策略,可手动回收)
```

**状态**:
- Available:可用,未绑定
- Bound:已绑定到 PVC
- Released:PVC 删了,PV 还在(数据保留)
- Failed:自动回收失败

**reclaimPolicy**:
- Retain:保留数据,手动清理(生产推荐)
- Delete:自动删 PV + 真实存储(开发 / 测试)
- Recycle(已废弃):清空数据(只剩 Retain / Delete)

### 5.2 StorageClass 的 volumeBindingMode

#### 5.2.1 Immediate(默认)

```
   1. PVC 创建 → 立即匹配 PV / 动态创建
   2. Pod 调度时,PV 已绑定
   3. 调度到 Node → 挂载
```

**问题**:
- 块存储(EBS)是 zone-specific,创建在 us-east-1a 的盘不能挂到 us-east-1b 的 Node
- 如果 Node 在 1b,PVC 已绑定 1a 的盘,Pod 调度失败

#### 5.2.2 WaitForFirstConsumer

```
   1. PVC 创建 → Pending(等 Pod)
   2. Pod 调度,选择 Node(在 us-east-1b)
   3. StorageClass 在 us-east-1b 创建 PV
   4. PVC 与 PV 绑定
   5. Pod 启动
```

**优势**:
- 拓扑约束,Pod 与 PV 同 zone
- 块存储场景必选

### 5.3 kubelet 挂载 Pod Volume 的完整流程

```
   1. kubelet syncPod 检测到新 Pod
   2. 计算 Pod 的 volumes
   3. 对每个 volume 调用 VolumeManager
   4. 对 CSI volume:
      a. kubelet 调用 CSI Node.NodeStageVolume
         - 全局挂载到 /var/lib/kubelet/plugins/kubernetes.io/csi/xxx/globalmount
      b. kubelet 调用 CSI Node.NodePublishVolume
         - 从全局挂载点 bind mount 到 Pod 路径
         - /var/lib/kubelet/pods/<pod-uid>/volumes/kubernetes.io~csi/xxx/mount
   5. 容器启动时,把 Pod 路径 bind mount 到容器 mount namespace
   6. 容器内可见 /data
```

### 5.4 CSI 三阶段挂载(Attach + Stage + Publish)

```
   ┌──────────────────────────────────────────────────┐
   │ 阶段 1: Attach(ControllerPublishVolume)         │
   │  - 由 CSI Controller 执行                        │
   │  - 把云盘挂到 Node(对 EBS,调用 EC2 AttachVolume) │
   │  - 在 Node 上看到 /dev/xvdf                      │
   └──────────────────────────────────────────────────┘
                            │
                            ▼
   ┌──────────────────────────────────────────────────┐
   │ 阶段 2: Stage(NodeStageVolume)                  │
   │  - 由 CSI Node 执行                              │
   │  - 格式化 /dev/xvdf → ext4                       │
   │  - 全局挂载到 /var/lib/kubelet/plugins/.../globalmount │
   │  - 一个 PV 一个 stage,多 Pod 共享                │
   └──────────────────────────────────────────────────┘
                            │
                            ▼
   ┌──────────────────────────────────────────────────┐
   │ 阶段 3: Publish(NodePublishVolume)               │
   │  - 由 CSI Node 执行                              │
   │  - bind mount 到 Pod 路径                        │
   │  - 每个 Pod 一份                                 │
   └──────────────────────────────────────────────────┘
```

## 6. 配置示例

### 6.1 生产级 StatefulSet + PVC(数据库)

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres
  namespace: production
spec:
  serviceName: postgres
  replicas: 3
  selector:
    matchLabels:
      app: postgres
  template:
    metadata:
      labels:
        app: postgres
    spec:
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
          - labelSelector:
              matchLabels:
                app: postgres
            topologyKey: kubernetes.io/hostname
      containers:
      - name: postgres
        image: postgres:16
        ports:
        - containerPort: 5432
        env:
        - name: POSTGRES_PASSWORD
          valueFrom:
            secretKeyRef:
              name: postgres-secret
              key: password
        volumeMounts:
        - name: data
          mountPath: /var/lib/postgresql/data
        - name: config
          mountPath: /etc/postgresql/postgresql.conf
          subPath: postgresql.conf
        resources:
          requests:
            cpu: 1000m
            memory: 2Gi
          limits:
            cpu: 2000m
            memory: 4Gi
  volumeClaimTemplates:
  - metadata:
      name: data
    spec:
      accessModes: [ReadWriteOnce]
      storageClassName: ssd
      resources:
        requests:
          storage: 200Gi
  - metadata:
      name: config
    spec:
      accessModes: [ReadWriteOnce]
      storageClassName: ssd
      resources:
        requests:
          storage: 1Gi
```

### 6.2 RWX 共享存储(NFS 替代)

```yaml
# StorageClass for CephFS(RWX)
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: cephfs
provisioner: cephfs.csi.ceph.com
parameters:
  clusterID: ceph-cluster-1
  fsName: cephfs
  pool: cephfs-data
  rootPath: /k8s
  csi.storage.k8s.io/provisioner-secret-name: ceph-secret
  csi.storage.k8s.io/provisioner-secret-namespace: kube-system
  csi.storage.k8s.io/node-stage-secret-name: ceph-secret
  csi.storage.k8s.io/node-stage-secret-namespace: kube-system
reclaimPolicy: Retain
allowVolumeExpansion: true
---
# PVC
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: shared-data
spec:
  accessModes: [ReadWriteMany]
  storageClassName: cephfs
  resources:
    requests:
      storage: 100Gi
```

### 6.3 本地存储(高性能)

```yaml
# StorageClass for local-path
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: local-path
provisioner: rancher.io/local-path
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer
---
# PVC
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: local-cache
spec:
  accessModes: [ReadWriteOnce]
  storageClassName: local-path
  resources:
    requests:
      storage: 500Gi
```

**适合**:
- 高性能数据库(TiDB / CockroachDB)
- 缓存(Redis / Aerospike)
- 临时大数据处理

**注意**:
- Pod 必须固定 Node(数据在 Node 上)
- Node 挂了,数据不可用(除非有副本)

### 6.4 对象存储挂载(oss/s3)

```yaml
# 用 OSS CSI Driver 把 OSS 挂载到 Pod
apiVersion: v1
kind: PersistentVolume
metadata:
  name: oss-pv
spec:
  capacity:
    storage: 5Ti
  accessModes: [ReadWriteMany]
  storageClassName: oss
  csi:
    driver: ossplugin.csi.alibaba.com
    volumeHandle: oss-pv
    volumeAttributes:
      bucket: my-bucket
      url: oss-cn-hangzhou.aliyuncs.com
      otherOpts: "-o max_stat_cache_size=0 -o allow_other"
    nodePublishSecretRef:
      name: oss-secret
      namespace: default
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: oss-pvc
spec:
  accessModes: [ReadWriteMany]
  storageClassName: oss
  resources:
    requests:
      storage: 5Ti
  volumeName: oss-pv
```

## 7. 常见陷阱与调优 ⚠️

### 7.1 PVC 陷阱

| 陷阱 | 现象 | 根因 | 解决 |
|------|------|------|------|
| **PVC 卡 Pending** | 一直 Bound 不了 | StorageClass 不存在 / 资源不足 / 配额满 | describe pvc 看 Events |
| **PVC 卡 Lost** | 状态 Lost | 关联 PV 被删 | 重建 PV 或删 PVC |
| **扩容失败** | Resizing 卡住 | StorageClass 未开 allowVolumeExpansion | 改 SC + 重新扩 |
| **跨 zone 失败** | Pod 调度失败 | Immediate 模式,PV 在别的 zone | WaitForFirstConsumer |

### 7.2 挂载陷阱

| 陷阱 | 现象 | 根因 | 解决 |
|------|------|------|------|
| **Pod 卡 ContainerCreating** | 挂载失败 | CSI Driver 异常 / 节点磁盘满 | 看 kubelet 日志 + CSI 日志 |
| **挂载点 stale** | Pod 启动失败 | 上次 Pod 没清理干净 | 重启 kubelet 或手动 umount |
| **权限错** | 应用读不到文件 | fsGroup 未设 / 权限 | 设 fsGroup 或 init container 改权限 |
| **subPath 误用** | 配置不更新 | subPath 是快照,不随 ConfigMap 更新 | 不用 subPath 或加 checksum |

### 7.3 性能陷阱

| 陷阱 | 现象 | 根因 | 解决 |
|------|------|------|------|
| **NFS 性能差** | 写入慢 | NFS 协议开销 + 网络延迟 | 用块存储 / 文件存储(NAS) |
| **云盘 IOPS 低** | 数据库慢 | 选了 HDD / 默认 IOPS | 选 SSD / Provisioned IOPS |
| **大文件读写慢** | 吞吐低 | 文件系统碎片 | 用块存储 + 直接 IO |
| **快照恢复慢** | 几小时 | 全量复制 | 用增量快照 |

### 7.4 数据安全陷阱

| 陷阱 | 现象 | 根因 | 解决 |
|------|------|------|------|
| **reclaimPolicy=Delete** | PVC 删了数据没了 | 默认配置 | 生产用 Retain |
| **StatefulSet 删了 PVC 残留** | 数据混乱 | 默认不删 PVC | retentionPolicy(1.27+) |
| **没有备份** | 数据丢失 | 仅靠 PV | 定期快照 + 异地备份 |
| **加密缺失** | 数据可被读 | 云盘未加密 | 启用云盘加密(KMS) |

## 11. 综合面试题

### 11.1 基础题

**Q1**: PV / PVC / StorageClass 三者关系?动态供给流程?

**答题要点**:
- PV:实际存储资源(管理员创建或动态生成)
- PVC:用户的存储申请单
- StorageClass:PV 类型 + 动态供给参数
- 流程:
  1. 用户创建 PVC(storageClassName=xxx)
  2. SC 的 provisioner(CSI)Watch 到
  3. CSI 调云 API 创建盘
  4. 创建 PV 关联盘
  5. PVC 与 PV 绑定

**Q2**: emptyDir / hostPath / PVC 区别,适用场景?

**答题要点**:
- emptyDir:Pod 内共享,Pod 删即失 → Sidecar 共享临时数据
- hostPath:Node 路径,Pod 跨 Node 数据不一致 → DaemonSet(节点级守护)
- PVC:持久化,跨 Pod 共享 → 数据库 / 有状态应用

### 11.2 进阶题

**Q3**: 块存储 vs 文件存储 vs 对象存储,在 K8s 里怎么选?

**答题要点**:
- 块存储(EBS / 云盘):
  - RWO,高 IOPS
  - 数据库 / 单 Pod 高性能
  - accessModes:ReadWriteOnce
- 文件存储(NFS / NAS / CephFS):
  - RWX,共享访问
  - Web 服务器静态资源 / 多 Pod 共享配置
  - accessModes:ReadWriteMany
- 对象存储(S3 / OSS):
  - 不挂载,API 访问
  - 备份 / 大文件 / 静态资源
  - 通过 oss-csi / s3-csi 挂载,但只读多

**Q4**: 一个 PVC 一直 Pending,怎么排查?

**答题要点**:
1. `kubectl describe pvc` 看 Events
2. 检查 storageClassName 是否存在:`kubectl get sc`
3. 检查 provisioner 是否运行:`kubectl get pods -n kube-system | grep csi`
4. 检查配额:`kubectl describe resourcequota -n <ns>`
5. 检查拓扑约束:WaitForFirstConsumer 模式下,要等 Pod 调度
6. 检查云配额(云盘数量 / 容量上限)
7. 看 CSI Controller 日志:`kubectl logs csi-controller-xxx`

**Q5**: StatefulSet 删了,数据还在吗?

**答题要点**:
- 默认 PVC 不删,数据保留(防止误删)
- 1.27+ 可配 `persistentVolumeClaimRetentionPolicy`:
  - whenDeleted: Delete / Retain(StatefulSet 删除时)
  - whenScaled: Retain(缩容时,数据保留)
- 生产建议:
  - 重要数据:Retain,手动清理
  - 测试 / 临时:Delete,自动清理

### 11.3 高级题

**Q6**: 设计一个 K8s 上的 MySQL 高可用方案,要求 RPO < 1min。

**答题要点**:
- 多副本 StatefulSet(3 副本:1 主 2 从)
- PV:云盘 SSD,跨 AZ
- 同步复制(MySQL Group Replication / MGR)
- Operator:Oracle MySQL Operator / Vitess / TiDB
- 备份:
  - 实时 binlog 同步到 S3
  - 每日全量快照
  - xtrabackup 增量
- 监控:复制延迟 / TPS / 慢查询
- 故障切换:
  - Operator 自动选主
  - VIP 切换(Service 注入)
  - 应用重连
- 演练:季度故障切换演练

**Q7**: 一个 Pod 卡 ContainerCreating,挂载相关,怎么排查?

**答题要点**:
1. `kubectl describe pod` 看 Events
2. 常见错误:
   - "Unable to attach or mount volumes":CSI Driver 异常
   - "volume not found":PV 被删
   - "mount failed":文件系统错 / 权限错
3. 在 Node 上排查:
   - `ssh node`
   - `lsblk`(看云盘是否挂上)
   - `mount | grep kubelet`(看挂载点)
   - `dmesg | tail`(内核错)
4. 看 CSI Node Pod 日志:
   - `kubectl logs csi-node-xxx -n kube-system`
5. 看 kubelet 日志:
   - `journalctl -u kubelet | grep <pod>`
6. 重启 CSI Node Pod 或 kubelet

### 11.4 设计题

**Q8**: 设计一个 K8s 集群的备份方案,覆盖 etcd / PV / 配置。

**答题要点**:
- **etcd 备份**:
  - 每日全量 snapshot
  - 每小时增量(wal)
  - 异地保存(S3 / OSS)
  - 定期恢复演练
- **PV 备份**:
  - VolumeSnapshot(每日)
  - 重要数据库:xtrabackup / pg_dump 到对象存储
  - 跨 region 复制
- **配置备份**:
  - GitOps(Argo CD),所有 YAML 在 Git
  - ConfigMap / Secret 定期导出(velero)
- **应用层**:
  - 数据库主从 / 多副本
  - 消息队列多副本
- **恢复**:
  - 工具:Velero(集群资源 + PV 一起备份)
  - RTO:1-4h(集群重建 + 数据恢复)
  - RPO:1h
- **演练**:
  - 季度灾难恢复演练
  - 模拟全集群丢失

## 12. 故障复盘

### 12.1 案例 1:PVC 跨 zone 调度失败

**业务影响**:2023 年某公司,Pod 创建后一直 Pending,因为 PVC 绑定的 PV 在另一个 zone。

**根因**:
- StorageClass 用 Immediate 模式
- PVC 创建时,云盘创建在 zone-a
- Pod 调度到 zone-b(因为 zone-b 资源够)
- 云盘不能跨 zone 挂载,Pod 卡 Pending

**修复过程**:
1. 删 PVC,改用 WaitForFirstConsumer
2. 重新创建 PVC,等 Pod 调度后才创建 PV
3. PV 与 Pod 在同 zone

**防范**:
- 块存储 StorageClass 必用 WaitForFirstConsumer
- 跨 zone 部署用 topology.kubernetes.io/zone 标签

### 12.2 案例 2:reclaimPolicy=Delete 导致数据丢失

**业务影响**:2022 年某公司,测试环境用 Delete 策略,误操作把生产 PVC 删了,数据全没。

**根因**:
- 测试 StorageClass 配 Delete(为了省钱)
- 生产误用同一个 StorageClass
- 删 PVC → PV + 真实云盘一起删
- 没有快照备份

**修复过程**:
1. 紧急:从应用层日志恢复部分数据
2. 创建新 PVC,从快照恢复(幸好前天有快照)
3. 损失 1 天数据

**防范**:
- 生产 StorageClass 必用 Retain
- 用 namespace + StorageClass 隔离
- 启用 PV 自动快照(每日)
- 关键数据额外备份到对象存储

### 12.3 案例 3:CSI Driver 升级导致挂载失败

**业务影响**:2024 年某公司,升级阿里云 disk-csi driver 后,新 Pod 挂载失败,持续 1 小时。

**根因**:
- CSI Driver 版本与 K8s 版本不兼容
- 旧 PV 用旧 CSI 创建,新 CSI 不识别
- 部分节点 CSI Node Pod 未更新

**修复过程**:
1. 紧急:回退 CSI Driver 版本
2. 修复后逐步升级(逐节点)
3. 验证:新 Pod + 旧 Pod 都能挂载

**防范**:
- 升级前查 CSI 兼容矩阵
- 测试环境先升级
- 升级期间停止滚动更新
- 监控 CSI Pod 健康度
