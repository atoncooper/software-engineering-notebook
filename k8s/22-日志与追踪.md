# 22. 日志与追踪

> 关键词:Fluent Bit、Loki、ELK、Jaeger、OpenTelemetry、LogQL、Tail-Based Sampling、结构化日志、日志保留、成本控制

------

## 22.1 问题定义与边界

### 22.1.1 解决什么

K8s 集群中每天产生海量日志与追踪数据:Pod stdout/stderr、容器内文件、APIServer audit、kubelet 事件、应用 trace。默认情况下这些数据 **分散在每个节点**,生命周期与 Pod 绑定,Pod 销毁即丢失。生产环境必须解决:

- **集中采集**:把分散在数千节点的日志/trace 汇聚到中心化存储
- **结构化**:从自由文本升级为可查询的字段(JSON、severity、trace_id)
- **关联**:日志 ↔ 指标 ↔ 追踪三方联动,通过 trace_id 跳转
- **采样**:在海量数据与成本之间权衡,关键错误全量保留、正常流量抽样
- **保留**:冷热分层、合规归档(SOX/等保要求 180 天以上)
- **多租户**:不同 BU 的日志隔离、配额、按需查询

### 22.1.2 不解决什么

- **指标采集**:由 Prometheus 负责(见 [21-监控与指标](./21-监控与指标.md))
- **Profile / 持续 profiling**:由 Pyroscope / Parca 负责
- **安全审计事件**:APIServer audit log 由集群运维层处理(见 [23-故障排查与诊断](./23-故障排查与诊断.md))
- **业务数据流水**:Kafka → 数仓的 ETL 不属于可观测性日志范畴

### 22.1.3 核心矛盾

```
数据量 vs 查询能力:5K 节点日均 50TB,无法全文索引
成本 vs 完整性:ES 全索引成本 5x 于 Loki
实时性 vs 采样率:Tail-Based Sampling 需缓冲,延迟升高
通用性 vs 厂商绑定:OpenTelemetry 标准化 vs 各家 SDK 优化
```

## 22.2 直觉解释

把日志与追踪系统想象成 **城市的监控与公安系统**:

| 城市系统 | K8s 可观测性 |
|---------|-------------|
| 摄像头(每个路口) | Fluent Bit DaemonSet(每个节点) |
| 视频流主干网 | 日志采集管道 |
| 视频存储中心 | Loki / ES 后端存储 |
| 视频检索(时间/地点) | LogQL / Lucene 查询 |
| 案件线索串联 | Trace Context(trace_id 跨服务) |
| 重点监控全量,普通抽样 | Tail-Based Sampling |
| 30 天录像覆盖 | 日志保留策略 |
| 不同辖区隔离 | 多租户日志隔离 |
| 视频压缩 H.264 | Loki chunk 压缩(10x) |

关键直觉:

1. **采集层**必须轻量(DaemonSet 资源占用 < 1% 节点 CPU)
2. **传输层**必须抗背压(批量、压缩、重试)
3. **存储层**必须分层(热 SSD / 温 HDD / 冷 S3)
4. **查询层**必须下推(避免把 TB 级数据拉到内存)
5. **关联层**必须标准化(W3C Trace Context)

## 22.3 核心概念与架构

### 22.3.1 K8s 容器日志机制

K8s 本身 **不提供** 日志采集能力,只定义了容器日志的 **输出接口**:

```
应用 → stdout/stderr
       ↓
容器运行时(containerd / CRI-O)接收
       ↓
写入 /var/log/pods/<ns>_<pod>_<uid>/<container>/<idx>.log
       ↓
软链 /var/log/containers/<pod>_<container>-<idx>.log → 上面那个文件
       ↓
kubelet 控制 log rotation(默认 10MB × 3 = 30MB / 容器)
       ↓
kubectl logs 直接读取这些文件
```

关键路径:

```
节点文件系统:
/var/log/pods/
├── kube-system_coredns-xxx_<uid>/
│   └── coredns/
│       ├── 0.log
│       └── 1.log
└── default_nginx-xxx_<uid>/
    └── nginx/
        └── 0.log

/var/log/containers/
├── coredns-xxx_<uid>-coredns-0.log → /var/log/pods/.../0.log
└── nginx-xxx_<uid>-nginx-0.log     → /var/log/pods/.../0.log
```

容器运行时配置(containerd):

```toml
# /etc/containerd/config.toml
[plugins."io.containerd.grpc.v1.cri"]
  # 日志目录,默认 /var/log/pods
  log_path_max_len = 256
  [plugins."io.containerd.grpc.v1.cri".containerd]
    # 单个日志文件最大,默认 10MB
    # 超过则轮转:0.log → 1.log,保留 N 个
    default_runtime_name = "runc"
```

**重要细节**:K8s 1.30 起,日志必须以 **JSON** 输出才能被结构化解析。`kubectl logs` 输出的是原始文本。

### 22.3.2 日志采集三种模式

```
模式 1:DaemonSet(节点级采集,推荐)
┌──────────────── Node ────────────────┐
│  Pod A   Pod B   Pod C   Pod D       │
│   ↓       ↓       ↓       ↓           │
│   └───────┴───────┴───────┘           │
│           ↓                           │
│      Fluent Bit DaemonSet             │
│           ↓                           │
│       /var/log/containers/*           │
└───────────────────────────────────────┘
优点:节点 1 个 agent,资源省
缺点:难以按 Pod 区分配额

模式 2:Sidecar(应用级采集)
┌─────────── Pod ────────────┐
│  ┌────────┐   ┌──────────┐ │
│  │ App    │ → │ Fluent   │ │
│  │ (file) │   │ Bit Side │ │
│  └────────┘   └──────────┘ │
└────────────────────────────┘
优点:Pod 级隔离、可读容器内文件
缺点:资源浪费(每 Pod 一个采集器)

模式 3:Frontend Ingestion(应用直推)
┌──────── Pod ────────┐
│  App → SDK → ────┐  │
└──────────────────┼──┘
                   ↓
            Loki / SLS / Kafka
优点:无 agent,延迟低
缺点:SDK 耦合,语言绑定
```

**选型决策树**:

| 场景 | 推荐 |
|------|------|
| 通用集群、节点数 < 5K | DaemonSet(Fluent Bit) |
| 多租户强隔离 | Sidecar + 配额 |
| 应用日志在文件(非 stdout) | Sidecar(读文件) |
| 高性能 / 低延迟 | Frontend Ingestion(直推) |
| 大厂自研平台 | 混合(DaemonSet + SDK 直推) |

### 22.4.5 Loki LogQL 实战

```bash
# 1. 基础查询:命名空间 default 的所有日志
{namespace="default"}

# 2. 多标签筛选
{namespace="default", app="nginx"}
{namespace="kube-system", container=~"corens|kube-proxy"}

# 3. 关键字过滤(类似 grep)
{namespace="default"} |= "error"
{namespace="default"} |~ "ERRO|WARN"   # 正则
{namespace="default"} != "debug"        # 排除

# 4. JSON 解析(提取字段)
{namespace="default"} | json
  | level="error"
  | status >= 500

# 5. Logfmt 解析
{namespace="default"} | logfmt
  | level="error"
  | duration > 1s

# 6. 提取正则字段
{namespace="default"} | regexp "(?P<ip>\\d+\\.\\d+\\.\\d+\\.\\d+).*"
  | ip="10.0.0.1"

# 7. 聚合统计:每分钟错误数
sum by (pod) (rate({namespace="default"} |= "error" [5m]))

# 8. TopK:错误最多的 10 个 Pod
topk(10, sum by (pod) (count_over_time({namespace="default"} |= "error" [1h])))

# 9. 关联 trace_id
{namespace="default"} | json | trace_id="abc123"
  # 在 Grafana 中点击 trace_id 跳转 Jaeger/Tempo

# 10. 复合查询
{namespace="default", app="api"} | json
  | level="error"
  | __error__ != "JSONParserErr"
  | line_format "{{.ts}} [{{.level}}] {{.msg}}"

# 11. 范围向量(用于告警)
sum by (namespace) (
  count_over_time({namespace="prod"} |= "panic" [5m])
) > 10

# 12. 偏移查询(对比昨天)
sum by (app) (count_over_time({namespace="default"}[1h] offset 1d))
```

## 22.5 底层原理

### 22.5.1 容器日志机制源码级剖析

**容器运行时(CRI)日志接口**:

```go
// kubernetes/cri-api/pkg/apis/runtime/v1/api.proto
service RuntimeService {
  // ContainerLogs returns stream of container logs
  rpc ContainerLogs(LogRequest) returns (stream LogResponse) {}
}

message LogRequest {
  string container_id = 1;
  bool tail = 2;
  int64 tail_lines = 3;
  bool follow = 4;
  int64 since_seconds = 5;
  google.protobuf.Timestamp since = 6;
}
```

**kubelet 实现**(`pkg/kubelet/kuberuntime/kuberuntime_manager.go`):

```go
func (m *kubeGenericRuntimeManager) GetContainerLogs(...) error {
  // 1. 调用 CRI ContainerLogs
  // 2. CRI shim 读取 /var/log/pods/.../<idx>.log
  // 3. 返回流式数据
  return m.runtimeService.GetContainerLogs(...)
}
```

**containerd 实现**(`containerd/pkg/cri/store/container/log.go`):

```go
// ReadLog reads log file with rotation awareness
func ReadLog(path string) (io.ReadCloser, error) {
  // 1. 打开 /var/log/pods/<ns>_<pod>_<uid>/<container>/<idx>.log
  // 2. 处理 symlink(/var/log/containers/ → /var/log/pods/)
  // 3. 处理轮转(当前文件 + 历史文件)
  // 4. 处理压缩(老文件可能 gzip)
}
```

**日志格式**:K8s 1.30 默认要求 **每行一条** JSON(如果是结构化日志)。但容器运行时不强制解析,只把 stdout 字节流写入文件。

**日志轮转**:

```go
// containerd CRI 配置
// max_log_size = 10MB(单文件)
// max_log_files = 3(保留个数)
// 超过则轮转:0.log → 1.log → 2.log → 删除
```

### 22.5.2 Fluent Bit 插件链

Fluent Bit 是 **流水线式** 处理:Input → Parser → Filter → Output。

```
┌─────────────────────────────────────────────────────┐
│                  Fluent Bit Pipeline                │
├─────────────────────────────────────────────────────┤
│                                                     │
│  [INPUT] Tail                                       │
│    Path /var/log/containers/*.log                   │
│    Parser cri                                       │
│    Tag kube.*                                       │
│         │                                           │
│         ▼                                           │
│  [FILTER] Kubernetes                                │
│    把 Pod 元数据(namespace/pod/container/labels)   │
│    注入到 record                                    │
│         │                                           │
│         ▼                                           │
│  [FILTER] Lua(自定义处理)                          │
│    - 提取 trace_id                                  │
│    - 脱敏(密码/手机号)                            │
│    - 多行合并                                       │
│         │                                           │
│         ▼                                           │
│  [FILTER] Modify                                    │
│    删除无用字段(降低 cardinality)                  │
│         │                                           │
│         ▼                                           │
│  [OUTPUT] Loki                                      │
│    Label namespace, app, pod                        │
│    LineFormat json                                  │
│         │                                           │
│         ▼                                           │
│  [OUTPUT] Kafka(fallback)                           │
│    Topic logs-fallback                              │
│                                                     │
└─────────────────────────────────────────────────────┘
```

**关键插件**:

1. **Tail Input**:监听文件变化,记录位置(checksum DB)
2. **Kubernetes Filter**:调用 K8s API 获取 Pod 元数据(缓存)
3. **Lua Filter**:用 Lua 脚本自定义处理
4. **Output**:Loki / ES / Kafka / SLS / stdout

**Tail Input 的位置管理**:

```python
# 伪代码
positions_db = "/var/log/flb_position.db"

# 记录每个文件的偏移量
# 格式:文件路径 → inode + offset
{
  "/var/log/containers/nginx-xxx.log": {
    "inode": 12345,
    "offset": 65536
  }
}

# 重启后从断点续传
# 轮转文件(inode 变化)→ 重新从头读
```

### 22.5.3 Loki LogQL 原理

Loki 设计哲学:**仅索引 label,不索引内容**(与 ES 相反)。

```
ES 索引模型:
  - 所有字段建倒排索引
  - 查询快(直接命中)
  - 索引膨胀(1GB 日志 → 5GB 索引)
  - 成本高 5x

Loki 索引模型:
  - 只索引 label(stream identifier)
  - 内容(chunk)压缩存储,不索引
  - 查询时把 chunk 拉回内存 grep
  - 索引极小(1GB 日志 → 100MB 索引)
  - 成本低 5x
```

**Loki 存储结构**:

```
Stream = label set 唯一标识
  例如: {namespace="default", app="nginx", pod="nginx-abc"}

Chunk = Stream 内一段时间的数据块(默认 1MB 或 1h)
  ┌──────────────────────────────────┐
  │ Chunk                            │
  │  ├── Stream ID                   │
  │  ├── 时间范围 [minT, maxT]       │
  │  ├── Entries:                    │
  │  │   ts1: "log line 1"           │
  │  │   ts2: "log line 2"           │
  │  │   ...                         │
  │  └── 压缩(snappy/zstd)          │
  └──────────────────────────────────┘

存储分层:
  - 热数据:本地 SSD(cache)
  - 温数据:对象存储(S3/OSS)的 chunk
  - 索引:TSDB(Loki 3.0)+ 对象存储
```

**LogQL 评估流程**:

```
{namespace="default"} |= "error"
        ↓
1. 流选择器 {namespace="default"}:
   - 在索引中查找所有匹配的 stream
   - 返回 stream ID 列表
        ↓
2. 时间范围过滤:
   - 仅查询 [start, end] 内的 chunk
        ↓
3. 拉取 chunk:
   - 从 cache 或对象存储读取 chunk
   - 解压
        ↓
4. 行过滤 |= "error":
   - 在 chunk 内 grep
   - 返回匹配的行
        ↓
5. 返回结果
```

### 22.5.5 Tail-Based Sampling 详解

**Head-Based Sampling**(传统):

```
请求进入 → 立即决定是否采样(基于 trace_id 哈希)
  - 优点:无缓冲,延迟低
  - 缺点:无法基于结果采样(可能丢错误)
```

**Tail-Based Sampling**(OTel 推荐):

```
请求处理中 → 收集所有 span → 缓冲
                          ↓
请求结束 → 评估整个 trace:
  - 是否有 error?
  - 是否超过 X 秒?
  - 是否命中关键路径?
                          ↓
         决策:保留 / 丢弃
                          ↓
         保留的 trace → Exporter
         丢弃的 → 不发送

优点:
  - 100% 错误全保留
  - 慢请求全保留
  - 正常请求抽样
  - 显著降低存储成本(5-10x)

缺点:
  - 需要缓冲(10-30s)
  - 内存占用高
  - 实现复杂
```

**OTel Tail Sampling 策略**:

```yaml
processors:
  tail_sampling:
    decision_wait: 30s           # 缓冲 30s
    num_traces: 50000            # 内存缓冲 5w 条
    expected_new_traces_per_sec: 1000
    policies:
      # 1. 错误全保留
      - name: errors
        type: status_code
        status_code:
          status_codes: [ERROR]
      
      # 2. 慢请求全保留
      - name: slow
        type: latency
        latency:
          threshold_ms: 1000
      
      # 3. 关键服务全保留
      - name: critical-service
        type: string_attribute
        string_attribute:
          key: service.name
          values: [payment, checkout]
      
      # 4. 其余 1% 抽样
      - name: baseline
        type: probabilistic
        probabilistic:
          sampling_percentage: 1
```

### 22.5.6 W3C Trace Context

```
HTTP Header:
  traceparent: 00-{trace-id}-{parent-id}-{trace-flags}
  tracestate:  vendor-specific

示例:
  traceparent: 00-0af7651916cd43dd8448eb211c80319c-b7ad6b7169203331-01
                │  │                                │                │
                │  │                                │                └── flags(01 = sampled)
                │  │                                └── parent-id(16字节 hex)
                │  └── trace-id(32字节 hex)
                └── version

Baggage(跨服务传递业务上下文):
  baggage: userId=12345,tenant=acme,env=prod
```

**跨服务传播**:

```
User → Gateway → Service A → Service B → DB
  │        │          │          │
  │        │          │          └── 继承 trace-id,新 span-id
  │        │          └── 继承 trace-id,新 span-id  
  │        └── 创建 trace-id,自己是 root span
  └── HTTP Header 携带 traceparent

最终 Jaeger 看到一条完整 trace:
  Gateway (root)
    └── Service A
          ├── Service B
          │     └── DB query
          └── Cache lookup
```

```python
metric_reader = PeriodicExportingMetricReader(
    OTLPMetricExporter(endpoint="http://otel-collector.observability:4317"),
    export_interval_millis=10000,
)
meter_provider = MeterProvider(resource=resource, metric_readers=[metric_reader])
metrics.set_meter_provider(meter_provider)

# 4. Logs(OTel Logs)
logger_provider = LoggerProvider(resource=resource)
logger_provider.add_log_record_processor(
    BatchLogRecordProcessor(
        OTLPLogExporter(endpoint="http://otel-collector.observability:4317")
    )
)
set_logger_provider(logger_provider)
handler = LoggingHandler(level=logging.INFO)
logging.getLogger().addHandler(handler)
logging.getLogger().setLevel(logging.INFO)

# 5. 自动埋点 Flask + requests
app = Flask(__name__)
FlaskInstrumentor().instrument_app(app)
RequestsInstrumentor().instrument()

@app.route("/checkout/<order_id>")
def checkout(order_id):
    # 自动创建 span(由 FlaskInstrumentor)
    span = trace.get_current_span()
    span.set_attribute("order.id", order_id)
    span.set_attribute("user.id", request.args.get("user_id"))
    
    # 业务日志会自动带 trace_id
    logging.info("processing checkout", extra={
        "order_id": order_id,
    })
    
    # 调用下游(自动传播 trace context)
    import requests
    resp = requests.get(f"http://payment/charge?order={order_id}")
    
    if resp.status_code != 200:
        span.record_exception(Exception("payment failed"))
        span.set_status(trace.Status(trace.StatusCode.ERROR))
        logging.error("payment failed", extra={
            "order_id": order_id,
            "status": resp.status_code,
        })
        return {"error": "payment_failed"}, 500
    
    return {"status": "ok"}
```

## 22.7 常见陷阱与调优

### 22.7.1 日志体积爆炸

**现象**:5K 节点,日均日志 200TB,远超预期 50TB。

**根因**:
- 应用 debug 日志开到 INFO 以上
- Nginx access log 每请求一行
- 业务日志 + access log 重复
- 调试日志未关闭

**调优**:

```yaml
# 1. 应用日志级别 ConfigMap 控制
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-log-config
data:
  LOG_LEVEL: "info"            # 不是 debug
  LOG_ACCESS: "false"          # 关闭 access log
  LOG_SAMPLING: "100"          # 1/100 抽样

# 2. Fluent Bit 过滤
[FILTER]
    Name grep
    Match kube.*
    Regex log ^(?!.*DEBUG).*$  # 排除 DEBUG

# 3. 采样(Fluent Bit Lua)
# lua-sampling.lua
function sample(cb_tag, timestamp, record)
  if record["level"] == "DEBUG" then
    return -1, 0, 0            -- 丢弃
  end
  if record["level"] == "INFO" and math.random() < 0.5 then
    return -1, 0, 0            -- 50% 抽样 INFO
  end
  return 2, 0, 0               -- 保留
end
```

### 22.7.2 多行日志(Java Stack Trace)

**现象**:Java 异常栈被拆成多行,每行当独立日志,无法关联。

**根因**:Fluent Bit 默认按行读取,Java stack trace 多行被切断。

**调优**:

```ini
# Fluent Bit tail 多行配置
[INPUT]
    Name              tail
    Path              /var/log/containers/*.log
    Parser            cri
    Multiline         On
    Multiline.Parser  java,python

# parsers.conf
[MULTILINE_PARSER]
    Name          java
    Type          regex
    Flush_Timeout 5000
    Rule          "start_state" "/^\d{4}-\d{2}-\d{2}.*$/" "cont"
    Rule          "cont" "/^\s+(at|Caused by|\.\.\.).*$/" "cont"

[MULTILINE_PARSER]
    Name          python
    Type          regex
    Flush_Timeout 5000
    Rule          "start_state" "/^\d{4}-\d{2}-\d{2}.*$/" "cont"
    Rule          "cont" "/^\s+.*$/" "cont"
```

### 22.7.3 JSON 解析失败

**现象**:Loki 中日志显示原始文本,无法用 `| json` 提取字段。

**根因**:
- 应用日志未严格 JSON
- 日志中混入非 JSON 行(printf 调试输出)
- 容器运行时前缀(CRI 格式)未剥离

**调优**:

```ini
# Fluent Bit CRI parser 必须先剥离前缀
[PARSER]
    Name        cri
    Format      regex
    Regex       ^(?<time>[^ ]+) (?<stream>stdout|stderr) (?<logtag>[^ ]*) (?<message>.*)$
    Time_Key    time

# 然后 message 字段再过 JSON parser
[FILTER]
    Name parser
    Match kube.*
    Key_Name message
    Parser json
    Preserve_Key true
    Reserve_Data true

# 容忍解析失败
[FILTER]
    Name modify
    Match kube.*
    Condition Key_value_does_not_exist level
    Add level unknown
```

### 22.7.4 Loki 索引膨胀(Cardinality 爆炸)

**现象**:Loki 内存飙升,查询变慢,日志显示 "too many streams"。

**根因**:label cardinality 太高,例如把 `pod` 名(每 Pod 唯一)放进 label。

```
错误:label pod=<pod-name> → 5K 节点 × 30 Pod/节点 = 15w stream
正确:label app=<app-name> → 仅 100 个 app
```

**调优**:

```ini
# Fluent Bit 输出仅用低 cardinality label
[OUTPUT]
    Name   loki
    Match  kube.*
    Labels namespace=$kubernetes['namespace_name'], app=$kubernetes['labels']['app']
    # 不要:pod=$kubernetes['pod_name']
    # 不要:container_id, pod_uid 等
```

**Loki 限制**:

```yaml
limits_config:
  max_global_streams_per_user: 10000      # 单 tenant stream 上限
  max_label_names_per_series: 10          # label 数量上限
  max_label_value_length: 2048            # label 值长度
  label_name_length_limit: 100
  cardinality_limit: 100000               # stream 上限
```

### 22.7.5 采样策略不当

**现象**:Tail-Based Sampling 内存爆,或采样后丢关键错误。

**根因**:
- `num_traces` 设置过小,trace 提前淘汰
- `decision_wait` 过短,trace 不完整就决策
- 策略顺序不对,后面的策略看不到完整数据

**调优**:

```yaml
processors:
  tail_sampling:
    decision_wait: 60s                    # 高 QPS 建议 30-60s
    num_traces: 100000                    # = expected_new_traces_per_sec × decision_wait × 1.5
    expected_new_traces_per_sec: 2000
    
    # 策略按顺序评估,先匹配先生效
    policies:
    # 1. 错误优先
    - name: errors
      type: status_code
      status_code:
        status_codes: [ERROR]
    
    # 2. 慢 trace
    - name: slow
      type: latency
      latency:
        threshold_ms: 2000
    
    # 3. 关键服务全保留
    - name: critical
      type: string_attribute
      string_attribute:
        key: service.name
        values: [payment, auth]
    
    # 4. 其余抽样
    - name: baseline
      type: probabilistic
      probabilistic:
        sampling_percentage: 1
```

### 22.7.6 OTel Collector 背压

**现象**:应用发送 trace 失败,Collector 日志 `Exporter enqueue failed`。

**根因**:下游(Jaeger / Loki)慢,Collector 队列满,反过来挤压 receiver。

**调优**:

```yaml
# 1. 增大队列
exporters:
  otlp/jaeger:
    sending_queue:
      enabled: true
      queue_size: 50000           # 默认 10000
      num_consumers: 10           # 默认 4
    retry_on_failure:
      enabled: true
      max_elapsed_time: 600s

# 2. 内存限制(背压触发)
processors:
  memory_limiter:
    check_interval: 1s
    limit_mib: 1536
    spike_limit_mib: 256
    # 当内存超过 limit,拒绝接收(应用收到 503)

# 3. 横向扩容 Collector
# mode: daemonset → 每节点一个
# 或 mode: deployment + 多副本
```

### 22.7.7 Fluent Bit OOM

**现象**:Fluent Bit Pod OOMKilled,频繁重启。

**根因**:
- `Mem_Buf_Limit` 设置过大
- 多行日志缓冲过多
- K8s API 调用过频(Kubernetes Filter)

**调优**:

```ini
[INPUT]
    Name tail
    Mem_Buf_Limit 50MB           # 单 input 缓冲,不要 100MB+
   storage.type filesystem        # 大于 Mem_Buf_Limit 部分落盘
    storage.max_chunks_up 64      # 内存中 chunk 数

[FILTER]
    Name kubernetes
    Kube_CA_File /var/run/secrets/kubernetes.io/serviceaccount/ca.crt
    Kube_Token_File /var/run/secrets/kubernetes.io/serviceaccount/token
    Use_Kubelet On               # 走 kubelet 而非 API server
    Kubelet_Port 10250
    Buffer_Size 32k              # 默认 0(无限),改为 32k
    Cache_Use_DNS On
```

```yaml
# 资源请求/限制
resources:
  requests:
    cpu: 100m
    memory: 128Mi
  limits:
    cpu: 500m
    memory: 512Mi                # 给 2x buffer
```

### 22.7.8 Jaeger 查询慢

**现象**:Jaeger UI 查 trace 列表要 30s+,服务依赖图加载失败。

**根因**:
- ES 索引未优化(shard 太少)
- span 数据量太大,未做归档
- 没有预聚合

**调优**:

```yaml
# 1. ES 索引模板
PUT _index_template/jaeger
{
  "index_patterns": ["jaeger-span-*"],
  "template": {
    "settings": {
      "number_of_shards": 10,        # 按 QPS 调整
      "number_of_replicas": 1,
      "refresh_interval": "10s",     # 降低刷新频率
      "index.query.default_field": [
        "traceID", "operationName", "serviceName", "tags.tag", "process.tags.tag"
      ]
    }
  }
}

# 2. Jaeger 配置归档(hot/warm)
storage:
  type: elasticsearch
  options:
    es:
      server-urls: http://es-hot:9200
      archive:
        enabled: true
        server-urls: http://es-warm:9200
        num-shards: 5

# 3. Spark 依赖分析(预聚合)
spark:
  enabled: true
  schedule: "0 2 * * *"
```

### 22.7.9 日志保留策略

**现象**:日志 6 个月后磁盘爆,无法查询历史。

**方案**:冷热分层 + 对象存储归档。

```yaml
# Loki 保留
loki:
  config:
    limits_config:
      retention_period: 720h          # 30 天热数据
    compactor:
      retention_enabled: true
      # 不同 tenant 不同保留
    compactor.retention_delete_mode: whole-stream-deletion
  
  # 对象存储分层(自动)
  storage_config:
    aws:
      s3: s3://loki-bucket
      region: us-east-1
    # 老数据自动迁移到 S3 IA / Glacier

# Jaeger 归档
jaeger:
  storage:
    type: elasticsearch
    options:
      es:
        archive:
          enabled: true               # 归档到 warm ES
```

```
   └─────── trace_id / log ─────────────┘
                │
                ▼
            Grafana 统一 UI
            (关联跳转)
```

**三者分工**:
- **指标**:聚合数字(CPU、QPS、错误率),用于告警

**关联**:

## 22.10 面试速答

**Q1: K8s 容器日志存在哪里?**

容器 stdout/stderr 由运行时写入 `/var/log/pods/<ns>_<pod>_<uid>/<container>/<idx>.log`,软链到 `/var/log/containers/`。kubelet 控制轮转(默认 10MB×3)。`kubectl logs` 读这些文件。

**Q2: 日志采集三种模式?**

DaemonSet(节点级,通用)、Sidecar(Pod 级,强隔离)、Frontend Ingestion(应用直推,高性能)。生产 5K 节点推荐 DaemonSet(Fluent Bit),资源占用低。

**Q3: Loki 与 ES 区别?**

Loki 仅索引 label(流标识),内容压缩存储不索引;ES 全文倒排索引。Loki 成本低 5-10x,但全文搜索弱;适合 K8s 日志场景。ES 适合复杂全文检索。

**Q4: Tail-Based Sampling 与 Head-Based Sampling?**

Head-Based 在请求入口决策(基于 trace_id 哈希),无法基于结果采样;Tail-Based 在 trace 完成后决策,可保留所有错误、慢请求,正常抽样。OTel 推荐 Tail-Based。

**Q5: W3C Trace Context 是什么?**

跨服务传播 trace 的标准 HTTP Header(`traceparent`),包含 trace-id、parent-id、flags。所有服务遵循同一标准,实现跨语言、跨进程链路。

**Q6: 日志 cardinality 爆炸是什么?**

Loki label 中含高基数字段(如 pod 名、user_id),导致 stream 数爆炸,内存与索引膨胀。解决:label 只用低基数字段(namespace、app)。

**Q7: Fluent Bit OOM 怎么排查?**

1. 检查 Mem_Buf_Limit 是否过大
2. 多行日志缓冲是否过多
3. K8s Filter 是否调 API 过频(改用 Kubelet)
4. 增加 storage.type filesystem 落盘
5. 调大 limits.memory(给 2x buffer)

**Q8: OTel Collector 背压怎么处理?**

1. 增大 sending_queue.queue_size
2. 启用 memory_limiter processor(超限拒绝)
3. 横向扩容 Collector(daemonset 或多副本)
4. 调优下游(Jaeger / Loki)

**Q9: 日志保留怎么做?**

Loki:`retention_period` + compactor;冷数据迁移 S3 IA/Glacier;Jaeger:archive 索引到 warm ES;合规保留:90/180/365 天按需配置。

**Q10: Loki LogQL 与 PromQL 区别?**

LogQL 借鉴 PromQL 语法但面向日志:流选择器 `{label="value"}` + 行过滤 `|= "error"` + 解析 `| json` + 聚合 `rate() / sum()`。PromQL 是数值时序,LogQL 是文本流。

**Q11: 应用日志为什么要 JSON?**

JSON 可结构化查询(`| json | level="error" | status >= 500`),非 JSON 只能 grep。生产强制 JSON,字段标准化(severity、ts、msg、trace_id)。

**Q12: Jaeger 查询慢怎么办?**

1. ES shard 调整(QPS 高则多 shard)
2. 启用归档(hot/warm)
3. Spark 依赖分析预聚合
4. 限制查询时间范围(7 天内)
5. 引入 ClickHouse 替代 ES

**Q13: 日志成本怎么控制?**

1. DEBUG 过滤
2. access log 抽样
3. Loki 压缩(zstd,10x)
4. 冷数据 S3 归档
5. Trace Tail Sampling 1%
6. 综合可降 80%

**Q14: 多行日志怎么处理?**

Fluent Bit 启用 Multiline + 自定义 parser(Java stack trace、Python traceback)。`Flush_Timeout 5000` 防止缓冲过久。

**Q15: Trace 与日志怎么关联?**

应用日志注入 `trace_id` 字段(从 OTel SDK 获取);Loki 查询时 `| json | trace_id="xxx"`;Grafana 配置 derivedFields,点击 trace_id 跳转 Jaeger。

### 题 5:解释 Tail-Based Sampling 工作原理

```
传统采样问题:
  - Head-Based(入口决策)无法基于结果采样
  - 错误请求可能被丢弃
  - 慢请求可能被丢弃

Tail-Based Sampling:

1. 数据结构:
   - Collector 维护 trace_id → span[] 缓存
   - 缓存大小:num_traces(默认 50000)
   - 缓存时间:decision_wait(默认 30s)

2. 工作流程:
   a. Span 到达 receiver
   b. 按 trace_id 聚合到缓存
   c. 等待 decision_wait(让 trace 收集完整)
   d. 评估策略链:
      - status_code: 有 ERROR → 保留
      - latency: > 1s → 保留
      - string_attribute: service.name in [payment] → 保留
      - probabilistic: 5% 抽样
   e. 命中任一策略 → 保留整个 trace
   f. 未命中 → 丢弃

3. 策略组合:
   policies:
   - errors         (优先级 1,错误全保留)
   - slow           (优先级 2,慢全保留)
   - critical       (优先级 3,关键服务全保留)
   - probabilistic  (兜底,1% 抽样)
   
   OR 关系:任一策略命中即保留

4. 内存与性能:
   - num_traces × 平均 trace 大小(1KB) = 50MB
   - 决策延迟:decision_wait + 处理时间
   - QPS:expected_new_traces_per_sec

5. 边界情况:
   - trace 跨多个 Collector:用 OTel Collector Gateway 集中决策
   - trace 超过 num_traces:LRU 淘汰,可能提前决策
   - trace 不完整(span 丢失):基于现有 span 决策

6. 监控:
   - otelcol_processor_tail_sampling_count_traces_sampled
   - otelcol_processor_tail_sampling_count_traces_not_sampled
   - 各策略命中率
```

### 题 7:K8s 日志机制与轮转细节

```
K8s 容器日志生命周期:

1. 应用 stdout/stderr 输出
2. 容器运行时(CRI)接收:
   - containerd: 通过 CRI shim
   - CRI-O: 直接处理
3. 写入文件:
   /var/log/pods/<ns>_<pod>_<uid>/<container>/<idx>.log
   符号链接:
   /var/log/containers/<pod>_<container>-<idx>.log → 上面

4. 轮转策略(containerd 默认):
   - max_log_size: 10MB
   - max_log_files: 3
   - 总上限:30MB / 容器
   - 超过则 0.log → 1.log → 2.log → 删除

5. kubectl logs 读取:
   - 调用 CRI ContainerLogs
   - CRI shim 读文件,流式返回
   - --since / --tail 等参数过滤

6. Pod 销毁后:
   - 日志文件保留(默认)
   - 但 K8s 不会清理,需运行时 GC
   - containerd: gc 老日志
   
7. 关键参数:
   containerd config:
   [plugins."io.containerd.grpc.v1.cri"]
     log_path_max_len = 256
   
   kubelet:
   --container-log-max-files=5      # 默认 5
   --container-log-max-size="100Mi" # 默认 100Mi

8. 调优建议:
   - 高日志量应用:调大 max-size(500MB)
   - 日志保留:Fluent Bit 持续采集,文件轮转无影响
   - 磁盘:节点 /var/log 单独挂盘(SSD)
   - 监控:节点日志盘水位
```

**故障现象**:
- Grafana 查询 Loki 全部超时
- Loki querier 内存 95%
- 持续 30 分钟无法恢复

**根因**:
1. 用户查询 30 天范围 + 全 namespace
   ```
   {namespace=~".+"} |= "error" [30d]
   ```
2. 匹配 50w stream
3. 拉取 50TB chunk 到内存
4. querier OOM,级联崩溃
5. query_frontend 未做防护

**修复**:
1. 紧急:重启 Loki querier
2. 配置硬限制:
   ```yaml
   limits_config:
     max_query_series: 1000
     max_query_length: 721h        # 30 天
     max_query_range: 24h          # 默认 24 小时
     split_queries_by_interval: 15m
     max_streams_match_per_query: 1000
   ```
3. Grafana 数据源配置:
   - maxLines: 5000
   - default range: 1h
4. 培训用户:
   - 缩小 namespace / app 范围
   - 时间范围 ≤ 7 天
5. 长期:引入 ClickHouse 处理大范围分析

**经验**:Loki 必须配置查询硬限制;UI 默认查询范围要小;用户教育是关键。

### 案例 3:OTel Collector 背压导致应用阻塞

**故障时间**:2024-10-08

**故障现象**:
- 业务应用 P99 延迟从 100ms 飙到 5s
- 应用日志报 "OTLP export timeout"
- OTel Collector 重启循环

**根因**:
1. Jaeger Collector ES 索引慢
2. OTel Collector exporter 队列满(10000)
3. memory_limiter 触发,拒绝接收
4. 应用 SDK 重试,占用业务线程
5. 业务请求被 trace 上报阻塞

**修复**:
1. 紧急:关闭应用 trace 上报(临时)
2. Collector 调优:
   - sending_queue.queue_size: 50000
   - memory_limiter.limit_mib: 4096
   - retry max_elapsed_time: 60s(避免长阻塞)
3. 应用 SDK 调优:
   - 导出超时 5s
   - 失败丢弃(不重试)
   - 异步队列
4. Jaeger 优化:
   - ES shard 调整
   - 归档分离
5. 多级架构:
   - App → Agent → Gateway → Backend
   - Gateway 层 Kafka 死信

**经验**:trace 上报不能阻塞业务;必须异步 + 超时;多级架构隔离故障。

### 案例 4:Jaeger 依赖图卡死

**故障时间**:2024-11-30

**故障现象**:
- Jaeger UI 服务依赖图加载失败
- 查询 trace 列表 30s+
- Jaeger collector CPU 100%

**根因**:
1. 微服务数 2000+,服务依赖关系复杂
2. Spark 依赖分析任务失败(数据量太大)
3. Jaeger 直接查 ES 计算依赖,耗尽资源
4. ES 慢查询拖累 Jaeger

**修复**:
1. 紧急:关闭依赖图功能
2. Spark 任务调优:
   - 增大 executor 内存
   - 分批处理(按天)
3. Jaeger collector 扩容(3 → 10 副本)
4. ES 优化:
   - 索引模板调整
   - shard 数 5 → 20
5. 长期:引入 ClickHouse 替代 ES

**经验**:大规模 trace 后端不能用 ES(分析弱);Spark 依赖分析必须定期跑;依赖图应预计算。

### 案例 5:Loki cardinality 爆炸

**故障时间**:2025-01-12

**故障现象**:
- Loki ingester 内存 90%
- 日志 "too many streams"
- 日志延迟 1 小时

**根因**:
1. Fluent Bit 配置错误:label 含 pod 名
   ```
   Labels pod=$kubernetes['pod_name']
   ```
2. 每次 Pod 重建(滚动更新),生成新 stream
3. 5K 节点 × 30 Pod/节点 = 15w stream
4. ingester 内存爆炸

**修复**:
1. 紧急:删除错误配置,重启 Fluent Bit
2. Loki 清理:
   - 删除过期 stream
   - compact 重写索引
3. label 规范:
   - 仅低 cardinality:namespace、app、version
   - 禁止:pod、container_id、uid
4. 监控:stream 数 > 10w 告警
5. 限制:
   ```yaml
   max_global_streams_per_user: 10000
   max_label_names_per_series: 10
   ```

**经验**:Loki label 设计必须严格控制 cardinality;配置需 review;监控 stream 数。

### 案例 6:Tail Sampling 内存爆

**故障时间**:2025-02-20

**故障现象**:
- OTel Collector OOMKilled
- 重启循环
- trace 部分丢失

**根因**:
1. QPS 从 1K/s 涨到 5K/s
2. tail_sampling.num_traces = 50000
3. decision_wait = 30s
4. 实际需要:5K × 30 = 150K trace 缓存
5. 50K 不够,LRU 淘汰,trace 提前决策(可能丢关键)
6. 内存:50K × 5KB = 250MB,接近 limit

**修复**:
1. 调整:
   - num_traces: 50000 → 200000
   - expected_new_traces_per_sec: 5000
   - decision_wait: 30s → 60s
2. 资源:
   - memory_limiter.limit_mib: 4096
3. 横向扩容:
   - daemonset → deployment(5 副本)
4. 降低流量:
   - probabilistic: 5% → 1%
5. 监控:
   - tail_sampling 内存使用
   - trace 淘汰率

**经验**:tail_sampling 容量需根据 QPS 调整;监控 LRU 淘汰率;必要时分片。
