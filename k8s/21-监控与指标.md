# 21. 监控与指标

> 关键词:Prometheus、Grafana、metrics-server、kube-state-metrics、cAdvisor、node-exporter、PromQL、Prometheus Operator、ServiceMonitor、PodMonitor、黄金信号、SLI/SLO/SLA、Thanos、Cortex、Mimir、VictoriaMetrics、告警分级、TSDB、High Cardinality

------

## 21.1 问题定义与边界

K8s 集群一旦上规模(几百节点、上万 Pod),运维面临一连串问题:

- 节点 CPU/内存使用率是多少?哪个节点最先饱和?
- Pod 的 OOM、CrashLoopBackOff 发生频率?
- HPA 没有 metrics 就不工作,metrics 从哪来?
- kube-apiserver 的 P99 延迟是多少?etcd 是否健康?
- 集群中有多少 Deployment 副本数不达标?多少 Pod 处于 Pending?
- 滚动更新时延迟是否飙升?错误率是否上升?
- 告警应该怎么配才能既不漏报也不风暴?

**K8s 监控栈要解决**:

> 用 **多源指标采集 + 时序存储 + 统一查询语言 + 可视化 + 告警** 的方式,把集群和应用的运行状态变成可量化、可告警、可追溯的时序数据,支撑 SRE 的 **测量 → 告警 → 排障 → 容量规划** 闭环。

**解决**:

- 集群节点资源使用率(CPU/内存/磁盘/网络)
- Pod 资源使用率(用于 HPA/VPA)
- K8s 控制面健康(apiserver/etcd/scheduler/controller-manager)
- K8s 对象状态(Deployment 副本数、Pod Phase、Node Condition)
- 应用业务指标(QPS、延迟、错误率)
- 指标查询语言(PromQL)
- 可视化仪表盘(Grafana)
- 告警规则与通知(Alertmanager)

**不解决**:

- **日志聚合** → 见 [22-日志与追踪](./22-日志与追踪.md)(Loki/ELK/Fluent Bit)
- **分布式追踪** → 见 [22-日志与追踪](./22-日志与追踪.md)(Jaeger/OpenTelemetry)
- **链路性能剖析** → Pyroscope/Parca(持续性能剖析)
- **业务事件流** → Kafka(指标是聚合数据,事件是个体记录)
- **安全审计** → APIServer Audit Log(见 [17-RBAC与认证授权](./17-RBAC与认证授权.md))
- **成本核算** → Kubecost/OpenCost(见 [30-成本与容量规划](./30-成本与容量规划.md))

**与 22 章的边界**:

| 维度 | 21 监控与指标 | 22 日志与追踪 |
|------|---------------|----------------|
| 数据模型 | 时序数值(name + labels + timestamp + value) | 文本日志 / span |
| 数据量 | 单集群 GB/天 ~ TB/天 | 单集群 TB/天 ~ PB/天 |
| 查询 | PromQL 聚合 | 全文检索 / trace ID |
| 用途 | 告警、容量、SLO | 排障、审计、追踪 |
| 工具 | Prometheus / Grafana | Loki / ELK / Jaeger |

## 21.2 直觉解释

把 K8s 监控想象成 **医院的监护系统**:

| 医院 | K8s 监控 |
|------|----------|
| 体温/血压/心率传感器 | cAdvisor / node-exporter / kubelet metrics |
| 病房汇总板 | kube-state-metrics(对象状态) |
| 检验科报告 | metrics-server(资源使用率聚合) |
| 病历库 | Prometheus TSDB(时序存储) |
| 医生查体 | PromQL 查询 |
| 监护大屏 | Grafana Dashboard |
| 报警器 | Alertmanager |
| 病情分级(危/重/轻) | P0/P1/P2/P3 告警分级 |
| 主任查房 | SRE oncall 巡检 |
| 年度体检报告 | SLO 月报 / 容量规划报告 |

关键直觉:

1. **指标不是日志**:指标是聚合数值(每秒 QPS、P99 延迟),日志是个体事件(这条请求失败了)。指标用于告警和趋势,日志用于根因。
2. **Pull 模型是主流**:Prometheus 主动去抓(push vs pull 的争论已有结论,云原生生态选 pull)。
3. **标签 (labels) 是灵魂**:`http_requests_total{method="POST",code="500",path="/api/v1/order"}` 比 `http_requests_total` 单值有用 100 倍。但 label 基数失控会爆 TSDB。
4. **4 种指标类型分工**:counter(只增不减,如请求总数)、gauge(可增可减,如当前内存)、histogram(分桶,算分位数)、summary(客户端算分位数,不可聚合)。
5. **黄金信号 4 件套**:延迟(latency)、流量(traffic)、错误(errors)、饱和度(saturation)。任何服务监控这 4 个就够 80% 场景。
6. **metrics-server ≠ Prometheus**:metrics-server 只给 K8s 内部用(HPA/VPA/kubectl top),不存历史,不暴露 PromQL;Prometheus 是通用监控,存历史,有 PromQL。两者各司其职。
7. **告警要分级**:P0(立即响应,电话叫醒)→ P1(1 小时响应)→ P2(工作日响应)→ P3(周报)。

**Pull vs Push 对比**:

| 维度 | Pull(Prometheus) | Push(Datadog/StatsD/InfluxDB Telegraf) |
|------|-------------------|------------------------------------------|
| 谁主动 | 服务端拉 | 客户端推 |
| 服务发现 | 服务端知道所有目标 | 客户端自注册 |
| 故障隔离 | 客户端挂了,服务端发现抓不到 | 客户端挂了,没人推 |
| 多租户 | 难(服务端要主动巡检) | 易(网关收 push) |
| 安全 | 服务端拉,需客户端暴露 | 客户端推,需鉴权 |
| 云原生主流 | 是,Prometheus 系 | 商业 SaaS |

### 21.3.3 4 种指标类型

| 类型 | 特性 | 例子 | PromQL 函数 |
|------|------|------|-------------|
| **Counter** | 只增不减(重启归零) | http_requests_total、bytes_sent_total | `rate()`、`increase()`、`irate()` |
| **Gauge** | 可增可减 | memory_usage_bytes、cpu_usage、queue_length | 直接查、`deriv()`、`predict_linear()` |
| **Histogram** | 分桶 + sum + count | http_request_duration_seconds_bucket | `histogram_quantile()`、`rate(_bucket[5m])` |
| **Summary** | 客户端预聚合分位数 | http_request_duration_seconds{quantile="0.99"} | 不可跨实例聚合 |

**Histogram vs Summary**:

```
Histogram(推荐):
  - 客户端只分桶,_bucket{le="0.1"}、_bucket{le="0.5"}、_bucket{le="+Inf"}
  - 服务端用 histogram_quantile(0.99, rate(bucket[5m])) 算分位数
  - 可跨实例聚合(多个 Pod 的桶可加)
  - 桶定义影响精度(预定义 le 边界)

Summary(不推荐):
  - 客户端算好分位数,{quantile="0.99"}
  - 不可跨实例聚合(不同 Pod 的 P99 不能直接平均)
  - 客户端开销大(流式分位数算法)
  - 灵活度低(分位数在客户端固定)
```

**生产建议**:用 Histogram,不用 Summary。所有主流 client library 都支持。

### 21.3.4 4 个核心组件职责区分

| 组件 | 部署形态 | 数据来源 | 暴露方式 | 用途 | 是否存历史 |
|------|----------|----------|----------|------|-----------|
| **metrics-server** | Deployment(2 副本) | kubelet `/metrics/resource` | K8s Aggregated API `metrics.k8s.io` | HPA/VPA/kubectl top | 否,仅当前值 |
| **kube-state-metrics** | Deployment(可多副本) | kube-apiserver(List-Watch) | HTTP `/metrics`(Prometheus 格式) | K8s 对象状态(Deployment/Pod/Node 副本数、状态) | 否,仅当前值 |
| **cAdvisor** | kubelet 内置 | 内核 cgroup | kubelet `/metrics/cadvisor` | Pod/容器 CPU/内存/网络/磁盘 IO | 否(由 Prometheus 存) |
| **node-exporter** | DaemonSet | 内核 `/proc`、`/sys` | HTTP `/metrics` | 节点 CPU/内存/磁盘/网络/文件系统 | 否(由 Prometheus 存) |

**关键区别**:

```
metrics-server:
  - 给 K8s 内部用(HPA/VPA/scheduler)
  - 不暴露 /metrics,只暴露 metrics.k8s.io API
  - 数据从 kubelet 拉,聚合后供 kubectl top 用
  - 不存历史,Prometheus 拿不到(除非用 prometheus adapter 转换)

kube-state-metrics:
  - 给 Prometheus 用
  - 不采集资源使用率,只看 K8s 对象状态
  - 例如:kube_pod_status_phase、kube_deployment_status_replicas
  - 不存历史,自己只是"翻译官",把 K8s API 翻成 Prometheus 格式

cAdvisor:
  - 由 kubelet 内置(不需要单独部署)
  - 采集 Pod/容器 级 CPU/内存/网络/磁盘
  - 暴露在 kubelet 的 /metrics/cadvisor 路径
  - 容器视角

node-exporter:
  - DaemonSet 部署(每节点一个)
  - 采集节点级 CPU/内存/磁盘/网络/文件系统
  - 暴露 /metrics
  - 节点视角(不是 Pod)
```

### 21.3.5 Prometheus Operator CRD 全景

```
Prometheus Operator:用 K8s 声明式 API 管理 Prometheus 栈

CRD 列表:
  1. Prometheus         - 定义一个 Prometheus 实例(副本数、存储、retention)
  2. Alertmanager       - 定义一个 Alertmanager 实例
  3. ServiceMonitor     - 定义监控一个 Service(通过 Service 选 Pod)
  4. PodMonitor         - 定义监控一组 Pod(直接选 Pod,不经 Service)
  5. Probe              - 定义黑盒监控(外部 URL/服务,blackbox exporter)
  6. PrometheusRule     - 定义告警规则/记录规则
  7. AlertmanagerConfig - 定义告警路由(命名空间级)
  8. ThanosRuler        - 定义 Thanos Ruler 实例
  9. Receiver           - 告警接收器(用于 AMP)

工作流:
  1. 用户创建 ServiceMonitor/PodMonitor
  2. Operator 监听这些 CR
  3. Operator 生成 Prometheus 配置(scrape_configs)
  4. 调用 Prometheus API reload
  5. Prometheus 按新配置抓取
```

### 21.3.6 SLI / SLO / SLA / 错误预算

```
SLI (Service Level Indicator):
  - 服务质量的量化指标
  - 例:HTTP 200 请求比例、P99 延迟
  - 公式:good / total

SLO (Service Level Objective):
  - 对 SLI 的目标值
  - 例:99.9% 请求 < 300ms,99.95% 请求成功
  - 内部目标(团队承诺)

SLA (Service Level Agreement):
  - 对外的合同承诺(违反有赔偿)
  - 例:99.9% 月可用性,违反赔 10% 月费
  - 通常比 SLO 宽松(SLO 99.95% → SLA 99.9%)

Error Budget(错误预算):
  - 1 - SLO = 错误预算
  - SLO 99.9% → 月错误预算 = 43.2 分钟
  - 预算用完 → 冻结发布,先修可靠性
  - 预算富余 → 可激进发布

K8s 上下文:
  - apiserver SLO:99.9% 请求 < 1s,99% watch 不丢事件
  - etcd SLO:99.99% 写 < 100ms
  - kubelet SLO:99% Pod 启动 < 5s
  - 应用 SLO:由业务方定义
```

### 21.3.7 Google 黄金信号在 K8s 的落地

```
Golden Signals(Google SRE Book):

1. Latency(延迟):
   - http_request_duration_seconds_bucket
   - 区分成功 vs 失败的延迟(慢错误比快成功更糟)
   - histogram_quantile(0.99, rate(...[5m]))

2. Traffic(流量):
   - http_requests_total(rate)
   - 字节流量:bytes_sent_total、bytes_received_total
   - K8s:Ingress QPS、Service 请求量

3. Errors(错误):
   - http_requests_total{code=~"5.."}
   - 业务错误(200 但业务失败)
   - K8s:Pod restart count、CrashLoopBackOff

4. Saturation(饱和度):
   - CPU 使用率、内存使用率、磁盘 IO、网络带宽
   - K8s:node CPU > 80%、Pod 内存接近 limit、conntrack 满
   - 队列长度、连接池占用

K8s 黄金信号映射:
  ┌────────────┬─────────────────────────────────────────────┐
  │ 信号       │ K8s 指标                                     │
  ├────────────┼─────────────────────────────────────────────┤
  │ Latency    │ apiserver_request_duration_seconds          │
  │            │ ingress_upstream_latency_seconds            │
  │            │ container_cpu_load_average_10s              │
  ├────────────┼─────────────────────────────────────────────┤
  │ Traffic    │ apiserver_request_total                     │
  │            │ nginx_ingress_controller_requests           │
  │            │ container_network_receive_bytes_total       │
  ├────────────┼─────────────────────────────────────────────┤
  │ Errors     │ apiserver_request_total{code=~"5.."}        │
  │            │ kube_pod_container_status_restarts_total    │
  │            │ kube_pod_status_phase{phase="Failed"}       │
  ├────────────┼─────────────────────────────────────────────┤
  │ Saturation │ node_cpu_seconds_total                      │
  │            │ node_memory_MemAvailable_bytes              │
  │            │ container_memory_working_set_bytes          │
  │            │ node_nf_conntrack_entries                   │
  └────────────┴─────────────────────────────────────────────┘
```

## 21.4 操作流程与命令

### 21.4.1 安装监控栈(kube-prometheus-stack Helm Chart)

```bash
# 1. 添加 Helm 仓库
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo update

# 2. 创建监控命名空间
kubectl create namespace monitoring

# 3. 安装 kube-prometheus-stack
#    包含:Prometheus Operator、Prometheus、Alertmanager、Grafana、node-exporter、kube-state-metrics
helm install kube-prom prometheus-community/kube-prometheus-stack \
  --namespace monitoring \
  --version 65.0.0 \
  --set prometheus.prometheusSpec.retention=15d \
  --set prometheus.prometheusSpec.storageSpec.volumeClaimTemplate.spec.resources.requests.storage=100Gi \
  --set grafana.adminPassword='admin123' \
  --set grafana.persistence.enabled=true \
  --set grafana.persistence.size=10Gi

# 4. 查看组件
kubectl get pods -n monitoring
# NAME: prometheus-kube-prom-prometheus-0
#       alertmanager-kube-prom-alertmanager-0
#       kube-prom-grafana-xxx
#       kube-prom-kube-state-metrics-xxx
#       kube-prom-prometheus-node-exporter-xxx (DaemonSet)

# 5. 端口转发访问 Grafana
kubectl port-forward svc/kube-prom-grafana -n monitoring 3000:80
# 访问 http://localhost:3000,用户名 admin,密码 admin123

# 6. 端口转发访问 Prometheus
kubectl port-forward svc/kube-prom-prometheus -n monitoring 9090:9090
# 访问 http://localhost:9090

# 7. 安装 metrics-server(若未安装)
helm repo add metrics-server https://kubernetes-sigs.github.io/metrics-server/
helm install metrics-server metrics-server/metrics-server \
  --namespace kube-system \
  --set args="{--kubelet-insecure-tls}"
```

### 21.4.3 检查 Prometheus 抓取状态

```bash
# 1. 查看 Prometheus 抓取目标
#    UI: Status -> Service Discovery
#    API:  GET /api/v1/targets

# 2. 查看抓取状态(kubectl exec 进 Prometheus pod)
kubectl exec -n monitoring prometheus-kube-prom-prometheus-0 -- \
  wget -qO- 'http://localhost:9090/api/v1/targets' | jq '.data.activeTargets[] | {job: .labels.job, health: .health, lastError: .lastError, lastScrape: .lastScrape}'

# 3. 查看抓取失败的目标
#    UI: Status -> Targets,筛选 DOWN

# 4. 查看 Prometheus 配置
kubectl exec -n monitoring prometheus-kube-prom-prometheus-0 -- \
  wget -qO- 'http://localhost:9090/api/v1/status/config'
```

## 21.5 底层原理

### 21.5.1 Prometheus 抓取机制

```
Prometheus 抓取(scrape)流程:

1. 服务发现(Service Discovery):
   - 静态配置(static_configs)
   - K8s 服务发现(kubernetes_sd_configs):从 kube-apiserver 拉 Pod/Service/Node/Endpoint
   - DNS、Consul、EC2、Azure、文件等

2. relabel_configs(scrape 前):
   - 过滤目标(metadata label)
   - 修改 label(重命名、拼接)
   - 设置 __address__、__metrics_path__、__scheme__

3. metric_relabel_configs(scrape 后):
   - 过滤不需要的指标(metric name)
   - 修改 label
   - drop high-cardinality labels

4. HTTP 抓取:
   - GET <scheme>://<address><metrics_path>
   - 默认 Accept: text/plain; version=0.0.4
   - 超时:scrape_timeout(默认 10s)
   - 抓取间隔:scrape_interval(默认 30s,可按 job 覆盖)

5. 解析 exposition format:
   - 文本格式,逐行解析
   - 三种行:HELP / TYPE / metric
   - TYPE 支持:counter、gauge、histogram、summary
   - 例:
     # HELP http_requests_total Total requests
     # TYPE http_requests_total counter
     http_requests_total{method="POST",code="200"} 1027
     http_requests_total{method="POST",code="500"} 3

6. 写入 TSDB:
   - 先写 WAL(Write-Ahead Log),防丢
   - 写入 Head block(内存 + mmap)
   - 每 2h Head 截断,flush 成可持久化的 block
   - 旧 block 周期性 compaction(合并、降采样)

抓取关键参数:
  scrape_interval: 30s      # 抓取间隔
  scrape_timeout: 10s       # 单次抓取超时
  sample_limit: 5000        # 单次抓取最大样本数(防爆炸)
  label_limit: 60           # 单个样本最大 label 数
  label_name_length_limit: 511
  label_value_length_limit: 2048
```

### 21.5.3 metrics-server 与 Aggregated API Server

```
metrics-server 架构:

  kubectl top -> apiserver -> /apis/metrics.k8s.io/v1beta1 -> metrics-server
                                                                |
                                                                v
                                                          kubelet /metrics/resource
                                                          (每个节点)

metrics-server 工作流程:
  1. 启动时注册 APIService:
     kind: APIService
     metadata:
       name: v1beta1.metrics.k8s.io
     spec:
       service:
         name: metrics-server
         namespace: kube-system
       group: metrics.k8s.io
       version: v1beta1
       insecureSkipTLSVerify: true  # 生产环境用真证书

  2. apiserver 收到 /apis/metrics.k8s.io/... 请求
     -> 转发给 metrics-server(代理)

  3. metrics-server 内部:
     - 启动时 List-Watch 所有 Node
     - 每 15s 拉一次每个节点的 kubelet /metrics/resource
     - 缓存在内存(只存当前值,不存历史)
     - 收到查询请求时,从内存返回

  4. 关键参数:
     --kubelet-preferred-address-types=InternalIP  # 优先用 IP 访问 kubelet
     --metric-resolution=15s                        # 抓取间隔
     --kubelet-insecure-tls                         # 不验证 kubelet 证书(测试用)

metrics-server 给谁用:
  - HPA(HorizontalPodAutoscaler):每 30s 查 metrics.k8s.io
  - VPA(VerticalPodAutoscaler)
  - kubectl top
  - scheduler(资源感知调度,1.27+)

不存历史的原因:
  - 设计目标:轻量、近实时(给 HPA 用)
  - 历史 -> Prometheus
  - 不与 Prometheus 重叠
```

### 21.5.4 kube-state-metrics 内部机制

```
kube-state-metrics 架构:

  kube-apiserver
       ^ List-Watch
       |
  kube-state-metrics
       |
       v /metrics (Prometheus exposition)
  Prometheus

内部组件:
  1. Informer:List-Watch K8s API(类似 client-go informer)
     - Pod / Deployment / Node / Service / ...
     - 全量 List + Watch 增量
     - 本地 cache

  2. Metric Generator:
     - 把 K8s 对象翻译成 metric
     - 例:Pod -> kube_pod_status_phase、kube_pod_container_resource_requests
     - 每个对象生成多条 metric
     - 高基数(每个 Pod 一组 label)

  3. HTTP Server:
     - /metrics 暴露所有 metric(text format)
     - 每次请求重新序列化(无缓存,但便宜)
     - 支持 self-monitor(自身 metrics)

  4. 分片(Sharding):
     - 大集群(>5K 节点)单实例扛不住
     - 通过 --pod 和 --total-shards 分片
     - 每个分片处理一部分资源

指标命名规则:
  kube_<resource>_<field>
  例:
    kube_pod_status_phase{namespace, pod, phase} 1|0
    kube_pod_container_resource_requests{namespace, pod, container, resource, unit} 0.1
    kube_node_status_condition{node, condition, status} 1|0
    kube_deployment_status_replicas{namespace, deployment} 3
    kube_deployment_spec_replicas{namespace, deployment} 3
    kube_hpa_status_current_replicas{namespace, hpa} 5

注意:
  - phase 是 label,value 是 0/1(每个 phase 一个时间序列)
  - 这是 KSM 故意设计,便于 PromQL 过滤
  - 但会带来基数膨胀(每 Pod x N phase = N 条 series)
```

### 21.5.5 cAdvisor 与 kubelet metrics

```
cAdvisor(Container Advisor):
  - Google 开源,2014
  - kubelet 内置(不需要单独部署)
  - 采集容器级资源使用
  - 通过 cgroup v1/v2 + /proc 收集

kubelet 暴露的 metrics 端点:
  1. /metrics                  - kubelet 自身(默认)
  2. /metrics/cadvisor         - cAdvisor(Pod/容器资源)
  3. /metrics/resource         - 简化版(给 metrics-server 用)
  4. /metrics/probes           - 探针结果
  5. /stats/summary            - JSON 格式(老接口,遗留)

关键指标:
  container_cpu_usage_seconds_total     - CPU 累计秒
  container_memory_working_set_bytes    - 实际内存(含不可驱逐)
  container_memory_rss                  - RSS
  container_memory_failcnt              - OOM 计数
  container_fs_reads_bytes_total        - 文件系统读
  container_network_receive_bytes_total - 网络接收
  container_start_time_seconds          - 容器启动时间

cAdvisor vs /metrics/resource:
  - cAdvisor:全量,有 Pid、网络、文件系统,基数大
  - /metrics/resource:精简,只有 CPU/内存,给 HPA 用
  - 生产环境:Prometheus 抓 cAdvisor(全量),metrics-server 抓 resource(精简)

cgroup v2 影响:
  - K8s 1.25+ 默认 cgroup v2(若内核支持)
  - cAdvisor 部分指标在 v2 下不可用(如 per-container disk IO)
  - 需 node-exporter 或 eBPF 补充
```

### 21.5.6 Histogram 分桶与 quantile 计算

```
Histogram 分桶设计:

  http_request_duration_seconds_bucket{le="0.005"} 24054    # <= 5ms 有 24054 个
  http_request_duration_seconds_bucket{le="0.01"}  33444    # <= 10ms 有 33444 个
  http_request_duration_seconds_bucket{le="0.025"} 100392
  http_request_duration_seconds_bucket{le="0.05"}  129389
  http_request_duration_seconds_bucket{le="0.1"}   133988
  http_request_duration_seconds_bucket{le="0.25"}  152815
  http_request_duration_seconds_bucket{le="0.5"}   163891
  http_request_duration_seconds_bucket{le="1"}     168320
  http_request_duration_seconds_bucket{le="2.5"}   169300
  http_request_duration_seconds_bucket{le="5"}     169350
  http_request_duration_seconds_bucket{le="10"}    169360
  http_request_duration_seconds_bucket{le="+Inf"}  169362
  http_request_duration_seconds_sum   8421.5                  # 总延迟
  http_request_duration_seconds_count 169362                  # 总请求数

P99 计算:
  histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m]))

计算过程:
  1. rate() 算每秒增长率(每桶)
  2. 找到包含 99% 数据的桶:
     - 总数 N = count(99% quantile) = N * 0.99
     - 找到第一个累积 >= N * 0.99 的桶
  3. 桶内线性插值:
     - 假设桶内均匀分布
     - quantile = le_lower + (le_upper - le_lower) * (target - cum_lower) / (cum_upper - cum_lower)

桶定义的重要性:
  - 桶太宽:P99 不准(线性插值误差大)
  - 桶太窄:基数爆炸
  - 经验:SLO 边界附近桶密,远离处桶疏
  - 例:SLO = 100ms,桶 50/75/100/250/500/1000ms

bucket 设计(client library):
  Python:
    Histogram('http_request_duration_seconds', '...',
              buckets=(0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5, 10))
  Go:
    prometheus.NewHistogram(prometheus.HistogramOpts{
      Name: "http_request_duration_seconds",
      Buckets: []float64{0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5, 10},
    })
```

### 21.5.7 TSDB 存储原理

```
Prometheus TSDB(Prometheus 2.x):

  内部结构(每个 block):
  +----------------------------------------------+
  | Block (2h)                                   |
  | +---------------+ +---------------+          |
  | | chunks/       | | index/        |          |
  | | (压缩数据)    | | (倒排索引)    |          |
  | +---------------+ +---------------+          |
  | +---------------+                            |
  | | meta.json     |                            |
  | +---------------+                            |
  +----------------------------------------------+

  1. Head(内存 + mmap):
     - 最新 2h 数据
     - 写入:WAL(防丢) -> Head chunk(内存)
     - 查询:直接查 Head

  2. Block(磁盘,2h 一个):
     - Head 满 2h 后,截断成 Block
     - chunks/:数据块(每个 chunk 120 样本,snappy 压缩)
     - index/:倒排索引(label -> series ID -> chunk)
     - meta.json:Block 元数据

  3. Compaction:
     - 把多个 2h Block 合并成更大的 Block(8h -> 24h -> ...)
     - 降采样:超过 retention 25% 的 Block,5min 一个采样点
     - 降采样:超过 retention 50% 的 Block,1h 一个采样点

  4. Retention:
     - 默认 15 天
     - 通过 --storage.tsdb.retention.time 控制
     - 也可用 --storage.tsdb.retention.size(优先于 time)

存储估算:
  - 单样本约 1.3 ~ 2 字节(压缩后)
  - 100 万 series x 30s 抓取 x 15 天 = 100M 样本 x 1.5B = 150GB
  - 实际还要算 index、WAL、block metadata

WAL(Write-Ahead Log):
  - 写入样本前先写 WAL
  - 崩溃后重启可恢复
  - WAL 文件 128MB 一个,循环写
  - 启动时 replay WAL

Head chunk:
  - 内存中,1h 一个 chunk
  - chunk 满后 mmap 到磁盘(仍在 Head 范围)
  - 截断成 Block 后释放
```

### 21.5.8 Alertmanager 工作流

```
Alertmanager 收到告警后的处理:

1. 接收告警(Prometheus -> Alertmanager):
   POST /api/v2/alerts
   [{
     "labels": {"alertname": "NodeHighCpu", "instance": "node-1", "severity": "warning"},
     "annotations": {"summary": "..."},
     "startsAt": "2024-...",
     "endsAt": "2024-..."
   }]

2. 分组(Grouping):
   - group_by: ["alertname", "cluster"]
   - 同组的告警合并成一封通知
   - group_wait: 30s    # 第一个告警等 30s,等其它同组告警
   - group_interval: 5m  # 同组后续告警间隔
   - repeat_interval: 4h # 同告警重复通知间隔

3. 抑制(Inhibition):
   - 高级别告警抑制低级别
   - 例:NodeDown 抑制 NodeHighCpu(节点挂了不再报 CPU 高)
   - inhibit_rules:
     source_match: {alertname: "NodeDown"}
     target_match: {alertname: "NodeHighCpu"}
     equal: ["instance"]

4. 静默(Silence):
   - 临时屏蔽告警(维护窗口)
   - 通过 UI 或 amtool 创建
   - 匹配 labels + 时间窗口

5. 路由(Routing):
   - 树形路由(top-level -> child routes)
   - matchers 匹配 labels
   - continue: true 继续匹配下一个 route

6. 接收器(Receiver):
   - webhook(钉钉/飞书/企业微信)
   - email
   - slack
   - pagerduty
   - opsgenie
   - victorops
   - pushover
   - wechat(企业微信)

告警状态机(Prometheus 端):
  inactive -> pending(for 期间) -> firing(已触发)

  for: 10m 表示告警表达式持续 10m 满足才 firing
  pending 期间不发给 Alertmanager
  firing 后才发送
```

```yaml
# PrometheusRule:告警 + 记录规则
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: kube-prom-alerts
  namespace: monitoring
  labels:
    release: kube-prom
spec:
  groups:
  # 1. 节点告警
  - name: node-alerts
    interval: 30s
    rules:
    # P1:节点 CPU > 85% 持续 10 分钟
    - alert: NodeHighCpu
      expr: |
        100 - (avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100) > 85
      for: 10m
      labels:
        severity: warning       # P1
        team: sre
      annotations:
        summary: "Node {{ $labels.instance }} CPU > 85%"
        description: "Node {{ $labels.instance }} CPU usage is {{ printf \"%.1f\" $value }}% for 10m"
        runbook: "https://wiki.example.com/runbooks/node-high-cpu"

    # P0:节点 NotReady
    - alert: NodeNotReady
      expr: kube_node_status_condition{condition="Ready", status!="true"} == 1
      for: 5m
      labels:
        severity: critical      # P0
        team: sre
      annotations:
        summary: "Node {{ $labels.node }} is NotReady"
        description: "Node {{ $labels.node }} has been NotReady for 5m"

    # P1:磁盘空间 < 10%
    - alert: NodeDiskRunningFull
      expr: |
        (node_filesystem_avail_bytes{fstype!~"tmpfs|overlay"} /
         node_filesystem_size_bytes{fstype!~"tmpfs|overlay"}) * 100 < 10
      for: 30m
      labels:
        severity: warning
      annotations:
        summary: "Node {{ $labels.instance }} disk {{ $labels.mountpoint }} < 10%"

    # P1:预测 4 小时后磁盘满
    - alert: NodeDiskWillFillIn4h
      expr: predict_linear(node_filesystem_avail_bytes[1h], 4 * 3600) < 0
      for: 10m
      labels:
        severity: warning

  # 2. Pod 告警
  - name: pod-alerts
    rules:
    # P1:Pod CrashLoopBackOff
    - alert: PodCrashLooping
      expr: increase(kube_pod_container_status_restarts_total[1h]) > 5
      for: 5m
      labels:
        severity: warning
      annotations:
        summary: "Pod {{ $labels.namespace }}/{{ $labels.pod }} restarting frequently"

    # P1:Deployment 副本数不达标
    - alert: DeploymentReplicasMismatch
      expr: |
        kube_deployment_spec_replicas != kube_deployment_status_replicas_available
      for: 15m
      labels:
        severity: warning
      annotations:
        summary: "Deployment {{ $labels.namespace }}/{{ $labels.deployment }} replicas mismatch"

    # P0:Pod Pending 超过 30 分钟
    - alert: PodStuckPending
      expr: kube_pod_status_phase{phase="Pending"} == 1
      for: 30m
      labels:
        severity: critical

  # 3. 控制面告警
  - name: control-plane-alerts
    rules:
    # P0:apiserver 不可达
    - alert: APIServerDown
      expr: up{job="apiserver"} == 0
      for: 5m
      labels:
        severity: critical
        team: sre

    # P1:apiserver P99 延迟 > 1s
    - alert: APIServerHighLatency
      expr: |
        histogram_quantile(0.99,
          sum(rate(apiserver_request_duration_seconds_bucket[5m])) by (le, verb)) > 1
      for: 10m
      labels:
        severity: warning

    # P1:etcd 磁盘 fsync 慢
    - alert: EtcdHighFsyncDuration
      expr: |
        histogram_quantile(0.99,
          rate(etcd_disk_wal_fsync_duration_seconds_bucket[5m])) > 0.01
      for: 5m
      labels:
        severity: warning

  # 4. 应用告警(基于黄金信号)
  - name: app-alerts
    rules:
    # P0:HTTP 5xx 错误率 > 5%
    - alert: HighErrorRate
      expr: |
        sum(rate(http_requests_total{code=~"5.."}[5m])) by (service) /
        sum(rate(http_requests_total[5m])) by (service) > 0.05
      for: 5m
      labels:
        severity: critical
        team: app
      annotations:
        summary: "Service {{ $labels.service }} 5xx error rate > 5%"

    # P1:HTTP P99 延迟 > 500ms
    - alert: HighLatency
      expr: |
        histogram_quantile(0.99,
          sum(rate(http_request_duration_seconds_bucket[5m])) by (le, service)) > 0.5
      for: 10m
      labels:
        severity: warning

  # 5. 记录规则(预聚合,降低查询压力)
  - name: recording-rules
    rules:
    - record: job:http_requests:rate5m
      expr: sum by (job)(rate(http_requests_total[5m]))

    - record: job:http_requests:error_rate5m
      expr: |
        sum by (job)(rate(http_requests_total{code=~"5.."}[5m])) /
        sum by (job)(rate(http_requests_total[5m]))

    - record: node:cpu_usage:ratio
      expr: |
        1 - avg by (instance)(rate(node_cpu_seconds_total{mode="idle"}[5m]))

    - record: cluster:memory_usage:ratio
      expr: |
        sum(container_memory_working_set_bytes{id="/"}) /
        sum(kube_node_status_allocatable{resource="memory"})
```

### 21.6.8 应用埋点示例(Python + prometheus_client)

```python
# app.py - Python Flask 应用埋点
from flask import Flask, request
from prometheus_client import Counter, Histogram, Gauge, generate_latest, CONTENT_TYPE_LATEST
import time

app = Flask(__name__)

# 1. Counter:请求计数
http_requests_total = Counter(
    'http_requests_total',
    'Total HTTP requests',
    ['method', 'path', 'code']
)

# 2. Histogram:延迟分布(注意 bucket 设计)
http_request_duration_seconds = Histogram(
    'http_request_duration_seconds',
    'HTTP request duration',
    ['method', 'path'],
    buckets=(0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5, 10)
)

# 3. Gauge:当前状态(队列长度、连接数)
active_connections = Gauge(
    'active_connections',
    'Active connections'
)

# 4. 业务 Counter
orders_processed_total = Counter(
    'orders_processed_total',
    'Total orders processed',
    ['status']   # success/fail
)

@app.before_request
def before():
    request.start_time = time.time()

@app.after_request
def after(response):
    duration = time.time() - request.start_time
    path = request.path
    # 简化 path,避免高基数(去掉 ID)
    if path.startswith('/api/orders/'):
        path = '/api/orders/:id'
    http_requests_total.labels(
        method=request.method,
        path=path,
        code=response.status_code
    ).inc()
    http_request_duration_seconds.labels(
        method=request.method,
        path=path
    ).observe(duration)
    return response

@app.route('/metrics')
def metrics():
    return generate_latest(), 200, {'Content-Type': CONTENT_TYPE_LATEST}

if __name__ == '__main__':
    app.run(host='0.0.0.0', port=8080)
```

## 21.7 常见陷阱与调优

### 21.7.1 陷阱表

| # | 陷阱 | 后果 | 解决 |
|---|------|------|------|
| 1 | high cardinality label(如 user_id、trace_id 当 label) | TSDB 爆炸,OOM | 严禁高基 label,用 metric_relabel drop |
| 2 | scrape_interval 全局 5s | 样本量 6 倍上涨,内存爆 | 默认 30s,关键 15s,非关键 60s |
| 3 | histogram bucket 太多(20+) | 基数 20 倍 | 8-12 个 bucket,SLO 边界密 |
| 4 | Prometheus 单实例无 HA | 实例挂监控盲区 | 2 副本 + Thanos/Cortex |
| 5 | retention 太长(180 天) | 磁盘爆 | 默认 15 天,长期用 Thanos |
| 6 | 不用 recording rules | 查询慢、Dashboard 卡 | 高频查询预聚合 |
| 7 | 告警无 for 持续时间 | 告警风暴 | 至少 5m for |
| 8 | 告警不分级别 | oncall 疲劳 | P0/P1/P2/P3 分级 |
| 9 | 告警无 runbook | 排障不知如何下手 | annotations.runbook |
| 10 | kube-state-metrics 不分片 | 大集群 KSM OOM | --total-shards=N 分片 |
| 11 | metrics-server 资源不足 | HPA 失效 | 至少 200m CPU / 512Mi 内存 |
| 12 | cAdvisor 在 cgroup v2 下指标缺失 | 监控盲区 | 升级 cAdvisor,补 node-exporter |
| 13 | alertmanager 单实例 | 告警丢 | 3 副本 + cluster 模式 |
| 14 | ServiceMonitor label 不匹配 Prometheus selector | 不被抓取 | release label 必须匹配 |
| 15 | node-exporter 不在所有节点 | DaemonSet 漏节点 | nodeSelector/tolerations 配置 |
| 16 | Pod label `pod-template-hash` 当 cardinality label | 滚动更新后基数翻倍 | metric_relabel drop pod-template-hash |
| 17 | WAL 不压缩 | 磁盘 IO 高 | walCompression: true |
| 18 | 不用 relabel drop 无用指标 | TSDB 浪费 | drop go_.*、process_.* 等 |
| 19 | 抓取超时 > 抓取间隔 | 抓取堆积 | scrape_timeout < scrape_interval |
| 20 | Alertmanager 无 inhibit | 告警风暴 | NodeDown 抑制 NodeHighCpu |

### 21.7.2 高基数(High Cardinality)陷阱详解


### 21.7.3 Prometheus 资源规划

```
经验公式(单 Prometheus 实例):
  内存(MB) ≈ series 数 × 1.5 KB + 1GB
  磁盘(GB/天) ≈ series 数 × 86400 / scrape_interval × 1.5B / 1e9

参考:
  - 1K 节点集群,每节点 30 Pod,每 Pod 100 metric -> 3M series
  - 内存:3M × 1.5KB = 4.5GB + 1GB = 5.5GB(实际 8-12GB)
  - 磁盘(30s 抓取):3M × 2880 × 1.5B = 13GB/天 -> 15 天 200GB

5K 节点集群:
  - series:15M ~ 30M
  - 单 Prometheus 内存:60-100GB
  - 磁盘:1-2TB(15 天)
  - 必须:分片(Prometheus federation / Thanos receive)

建议:
  - 单 Prometheus 上限:5M series(经验值)
  - 超过 -> 拆分(按 namespace / team / cluster)
  - 长期存储:Thanos / Cortex / Mimir / VictoriaMetrics
```

### 21.7.6 告警风暴治理

```
告警风暴:一次故障引发几百上千条告警,oncall 疲劳

治理策略:

1. 分组(group_by):
   - group_by: [alertname, cluster, namespace]
   - 同组合并成一封通知

2. 抑制(inhibit_rules):
   - 高级别抑制低级别
   - 例:NodeDown 抑制 NodeHighCpu、NodeDiskFull
   - 例:ClusterDown 抑制 NodeDown
   - 例:PodDown 抑制 PodHighLatency

3. 静默(silence):
   - 维护窗口预先静默
   - 通过 amtool/UI 创建
   - 支持定时生效

4. for 持续时间:
   - 至少 5m,避免抖动
   - 关键告警 1-5m
   - 警告告警 10-30m

5. repeat_interval:
   - P0: 1h(频繁提醒)
   - P1: 4h
   - P2: 24h

6. 告警分组路由:
   - 按团队路由(team=label)
   - 按命名空间路由
   - 按集群路由

7. 告警质量审查:
   - 月度审查:哪些告警未触发?是否可删?
   - 哪些告警频繁误报?调阈值或 for
   - 哪些告警无 action?删
```

## 21.8 工业案例与基准数据

### 21.8.1 阿里 ACK:Prometheus + SLS 监控栈

**场景**:万节点集群,多租户,业务种类多。

**方案**:

1. **ARMS Prometheus**(阿里云托管):
   - 兼容开源 Prometheus
   - 与 ACK 深度集成(一键安装)
   - 多租户隔离(RAM + namespace)
   - 弹性扩容

2. **SLS 时序存储**:
   - 自研时序引擎,兼容 PromQL
   - PB 级存储,成本低于本地 Prometheus
   - 长期保留(180 天+)

3. **Grafana 服务**:
   - 托管 Grafana,免运维
   - 与 ARMS 数据源打通
   - 大屏展示

4. **混合监控**:
   - 短期(7 天):ARMS Prometheus(本地 SSD)
   - 长期(180 天):SLS 时序存储(对象存储后端)
   - 全局查询:PromQL 透明跨存储

5. **告警**:
   - ARMS Alertmanager
   - 钉钉/短信/电话
   - 与阿里云监控打通

**规模数据**:
- 单集群 5K 节点
- Pod 数 15 万+
- series 数 30M+(单 Prometheus)
- 采用 Thanos Receive 分片,8 个 shard
- 查询 P99 < 2s(7 天内)< 5s(180 天)

**特色**:
- 与云监控(CloudMonitor)打通
- GPU 监控(DCGM exporter)
- 网络监控(eBPF + Cilium)
- 服务网格监控(Istio + Kiali)

### 21.8.2 字节跳动:ByteMonitor 自研监控

**场景**:抖音/今日头条基础设施,超大规模集群。

## 21.10 面试速答

**Q1: metrics-server 和 Prometheus 区别?**

metrics-server 给 K8s 内部用(HPA/VPA/kubectl top),只暴露 metrics.k8s.io API,不存历史;Prometheus 给监控用,暴露 /metrics 抓取,存历史(15 天+),有 PromQL。两者各司其职,生产环境都需要。

**Q2: kube-state-metrics 和 cAdvisor 区别?**

kube-state-metrics 采集 K8s 对象状态(Deployment 副本数、Pod Phase、Node Condition),从 kube-apiserver List-Watch;cAdvisor 采集 Pod/容器 资源使用率(CPU/内存/网络),由 kubelet 内置,从 cgroup 读取。两者数据来源和维度完全不同。

**Q3: Prometheus 4 种指标类型?**

counter(只增不减,如请求总数)、gauge(可增可减,如内存)、histogram(分桶,服务端算分位数)、summary(客户端算分位数,不可跨实例聚合)。生产用 histogram,不用 summary。

**Q4: high cardinality 是什么?怎么避免?**

高基数 label(如 user_id、trace_id)导致 series 数爆炸,TSDB 内存涨爆。避免:严禁高基 label 当 label,用 metric_relabel_configs drop 掉,用聚合后的维度(如 path 而不是 user_id)。

**Q5: PromQL 算 P99 延迟?**

`histogram_quantile(0.99, sum(rate(http_request_duration_seconds_bucket[5m])) by (le, service))`。先用 rate 算每秒增长率,按 le 和 service 分组求和,histogram_quantile 算分位数。

**Q6: SLI/SLO/SLA 区别?**

SLI 是指标(如 99.9% 请求成功),SLO 是内部目标(99.95%),SLA 是外部合同(99.9%,违反赔钱)。SLO 比 SLA 严,留 buffer。错误预算 = 1 - SLO,SLO 99.9% 月错误预算 43.2 分钟。

**Q7: 黄金信号 4 件套?**

延迟(Latency)、流量(Traffic)、错误(Errors)、饱和度(Saturation)。任何服务监控这 4 个就够 80% 场景。延迟区分成功 vs 失败的延迟,饱和度关注 CPU/内存/连接池等。

**Q8: Prometheus Operator 的 CRD 有哪些?**

Prometheus(Prometheus 实例)、Alertmanager(Alertmanager 实例)、ServiceMonitor(通过 Service 监控)、PodMonitor(直接监控 Pod)、Probe(黑盒监控)、PrometheusRule(告警/记录规则)、AlertmanagerConfig(命名空间级告警路由)、ThanosRuler(Thanos 规则评估)。

**Q9: Thanos 解决什么问题?**

单 Prometheus 不支持长期存储和 HA。Thanos 通过 Sidecar 把 Prometheus 数据上传到对象存储(S3/OSS),Store Gateway 读历史数据,Query 节点全局查询,实现长期存储 + 跨集群查询 + HA。

**Q10: 告警分级怎么做?**

P0(critical,电话叫醒,5m 内响应)、P1(warning,1h 响应)、P2(info,工作日响应)、P3(周报统计)。按 severity label 分,Alertmanager 路由到不同 receiver(P0 → PagerDuty,P1 → 钉钉,P2 → 邮件)。

**Q11: 告警风暴怎么治理?**

分组(group_by)、抑制(inhibit)、静默(silence)、for 持续时间、repeat_interval、按团队路由。NodeDown 抑制 NodeHighCpu,维护窗口预先静默。

**Q12: ServiceMonitor 和 PodMonitor 区别?**

ServiceMonitor 通过 Service 选 Pod(适合有 Service 的应用),PodMonitor 直接选 Pod(不经 Service,适合 headless 或无 Service 应用,如 DaemonSet)。

**Q13: 单 Prometheus 上限?**

经验值 5M series。超过拆分(按 namespace/team/cluster)或用 Thanos Receive 分片。1K 节点集群(30K Pod)约 3M series,5K 节点约 15M+,必须分片。

**Q14: recording rule 是什么?**

预聚合规则,把高频查询的表达式预计算并存储为新的 metric。降低查询压力,Dashboard 加速。例:`record: job:http_requests:rate5m` 预计算每 5 分钟的请求率。

**Q15: Prometheus HA 怎么做?**

2 副本 Prometheus(相同配置,都抓相同 target),前端 Thanos Query 去重(deduplication by replica label)。Alertmanager 3 副本 cluster 模式(Gossip 协议同步静默和通知状态)。

### 题 2:Prometheus OOM 排查与优化

```
现象:
  - Prometheus Pod OOMKilled
  - 重启后 5 分钟又 OOM
  - 监控盲区

排查:

1. 看监控(若有):
   - prometheus_tsdb_head_series(Head 中的 series 数)
   - prometheus_tsdb_head_samples_appended_total(写入速率)
   - process_resident_memory_bytes(进程内存)
   - go_memstats_gc_duration_seconds(GC 时间)

2. 找高基数 metric:
   PromQL: topk(10, count by (__name__)({__name__=~".+"}))
   - 找 series 数最多的 metric
   - 通常是某个 label 基数失控(如 user_id、trace_id)

3. 看 scrape target:
   PromQL: scrape_samples_post_metric_relabeling
   - 找样本数最多的 target
   - 检查 metric_relabel_configs 是否 drop

4. 查询大内存:
   - 是否有大范围查询(30 天+)?
   - 是否有高基数 join?
   - 检查 query.log

5. WAL 检查:
   - WAL 文件大小是否异常?
   - 是否有大量未压缩 WAL?

优化:

1. 降低 series 数:
   - metric_relabel drop 无用 metric
     metricRelabelConfigs:
     - source_labels: [__name__]
       regex: 'go_(gc|memstats|threads)_.*'
       action: drop
   - drop 高基数 label
     - source_labels: [user_id, trace_id]
       action: labeldrop
       regex: '(.+)'

2. 调整 retention:
   - retention: 15d -> 7d(短期)
   - 长期用 Thanos

3. 分片:
   - 按 namespace 拆 Prometheus
   - 或用 Thanos Receive 分片

4. 内存调优:
   - resources.limits.memory 提高
   - enableFeatures: memory-snapshot-on-shutdown
   - --storage.tsdb.head-chunks-write-queue-size=0(关闭写队列)

5. scrape_interval 调整:
   - 非关键 30s -> 60s
   - 样本量减半

6. 查询限制:
   - query.max-samples=50000000(限制单查询样本数)
   - query.timeout=2m

7. recording rules:
   - 高频查询预聚合

最终方案:
  - drop 5 个无用 metric(series 减 30%)
  - scrape_interval 30s -> 60s(非关键)
  - 内存 16GB -> 32GB
  - 加 Thanos 长期存储(本地 7 天)
  - 加 recording rules(Dashboard 加速)
```

### 题 3:实现 SLO 监控与告警

```
场景:订单服务 SLO = 99.9% 请求 < 300ms,99.95% 请求成功

实现:

1. SLI 定义:
   - 延迟 SLI:http_request_duration_seconds_bucket{le="0.3"} / http_request_duration_seconds_count
   - 成功率 SLI:http_requests_total{code!~"5.."} / http_requests_total

2. Recording Rules(预聚合,降低查询压力):
   groups:
   - name: slo
     rules:
     # 延迟 SLI(5 分钟窗口)
     - record: order:latency_sli:ratio_rate5m
       expr: |
         sum(rate(http_request_duration_seconds_bucket{service="order", le="0.3"}[5m]))
         / sum(rate(http_request_duration_seconds_count{service="order"}[5m]))

     # 成功率 SLI(5 分钟窗口)
     - record: order:success_sli:ratio_rate5m
       expr: |
         sum(rate(http_requests_total{service="order", code!~"5.."}[5m]))
         / sum(rate(http_requests_total{service="order"}[5m]))

     # 错误预算消耗速率(5 分钟)
     - record: order:error_budget_burn:rate5m
       expr: |
         (1 - order:success_sli:ratio_rate5m) / (1 - 0.9995)

     # 30 天错误预算(累积)
     - record: order:error_budget_remaining:30d
       expr: |
         1 - (
           sum(rate(http_requests_total{service="order", code=~"5.."}[30d]))
           / (sum(rate(http_requests_total{service="order"}[30d])) * 0.0005)
         )

3. SLO 告警:
   # P0:错误预算消耗过快(1 小时消耗 2% 预算)
   - alert: SLOBurnRateHigh
     expr: order:error_budget_burn:rate5m > 14.4
     for: 5m
     labels:
       severity: critical
       service: order
     annotations:
       summary: "Order service SLO burn rate too high"

   # P1:错误预算消耗较快(6 小时消耗 5% 预算)
   - alert: SLOBurnRateMedium
     expr: order:error_budget_burn:rate30m > 6
     for: 30m
     labels:
       severity: warning

   # P1:SLO 即将违约(剩余预算 < 20%)
   - alert: SLOAlmostBreach
     expr: order:error_budget_remaining:30d < 0.2
     for: 1h
     labels:
       severity: warning

4. Grafana Dashboard:
   - SLO 总览(延迟、成功率、错误预算)
   - Burn Rate 多窗口(5m/30m/1h/6h/1d)
   - 错误预算趋势(30 天)
   - Top 10 错误 path

5. 工作流:
   - SLO 违约 → 冻结发布
   - 错误预算富余 → 可激进发布
   - 月度 SLO 报告 → 服务改进
```

### 题 4:大规模集群 Prometheus 分片方案

```
场景:5K 节点,200K Pod,30M series,单 Prometheus 扛不住

方案对比:

方案 1:Prometheus Federation(联邦)
  - 多个下层 Prometheus(按 namespace 分)
  - 上层 Prometheus 联邦(federation)抓下层
  - 优点:简单
  - 缺点:上层成为瓶颈,查询慢
  - 适合:中等规模(2-3K 节点)

方案 2:Thanos Receive
  - 多个 Prometheus(remote_write)→ Thanos Receive
  - Receive 分片(按 tenant/namespace hash)
  - 对象存储长期保留
  - 优点:全局查询、HA、长期存储
  - 缺点:复杂度高
  - 适合:大规模(5K+ 节点)

方案 3:Cortex/Mimir
  - 微服务架构(Distributor/Ingester/Store)
  - 多租户强
  - 优点:多租户、性能好
  - 缺点:部署复杂
  - 适合:多租户 SaaS

方案 4:VictoriaMetrics
  - 单二进制(简单)
  - 集群模式(vminsert/vmselect/vmstorage)
  - 优点:简单高效、压缩好
  - 缺点:生态弱
  - 适合:简单运维需求

实施(Thanos Receive 方案):

1. Prometheus 部署(每集群或每 namespace 一个):
   - Prometheus + Thanos Sidecar
   - retention: 2 天(本地短期)
   - remote_write → Thanos Receive

2. Thanos Receive(8 shards):
   - 每个 shard 处理 1/8 数据(按 tenant hash)
   - 内存:8 GB/shard
   - 接收 remote_write,写入本地 TSDB + 上传 S3

3. Thanos Store Gateway:
   - 读 S3 历史数据
   - 内存:16 GB

4. Thanos Query:
   - 全局查询入口
   - 聚合 Receive + Store
   - 副本去重(dedup)
   - 内存:16 GB

5. Thanos Compactor:
   - 周期性 compaction S3 block
   - 降采样(5min/1h)

6. Thanos Ruler:
   - 集中告警评估
   - 跨集群规则

资源估算(5K 节点):
  - Prometheus(10 个,每 namespace 一个):每个 8GB
  - Thanos Receive(8 shards):64 GB 总
  - Thanos Store(2 副本):32 GB
  - Thanos Query(2 副本):16 GB
  - Thanos Compactor:8 GB
  - S3 存储:1.5 TB/15 天
  - 总内存:~200 GB
  - 总 CPU:~40 核

查询性能:
  - 1 小时内查询:< 1s
  - 1 天查询:< 3s
  - 30 天查询:< 10s
```

### 题 5:告警风暴治理

```
场景:某次故障,5 分钟收到 500 条告警,oncall 疲劳

治理:

1. 告警分级(P0/P1/P2/P3):
   - P0:critical,电话叫醒,5m 响应
   - P1:warning,1h 响应
   - P2:info,工作日响应
   - P3:统计,周报

2. 分组(group_by):
   group_by: ['alertname', 'cluster', 'namespace']
   - 同组告警合并成一封通知

3. 抑制(inhibit_rules):
   - NodeDown 抑制 NodeHighCpu、NodeDiskFull、NodeMemoryFull
   - PodDown 抑制 PodHighLatency、PodHighErrorRate
   - APIServerDown 抑制 APIServerHighLatency
   - 集群级故障抑制节点级告警

4. 静默(silence):
   - 维护窗口预先静默
   - 通过 amtool/UI 创建
   - 支持定时生效
   - 双人审批

5. for 持续时间:
   - critical: 1-5m
   - warning: 5-15m
   - info: 15-30m

6. repeat_interval:
   - P0: 1h(频繁提醒)
   - P1: 4h
   - P2: 24h

7. 路由:
   - 按团队路由(team=label)
   - 按命名空间路由
   - 按集群路由

8. 告警质量审查:
   - 月度审查
   - 哪些告警未触发?是否可删?
   - 哪些告警频繁误报?调阈值或 for
   - 哪些告警无 action?删
   - 哪些告警重复?合并

9. 智能降噪:
   - 聚类(同根因告警合并)
   - 异常检测(替代部分静态阈值)
   - 历史相似告警关联

10. oncall 工具:
    - 告警认领(ack)
    - 告警转派
    - 告警历史(同告警上次如何处理)
    - runbook 自动打开

效果:
  - 故障告警数:500 → 30(分组+抑制)
  - oncall 响应时间:5m → 2m(关键告警突出)
  - 误报率:30% → 5%(审查 + 调阈值)
```

### 题 6:Prometheus 与 HPA 的关系

```
HPA 需要 metrics,有 3 种来源:

1. Resource metrics(CPU/内存):
   - 来源:metrics-server
   - API:metrics.k8s.io
   - HPA 配置:type: Resource

2. Custom metrics(QPS、队列长度等):
   - 来源:Prometheus Adapter
   - API:custom.metrics.k8s.io
   - HPA 配置:type: Pods/Object

3. External metrics(外部指标):
   - 来源:外部系统(如 SQS 队列长度)
   - API:external.metrics.k8s.io
   - HPA 配置:type: External

Prometheus Adapter:
  - 把 Prometheus 的指标转成 K8s API
  - 让 HPA 能基于 Prometheus 指标伸缩
  - 配置规则(seriesQuery + metricsQuery)

工作流:
  HPA Controller → K8s API(custom.metrics.k8s.io)→ Prometheus Adapter → PromQL 查询 → Prometheus → 返回

HPA 配置示例(基于 QPS):
  metrics:
  - type: Pods
    pods:
      metric:
        name: http_requests_per_second
      target:
        type: AverageValue
        averageValue: "1000"

Prometheus Adapter 规则:
  - seriesQuery: 'http_requests_total{namespace!="",pod!=""}'
  - metricsQuery: 'sum(rate(<<.Series>>{<<.LabelMatchers>>}[2m])) by (<<.GroupBy>>)'

注意:
  - HPA 查询间隔:30s(默认)
  - PromQL 必须快(< 1s),否则 HPA 卡
  - 用 recording rules 加速
  - scaling 过激可能引发雪崩,加 stabilizationWindowSeconds
```

### 题 7:解释 Prometheus Pull 模型的优劣

```
Pull 模型(Prometheus 主动抓):

优点:
1. 服务发现集中管理:Prometheus 知道所有目标,目标变更只需改 Prom 配置
2. 故障隔离:目标挂了,Prom 抓不到(报 up=0),目标不影响 Prom
3. 主动控制抓取频率:不同 target 不同 interval
4. 缓解"客户端推爆服务端":服务端限速
5. 易调试:curl <target>/metrics 直接看
6. 标签集中:relabel 统一处理
7. 多 Prometheus 抓同一目标( HA,目标无需感知)

缺点:
1. 短生命周期任务难以监控(批处理任务跑完就退出,Prom 可能没抓到)
   - 解决:Pushgateway(临时中转,批处理推到 gateway,Prom 抓 gateway)
2. NAT/防火墙后端难以被抓
   - 解决:SSH 隧道、Pushgateway
3. 大规模时服务发现开销大
   - 解决:分片、Thanos Receive
4. 网络抖动可能丢数据
   - 解决:Prometheus 不会回填,接受短期丢点

vs Push 模型:
  - Push 适合短任务、NAT 后端
  - Pull 适合长运行服务(云原生主流)
  - Prometheus 接受 Pushgateway 作为补充

Pushgateway 使用场景:
  - 批处理 Job(CronJob)
  - 短生命周期 Pod
  - NAT 后端

注意:
  - Pushgateway 不删除数据(除非显式),Job 重跑前要清
  - Pushgateway 自身无 HA(单点)
  - 不适合长运行服务(用 Pull)
```

### 题 8:监控数据与日志数据的边界

```
监控(Prometheus)vs 日志(Loki/ELK):

数据模型:
  监控:时序数值(name + labels + timestamp + value)
  日志:文本事件(timestamp + metadata + message)

数据量:
  监控:GB/天 ~ TB/天(单集群)
  日志:TB/天 ~ PB/天(单集群)

查询:
  监控:PromQL 聚合(sum/rate/histogram_quantile)
  日志:全文检索/LogQL/结构化查询

用途:
  监控:告警、容量、SLO、趋势
  日志:排障、审计、追踪根因

保留:
  监控:15 天 ~ 6 个月
  日志:7 天 ~ 90 天(合规可能更长)

成本:
  监控:低(每样本 1-2 字节)
  日志:高(每事件 100B-1KB)

边界:
  - 监控回答"多少 / 多久 / 多快"(聚合)
  - 日志回答"什么 / 为什么"(个体)
  - 例:
    * 监控:5xx 错误率 5%
    * 日志:第 12345 号请求,用户 A,返回 500,原因 OOM

协同:
  - 监控告警 → 看日志根因
  - Grafana 同时显示指标 + 日志(Exemplar)
  - OpenTelemetry:统一 traces + metrics + logs

实践:
  1. 监控先(告警)
  2. 日志跟进(根因)
  3. 追踪贯穿(跨服务)
  4. 不要混用:
     - 不要把每条请求记成监控指标(基数爆炸)
     - 不要把统计写日志(查询难)
```

## 21.12 故障复盘

### 案例 1:Prometheus OOM 集群监控盲区

**故障时间**:2023-08-15

**故障现象**:
- Prometheus Pod 持续 OOMKilled
- 重启后 10 分钟又 OOM
- 集群监控盲区 2 小时
- 告警丢失(Alertmanager 收不到新告警)

**根因**:
- 业务团队上线新功能,埋点时把 `user_id` 当 label
- 100 万活跃用户 × 5 个 path = 500 万 series
- TSDB Head 内存暴涨至 60GB(原 16GB)
- 触发 OOMKilled

**排查过程**:
1. 看 Prometheus UI → Status → TSDB Status
   - Head series:5M(正常 1M)
2. PromQL 查 series 最多的 metric:
   `topk(10, count by (__name__)({__name__=~".+"}))`
   - 找到 `app_user_actions_total` 有 500 万 series
3. 看 label:`{user_id="12345", ...}`
   - 确认是 user_id 导致高基数

**修复**:
1. 紧急 metric_relabel_configs drop user_id label:
   ```yaml
   metricRelabelConfigs:
   - source_labels: [user_id]
     action: labeldrop
     regex: '(.+)'
   ```
2. 通知业务团队修复埋点(去掉 user_id label)
3. Prometheus 内存临时调到 32GB
4. 加 high cardinality 告警:
   `prometheus_tsdb_head_series > 2000000`

**经验**:
- 应用埋点必须审查 label 设计
- 上线前在 staging 测试 series 数
- Prometheus 加 high cardinality 告警
- 业务方需了解"什么不能当 label"

### 案例 2:TSDB 卡死导致查询全失败

**故障时间**:2023-11-20

**故障现象**:
- Grafana 所有 Dashboard 加载超时
- PromQL 查询全部 timeout
- Prometheus 进程 CPU 100%
- 但抓取正常,告警正常

**根因**:
- 集群升级 K8s 1.27,默认 cgroup v2
- cAdvisor 在 cgroup v2 下产生异常 metric
- 大量 `container_filesystem_reads_total` 等 IO 指标
- 单 Pod 几千 series,导致 TSDB 索引膨胀
- 查询时索引扫描慢,卡死

**排查过程**:
1. Prometheus UI → Status → TSDB Status
   - 索引大小:50GB(正常 5GB)
2. 看抓取目标样本数:
   `scrape_samples_post_metric_relabeling`
   - kubelet/cAdvisor 的样本数 50 万(正常 5 万)
3. 检查 metric:
   - `container_filesystem_*` 系列大量 series
   - cgroup v2 下每个挂载点一个 series

**修复**:
1. metric_relabel drop 文件系统相关指标:
   ```yaml
   metricRelabelConfigs:
   - source_labels: [__name__]
     regex: 'container_filesystem_.*'
     action: drop
   ```
2. 升级 cAdvisor 到支持 cgroup v2 的版本
3. 用 node-exporter 补充节点级 IO 监控
4. 加查询超时配置:`--query.timeout=2m`

**经验**:
- 集群升级前必须在 staging 验证监控
- cgroup v1 → v2 切换影响 cAdvisor
- 关注 `scrape_samples_post_metric_relabeling` 指标
- 索引膨胀比数据膨胀更危险

### 案例 3:抓取超时雪崩

**故障时间**:2024-02-08

**故障现象**:
- 大量 target 显示 DOWN
- Prometheus 日志:scrape timeout
- 抓取队列堆积
- 监控数据大面积丢失

**根因**:
- 业务高峰期,某服务的 /metrics 接口慢(返回 30s)
- 全局 scrape_interval: 15s,scrape_timeout: 10s
- Prometheus 同时抓 1000+ target
- 慢 target 占满抓取 goroutine
- 其它 target 排队,连锁超时

**排查过程**:
1. Prometheus UI → Targets
   - 80% target DOWN
   - lastError: context deadline exceeded
2. 看 slow target:
   - 某服务 /metrics 返回 30s
   - 该服务暴露了 50 万 series(基数大)
3. Prometheus 日志:
   - "scrape pool target alert reached"
   - 抓取队列堆积

**修复**:
1. 紧急隔离慢 target:
   ```yaml
   - job_name: slow-app
     scrape_interval: 60s
     scrape_timeout: 30s
     sample_limit: 5000   # 限制样本数
   ```
2. 业务方优化 /metrics(减少 series)
3. 全局 scrape_interval 调回 30s
4. 加 scrape 超时告警:
   `scrape_duration_seconds > 0.8 * scrape_interval`

**经验**:
- 单 target 慢可拖垮整个 Prometheus
- 必须配 sample_limit 防爆炸
- scrape_timeout < scrape_interval
- 关键与非关键 target 分 job 配置

### 案例 4:告警风暴淹没 oncall

**故障时间**:2024-04-12

**故障现象**:
- 网络故障导致 50 个节点间歇性 NotReady
- 5 分钟收到 800 条告警
- 钉钉群被刷屏
- oncall 工程师漏看关键 P0

**根因**:
- 告警未分组(group_by 缺失)
- 无抑制规则(NodeDown 未抑制 NodeHighCpu)
- 每节点 × 多个告警规则 = 告警风暴
- repeat_interval 太短(15m)

**修复**:
1. Alertmanager 配置分组:
   ```yaml
   route:
     group_by: ['alertname', 'cluster']
     group_wait: 30s
     group_interval: 5m
     repeat_interval: 4h
   ```
2. 加抑制规则:
   ```yaml
   inhibit_rules:
   - source_match: {alertname: "NodeNotReady"}
     target_match_re: {alertname: "Node.*"}
     equal: ["node"]
   ```
3. 调整 for 持续时间:
   - NodeNotReady: for 5m(避免抖动)
4. 告警分级:
   - P0:NodeNotReady(> 5m)→ PagerDuty
   - P1:NodeNotReady(< 5m)→ 钉钉
5. 加告警风暴检测:
   `sum(rate(ALERTS_FOR_STATE[5m])) > 50`

**经验**:
- 告警必须分组 + 抑制
- repeat_interval 不应短于 1 小时
- 关键告警走 PagerDuty(不被刷屏)
- 定期审查告警质量

### 案例 5:metrics-server 故障导致 HPA 失效

**故障时间**:2024-05-30

**故障现象**:
- 业务高峰期,多个服务未自动扩容
- HPA 状态:unable to read metrics
- 服务过载,响应慢

**根因**:
- metrics-server 单副本(资源不足)
- 抓取 5K 节点 kubelet 超时
- metrics-server 卡死
- HPA 拿不到 metrics,不扩容

**排查过程**:
1. kubectl top node 失败
   - 错误:metrics not available
2. kubectl get apiservice | grep metrics
   - v1beta1.metrics.k8s.io → False
3. 看 metrics-server 日志:
   - "context deadline exceeded"
   - 抓取超时

**修复**:
1. metrics-server 扩到 2 副本
2. 资源调高(500m CPU, 1GB 内存)
3. 加 `--kubelet-preferred-address-types=InternalIP`
4. 加超时配置:`--metric-resolution=60s`
5. 加监控:metrics-server 自身指标 + HPA 状态告警

**经验**:
- metrics-server 是 K8s 关键组件,必须 HA
- 监控监控组件本身(元监控)
- HPA 状态需告警
- 关键路径无单点

### 进阶主题

- **OpenTelemetry**:统一 traces + metrics + logs 标准
- **eBPF 监控**:内核级网络/进程监控(Cilium、Pixie)
- **Continuous Profiling**:Pyroscope/Parca 持续性能剖析
- **AI for AIOps**:智能异常检测、告警降噪
- **Edge Monitoring**:边缘集群监控(K3s + 轻量 Prometheus)
- **SRE 实践**:错误预算、SLO 仪表盘、冻结发布机制

### 工具速查

```bash
# Prometheus
kubectl get prometheus -A
kubectl get servicemonitor -A
kubectl get podmonitor -A
kubectl get prometheusrule -A
kubectl get alertmanager -A

# metrics
kubectl top node
kubectl top pod -A
kubectl get apiservice | grep metrics

# PromQL(通过 API)
kubectl exec -n monitoring prometheus-0 -- \
  wget -qO- 'http://localhost:9090/api/v1/query?query=up'

# Alertmanager
amtool alert --alertmanager.url=http://localhost:9093
amtool silence add --alertmanager.url=http://localhost:9093 ...
amtool silence query --alertmanager.url=http://localhost:9093

# Thanos
thanos query --http-address=0.0.0.0:10902 --store=...
thanos tools bucket ls s3://bucket
```
