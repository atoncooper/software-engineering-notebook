# 08 - 调度器

> kube-scheduler 是 K8s 的"HR",决定每个 Pod 落到哪个 Node。本章从两阶段调度到调度框架、亲和性、污点容忍、优先级、抢占、批调度,把调度的全场景讲透。

---

## 1. 问题定义与边界

### 1.1 本章解决什么

- scheduler 怎么从 1000 个 Node 中选 1 个?过滤 + 打分细节?
- 调度框架(Scheduling Framework)的 13 个扩展点是什么?
- 亲和性 / 反亲和性 / 污点 / 容忍 / 拓扑分布怎么用?
- 优先级 + 抢占怎么工作?
- 大规模集群(Gang / 离线混部)怎么扩展?

### 1.2 不解决什么

- 不讲 kubelet 内部(见第 13 章)
- 不讲 Operator 自定义控制器(见第 28 章)
- 不讲 Cluster Autoscaler(见第 10 章)

## 2. 直觉解释

### 2.1 "HR 招聘"类比

```
   新员工(Pod)申请
        │
        ▼
   ┌─────────────────────────────┐
   │ 第 1 步:Filter(过滤)       │  ← HR 初筛
   │ 把不符合硬要求的 Node 去掉  │
   │ - 资源不够 → 去掉           │
   │ - 污点不容忍 → 去掉         │
   │ - 亲和性不符 → 去掉         │
   └────────────┬────────────────┘
                │
                ▼
   ┌─────────────────────────────┐
   │ 第 2 步:Score(打分)        │  ← 面试官评分
   │ 对剩余 Node 打 0-100 分     │
   │ - 资源均衡(LeastAllocated) │
   │ - 镜像已缓存(ImageLocality)│
   │ - 拓扑分布(PodTopologySpread)│
   └────────────┬────────────────┘
                │
                ▼
   ┌─────────────────────────────┐
   │ 第 3 步:Bind(绑定)         │  ← 发 Offer
   │ 选最高分,绑定到 Node        │
   │ 写 Pod.spec.nodeName        │
   └─────────────────────────────┘
```

### 2.2 调度难点

- **资源碎片**:1k 节点但找不到 1 个能跑 8 GPU 的 Pod
- **公平性**:大业务把持资源,小业务等不到
- **拓扑约束**:跨 AZ 分布,避免单 AZ 故障全挂
- **优先级**:关键业务优先,离线可被抢占
- **批调度**:分布式训练 100 个 Pod,要么全调度要么全不调度

## 3. 核心概念

### 3.1 调度流程总览

```
   ┌─────────────────────────────────────────┐
   │ kube-scheduler                          │
   │                                          │
   │ ┌─────────────────────────────────────┐ │
   │ │ Informer                            │ │
   │ │  - Watch Pod (nodeName="")          │ │
   │ │  - Watch Node                       │ │
   │ │  - 本地缓存                          │ │
   │ └────────────┬────────────────────────┘ │
   │              │                            │
   │              ▼                            │
   │ ┌─────────────────────────────────────┐ │
   │ │ Active Queue                        │ │
   │ │  - 待调度 Pod 队列(按优先级)       │ │
   │ └────────────┬────────────────────────┘ │
   │              │                            │
   │              ▼                            │
   │ ┌─────────────────────────────────────┐ │
   │ │ ScheduleOne                         │ │
   │ │  ┌─────────────────────────────┐    │ │
   │ │  │ 1. Filter                    │    │ │
   │ │  │ 2. Score                     │    │ │
   │ │  │ 3. Reserve                   │    │ │
   │ │  │ 4. Permit                    │    │ │
   │ │  │ 5. PreBind                   │    │ │
   │ │  │ 6. Bind                      │    │ │
   │ │  │ 7. PostBind                  │    │ │
   │ │  └─────────────────────────────┘    │ │
   │ └─────────────────────────────────────┘ │
   └─────────────────────────────────────────┘
```

### 3.2 调度框架(Scheduling Framework,1.19+)

13 个扩展点,可在任一点插入自定义插件:

```
   QueueSort     ← 排序 Active Queue
       │
       ▼
   PreFilter     ← 预过滤(检查 Pod 是否可调度)
       │
       ▼
   Filter        ← 过滤不满足的 Node
       │
       ▼
   PostFilter    ← Filter 全部失败时调用(如触发抢占)
       │
       ▼
   PreScore      ← 打分前预处理
       │
       ▼
   Score         ← 打分(可多插件累加)
       │
       ▼
   NormalizeScore ← 标准化分数(0-100)
       │
       ▼
   Reserve       ← 预留资源(防止并发抢)
       │
       ▼
   Permit        ← 是否允许绑定(可延迟,如 Gang 调度)
       │
       ▼
   PreBind       ← 绑定前(如挂 PV)
       │
       ▼
   Bind          ← 实际绑定(写 nodeName)
       │
       ▼
   PostBind      ← 绑定后回调
```

### 3.3 内置插件

| 扩展点 | 内置插件 | 作用 |
|--------|---------|------|
| Filter | NodeUnschedulable | 跳过 cordon 的 Node |
| Filter | TaintToleration | 污点不容忍的 Node |
| Filter | NodeAffinity | nodeSelector / nodeAffinity |
| Filter | PodTopologySpread | 拓扑分布约束 |
| Filter | NodeResourcesFit | 资源是否够 |
| Filter | VolumeRestrictions | PV 拓扑 / 限同一 zone |
| Filter | NodePorts | 端口冲突 |
| Filter | VolumeZone | PV 跨 zone 限制 |
| Score | NodeResourcesFit | LeastAllocated / MostAllocated |
| Score | InterPodAffinity | Pod 亲和性打分 |
| Score | ImageLocality | 镜像已缓存加分 |
| Score | PodTopologySpread | 拓扑分布打分 |
| PostFilter | DefaultPreemption | 触发抢占 |

### 3.4 资源请求与限制

```yaml
resources:
  requests:                    # 调度依据
    cpu: 500m
    memory: 512Mi
    nvidia.com/gpu: 1          # 扩展资源(GPU)
  limits:                      # 运行时限制
    cpu: 1000m
    memory: 1Gi
```

**关键**:
- **调度看 requests,不看 limits**
- 调度器累加 Node 上所有 Pod 的 requests,不能超 Node capacity
- limits 用于 cgroup 限制运行时

**Node 资源**:
```
   Node Capacity      = 16 CPU / 64Gi
   - kubeReserved     = 0.5 CPU / 1Gi
   - systemReserved   = 0.5 CPU / 1Gi
   - evictionThreshold = 0.1 CPU / 100Mi
   = Allocatable      = 14.9 CPU / 61.9Gi
```

调度器看 `Allocatable`,不看 `Capacity`。

### 3.5 nodeSelector 与 nodeAffinity

#### 3.5.1 nodeSelector(简单)

```yaml
spec:
  nodeSelector:
    disktype: ssd
    zone: us-east-1a
```

#### 3.5.2 nodeAffinity(高级)

```yaml
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:    # 硬约束
        nodeSelectorTerms:
        - matchExpressions:
          - key: disktype
            operator: In
            values: [ssd, nvme]
          - key: zone
            operator: In
            values: [us-east-1a, us-east-1b]
      preferredDuringSchedulingIgnoredDuringExecution:   # 软约束
      - weight: 80
        preference:
          matchExpressions:
          - key: cpu-type
            operator: In
            values: [intel]
```

**operator**:
- In / NotIn
- Exists / DoesNotExist
- Gt / Lt(数值比较)

**注意**:
- requiredDuringSchedulingIgnoredDuringExecution:调度时强制,运行时不再检查
- requiredDuringSchedulingRequiredDuringExecution:调度 + 运行时都检查(1.30+ 实验)

### 3.6 Pod 亲和性与反亲和性

```yaml
spec:
  affinity:
    podAffinity:                # 与某些 Pod 在一起
      requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels:
            app: cache
        topologyKey: kubernetes.io/hostname      # 同 Node
    podAntiAffinity:            # 不与某些 Pod 在一起
      requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels:
            app: web
        topologyKey: kubernetes.io/hostname      # 不同 Node
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        podAffinityTerm:
          labelSelector:
            matchLabels:
              app: web
          topologyKey: topology.kubernetes.io/zone  # 跨 zone
```

**用途**:
- podAffinity:Web 与 Cache 同 Node(降低延迟)
- podAntiAffinity:Web 副本跨 Node / 跨 zone(高可用)

**注意**:
- 反亲和性计算开销大,大规模集群(>500 节点)性能下降
- 优先用 PodTopologySpread 替代

### 3.7 污点与容忍(Taint and Toleration)

#### 3.7.1 给 Node 打污点

```bash
kubectl taint nodes node1 dedicated=gpu:NoSchedule
kubectl taint nodes node2 dedicated=gpu:NoExecute
kubectl taint nodes node3 maintenance:NoSchedule
```

**污点效果**:
- NoSchedule:不调度新 Pod(已有的不变)
- PreferNoSchedule:尽量不调度(软约束)
- NoExecute:立即驱逐不容忍的 Pod

#### 3.7.2 Pod 容忍污点

```yaml
spec:
  tolerations:
  - key: "dedicated"
    operator: "Equal"
    value: "gpu"
    effect: "NoSchedule"
  - key: "maintenance"
    operator: "Exists"          # 不管 value
    effect: "NoSchedule"
  - key: "node.kubernetes.io/not-ready"
    operator: "Exists"
    effect: "NoExecute"
    tolerationSeconds: 300      # 容忍 5min 后驱逐
```

**自动污点**:
- `node.kubernetes.io/not-ready`:Node NotReady
- `node.kubernetes.io/unreachable`:Node 失联
- `node.kubernetes.io/memory-pressure`:内存压力
- `node.kubernetes.io/disk-pressure`:磁盘压力
- `node.kubernetes.io/network-unavailable`:网络不可用

### 3.8 PodTopologySpread(拓扑分布)

```yaml
spec:
  topologySpreadConstraints:
  - maxSkew: 1                  # 最大差值
    topologyKey: kubernetes.io/hostname
    whenUnsatisfiable: DoNotSchedule   # 硬约束 / ScheduleAnyway 软约束
    labelSelector:
      matchLabels:
        app: web
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: ScheduleAnyway
    labelSelector:
      matchLabels:
        app: web
```

**含义**:
- maxSkew=1:任意两个 topology domain(如 zone)的 Pod 数差不超过 1
- 优先级:DoNotSchedule > ScheduleAnyway
- 替代 podAntiAffinity,性能更好

### 3.9 优先级与抢占

#### 3.9.1 PriorityClass

```yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: high-priority
value: 1000000
globalDefault: false
description: "Critical production workloads"
preemptionPolicy: PreemptLowerPriority      # 默认值
---
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: low-priority
value: 100
preemptionPolicy: Never                     # 不抢占
```

#### 3.9.2 抢占流程

```
   1. 高优 Pod 调度失败(Filter 全失败)
   2. PostFilter 触发抢占
   3. 找一个 Node:驱逐上面低优 Pod 后,高优 Pod 能调度
   4. 选牺牲 Pod(优先级最低、最少中断)
   5. 驱逐牺牲 Pod(发 DELETE)
   6. 等 Pod 终止 + 资源释放
   7. 高优 Pod 重新调度到该 Node
```

**注意**:
- 抢占有延迟(等牺牲 Pod 优雅终止)
- PodDisruptionBudget 保护:不能违反 PDB 驱逐
- PriorityClass 用得不当会引发雪崩

### 3.10 扩展资源(Extended Resources)

```yaml
# Node 上声明扩展资源
kubectl patch node node1 --patch '{
  "status": {
    "capacity": {
      "nvidia.com/gpu": "4"
    }
  }
}'

# Pod 请求扩展资源
resources:
  limits:
    nvidia.com/gpu: 1
```

**特点**:
- 调度器按扩展资源调度
- kubelet 不感知,需 device plugin 上报
- 常见:GPU / FPGA / SR-IOV VF

## 5. 底层原理

### 5.1 调度器缓存(scheduler cache)

```
   ┌─────────────────────────────────────────┐
   │ kube-scheduler                          │
   │                                          │
   │ ┌─────────────────────────────────────┐ │
   │ │ Cache (本地内存)                    │ │
   │ │  - NodeInfo(每个 Node 的状态)      │ │
   │ │    - 总资源 / 已用 / 可用           │ │
   │ │    - 上面有哪些 Pod                 │ │
   │ │  - PodInfo                          │ │
   │ │  - 假设调度(assumed)               │ │
   │ └─────────────────────────────────────┘ │
   │                                          │
   │ 优点:调度决策快,不依赖 apiserver       │
   │ 缺点:可能与 etcd 不一致(短暂)         │
   └─────────────────────────────────────────┘
```

### 5.2 Reserve 阶段

```
   1. Pod 通过 Filter + Score,选了 Node-A
   2. Reserve:在 cache 中假设调度到 Node-A(扣减资源)
   3. Bind 异步执行(写 apiserver)
   4. Bind 成功:cache 与 etcd 一致
   5. Bind 失败:释放 Reserve(cache 回滚)
```

**作用**:防止并发调度同一 Node 上的资源超卖。

### 5.3 Permit 阶段(批调度)

```
   1. Gang 调度插件:Permit 阶段等待
   2. 收集所有相关 Pod(同 Gang)
   3. 全部就绪 → 批准绑定
   4. 部分就绪 → 等待 / 拒绝
   5. 拒绝 → 释放所有 Reserve
```

**典型应用**:Volcano / Coscheduling(分布式训练)。

### 5.4 PostFilter(抢占)

```go
// 简化逻辑
func PostFilter(pod) {
    for each Node {
        // 找到 Node 上所有低优 Pod
        victims := findLowerPriorityPods(pod, Node)
        // 驱逐 victims 后,pod 能否调度
        if canScheduleAfterRemove(pod, Node, victims) {
            candidates = append(candidates, {Node, victims})
        }
    }
    // 选最少中断 / 最高优 Node
    best := selectBestCandidate(candidates)
    // 驱逐
    for v in best.victims {
        evictPod(v)
    }
    // 重新调度 pod
    schedulePod(pod)
}
```

## 6. 配置示例

### 6.1 生产级 Deployment(完整调度约束)

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
spec:
  replicas: 6
  selector:
    matchLabels:
      app: web-app
  template:
    metadata:
      labels:
        app: web-app
    spec:
      affinity:
        # 1. Node 亲和:必须在 SSD + 特定 zone
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: disktype
                operator: In
                values: [ssd, nvme]
              - key: topology.kubernetes.io/zone
                operator: In
                values: [us-east-1a, us-east-1b, us-east-1c]
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 80
            preference:
              matchExpressions:
              - key: cpu-type
                operator: In
                values: [intel]
          - weight: 50
            preference:
              matchExpressions:
              - key: network
                operator: In
                values: [10gbps]
        
        # 2. Pod 反亲和:副本分散到不同 Node
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
          - labelSelector:
              matchLabels:
                app: web-app
            topologyKey: kubernetes.io/hostname
      
      # 3. 拓扑分布:跨 zone 均匀
      topologySpreadConstraints:
      - maxSkew: 1
        topologyKey: topology.kubernetes.io/zone
        whenUnsatisfiable: DoNotSchedule
        labelSelector:
          matchLabels:
            app: web-app
      
      # 4. 容忍污点
      tolerations:
      - key: "node.kubernetes.io/not-ready"
        operator: "Exists"
        effect: "NoExecute"
        tolerationSeconds: 300
      - key: "node.kubernetes.io/unreachable"
        operator: "Exists"
        effect: "NoExecute"
        tolerationSeconds: 300
      
      # 5. 优先级
      priorityClassName: high-priority
      
      # 6. 资源
      containers:
      - name: app
        image: web-app:v1.0
        resources:
          requests:
            cpu: 500m
            memory: 512Mi
          limits:
            cpu: 1000m
            memory: 1Gi
```

## 7. 常见陷阱与调优 ⚠️

### 7.1 资源调度陷阱

| 陷阱 | 现象 | 根因 | 解决 |
|------|------|------|------|
| **资源碎片** | 大 Pod 调度不上 | requests 累加超 Allocatable | 节点池分规格 / 调整 Pod 大小 |
| **CPU 超卖** | 节点 CPU 100% | limits > requests,导致超卖 | 关键业务 limits=requests |
| **内存超卖** | OOM 频繁 | 同上 | 内存 limits=requests |
| **GPU 调度失败** | Pod 卡 Pending | GPU 不够 / device plugin 异常 | 看 nvidia-device-plugin |

### 7.2 亲和性陷阱

| 陷阱 | 现象 | 根因 | 解决 |
|------|------|------|------|
| **podAntiAffinity 性能差** | 调度慢 | 反亲和计算 O(n) | 改 PodTopologySpread |
| **亲和性过严** | Pod 卡 Pending | topologyKey 写错 | 检查 label |
| **跨 zone 失败** | Pod 都到同一 zone | topologyKey 配置错 | 用 topology.kubernetes.io/zone |

### 7.3 污点陷阱

| 陷阱 | 现象 | 根因 | 解决 |
|------|------|------|------|
| **污点不容忍** | Pod 卡 Pending | Node 有污点 | 加 tolerations |
| **NoExecute 误用** | Pod 大量驱逐 | NoExecute 立即驱逐 | 用 NoSchedule |
| **污点残留** | Node 仍不可调度 | 忘删污点 | `kubectl taint nodes node1 key-` |

### 7.4 抢占陷阱

| 陷阱 | 现象 | 根因 | 解决 |
|------|------|------|------|
| **抢占雪崩** | 大量 Pod 被驱逐 | 优先级配置混乱 | 严格优先级设计 |
| **PDB 失效** | 抢占违反 PDB | PDB 配置错 / 抢占不尊重 PDB | 检查 PDB + minAvailable |
| **抢占卡住** | 高优 Pod 也 Pending | 牺牲 Pod 优雅终止慢 | 降 grace period |

### 7.5 大规模集群陷阱

| 陷阱 | 现象 | 根因 | 解决 |
|------|------|------|------|
| **调度延迟高** | Pod Pending 几分钟 | 调度器串行 + 节点多 | 启用并行调度 / 调度器分片 |
| **Informer 同步慢** | 节点状态不一致 | 节点多 + Watch 延迟 | 调度器分片 / KubeZoo |
| **Score 计算慢** | Pod 排队 | podAntiAffinity 计算量大 | 改 PodTopologySpread |

## 11. 综合面试题

### 11.1 基础题

**Q1**: 描述 K8s 调度器的两阶段调度。

**答题要点**:
- Filter:过滤不满足硬约束的 Node(资源 / 污点 / 亲和性)
- Score:对剩余 Node 打分(0-100),多插件累加
- Reserve:在 cache 中预留资源
- Bind:异步绑定到 Node(写 nodeName)

**Q2**: nodeSelector / nodeAffinity / podAntiAffinity 区别?

**答题要点**:
- nodeSelector:简单等值匹配
- nodeAffinity:支持 In/NotIn/Exists + 软约束(preferred)
- podAntiAffinity:基于其他 Pod 的位置,避免同 Node/zone

### 11.2 进阶题

**Q3**: 一个 Pod 卡 Pending,怎么排查?

**答题要点**:
1. `kubectl describe pod` 看 Events,常见:
   - Insufficient cpu/memory:资源不足
   - node(s) had untolerated taint:污点不容忍
   - didn't match node selector:亲和性不符
   - node(s) didn't match PodTopologySpread:拓扑约束
2. 检查节点资源:`kubectl top nodes` / `kubectl describe node`
3. 检查污点:`kubectl get nodes -o custom-columns=NAME:.metadata.name,TAINTS:.spec.taints`
4. 检查节点标签:`kubectl get nodes --show-labels`
5. 解决:
   - 加节点 / 降 requests
   - 加 tolerations
   - 改 nodeSelector
   - 调整 PodTopologySpread maxSkew

**Q4**: 抢占机制怎么工作?有什么风险?

**答题要点**:
- 触发:高优 Pod 调度失败
- PostFilter:找低优 Pod 驱逐后,高优 Pod 能调度的 Node
- 选择牺牲 Pod:最低优 + 最少中断 + 不违反 PDB
- 驱逐:发 DELETE,等优雅终止
- 重新调度:高优 Pod 重试
- 风险:
  - 雪崩:优先级配置混乱,连环抢占
  - 资源浪费:驱逐过程中资源空转
  - 服务中断:被驱逐的 Pod 影响业务
- 防范:
  - 严格优先级设计(高/中/低/批)
  - PDB 保护关键业务
  - 监控抢占频率

### 11.3 高级题

**Q5**: 设计一个 K8s 集群的节点池策略,支撑多业务(在线 / 离线 / GPU)。

**答题要点**:
- **节点池划分**:
  - 在线池:高配 CPU + 大内存,Guaranteed QoS
  - 离线池:中配,BestEffort + 低优
  - GPU 池:GPU 节点,污点隔离
  - 系统池:DaemonSet / 监控专用,taint 系统专用
- **调度策略**:
  - 在线业务:nodeAffinity → 在线池 + 高优 PriorityClass
  - 离线业务:nodeAffinity → 离线池 + 低优
  - GPU 业务:nodeSelector accelerator=gpu + 污点容忍
  - 系统组件:DaemonSet + tolerations
- **混部**(可选):
  - 同节点跑在线 + 离线
  - 在线 Guaranteed,离线 BestEffort
  - 资源回收:CPU / 内存 / IO 实时隔离
  - 离线 Pod 可被驱逐
- **自动伸缩**:
  - Cluster Autoscaler 按池扩缩
  - 在线池优先扩容
  - 离线池夜间扩,白天缩
- **监控**:
  - 各池资源利用率
  - 在线 P99 延迟
  - 离线 Pod 驱逐率

**Q6**: 大集群(5000+ 节点)调度器性能怎么优化?

**答题要点**:
1. **调度器分片**:多 scheduler 实例,每个负责部分 namespace / node
2. **并行调度**:启用 `--parallelism=64`,多 Pod 并发调度
3. **cache 优化**:增大调度器 cache,降低 apiserver 查询
4. **避免 podAntiAffinity**:大规模计算量大,改用 PodTopologySpread
5. **禁用不用的插件**:调度框架配置,去掉无用插件
6. **预过滤优化**:PreFilter 阶段提前过滤明显不行的 Node
7. **节点池分片**:不同业务用不同节点池,调度器只看部分 Node
8. **Volcano / Koordinator**:大厂扩展调度器,优化大规模场景

### 11.4 设计题

**Q7**: 设计一个分布式训练任务的调度方案,要求 1000 个 Pod 同时调度。

**答题要点**:
- **Gang 调度**:Volcano PodGroup,minMember=1000
- **资源预留**:全部 Pod 通过 Filter 后才 Bind
- **失败重试**:整组失败重试
- **拓扑约束**:
  - 跨机架(PodTopologySpread topologyKey=topology.kubernetes.io/zone)
  - 但同区域内(降低 RDMA 跨区域开销)
- **网络**:InfiniBand / RDMA,节点亲和性
- **优先级**:高优,防止被抢占
- **资源**:
  - GPU:每 Pod 1-8 GPU
  - CPU / 内存:配足
- **容错**:
  - Pod 失败:Checkpoint + 重启
  - 节点故障:重新调度整组
- **监控**:训练进度 / Loss / GPU 利用率

## 12. 故障复盘

### 12.1 案例 1:优先级配置混乱导致抢占雪崩

**业务影响**:2023 年某公司,新业务用 PriorityClass=1000000(误以为是低),把所有老业务(默认 PriorityClass=0)全驱逐了。

**根因**:
- 优先级 value 越大越优先,新人理解反
- 没有优先级使用规范
- 抢占连锁(老业务被驱逐,新业务又调度)

**修复过程**:
1. 紧急:删除错误 PriorityClass
2. 业务恢复(老业务重新调度)
3. 制定优先级规范:
   - 系统级:1000000+(kube-system)
   - 关键业务:900000-999999
   - 一般业务:100000-899999
   - 离线 / 批处理:0-99999

**防范**:
- 优先级文档化
- PriorityClass 创建需审批
- 监控抢占事件,异常告警

### 12.2 案例 2:podAntiAffinity 导致调度卡死

**业务影响**:2022 年某公司,Web 应用 6 副本,但集群只有 5 节点,第 6 个 Pod 一直 Pending。

**根因**:
- podAntiAffinity required:每个 Pod 必须独占一个 Node
- 5 节点只能跑 5 副本,第 6 个无 Node 可用
- 业务方误以为可以扩

**修复过程**:
1. 紧急:加节点
2. 改 podAntiAffinity 为 preferred(软约束)
3. 业务方可扩副本

**防范**:
- 反亲和性配置时考虑节点数
- 用 PodTopologySpread 替代(maxSkew 可调)
- 监控 Pending Pod,告警

### 12.3 案例 3:污点误删导致业务调度到 GPU 节点

**业务影响**:2024 年某公司,运维误删 GPU 节点的污点,普通 Pod 调度到 GPU 节点,占用 GPU 资源。

**根因**:
- 污点管理不规范
- 没有定期校验污点配置

**修复过程**:
1. 紧急:重新打污点
2. 已调度 Pod 优雅驱逐
3. GPU 业务恢复

**防范**:
- 污点用 IaC 管理(Terraform / Ansible)
- 定期巡检污点配置
- 关键节点用 nodeAffinity 双重保护
