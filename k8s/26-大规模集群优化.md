## 26.1 问题定义与边界

### 26.1.1 本章解决什么

K8s 单集群从 1000 节点 → 5000 节点 → 10000 节点的演进中,会遇到一连串瓶颈:

- 为什么官方默认软上限是 **单集群 5000 节点**?这个数字从哪儿来?
- etcd 数据库从 1GB 涨到 50GB,为什么 apiserver 开始 5xx?怎么调?
- apiserver QPS 上万后,如何防止某租户把控制面打挂?APF 怎么配?
- Watch 延迟从 100ms 飙到 5s,Pod 创建卡住,根因是什么?
- 调度器 throughput 从 100 Pods/s 掉到 10 Pods/s,卡在哪儿?
- kubelet PLEG 超时,节点 NotReady,Pod 被批量 Evict,怎么救?
- 大规模集群的 DNS、网络、存储、监控,每一项都有专门的优化路径?

**本章解决**:

> 用 **控制面瓶颈建模 + etcd/APIServer/调度器/kubelet 分层调优 + 网络存储可观测性配套 + 工业基准数据** 的方式,把单集群从 1K 节点推到 5K(甚至 10K)节点的工程路径讲透,并给出何时该切到多集群的判断框架。

**解决**:

- 单集群可扩展性阈值的来源与突破方式
- etcd 8 维调优(磁盘 / quota / auto-compaction / defrag / mlock / heartbeat / election / db size)
- APF(API Priority and Fairness)完整机制(FlowSchema + PriorityLevelConfiguration + 队列 + 公平性)
- APIServer Watch Cache 机制与缓存穿透问题
- kube-scheduler 扩展(Scheduling Framework、Profile、Plugin、Extender、Multiple Schedulers)
- Volcano 批调度(Gang Scheduling、Queue、PodGroup)与 Kueue / YuniKorn 对比
- kubelet 优化(PLEG、CPU Manager static、Topology Manager、Memory Manager、Kubelet QoS)
- 大规模网络优化(IPVS 模式、NodeLocalDNS、Conntrack 表、Cilium eBPF)
- 大规模存储优化(多 CSI、Volume Attachment 限流、快照后端)
- 大规模可观测性优化(Thanos / Cortex / Mimir、采样、分区 Prometheus)

**不解决**:

- **多集群管理** → 见 [24-集群运维](./24-集群运维.md)(Karmada / Cluster API / KubeFed)
- **大厂平台总览** → 见 [25-大厂K8s平台](./25-大厂K8s平台.md)(阿里 ACK / 字节 TCE / GKE / EKS)
- **故障复盘** → 见 [29-故障复盘集](./29-故障复盘集.md)(etcd 雪崩、调度器死锁等事故根因)
- **成本与容量** → 见 [30-成本与容量规划](./30-成本与容量规划.md)(FinOps、混部)
- **CRD / Operator** → 见 [27-CRD与Operator生态](./27-CRD与Operator生态.md)

## 26.2 直觉解释

把大规模 K8s 集群想象成 **一座大型医院**:

| 大型医院 | 大规模 K8s |
|----------|-----------|
| 门诊量从 1K 人/天 → 50K 人/天 | 节点从 1K → 5K → 10K |
| 挂号处(前台)排长队 | apiserver QPS 飙升 |
| 病历室(etcd)档案堆满 | etcd 数据库涨到 50GB |
| 通知板(Watch)更新滞后 | Watch 延迟从 100ms → 5s |
| 调度护士(scheduler)忙不过来 | 调度 throughput 下降 |
| 病房护士(kubelet)手忙脚乱 | PLEG 超时、节点 NotReady |
| 急诊优先 vs 普通门诊 | APF 优先级队列 |
| 分诊台(FlowSchema)分类 | 按 user/resource/verb 分流 |
| 限流器(每科室配额) | PriorityLevelConfiguration |
| 病历室定期归档 | etcd compaction + defrag |
| 病历室锁定内存 | etcd mlock |
| 大医院分院(多集群) | 单集群到上限后拆分 |

**关键直觉**:

1. **规模 → 数据量 → 控制面压力**:节点数 × Pod 数 × Event 数 × Watch 数 = 控制面负载。5K 节点 × 200 Pod/节点 = 1M Pod,每个 Pod 20+ 个 Event,etcd 里光 Event 就 2000 万条。
2. **etcd 是天花板**:etcd 的 Raft 写入需要 quorum,任何写都要落盘 + 复制。单 etcd 集群 QPS 上限 ~10K,5K 节点集群轻松打满。
3. **APIServer 是网关**:所有请求都过 apiserver,没有 APF 时,某租户一个 LIST Pod 全集就能把控制面打挂。
4. **Watch 是双刃剑**:Watch 让控制器近实时感知变化,但 5K 节点上每个组件都 Watch,Watch 缓存一旦穿透就回源 etcd,雪崩。
5. **调度器是漏斗**:默认调度器单实例 ~100 Pods/s,5K 节点滚动更新一次 50K Pod,调度器要 500 秒才能消化,必须分片或扩展。
6. **kubelet 是末端**:5K 节点 = 5K 个 kubelet,每个 kubelet 都在 List-Watch + 上报状态。任何一个慢了,Node NotReady,Pod 被批量 Evict。
7. **网络是隐形杀手**:5K 节点的 Service 数 10万+,iptables 模式 kube-proxy 重写一次要 5 分钟;DNS QPS 上百万;Conntrack 表爆满丢包。
8. **可观测性自身需要扩展**:Prometheus 抓 5K 节点 + 1M Pod,series 数 30M+,单实例必爆,必须分区 + 长期存储。
9. **没有银弹**:单集群 10K 节点不是不可能,而是工程代价指数级上升,**多集群** 通常更经济。

## 26.3 核心概念与架构

### 26.3.1 控制面瓶颈模型

```
                  ┌───────────────────────────────────────────────┐
                  │           大规模集群控制面瓶颈模型             │
                  └───────────────────────────────────────────────┘

   ┌────────┐  QPS  ┌────────────┐  Watch  ┌──────────┐  Watch  ┌──────────┐
   │ kubectl│──────▶│            │────────▶│          │────────▶│controller│
   │ CI/CD  │       │            │         │          │         │ -manager │
   │ 用户   │       │            │         │          │         └──────────┘
   └────────┘       │  APIServer │         │   etcd   │                    │
                    │            │  Watch  │          │  Watch  ┌──────────┐
   ┌────────┐  QPS  │            │────────▶│          │────────▶│ scheduler│
   │kubelet │──────▶│            │         │          │         │          │
   │ (5K个) │       │            │         │          │         └──────────┘
   └────────┘       └─────┬──────┘         └────┬─────┘                    │
        ▲                 │                     │                          │
        │ Watch            │ Watch              │ 写入                     │
        │                 ▼                     ▼                          │
        │           ┌────────────┐        ┌──────────┐                     │
        │           │ Watch Cache│        │  Raft    │                     │
        │           │ (内存)     │        │  Quorum  │                     │
        │           └────────────┘        └──────────┘                     │
        │                                                                   │
        └───────────────────── 上报状态 (List/Watch) ◀──────────────────────┘

   瓶颈点:
   1. etcd Raft 写入:每写都要 quorum 落盘,单集群 ~10K QPS 上限
   2. etcd DB Size:超过 8GB 性能下降,超过 quota 只读
   3. APIServer Watch Cache:每个 resource 一份缓存,LIST 穿透回源
   4. APIServer 限流:默认 400 QPS,无 APF 时整集群共享
   5. 调度器单实例:~100 Pods/s,锁竞争 + cache 失效
   6. kubelet PLEG:每秒 relist,容器多时卡死
   7. kube-proxy:iptables 重写 5K 节点要分钟级
   8. CoreDNS:每 Pod 几十次解析,5K 节点 QPS 上百万
   9. Prometheus:30M+ series,单实例必爆
```

### 26.3.2 K8s 可扩展性阈值(官方)

K8s 社区 [Scaling Performance](https://github.com/kubernetes/community/blob/master/sig-scalability/configs-and-limits/thresholds.md) 给出 **官方可扩展性阈值**:

| 维度 | 阈值 | 来源 |
|------|------|------|
| 单集群节点数 | 5,000 | SLA:Pod 启动 P99 < 5s |
| 单集群 Pod 数 | 150,000 | 5K 节点 × 30 Pod/节点 |
| 单集群容器数 | 300,000 | 150K Pod × 2 容器/Pod |
| 单集群 Service 数 | 5,000 | Endpoints 上限 |
| 单集群 Pod/Service 端点 | 50,000(单 Service)| EndpointSlice 默认 1000 端点/片 |
| 单命名空间 Pod 数 | 10,000(软)| 默认 5000,可调 |
| 单节点 Pod 数 | 110 | 默认 CIDR 限制 + kubelet |
| 单 Pod 容器数 | 无硬限 | 实践 < 10 |
| etcd 数据库大小 | 8GB(推荐)| quota 8GB,超只读 |
| etcd 集群成员数 | 3 / 5 / 7 | 推荐 5(容 2 故障)|
| apiserver QPS | 单实例 ~5K | 多副本扩展 |
| scheduler throughput | ~100 Pods/s | 单实例默认 |

**5K 节点阈值的来源**:

1. **etcd**:5K 节点 + 150K Pod,每 Pod 20+ Event,etcd 数据库涨到 50GB+(默认 quota 8GB 必爆)
2. **APIServer Watch Cache**:5K 节点每节点 110 Pod = 550K Pod,LIST 一次 Pod 全集要 30s+,Watch Cache 内存 10GB+
3. **scheduler**:5K 节点滚动更新一次 50K Pod,默认调度器要 500s,违反 P99 < 5s SLO
4. **kubelet**:5K kubelet 同时 List-Watch,apiserver 负载 50K QPS+
5. **kube-proxy**:5K 节点 Service 5万+,iptables 重写一次要分钟级,导致 Service 不可达

**突破阈值的方式**:

| 阈值 | 突破方式 |
|------|----------|
| etcd DB | events 单独 etcd + auto-compaction + defrag |
| etcd QPS | apiserver Watch Cache + cache 复用 |
| apiserver QPS | 多副本 + APF 限流 + sharded apiserver |
| scheduler throughput | 分片调度器 + Volcano + 自研调度器 |
| kubelet PLEG | 改造 PLEG(事件驱动)+ 批量上报 |
| kube-proxy | 切 IPVS / Cilium eBPF |
| CoreDNS | NodeLocalDNS + 多副本 + 缓存 |
| Prometheus | 分区 + Thanos 长期存储 |

### 26.3.4 APF(API Priority and Fairness)

**APF 是 K8s 1.20+ GA 的限流机制**,替代了早期的 max-in-flight。核心思想:

> 把 API 请求按 **优先级** 分成多个等级,每个等级有独立的队列和令牌桶,保证高优先级请求不被低优先级拖垮,同一优先级内按 Flow 公平分配。

```
                      ┌─────────────────────────────┐
                      │       Incoming Request      │
                      └──────────────┬──────────────┘
                                     │
                                     ▼
                      ┌─────────────────────────────┐
                      │    FlowSchema 匹配          │
                      │  (按 user/group/resource/   │
                      │   namespace/verb 分类)      │
                      └──────────────┬──────────────┘
                                     │
            ┌────────────────────────┼────────────────────────┐
            ▼                        ▼                        ▼
   ┌─────────────────┐    ┌─────────────────┐    ┌─────────────────┐
   │ PriorityLevel   │    │ PriorityLevel   │    │ PriorityLevel   │
   │   "exempt"      │    │   "system"      │    │   "default"     │
   │ (kubelet/etcd)  │    │ (controller)    │    │ (普通用户)      │
   └────────┬────────┘    └────────┬────────┘    └────────┬────────┘
            │                      │                      │
            │ 不限流                ▼                      ▼
            │            ┌──────────────────┐   ┌──────────────────┐
            │            │ Queue + Token    │   │ Queue + Token    │
            │            │ Bucket           │   │ Bucket           │
            │            │                  │   │                  │
            │            │ assured seats=50 │   │ assured seats=10 │
            │            │ queue length=128 │   │ queue length=64  │
            │            │ QPS=100          │   │ QPS=10           │
            │            │ burst=200        │   │ burst=20         │
            │            └────────┬─────────┘   └────────┬─────────┘
            │                     │                      │
            └─────────────────────┼──────────────────────┘
                                  ▼
                      ┌─────────────────────┐
                      │   etcd 写入         │
                      └─────────────────────┘
```

**两个核心 CRD**:

1. **FlowSchema**:把请求分类到 PriorityLevel
   - 按 user / group / resource / namespace / verb 匹配
   - 一个请求匹配第一个 FlowSchema(distinguish)
   - 规则:`exempt` > `system` > `node` > `kube-system` > `global-default`

2. **PriorityLevelConfiguration**:定义某个优先级的行为
   - type: `Limited`(限流)/ `Exempt`(不限)
   - limited:
     - `assuredConcurrencyShares`(并发配额,类似权重)
     - `queueLengthLimit`(队列长度)
     - `limitResponse`:`Queue`(排队)或 `Reject`(拒绝)
   - queue 模式下用 **公平排队(Weighted Fair Queuing,WFQ)** 保证 flow 间公平

**默认 FlowSchema**(K8s 1.30):

| FlowSchema | PriorityLevel | 说明 |
|------------|---------------|------|
| exempt | exempt | 系统紧急请求(系统 masters、healthz) |
| system | system | kube-system 命名空间请求 |
| node | node | kubelet 上报状态 |
| leader-election | leader-election | leader election 请求 |
| workload-high | workload-high | controller 高优先级 |
| workload-low | workload-low | controller 低优先级 |
| global-default | global-default | 其他所有请求 |

```
   │                               │  │ Watcher List    │  │    │
   │                               │  │ (per client)    │  │    │
   │                               │  └─────────────────┘  │    │
   │                               └───────────┬───────────┘    │
   │                                           │                │
   │   ┌───────────────────┐                   │                │
   │   │ APIServer Watch   │ ◀── event ────────┘                │
   │   │ Handler           │                                    │
   │   └───────────────────┘                                    │
   │                                                             │
   └─────────────────────────────────────────────────────────────┘

   关键机制:
   1. Cacher 启动时 LIST 全量到 cache(按 resourceVersion 排序)
   2. 之后所有 Watch 从 cache 取,不回源 etcd
   3. etcd Watch 推送增量,cacher 更新 cache
   4. 客户端 Watch 带个 RV,cacher 从该 RV 之后推送
   5. 如果 RV 太老(超过 cache 历史),cacher 拒绝,客户端必须重新 LIST

   穿透问题:
   - LIST 不带 resourceVersion=0 → 强一致读,回源 etcd
   - LIST 带 resourceVersion=""  → 同上
   - LIST 带 resourceVersion=0   → 从 cache 读(快)
   - 但 cache miss 时仍回源 etcd

   cache 容量:
   - 默认缓存最近 1000 个事件
   - 超过会强制客户端重新 LIST(代价大)
   - 5K 节点集群 Pod 事件量 > 1000/秒,cache 很容易穿透
```

### 26.3.6 调度器扩展机制

**K8s 调度器从 1.19 开始全面转向 Scheduling Framework**,旧的调度器扩展(Scheduler Extender)已不推荐。

```
   ┌────────────────────────────────────────────────────────────────────┐
   │              kube-scheduler Scheduling Framework                   │
   │                                                                    │
   │   每个方块都是一个扩展点,可用自定义插件替换或追加                  │
   ├────────────────────────────────────────────────────────────────────┤
   │                                                                    │
   │   QueueSort ──▶ PreFilter ──▶ Filter ──▶ PostFilter ──▶ PreScore  │
   │      │            │           │           │              │        │
   │      │            ▼           ▼           ▼              ▼        │
   │      │      (过滤不满足  (打分前的  (过滤失败后            (打分前) │
   │      │       硬条件的)   检查)       抢占逻辑)                      │
   │      ▼                                                              │
   │   (待调度队列排序)                                                  │
   │                                                                      │
   │   ──▶ Score ──▶ NormalizeScore ──▶ Reserve ──▶ Permit ──▶ PreBind │
   │       │            │                  │          │          │     │
   │       │            ▼                  ▼          ▼          ▼     │
   │       │       (分数归一化)        (预留资源)  (等待,如     (绑定前 │
   │       │                              Gang)        hook)          │
   │       ▼                                                              │
   │   (节点打分)                                                        │
   │                                                                      │
   │   ──▶ Bind ──▶ PostBind                                             │
   │       │         │                                                    │
   │       ▼         ▼                                                    │
   │   (绑定)     (绑定后清理)                                            │
   │                                                                      │
   └────────────────────────────────────────────────────────────────────┘

   13 个扩展点:
   1. QueueSort:        待调度 Pod 队列排序(默认按优先级 + 创建时间)
   2. PreFilter:        过滤前预处理(如计算 Pod 总资源需求)
   3. Filter:           节点过滤(硬条件,如资源不够、污点不容忍)
   4. PostFilter:       过滤失败后执行(如抢占)
   5. PreScore:         打分前预处理
   6. Score:            节点打分(软条件,如镜像已缓存)
   7. NormalizeScore:   分数归一化(0-100)
   8. Reserve:          预留资源(简化多 Pod 调度时的资源竞争)
   9. Permit:           允许/拒绝/延迟 Bind(Gang Scheduling 用)
   10. PreBind:         绑定前 hook(如挂载 Volume)
   11. Bind:            实际绑定(写 Pod.spec.nodeName)
   12. PostBind:        绑定后清理
   13. Unreserve:       Permit 拒绝后释放预留资源
```

**多种扩展方式对比**:

| 方式 | 说明 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|----------|
| **Scheduler Framework Plugin** | 编译进调度器的 Go 插件 | 性能最好,灵活 | 需重新编译调度器 | 大规模、性能敏感 |
| **Scheduler Plugin (Webhook)** | HTTP 扩展点 | 无需编译 | 网络延迟,序列化开销 | 中等规模,快速迭代 |
| **Multiple Schedulers** | 部署多个调度器 | 完全独立 | 资源竞争(都看同一节点) | 不同业务用不同策略 |
| **Volcano / YuniKorn** | 替换默认调度器 | Gang / Queue | 与默认不兼容 | 批处理、AI 训练 |
| **Kueue** | 在默认调度器上层加队列 | 不替换调度器 | 多一层抽象 | 批处理作业排队 |

### 26.3.7 Volcano 批调度

**Volcano**(原 kube-batch)是华为开源的 **批调度器**,核心解决 **Gang Scheduling**(gang 调度)问题:一组 Pod 必须全部调度成功,否则全部失败。

```
   ┌─────────────────────────────────────────────────────────────┐
   │                  Volcano 架构                              │
   ├─────────────────────────────────────────────────────────────┤
   │                                                             │
   │   ┌──────────────┐  ┌──────────────┐  ┌──────────────┐    │
   │   │   PodGroup   │  │    Queue     │  │   Command    │    │
   │   │  (一组 Pod)  │  │ (资源池)     │  │ (vcctl CLI)  │    │
   │   └──────┬───────┘  └──────┬───────┘  └──────────────┘    │
   │          │                 │                                 │
   │          └─────────┬───────┘                                │
   │                    ▼                                         │
   │          ┌──────────────────┐                                │
   │          │ Volcano Scheduler│                                │
   │          │  (替代/共存默认) │                                │
   │          │                  │                                │
   │          │ - Gang: 全或无   │                                │
   │          │ - Queue: 资源池  │                                │
   │          │ - Plugin:        │                                │
   │          │   * binpack      │                                │
   │          │   * drf          │                                │
   │          │   * predicates   │                                │
   │          │   * proportion   │                                │
   │          │   * gang         │                                │
   │          │   * tdm          │                                │
   │          └──────────────────┘                                │
   │                                                             │
   └─────────────────────────────────────────────────────────────┘

   Gang Scheduling 流程:
   1. 用户提交 Job(如 100 个 worker 的训练任务)
   2. Volcano 创建 PodGroup,minAvailable=100
   3. 调度器检查:能否同时调度 100 个 Pod?
      - 是 → 全部 Bind
      - 否 → 全部 Pending,等资源
   4. 避免部分 Pod 调度成功但训练无法启动(浪费资源)
```

**PodGroup 关键字段**:

```yaml
apiVersion: scheduling.volcano.sh/v1beta1
kind: PodGroup
metadata:
  name: train-job-pg
spec:
  minMember: 100              # 最少调度 100 个 Pod 才能启动
  minResources:
    cpu: "200"
    memory: "400Gi"
    nvidia.com/gpu: "100"
  queue: training-queue       # 所属队列
  priorityClassName: high
  schedulerName: volcano       # 用 volcano 调度
```

## 26.5 底层原理

### 26.5.1 etcd MVCC + Raft + Quota

#### 26.5.1.1 etcd MVCC 多版本

```
   etcd 是 KV 存储,但每个 key 有多个历史版本:

   ┌────────────────────────────────────────────────────────────┐
   │  Key: /registry/pods/default/nginx-pod                    │
   ├────────────────────────────────────────────────────────────┤
   │  rev=1000  create                                          │
   │  rev=1005  update status=Running                           │
   │  rev=1010  update labels                                   │
   │  rev=1015  update status=Ready                             │
   │  ...                                                       │
   │  rev=789456 latest                                         │
   └────────────────────────────────────────────────────────────┘

   为什么要 MVCC:
   - Watch 需要历史版本(从某个 RV 之后推送)
   - 事务需要 compare-and-swap
   - 一致性读(线性一致)需要读最新版本

   问题:历史版本无限增长 → DB 爆满
   解决:
   - auto-compaction:定期删除旧版本(保留 1h)
   - defrag:物理释放空间
```

#### 26.5.1.2 Raft 共识

```
   etcd 用 Raft 保证多副本一致:

   ┌──────────┐   Vote   ┌──────────┐   Vote   ┌──────────┐
   │  etcd1   │◀────────▶│  etcd2   │◀────────▶│  etcd3   │
   │ (Leader) │          │(Follower)│          │(Follower)│
   └────┬─────┘          └──────────┘          └──────────┘
        │
        │ AppendEntries(日志复制)
        ▼
   ┌──────────┐          ┌──────────┐          ┌──────────┐
   │  etcd1   │─────────▶│  etcd2   │          │  etcd3   │
   │ (Leader) │─────────▶│          │          │          │
   └──────────┘          └──────────┘          └──────────┘
        │
        │ 一旦 majority(quorum)确认,commit
        ▼
   写入 MVCC,返回客户端 OK

   关键参数:
   - heartbeat-interval:Leader 心跳间隔(默认 100ms)
   - election-timeout:Follower 没收到心跳的超时(默认 1000ms)
   - 跨 AZ 延迟高,默认值易触发 leader 选举

   Raft 写入流程(每次写都要):
   1. 客户端发送写请求到 Leader
   2. Leader 写 raft log(本地 wal)
   3. Leader 复制 log 到所有 Follower
   4. 等待 majority(quorum)确认
   5. Leader commit,应用到 MVCC
   6. 返回客户端 OK

   性能瓶颈:
   - 每次写都要 fsync(wal 落盘)
   - 每次写都要网络往返(majority 确认)
   - 单集群 QPS 上限 ~10K(SSD + 3 副本)
```

#### 26.5.1.3 Quota 与 NOSPACE alarm

```
   etcd 有两种 alarm:
   - NOSPACE:DB size 接近 quota,触发只读
   - NO_SPACE:磁盘满,无法写 wal

   NOSPACE 触发条件:
   - etcd_mvcc_db_total_size_in_bytes >= quota-backend-bytes

   影响:
   - etcd 进入只读模式
   - 任何写操作返回 503 Service Unavailable
   - apiserver 所有写操作失败(创建 Pod/Service/... 全挂)

   恢复:
   1. etcdctl compact --rev=<latest>
   2. etcdctl defrag(每个成员轮流)
   3. etcdctl alarm disarm

   监控指标:
   - etcd_mvcc_db_total_size_in_bytes(DB 当前大小)
   - etcd_server_quota_backend_bytes(quota)
   - etcd_server_alarm_triggered{alarm=NOSPACE}
```

### 26.5.2 APIServer Watch Cache + APF

#### 26.5.2.1 Cacher 源码流程

```
   APIServer 启动时,每个 resource 启动一个 Cacher:

   ┌──────────────────────────────────────────────────────────┐
   │  APIServer 启动                                           │
   │     │                                                     │
   │     ▼                                                     │
   │  注册 resource table(Pod/Node/Service/...)             │
   │     │                                                     │
   │     ▼                                                     │
   │  对每个 resource 启动 Cacher                              │
   │     │                                                     │
   │     ├──▶ LIST 全量到 cache(初始化)                     │
   │     │                                                     │
   │     ├──▶ 启动 etcd Watch(from latest RV)                │
   │     │     │                                               │
   │     │     └──▶ event 推送 → 更新 cache + 通知 watchers  │
   │     │                                                     │
   │     └──▶ 接收客户端 Watch 请求                            │
   │           │                                               │
   │           ├──▶ 从 cache 推送(快)                       │
   │           │                                               │
   │           └──▶ RV 太老 → 拒绝,要求重新 LIST             │
   └──────────────────────────────────────────────────────────┘

   关键源码(staging/src/k8s.io/apiserver/pkg/storage/cacher/):
   - cacher.go:WatchCache 结构
   - watch_cache.go:事件环形缓冲区
   - cacher.go:listResourceVersion:从 cache 读

   穿透场景:
   1. 客户端 LIST 不带 RV(强一致读)→ 回源 etcd
   2. 客户端 Watch RV < cache 最老 RV → 拒绝,要求重新 LIST
   3. Cacher 未就绪(启动中)→ 回源 etcd

   5K 节点穿透问题:
   - Pod 事件量 > 1000/秒,默认 cache 1000 事件
   - 控制器 Watch 断开后重连,RV 太老 → 重新 LIST 全量
   - LIST 全量 Pod(550K)→ apiserver 内存飙升 → OOM
```

#### 26.5.2.2 APF 队列与公平性

```
   APF 内部队列结构:

   ┌──────────────────────────────────────────────────────────┐
   │  PriorityLevel "global-default"                          │
   │  ├─ Queue 1 [flow=user-a]                                │
   │  ├─ Queue 2 [flow=user-b]                                │
   │  ├─ Queue 3 [flow=user-c]                                │
   │  ├─ ...                                                  │
   │  └─ Queue 64 [flow=user-N]                               │
   │                                                          │
   │  Dispatching:                                            │
   │  - 每秒 assuredConcurrencyShares 个 seat 可用            │
   │  - WFQ(Weighted Fair Queuing)从所有 queue 选           │
   │  - 每个 flow 按权重公平分配                              │
   │  - queue 满 → Reject(429 Too Many Requests)            │
   └──────────────────────────────────────────────────────────┘

   WFQ 算法核心:
   - 每个 flow 有虚拟完成时间(Virtual Finish Time)
   - 选 VFT 最小的 flow 出队
   - 保证:长期看,每个 flow 获得的 seat 与其权重成正比

   公平性保证:
   - 用户 A 大量 LIST Pod 不会饿死用户 B 的写 Pod
   - 但如果整个 PriorityLevel 满了,所有 flow 都受影响

   关键指标:
   - apiserver_flow_dispatch_rps{priority_level}:实际 QPS
   - apiserver_flow_request_wait_duration_seconds:排队延迟
   - apiserver_flow_request_rejected_total:被拒绝请求数
```

### 26.5.3 调度器 Framework Pipeline

#### 26.5.3.1 调度循环源码流程

```
   kube-scheduler 主循环(scheduler.go):

   ┌──────────────────────────────────────────────────────────┐
   │  1. NextPod()                                            │
   │     - 从 active queue 取一个待调度 Pod                   │
   │     - QueueSort 插件决定顺序                             │
   │                                                          │
   │  2. PreFilter                                             │
   │     - 预处理:计算 Pod 总资源需求                        │
   │     - 检查 node 数量是否足够                             │
   │                                                          │
   │  3. Filter(并发,parallelism=16)                       │
   │     - 对每个 Node 跑所有 filter 插件                     │
   │     - 任一插件失败 → 节点不可用                          │
   │     - 5K 节点 → 跑 5000 次 × N 插件                      │
   │     - percentageOfNodesToScore=50 → 跑 2500 个就够       │
   │                                                          │
   │  4. PostFilter(如果 Filter 全失败)                     │
   │     - 优先级抢占:驱逐低优先级 Pod 释放资源              │
   │                                                          │
   │  5. PreScore                                              │
   │     - 打分前预处理                                       │
   │                                                          │
   │  6. Score(并发)                                         │
   │     - 对 Filter 通过的 Node 跑所有 score 插件            │
   │     - 每个插件给 0-100 分                                │
   │     - 按权重加权求和                                     │
   │                                                          │
   │  7. NormalizeScore                                        │
   │     - 分数归一化(0-100)                                │
   │                                                          │
   │  8. Reserve                                                │
   │     - 预留资源(防止并发调度冲突)                      │
   │     - 失败 → Unreserve                                   │
   │                                                          │
   │  9. Permit                                                │
   │     - Allow:继续 Bind                                   │
   │     - Deny:失败,回 Unreserve                            │
   │     - Wait:Gang Scheduling,等所有 Pod 就绪              │
   │                                                          │
   │  10. PreBind                                              │
   │      - 挂载 Volume、设置 annotation 等                   │
   │                                                          │
   │  11. Bind                                                 │
   │      - 写 Pod.spec.nodeName 到 etcd                      │
   │                                                          │
   │  12. PostBind                                             │
   │      - 清理、metric 上报                                 │
   └──────────────────────────────────────────────────────────┘

   性能瓶颈:
   - Filter 阶段:5K 节点 × 10 插件 = 50K 次插件调用
   - Score 阶段:5K 节点 × 10 插件 = 50K 次插件调用
   - 单 Pod 调度耗时 P99 ~100ms(5K 节点)
   - throughput = 1000ms / 100ms = 10 Pods/s(单实例)
   - 5K 节点滚动 50K Pod → 5000s = 83 分钟

   优化:
   - percentageOfNodesToScore=50:只评 2500 个
   - parallelism=64:并发打分
   - 调度器分片(多副本,各管一部分节点)
   - 自定义插件(快速 Filter)
```

#### 26.5.3.2 Volcano Gang Scheduling 实现

```
   Volcano Gang Scheduling 流程:

   ┌──────────────────────────────────────────────────────────┐
   │  1. 用户提交 Job(minAvailable=4)                        │
   │                                                          │
   │  2. Volcano controller 创建 PodGroup                     │
   │     - PodGroup.status.phase = Pending                    │
   │     - 创建 4 个 Pod,都 schedulerName=volcano            │
   │                                                          │
   │  3. Volcano scheduler 调度                               │
   │     - Permit 插件:检查 PodGroup 是否满足 minAvailable   │
   │     - 资源够 4 个 → 全部 Allow → Bind                    │
   │     - 资源不够 → 全部 Wait(占位但不 Bind)              │
   │                                                          │
   │  4. 资源不足时:                                          │
   │     - 4 个 Pod 都 Wait                                   │
   │     - 等其他 Pod 释放资源                                │
   │     - 超时 → PodGroup.phase = Failed → 全部 Unreserve   │
   │                                                          │
   │  5. 资源够时:                                            │
   │     - 4 个 Pod 都 Allow                                  │
   │     - 全部 Bind                                          │
   │     - PodGroup.phase = Running                           │
   └──────────────────────────────────────────────────────────┘

   关键插件:
   - gang:Gang Scheduling 核心
   - binpack:节点装箱(优先填满)
   - drf:Dominant Resource Fairness(主导资源公平)
   - proportion:队列资源比例
   - tdm:Time-Sharing Dispatching(分时调度)
```

### 26.5.4 Kubelet PLEG 与 CPU Manager

#### 26.5.4.1 PLEG 源码流程

```
   kubelet PLEG(Pod Lifecycle Event Generator):

   ┌──────────────────────────────────────────────────────────┐
   │  PLEG 主循环(pleg.go)                                   │
   │                                                          │
   │  while true:                                             │
   │    1. relist:                                            │
   │       - 调 CRI RuntimeService.ListPodSandbox             │
   │       - 调 CRI RuntimeService.ListContainers             │
   │       - 对比上次状态,生成 PodLifecycleEvent             │
   │       - 推送到 eventChannel                              │
   │                                                          │
   │    2. sleep(1s)(relistPeriod)                          │
   │                                                          │
   │  事件处理:                                              │
   │  - kubelet syncLoop 消费 eventChannel                    │
   │  - 触发 Pod sync(同步容器状态)                         │
   └──────────────────────────────────────────────────────────┘

   PLEG NotThrough 问题:
   - relist 超时(默认 3s)
   - 容器多(100+)时,ListContainers 慢
   - CRI 卡死(docker hang)
   - kubelet 状态不更新 → Node NotReady

   K8s 1.26+ Evented PLEG:
   - 基于 CRI 事件,无需 relist
   - CRI 主动推送容器状态变化
   - 大幅降低 PLEG 延迟和 CPU 开销
   - 5K 节点 + 110 Pod/节点 必须开启

   监控指标:
   - kubelet_pleg_relist_duration_seconds(PLEG relist 耗时)
   - kubelet_pleg_last_seen_seconds(最后事件时间)
   - 大于 10s → Node NotReady
```

#### 26.5.4.2 CPU Manager static policy

```
   CPU Manager static policy 流程:

   ┌──────────────────────────────────────────────────────────┐
   │  1. Pod 调度到 Node                                      │
   │                                                          │
   │  2. kubelet syncPod                                      │
   │     - 检查 Pod QoS                                       │
   │     - Guaranteed?(requests=limits, 整数 CPU)            │
   │                                                          │
   │  3. CPU Manager 分配 CPU                                 │
   │     - defaultCPUPool:共享 CPU 池                         │
   │     - staticCPUPool:独占 CPU 池                          │
   │     - Guaranteed Pod → 从 staticCPUPool 分配             │
   │     - BestEffort/Burstable → 从 defaultCPUPool 共享      │
   │                                                          │
   │  4. cpuset.cpus 写入 cgroup                              │
   │     - /sys/fs/cgroup/cpuset/kubepods/podX/cpu.cpus       │
   │     - 容器只能用这些 CPU 核心                            │
   │                                                          │
   │  5. Pod 删除                                             │
   │     - CPU 回收到 staticCPUPool                           │
   │     - 可分配给其他 Guaranteed Pod                        │
   └──────────────────────────────────────────────────────────┘

   优势:
   - 独占 CPU,无上下文切换
   - L1/L2 cache 命中率高
   - 适合 latency-sensitive(数据库、中间件)

   注意:
   - staticCPUPool 有限(节点 CPU - kubeReserved - systemReserved)
   - Guaranteed Pod 太多 → staticCPUPool 耗尽 → 调度失败
   - 不要在生产随意开启,先评估业务类型
```

#### 26.5.4.3 Topology Manager

```
   Topology Manager 协调多个 Manager 的 NUMA 亲和:

   ┌──────────────────────────────────────────────────────────┐
   │  Pod 调度到 Node                                          │
   │     │                                                     │
   │     ▼                                                     │
   │  Topology Manager Hint Providers:                        │
   │     ├── CPU Manager      → "NUMA 0, cpu 0-3"             │
   │     ├── Device Manager   → "NUMA 0, gpu 0"               │
   │     ├── Memory Manager   → "NUMA 0, 4Gi"                 │
   │     └── Hook             → "NIC NUMA 0"                  │
   │                                                           │
   │  Topology Manager 合并 hints:                             │
   │     ├── best-effort:   尽量亲和,失败也调度               │
   │     ├── restricted:    必须亲和,失败拒绝                 │
   │     └── single-numa-node: 必须单 NUMA                     │
   │                                                           │
   │  通过 → 各 Manager 应用 hint                              │
   │  失败 → Pod 调度失败(restricted/single-numa-node)       │
   └──────────────────────────────────────────────────────────┘

   适合场景:
   - GPU 训练:GPU + NIC 必须同 NUMA(避免跨 NUMA PCIE)
   - 大内存数据库:Memory + CPU 同 NUMA
   - 高吞吐网络:CPU + NIC 同 NUMA

   policy=single-numa-node 示例:
   - Pod 请求 4 CPU + 1 GPU + 16Gi memory
   - 节点 2 NUMA,每 NUMA 16 CPU + 1 GPU + 32Gi
   - 必须全部分配在 NUMA 0 或 NUMA 1
   - 不能跨 NUMA(否则 PCIE 跨 NUMA,延迟高)
```

## 26.10 面试速答

**Q1: K8s 单集群 5000 节点上限从哪儿来?**

社区 SIG-Scalability 的官方阈值。来源是 Pod 启动 P99 < 5s 的 SLA:5K 节点 + 150K Pod 时,etcd DB 涨到 50GB(超 8GB quota 必爆)、apiserver Watch Cache 内存 10GB+、调度器单实例 throughput 不够(50K Pod 滚动要 500s)。突破需要 events 单独 etcd + APF + 调度器分片 + NodeLocalDNS + 分区 Prometheus。

**Q2: etcd 调优 8 维是哪些?**

磁盘(独立 NVMe + wal/data 分盘)、quota(8GB)、auto-compaction(1h)、defrag(定期)、mlock(防止 swap)、heartbeat/election(跨 AZ 调大)、snapshot-count(1万)、DB size 监控(80% 告警)。

**Q3: APF 是什么?为什么需要?**

API Priority and Fairness,K8s 1.20+ GA。把请求按优先级分流(exempt/system/node/leader-election/workload/global-default),每个 PriorityLevel 有独立队列 + 令牌桶,保证高优先级(kubelet 上报)不被低优先级(LIST Pod)拖垮,同优先级内按 Flow 公平(WFQ)。替代了早期的 max-in-flight。

**Q4: APF 的两个 CRD 是什么?**

FlowSchema(把请求分类到 PriorityLevel,按 user/resource/verb)和 PriorityLevelConfiguration(定义优先级行为,Limited/Exempt,assuredConcurrencyShares/queueLengthLimit/limitResponse)。

**Q5: Watch Cache 穿透是什么?怎么避免?**

客户端 LIST 不带 resourceVersion=0 时,apiserver 强一致读,回源 etcd。5K 节点 LIST 全量 Pod 要 30s+。避免:用 Informer + Watch(不要全量 LIST)、--watch-cache-sizes=Pod=10000、监控 apiserver_cache_list_total。

**Q6: 调度器 Scheduling Framework 的 13 个扩展点?**

QueueSort、PreFilter、Filter、PostFilter、PreScore、Score、NormalizeScore、Reserve、Permit、PreBind、Bind、PostBind、Unreserve。可编译进调度器的 Go 插件替换或追加。

**Q7: Volcano 解决什么问题?**

Gang Scheduling:一组 Pod 必须全调度成功,否则全失败。AI 训练(100 worker)如果只调度 50 个,训练无法启动,浪费资源。Volcano 用 PodGroup + Permit 插件实现。

**Q8: kubelet PLEG 是什么?为什么卡?**

Pod Lifecycle Event Generator,每秒 relist 容器状态。容器多(100+)或 CRI 卡死时,relist 超时(3s),kubelet 状态不更新,Node NotReady,Pod 被批量 Evict。K8s 1.26+ Evented PLEG 基于 CRI 事件,无需 relist。

**Q9: CPU Manager static policy 怎么工作?**

Guaranteed Pod(requests=limits + 整数 CPU)从 staticCPUPool 分配独占 CPU,写入 cpuset.cpus。其他 Pod 共享 defaultCPUPool。优势:无上下文切换,L1/L2 cache 命中率高。注意:staticCPUPool 有限,Guaranteed Pod 太多会耗尽。

**Q10: Topology Manager 解决什么?**

协调 CPU Manager + Device Manager + Memory Manager 的 NUMA 亲和。policy=single-numa-node 要求所有资源同 NUMA,适合 GPU 训练(GPU + NIC + CPU 同 NUMA,避免跨 NUMA PCIE 延迟)。

**Q11: kube-proxy iptables vs IPVS vs eBPF?**

iptables:5K 节点 × 5万 Service = 250万 规则,重写要分钟级。IPVS:Hash 表 O(1),但仍是 kube-proxy。eBPF(Cilium):完全绕过 kube-proxy,socket-level 转发,性能最佳。5K 节点推荐 Cilium eBPF。

**Q12: NodeLocalDNS 怎么工作?**

DaemonSet,每节点一个 DNS 缓存。拦截 169.254.20.10:53 的请求,命中本地缓存直接返回,miss 才转发 CoreDNS。5K 节点 DNS QPS 从 100万 降到 10万(90% 命中本地)。

**Q13: 大规模集群 Conntrack 怎么调?**

5K 节点 + 200K Pod,默认 nf_conntrack_max=262144 会爆满丢包。调到 nf_conntrack_max=1048576,buckets=262144,tcp_timeout_established=86400。

**Q14: 大规模集群 Prometheus 怎么扩?**

单 Prometheus 上限 5M series,5K 节点 = 30M+ series,必爆。方案:分区(按业务/namespace,每片 5M series)+ Thanos Sidecar + 对象存储 + Thanos Query 全局查询。

**Q15: 5K 节点 Pod 创建 P99 应该是多少?**

官方 SLA < 5s。包括:apiserver 准入(50ms)+ etcd 写入(100ms)+ 调度(1s)+ kubelet 拉镜像(2s)+ 容器启动(1s)。超过 5s 通常卡在调度或镜像拉取。

### 题 1:设计 5K 节点 K8s 集群(端到端)

```
需求:5K 节点,200 Pod/节点 = 1M Pod,要求 Pod 创建 P99 < 5s

设计:

1. 控制面(专用物理机,不混部):
   - etcd:5 副本(跨 3 AZ),独立 NVMe,events 单独 etcd 集群
   - apiserver:5 副本,APF 启用,Watch Cache 调优
   - scheduler:3 副本(leader election),percentageOfNodesToScore=30
   - controller-manager:3 副本(leader election)

2. etcd 调优:
   - quota=8GB,auto-compaction=1h
   - heartbeat=250ms,election=2500ms
   - mlock systemd LimitMEMLOCK=infinity
   - 监控 DB size,80% 告警

3. APF 配置:
   - kubelet 上报 → node 优先级(高并发)
   - controller → workload-high
   - 普通用户 → global-default(限流)
   - CI/CD → workload-low

4. 调度器:
   - Scheduling Framework 自定义插件
   - parallelism=32,percentageOfNodesToScore=30
   - PodTopologySpread 跨 zone
   - 自定义 GPU Topology 插件

5. kubelet:
   - CPU Manager static(latency-sensitive)
   - Topology Manager single-numa-node(GPU 节点)
   - kubeReserved + systemReserved
   - Evented PLEG(K8s 1.26+)
   - maxPods=110

6. 网络:
   - Cilium eBPF(替代 kube-proxy)
   - NodeLocalDNS(DaemonSet)
   - Conntrack: nf_conntrack_max=1048576
   - 内核参数调优(somaxconn, file-max, ...)

7. 存储:
   - 多 CSI(EBS + NAS + 本地盘)
   - VolumeSnapshot 备份
   - VolumeAttachment 限流

8. 监控:
   - Prometheus 5 分片(每 1K 节点一片)
   - Thanos 长期存储(对象存储)
   - Grafana 全局视图
   - 关键指标:etcd DB size, apiserver P99, PLEG 延迟

9. 告警:
   - etcd DB > 6GB(P0)
   - apiserver 5xx > 1%(P0)
   - Node NotReady > 0.1%(P1)
   - Pod Pending > 100(P2)

10. 容量规划:
    - 控制面专用物理机(64 核 / 256GB)
    - 业务节点 200K Pod × 2GB = 400TB 内存
    - 网络:5K 节点 × 1Gbps = 5Tbps
    - 存储:1M Pod × 10GB = 10PB

验收:
- Pod 创建 P99 < 5s ✓
- Watch 延迟 P99 < 1s ✓
- etcd RTT P99 < 50ms ✓
- Node NotReady 率 < 0.1% ✓
```

### 题 2:etcd 雪崩怎么排查?

```
现象:apiserver 5xx,所有写操作失败,etcdctl 报 NOSPACE alarm

排查:

1. 看 etcd alarm
   etcdctl alarm list
   # NOSPACE

2. 看 DB size
   etcdctl endpoint status -w table
   # DB SIZE = 8.5 GB(quota 8GB)

3. 看监控
   - etcd_mvcc_db_total_size_in_bytes 持续上涨
   - etcd_server_quota_backend_bytes = 8GB
   - 80% 没告警 → 监控缺失

根因:
- auto-compaction 未启用或配置错误
- events 写入量大(5K 节点 × 100 events/Pod)
- defrag 从未执行

修复:

1. 紧急扩容(临时)
   - etcdctl compact --rev=<latest>
   - etcdctl defrag(每个成员轮流,非 leader 先)
   - etcdctl alarm disarm

2. 长期修复
   - 启用 auto-compaction-retention=1h
   - 定期 defrag(CronJob)
   - events 单独 etcd
   - 监控 DB size,80% 告警

3. 验证
   - etcdctl endpoint status,DB size 下降
   - apiserver 5xx 消失
   - 业务恢复正常
```

### 题 3:5K 节点 Pod 创建慢怎么排查?

```
现象:Pod 创建 P99 从 1s 飙到 30s

排查路径:

1. 看 apiserver 延迟
   - apiserver_request_duration_seconds{verb=POST,resource=pods}
   - P99 = 5s(正常 < 100ms)→ 准入 + etcd 写慢

2. 看 etcd
   - etcd_disk_wal_fsync_duration_seconds P99 > 100ms
   - etcd_network_peer_round_trip_time_seconds P99 > 100ms
   - 磁盘 IO 瓶颈 or 网络问题

3. 看 APF 排队
   - apiserver_flow_request_wait_duration_seconds
   - global-default 排队 5s+ → APF 限流

4. 看调度延迟
   - scheduler_e2e_scheduling_duration_seconds P99 = 20s
   - 5K 节点 + percentageOfNodesToScore=100 → 慢

5. 看 kubelet
   - kubelet_pleg_relist_duration_seconds P99 > 1s
   - PLEG 卡 → kubelet 状态不更新

6. 看镜像拉取
   - kubelet image pull duration
   - 镜像仓库瓶颈 or 网络带宽

定位:

假设根因是调度器 percentageOfNodesToScore=100(5K 节点全评)

修复:
- percentageOfNodesToScore=30(只评 1500 个)
- parallelism=32
- 验证:P99 < 5s
```

### 题 4:Node NotReady 雪崩怎么救?

```
现象:5K 节点同时 100+ NotReady,业务 Pod 大量 Evict

排查:

1. 看节点 NotReady 原因
   kubectl describe node <node> | grep -A5 Conditions
   # KubeletNotReady: PLEG is not healthy

2. 看 PLEG 延迟
   - kubelet_pleg_relist_duration_seconds P99 > 10s
   - kubelet_pleg_last_seen_seconds > 60s

3. 看 kubelet 日志
   journalctl -u kubelet | grep PLEG
   # "PLEG: relist timed out"

4. 看 CRI
   crictl ps  # 是否卡死
   crictl logs <container-runtime>

根因(常见):
- containerd / docker 卡死(磁盘 IO 满)
- 内核 bug(高负载下 cgroup 卡)
- 网络插件(CNI)死锁

应急:
1. 重启 kubelet(systemctl restart kubelet)
2. 重启 containerd(systemctl restart containerd)
3. 严重时重启节点

长期:
1. Evented PLEG(K8s 1.26+)
2. kubelet 资源预留(kubeReserved)
3. 节点自愈(Node Problem Detector + Cluster Autoscaler)
4. 监控 PLEG 延迟,P99 > 1s 告警
5. PodDisruptionBudget 保护关键服务
```

### 题 5:大规模集群滚动更新怎么不雪崩?

```
场景:5K 节点,Deployment 50K Pod,滚动更新

风险:
- 50K Pod 同时重建 → apiserver QPS 飙升
- 调度器 throughput 不够,Pod Pending 堆积
- 镜像拉取雪崩(镜像仓库过载)
- 服务短暂不可用

方案:

1. 分批滚动
   - maxUnavailable=1%
   - maxSurge=1%
   - 50K × 1% = 500 Pod/批
   - 每批间隔 5 分钟(观察)

2. PodDisruptionBudget
   - 关键服务:PDB minAvailable=90%
   - 防止同时驱逐过多

3. 镜像预拉
   - DaemonSet 提前拉新镜像
   - 避免更新时全部节点同时拉

4. 金丝雀
   - 先更新 1% 节点,观察 30 分钟
   - 指标正常再继续

5. 流量控制
   - readinessProbe 配置正确
   - preStop hook 优雅退出
   - Service mesh 流量切分

6. 监控
   - apiserver QPS
   - Pod Pending 数
   - 服务错误率
   - 镜像拉取延迟

7. 回滚预案
   - 一键回滚到旧版本
   - 保留旧 ReplicaSet(可回滚)
```

### 题 6:什么时候该从单集群切到多集群?

```
判断框架:

切多集群的信号:
1. 单集群 > 5K 节点 + 深调优工程代价高
2. 多地域部署(降低延迟,数据合规)
3. 多租户强隔离(金融/政府,集群级隔离)
4. 故障隔离(核心业务不能受影响)
5. 团队规模 > 50 人,需要独立运维
6. 升级风险高(单集群升级影响全业务)
7. 控制面故障影响范围太大

不切的理由:
1. 单集群 < 5K 节点(还能撑)
2. 资源利用率优先(单集群全局调度更高效)
3. 运维人力不足(多集群运维复杂)
4. 跨集群调度需求弱

切多集群的代价:
1. 控制面成本翻倍(每集群一套)
2. 跨集群调度难(Karmada / KubeFed 不成熟)
3. 全局可观测性复杂(Thanos 全局视图)
4. 多集群 CI/CD 复杂(Argo CD 多集群)
5. 网络互通复杂(跨集群 Service Mesh)

推荐路径:
- 0-1K 节点:单集群
- 1K-5K 节点:单集群深调优
- 5K-10K 节点:评估,可能切多集群
- 10K+ 节点:多集群联邦(Karmada)
```

## 26.12 故障复盘

### 26.12.1 etcd 雪崩导致全集群不可用(2023 阿里)

**现象**:某天凌晨,5K 节点集群 apiserver 全部 5xx,所有写操作失败,kubectl 命令超时。

**排查**:
1. `kubectl get pod` 超时 → apiserver 不可用
2. `etcdctl endpoint status` → DB size = 8.2GB(quota 8GB)
3. `etcdctl alarm list` → NOSPACE
4. 监控:etcd_mvcc_db_total_size_in_bytes 在 1 小时内从 6GB 涨到 8GB

**根因**:
- events 写入量突增(某业务批量提交 10 万 Job,每 Job 20+ events)
- auto-compaction 配置错误(配成 retention=24h,但 events 每秒 1000+ 写入)
- defrag 从未执行
- DB size 监控告警阈值设错(设成 95%,触发时已经只读)

**修复**:
1. 紧急:`etcdctl compact --rev=<latest>` + `etcdctl defrag`(非 leader 先做)
2. `etcdctl alarm disarm` 解除只读
3. 长期:events 单独 etcd 集群(3 副本)
4. auto-compaction-retention=1h
5. 定期 defrag(CronJob,每天低峰期)
6. DB size 监控 80% 告警(P1),90% 告警(P0)

**防范**:
- events 写入限流(APF)
- DB size 告警 80% / 90% 两级
- 定期 defrag 自动化
- 演练 etcd 故障恢复

### 26.12.2 APIServer 限流雪崩(2022 字节)

**现象**:某业务团队批量提交 5 万 Pod,apiserver QPS 飙到 50K,其他团队 kubectl 全部超时。

**排查**:
1. apiserver P99 延迟从 100ms 飙到 30s
2. APF global-default 队列满,Reject 率 80%
3. 其他团队请求也被限流(全局共享)

**根因**:
- 未启用 APF(K8s 1.18 升级到 1.22 但没开 APF)
- max-requests-inflight=400(默认),全集群共享
- 某团队批量 LIST Pod 全集(550K Pod)→ 占满 inflight

**修复**:
1. 紧急:重启 apiserver(临时缓解)
2. 长期:启用 APF(--feature-gates=APIPriorityAndFairness=true)
3. 自定义 FlowSchema:批量 CI/CD → workload-low
4. 关键业务 → workload-high
5. Watch Cache 调优(--watch-cache-sizes=Pod=10000)

**防范**:
- APF 默认启用
- 大批量操作走 workload-low 优先级
- 监控 APF 排队延迟 + Reject 率
- 培训团队:不要 kubectl get pod 全量(用 label selector)

### 26.12.3 调度器卡死、Pod 持续 Pending(2023 腾讯)

**现象**:3K 节点集群,新 Pod 全部 Pending,调度器 30 分钟无响应。

**排查**:
1. `kubectl get pod` → 5000+ Pending
2. scheduler 日志:`"scheduler cache: node not found"`
3. scheduler cache 失效(节点被删除但 cache 未更新)
4. 自定义 Extender(Webhook)超时 60s

**根因**:
- 自定义 Extender 调外部服务,外部服务挂了
- 调度器等 Extender 响应,卡在 PreFilter
- 默认 timeout 60s,Pod 卡 60s 后才尝试下一个
- 累积效应:5000 Pod × 60s = 调度器吞吐归零

**修复**:
1. 紧急:重启调度器
2. 短期:Extender 配置 timeout=5s + circuit breaker
3. 长期:改用 Scheduling Framework Plugin(编译进调度器,无网络调用)
4. Extender 降级:失败时 fallback 到默认插件

**防范**:
- 自定义插件用 Framework Plugin,不用 Extender
- 必须用 Extender 时,配置短 timeout + circuit breaker
- 调度器 HA(3 副本,leader election)
- 监控调度延迟,P99 > 5s 告警

### 26.12.4 kubelet PLEG 卡死、节点 NotReady 雪崩(2024 美团)

**现象**:2K 节点同时 NotReady,Pod 被批量 Evict,业务大量报警。

**排查**:
1. `kubectl get nodes` → 2000+ NotReady
2. 节点上 `journalctl -u kubelet` → `PLEG: relist timed out`
3. `crictl ps` → 卡死,containerd 无响应
4. 节点磁盘 IO 100%(日志写满)

**根因**:
- 业务 Pod 日志输出 1GB/s(无采样)
- 节点磁盘被日志写满
- containerd 元数据写在同磁盘,IO 队列阻塞
- kubelet PLEG relist 调 CRI,卡在磁盘 IO

**修复**:
1. 紧急:清理日志,重启 containerd + kubelet
2. 短期:日志限流(Fluent Bit rate limit)
3. 长期:
   - 日志单独磁盘(不与 containerd 共享)
   - 业务日志采样 + 聚合
   - Evented PLEG(K8s 1.26+,减少 relist)
   - 节点自愈(Node Problem Detector + 重启)

**防范**:
- 日志磁盘独立
- 日志限流 + 采样
- PLEG 延迟监控(P99 > 1s 告警)
- 节点磁盘水位告警(80%)
- Evented PLEG 升级

### 26.12.5 大规模滚动更新雪崩(2022 滴滴)

**现象**:5K 节点集群,Deployment 50K Pod 滚动更新,10 分钟内服务 5xx 飙到 30%。

**排查**:
1. 滚动更新触发:50K Pod 同时重建
2. apiserver QPS 飙到 100K(创建 + 删除)
3. 调度器 throughput 不够,Pod Pending 堆积
4. 镜像仓库过载,拉镜像超时
5. readinessProbe 失败,Service 剔除 Pod,但流量未平滑切换

**根因**:
- maxUnavailable=25%(默认),50K × 25% = 12.5K 同时重建
- 没有 PodDisruptionBudget
- 镜像未预拉
- readinessProbe 配置过严(initialDelaySeconds=60s)

**修复**:
1. 紧急:暂停滚动更新,回滚到旧版本
2. 短期:maxUnavailable=1%,maxSurge=1%
3. 中期:
   - PodDisruptionBudget(minAvailable=95%)
   - 镜像预拉(DaemonSet 提前拉)
   - readinessProbe initialDelaySeconds=10s
   - preStop hook(优雅退出 + sleep 10s)
4. 长期:
   - 金丝雀发布(Argo Rollouts)
   - 流量切分(先 1% 流量到新版本)
   - 监控驱动(错误率 > 1% 自动暂停)

**防范**:
- 大规模更新用 Argo Rollouts / Flagger
- PDB 保护关键服务
- 镜像预拉
- 监控驱动自动暂停
- 演练滚动更新流程

### 26.12.6 NetworkPolicy 误配全集群断网(2023 小红书)

**现象**:某团队配置 NetworkPolicy default-deny,导致 5K 节点 Pod 间无法通信,全部 5xx。

**排查**:
1. 所有 Pod 间请求超时
2. 最近变更:某 namespace 配置 default-deny-all
3. CNI(Cilium)policy 计算量大,5K 节点全量同步

**根因**:
- default-deny-all 范围太广(选了所有 namespace)
- Cilium 计算策略规则,5K 节点 × 10万 Pod,计算量爆炸
- 策略同步到所有节点,网络带宽打满

**修复**:
1. 紧急:删除误配 NetworkPolicy
2. Cilium 重启(强制重新计算)
3. 验证:Pod 间通信恢复

**防范**:
- NetworkPolicy 变更走 GitOps + PR review
- staging 环境先验证
- 干运行(dry-run)模式
- 策略分批应用(先 1 节点,再 10,再 100,...)
- 监控 Cilium 策略计算延迟
