## 25.1 问题定义与边界

### 25.1.1 自建 K8s 的痛点

`kubeadm init` 一行命令拉起一个集群,但生产化一条路走下来,工程量远超想象:

| 维度 | 自建 K8s 必须自己解决 | 托管 K8s 已经解决 |
|------|----------------------|-------------------|
| 控制面 | apiserver/etcd/scheduler/controller-manager 高可用、备份、升级 | 云厂商托管,SLA 99.95%+ |
| etcd | 磁盘选型、quorum、compaction、defrag、备份恢复 | 隐藏在托管层,自动备份 |
| 网络 | CNI 选型、Pod CIDR 规划、跨 AZ、NetworkPolicy、Service Mesh | 云厂商 VPC-CNI 集成 |
| 存储 | CSI 开发、卷生命周期、快照、扩容、跨可用区 | 云盘 CSI、文件存储 CSI、对象存储集成 |
| IAM | ServiceAccount Token、OIDC Provider、Webhook | IRSA(AWS)、WI(GCP)、RRSA(Azure)、RAM(阿里) |
| 弹性 | Cluster Autoscaler、节点池、Spot 实例、缩容策略 | 节点池、超级节点、Spot 竞价策略 |
| 升级 | kubeadm upgrade、版本兼容、etcd 迁移、滚动升级 | 一键升级、自动升级通道 |
| 安全 | CIS Benchmark、PSA、镜像签名、运行时安全 | 托管节点硬化、Bottlerocket、CIS 镜像 |
| 可观测性 | Prometheus、Grafana、Loki、Jaeger 自建 | 云监控集成、托管 Prometheus |
| 多集群 | Karmada、Cluster API、联邦 | 舰队(Fleet)、Hub、多集群网关 |

**结论**:自建 K8s 在 100 节点以下尚可,2000 节点以上、多集群、多区域、强 SLA 场景,托管平台的工程经济性显著优于自建。

### 25.1.2 大厂 K8s 平台解决什么

大厂 K8s 平台 = **托管 K8s 控制面** + **云原生增值能力** + **商业化支持**,具体解决四类问题:

1. **降低运维成本**:控制面免运维、节点池托管、自动升级、自动修复
2. **提升资源效率**:Serverless 容器按量计费、Spot 实例、混部节点提升利用率
3. **加强企业能力**:IAM 集成、合规审计、私有网络、安全沙箱、镜像仓库
4. **打通云生态**:云监控、日志服务、消息队列、数据库、AI 平台

### 25.1.3 不解决什么

托管平台并非银弹,以下场景仍需用户自己处理:

- **应用架构**:微服务拆分、领域模型、Saga 分布式事务
- **业务 SLO**:错误预算、告警阈值、降级策略
- **跨云迁移**:Vendor Lock-in 风险(每个云的 IngressClass、StorageClass、IAM 都不同)
- **数据层**:数据库高可用、缓存一致性、消息队列语义
- **应用安全**:业务越权、SQL 注入、XSS、CSRF

### 25.1.4 选型决策边界

```
何时选托管 K8s:
  ✓ 团队 < 10 人,但需要 1000+ 节点
  ✓ 业务跨多区域、多可用区
  ✓ 需要 SLA 99.9%+
  ✓ 强合规要求(等保、PCI-DSS、HIPAA)
  ✓ 希望专注应用而非基础设施

何时仍选自建 K8s:
  ✓ 私有数据中心、强数据主权
  ✓ 特殊硬件(GPU/NPU/FPGA 调度深度定制)
  ✓ 成本极致敏感(已有机房、长期租约)
  ✓ 需要深度修改 K8s 源码(大厂内部平台)
  ✓ 跨云、避免 Vendor Lock-in
```

## 25.2 直觉解释

把大厂 K8s 平台想象成 **「商品房小区」vs「自建别墅」**:

| 维度 | 自建别墅(自建 K8s) | 商品房小区(托管 K8s) |
|------|--------------------|-----------------------|
| 土地 | 自己买服务器 | 云厂商机房 |
| 主体结构 | 自己搭控制面 | 物业(云厂商)统一建 |
| 水电气网 | 自己拉线 | 物业统一接入 |
| 安保 | 自己请保安 | 物业统一安保 + 门禁 |
| 维修 | 自己修 | 物业维修,但付费 |
| 装修 | 自由度高 | 受物业规则约束 |
| 邻居 | 无 | 共享设施 |
| 成本 | 一次性高 | 按月付费,长期可能更贵 |
| 灵活性 | 高 | 中(受平台约束) |

**关键概念**:

- **托管控制面**:物业把「物业办公室」建好,你只管用
- **节点池**:楼栋,每栋楼配置不同(普通楼、豪华楼、临时楼)
- **Serverless 容器**:酒店式公寓,按天计费,无固定住所
- **混部节点**:合租公寓,在线 + 离线共用资源
- **安全沙箱**:VIP 独立别墅,与外界完全隔离
- **Spot 实例**:法拍房,便宜但随时可能被收回

**六大平台直觉对比**:

```
阿里 ACK:    「电商双十一战场」,万节点混部鼻祖,自研 CNI、混部、Serverless
字节火山:    「短视频弹性怪兽」,内部 ByteKube 经验外化,超级节点极速弹性
腾讯 TKE:    「游戏 + 社交场景」,与微信/QQ 同源,原生节点 + 超级节点双形态
Google GKE:  「Borg 嫡传正统」,原生体验最强,Autopilot 全托管,Anthos 混合云
AWS EKS:     「全球部署之王」,区域最广,Fargate Serverless,Spot 实例成熟
Azure AKS:   「企业 Windows 之王」,Windows 节点一流,Azure AD 深度集成
```

**关键设计**:
- apiserver 多副本跨 AZ 部署,前置负载均衡
- etcd 隐藏在内网,用户无法直接访问,自动备份
- 用户 VPC 与控制面 VPC 隔离(VPC peering 或 PrivateLink)
- API 请求经云负载均衡 → apiserver

### 25.3.3 节点池(Node Pool)模型

各大平台节点池模型对照:

| 平台 | 普通节点池 | 弹性节点池 | Serverless 节点 | GPU 节点 | Spot/竞价 |
|------|-----------|-----------|----------------|---------|----------|
| 阿里 ACK | ✓ ECS 节点池 | ✓ 弹性实例 | ✓ ASK Pod | ✓ GPU 节点池 | ✓ 抢占式实例 |
| 腾讯 TKE | ✓ 原生节点(CVM) | ✓ 弹性伸缩组 | ✓ 超级节点(Pod 直达) | ✓ GPU 节点 | ✓ 竞价实例 |
| 字节火山 | ✓ 弹性容器实例 | ✓ 弹性节点池 | ✓ VCI Pod | ✓ GPU 节点 | ✓ 竞价实例 |
| AWS EKS | ✓ Managed Node Group | ✓ Self-managed ASG | ✓ Fargate Pod | ✓ GPU 节点 | ✓ Spot |
| GKE | ✓ Standard Node Pool | ✓ Autopilot | ✓ GKE Autopilot | ✓ GPU Pool | ✓ Spot VM |
| Azure AKS | ✓ System/User Pool | ✓ VMSS | ✓ ACI Pod | ✓ GPU Pool | ✓ Spot VMSS |

**关键概念**:
- **系统节点池**:运行 kube-proxy、CoreDNS、CNI 等关键组件,通常不可驱逐
- **用户节点池**:运行业务 Pod,可弹性伸缩
- **超级节点/Serverless 节点**:Pod 直接在云厂商虚拟化层调度,无 VM 中介

### 25.3.4 Serverless 容器架构

```
传统节点模型:                       Serverless 容器模型:
┌─────────────────────┐             ┌──────────────────────────────┐
│  VM (Node)          │             │  云厂商虚拟化层              │
│                     │             │  ┌────────────────────────┐  │
│  ┌───────────────┐  │             │  │ Pod A (microVM)        │  │
│  │ Pod A         │  │             │  │  Firecracker/Kata      │  │
│  ├───────────────┤  │             │  ├────────────────────────┤  │
│  │ Pod B         │  │   →         │  │ Pod B (microVM)        │  │
│  ├───────────────┤  │             │  │  Firecracker/Kata      │  │
│  │ Pod C         │  │             │  ├────────────────────────┤  │
│  └───────────────┘  │             │  │ Pod C (microVM)        │  │
│  kubelet + runtime  │             │  └────────────────────────┘  │
│                     │             │  Virtual Kubelet 适配器       │
└─────────────────────┘             └──────────────────────────────┘
按 VM 计费                           按 Pod 计费(秒级)
节点利用率 20-60%                    资源利用率 100%
冷启动 30s+(节点启动)              冷启动 1-3s(Pod 启动)
```

**Virtual Kubelet 机制**:
- Virtual Kubelet 是 K8s 节点模拟器
- 注册一个「虚拟节点」到集群
- 把对该节点的 Pod 创建请求转发到云厂商后端
- 后端用 microVM(Firecracker/Kata)隔离 Pod
- 典型实现:ACK ASK、TKE 超级节点、EKS Fargate、ACI

### 25.3.5 混部架构(Co-location)

```
                单节点资源视图(混部)
   ┌────────────────────────────────────────────────────┐
   │                  节点总容量(100%)                │
   │                                                    │
   │  ┌──────────────────────────────────────────────┐  │
   │  │       在线业务(高优先级,Latency-sensitive)│  │
   │  │       CPU Request: 30%    实际使用: 20%      │  │
   │  └──────────────────────────────────────────────┘  │
   │  ┌──────────────────────────────────────────────┐  │
   │  │       离线业务(低优先级,Best-Effort)      │  │
   │  │       使用「在线业务空闲的 80%」              │  │
   │  │       CPU 实际占用: 60%                      │  │
   │  └──────────────────────────────────────────────┘  │
   │  ┌──────────────────────────────────────────────┐  │
   │  │       系统预留(kubelet/daemonset)          │  │
   │  │       10%                                       │
   │  └──────────────────────────────────────────────┘  │
   └────────────────────────────────────────────────────┘

   关键机制:
     1. 在线业务优先级高,可抢占离线
     2. 离线业务使用 cgroup 子系统 + cpu.shares/cfs_quota
     3. 内存压力时,离线先被 OOM Kill
     4. CPU 升频/降频由在在线业务驱动
     5. 网络带宽优先级:在线 > 离线
     6. 磁盘 IO 优先级:在线 > 离线
```

**主流混部方案**:
- **阿里 ACK Koordinator**:开源,基于 Koordinator 调度器
- **字节 AllSpark**:内部使用,火山引擎对外
- **腾讯 CSC(Cloud Service Center)**:TKE 集成
- **Google Borg**:鼻祖,论文 2015 公开
- **Microsoft Apollo**:内部平台

### 25.3.7 IAM 集成模式

K8s ServiceAccount 与云 IAM 的对接是托管平台的核心能力:

```
传统模式(已弃用):
  Pod → ServiceAccount → 静态 Cloud Credentials(Secret) → 云 API
  
  问题:凭证轮转、权限过大、审计困难

现代模式(IAM Roles for ServiceAccount):
  Pod → ServiceAccount → OIDC Token(JWT) → 云 IAM AssumeRole → 临时凭证 → 云 API
  
  优点:
    • 凭证自动轮转(1 小时)
    • Pod 级权限隔离
    • 审计到具体 ServiceAccount
    • 无需分发长期凭证
```

| 平台 | 机制名称 | 协议 | 关键组件 |
|------|---------|------|---------|
| AWS EKS | IRSA(IAM Roles for SA) | OIDC | IAM OIDC Provider + STS |
| GCP GKE | WI(Workload Identity) | OIDC | GCP IAM + Service Account |
| Azure AKS | RRSA(Role-based Access for SA) | OIDC | Azure AD + Workload Identity |
| 阿里 ACK | RRSA(RamRole for SA) | OIDC | RAM OIDC + STS |
| 腾讯 TKE | CAM Pod Identity | OIDC | CAM + STS |

### 25.3.8 网络增强(CNI)

各平台 CNI 对照:

| 平台 | CNI | 模式 | Pod IP 来源 | 关键特性 |
|------|-----|------|------------|---------|
| AWS EKS | AWS VPC CNI | VPC 原生 | ENI 辅助 IP | Pod 直接拿到 VPC IP,无 NAT |
| GCP GKE | VPC-native CNI | VPC 原生 | Alias IP Range | Pod IP 来自子网别名范围 |
| Azure AKS | Azure CNI | VPC 原生 | 子网 IP | Pod 直接在 VPC 子网 |
| 阿里 ACK | Terway | VPC 原生 | ENI 辅助 IP / 共享 IP | 支持 NetworkPolicy、共享 IP 模式 |
| 腾讯 TKE | VPC-CNI | VPC 原生 | ENI 辅助 IP | 与 CVM 网络一致 |
| 通用 | Calico | Overlay/BGP | Pod CIDR | 跨平台,NetworkPolicy 强 |
| 通用 | Cilium | eBPF | Pod CIDR | 高性能,内核态 |

**ENI(弹性网络接口)模式**(AWS/阿里/腾讯):
- 每个 VM 有多个 ENI
- 每个 ENI 有多个辅助 IP
- Pod 直接绑定 ENI 辅助 IP
- 优点:无 NAT、性能好、与 VPC 安全组一致
- 缺点:IP 数量受 ENI 限制(大实例 100+ IP,小实例 6 IP)

### 25.3.10 弹性伸缩策略

```
HPA(水平 Pod 伸缩):
  - 基于 CPU/Memory/Custom Metric
  - 各平台通用

VPA(垂直 Pod 伸缩):
  - 调整 Pod 资源 request
  - 各平台通用(需开启)

CA(Cluster Autoscaler):
  - 节点池级别伸缩
  - 各平台实现:
    * AWS: ASG + Cluster Autoscaler / Karpenter
    * GCP: MIG + Cluster Autoscaler
    * Azure: VMSS + Cluster Autoscaler
    * 阿里: ESS + Cluster Autoscaler
    * 腾讯: AS + Cluster Autoscaler

Karpenter(AWS 开源):
  - 节点级即时伸缩
  - 比 CA 快 5-10 倍
  - 支持 Spot 实例多样化策略

Serverless 容器伸缩:
  - Pod 级别直接调度
  - 无需节点伸缩
  - 秒级冷启动
```

## 25.5 底层原理

### 25.5.1 托管控制面架构

以 AWS EKS 为例,深度剖析托管控制面:

```
┌──────────────────────────────────────────────────────────────────┐
│                      AWS EKS 托管控制面                          │
│                                                                  │
│   ┌────────────────────────────────────────────────────┐         │
│   │             Network Load Balancer                  │         │
│   │       (公开 API endpoint, TLS 终结)              │         │
│   └──────────────────────┬─────────────────────────────┘         │
│                          │                                       │
│         ┌────────────────┼────────────────┐                      │
│         │                │                │                      │
│         ▼                ▼                ▼                      │
│   ┌──────────┐    ┌──────────┐    ┌──────────┐                  │
│   │apiserver1│    │apiserver2│    │apiserver3│   (跨 AZ)         │
│   │          │    │          │    │          │                  │
│   │  Authn   │    │  Authn   │    │  Authn   │                  │
│   │  Authz   │    │  Authz   │    │  Authz   │                  │
│   │  Admission│   │  Admission│   │  Admission│                 │
│   └────┬─────┘    └────┬─────┘    └────┬─────┘                  │
│        │               │               │                         │
│        └───────────────┼───────────────┘                         │
│                        │                                         │
│                        ▼                                         │
│              ┌──────────────────┐                                │
│              │  etcd 集群(3 节点)│                                │
│              │  跨 AZ, 自动备份  │                                │
│              │  Raft quorum = 2 │                                │
│              └──────────────────┘                                │
│                                                                  │
│   用户 VPC                          EKS 内部 VPC                 │
│   ┌──────────────────┐              ┌──────────────────┐         │
│   │ Worker Nodes     │ ←──────────→ │ Control Plane    │         │
│   │                  │  ENI 跨 VPC  │                  │         │
│   │ kubelet          │  PrivateLink │ apiserver        │         │
│   │ kube-proxy       │              │                  │         │
│   │ CNI              │              │                  │         │
│   └──────────────────┘              └──────────────────┘         │
└──────────────────────────────────────────────────────────────────┘
```

**关键设计点**:

1. **apiserver 多副本**:EKS 至少 3 个 apiserver 跨 AZ,GKE 也类似
2. **etcd 隐藏**:用户无法 kubectl 直连 etcd,只能通过 apiserver
3. **跨 VPC 通信**:通过 ENI 跨 VPC(ENI Cross-Account),Worker Node 与 apiserver 通信走 PrivateLink
4. **自动备份**:EKS 每 5 分钟备份 etcd 到 S3,GKE 自动快照到 Cloud Storage
5. **API 限流**:基于令牌桶,EKS 默认每秒 3000 请求,突发 6000
6. **资源隔离**:不同集群的控制面资源完全隔离,避免邻居效应

### 25.5.2 Serverless 容器实现机制

**Virtual Kubelet 工作流**:

```
1. Pod 创建请求到达 apiserver
       ↓
2. 调度器看到虚拟节点(virtual-kubelet-node)
   假设该节点有「无限资源」
       ↓
3. Pod 被 bind 到虚拟节点
       ↓
4. Virtual Kubelet(运行在某个真实节点上的 Pod)
   收到 Pod 事件
       ↓
5. Virtual Kubelet 调用云厂商 API:
   - ACK ASK:    ECI CreateContainerGroup
   - TKE 超级节点: CIS CreateContainerInstances
   - EKS Fargate: Fargate StartTask
   - GKE Autopilot: 云内部 API
       ↓
6. 云厂商后端:
   a. 分配 IP(VPC ENI)
   b. 启动 microVM(Firecracker / Kata)
   c. 拉取镜像
   d. 启动容器
       ↓
7. Virtual Kubelet 上报 Pod 状态到 apiserver
   (Phase=Running, IP=10.0.x.x)
       ↓
8. kube-proxy 看到虚拟节点上的 Pod IP
   写入 iptables/IPVS 规则
       ↓
9. Service 流量通过 iptables 转发到虚拟节点 Pod IP
   (走 VPC 路由,无需 NAT)
```

**冷启动优化**:

```
冷启动时间分解(典型):
  调度:           10ms
  Virtual Kubelet: 50ms
  云 API 调用:    200ms
  microVM 启动:   100-300ms(Firecracker 125ms)
  镜像拉取:       1-3s(取决于镜像大小)
  容器启动:       100-500ms
  ─────────────────────
  总计:           1.5-4s
  
优化手段:
  1. 镜像预拉取(云厂商镜像缓存)
     - AWS Fargate 平台缓存
     - 阿里 ECI 内置镜像
  2. 镜像加速(Nydus / Stargz)
     - 按需加载,只下载需要的层
     - 启动时间从 3s → 500ms
  3. microVM 池预热
     - 云厂商预启动一批 microVM
     - Pod 来了直接绑
  4. 镜像瘦身
     - distroless / scratch
     - 多阶段构建
```

### 25.5.3 混部架构(Koordinator)

阿里 ACK Koordinator 混部核心机制:

```
                Koordinator 混部架构
   ┌─────────────────────────────────────────────────────┐
   │                  Koordlet (DaemonSet)               │
   │   ┌─────────────────────────────────────────────┐   │

   │   ┌─────────────────────────────────────────────┐   │
   │   │  QoS Manager                               │   │
   │   │  • CPU Suppress(压制离线)                │   │
   │   │  • Memory Evict(驱逐离线)                │   │
   │   │  • IO Throttle(限速离线)                 │   │
   │   │  • Network Throttle                       │   │
   │   └─────────────────────────────────────────────┘   │
   │   ┌─────────────────────────────────────────────┐   │
   │   │  Runtime Hooks                             │   │
   │   │  • CRI hooks(注入 cgroup)               │   │
   │   │  • CSI hooks                               │   │
   │   │  • Network hooks                           │   │
   │   └─────────────────────────────────────────────┘   │
   └─────────────────────────────────────────────────────┘
   
   ┌─────────────────────────────────────────────────────┐
   │              Koordinator Scheduler                  │
   │   ┌─────────────────────────────────────────────┐   │
   │   │  节点排序(混部感知)                       │   │
   │   │  • 在线高负载节点降权                       │   │
   │   │  • 离线任务反亲和                           │   │
   │   │  • CPU 拓扑对齐                             │   │
   │   └─────────────────────────────────────────────┘   │
   │   ┌─────────────────────────────────────────────┐   │
   │   │  Pod 抢占                                   │   │
   │   │  • 离线 Pod 可被在线 Pod 抢占                │   │
   │   │  • 抢占策略:优先级 + QoS                   │   │
   │   └─────────────────────────────────────────────┘   │
   └─────────────────────────────────────────────────────┘
```

**CPU Suppress 机制**(关键):

```
CPU 资源分配:
  节点 16 核,在线 Pod request=4 核,实际使用 2 核
  
  阶段 1(无离线):
    在线 cgroup: cpu.cfs_quota=4核
    离线 cgroup: cpu.cfs_quota=12核(剩余)
    
  阶段 2(在线负载上升):
    在线实际使用 3.5 核
    Koordlet 探测到,5s 内调整:
      在线 cgroup: cpu.cfs_quota=4 核(不变,但实际使用上升)
      离线 cgroup: cpu.cfs_quota=10.5 核(被压制)
    
  阶段 3(在线突发):
    在线实际使用 6 核(超过 request)
    Koordlet 探测到,1s 内调整:
      在线 cgroup: cpu.cfs_quota=8 核(允许超用)
      离线 cgroup: cpu.cfs_quota=8 核(继续压制)
    
  阶段 4(在线回落):
    在线实际使用 2 核
    Koordlet 探测到,30s 内调整:
      在线 cgroup: cpu.cfs_quota=4 核
      离线 cgroup: cpu.cfs_quota=12 核(恢复)
```

**Memory Evict 机制**:

```
内存压力分级:
  - Minor: 离线 Pod 限速内存分配
  - Major:  离线 Pod 部分 OOM Kill
  - Critical: 在线 Pod 风险,大规模驱逐离线

判断指标:
  - /proc/meminfo MemAvailable
  - cgroup memory.usage_in_bytes
  - PSI(Pressure Stall Information)

驱逐策略:
  - 优先驱逐低优先级 Pod
  - 按 QoS 等级(BestEffort 优先驱逐)
  - 按内存使用量(占用大的先驱逐)
```

### 25.5.4 安全沙箱机制

**Firecracker(AWS)**:

```
Firecracker microVM 架构:
  ┌─────────────────────────────────┐
  │  Host Linux Kernel              │
  │  ┌───────────────────────────┐  │
  │  │ KVM (Kernel Virtual Machine)│
  │  └───────────────────────────┘  │
  │  ┌───────────────────────────┐  │
  │  │ Firecracker VMM           │  │
  │  │  • 极简设备模拟            │  │
  │  │  • 仅 4 个设备:           │  │
  │  │    - serial console       │  │
  │  │    - block device         │  │
  │  │    - network device       │  │
  │  │    - virtio keyboard      │  │
  │  └───────────────────────────┘  │
  │  ┌───────────────────────────┐  │
  │  │ Guest Kernel(独立)      │  │
  │  │  • Linux 5.10+            │  │
  │  └───────────────────────────┘  │
  │  ┌───────────────────────────┐  │
  │  │ Container Runtime         │  │
  │  │  • runc / containerd      │  │
  │  └───────────────────────────┘  │
  │  ┌───────────────────────────┐  │
  │  │ Application Container     │  │
  │  └───────────────────────────┘  │
  └─────────────────────────────────┘
  
启动流程:
  1. Firecracker 进程启动 (10ms)
  2. 加载内核 + initramfs (50ms)
  3. 启动 guest 内核 (30ms)
  4. 启动 containerd (40ms)
  5. 拉取镜像(已在主机缓存,跳过)
  6. 启动容器 (50ms)
  总计: ~180ms(典型 125-200ms)
```

**Kata Containers**:

```
Kata 架构(类似但更通用):
  - 支持 QEMU、Firecracker、Cloud Hypervisor 等多种 VMM
  - 兼容 OCI 标准,可作为 containerd 的 runtime
  - Pod 内多个容器共享一个 microVM
  - 适合已有 K8s 集群替换 runtime
  
  Host Kernel
    └── QEMU/KVM
         └── Guest Kernel
              └── kata-agent
                   ├── container A (runc)
                   └── container B (runc)
```

**gVisor**:

```
gVisor 架构(用户态内核):
  - 不创建新 VM
  - 在用户态实现 Linux 系统调用
  - 容器系统调用被拦截到 gVisor 的 Sentry 进程
  - Sentry 实现 200+ 系统调用
  - 不需要 guest kernel
  
  Host Kernel
    └── runsc(Google 修改的 OCI runtime)
         └── Sentry(用户态内核)
              ├── container A
              └── container B
              
启动时间:< 100ms
内存开销:20-50MB
兼容性:90% Linux 应用,部分系统调用未实现
```

### 25.5.5 IRSA / WI / RRSA 工作流

以 AWS IRSA 为例,深度剖析:

```
1. 集群创建时,创建 OIDC Provider
   ┌──────────────────────────────────┐
   │ AWS IAM OIDC Provider            │
   │ Provider URL:                    │
   │   https://oidc.eks.us-west-2    │
   │   .amazonaws.com/id/EXAMPLED539 │
   │                                  │
   │ 客户端 ID: sts.amazonaws.com    │
   └──────────────────────────────────┘
   
2. 创建 IAM Role,信任策略指向 OIDC Provider
   {
     "Effect": "Allow",
     "Principal": {
       "Federated": "arn:aws:iam::xxx:oidc-provider/oidc.eks..."
     },
     "Action": "sts:AssumeRoleWithWebIdentity",
     "Condition": {
       "StringEquals": {
         "oidc.eks...:sub": "system:serviceaccount:default:my-sa"
       }
     }
   }
   
3. 给 Role 授权 S3 读取权限
   Policy: AmazonS3ReadOnlyAccess

4. 给 K8s SA 加 annotation
   apiVersion: v1
   kind: ServiceAccount
   metadata:
     name: my-sa
     annotations:
       eks.amazonaws.com/role-arn: arn:aws:iam::xxx:role/my-role
   
5. Pod 启动流程:
   ┌─────────────────────────────────────────────────────┐
   │ 1. kubelet 创建 Pod                                │
   │ 2. Mutating Webhook(EKS Pod Identity Webhook)   │
   │    注入:                                           │
   │    - AWS_ROLE_ARN=<role-arn>                       │
   │    - AWS_WEB_IDENTITY_TOKEN_FILE=/var/run/secrets/ │
   │      eks.amazonaws.com/serviceaccount/token        │
   │    - 挂载 projected volume                         │
   │ 3. Pod 启动                                        │
   │ 4. AWS SDK 自动检测环境变量                         │
   │ 5. SDK 调用 STS:AssumeRoleWithWebIdentity         │
   │    - 传入 OIDC Token(JWT)                       │
   │ 6. STS 验证:                                      │
   │    - OIDC Token 签名(用集群 OIDC Provider 公钥)│
   │    - Token 过期时间                                │
   │    - Role 信任策略中的 sub 匹配                    │
   │ 7. STS 返回临时凭证(AccessKey + SecretKey + SessionToken)│
   │    有效期 1 小时                                  │
   │ 8. SDK 用临时凭证调用 S3                           │
   │ 9. 凭证过期前 5 分钟,SDK 自动刷新                 │
   └─────────────────────────────────────────────────────┘
```

**安全性分析**:
- OIDC Token 由 apiserver 签发(kube-controller-manager 的 private key)
- Token 1 小时过期,自动轮转(projected volume 配置)
- 临时凭证 1 小时过期,SDK 自动刷新
- 无长期凭证泄露风险
- 审计到具体 ServiceAccount(CloudTrail 记录 role-arn + SA)

### 25.5.6 Karpenter 节点弹性机制

AWS Karpenter 是新一代节点伸缩器,核心机制:

```
传统 Cluster Autoscaler:
  1. Pod Pending
  2. CA 监听到 Pending Pod
  3. CA 评估节点池,选择 ASG
  4. CA 调用 ASG API,增加 DesiredCapacity
  5. ASG 启动新 EC2 实例
  6. 实例启动 → kubelet 注册 → kubelet ready
  7. 调度器把 Pod 调度到新节点
  总耗时:60-180s

Karpenter:
  1. Pod Pending
  2. Karpenter 监听到 Pending Pod
  3. Karpenter 直接调用 EC2 RunInstances
     (绕过 ASG)
  4. 选择最合适的实例类型(Consolidation)
  5. EC2 启动 → Karpenter 等待 ready
  6. 节点 ready 后,Karpenter 直接 bind Pod
     (绕过 scheduler)
  总耗时:20-60s
```

## 25.7 常见陷阱与调优

### 25.7.1 托管 vs 自建成本临界点

```
成本对比(假设 100 节点集群):

自建 K8s:
  服务器(100 台 4c8g):     100 × $80/月 = $8,000/月
  控制面 3 台(8c16g):       3 × $200/月 = $600/月
  运维人力(0.5 FTE):        $4,000/月
  监控/日志系统:             $500/月
  网络负载均衡:              $200/月
  ──────────────────────────
  合计: ~$13,300/月

EKS 托管:
  控制面费用:               $73/月($0.10/小时)
  Worker 节点(100 台):      $8,000/月
  网络负载均衡:              $200/月
  CloudWatch 日志:          $200/月
  运维人力(0.2 FTE):        $1,600/月
  ──────────────────────────
  合计: ~$10,073/月

结论:
  - 100 节点以下,自建和托管差异小
  - 100-1000 节点,托管便宜 20-30%
  - 1000+ 节点,自建可能更便宜(可砍掉云厂商加价)
  - 但自建隐藏成本:运维、培训、文档、故障

真实临界点:
  - 50 节点以下:托管几乎一定更划算
  - 50-500 节点:托管通常更划算
  - 500-5000 节点:看团队规模和云议价能力
  - 5000+ 节点:大厂自建(字节、阿里、Google)
```

### 25.7.2 Vendor Lock-in 风险

```
会被锁定的组件:
  - IAM 集成(IRSA / WI / RRSA 互不兼容)
  - IngressClass(每个云自己的 Ingress Controller)
  - StorageClass(每个云的 CSI)
  - CNI(VPC-CNI 互不兼容)
  - Service Type=LoadBalancer(云厂商 LB 集成)
  - 节点池 API(eksctl vs gcloud vs az)
  - 监控/日志集成

规避策略:
  1. 用 Cluster API 跨云部署
  2. 用 Crossplane 管理云资源
  3. 用 Istio / Linkerd 替代云厂商 Ingress
  4. 用 Velero 备份,支持跨云恢复
  5. 用 Argo CD / Flux CD GitOps 部署
  6. 用 OpenTelemetry 标准化可观测性
  7. 关键组件(Helm Chart)抽象云差异
```

### 25.7.3 跨可用区陷阱

```
陷阱 1:Pod 跨 AZ 过度分散
  现象:Service 跨 AZ 流量产生跨 AZ 费用
  原因:Pod 默认均匀分布到所有节点
  修复:topologySpreadConstraints 控制
  
  topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: ScheduleAnyway
    labelSelector:
      matchLabels:
        app: api

陷阱 2:StatefulSet 跨 AZ 卷
  现象:Pod 在 AZ-a,卷在 AZ-b,跨 AZ 挂载慢且贵
  原因:云盘通常单 AZ
  修复:
    - 用 Regional 卷(GKE Regional PD,EKS EBS Multi-Attach)
    - Pod 与卷同 AZ(节点亲和 + 卷拓扑)

陷阱 3:跨 AZ 延迟
  现象:同 AZ RTT 0.1ms,跨 AZ 1-2ms
  影响:数据库连接、gRPC 流式、长连接
  修复:
    - 同 AZ 优先(topologyAware Hints)
    - Service topology aware routing
    - 本地缓存

陷阱 4:NAT 网关跨 AZ
  现象:NAT 单 AZ,跨 AZ 流量走 NAT 贵
  修复:每 AZ 一个 NAT(贵但稳)
```

### 25.7.4 API 限流

```
现象:
  - kubectl 命令慢
  - Pod 创建延迟高
  - 控制器 Watch 频繁重连
  - HPA 更新不及时

诊断:
  # 1. 检查 APF
  kubectl get --raw='/apis/flowcontrol.apiserver.k8s.io/v1beta3/prioritylevelconfigurations'
  
  # 2. 检查 apiserver 指标
  kubectl get --raw='/metrics' | grep apiserver_request
  
  # 3. 集群规模
  kubectl get nodes | wc -l
  kubectl get pods -A | wc -l

调优:
  1. 减少 List 请求(用 Informer / Watch)
  2. 减小 List 范围(namespace 限定)
  3. ResourceVersion 处理(List + Watch)
  4. 控制器使用 SharedInformer
  5. 分级 PriorityClass
  6. 升级集群 QPS 配额
```

### 25.7.5 Pod 阻塞(Stuck Pod)

```
常见 Pod 阻塞状态:
  1. Pending:调度失败
  2. ContainerCreating:卷/网络问题
  3. CrashLoopBackOff:容器崩溃
  4. ImagePullBackOff:镜像拉取失败
  5. Terminating(卡死):finalizer 阻塞

诊断流程:
  kubectl describe pod <pod>    # Events
  kubectl get pod <pod> -o yaml # Status
  kubectl logs <pod>            # 容器日志
  kubectl get events --sort-by=.lastTimestamp | tail -50

常见根因:
  1. Insufficient cpu/memory:节点资源不足
  2. No nodes available:节点池满
  3. Volume mounting:CSI 故障
  4. CNI 故障:IP 耗尽
  5. 镜像仓库不可达
  6. finalizer 控制器死了
```

### 25.7.6 节点池扩容慢

```
扩容慢根因:
  1. 镜像拉取慢(几 GB 镜像)
     - 用镜像加速(Nydus / Stargz)
     - 预热节点池
  
  2. User Data 脚本慢
     - 简化 bootstrap 脚本
     - 用镜像而不是脚本配置
  
  3. 实例启动慢
     - 用 Bottlerocket(AWS,启动快)
     - 用阿里 Cloud Linux / TencentOS
  
  4. kubelet 注册慢
     - 调整 --node-status-update-frequency
     - 调整 --max-pods(默认 110)
  
  5. CA 调度延迟
     - 切换到 Karpenter
     - 缩小 nodeSelector / taints

诊断:
  # 节点启动时间分解
  kubectl get nodes -o custom-columns=NAME:.metadata.name,CREATED:.metadata.creationTimestamp
  
  # 看 kubelet 日志
  journalctl -u kubelet --since "10 minutes ago"
  
  # 看实例启动事件
  # AWS: CloudTrail
  # GCP: Cloud Audit Logs
  # Azure: Activity Log
```

### 25.7.7 Spot 实例驱逐雪崩

```
现象:
  - Spot 市场价格波动,多个节点同时被驱逐
  - 业务 Pod 大规模重建
  - 服务降级或不可用

防范:
  1. 跨实例类型多样化(Karpenter Provisioner)
  2. 跨 AZ 多样化
  3. PDB(PodDisruptionBudget)防止同时驱逐过多
  4. on-demand 兜底(关键服务至少 30% on-demand)
  5. 优雅终止(terminationGracePeriodSeconds)
  6. AWS Node Termination Handler 主动响应
  7. 预热备用节点(始终保留 1-2 个 on-demand)

节点驱逐处理:
  # AWS Node Termination Handler
  helm upgrade --install aws-node-termination-handler \
    eks/aws-node-termination-handler \
    --namespace kube-system \
    --set enableSpotInterruptionDraining=true \
    --set enableRebalanceMonitoring=true \
    --set enableRebalanceDraining=true
```

### 25.7.8 Fargate / Serverless 冷启动

```
现象:
  - 流量突增时,Pod 启动慢(2-5s)
  - 用户感知到延迟
  - HPA 触发后,新 Pod 启动期间请求堆积

防范:
  1. 预热:定时任务保持最低 Pod 数
  2. HPA 提前触发(target CPU 50% 而不是 80%)
  3. KEDA 自定义指标提前触发
  4. 镜像加速(Stargz / Nydus)
  5. 镜像瘦身(distroless)
  6. 关键服务用 on-demand 而非 Fargate
  7. 就绪探针配置宽松(避免过早剔除)
```

## 25.10 面试速答

> 15 个高频问题,一句话答案。

**Q1: 托管 K8s 和自建 K8s 的核心区别是什么?**
A: 托管 K8s 的控制面(apiserver/etcd/scheduler/controller-manager)由云厂商运维并保证 SLA,用户只管 Worker Node 和应用;自建 K8s 需要用户自己运维控制面、备份 etcd、升级版本。

**Q2: Serverless 容器(ASK/Fargate/Autopilot)和普通 K8s 节点的区别?**
A: Serverless 容器没有 VM 节点,Pod 直接在云厂商虚拟化层用 microVM(Firecracker/Kata)运行,按 Pod 秒级计费,无需节点运维;普通节点按 VM 小时计费,需要节点池管理。

**Q3: IRSA(WI/RRSA)的工作原理?**
A: 集群创建 OIDC Provider,Pod 启动时拿到 ServiceAccount 的 JWT Token,通过 STS AssumeRoleWithWebIdentity 换取云 IAM 临时凭证(1 小时过期),AWS SDK 自动刷新,实现 Pod 级 IAM 权限隔离。

**Q4: Spot 实例如何防止驱逐雪崩?**
A: 1) 实例类型多样化(Karpenter Provisioner 配 10+ 类型);2) 跨 AZ 多样化;3) PDB 防止同时驱逐过多;4) 关键服务至少 30% on-demand 兜底;5) Node Termination Handler 主动 drain。

**Q5: 混部架构的核心机制?**
A: 在线业务(LS)优先级高,离线业务(BE)使用在线空闲资源;节点上的 Koordlet 实时监控,在线业务突发时 1s 内压制离线 CPU、驱逐离线内存;在线业务回落后再恢复离线。

**Q6: Firecracker 和 Kata Containers 的区别?**
A: Firecracker 是 AWS 极简 microVM(仅 4 个虚拟设备),启动 125ms,内存 5MB;Kata 兼容 OCI 标准,支持多种 VMM(QEMU/Firecracker/Cloud Hypervisor),启动 1-2s,内存 50-100MB,更适合现有 K8s 集群。

**Q7: AWS VPC CNI 的工作原理?**
A: 每个 Pod 直接绑定 ENI 的辅助 IP,Pod IP 与 VPC 子网 IP 一致,无 NAT,与 VPC 安全组一致;缺点是 IP 数量受 ENI 限制(小实例 6 IP,大实例 100+ IP),需要预留 IP。

**Q8: EKS 控制面 SLA 99.95% 意味着什么?**
A: 月度停机时间不超过 21.9 分钟(43800 × 0.0005),如果超过,云厂商按比例退款(10%-30%);但只覆盖控制面,Worker Node 故障不在 SLA 内。

**Q9: Autopilot 和 Standard GKE 的区别?**
A: Autopilot 是全托管,云厂商管理节点池、安全、网络、扩展,用户只声明 Pod;Standard 是半托管,用户管理节点池。Autopilot 节点利用率高 30%(云厂商统一调度),但灵活性低(不能 SSH 节点、不能自定义 DaemonSet)。

**Q10: Karpenter 比 Cluster Autoscaler 好在哪?**
A: Karpenter 直接调用 EC2 RunInstances,绕过 ASG,扩容速度 20-60s(vs CA 60-180s);支持实例类型多样化(Spot 友好);支持整合(把 Pod 合并到更少节点,省钱)。

**Q11: 托管 K8s 的 API 限流如何排查?**
A: 1) `kubectl get --raw='/apis/flowcontrol.apiserver.k8s.io/v1beta3/prioritylevelconfigurations'` 查 APF;2) 查 apiserver_request 指标;3) 减少全集群 List 请求,用 Informer/Watch;4) 申请提升 QPS 配额(EKS 可到 10000+)。

**Q12: 跨 AZ 流量费用的成因和优化?**
A: 跨 AZ 流量每个方向 $0.01-0.02/GB。优化:1) topologySpreadConstraints 控制 Pod 分散度;2) Service Topology Aware Hints 同 AZ 优先;3) 数据库同 AZ 部署;4) Regional 卷(GKE Regional PD);5) 缓存本地化。

**Q13: 阿里 ACK Koordinator 和字节 AllSpark 的本质区别?**
A: 两者都基于 cgroup + 自定义调度器实现混部。Koordinator 已开源(Linux 基金会),社区驱动;AllSpark 是字节内部实现,火山引擎对外提供能力但不开源;Koordinator 更通用,AllSpark 更深度集成字节内部生态。

**Q14: Serverless 容器何时比 VM 节点更划算?**
A: 临界点是 Pod 利用率。如果 Pod 长期高负载(>60%),VM 节点更便宜;如果 Pod 间歇性、低负载、突发,Serverless 按秒计费更划算。一般经验:Pod 月运行时间 < 30% 选 Serverless,> 70% 选 VM,30-70% 看具体价格。

**Q15: 多云 K8s 部署的关键挑战?**
A: 1) IAM 不互通(IRSA vs WI vs RRSA);2) CNI 不互通(VPC-CNI 各家不同);3) Ingress/StorageClass 不互通;4) 配置管理需抽象(Helm + values.yaml 多环境);5) 跨云网络互联(Transit Gateway / VPC Peering);6) 故障切换难度(数据同步是核心)。

## 25.11 综合面试题

### 题目 1(基础):解释托管 K8s 控制面的架构,以及为什么 etcd 由云厂商托管更安全?

**答题要点**:
- 控制面组成:apiserver(多副本)+ etcd(3 节点 Raft)+ scheduler + controller-manager + cloud-controller
- apiserver 多副本跨 AZ,前置 LB,SLA 99.95%
- etcd 隐藏在云厂商 VPC,用户无法直接访问
- 安全性:
  1. etcd 是 K8s 唯一有状态组件,数据丢失 = 集群丢失
  2. 云厂商自动备份(5 分钟一次)到对象存储
  3. 跨 AZ 部署,单 AZ 故障不影响 quorum
  4. mTLS 加密通信
  5. 用户无 root 权限,减少误操作
- 自建 etcd 的痛点:磁盘选型、compaction、defrag、备份恢复测试、quorum 维护

### 题目 2(中级):设计一个支持双 11 流量突增的 K8s 集群弹性方案,要求 30 秒内扩容 1000 Pod。

**答题要点**:
- 多层弹性:
  1. **HPA**:基于 CPU + 自定义指标(QPS),target 50% 触发
  2. **KEDA**:基于消息队列深度提前触发
  3. **Cluster Autoscaler / Karpenter**:节点池扩容
  4. **Serverless 容器**:突发到 ASK/VCI/Fargate,避免节点启动延迟
- 关键设计:
  1. 预热:日常保留 30% 余量
  2. 多 AZ:3 AZ 部署,单 AZ 故障不影响
  3. Spot + on-demand 混合:on-demand 兜底,Spot 突发
  4. 镜像加速:Stargz / Nydus,镜像预拉取
  5. Pod 优先级:核心业务高优先级,可抢占低优先级
  6. PDB:防止驱逐雪崩
- 30 秒目标:
  - 节点扩容太慢(60s+),必须用 Serverless
  - Serverless 冷启动 1-3s
  - 1000 Pod 并发启动,需多 AZ 同时扩容
- 监控:
  - Prometheus + 自定义指标
  - 蓝绿/金丝雀发布
  - 自动回滚机制

### 题目 3(中级):你在 EKS 上部署的服务突然 P99 延迟飙升到 5 秒,如何排查?

**答题要点**:
- 排查路径:
  1. **应用层**:看应用日志、APM(Trace),定位慢请求
  2. **Pod 层**:`kubectl top pod`,看 CPU/内存是否到 limit
  3. **节点层**:`kubectl top node`,看节点是否负载高
  4. **网络层**:跨 AZ 流量?VPC-CNI IP 耗尽?NLB 健康检查?
  5. **API 层**:apiserver 是否慢?(`kubectl get --raw='/metrics'`)
  6. **云服务**:RDS / ElastiCache 是否慢?
- 常见根因:
  1. Pod CPU throttling(limit 太低)
  2. 跨 AZ 数据库查询
  3. DNS 解析慢(CoreDNS 过载)
  4. apiserver 限流(controller 大量 List)
  5. 节点 NotReady 但 endpoints 未更新
  6. EBS 卷 IO 瓶颈
- 修复:
  - 提升 limit / HPA
  - Service Topology Aware Hints
  - NodeLocalDNS
  - 优化 controller(List-Watch 替代 List)
  - 换 IO 更高的卷(io2 / gp3)

### 题目 4(高级):设计一个跨云 K8s 多活架构,业务部署在 AWS EKS + 阿里 ACK,要求单云故障 5 分钟内切换。

**答题要点**:

  2. **数据层**:Aurora Global Database(亚秒级同步)+ RDS 跨区域只读

### 题目 5(高级):深度剖析 IRSA 工作流,以及如何防止 IRSA Token 被滥用?

**答题要点**:
- IRSA 工作流(深度):
  1. 集群创建时,创建 IAM OIDC Provider(信任集群的 OIDC 签名)
  2. 创建 IAM Role,信任策略指向 OIDC Provider,Condition 限定 `sub: system:serviceaccount:<ns>:<sa>`
  3. 给 K8s SA 加 annotation `eks.amazonaws.com/role-arn`
  4. Pod 启动时,EKS Pod Identity Webhook(Mutating)注入:
     - 环境变量 `AWS_ROLE_ARN`、`AWS_WEB_IDENTITY_TOKEN_FILE`
     - 挂载 projected volume(token 自动轮转)
  5. AWS SDK 调用 STS `AssumeRoleWithWebIdentity`,传入 OIDC JWT Token
  6. STS 验证:
     - Token 签名(用集群 OIDC 公钥)
     - Token 过期时间
     - Role 信任策略中的 `sub` 匹配
  7. STS 返回临时凭证(AccessKey/SecretKey/SessionToken),1 小时过期
  8. SDK 自动在过期前 5 分钟刷新
- 防止滥用:
  1. **最小权限**:Role 只授予必需的 Action,避免 `*`
  2. **Condition 限定**:不仅限定 `sub`,还可限定 `aud`、`iss`
  3. **审计**:CloudTrail 记录所有 AssumeRole 调用,可追溯到具体 SA
  4. **网络隔离**:Pod 无法直接访问其他云资源(VPC 安全组)
  5. **Token 短期**:OIDC Token 1 小时过期,临时凭证 1 小时过期
  6. **定期轮转**:K8s SA Token 自动轮转(projected volume)
  7. **监控**:告警异常 AssumeRole 调用(新 IP、新 User-Agent)
  8. **Boundary Policy**:IAM Permissions Boundary 限制最大权限
- 与传统凭证对比:
  - 传统:长期 AK/SK 写在 Secret,泄露后 1 年有效
  - IRSA:1 小时短期凭证,泄露窗口小

### 题目 6(高级):混部架构中,如何在 CPU 突发时保护在线业务 P99 延迟?详细描述 Koordinator 的机制。

**答题要点**:
- 问题背景:在线业务 P99 延迟敏感(10ms 内),离线任务 CPU 突发会抢占在线
- Koordinator 机制:
  1. **CPU Suppress**(关键):
     - Koordlet 实时监控(100ms 一次)节点 CPU 利用率
     - 在线业务 CPU 上升时,1s 内调整离线 cgroup `cpu.cfs_quota`
     - 离线 CPU 被压制,在线获得更多 CPU
  2. **CPU Set 隔离**:
     - 在线 Pod 用 cpuset 独占 CPU(不与其他共享)
     - 离线 Pod 用 cfs_quota(可被压制)
     - 防止离线抢占在线的物理核
  3. **CPU 升频**:
     - 在线 Pod 触发 CPU 升频到最高频率(turbo)
     - 离线 Pod 不触发升频(用 ondemand governor)
     - 在线突发时立刻获得最高频率
  4. **内存 Evict**:
     - 内存压力分级(Minor/Major/Critical)
     - Critical 时大规模驱逐离线 Pod
     - PSI(Pressure Stall Information)实时感知
  5. **网络 QoS**:
     - 在线 Pod 优先级高(tc filter)
     - 离线 Pod 限速(tc tbf)
     - 防止离线大流量打满网卡
  6. **IO Throttle**:
     - 在线 Pod IO 优先级高(blkio)
     - 离线 Pod IO 限速
     - 防止离线大 IO 影响在线磁盘
- 调度器协同:
  - 在线 Pod 调度时,避开离线高负载节点
  - 离线 Pod 调度时,避开在线高负载节点
  - 反亲和性 + 节点资源预测
- 验证:
  - 在线 P99 延迟 < 10ms(不受离线影响)
  - 离线任务吞吐 < 单独跑的 90%(被压制但可用)
  - 节点整体利用率 70%+(混部价值)

## 25.12 故障复盘

### 案例 1:EKS 控制面故障导致全集群不可用

**故障时间**:2023-11-15 02:00 UTC

**故障现象**:
- AWS us-east-1 区域,EKS apiserver 大规模超时
- 所有 `kubectl` 命令超时
- Pod 创建失败,HPA 无法触发
- 业务流量突增时无法扩容,导致 5xx 错误

**影响范围**:
- 数千个 EKS 集群受影响
- 多家大公司(Neflix、Disney+)服务降级
- 持续 3 小时

**根因**:
- EKS 内部 etcd 集群存储故障
- EBS 卷性能下降,etcd fsync 延迟飙升
- apiserver 等待 etcd 响应,导致请求堆积
- 重试风暴进一步恶化

**修复**:
1. AWS 紧急切换 etcd 到备用存储
2. 限流 apiserver,防止雪崩
3. 重启部分 apiserver 实例
4. 3 小时后完全恢复

**事后改进**:
1. AWS 增加 etcd 存储冗余
2. 改进 etcd 性能监控
3. 限流机制优化
4. 跨 region 备份

**用户侧防范**:
1. 多区域部署,Route 53 健康检查切换
2. 应用层降级(本地缓存、断路器)
3. 关键服务预留容量(不依赖 HPA)
4. 监控 EKS 健康状态,提前告警
5. 定期演练控制面故障

**经验**:托管控制面 SLA 99.95% 仍可能故障,业务必须设计容错。

### 案例 2:Serverless 容器冷启动导致 5xx 雪崩

**故障时间**:2024-03-22 春晚活动

**故障现象**:
- 某互联网公司用阿里 ASK(Serverless 容器)
- 春晚红包活动流量突增 100 倍
- Pod 冷启动 3-5 秒,大量请求堆积
- 网关 5xx 错误率 30%
- 持续 8 分钟

**根因**:
1. 完全依赖 Serverless,无预热
2. 镜像 1.5GB,冷启动慢
3. HPA 触发延迟 + Pod 启动延迟叠加
4. 网关超时 5s,Pod 还没启动完
5. 重试雪崩:用户重试 + 健康检查失败

**修复**:
1. 紧急扩容网关超时到 30s
2. 手动预热 500 Pod(发送空请求触发)
3. 切换部分流量到 ECS 兜底
4. 8 分钟后恢复

**事后改进**:
1. **预热**:日常保持最低 200 Pod,活动前预热到 1000
2. **镜像优化**:1.5GB → 200MB(多阶段构建 + distroless)
3. **镜像加速**:用 Nydus 按需加载,冷启动 5s → 1s
4. **HPA 提前**:target CPU 50% 而不是 80%
5. **KEDA**:基于消息队列深度提前 5 分钟触发
6. **多策略**:70% VM + 30% Serverless,VM 兜底
7. **网关降级**:超时 + 重试 + 熔断

**经验**:Serverless 不是银弹,关键场景必须 VM + Serverless 混合。

### 案例 3:Spot 实例大规模驱逐导致业务中断

**故障时间**:2024-06-10

**故障现象**:
- AWS EKS 集群,Spot 实例占 80%
- 突发 Spot 价格波动,5 分钟内 200 节点被驱逐
- 业务 Pod 大规模重建,资源不足
- PDB 未配置,多个 Pod 同时被驱逐
- 数据库连接池打满(新 Pod 全部尝试连接)
- 持续 15 分钟,5xx 错误率 50%

**根因**:
1. Spot 实例类型过于集中(只用 m5.xlarge)
2. PDB 配置错误(minAvailable: 0)
3. 没有兜底的 on-demand 节点
4. 数据库连接池未做预热保护
5. Pod 优先级未配置,关键服务被驱逐

**修复**:
1. 紧急扩容 on-demand 节点池
2. 关闭 HPA 防止进一步扩容
3. 数据库连接池限流
4. 15 分钟后恢复

**事后改进**:
1. **实例多样化**:Karpenter Provisioner 配 10+ 实例类型
2. **跨 AZ 多样化**:3 AZ 部署
3. **PDB 严格**:关键服务 minAvailable: 50%
4. **混合策略**:50% on-demand + 50% Spot
5. **Node Termination Handler**:主动响应 Spot 中断,提前 drain
6. **优先级**:关键服务 PriorityClass 高,不会被驱逐
7. **数据库保护**:连接池预热 + 限流 + 重试退避

**经验**:Spot 实例必须有多层保护,关键服务不能完全依赖 Spot。

### 案例 4:跨 AZ 网络抖动导致服务延迟飙升

**故障时间**:2024-08-05

**故障现象**:
- 三 AZ 部署的 EKS 集群
- 某个 AZ 网络设备故障,跨 AZ 延迟从 1ms 飙升到 50ms
- 业务 P99 延迟从 50ms 飙升到 2 秒
- 数据库连接超时,大量重试

**根因**:
1. Pod 跨 AZ 分散,topologySpreadConstraints 配置过严
2. Service 默认轮询,跨 AZ 流量大
3. 数据库主节点在故障 AZ,跨 AZ 写入
4. CoreDNS 跨 AZ 解析慢

**修复**:
1. 紧急把数据库 failover 到健康 AZ
2. 调整 topologySpreadConstraints,允许同 AZ 调度
3. 启用 Service Topology Aware Hints
4. 1 小时后恢复

**事后改进**:
1. **同 AZ 优先**:Service Topology Aware Hints
2. **数据库多 AZ**:Aurora Multi-AZ,自动 failover
3. **CoreDNS 部署**:每 AZ 至少 1 个副本
4. **监控跨 AZ 延迟**:CloudWatch 跨 AZ 监控
5. **演练**:定期断 AZ 演练

**经验**:跨 AZ 不是免费的,延迟 + 费用都需要权衡。

### 案例 5:APIServer 限流导致控制器大面积延迟

**故障时间**:2024-04-18

**故障现象**:
- 5000 节点集群
- 多个控制器(Cert-Manager、Argo CD、Prometheus Operator)同时大量 List
- apiserver QPS 飙到上限
- HPA 更新延迟 5 分钟
- Pod 创建延迟 30 秒

**根因**:
1. 控制器未优化,频繁全集群 List
2. APF 未合理分级
3. Prometheus 抓取指标频繁
4. 多个 Operator 重启,List 风暴

**修复**:
1. 紧急重启部分 Operator
2. 降低 Prometheus 抓取频率
3. 临时提升集群 QPS 配额
4. 1 小时后恢复

**事后改进**:
1. **控制器优化**:用 Informer/Watch 替代 List
2. **APF 分级**:关键控制器高优先级
3. **Prometheus 优化**:降低抓取频率,用 kube-state-metrics 缓存
4. **Operator 治理**:统一管理 Operator,避免重复
5. **监控 APF**:apiserver_flow_schema 指标
6. **QPS 配额**:提前申请提升

**经验**:大规模集群的 apiserver 是稀缺资源,必须治理。

## 本章小结

大厂 K8s 平台是 K8s 工程化的最高形态,核心价值在于:

1. **降低运维成本**:托管控制面、自动升级、SLA 保障
2. **提升资源效率**:Serverless 容器、Spot 实例、混部节点
3. **打通云生态**:IAM、网络、存储、监控深度集成
4. **加速业务落地**:从基础设施到应用的全栈优化

选型决策应基于:
- **数据合规**:决定国内 vs 国外
- **成本**:Spot、混部、节点池组合
- **团队技能**:熟悉哪个云
- **生态**:已有云资源
- **性能**:单集群规模、API 延迟

关键趋势:
- **Serverless 化**:Autopilot、Fargate、ASK 越来越受欢迎
- **混部普及**:Koordinator 开源后,混部成为大厂标配
- **多集群**:Cluster API、Karmada、Crossplane 成熟
- **安全沙箱**:Firecracker、Kata 在 Serverless 场景成为标配
- **FinOps**:成本可观测性、混部、Spot 成为核心能力

下一章 [26-大规模集群优化](./26-大规模集群优化.md) 将深入剖析单集群从 1000 → 5000 → 10000 节点的演进路径,涵盖 etcd 调优、调度器扩展、APF 限流等核心优化。
