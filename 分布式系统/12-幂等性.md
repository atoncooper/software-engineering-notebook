## 0. 为什么幂等性是分布式系统的"第一公民"

单机环境下,一次操作要么成功要么失败,客户端明确知道结果。分布式环境下,**网络抖动、超时重试、消息重复投递** 是常态:

- HTTP 请求超时,客户端重试,但服务端可能已经处理完
- MQ 投递成功,但 ACK 丢失,触发重投
- 数据库事务提交成功,但客户端连接断开,触发重试
- 网络分区,客户端不知道服务端是否处理

如果操作不幂等,这些场景下会导致:

- 重复扣款
- 重复发货
- 重复发券
- 数据脏写

> **幂等性 (Idempotency)**:同一操作执行一次与执行多次,对系统状态产生相同的影响。

数学定义:$f(f(x)) = f(x)$,即 $f$ 是闭包算子。

幂等性不是"免费午餐",需要在 API 设计、存储设计、状态机设计多个层面主动保证。本章系统梳理工程实现。

## 1. 定义与动机

### 1.1 幂等的严格定义

| 类型 | 定义 | 例子 |
|------|------|------|
| **强幂等** | 任意次执行结果相同(包括返回值) | `GET /user/123`、`DELETE /user/123` 第二次返回 404 |
| **弱幂等** | 系统状态相同,返回值可不同 | `POST /pay` 第一次返回 SUCCESS,第二次返回 DUPLICATE |
| **业务幂等** | 业务语义上的幂等(扣款金额一致) | 重复扣款检测,返回"已处理" |

### 1.2 不幂等的典型场景

| 操作 | 不幂等的原因 |
|------|------------|
| `POST /order` (无 ID) | 每次创建新订单 |
| `UPDATE balance = balance - 100` | 重复执行多次扣多次 |
| `INSERT INTO log VALUES(...)` | 重复插入多行 |
| `INSERT INTO account VALUES(...)` | 重复插入报错 |
| 发短信、发邮件 | 重复发送 |

### 1.3 幂等的工程价值

1. **可重试**:失败可安全重试,客户端逻辑简单
2. **可恢复**:MQ/网络故障下重投不会污染数据
3. **可对账**:外部对账时幂等键辅助定位
4. **可灰度**:灰度发布期间重复请求不影响数据

## 2. 原理与算法

### 2.1 幂等键 (Idempotency Key)

#### 2.1.1 核心思想

客户端为每次操作生成唯一 ID,服务端记录"已处理过的 ID + 结果",重复请求直接返回缓存结果。

```
客户端                              服务端
  |  POST /pay                       |
  |  Idempotency-Key: abc-123        |
  |  {user: 1001, amount: 100}      |
  | ────────────────────────────────→|
  |                                  | 检查 abc-123 是否已处理
  |                                  | 否 → 执行扣款,记录结果
  |                                  | 是 → 直接返回记录的结果
  |←──────────────────────────────── |
  |  200 OK {status: SUCCESS}        |
  |                                  |
  | (超时,重试)                       |
  |  POST /pay                       |
  |  Idempotency-Key: abc-123        |
  |  {user: 1001, amount: 100}      |
  | ────────────────────────────────→|
  |                                  | 检查 abc-123 → 已处理
  |←──────────────────────────────── |
  |  200 OK {status: SUCCESS}        | (返回相同结果)
```

#### 2.1.2 实现:幂等表

```sql
CREATE TABLE idempotency_record (
    idempotency_key VARCHAR(64) NOT NULL,
    business_type VARCHAR(32) NOT NULL,
    request_payload TEXT,
    response_payload TEXT,
    status ENUM('PROCESSING', 'SUCCESS', 'FAILED'),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (business_type, idempotency_key)
);
```

```java
public class IdempotentService {
    private final JdbcTemplate jdbc;
    private final PayService payService;

    public PayResponse pay(String idempotencyKey, PayRequest req) {
        // 1. 原子插入幂等记录(PROCESSING),冲突则已有记录
        try {
            jdbc.update("INSERT INTO idempotency_record(business_type, idempotency_key, status) " +
                        "VALUES('pay', ?, 'PROCESSING')", idempotencyKey);
        } catch (DuplicateKeyException e) {
            // 已存在,返回之前结果(或等待)
            return getExistingResult(idempotencyKey);
        }

        try {
            PayResponse resp = payService.doPay(req);
            jdbc.update("UPDATE idempotency_record SET status='SUCCESS', response_payload=? " +
                        "WHERE business_type='pay' AND idempotency_key=?",
                        toJson(resp), idempotencyKey);
            return resp;
        } catch (Exception e) {
            jdbc.update("UPDATE idempotency_record SET status='FAILED' " +
                        "WHERE business_type='pay' AND idempotency_key=?", idempotencyKey);
            throw e;
        }
    }

    private PayResponse getExistingResult(String key) {
        // 若 PROCESSING:可能并发请求,可等待或返回 409
        // 若 SUCCESS:返回缓存结果
        // 若 FAILED:允许重试(删除记录后重试)
        return jdbc.queryForObject(
            "SELECT response_payload FROM idempotency_record " +
            "WHERE business_type='pay' AND idempotency_key=? AND status='SUCCESS'",
            (rs, i) -> fromJson(rs.getString("response_payload"), PayResponse.class), key);
    }
}
```

#### 2.1.3 关键细节

1. **INSERT 必须原子**:用 `INSERT ... ON DUPLICATE KEY` 或唯一索引 + `DuplicateKeyException` 捕获。
2. **状态机**:PROCESSING / SUCCESS / FAILED,处理中请求需要特殊处理(返回 409 或等待)。
3. **请求体校验**:同 key 但请求体不同,说明客户端误用,应拒绝。
4. **TTL**:幂等记录需要清理(典型 24h ~ 7d),否则表无限增长。
5. **业务 + Key 联合唯一**:不同业务的 key 空间独立,避免冲突。

```sql
-- 用 Redis 做幂等记录(性能高)
SET idem:pay:abc-123 PROCESSING NX EX 86400
-- 业务完成后:
SET idem:pay:abc-123 <json_response> EX 86400
```

```go
// Go: Redis 幂等
func (s *PayService) Pay(idemKey string, req PayRequest) (*PayResponse, error) {
    ctx := context.Background()
    // 1. 抢占
    ok, _ := s.Redis.SetNX(ctx, "idem:pay:"+idemKey, "PROCESSING", 24*time.Hour).Result()
    if !ok {
        // 已存在,读取已有结果
        val, _ := s.Redis.Get(ctx, "idem:pay:"+idemKey).Result()
        if val == "PROCESSING" {
            return nil, ErrConcurrentRequest
        }
        var cached PayResponse
        json.Unmarshal([]byte(val), &cached)
        return &cached, nil
    }
    // 2. 执行
    resp, err := s.doPay(req)
    if err != nil {
        s.Redis.Del(ctx, "idem:pay:"+idemKey)  // 失败允许重试
        return nil, err
    }
    // 3. 缓存结果
    data, _ := json.Marshal(resp)
    s.Redis.Set(ctx, "idem:pay:"+idemKey, data, 24*time.Hour)
    return resp, nil
}
```

### 2.2 Token 机制

#### 2.2.1 适用场景

表单提交、前端按钮防抖:

```
1. 前端进入页面时,先 GET /api/token 获取一个 token
2. 服务端把 token 存 Redis (SET token "" NX EX 600)
3. 提交时附带 token
4. 服务端验证 token 存在,然后 DEL token
5. 重复提交时 token 已删,拒绝
```

```java
// 服务端
@GetMapping("/api/token")
public String getToken() {
    String token = UUID.randomUUID().toString();
    redis.opsForValue().set("form_token:" + token, "1", Duration.ofMinutes(10));
    return token;
}

@PostMapping("/api/order")
public OrderResponse createOrder(@RequestHeader("X-Token") String token,
                                  @RequestBody OrderRequest req) {
    // 原子 DEL(用 Lua),返回 1 表示成功消费
    String script = "if redis.call('GET',KEYS[1]) then return redis.call('DEL',KEYS[1]) else return 0 end";
    Long consumed = redis.execute(new DefaultRedisScript<>(script, Long.class),
            Collections.singletonList("form_token:" + token));
    if (consumed == null || consumed == 0) {
        throw new BadRequestException("Token expired or duplicate submit");
    }
    return orderService.create(req);
}
```

#### 2.2.2 与幂等键的区别

| 维度 | 幂等键 | Token |
|------|--------|-------|
| 谁生成 | 客户端 | 服务端 |
| 用途 | 业务幂等(重试安全) | 防重复提交(短期) |
| 生命周期 | 业务相关(24h~7d) | 短期(分钟级) |
| 返回 | 重复时返回原结果 | 重复时拒绝 |
| 适用 | API 调用、MQ 消费 | 表单、前端按钮 |

### 2.3 CAS (Compare-And-Swap)

#### 2.3.1 乐观锁实现

数据库 CAS 是最简单高效的幂等方式,适合"更新已有数据"的操作:

```sql
-- 扣款,带版本号
UPDATE account
SET balance = balance - 100, version = version + 1
WHERE user_id = 1001 AND version = 5 AND balance >= 100;
-- affected rows = 1 → 成功
-- affected rows = 0 → 版本冲突或余额不足,需重试或返回失败
```

```java
public boolean deductCAS(Long userId, BigDecimal amount, int expectedVersion) {
    int affected = jdbc.update(
        "UPDATE account SET balance = balance - ?, version = version + 1 " +
        "WHERE user_id = ? AND version = ? AND balance >= ?",
        amount, userId, expectedVersion, amount);
    return affected == 1;
}

public PayResponse payWithCAS(Long userId, BigDecimal amount) {
    for (int retry = 0; retry < 3; retry++) {
        Account acc = jdbc.queryForObject("SELECT * FROM account WHERE user_id = ?",
                (rs, i) -> new Account(rs.getLong("user_id"),
                        rs.getBigDecimal("balance"), rs.getInt("version")), userId);
        if (acc.getBalance().compareTo(amount) < 0) throw new InsufficientBalance();
        if (deductCAS(userId, amount, acc.getVersion())) {
            return PayResponse.success();
        }
        // 版本冲突,重试
    }
    throw new ConcurrentUpdateConflict();
}
```

#### 2.3.2 CAS 的优势

- 无需额外表
- 数据库原生支持,原子性强
- 性能高(单 SQL)

#### 2.3.3 CAS 的局限

- 需要业务字段带版本号
- 高并发下重试次数多(乐观锁劣势)
- 不适合"创建操作"(无初始版本)

### 2.4 唯一索引 + 状态机

#### 2.4.1 业务唯一键

利用业务字段本身做唯一约束:

```sql
-- 订单表:订单号唯一
CREATE TABLE orders (
    order_no VARCHAR(32) PRIMARY KEY,
    user_id BIGINT,
    amount DECIMAL(10,2),
    status ENUM('CREATED', 'PAID', 'CANCELED'),
    created_at TIMESTAMP
);

-- 重复请求同 order_no → 主键冲突 → 幂等
INSERT INTO orders(order_no, user_id, amount) VALUES(?, ?, ?);
-- 冲突时捕获 DuplicateKeyException,查询返回已有订单
```

```java
public Order createOrder(OrderRequest req) {
    String orderNo = req.getClientOrderNo();  // 客户端生成的唯一号
    try {
        return orderRepo.insert(new Order(orderNo, req.getUserId(), req.getAmount()));
    } catch (DuplicateKeyException e) {
        return orderRepo.findByOrderNo(orderNo);  // 返回已有订单
    }
}
```

#### 2.4.2 状态机幂等

对于状态流转(订单状态、支付状态),用状态机保证幂等:

```sql
-- 状态流转 UPDATE
UPDATE orders
SET status = 'PAID', paid_at = NOW()
WHERE order_no = ? AND status IN ('CREATED');  -- 只有 CREATED 才能转 PAID
-- affected rows = 1 → 首次支付
-- affected rows = 0 → 已是 PAID 或其他状态
```

```java
public PayResponse pay(String orderNo) {
    int affected = jdbc.update(
        "UPDATE orders SET status='PAID', paid_at=NOW() " +
        "WHERE order_no=? AND status='CREATED'", orderNo);
    if (affected == 1) {
        // 首次支付成功
        return PayResponse.firstSuccess();
    }
    Order order = jdbc.queryForObject("SELECT * FROM orders WHERE order_no=?",
            mapper, orderNo);
    if (order.status == 'PAID') {
        return PayResponse.alreadyPaid();  // 已支付,幂等返回
    }
    throw new InvalidStatusTransition(order.status);
}
```

状态机表(典型订单状态):

```
  CREATED → PAID → SHIPPED → DELIVERED → COMPLETED
     ↓       ↓
  CANCELED  CANCELED (退款)
```

每个状态转移用 `UPDATE ... WHERE status IN (...)` 保证原子 + 幂等。

### 2.5 去重表 (Dedup Table)

针对 MQ 消费、回调通知等场景:

```sql
CREATE TABLE consumed_messages (
    consumer_group VARCHAR(64),
    message_id VARCHAR(64),
    consumed_at TIMESTAMP,
    PRIMARY KEY (consumer_group, message_id)
);
```

```java
@KafkaListener(topics = "payment-events", groupId = "order-service")
public void onPaymentEvent(PaymentEvent event) {
    try {
        jdbc.update("INSERT INTO consumed_messages(consumer_group, message_id) " +
                    "VALUES('order-service', ?)", event.getMessageId());
    } catch (DuplicateKeyException e) {
        return;  // 已消费,跳过
    }
    try {
        orderService.handlePayment(event);
    } catch (Exception e) {
        jdbc.update("DELETE FROM consumed_messages WHERE consumer_group='order-service' " +
                    "AND message_id=?", event.getMessageId());  // 处理失败,允许重试
        throw e;
    }
}
```

> ⚠️ **易错**:去重表先 insert 再处理,处理失败要删除记录,否则该消息永远无法重试。

## 3. 🎓 学术深度

### 3.1 幂等的代数结构

幂等操作 $f$ 满足 $f \circ f = f$,在代数上是**投影算子**。

进一步:

- **强幂等**:$f(f(x)) = f(x)$ 对所有 $x$ 成立
- **业务幂等**:$f$ 在业务语义上是闭包,如"扣款 100 元"操作,即使多次调用,账户余额也只扣一次

> 🎓 数学上,幂等操作总是可以分解为"检测 + 应用"两步:先检测是否已应用,若否则应用。这与 §2.1 幂等键的"先查后做"一一对应。

### 3.2 Exactly-Once 语义的不可能性

> 📜 FLP 类比:在异步网络下,真正的 exactly-once 投递不可能(只能 at-least-once + 幂等消费)。

原因:消息投递成功的 ACK 也可能丢失,消费者无法区分"投递成功 ACK 丢失"和"投递失败"。

工程方案:**at-least-once + 幂等消费 = 业务层 exactly-once**。Kafka、RocketMQ、Pulsar 都采用此思路。

### 3.3 两阶段幂等 (Two-Phase Idempotency)

```
Phase 1 (Reserve): 预占资源(标记 PROCESSING)
Phase 2 (Confirm/Cancel): 确认或回滚
```

这与 [[06-事务-TCC与Saga]] 的 TCC 类似,本质是"幂等 + 两阶段"。TCC 的 Confirm/Cancel 必须幂等(重试安全)。

### 3.4 幂等与共识

> 🎓 在共识系统中,所有日志条目天然幂等:同一 log index 的 entry 被重复 apply,结果相同(状态机抽象)。

这是 Raft/Paxos 实现"复制状态机"的理论基础。客户端请求 → 转化为日志条目 → 共识 → apply 到状态机。重复 apply 同一 entry 不影响状态机。

### 3.5 幂等性的边界:副作用

数学幂等不等于业务幂等。例如:

```http
POST /sms/send
{ to: "+8613800138000", text: "Your code is 1234" }
```

- 数学上:每次返回成功 → 幂等
- 业务上:每次发送一条短信 → 不幂等

外发副作用(HTTP、短信、邮件)必须用幂等键 + 状态机严格控制:

```java
public void sendSms(String idemKey, String to, String text) {
    if (!tryMarkProcessing(idemKey)) {
        return;  // 已处理或处理中
    }
    try {
        smsClient.send(to, text);
        markSuccess(idemKey, response);
    } catch (Exception e) {
        markFailed(idemKey);  // 允许重试
        throw e;
    }
}
```

## 4. 🏭 工业实战

### 4.1 Stripe 的 Idempotency-Key

Stripe 是幂等键设计的工业标杆:

```http
POST /v1/charges
Idempotency-Key: client-generated-uuid
{
  "amount": 1000,
  "currency": "usd",
  "source": "tok_xxx"
}
```

- 客户端生成 UUID 作为 key
- 服务端记录 key + 请求参数 hash + 响应
- 同 key 不同请求参数 → 返回 422 (api_error)
- key 保留 24 小时
- 重复请求返回首次结果(包括首次的错误)

```java
// 参照 Stripe 设计的实现
public class StripeLikeIdempotency {
    public Response handle(String idemKey, String reqBody, RequestHandler handler) {
        // 1. 计算请求体 hash
        String reqHash = sha256(reqBody);

        // 2. 抢占 INSERT
        try {
            jdbc.update("INSERT INTO idem(key, req_hash, status, created_at) " +
                        "VALUES(?, ?, 'PROCESSING', NOW())", idemKey, reqHash);
        } catch (DuplicateKeyException e) {
            // 已存在
            IdemRecord rec = jdbc.queryForObject("SELECT * FROM idem WHERE key=?", mapper, idemKey);
            if (!rec.reqHash.equals(reqHash)) {
                throw new ApiError(422, "Idempotency key reused with different params");
            }
            if (rec.status.equals("PROCESSING")) {
                throw new ApiError(409, "Request in progress");
            }
            return Response.fromJson(rec.responseBody);
        }

        // 3. 执行
        try {
            Response resp = handler.handle(reqBody);
            jdbc.update("UPDATE idem SET status='SUCCESS', response_body=?, completed_at=NOW() " +
                        "WHERE key=?", resp.toJson(), idemKey);
            return resp;
        } catch (Exception e) {
            jdbc.update("UPDATE idem SET status='FAILED', response_body=? WHERE key=?",
                    errorJson(e), idemKey);
            throw e;
        }
    }
}
```

### 4.3 Kafka 消费者幂等

```java
// 1. 业务幂等键 + 去重表
@KafkaListener(topics = "orders")
public void onOrder(OrderEvent event) {
    try {
        jdbc.update("INSERT INTO consumed(message_id) VALUES(?) ON CONFLICT DO NOTHING",
                    event.getMessageId());
        if (affectedRows() == 0) return;  // 已消费
        orderService.process(event);
    } catch (Exception e) {
        // 处理失败:ack 不提交,让 Kafka 重投
        throw e;
    }
}

// 2. Kafka 0.11+ Producer 幂等(端到端 exactly-once)
props.put("enable.idempotence", true);  // 启用幂等 producer
props.put("acks", "all");
props.put("transactional.id", "order-producer-1");
```

Kafka 幂等 producer 原理:

- Producer 启动时获得 producer_id + epoch
- 每条消息带 sequence_number
- Broker 按 (topic, partition, producer_id) 去重
- 同 sequence_number 重复投递,broker 只持久化一次

### 4.5 状态机驱动的订单系统

```java
public enum OrderStatus {
    CREATED, PAID, SHIPPED, DELIVERED, COMPLETED, CANCELED, REFUNDED
}

public class OrderStateMachine {
    private static final Map<OrderStatus, Set<OrderStatus>> TRANSITIONS = Map.of(
        CREATED, Set.of(PAID, CANCELED),
        PAID, Set.of(SHIPPED, REFUNDED),
        SHIPPED, Set.of(DELIVERED),
        DELIVERED, Set.of(COMPLETED, REFUNDED),
        COMPLETED, Set.of(),
        CANCELED, Set.of(),
        REFUNDED, Set.of()
    );

    public boolean canTransit(OrderStatus from, OrderStatus to) {
        return TRANSITIONS.getOrDefault(from, Set.of()).contains(to);
    }
}

public void pay(String orderNo) {
    int affected = jdbc.update(
        "UPDATE orders SET status='PAID', paid_at=NOW() " +
        "WHERE order_no=? AND status='CREATED'", orderNo);
    if (affected == 0) {
        // 幂等:已是 PAID 或非法转移
        Order o = findByNo(orderNo);
        if (o.status == PAID) return;
        throw new IllegalStatusTransition(o.status, "PAID");
    }
}
```

### 4.6 工业级幂等模板

```java
public class IdempotentTemplate {
    public <T> T execute(String businessType, String idemKey,
                          Supplier<T> action) {
        // 1. 抢占幂等记录
        IdemRecord rec;
        try {
            rec = idemRepo.insert(businessType, idemKey, PROCESSING);
        } catch (DuplicateKeyException e) {
            rec = idemRepo.find(businessType, idemKey);
            return handleExisting(rec);
        }
        // 2. 执行业务
        try {
            T result = action.get();
            idemRepo.markSuccess(rec, toJson(result));
            return result;
        } catch (RetryableException e) {
            idemRepo.delete(rec);  // 可重试,删除记录
            throw e;
        } catch (Exception e) {
            idemRepo.markFailed(rec, toJson(e));  // 不可重试,记录失败
            throw e;
        }
    }

    @SuppressWarnings("unchecked")
    private <T> T handleExisting(IdemRecord rec) {
        switch (rec.status) {
            case PROCESSING:
                throw new ConcurrentRequestException();
            case SUCCESS:
                return (T) fromJson(rec.response, Object.class);
            case FAILED:
                throw new PreviousFailedException();
            default:
                throw new IllegalStateException();
        }
    }
}

// 使用
PayResponse resp = idempotent.execute("pay", idemKey,
    () -> payService.doPay(req));
```

## 5. 面试要点

### 5.1 高频问答

**Q1: 什么是幂等性?为什么分布式系统需要?**

> 幂等性是"同一操作多次执行,系统状态相同"的性质。分布式系统需要它是因为网络超时、消息重投、客户端重试是常态,没有幂等性会导致重复扣款、重复发货等数据问题。

**Q2: 实现幂等有哪些方式?**

> (1) 幂等键 + 幂等表(适合 API);(2) Token 机制(适合表单防抖);(3) CAS 乐观锁(适合更新);(4) 唯一索引(适合创建);(5) 状态机(适合状态流转);(6) 去重表(适合 MQ 消费)。

**Q3: 幂等键怎么实现?并发请求怎么处理?**

> 客户端生成唯一 ID(如 UUID),服务端用 `INSERT ... ON CONFLICT` 或唯一索引抢占幂等记录,状态 PROCESSING。并发同 key 请求:第二个请求 INSERT 冲突,看到状态 PROCESSING,返回 409 让客户端等待或重试。

**Q4: CAS 乐观锁和悲观锁的选型?**

> 悲观锁(SELECT FOR UPDATE)适合写多读少、竞争激烈;乐观锁(CAS)适合读多写少、冲突少。CAS 高并发下重试开销大,但无锁等待,吞吐更高。

**Q5: Kafka 怎么实现 exactly-once?**

> Producer 端:enable.idempotence=true,Kafka 自动去重(broker 按 producer_id + sequence_number);Consumer 端:用事务跨 consume-process-produce,或业务层幂等(去重表)。本质是 at-least-once + 幂等消费 = 业务 exactly-once。

**Q6: 幂等键的 TTL 怎么设?**

> 取决于业务场景和客户端重试窗口:支付类建议 24h ~ 7d(对账周期);查询类 1h ~ 24h;表单 token 5 ~ 30 分钟。太短可能客户端重试时已过期;太长存储成本高。

**Q7: 外发副作用(HTTP 调用、发短信)怎么幂等?**

> 用幂等键 + 状态机:先标记 PROCESSING,再外发,根据结果标记 SUCCESS/FAILED。重复请求时根据状态返回。外发失败时,根据"是否真的发送成功"决定是否允许重试(如对方支持幂等键则可重试,否则需人工介入)。

**Q8: 状态机幂等的核心是什么?**

> `UPDATE ... WHERE status IN (...)` 把"状态转移条件"放进 WHERE 子句,数据库原子保证只有一个请求能成功转移。affected rows = 0 表示状态已变(可能已被同请求处理过),返回当前状态即可。

### 5.2 易错点 ⚠️

1. **"GET 一定幂等"** — 不一定。GET 触发副作用(如统计、缓存击穿)就不幂等。
2. **"幂等键用 UUID 就够"** — 不够,还需要业务类型区分(不同业务的 key 空间隔离)。
3. **"DELETE 一定幂等"** — 不一定。第一次返回 200,第二次 404,严格说返回值不同;但状态幂等(已删除保持删除)。
4. **"乐观锁永远比重试"** — 错。高并发写竞争时,CAS 重试可能超过限制,需要退化为悲观锁或队列。
5. **"幂等记录可以一直存"** — 错。需要 TTL 清理,否则表无限增长。
6. **"Kafka 消费者自动幂等"** — 错。Kafka 提供 at-least-once,消费者必须自己实现幂等。

## 9. 速查表 (Cheat Sheet)

```
选型决策:
  是创建操作(无初始版本)?
    → 唯一索引 (业务唯一键) 或 幂等键+幂等表
  是更新操作(已有版本号)?
    → CAS 乐观锁 (UPDATE ... WHERE version=?)
  是状态流转?
    → 状态机 (UPDATE ... WHERE status IN (...))
  是 MQ 消费?
    → 去重表 (message_id 唯一)
  是表单防抖?
    → Token 机制 (服务端发 + 一次性消费)
  是 API 重试?
    → 幂等键 + 幂等表 (Stripe 风格)
  外发副作用?
    → 幂等键 + 状态机,失败需根据"是否真发出"决定重试

幂等记录清理:
  - Redis: TTL 自动过期
  - DB: 定时任务清理,或分区表按天分
  - 业务层: 对账任务核销
```
