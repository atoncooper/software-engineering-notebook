## 3.1 物理时钟

### 3.1.1 为什么需要时钟

分布式系统中时钟用于：

- **排序事件**：哪个先发生？
- **超时检测**：对方是否故障？
- **TTL/过期**：缓存、会话
- **时间戳冲突解决**：LWW（Last-Writer-Wins）
- **事务隔离**：MVCC、快照隔离

### 3.1.2 物理时钟的问题

#### 时钟漂移（Clock Drift）

- 石英晶振每天漂移 ~1 秒（$10^{-6}$ 比率）
- 不同节点时钟逐渐偏离
- 即使 NTP 同步，仍存在毫秒级误差

#### NTP 的局限

- NTP（Network Time Protocol）：分层时间同步
- Stratum 0：原子钟、GPS
- Stratum 1：直接同步 Stratum 0
- Stratum 2-15：逐级同步

**问题**：

- 网络延迟导致同步误差
- NTP 会**调整时钟**（逐步拉回），可能造成「时间变慢/变快」
- NTP 可能「跳变」（step 模式），导致时间倒退 → 破坏基于时间戳的逻辑

#### 闰秒（Leap Second）

- 地球自转不均匀，需要插入闰秒（如 23:59:60）
- 闰秒导致同一 UTC 分钟有 61 秒
- 2012 年闰秒导致 Reddit、Mozilla、LinkedIn 等大量系统故障

**Google 的 Smear Leap Second** 🔥：

- 在 24 小时内逐步拉慢时钟（每秒慢 ~11.6 微秒）
- 闰秒到来时已平滑过渡
- AWS、Microsoft 后来也采用类似方案

⚠️ **生产陷阱**：

- JVM 对闰秒敏感，会触发 bug
- Cassandra 曾因闰秒导致数据版本错乱
- 解决：使用 Smear Leap Second 或 GPS 时钟

### 3.1.3 UTC / TAI / GPS

| 时标 | 含义 |
|------|------|
| **TAI**（International Atomic Time） | 国际原子时，无闰秒 |
| **UTC**（Coordinated Universal Time） | TAI + 闰秒修正 |
| **GPS** | GPS 卫星时间，类似 TAI（无闰秒但有周数翻转） |
| **Monotonic Clock** | 单调时钟，仅进程内可用，不可跨节点比较 |

⚠️ **关键**：**跨节点比较只能用 UTC，但 UTC 有跳变风险**。Spanner 的 TrueTime 用 TAI + 闰秒表解决。

## 3.2 Lamport 逻辑时钟

📜 [Lamport 1978] *Time, Clocks, and the Ordering of Events in a Distributed System*

### 3.2.1 happens-before 关系（→）⭐

> **定义**：事件 $e_1$ happens-before $e_2$（记作 $e_1 \to e_2$），当且仅当：
>
> 1. 同进程内：$e_1$ 在 $e_2$ 之前发生
> 2. 跨进程：$e_1$ 发送消息，$e_2$ 接收该消息
> 3. 传递：$e_1 \to e_2$ 且 $e_2 \to e_3$，则 $e_1 \to e_3$

**并发**：若 $e_1 \not\to e_2$ 且 $e_2 \not\to e_1$，则 $e_1 \| e_2$（并发）。

### 3.2.2 Lamport 时钟算法

每个进程 $p_i$ 维护逻辑时钟 $C_i$，初值为 0：

```pseudocode
# 本地事件
function localEvent():
    C_i = C_i + 1
    timestamp = C_i

# 发送消息
function sendMessage(m):
    C_i = C_i + 1
    send(C_i, m)  # 把时钟随消息一起发送

# 接收消息
function receiveMessage(timestamp_c, m):
    C_i = max(C_i, timestamp_c) + 1
    # 处理消息
```

### 3.2.3 性质

**Clock Condition**：

$$
e_1 \to e_2 \implies C(e_1) < C(e_2)
$$

⚠️ **关键**：**反过来不成立**——$C(e_1) < C(e_2)$ 不意味着 $e_1 \to e_2$。

**全序构造**：

- 用 $(C_i, i)$（时钟 + 进程号）构造全序
- 当 $C_i = C_j$ 时，进程号小的在前

### 3.2.4 ⚠️ Lamport 时钟不能检测并发

**例**：

- 进程 A：事件 $e_1$，$C_A = 1$
- 进程 B：事件 $e_2$，$C_B = 1$
- $e_1$ 与 $e_2$ 并发
- 但 $C(e_1) = C(e_2) = 1$，无法判断

→ **向量时钟**解决此问题。

### 3.2.5 应用

- **分布式互斥**：用 Lamport 时钟实现公平锁（先到先得）
- **分布式快照**：Chandy-Lamport 算法基础
- **数据库事务时间戳**：简化冲突解决

## 3.3 向量时钟

📜 [Mattern 1989] / [Fidge 1988] 独立提出。

### 3.3.1 数据结构

每个进程 $p_i$ 维护向量 $VC_i = (v_1, v_2, \dots, v_n)$，其中 $v_j$ 表示 $p_i$ 已知 $p_j$ 发生过的事件数。

### 3.3.2 算法

```pseudocode
# 初始化
VC_i = [0, 0, ..., 0]

# 本地事件
function localEvent():
    VC_i[i] = VC_i[i] + 1

# 发送消息
function sendMessage(m):
    VC_i[i] = VC_i[i] + 1
    send(VC_i, m)

# 接收消息
function receiveMessage(VC_sender, m):
    for j in 1..n:
        VC_i[j] = max(VC_i[j], VC_sender[j])
    VC_i[i] = VC_i[i] + 1
```

### 3.3.3 比较规则 ⭐

对两个向量时钟 $VC_1$ 和 $VC_2$：

- $VC_1 < VC_2$ 当且仅当 $\forall j: VC_1[j] \leq VC_2[j]$ 且 $\exists j: VC_1[j] < VC_2[j]$
- $VC_1 = VC_2$ 当且仅当 $\forall j: VC_1[j] = VC_2[j]$
- 否则 **并发**（$VC_1 \| VC_2$）

### 3.3.4 检测并发示例

```
进程 A: [1,0,0]  [2,0,0]  [2,1,0]  [3,1,0]
进程 B: [0,1,0]  [1,1,0]  [2,2,0]  [2,3,0]
进程 C: [0,0,1]  [0,0,2]  [0,0,3]
```

- A 的 $[3,1,0]$ 与 B 的 $[2,3,0]$：A[0]>B[0] 且 A[1]<B[1] → 并发
- A 的 $[2,1,0]$ 与 B 的 $[2,2,0]$：A<B（A 是 B 的因）→ 因果序

### 3.3.5 应用

- **Dynamo**：检测版本冲突，触发应用层冲突解决
- **Riak**：同上
- **Cassandra**：早期用向量时钟，后改用 HAACL（Hash of All Active Changes）
- **协同编辑**：检测并发编辑

### 3.3.6 ⚠️ 向量时钟的问题

1. **存储开销 $O(n)$**：$n$ 个进程需 $n$ 元向量
2. **传播开销**：每次消息携带完整向量
3. **进程动态加入/退出**：需管理进程集合
4. **GC 困难**：旧向量时钟难以回收

**优化**：

- **版本向量**（Version Vector）：仅记录写操作，开销小
- **Dotted Version Vector**：解决副本复制的伪并发问题
- **区间树时钟**（Interval Tree Clock）：动态进程数

## 3.4 混合逻辑时钟（HLC）

📜 [Kulkarni, Demirbas, Madeppa, Bond, Bisht, Kuhfleisch 2014] *Logical Physical Clocks*。

### 3.4.1 动机

- 物理时钟：直观但不可信（漂移、跳变）
- 逻辑时钟：可信但与真实时间无关
- **HLC**：结合两者——保留物理时间近似，用逻辑部分保证因果序

### 3.4.2 HLC 时间戳

HLC 时间戳三元组 $(pt, l, c)$：

- $pt$：物理时间（来自本地时钟）
- $l$：逻辑部分（最大物理时间）
- $c$：计数器（同一 $l$ 内的事件序）

### 3.4.3 算法

```pseudocode
# 初始化
l_i = 0  # 逻辑部分
c_i = 0  # 计数器

# 本地事件
function localEvent():
    pt_now = physicalClock()
    if pt_now > l_i:
        l_i = pt_now
        c_i = 0
    else:
        c_i = c_i + 1
    timestamp = (pt_now, l_i, c_i)

# 发送消息
function sendMessage(m):
    # 同 localEvent 更新
    ...
    send((l_i, c_i), m)

# 接收消息
function receiveMessage(l_m, c_m, m):
    pt_now = physicalClock()
    if pt_now > l_i and pt_now > l_m:
        l_i = pt_now
        c_i = 0
    elif l_i == l_m:
        c_i = max(c_i, c_m) + 1
    elif l_i > l_m:
        c_i = c_i + 1
    else:  # l_m > l_i
        l_i = l_m
        c_i = c_m + 1
```

### 3.4.4 性质

1. **保持因果序**：$e_1 \to e_2 \implies HLC(e_1) < HLC(e_2)$
2. **接近物理时间**：$|l_i - pt| \leq \epsilon$（时钟误差上界）
3. **有界计数器**：在物理时钟稳定时，$c$ 不会无限增长

### 3.4.5 应用

- **CockroachDB**：使用 HLC 实现外部一致性（替代 TrueTime）
- **YugabyteDB**：同上
- **MongoDB sharded cluster**：ClusterTime 类似 HLC

## 3.5 TrueTime 与外部一致性

📜 [Spanner 2012] *Spanner: Google's Globally-Distributed Database*

### 3.5.1 外部一致性 ⭐

> **外部一致性**（External Consistency）：若事务 $T_1$ 在 $T_2$ 开始前完成，则任何事务看到的顺序中 $T_1$ 在 $T_2$ 之前。

外部一致性 = 线性一致性 + 跨事务。

### 3.5.2 TrueTime API

TrueTime 不返回单一时间，而返回**时间区间** $TT(t)$：

```pseudocode
# TrueTime API
function TT.now():
    return [earliest, latest]  # 真实时间在此区间内

# 时间是否已过 t
function TT.after(t):
    return t < TT.now().earliest

# 时间是否还未到 t
function TT.before(t):
    return t > TT.now().latest
```

**关键**：真实时间 $t_{true} \in TT.now()$，误差为 $\epsilon$（典型 7ms）。

### 3.5.3 TrueTime 实现 🔥

Google 数据中心部署：

- **GPS 接收器**：每个数据中心多个
- **原子钟**：作为 GPS 故障的备份
- **时间参考**：每个数据中心多个 time master（GPS + 原子钟混合）
- **机器轮询**：每 30 秒同步多个 master，取最小误差

**误差来源**：

- master 间误差
- 网络延迟
- 本地时钟漂移

**典型 $\epsilon$**：1-7ms（多数时间 < 4ms），最坏 250ms（极端故障）。

### 3.5.4 Commit Wait 机制 ⭐

Spanner 的 2PC 写流程：

```pseudocode
function writeTransaction():
    # 1. 选 coordinator
    # 2. prepare 阶段：每个 Paxos Group 选出 prepare 时间戳
    # 3. coordinator 选 commit 时间戳 s
    s = max(prepare_timestamps) + 1
    # 4. Commit Wait：等待 TT.after(s) 为 true
    while not TT.after(s):
        sleep(epsilon)
    # 5. 应用并返回
```

**为什么需要 Commit Wait**：

- $s$ 是基于本地时钟选的，但本地时钟可能慢于真实时间
- 若不等待，可能后续事务 $T_2$ 用更小时间戳但真实时间更晚，违反外部一致性
- 等待 $\epsilon$ 后，保证 $s < t_{true}$，外部一致性成立

### 3.5.5 Spanner 外部一致性证明直觉

假设 $T_1$ 在 $T_2$ 之前完成：

- $T_1$ commit 时间戳 $s_1$，等待 $TT.after(s_1)$ 后返回
- $T_2$ 开始时间 $t_{start} > s_1 + \epsilon_{commit\_wait}$
- $T_2$ 选 commit 时间戳 $s_2 \geq t_{start} > s_1$
- 故 $s_1 < s_2$，外部一致性成立

### 3.5.6 ⚠️ Commit Wait 的代价

- 写延迟增加 $\epsilon$（典型 7ms）
- 跨地域事务尤其明显
- Spanner 通过 Paxos Group 副本位置优化

### 3.5.7 TrueTime vs HLC

| 维度 | TrueTime | HLC |
|------|---------|-----|
| 依赖 | 专用硬件（GPS/原子钟） | NTP + 逻辑部分 |
| 误差 | $\epsilon$ 已知（典型 7ms） | 与 NTP 同（10-100ms） |
| 外部一致性 | 严格保证 | 近似保证 |
| Commit Wait | 必须 | 不必须 |
| 部署成本 | 高（需硬件） | 低 |
| 典型系统 | Spanner | CockroachDB、YugabyteDB |

## 3.6 全序广播与时间

### 3.6.1 全序广播（Atomic Broadcast）

> **定义**：所有正确节点按相同顺序接收消息。

**与共识等价**：详见 [§5 共识](./05-共识-问题与FLP.md)。

### 3.6.2 全序广播与线性一致性

- 线性一致性可由全序广播实现
- 每个操作作为消息广播，按顺序应用
- 共识算法（Paxos/Raft）本质是全序广播

### 3.6.3 时间戳与全序

- Lamport 时钟提供全序
- 但 Lamport 时钟不保证「实时性」
- TrueTime/HLC 提供「接近实时」的全序

## 3.7 🎓 形式化与因果记忆

### 3.7.1 因果记忆

📜 [Ahamad et al. 1995]：

> **因果记忆**（Causal Memory）：所有读操作遵守因果一致性的共享内存模型。

**性质**：

- 因果记忆 ⊊ 顺序一致内存
- 在异步系统 + 网络可靠下可实现
- 在 CAP 中是 AP 系统的一致性上界

### 3.7.2 区间一致性

📜 [Torres-Rojas, Ahamad 1999]：

> **区间一致性**（Interval Consistency）：用时间区间而非时间点刻画事件顺序。

介于因果一致与线性一致之间。

### 3.7.3 HLC 的形式化性质

**定理**（Kulkarni et al. 2014）：

- HLC 满足：$e_1 \to e_2 \implies HLC(e_1) < HLC(e_2)$
- $|HLC.pt - l| \leq \epsilon$
- $c$ 在网络稳定时有界

### 3.7.4 向量时钟的下界

- $O(n)$ 空间是必要的（Charron-Bost 1991）
- 任何能检测并发的机制至少需 $\Omega(n)$ 位
- 优化方向：减少进程数、GC 旧向量

## 3.8 🏭 工业实战

### 3.8.1 Google TrueTime 实现 🔥

**部署架构**：

```
       ┌──────────────┐
       │ GPS Receiver │ (每数据中心多个)
       └──────┬───────┘
              │
       ┌──────┴───────┐
       │ Atomic Clock │ (备份)
       └──────┬───────┘
              │
       ┌──────┴───────┐
       │ Time Master  │ (mixer)
       └──────┬───────┘
              │ 每 30s 轮询
       ┌──────┴───────┐
       │  Machine A   │
       │  (本地时钟)  │
       └──────────────┘
```

**关键工程细节**：

- 多个 time master 独立运行，避免单点
- 机器同时查询多个 master，取最小误差
- 本地时钟漂移用卡尔曼滤波预测
- $\epsilon$ 在监控系统中实时上报，超过阈值告警

### 3.8.2 CockroachDB HLC 实现

- 不依赖专用硬件
- 节点间通过 HLC 同步
- 误差通过「读时校验」发现：若发现 $HLC.pt$ 落后于实际时间，触发等待
- 写事务：选 HLC 时间戳，等待 max-offset 后提交（类似 Commit Wait）

### 3.8.3 Cassandra 的时间问题

⚠️ **生产事故**：

- 早期 Cassandra 用本地时间戳 LWW
- 节点时钟漂移导致数据「消失」（旧时间戳覆盖新数据）
- 解决：用微秒级时间戳 + 时间偏差监控

### 3.8.4 MongoDB ClusterTime

- 类似 HLC，但仅用于 sharded cluster 内部
- 操作日志（oplog）按 ClusterTime 排序
- 不保证外部一致性，但保证因果一致（causal consistency session）

### 3.8.5 ⚠️ 工业陷阱汇总

- ⚠️ **依赖本地时间戳做 LWW**：节点时钟漂移会导致数据丢失
- ⚠️ **NTP step 模式跳变**：可能导致时间倒退，破坏逻辑
- ⚠️ **闰秒**：触发 bug（2012 年 Reddit 故障）
- ⚠️ **VM 时钟漂移**：虚拟机迁移后时钟可能跳变
- 🔥 **生产建议**：

  - 关键时间戳用 HLC 或服务器端生成
  - 监控节点间时钟偏差（< 100ms）
  - 用 Smear Leap Second
  - 虚拟机用 NTP + kvm-clock

## 3.9 面试要点

### ⭐ Q1：分布式系统为什么没有全局时钟？

**骨架**：

1. 物理时钟有漂移（晶振不精确）
2. NTP 同步有网络延迟误差
3. 闰秒、跳变破坏单调性
4. 没有共享内存无法原子读取多个节点时钟

**关键点**：物理时钟的不可靠性

**加分项**：提到 TrueTime 用 GPS+原子钟+Commit Wait 近似解决

### ⭐ Q2：Lamport 时钟的工作原理？

**骨架**：

1. 每进程维护计数器 $C_i$
2. 本地事件：$C_i$++
3. 发消息：$C_i$++，附带 $C_i$
4. 收消息：$C_i = \max(C_i, C_{msg}) + 1$
5. 性质：$e_1 \to e_2 \implies C(e_1) < C(e_2)$

**关键点**：算法步骤 + happens-before 单向蕴含

**加分项**：指出**反过来不成立**，无法检测并发

### ⭐ Q3：Lamport 时钟能检测并发吗？

**骨架**：

- **不能**
- $C(e_1) < C(e_2)$ 不意味着 $e_1 \to e_2$
- 需要向量时钟才能检测并发

**关键点**：明确「不能」并指出向量时钟

**加分项**：举例说明

### ⭐ Q4：向量时钟怎么检测并发？

**骨架**：

1. 每进程维护 $n$ 元向量 $VC_i$
2. 本地事件：$VC_i[i]$++
3. 收消息：$VC_i[j] = \max(VC_i[j], VC_{msg}[j])$ for all $j$，再 $VC_i[i]$++
4. 比较：
   - $VC_1 < VC_2$ 当且仅当 $\forall j: VC_1[j] \leq VC_2[j]$ 且 $\exists j: VC_1[j] < VC_2[j]$
   - 否则并发

**关键点**：比较规则

**加分项**：提到 Dynamo 用向量时钟检测冲突

### ⭐ Q5：TrueTime 是什么？Spanner 怎么实现外部一致性？

**骨架**：

1. TrueTime 返回时间区间 $TT.now() = [earliest, latest]$
2. 通过 GPS + 原子钟实现，误差 $\epsilon \approx 7ms$
3. Commit Wait：选 commit 时间戳 $s$ 后，等待 $TT.after(s)$
4. 保证 $s < t_{true}$，外部一致性成立

**关键点**：时间区间而非点 + Commit Wait

**加分项**：与 HLC 对比

### ⭐ Q6：向量时钟有什么问题？

**骨架**：

1. 存储开销 $O(n)$
2. 消息开销大
3. 进程动态加入困难
4. GC 困难

**关键点**：$O(n)$ 空间开销

**加分项**：提到优化方案（版本向量、Dotted Version Vector、区间树时钟）

### ⭐ Q7：HLC 是什么？为什么需要它？

**骨架**：

1. HLC = 物理时间 + 逻辑计数器
2. 解决逻辑时钟「无真实时间」+ 物理时钟「不可信」的问题
3. 保留因果序 + 接近物理时间
4. 用于 CockroachDB 等

**关键点**：混合物理 + 逻辑

**加分项**：与 TrueTime 对比

### ⭐ Q8：NTP 为什么不可靠？

**骨架**：

1. 网络延迟导致同步误差
2. 时钟漂移累积
3. step 模式会跳变（时间倒退）
4. 闰秒问题

**关键点**：网络延迟 + 跳变

**加分项**：提到 Smear Leap Second

### ⭐ Q9：闰秒为什么会导致系统故障？

**骨架**：

1. 闰秒导致同一分钟有 61 秒
2. 时间倒退破坏基于时间戳的逻辑
3. 代码假设时间单调递增

**关键点**：时间非单调

**加分项**：提到 2012 年闰秒事故 + Google Smear 方案

### ⭐ Q10：Spanner 的 Commit Wait 为什么必要？

**骨架**：

1. commit 时间戳 $s$ 基于本地时钟
2. 本地时钟可能慢于真实时间
3. 若不等待，后续事务可能选更小 $s$，违反外部一致性
4. 等待 $\epsilon$ 后保证 $s < t_{true}$

**关键点**：本地时钟与真实时间的偏差
