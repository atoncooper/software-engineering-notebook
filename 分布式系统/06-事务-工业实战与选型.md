## 6.1 Seata 四模式对比 🔥

### 6.1.1 Seata 简介

> **Seata**（Simple Extensible Autonomous Transaction Architecture）：阿里开源的分布式事务框架，提供四种模式适配不同场景。

### 6.1.2 四模式对比

| 维度 | XA | AT | TCC | Saga |
|------|----|----|-----|------|
| **隔离性** | 强（DB 锁） | 中（全局锁） | 业务层（预留） | 弱（无） |
| **一致性** | 强 | 强（最终） | 最终 | 最终 |
| **性能** | 差 | 中 | 好 | 好 |
| **业务侵入** | 无 | 无（自动生成 SQL） | 大（三接口） | 中（执行+补偿） |
| **数据源** | XA 兼容 | 关系型 DB | 任意 | 任意 |
| **适合场景** | 强一致 + 同质 DB | 中小规模业务 | 高并发互联网 | 长事务 + 跨服务 |
| **复杂度** | 低 | 低 | 高 | 中 |

### 6.1.3 AT 模式详解 ⭐

> **AT（Automatic Transaction）**：Seata 自研模式，**自动生成反向 SQL 实现补偿**，业务无侵入。

#### 流程

```
1. 一阶段：业务 SQL 执行 + 记录 undo log + 注册分支事务
2. 二阶段：
   - 全局提交：异步删除 undo log
   - 全局回滚：根据 undo log 反向恢复
```

#### 关键：全局锁

> AT 模式通过「全局锁」保证写隔离：事务 A 修改行 R 前，需先获取 R 的全局锁。

```java
// AT 模式示例（业务无感知）
@GlobalTransactional
public void transfer(Long from, Long to, BigDecimal amount) {
    accountMapper.deduct(from, amount);   // 自动记录 undo log
    accountMapper.credit(to, amount);     // 自动记录 undo log
}
// Seata 自动：
# 1. 解析 SQL，记录执行前镜像（before image）
# 2. 执行 SQL
# 3. 记录执行后镜像（after image）
# 4. 生成 undo log
# 5. 注册分支事务到 TC
# 全局回滚时，根据 undo log 生成反向 SQL 恢复
```

#### AT 模式的优势

- 业务无侵入（注解驱动）
- 自动补偿
- 性能优于 XA

#### AT 模式的劣势

- 仅支持关系型 DB
- 全局锁可能成为瓶颈
- SQL 解析有限制（不支持复杂 JOIN）

### 6.1.4 四模式选型

| 场景 | 推荐 |
|------|------|
| 跨同质 DB、强一致、短事务 | XA |
| 单一关系型 DB、中小规模、业务无侵入 | AT |
| 高并发互联网、跨服务、强隔离 | TCC |
| 长事务、跨多服务、可容忍弱隔离 | Saga |

## 6.2 选型决策树 ⭐

### 6.2.1 决策流程

```
                  分布式事务选型
                       │
                       ▼
              是否跨服务/资源？
                       │
              ┌────────┴────────┐
              否                 是
              │                  │
              ▼                  ▼
        本地事务 + 一致性       跨资源类型？
        保证（如唯一索引）         │
                                ├──────────────┐
                                │              │
                            同质 DB         异构资源
                                │              │
                                ▼              ▼
                          事务长度？      是否需要强一致？
                                │              │
                       ┌────────┴────┐    ┌────┴────┐
                       短            长    是        否
                       │             │    │         │
                       ▼             ▼    ▼         ▼
                     XA / AT      Saga   TCC     消息事务
                                       (业务侵入)  (最终一致)
```

### 6.2.2 详细决策表

| 业务场景 | 跨资源 | 事务长度 | 一致性 | 隔离性 | 推荐方案 |
|---------|-------|---------|-------|-------|---------|
| 转账（同银行） | 否 | 短 | 强 | 强 | 本地事务 |
| 跨行转账 | 是 | 短 | 强 | 强 | XA / TCC |
| 电商下单 | 是 | 短 | 最终 | 中 | TCC / 消息事务 |
| 订单全流程（创建→支付→发货→收货） | 是 | 长 | 最终 | 弱 | Saga |
| 写 DB + 发 MQ | 是 | 短 | 最终 | 弱 | 消息事务 |
| 跨地域全球数据库 | 是 | 短 | 强 | 强 | Spanner/CockroachDB |
| 缓存与 DB 一致 | 是 | 短 | 最终 | 弱 | 消息事务 / Canal |
| 微服务跨服务调用 | 是 | 短 | 最终 | 中 | TCC / 消息事务 |

### 6.2.3 选型原则

1. **能不用分布式事务就不用**——本地事务 + 一致性保证优先
2. **强一致需求**：XA / TCC / Spanner
3. **高并发需求**：TCC / 消息事务
4. **长事务**：Saga
5. **跨地域**：Spanner / CockroachDB
6. **业务无侵入**：AT / 消息事务
7. **业务可侵入**：TCC / Saga

## 6.3 行业案例

### 6.3.1 金融行业（银行核心系统）🔥

**场景**：跨行转账、清算结算

**特点**：

- 强一致（不能丢钱、不能多钱）
- 强隔离（避免超扣）
- 监管要求高

**方案**：

- **核心账务**：XA（同质 Oracle/DB2）+ TCC（跨服务）
- **清算结算**：Saga（长流程）+ 人工兜底
- **对账系统**：本地消息表 + 定时对账

**陷阱**：

- ⚠️ 长事务持锁影响吞吐
- ⚠️ 跨行清算可能数小时，不能 XA
- ⚠️ 监管要求「可追溯」，所有事务需记录审计日志

### 6.3.2 电商行业（淘宝/天猫）🔥

**场景**：下单、支付、库存、优惠

**特点**：

- 高并发（双 11 单秒数十万 TPS）
- 最终一致可接受
- 业务流程长

**方案**：

- **下单核心链路**：TCC（订单 + 库存 + 优惠）
- **支付链路**：TCC（账户 + 交易记录）
- **物流链路**：Saga（创建→揽收→运输→签收）
- **DB + MQ**：RocketMQ 事务消息
- **缓存与 DB**：Canal（binlog → 缓存失效）

**陷阱**：

- ⚠️ 双 11 流量洪峰，TCC 三阶段可能成为瓶颈
- ⚠️ 库存超卖：需 Redis 预扣 + DB 兜底
- ⚠️ 补偿失败需快速告警

### 6.3.3 物流行业

**场景**：订单全生命周期

**特点**：

- 事务超长（数小时到数天）
- 跨多个外部系统（仓储、运输、配送）
- 不可补偿操作多（已发车、已签收）

**方案**：

- **Saga 编排式**：状态机驱动
- **不可补偿操作**：人工介入 + 标记异常
- **跨系统**：消息事务 + 异步通知

### 6.3.4 游戏行业

**场景**：充值、道具交易、玩家数据

**特点**：

- 高并发（开服瞬间）
- 强一致（不能丢道具）
- 短事务为主

**方案**：

- **充值**：TCC（账户 + 道具）
- **交易**：TCC（买卖双方 + 中介）
- **跨服数据**：Spanner/CockroachDB

### 6.3.5 SaaS / 多租户

**场景**：跨租户数据隔离

**特点**：

- 数据量大
- 多租户隔离
- 中等并发

**方案**：

- **租户内**：本地事务
- **跨租户**：通常不需要（业务隔离）
- **配置变更**：消息事务

## 6.4 跨地域事务选型

### 6.4.1 部署模式对比

| 模式 | 一致性 | 延迟 | 适用 |
|------|-------|------|------|
| **单写多读** | 强（写单点） | 低（本地读） | 读多写少 |
| **多写异步复制** | 弱 | 低 | 容忍数据丢失 |
| **多写强一致（Spanner）** | 强 | 中高 | 全球强一致 |
| **单元化** | 强（单元内） | 低 | 大规模互联网 |

### 6.4.2 单元化（LDC）🔥

> **逻辑数据中心（Logical Data Center）**：蚂蚁金服提出的方案，按用户 ID 路由到固定单元，单元内强一致，跨单元弱一致。

**架构**：

```
       用户请求
           │
           ▼
       路由层（按 UID）
           │
   ┌───────┼───────┐
   ▼       ▼       ▼
 单元A    单元B    单元C
 （UID 1）（UID 2）（UID 3）
   │       │       │
   └───────┼───────┘
           │
       跨单元（消息事务）
```

**优势**：

- 单元内强一致（本地事务）
- 跨单元最终一致（消息事务）
- 水平扩展（增加单元）
- 容灾（单单元故障不影响其他）

**劣势**：

- 路由复杂
- 跨单元操作需特殊处理
- 单元扩容需重新分片

### 6.4.3 跨地域方案对比

| 方案 | 一致性 | 延迟 | 复杂度 | 典型 |
|------|-------|------|-------|------|
| Spanner | 外部一致 | 中高 | 高 | Google |
| CockroachDB | 外部一致（近似） | 中 | 高 | 开源 |
| 单元化（LDC） | 单元强 | 低 | 高 | 蚂蚁 |
| Cassandra | 最终一致 | 低 | 中 | Netflix |
| MySQL 异步复制 | 弱 | 低 | 低 | 传统 |

## 6.5 高并发事务优化

### 6.5.1 双 11 级别优化 🔥

#### 1. 异步化

```java
// 同步：扣库存 + 扣余额 + 创建订单（串行）
@Transactional
public Order createOrder(...) {
    stockService.deduct(...);   // 同步
    accountService.deduct(...); // 同步
    return orderRepo.insert(...);
}

// 异步：扣库存 + 发 MQ（异步扣余额 + 创建订单）
@Transactional
public Order createOrder(...) {
    stockService.deduct(...);   // 同步（核心）
    mqProducer.send(...);       // 异步通知其他服务
    return orderRepo.insert(...);
}
```

#### 2. 分库分表

```java
// 按 user_id 分库分表
@ShardingKey("user_id")
public class Order {...}

// 路由：user_id % 16 → 库；user_id / 16 % 16 → 表
```

#### 3. 缓存预扣

```java
// 库存预扣（Redis）+ 异步落库
public boolean deductStock(String sku, int count) {
    // Redis 原子扣减
    Long remaining = redis.decrBy("stock:" + sku, count);
    if (remaining < 0) {
        redis.incrBy("stock:" + sku, count);  // 回滚
        return false;
    }
    // 异步落库
    mqProducer.send("stock_deduct", new DeductMsg(sku, count));
    return true;
}
```

#### 4. 限流降级

```java
@SentinelResource(value = "createOrder", blockHandler = "onBlock")
public Order createOrder(...) {...}

public Order onBlock(...) {
    // 限流降级：返回友好提示
    throw new BizException("系统繁忙，请稍后重试");
}
```

### 6.5.2 性能对比

| 方案 | TPS | 延迟 | 一致性 |
|------|-----|------|-------|
| 同步 2PC | 1k | 100ms | 强 |
| 同步 TCC | 5k | 50ms | 最终 |
| 异步消息事务 | 50k | 10ms | 最终 |
| 缓存预扣 + 异步 | 100k+ | 5ms | 最终 |

## 6.6 长事务处理

### 6.6.1 长事务的挑战

- 持锁时间长，影响并发
- 故障恢复慢
- 性能瓶颈

### 6.6.2 拆分策略

#### 1. 业务拆分

```java
// 错误：一个长事务包含多个步骤
@Transactional
public void longProcess() {
    step1();  // 1s
    step2();  // 5s
    step3();  // 10s
    step4();  // 1s
}

// 正确：拆成多个短事务 + Saga 协调
public void longProcess() {
    saga.step("step1", () -> step1(), () -> compensate1())
        .step("step2", () -> step2(), () -> compensate2())
        .step("step3", () -> step3(), () -> compensate3())
        .step("step4", () -> step4(), () -> compensate4())
        .execute();
}
```

#### 2. 异步化

```java
// 长流程异步化
public void startProcess() {
    // 立即返回，异步处理
    mqProducer.send("long_process_start", request);
}

@MQConsumer("long_process_start")
public void onMessage(Request req) {
    // 异步执行长流程
    saga.execute(req);
}
```

#### 3. 状态机

```java
// 用状态机管理长流程
public enum OrderState {
    CREATED, PAID, SHIPPED, DELIVERED, COMPLETED, CANCELLED
}

public void process(Order order) {
    while (order.state != COMPLETED && order.state != CANCELLED) {
        switch (order.state) {
            case CREATED: pay(order); break;
            case PAID: ship(order); break;
            case SHIPPED: deliver(order); break;
            case DELIVERED: complete(order); break;
        }
    }
}
```

## 6.7 🏭 生产陷阱与建议

### 6.7.1 ⚠️ 陷阱汇总

- ⚠️ **过度使用分布式事务**：能用本地事务就不用分布式
- ⚠️ **XA 性能瓶颈**：高并发场景慎用
- ⚠️ **TCC 业务侵入大**：每个接口三方法，开发成本高
- ⚠️ **Saga 隔离性弱**：中间状态可见，业务需容忍
- ⚠️ **补偿失败**：需重试 + 告警 + 人工介入
- ⚠️ **不可补偿操作**：发邮件、外部 API 需特殊处理
- ⚠️ **消息重复**：所有 MQ 方案都可能重复，消费者必须幂等
- ⚠️ **TSO 单点**：Percolator/TiDB 的 TSO 需 HA
- ⚠️ **跨地域延迟**：Spanner Commit Wait 增加延迟
- ⚠️ **监控缺失**：事务失败需告警，补偿需监控

### 6.7.2 🔥 生产建议

#### 1. 优先级

```
本地事务 > 消息事务 > TCC > Saga > XA > 跨地域强一致
```

#### 2. 监控

- 事务成功率
- 事务平均/P99 延迟
- 补偿触发率
- 补偿成功率
- 重试次数

#### 3. 兜底

- **对账系统**：定时对账，发现不一致自动修复
- **人工介入**：补偿失败的告警与人工处理
- **降级**：故障时降级到最终一致

#### 4. 测试

- **混沌工程**：注入故障验证事务正确性
- **压测**：双 11 级别压测验证容量
- **回滚演练**：定期演练回滚流程

### 6.7.3 工程化清单

- [ ] 选型文档：明确每个场景的事务方案
- [ ] 监控告警：事务成功率、延迟、补偿率

- [ ] 幂等保证：所有消费者幂等

## 6.8 面试要点

### ⭐ Q1：Seata 四种模式的区别？

**骨架**：

1. **XA**：基于 DB XA 协议，强一致，性能差
2. **AT**：自动生成 undo log，业务无侵入，关系型 DB
3. **TCC**：业务三接口，高并发，业务侵入大
4. **Saga**：长事务，补偿事务，隔离性弱

**关键点**：四模式 + 适用场景

**加分项**：提到 AT 自动生成反向 SQL

### ⭐ Q2：AT 模式怎么实现？

**骨架**：

1. 一阶段：执行 SQL + 记录 before/after image + 生成 undo log
2. 二阶段提交：异步删除 undo log
3. 二阶段回滚：根据 undo log 反向恢复
4. 全局锁保证写隔离

**关键点**：undo log + 全局锁

**加分项**：提到 before/after image

### ⭐ Q3：电商下单用什么事务方案？

**骨架**：

1. 核心链路（订单 + 库存 + 优惠）：TCC
2. 支付：TCC
3. 物流：Saga
4. DB + MQ：消息事务
5. 缓存与 DB：Canal binlog

**关键点**：分场景选不同方案

**加分项**：提到双 11 异步化与缓存预扣

### ⭐ Q4：金融行业事务方案？

**骨架**：

1. 核心账务：XA（同质 DB）+ TCC（跨服务）
2. 清算结算：Saga + 人工兜底
3. 对账：本地消息表 + 定时对账
4. 强一致 + 强隔离 + 可追溯

**关键点**：强一致 + 强隔离

**加分项**：提到监管要求

### ⭐ Q5：跨地域事务怎么选？

**骨架**：

1. 全球强一致：Spanner / CockroachDB
2. 大规模互联网：单元化（LDC）
3. 容忍弱一致：Cassandra
4. 传统：MySQL 异步复制

**关键点**：一致性 vs 延迟权衡

**加分项**：提到单元化原理

### ⭐ Q6：双 11 高并发事务怎么落地？

**骨架**：

1. 异步化：同步 TCC → 异步消息事务
2. 分库分表：按 user_id 分片
3. 缓存预扣：Redis 原子扣减 + 异步落库
4. 限流降级：Sentinel
5. 监控告警：事务成功率、延迟

**关键点**：异步化 + 分片 + 缓存

**加分项**：提到性能数据（50k → 100k+ TPS）

### ⭐ Q7：长事务怎么处理？

**骨架**：

1. 拆分：用 Saga 拆成多个短事务
2. 异步化：MQ 异步执行
3. 状态机：管理长流程状态
4. 不可补偿操作：人工介入

**关键点**：拆分 + 异步 + 状态机

**加分项**：举例订单全流程

### ⭐ Q8：分布式事务选型原则？

**骨架**：

1. 能不用就不用——本地事务优先
2. 强一致：XA / TCC / Spanner
3. 高并发：TCC / 消息事务
4. 长事务：Saga
5. 跨地域：Spanner / LDC
6. 业务无侵入：AT / 消息事务

**关键点**：本地事务优先 + 按需求选

**加分项**：提到「过度使用分布式事务」是反模式

### ⭐ Q9：TCC 业务侵入大，有替代方案吗？

**骨架**：

1. AT 模式（业务无侵入，仅关系型 DB）
2. 消息事务（业务侵入小，最终一致）
3. Spanner/CockroachDB（数据库原生事务）

**关键点**：AT 是折衷

**加分项**：提到 AT 的限制（仅关系型 DB）

### ⭐ Q10：如何保证分布式事务的最终一致性？

**骨架**：

1. 重试机制：失败自动重试
2. 对账系统：定时对账，发现不一致自动修复
3. 人工兜底：重试失败的告警与人工处理
4. 监控：事务成功率、补偿率

**关键点**：重试 + 对账 + 兜底

**加分项**：提到混沌工程验证
