## 5.1 算法对比表

### 5.1.1 完整对比

| 维度 | Paxos | Multi-Paxos | Raft | ZAB | PBFT | HotStuff |
|------|-------|-------------|------|-----|------|---------|
| **故障模型** | Crash | Crash | Crash | Crash | Byzantine | Byzantine |
| **容错下界** | $f < n/2$ | $f < n/2$ | $f < n/2$ | $f < n/2$ | $f < n/3$ | $f < n/3$ |
| **典型 $n$** | $2f+1$ | $2f+1$ | 3 / 5 / 7 | 3 / 5 / 7 | $3f+1$ | $3f+1$ |
| **Leader** | 无（可选） | 有 | 有 | 有 | 有 | 有（轮换） |
| **阶段数** | 2 | 1（steady） | 1（steady） | 3 | 3 | 4 |
| **消息复杂度** | $O(n)$ | $O(n)$ | $O(n)$ | $O(n)$ | $O(n^2)$ | $O(n)$ |
| **编号** | proposal ID | proposal ID | (term, index) | zxid | (view, seq) | (view, seq) |
| **设计目标** | 通用 | 性能 | 易理解 | 高吞吐 | 实用 BFT | 线性 BFT |
| **典型工业** | Chubby | Spanner | etcd, TiKV | ZooKeeper | Fabric | Diem |

### 5.1.2 选型决策

| 场景 | 推荐 | 原因 |
|------|------|------|
| 协调服务（小规模） | Raft（etcd） | 易实现 + 生态成熟 |
| 大规模分布式存储 | Multi-Raft | 分片隔离 + 高吞吐 |
| 数据库复制 | Raft / Multi-Paxos | 性能 + 一致性 |
| 联盟链 | PBFT / HotStuff | 拜占庭容错 + 高吞吐 |
| 公链 | PoW / PoS | 大规模拜占庭 + 节点不可控 |
| 跨组织元数据 | Paxos / Raft | 简单 + 强一致 |

### 5.1.3 本质相似

- 所有共识算法都基于 **Quorum + 全序日志**
- 都通过 **多数 Quorum** 保证 Safety
- 都依赖 **部分同步假设** 绕过 FLP
- 差异主要在「表达方式」与「工程优化」

## 5.2 工业实现

### 5.2.1 etcd-raft 🔥

**架构**：

- Go 实现
- 5 节点典型部署
- WAL（Write-Ahead Log）持久化
- MVCC + Watch

**关键工程细节**：

#### WAL 持久化

```pseudocode
function append_log(entry):
    # 1. 序列化
    data = serialize(entry)
    # 2. 写 WAL（必须 fsync）
    wal.append(data)
    wal.fsync()  # 关键！否则故障丢日志
    # 3. 写内存
    memtable.append(entry)
```

⚠️ **关键**：fsync 是 Safety 关键，未 fsync 的日志故障后丢失。

#### ReadIndex（线性一致读）⭐

普通 Raft 读：走 Raft 协议（性能差）。etcd 优化：

```pseudocode
function linearizable_read(key):
    # 1. Leader 记录当前 commitIndex
    read_index = commitIndex
    
    # 2. 发心跳确认自己仍是 Leader
    send_heartbeat()
    wait_until(majority_acked)
    
    # 3. 等待 state machine apply 到 read_index
    wait_until(lastApplied >= read_index)
    
    # 4. 读
    return state_machine.get(key)
```

#### Lease Read（更优化的线性一致读）⭐

```pseudocode
function lease_read(key):
    # Leader 有 Lease（由心跳维持），保证无其他 Leader
    # 直接读 commitIndex
    if lease_valid():
        wait_until(lastApplied >= commitIndex)
        return state_machine.get(key)
    else:
        # 回退到 ReadIndex
        return linearizable_read(key)
```

⚠️ **Lease Read 风险**：时钟漂移可能导致 Lease 误判有效 → 读到旧值。需配合 monotonic clock + 保守 Lease 时长。

#### PreVote（避免抖动）⭐

问题：网络分区节点回归时，可能以更高 Term 触发选举，导致不必要的 Leader 切换。

解决：

```pseudocode
function before_election():
    # PreVote：先询问「我会当选吗」
    send(PreVote, my_term)
    if majority_yes:
        # 进入正式选举
        start_real_election()
    # 否则保持 Follower
```

#### CheckQuorum

Leader 主动检查是否能联系 majority，否则主动下台。避免「孤立 Leader」继续接受写。

### 5.2.2 TiKV Multi-Raft 🔥

**架构**：

```
TiKV 集群
├── Node 1
│   ├── Region 1 (Leader)
│   ├── Region 2 (Follower)
│   └── Region 3 (Follower)
├── Node 2
│   ├── Region 1 (Follower)
│   ├── Region 2 (Leader)
│   └── Region 3 (Follower)
└── Node 3
    ├── Region 1 (Follower)
    ├── Region 2 (Follower)
    └── Region 3 (Leader)
```

**关键设计**：

- 数据按 Range 分片为 Region（默认 96MB）
- 每个 Region 独立 Raft Group
- PD（Placement Driver）调度 Region
- 跨 Region 事务用 2PC

**优势**：

- 分片隔离：单 Region 故障不影响其他
- 并行复制：多 Region 并发
- 弹性扩缩容：Region 迁移

**挑战**：

- 心跳开销：大量 Region 心跳
- PD 单点：需 PD 自身高可用（etcd）
- 跨 Region 事务复杂

→ 详见 [§8 存储-Spanner与NewSQL](./08-存储-Spanner与NewSQL.md)。

### 5.2.3 Chubby 的 Paxos 工程化 📜

📜 [Burrows 2006] *The Chubby lock service for loosely-coupled distributed systems*
📜 [Chandra et al. 2007] *Paxos Made Live*

**关键工程经验**：

#### Master Lease

- Master 通过 Quorum 获 Lease（12s）
- Lease 期间无其他 Master
- 客户端只访问当前 Master

#### 日志与快照

- 持久化日志（fsync）
- 周期性快照截断日志
- 快照原子写（先写新快照，再删旧日志）

#### 客户端 Caching

- 客户端缓存 ZNode 数据
- Master 通知缓存失效（通过 KeepAlive 中的 event）

#### 故障切换

- Master 故障 → 客户端 KeepAlive 超时
- 新 Master 选出 → 客户端重连
- 故障期间写不可用（典型 5-15s）

#### ⚠️ Chubby 工程教训

- 磁盘 fsync 性能关键（影响吞吐）
- 客户端 Session 管理复杂
- 「Paxos 理论 → 工程实现」gap 巨大

### 5.2.4 Spanner Paxos Group 📜

📜 [Spanner 2012]

**架构**：

- 每个 Tablet 一个 Paxos Group
- 5 副本跨 DC
- Paxos 复制 + TrueTime 跨 Group 事务

**跨 Paxos Group 事务**：

1. 选 Coordinator Group
2. 各 Group Paxos prepare（写锁）
3. Coordinator 选 commit timestamp（TrueTime）
4. Commit Wait
5. 各 Group Paxos commit

→ 详见 [§8 存储-Spanner](./08-存储-Spanner与NewSQL.md) 与 [§3 时间与时钟](./03-时间与时钟.md)。

### 5.2.5 ZooKeeper ZAB 实现

- zxid 全局单调
- Ephemeral 节点 + Watcher

## 5.3 工程难点

### 5.3.1 持久化 ⚠️

> **关键**：所有 Safety 都依赖日志持久化。未 fsync 的日志故障后丢失，违反 Safety。

```pseudocode
# 正确
function append_log(entry):
    wal.append(entry)
    wal.fsync()  # 必须
    memtable.append(entry)

# 错误（危险）
function append_log_unsafe(entry):
    memtable.append(entry)  # 仅内存
    wal.append(entry)  # 未 fsync，故障后丢失
```

**性能 vs 安全权衡**：

- 每次 fsync：高安全，低性能
- 批量 fsync：中安全，中性能
- 组提交（Group Commit）：合并多个 fsync

🔥 **生产建议**：

- 关键路径强制 fsync
- SSD + 单独 WAL 设备
- 监控 fsync 延迟

### 5.3.2 读一致性 ⚠️

Raft/ZAB 默认读可能不一致（Follower 本地读）：

| 方式 | 一致性 | 性能 |
|------|-------|------|
| 走 Raft 协议 | 线性一致 | 差 |
| ReadIndex | 线性一致 | 中 |
| Lease Read | 线性一致 | 好 |
| Follower 本地读 | 顺序一致 | 最好 |

🔥 **生产建议**：

- 强一致需求：ReadIndex / Lease Read
- 性能优先：Follower 本地读 + 客户端容错

### 5.3.3 跨地域共识 ⚠️

跨 DC 共识延迟高（10-100ms RTT）：

- 写延迟 = Quorum DC 中最慢 RTT
- Leader 选举超时需调大
- 故障切换期间不可用

**优化**：

- **Multi-Raft**：Region 级共识，Leader 就近
- **Spanner 模式**：Paxos Group 内跨 DC，Group 内就近 Leader
- **PACELC**：跨 DC 强一致 → 高延迟

🔥 **生产建议**：

- 跨地域用 Multi-Raft + 就近读
- 强一致写跨地域，本地读最终一致
- 评估 P99 延迟是否可接受

### 5.3.4 性能优化

#### 批处理（Batching）

- 多条日志合并为一个 AppendEntries
- 减少 RPC 次数

#### 流水线（Pipelining）

- Leader 不等 ACK 就发下一条
- 提升吞吐

#### 并行复制（Parallel Replication）

- 多个日志位置并行复制
- 但需保证顺序应用

#### 异步快照

- 快照不阻塞写
- 用 Copy-On-Write

### 5.3.5 ⚠️ 常见陷阱

- ⚠️ **未 fsync**：Safety 违反
- ⚠️ **Election timeout 过小**：网络抖动触发频繁选举
- ⚠️ **Snapshot 阻塞**：需异步
- ⚠️ **成员变更并发**：脑裂
- ⚠️ **跨地域 election timeout**：需基于 P99 RTT
- ⚠️ **Follower 本地读**：读到旧值
- ⚠️ **客户端重试导致重复**：需客户端 ID + 序号去重

## 5.4 🏭 跨地域共识

### 5.4.1 部署模式

| 模式 | 描述 | 延迟 | 一致性 |
|------|------|------|-------|
| **单 DC** | 共识在单 DC | 低 | 强 |
| **跨 DC Quorum** | 副本跨 DC，Quorum 跨 DC | 高 | 强 |
| **Multi-Raft** | 数据分片，Leader 就近 | 中 | 强 |
| **本地读 + 异步复制** | 本地读，异步跨 DC | 低 | 弱 |

### 5.4.2 Spanner 模式 🔥

- 每 Paxos Group 跨 3-5 DC
- Leader 优选「就近 DC」
- 跨 Group 事务用 2PC + TrueTime
- Commit Wait 保证外部一致性
- 详见 [§8 存储-Spanner](./08-存储-Spanner与NewSQL.md)

### 5.4.3 CockroachDB 模式

- Multi-Raft，每个 Range 跨 DC
- HLC 替代 TrueTime
- 类似 Spanner 但无专用硬件

### 5.4.4 Cassandra 模式

- 无主，本地 DC 优先写
- 跨 DC 异步复制
- 最终一致

### 5.4.5 跨地域共识对比

| 系统 | 模式 | 一致性 | 延迟 |
|------|------|-------|------|
| Spanner | 跨 DC Quorum + TrueTime | 外部一致 | 中 |
| CockroachDB | Multi-Raft + HLC | 外部一致（近似） | 中 |
| Cassandra | 本地 DC + 异步 | 最终一致 | 低 |
| MySQL 跨 DC | 半同步 | 强 | 中高 |

## 5.5 面试要点

### ⭐ Q1：Paxos / Raft / ZAB 的区别？

**骨架**：

| 维度 | Paxos | Raft | ZAB |
|------|-------|------|-----|
| 设计目标 | 通用 | 易理解 | 高吞吐 |
| 编号 | proposal ID | (term, index) | zxid |
| 阶段 | 2 | 2 | 3 |
| 选举 | 不指定 | random timeout | 同步询问 |
| 典型 | Chubby | etcd | ZooKeeper |

**关键点**：本质相似，差异在表达

**加分项**：提到都是 Crash 模型 + $f < n/2$

### ⭐ Q2：Raft 和 PBFT 的区别？

**骨架**：

1. 故障模型：Crash vs Byzantine
2. 容错下界：$f < n/2$ vs $f < n/3$
3. 消息复杂度：$O(n)$ vs $O(n^2)$
4. 签名：不需要 vs 需要
5. 应用：数据库 vs 区块链

**关键点**：故障模型是根本差异

**加分项**：提到 HotStuff 优化到 $O(n)$

### ⭐ Q3：etcd 的线性一致读怎么实现？

**骨架**：

1. **ReadIndex**：读前 Leader 发心跳确认仍是 Leader，读 commitIndex
2. **Lease Read**：Leader 在 Lease 内直接读，无需 ReadIndex
3. 都保证线性一致

**关键点**：ReadIndex / Lease Read

**加分项**：提到 Lease Read 的时钟风险

### ⭐ Q4：TiKV 的 Multi-Raft 是什么？

**骨架**：

1. 数据按 Range 分片为 Region
2. 每个 Region 独立 Raft Group
3. PD 调度 Region
4. 跨 Region 事务用 2PC

**关键点**：分片隔离 + PD 调度

**加分项**：提到优势（并行复制、弹性扩容）

### ⭐ Q5：共识算法为什么必须 fsync？

**骨架**：

1. Safety 依赖日志持久化
2. 未 fsync 的日志故障后丢失
3. 节点重启后状态不一致 → Safety 违反
4. 必须在响应客户端前 fsync

**关键点**：Safety 关键

**加分项**：提到批量 fsync / 组提交优化

### ⭐ Q6：跨地域共识有什么挑战？

**骨架**：

1. 跨 DC RTT 高（10-100ms）
2. 写延迟 = Quorum 最慢 RTT
3. Election timeout 需调大
4. 故障切换期间不可用

**关键点**：高延迟

**加分项**：提到 Multi-Raft / Spanner 模式优化

### ⭐ Q7：Chubby 的 Paxos 工程化有哪些经验？

**骨架**：

1. Master Lease 保证 Master 唯一
2. 持久化日志 + 快照
3. 客户端 Caching + 通知失效
4. 故障切换 5-15s

**关键点**：Master Lease + 客户端 Cache

**加分项**：提到 Paxos Made Live 的工程教训

### ⭐ Q8：Raft 选举抖动怎么解决？

**骨架**：

1. 调大 election timeout
2. 用 PreVote 避免不必要选举
3. CheckQuorum 主动检查 Leader 联系性
4. 监控选举频率

**关键点**：PreVote + CheckQuorum

**加分项**：提到 etcd 的实现

### ⭐ Q9：共识算法的客户端如何实现 Exactly-Once？

**骨架**：

1. 客户端 ID + 序号
2. 服务端去重
3. 故障重试时用相同 ID + 序号

**关键点**：ID + 序号去重

**加分项**：提到 Chubby 的客户端缓存

### ⭐ Q10：共识算法的快照机制？

**骨架**：

1. 周期性快照状态机
2. 截断已快照的日志
3. 新节点用 InstallSnapshot 同步
4. 异步快照避免阻塞写

**关键点**：快照 + 日志截断

**加分项**：提到快照原子性（先写新再删旧）
