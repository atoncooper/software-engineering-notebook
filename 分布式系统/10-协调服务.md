## 0. 什么是协调服务

分布式系统中,有一类"轻数据、重元信息"的需求:

- **配置中心**:全局配置下发(开关、阈值、连接串)
- **命名服务**:服务实例注册与发现
- **Leader 选举**:选出主节点,故障时切换
- **分布式锁**:跨进程互斥
- **元数据存储**:Region 路由表、分片归属
- **集群成员管理**:谁在线、谁下线

如果业务系统自己用 Paxos/Raft 实现一遍,工程成本巨大。**协调服务 (Coordination Service)** 把这些共性能力抽取出来,提供线性一致(或接近)的小数据存储 + 通知机制,作为分布式系统的"骨架"。

```
应用层 (业务)
   ↓ 依赖
协调服务 (ZK / etcd / Consul / Nacos)   ← 本章
   ↓ 内部
共识层 (ZAB / Raft / Paxos / Distro)   ← §5
   ↓ 底层
存储 (B-tree / LSM / 内存树)
```

> 🎓 **学术视角**:协调服务 = 强一致小存储 + Watch 通知 + 临时节点语义。本质上是一个"分布式协调原语"的集合,核心抽象是 **层级命名空间 + 顺序临时节点**。

## 1. 定义与动机

### 1.1 设计哲学

> "与其在每个应用里实现 Paxos,不如提供一组简单的协调原语,让应用用这些原语构建更复杂的协议。" —— ZooKeeper 原始论文 (Hunt 2010)

#### 1.1.1 ZooKeeper 论文的核心论断

1. **协调 ≠ 一致性**:协调服务不需要提供完整的事务、SQL,只需要几个简单的"文件系统式"操作。
2. **Wait-Free**:客户端不需要阻塞等待其他客户端,通过 watch 异步感知变化。
3. **Linearizable Writes, FIFO Reads**:写线性一致;读默认是 client FIFO(读到客户端已经看到的最新值),可强制 leader read 保证线性一致。

### 1.2 协调服务的核心抽象

| 抽象 | 含义 | 典型用法 |
|------|------|---------|
| **层级命名空间** | 类似文件系统的树形 znode | 配置树、服务树 |
| **持久节点** | 创建后除非主动删除否则永久存在 | 配置项、路由表 |
| **临时节点** | 客户端 session 断开自动删除 | 服务注册、Leader 占位 |
| **顺序节点** | 节点名后自动追加单调递增序号 | 队列、分布式锁公平排队 |
| **Watch 通知** | 节点变化时异步通知客户端 | 配置变更、Leader 切换 |
| **CAS (compare-and-set)** | 带版本号的原子更新 | 互斥、配置更新 |

### 1.3 一致性权衡

| 服务 | 写一致性 | 读一致性 | 备注 |
|------|---------|---------|------|
| ZooKeeper | Linearizable | Sequential(默认) / Linearizable(sync) | ZAB 共识 |
| etcd | Linearizable | Linearizable(默认) / Serializable(可选) | Raft |
| Consul | Linearizable | Linearizable / Stale(默认读任意 follower) | Raft |
| Nacos | AP 或 CP(切换) | AP 默认最终一致 / CP Raft | Distro + Raft 双模 |

## 2. 原理与算法

### 2.1 ZooKeeper:ZAB + 树形 ZNode

#### 2.1.1 数据模型

- 类 Unix 文件路径:`/app1/config/timeout`,每个路径段称为一个 **znode**。
- znode 类型:
  - `PERSISTENT`:持久(默认)
  - `EPHEMERAL`:临时,session 断开自动删
  - `PERSISTENT_SEQUENTIAL`:持久 + 顺序后缀
  - `EPHEMERAL_SEQUENTIAL`:临时 + 顺序后缀
  - `CONTAINER`:容器节点(子节点都被删时自身可被删,用于 Leader/锁)
  - `TTL`:持久 + TTL 过期

- 每个 znode 携带 **stat** 结构:`czxid / mzxid / pzxid / version / cversion / ephemeralOwner / dataLength`。

#### 2.1.2 ZAB 协议回顾 (详见 [[05-共识-ZAB]])

- zxid = (epoch, counter),64 位。
- 三阶段:Discovery / Synchronization / Broadcast。
- Leader 写入走 2PC 风格:PROPOSAL → ACK → COMMIT。

#### 2.1.3 Watch 机制

- 客户端注册 watch:`getData(path, watch=true)`。
- 节点变化时,服务端推送 `WatcherEvent` 给客户端。
- **一次性触发**:触发后失效,需重新注册。
- ZK 3.6+ 引入 **Persistent Watch / Recursive Watch**,缓解"反复注册"的开销。

```java
// Java: ZK 客户端注册配置 watch
Stat stat = new Stat();
zk.getData("/config/timeout", event -> {
    System.out.println("Config changed: " + event);
    // 重新注册(避免丢失后续变更)
    try { zk.getData("/config/timeout", this, stat); }
    catch (Exception e) { /* ... */ }
}, stat);
```

#### 2.1.4 Session 与临时节点

- 客户端连接 ZK 时分配 64 位 sessionID,协商 sessionTimeout。
- 客户端定期发 PING 续约;超过 sessionTimeout 未续约,session 失效,所有临时节点被删。
- 临时节点是"心跳/健康检查"的天然载体:服务实例注册 `/services/payment/i-12345`(临时),实例宕机 → session 超时 → 节点消失 → 客户端 watch 触发。

#### 2.1.5 Leader 选举原语

经典 ZK 选举算法 (Hunt 2010 论文):

```
1. 所有参与选举的客户端在 /election 下创建临时顺序节点
   /election/n_00000001, /election/n_00000002, ...
2. 每个客户端取列表中所有节点,看自己是否序号最小
3. 序号最小 → Leader;否则 watch 前一个节点
4. Leader 宕机 → session 失效 → 临时节点消失 → 后继节点被通知 → 自己变 Leader
```

```java
public class ZkLeaderElection {
    private final ZooKeeper zk;
    private final String electionPath = "/election";
    private String myNode;

    public void nominate() throws Exception {
        myNode = zk.create(electionPath + "/n_", new byte[0],
                ZooDefs.Ids.OPEN_ACL_UNSAFE,
                CreateMode.EPHEMERAL_SEQUENTIAL);
        checkLeader();
    }

    private void checkLeader() throws Exception {
        List<String> children = zk.getChildren(electionPath, false);
        Collections.sort(children);
        String smallest = children.get(0);
        if (myNode.equals(electionPath + "/" + smallest)) {
            becomeLeader();
            return;
        }
        // watch 前一个,避免惊群
        int myIdx = children.indexOf(myNode.substring(electionPath.length() + 1));
        String prev = children.get(myIdx - 1);
        Stat stat = zk.exists(electionPath + "/" + prev, event -> {
            if (event.getType() == EventType.NodeDeleted) {
                try { checkLeader(); } catch (Exception e) { /* ... */ }
            }
        });
        if (stat == null) checkLeader();  // 前任已消失,重新检查
    }

    private void becomeLeader() { /* ... */ }
}
```

> ⚠️ **易错**:不要让所有 follower 都 watch 最小节点,会导致"惊群"(Leader 切换时所有 follower 同时被唤醒)。正确做法是 watch **前一个**节点,形成链式通知。

### 2.2 etcd:Raft + KV

#### 2.2.1 数据模型

- 平铺 KV(无层级),但 key 用 `/` 分隔实现"伪目录":
  - `etcdctl put /services/payment/i-12345 ...`
- **Lease**:租约,关联到 key,key 在租约过期时自动删除(等价 ZK 临时节点)。
- **Revision**:全局单调递增版本号,每次写 +1。
- **MVCC**:每个 key 保留多版本历史,可按 revision 查询历史值(用于 watch 回溯)。
- **Compact**:清理旧 revision,释放空间。

#### 2.2.2 Raft 实现

etcd 的 Raft 库 (etcd-raft) 是工业级 Raft 实现的标杆:

- WAL 持久化 + Snapshot 压缩
- PreVote / CheckQuorum 防止网络分区脑裂
- ReadIndex / Lease Read 实现线性一致读
- Joint Consensus 成员变更

#### 2.2.3 Watch 机制 (相比 ZK 的改进)

- **历史回放**:客户端可指定 `startRevision`,服务端从该 revision 开始推送(支持"断点续传")。
- **持续触发**:不需要反复注册。
- **流式**:gRPC stream,效率高。

```go
// Go: etcd watch 服务实例变化
cli, _ := clientv3.New(clientv3.Config{Endpoints: []string{"localhost:2379"}})
rch := cli.Watch(context.Background(), "/services/payment/", clientv3.WithPrefix())
for wresp := range rch {
    for _, ev := range wresp.Events {
        switch ev.Type {
        case clientv3.EventTypePut:
            fmt.Printf("Instance UP: %s = %s\n", ev.Kv.Key, ev.Kv.Value)
        case clientv3.EventTypeDelete:
            fmt.Printf("Instance DOWN: %s\n", ev.Kv.Key)
        }
    }
}
```

#### 2.2.4 事务 (Mini-Txn)

etcd 支持 **compare-and-swap** 风格的原子操作:

```go
// 原子地"如果 key 不存在则创建"
txn := cli.Txn(context.Background()).
    If(clientv3.Compare(clientv3.CreateRevision("/leader"), "=", 0)).
    Then(clientv3.OpPut("/leader", myID, clientv3.WithLease(leaseID))).
    Else(clientv3.OpGet("/leader"))
resp, _ := txn.Commit()
if resp.Succeeded {
    // 我是 leader
}
```

> 🎓 etcd Txn 不是 SQL 事务,只是"多个 compare + 多个 then/else 操作"的原子执行,等价 ZK 的 `multi`。

#### 2.2.5 Lease + KeepAlive

```go
// 申请 10s 租约,自动续约
lease := clientv3.NewLease(cli)
resp, _ := lease.Grant(context.Background(), 10)
leaseID := resp.ID
// 后台 keepalive
ch, _ := lease.KeepAlive(context.Background(), leaseID)
go func() {
    for range ch { /* 续约成功 */ }
}()
// 把 key 绑定到 lease
cli.Put(context.Background(), "/services/payment/i-12345", "10.0.0.5:8080",
    clientv3.WithLease(leaseID))
// 进程崩溃 → keepalive 停止 → 10s 后 lease 过期 → key 自动删除
```

### 2.3 Consul:Raft + Service Discovery

#### 2.3.1 与 etcd 的差异

| 维度 | etcd | Consul |
|------|------|--------|
| 数据模型 | 纯 KV | KV + 服务目录(原生) |
| 服务发现 | 客户端自己写 key | 内建 service / health check |
| 健康检查 | 应用层 keepalive | agent 主动探测 (HTTP/TCP/Script) |
| 跨 DC | 无原生支持 | 原生 multi-DC WAN gossip |
| DNS 接口 | 无 | 内建 DNS(可被 nginx/k8s 直接解析) |
| 部署形态 | 集群 + 客户端 SDK | server + agent(每节点一个) |

#### 2.3.2 架构

```
DC1:
  Consul Servers (Raft, 3/5 节点)
   ↑ gossip (LAN)
  Consul Agents (每台机器一个,跑 health check)
   ↓
  服务进程

跨 DC:
  Consul Servers (DC1) ←— WAN Gossip —→ Consul Servers (DC2)
```

#### 2.3.3 健康检查

Consul Agent 内建多种检查:

```json
{
  "check": {
    "id": "api-health",
    "name": "HTTP API on port 5000",
    "http": "http://localhost:5000/health",
    "interval": "10s",
    "timeout": "2s"
  }
}
```

服务实例异常 → 检查失败 → agent 标记为 critical → server 更新目录 → 客户端 watch 收到通知 / DNS 查询自动剔除。

#### 2.3.4 Sessions & Locks

Consul 提供 Session API(类似 etcd Lease)+ Lock API:

```bash
# 1. 创建 session
curl -X PUT -d '{"TTL": "30s", "Behavior": "release"}' \
  http://localhost:8500/v1/session/create
# 返回 {"ID": "abc-123"}

# 2. 用 session 抢锁
curl -X PUT -d 'leader-node-1' \
  http://localhost:8500/v1/kv/leader?acquire=abc-123
# 返回 true/false

# 3. 释放锁
curl -X PUT -d 'leader-node-1' \
  http://localhost:8500/v1/kv/leader?release=abc-123
```

### 2.4 Nacos:AP/CP 双模

Nacos 是阿里开源的配置 + 注册中心,设计上同时支持 AP 和 CP:

#### 2.4.1 两种模式

- **AP 模式 (默认)**:服务发现用 Distro 协议(每节点负责一部分数据,异步同步)。可用性优先,跨节点最终一致。
- **CP 模式**:配置管理和 Raft 协议(强一致)。配置必须强一致,避免读到旧配置。

切换:`@NacosValue(value = "${nacos.naming.mode:AP}")` 或 SDK 指定。

#### 2.4.2 Distro 协议 (AP)

- 每节点负责一部分 client(按 hash 分配),client 注册数据先写本地,再异步同步给其他节点。
- 节点故障时,其他节点接管其 client。
- 类似 Dynamo,但更轻量(只同步注册数据,不复制全部)。

#### 2.4.3 配置中心

```java
// Java: Nacos 配置监听
@NacosConfigListener(dataId = "payment-service.yaml", groupId = "PROD")
public void onConfigChange(String config) {
    System.out.println("Config updated: " + config);
    // 重新加载阈值、限流规则等
}
```

### 2.5 协调服务能做什么 —— 原语清单

| 原语 | ZK 实现 | etcd 实现 | Consul 实现 |
|------|---------|----------|------------|
| **配置中心** | `getData` + watch | `Get` + watch | KV + watch |
| **服务注册** | 临时节点 `/svc/i-12345` | Lease-bound key | service + check |
| **服务发现** | `getChildren` + watch | `Get /svc/` prefix | DNS / HTTP / watch |
| **Leader 选举** | 临时顺序节点 + 链式 watch | Txn CAS + Lease | Session + Lock |
| **分布式锁** | 临时顺序节点 + watch | Txn + Lease | Session + Lock |
| **队列** | 顺序节点 | (不推荐,用 MQ) | (不推荐) |
| **成员管理** | 临时节点 | Lease + key prefix | service + check |
| **元数据存储** | 小 znode (< 1MB) | KV (< 1MB) | KV (< 512KB) |

## 3. 🎓 学术深度

### 3.1 ZooKeeper 论文 (Hunt 2010) 的核心贡献

#### 3.1.1 Wait-Free 协调原语

> 与传统基于锁的协调不同,ZK 提供 wait-free 操作:客户端的读不会因其他客户端的写而阻塞,反之亦然。这极大简化了应用编程模型。

#### 3.1.2 Linearizable Writes + FIFO Client Order

ZK 论文证明其满足两个核心性质:

- **Atomic / Linearizable Writes**:所有写操作序列化,与全局真实顺序一致。
- **FIFO Client Order**:同一客户端的读看到自己之前的写(读到的版本 ≥ 客户端已写版本)。

这是**协调服务的本质**:不需要全线性一致,只需要"我自己写完之后能立刻读到"。

#### 3.1.3 同步读 vs 异步读

- 默认读:可读到旧数据(follower 落后),但满足 FIFO。
- `sync()` 操作:强制 leader 同步后再读,提供线性一致读。

```java
// 强一致读
zk.sync("/config", (rc, path, ctx) -> {
    byte[] data = zk.getData("/config", false, null);
    // 此时一定是最新值
}, null);
```

### 3.2 etcd 的 Linearizable Read 实现

etcd Raft 库通过两种方式实现线性一致读:

#### ReadIndex

1. Leader 记录当前 commit index。
2. Leader 发心跳,确认自己还是 Leader(防止旧 Leader 返回旧数据)。
3. 等待 apply index ≥ commit index。
4. 读取状态机。

#### Lease Read

1. Leader 依靠 lease(在租约内确认自己还是 Leader)省略心跳。
2. 直接读取,无需额外 RPC。
3. 风险:时钟漂移可能在 lease 过期后仍认为自己是 Leader(导致 stale read)。

> 🎓 etcd 默认使用 ReadIndex,Lease Read 性能更高但有 clock 依赖。

### 3.3 Chubby (Google) vs ZK

Google Chubby 是 ZK 的"前辈",论文 (Burrows 2006) 比 ZK 早 4 年:

| 维度 | Chubby | ZK |
|------|--------|-----|
| 接口 | 锁 + 文件(类似 POSIX) | znode 树 |
| 一致性 | Linearizable | Linearizable Write + FIFO Read |
| 缓存 | 客户端缓存 + lease | 无原生缓存(应用自管) |
| 用途 | Leader 选举为主 | 通用协调 |
| 论文影响 | 工业实践总结 | 学术化抽象 |

> 🎓 ZK 论文明确表示"参考 Chubby 但简化为 wait-free",Chubby 的设计经验(如客户端缓存、lease 续约机制)被广泛吸收到 ZK/etcd 工程实现中。

### 3.4 CAP 视角下的协调服务

| 服务 | 分区时表现 | 属于 |
|------|----------|------|
| ZK | 少数派分区不可用 | CP |
| etcd | 少数派分区不可用 | CP |
| Consul | 少数派分区不可用(server),但 agent 本地查询仍可用 | CP + 边缘 AP |
| Nacos (AP) | 所有节点都可读写(最终一致) | AP |
| Nacos (CP) | 少数派不可用 | CP |

> ⚠️ **易错**:有人认为"ZK 是 CP,所以不适合做服务发现"。这是误解。CP 服务发现并非不可用,只是分区时少数派客户端无法注册/查询;实践中分区很短,且 CP 保证"看到的服务一定真实在线",反而比 AP 更安全。Nacos AP 模式追求可用性,代价是可能短暂读到已下线实例。

### 3.5 Watch 一致性

不同服务的 watch 语义:

- **ZK**:事件触发顺序与状态机 apply 顺序一致;但**一次性**,触发后需重新注册,期间变更可能丢失。
- **etcd**:从指定 revision 开始的连续事件流;即使客户端断连重连也能续传。
- **Consul**:基于 blocking query (`?index=N`),长轮询,无原生流式(Consul 1.0+ 支持 watch stream)。

## 4. 🏭 工业实战

### 4.1 选型对比表

| 维度 | ZooKeeper | etcd | Consul | Nacos |
|------|-----------|------|--------|-------|
| 共识 | ZAB | Raft | Raft | Distro + Raft |
| 一致性 | CP | CP | CP / edge AP | AP / CP 可切换 |
| 数据模型 | znode 树 | KV | KV + 服务 | KV + 服务 |
| 多 DC | 需要自己搭 | 需要自己搭 | 原生 WAN gossip | 集群同步 |
| 配置中心 | 弱 | 中 | 中 | 强 |
| 服务发现 | 弱 | 弱(需自建) | 强 | 强 |
| Spring Cloud | 已淘汰 | 已淘汰 | 强(Spring Cloud Consul) | 强(Spring Cloud Alibaba) |
| K8s | 不用 | **核心组件** | 部分场景 | 部分场景 |
| Dubbo | 早期主流 | 一般 | 一般 | **主流** |
| 性能(写 QPS) | ~10k | ~10k | ~5k | ~20k |
| 部署复杂度 | 中 | 中 | 中(需 agent) | 低 |

### 4.2 K8s 为什么选 etcd

K8s 把所有集群状态(pod、service、deployment、secret)都存在 etcd:

- **强一致**:K8s controller 不能容忍读到旧版本(可能重复调度)。
- **Watch 历史回放**:controller 重启后可从指定 revision 续传,避免丢失事件。
- **MVCC**:支持资源版本 (`resourceVersion`),客户端乐观并发控制。
- **小型数据**:K8s 数据全在内存级别(几 GB),etcd 的 2GB/8GB 限制够用。

```go
// K8s apiserver 用 etcd 的典型写法(简化)
cli.Txn(ctx).
    If(clientv3.Compare(clientv3.ModRevision("/pods/p1"), "=", expectedRev)).
    Then(clientv3.OpPut("/pods/p1", newData)).
    Else(clientv3.OpGet("/pods/p1"))
```

### 4.3 Dubbo / Spring Cloud Alibaba 选 Nacos

Nacos 同时承担"配置 + 注册"两个角色,与 Spring Cloud Alibaba 深度集成:

- 配置中心:支持 yaml/properties/json,热更新 + 灰度发布。
- 服务发现:支持权重路由、健康检查、跨集群路由。
- 双模切换:服务发现默认 AP(可用性优先),配置默认 CP(强一致)。

```java
// Spring Cloud Alibaba + Nacos
@RefreshScope
@RestController
public class PaymentController {
    @Value("${payment.timeout:3000}")
```

### 4.4 HBase on ZK

HBase 用 ZK 做:

- **Master 选举**:多个 Master 同时启动,只有抢到 `/hbase/master` 临时节点的成为 active。
- **RegionServer 注册**:RegionServer 启动时在 `/hbase/rs/` 下创建临时节点,Master watch 该目录感知上下线。
- **Meta 路由**:客户端通过 `/hbase/meta-region-server` 找到 `hbase:meta` 所在 RS。
- **集群状态**:负载均衡、split/merge 状态都存在 ZK。

```
/hbase
├── master             (临时节点,Master 选举)
├── meta-region-server (Meta Region 位置)
├── rs/                (RegionServer 注册目录)
│   ├── rs-1
│   └── rs-2
├── table              (表状态)
│   └── payment
│       └── tablelock
├── balancing          (负载均衡锁)
└── splitWAL           (WAL 切分任务分配)
```

### 4.5 Kafka 对 ZK 的依赖演变

- **Kafka < 2.8**:严重依赖 ZK,存储 topic/broker/partition 元数据、消费者位移(Kafka < 0.9)、Leader 选举、controller 选举。
- **Kafka 2.8+**:KRaft 模式,内置 Raft 替代 ZK。
- **Kafka 3.3+**:KRaft 生产可用。
- **Kafka 4.0 (规划)**:完全移除 ZK。

```java
// KRaft 模式启动
// kafka-storage.sh format --config server.properties --cluster-id xxx
// kafka-server-start.sh server.properties
```

迁移原因:ZK 元数据规模受限(Kafka 集群超过 20 万 partition 时 ZK 成瓶颈)、controller 切换慢、运维复杂。

### 4.6 分布式锁实战对比

详见 [[11-分布式锁]],此处给出协调服务的锁原语对比:

| 服务 | 锁实现 | 公平性 | 防脑裂 |
|------|-------|-------|--------|
| ZK | 临时顺序节点 + watch 链 | 公平 | 是(临时节点随 session 失效) |
| etcd | Txn CAS + Lease | 非公平 / 可改公平 | 是(Lease 过期自动释放) |
| Consul | Session + Lock | 非公平 | 是(Session 失效自动释放) |
| Redis | SET NX + EX | 非公平 | **弱**(需 Fencing Token) |

## 5. 面试要点

### 5.1 高频问答

**Q1: ZooKeeper 和 etcd 的核心区别?**

> (1) 数据模型:ZK 是 znode 树,etcd 是 KV(用 `/` 模拟层级)。(2) 一致性:ZK 写线性一致、读 FIFO(默认顺序一致),etcd 默认线性一致读。(3) Watch:ZK 一次性触发需重新注册,etcd 持续流式 + 历史回放。(4) 协议:ZK 用 ZAB,etcd 用 Raft。(5) 临时节点:ZK 原生支持,etcd 用 Lease 模拟。

**Q2: 为什么 ZK 不适合存大量数据?**

> (1) ZK 设计目标是协调原语,单 znode 默认上限 1MB;(2) 写入要走 ZAB 共识,网络放大 N 倍;(3) follower 全量内存,扩容成本高;(4) snapshot 文件大时启动慢。业界共识:ZK/etcd 只存"KB 级元数据"。

**Q3: ZK 的临时节点为什么能做 Leader 选举?**

> 临时节点绑定 session,session 由心跳维持。Leader 进程崩溃 → 心跳停 → session 超时 → 临时节点删除 → 后继 watch 触发 → 自动切换。这避免了"Leader 进程死了但锁没释放"的死锁问题。

**Q4: etcd 的 Lease Read 和 ReadIndex 区别?**

> ReadIndex:Leader 处理读时先发心跳确认仍是 Leader,再读;安全,但每次读多一轮 RPC。Lease Read:Leader 在租约内直接读,省略心跳;性能高,但依赖时钟正确性,有时钟漂移风险。etcd 默认 ReadIndex。

**Q5: Nacos 的 AP 和 CP 模式怎么选?**

> 服务发现默认 AP:分区时各节点仍可注册/查询,牺牲一致性换可用性,适合"短暂读到已下线实例可容忍"的场景。配置管理默认 CP:配置必须强一致,避免部分节点读到旧配置导致行为不一致。切换通过 SDK 指定。

**Q6: ZK 的 watch 为什么是一次性的?**

> 历史 ZK 设计权衡:一次性简化服务端实现(不维护客户端 watch 列表),避免"客户端未 ack 导致事件堆积"。代价是应用需在事件处理后重新注册,期间变更可能丢失(用 `sync()` + 重新 `getData` 兜底)。ZK 3.6 引入 Persistent Watch 缓解该问题。

**Q7: 一致性哈希环能做协调服务吗?**

> 不能。一致性哈希只解决"路由"问题,不解决"强一致写入"问题。协调服务核心是**共识算法**(ZAB/Raft)保证多副本一致。一致性哈希可用于协调服务的客户端路由(但通常协调服务集群规模小,直接列出节点列表即可)。

**Q8: 服务发现有哪几种实现方式?**

> (1) 协调服务:ZK/etcd/Consul/Nacos,客户端 watch 拉取实例列表。(2) DNS:Consul DNS、K8s ClusterIP。(3) LB + 健康检查:Nginx + consul-template、Spring Cloud LoadBalancer。(4) Service Mesh:Envoy xDS 下发实例。协调服务方式是基础,其他方式多在协调服务之上封装。

### 5.2 易错点 ⚠️

1. **"ZK 是最终一致"** — 错。ZK 写线性一致;读默认顺序一致(同一客户端 FIFO)。
2. **"etcd 的 Watch 需要重新注册"** — 错。etcd Watch 是持续流,断线重连可从 revision 续传。
3. **"临时节点会立刻删除"** — 错。session 超时(默认几十秒)后才删,期间 watch 不会触发。
4. **"Consul 是 AP"** — 不准确。Consul server 是 CP(Raft),agent 本地查询是 AP(edge)。
5. **"K8s 用 ZK"** — 错。K8s 用 etcd。
