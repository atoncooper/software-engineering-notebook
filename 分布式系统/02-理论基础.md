## 2.1 CAP 定理

### 2.1.1 三个性质

> **CAP 定理**（Brewer 2000 提出，Gilbert-Lynch 2002 形式化证明）：
> 在网络可能分区的分布式系统中，**一致性**（Consistency）、**可用性**（Availability）、**分区容忍性**（Partition Tolerance）三者不可同时满足。

| 性质 | 含义 | 形式化 |
|------|------|-------|
| **C**（一致性） | 所有节点同一时刻看到相同数据 | 等价于线性一致性（详见 §2.4） |
| **A**（可用性） | 每个非故障节点的请求都能得到（非错误）响应 | 系统整体持续可用 |
| **P**（分区容忍） | 网络分区时系统仍能运作 | 节点间消息可能丢失 |

### 2.1.2 P 不可选 ⭐

⚠️ **关键误解**：「三选二」暗示 P 可选。**实际上 P 不是可选项**：

- 网络分区是物理事实（交换机故障、链路断开、丢包严重）
- 任何真实分布式系统都必须容忍分区
- **真正的取舍是：分区发生时，C 还是 A？**

### 2.1.3 分区下的取舍

**选 C（CP 系统）**：

- 分区时拒绝写入不可达副本的请求
- 保证一致性，但牺牲可用性
- 例：ZooKeeper、etcd、HBase、Spanner

**选 A（AP 系统）**：

- 分区时仍接受所有节点请求
- 分区恢复后再修复不一致
- 保证可用性，但牺牲强一致性
- 例：Cassandra（默认）、Dynamo、Eureka

### 2.1.4 ⚠️ CAP 常见误解

| 误解 | 真相 |
|------|------|
| 「三选二」 | P 不可选，只有 C vs A |
| 「CA 系统」 | 真实网络必有分区，不存在纯 CA |
| 「CP 一定不可用」 | 仅分区时不可用，平时高可用 |
| 「AP 一定不一致」 | 仅分区时弱一致，平时可线性一致 |
| 「CAP 是定理所以严格」 | Gilbert-Lynch 形式化有强假设，实际系统在「软实时」下可灵活取舍 |

### 2.1.5 🎓 形式化定义

📜 [Gilbert, Lynch 2002] *Brewer's Conjecture and the Feasibility of Consistent, Available, Partition-Tolerant Web Services*：

- **一致性**：所有读返回最近写（线性一致）
- **可用性**：每个请求收到非错误响应（有限时延内）
- **分区容忍**：网络可任意丢消息（分区成两个子集，子集间消息全丢）

**定理**：异步网络中，三个性质不可同时满足。

**证明直觉**（详见 [§21 学术-CAP形式化](./21-学术-CAP形式化.md)）：

- 假设系统满足 C + A + P
- 分区为 $\{A, B\}$ 两部分
- 客户端写 $A$，读 $B$：要么 $A$ 拒绝（违反 A），要么 $B$ 返回旧值（违反 C）

## 2.2 PACELC 定理 ⭐

### 2.2.1 为什么需要 PACELC

CAP 只刻画了「分区时」的取舍，**未刻画「无分区时」的取舍**。

但实际系统中：

- 分区是少数情况
- 大部分时间是「正常运行」
- 正常运行时也有 **延迟 vs 一致性** 的取舍（强一致需 Quorum 等待）

### 2.2.2 PACELC 定义

📜 [Abadi 2010] *Consistency Tradeoffs in Modern Distributed Database System Design*：

> **PACELC**：Partition (P) 时取 Availability vs Consistency (AC)；Else (E) 无分区时取 Latency vs Consistency (LC)。

形式化：

$$
\text{if } P \text{ then } A \text{ or } C; \quad \text{else } L \text{ or } C
$$

### 2.2.3 工业系统 PACELC 归类

| 系统 | 分区时 | 无分区时 | 标签 |
|------|-------|---------|------|
| **Spanner** | C | C | PC+EC |
| **MongoDB**（默认） | C | C | PC+EC |
| **HBase** | C | C | PC+EC |
| **etcd / ZooKeeper** | C | C | PC+EC |
| **Cassandra**（默认） | A | L | PA+EL |
| **Dynamo** | A | L | PA+EL |
| **Redis Cluster** | A | L | PA+EL（异步复制） |
| **MySQL**（半同步） | C | C+L | PC+EC/EL（可配） |
| **Riak** | A | L | PA+EL |
| **PNUTS** | C | L | PC+EL |

⚠️ **同一系统不同配置可切换**：

- Cassandra 调整 `consistency level`：ONE（EL）vs ALL（EC）
- MongoDB 调整 `write concern`：1（EL）vs majority（EC）

🔥 **面试加分**：能说出 PACELC 并举具体系统归类，远胜只答 CAP。

## 2.3 BASE 理论

### 2.3.1 BASE 含义

📜 [Pritchett 2008] *BASE: An ACID Alternative*：

| 缩写 | 含义 |
|------|------|
| **BA**（Basically Available） | 基本可用——允许部分失败时降级，而非完全不可用 |
| **S**（Soft state） | 软状态——允许中间状态存在，不要求时刻一致 |
| **E**（Eventually consistent） | 最终一致——无新写入时，副本最终收敛 |

### 2.3.2 BASE vs ACID

| 维度 | ACID | BASE |
|------|------|------|
| 一致性 | 强一致 | 最终一致 |
| 可用性 | 低（需协调） | 高 |
| 性能 | 低 | 高 |
| 适用场景 | 金融、关键事务 | 互联网高并发 |
| 典型 | 关系型数据库 | NoSQL（Dynamo、Cassandra） |

### 2.3.3 BASE 与 CAP 的关系

- BASE 是 AP 系统的工程实践
- 「最终一致」是 CAP 中 A 的代价
- 不是所有系统都应 BASE——金融、库存等场景必须 ACID

⚠️ **常见误区**：BASE ≠ 不一致。BASE 是「最终一致」，需要明确的收敛机制（读修复、反熵、TTL）。

## 2.4 一致性模型谱系 ⭐

> 一致性不是「强/弱」二元，而是从强到弱的谱系。每一档对应不同的工程代价与可扩展性。

### 2.4.1 谱系总览

```
强 ─────────────────────────────────────────── 弱
线性一致 → 顺序一致 → 因果一致 → 读己之写 → 单调读 → 最终一致
   │          │          │          │          │
  同步       全序       因果       Session    异步
  全局       单进程     偏序       可见       收敛
```

### 2.4.2 线性一致性（Linearizability）⭐

📜 [Herlihy, Wing 1990] *Linearizability: A Correctness Condition for Concurrent Objects*

> **定义**：所有操作看起来是在「某一瞬时」原子完成，且该瞬时位于请求开始与响应结束之间。

**特征**：

- **全局有序**：所有节点看到操作顺序一致
- **真实时间约束**：若操作 A 在操作 B 开始前完成，则 A 在 B 之前
- **单副本语义**：系统看起来像单一副本

**例**：

- 客户端 1 写 $x=5$（10:00:00 完成）
- 客户端 2 读 $x$（10:00:01 开始）→ 必须读到 5

**代价**：

- 需要 Quorum 同步、共识算法
- 分区下不可用（违反 A）
- 高延迟（需等待多数副本）

**典型**：etcd、ZooKeeper、Spanner、Paxos/Raft 复制状态机

### 2.4.3 顺序一致性（Sequential Consistency）

📜 [Lamport 1979] *How to Make a Multiprocessor Computer That Correctly Executes Multiprocess Programs*

> **定义**：所有节点看到操作顺序一致，但该顺序无需与真实时间一致。

**与线性一致区别**：

- 线性一致要求顺序与真实时间一致
- 顺序一致只要求全局一致，可与时间无关

**例**：

- 真实时间：客户端 1 写 $x=5$（10:00:00 完成），客户端 2 写 $x=10$（10:00:01 完成）
- 顺序一致允许客户端 3 看到顺序：$x=10$ 先于 $x=5$
- 线性一致不允许：必须 $x=5$ 先于 $x=10$

**代价**：低于线性一致，但仍需同步

**典型**：ZooKeeper 的写（顺序一致但不线性一致——读可读到旧值）

⚠️ **易错**：ZooKeeper 的写是线性一致，但**读不是**（默认本地读）。要线性一致读需用 `sync()`。

### 2.4.4 因果一致性（Causal Consistency）

📜 [Ahamad et al. 1995] *Causal Memory: Definitions, Implementation, and Programming*

> **定义**：有因果关系的事件按因果顺序可见，无因果关系的并发事件可见顺序可不同。

**因果关系（happens-before，→）**：

1. 同进程内：事件 $e_1$ 早于 $e_2$，则 $e_1 \to e_2$
2. 跨进程：$e_1$ 发送消息 $m$，$e_2$ 接收 $m$，则 $e_1 \to e_2$
3. 传递：$e_1 \to e_2$ 且 $e_2 \to e_3$，则 $e_1 \to e_3$

**例**：

- Bob 发帖「Hello」
- Alice 看到后回复「Hi」
- 因果：Bob 的帖 → Alice 的回复
- 因果一致要求：所有节点必须先看到 Bob 的帖，再看到 Alice 的回复
- 但其他不相关并发帖的顺序可不同

**代价**：低于顺序一致，可用向量时钟实现

**典型**：COPS、MongoDB sharded cluster（因果一致会话）、CockroachDB

### 2.4.5 Session 一致性（Read-Your-Writes / Monotonic Reads）

> **Session 模型**：客户端视角的一致性，不强求系统全局一致。

| 模型 | 含义 |
|------|------|
| **Read-Your-Writes** | 客户端读到自己的写 |
| **Monotonic Reads** | 客户端不会看到时间倒流（一旦读到 v2，不会再读到 v1） |
| **Monotonic Writes** | 同一客户端的写按发起顺序可见 |
| **Writes-Follow-Reads** | 客户端读到 v 后写 v'，则 v' 在 v 之后可见 |

**典型**：大部分 NoSQL 提供 Session 一致性（通过 Sticky Session 或 Read-Your-Writes Token）

### 2.4.6 最终一致性（Eventual Consistency）⭐

> **定义**：无新写入时，所有副本最终收敛到相同值。

**关键**：

- 不保证何时收敛
- 不保证过程中读到的值
- 只保证「最终」

**收敛条件**：

- 网络恢复
- 无新写入
- 足够长时间

**典型**：Cassandra（默认）、Dynamo、DNS

### 2.4.7 一致性层级与代价

| 模型 | 全局有序 | 时间约束 | 典型代价 | 应用 |
|------|---------|---------|---------|------|
| 线性一致 | ✅ | ✅ | Quorum + 共识，高延迟 | etcd、Spanner |
| 顺序一致 | ✅ | ❌ | 同步，中延迟 | ZooKeeper 写 |
| 因果一致 | 部分（因果） | ❌ | 向量时钟，中延迟 | COPS、CockroachDB |
| Session | 客户端内 | ❌ | Sticky 或 Token | 大部分 NoSQL |
| 最终一致 | ❌ | ❌ | 异步复制，低延迟 | Cassandra、Dynamo |

🔥 **工程含义**：一致性越强，可扩展性越差、延迟越高。**选最强一致性的代价 = 系统吞吐天花板**。

### 2.4.8 🎓 外部一致性（External Consistency）

📜 [Spanner 2012]：

> **外部一致性**：若事务 $T_1$ 在 $T_2$ 开始前完成，则任何事务看到的顺序中 $T_1$ 在 $T_2$ 之前。

外部一致性 = 线性一致性 + 跨事务。Spanner 通过 TrueTime 实现外部一致性。

→ 详见 [§3 时间与时钟](./03-时间与时钟.md) 与 [§8 存储-Spanner](./08-存储-Spanner与NewSQL.md)。

## 2.5 拜占庭将军问题

### 2.5.1 问题陈述

📜 [Lamport, Shostak, Pease 1982] *The Byzantine Generals Problem*：

> $n$ 位将军围攻一座城，必须协同决定「进攻」或「撤退」。他们通过信使通信。但将军中可能有叛徒（拜占庭节点），叛徒可对每位将军说不同的话。忠诚将军需达成一致行动。

### 2.5.2 两类消息

| 类型 | 假设 | 下界 |
|------|------|------|
| **口头消息**（Oral Messages） | 信使不可伪造签名 | $n \geq 3f+1$ |
| **签名消息**（Signed Messages） | 信使可验证签名，叛徒无法伪造 | $n \geq f+2$ |

### 2.5.3 拜占庭下界 $n \geq 3f+1$ ⭐

**直觉证明**（$n=3, f=1$ 不可解）：

```
    司令官 A（拜占庭）
       /        \
   进攻          撤退
     /            \
  将军 B        将军 C
```

- A 对 B 说「进攻」，对 C 说「撤退」（拜占庭行为）
- B 收到「进攻」，C 收到「撤退」
- B、C 互相转述：B 说「A 命令进攻」，C 说「A 命令撤退」
- B 无法判断 A 是叛徒还是 C 是叛徒
- 同样 C 也无法判断
- **3 个节点不够**

**$n=4, f=1$ 可解**：

- A 对 B、C、D 说值
- B、C、D 互相转述
- 即使 A 是叛徒说不同话，B、C、D 三人中至少两人收到相同消息（忠诚节点）
- 多数派达成一致

**通用**：$n \geq 3f+1$ 时，忠诚节点占 $\geq 2/3$，可形成多数派。

→ 完整证明见 [§21 学术-Byzantine下界](./21-学术-Byzantine下界.md)。

### 2.5.4 与 Crash 故障对比

| 维度 | Crash | Byzantine |
|------|-------|-----------|
| 故障行为 | 要么正常，要么沉默 | 可任意（撒谎、伪造） |
| 容错下界 | $n \geq 2f+1$ | $n \geq 3f+1$ |
| 消息验证 | 不需要 | 需要签名/MAC |
| 典型算法 | Paxos、Raft | PBFT、HotStuff |
| 应用 | 数据库、协调服务 | 区块链、跨组织系统 |

## 2.6 🎓 不可能性结果汇总

### 2.6.1 CAP 形式化

详见 [§21 学术-CAP形式化](./21-学术-CAP形式化.md)。

### 2.6.2 FLP 不可能定理

📜 [Fischer, Lynch, Paterson 1985]：

> 异步系统 + $f \geq 1$ + 故障停止模型 → 共识不可解（无法同时满足 Safety + Liveness）。

详见 [§5 共识-问题与FLP](./05-共识-问题与FLP.md) 与 [§21 学术-FLP证明](./21-学术-FLP证明.md)。

**绕过方式**：

1. 部分同步假设（Dwork-Lynch-Stockmeyer）
2. Failure Detector（Chandra-Toueg）
3. 随机化（随机化 Paxos）

### 2.6.3 Coordinated Attack 不可能

📜 [Gray 1978] *Notes on Data Base Operating Systems*：

> 两将军问题：两个将军通过不可靠信使通信，无法达成确切一致进攻时间。

**直觉**：

- A 发送「明早 8 点进攻」给 B
- B 回复「收到」
- A 需回复「确认收到」给 B
- B 需回复「确认收到」给 A
- ……
- 无限循环，永远无法 100% 确认对方收到

**结论**：同步系统中消息可能丢失时，**确切一致不可达**。

**实际解法**：接受「足够可能一致」（3 次握手、TCP 三次握手、2PC 的 ACK 机制都是这一思想）。

### 2.6.4 分布式快照边界

📜 [Chandy-Lamport 1985] *Distributed Snapshots: Determining Global States of Distributed Systems*：

- 异步系统中无法获得「瞬时全局状态」
- 通过 Marker 算法可获得「因果一致的全局快照」
- 详见 [§16 计算-Flink与流处理](./16-计算-Flink与流处理.md)

### 2.6.5 因果一致性边界

📜 [Mahajan, Alvisi, Dahlin 2011]：

> 在分区存在的情况下，因果一致性是「不牺牲可用性」可达到的最强一致性。

即：因果一致 = AP 系统一致性上界。

## 2.7 🏭 工业系统 PACELC 归类

### 2.7.1 CP 系统详解（PC+EC）

#### ZooKeeper

- **分区时**：少数派不可用（无法形成 Quorum）
- **平时**：写需过半，延迟较高
- **读**：默认本地，顺序一致（非线性一致）；`sync()` 后线性一致

#### etcd

- Raft 复制，写需过半
- 读默认线性一致（ReadIndex 机制）
- 详见 [§10 协调服务](./10-协调服务.md)

#### Spanner

- Paxos Group + TrueTime
- 外部一致性
- 详见 [§8 存储-Spanner](./08-存储-Spanner与NewSQL.md)

#### HBase

- 强一致（同一 Region 单点服务）
- Region 迁移期间不可用

### 2.7.2 AP 系统详解（PA+EL）

#### Cassandra

- Dynamo 风格 Quorum
- 默认 ONE：低延迟、最终一致
- 调到 ALL：强一致但高延迟
- 详见 [§8 存储-Cassandra](./08-存储-Cassandra.md)

#### Dynamo

- 原型系统，Sloppy Quorum + Hinted Handoff
- 最终一致

#### Redis Cluster

- 异步复制
- 故障切换期间可能丢数据
- 详见 [§8 存储-Redis与MongoDB](./08-存储-Redis与MongoDB.md)

### 2.7.3 可切换系统

| 系统 | 参数 | CP 模式 | AP 模式 |
|------|------|---------|---------|
| Cassandra | `consistency level` | ALL/QUORUM | ONE/LOCAL_ONE |
| MongoDB | `write concern` | `majority` | `1` |
| Kafka | `acks` + `min.insync.replicas` | `all` + `>1` | `1` |
| MySQL | `semi-sync` | ON | OFF |

🔥 **生产建议**：

- 默认配置往往是「性能优先」的弱一致——金融场景必须显式调强
- 强一致模式下的延迟需评估 P99，避免雪崩

### 2.7.4 ⚠️ 工业陷阱

- ⚠️ **Cassandra 默认 ONE**：弱一致，金融场景易踩坑
- ⚠️ **MongoDB Write Concern 默认 1**：主节点写入即返回，主节点故障会丢数据
- ⚠️ **Kafka acks=1**：仅主副本写入即返回，主副本故障丢数据
- ⚠️ **Redis 异步复制**：故障切换期间未同步数据丢失
- 🔥 **生产标配**：金融级用 `majority`/`all` + min.insync.replicas=2，性能用缓存 + 异步补偿

## 2.8 面试要点

### ⭐ Q1：CAP 定理怎么理解？

**骨架**：

1. C：所有节点同一时刻看到相同数据（线性一致）
2. A：非故障节点请求都能得到响应
3. P：网络分区时仍能运作
4. **P 不可选**——网络必然分区
5. 分区下 C vs A 不可兼得

**关键点**：必须强调 P 不可选，不能答「三选二」

**加分项**：提到 PACELC、提到「CA 系统不存在」、提到分区是少数情况

**常见追问**：
- 举 CP 例子？→ ZooKeeper、etcd、Spanner、HBase
- 举 AP 例子？→ Cassandra、Dynamo、Eureka
- 非分区时？→ C 与 A 可兼得

### ⭐ Q2：为什么说「CA 系统」不存在？

**骨架**：

1. 真实网络必然有分区（交换机故障、链路断、丢包严重）
2. 系统必须能容忍分区（P）
3. 「CA」意味着不容忍分区——真实系统做不到
4. 单机数据库可视为「CA」（无网络），但分布式系统必含 P

**关键点**：网络分区是物理事实

**加分项**：提到「单机 RDBMS 在 CAP 中是 CA」是教学简化

### ⭐ Q3：PACELC 是什么？

**骨架**：

1. CAP 只刻画分区时的 C vs A
2. PACELC 扩展：无分区时也有 Latency vs Consistency 取舍
3. 形式化：if P then A/C; else L/C
4. 举例：Cassandra 是 PA+EL（弱一致低延迟）；Spanner 是 PC+EC（强一致高延迟）

**关键点**：能区分「分区时」与「平时」

**加分项**：举具体系统归类（见 §2.7）

### ⭐ Q4：线性一致性和顺序一致性的区别？

**骨架**：

- 线性一致：全局有序 + 时间约束（A 在 B 开始前完成则 A 必在 B 前）
- 顺序一致：全局有序，但顺序可与真实时间无关
- 线性一致 ⊊ 顺序一致

**关键点**：时间约束是关键差异

**加分项**：举 ZooKeeper 例子——写线性一致，读默认顺序一致（`sync()` 后线性一致）

### ⭐ Q5：什么是最终一致性？它「最终」是多久？

**骨架**：

1. 定义：无新写入时，所有副本最终收敛
2. 不保证何时、不保证过程中
3. 收敛机制：读修复、反熵、TTL
4. 「最终」无固定时长——取决于网络、副本数、写入速率

**关键点**：强调「最终」无明确时长

**加分项**：提到因果一致是 AP 系统一致性上界

### ⭐ Q6：拜占庭将军问题是什么？下界是多少？

**骨架**：

1. 问题：$n$ 将军中 $f$ 个叛徒，忠诚将军需达成一致
2. 下界：口头消息 $n \geq 3f+1$，签名消息 $n \geq f+2$
3. 直觉：3 将军 1 叛徒不可解（A 对 B 说进攻，对 C 说撤退，B、C 无法判断谁叛变）
4. 应用：PBFT、区块链

**关键点**：$3f+1$ 与 $2f+1$ 的对比

**加分项**：提到签名消息可降到 $f+2$

### ⭐ Q7：BASE 理论是什么？

**骨架**：

1. BA：基本可用（降级而非完全不可用）
2. S：软状态（允许中间状态）
3. E：最终一致
4. 是 AP 系统的工程实践

**关键点**：BASE ≠ 不一致，是「最终一致」

**加分项**：与 ACID 对比；提到金融场景不应 BASE

### ⭐ Q8：FLP 不可能定理说什么？

**骨架**：

1. 异步系统 + $f \geq 1$ → 共识不可解
2. 无法同时满足 Safety + Liveness + 容错
3. 绕过：部分同步、Failure Detector、随机化

**关键点**：异步系统是关键假设

**加分项**：提到 Chandra-Toueg 用 ◇S 绕过

### ⭐ Q9：ZooKeeper 是 CP 还是 AP？读一致吗？

**骨架**：

1. CP 系统（ZAB 协议，写需过半）
2. **写线性一致，读默认顺序一致**（本地读，可能旧值）
3. 要线性一致读需 `sync()`

**关键点**：读写一致性不同

**加分项**：提到 ZAB 与 Raft 区别

### ⭐ Q10：Cassandra 是什么一致性？

**骨架**：

1. 默认 ONE：最终一致
2. 可调到 QUORUM/ALL：强一致
3. AP 系统（PA+EL）
4. 通过一致性级别在 C 与 L 间切换

**关键点**：可调一致性是 Cassandra 特色

**加分项**：提到 QUORUM 仍是线性一致（W+R>N）
