# 第 5 章 共识 —— 问题定义与 FLP 不可能定理

> **本章导读**
> 共识（Consensus）是分布式系统最核心的问题：多个节点对单个值达成一致。它看起来简单——「大家投票决定」——但 FLP 定理证明：在纯异步系统中，即使只有 1 个节点可能故障，共识也不可解。这是分布式系统最重要的不可能性结果。本章建立共识问题的形式化定义，证明 FLP 的直觉，并讨论实际系统如何绕过它（部分同步、Failure Detector、随机化）。后续章节将分别讨论 Paxos、Raft、ZAB、PBFT。

> 3. 实际系统如何绕过 FLP？
> 4. 共识与原子广播为何等价？
>

## 5.1 共识问题定义

### 5.1.1 形式化定义

> **共识问题**（Consensus）：$n$ 个进程，每个进程 $p_i$ 提出值 $v_i \in V$，所有正确进程需对同一个值 $v$ 达成决定。

### 5.1.2 两个性质

共识算法需满足：

| 性质 | 含义 |
|------|------|
| **Termination**（终止性，Liveness） | 所有正确进程最终决定一个值 |
| **Agreement**（一致性，Safety） | 所有正确进程决定同一个值 |
| **Validity**（有效性，Safety） | 决定的值必须是某个进程提议的 |

### 5.1.3 变体

| 变体 | 说明 |
|------|------|
| **Consensus** | 单值共识 |
| **Multi-Consensus** | 多值共识（日志） |
| **Atomic Broadcast** | 全序广播 |
| **State Machine Replication** | 状态机复制 |

→ 这四者在异步系统 + $f < n/2$ 下等价可约。

### 5.1.4 共识与一致性的关系

| 概念 | 范畴 |
|------|------|
| **共识**（Consensus） | 算法/问题 |
| **一致性**（Consistency） | 性质/模型 |
| **原子广播**（Atomic Broadcast） | 通信原语 |

**关系**：

- 共识算法实现一致性（线性一致）
- 原子广播 ≡ 共识（可相互约简）
- SMR = 共识 + 确定性状态机

## 5.2 共识与原子广播的等价性 🎓

📜 [Chandra, Toueg 1996]：

### 5.2.1 Atomic Broadcast 定义

> **原子广播**（Atomic Broadcast, a-broadcast）：满足以下性质的消息广播：
>
> - **Validity**：若广播消息 $m$ 的进程正确，则所有正确进程最终交付 $m$
> - **Integrity**：每个消息至多被交付一次，且仅被广播过它的进程交付
> - **Agreement**：若某正确进程交付 $m$，则所有正确进程都交付 $m$
> - **Total Order**：若进程 $p$ 先交付 $m_1$ 后交付 $m_2$，则任何进程都先交付 $m_1$ 后交付 $m_2$

### 5.2.2 等价证明直觉

**共识 → 原子广播**：

- 每条消息触发一次共识
- 共识决定消息的全局顺序

**原子广播 → 共识**：

- 用原子广播广播提议值
- 第一个被交付的消息即共识结果

**结论**：在异步系统 + $f < n/2$ 下，二者等价。解决了共识就解决了原子广播。

### 5.2.3 工程含义

- Paxos/Raft 本质是原子广播
- 实现了原子广播 = 实现了 SMR
- 不必单独设计「共识」和「日志复制」——一体两面

## 5.3 FLP 不可能定理 ⭐🎓

📜 [Fischer, Lynch, Paterson 1985] *Impossibility of Distributed Consensus with One Faulty Process*

### 5.3.1 定理陈述

> **FLP 定理**：在异步系统中（消息延迟无上界），即使只有 1 个进程可能 Crash-Stop 故障，也不存在同时满足 Termination + Agreement + Validity 的共识算法。

### 5.3.2 关键假设

1. **异步系统**：消息延迟无上界，节点处理速度无上界
2. **Crash-Stop 故障**：进程可永久崩溃，不恢复
3. **可靠网络**：消息最终交付（不丢），但可能任意延迟
4. **$f \geq 1$**：至少 1 个进程可能故障

### 5.3.3 证明直觉 ⭐

完整证明见 [§21 学术-FLP证明](./21-学术-FLP证明.md)，这里给直觉：

#### 核心矛盾

异步系统中**无法区分「慢」与「死」**：

- 进程 A 等待进程 B 的消息
- B 可能崩溃了，也可能只是慢
- A 无法判断，要么无限等待（违反 Termination），要么放弃（可能违反 Agreement）

#### 证明结构

1. **初始配置（configuration）**：所有进程未开始
2. **bivalent 配置**：存在两种执行路径，分别决定 0 和 1
3. **关键引理**：任何共识算法必存在初始 bivalent 配置
4. **关键引理**：从 bivalent 配置出发，存在一个无限执行，永远保持 bivalent（不决定）
5. **结论**：算法无法保证 Termination

#### 「永远不决定」的执行如何构造

证明中关键构造一个**adversary**（对手）：

- 对手控制消息调度
- 对手选择性地延迟消息，使系统始终保持 bivalent
- 由于异步性，被延迟的进程不能被判断为故障
- 故算法无法终止

### 5.3.4 FLP 的物理含义

⚠️ **FLP 不是说共识不可解，而是说**：

- **纯异步系统**（无任何时间假设）下不可解
- 实际系统都有时间假设（部分同步、Failure Detector）
- 实际系统都能在「大部分时间」正确共识，极端情况下可能阻塞

### 5.3.5 FLP 的弱化结论

| 弱化方向 | 结论 |
|---------|------|
| 放弃 Termination | 可保证 Agreement + Validity（如 Paxos 在极端情况下不终止） |
| 放弃容错 | $f=0$ 时可解 |
| 放弃异步假设 | 部分同步可解 |
| 引入 Failure Detector | 可解（Chandra-Toueg） |
| 引入随机化 | 可解（随机化 Paxos，概率终止） |

## 5.4 绕过 FLP 的方法

### 5.4.1 部分同步假设 📜

📜 [Dwork, Lynch, Stockmeyer 1988]：

> **部分同步**（Partial Synchrony）：存在未知的时间 $T$ 与上界 $\Delta$，使得 $t > T$ 后网络变为同步（消息延迟 < $\Delta$）。

**意义**：

- 真实网络「大部分时间同步，偶尔异步」
- 算法可在同步期达成共识
- 异步期可阻塞，但同步期恢复后必达成

**典型**：几乎所有工业共识算法（Paxos、Raft）都假设部分同步。

### 5.4.2 Failure Detector 📜

📜 [Chandra, Toueg 1996]：

> 引入 Failure Detector 作为「外部信息源」，让进程能「知道」哪些节点故障。

**关键结果**：

- 在异步系统 + Eventually Strong Failure Detector（◇S）+ $f < n/2$ 下，共识可解
- ◇S：每个故障节点最终被怀疑；存在某个时刻后至少一个正常节点不被怀疑

**工业实现**：

- 心跳 + Timeout（固定或 Phi Accrual）
- Raft 的 Leader Lease
- Paxos 的 Leader 选举

### 5.4.3 随机化 📜

📜 [Ben-Or 1983]：

- 引入随机性，让进程「抛硬币」
- 以概率 1 终止
- 不保证最坏情况终止，但期望终止

**典型**：Ben-Or 算法、随机化 Paxos。

### 5.4.4 放弃 Termination

- Paxos 在极端情况下可能 live-lock（多个 Proposer 互相打断）
- Safety 永远保证，Liveness 大部分时间保证
- 工程上可接受（概率极低 + 可重试）

### 5.4.5 实际系统的做法 🔥

| 系统 | 绕过方式 |
|------|---------|
| **Paxos** | 部分同步 + 单 Leader 优化（Multi-Paxos） |
| **Raft** | 部分同步 + 随机化选举超时 |
| **ZAB** | 类似 Raft，部分同步 + Leader 选举 |
| **PBFT** | 部分同步 + View Change |
| **HotStuff** | 部分同步 + Leader 轮换 |

🔥 **核心**：所有工业共识算法都假设「部分同步」——这是绕过 FLP 的根本前提。

## 5.5 Coordinated Attack 不可能 🎓

📜 [Gray 1978]：

### 5.5.1 两将军问题

> 两位将军围攻城池，需协同决定进攻或撤退。通过信使通信，但信使可能被俘（消息丢失）。如何达成确切一致？

### 5.5.2 不可能性

**结论**：在同步系统 + 消息可能丢失下，两将军无法达成 100% 一致。

**直觉**：

- A 发「进攻」给 B
- B 回复「收到」
- A 需确认 B 收到 ACK
- ……
- 无限循环

**关键**：与 FLP 不同——这是**同步**系统的不可能性，原因是消息丢失。

### 5.5.3 工程解法

接受「足够可能一致」：

- **TCP 三次握手**：3 次后认为连接建立
- **2PC**：协调者发送 PREPARE → 参与者 ACK → 协调者发送 COMMIT
- **工程含义**：100% 一致不可达，工程接受 99.999...% 一致

## 5.6 共识的复杂度下界

### 5.6.1 消息复杂度

| 算法 | 消息数 | 轮数 | 容错 |
|------|-------|------|------|
| **Basic Paxos** | $O(n)$ | 2 | $f < n/2$ |
| **Multi-Paxos** | $O(n)$（steady state） | 1 | $f < n/2$ |
| **Raft** | $O(n)$ | 1 | $f < n/2$ |
| **PBFT** | $O(n^2)$ | 3 | $f < n/3$ |
| **HotStuff** | $O(n)$ | 4 | $f < n/3$ |

### 5.6.2 时间复杂度下界

📜 [Dolev, Strong 1983]：

- Crash 模型：至少 $f+1$ 轮
- Byzantine 模型：至少 $f+1$ 轮（口头消息）

### 5.6.3 容错下界

| 故障模型 | 容错下界 | 算法 |
|---------|---------|------|
| Crash-Stop | $f < n/2$ | Paxos, Raft |
| Crash-Recovery | $f < n/2$ | 工业系统 |
| Byzantine | $f < n/3$ | PBFT, HotStuff |
| Byzantine + 签名 | $f < n$ | 区块链 |

## 5.7 🏭 工业视角

### 5.7.1 共识在工业系统中的角色

```
       应用层
         │
    ┌────┴────┐
    │ 协调服务 │ ← ZooKeeper / etcd
    └────┬────┘
         │
    ┌────┴────┐
    │ 元数据  │ ← 集群成员、配置、选主
    └────┬────┘
         │
    ┌────┴────┐
    │ 共识算法 │ ← Paxos / Raft / ZAB
    └─────────┘
```

### 5.7.2 工业共识算法选型

| 场景 | 推荐 | 原因 |
|------|------|------|
| 协调服务（小规模） | Raft（etcd） | 易理解、生态成熟 |
| 数据库复制 | Raft / Multi-Paxos | 性能 + 一致性 |
| 大规模分布式存储 | Multi-Raft（TiKV） | 分片隔离 |
| 跨组织共识 | PBFT / HotStuff | 拜占庭容错 |
| 公链 | PoW / PoS | 大规模拜占庭 |

### 5.7.3 ⚠️ 工业陷阱

- ⚠️ **Raft 选举抖动**：网络抖动触发频繁选举，需调大 election timeout
- ⚠️ **Paxos Live-lock**：多 Proposer 互相打断，需单 Leader 优化
- ⚠️ **跨地域共识延迟**：跨 DC 共识 P99 高，需考虑本地化读
- ⚠️ **日志压缩误操作**：Raft snapshot 期间被覆盖

## 5.8 面试要点

### ⭐ Q1：什么是共识问题？

**骨架**：

1. $n$ 个进程对单个值达成一致
2. 三性质：Termination / Agreement / Validity
3. 与原子广播、SMR 等价

**关键点**：三性质

**加分项**：提到共识与一致性的关系

### ⭐ Q2：FLP 不可能定理的内容？

**骨架**：

1. 异步系统 + $f \geq 1$ → 共识不可解
2. 无法同时满足 Termination + Agreement
3. 证明直觉：异步系统无法区分「慢」与「死」

**关键点**：异步 + $f \geq 1$ + 不可同时满足

**加分项**：提到证明中的 bivalent 配置

### ⭐ Q3：FLP 是说共识不可解吗？

**骨架**：

- **不是**
- FLP 是说**纯异步系统**下不可解
- 实际系统通过部分同步、Failure Detector 绕过

**关键点**：「纯异步」是关键假设

**加分项**：提到 Chandra-Toueg 用 ◇S 绕过

### ⭐ Q4：实际系统如何绕过 FLP？

**骨架**：

1. 部分同步假设（Dwork-Lynch-Stockmeyer）
2. Failure Detector（Chandra-Toueg）
3. 随机化（Ben-Or）
4. 放弃 Termination（Paxos live-lock）

**关键点**：部分同步是工业主流

**加分项**：举例 Raft 用随机化选举超时

### ⭐ Q5：共识和原子广播为什么等价？

**骨架**：

1. 共识 → 原子广播：每条消息触发一次共识
2. 原子广播 → 共识：用原子广播广播提议，第一个交付即结果
3. 在异步 + $f < n/2$ 下等价

**关键点**：双向约简

**加分项**：提到 SMR = 原子广播 + 确定性状态机

### ⭐ Q6：两将军问题和 FLP 的区别？

**骨架**：

1. 两将军：同步系统 + 消息可能丢失 → 不可解
2. FLP：异步系统 + 消息可靠 + 节点可能故障 → 不可解
3. 两将军的根因是消息丢失，FLP 的根因是异步

**关键点**：不同假设下的不同不可能性

**加分项**：提到 2PC 是两将军的工程近似

### ⭐ Q7：拜占庭共识的容错下界？

**骨架**：

1. 拜占庭故障 + 口头消息：$n \geq 3f+1$
2. 拜占庭 + 签名消息：$n \geq f+2$
3. Crash 故障：$n \geq 2f+1$

**关键点**：$3f+1$ vs $2f+1$

**加分项**：提到 PBFT、HotStuff

### ⭐ Q8：共识算法的消息复杂度下界？

**骨架**：

1. Crash 模型：至少 $f+1$ 轮
2. Byzantine 模型：至少 $f+1$ 轮
3. 消息数：Basic Paxos $O(n)$，PBFT $O(n^2)$，HotStuff 优化到 $O(n)$

**关键点**：轮数下界 $f+1$

**加分项**：提到 HotStuff 的线性化创新
