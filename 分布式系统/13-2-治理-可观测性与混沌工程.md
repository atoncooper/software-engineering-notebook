## 0. 可观测性三支柱

分布式系统的可观测性(Observability)由三大支柱组成:

- **Logging**:日志,记录离散事件
- **Metrics**:指标,聚合数值
- **Tracing**:链路追踪,跨服务调用关系

> "Monitoring tells you when something is wrong. Observability lets you ask why." — Charity Majors

三者互补,共同支撑故障定位、性能优化、容量规划。

---

## 1. Logging

### 1.1 日志级别

| 级别 | 用途 | 量 |
|------|------|---|
| ERROR | 错误,需立即处理 | 少 |
| WARN | 警告,可能有问题 | 中 |
| INFO | 关键业务事件 | 中 |
| DEBUG | 调试细节 | 多 |
| TRACE | 详细追踪 | 极多(生产关) |

### 1.2 结构化日志

JSON 格式,便于机器解析:

```json
{
  "timestamp": "2024-01-01T12:00:00Z",
  "level": "INFO",
  "service": "payment",
  "trace_id": "abc123",
  "span_id": "def456",
  "user_id": "1001",
  "event": "payment_success",
  "amount": 100.00,
  "duration_ms": 50
}
```

### 1.3 日志收集栈

```
应用 → Filebeat (采集) → Kafka (缓冲) → Logstash (处理) → Elasticsearch (存储) → Kibana (查询)
                                                    ↓
                                                  HDFS (归档)
```

或更轻量:

```
应用 → Fluent Bit → Loki → Grafana
```

### 1.4 关键设计

1. **Trace ID 全链路**:每请求一个 trace_id,所有日志带这个 ID
2. **采样**:DEBUG/TRACE 生产采样,避免日志爆炸
3. **脱敏**:密码、身份证等敏感信息打码
4. **不阻塞业务**:异步写入,失败兜底
5. **合理级别**:ERROR 才告警,INFO 不告警

## 2. Metrics

### 2.1 指标类型

| 类型 | 含义 | 例子 |
|------|------|------|
| **Counter** | 单调递增 | 请求总数 |
| **Gauge** | 任意变化 | 当前连接数 |
| **Histogram** | 分布 | 请求延迟分布 |
| **Summary** | 分位数 | P99 延迟 |

### 2.2 USE 方法

> Brendan Gregg, *Utilization Saturation and Errors*

- **Utilization**:使用率(CPU、内存、磁盘、网络)
- **Saturation**:饱和度(队列长度、等待时间)
- **Errors**:错误数

### 2.3 RED 方法

> Tom Wilkie,针对微服务

- **Rate**:请求速率
- **Errors**:错误率
- **Duration**:延迟分布

### 2.4 四黄金信号

> Google SRE

- **Latency**:延迟
- **Traffic**:流量
- **Errors**:错误
- **Saturation**:饱和度

### 2.5 Prometheus

工业标准指标系统:

```yaml
# prometheus.yml
scrape_configs:
  - job_name: 'payment'
    metrics_path: /actuator/prometheus
    static_configs:
      - targets: ['payment:8080']
```

```java
// Spring Boot + Micrometer
@Autowired
private MeterRegistry registry;

public void processOrder() {
    Timer.Sample sample = Timer.start(registry);
    try {
        // 业务
        registry.counter("orders_total", "status", "success").increment();
    } catch (Exception e) {
        registry.counter("orders_total", "status", "error").increment();
    } finally {
        sample.stop(Timer.builder("orders_duration").register(registry));
    }
}
```

```promql
# 查询:最近 5 分钟订单 QPS
rate(orders_total[5m])

# 查询:P99 延迟
histogram_quantile(0.99, rate(orders_duration_bucket[5m]))
```

### 2.6 Grafana 可视化

- 仪表盘(Dashboard)
- 告警(Alert)
- 模板变量(可切换服务、时间范围)

## 3. Tracing

### 3.1 概念

```
[Trace abc123]
  ┌─ Service A (span 1) ─────────────────────────────┐
  │   ┌─ Service B (span 2) ───────┐                  │
  │   │   ┌─ Service C (span 3) ┐ │                  │
  │   │   └─────────────────────┘ │                  │
  │   └──────────────────────────┘                  │
  └──────────────────────────────────────────────────┘
```

- **Trace**:完整请求链路
- **Span**:单个服务的一次操作
- **Trace ID**:全链路唯一
- **Span ID**:Span 唯一
- **Parent Span ID**:父 Span

### 3.2 OpenTelemetry

CNCF 标准,统一 Logging + Metrics + Tracing:

```java
// OpenTelemetry SDK
Tracer tracer = openTelemetry.getTracer("payment");
Span span = tracer.spanBuilder("processPayment").startSpan();
try (Scope scope = span.makeCurrent()) {
    span.setAttribute("user_id", userId);
    span.setAttribute("amount", amount);
    // 业务
    payService.pay(userId, amount);
} catch (Exception e) {
    span.recordException(e);
    span.setStatus(StatusCode.ERROR);
    throw e;
} finally {
    span.end();
}
```

### 3.3 工业实现

- **Jaeger**:Uber 开源,CNCF
- **Zipkin**:Twitter 开源
- **SkyWalking**:Apache,中国活跃
- **Datadog APM**:商业
- **Elastic APM**:商业

### 3.4 采样策略

- **头部采样**:固定比例(如 1%),简单但可能漏关键 trace
- **尾部采样**:全部跟踪,根据规则(慢/错)决定保留,精准但开销大
- **自适应**:根据流量自动调整

## 4. 告警

### 4.1 告警原则

1. **可操作性**:告警必须能让人行动(无操作价值的告警是噪音)
2. **及时性**:故障发生 → 告警,延迟 < 1min
3. **准确性**:误报率低
4. **分级**:P0(立即) / P1(1h) / P2(1d)

### 4.2 SLO-based Alerting

> Google SRE

```
SLO: 99.9% 请求 < 100ms (30 天窗口)
SLI: 实际测量指标(P99 latency)
Error Budget: 0.1% 错误预算

告警:
  - 错误预算消耗速率 > 14.4x (2h 内耗尽) → P0
  - 错误预算消耗速率 > 6x (12h 内耗尽) → P1
  - 错误预算消耗速率 > 3x (3 天内耗尽) → P2
```

### 4.3 Alertmanager

```yaml
groups:
  - name: payment
    rules:
      - alert: HighErrorRate
        expr: |
          rate(orders_total{status="error"}[5m]) /
          rate(orders_total[5m]) > 0.05
        for: 5m
        labels:
          severity: P0
        annotations:
          summary: "Payment error rate > 5%"
```

## 5. 混沌工程

### 5.1 概念

> Netflix, Chaos Engineering

主动注入故障,验证系统容错能力。不是"测试",而是"实验"。

### 5.2 实验方法

1. **假设**:基于稳态(如"P99 < 100ms")
2. **注入故障**:杀实例、网络延迟、磁盘满
3. **观察**:稳态是否被打破
4. **改进**:发现薄弱点 → 加固

### 5.3 Chaos Monkey (Netflix)

```python
# 随机杀 EC2 实例
def chaos_monkey():
    while True:
        instances = ec2.list_instances()
        victim = random.choice(instances)
        ec2.terminate(victim)
        sleep(3600)
```

### 5.4 Chaos Toolkit

```json
{
  "version": "1.0.0",
  "title": "Kill a random pod",
  "description": "Test Kubernetes resilience",
  "method": [{
    "type": "action",
    "name": "kill-pod",
    "provider": {
      "type": "python",
      "module": "chaosk8s.pod.actions",
      "func": "terminate_pods",
      "arguments": {
        "label_selector": "app=payment",
        "qty": 1
      }
    }
  }]
}
```

### 5.5 Chaos Mesh

Kubernetes 原生混沌工程平台:

```yaml
apiVersion: chaos-mesh.org/v1alpha1
kind: PodChaos
metadata:
  name: payment-kill
spec:
  action: pod-kill
  mode: one
  selector:
    namespaces: [production]
    labelSelectors:
      app: payment
  scheduler:
    cron: "@every 1h"
```

支持:

- Pod Kill / Pause
- Network Delay / Loss / Partition
- IO Latency / Errors
- CPU / Memory Stress
- Time Skew(模拟时钟漂移)
- Disk Fill

### 5.6 实验

- **Chaos Monkey**:随机杀实例
- **Latency Monkey**:注入网络延迟
- **Chaos Gorilla**:模拟整个 AZ 故障
- **Chaos Kong**:模拟整个 Region 故障

### 5.7 实施原则

1. **从小开始**:单实例故障,逐步到 AZ/Region
2. **业务低峰**:首次实验在低峰期
3. **可快速回滚**:故障注入可立即撤销
4. **监控完备**:实验前确保可观测性
5. **复盘**:每次实验后复盘改进

## 7. 面试要点

**Q1: 可观测性三支柱是什么?**

> Logging(日志,离散事件)、Metrics(指标,聚合数值)、Tracing(链路追踪,跨服务关系)。三者互补:Logging 查具体事件,Metrics 看趋势,Tracing 定位跨服务瓶颈。

**Q2: Trace ID 怎么实现全链路?**

> 入口服务生成 trace_id,通过 HTTP Header / RPC metadata 传递到下游。下游把 trace_id 写入自己的日志 + tracing 上报。所有日志带 trace_id,可串联全链路。OpenTelemetry 标准化了这一过程。

**Q3: Google SRE 四黄金信号?**

> Latency(延迟)、Traffic(流量)、Errors(错误)、Saturation(饱和度)。任何服务的监控都应覆盖这四个维度,是 SRE 的基础。

**Q4: SLO 和 SLA 的区别?**

> SLO(Service Level Objective):内部目标,如"99.9% 请求 < 100ms"。SLA(Service Level Agreement):对外合同,违约赔偿,如"99.5% 可用,否则退款"。SLA 通常比 SLO 宽松,留 buffer。

**Q5: 混沌工程是什么?为什么需要?**

> 主动注入故障验证系统容错。需要因为:分布式系统故障组合多,常规测试覆盖不全;故障是常态,需要持续验证容错能力;提前发现薄弱点比生产事故好。Netflix Chaos Monkey 是经典实践。

**Q6: 滑动窗口指标怎么实现?**

> Prometheus 用时间窗口聚合:`rate(orders_total[5m])`。底层是 time series DB,按时间分桶,查询时聚合窗口内数据。Histogram 用 bucket 边界(如 0.1, 0.5, 1, 5, 10s)统计,查 P99 用 `histogram_quantile(0.99, ...)`。

**Q7: 告警怎么避免噪音?**

> (1) SLO-based 告警(基于错误预算而非固定阈值);(2) 多窗口告警(短期 + 长期都满足才告警);(3) 告警抑制(已知故障不重复告警);(4) 严格分级(P0 立即,P1 1h,P2 1d);(5) 定期审查告警,删除误报多的。

**Q8: 日志采样策略?**

> INFO 全采(关键事件)、ERROR 全采(必须告警)、DEBUG/TRACE 采样(如 1%)。尾部采样:全采但按规则保留(慢请求、错误请求全留,正常请求采样)。生产环境主要用 INFO + ERROR,DEBUG 仅排查时临时开启。
