## 1. 理论基础

### Q1: CAP 定理是什么?

> **速答**:分布式系统在网络分区时,一致性(C)和可用性(A)二选一。
>
> **展开**:CAP 由 Gilbert-Lynch 2002 形式化证明。C 是线性一致,A 是每个请求都有响应,P 是网络分区。三者不可同时满足,但 P 是网络属性(总会发生),所以实际是 CP vs AP 选型。ZK/etcd 是 CP,Cassandra/Dynamo 是 AP。PACELC 补充:无分区时也要在 L(延迟)和 C(一致性)间权衡。

### Q2: BASE 是什么?

> **速答**:Basically Available + Soft state + Eventually consistent,AP 系统的设计哲学。
>
> **展开**:BASE 是 CAP 中选 AP 的工程化:基本可用(允许部分功能降级)、软状态(允许中间不一致)、最终一致(过段时间收敛)。Dynamo、Cassandra 是 BASE 的典型实现。

### Q3: FLP 不可能性是什么?

> **速答**:异步网络 + 一个节点故障 = 共识不可能。
>
> **展开**:Fischer-Lynch-Paterson 1985 证明,在异步网络(无时钟假设)下,即使只有一个节点故障,也无法同时保证共识的 safety 和 liveness。工程绕过:部分同步假设(Eventually Stable)、故障检测器、随机化。

### Q4: 一致性模型有哪些?

> **速答**:Linearizability > Sequential > Causal > Read-Your-Writes > Eventual。
>
> **展开**:
> - Linearizability:单对象强一致,操作有全序,实时顺序保留
> - Sequential:单对象,允许 reorder 但所有客户端一致
> - Causal:保留因果关系(无并发时同 Sequential)
> - Read-Your-Writes:客户端读到自己之前的写
> - Eventual:过段时间收敛

## 2. 共识

### Q5: Paxos 和 Raft 的区别?

> **速答**:Paxos 学术、抽象、难懂;Raft 工程化、易理解、易实现。
>
> **展开**:Paxos 是 Basic Paxos(单值)+ Multi-Paxos(日志),但 Multi-Paxos 没明确 Leader 选举、日志复制细节,实现各异。Raft 把共识分解为 Leader Election + Log Replication + Safety,明确每一步,工业首选(etcd/Consul/TiKV)。

### Q6: Raft 怎么选主?

> **速答**:随机超时触发,Follower 转 Candidate,RequestVote 多数派同意即当选。
>
> **展开**:Raft 用随机化避免分票。Follower 在 election timeout(150-300ms 随机)内未收到 Leader 心跳 → 转 Candidate,term+1,发 RequestVote。Candidate 收到多数派同意 → 当选。任期 term 单调递增,旧 term 的 Leader 见到新 term 自动降级。Log Up-to-Date 要求:Candidate 的日志必须 ≥ 多数派。

### Q7: 拜占庭共识需要多少节点?

> **速答**:n ≥ 3f+1,f 为拜占庭节点数。
>
> **展开**:PBFT、HotStuff 等拜占庭共识需 3f+1 节点容忍 f 个拜占庭。原因:需 Quorum 2f+1,即使 f 个拜占庭不响应,仍有 f+1 个诚实节点;且 2f+1 中需 f+1 诚实才能盖过 f 拜占庭。区块链用 PoW/PoS 替代 BFT,适合公网。

## 3. 复制

### Q8: 主从复制 vs 多主 vs 无主?

> **速答**:主从简单但单点;多主可用性高但冲突;无主(Quorum)去中心化。
>
> **展开**:
> - 主从:Leader 写、Follower 读,故障切换有窗口
> - 多主:多 Leader 写,冲突需解决(LWW/CRDT/应用层)
> - 无主(Dynamo/Cassandra):Quorum W+R>N,去中心化

### Q9: Quorum 怎么保证一致?

> **速答**:W+R>N,读写 Quorum 必有交集。
>
> **展开**:N 个副本,W 写确认数,R 读返回数。W+R>N → 交集至少 1 个节点既在 W 又在 R,持有最新版本。读时通过版本号比较拿最新。强一致需 W+R>N 且 W>N/2,但不是线性一致(读写交叉场景仍有问题)。

### Q10: Read Repair 是什么?

> **速答**:读时发现副本不一致,顺便修复旧副本。
>
> **展开**:Dynamo/Cassandra 读时并发读多个副本,选最新版本返回,同时把最新版本异步写回旧副本。无需主动扫描,适合"读多写少"的热点 key。

## 4. 事务

### Q11: 2PC 有什么缺陷?

> **速答**:同步阻塞、协调者单点、不一致风险。
>
> **展开**:Phase 1(Prepare)所有参与者锁资源,期间阻塞;协调者故障,参与者卡在 prepared 状态;Phase 2 部分参与者 commit 部分失败,数据不一致。3PC 加 CanCommit + Timeout 缓解,但工程上少用。

### Q12: TCC 怎么解决空回滚、悬挂、幂等?

> **速答**:三个陷阱分别用"反向操作 + 状态检查 + 唯一事务 ID"。
>
> **展开**:
> - 空回滚:Try 未到但 Cancel 来了 → Cancel 检查 Try 是否执行,未执行则记录"已 Cancel",返回成功
> - 悬挂:Cancel 先于 Try → Try 检查是否已 Cancel,是则跳过
> - 幂等:每步带事务 ID + 状态记录,重复请求查状态

### Q13: Saga 怎么补偿?

> **速答**:每步定义补偿操作,失败时反向调用已成功步骤的补偿。
>
> **展开**:Saga 把长事务拆成短事务序列,每步有补偿。失败时从当前步向前回滚补偿。两种实现:Choreography(事件驱动)/ Orchestration(中心协调器)。补偿需幂等。

### Q14: Outbox 模式是什么?

> **速答**:DB 写入时同时写 outbox 表,CDC 异步投递到 MQ。
>
> **展开**:解决"DB+MQ 一致性"。业务表 + outbox 表同事务写入,Debezium 监听 outbox 表变更,转发到 MQ。保证 DB commit 成功则 MQ 必发,无需应用层重试。详见 [[06-事务-消息事务与Outbox]]。

## 5. 存储

### Q15: LSM-Tree 和 B-Tree 的区别?

> **速答**:LSM 顺序写、追加、写快读慢;B-Tree 就地更新、读快写慢。
>
> **展开**:LSM-Tree 写 WAL + MemTable,异步 flush + Compaction,写吞吐是 B-Tree 10x+。代价:读多 Level 查找(用 Bloom Filter 优化)、Compaction 写放大。B-Tree 适合读多写少(RDBMS),LSM 适合写多读少(HBase/Cassandra/RocksDB)。

### Q16: HBase 为什么快?

> **速答**:LSM-Tree 顺序写 + BlockCache + Bloom Filter + Region 分片。
>
> **展开**:写快:顺序写 WAL + MemTable(内存)。读快:BlockCache 缓存 + Bloom Filter 过滤 + Block Index 二分。海量:Region 分片 + HDFS 多节点并行。性能数据:单 RS 写 5-20w QPS,读 10-50w QPS(BlockCache 命中)。

### Q17: Redis 为什么单线程还快?

> **速答**:内存操作 + IO 多路复用 + 无锁。
>
> **展开**:内存操作本身 <1μs;单线程无锁、无上下文切换;epoll IO 多路复用高效;瓶颈在网络 IO 而非 CPU。Redis 6.0+ 多线程 IO(网络读写多线程,命令执行仍单线程)。

### Q18: Spanner 的 TrueTime 解决什么问题?

> **速答**:分布式时钟,提供有界误差,实现外部一致性。
>
> **展开**:传统 NTP 漂移大,无法支持时间戳全序。TrueTime 用 GPS+原子钟,误差 <7ms。配合 Commit Wait(等 TT.after(s)),实现 external consistency(线性一致 + 实时顺序)。代价:增加 7ms 提交延迟。

## 6. 消息队列

### Q19: Kafka 为什么快?

> **速答**:顺序写 + Zero-Copy + Page Cache + 批量压缩 + Partition 并行。
>
> **展开**:顺序写磁盘几百 MB/s;sendfile 实现 Zero-Copy(2 次拷贝 vs 4 次);Page Cache 加速读;批量 + snappy/lz4/zstd 压缩减少网络和存储;Partition 水平扩展。单 broker 吞吐 100MB/s+。

### Q20: Kafka 怎么保证不丢消息?

> **速答**:acks=all + 副本数 3 + min.insync.replicas=2 + 处理后 commit offset。
>
> **展开**:
> - Producer:acks=all(所有 ISR 确认)+ retries + enable_idempotence
> - Broker:replication.factor=3 + min.insync.replicas=2 + unclean.leader.election.enable=false
> - Consumer:手动提交 offset,处理完再 commit
> - 业务:消费幂等(去重表)

### Q21: Kafka 怎么实现 Exactly-Once?

> **速答**:Idempotent Producer + Transactional Producer + Consumer read_committed。
>
> **展开**:
> - Idempotent:producer_id + sequence_number,broker 去重
> - Transactional:transactional.id,跨 partition 原子
> - Consumer:isolation.level=read_committed,只读已提交
> - 端到端:consume-process-produce 在一个事务内
> - 本质:at-least-once + 幂等

## 7. 协调服务

### Q22: ZK 临时节点为什么能做 Leader 选举?

> **速答**:临时节点绑定 session,session 失效自动删除,Leader 崩溃自动触发切换。
>
> **展开**:Leader 注册临时节点 /leader。Leader 进程崩溃 → 心跳停 → session 超时 → 临时节点删除 → 后继 watch 触发 → 自动选举。无需人工干预,无死锁风险。

### Q23: etcd 和 ZK 的区别?

> **速答**:etcd Raft + KV + Watch 持续;ZK ZAB + znode 树 + Watch 一次性。
>
> **展开**:
> - 数据模型:etcd 平铺 KV(用 / 模拟层级),ZK 树形 znode
> - 一致性:etcd 默认线性一致读,ZK 写线性一致读顺序一致
> - Watch:etcd 持续流式 + 历史回放,ZK 一次性需重新注册
> - 协议:etcd Raft,ZK ZAB
> - 临时节点:etcd 用 Lease,ZK 原生

## 8. 分布式锁

### Q24: Redis 分布式锁的陷阱?

> **速答**:主从异步丢锁、GC STW 过期、释放需 Lua 验证。
>
> **展开**:
> - 主从切换:主挂从升,锁数据未同步丢失 → Redlock 多节点 Quorum
> - GC STW:锁过期但客户端仍以为持有 → Fencing Token
> - 释放:直接 DEL 可能删别人的锁 → Lua 验证 token 后删
> - 正确性场景必须加 Fencing

### Q25: Fencing Token 是什么?

> **速答**:锁服务每次发锁附带单调递增 token,存储层拒绝过期 token 的写入。
>
> **展开**:客户端 A 获锁 token=33,GC STW 锁过期;B 获锁 token=34,写入存储;A STW 结束,带 token=33 写存储 → 存储记住已见 34,拒绝 33。把"锁失效"问题转化为"存储层单调 token 检查",不依赖锁服务正确性。

## 9. 幂等性

### Q26: 怎么实现幂等?

> **速答**:幂等键 + 幂等表 / CAS / 唯一索引 / 状态机 / 去重表。
>
> **展开**:
> - 创建:唯一索引(业务唯一键)
> - 更新:CAS 乐观锁(version)
> - 状态流转:状态机(WHERE status IN)
> - MQ 消费:去重表(message_id)
> - 表单防抖:Token 机制
> - API 重试:幂等键 + 幂等表(Stripe 风格)

## 10. 容错

### Q27: 脑裂怎么避免?

> **速答**:Quorum + Fencing + Witness + Lease。
>
> **展开**:
> - Quorum:多数派才能形成决策,少数派自动停摆
> - Fencing Token:即使双主,存储层拒绝过期 token
> - Witness:偶数集群打破 2-2 平局
> - STONITH:物理杀死对方
> - Lease:租约过期自动降级

### Q28: 同城双活 vs 异地多活?

> **速答**:同城延迟 <1ms 强同步;异地 10-100ms 异步。
>
> **展开**:
> - 同城双活:同城市两 AZ,RPO=0,延迟低
> - 异地多活:跨城市,RPO>0(秒-分钟丢失),容灾范围大
> - 单元化(LDC):按 user_id 哈希分配到固定单元,本地闭环,跨单元异步

## 11. 综合

### Q29: 设计一个秒杀系统

> **速答**:前端限流 + 缓存预减库存 + 异步下单 + 分布式锁 + 幂等。
>
> **展开**:
> 1. 前端:按钮置灰、限流(验证码、答题)
> 2. 网关:限流(QPS 阈值)
> 3. 缓存:Redis 预减库存(Lua 原子)
> 4. 下单:MQ 异步处理,削峰
> 5. DB:库存分片(1000 库存分 10 片,各 100)
> 6. 幂等:幂等键防重复下单
> 7. 监控:实时大屏 + 告警

### Q30: 设计一个分布式 ID 生成器

> **速答**:雪花算法 + 时钟回拨处理。
>
> **展开**:
> - Snowflake:64 位 = 1 符号 + 41 时间戳 + 10 机器 + 12 序列
> - 时钟回拨:等待 / 报错 / 借未来时间
> - 替代:UUID(无序,索引差)、DB 自增(单点)、号段模式(预分配,需协调)
> - 百度 UidGenerator、美团 Leaf、TiDB AUTO_RANDOM
