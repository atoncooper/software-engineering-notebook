## 0. 通信是分布式系统的基础

分布式系统本质是"通过网络通信的多个独立节点"。通信协议决定:

- **性能**:延迟、吞吐
- **可靠性**:丢包、乱序、重传
- **语义**:同步/异步、阻塞/非阻塞
- **安全**:TLS、mTLS
- **演化**:版本兼容

本章梳理从 TCP 到 gRPC 的核心通信协议。

---

## 1. TCP 基础

### 1.1 三次握手

```
Client ── SYN (seq=x) ──→ Server
Client ←── SYN+ACK (seq=y, ack=x+1) ── Server
Client ── ACK (ack=y+1) ──→ Server
```

为什么 3 次?

- 2 次:Server 无法确认 Client 收到 SYN+ACK,可能建立半连接
- 4 次:第 4 次 ACK 已经在数据包中携带,没必要单独发

### 1.2 四次挥手

```
Client ── FIN ──→ Server
Client ←── ACK ── Server
Client ←── FIN ── Server
Client ── ACK ──→ Server
```

- 全双工关闭:两个方向各自关闭
- TIME_WAIT:2 MSL,防止旧连接干扰新连接

### 1.3 流量控制与拥塞控制

- **流量控制**:滑动窗口,接收方告诉发送方"我能接收多少"
- **拥塞控制**:
  - 慢启动:拥塞窗口指数增长
  - 拥塞避免:线性增长
  - 快重传:3 个重复 ACK 立即重传
  - 快恢复:不回到慢启动

### 1.4 TCP 的痛点

- 队头阻塞(HoL):一个包丢失,后续包都等待
- 三次握手延迟:1.5 RTT
- TCP 状态机复杂(TIME_WAIT 等)
- 内核空间实现,迭代慢

## 2. HTTP

### 2.1 HTTP/1.0

- 每请求一个 TCP 连接
- 连接建立开销大

### 2.2 HTTP/1.1

- Keep-Alive:复用 TCP 连接
- Pipeline:可连续发请求,但响应必须按序(队头阻塞)
- Host header:支持虚拟主机

### 2.3 HTTP/2

- 二进制分帧
- 多路复用:一个 TCP 连接多个并发请求
- 头部压缩(HPACK)
- Server Push

问题:TCP 层队头阻塞(一个流丢包,所有流等待)

### 2.4 HTTP/3 (over QUIC)

- 基于 UDP + QUIC
- 无 TCP 队头阻塞
- 0-RTT 重连
- 连接迁移(切换网络不断连)

---

## 3. QUIC

> 📜 Google, 2013+,IETF QUIC 2021

### 3.1 设计目标

- 解决 TCP 队头阻塞
- 减少连接建立延迟
- 改善丢包恢复
- 连接迁移

### 3.2 核心特性

#### 3.2.1 多流无队头阻塞

```
QUIC 一个连接内多个独立 Stream
Stream A 丢包 → 只影响 Stream A,其他流继续
```

TCP 队头阻塞:

```
TCP 一个流,任何丢包都阻塞后续所有数据
```

#### 3.2.2 0-RTT 重连

首次连接:1 RTT(对比 TCP+TLS 的 3 RTT)
重连:0 RTT(用之前的密钥恢复)

#### 3.2.3 连接迁移

- 连接 ID 而非 IP+Port 标识
- WiFi 切 4G 不影响连接

#### 3.2.4 用户态实现

- 不依赖内核升级
- 迭代快

### 3.3 应用

- HTTP/3
- gRPC over QUIC(实验)
- Cloudflare / Google / Facebook 大规模部署

## 4. RPC

### 4.1 RPC 模型

> Remote Procedure Call:让远程调用像本地函数调用一样

```
Client                Server
  ↓                    ↓
  stub                stub
  ↓                    ↓
marshal ───网络──→ unmarshal
                     ↓
                   业务
                     ↓
marshal ←──网络─── marshal
  ↓
结果
```

### 4.2 关键问题

1. **序列化**:JSON / Protobuf / Thrift / Avro
2. **传输**:TCP / HTTP/2
3. **服务发现**:注册中心 / DNS
4. **负载均衡**:客户端 LB
5. **错误处理**:超时 / 重试 / 熔断
6. **多路复用**:单连接多请求
7. **流控**:防止压垮下游

### 4.3 同步 vs 异步

```java
// 同步(阻塞)
Response resp = client.call(request);

// 异步(Future)
Future<Response> future = client.callAsync(request);
Response resp = future.get();

// 异步(回调)
client.callAsync(request, new Callback() {
    public void onSuccess(Response resp) { /* ... */ }
    public void onError(Throwable e) { /* ... */ }
});
```

### 4.4 gRPC

> Google 2015,基于 HTTP/2 + Protobuf

```protobuf
// hello.proto
syntax = "proto3";
package hello;

service HelloService {
  rpc SayHello (HelloRequest) returns (HelloResponse);
  rpc StreamHello (stream HelloRequest) returns (stream HelloResponse);
}

message HelloRequest {
  string name = 1;
}

message HelloResponse {
  string message = 1;
}
```

```java
// Server
public class HelloServiceImpl extends HelloServiceGrpc.HelloServiceImplBase {
    @Override
    public void sayHello(HelloRequest req, StreamObserver<HelloResponse> resp) {
        resp.onNext(HelloResponse.newBuilder().setMessage("Hello " + req.getName()).build());
        resp.onCompleted();
    }
}

// Client
ManagedChannel channel = ManagedChannelBuilder.forAddress("localhost", 8080)
    .usePlaintext().build();
HelloServiceGrpc.HelloServiceBlockingStub stub = HelloServiceGrpc.newBlockingStub(channel);
HelloResponse resp = stub.sayHello(HelloRequest.newBuilder().setName("World").build());
```

### 4.5 gRPC 四种调用模式

| 模式 | 含义 |
|------|------|
| Unary | 一请求一响应(常规 RPC) |
| Server Streaming | 一请求多响应(订阅) |
| Client Streaming | 多请求一响应(上传) |
| Bidirectional Streaming | 双向流(实时通信) |

### 4.6 其他 RPC

- **Thrift**:Facebook,二进制 + IDL
- **Dubbo**:阿里,Java 生态
- **brpc**:百度,C++ 高性能
- **Tars**:腾讯,多语言
- **JSON-RPC**:简单,基于 JSON
- **Apache Arrow Flight**:数据分析专用

## 5. 序列化

### 5.1 对比

| 格式 | 类型 | 速度 | 大小 | Schema | 适用 |
|------|------|------|------|--------|------|
| JSON | 文本 | 慢 | 大 | 弱 | Web API |
| XML | 文本 | 慢 | 大 | 弱(DTD) | 老系统 |
| Protobuf | 二进制 | 快 | 小 | 强 | RPC |
| Thrift | 二进制 | 快 | 小 | 强 | RPC |
| Avro | 二进制 | 中 | 小 | 强(schema 携带) | 大数据 |
| MessagePack | 二进制 | 中 | 中 | 弱 | 通用 |
| CBOR | 二进制 | 中 | 中 | 弱 | IoT |

### 5.2 Protobuf

```protobuf
message User {
  int64 id = 1;
  string name = 2;
  repeated string emails = 3;
  map<string, string> metadata = 4;
}
```

- 字段编号:向后兼容(新增字段不影响旧版本)
- 字段类型:变长编码(varint),小整数占少字节
- 不带字段名:序列化紧凑

### 5.3 Avro

```json
{
  "type": "record",
  "name": "User",
  "fields": [
    {"name": "id", "type": "long"},
    {"name": "name", "type": "string"}
  ]
}
```

- Schema 携带在读端解析,无字段编号
- 写端写 Schema,读端对照 Schema
- 适合长期存储(Kafka 默认序列化)

## 6. 服务发现

### 6.1 客户端发现

```
Client → Service Registry → 拿实例列表 → 自己选 → 调用
```

- 客户端需内置 LB 逻辑
- 性能高(少一跳)
- 例子:Eureka + Spring Cloud LoadBalancer

### 6.2 服务端发现

```
Client → Load Balancer (查询 Registry) → 调用
```

- 客户端简单
- 多一跳
- 例子:Envoy + Istio / Nginx + Consul Template

### 6.3 注册中心对比

详见 [[10-协调服务]]。

| 注册中心 | 一致性 | 适用 |
|---------|-------|------|
| ZK | CP | 强一致 |
| etcd | CP | K8s |
| Consul | CP+AP | 多 DC |
| Nacos | AP/CP | 国内主流 |
| Eureka | AP | Spring Cloud Netflix(退役) |

## 8. 工业实践

### 8.1 RPC vs HTTP

| 维度 | RPC (gRPC) | HTTP/REST |
|------|------------|-----------|
| 协议 | HTTP/2 | HTTP/1.1 或 2 |
| 序列化 | Protobuf | JSON |
| 性能 | 高 | 中 |
| 跨语言 | 强(IDL) | 强 |
| 可读性 | 弱(二进制) | 强(JSON) |
| 浏览器支持 | 弱(gRPC-Web) | 强 |
| 适用 | 内部服务 | 对外 API |

### 8.2 内部 vs 外部

- 内部:gRPC / Thrift / Dubbo(性能优先)
- 外部:HTTP/REST / GraphQL(可读性优先)

### 8.3 长连接管理

```java
// gRPC 连接管理
ManagedChannel channel = ManagedChannelBuilder
    .forAddress("service", 8080)
    .usePlaintext()
    .keepAliveTime(30, TimeUnit.SECONDS)      // ping 间隔
    .keepAliveTimeout(10, TimeUnit.SECONDS)   // ping 超时
    .keepAliveWithoutCalls(true)              // 空闲也 ping
    .build();
```

### 8.4 超时与重试

```java
// gRPC 客户端
HelloServiceGrpc.HelloServiceBlockingStub stub = HelloServiceGrpc.newBlockingStub(channel)
    .withDeadlineAfter(5, TimeUnit.SECONDS);

// 重试策略
ManagedChannel channel = ManagedChannelBuilder.forAddress("service", 8080)
    .defaultServiceConfig(Map.of(
        "methodConfig", List.of(Map.of(
            "name", List.of(Map.of("service", "hello.HelloService")),
            "retryPolicy", Map.of(
                "maxAttempts", 3.0,
                "initialBackoff", "0.1s",
                "maxBackoff", "1s",
                "retryableStatusCodes", List.of("UNAVAILABLE", "DEADLINE_EXCEEDED")
            )
        ))
    ))
    .enableRetry()
    .build();
```

## 9. 面试要点

**Q1: TCP 三次握手为什么?**

> 3 次确认双方收发能力正常。2 次:Server 无法确认 Client 收到 SYN+ACK,可能半连接。4 次:第 4 次 ACK 可在数据包中携带,没必要单独发。

**Q2: HTTP/2 解决了 HTTP/1.1 什么问题?**

> (1) 多路复用:一个 TCP 连接并发多请求,解决 1.1 队头阻塞(应用层);(2) 二进制分帧:更紧凑;(3) 头部压缩:HPACK 减少冗余;(4) Server Push。但 HTTP/2 仍有 TCP 层队头阻塞(一个流丢包影响所有流),HTTP/3 用 QUIC 解决。

**Q3: QUIC 相比 TCP 的优势?**

> (1) 多流无队头阻塞:一个流丢包不影响其他流;(2) 0-RTT 重连:1 RTT 首次,0 RTT 重连;(3) 连接迁移:连接 ID 而非 IP+Port,WiFi 切 4G 不断连;(4) 用户态实现:迭代快,不依赖内核。

**Q4: gRPC 和 REST 怎么选?**

> 内部服务用 gRPC(性能高、强类型、IDL、多语言);对外 API 用 REST(可读、浏览器友好、生态成熟)。gRPC-Web 桥接但复杂。简单说:微服务间用 gRPC,API 网关对外用 REST。

**Q5: Protobuf 比 JSON 好在哪?**

> (1) 二进制紧凑,体积小 3-10 倍;(2) 解析快 10-100 倍;(3) 强类型 + IDL,跨语言;(4) 字段编号向后兼容。代价:可读性差(二进制),需 .proto 文件。

**Q6: RPC 的核心问题有哪些?**

> (1) 序列化(Protobuf/JSON);(2) 传输(TCP/HTTP2);(3) 服务发现(注册中心);(4) 负载均衡(客户端 LB);(5) 错误处理(超时/重试/熔断);(6) 多路复用(单连接多请求);(7) 流控(防压垮下游)。

**Q7: 同步 RPC 和异步 RPC 怎么选?**

> 同步:简单,适合短耗时(几十 ms 内)操作。异步:适合长耗时(秒级)或高并发场景,避免线程阻塞。生产推荐异步 + Future/Callback,提升吞吐。

**Q8: 服务发现客户端 vs 服务端模式?**

> 客户端:从注册中心拿实例列表,自己选(少一跳,性能高,需客户端 LB 逻辑)。服务端:经过 LB(LB 查注册中心),客户端简单(多一跳,可用 Nginx/Envoy)。Service Mesh 模式是服务端发现的变种(Sidecar 作 LB)。

## 11. 速查表

```
TCP: 三次握手 / 四次挥手 / 流量控制 / 拥塞控制
HTTP/1.1: Keep-Alive, Pipeline (应用层 HoL)
HTTP/2: 二进制 / 多路复用 / HPACK (TCP 层 HoL 仍存在)
HTTP/3: over QUIC, 无 HoL, 0-RTT, 连接迁移

QUIC: UDP + 多流 + TLS 1.3 + 用户态

RPC:
  序列化: Protobuf / Thrift / Avro / JSON
  传输: TCP / HTTP/2
  框架: gRPC / Dubbo / Thrift / brpc / Tars

gRPC 四模式:
  Unary / Server Streaming / Client Streaming / Bidirectional

序列化对比:
  Protobuf: 快 + 小, RPC
  Avro: schema 携带, Kafka
  JSON: 可读, Web API

选型:
  内部: gRPC (Protobuf + HTTP/2)
  外部: REST / GraphQL (JSON)
  实时: WebSocket / SSE / gRPC Streaming
```
