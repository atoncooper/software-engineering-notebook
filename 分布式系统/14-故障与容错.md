## 0. 故障是常态,不是异常

分布式系统的第一性原理:**任何组件都可能故障,且故障形式不可预知**。

- 网络分区(光缆被挖断、BGP 路由错误)
- 节点崩溃(电源、硬件、内核 panic)
- 节点假死(GC STW、CPU 飙高、磁盘满)
- 时钟漂移(NTP 失败、闰秒)
- 软件缺陷(内存泄漏、死锁、配置错误)
- 人为误操作(误删库、误改配置)

单机系统的"故障 = 进程退出",但分布式系统的"故障"还包括:

- **Byzantine 故障**:节点撒谎、伪造消息(本章不重点讨论,详见 [[05-共识-拜占庭共识]])
- **Omission 故障**:消息丢失或延迟
- **Timing 故障**:时钟漂移导致超时判断错误
- **Performance 故障**:节点慢但未崩溃(slow but alive)

容错设计的核心目标:**在故障发生时,系统仍能提供服务(可用性)且数据不丢不错(一致性)**。

## 1. 定义与动机

### 1.1 故障分类

#### 1.1.1 故障模型 (Failure Models)

| 模型 | 行为 | 应对 |
|------|------|------|
| **Crash-Stop** | 进程崩溃后不再恢复 | 重启 + 状态恢复 |
| **Crash-Recovery** | 崩溃后可恢复(可能有状态丢失) | WAL + Snapshot |
| **Omission** | 消息丢失/拒绝响应 | 重传 + 超时 |
| **Timing** | 响应延迟超预期 | 超时检测 + Phi Accrual |
| **Byzantine** | 任意行为(撒谎、伪造) | $n \ge 3f+1$ 共识 |

#### 1.1.2 故障域 (Failure Domain)

工业上按"故障影响范围"划分:

| 域 | 范围 | 典型故障 |
|---|------|---------|
| **节点** | 单机 | 进程崩溃、磁盘坏 |
| **机架** | 一排机器 | 机架电源、Top-of-Rack 交换机 |
| **可用区 (AZ)** | 数据中心内独立故障域 | 制冷故障、火灾 |
| **区域 (Region)** | 地理区域 | 大规模断网、自然灾害 |
| **全球** | 跨 Region | DNS 故障、BGP 全局错误 |

容错的核心原则:**避免单点故障 + 跨故障域分布**。

### 1.2 可用性指标

| 指标 | 含义 | 公式 |
|------|------|------|
| **MTBF** | Mean Time Between Failures,平均故障间隔 | 总运行时间 / 故障次数 |
| **MTTR** | Mean Time To Recover,平均恢复时间 | 总宕机时间 / 故障次数 |
| **Availability** | 可用性 | MTBF / (MTBF + MTTR) |
| **RPO** | Recovery Point Objective,数据丢失容忍 | 时间窗口 |
| **RTO** | Recovery Time Objective,恢复时间目标 | 时间窗口 |

可用性等级:

| 等级 | 可用性 | 年宕机时间 |
|------|--------|----------|
| 2 个 9 | 99% | 3.65 天 |
| 3 个 9 | 99.9% | 8.76 小时 |
| 4 个 9 | 99.99% | 52.6 分钟 |
| 5 个 9 | 99.999% | 5.26 分钟 |
| 6 个 9 | 99.9999% | 31.5 秒 |

> ⚠️ **易错**:5 个 9 不等于"每天宕机 1 秒",而是"全年累计 5 分钟"。可用性是年度统计,不是瞬时。

### 1.3 RPO / RTO 业务矩阵

| 业务等级 | RPO | RTO | 示例 |
|---------|-----|-----|------|
| L0 核心 | 0 | < 1min | 支付核心、交易撮合 |
| L1 重要 | < 1min | < 5min | 订单、库存、用户中心 |
| L2 一般 | < 5min | < 30min | 内容、社交、推荐 |
| L3 边缘 | < 1h | < 4h | 日志、报表、内部工具 |

## 2. 原理与算法

### 2.1 脑裂 (Split-Brain)

#### 2.1.1 现象

网络分区导致集群分成两个互不通信的子集,各自认为对方已死,各自选出 Leader,产生**双主**:

```
原集群: [A, B, C, D, E]  Leader=A
分区1: [A, B]            Leader=A (原Leader继续)
分区2: [C, D, E]         Leader=C (重新选举,3/5多数)

→ A 和 C 同时认为自己是 Leader
→ 客户端可能写入任意一方
→ 分区恢复后数据冲突
```

#### 2.1.2 脑裂的危害

- 双写:两个 Leader 各自接受写入,数据不一致
- 数据丢失:分区恢复后,某方的写入被覆盖
- 资源争抢:共享资源(如 IP、存储)被双方同时持有

#### 2.1.3 防御机制

**1. Quorum (多数派)**

Raft / Paxos / ZAB 都要求 Quorum:$N = 2f+1$,容忍 $f$ 个节点故障,需 $f+1$ 个节点存活才能继续。少数派分区无法形成 Quorum,自动停止服务。

```
5 节点集群分区:
  分区1 [A, B] (2/5) < 3 → 无法选举,停止服务
  分区2 [C, D, E] (3/5) ≥ 3 → 选举 C,继续服务
```

**2. Fencing Token**

详见 [[11-分布式锁]]。即使双主发生,Fencing 保证只有最新 token 的写入生效。

**3. Witness / Tiebreaker**

偶数节点集群(如 4 节点)分区时 2-2 平局,Witness 节点(轻量第三方)打破平局:

```
4 节点 + Witness:
  分区 [A, B] vs [C, D] (2-2 平局)
  Witness 在哪一侧,哪一侧获胜
```

**4. STONITH (Shoot The Other Node In The Head)**

HA 集群中,确认对方死亡前先"杀死"对方(切电源、fence),防止双活:

```
A 检测 B 故障 → A 通过 IPMI 关闭 B 电源 → A 确认 B 真死 → A 接管
```

**5. Lease / 租约**

Leader 持有租约,租约期内才能服务。租约过期后必须续约才能继续。分区时少数派 Leader 无法续约,自动降级。

```java
public class LeaseBasedLeader {
    private long leaseExpiry;
    private final EtcdClient etcd;

    public boolean isLeader() {
        return System.currentTimeMillis() < leaseExpiry;
    }

    public void renewLease() {
        // 通过 etcd 续约,需要 Quorum
        long newLease = etcd.renew(leaseKey);
        if (newLease > 0) {
            leaseExpiry = System.currentTimeMillis() + newLease;
        } else {
            leaseExpiry = 0;  // 失去 Leader 身份
        }
    }
}
```

### 2.2 多活 (Multi-Site / Multi-Active)

#### 2.2.1 同城双活

同一城市两个 AZ,通过专线互联,延迟 < 1ms:

- 数据强同步(同步复制)
- 写入任一 AZ,实时同步到另一 AZ
- 一个 AZ 故障,另一个 AZ 接管,RPO=0,RTO<1min

```
        用户
        ↓
   全局 LB (DNS / Anycast)
   /         \
AZ-1         AZ-2
[App] ←同步→ [App]
 ↓             ↓
[DB Master] ←同步复制→ [DB Standby]
```

#### 2.2.2 异地多活

跨城市/跨国家部署,延迟 10~100ms:

- 数据异步复制(强同步会拖垮写入)
- 每个站点都能独立服务
- 故障时切换 DNS / 流量入口
- RPO > 0(可能丢失最近几秒数据)

#### 2.2.3 单元化 (LDC - Logic Data Center)

> 📚 阿里支付宝单元化架构

核心思想:**把用户按 ID 哈希到固定单元,每个单元独立完整(应用 + 数据)**。

```
用户请求 → 路由层 (按 user_id 取模) → 单元 R1 / R2 / R3 / R4
                                      ↓
                                  [完整服务栈]
                                  ↓
                              [本地数据库]

跨单元数据通过:
  - 异步消息同步(弱一致)
  - 中心化服务(全局账户、风控)
```

单元化的关键约束:

- **路由不可变**:用户一旦绑定到某单元,数据不迁移(否则需全量同步)
- **跨单元调用最小化**:同单元闭环,跨单元走异步
- **全局数据集中**:全局 ID、风控等少量数据放中心

#### 2.2.4 异地多活的复制方案

| 方案 | 一致性 | 延迟 | 复杂度 |
|------|-------|------|-------|
| 异步复制 | 最终一致 | 秒级 | 低 |
| 半同步 | 至少一个从库确认 | 中 | 中 |
| 强同步(同步复制) | 强一致 | 高 | 高 |
| Spanner TrueTime | 外部一致 | 中(Commit Wait) | 极高 |
| CockroachDB Multi-Region | 强一致 | 取决于配置 | 高 |

### 2.3 故障检测 (Failure Detection)

#### 2.3.1 心跳超时

最朴素的检测:节点间定期心跳,超时即认为死亡。

缺陷:

- 超时阈值难定:太短误判(网络抖动),太长发现慢
- 网络抖动导致误判 → 频繁切换 → 雪崩

#### 2.3.2 Phi Accrual (Cassandra/Akka)

> 📜 Hayashibara et al., 2004 — *The φ Accrual Failure Detector*

不输出"死/活"二元结果,而是输出** suspicion level φ**:$\phi = -\log_{10}(P(t_{now} - t_{last}) \mid \text{历史心跳间隔})$

- φ 越大,越可能是真死
- 应用根据场景设阈值(如 φ=8 表示"99.99999% 概率已死")

```python
import math
from collections import deque

class PhiAccrualDetector:
    def __init__(self, window_size=1000):
        self.history = deque(maxlen=window_size)
        self.last_heartbeat = None

    def heartbeat(self):
        now = time.time()
        if self.last_heartbeat:
            self.history.append(now - self.last_heartbeat)
        self.last_heartbeat = now

    def phi(self):
        if len(self.history) < 10:
            return 0.0
        mean = sum(self.history) / len(self.history)
        std = (sum((x - mean) ** 2 for x in self.history) / len(self.history)) ** 0.5
        delta = time.time() - self.last_heartbeat
        # 假设心跳间隔服从正态分布
        p = 1 - norm_cdf(delta, mean, std)
        return -math.log10(p)
```

#### 2.3.3 Gossip 故障检测

Cassandra 用 Gossip 协议传播节点状态:

- 每节点定期 Gossip 自己的状态(ALIVE / SUSPECT / DEAD)
- 接收者合并并传播
- SUSPECT 状态经过一段时间仍无心跳 → DEAD

### 2.4 容错模式

#### 2.4.1 主从切换 (Active-Standby)

```
正常: Master(主) ←复制→ Slave(备)
故障: Master 挂 → 提升 Slave → 客户端重连
```

关键问题:

- **何时切换**:故障检测 + Quorum 投票
- **如何切换**:VIP 漂移 / DNS 切换 / 客户端重连
- **如何防止脑裂**:Quorum + Fencing

#### 2.4.2 多主 (Active-Active)

多个节点都可写,冲突在合并时解决:

- Dynamo / Cassandra:Last-Write-Wins 或 CRDT
- CouchDB:应用层冲突解决
- Galera:同步复制 + 认证冲突检测

#### 2.4.3 故障注入 (Chaos Engineering)

Netflix Chaos Monkey 思路:主动注入故障验证容错:

- 随机杀节点
- 网络延迟 / 分区
- 磁盘故障
- 时钟漂移

详见 [[13-治理-可观测性与混沌工程]]。

#### 2.4.4 熔断 / 限流 / 降级

| 模式 | 触发 | 行为 |
|------|------|------|
| **熔断 (Circuit Breaker)** | 错误率 > 阈值 | 直接拒绝请求,不调下游 |
| **限流 (Rate Limit)** | QPS > 阈值 | 排队或拒绝 |
| **降级 (Degradation)** | 下游不可用 | 返回缓存/默认值 |
| **隔离 (Bulkhead)** | 某资源耗尽 | 限制影响范围 |

```java
// Resilience4j 熔断器
CircuitBreakerConfig config = CircuitBreakerConfig.custom()
    .failureRateThreshold(50)              // 50% 错误率触发
    .slowCallRateThreshold(50)             // 50% 慢调用触发
    .slowCallDurationThreshold(Duration.ofSeconds(2))
    .waitDurationInOpenState(Duration.ofSeconds(30))
    .slidingWindowSize(10)
    .build();
CircuitBreaker cb = CircuitBreaker.of("payment", config);

Supplier<PayResponse> protected = CircuitBreaker.decorateSupplier(
    cb, () -> payService.pay(req));
```

### 2.5 超时与重试

#### 2.5.1 超时层次

```
客户端 → 网关 → 服务 A → 服务 B → 数据库
   30s     10s     5s       2s       1s
```

原则:**外层 > 内层**,避免外层已超时但内层仍在跑。

#### 2.5.2 重试策略

- **指数退避 (Exponential Backoff)**:$t = b \cdot 2^k + \text{jitter}$
- **抖动 (Jitter)**:加随机量避免同步重试风暴
- **重试上限**:防止无限重试

```java
public <T> T retryWithBackoff(Supplier<T> action, int maxRetries) {
    int attempt = 0;
    while (true) {
        try {
            return action.get();
        } catch (RetryableException e) {
            attempt++;
            if (attempt >= maxRetries) throw e;
            long backoff = (long) (100 * Math.pow(2, attempt));
            long jitter = ThreadLocalRandom.current().nextLong(50);
            sleep(backoff + jitter);
        }
    }
}
```

> ⚠️ **易错**:不是所有错误都可重试。非幂等操作重试可能导致重复扣款;5xx 错误通常可重试,4xx 不可。

## 3. 🎓 学术深度

### 3.1 CAP 与 PACELC 的故障视角

详见 [[02-理论基础]]。CAP 说"分区时 C 和 A 二选一";PACELC 补充"无分区时也要在 L(延迟) 和 C(一致性) 间权衡"。

工程含义:任何分布式系统都有 trade-off,关键是**显式选择**并匹配业务需求。

### 3.2 FLP 不可能性

详见 [[05-共识-问题与FLP]]。FLP 说"异步网络 + 一个节点故障 = 共识不可能"。

工程含义:完全异步(无超时假设)下无法同时保证 safety + liveness。实际系统通过**部分同步假设**(Eventually Stable)绕过。

### 3.3 Byzantine 容错的代价

详见 [[05-共识-拜占庭共识]]。$n \ge 3f+1$,消息复杂度 $O(n^2)$(PBFT)。

工程含义:Byzantine 容错成本高,只在区块链、金融监管等场景用。互联网业务多假设 Crash 故障即可。

### 3.4 故障检测器的分类

> 📜 Chandra & Toueg, 1996 — *Unreliable Failure Detectors*

| 类型 | Completeness | Accuracy |
|------|-------------|----------|
| **Perfect (P)** | 强 | 强 |
| **Strong (S)** | 强 | 弱(最终) |
| **Eventually Strong (◇S)** | 弱(最终) | 弱(最终) |
| **Eventually Perfect (◇P)** | 弱 | 弱 |

共识算法等价性:

- **Perfect FD** → 同步系统,共识 trivial
- **Eventually Strong ◇S** → 异步系统 + ◇S 等价于共识可解(Chandra-Toueg)

Raft / Paxos 隐含使用 ◇S 类 FD(超时检测,最终能正确识别故障)。

### 3.5 Dijkstra 的 Self-Stabilization

> 📜 Dijkstra, 1974 — *Self-stabilizing systems in spite of distributed control*

系统在任意初始状态(包括故障后)经过有限步能自动恢复到合法状态。这是**自愈**的理论基础。

工程应用:

- 协调服务(ZK/etcd)故障恢复后自动重新同步
- Gossip 协议最终一致
- CRDT 自动收敛

## 4. 🏭 工业实战

### 4.1 阿里单元化 (LDC)

支付宝双 11 的核心架构:

```
路由层: 按 user_id 取模
  user_id % 4 = 0 → 单元 R1 (上海)
  user_id % 4 = 1 → 单元 R2 (上海)
  user_id % 4 = 2 → 单元 R3 (深圳)
  user_id % 4 = 3 → 单元 R4 (深圳)

每个单元:
  - 完整应用栈(支付、订单、账户)
  - 本地数据库(只存自己单元用户数据)
  - 本地缓存、本地消息队列

跨单元:
  - 异步消息(最终一致)
  - 中心化服务(全局账户、风控)

故障切换:
  - R1 整体故障 → R1 流量切到 R5(备用单元)
  - R1 数据从 R5 异步副本恢复
```

优势:

- 跨城延迟消除(本地闭环)
- 单元故障隔离(不影响其他)
- 横向扩展(加单元即可)

约束:

- 路由不可变(user 永远在某单元)
- 跨单元业务弱一致
- 中心化服务成为瓶颈(需单独优化)

Netflix AWS 部署:

- 多 Region 独立部署(美东、美西、欧、亚)

- 跨 Region 用异步复制(Cassandra 多 DC、DynamoDB Global Table)

### 4.5 Kafka 高可用

- **Replica**:每个 partition 有 N 个副本
- **ISR (In-Sync Replicas)**:与 Leader 同步的副本集合
- **Controller**:集群元数据管理,本身高可用(ZK 或 KRaft)
- **Leader Election**:ISR 中选新 Leader

```
Partition-1:
  Leader: Broker-1
  ISR: [Broker-1, Broker-2, Broker-3]
  OSR: [Broker-4]  (落后)

Leader Broker-1 故障:
  Controller 从 ISR 选 Broker-2 为新 Leader
  ISR 变为 [Broker-2, Broker-3]
```

关键配置:

- `acks=all`:写需所有 ISR 确认,数据不丢
- `min.insync.replicas=2`:至少 2 个 ISR 才允许写
- `unclean.leader.election.enable=false`:禁止 OSR 当 Leader(避免数据丢失)

### 4.6 K8s 故障容错

K8s 内建多层级容错:

| 层 | 机制 |
|---|------|
| Pod | restartPolicy + liveness/readiness probe |
| Deployment | replicas + 滚动更新 |
| Node | node-controller + 自动驱逐 |
| AZ | podAntiAffinity 跨 AZ 调度 |
| Region | Multi-cluster (KubeFed / Cluster API) |

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment
spec:
  replicas: 6
  template:
    spec:
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            - labelSelector:
                matchLabels:
                  app: payment
              topologyKey: topology.kubernetes.io/zone  # 跨 AZ
      containers:
        - name: payment
          livenessProbe:
            httpGet: { path: /health, port: 8080 }
            periodSeconds: 10
            failureThreshold: 3
          readinessProbe:
            httpGet: { path: /ready, port: 8080 }
            periodSeconds: 5
```

## 5. 面试要点

### 5.1 高频问答

**Q1: 什么是脑裂?如何避免?**

> 网络分区导致集群分裂成多个子集,各自选主产生双主。避免方式:(1) Quorum 多数派(Raft/Paxos);(2) Fencing Token;(3) Witness 节点(偶数集群);(4) STONITH 物理隔离;(5) Lease 租约(过期自动降级)。

**Q2: RPO 和 RTO 是什么?举例说明。**

> RPO(Recovery Point Objective):数据丢失容忍量,如"丢失最近 1 分钟数据可接受"。RTO(Recovery Time Objective):恢复时间目标,如"故障后 5 分钟内恢复服务"。金融核心系统 RPO=0(不丢数据)、RTO<1min;日志系统 RPO=1h、RTO<4h。

**Q3: 同城双活和异地多活的区别?**

> 同城双活:同城市两个 AZ,延迟 < 1ms,可强同步,RPO=0。异地多活:跨城市,延迟 10~100ms,只能异步,RPO>0。前者追求强一致,后者追求容灾范围。

**Q4: 单元化是什么?为什么需要?**

> 单元化(LDC)是把用户按 ID 哈希分到固定单元,每单元独立完整(应用+数据)。需要的原因:(1) 消除跨城延迟(本地闭环);(2) 故障隔离(单单元故障不影响其他);(3) 横向扩展(加单元即可)。代价:跨单元业务弱一致、路由不可变。

**Q5: Quorum 为什么能防止脑裂?**

> Quorum 要求多数派(N/2+1)才能形成决策。网络分区时,只有一侧能达到多数派,另一侧少数派无法选举 Leader,自动停止服务。少数派的存在保证不会两个子集都达到多数派(不可能两个 ≥N/2+1 的子集不相交)。

**Q6: 心跳超时和 Phi Accrual 的区别?**

> 心跳超时是二元判断(超时=死),阈值难定,易误判。Phi Accrual 输出 suspicion level φ(连续值),根据历史心跳间隔分布动态调整,允许应用按场景设阈值。Cassandra、Akka 用 Phi Accrual,误判率显著降低。

**Q7: 如何设计一个高可用 MySQL 集群?**

> (1) 一主多从,半同步复制(至少一个 slave 确认);(2) MGR / Orchestrator 自动故障切换;(3) 跨 AZ 部署 slave;(4) ProxySQL / Vitess 路由层;(5) 定期演练故障切换;(6) 备份 + 异地冷备(PITR)。RPO=0(半同步)、RTO<30s(自动切换)。

**Q8: 熔断、限流、降级的区别?**

> 熔断:错误率超阈值时直接拒绝,保护下游;限流:QPS 超阈值时排队或拒绝,保护自身;降级:下游不可用时返回缓存/默认值,保证核心功能。三者互补:限流是入口控制,熔断是异常隔离,降级是兜底保障。

### 5.2 易错点 ⚠️

1. **"Quorum 集群不能分区脑裂"** — 是。但偶数节点集群(4 节点)2-2 分区时无法形成 Quorum,双方都停摆,需要 Witness。
2. **"主从复制就是高可用"** — 错。需要自动故障切换机制(Manager/Orchestrator),否则主挂了还要人工干预,RTO 极长。
3. **"同城双活就是同步复制"** — 不一定。同步复制影响写入性能,很多系统用半同步(至少一个 slave 确认)折中。
4. **"故障切换越快越好"** — 错。太快会误切换(网络抖动),导致不必要的服务中断。需要"确认-等待-切换"的稳态流程。
5. **"多 AZ = 多活"** — 不一定。多 AZ 部署但流量只打一个 AZ,另一个只是热备,叫"主从"而非"多活"。

## 9. 速查表 (Cheat Sheet)

```
故障等级与方案:
  节点故障 → 重启 + WAL 恢复 + 副本接管
  机架故障 → 跨机架副本 + Rack-Aware
  AZ 故障 → 跨 AZ 部署 + 自动切换 (同城双活)
  Region 故障 → 跨 Region 异步复制 + DNS 切换 (异地多活)
  全球故障 → 多云部署 + Anycast DNS

脑裂防御组合:
  必选: Quorum (N=2f+1) + Fencing Token
  偶数集群: + Witness
  关键基础设施: + STONITH (物理隔离)

RPO/RTO 设计:
  RPO=0 → 同步复制 / Quorum
  RPO<1min → 半同步 + 快速切换
  RPO<5min → 异步复制 + 监控告警
  RTO<1min → 自动切换
  RTO<5min → 半自动(人工确认)
  RTO<30min → 人工操作 + 文档

容错原语:
  Quorum / Lease / Fencing / Watchdog / Circuit Breaker
  / Rate Limiter / Bulkhead / Backoff / Retry / Chaos
```
