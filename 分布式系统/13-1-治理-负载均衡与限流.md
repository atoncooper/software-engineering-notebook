## 0. 治理的本质

微服务/分布式系统中,服务实例多、调用链长,需要"治理"来保证:

- **流量合理分布**:负载均衡
- **流量不超载**:限流
- **故障不扩散**:熔断、隔离
- **请求可追溯**:可观测性
- **架构可演进**:Service Mesh

本章梳理负载均衡与限流,后续章节深入可观测性和 Service Mesh。

## 1. 负载均衡

### 1.1 维度

- **服务端 LB**:客户端 → LB → 后端实例(Nginx / HAProxy / LVS / SLB)
- **客户端 LB**:客户端自己选后端实例(gRPC、Spring Cloud LoadBalancer、Dubbo)
- **服务网格 LB**:Sidecar 代理流量(Envoy / Istio)

### 1.2 算法

#### 1.2.1 轮询 (Round Robin)

```java
List<Server> servers = ...;
AtomicInteger idx = new AtomicInteger(0);
Server next = servers.get(idx.getAndIncrement() % servers.size());
```

简单,均匀。问题:不考虑实例性能差异。

#### 1.2.2 加权轮询 (Weighted Round Robin)

```
Server A (weight=5) - 性能强
Server B (weight=3) - 性能中
Server C (weight=2) - 性能弱
→ 按权重比例分配
```

#### 1.2.3 最少连接 (Least Connections)

```
选当前活跃连接数最少的实例
适合长连接 (WebSocket / gRPC)
```

#### 1.2.4 一致性哈希

详见 [[07-分片与路由]]。同一 client/key 落同实例,适合有状态服务。

#### 1.2.5 P2C (Power of Two Choices)

> 📜 《The Power of Two Choices in Randomized Load Balancing》

随机选 2 个实例,选连接数较少的。比"完全随机"均匀性提升指数级,且实现简单。gRPC 默认 P2C。

#### 1.2.6 EWMA (Exponentially Weighted Moving Average)

按 RTT 加权,RTT 短的实例优先。Finagle、Linkerd 用 EWMA。

### 1.3 工业实现

#### 1.3.1 L4 vs L7

- **L4**(传输层):基于 IP/端口,LVS、F5,性能极高(百万 QPS)
- **L7**(应用层):基于 HTTP/URL/Header,Nginx、Envoy,功能丰富

```
Client → L4 LB (LVS) → L7 LB (Nginx) → 应用实例
         ↑                ↑
       百万 QPS        七层路由
```

#### 1.3.2 DNS 负载均衡

```
www.example.com → A 记录返回多个 IP
                → 客户端随机选一个
```

- 简单、跨 Region
- DNS 缓存导致切换慢
- 不感知后端健康

#### 1.3.3 Anycast

```
同一 IP 在多个 Region BGP 宣告
客户端路由到最近的 Region
```

- 全球 LB
- 需 BGP 权限
- Cloudflare、Google 用 Anycast

#### 1.3.4 gRPC 客户端 LB

```python
# gRPC 内置客户端 LB
channel = grpc.insecure_channel(
    'dns:///service:8080',
    options=[
        ('grpc.lb_policy_name', 'round_robin'),
        ('grpc.service_config', json.dumps({
            "loadBalancingConfig": [{"round_robin": {}}]
        }))
    ]
)
```

#### 1.3.5 Spring Cloud LoadBalancer

```java
@Bean
public ReactorLoadBalancer<ServiceInstance> reactorLoadBalancer(
        Environment env, LoadBalancerClientFactory factory) {
    String name = env.getProperty(LoadBalancerClientFactory.PROPERTY_NAME);
    return new RoundRobinLoadBalancer(
        factory.getLazyProvider(name, ServiceInstanceListSupplier.class), name);
}
```

## 2. 限流

### 2.1 为什么需要限流

- 保护后端:防止雪崩
- 公平性:多租户隔离
- SLA:保证核心接口稳定
- 成本:防止流量突增(云账单)

### 2.2 算法

#### 2.2.1 计数器 (Fixed Window)

```
每秒一个计数器,超过阈值拒绝
窗口切换时计数归零
```

问题:**临界突刺**。窗口切换前后各来一半流量,瞬时 2x。

```java
public class FixedWindowRateLimiter {
    private final int limit;
    private final AtomicInteger counter = new AtomicInteger(0);
    private volatile long windowStart = System.currentTimeMillis();

    public synchronized boolean tryAcquire() {
        long now = System.currentTimeMillis();
        if (now - windowStart > 1000) {
            counter.set(0);
            windowStart = now;
        }
        return counter.incrementAndGet() <= limit;
    }
}
```

#### 2.2.2 滑动窗口 (Sliding Window)

```
把 1s 切成 N 个子窗口(如 10 个 100ms)
滑动统计最近 1s 的总数
```

平滑了临界突刺。

```java
public class SlidingWindowRateLimiter {
    private final int limit;
    private final int windowSizeMs = 100;  // 子窗口
    private final int subWindowCount = 10;
    private final int[] counters = new int[subWindowCount];
    private long windowStart = System.currentTimeMillis();

    public synchronized boolean tryAcquire() {
        long now = System.currentTimeMillis();
        long elapsed = now - windowStart;
        int slide = (int) (elapsed / windowSizeMs);
        if (slide >= subWindowCount) {
            // 全部归零
            Arrays.fill(counters, 0);
            windowStart = now;
        } else {
            // 滑动 slide 个子窗口
            for (int i = 0; i < slide; i++) {
                counters[i % subWindowCount] = 0;
            }
            windowStart += slide * windowSizeMs;
        }
        int currentIdx = (int) ((now - windowStart) / windowSizeMs) % subWindowCount;
        int total = Arrays.stream(counters).sum();
        if (total >= limit) return false;
        counters[currentIdx]++;
        return true;
    }
}
```

#### 2.2.3 漏桶 (Leaky Bucket)

```
请求以任意速度进入桶
桶以恒定速度漏出(处理)
桶满则拒绝
```

- 平滑输出
- 不能应对突发

```java
public class LeakyBucketRateLimiter {
    private final int capacity;       // 桶容量
    private final int leakRatePerSec; // 漏出速率
    private final AtomicInteger water = new AtomicInteger(0);
    private volatile long lastLeakTime = System.currentTimeMillis();

    public synchronized boolean tryAcquire() {
        long now = System.currentTimeMillis();
        int leaked = (int) ((now - lastLeakTime) / 1000.0 * leakRatePerSec);
        if (leaked > 0) {
            water.updateAndGet(w -> Math.max(0, w - leaked));
            lastLeakTime = now;
        }
        if (water.get() < capacity) {
            water.incrementAndGet();
            return true;
        }
        return false;
    }
}
```

#### 2.2.4 令牌桶 (Token Bucket)

```
以恒定速率向桶里放令牌(最多桶容量)
请求消耗令牌
无令牌则拒绝
```

- 允许突发(桶满时一次性消耗多个令牌)
- 工业最常用

```java
public class TokenBucketRateLimiter {
    private final int capacity;       // 桶容量(允许突发)
    private final int refillRatePerSec;
    private final AtomicInteger tokens;
    private volatile long lastRefillTime = System.currentTimeMillis();

    public TokenBucketRateLimiter(int capacity, int refillRatePerSec) {
        this.capacity = capacity;
        this.refillRatePerSec = refillRatePerSec;
        this.tokens = new AtomicInteger(capacity);
    }

    public synchronized boolean tryAcquire(int permits) {
        long now = System.currentTimeMillis();
        int refilled = (int) ((now - lastRefillTime) / 1000.0 * refillRatePerSec);
        if (refilled > 0) {
            tokens.updateAndGet(t -> Math.min(capacity, t + refilled));
            lastRefillTime = now;
        }
        if (tokens.get() >= permits) {
            tokens.addAndGet(-permits);
            return true;
        }
        return false;
    }
}
```

#### 2.2.5 漏桶 vs 令牌桶

| 维度 | 漏桶 | 令牌桶 |
|------|------|-------|
| 输出 | 恒定 | 允许突发 |
| 实现 | 复杂 | 简单 |
| 适用 | 严格平滑 | 一般限流 |
| 工业 | 流量整形 | API 限流 |

#### 2.2.6 分布式限流(Redis)

```lua
-- Redis Lua 实现令牌桶
local key = KEYS[1]
local capacity = tonumber(ARGV[1])
local refill_rate = tonumber(ARGV[2])
local now = tonumber(ARGV[3])
local permits = tonumber(ARGV[4])

local bucket = redis.call('HMGET', key, 'tokens', 'last_time')
local tokens = tonumber(bucket[1]) or capacity
local last_time = tonumber(bucket[2]) or now

local delta = math.max(0, now - last_time)
local refilled = math.min(capacity, tokens + delta * refill_rate / 1000)

if refilled >= permits then
    refilled = refilled - permits
    redis.call('HMSET', key, 'tokens', refilled, 'last_time', now)
    redis.call('PEXPIRE', key, 60000)
    return 1
else
    return 0
end
```

### 2.3 限流维度

- **全局**:全集群限流
- **接口级**:每接口独立阈值
- **用户级**:per-user QPS
- **IP 级**:per-IP(防爬虫)
- **租户级**:多租户隔离

### 2.4 限流位置

```
入口网关(Nginx / API Gateway)
  ↓ 限流 1: 全局粗粒度
服务实例(Filter / Interceptor)
  ↓ 限流 2: 接口细粒度
下游调用(Client Side)
  ↓ 限流 3: 防止打爆下游
```

### 2.5 工业实现

#### 2.5.1 Sentinel (阿里)

```java
@SentinelResource(value = "queryOrder", blockHandler = "blockHandler")
public Order queryOrder(Long orderId) { /* ... */ }

public Order blockHandler(Long orderId, BlockException ex) {
    return Order.degraded();  // 降级
}
```

支持 QPS 限流、并发线程数限流、熔断、热点参数限流、系统自适应限流。

#### 2.5.2 Resilience4j

```java
RateLimiterConfig config = RateLimiterConfig.custom()
    .limitForPeriod(100)
    .limitRefreshPeriod(Duration.ofSeconds(1))
    .timeoutDuration(Duration.ofMillis(100))
    .build();
RateLimiter limiter = RateLimiter.of("orderQuery", config);

Supplier<Order> protected = RateLimiter.decorateSupplier(limiter,
    () -> queryOrder(orderId));
```

#### 2.5.3 Nginx 限流

```nginx
http {
    limit_req_zone $binary_remote_addr zone=api:10m rate=100r/s;

    server {
        location /api/ {
            limit_req zone=api burst=200 nodelay;
            limit_req_status 429;
            proxy_pass http://backend;
        }
    }
}
```

### 2.6 自适应限流

> 📜 《Adaptive Concurrency Control》

不设固定阈值,根据系统指标(CPU、RTT、错误率)自动调整:

- BBR (Google):基于 CPU + RTT
- Concurrency Limits (Netflix):基于 Little's Law
- Sentinel 系统自适应:基于负载

```java
// Sentinel 系统自适应限流
SystemRule rule = new SystemRule();
rule.setHighestSystemLoad(2.0);   // CPU load 阈值
rule.setHighestCpuUsage(0.6);     // CPU 使用率
rule.setAvgRt(10);                 // 平均 RT (ms)
rule.setQps(1000);                 // 全局 QPS
rule.setMaxThread(100);            // 最大线程
SystemRuleManager.loadRules(Collections.singletonList(rule));
```

## 3. 熔断与降级

### 3.1 熔断器 (Circuit Breaker)

```
状态机:
  Closed (正常)
    ↓ 错误率 > 阈值
  Open (熔断,直接拒绝)
    ↓ 等待时间到
  Half-Open (半开,放少量请求测试)
    ↓ 成功 → Closed
    ↓ 失败 → Open
```

```java
// Resilience4j
CircuitBreakerConfig config = CircuitBreakerConfig.custom()
    .failureRateThreshold(50)
    .slowCallRateThreshold(50)
    .slowCallDurationThreshold(Duration.ofSeconds(2))
    .waitDurationInOpenState(Duration.ofSeconds(30))
    .slidingWindowSize(10)
    .minimumNumberOfCalls(5)
    .build();
CircuitBreaker cb = CircuitBreaker.of("payment", config);

Supplier<PayResponse> protected = CircuitBreaker.decorateSupplier(cb,
    () -> payService.pay(req));
```

### 3.2 降级策略

| 策略 | 含义 |
|------|------|
| **返回默认值** | 推荐不可用时返回空列表 |
| **返回缓存** | DB 异常时返回缓存值 |
| **简化逻辑** | 跳过非核心步骤 |
| **异步重试** | 失败入队,稍后重试 |
| **拒绝服务** | 直接返回错误,保护核心 |

### 3.3 隔离 (Bulkhead)

```
线程池隔离:
  服务 A 用线程池 1 (50 线程)
  服务 B 用线程池 2 (20 线程)
  → 服务 B 慢不会拖垮服务 A

信号量隔离:
  每服务一个信号量,超过则拒绝
```

Hystrix、Resilience4j、Sentinel 都支持 Bulkhead。

## 4. 面试要点

**Q1: 负载均衡算法有哪些?怎么选?**

> 轮询(均匀)、加权轮询(考虑性能差异)、最少连接(长连接)、一致性哈希(有状态)、P2C(随机选 2 取优)、EWMA(RTT 加权)。无状态服务用轮询/P2C,有状态用一致性哈希,长连接用最少连接。

**Q2: 限流算法有哪些?**

> 计数器(简单,有临界突刺)、滑动窗口(平滑)、漏桶(恒定输出,不应对突发)、令牌桶(允许突发,最常用)。生产推荐令牌桶 + 滑动窗口组合。

**Q3: 令牌桶和漏桶的区别?**

> 令牌桶:桶里放令牌,请求消耗令牌,允许突发(桶满时一次性消耗多个)。漏桶:请求进桶,恒定速率漏出,输出平滑。令牌桶允许突发,漏桶严格平滑。工业 API 限流用令牌桶,流量整形用漏桶。

**Q4: 分布式限流怎么做?**

> 单机限流不够时用 Redis 集中限流:Lua 原子操作 + 令牌桶。每请求一次 Redis,Redis 是瓶颈,可分片(每用户一个 key)。或用 Sentinel Cluster 模式(token server 集中分配)。

**Q5: 熔断器状态机?**

> Closed(正常,错误率超阈值转 Open)→ Open(熔断,直接拒绝,等待时间到转 Half-Open)→ Half-Open(放少量请求测试,成功转 Closed,失败转 Open)。保护下游,快速失败。

**Q6: 限流和熔断的区别?**

> 限流是入口控制,主动预防(防止自己被压垮)。熔断是异常隔离,被动响应(下游不可用时保护自己)。限流是"我不能处理这么多",熔断是"下游不行,我不调用"。

**Q7: P2C 是什么?为什么比随机好?**

> Power of Two Choices:随机选 2 个实例,选连接数少的。比"完全随机"均匀性提升指数级,因为"两个都满"的概率是 $p^2$(p 是单实例满的概率)。gRPC 默认 P2C。

**Q8: 限流维度怎么设计?**

> 全局(防总流量)、接口(保护慢接口)、用户(per-user 公平)、IP(防爬虫)、租户(多租户隔离)。组合用:全局粗 + 接口细 + 用户公平。
