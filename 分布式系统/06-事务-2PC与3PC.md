## 6.1 分布式事务问题定义

### 6.1.1 问题

> **分布式事务**（Distributed Transaction）：跨多个节点（或多个资源管理器）的操作需满足 ACID——要么全部成功提交，要么全部回滚。

### 6.1.2 ACID 在分布式下的挑战

| 性质 | 单机 | 分布式挑战 |
|------|------|-----------|
| **Atomicity** | WAL + Undo | 跨节点协调，部分失败 |
| **Consistency** | 约束检查 | 跨节点约束难统一 |
| **Isolation** | 锁/MVCC | 跨节点锁开销大 |
| **Durability** | fsync | 跨节点持久化协调 |

### 6.1.3 分布式事务分类

| 类型 | 说明 | 典型 |
|------|------|------|
| **跨数据库** | 同一应用跨多个 DB | 转账（扣款 DB + 入账 DB） |
| **跨服务** | 微服务跨服务调用 | 下单（订单服务 + 库存服务 + 支付服务） |
| **跨资源** | DB + MQ + 缓存 | 写 DB + 发 MQ + 失效缓存 |
| **跨地域** | 跨 DC 数据一致 | 全球数据库 |

## 6.2 2PC（两阶段提交）⭐🔥

📜 [Gray 1978] *Notes on Data Base Operating Systems*
📜 [Lampson, Sturgis 1976] *Crash Recovery in a Distributed Data Storage System*

### 6.2.1 角色

| 角色 | 职责 |
|------|------|
| **Coordinator**（协调者） | 推进两阶段流程，决定 commit/abort |
| **Participant**（参与者） | 执行实际操作，投票 yes/no |

### 6.2.2 两阶段流程 ⭐

```
Phase 1: Prepare (Voting)
─────────────────────────
Client ──► Coordinator
              │
              ├──Prepare──► Participant 1
              ├──Prepare──► Participant 2
              └──Prepare──► Participant 3
                  │             │             │
                  ▼             ▼             ▼
              YES/NO        YES/NO        YES/NO

Phase 2: Commit / Abort
──────────────────────
Coordinator 收集所有响应
  - 全 YES → Commit
  - 任一 NO 或超时 → Abort
              │
              ├──Commit/Abort──► Participant 1
              ├──Commit/Abort──► Participant 2
              └──Commit/Abort──► Participant 3
                  │             │             │
                  ▼             ▼             ▼
              ACK           ACK           ACK
```

### 6.2.3 算法伪代码

```pseudocode
# Coordinator
function two_phase_commit(participants, tx):
    # Phase 1: Prepare
    prepare_log = []
    for each p in participants:
        try:
            resp = p.prepare(tx)
            prepare_log.append(resp)
        except Timeout:
            prepare_log.append(NO)
    
    # 决策
    if all(prepare_log == YES):
        decision = COMMIT
    else:
        decision = ABORT
    
    # 持久化决策（关键！）
    persist(decision_log, tx, decision)
    
    # Phase 2: Commit/Abort
    for each p in participants:
        try:
            p.commit_or_abort(tx, decision)
        except Timeout:
            # 重试
            retry_later(p, tx, decision)
    
    return decision

# Participant
function prepare(tx):
    # 执行操作，但未 commit
    write_to_wal(tx, PREPARED)
    if can_commit:
        return YES
    else:
        return NO

function commit_or_abort(tx, decision):
    if decision == COMMIT:
        write_to_wal(tx, COMMITTED)
        apply(tx)
    else:
        write_to_wal(tx, ABORTED)
        rollback(tx)
    return ACK
```

### 6.2.4 Java 实现示例

```java
// Coordinator
public class TwoPhaseCoordinator {
    private final List<Participant> participants;
    private final DecisionLog decisionLog;  // 必须持久化
    
    public TransactionResult commit(Transaction tx) {
        // Phase 1: Prepare
        List<PrepareResponse> responses = new ArrayList<>();
        for (Participant p : participants) {
            try {
                PrepareResponse resp = p.prepare(tx).get(5, TimeUnit.SECONDS);
                responses.add(resp);
            } catch (TimeoutException e) {
                responses.add(PrepareResponse.NO);  // 超时视为 NO
            } catch (Exception e) {
                responses.add(PrepareResponse.NO);
            }
        }
        
        // 决策：全 YES 才 COMMIT
        Decision decision = responses.stream().allMatch(r -> r == PrepareResponse.YES)
                ? Decision.COMMIT : Decision.ABORT;
        
        // 关键：持久化决策（崩溃恢复依据）
        decisionLog.persist(tx.id(), decision);
        
        // Phase 2: 通知
        for (Participant p : participants) {
            while (true) {
                try {
                    p.commitOrAbort(tx.id(), decision).get(10, TimeUnit.SECONDS);
                    break;  // 成功，退出重试
                } catch (TimeoutException e) {
                    // 重试，直到成功（幂等保证）
                    log.warn("Participant {} timeout, retrying", p.id());
                }
            }
        }
        
        return new TransactionResult(decision);
    }
}

// Participant
public class TwoPhaseParticipant implements Participant {
    private final WalManager wal;
    private final StateMachine stateMachine;
    
    @Override
    public PrepareResponse prepare(Transaction tx) {
        // 持久化 PREPARED 状态（关键！）
        wal.append(tx.id(), WalEntry.PREPARED, tx.operations());
        wal.fsync();  // 必须 fsync
        
        if (stateMachine.canApply(tx)) {
            return PrepareResponse.YES;
        } else {
            wal.append(tx.id(), WalEntry.ABORTED);
            return PrepareResponse.NO;
        }
    }
    
    @Override
    public void commitOrAbort(String txId, Decision decision) {
        // 幂等检查
        WalEntry existing = wal.get(txId);
        if (existing != null && existing.state == decision.toWalState()) {
            return;  // 已处理，幂等返回
        }
        
        if (decision == Decision.COMMIT) {
            wal.append(txId, WalEntry.COMMITTED);
            wal.fsync();
            stateMachine.apply(txId);
        } else {
            wal.append(txId, WalEntry.ABORTED);
            wal.fsync();
            stateMachine.rollback(txId);
        }
    }
    
    // 崩溃恢复：扫描 WAL，处理未决事务
    public void recover() {
        for (WalEntry entry : wal.scanUndecided()) {
            if (entry.state == WalState.PREPARED) {
                // 询问协调者决策
                Decision d = askCoordinator(entry.txId);
                commitOrAbort(entry.txId, d);
            }
        }
    }
}
```

### 6.2.5 2PC 的三大缺陷 ⚠️🔥

#### 缺陷 1：同步阻塞

> 在 Prepare 到 Commit 期间，所有参与者**持锁等待**，事务无法继续。

**影响**：

- 任一参与者慢，整个事务阻塞
- 锁资源不释放，可能引发死锁/超时
- 吞吐量急剧下降

#### 缺陷 2：协调者单点故障

> 协调者在 Phase 2 决策后、通知前崩溃，参与者将**永久阻塞**在 PREPARED 状态。

**场景**：

```
Coordinator: 决策 COMMIT，持久化决策日志
Coordinator: 发送 COMMIT 给 P1（成功），准备发给 P2、P3
Coordinator: 崩溃！
P2, P3: 仍处于 PREPARED，持锁等待
→ 永久阻塞，直到协调者恢复
```

**缓解**：

- 协调者 HA（主备切换）
- 参与者超时后自主 abort（但有风险，见缺陷 3）

#### 缺陷 3：不一致风险

> 协调者发送 COMMIT 时部分成功部分失败，导致部分参与者 commit、部分仍 PREPARED。

**场景**：

```
Coordinator 发 COMMIT：
  P1: 收到，commit
  P2: 网络分区，未收到
  P3: 收到，commit
→ P1、P3 已 commit，P2 仍 PREPARED → 数据不一致
```

**缓解**：

- 协调者重试未 ACK 的参与者
- 但参与者恢复后才能补 commit，期间不一致

### 6.2.6 2PC 的 Safety 与 Liveness

| 性质 | 保证 | 前提 |
|------|------|------|
| **Safety**（一致性） | ✅ 保证 | 协调者持久化决策 + 参与者持久化 PREPARED |
| **Liveness**（活性） | ❌ 不保证 | 协调者故障时阻塞 |

### 6.2.7 工业实现

#### XA 协议

- X/Open 标准，关系型数据库通用 2PC
- MySQL XA、PostgreSQL Prepared Transaction、Oracle XA
- Java JTA（Java Transaction API）基于 XA

```sql
-- MySQL XA 示例
XA START 'tx_id';
UPDATE account SET balance = balance - 100 WHERE id = 1;
XA END 'tx_id';
XA PREPARE 'tx_id';
-- 协调者收集所有 PREPARE 响应
XA COMMIT 'tx_id';
-- 或 XA ROLLBACK 'tx_id';
```

#### Seata XA 模式

- 阿里开源 Seata 框架的 XA 模式
- 基于 XA 协议 + TC（Transaction Coordinator）
- 详见 [06-事务-工业实战与选型](./06-事务-工业实战与选型.md)

### 6.2.8 ⚠️ 2PC 生产陷阱

- ⚠️ **协调者单点**：必须 HA 部署
- ⚠️ **同步阻塞**：长事务持锁，性能差
- ⚠️ **PREPARED 状态清理**：参与者崩溃后 PREPARED 事务需人工或自动清理
- ⚠️ **XA 性能差**：比本地事务慢 10-100 倍
- 🔥 **生产建议**：

  - 仅在强一致 + 跨同质数据库场景用 XA
  - 优先考虑 TCC / Saga / 消息事务（见后续章节）
  - 协调者用 Raft 实现 HA（如 Seata TC）

## 6.3 3PC（三阶段提交）

📜 [Skeen 1981] *A Quorum-Based Commit and Abort Protocol*

### 6.3.1 设计动机

3PC 试图解决 2PC 的「协调者故障导致阻塞」问题，通过引入 **CanCommit** 阶段 + **超时机制**，让参与者在协调者故障时能自主决策。

### 6.3.2 三阶段流程 ⭐

```
Phase 1: CanCommit (询问能否提交)
─────────────────────────────────
Coordinator ──CanCommit──► Participants
                ◄──YES/NO──

Phase 2: PreCommit (预提交)
──────────────────────────
Coordinator 收全 YES
  ├──PreCommit──► Participants
                ◄──ACK──
Coordinator 收任一 NO 或超时
  └──Abort──────► Participants

Phase 3: DoCommit (真正提交)
────────────────────────────
Coordinator ──DoCommit──► Participants
                ◄──ACK──
```

### 6.3.3 算法伪代码

```pseudocode
# Coordinator
function three_phase_commit(participants, tx):
    # Phase 1: CanCommit
    can_commit_responses = []
    for each p in participants:
        resp = p.can_commit(tx)
        can_commit_responses.append(resp)
    
    if not all(can_commit_responses == YES):
        abort(participants, tx)
        return ABORT
    
    # Phase 2: PreCommit
    precommit_log = []
    for each p in participants:
        resp = p.pre_commit(tx)
        precommit_log.append(resp)
    
    if not all(precommit_log == ACK):
        abort(participants, tx)
        return ABORT
    
    # Phase 3: DoCommit
    persist(decision_log, tx, COMMIT)
    for each p in participants:
        p.do_commit(tx)
    return COMMIT

# Participant
function can_commit(tx):
    # 仅检查能否提交（不持锁）
    return YES if can_commit else NO

function pre_commit(tx):
    # 执行操作，写 PREPARED 日志，但不真正 commit
    write_to_wal(tx, PREPARED)
    return ACK

function do_commit(tx):
    write_to_wal(tx, COMMITTED)
    apply(tx)
    return ACK

# 关键：参与者超时处理
function on_coordinator_timeout(tx):
    state = get_state(tx)
    if state == PREPARED:
        # 协调者在 PreCommit 后故障
        # 因为之前 CanCommit 全 YES，可安全 commit
        do_commit(tx)
    elif state == INIT:
        # 协调者在 PreCommit 前故障
        # 安全 abort
        abort(tx)
```

### 6.3.4 3PC 的「无阻塞」特性

> **关键改进**：参与者在协调者故障时，可通过自身状态 + 超时机制决策，无需等待协调者恢复。

| 参与者状态 | 超时后行为 | 理由 |
|----------|-----------|------|
| INIT（未收到 CanCommit） | Abort | 协调者未启动事务 |
| PREPARED（收到 PreCommit） | Commit | CanCommit 已全 YES，安全 commit |
| COMMITTED | 已完成 | — |

### 6.3.5 3PC 的剩余问题 ⚠️

#### 问题 1：仍可能不一致（网络分区）

```
Coordinator 发 PreCommit，P1、P2 收到，P3 因网络分区未收到
Coordinator 崩溃
P1、P2：PREPARED 状态，超时后自主 commit
P3：INIT 状态，超时后自主 abort
→ P1、P2 commit，P3 abort，不一致
```

**根因**：3PC 假设「网络可靠 + 仅节点故障」，但真实网络有分区。

#### 问题 2：消息开销大

- 比 2PC 多一轮 RPC（CanCommit）
- 延迟增加

#### 问题 3：实际很少使用

- 不能完全解决不一致
- 多一轮开销
- 工程上更倾向用 2PC + 协调者 HA

### 6.3.6 3PC 的理论价值

> **学术意义**：3PC 在「同步网络 + 仅节点崩溃」假设下实现了非阻塞，是理论上的改进。
> **工程意义**：实际网络是异步的（有分区），3PC 的非阻塞特性失效，故很少工业落地。

## 6.4 协调者 HA

### 6.4.1 为什么需要协调者 HA

2PC 的核心弱点是协调者单点。解法：协调者本身用共识算法（Raft/Paxos）实现 HA。

### 6.4.2 实现方式

```
        Client
          │
          ▼
    ┌─────────────┐
    │ Coordinator │ ◄── Raft 复制
    │   (Leader)  │
    └─────────────┘
          │
       ┌──┼──┐
       ▼  ▼  ▼
      P1  P2  P3
```

协调者集群内部用 Raft：

- 决策日志在多数节点持久化
- Leader 故障 → 选新 Leader → 读取日志恢复
- 客户端只访问 Leader

### 6.4.3 代码示例（Go 风格）

```go
// HA Coordinator using Raft
type HACoordinator struct {
    raft      *raft.Raft
    commitLog map[string]Decision  // 持久化 + Raft 复制
}

func (c *HACoordinator) Commit(tx Transaction) error {
    // Phase 1: Prepare
    responses := []PrepareResponse{}
    for _, p := range tx.Participants {
        resp, err := p.Prepare(tx)
        if err != nil || resp == NO {
            responses = append(responses, NO)
        } else {
            responses = append(responses, YES)
        }
    }
    
    // 决策
    decision := ABORT
    if allYes(responses) {
        decision = COMMIT
    }
    
    // 关键：通过 Raft 持久化决策
    op := DecisionOp{TxID: tx.ID, Decision: decision}
    future := c.raft.Apply(op.Serialize(), 5*time.Second)
    if err := future.Error(); err != nil {
        return err  // Raft 未达成共识，返回错误
    }
    
    // Phase 2: 通知参与者
    for _, p := range tx.Participants {
        go func(p Participant) {
            for {
                err := p.CommitOrAbort(tx.ID, decision)
                if err == nil {
                    return
                }
                time.Sleep(retryInterval)  // 指数退避
            }
        }(p)
    }
    
    return nil
}

// Raft Apply 完成后，决策已持久化在多数节点
// 即使当前 Leader 崩溃，新 Leader 也能恢复决策并继续通知
```

### 6.4.4 工业实践

- **Seata TC**：用 Raft 实现 HA（v1.5+）
- **OceanBase**：RootServer 用 Paxos
- **TiDB**：PD 用 Raft
- **Spanner**：Coordinator 用 Paxos Group

## 6.5 2PC vs 3PC 对比

| 维度 | 2PC | 3PC |
|------|-----|-----|
| 阶段数 | 2 | 3 |
| RPC 轮数 | 2 | 3 |
| 同步阻塞 | 是 | 弱（仍持锁，但有超时） |
| 协调者单点 | 是 | 部分缓解 |
| 不一致风险 | 有 | 有（网络分区下） |
| 实际应用 | XA、Seata XA | 几乎无 |
| 理论价值 | 经典 | 非阻塞（理想假设） |

🔥 **结论**：**实际系统几乎都用 2PC + 协调者 HA**，3PC 主要有理论价值。

## 6.6 🎓 学术深度

### 6.6.1 2PC 的 Safety 证明直觉

**Safety**：所有参与者要么都 commit 要么都 abort。

证明：

1. Coordinator 决策前，所有参与者处于 PREPARED
2. 决策持久化后，不可更改
3. 即使 Coordinator 故障，新 Coordinator 读取日志恢复同一决策
4. 所有参与者最终收到同一决策

### 6.6.2 2PC 的 Liveness 不保证

- 协调者故障 → 参与者阻塞
- 网络分区 → 部分参与者收不到决策
- FLP 限制：异步系统不能同时保证 Safety + Liveness + 容错

### 6.6.3 3PC 的非阻塞证明

在「同步网络 + 仅 Crash 故障」假设下：

1. 消息延迟有上界
2. 参与者超时 = 协调者故障
3. PREPARED 状态超时 → 安全 commit（CanCommit 已全 YES）

**网络分区破坏假设**：异步网络下 3PC 仍可能不一致。

### 6.6.4 不可能性结果

📜 [Gray 1978]：

> 不存在一个分布式提交协议，在异步网络 + 节点故障下，同时满足：
> - 非阻塞（不依赖协调者恢复）
> - 一致性
> - 容错

这是 2PC/3PC 固有 trade-off 的理论基础。

## 6.7 🏭 工业实战

### 6.7.1 MySQL XA

```sql
-- 启用 XA
XA START 'transfer_001';
UPDATE db1.account SET balance = balance - 100 WHERE id = 1;
XA END 'transfer_001';
XA PREPARE 'transfer_001';

-- 在另一个 DB
XA START 'transfer_001';
UPDATE db2.account SET balance = balance + 100 WHERE id = 2;
XA END 'transfer_001';
XA PREPARE 'transfer_001';

-- 协调者收集 PREPARE 响应
-- 全 YES 则 COMMIT，任一 NO 则 ROLLBACK
XA COMMIT 'transfer_001';  -- 在两个 DB 都执行
```

⚠️ **MySQL XA 陷阱**：

- ⚠️ XA PREPARE 后连接断开，事务保持 PREPARED 状态占资源
- ⚠️ 长时间 PREPARED 事务导致 binlog 膨胀
- ⚠️ MySQL 5.7 前 XA 有 bug（可能丢数据）
- 🔥 生产建议：避免长事务，监控 PREPARED 数量

### 6.7.2 Seata XA 模式

```java
// Seata XA 模式示例
@GlobalTransactional
public void transfer(Long from, Long to, BigDecimal amount) {
    // 调用账户服务（扣款）
    accountService.deduct(from, amount);
    // 调用账户服务（入账）
    accountService.credit(to, amount);
}

// Seata 内部流程：
// 1. TC（Transaction Coordinator）开启全局事务
// 2. 各 RM（Resource Manager）执行 SQL，进入 XA PREPARED
// 3. TC 收集所有 RM 状态
// 4. 全 PREPARED → TC 发 XA COMMIT
// 5. 任一失败 → TC 发 XA ROLLBACK
```

### 6.7.3 ⚠️ 工业陷阱汇总

- ⚠️ **XA 性能差**：比本地事务慢 10-100 倍
- ⚠️ **PREPARED 资源占用**：长事务持锁持资源
- ⚠️ **协调者故障恢复慢**：参与者需等协调者恢复
- ⚠️ **跨异构 DB 困难**：不同 DB 的 XA 实现差异
- 🔥 **替代方案**：

  - TCC（业务侵入但高性能）
  - Saga（长事务，最终一致）
  - 消息事务（解耦，最终一致）
  - 详见后续章节

## 6.8 面试要点

### ⭐ Q1：2PC 的两阶段流程？

**骨架**：

1. **Phase 1 Prepare**：协调者发 Prepare，参与者投票 YES/NO
2. **Phase 2 Commit/Abort**：全 YES 则 Commit，任一 NO 或超时则 Abort

**关键点**：两阶段 + 决策基于全 YES

**加分项**：提到决策需持久化

### ⭐ Q2：2PC 的三大缺陷？

**骨架**：

1. **同步阻塞**：Prepare 到 Commit 期间持锁等待
2. **协调者单点**：协调者故障导致参与者阻塞
3. **不一致风险**：Commit 通知部分失败

**关键点**：三大缺陷

**加分项**：对每个缺陷给出缓解措施

### ⭐ Q3：2PC 协调者故障如何处理？

**骨架**：

1. 协调者 HA（Raft/Paxos 复制决策日志）
2. 参与者崩溃恢复：扫 WAL，PREPARED 状态询问协调者
3. 协调者恢复后：读决策日志，继续通知

**关键点**：HA + WAL 恢复

**加分项**：提到 Seata TC 用 Raft

### ⭐ Q4：3PC 相比 2PC 改进了什么？

**骨架**：

1. 引入 CanCommit 阶段
2. 参与者超时自主决策（PREPARED → Commit）
3. 理论上非阻塞

**关键点**：超时自主决策

**加分项**：提到网络分区下仍可能不一致

### ⭐ Q5：3PC 为什么实际很少用？

**骨架**：

1. 多一轮 RPC 开销
2. 网络分区下仍可能不一致
3. 2PC + HA 已足够
4. 工程上倾向 TCC/Saga/消息事务

**关键点**：网络分区破坏非阻塞假设

**加分项**：提到 3PC 主要有理论价值

### ⭐ Q6：2PC 的 Safety 怎么保证？

**骨架**：

1. 协调者持久化决策
2. 参与者持久化 PREPARED 状态
3. 决策不可更改
4. 崩溃恢复后读取日志继续

**关键点**：WAL 持久化

**加分项**：提到 fsync 必须

### ⭐ Q7：为什么 2PC 性能差？

**骨架**：

1. 多轮 RPC（Prepare + Commit）
2. 同步阻塞，持锁等待
3. 协调者串行决策
4. fsync 开销

**关键点**：RPC + 阻塞 + fsync

**加分项**：提到比本地事务慢 10-100 倍

### ⭐ Q8：MySQL XA 怎么用？有什么坑？

**骨架**：

1. XA START/END/PREPARE/COMMIT
2. 跨 DB 协调
3. 坑：PREPARED 占资源、binlog 膨胀、5.7 前 bug

**关键点**：SQL 语法 + 坑

**加分项**：提到 Seata XA 模式

### ⭐ Q9：2PC 和 3PC 的本质区别？

**骨架**：

1. 2PC 假设协调者可靠，故障时阻塞
2. 3PC 假设网络同步，参与者可自主决策
3. 真实网络异步，3PC 优势失效
4. 工程都用 2PC + HA

**关键点**：假设差异

**加分项**：提到 Gray 1978 的不可能性结果

### ⭐ Q10：什么场景适合用 2PC？

**骨架**：

1. 强一致需求（金融）
2. 跨同质数据库（MySQL → MySQL）
3. 短事务（避免长阻塞）
4. 协调者可 HA 部署

**关键点**：强一致 + 同质 DB + 短事务

**加分项**：提到不适合长事务、跨异构、高并发场景
