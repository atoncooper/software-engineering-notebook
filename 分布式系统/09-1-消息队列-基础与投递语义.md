## 0. 消息队列的本质

消息队列(Message Queue / MQ)是分布式系统的"血管",解决:

- **解耦**:生产者不需要知道消费者是谁
- **异步**:慢操作异步化,提升响应速度
- **削峰**:突发流量先入队,消费者按节奏处理
- **广播**:一份数据多消费者处理

形式化:MQ 是一个**异步通信原语**,生产者发消息到 queue,消费者从 queue 取消息,中间由 broker 中转。

```
Producer → [Broker (Queue)] → Consumer
              ↑
           持久化、复制、路由
```

本章梳理 MQ 的基础概念和投递语义(at-most-once / at-least-once / exactly-once),后续章节深入 Kafka / RocketMQ / Pulsar。

---

## 1. 消息模型

### 1.1 P2P (Point-to-Point)

```
Producer → [Queue] → Consumer
```

- 一条消息只被一个消费者消费
- 多消费者竞争消费(负载均衡)
- 典型:ActiveMQ Classic、RabbitMQ 工作队列

### 1.2 Pub/Sub (发布订阅)

```
Producer → [Topic] → Subscriber 1
                  → Subscriber 2
                  → Subscriber 3
```

- 一条消息被所有订阅者消费
- 每个订阅者独立消费进度
- 典型:Kafka、RocketMQ、Pulsar

### 1.3 混合模型(Consumer Group)

```
Producer → [Topic] → Consumer Group A (3 consumers 负载均衡)
                  → Consumer Group B (2 consumers 负载均衡)
```

- 同一 Group 内:竞争消费(P2P 语义)
- 不同 Group 间:各自消费(Pub/Sub 语义)
- 典型:Kafka Consumer Group

## 2. 投递语义

### 2.1 三种语义

| 语义 | 含义 | 实现复杂度 |
|------|------|----------|
| **At-most-once** | 消息可能丢,不会重 | 低 |
| **At-least-once** | 消息不会丢,可能重 | 中 |
| **Exactly-once** | 消息不丢不重 | 高(需协调) |

### 2.2 At-most-once

- Producer 发完不等 ACK
- Broker 不持久化
- Consumer 收到立即 ACK,处理失败不重试

适用:监控指标、日志(可丢)

### 2.3 At-least-once

- Producer 重试直到 ACK
- Broker 持久化(写盘 + 副本)
- Consumer 处理完再 ACK(失败不 ACK,broker 重投)

适用:大多数业务场景

**问题**:Consumer 处理完但 ACK 丢失 → broker 重投 → 重复消费。需要业务幂等(详见 [[12-幂等性]])。

### 2.4 Exactly-once

> 📜 FLP 类比:异步网络下"真正的" exactly-once 不可能。工程方案:**at-least-once + 幂等消费 = 业务 exactly-once**。

#### 2.4.1 Producer 端幂等

Kafka 0.11+ Idempotent Producer:

- Producer 启动时获得 `producer_id` + `epoch`
- 每条消息带 `sequence_number`
- Broker 按 (topic, partition, producer_id, sequence_number) 去重
- 重发的相同消息 broker 只持久化一次

#### 2.4.2 Consumer 端事务

Kafka 0.11+ Transactional Producer:

- Producer 用 `transactional.id` 开启事务
- `beginTransaction()` → send → sendOffsetsToConsumer → `commitTransaction()`
- Consumer 设 `isolation.level=read_committed`,只读已提交事务的消息

#### 2.4.3 业务幂等

最实用的方案:

- Consumer 用 message_id 做去重表
- 处理 + 去重表 insert 在同一数据库事务中
- 重复消费时去重表冲突,跳过

```java
@KafkaListener(topics = "orders")
public void onOrder(OrderEvent event) {
    jdbc.update("INSERT INTO consumed(message_id) VALUES(?) ON CONFLICT DO NOTHING",
                event.getMessageId());
    if (affectedRows() == 0) return;  // 已处理
    orderService.process(event);
}
```

## 3. 核心组件

### 3.1 Producer

- 序列化消息
- 路由(选 partition/topic)
- 发送(同步/异步)
- 重试 + 幂等

### 3.2 Broker

- 接收消息
- 持久化(写盘 + 副本)
- 索引(offset / 时间戳)
- 投递给 Consumer

### 3.3 Consumer

- 拉取消息(pull)或接收推送(push)
- 反序列化
- 业务处理
- ACK / Commit Offset

### 3.4 Topic / Partition

- Topic:逻辑分类(如 `orders`、`logs`)
- Partition:Topic 的物理分片,并行消费单位
- Partition 数决定最大并行度

### 3.5 Offset

- Consumer 在 Partition 中的消费位置
- 持久化(broker 端或 zk/etcd)
- 故障恢复后从 offset 继续

## 4. 关键问题

### 4.1 消息顺序

#### 4.1.1 全局顺序

- 整个 Topic 内消息严格有序
- 只能用 1 个 Partition,丧失并行
- 适用:极少数严格顺序场景(如 binlog 复制)

#### 4.1.2 分区顺序

- 同 key 的消息落同 Partition,Partition 内有序
- 不同 key 可并行
- 大多数场景的标准方案

```java
// Kafka: 用 user_id 作 key,保证同 user 的消息有序
producer.send(new ProducerRecord<>("orders", userId, orderEvent));
```

### 4.2 消息堆积

- Consumer 跟不上 Producer 速度
- 解决:
  - 加 Partition + Consumer(同 Group)
  - Consumer 异步处理(收到消息丢线程池,立即 ACK)
  - 降级(只处理关键字段,后续补偿)

### 4.3 消息丢失

| 阶段 | 丢失原因 | 防御 |
|------|---------|------|
| Producer → Broker | 网络丢包 | ACK + 重试 |
| Broker 内 | 写盘前 crash | 副本 + acks=all |
| Broker → Consumer | Consumer 拉取后 crash | 处理完再 commit offset |
| Consumer 内 | 业务异常 | 重试 + 死信队列 |

### 4.4 消息重复

- Producer 重试(网络抖动 ACK 丢失)
- Consumer 重投(ACK 丢失)
- Rebalance 时 offset 未及时 commit
- 防御:业务幂等(幂等键 / 去重表)

### 4.5 死信队列 (DLQ)

处理失败的消息转入 DLQ,主流程继续:

```java
@KafkaListener(topics = "orders")
public void onOrder(OrderEvent event) {
    try {
        orderService.process(event);
    } catch (NonRetryableException e) {
        // 不可重试错误,转 DLQ
        kafkaTemplate.send("orders.DLQ", event);
        ack.acknowledge();
    } catch (RetryableException e) {
        // 可重试错误,抛出让 Kafka 重投
        throw e;
    }
}
```

## 5. 选型对比

### 5.1 主流 MQ

| MQ | 吞吐 | 延迟 | 顺序 | 事务 | 协议 | 适用 |
|----|------|------|------|------|------|------|
| **Kafka** | 极高(100w/s) | ms | 分区 | 0.11+ | 私有 | 日志、流处理 |
| **RocketMQ** | 高(10w/s) | ms | 分区 | 强 | 私有 | 电商、金融 |
| **Pulsar** | 极高 | ms | 分区 | 强 | 私有 | 多租户、流批一体 |
| **RabbitMQ** | 中(1w/s) | μs | 队列 | 弱 | AMQP | 业务消息、复杂路由 |
| **ActiveMQ** | 低 | ms | 队列 | 强 | JMS/AMQP | 传统企业 |
| **NATS** | 极高 | μs | 弱 | 无 | 私有 | 微服务通信 |
| **Redis Stream** | 高 | μs | 队列 | 弱 | RESP | 轻量级 MQ |

## 6. 面试要点

**Q1: 消息队列的三大用途?**

> 解耦(生产者不关心消费者)、异步(慢操作异步化)、削峰(突发流量入队)。最常见例子:订单创建后异步发短信、库存扣减。

**Q2: at-least-once 和 exactly-once 怎么实现?**

> at-least-once:Producer 重试 + Broker 持久化 + Consumer 处理完再 ACK。exactly-once:在 at-least-once 基础上加幂等(Producer 端 idempotent producer 或 Consumer 端业务幂等)。真正网络层 exactly-once 不可能(FLP),业务层幂等是工程唯一可靠方案。

**Q3: Kafka 怎么保证消息顺序?**

> 全局顺序:单 Partition,丧失并行。分区顺序:同 key 落同 Partition,Partition 内有序。生产用分区顺序,选业务 key(如 user_id、order_id)保证同 key 顺序。

**Q4: 消息丢失的几个环节?**

> (1) Producer → Broker:网络丢包,用 ACK + 重试;(2) Broker 内:写盘前 crash,用副本 + acks=all;(3) Broker → Consumer:Consumer 拉取后 crash,处理完再 commit offset;(4) Consumer 内:业务异常,用重试 + DLQ。

**Q5: 消息堆积怎么处理?**

> (1) 加 Partition + Consumer(同 Group 内并行);(2) Consumer 异步处理(收到丢线程池立即 ACK);(3) 临时降级(只处理关键字段);(4) 监控告警 + 容量规划预防。

## 8. 速查表 (Cheat Sheet)

```
投递语义:
  at-most-once:   发完不等,可能丢
  at-least-once:  重试+ACK,可能重
  exactly-once:   at-least-once + 幂等

核心组件: Producer / Broker / Consumer / Topic / Partition / Offset

常见问题:
  顺序: 分区顺序(同 key 同 partition)
  堆积: 加 partition + consumer / 异步处理
  丢失: ACK + 副本 + 处理后 commit
  重复: 业务幂等

主流 MQ:
  日志/流处理 → Kafka
  电商/金融 → RocketMQ
  多租户/流批 → Pulsar
  业务路由 → RabbitMQ
  轻量级 → Redis Stream
```
