## 0. 为什么分布式锁难

单机锁(如 Java `synchronized`、Go `sync.Mutex`)依赖:

1. 共享内存(进程内可见)
2. 操作系统/语言运行时提供原子原语(CAS、futex)
3. 进程崩溃时 OS 释放锁(或 kernel 检测进程死亡)

分布式环境下,**以上三条全部失效**:

- 没有共享内存,只能通过网络通信
- 网络分区导致"我以为我持有锁、对方也以为他持有"
- 持锁进程 GC STW / 网络抖动 / 时钟漂移,锁过期但进程仍以为持有

> 🎓 Martin Kleppmann 在 *Designing Data-Intensive Applications* 第 8 章指出:分布式锁的本质矛盾是"用不可靠的时钟和网络,模拟单机锁的互斥语义"。

本章按"实现方式"展开,最后给出工业级 Fencing 方案。

## 1. 定义与动机

### 1.1 分布式锁的形式定义

> 一个分布式锁 $L$ 是一个原语,提供 `acquire()` / `release()` 操作,满足:
>
> - **Mutual Exclusion (Safety)**:任意时刻至多一个客户端持有锁
> - **Liveness (Progress)**:锁最终能被释放,等待者最终能获取(避免无限等待)
> - **Fault Tolerance**:持锁客户端崩溃时,锁最终能被释放给其他客户端

### 1.2 用途分类

| 场景 | 要求 | 例子 |
|------|------|------|
| **效率锁 (Efficiency)** | 偶尔失效可接受,目标是减少重复工作 | 防止缓存击穿、限流 |
| **正确性锁 (Correctness)** | 绝对不能两个客户端同时持锁 | 金融扣款、库存扣减、配置变更 |
| **Leader 选举** | 持锁者即 Leader,锁失效即切换 | HBase Master、K8s Leader |

> ⚠️ **易错**:用 Redis 锁做"正确性"场景而不加 Fencing,是分布式系统最常见的事故源。

### 1.3 难点矩阵

| 问题 | 单机 | 分布式 |
|------|------|--------|
| 原子性 | CPU CAS | 网络多跳,中途崩溃 |
| 可见性 | 共享内存 | 网络传播延迟 |
| 持有者检测 | OS 进程表 | 心跳/Lease |
| 锁失效 | 进程死锁有 OS 兜底 | 进程 STW,锁超时但持有者"还活着" |
| 时钟 | 单调时钟可用 | 跨节点时钟漂移 |

## 2. 原理与算法

### 2.1 单 Redis 锁

#### 2.1.1 基本形式

```
SET lock_key <token> NX PX 30000
```

- `NX`:不存在才设置(原子性)
- `PX 30000`:30s 过期(避免持锁者崩溃后死锁)
- `<token>`:客户端唯一标识(UUID),用于安全释放

#### 2.1.2 释放:Lua 原子

释放时必须先验证 token 再删,否则可能删别人的锁:

```lua
-- release.lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
```

```java
// Java: 安全释放 Redis 锁
public boolean releaseLock(String key, String token) {
    String script =
        "if redis.call('GET', KEYS[1]) == ARGV[1] then " +
        "  return redis.call('DEL', KEYS[1]) " +
        "else return 0 end";
    Long result = (Long) jedis.eval(script, Collections.singletonList(key),
            Collections.singletonList(token));
    return result != null && result == 1;
}
```

```go
// Go: 安全释放
var releaseScript = redis.NewScript(`
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
`)
func releaseLock(rdb *redis.Client, key, token string) bool {
    res, _ := releaseScript.Run(context.Background(), rdb,
        []string{key}, token).Int()
    return res == 1
}
```

#### 2.1.3 锁续约 (Watchdog)

锁过期但业务未完成时,需要续约:

```java
public class RedisLock {
    private final Jedis jedis;
    private final String key;
    private final String token;
    private final ScheduledExecutorService scheduler = Executors.newSingleThreadScheduledExecutor();
    private ScheduledFuture<?> renewTask;

    public void acquire(long ttlMs) {
        String result = jedis.set(key, token, SetParams.setParams().nx().px(ttlMs));
        if (!"OK".equals(result)) throw new IllegalStateException("Lock busy");
        // Watchdog:每 ttl/3 续约一次
        renewTask = scheduler.scheduleAtFixedRate(() -> {
            String script =
                "if redis.call('GET', KEYS[1]) == ARGV[1] then " +
                "  return redis.call('PEXPIRE', KEYS[1], ARGV[2]) " +
                "else return 0 end";
            jedis.eval(script, Arrays.asList(key), Arrays.asList(token, String.valueOf(ttlMs)));
        }, ttlMs / 3, ttlMs / 3, TimeUnit.MILLISECONDS);
    }

    public void release() {
        if (renewTask != null) renewTask.cancel(false);
        releaseLock(key, token);
        scheduler.shutdown();
    }
}
```

Redisson 的 Watchdog 默认 30s TTL、每 10s 续约一次,是工业标配。

#### 2.1.4 单 Redis 锁的缺陷

1. **单点故障**:Redis 主从异步复制,主挂从升,锁可能丢失。
2. **主从切换期双持**:客户端 A 在主上获取锁,主还没同步到从就挂了,从升主后客户端 B 又能获取同把锁。
3. **STW 风险**:客户端 GC STW 期间锁过期,STW 结束后客户端仍以为持有锁,但已被其他客户端获取。

### 2.2 Redlock:多节点 Quorum

> 📜 antirez (Salvatore Sanfilippo, Redis 作者), 2014

Redlock 试图解决单点问题:在 $N$(通常 5)个**独立** Redis 实例上同时获取锁,只要 $(N/2 + 1)$ 个成功就算获锁。

#### 2.2.1 算法步骤

```
1. 客户端获取当前时间 T0
2. 依次向 N 个 Redis 实例发送 SET NX PX,使用相同 key 和 token
3. 每个请求设独立超时(如 50ms),避免某实例挂导致长时间阻塞
4. 统计成功数:
   - 成功数 ≥ (N/2 + 1)
   - 且 总耗时 < TTL (锁还有效)
   → 获锁成功,实际 TTL = TTL - (T1 - T0)
5. 否则:向所有实例发 DEL 释放,获锁失败
```

```java
public class Redlock {
    private final List<Jedis> redises;
    private final int quorum;
    private final long ttlMs;

    public Redlock(List<Jedis> redises, long ttlMs) {
        this.redises = redises;
        this.quorum = redises.size() / 2 + 1;
        this.ttlMs = ttlMs;
    }

    public boolean tryLock(String key, String token) {
        long start = System.currentTimeMillis();
        int success = 0;
        for (Jedis jedis : redises) {
            try {
                String result = jedis.set(key, token,
                        SetParams.setParams().nx().px(ttlMs));
                if ("OK".equals(result)) success++;
            } catch (Exception e) {
                // 实例不可用,忽略
            }
        }
        long elapsed = System.currentTimeMillis() - start;
        if (success >= quorum && elapsed < ttlMs) {
            return true;  // 获锁成功
        }
        // 失败:向所有实例释放
        release(key, token);
        return false;
    }

    private void release(String key, String token) {
        String script = "if redis.call('GET',KEYS[1])==ARGV[1] then return redis.call('DEL',KEYS[1]) else return 0 end";
        for (Jedis jedis : redises) {
            try { jedis.eval(script, Collections.singletonList(key), Collections.singletonList(token)); }
            catch (Exception e) { /* ignore */ }
        }
    }
}
```

#### 2.2.2 Redlock 的争议

> 🎓 Martin Kleppmann, 2016 — *A critique of Redlock*

Kleppmann 的核心反驳:

1. **依赖时钟同步**:Redlock 用 TTL 计算锁剩余有效期,跨节点时钟漂移会破坏正确性。
2. **GC STW 悲剧**:
   - 客户端 A 获锁,TTL=10s
   - A 触发 GC STW 15s,期间锁过期
   - 客户端 B 在另一个节点获锁
   - A STW 结束,以为自己仍持锁,继续写共享资源
   - **两个客户端同时写!**
3. **网络延迟**:Redlock 假设消息瞬时到达,实际网络延迟可能让"T0 ~ T1"远超预期。

antirez 的反驳:Redis 不追求"正确性"级别锁,作为"效率锁"足够;若需正确性,用 ZK/etcd。

> 🎓 **学术结论**:Redlock 在 CERN 类时钟同步良好的环境可用作效率锁;**绝对不能用于正确性场景**(如金融、库存),除非配合 Fencing。

### 2.3 Fencing Token:正确性的终极方案

> 📜 Google Chubby 论文 (Burrows 2006) 提出,Kleppmann 在 DDIA 推广。

核心思想:锁本身可能失效,但用**单调递增的 Fencing Token** 防止过期锁的写操作生效。

#### 算法

```
1. 协调服务(锁服务)每次发锁时附带一个单调递增 token:
   client A 拿到 token=33
   A GC STW,锁过期
   client B 拿到 token=34
2. 客户端在写存储时附带 token
3. 存储记住"已见过的最大 token",拒绝任何比它小的 token 的写入
```

```
时间线:
  A: acquire(token=33) --------[GC 15s]--------- write(v, token=33)
  B:                           acquire(token=34) write(v, token=34)
                                                       ↓
                                       Storage: 已见到 34,拒绝 33
```

#### 工程实现

```java
// 1. 锁服务返回 token (用 etcd 的 revision 天然单调)
public class FencingLock {
    private final etcd.Client etcd;
    private long token;  // = lease revision

    public boolean acquire(String key) {
        long rev = etcd.txnIfCreateRevisionZero(key)
                       .thenPut(key, myId, withLease(leaseID))
                       .commit()
                       .getHeader().getRevision();
        if (rev == 0) return false;
        this.token = rev;  // Fencing token = etcd revision
        return true;
    }

    public long getToken() { return token; }
}

// 2. 写存储时附带 token
public class Storage {
    private long lastSeenToken = 0;

    public synchronized void write(String key, byte[] value, long fencingToken) {
        if (fencingToken <= lastSeenToken) {
            throw new IllegalStateException("Stale token: " + fencingToken);
        }
        lastSeenToken = fencingToken;
        store.put(key, value);
    }
}
```

#### MySQL 实现

```sql
-- 业务表加 fencing_token 列
ALTER TABLE orders ADD COLUMN fencing_token BIGINT NOT NULL DEFAULT 0;

-- 写入时用 CAS 保证 token 单调
UPDATE orders
SET status = 'PAID', fencing_token = ?
WHERE id = ? AND fencing_token < ?;
-- 如果 affected rows = 0,说明是过期锁的写入,拒绝
```

> 🎓 **核心洞察**:Fencing 把"锁失效问题"转化为"存储层单调 token 检查",不依赖锁服务本身的正确性。这是工业级正确性锁的**唯一可靠方案**。

### 2.4 ZK 分布式锁

#### 2.4.1 算法

ZK 锁利用"临时顺序节点"+ 链式 watch,天然支持公平排队:

```
1. 在 /locks/my_lock 下创建临时顺序节点 /locks/my_lock/lock_00000001
2. 获取 /locks/my_lock 所有子节点,排序
3. 如果自己是序号最小 → 获锁成功
4. 否则 watch 前一个节点(防止惊群)
5. 前一个节点删除(释放锁或 session 失效)→ 自己被通知 → 重新检查是否最小
6. 释放锁:删除自己的节点
```

```java
public class ZkDistributedLock {
    private final ZooKeeper zk;
    private final String lockPath;
    private String myNode;

    public void lock() throws Exception {
        myNode = zk.create(lockPath + "/lock-", new byte[0],
                ZooDefs.Ids.OPEN_ACL_UNSAFE,
                CreateMode.EPHEMERAL_SEQUENTIAL);
        while (true) {
            List<String> children = zk.getChildren(lockPath, false);
            Collections.sort(children);
            int myIdx = children.indexOf(myNode.substring(lockPath.length() + 1));
            if (myIdx == 0) return;  // 我是最小,获锁成功
            String prev = children.get(myIdx - 1);
            CountDownLatch latch = new CountDownLatch(1);
            Stat stat = zk.exists(lockPath + "/" + prev, event -> {
                if (event.getType() == EventType.NodeDeleted) latch.countDown();
            });
            if (stat != null) latch.await();
            // 前任删除,重检
        }
    }

    public void unlock() throws Exception {
        zk.delete(myNode, -1);
    }
}
```

#### 2.4.2 ZK 锁的优势

1. **公平锁**:顺序节点天然 FIFO。
2. **无惊群**:每个等待者只 watch 前一个,而不是所有 watch 最小节点。
3. **锁自动释放**:session 失效 → 临时节点删除 → 自动释放。
4. **可用性**:ZK 集群多数派存活即可,无需 Quorum 抢锁。

#### 2.4.3 ZK 锁的劣势

1. **性能**:每次获锁需多次 ZK 操作(create + getChildren + exists),比 Redis 慢一个数量级。
2. **Session 超时窗口**:session timeout 期间,客户端可能"以为"还持有锁,实际已被别人拿走(同样需要 Fencing)。

### 2.5 etcd 分布式锁

etcd 提供 `concurrency` 包,封装了 Lease + Txn CAS 的锁原语:

```go
import "go.etcd.io/etcd/clientv3/concurrency"

func etcdLock() {
    cli, _ := clientv3.New(clientv3.Config{Endpoints: []string{"localhost:2379"}})
    s, _ := concurrency.NewSession(cli)
    defer s.Close()
    m := concurrency.NewMutex(s, "/locks/my-lock")
    m.Lock(context.Background())
    defer m.Unlock(context.Background())

    // 业务逻辑
    // etcd 的 Lease 保证:进程崩溃 → lease 过期 → key 删除 → 锁释放
}
```

etcd 的锁实现原理:

1. 创建 Lease(默认 60s)。
2. Txn CAS:`If(CreateRevision(key) == 0) Then Put(key, leaseID) Else Get(key)`。
3. 失败则 watch key,等待删除后重试。

> 🎓 etcd v3 的锁不是公平锁(没有顺序节点),通过 revision + lease 实现"先到先得 + 自动释放"。公平锁需自己用 prefix + revision 排序。

### 2.6 数据库锁 (悲观/乐观)

#### 2.6.1 悲观锁:SELECT FOR UPDATE

```sql
BEGIN;
SELECT * FROM account WHERE user_id = 1001 FOR UPDATE;
-- 业务逻辑
UPDATE account SET balance = balance - 100 WHERE user_id = 1001;
COMMIT;
```

- 利用数据库行锁实现互斥
- 持锁期间阻塞其他事务
- 适合强一致 + 短事务

#### 2.6.2 乐观锁:版本号 CAS

```sql
-- 表带 version 字段
UPDATE account
SET balance = balance - 100, version = version + 1
WHERE user_id = 1001 AND version = 5;
-- affected rows = 0 说明并发冲突,重试
```

```java
public boolean deductWithOptimistic(Long userId, BigDecimal amount) {
    for (int i = 0; i < 3; i++) {
        Account acc = repo.findById(userId);
        if (acc.getBalance().compareTo(amount) < 0) throw new InsufficientBalance();
        int affected = repo.deductCAS(userId, amount, acc.getVersion());
        if (affected == 1) return true;
        // 版本冲突,重试
    }
    return false;
}
```

#### 2.6.3 数据库锁适用场景

- 强一致数据库(MySQL/PG/Oracle)已有,无需引入协调服务
- 事务路径短,持锁时间 < 几百毫秒
- 跨表/跨行需要原子性

不适用:

- 跨数据库实例(无法用同一行锁)
- 持锁时间长(影响其他事务)
- 高并发(行锁竞争激烈)

## 3. 🎓 学术深度

### 3.1 锁的 CAP 视角

| 方案 | 网络分区时 | 一致性 | 可用性 |
|------|----------|-------|-------|
| 单 Redis | 主挂则锁不可用 | 弱(主从异步) | 中 |
| Redlock | Quorum 失败则锁不可用 | 中(依赖时钟) | 中 |
| ZK | 少数派分区不可获锁 | 强 | 弱(CP) |
| etcd | 少数派分区不可获锁 | 强 | 弱(CP) |
| DB FOR UPDATE | DB 主挂则不可用 | 强 | 弱 |

### 3.2 Fencing 与 Linearizability

> 🎓 Kleppmann 论证:Fencing 把"锁服务 + 存储服务"组合成线性一致的系统,即使锁服务本身不是线性一致。

形式化:存储服务的 `write(key, value, token)` 必须满足:对任意 token 序列 $t_1 < t_2 < \dots$,存储只接受 $t_i > t_{i-1}$ 的写入,即"单调 token"约束。这与 Lamport 时钟的精神一致:用全序关系消除并发歧义。

### 3.3 Lease vs Lock

> 📜 Gray & Lamport, 2006 — *Clocks, Causality, and Lamport*

Lease 是"带期限的授权",Lock 是"持锁者主动释放的授权"。Lease 更适合分布式环境:

- Lease 持有者即使在 STW/网络分区下,过期后授权自动失效
- Lock 依赖持锁者主动 release,崩溃时需要外部检测

ZK 临时节点本质是 Lease(绑定 session 超时),etcd Lease 是显式 Lease。Redis PX 也是 Lease。

### 3.4 公平性 vs 性能

| 公平性 | 性能 | 实现 |
|-------|------|------|
| 公平 (FIFO) | 慢 | ZK 顺序节点、etcd 前缀排序 |
| 非公平 | 快 | Redis SET NX、etcd 默认锁 |
| 默认非公平 + 可选公平 | 折中 | Redisson 公平锁(基于 Lua + 等待列表) |

> 🎓 公平锁的代价:等待链路 watch 链若中间节点慢,整体延迟放大;非公平锁有"饥饿"风险。

### 3.5 STW 的不可避免性

JVM GC STW 是分布式锁失效的"经典事故源"。理论分析:

- 即使有 Watchdog 续约,STW 期间 Watchdog 也无法运行
- 即使 STW 结束后立刻续约,可能锁已过期被别人取走

唯一可靠方案:**Fencing + 存储层校验**。这不是"修复锁",而是承认锁不可靠,把正确性放到存储层。

## 4. 🏭 工业实战

### 4.1 Redisson:Java 生态事实标准

Redisson 提供丰富的锁实现:

```java
// 1. 可重入锁
RLock lock = redisson.getLock("myLock");
lock.lock();
try { /* ... */ } finally { lock.unlock(); }

// 2. 公平锁
RLock fairLock = redisson.getFairLock("myFairLock");

// 3. 读写锁
RReadWriteLock rwLock = redisson.getReadWriteLock("myRWLock");
rwLock.readLock().lock();
rwLock.writeLock().lock();

// 4. 联锁(多 key 同时锁)
RLock multiLock = redisson.getMultiLock(lock1, lock2, lock3);

// 5. Redlock
RLock redLock = redisson.getRedLock(lock1, lock2, lock3);
```

Redisson 内部:
- Watchdog 默认 30s TTL,10s 续约
- Lua 脚本保证加锁/释放原子
- 可重入通过 hash 结构(字段=threadId,值=重入次数)实现

### 4.2 Curator:ZK 锁封装

```java
InterProcessMutex lock = new InterProcessMutex(curatorClient, "/locks/myLock");
try {
    if (lock.acquire(5, TimeUnit.SECONDS)) {
        try { /* 业务 */ } finally { lock.release(); }
    }
} catch (Exception e) { /* ... */ }
```

Curator 内部就是 §2.4 的算法 + 各种异常处理。

### 4.3 etcd concurrency 包

```go
s, _ := concurrency.NewSession(cli, concurrency.WithTTL(60))
m := concurrency.NewMutex(s, "/locks/myLock")
m.Lock(context.Background())
defer m.Unlock(context.Background())
```

### 4.4 选型决策表

| 场景 | 推荐 | 原因 |
|------|------|------|
| 效率锁(防缓存击穿、限流) | 单 Redis + Redisson | 性能高,失败可容忍 |
| 正确性锁(扣款、库存) | DB FOR UPDATE / CAS | 数据库原生强一致 |
| 正确性 + 跨系统协调 | ZK/etcd + Fencing | 强一致协调 + 存储层防御 |
| Leader 选举 | ZK/etcd Lease | session 失效自动切换 |
| 公平排队 | ZK 顺序节点 | FIFO 原生支持 |
| 高并发短事务 | 乐观锁(CAS) | 无锁等待 |
| 跨 DC 协调 | etcd + Fencing | 强一致 |

### 4.5 工业级正确性锁模板 (etcd + Fencing)

```java
public class CorrectLock {
    private final EtcdClient etcd;
    private final Storage storage;
    private long fencingToken;

    public void executeWithLock(String resource, Runnable task) {
        // 1. 从 etcd 获取锁 + Fencing Token
        fencingToken = etcd.acquireWithToken(resource);
        try {
            // 2. 业务逻辑,所有写操作都带 Fencing Token
            storage.setFencing(fencingToken);
            task.run();
        } finally {
            etcd.release(resource);
        }
    }
}

// 业务层
correctLock.executeWithLock("account:" + userId, () -> {
    storage.update("UPDATE account SET balance = balance - 100 " +
                   "WHERE user_id = ? AND fencing_token < ?",
                   userId, correctLock.getFencingToken());
});
```

### 4.6 故障案例

#### 案例 1: Redis 主从切换导致双持 (某支付公司)

- A 在 Redis 主获取锁,TTL=10s
- 主挂,从升主,锁数据未同步丢失
- B 在新主获取锁
- A、B 同时扣款,资金错账

修复:改用 ZK + Fencing,或业务层用 `account_version` CAS。

#### 案例 2: GC STW 导致过期锁仍写入 (某电商)

- A 获锁,准备扣库存
- Full GC 30s,锁 TTL=10s 已过期
- B 获锁扣完库存
- A GC 结束,继续扣,库存负数

修复:Fencing Token,存储层拒绝 token 较小的写入。

#### 案例 3: Redlock 时钟漂移 (某广告系统)

- 5 个 Redis 实例时钟不同步,某实例慢 5s
- A 获锁,计算实际 TTL 时偏大
- 锁实际已过期但 A 仍以为持有

修复:换 ZK;或配合 Fencing。

## 5. 面试要点

### 5.1 高频问答

**Q1: Redis 分布式锁怎么实现?**

> `SET key token NX PX 30000`。NX 保证原子性,PX 防止持锁者崩溃死锁,token 用于安全释放(防止删别人的锁)。释放用 Lua 脚本原子验证+删除。

**Q2: Redis 锁有什么问题?**

> (1) 主从异步复制,主挂从升锁丢失;(2) 客户端 STW 期间锁过期,业务仍以为持有;(3) 单点故障。解决:Redisson Watchdog 续约 + Fencing Token + 存储层校验。

**Q3: Redlock 算法是什么?为什么有争议?**

> 在 N(5) 个独立 Redis 实例上 Quorum 获锁。争议:依赖时钟同步,无法防御 GC STW 场景(Kleppmann 批评)。antirez 反驳:Redlock 适合效率锁不适合正确性锁。结论:正确性场景必须加 Fencing。

**Q4: Fencing Token 是什么?为什么需要?**

> 锁服务每次发锁时附带单调递增 token,客户端写存储时携带 token,存储记住最大 token,拒绝任何更小的写入。这样即使锁失效(主从切换、STW),过期锁的写入也会被存储拒绝。是工业级正确性锁的唯一可靠方案。

**Q5: ZK 锁和 Redis 锁哪个更好?**

> ZK 优势:临时节点 session 失效自动释放、顺序节点公平排队、链式 watch 无惊群、强一致。Redis 优势:性能高一个数量级、部署简单。正确性场景选 ZK,效率场景选 Redis。

**Q6: 锁过期了业务还没完成怎么办?**

> (1) Watchdog 自动续约(Redisson 默认 30s TTL,10s 续);(2) 业务幂等设计,即使锁过期重复执行也无害;(3) Fencing Token 防止过期锁的写入生效。

**Q7: 分布式锁和数据库行锁的区别?**

> (1) 数据库行锁仅限单 DB;分布式锁可跨 DB/跨系统;(2) 数据库行锁随事务释放,分布式锁需显式 release 或 lease 过期;(3) 数据库行锁强一致(同 DB 内),分布式锁视实现而定。

**Q8: 什么是可重入锁?分布式环境如何实现?**

> 同一线程多次获取同一把锁不阻塞。Redis 实现用 hash 结构:`HSET lock threadId 1`(首次)、`HINCRBY lock threadId 1`(重入),释放时 `HINCRBY -1`,值为 0 时 DEL。ZK 实现需在节点数据中记录持有次数。

### 5.2 易错点 ⚠️

1. **"Redis 锁是强一致"** — 错。主从异步,切换会丢锁。
2. **"Redlock 解决了一切"** — 错。无法防 GC STW,正确性场景仍需 Fencing。
3. **"ZK 锁不会失效"** — 错。session timeout 窗口内仍可能"客户端以为持有但实际已被别人拿"。
4. **"释放锁直接 DEL 就行"** — 错。必须先验证 token 再删,否则可能删别人的锁。
5. **"锁 + 业务幂等就万无一失"** — 部分对。幂等是兜底,但有些场景(如外发 HTTP 请求)幂等不保证,Fencing 仍是必要的。

## 9. 速查表 (Cheat Sheet)

```
选型决策:
  是效率锁(失败可容忍)?
    Yes → Redis 单实例 + Redisson
         需要多节点? → Redlock (但仍只是效率锁)
  是正确性锁(失败=资损)?
    Yes → 数据库行锁/乐观锁(若单 DB)
         跨 DB/跨系统? → etcd/ZK + Fencing Token + 存储层校验
  是 Leader 选举?
    → ZK/etcd 临时节点/Lease

永远要做:
  - 释放锁时验证 token (Lua 原子)
  - 设合理 TTL (典型 10~60s)
  - 用 Watchdog 续约(长任务)
  - 业务幂等设计(兜底)

绝不要做:
  - 用 SET key value (无 NX/PX)
  - 释放锁直接 DEL (无 token 验证)
  - 用 Redlock 做正确性锁(无 Fencing)
  - 用 TTL=∞ (无过期会死锁)
```
