## 0. 工业场景下的 MQ 选型

理论分析后,工业选型最终落在几个具体问题:

- 数据量级:万级 / 十万 / 百万 TPS?
- 延迟要求:μs / ms / s?
- 一致性:at-most-once / at-least-once / exactly-once?
- 顺序要求:无 / 分区 / 全局?
- 事务:是否需要"DB+MQ 一致"?
- 多租户:是否需要租户隔离?
- 跨 DC:是否需要多活?
- 团队:已有经验 / 运维能力?

本章从场景出发,给出选型决策与工业实践。

## 2. 选型决策树

```
数据量级?
  < 1k TPS:
    延迟敏感 → RabbitMQ / Redis Stream
    简单 → Redis Stream / RabbitMQ
  1k ~ 10w TPS:
    业务消息(订单/支付) → RocketMQ
    事件驱动 / 复杂路由 → RabbitMQ
  > 10w TPS:
    日志 / 大数据 → Kafka
    多租户 / 弹性 → Pulsar
    电商金融 → RocketMQ(单集群可 10w+)

特殊需求?
  严格事务(DB+MQ 一致) → RocketMQ 事务消息 / Outbox+CDC
  跨 DC 多活 → Pulsar(原生) / RocketMQ(Dledger) / Kafka(MirrorMaker)
  任意延迟消息 → RocketMQ 5.x / Pulsar
  Key_Shared 订阅 → Pulsar
  流处理 → Kafka Streams / Flink on Kafka
  轻量级(已有 Redis) → Redis Stream
  微服务通信(请求-响应) → NATS

团队经验?
  已有 Kafka → 继续 Kafka
  已有 RabbitMQ → 继续 RabbitMQ
  全新选型 + 中国 → RocketMQ / Kafka
  全新选型 + 海外 → Kafka / Pulsar
```

## 3. 典型场景与方案

### 3.1 日志聚合

```
应用 → Filebeat → Kafka → Logstash → Elasticsearch
                                    → HDFS(归档)
```

- 选 Kafka:高吞吐、持久化、生态成熟
- partition 数:按吞吐算,典型 12~72
- retention:7 天(默认)~ 30 天(归档前)
- 压缩:zstd(性能 + 压缩比)

### 3.2 订单系统

```
订单服务 → 事务消息 → RocketMQ → 库存服务
                          ↓
                       通知服务
                          ↓
                       积分服务
```

- 选 RocketMQ:事务消息保证 DB+MQ 一致
- 顺序消息:同 orderId 落同 queue,保证状态变更有序
- DLQ:重试 16 次失败转 DLQ + 告警
- 监控:消息堆积、消费延迟、死信数量

### 3.3 实时数仓

```
MySQL CDC → Kafka → Flink 实时计算
              ↓
           Iceberg/Hudi (湖仓)
              ↓
           OLAP (Presto/StarRocks)
```

- 选 Kafka:与 Flink/Spark 集成成熟
- partition 数:与 Flink 并行度匹配
- Schema Registry:Protobuf/Avro,保证上下游兼容

### 3.4 微服务通信

```
订单服务 → NATS → 库存服务(请求-响应)
              → 支付服务(事件)
```

- 选 NATS:低延迟、轻量、支持请求-响应
- 替代 HTTP REST,适合内部微服务
- 不适合:持久化、复杂路由

### 3.5 多租户 SaaS

```
租户 A → Pulsar Topic A → Consumer A
租户 B → Pulsar Topic B → Consumer B
租户 C → Pulsar Topic C → Consumer C
```

- 选 Pulsar:原生多租户(tenant/namespace/topic 三级)
- 资源隔离:每租户独立 broker / bookie 配额
- 监控:按租户维度统计

### 3.6 跨 Region 多活

```
Region US → Pulsar Cluster US ←→ Geo-Replication ←→ Pulsar Cluster EU ← Region EU
                ↓                                                  ↓
            本地 Consumer                                      本地 Consumer
```

- 选 Pulsar:原生 Geo-Replication
- 配置即可,无需外部工具
- 同步/异步可选

## 4. 工业级生产实践

### 4.1 监控指标

| 指标 | 含义 | 告警阈值 |
|------|------|---------|
| Producer TPS | 每秒生产消息数 | > 容量 80% |
| Consumer TPS | 每秒消费消息数 | < Producer TPS 持续 |
| Lag | 消息堆积数 | > 10000 持续 5min |
| Produce Error Rate | 生产失败率 | > 0.1% |
| Consume Error Rate | 消费失败率 | > 0.5% |
| Broker CPU | Broker CPU 使用率 | > 80% |
| Broker Disk | 磁盘使用率 | > 80% |
| Network IO | 网络流量 | 接近网卡上限 |
| Replica Lag | Follower 落后 Leader | > 10000 |
| Active Controller | Kafka Controller 数量 | ≠ 1 |

### 4.2 容量规划

```
估算公式:
  单 Broker 吞吐 = min(磁盘 IO, 网络, CPU)
  Kafka 典型:100MB/s 顺序写,~100w 消息/s(1KB 消息)
  需要 Broker 数 = 总吞吐 / 单 Broker 吞吐 × 1.5(冗余)

存储:
  日均消息量 × 平均大小 × 副本数 × retention 天数
  例:1亿/天 × 1KB × 3 副本 × 7 天 = 2.1TB
  加 30% 余量 → 3TB
```

### 4.3 高可用配置清单

**Kafka**:
```
replication.factor=3
min.insync.replicas=2
acks=all
unclean.leader.election.enable=false
enable.idempotence=true
```

**RocketMQ**:
```
brokerRole=ASYNC_MASTER / SYNC_MASTER
ha.enable=true  (Dledger)
sendMessageThreadPoolNums=...
```

**Pulsar**:
```
BookKeeper:
  ensembleSize=3
  writeQuorum=2
  ackQuorum=2
```

### 4.4 消费幂等设计

```java
@KafkaListener(topics = "orders")
public void onOrder(OrderEvent event) {
    // 1. 去重表(主键 message_id)
    try {
        consumedMessageRepo.insert(event.getMessageId());
    } catch (DuplicateKeyException e) {
        return;  // 已消费
    }
    // 2. 业务处理(同事务)
    try {
        orderService.process(event);
    } catch (Exception e) {
        consumedMessageRepo.delete(event.getMessageId());  // 允许重试
        throw e;
    }
}
```

### 4.5 死信处理

```java
@KafkaListener(topics = "orders.DLT")  // Dead Letter Topic
public void handleDlq(OrderEvent event) {
    // 1. 告警
    alertService.send("Order DLQ: " + event.getMessageId());
    // 2. 记录到 DB,供人工查询
    dlqRepo.save(event);
    // 3. 可选:自动补偿(部分场景)
    if (isCompensable(event)) {
        compensateService.handle(event);
    }
}
```

### 4.6 消息堆积应急

```
1. 紧急扩容 Consumer(加实例)
2. 同 Group 内 partition 数不够? → 加 partition
3. 临时降级:跳过部分非关键消息
4. 业务侧异步化:Consumer 收到丢线程池立即 ACK
5. 堆积过多? → 转储到 DB / 文件,慢慢消化
6. 事后复盘:为什么堆积?容量不够?消费慢?异常?
```

## 5. 常见陷阱

### 5.1 Kafka 陷阱

1. **partition 数过少**:并行度不足,吞吐瓶颈
2. **partition 数过多**:元数据开销、rebalance 时间长
3. **acks=1**:Leader 挂可能丢数据,生产用 all
4. **auto.offset.reset=latest**:首次消费丢历史消息
5. **enable.auto.commit=true**:可能重复消费,生产用手动提交

### 5.2 RocketMQ 陷阱

1. **MessageQueue 数过少**:并行度不足
2. **半消息不回查**:Broker 回查失败,半消息停留
3. **延迟消息级别用错**:4.x 只支持 18 个级别
4. **DLQ 不监控**:死信堆积无人处理
5. **广播消费 + 集群消费混用**:行为不一致

### 5.3 Pulsar 陷阱

1. **Bookie 数过少**:Quorum 写失败
2. **Broker 资源不够**:无状态但仍需 CPU/内存
3. **跨 DC 复制延迟高**:影响多活一致性
4. **Schema 不兼容**:下游反序列化失败
5. **Key_Shared 模式 key 倾斜**:某 consumer 过载

### 5.4 RabbitMQ 陷阱

1. **队列堆积**:RabbitMQ 不擅长大量堆积
2. **镜像队列性能**:同步复制慢
3. **没有死信配置**:失败消息无限重试
4. **连接数过多**:每连接一个 Erlang 进程,资源消耗大

## 8. 面试要点

**Q1: Kafka、RocketMQ、Pulsar 怎么选?**

> 大数据/日志 → Kafka(生态成熟、吞吐极高);电商金融/业务消息 → RocketMQ(事务消息、延迟消息);多租户/弹性扩缩容/跨 DC → Pulsar(计算存储分离、原生多租户)。三者非互斥,大公司常组合用。

**Q2: 事务消息场景怎么选?**

> RocketMQ 事务消息:原生半消息+回查,Java SDK 方便,适合"DB+MQ 一致"。Outbox+CDC:更通用(任意 MQ + Debezium),但 CDC 有秒级延迟。轻量场景用 Redis Stream + 业务幂等。金融核心用 RocketMQ 或 Outbox。

**Q3: 消息堆积怎么应急?**

> (1) 加 Consumer;(2) 加 partition(若 partition < consumer);(3) Consumer 异步处理(收到丢线程池立即 ACK);(4) 临时降级(跳过非关键);(5) 转储堆积到 DB/文件慢慢消化;(6) 事后复盘容量规划。

**Q4: 怎么保证消息不丢不重?**

> 不丢:acks=all + 副本数 3 + min.insync.replicas=2 + Consumer 手动提交 offset + 处理完再 ACK。不重:业务幂等(幂等键/去重表/CAS)。底层 at-least-once + 业务幂等 = 业务 exactly-once。

**Q5: 跨 DC 多活怎么做?**

> Kafka:MirrorMaker 2(异步,最终一致);RocketMQ:Dledger 跨 DC 同步(强一致但延迟高);Pulsar:原生 Geo-Replication(同步/异步可配)。考虑业务对一致性的容忍度选同步或异步。

**Q6: MQ 和 RPC 怎么选?**

> MQ:解耦、异步、削峰、广播,适合非实时、可容忍延迟的场景。RPC:同步、低延迟、请求-响应,适合实时交互。一般:核心交易用 RPC,事件通知/异步处理用 MQ。

**Q7: Kafka partition 数选多少?**

> (1) 吞吐:partition 数 ≥ 期望吞吐 / 单 partition 吞吐(10MB/s);(2) 并行:partition 数 ≥ consumer 数;(3) 不过多:元数据、文件句柄、rebalance 时间。典型小集群 6~12,大集群 24~72。可后续加但不可减(减会破坏顺序)。

**Q8: RabbitMQ 和 Kafka 的本质区别?**

> RabbitMQ:Push 模型、复杂路由(Exchange/Binding)、AMQP 协议、低延迟、不擅长大量堆积。Kafka:Pull 模型、简单路由(topic/partition)、私有协议、高吞吐、堆积友好。RabbitMQ 偏业务消息(复杂路由),Kafka 偏大数据(吞吐)。

## 10. 速查表

```
选型决策:
  日志/大数据 → Kafka
  电商金融 → RocketMQ
  多租户/弹性/跨DC → Pulsar
  复杂路由/低延迟 → RabbitMQ
  轻量级 → Redis Stream / NATS

生产配置:
  Kafka:    replication=3, acks=all, min.insync.replicas=2, idempotence=true
  RocketMQ: Dledger (3+ nodes), SYNC_MASTER
  Pulsar:   ensemble=3, writeQuorum=2, ackQuorum=2

监控:
  Producer TPS / Consumer TPS / Lag / Error Rate
  Broker CPU/Disk/Net / Replica Lag

应急:
  堆积 → 加 Consumer / 加 Partition / 异步处理 / 降级
  消费失败 → 重试 → DLQ → 告警 → 人工
```
