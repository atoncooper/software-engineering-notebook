# 第 4 章 复制 —— 主从、Quorum 与状态机复制

> **本章导读**
> 复制（Replication）是分布式系统的基础机制：同一数据保存多份，以换取可用性、容错性、读吞吐。但「多副本」立即引出三个问题：写到哪里（同步 vs 异步）、读到什么（强一致 vs 弱一致）、不一致如何修复（Read Repair / Anti-Entropy）。本章系统化三种复制架构——主从、多主、无主 Quorum——以及它们在工程上的实现细节（ISR、Sloppy Quorum、Read Repair）。理解复制是理解共识（§5）与存储系统（§8）的前提。

> 4. Read Repair 与 Anti-Entropy 各解决什么问题？
> 5. 状态机复制（SMR）与共识的关系？

## 4.1 复制基础

### 4.1.1 为什么需要复制

| 目标 | 说明 |
|------|------|
| **高可用** | 节点故障时其他副本继续服务 |
| **容错** | 数据多份，单点故障不丢数据 |
| **读吞吐** | 读请求分散到多副本 |
| **低延迟** | 副本地理分布，就近访问 |
| **数据局部性** | 跨地域访问本地副本 |

### 4.1.2 复制的三个核心问题

1. **写传播**：写操作如何到达所有副本？
2. **一致性问题**：副本间数据何时一致？
3. **冲突处理**：并发写如何解决？

### 4.1.3 三种架构

| 架构 | 写入路径 | 一致性 | 典型 |
|------|---------|-------|------|
| **主从**（Primary-Backup） | 写主→同步/异步到从 | 强（同步） | MySQL、Kafka、HBase |
| **多主**（Multi-Master） | 任一主可写 | 最终一致 | Dynamo、Cassandra（跨 DC） |
| **无主**（Leaderless / Quorum） | 任一副本可写 | 可调 | Dynamo、Cassandra |

## 4.2 同步 / 异步 / 半同步

### 4.2.1 三种模式

#### 同步复制（Synchronous）

```pseudocode
# 主节点
function write(data):
    logLocal(data)
    for each backup:
        send(data)  # 阻塞等待 ACK
    return success
```

- **优点**：强一致，主故障不丢数据
- **缺点**：写延迟 = 最慢副本延迟；任一副本故障 → 写阻塞

#### 异步复制（Asynchronous）

```pseudocode
# 主节点
function write(data):
    logLocal(data)
    return success  # 立即返回
# 后台线程异步推送
```

- **优点**：低延迟；单副本故障不影响写
- **缺点**：主故障时未同步数据丢失

#### 半同步复制（Semi-Synchronous）

```pseudocode
# 主节点
function write(data):
    logLocal(data)
    acks = 0
    for each backup in parallel:
        send(data)
        if received_ack: acks++
        if acks >= K: break  # 至少 K 个副本 ACK
    return success
```

- **优点**：兼顾延迟与持久性
- **缺点**：K 个副本都故障仍丢数据

### 4.2.2 取舍矩阵

| 模式 | 一致性 | 延迟 | 可用性 | 持久性 |
|------|-------|------|-------|-------|
| 同步（全部） | 强 | 高 | 低 | 高 |
| 半同步（K 个） | 中 | 中 | 中 | 中 |
| 异步 | 弱 | 低 | 高 | 低 |

### 4.2.3 工业实现

| 系统 | 同步 | 半同步 | 异步 |
|------|------|-------|------|
| MySQL | — | semi-sync（K 个 ACK） | 默认 |
| PostgreSQL | — | `synchronous_commit` 等级 | 默认 |
| Kafka | `acks=all` | `min.insync.replicas` + `acks=all` | `acks=1` / `acks=0` |
| MongoDB | `w=majority` | `w=K` | `w=1` |
| Cassandra | `consistency=ALL` | `QUORUM` | `ONE` |

## 4.3 主从复制

### 4.3.1 架构

```
        Client
          │
          ▼
      ┌───────┐
      │ Primary│
      └───┬───┘
          │ 复制流
   ┌──────┼──────┐
   ▼      ▼      ▼
┌─────┐┌─────┐┌─────┐
│Rep1 ││Rep2 ││Rep3 │
└─────┘└─────┘└─────┘
```

### 4.3.2 工作流程

1. 客户端写主节点
2. 主节点本地持久化（WAL/binlog）
3. 主节点将日志推送到从节点（或从节点拉取）
4. 从节点回放日志
5. 同步模式下主节点等待 ACK

### 4.3.3 关键问题

#### 故障切换（Failover）

主节点故障时：

1. **检测**：心跳超时
2. **选举**：从节点中选新主（通常最新日志的从节点）
3. **提升**：新主开始接受写入
4. **通知**：客户端切换到新主

⚠️ **脑裂风险**：旧主未真死，恢复后又接受写入 → 数据冲突。解决：Fencing（详见 [§11 分布式锁](./11-分布式锁.md)）。

#### 复制滞后（Replication Lag）

异步复制下，从节点可能落后主节点：

- 读从节点可能读到旧数据
- 解决：读主、读己之写、强制读主

### 4.3.4 工业实现

| 系统 | 复制方式 | 故障切换 |
|------|---------|---------|
| **MySQL** | binlog 异步/半同步 | MHA、Orchestrator、MGR |
| **PostgreSQL** | WAL 流复制 | Patroni、repmgr |
| **Kafka** | ISR 同步 | Controller 自动选举 |
| **Redis** | 全量+增量（offset） | Sentinel / Cluster |
| **MongoDB** | OpLog 异步 | Replica Set 自动选举 |
| **etcd** | Raft 日志复制 | Raft 选举 |

## 4.4 多主复制

### 4.4.1 架构

```
       Client A            Client B
          │                    │
          ▼                    ▼
      ┌───────┐            ┌───────┐
      │Master1│◄──────────►│Master2│
      └───────┘  双向复制   └───────┘
```

### 4.4.2 优点

- **多地域写入**：每个地域一个主，本地写低延迟
- **容错**：一个主故障，其他主继续服务
- **写可用性高**：不受单主限制

### 4.4.3 缺点

- **冲突**：并发写不同主，冲突需解决
- **复杂性**：冲突解决策略多样
- **一致性弱**：最终一致为主

### 4.4.4 冲突解决策略

| 策略 | 说明 | 典型 |
|------|------|------|
| **LWW**（Last-Writer-Wins） | 时间戳最大的写胜出 | Cassandra、Dynamo |
| **Version Vector** | 向量时钟检测冲突，应用层解决 | Dynamo、Riak |
| **CRDT** | 数据结构本身可合并 | Riak、Redis（部分） |
| **应用层解决** | 业务规则合并 | 协同编辑 |
| **拓扑约束** | 同一 key 仅一个主可写 | 多地域路由 |

### 4.4.5 工业实现

- **DynamoDB Global Tables**：多地域多主，LWW 冲突解决
- **Cassandra 多 DC**：每个 DC 一个主，DC 间多主
- **CouchDB**：多主 + 应用层冲突解决
- ** Riak**：多主 + 向量时钟 + CRDT

⚠️ **多主与单主的取舍**：

- 多主适合「跨地域写多读多」场景
- 单主适合「强一致 + 单地域写多」场景
- 不要为多主而多主——冲突解决的复杂性远超收益

## 4.5 无主复制与 Quorum

📜 [Dynamo 2007]

### 4.5.1 架构

无主（Leaderless）：所有副本地位平等，任一可接收读写。

```
        Client
          │
   ┌──────┼──────┐
   ▼      ▼      ▼
┌─────┐┌─────┐┌─────┐
│ N1  ││ N2  ││ N3  │  ← 副本集
└─────┘└─────┘└─────┘
```

### 4.5.2 Quorum 机制 ⭐

设副本数 $N$，写 Quorum $W$，读 Quorum $R$。

**写流程**：

```pseudocode
function write(key, value):
    # 1. 客户端发送到所有 N 个副本
    responses = []
    for each replica in N:
        async send(key, value, timestamp)
    # 2. 等待 W 个 ACK
    wait until W responses received
    return success
```

**读流程**：

```pseudocode
function read(key):
    # 1. 客户端发送到所有 N 个副本
    responses = []
    for each replica in N:
        async send(key)
    # 2. 等待 R 个响应
    wait until R responses received
    # 3. 返回最新版本
    return latest(responses)
```

### 4.5.3 Quorum 强一致条件 ⭐

> **强一致条件**：$W + R > N$ 时，读写 Quorum 必有交集，读必能看到最新写。

**证明直觉**：

- 写成功的 $W$ 个副本，读成功的 $R$ 个副本
- 总共 $W + R$ 个「成功标记」，但只有 $N$ 个副本
- 由鸽巢原理，必有 $W + R - N \geq 1$ 个副本同时被写和读
- 该副本持有最新数据

**典型配置**：

| 配置 | W | R | N | 性质 |
|------|---|---|---|------|
| 强一致，均衡 | $\lceil (N+1)/2 \rceil$ | $\lceil (N+1)/2 \rceil$ | $N$ | 中等延迟 |
| 写快读慢 | 1 | $N$ | $N$ | 读强一致 |
| 写慢读快 | $N$ | 1 | $N$ | 写强一致 |
| 弱一致 | 1 | 1 | $N$ | 最终一致 |

**例**：$N=3$，$W=R=2$，则 $W+R=4 > 3$，强一致。

### 4.5.4 Quorum 的微妙问题

⚠️ **Quorum ≠ 线性一致**：

- $W+R>N$ 保证「读到最新写」
- 但不保证「读到所有写按顺序」
- 多客户端并发写时仍可能违反线性一致

要达到线性一致需配合：

- 时间戳排序（HLC/TrueTime）
- 读修复 + 反熵

### 4.5.5 工业实现

| 系统 | 默认 $N$ | 可调 $W, R$ |
|------|---------|-------------|
| **Cassandra** | 3 | `consistency level`：ONE / QUORUM / ALL |
| **Dynamo** | 3 | 配置 |
| **Riak** | 3 | 可配 |
| **Voldemort** | 3 | 可配 |

## 4.6 Read Repair 与 Anti-Entropy

无主复制下，副本可能不一致（部分写失败）。两种修复机制：

### 4.6.1 Read Repair（读时修复）⭐

```pseudocode
function read(key):
    responses = wait(R responses)
    if values_differ(responses):
        # 找到最新值
        latest = max_by_version(responses)
        # 异步推送给旧副本
        for each stale_replica:
            async send_repair(stale_replica, latest)
    return latest
```

**优点**：

- 修复发生在读路径，无需后台任务
- 热点数据持续修复

**缺点**：

- 冷数据不读不修复
- 仅修复读到的 key

### 4.6.2 Anti-Entropy（反熵）⭐

后台进程定期对比副本差异：

#### 基于 Merkle Tree

```pseudocode
# 每个副本维护 key-range 的 Merkle Tree
function antiEntropy():
    for each peer:
        # 1. 交换 Merkle Tree 根
        # 2. 对比子树，找出差异 range
        # 3. 同步差异 range 的数据
```

**优点**：

- 仅传输差异，带宽高效
- 修复所有 key

**缺点**：

- Merkle Tree 重建开销
- 修复延迟（周期性）

#### 基于全量扫描

- 简单但带宽开销大
- 适用于小数据集

### 4.6.3 工业实现

| 系统 | Read Repair | Anti-Entropy |
|------|-------------|--------------|
| Cassandra | 默认开启 | Merkle Tree（周期性） |
| Dynamo | 默认开启 | Merkle Tree |
| Riak | 默认开启 | Active Anti-Entropy（AAE） |

## 4.7 Sloppy Quorum 与 Hinted Handoff

### 4.7.1 问题

Quorum 要求写 $W$ 个**首选副本**（primary replicas）。但若部分首选副本故障：

- 严格 Quorum：写失败
- Sloppy Quorum：写其他「替补」节点

### 4.7.2 Sloppy Quorum

```pseudocode
function write(key, value):
    primary_replicas = hash(key) → top N nodes
    available = primary_replicas.filter(is_alive)
    if len(available) < W:
        # 用其他节点替补
        substitutes = next_n_alive_nodes()
        write_to = available + substitutes[:W - len(available)]
    else:
        write_to = available[:W]
    # 写入 write_to
```

⚠️ **关键**：Sloppy Quorum **不保证 $W + R > N$**（替补节点不在首选集中）。

### 4.7.3 Hinted Handoff

替补节点持有数据时附带「hint」标记真正归属节点：

```pseudocode
function write_to_substitute(substitute, key, value, hint=primary_owner):
    substitute.store(key, value, hint=primary_owner)

# 后台进程
function hintedHandoff():
    for each stored_key with hint:
        if hint_owner.is_alive:
            send(hint_owner, key, value)
            delete_local(key)
```

**优点**：

- 故障期间写不丢失
- 故障节点恢复后自动同步

**缺点**：

- 替补节点承担额外负载
- Hint 累积可能 OOM

### 4.7.4 工业实现

- **Cassandra**：默认开启 Hinted Handoff
- **Dynamo**：原生支持

⚠️ **生产陷阱**：Hinted Handoff 累积过多会导致节点恢复时压力过大（Cassandra 曾有相关事故）。

## 4.8 Chain Replication 与 CRAQ

### 4.8.1 Chain Replication 📜

📜 [van Renesse, Schneider 2004] *Chain Replication for Supporting High Throughput and Availability*：

```
HEAD → N1 → N2 → N3 → TAIL
```

- **写**：客户端写 HEAD，沿链传播到 TAIL，TAIL ACK 后返回
- **读**：客户端读 TAIL（保证强一致）

**优点**：

- 强一致（线性一致）
- 读吞吐高（仅 TAIL 处理读，但 TAIL 不处理写）
- 故障处理简单（移除节点）

**缺点**：

- 写延迟 = 链长度 × 单跳延迟
- TAIL 是读瓶颈

### 4.8.2 CRAQ 📜

📜 [Terrace, Freedman, Liu, et al. 2009] *Object Storage on CRAQ*：

- 每个节点保持**多版本**（已确认 + 脏）
- 写：沿链传播，每个节点存为「脏版本」
- 读：

  - 任意节点可读
  - 若该节点最新版本是干净的，直接返回
  - 否则向 TAIL 确认最新已提交版本

**优点**：

- 强一致 + 高读吞吐
- 读可分散到所有节点

**典型**：CRAQ、Microsoft Azure 的某些存储组件。

## 4.9 🎓 复制理论

### 4.9.1 状态机复制（SMR）⭐

📜 [Lamport 1978] / [Schneider 1990] *Implementing Fault-Tolerant Services Using the State Machine Approach*：

> **状态机复制**（State Machine Replication）：所有副本按相同顺序执行相同命令，则副本状态相同。

**三要素**：

1. **确定性状态机**：相同输入 → 相同输出 + 状态
2. **全序广播**：所有副本看到相同命令顺序
3. **副本独立性**：副本间无需协调（只要命令顺序一致）

**与共识等价**：

- 全序广播 = 共识
- SMR = 全序广播 + 确定性状态机
- Paxos/Raft 实现全序广播 → 实现 SMR

### 4.9.2 Virtual Synchrony

📜 [Birman, Joseph 1987]：

> **Virtual Synchrony**：进程组视图变更时，所有正确成员看到相同的视图变更顺序，且变更前的消息要么全部交付要么全部不交付。

介于同步与异步之间，用于组通信系统（如 JGroups、Spread）。

### 4.9.3 Primary-Backup 与 Quorum 的等价性

📜 [Attiya, Bar-Noy, Dolev 1995]：

- 在 $f < n/2$ 的 Crash 模型下
- Primary-Backup 与 Quorum 表达能力等价
- 任何一种可实现的一致性级别，另一种也可实现

### 4.9.4 Quorum 系统的负载与容量

📜 [Naor, Wool 1998] *The Load, Capacity, and Availability of Quorum Systems*：

- Quorum 系统的「负载」= 任一节点被访问的最大概率
- Majority Quorum 负载 = 1/2（最优）
- 不同 Quorum 拓扑（树、网格）影响负载与容错

## 4.10 🏭 工业实战

### 4.10.1 MySQL 复制详解

- **基于 binlog**：statement / row / mixed 三种格式
- **半同步**：MySQL 5.5+ 原生支持
- **MGR**（MySQL Group Replication）：基于 Paxos 变种
- **常见陷阱**：
  - ⚠️ 大事务导致 binlog 同步阻塞
  - ⚠️ 从库回放单线程 → 复制滞后（5.7+ 并行复制改善）
  - 🔥 生产建议：用 row 格式 + 半同步 + 并行复制

### 4.10.2 Kafka ISR 机制 🔥

- **ISR**（In-Sync Replicas）：与 Leader 同步的副本集
- Leader 故障时，从 ISR 中选新 Leader
- `acks=all` + `min.insync.replicas=2`：强一致 + 容错
- ⚠️ ISR 缩小到 1 时仍可写 → 数据可能丢失
- 🔥 生产建议：监控 ISR 数量，过小告警

### 4.10.3 Cassandra 读写路径

- **写**：写 CommitLog + MemTable，异步刷 SSTable
- **读**：BloomFilter → SSTable Index → SSTable Data
- **Read Repair**：读时检测副本差异，异步修复
- **Anti-Entropy**：Merkle Tree 周期对比
- ⚠️ **LeveledCompactionStrategy**：读性能稳定但写放大；**SizeTieredStrategy**：写快但读性能波动

### 4.10.4 MongoDB Replica Set

- 1 Primary + N Secondary + 1 Arbiter（可选）
- 选举基于 Raft 变种
- OpLog 异步复制
- ⚠️ WriteConcern=1（默认）→ 主故障丢数据
- 🔥 生产建议：`w=majority` + `j=true`

### 4.10.5 ⚠️ 工业陷阱汇总

- ⚠️ **异步复制丢数据**：MySQL 异步、Redis 异步、Kafka acks=1
- ⚠️ **从库读导致读己之写破坏**：写主读从时需 Sticky 或 Read-Your-Writes Token
- ⚠️ **Hinted Handoff 累积**：节点恢复时压力激增
- ⚠️ **Merkle Tree 重建开销**：大数据集 AE 周期长
- ⚠️ **复制滞后导致读旧值**：跨地域复制尤其严重

## 4.11 面试要点

### ⭐ Q1：三种复制架构的区别？

**骨架**：

1. 主从：单主写，从异步/同步复制；强一致可能；典型 MySQL
2. 多主：多主可写；冲突需解决；最终一致；典型 Cassandra 跨 DC
3. 无主：任一副本可写；Quorum 控制；典型 Dynamo、Cassandra

**关键点**：写入路径 + 一致性 + 典型系统

**加分项**：提到每种架构的优缺点与适用场景

### ⭐ Q2：Quorum 机制 W+R>N 为什么保证强一致？

**骨架**：

1. 写 W 个副本成功，读 R 个副本
2. 由鸽巢原理，W+R>N 时必有交集
3. 交集副本持有最新数据
4. 读时返回最新版本

**关键点**：鸽巢原理 + 交集必有

**加分项**：举例 N=3, W=R=2；指出 Quorum 不等于线性一致

### ⭐ Q3：同步、异步、半同步的取舍？

**骨架**：

1. 同步：强一致，高延迟，单副本故障阻塞
2. 异步：低延迟，主故障丢数据
3. 半同步：K 个 ACK，兼顾

**关键点**：延迟 vs 持久性的权衡

**加分项**：举例 MySQL 半同步、Kafka acks=all

### ⭐ Q4：Read Repair 和 Anti-Entropy 各是什么？

**骨架**：

1. **Read Repair**：读时发现副本不一致，异步修复旧副本
   - 优点：热数据持续修复
   - 缺点：冷数据不修复
2. **Anti-Entropy**：后台 Merkle Tree 对比，周期修复
   - 优点：修复所有 key
   - 缺点：周期延迟

**关键点**：触发时机（读 vs 后台）

**加分项**：提到 Merkle Tree 优化

### ⭐ Q5：Sloppy Quorum 是什么？为什么不保证强一致？

**骨架**：

1. 首选副本部分故障时，用替补节点
2. 替补不在首选集中
3. 写 W 个 + 读 R 个可能无交集
4. 故不保证 $W+R>N$

**关键点**：替补节点不在首选集

**加分项**：提到 Hinted Handoff

### ⭐ Q6：什么是状态机复制？与共识的关系？

**骨架**：

1. 所有副本按相同顺序执行相同命令 → 状态相同
2. 三要素：确定性状态机 + 全序广播 + 副本独立
3. 全序广播 = 共识
4. Paxos/Raft 实现全序广播 → 实现 SMR

**关键点**：全序广播 = 共识

**加分项**：提到确定性是关键（非确定性状态机无法 SMR）

### ⭐ Q7：主从复制的脑裂问题如何解决？

**骨架**：

1. 脑裂：旧主未真死，恢复后又接受写
2. 解决：Fencing Token（详见 §11）
3. 旧主写时 fence token 已过期，写被拒

**关键点**：Fencing

**加分项**：提到 STONITH（Shoot The Other Node In The Head）

### ⭐ Q8：Chain Replication 是什么？

**骨架**：

1. 副本组成链 HEAD→N1→...→TAIL
2. 写：HEAD → 沿链 → TAIL ACK
3. 读：TAIL
4. 强一致，读吞吐高

**关键点**：链式传播 + TAIL 处理读

**加分项**：提到 CRAQ 改进（读分散）

### ⭐ Q9：Kafka 的 ISR 是什么？

**骨架**：

1. ISR = 与 Leader 同步的副本集
2. Leader 故障从 ISR 选新 Leader
3. acks=all + min.insync.replicas=K 保证强一致
4. ISR 缩小到 1 时仍可写但有丢数据风险

**关键点**：ISR 动态调整

**加分项**：提到 ISR 监控告警

### ⭐ Q10：Cassandra 默认一致性是什么？怎么调强一致？

**骨架**：

1. 默认 ONE（最终一致，低延迟）
2. 调到 QUORUM：W+R>N，强一致
3. 调到 ALL：最强一致，最高延迟
4. 通过 consistency level 在 C 与 L 间切换

**关键点**：可调一致性

**加分项**：提到 LOCAL_QUORUM 跨 DC 优化
