## 0. 为什么需要分片

单机存储/吞吐的天花板由物理资源决定（CPU、内存、磁盘 IOPS、网络带宽）。当数据量或 QPS 超过单机上限时,只有两条路:

1. **垂直扩展 (Scale-Up)**:换更强的机器。成本指数上升,存在硬上限。
2. **水平扩展 (Scale-Out)**:把数据分散到多台机器。这就是**分片 (Sharding / Partitioning)**。

分片与复制是正交的两个维度:

```
复制 (Replication): 同一份数据有多个副本,提升可用性与读吞吐
分片 (Partitioning): 不同数据分布在不同节点,提升写吞吐与总容量
```

二者组合形成工业系统常见的 **分区-副本 (Partition-Replica)** 拓扑:每个分片有 1 个 Leader + N 个 Follower。

分片的核心难题不是"如何切",而是**切完之后如何路由、如何再平衡、如何避免热点**。本章围绕这三件事展开。

## 1. 定义与动机

### 1.1 分片的本质

> 把 key space $K$ 划分为 $P$ 个不相交的子集 $\{P_1, P_2, \dots, P_n\}$,满足 $\bigcup P_i = K$ 且 $P_i \cap P_j = \emptyset (i \ne j)$,并由路由函数 $f: K \to \{1, \dots, n\}$ 决定 key 属于哪个分片。

### 1.2 设计目标

| 目标 | 含义 | 冲突 |
|------|------|------|
| **均匀性 (Uniformity)** | 各分片数据量/QPS 大致相等 | 与数据倾斜天然冲突 |
| **稳定性 (Stability)** | 节点增减时 key 迁移量最小 | 与"完全均匀"冲突 |
| **确定性 (Determinism)** | 同一 key 永远落到同一分片 | 与"动态调度"冲突 |
| **局部性 (Locality)** | 相关 key 落到同一分片,支持范围查询 | 与"哈希均匀"冲突 |
| **可发现性 (Discoverability)** | 客户端能快速定位 key 所在节点 | 与"去中心化"部分冲突 |

> ⚠️ **易错点**:均匀性 ≠ 稳定性。`key mod N` 完全均匀,但 $N$ 变化时几乎所有 key 都要迁移;一致性哈希牺牲"绝对均匀"换"最小迁移"。

### 1.3 常见分片策略速览

| 策略 | 路由函数 | 优点 | 缺点 |
|------|---------|------|------|
| **Range Sharding** | key 落在区间 $[a,b)$ | 支持范围扫描 | 易热点(顺序写) |
| **Hash Sharding** | $h(k) \mod N$ | 均匀、简单 | $N$ 变化时大迁移 |
| **Consistent Hashing** | ring + 顺时针找节点 | 增减节点迁移少 | 节点少时不均 |
| **Virtual Node** | 一致性哈希 + 多虚节点 | 均匀性 ↑ | 路由表变大 |
| **Rendezvous Hashing** | $\arg\max_i h(k, i)$ | 均匀、无虚节点 | $O(N)$ 计算 |
| **Jump Hash** | 跳跃查找 | $O(\log N)$、内存小 | 不支持任意节点删除顺序 |
| **Maglev** | 查表 + 偏移序列 | 接近均匀、查找 $O(1)$ | 构表 $O(M \cdot N)$ |

## 2. 原理与算法

### 2.1 哈希分片 (Hash Partitioning)

最朴素的方案:

$$\text{shard}(k) = \text{hash}(k) \bmod N$$

- 优点:实现简单,均匀性好。
- 致命缺陷:**节点数 $N$ 变化时,$N \cdot \frac{|N'-N|}{N'}$ 比例的 key 需要迁移**。例如 $N=10 \to N=11$,约 90% 的 key 被重定位。

```java
// Java: 朴素 hash 分片
public class HashSharder {
    private final int n;
    public HashSharder(int n) { this.n = n; }
    public int shard(String key) {
        return Math.floorMod(key.hashCode(), n);
    }
}
```

```go
// Go: 朴素 hash 分片
func shard(key string, n int) int {
    h := fnv.New32a()
    h.Write([]byte(key))
    return int(h.Sum32()) % n
}
```

适用场景:$N$ 永不变(如静态分库分表),或可接受全量迁移。

### 2.2 一致性哈希 (Consistent Hashing)

> 📜 Karger et al., 1997, MIT — *Consistent Hashing and Random Trees*

#### 2.2.1 核心思想

把 key 和节点都映射到同一**哈希环**上,$\text{hash} \in [0, 2^{32})$。key 顺时针找到的**第一个节点**即为路由目标。

```
        0
       / \
   Node A   Node C
      |      |
   key1   key2
       \ /
      Node B
```

#### 2.2.2 稳定性证明 (直觉)

考虑节点集合 $S \to S' = S \cup \{x\}$。新节点 $x$ 只接管环上 $(x, x']$ 段的 key(其中 $x'$ 是 $x$ 在 $S$ 中的前驱)。这段的期望长度为 $\frac{1}{|S|+1}$,因此**新增一个节点平均只迁移 $\frac{1}{N+1}$ 的 key**,与朴素 hash 的 $\frac{N}{N+1}$ 形成鲜明对比。

删除节点同理:被删节点的 key 全部迁移到其后继。

#### 2.2.3 均匀性问题

当节点数 $N$ 较小时,环上节点分布不均(随机性导致某些节点管辖的弧段远大于其他)。解决方案:**虚拟节点 (Virtual Node / vnode)**。每个物理节点对应 $V$ 个虚节点($V \approx 100 \sim 200$)。

```java
public class ConsistentHash<V> {
    private final TreeMap<Integer, V> ring = new TreeMap<>();
    private final int virtualNodes;  // 每个物理节点的虚节点数
    private final HashFunction hash;

    public ConsistentHash(int virtualNodes, HashFunction hash) {
        this.virtualNodes = virtualNodes;
        this.hash = hash;
    }

    public void addNode(V node) {
        for (int i = 0; i < virtualNodes; i++) {
            int h = hash.hash(node.toString() + "#" + i);
            ring.put(h, node);
        }
    }

    public void removeNode(V node) {
        for (int i = 0; i < virtualNodes; i++) {
            int h = hash.hash(node.toString() + "#" + i);
            ring.remove(h);
        }
    }

    public V route(String key) {
        if (ring.isEmpty()) return null;
        int h = hash.hash(key);
        // 顺时针找第一个 >= h 的节点
        Map.Entry<Integer, V> e = ring.ceilingEntry(h);
        return e != null ? e.getValue() : ring.firstEntry().getValue();
    }
}
```

```go
type ConsistentHash struct {
    ring         map[uint32]string
    hashes       []uint32  // 排序后的 hash 列表
    virtualNodes int
}

func (c *ConsistentHash) AddNode(node string) {
    for i := 0; i < c.virtualNodes; i++ {
        h := crc32.ChecksumIEEE([]byte(fmt.Sprintf("%s#%d", node, i)))
        c.ring[h] = node
        c.hashes = append(c.hashes, h)
    }
    sort.Slice(c.hashes, func(i, j int) bool { return c.hashes[i] < c.hashes[j] })
}

func (c *ConsistentHash) Route(key string) string {
    if len(c.hashes) == 0 {
        return ""
    }
    h := crc32.ChecksumIEEE([]byte(key))
    // 二分查找第一个 >= h 的位置
    idx := sort.Search(len(c.hashes), func(i int) bool { return c.hashes[i] >= h })
    if idx == len(c.hashes) {
        idx = 0
    }
    return c.ring[c.hashes[idx]]
}
```

#### 2.2.4 复杂度

| 操作 | 复杂度 | 备注 |
|------|--------|------|
| 路由 | $O(\log (NV))$ | 二分查找排序数组 |
| 增删节点 | $O(V \log (NV))$ | 插入/删除 $V$ 个虚节点 |
| 内存 | $O(NV)$ | 每个虚节点一个条目 |

### 2.3 Rendezvous Hashing (HRW)

> 📜 Thaler & Ravishankar, 1996 — *A Name-Based Mapping Scheme for Rendezvous*

也称作 **Highest Random Weight (HRW)**。

$$\text{shard}(k) = \arg\max_{i \in S} h(k, i)$$

其中 $h$ 是某个哈希函数(如 MD5、Murmur)。

- 优点:无需虚节点即可达到理论上的最优均匀性;增删节点时只迁移 $\frac{1}{N}$ 的 key,与一致性哈希相同。
- 缺点:路由需要计算所有节点的 $h(k, i)$,$O(N)$。

```python
import hashlib

def rendezvous(key: str, nodes: list[str]) -> str:
    """HRW: 选择权重最大的节点"""
    def weight(k: str, n: str) -> int:
        h = hashlib.md5(f"{k}:{n}".encode()).digest()
        return int.from_bytes(h[:8], 'big')
    return max(nodes, key=lambda n: weight(key, n))
```

```go
func rendezvous(key string, nodes []string) string {
    var best string
    var bestW uint64
    for _, n := range nodes {
        h := md5.Sum([]byte(key + ":" + n))
        w := binary.BigEndian.Uint64(h[:8])
        if w > bestW {
            bestW = w
            best = n
        }
    }
    return best
}
```

**优化**:用 weighted rendezvous (Skeletal Hashing / Maglev-like) 把 $O(N)$ 降到 $O(\log N)$,但牺牲少量均匀性。

适用:节点数中等(几十到几百)、且需要"无虚节点结构"的场景,如 Cache 路由、DNS 路由。

### 2.4 Jump Consistent Hash

> 📜 Lamping & Veach, Google, 2014 — *A Fast, Minimal Memory, Consistent Hashing Algorithm*

Jump Hash 解决的问题是:**给定 $N$ 个节点,key 在 $[0, N)$ 中分布,且当 $N \to N+1$ 时只迁移 $\frac{1}{N+1}$ 的 key**。它要求节点编号必须是 $0, 1, \dots, N-1$ 连续整数。

```go
// Google 官方实现(仅 7 行)
func JumpHash(key uint64, numBuckets int) int {
    var b, j int64
    b = -1
    j = 0
    for j < int64(numBuckets) {
        b = j
        key = key*2862933555777941757 + 1
        j = int64(float64(b+1) * (float64(int64(1<<31)) / float64((key>>33)+1)))
    }
    return int(b)
}
```

```python
def jump_hash(key: int, num_buckets: int) -> int:
    b, j = -1, 0
    while j < num_buckets:
        b = j
        key = (key * 2862933555777941757 + 1) & 0xFFFFFFFFFFFFFFFF
        j = int((b + 1) * (float(1 << 31) / float((key >> 33) + 1)))
    return b
```

- 时间复杂度:$O(\log N)$。
- 空间复杂度:$O(1)$ — 这是一致性哈希中**唯一**做到常数空间的算法。
- 缺点:节点必须是连续编号,无法处理"任意节点删除"的场景(节点 3 删了,4/5/... 必须前移)。

工业应用:Vipshop、YouTube CDN、Google 多处内部系统;Vipshop 替换 Memcached 的一致性哈希后 CPU 显著下降。

### 2.5 Maglev 一致性查表

> 📜 Google, 2016, NSDI — *Maglev: A Fast and Reliable Software Network Load Balancer*

Maglev 是 Google 软件负载均衡器,每秒百万级 QPS,核心创新是 **Lookup Table + 偏移序列 (Permutation)**。

#### 算法流程

1. 选择表大小 $M$,$M$ 是远大于节点数 $N$ 的素数(如 $M = 65537$,$N \approx 100$)。
2. 对每个节点 $i$,生成一个长度为 $M$ 的偏移序列 $P_i = [\text{offset}_i, (\text{offset}_i + \text{skip}_i) \bmod M, (\text{offset}_i + 2 \cdot \text{skip}_i) \bmod M, \dots]$。
3. 通过"贪心走环"把每个节点依次填入查找表 `table[M]`,保证每个节点至少出现 $\lfloor M/N \rfloor$ 次。
4. 查找:`shard(k) = table[hash(k) mod M]`,**$O(1)$**。

```
构造阶段:
  对每一列 c in 0..M-1:
    for each node i (按优先级排序):
      idx = P_i[c]   # 该节点想填的位置
      while table[idx] 已被占用:
          idx = (idx + 1) mod M
      table[idx] = i
```

- 优点:查找 $O(1)$;节点变化时迁移量接近 $\frac{1}{N}$(略高于一致性哈希,因表项被替换时非"理想迁移")。
- 缺点:构表 $O(M \cdot N)$,节点频繁变化时构表开销大。

```go
const M = 65537

type Maglev struct {
    table [M]int
    nodes []string
}

func (m *Maglev) buildLookup() {
    // 1. 计算每个节点的 offset / skip
    offsets := make([]int, len(m.nodes))
    skips := make([]int, len(m.nodes))
    for i, n := range m.nodes {
        h := sha1.Sum([]byte(n))
        offsets[i] = int(binary.BigEndian.Uint32(h[:4])) % M
        skips[i] = (int(binary.BigEndian.Uint32(h[4:8])) % (M - 1)) + 1
    }
    // 2. 贪心填充
    for i := range m.table {
        m.table[i] = -1
    }
    filled := 0
    indices := make([]int, len(m.nodes))  // 每个节点走到第几步
    for filled < M {
        for i := range m.nodes {
            if filled >= M { break }
            idx := (offsets[i] + indices[i]*skips[i]) % M
            for m.table[idx] >= 0 {
                idx = (idx + 1) % M
            }
            m.table[idx] = i
            indices[i]++
            filled++
        }
    }
}

func (m *Maglev) Route(key string) string {
    h := sha1.Sum([]byte(key))
    idx := int(binary.BigEndian.Uint32(h[:4])) % M
    return m.nodes[m.table[idx]]
}
```

工业应用:Google Maglev、GCP L7 LB、Cloudflare(变体)、Kubernetes MetalLB(部分实现)。

### 2.6 路由与元数据管理

**核心矛盾**:节点知道全部分片 → 路由 $O(1)$ 但增删节点要全量广播;节点只知道本地分片 → 增删灵活但客户端要查元数据。

| 模式 | 元数据位置 | 路由 | 优缺点 |
|------|-----------|------|--------|
| **中心化路由表** | 元数据服务 (MDS) | 客户端 → MDS → 节点 | 客户端轻、MDS 单点风险 |
| **客户端缓存 + MDS** | MDS + 客户端缓存 | 客户端缓存命中直接访问 | 平衡,常见方案 |
| **去中心化 (Gossip)** | 每个节点持有部分 + Gossip 同步 | 任意节点可重定向 | 强去中心、最终一致 |
| **路由层代理** | Proxy 持有路由表 | 客户端 → Proxy → 节点 | 客户端零感知、多一跳 |

#### 2.6.1 中心化 (HBase / MySQL Sharding-Sphere / TiDB PD)

HBase 通过 `MetaRegionServer` 提供全局 Region 路由表;客户端缓存后直接访问 RegionServer。Region 分裂/合并时 PD/Master 推送或客户端刷新。

#### 2.6.2 去中心化 (Cassandra / Dynamo)

Cassandra 通过 Gossip 同步集群状态,每个节点都知道所有 token range 的归属。客户端可连任意节点,被路由到正确节点(返回 `UNAVAILABLE` 或重定向)。

### 2.7 再平衡 (Rebalancing)

当节点增减、负载不均时,需要把部分 key 从一个节点迁移到另一个。设计要点:

1. **最小迁移**:只迁移"必要"的 key,而非全量 rehash。
2. **在线迁移**:迁移期间双写或读修复,避免服务中断。
3. **反压**:迁移速度受限于目标节点的 IO/CPU,需限速。
4. **回滚**:迁移失败要能恢复原状态。

#### 一致性哈希下的再平衡

新增节点 $x$ 时,$x$ 的前驱 $p$ 需要把 $(p, x]$ 范围内的 key 同步给 $x$:

```python
def rebalance_add(ring, new_node, data_store):
    pred = ring.predecessor(new_node)
    migrate_keys = [k for k in data_store[pred] if ring.route(k) == new_node]
    for k in migrate_keys:
        data_store[new_node].put(k, data_store[pred].get(k))
        data_store[pred].delete(k)  # 双写期间用 tombstone
```

#### 范围分片下的再平衡 (HBase Region Split/Merge)

- **Split**:Region 太大(默认 10GB)时一分为二,旧的 Region 下线,新的两个上线。
- **Merge**:两个相邻小 Region 合并为一个。
- **Move**:Region Server 负载不均时,把 Region 从一个 RS 移到另一个(底层是 HDFS 复制 + WAL 切换)。

### 2.8 分片键设计与热点问题

#### 2.8.1 分片键选择原则

1. **高基数**:取值范围大,避免数据集中。
2. **分布均匀**:统计直方图接近均匀。
3. **查询局部性**:常用查询条件包含分片键,避免广播查询。
4. **不可变**:分片键一旦确定就不应改变(否则需全量迁移)。

> ⚠️ **易错**:用 `user_id` 作为分片键,但如果某大 V 用户的数据量是普通用户的 $10^6$ 倍,该分片成为**单点热点**。需要"热点打散"。

#### 2.8.2 热点打散方案

| 方案 | 做法 | 代价 |
|------|------|------|
| **Salting** | key 前加随机前缀:`{0..N-1}_hotKey` | 范围查询需广播 |
| **Hashing Suffix** | key 后加 hash 后缀 | 范围查询失效 |
| **Bucketing** | 一个逻辑分片拆成 $K$ 个物理分片,聚合时合并 | 写入路径变复杂 |
| **动态分裂** | 监控热点自动 split | 治标不治本,雪崩风险 |
| **LDC 单元化** | 按 user_id 取模分配到固定单元 | 跨单元访问需路由层 |

HBase 的热点处理典型做法是 **Salted Key + Pre-Split**:

```java
// HBase: 创建表时预分裂,避免默认全部写入第一个 Region
byte[][] splits = new byte[][] {
    Bytes.toBytes("0"), Bytes.toBytes("1"), Bytes.toBytes("2"),
    /* ... */ Bytes.toBytes("9"), Bytes.toBytes("a"), /* ... */
};
admin.createTable(TableDescriptorBuilder.newBuilder(TableName.valueOf("events"))
    .setColumnFamily(ColumnFamilyDescriptorBuilder.newBuilder(Bytes.toBytes("cf")).build())
    .build(), splits);
```

## 3. 🎓 学术深度

### 3.1 一致性哈希的迁移量上界

> 📜 Karger 1997 原文 Proposition: 对 $|S| = N$ 个节点,新增 1 个节点时,期望迁移的 key 数为 $\frac{K}{N+1}$,且**以高概率**不超过 $\frac{K \cdot \ln N}{N}$。

**证明 (sketch)**:把环看作 $[0,1)$ 上的随机点,新增点 $x$ 后,其接管的前驱段长度 $L$ 服从 $\text{Beta}(\alpha=1, \beta=N-1)$,期望 $E[L] = \frac{1}{N}$。$L$ 的尾界由 $\Pr[L > t] \le (1-t)^{N-1} \le e^{-(N-1)t}$ 给出,取 $t = \frac{\ln N}{N}$ 即得上界。

### 3.2 虚节点的均匀性收敛

设虚节点数为 $V$,$N$ 个物理节点。每个物理节点管辖的环弧段总长 $S_i = \sum_{j=1}^{V} L_{i,j}$,其中 $L_{i,j}$ i.i.d. $\sim \text{Exp}(NV)$。

由大数定律:$\frac{S_i}{1/N} \to 1$ a.s.,即 $S_i \approx \frac{1}{N}$。方差由 Chernoff bound 控制:

$$\Pr\left[\left|S_i - \frac{1}{N}\right| > \epsilon \cdot \frac{1}{N}\right] \le 2 \exp\left(-\frac{V \epsilon^2}{3}\right)$$

工程上取 $V = 150 \sim 200$ 即可将负载偏差控制在 $\pm 10\%$ 内(以高概率)。Cassandra 默认 $V=256$。

### 3.3 Rendezvous Hashing 的对称性

HRW 满足 **Symmetry / Balance / Monotonicity / Spread / Load** 五条公理(Karger 1997 列出的一致性哈希应满足的性质),且在节点权重相等时达到理论最优:

- **Monotonicity**:节点集合 $S \to S'$($S \subseteq S'$),key 不会从 $S$ 中的节点移到 $S' \setminus S$ 之外。
- **Spread**:对同一 key,不同客户端路由结果一致(无状态)。

HRW 的劣势仅在于 $O(N)$ 路由成本,这可以通过 **Skeletal Hashing** 改进(分组 + HRW 嵌套,降到 $O(\log N)$)。

### 3.4 Jump Hash 的概率分析

Jump Hash 的核心循环:

$$j \leftarrow (b+1) \cdot \frac{2^{31}}{(k \gg 33) + 1}$$

直觉:每次 $j$ 跳跃到一个新位置 $b' > b$,其分布使得 $\Pr[\text{key 最终在 } b] = 1/N$,且 $N$ 增加时只迁移 $\frac{1}{N+1}$ 的 key。Lamping & Veach 在原文用 **几何分布** 证明了这一性质:每个"跳跃步长"对应几何分布的累积分布,期望跳跃次数 $O(\ln N)$。

### 3.5 Maglev 的最小冲突填充

Maglev 的贪心填充算法本质是"轮转调度 + 偏移序列",论文证明:

- 每个节点在表中至少出现 $\lfloor M/N \rfloor$ 次,至多 $\lceil M/N \rceil$ 次。
- 节点变更时,迁移量"高概率"不超过 $O(M/N)$,与传统一致性哈希相当。

> 🎓 **学术延伸**:Maglev 的偏移序列 $P_i$ 设计要求 $\gcd(\text{skip}_i, M) = 1$,$M$ 为素数,以保证 $P_i$ 是 $[0, M)$ 的置换。否则表中会留下空洞。

### 3.6 一致性哈希与无状态路由的等价

> 📜 Goel et al., 2014 — *A New Near-Optimal Consistent Hash Function*

一致性哈希族 $\mathcal{H}$ 满足:$\forall S, \forall k$,$\Pr[h(k) \in S] = \frac{|S|}{|\text{全集}|}$。这等价于无状态随机路由的"长期均匀性",只是把随机性"固化"到 $h$ 上。这一视角把"分片"与"路由"统一在概率论下。

## 4. 🏭 工业实战

### 4.1 Dynamo / Cassandra:Token Ring + vnode

Dynamo (📜 DeCandia 2007) 首次大规模工业落地一致性哈希 + vnode:

- **Token Ring**:每节点被分配 $V$ 个 token(默认 $V=256$),环上总点数 $NV$。
- **复制**:顺时针取接下来 $N-1$ 个**不同物理节点**作为副本(Rack-Aware 策略避免同机架多副本)。
- **Read Repair / Hinted Handoff**:写入失败时把数据暂存到协调者的"提示"节点,目标节点恢复后回传。

Cassandra 进一步引入:

- **Virtual Node (vnode)**:从早期手工分配 token 到自动分配,运维大幅简化。
- **Range Tombstone**:删除大范围 key 时使用 range tombstone,避免逐 key 标记。

```
Cassandra 复制拓扑 (RF=3):
  Node A: token [0, 1000)  ← key k1 (hash=500)
                          → 副本: Node A, B, C (顺时针前 3 个不同节点)
```

### 4.2 Redis Cluster:16384 Slot

Redis Cluster 不用一致性哈希,而用 **固定 16384 slot**:

- $\text{slot}(k) = \text{CRC16}(k) \bmod 16384$。
- 集群有 16384 个 slot,每个节点负责一部分。
- 客户端缓存 slot → node 映射,变更时通过 `MOVED`/`ASK` 重定向。

```python
def slot(key: str) -> int:
    # Redis 实际使用 hash tag 优化:取 {tag} 内的部分计算
    if "{" in key and "}" in key:
        start = key.index("{")
        end = key.index("}", start + 1)
        if end > start + 1:
            key = key[start+1:end]
    return crc16(key) % 16384
```

**Hash Tag**:用 `{user:1001}:cart`、`{user:1001}:profile` 让同一 user 的多个 key 落到同一 slot,支持多键事务。

**为什么 16384?** 作者 antirez 解释:Redis 节点间用 gossip 同步 slot 映射,每比特表示 1 个 slot 是否归本节点。16384 bit = 2KB,在 gossip 包里开销可接受;选 65536 会让心跳包过大,选 1024 又限制集群规模(单节点平均 slot 数 < 1)。16384 是经验权衡。

### 4.3 HBase:Range Region + Meta 表

HBase 走 Range 路线:

- 表按 rowkey 字典序划分成多个 **Region**,每个 Region 是连续范围 $[start, end)$。
- RegionServer 承载若干 Region;`hbase:meta` 表记录所有 Region 的位置。
- 客户端首次访问时:`ZK → hbase:meta → RegionServer`,之后缓存。

热点问题(HBase 著名的"顺序写热点"):

- rowkey 自增会导致所有写入打到最后一个 Region。
- 解决:rowkey 前加 `[salt_prefix] = hash(key) mod N`,或反转 rowkey。

```java
// HBase: 用 salt 避免时间序列热点
byte[] saltedRowkey = Bytes.add(
    Bytes.toBytes(Math.abs(Bytes.hashCode(userId) % 16)),  // 0~15 的 salt
    Bytes.toBytes("|"),
    Bytes.toBytes(timestamp),
    Bytes.toBytes("|"),
    Bytes.toBytes(userId)
);
```

### 4.4 TiDB / CockroachDB:Range + Raft

TiDB 类似 HBase 但每个 Range 是一个 **Raft Group**:

- PD (Placement Driver) 维护全局 Range 元数据。
- Range 大小默认 96MB,自动分裂/合并。
- 写入通过 Raft 复制到 3 副本。

热点处理:PD 监控 QPS/流量,自动分裂热点 Range;客户端可加 `SHARD_ROW_ID_BITS` 让自增主键打散。

```sql
-- TiDB: 显式打散自增 ID
CREATE TABLE events (
    id BIGINT NOT NULL PRIMARY KEY CLUSTERED,
    data VARCHAR(255)
) SHARD_ROW_ID_BITS = 4 PRE_SPLIT_REGIONS = 4;
-- 4 位 shard → 16 个 pre-split region,避免冷启动热点
```

### 4.5 Kafka:Partition + Replica

Kafka 分片称为 **Partition**:

- 每个 topic 有 $P$ 个 partition,producer 按 key hash 路由:`partition = hash(key) % P`。
- partition 分布在 broker 上,每个 partition 有 1 leader + N follower。
- **Consumer Group**:同一 group 内的 consumer 各自消费不同 partition,实现并行。

热点:**partition 数固定**,某个 key QPS 过高时整个 partition 饱和。解决:

- 增加 partition 数(但 key 已 hash 不能改),或
- producer 端打散:把单一 key 拆成 `key_0, key_1, ..., key_K`,consumer 聚合。

### 4.6 热点打散实战清单 (阿里巴巴双 11)

| 场景 | 策略 |
|------|------|
| 大 V 微博 feed | 按 `user_id` hash 后再加 8 个子分片,合并读 |
| 秒杀商品库存 | Redis 集群 + 库存分片(库存 1000 → 10 个分片各 100),CAS 扣减 |
| 订单 ID 主键 | 雪花算法 + 反转低位做分片键 |
| 全局序列号 | TDDL Sequence + 分段缓存(每节点取 1000 段) |

## 5. 面试要点

### 5.1 高频问答

**Q1: 什么是一致性哈希?解决了什么问题?**

> 把节点和 key 映射到同一哈希环,key 顺时针找到的第一个节点即为路由目标。解决传统 hash 模 N 在节点增减时**几乎所有 key 都要迁移**的问题,使迁移量降到 $\frac{1}{N+1}$。

**Q2: 一致性哈希为什么需要虚拟节点?**

> 节点数少时,环上节点分布不均,导致某些节点负载是其他节点的数倍。引入虚拟节点(每个物理节点对应 $V$ 个虚节点,$V \approx 150$)后,由大数定律,负载偏差收敛到 $O(1/\sqrt{V})$。

**Q3: Jump Hash 与一致性哈希环相比的优劣?**

> Jump Hash 优点:$O(\log N)$ 路由,$O(1)$ 内存。缺点:节点必须连续编号 $0..N-1$,不支持任意节点删除(必须重映射);无虚节点机制,无法直接表达"节点权重"。

**Q4: Redis Cluster 为什么用 16384 slot 而不是一致性哈希?**

> 16384 是固定值,gossip 包 2KB 可承载;节点变更时通过 MOVED 重定向,客户端缓存易维护;slot 数固定让 slot → node 映射可以用 bitmap 表达。一致性哈希环在 1000+ 节点时路由表过大且不直观。

**Q5: Maglev 的查找复杂度?为什么这么快?**

> $O(1)$。因为查找就是 `table[hash(key) mod M]`,直接数组下标。代价是构表 $O(M \cdot N)$,且表大小 $M$ 固定(Google 用 65537)。适合"节点变化少、QPS 极高"的负载均衡场景。

**Q6: 分片键选择有哪些原则?**

> (1) 高基数;(2) 分布均匀;(3) 查询条件覆盖,避免广播;(4) 不可变;(5) 业务语义清晰。具体场景:订单系统常用 `user_id`,日志系统常用 `timestamp + hash`,社交关系常用 `user_id`。

**Q7: 一致性哈希如何处理节点删除?**

> 把被删节点的虚节点全部从环上移除,其 key 全部迁移到环上对应位置的下一个节点。迁移量等于被删节点承载的 key 数,即 $\frac{K}{N}$。

**Q8: 数据倾斜怎么解决?**

> (1) Salt/Hash 后缀打散;(2) vnode 增加均匀性;(3) 动态分裂(HBase Region Split);(4) 业务层"大 key 拆分"(如把超大 list 拆成多个小 list,key 加 `_0/_1/...` 后缀)。

### 5.2 易错点 ⚠️

1. **"一致性哈希就是 ring"** — 错。Rendezvous HRW 也是一致性哈希,只是不画环。
2. **"vnode 越多越好"** — 错。vnode 增加内存和路由表大小;Cassandra 早期 100,稳定后默认 256。
3. **"Range Sharding 必然热点"** — 错。Range 优势是范围扫描,只对**单调自增 key** 才有热点问题。
4. **"Hash 分片一定均匀"** — 错。哈希函数本身可能倾斜(MurmurHash 较好,Java String.hashCode 在短 key 上分布差)。
5. **"客户端缓存路由表就高可用了"** — 错。客户端缓存过期前会路由到旧节点,需要服务端 `MOVED`/重定向。

## 9. 速查表 (Cheat Sheet)

```
选型决策树:
  节点变化频繁?
    Yes → 一致性哈希 + vnode (Dynamo/Cassandra 风格)
         需要 O(1) 查找? → Maglev
         需要 O(log N) 查找、O(1) 内存、节点连续? → Jump Hash
    No  → 范围分片 (HBase/TiDB 风格)
         需要范围扫描? → Range Sharding
         只需点查? → Hash Sharding / Redis Slot

节点数:
  < 100   → 任意方案均可,vnode=100~150
  100~1k  → vnode=150~256,或 Jump Hash
  > 1k    → Maglev (查找表内存可控) 或 TiDB Range

热点场景:
  写热点 → Salt + Pre-Split
  读热点 → 多级缓存 + 副本就近
  Key 热点 → 业务拆分 (大 key → 多小 key)
```
