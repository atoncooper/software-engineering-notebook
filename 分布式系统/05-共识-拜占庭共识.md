# 第 5 章 共识 —— 拜占庭容错（PBFT 与 HotStuff）

> **本章导读**
> Paxos/Raft 假设节点要么正常要么沉默（Crash 模型）。但区块链、跨组织系统面临**拜占庭故障**——节点可任意行为，包括撒谎、伪造。PBFT（1999）是第一个实用的拜占庭容错算法，需 $n \geq 3f+1$ 节点、3 阶段消息。HotStuff（2018）将消息复杂度优化到线性 $O(n)$，是 Libra/Diem 的共识基础。本章覆盖拜占庭共识的核心算法与工程演进。

## 5.1 拜占庭共识概述

### 5.1.1 为什么需要拜占庭共识

- **Crash 模型**（Paxos/Raft）：节点要么正常要么沉默
- **Byzantine 模型**：节点可任意行为（撒谎、伪造、共谋）

**适用场景**：

- 区块链（比特币、以太坊）
- 跨组织系统（多方数据库）
- 金融结算（多方签名）

### 5.1.2 容错下界 ⭐

> **$n \geq 3f+1$**：在异步系统 + 拜占庭故障下，共识需要至少 $3f+1$ 节点。

**直觉**：

- $n$ 节点中 $f$ 个拜占庭
- 需要 $n - f$ 个节点响应（容忍 $f$ 不响应）
- 其中 $f$ 个可能是拜占庭
- 故诚实响应 $= n - 2f$，需大于 $f$（拜占庭）才能 majority
- $n - 2f > f \Rightarrow n > 3f \Rightarrow n \geq 3f+1$

### 5.1.3 与 Crash 共识对比

| 维度 | Crash（Paxos/Raft） | Byzantine（PBFT/HotStuff） |
|------|---------------------|---------------------------|
| 故障假设 | 节点 Crash | 节点可任意行为 |
| 容错下界 | $n \geq 2f+1$ | $n \geq 3f+1$ |
| 消息验证 | 不需要 | 需要签名/MAC |
| 消息复杂度 | $O(n)$ | $O(n^2)$（PBFT） / $O(n)$（HotStuff） |
| 阶段数 | 2 | 3（PBFT） / 4（HotStuff） |
| 典型 | 数据库、协调服务 | 区块链、跨组织 |

## 5.2 PBFT ⭐

📜 [Castro, Liskov 1999] *Practical Byzantine Fault Tolerance*

### 5.2.1 系统模型

- 异步系统 + $n = 3f+1$ 节点
- 拜占庭故障 $\leq f$
- 节点间消息可能延迟、乱序，但最终交付
- **签名/MAC** 验证消息真实性

### 5.2.2 三阶段流程 ⭐

```
Client ──► Primary ──► Backup1, Backup2, ... (n-1 个)
                │
                ▼
        Phase 1: Pre-Prepare
                │
                ▼
        Phase 2: Prepare
                │
                ▼
        Phase 3: Commit
                │
                ▼
        执行 + 回复 Client
```

#### Phase 1: Pre-Prepare

```pseudocode
# Primary 收到 Client 请求
function onReceiveRequest(req):
    seq = next_seq()
    msg = (VIEW, seq, digest(req))
    # 签名
    signed_msg = sign(msg, primary_private_key)
    # 广播给所有 Backups
    for each backup:
        send(PRE-PREPARE, signed_msg)

# Backup 收到 Pre-Prepare
function onReceivePrePrepare(msg):
    if verify_signature(msg) and
       msg.view == current_view and
       not already_received(msg.seq):
        log(msg)
        # 进入 Prepare 阶段
        broadcast(PREPARE, msg.seq, msg.digest)
```

**作用**：Primary 提议请求顺序。

#### Phase 2: Prepare

```pseudocode
# Backup 收到 2f 个 Prepare
function onReceivePrepare(msg):
    if verify_signature(msg) and msg.seq matches logged pre-prepare:
        prepare_count[msg.seq] += 1
        if prepare_count[msg.seq] == 2f:
            # Prepared 状态
            log("prepared", msg.seq)
            # 进入 Commit 阶段
            broadcast(COMMIT, msg.seq, msg.digest)
```

**作用**：确保 majority 节点同意该顺序。

**Prepared 条件**：收到 1 个 Pre-Prepare + 2f 个 Prepare（共 2f+1，含自己）。

#### Phase 3: Commit

```pseudocode
# Backup 收到 2f+1 个 Commit
function onReceiveCommit(msg):
    if verify_signature(msg) and msg.seq matches:
        commit_count[msg.seq] += 1
        if commit_count[msg.seq] == 2f+1:
            # Committed
            execute(req)
            send_reply(client)
```

**作用**：确保 majority 节点已 Prepared，可安全执行。

### 5.2.3 为什么需要三阶段？⭐

| 阶段 | 作用 | 缺失会怎样 |
|------|------|------------|
| Pre-Prepare | Primary 提议顺序 | 无统一顺序 |
| Prepare | 节点间交换顺序确认 | Primary 故障后无法恢复顺序 |
| Commit | 确认 majority 已 Prepared | 节点状态不一致（部分 Prepared，部分未） |

**关键**：Commit 阶段解决「Prepared 但未传播」的状态不一致。若无 Commit，节点 A Prepared 后执行，节点 B 未 Prepared，A 故障后 B 无法恢复 A 的执行结果。

### 5.2.4 View Change（视图变更）⭐

Primary 故障时需切换：

```pseudocode
# Backup 检测 Primary 故障（超时）
function onViewTimeout():
    send(VIEW-CHANGE, new_view, last_prepared_seq, prepared_set)

# 新 Primary 收集 2f+1 个 VIEW-CHANGE
function onBecomeNewPrimary():
    # 构造 NEW-VIEW 消息
    # 包含所有未完成请求的新顺序
    send(NEW-VIEW, view_changes, pre_prepare_set)
```

**保证**：View Change 时，所有已 Prepared 的请求必须保留（不能丢失）。

### 5.2.5 PBFT 的复杂度

- **消息复杂度**：$O(n^2)$（每个节点广播给所有节点）
- **轮数**：3（Pre-Prepare + Prepare + Commit）
- **典型部署**：$n = 4$（容忍 1 拜占庭）

⚠️ **限制**：$O(n^2)$ 限制 PBFT 不适合大规模节点（> 100）。

## 5.3 HotStuff ⭐

📜 [Yin, Malkhi, Reiter, Gueta, Abraham 2018] *HotStuff: BFT Consensus with Linearity and Responsiveness*

### 5.3.1 设计目标

- **线性消息复杂度** $O(n)$（vs PBFT $O(n^2)$）
- **响应性**（Responsiveness）：非故障 Leader 推动进展，不需等超时
- **门限签名**（Threshold Signature）：聚合多签名为单一签名

### 5.3.2 四阶段流程

```
Phase 1: Prepare
Phase 2: Pre-Commit
Phase 3: Commit
Phase 4: Decide
```

```pseudocode
# Leader
function hotStuff_round(cmd):
    # 1. Prepare: 广播 cmd
    send(PREPARE, cmd)
    # 等待 n-f 个签名 → 形成门限签名 QC1
    
    # 2. Pre-Commit: 广播 QC1
    send(PRE-COMMIT, QC1)
    # 等待 n-f 个签名 → QC2
    
    # 3. Commit: 广播 QC2
    send(COMMIT, QC2)
    # 等待 n-f 个签名 → QC3
    
    # 4. Decide: 广播 QC3
    send(DECIDE, QC3)
    # 执行 cmd
```

### 5.3.3 关键优化

#### 门限签名

- $n$ 个节点各自签名
- 任意 $n - f$ 个签名可聚合为 1 个门限签名
- Leader 只需广播聚合签名，消息 $O(1)$

#### 线性 View Change

- PBFT 的 View Change 需广播所有 Prepared 状态 → $O(n^2)$
- HotStuff 用 QC（Quorum Certificate）链：每个 QC 指向前一个 QC
- View Change 仅需传一个 QC → $O(n)$

#### Chaining

- HotStuff 流水线化多个 round
- 不必等前一个 round 完成，提升吞吐

### 5.3.4 与 PBFT 对比

| 维度 | PBFT | HotStuff |
|------|------|---------|
| 阶段数 | 3 | 4 |
| 消息复杂度 | $O(n^2)$ | $O(n)$ |
| View Change | $O(n^2)$ | $O(n)$ |
| 签名 | 个体签名 | 门限签名 |
| 流水线 | 否 | 是 |
| 适合规模 | < 20 节点 | 数百节点 |

## 5.4 其他拜占庭共识

### 5.4.1 Tendermint 📜

📜 [Buchman 2016] *Tendermint: Byzantine Fault Tolerance in the Age of Blockchains*

- 类 PBFT，但引入「Pre-vote + Pre-commit」两阶段
- 流水线化
- 用于 Cosmos 生态

### 5.4.2 DiemBFT / LibraBFT

- HotStuff 变种
- 用于 Diem（原 Libra）区块链

### 5.4.3 PoW（Proof of Work）📜

📜 [Nakamoto 2008] *Bitcoin: A Peer-to-Peer Electronic Cash System*

- **非 BFT 共识**：通过工作量证明绕过 $n \geq 3f+1$ 假设
- 适合开放网络（无法控制节点身份）
- **代价**：高能耗、低吞吐（比特币 7 TPS）
- **概率一致**：仅概率上达成一致，6 个块后视为最终

### 5.4.4 PoS（Proof of Stake）

- 用「代币持有量」替代 PoW 的算力
- 节能、高吞吐
- 以太坊 2.0、Cardano、Polkadot

### 5.4.5 拜占庭共识算法对比

| 算法 | 故障模型 | 消息复杂度 | 轮数 | 适合规模 | 典型 |
|------|---------|-----------|------|---------|------|
| PBFT | Byzantine | $O(n^2)$ | 3 | < 20 | Hyperledger Fabric |
| HotStuff | Byzantine | $O(n)$ | 4 | 数百 | Diem |
| Tendermint | Byzantine | $O(n^2)$ | 3 | 数十 | Cosmos |
| PoW | Byzantine | — | — | 任意 | Bitcoin |
| PoS | Byzantine | $O(n)$ | — | 任意 | Ethereum 2.0 |

## 5.5 🎓 学术深度

### 5.5.1 $n \geq 3f+1$ 下界证明

详见 [§21 学术-Byzantine下界](./21-学术-Byzantine下界.md)。

**核心**：用「3-节点不可能」+「Liveness 需 majority」证明。

### 5.5.2 同步 vs 异步

- **同步模型**：Dolev-Strong 1983，$f+1$ 轮足够
- **异步模型**：PBFT 假设部分同步，需 $3f+1$ 节点
- **随机化**：Ben-Or 1983，概率终止

### 5.5.3 Optimal Resilience

> **最优容错**：在异步 + 拜占庭下，$f < n/3$ 是最优的，不可能更高。

### 5.5.4 HotStuff 的响应性

> **Responsiveness**：非故障 Leader 推动进展的速度仅取决于实际网络延迟，与超时无关。

HotStuff 是第一个同时实现 Linear + Responsive 的 BFT 算法。

## 5.6 🏭 工业实战

### 5.6.1 Hyperledger Fabric

- 早期用 PBFT
- 后期改为 Raft（非拜占庭，许可链场景）

### 5.6.2 Cosmos（Tendermint）

- 即时最终性（Instant Finality）
- 用于跨链协议

### 5.6.3 Diem / Aptos

- HotStuff 变种
- 高吞吐 + 即时最终性

### 5.6.4 区块链共识选型

| 场景 | 共识 | 原因 |
|------|------|------|
| 联盟链（小规模，可信节点） | PBFT / Raft | 性能高，节点可控 |
| 公链（大规模，不可信） | PoW / PoS | 容忍大量拜占庭节点 |
| 跨链 | Tendermint | 即时最终性 + 拜占庭 |

### 5.6.5 ⚠️ 工业陷阱

- ⚠️ **PBFT 大规模扩展性差**：$O(n^2)$ 限制节点数
- ⚠️ **门限签名实现复杂**：需密码学库支持
- ⚠️ **PoW 能耗**：环保争议，部分国家禁止
- ⚠️ **PoS「无利害关系」**（Nothing at Stake）：需 Slash 机制
- 🔥 **生产建议**：

  - 联盟链用 PBFT/HotStuff
  - 公链根据规模与去中心化需求选 PoW/PoS
  - 注意密码学库的安全审计

## 5.7 面试要点

### ⭐ Q1：PBFT 的三阶段是什么？

**骨架**：

1. **Pre-Prepare**：Primary 提议顺序
2. **Prepare**：节点间确认顺序（达到 2f+1 一致）
3. **Commit**：确认 majority 已 Prepared，可执行

**关键点**：三阶段 + 每阶段 quorum

**加分项**：解释为何需要 Commit 阶段

### ⭐ Q2：PBFT 为什么需要三阶段？

**骨架**：

1. Pre-Prepare：提议顺序
2. Prepare：节点间交换，但 Prepared 状态仅本地
3. Commit：确保 majority 已 Prepared，故障后可恢复
4. 若无 Commit，节点状态不一致 → 故障后无法恢复

**关键点**：Commit 解决状态一致性

**加分项**：与两阶段对比

### ⭐ Q3：HotStuff 相比 PBFT 优化了什么？

**骨架**：

1. 消息复杂度：$O(n^2)$ → $O(n)$（门限签名）
2. View Change：$O(n^2)$ → $O(n)$（QC 链）
3. 流水线化：提升吞吐
4. 响应性：非故障 Leader 不需等超时

**关键点**：线性消息复杂度

**加分项**：提到门限签名

### ⭐ Q4：为什么拜占庭共识需要 $n \geq 3f+1$？

**骨架**：

1. $n$ 节点，$f$ 拜占庭
2. 需 $n - f$ 响应（容忍 $f$ 不响应）
3. 其中 $f$ 可能拜占庭
4. 诚实响应 $n - 2f$，需 $> f$ 才能多数
5. $n - 2f > f \Rightarrow n > 3f$

**关键点**：诚实响应需超过拜占庭

**加分项**：举例 $n=3, f=1$ 不可解

### ⭐ Q5：PBFT 和 PoW 的本质区别？

**骨架**：

1. PBFT：许可链，节点身份已知，需 $3f+1$
2. PoW：开放网络，节点身份未知，用算力绕过身份假设
3. PBFT：确定性一致，即时最终性
4. PoW：概率一致，需多个块确认

**关键点**：节点身份假设

**加分项**：提到吞吐与去中心化的权衡

### ⭐ Q6：PBFT 的 View Change 解决什么问题？

**骨架**：

1. Primary 故障时切换
2. 收集 2f+1 个 VIEW-CHANGE
3. 新 Primary 构造 NEW-VIEW
4. 保留所有已 Prepared 的请求

**关键点**：保留 Prepared 状态

**加分项**：与 Raft 的选举对比

### ⭐ Q7：HotStuff 的门限签名是什么？

**骨架**：

1. $n$ 节点各自签名
2. 任意 $n - f$ 个签名可聚合为 1 个
3. 验证只需 1 次（而非 $n$ 次）
4. 消息从 $O(n)$ 降到 $O(1)$

**关键点**：聚合签名

**加分项**：提到 ECDSA / BLS 签名方案

### ⭐ Q8：PoS 相比 PoW 的优缺点？

**骨架**：

**优点**：

1. 节能
2. 高吞吐
3. 无需算力硬件

**缺点**：

1. 「无利害关系」需 Slash 机制
2. 富者愈富
3. 长程攻击风险

**关键点**：能耗 vs 安全模型

**加分项**：提到以太坊 2.0 的 Casper
