## 一、问题定义

### 1.1 解决什么问题

单核性能增速在 2004 年前后因功耗墙、频率墙、ILP 墙趋于停滞（ Dennard scaling 失效），摩尔晶体管红利只能靠**增加核心数**消化。于是：

- 单线程程序不再自动变快；
- 必须显式并行才能继续提升吞吐；
- 并行程序的效率受**硬件架构**决定性影响：在 NUMA 上不绑核可能慢 2-3 倍；在 GPU 上不合并访存可能损失 90% 带宽；在多 socket 上不感知缓存一致性可能被 false sharing 拖死。

本章的目标：建立**架构 → 性能**的因果链，让你在写并行代码前就知道"它会在哪种硬件上慢、为什么慢、怎么不慢"。

### 1.2 与串行思维的区别

| 维度 | 串行思维 | 并行思维 |
|------|----------|----------|
| 性能瓶颈 | 算法复杂度 $O(n)$ | 计算、通信、同步三者权衡 |
| 正确性 | 程序逻辑 | 程序逻辑 + 时序（数据竞争/死锁） |
| 调试 | 复现易 | 时序敏感、难复现 |
| 扩展性 | 不关心 | 强/弱扩展曲线 |
| 内存 | 任意访问 | 必须考虑层级（cache→DRAM→NVLink→IB） |

### 1.3 硬件平台差异概述

| 平台 | 内存模型 | 典型并行度 | 主要瓶颈 |
|------|----------|-----------|----------|
| 多核 CPU | 共享内存 / NUMA | 8-128 核 | 内存带宽、缓存一致性 |
| GPU | 共享显存 / SIMT | 数千线程 | 显存带宽、occupancy |
| 多 GPU 节点 | 分布式显存 + NVLink | 4-8 卡 | NVLink 带宽 |
| 集群 | 分布式内存 + IB/RoCE | 数百-数万卡 | 网络带宽/延迟 |
| TPU pod | 分布式 HBM + ICI | 数千核 | ICI 拓扑 |

## 三、原理与机制

### 3.1 直觉：为什么并行难

> **核心矛盾**：硬件按"层级 + 共享 + 一致性"组织，程序员却按"逻辑顺序 + 共享变量"思考。两者的 gap 就是并行编程的全部难点。

一个串行程序假设：**我写的顺序就是执行的顺序**。但实际硬件会：

1. **乱序执行**：CPU 为填满流水线，会重排指令；
2. **缓存延迟写回**：写操作先到 L1，未必立刻被其他核看到；
3. **跨核一致性**：核 A 写了 `x=1`，核 B 何时看到 `x=1` 取决于一致性协议；
4. **NUMA 延迟**：访问本地内存 80ns，跨 socket 140ns。

并行程序的正确性必须显式约束这些行为（用锁、屏障、原子操作），性能必须显式利用这些层级（用线程绑定、对齐、预取）。

### 3.2 Flynn 分类 🎓

按**指令流数 × 数据流数**分类：

| 类型 | 指令流 | 数据流 | 典型硬件 |
|------|--------|--------|----------|
| SISD | 1 | 1 | 单核 CPU（80486 时代） |
| SIMD | 1 | 多 | AVX-512、SVE、GPU（SIMT 近似） |
| MISD | 多 | 1 | 罕见（冗余容错系统） |
| MIMD | 多 | 多 | 多核 CPU、集群、多 GPU |

实际硬件通常是**混合**：
- 现代多核 CPU = MIMD（多核） + 每核内 SIMD（AVX） + SMT（超线程）；
- NVIDIA GPU = SIMT（warp）+ 多 SM（MIMD）。

### 3.3 内存架构：UMA vs NUMA

```
UMA（一致内存访问）           NUMA（非一致内存访问）
   ┌───────────┐                ┌──────────┐   ┌──────────┐
   │  CPU 0..n │                │ Socket0  │   │ Socket1  │
   │  ┌─────┐  │                │ ┌──────┐ │   │ ┌──────┐ │
   │  │ L3  │  │                │ │ L3   │ │   │ │ L3   │ │
   │  └──┬──┘  │                │ └──┬───┘ │   │ └──┬───┘ │
   └─────┼─────┘                │    │     │   │    │     │
         │                      │ DRAM0│   │   │ DRAM1│   │
     ┌───┴───┐                  └──┬──┘   │   └──┬──┘   │
     │ DRAM  │                     │ QPI/UPI  │  │ QPI/UPI
     └───────┘                     └────┬─────┘  └────┬─────┘
                                       └──── 互联 ────┘
                                       
  访存延迟均匀                     本地 ~80ns，跨 socket ~140ns
  扩展性差（总线竞争）             扩展性好，但要 first-touch
```

**NUMA 关键性质** 🔥：
- 每个 CPU socket 有**本地内存**，访问最快；
- 跨 socket 访问通过 QPI（Intel）/ Infinity Fabric（AMD）/ Ultra Path（新 Intel）互联；
- Linux 默认按"first-touch"分配物理页：**哪个核先写，页就分配在哪个 NUMA 节点**；
- 不绑核的线程可能在 OS 调度下跨 NUMA 迁移，导致本地变远程，性能骤降。

### 3.4 缓存一致性协议 MESI 🎓

每个缓存线有 4 状态：

| 状态 | 含义 | 是否脏 | 其他副本 |
|------|------|--------|----------|
| M (Modified) | 已修改，与内存不一致 | 是 | 无 |
| E (Exclusive) | 独占，与内存一致 | 否 | 无 |
| S (Shared) | 共享，与内存一致 | 否 | 可能有 |
| I (Invalid) | 无效 | — | — |

**写一个 Shared 行**触发：
1. 当前核发 "Read-for-Ownership" (RFO)；
2. 总线广播 Invalidate；
3. 其他持有 S 副本的核置 I；
4. 当前核升级为 M，开始写。

这就是 **coherence traffic** 的来源。即使两个核写**不同变量**，只要位于同一缓存线，也会触发上述流程——**false sharing**。

### 3.5 物理墙：内存墙 / IO 墙 / 通信墙 / 功耗墙

| 墙 | 成因 | 量化（2024 数据） |
|----|------|------------------|
| **内存墙** | CPU 算力增速 >> DRAM 带宽增速 | H100 算力 1979 TFLOPS，HBM 带宽 3.35 TB/s，每字节只能做 ~590 FLOP |
| **IO 墙** | 存储带宽 << 计算带宽 | NVMe SSD 7 GB/s vs H100 内 3.35 TB/s，差 ~480 倍 |
| **通信墙** | 跨节点带宽 << 节点内带宽 | NVLink 900 GB/s vs IB NDR 50 GB/s，跨节点是瓶颈 |
| **功耗墙** | Dennard 缩放失效，频率无法再升 | H100 SXM 700W TDP，单机柜 40+ kW |

**Roofline 模型**（详见 §2）就是把这些墙画在一张图上，告诉你某个 kernel 是被哪堵墙卡住的。

### 3.6 阿姆达尔定律（预告，详见 §2） 📜

$$
S_P \le \frac{1}{(1-f) + f/P}
$$

含义：即使无限加核，加速比也被串行比例 $(1-f)$ 封顶。这把"并行是银弹"的幻想直接打破，是后续所有性能分析的起点。

## 四、算法 / 流程

### 4.1 NUMA first-touch 分配伪代码

```
// 错误：主线程一次性分配 → 全部分配在 NUMA 节点 0
double* A = malloc(N * sizeof(double));
for (i in 0..N) A[i] = 0;   // 主线程触摸，全部在 node 0

// 正确：每个线程触摸自己将访问的部分
double* A = malloc(N * sizeof(double));
#pragma omp parallel for
for (i in 0..N) A[i] = 0;   // 触摸线程决定物理页位置
```

复杂度分析：
- $W = O(N)$
- $C = 0$（共享内存）
- $D = O(1)$（无依赖）

### 4.2 缓存一致性触发的伪代码

```
// false sharing 示例
struct { int x; int y; } s;   // x, y 同一缓存线
// 线程 T0 反复写 s.x
// 线程 T1 反复写 s.y
// 虽然 x ≠ y，但每次写都触发 RFO → 性能急剧下降
```

## 六、代码示例

### 6.1 最小可运行版（教学）：观察 false sharing

```cpp
// file: false_sharing.cpp
// 编译: g++ -O2 -fopenmp -pthread false_sharing.cpp -o fs
// 运行: ./fs
#include <atomic>
#include <chrono>
#include <cstdio>
#include <thread>
#include <vector>

struct Bad {
    std::atomic<int> x{0};
    std::atomic<int> y{0};  // 与 x 位于同一缓存线！
};

struct Good {
    alignas(64) std::atomic<int> x{0};  // 独占缓存线
    alignas(64) std::atomic<int> y{0};
};

constexpr int N = 100'000'000;

void worker(std::atomic<int>& counter) {
    for (int i = 0; i < N; ++i) counter.store(i, std::memory_order_relaxed);
}

template <typename T>
long bench() {
    T s;
    auto t0 = std::chrono::high_resolution_clock::now();
    std::thread t1(worker, std::ref(s.x));
    std::thread t2(worker, std::ref(s.y));
    t1.join(); t2.join();
    auto t1c = std::chrono::high_resolution_clock::now();
    return std::chrono::duration_cast<std::chrono::milliseconds>(t1c - t0).count();
}

int main() {
    printf("Bad  (false sharing): %ld ms\n", bench<Bad>());
    printf("Good (cache aligned): %ld ms\n", bench<Good>());
    return 0;
}
```

**预期输出**（典型 8 核 x86 机器）：
```
Bad  (false sharing): ~1200 ms
Good (cache aligned): ~400 ms
```
3 倍差距来自 coherence traffic。

### 6.2 生产级版（工程）：NUMA 感知 + 绑核 + 对齐

```cpp
// file: numa_aware.cpp
// 编译: g++ -O3 -fopenmp -mavx2 numa_aware.cpp -o numa -lnuma
// 运行: numactl --cpunodebind=0 --membind=0 ./numa
#include <numa.h>
#include <omp.h>
#include <chrono>
#include <cstdio>
#include <vector>

constexpr size_t N = 1ull << 26;  // 64M doubles = 512 MB

int main() {
    if (numa_available() < 0) { printf("NUMA not available\n"); return 1; }
    printf("NUMA nodes: %d\n", numa_num_configured_nodes());

    // 1. first-touch 并行初始化（关键！）
    std::vector<double> A(N), B(N), C(N);

    auto t0 = std::chrono::high_resolution_clock::now();

    #pragma omp parallel
    {
        // 2. 绑核：让每个线程绑定到当前 CPU
        #pragma omp single
        {
            int threads = omp_get_num_threads();
            printf("Threads: %d\n", threads);
        }

        #pragma omp for schedule(static)
        for (size_t i = 0; i < N; ++i) {
            A[i] = 0.0;  // 触摸，决定物理页 NUMA 位置
            B[i] = 1.0;
            C[i] = 0.0;
        }

        // 3. 实际计算
        #pragma omp for schedule(static)
        for (size_t i = 0; i < N; ++i) {
            C[i] = A[i] + B[i] * 2.0;
        }
    }

    auto t1 = std::chrono::high_resolution_clock::now();
    double ms = std::chrono::duration<double, std::milli>(t1 - t0).count();

    double bytes = 3.0 * N * sizeof(double);
    double gb_s = bytes / (ms / 1000.0) / 1e9;
    printf("Time: %.1f ms, Bandwidth: %.1f GB/s\n", ms, gb_s);
    return 0;
}
```

**对比实验**（双 socket EPYC 机器）：
```
$ numactl --cpunodebind=0 --membind=0 ./numa    # 全本地
Time: 220 ms, Bandwidth: 21 GB/s

$ numactl --cpunodebind=0 --membind=1 ./numa    # CPU 在 0, 内存全在 1 → 全远程
Time: 580 ms, Bandwidth: 8 GB/s

$ OMP_PROC_BIND=close numactl --cpunodebind=0 ./numa   # 绑核 + 本地内存
Time: 180 ms, Bandwidth: 26 GB/s
```

🔥 **工程要点**：
- `OMP_PROC_BIND=close/spread` 让 OpenMP 绑核；
- `numactl --membind` 控制内存分配位置；
- first-touch 决定物理页落在哪个 socket；
- 三者缺一不可。

### 6.3 手把手：观察 MESI 一致性流量

用 `perf` 观察 cache miss 与 coherence 事件：

```bash
# 实验：false sharing 的性能计数器
perf stat -e cache-misses,mem_load_l3_hit_retired.xsnp_hit,\\
          mem_load_l3_hit_retired.xsnp_hitm ./fs

# 输出示例（Bad 版本）：
#  cache-misses:        50,000,000   ← 远高于 Good
```

## 七、常见陷阱与最佳实践 ⚠️

| 陷阱 | 后果 | 对策 |
|------|------|------|
| False sharing | 多线程性能损失 2-10 倍 | `alignas(64)` / padding / 每线程独立数组 |
| NUMA 远程访存 | 带宽降 2-3 倍 | `numactl --membind` + first-touch |
| 不绑核 | 线程跨核迁移丢缓存 | `OMP_PROC_BIND=close` / `sched_setaffinity` |
| 跨 socket 频繁同步 | UPI 成为瓶颈 | 把通信密集的线程放在同 socket |
| 缓存线大小假设错误 | 对齐失效 | 运行时查 `std::hardware_destructive_interference_size` |
| 自旋锁跨核 | 触发 RFO 风暴 | 用 MCS 锁 / exponential backoff |
| 大数组按行分配但按列访问 | 缓存利用率低 | 改数据布局（AoS→SoA） |

## 十、综合面试题

1. **基础**：为什么现代 CPU 既有 SIMD 又有多核？两者解决什么不同问题？
   - 答题要点：SIMD 提升单核数据级并行（同一指令处理多数据），多核提供线程级并行（不同指令流）。SIMD 受限于向量宽度，多核受限于核数。

2. **进阶**：在 8 核双 socket NUMA 机器上跑一个内存带宽受限程序，发现比预期慢 2 倍。如何排查？
   - 答题要点：(1) `numactl --hardware` 看拓扑；(2) `perf stat -e cache-misses,node-loads` 看远程访存比例；(3) 检查是否 first-touch；(4) 检查是否绑核；(5) 检查数据是否跨 socket 分配。

3. **深度**：MESI 协议下，两个线程分别 `++x` 和 `++y`（x、y 同一缓存线）100 万次，会产生多少次 RFO？
   - 答题要点：每次写都触发一次 RFO（若另一核持有 S/M），因此约 200 万次跨核 invalidate。若 x、y 对齐到不同缓存线，则为 0。

4. **设计**：设计一个 NUMA 感知的并行 reduce，使带宽利用率最大化。
   - 答题要点：(1) 数据按 NUMA 节点分片，first-touch 在本地节点；(2) 每节点内多线程并行 reduce 到本地部分和；(3) 跨节点只交换部分和（小数据量）；(4) 绑核避免迁移；(5) 用 `sched_setaffinity` 或 `OMP_PROC_BIND`。

5. **工程**：为什么 GPU 上 false sharing 不是主要问题，而 CPU 上是？
   - 答题要点：GPU 共享内存由程序员显式管理，不存在硬件一致性协议；全局内存访问按 warp 合并，按 128B 事务处理。CPU 缓存一致性对程序员透明，false sharing 隐式发生。

6. **学术**：Dennard 缩放失效后，体系结构如何继续提升性能？
   - 答题要点：(1) 多核（核心数增长）；(2) SIMD 宽度增长（AVX2→AVX-512→SVE）；(3) 专用加速器（GPU/TPU/NPU）；(4) 异构集成（chiplet/HBM）；(5) 近数据计算（PIM）。
