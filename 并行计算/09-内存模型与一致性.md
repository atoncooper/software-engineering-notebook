## 一、问题定义

### 1.1 解决什么问题

直觉上,程序员以为代码会"按写的顺序执行"。但实际:

```cpp
// 线程 1
x = 1;       // 写 x
flag = true; // 写 flag

// 线程 2
while (!flag) ;
assert(x == 1);  // 一定成立吗?——不一定!
```

在 x86 / ARM / C++ 默认内存模型下,`assert` 可能失败。原因:
1. **编译器重排**:编译器可能把 `flag=true` 提前;
2. **CPU 乱序**:CPU 乱序执行可能让 `flag` 先于 `x` 可见;
3. **Store Buffer**:x86 的 store buffer 让写延后可见。

**内存模型**(Memory Model)就是精确定义"什么时候什么顺序的保证成立"。它是并发程序正确性的**数学根基**。

### 1.2 为什么必须懂

- **正确性**:不懂内存模型,你写的无锁代码 99% 有微妙 bug;
- **性能**:懂内存模型才能选最弱的同步原语(避免不必要的强屏障);
- **可移植性**:x86 上能跑的代码 ARM 上可能挂(TSO vs relaxed);
- **面试**:大厂并发岗必考"为什么需要 memory_order_acquire"。

## 三、原理与机制

### 3.1 Sequential Consistency(SC)📜🎓

Lamport 1979 定义:

> 多线程程序执行结果 = 所有线程操作按某种全局交错(interleaving)执行的结果,且每线程内操作保持程序顺序。

**直觉**:存在一个全局时钟,所有线程的操作按此时钟排队,且每线程内顺序不变。

```
SC 允许:
  T1: W(x=1), W(y=1)
  T2: R(y)=1, R(x)=1     ✅ 合法交错

SC 禁止:
  T1: W(x=1), W(y=1)
  T2: R(y)=1, R(x)=0     ❌ 不存在交错能产生此结果
```

**代价**:SC 禁止几乎所有重排,性能差。现代 CPU 都不用 SC。

### 3.2 x86 TSO(Total Store Order)🎓🔥

x86 用 **store buffer**:每个核有一个 FIFO 写缓冲,写操作先入 buffer,稍后刷到缓存。

```
            ┌──────────────┐
   核 0 ──→ │ Store Buffer │ ──→ L1 Cache ──→ ...
            └──────────────┘
```

**后果**:
- **写-写不重排**:store buffer FIFO,同核写保持顺序;
- **读-读不重排**;
- **读-写不重排**(读后写);
- **写-读可重排**!写还在 buffer,读先去 cache 读旧值。

```
TSO 下合法:
  T1: W(x=1), R(y)=0   ← R(y) 可先于 W(x) 完成(读 cache,y 还是 0)
  T2: W(y=1), R(x)=0   ← 同理

结果:两线程都读到 0 —— SC 下不可能,TSO 下可能!
```

🔥 **经典案例**:Peterson 算法在 x86 上可能失效(见 §6.2)。

**修复**:用 `MFENCE` / `SFENCE` 屏障,强制刷 store buffer。

### 3.3 ARM/POWER Relaxed Memory Model 🎓

ARM/POWER 比 x86 更宽松,**几乎允许所有重排**(除了显式依赖):

| 重排 | x86 TSO | ARM/POWER |
|------|---------|-----------|
| 写-写 | 禁 | 禁(同地址) |
| 读-读 | 禁 | 允许 |
| 读-写 | 禁 | 允许 |
| 写-读 | 允许 | 允许 |

**后果**:ARM 上需要更多屏障(`DMB` / `DSB` / `ISB`)。

🔥 **工程意义**:在 x86 上"凑巧能跑"的并发代码,移植到 ARM(如 Apple Silicon、AWS Graviton、鲲鹏)常常挂。Apple M1 转型期大量此类 bug。

### 3.4 C++ 内存模型(自 C++11)📜

C++11 引入标准内存模型,5 种 `memory_order`:

| 序 | 语义 | 同步 |
|----|------|------|
| `relaxed` | 仅保证原子,无顺序 | 无 |
| `consume` | 数据依赖(已弃用,等同 acquire) | 弱 |
| `acquire` | 后续读/写不能提前到此之前 | 读-读/读-写 屏障 |
| `release` | 之前读/写不能推迟到此之后 | 写-写/读-写 屏障 |
| `acq_rel` | acquire + release(读写同时) | both |
| `seq_cst` | 全局总序,最强 | 全屏障 |

#### Acquire-Release 配对

```cpp
std::atomic<bool> ready{false};
int data = 0;

// 线程 1
data = 42;
ready.store(true, std::memory_order_release);  // release: 之前写不能过此

// 线程 2
while (!ready.load(std::memory_order_acquire)) ;  // acquire: 之后读不能提前
assert(data == 42);  // ✅ 保证成立
```

**机制**:
- `release` 之前的所有写(包括 `data=42`)对获取该原子变量的线程可见;
- `acquire` 之后的所有读不会重排到 load 之前。

🔥 **关键**:acquire-release **比 seq_cst 快**(无需全局屏障),覆盖 90% 同步场景。

#### SeqCst 的额外保证

seq_cst 在 acquire-release 基础上,额外保证**所有 seq_cst 操作存在一个全局总序**。需要全局顺序的场景(如 Dekker/Peterson 互斥)必须用 seq_cst。

### 3.5 DRF 定理(Data-Race-Free)🎓📜

> **DRF 定理**(Adve-Hill):对于 Data-Race-Free 程序,所有 relaxed 内存模型的执行结果 = 某 SC 执行结果。

**含义**:只要你用同步原语(锁、atomic)消除所有数据竞争,程序行为就像在 SC 下——你不用关心底层 TSO/relaxed。

**反例**:有数据竞争的程序,行为未定义(可能看到部分写、撕裂值等)。

🔥 **工程指导**:
1. 用 TSan 找出所有数据竞争;
2. 用锁或 atomic 消除;
3. 消除后程序语义 = SC,可按直觉推理。

### 3.6 Happens-Before 关系 🎓

语言层用 **happens-before** 形式化同步:

- **Sequenced-Before**(SB):同线程内,程序顺序;
- **Synchronizes-With**(SW):跨线程,如 release store → acquire load;
- **Happens-Before**(HB):SB ∪ SW 的传递闭包。

**关键定理**:若 A happens-before B,则 A 的内存效果对 B 可见。

```
线程1: data=1 (SB) → ready.store(release) (SW) 
                                          ↓
线程2: ready.load(acquire) (SW) → assert(data==1) (SB)

data=1 →ready.store(release) (SB)
ready.store(release) → ready.load(acquire) (SW)
ready.load(acquire) → assert(data==1) (SB)
传递:data=1 → assert(data==1) (HB) ✅
```

### 3.7 Java 内存模型(JMM)📜

Java 自 JDK 5 有正式 JMM(JSR-133):

- `volatile` = C++ 的 seq_cst;
- `synchronized` = 监视器锁,release/acquire;
- `final` 字段:构造函数结束后对所有线程可见(安全发布);
- `AtomicInteger.lazySet` = relaxed。

🔥 **volatile 在 Java ≠ volatile 在 C**:
- C `volatile`:不缓存到寄存器,不保证原子/可见性/顺序;
- Java `volatile`:seq_cst 原子,全同步。

### 3.8 Rust / Go 内存模型

- **Rust**:与 C++ 一致(`AtomicUsize` 等,`Ordering::Acquire/Release/SeqCst`);
- **Go**:happens-before 模型,`sync/atomic` 提供 relaxed/acquire/release/seqcst;
- **Go channel**:send happens-before 对应 receive,简化推理。

### 3.9 内存屏障指令

| 架构 | 全屏障 | Load 屏障 | Store 屏障 |
|------|--------|----------|-----------|
| x86 | `MFENCE` | `LFENCE`(仅阻止读重排,实际不需要) | `SFENCE` |
| ARM | `DMB ISH` | `LDAR`(acquire load) | `STLR`(release store) |
| POWER | `sync` | `lwsync` | `lwsync` |

🔥 **C++ atomic 编译到对应指令**:
- `seq_cst` store → x86 `MOV`(因 TSO 已够)+ 全局 `MFENCE`(部分场景);
- `seq_cst` load → x86 `MOV`(无需屏障);
- `acquire` load → ARM `LDAR`;
- `release` store → ARM `STLR`。

## 四、算法 / 流程

### 4.1 选 memory_order 决策树

```
需要全局总序(互斥算法、Dekker/Peterson)?
├─ 是 → seq_cst
└─ 否 → 单纯发布/读取数据?
        ├─ 是 → release/acquire 配对
        └─ 仅原子计数(无同步语义)?
            ├─ 是 → relaxed
            └─ RMW 且需同步?
                └─ acq_rel
```

### 4.2 推理程序正确性的流程

```
1. 画出所有 sequenced-before(同线程)
2. 标出 synchronizes-with(release→acquire)
3. 求传递闭包得 happens-before
4. 检查是否有冲突操作无 HB 关系
   → 有则数据竞争,行为未定义
5. 若 DRF,按 SC 推理
```

## 六、代码示例

### 6.1 最小可运行版(教学):Acquire-Release 发布

```cpp
// file: acquire_release.cpp
// 编译: g++ -O2 -pthread acquire_release.cpp -o ar
#include <atomic>
#include <thread>
#include <cassert>
#include <cstdio>

int payload = 0;
std::atomic<bool> ready{false};

void producer() {
    payload = 42;                                    // 普通写
    ready.store(true, std::memory_order_release);    // release: 之前的写不能过此
}

void consumer() {
    while (!ready.load(std::memory_order_acquire))   // acquire: 之后的读不能提前
        ;
    assert(payload == 42);  // ✅ 保证成立
    printf("consumer saw payload=%d\n", payload);
}

int main() {
    std::thread t1(producer);
    std::thread t2(consumer);
    t1.join(); t2.join();
    return 0;
}
```

🔥 **若改用 `relaxed`**:`assert` 可能失败(无同步保证)。

### 6.2 手把手:Peterson 算法在 TSO 下失效

```cpp
// file: peterson_tso.cpp
// 演示 Peterson 互斥算法在 x86 TSO 下可能失效
// 编译: g++ -O2 -pthread peterson_tso.cpp -o pet
// 注意:实际复现需关闭优化 + 特定 CPU,概念演示为主
#include <atomic>
#include <thread>
#include <cstdio>

// Peterson 算法(两线程互斥)
// SC 下正确,TSO 下可能失效
class PetersonSC {
    std::atomic<bool> flag[2]{false, false};
    std::atomic<int> turn{0};
public:
    void lock(int id) {
        int other = 1 - id;
        flag[id].store(true, std::memory_order_relaxed);  // ⚠️ relaxed
        turn.store(other, std::memory_order_relaxed);     // ⚠️ relaxed
        while (flag[other].load(std::memory_order_relaxed) &&
               turn.load(std::memory_order_relaxed) == other)
            ;
    }
    void unlock(int id) {
        flag[id].store(false, std::memory_order_relaxed);
    }
};

// 修复版:用 seq_cst
class PetersonFixed {
    std::atomic<bool> flag[2]{false, false};
    std::atomic<int> turn{0};
public:
    void lock(int id) {
        int other = 1 - id;
        flag[id].store(true, std::memory_order_seq_cst);  // ✅ seq_cst
        turn.store(other, std::memory_order_seq_cst);
        while (flag[other].load(std::memory_order_seq_cst) &&
               turn.load(std::memory_order_seq_cst) == other)
            ;
    }
    void unlock(int id) {
        flag[id].store(false, std::memory_order_seq_cst);
    }
};

int main() {
    // 概念演示:实际复现需要关闭优化和特定 CPU
    printf("Peterson with relaxed may fail on TSO/ARM\n");
    printf("Peterson with seq_cst is correct\n");
    printf("Reason: TSO allows write-read reordering;\n");
    printf("  flag[id]=true, turn=other 可被重排为 turn=other, flag[id]=true\n");
    printf("  导致两线程同时进入临界区\n");
    return 0;
}
```

🔥 **失效机理**:
```
线程 0:                    线程 1:
flag[0]=true               flag[1]=true
turn=1                     turn=0
↑ x86 store buffer 可重排  ↑ 同理
turn=1 实际先于 flag[0]     turn=0 实际先于 flag[1]

两线程都看到对方 flag=false,都进入临界区!
```

**修复**:用 `seq_cst`(全屏障)或显式 `MFENCE`。

### 6.3 手把手:5 种 memory_order 对比

```cpp
// file: orders_cmp.cpp
// 演示不同 memory_order 的实际指令差异(x86)
// 编译: g++ -O2 -S orders_cmp.cpp -o orders.s
#include <atomic>

std::atomic<int> x{0};

void relaxed_store() { x.store(1, std::memory_order_relaxed); }
void release_store() { x.store(1, std::memory_order_release); }
void seqcst_store() { x.store(1, std::memory_order_seq_cst); }

void relaxed_load() { (void)x.load(std::memory_order_relaxed); }
void acquire_load() { (void)x.load(std::memory_order_acquire); }
void seqcst_load() { (void)x.load(std::memory_order_seq_cst); }
```

**x86-64 汇编输出**(关键差异):
```asm
relaxed_store:  mov DWORD PTR x[rip], 1     ; 普通 MOV
release_store:  mov DWORD PTR x[rip], 1     ; 普通 MOV(TSO 已满足 release)
seqcst_store:   mov DWORD PTR x[rip], 1
                mfence                       ; ⚠️ 额外屏障!

relaxed_load:   mov eax, DWORD PTR x[rip]   ; 普通 MOV
acquire_load:   mov eax, DWORD PTR x[rip]   ; 普通 MOV(TSO 已满足 acquire)
seqcst_load:    mov eax, DWORD PTR x[rip]   ; 普通 MOV(读不需屏障)
```

🔥 **关键观察**:
- x86 上 `release`/`acquire` 几乎免费(因 TSO);
- `seq_cst` store 多一个 `MFENCE`(约 10-30 周期);
- ARM 上差异更大:acquire→`LDAR`,release→`STLR`,seq_cst→额外 `DMB`。

🔥 **性能指导**:x86 上能用 acquire-release 就别用 seq_cst,但差异不大;ARM 上差异显著,务必选对。

### 6.4 生产级版(工程):双检锁(DCLP)正确实现

```cpp
// file: dclp.cpp
// 经典双检锁单例,演示内存模型陷阱
// 编译: g++ -O2 -pthread dclp.cpp -o dclp
#include <atomic>
#include <memory>
#include <thread>
#include <cstdio>

class Singleton {
public:
    int data;
    Singleton(int d) : data(d) {
        printf("Singleton constructed\n");
    }
    static Singleton* instance() {
        Singleton* p = instance_.load(std::memory_order_acquire);  // ① acquire
        if (!p) {
            std::lock_guard<std::mutex> lk(mtx_);
            p = instance_.load(std::memory_order_relaxed);  // ② 持锁后再检
            if (!p) {
                p = new Singleton(42);  // ③ 构造
                instance_.store(p, std::memory_order_release);  // ④ release
            }
        }
        return p;
    }
private:
    static std::atomic<Singleton*> instance_;
    static std::mutex mtx_;
};
std::atomic<Singleton*> Singleton::instance_{nullptr};
std::mutex Singleton::mtx_;

// === 反例:错误的双检锁 ===
class BadSingleton {
public:
    int data;
    BadSingleton(int d) : data(d) {}
    static BadSingleton* instance() {
        // ⚠️ 错误 1: 用 volatile 不保证原子/有序
        // ⚠️ 错误 2: 无 acquire/release
        if (!instance_bad_) {
            std::lock_guard<std::mutex> lk(mtx_bad_);
            if (!instance_bad_) {
                instance_bad_ = new BadSingleton(42);
                // ⚠️ 错误 3: new 可能被重排为"分配内存→赋值指针→构造对象"
                // 其他线程看到非 null 指针但对象未构造完
            }
        }
        return instance_bad_;
    }
private:
    static BadSingleton* instance_bad_;
    static std::mutex mtx_bad_;
};
BadSingleton* BadSingleton::instance_bad_{nullptr};
std::mutex BadSingleton::mtx_bad_;

int main() {
    std::vector<std::thread> ts;
    for (int t = 0; t < 8; ++t) {
        ts.emplace_back([]() {
            for (int i = 0; i < 1000; ++i) {
                [[maybe_unused]] auto p = Singleton::instance();
            }
        });
    }
    for (auto& t : ts) t.join();
    return 0;
}
```

🔥 **DCLP 三大陷阱**:
1. **`volatile` 不够**:C++ `volatile` 不保证原子/可见/有序;
2. **`new` 重排**:`p = new T()` 可能被拆为"alloc→assign→ctor",其他线程看到未构造对象;
3. **内存序**:必须 acquire-load + release-store。

**最佳实践**:用 `std::call_once` 或 Meyers 单例(局部静态变量,C++11 起线程安全):
```cpp
static Singleton& instance() {
    static Singleton inst(42);  // C++11 起线程安全
    return inst;
}
```

### 6.5 手把手:用 TSan 验证 happens-before

```cpp
// file: hb_demo.cpp
// 编译: g++ -O1 -g -fsanitize=thread -pthread hb_demo.cpp -o hb
#include <atomic>
#include <thread>
#include <cstdio>

int data = 0;
std::atomic<bool> ready{false};

void producer() {
    data = 42;
    ready.store(true, std::memory_order_release);
}

void consumer() {
    while (!ready.load(std::memory_order_acquire)) ;
    printf("data=%d\n", data);  // TSan 确认无 race
}

int main() {
    std::thread t1(producer), t2(consumer);
    t1.join(); t2.join();
    return 0;
}
```

TSan 无警告——`data` 的访问通过 release-acquire 建立 happens-before。

**对比**:若把 acquire/release 改成 relaxed,TSan 会报 data race。

## 七、常见陷阱与最佳实践 ⚠️

| 陷阱 | 后果 | 对策 |
|------|------|------|
| 用 C `volatile` 同步 | 全部不保证 | 用 `std::atomic` |
| 双检锁无内存序 | 部分初始化泄漏 | acquire/release 或 call_once |
| 自旋锁用 relaxed | 失去同步 | acquire-load + release-store |
| Peterson 用 relaxed | TSO 下失效 | seq_cst |
| 假设 x86 行为可移植 | ARM 上挂 | 用标准内存序,不依赖架构 |
| seq_cst 滥用 | 性能损失(ARM 显著) | 评估能否降为 acquire-release |
| 忽视 store buffer | 写后读看到旧值 | 用屏障或 atomic |
| 用 `memory_order_consume` | 编译器实际当 acquire | 别用(已弃用) |
| 假设 RMW 自动同步 | 仅对自身原子 | 跨变量仍需 acquire/release |
| 不跑 TSan | 微妙 bug 上线 | CI 加 TSan |

## 十、综合面试题

1. **基础**:为什么 `memory_order_relaxed` 不能用来发布数据?
   - 答:relaxed 无同步语义,不建立 happens-before。发布者 `data=42; ready.store(true, relaxed)` 可能被重排为 `ready=true; data=42`,读者看到 `ready=true` 但 `data` 还是 0。必须用 release-store + acquire-load 建立 synchronizes-with。

2. **进阶**:x86 上 `seq_cst` store 比 `release` store 多什么指令?为什么?
   - 答:多一个 `MFENCE`。x86 TSO 已保证写-写不重排(满足 release),但 seq_cst 要求全局总序,需 `MFENCE` 确保 store 之前的所有写(包括其他原子)在该 store 之前全局可见。代价约 10-30 周期。

3. **深度**:证明 DRF-SC 定理(直觉)。
   - 答:若程序无数据竞争,则所有冲突访问间存在 happens-before。happens-before 由 sequenced-before(程序序)和 synchronizes-with(同步原语)组成。同步原语(锁/atomic)在硬件层插入屏障,保证 release 之前的写在 acquire 之后可见。故无竞争程序的所有内存效果与某 SC 交错一致。反之,有竞争则可能看到部分写、撕裂,行为未定义。

4. **设计**:写一个无锁的单生产者-单消费者队列,内存序怎么选?
   - 答:用环形缓冲 + head/tail 原子变量。生产者写数据后 `tail.store(release)`,消费者 `tail.load(acquire)` 后读数据。对称地,消费者读完后 `head.store(release)`,生产者 `head.load(acquire)`。无需 seq_cst,acquire-release 足够,性能最优。

5. **工程**:代码在 x86 上跑 3 年无问题,移植到 AWS Graviton(ARM)后偶发崩溃。怎么排查?
   - 答:(1) 99% 是内存模型 bug——x86 TSO 强,掩盖了 relaxed bug;(2) 跑 TSan(x86 上跑)找数据竞争;(3) 检查所有手写无锁代码的 memory_order;(4) 检查是否误用 `volatile` 同步;(5) 检查双检锁、自旋锁实现;(6) 用 `std::atomic` 替换所有手写同步。

6. **学术**:比较 SC / TSO / Relaxed 在 Dekker 互斥算法上的正确性。
   - 答:Dekker 算法依赖"写 flag 后读对方 flag"的顺序。SC 下正确。TSO 下写-读可重排,两线程可能都读到对方 flag=false 同时进入临界区——失效,需 `MFENCE`。Relaxed(ARM)下更严重,读-读、读-写都可重排,需 `DMB` 全屏障。故 Dekker 在 TSO/Relaxed 下必须用 seq_cst 或显式屏障。
