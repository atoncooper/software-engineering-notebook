## 一、问题定义

### 1.1 解决什么问题

写完并行程序后，工程上必须回答三个问题：

1. **它比串行快多少？**（加速比 $S_P$）
2. **加更多核还能继续变快吗？**（强扩展 / 弱扩展）
3. **现在的瓶颈是计算、带宽还是延迟？**（Roofline 定位）

没有性能模型，调优就是盲调。本章把这三组工具一次讲透。

### 1.2 与上一章的衔接

§1 给出了物理"墙"（内存墙/通信墙/功耗墙）；本章把这些墙**数学化**：Amdahl 把串行比例封顶化，Roofline 把算力与带宽统一在一张图上。

## 二、核心概念与术语

| 术语 | 含义 |
|------|------|
| Speedup $S_P$ | $S_P = T_1 / T_P$ |
| Efficiency $E_P$ | $E_P = S_P / P$ |
| Strong Scaling | 问题规模固定，$P$ 增大，看 $S_P$ |
| Weak Scaling | 每处理器问题规模固定，$P$ 增大，看效率是否保持 |
| Work $W$ | 总操作数 $= T_1$ |
| Span $D$ | 关键路径长度 $= T_\infty$ |
| Parallelism $W/D$ | 平均可用并行度 |
| Arithmetic Intensity $I$ | FLOP / Byte |
| Roofline | 算力 × 算术强度的性能上限曲线 |
| Karp-Flatt $e$ | 实测串行比例 |

## 三、原理与机制

### 3.1 阿姆达尔定律（强扩展） 📜🎓

**问题**：程序中可并行占比 $f$，串行占比 $1-f$，$P$ 个处理器下：

$$
T_P = T_1 \left( (1-f) + \frac{f}{P} \right)
$$

$$
S_P = \frac{T_1}{T_P} = \frac{1}{(1-f) + f/P}
$$

$$
\lim_{P\to\infty} S_P = \frac{1}{1-f}
$$

**含义**：即使无限加核，加速比被串行比例 $(1-f)$ **封顶**。

**数值直觉**：
- $f=0.99$（仅 1% 串行）→ 最大加速比 100；
- $f=0.999$（0.1% 串行）→ 最大加速比 1000；
- 这就是为什么千卡训练里**任何 0.1% 的串行代码都会变成致命瓶颈**。

### 3.2 古斯塔夫森定律（弱扩展） 📜

Amdahl 假设**问题规模固定**。Gustafson 指出：实际中加核通常是为了**解决更大问题**，于是：

$$
S_P = P - \alpha(P-1)
$$

其中 $\alpha$ 是串行执行时间占比（在 $P$ 个处理器上跑规模 $P\cdot n$ 时）。

**含义**：问题规模随 $P$ 线性增长时，加速比近似线性——前提是串行部分 $\alpha$ 不随规模增长。

**对比**：

| 维度 | Amdahl | Gustafson |
|------|--------|-----------|
| 问题规模 | 固定 | 随 $P$ 增长 |
| 适用 | 强扩展 | 弱扩展 |
| 结论 | 悲观（封顶） | 乐观（近线性） |
| 典型场景 | 固定 1B 模型加卡 | 模型随卡数增大 |

### 3.3 Karp-Flatt 度量 🎓

Amdahl 中 $f$ 难以直接测量。Karp-Flatt 给出从实测 $S_P$ 反推串行比例 $e$：

$$
e = \frac{(1/S_P) - (1/P)}{1 - 1/P}
$$

**用途**：实测不同 $P$ 下的 $S_P$，若 $e$ 接近常数，说明瓶颈是串行代码；若 $e$ 随 $P$ 增长，说明是通信/同步开销主导。

### 3.4 Work-Span 模型 🎓

**对算法**而非硬件建模，定义：
- $W$：总操作数（work）；
- $D$：关键路径长度（span，即无限处理器下运行时间）。

**调度下界**：
$$
T_P \ge \max\left(\frac{W}{P},\ D\right)
$$

- $W/P$：所有处理器均匀分摊 work；
- $D$：关键路径无法并行。

**并行度** $\Phi = W/D$：表示该算法最多能利用 $\Phi$ 个处理器。

**例子**：并行 reduce
- $W = n-1$ 次加法
- $D = \log_2 n$（树形归约）
- $\Phi = (n-1)/\log_2 n$ → 千万元素 reduce 最多用 ~350 万核就饱和

### 3.5 Roofline 模型 📜🔥

**核心公式**：

$$
\text{Attainable FLOP/s} = \min\left(\pi_{\text{peak}},\ \beta_{\text{peak}} \cdot I\right)
$$

其中：
- $\pi_{\text{peak}}$：峰值算力（FLOP/s）；
- $\beta_{\text{peak}}$：峰值带宽（Byte/s）；
- $I$：算术强度（FLOP/Byte）。

**图示**（对数坐标）：
```
FLOP/s (log)
  │
π ├─────────────────────────  ← 算力屋顶
  │                         ╲
  │                          ╲
  │                           ╲  ← 带宽斜线（斜率=带宽）
  │                            ╲
  │                             ╲
  └──────────────────────────────→ Arithmetic Intensity (log)
            I_peak = π/β
```

- 左侧（$I < \pi/\beta$）：**带宽受限**；
- 右侧（$I > \pi/\beta$）：**算力受限**；
- 拐点 $I_{\text{peak}} = \pi / \beta$。

**H100 SXM 关键数字**：
- $\pi$（FP16 Tensor Core 稠密）= 989 TFLOP/s；
- $\beta$（HBM3）= 3.35 TB/s；
- 拐点 $I = 989/3.35 \approx 295$ FLOP/Byte。

也就是说：**任何 kernel 要在 H100 上跑满算力，每读 1 字节至少要做 295 次运算**。

### 3.6 强弱扩展曲线解读

```
Strong Scaling                  Weak Scaling
S_P                              E_P (efficiency)
  │     ╱                         │ ━━━━━━━━━━ 1.0
  │   ╱                           │
  │ ╱                             │
  │╱                              │
  └──────→ P                      └──────→ P
   理想: S_P=P                    理想: E_P=1
   实际: 受 Amdahl 封顶            实际: 受通信/同步拖累
```

## 四、算法 / 流程

### 4.1 Roofline 实测流程

```
1. 确定硬件峰值 π, β（查 spec）
2. 测量 kernel 实际 FLOP/s（用 profiler）
3. 计算 kernel 算术强度 I = FLOPs / Bytes
4. 在 Roofline 图上画点 (I, 实际 FLOP/s)
5. 看点离哪条屋顶近 → 瓶颈定位
6. 若离带宽屋近 → 优化访存（合并/pack）
7. 若离算力屋近 → 优化计算（Tensor Core/向量化）
```

### 4.2 强扩展测试流程

```
for P in [1, 2, 4, 8, 16, 32, 64]:
    T_P = bench(problem_size=FIXED, processors=P)
    S_P = T_1 / T_P
    e = ((1/S_P) - (1/P)) / (1 - 1/P)   # Karp-Flatt
    print(P, T_P, S_P, e)
```

## 六、代码示例

### 6.1 最小可运行版（教学）：Python 绘制 Roofline 与 Amdahl

```python
# file: roofline_amdahl.py
# 运行: python roofline_amdahl.py
import numpy as np
import matplotlib.pyplot as plt

# === Amdahl 与 Gustafson 对比 ===
P = np.arange(1, 257)

def amdahl(f, P):
    return 1 / ((1 - f) + f / P)

def gustafson(alpha, P):
    return P - alpha * (P - 1)

plt.figure(figsize=(10, 4))
plt.subplot(1, 2, 1)
for f in [0.9, 0.99, 0.999]:
    plt.plot(P, amdahl(f, P), label=f'Amdahl f={f}')
plt.plot(P, P, 'k--', label='Ideal')
plt.xscale('log'); plt.yscale('log')
plt.xlabel('P'); plt.ylabel('Speedup'); plt.legend(); plt.title('Strong Scaling')

# === Roofline H100 ===
pi = 989e12   # FP16 TC dense TFLOPS
beta = 3.35e12  # HBM TB/s
I = np.logspace(-2, 4, 500)  # FLOP/Byte
roof = np.minimum(pi, beta * I)
peak_point = pi / beta

plt.subplot(1, 2, 2)
plt.loglog(I, roof, 'b-', label='H100 Roofline')
plt.axvline(peak_point, color='r', ls='--', label=f'I_peak={peak_point:.0f}')
plt.xlabel('Arithmetic Intensity (FLOP/Byte)')
plt.ylabel('Attainable FLOP/s')
plt.legend(); plt.title('H100 SXM Roofline (FP16)')
plt.tight_layout()
plt.savefig('roofline_amdahl.png', dpi=100)
print("Saved roofline_amdahl.png")
```

**输出图**：左侧 Amdahl 曲线随 $f$ 不同呈现不同封顶；右侧 H100 Roofline 在 $I \approx 295$ 处拐弯。

### 6.2 生产级版（工程）：实测 GPU kernel Roofline

```cpp
// file: roofline_bench.cu
// 编译: nvcc -O3 -arch=sm_90 roofline_bench.cu -o rb
// 运行: ./rb
#include <cuda_runtime.h>
#include <cstdio>
#include <cstdint>

// 向量加：算术强度极低
__global__ void vec_add(const float* a, const float* b, float* c, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) c[i] = a[i] + b[i];
}

// GEMM-like（简化）：算术强度高
__global__ void gemm_like(const float* A, const float* B, float* C, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) {
        float acc = 0;
        #pragma unroll 8
        for (int k = 0; k < 64; ++k) acc += A[i*64+k] * B[k];
        C[i] = acc;
    }
}

#define CK(x) do { auto _e = (x); if (_e != cudaSuccess) { \
    printf("CUDA err %s:%d: %s\n", __FILE__, __LINE__, cudaGetErrorString(_e)); exit(1); \
}} while(0)

int main() {
    const int N = 1 << 24;  // 16M
    float *a, *b, *c;
    CK(cudaMallocManaged(&a, N * sizeof(float)));
    CK(cudaMallocManaged(&b, N * sizeof(float)));
    CK(cudaMallocManaged(&c, N * sizeof(float)));
    for (int i = 0; i < N; ++i) { a[i] = i * 0.001f; b[i] = -i * 0.001f; }

    int block = 256, grid = (N + block - 1) / block;

    // 预热
    vec_add<<<grid, block>>>(a, b, c, N);
    CK(cudaDeviceSynchronize());

    // 计时
    cudaEvent_t s, e;
    cudaEventCreate(&s); cudaEventCreate(&e);
    cudaEventRecord(s);
    for (int t = 0; t < 100; ++t) vec_add<<<grid, block>>>(a, b, c, N);
    cudaEventRecord(e);
    CK(cudaDeviceSynchronize());
    float ms = 0; cudaEventElapsedTime(&ms, s, e);

    // vec_add: 1 FLOP / 12 Bytes (读2写1) → I = 1/12 ≈ 0.083
    double flops = 100.0 * N;
    double bytes = 100.0 * N * 3 * sizeof(float);
    double gflops = flops / (ms / 1000.0) / 1e9;
    double gbs = bytes / (ms / 1000.0) / 1e9;
    printf("vec_add: %.2f GFLOP/s, %.2f GB/s, I=%.3f\n", gflops, gbs, 1.0/12);

    CK(cudaFree(a)); CK(cudaFree(b)); CK(cudaFree(c));
    return 0;
}
```

**预期输出**（H100）：
```
vec_add: 3,400 GFLOP/s, 40800 GB/s, I=0.083
```
对比 H100 HBM 带宽 3350 GB/s：**带宽利用率 ~12%**——典型带宽受限 kernel，点在 Roofline 斜线下方很远。优化方向是减少访存次数（如 kernel fusion）。

### 6.3 手把手：用 Nsight Compute 看 Roofline

```bash
# 2. 用 NCU 采集

# 3. 输出会直接给出：
#    - 实测 FLOP/s 与带宽

#    - 在 Roofline 图上的位置

```

## 七、常见陷阱与最佳实践 ⚠️

| 陷阱 | 后果 | 对策 |
|------|------|------|
| 用 Amdahl 解释弱扩展 | 结论悲观错误 | 弱扩展用 Gustafson |
| 用峰值算力当 Roofline 屋顶 | 高估性能 | 用实测峰值（通常 70-80%） |
| 忽略通信开销 | scaling 曲线过早饱和 | 用 Karp-Flatt 看 $e$ 是否随 P 增长 |
| Roofline 不考虑 cache 命中 | 低估带宽受限 kernel 性能 | 用多层 Roofline（L1/L2/HBM） |
| 强扩展测到 P=1024 | 显得加速比差 | 改用弱扩展测大规模 |
| MFU 用 FP16 峰值除以 FP32 实测 | MFU 失真 | 算力与峰值同一精度 |

| 问 | 答 |
|----|-----|
| Amdahl 公式？ | $S_P = 1/((1-f)+f/P)$，串行比例封顶 |

## 十、综合面试题

1. **基础**：程序中 5% 串行，1024 核时加速比上限？
   - 答：$S_{1024} = 1/(0.05 + 0.95/1024) \approx 19.6$，远低于 1024。即使 0.5% 串行，上限也只有 ~170。

2. **进阶**：实测 64 GPU 训练 MFU=55%，强扩展到 256 GPU 时 MFU 降到 30%。可能原因？
   - 答：(1) AllReduce 通信占比随 P 增大；(2) 显存冗余增加导致 batch 减小；(3) straggler；(4) 网络拥塞。用 Karp-Flatt 验证。

3. **深度**：某 GPU kernel 算术强度 $I=10$ FLOP/Byte，实测 200 TFLOP/s，硬件峰值 1000 TFLOP/s、带宽 3000 GB/s。瓶颈在哪？怎么优化？
   - 答：Roofline 上限 $= \min(1000, 3000\times 10) = 1000$ TFLOP/s，实测 200 TFLOP/s，离上限很远。可能瓶颈：(1) 访存未合并；(2) occupancy 低；(3) 没用 Tensor Core。优化：合并访存 → Tile 化 → 用 wmma。

4. **设计**：设计一个强扩展实验，验证你的 reduce 实现是否达到 Work-Span 下界。
   - 答：固定 $n=10^8$，测 $P \in \{1,2,4,\dots,256\}$ 下的 $T_P$。理想 $T_P = \max((n-1)/P, \log_2 n)$。绘制 $T_P$ vs $P$ 曲线，对照下界。当 $P > (n-1)/\log_2 n \approx 3\times 10^6$ 时进入 span 限制（实际在 $P \approx$ 数千就饱和，因通信开销）。

5. **工程**：为什么 LLM 训练常用 MFU 而非强扩展加速比？
   - 答：(1) 模型规模随卡数增长（弱扩展）；(2) MFU 直接反映硬件利用率，便于跨硬件/模型比较；(3) 业界以 MFU 50%+ 为优秀基线（H100 Llama 训练）。

6. **学术**：证明 Work-Span 调度下界 $T_P \ge \max(W/P, D)$。
   - 答：(1) 每个处理器每步执行 1 op，$P$ 个处理器 $T_P$ 步最多执行 $P\cdot T_P$ op，故 $W \le P\cdot T_P \Rightarrow T_P \ge W/P$。(2) 关键路径上 $D$ 个 op 存在依赖，无法并行，故 $T_P \ge D$。两者取 max。
