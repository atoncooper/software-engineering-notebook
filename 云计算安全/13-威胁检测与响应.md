## 一 问题定义

### 1.1 业务痛点

1. **检测滞后**：行业平均 MTTD（Mean Time To Detect）= 204 天，MTTR（Mean Time To Respond）= 73 天（IBM 2023）。云环境下攻击者从初始访问到外泄可压缩到几小时。
2. **告警疲劳**：GuardDuty 单账户日均 100+ finding，95% 低优先级；SOC 团队淹没在告警中。
3. **云取证难**：容器易失、实例 ephemeral、跨账号调用链复杂；传统磁盘取证不适用。
4. **自动化陷阱**：自动化响应误伤合法用户（如封禁管理员 IP）；SOAR 剧本设计不当引发连锁故障。
5. **跨云不一致**：AWS GuardDuty 与 Azure Defender 规则、严重性、API 不统一。

### 1.2 云厂商差异

| 维度 | AWS | Azure | GCP | 阿里云 | 华为云 |
|------|-----|-------|-----|--------|--------|
| 威胁检测 | GuardDuty | Defender for Cloud | SCC Premium | 云安全中心 | SecMaster |
| 调查 | Detective | Sentinel | Chronicle | - | - |
| 自动响应 | Lambda + EventBridge | Logic App | Cloud Functions | 函数计算 | FunctionGraph |
| SOAR | 第三方 | Sentinel Playbook | Chronicle SOAR | - | - |
| 威胁情报 | AWS TI | MS TI | Mandiant | 阿里云 TI | 华为云 TI |
| 取证 | Fargate snapshot | Azure 工具 | GKE snapshot | - | - |

### 1.3 反模式

- ❌ GuardDuty finding 仅发邮件，无自动化响应。
- ❌ 检测规则无 MITRE ATT&CK 映射，覆盖率不可评估。
- ❌ Playbook 自动隔离 EC2 但未保留 snapshot，证据丢失。
- ❌ Critical finding 30 分钟才通知（Slack 邮件链路慢）。
- ❌ 跨账号 STS 调用链不追溯，找根因靠人工翻 CloudTrail。
- ❌ IR 演练只做桌面推演，无实际触发 GuardDuty 的 red team 测试。

## 三 原理与机制

### 3.1 杀伤链 vs MITRE ATT&CK 🎓

**Cyber Kill Chain（Lockheed Martin）**：7 阶段，线性模型。
1. Reconnaissance → 2. Weaponization → 3. Delivery → 4. Exploitation → 5. Installation → 6. C2 → 7. Action on Objectives

**MITRE ATT&CK**：14 战术（Tactics）× 数百技术（Techniques），矩阵模型。
- Reconnaissance / Resource Development / Initial Access / Execution / Persistence / Privilege Escalation / Defense Evasion / Credential Access / Discovery / Lateral Movement / Collection / Command and Control / Exfiltration / Impact

**对比**：

| 维度 | Kill Chain | ATT&CK |
|------|-----------|--------|
| 模型 | 线性 7 阶段 | 矩阵 14 战术 × N 技术 |
| 适用 | 网络边界防御 | 端点+云+身份 |
| 检测覆盖 | 阶段切分 | 技术级覆盖矩阵 |
| 行业采用 | 经典 | 主流 |

### 3.2 GuardDuty 检测原理 🎓

GuardDuty 三类检测源：

1. **签名规则**：基于 AWS 维护的威胁情报（恶意 IP、域名）。
2. **机器学习**：对 CloudTrail、VPC Flow、DNS 建立基线，检测异常。
3. **异常检测**：基于 EC2 行为基线（网络行为、API 调用模式）。

**Finding 结构**：

```json
{
  "schemaVersion": "2.0",
  "accountId": "123456789012",
  "region": "us-east-1",
  "type": "UnauthorizedAccess:IAMUser/InstanceCredentialExfiltration.OutsideAWS",
  "severity": 8.0,  // 0-10，1.0-3.9 Low，4.0-6.9 Medium，7.0-8.9 High，9.0-10 Critical
  "title": "Credentials generated for an EC2 instance are being used outside of AWS.",
  "description": "IAM Access Key ABC... was generated on EC2 instance i-xxx and is being used from IP 1.2.3.4.",
  "service": {
    "action": {
      "actionType": "NETWORK_CONNECTION",
      "networkConnectionAction": {"remoteIpDetails": {"ipAddressV4": "1.2.3.4"}}
    },
    "evidence": {...},
    "firstSeen": "2026-07-04T10:00:00Z",
    "lastSeen": "2026-07-04T11:00:00Z"
  },
  "resource": {
    "resourceType": "Instance",
    "instanceDetails": {"instanceId": "i-xxx", ...}
  }
}
```

**关键 Finding 类型**：
- `UnauthorizedAccess:IAMUser/ConsoleLoginFromBadLocation`：异常地理位置登录
- `UnauthorizedAccess:IAMUser/InstanceCredentialExfiltration.OutsideAWS`：EC2 凭证在 AWS 外使用（Capital One 模式）
- `Persistence:IAMUser/BackdoorClassicKey`：创建经典 AccessKey（持久化）
- `DefenseEvasion:IAMUser/RootCredentialUsage`：Root 凭证使用
- `Exfiltration:S3/MaliciousIPCaller`：S3 数据被恶意 IP 访问
- `Trojan:EC2/DriveBySourceTraffic`：EC2 与 C2 通信

### 3.3 NIST IR 生命周期 🎓

**NIST SP 800-61** 四阶段：

```
Preparation → Detection & Analysis → Containment, Eradication, Recovery → Post-Incident
   ↑                                                                        ↓
   └─────────────────────────────── feedback ──────────────────────────────┘
```

**1. Preparation（准备）**：
- IR 团队组建与培训
- Runbook 文档化
- 工具准备（取证 VM、Quarantine VPC）
- 联系人目录（法务、PR、监管）

**2. Detection & Analysis（检测分析）**：
- 告警分类（True/False Positive）
- 严重性评估（数据范围、业务影响）
- 杀伤链定位（攻击者当前阶段）
- 取证证据收集（按易失性顺序）

**3. Containment, Eradication, Recovery（遏制、根除、恢复）**：
- Containment：隔离实例、disable 凭证、block IP
- Eradication：删除后门、修补漏洞、轮转密钥
- Recovery：从干净备份恢复、验证完整性、重新上线

**4. Post-Incident（事后）**：
- 复盘会议（无指责文化）
- 根因分析（5 Whys）
- 改进措施跟踪
- 报告监管（如适用）

### 3.4 SOAR Playbook 机制 🎓

**Playbook 触发方式**：
- 自动：SIEM/检测服务 finding 触发
- 半自动：SOC 分析师手动触发
- 定时：周期性巡检

**人在环（Human-in-the-loop）**：
- Critical finding：自动响应需 SOC 批准
- Medium finding：自动响应 + 事后通知
- Low finding：完全自动

**示例 Playbook 流程**：

```
1. GuardDuty finding: UnauthorizedAccess:IAMUser/InstanceCredentialExfiltration
2. SOAR 触发 Playbook
3. 自动步骤：
   a. 获取 finding 详情（GuardDuty API）
   b. 提取 access key id
   c. disable access key（IAM API）
   d. 隔离 EC2 实例（改 SG 为 quarantine）
   e. 创建 EBS snapshot（取证）
4. 人工审批：
   a. 通知 SOC oncall（Slack）
   b. 等待 15 分钟审批
5. 审批后自动步骤：
   a. 终止 EC2 实例
   b. CloudTrail 回溯 24h 该 key 所有调用
   c. 生成事件报告
6. 事后：
   a. JIRA 创建跟踪 ticket
   b. 复盘会议安排
```

### 3.5 实例隔离（Quarantine）机制 🎓

**网络隔离**：将实例 SG 替换为 quarantine SG（仅允许 SOC 取证访问）。

```python
def quarantine_instance(instance_id, region):
    ec2 = boto3.client("ec2", region_name=region)
    
    # 1. 创建 quarantine SG（如不存在）
    quarantine_sg = ensure_quarantine_sg(ec2, region)
    
    # 2. 备份原 SG 列表（恢复用）
    original_sgs = ec2.describe_instances(InstanceIds=[instance_id]) \
        ["Reservations"][0]["Instances"][0]["SecurityGroups"]
    backup_sgs = [sg["GroupId"] for sg in original_sgs]
    
    # 3. 替换为 quarantine SG（保留管理 SG）
    ec2.modify_instance_attribute(
        InstanceId=instance_id,
        Groups=[quarantine_sg],  # 仅 quarantine
    )
    
    # 4. 创建 EBS snapshot（取证）
    for dev in ec2.describe_instances(InstanceIds=[instance_id]) \
        ["Reservations"][0]["Instances"][0]["BlockDeviceMappings"]:
        if "Ebs" in dev:
            ec2.create_snapshot(
                VolumeId=dev["Ebs"]["VolumeId"],
                Description=f"quarantine-forensics-{instance_id}-{int(time.time())}",
                TagSpecifications=[{
                    "ResourceType": "snapshot",
                    "Tags": [
                        {"Key": "Incident", "Value": instance_id},
                        {"Key": "OriginalSGs", "Value": ",".join(backup_sgs)},
                    ],
                }],
            )
    
    # 5. 写入 DynamoDB（恢复用）
    restore_table.put_item(Item={
        "InstanceId": instance_id,
        "OriginalSGs": backup_sgs,
        "QuarantineTime": int(time.time()),
        "FindingId": finding_id,
    })
```

**注意**：替换 SG 不断网络连接（已建立的 TCP 不重置），但新连接被阻止。彻底隔离需 detach ENI 或停机。

```
function PROCESS_GUARDDUTY_FINDING(finding):
    # 1. 解析 finding
    severity = finding.severity
    finding_type = finding.type
    resource = finding.resource
    
    # 2. 路由到对应 Playbook
    playbook = PLAYBOOK_REGISTRY[finding_type]
    
    # 3. 严重性决策
    if severity >= 9.0:  # Critical
        run_playbook(playbook, finding, requires_approval=True)
    elif severity >= 7.0:  # High
        run_playbook(playbook, finding, requires_approval=False, notify=True)
    elif severity >= 4.0:  # Medium
        log_to_siem(finding)
        daily_digest(finding)
    else:  # Low
        log_to_siem(finding)
    
    # 4. MITRE ATT&CK 映射
    attack_tactic = ATT&CK_MAP[finding_type]
    update_coverage_matrix(attack_tactic)
```

```
function RECONSTRUCT_KILL_CHAIN(incident_id):
    # 给定一个事件，从 CloudTrail + VPC Flow + EDR 日志还原攻击链
    all_events = []
    
    # 1. 收集所有相关日志
    cloudtrail = CloudTrail.query(finding.firstSeen - 24h, finding.lastSeen + 24h)
    vpc_flow = VPCFlow.query(...)
    edr = EDR.query(...)
    
    all_events.extend(cloudtrail + vpc_flow + edr)
    
    # 2. 按 ATT&CK 战术分类
    kill_chain = {tactic: [] for tactic in ATT&CK_TACTICS}
    for event in all_events:
        tactic = classify_event(event)
        kill_chain[tactic].append(event)
    
    # 3. 时间线排序
    for tactic in kill_chain:
        kill_chain[tactic].sort(key=lambda e: e.timestamp)
    
    # 4. 输出时间线
    return Timeline(kill_chain)
    # 复杂度：O(N log N) 排序
```

```
function VISUALIZE_ATTACK_PATH(incident):

    # 高亮外泄路径
```

## 六 代码/配置示例

### 6.1 教学示例：GuardDuty Finding 处理

```python
import boto3
import json

def lambda_handler(event, context):
    finding = json.loads(event["detail"]["finding"])
    
    severity = finding["severity"]
    finding_type = finding["type"]
    resource_type = finding["resource"]["resourceType"]
    
    # Critical/High 立即响应
    if severity >= 7.0:
        if finding_type.startswith("UnauthorizedAccess:IAMUser/InstanceCredentialExfiltration"):
            handle_credential_exfil(finding)
        elif finding_type.startswith("Recon:EC2"):
            handle_recon(finding)
        elif finding_type.startswith("Exfiltration:S3"):
            handle_s3_exfil(finding)
    
    # 写入 SIEM
    send_to_siem(finding)
    
    # 通知 Slack
    notify_slack(finding)

def handle_credential_exfil(finding):
    access_key_id = finding["service"]["action"]["awsApiCallAction"]["apiKey"]
    instance_id = finding["resource"]["instanceDetails"]["instanceId"]
    
    # 1. Disable access key
    iam = boto3.client("iam")
    iam.update_access_key(
        AccessKeyId=access_key_id,
        Status="Inactive",
    )
    
    # 2. Quarantine instance
    ec2 = boto3.client("ec2")
    ec2.modify_instance_attribute(
        InstanceId=instance_id,
        Groups=["sg-quarantine"],
    )
    
    # 3. Snapshot for forensics
    volumes = ec2.describe_volumes(Filters=[{"Name": "attachment.instance-id", "Values": [instance_id]}])
    for vol in volumes["Volumes"]:
        ec2.create_snapshot(
            VolumeId=vol["VolumeId"],
            Description=f"forensics-{instance_id}-{finding['id']}",
```

### 6.6 实例隔离 + 内存取证

```python
import boto3
import time

def isolate_and_forensics(instance_id, region, finding_id):
    ec2 = boto3.client("ec2", region_name=region)
    ssm = boto3.client("ssm", region_name=region)
    
    # 1. 备份原 SG
    instance = ec2.describe_instances(InstanceIds=[instance_id])["Reservations"][0]["Instances"][0]
    original_sgs = [sg["GroupId"] for sg in instance["SecurityGroups"]]
    
    # 2. 替换 SG（隔离）
    ec2.modify_instance_attribute(
        InstanceId=instance_id,
        Groups=["sg-quarantine"],
    )
    
    # 3. EBS Snapshot（磁盘取证）
    for dev in instance["BlockDeviceMappings"]:
        if "Ebs" in dev:
            snap = ec2.create_snapshot(
                VolumeId=dev["Ebs"]["VolumeId"],
                Description=f"forensics-{instance_id}-{finding_id}",
                TagSpecifications=[{
                    "ResourceType": "snapshot",
                    "Tags": [
                        {"Key": "Incident", "Value": finding_id},
                        {"Key": "OriginalSGs", "Value": ",".join(original_sgs)},
                        {"Key": "Forensics", "Value": "true"},
                    ],
                }],
            )
    
    # 4. 内存 dump（如实例还在运行）
    try:
        ssm.send_command(
            InstanceIds=[instance_id],
            DocumentName="AWS-RunShellScript",
            Parameters={"commands": [
                "sudo yum install -y gdb",
                f"sudo gcore -o /tmp/memdump $(pgrep -f 'app')",
                f"sudo chmod 644 /tmp/memdump.*",
                f"aws s3 cp /tmp/memdump.* s3://forensics/{finding_id}/",
            ]},
        )
    except Exception as e:
        print(f"Memory dump failed: {e}")
    
    # 5. 记录到 DynamoDB（恢复用）
    dynamodb = boto3.client("dynamodb", region_name=region)
    dynamodb.put_item(
        TableName="incident-forensics",
        Item={
            "InstanceId": {"S": instance_id},
            "FindingId": {"S": finding_id},
            "OriginalSGs": {"SS": original_sgs},
            "QuarantineTime": {"N": str(int(time.time()))},
            "Status": {"S": "QUARANTINED"},
        },
    )
```

## 七 常见陷阱与最佳实践

### 7.1 陷阱表 ⚠️

| 陷阱 | 描述 | 后果 | 规避 |
|------|------|------|------|
| 自动响应误伤 | Playbook 封禁合法 IP | 业务中断 | 人在环审批 + 白名单 |
| Snapshot 没保留 | 隔离后立即终止实例 | 证据丢失 | Snapshot 保留 90 天 |
| 跨账号 STS 链不追溯 | 只看当前账号 | 找不到根因 | Detective 自动关联 |
| Critical finding 邮件通知 | 邮件链路 30 分钟 | MTTD 长 | PagerDuty + Slack 直接 page |
| GuardDuty 不开 K8s | EKS 攻击无检测 | 横向移动不可见 | K8s Audit Log 数据源 |
| 不演练 Playbook | 真事件时 SOAR 失败 | 响应瘫痪 | 季度游戏日演练 |
| 隔离 SG 仍允许 egress | 仅替换 Inbound | 数据继续外泄 | egress 全 deny |
| 凭证 disable 不 revoke | STS 临时凭证仍有效 | 攻击继续 | revoke sessions + 等待 TTL |
| WAF 封禁 IP 误封 NAT | 企业出口共用 IP | 全公司访问受阻 | 限频率不直接封 |
| 取证不记录 hash | 证据可被质疑 | 法庭不可用 | SHA-256 + 链式签名 |

### 7.2 最佳实践

1. **多账号集中**：GuardDuty Organization 配置，所有账号自动开启，finding 集中到安全账号。
2. **MITRE ATT&CK 覆盖率**：定期评估哪些 T 编号无检测规则，优先补齐。
3. **Detection-as-Code**：Sigma 规则版本化 + CI 测试 + 自动部署。
4. **人在环**：Critical 自动响应需 SOC 批准，Medium 自动 + 通知，Low 完全自动。
5. **取证优先**：响应前先 snapshot，证据完整性 > 速度。
6. **MTTD/MTTR 度量**：每事件记录检测时间、响应时间，季度复盘改进。
7. **Purple Team 演练**：红队模拟 ATT&CK，蓝队检测响应，季度一次。
8. **Canary Token**：假凭证（AWS AccessKey、DB 口令）散布，触发即告警。
9. **Playbook 模板化**：通用步骤（隔离、snapshot、通知）抽公共库，复用。
10. **跨云统一**：用 Sigma 规则跨 AWS/Azure/GCP，避免检测逻辑碎片化。

## 九 面试速答 ⭐

**Q1：GuardDuty 检测原理？**
基于 CloudTrail、VPC Flow、DNS 三类日志，结合 AWS 维护的威胁情报（恶意 IP/域名）、机器学习基线、签名规则。Finding 严重性 0-10，>=7 High，>=9 Critical。

**Q2：MTTD/MTTR 怎么优化？**
MTTD：自动检测（GuardDuty）+ Sigma 规则覆盖 ATT&CK + Canary Token 早期告警；MTTR：SOAR Playbook 自动隔离/取证 + 人在环审批 + Runbook 文档化。

**Q3：实例隔离怎么做？**
1) 替换 SG 为 quarantine SG（无 egress）；2) EBS Snapshot 取证；3) SSM 内存 dump；4) DynamoDB 记录原 SG 用于恢复；5) 等待 SOC 审批后终止或恢复。

**Q4：MITRE ATT&CK 怎么用？**
每个检测规则映射 T 编号（如 T1078 Valid Accounts），定期评估覆盖率热图（哪些 T 无规则），用 Atomic Red Team 测试规则有效性，Purple Team 演练验证。

**Q5：Capital One 事件如何被检测？**
GuardDuty UnauthorizedAccess:IAMUser/InstanceCredentialExfiltration.OutsideAWS finding——EC2 凭证在 AWS 外使用。但 Capital One 当时未开 GuardDuty，事后才从 CloudTrail 追溯。启示：开 GuardDuty 是基础。

**Q6：自动响应误伤怎么办？**
1) Critical 人在环审批；2) 维护白名单（管理员 IP、合规扫描器）；3) 频率限制（不直接封 IP，先 throttle）；4) 演练验证 Playbook；5) 监控 Playbook 失败率 > 阈值告警。

**Q7：跨账号 STS 链怎么追溯？**
CloudTrail userIdentity.sessionContext.sessionIssuer.arn 指向上一 assume role，递归查 AssumeRole 事件。AWS Detective 自动构建资源图，可视化调用链。

**Q8：取证证据完整性怎么保证？**
1) 收集时记录 SHA-256；2) WORM 桶 + Legal Hold 存储；3) 链式签名（每访问一次签名）；4) 时间戳用 NTP 同步；5) Chain of Custody 文档化（收集人、时间、源）。

**Q9：GuardDuty 与 Sentinel 怎么选？**
AWS 主用 GuardDuty；Azure 主用 Defender for Cloud；跨云场景两者都开，finding 集中到 Splunk/Sentinel 统一分析。Sigma 规则跨平台复用检测逻辑。

**Q10：Canary Token 是什么？**
假凭证（AWS AccessKey、DB 口令、API Key）散布在代码、配置、文档中，被使用即触发告警。Thinkst Canary、SpaceCrab 等工具。早期告警，攻击者拿到即用，触发即暴露。

## 十 综合面试题

1. **设计题**：200 账号 AWS Organization，如何设计威胁检测体系？
   要点：1) GuardDuty Organization 配置，安全账号为 admin；2) 所有账号自动开启 GuardDuty + Security Hub；3) Finding 集中到 Security Hub；4) EventBridge 路由 Critical finding 到 Lambda 自动响应；5) Detective 构建跨账号调用图；6) Sigma 规则跨账号统一；7) 季度 Purple Team 演练。

2. **场景题**：GuardDuty 报 UnauthorizedAccess:EC2/SSHBruteForce，怎么响应？
   要点：1) 查 IP 是否已知扫描器（AbuseIPDB）；2) 查 EC2 是否被攻破（最近登录、SSH key）；3) 限制 SG 仅允许企业 IP；4) 改用 SSM Session Manager 替代 SSH；5) Fail2ban 或 AWS WAF rate limit；6) 评估是否需要隔离实例。

3. **原理题**：MITRE ATT&CK 矩阵覆盖率怎么评估？
   要点：1) 列出所有检测规则 → 映射 T 编号；2) ATT&CK 矩阵标红已覆盖；3) 评估未覆盖 T 优先级（如 Lateral Movement 高优先）；4) Atomic Red Team 测试规则有效性；5) 季度复盘 + 补规则；6) 评估矩阵：覆盖 T 数 / 总 T 数。

4. **场景题**：发现某 IAM Role 在凌晨 3 点调用 CreateAccessKey 创建新 key，怎么调查？
   要点：1) GuardDuty Persistence:IAMUser/BackdoorClassicKey finding；2) 立即 disable 新 key；3) CloudTrail 查该 Role 24h 所有调用；4) 追溯 STS 链找原始调用者；5) 检查是否其他持久化（创建 User、修改 Key Policy）；6) 轮转所有该 Role 用过的密钥；7) IR 复盘。

5. **设计题**：SOAR Playbook 自动化到什么程度？
   要点：1) 完全自动：Low finding（如 Recon:EC2/PortProbe）封 IP；2) 自动+通知：Medium finding（如 UnauthorizedAccess:IAMUser/ConsoleLogin）发 Slack；3) 人在环：Critical finding（如 Credential Exfiltration）需 SOC 批准；4) 演练阈值：每周 Playbook 失败率 < 5%；5) 白名单：管理员 IP、合规扫描器不触发。

6. **原理题**：GuardDuty 与 CrowdStrike Falcon 区别？
   要点：GuardDuty 是云控制面检测（CloudTrail/VPC Flow），无需 agent；Falcon 是端点检测（EDR），需 agent。GuardDuty 适合 IAM/网络异常，Falcon 适合进程/文件异常。两者互补：GuardDuty 发现 EC2 异常 → Falcon 查端点根因。

7. **对比题**：Sentinel 和 Splunk SOAR 怎么选？
   要点：1) Sentinel：SaaS、Logic App、Azure 集成、KQL；2) Splunk SOAR：自建/云、Python Playbook、300+ 集成；3) Azure 为主 + 中小规模 → Sentinel；4) 多云 + 复杂自动化 → Splunk SOAR；5) 成本：Sentinel 按摄入量，Splunk 按 ingestion + SOAR 单独。

8. **场景题**：Lambda 函数被攻击者用作挖矿跳板，怎么处理？
   要点：1) GuardDuty CryptoCurrency:EC2/BitcoinTool.B finding；2) 立即 set Lambda concurrency to 0（停止新调用）；3) CloudTrail 查最近调用者；4) 检查 Lambda 代码是否被改（CodeSha256）；5) 检查 IAM Role 权限是否过宽；6) 限制 Lambda VPC 配置；7) 添加资源策略限制调用源。

9. **设计题**：容器化集群如何检测横向移动？
   要点：1) K8s Audit Log（kubectl exec、port-forward）；2) Falco 检测容器内异常进程；3) NetworkPolicy 默认 deny + 异常连接告警；4) Service Account 异常使用（如某 Pod 用 default SA 访问 K8s API）；5) GuardDuty EKS Protection；6) 容器运行时 EDR（Sysdig、Aqua）。

10. **原理题**：Canary Token 在云环境怎么部署？
    要点：1) AWS AccessKey Canary：创建 IAM User 仅 `iam:GetUser` 权限，key 散布代码/文档；2) DB 口令 Canary：DB 表插入假凭证，访问即告警；3) AWS CloudTrail 监控该 key 任何 API 调用；4) GuardDuty 自定义规则；5) 假凭证命名诱饵（如 "production-db-master-key"）；6) Thinkst Canary 商用产品。

### 事故案例 🏭
- **Capital One（2019）**: SSRF + IAM 凭证外泄 + S3 数据下载，GuardDuty 未开导致事后才发现。启示：基础检测服务必开。
- **SolarWinds（2020）**: SUNSPUR 后门通过 Orion 更新植入，CloudTrail 记录了异常但客户未告警。启示：检测规则覆盖率 + 主动狩猎。
- **Uber（2022）**: 攻击者 MFA 疲劳 + 拿到 admin，访问内部工具。启示：MFA 抗疲劳、特权账号监控。
- **LastPass（2022）**: DevOps 工程师凭证失窃 → 访问云存储 → 4 个月才完整披露。启示：开发环境凭证监控。
- **Codecov（2021）**: bash 上传器后门 2 个月未发现，CI token 被收集。启示：第三方脚本完整性 + 出站监控。
