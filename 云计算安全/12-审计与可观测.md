## 一 问题定义

### 1.1 业务痛点

1. **日志碎片化**：AWS 一家中型账户每天产生 100GB+ CloudTrail 日志，分布在 K8s 审计日志、应用日志、DB 慢查询、VPC Flow、WAF 日志等多个源，难关联。
2. **可篡改**：传统 S3 桶管理员可删除任意对象；攻击者拿到管理员权限后第一件事是清日志。
3. **隐私冲突**：审计日志含 PII（如 user-agent、SQL 语句），但合规要求日志保留 1-7 年。
4. **取证困难**：容器易失（Pod 销毁即丢现场），云主机磁盘 ephemeral，传统取证流程不适用。
5. **告警疲劳**：GuardDuty 单账户日均 100+ finding，95% 是误报或低优先级。

### 1.2 云厂商差异

| 维度 | AWS | Azure | GCP | 阿里云 | 华为云 |
|------|-----|-------|-----|--------|--------|
| 审计服务 | CloudTrail | Activity Log | Cloud Audit Logs | ActionTrail | CTS |
| 日志检索 | Athena | Log Analytics | BigQuery | SLS | LTS |
| SIEM 合作 | Splunk/Sumo Logic | Sentinel | Chronicle | 自研 SLS | 自研 LTS |
| 不可篡改 | S3 Object Lock | Immutable Blob | Bucket Lock | OSS WORM | OBS WORM |
| 网络抓包 | VPC Traffic Mirroring | Packet Capture | Packet Mirroring | VPC 流量镜像 | VPC 流量镜像 |
| 取证服务 | 没有（自建） | Azure 工具 | 没有 | 没有 | 没有 |

### 1.3 反模式

- ❌ CloudTrail 写到普通 S3 桶，IAM 管理员可删除。
- ❌ 应用日志直接打 stdout 含 password=xxx。
- ❌ 日志保留期 90 天但合规要求 1 年。
- ❌ CloudTrail 未开数据事件（S3 GetObject），取证时不知道谁读了数据。
- ❌ 多账号场景下每账号独立 CloudTrail，没有 Organization Trail 集中。
- ❌ Lambda 函数日志含完整请求体（含 PII），未脱敏。

## 三 原理与机制

### 3.1 CloudTrail 事件结构 🎓

CloudTrail 事件 JSON 结构：

```json
{
  "eventVersion": "1.08",
  "userIdentity": {
    "type": "AssumedRole",
    "principalId": "AROAEXAMPLE:app-role",
    "arn": "arn:aws:sts::123456789012:assumed-role/app-role/session",
    "sessionContext": {
      "sessionIssuer": {...},
      "attributes": {"mfaAuthenticated": "false", "creationDate": "2026-07-04T10:00:00Z"}
    }
  },
  "eventTime": "2026-07-04T10:05:23Z",
  "eventSource": "s3.amazonaws.com",
  "eventName": "GetObject",
  "awsRegion": "us-east-1",
  "sourceIPAddress": "203.0.113.10",
  "userAgent": "aws-sdk-go/1.44",
  "requestParameters": {"bucketName": "prod-data", "key": "customer.csv"},
  "responseElements": null,
  "resources": [{"type": "AWS::S3::Object", "ARN": "arn:aws:s3:::prod-data/customer.csv"}],
  "readOnly": true,
  "eventType": "AwsApiCall",
  "managementEvent": false,
  "eventCategory": "Data"
}
```

**关键字段**：
- `userIdentity`：调用者（含嵌套 sessionContext，追溯 STS 链）
- `sourceIPAddress`：源 IP（可识别异常地理位置）
- `userAgent`：调用工具（aws-cli、Terraform、Console）
- `requestParameters`：请求参数（脱敏后）
- `eventCategory`：Management / Data / Insight

### 3.2 STS 调用链追溯 🎓

跨账号 STS 调用产生嵌套 sessionContext：

```
Account A user → assume role in Account B → assume role in Account C
```

事件链：
1. A 中 `AssumeRole` 调用：`userIdentity.arn = A:user`，`requestParameters.roleArn = B:role`
2. B 中 `AssumeRole` 调用：`userIdentity.arn = B:role/session`，`sessionIssuer = B:role`，`sourceIdentity = A:user`
3. C 中 `AssumeRole` 调用：`userIdentity.arn = C:role/session`，三层 sessionContext 嵌套

**取证要点**：用 `sourceIdentity`（如配置）追溯原始调用者；否则需用 `sessionContext.sessionIssuer` 逐层回溯。

### 3.3 WORM 不可篡改机制 🎓

**S3 Object Lock 工作机制**：

1. 桶启用 Object Lock 时同时启用 Versioning（强制）。
2. 上传对象时指定 Retention：
   - Mode: COMPLIANCE（合规，到期前任何人都不能删，包括 root）或 GOVERNANCE（治理，有 `s3:BypassGovernanceRetention` 权限可绕过）
   - RetainUntilDate: 保留到期时间
3. 可单独加 Legal Hold（独立于 Retention）。
4. 删除操作：
   - COMPLIANCE 模式：到期前 DELETE 失败。
   - GOVERNANCE 模式：DELETE 失败，除非有 bypass 权限。
   - 加 Legal Hold：DELETE 失败，直到移除 Legal Hold。

**安全属性**：
- 即使攻击者拿到 root，COMPLIANCE 模式对象也无法删除（直到到期）。
- 适用于 CloudTrail 日志、金融交易记录、医疗病历。

### 3.4 OpenTelemetry 三支柱 🎓

**Logs / Metrics / Traces 区别**：

| 维度 | Logs | Metrics | Traces |
|------|------|---------|--------|
| 数据类型 | 事件流 | 数值时序 | 调用链 |
| 体积 | 大（每事件 1-10KB） | 小（每点 8-16B） | 中（每 span 1KB） |
| 用途 | 取证、审计 | 告警、容量规划 | 性能分析、根因定位 |
| 查询 | 全文检索 | 聚合查询 | span 树查询 |
| 工具 | ELK、Loki、CloudWatch Logs | Prometheus、CloudWatch Metrics | Jaeger、Tempo、CloudWatch X-Ray |

**OpenTelemetry 统一**：

```python
from opentelemetry import trace, metrics
from opentelemetry._logs import get_logger

tracer = trace.get_tracer("app")
meter = metrics.get_meter("app")
logger = get_logger("app")

with tracer.start_as_current_span("process_order") as span:
    span.set_attribute("order.id", order_id)
    counter = meter.create_counter("orders_processed")
    counter.add(1, {"status": "success"})
    logger.info("Order processed", extra={"order_id": order_id})
```

### 3.5 取证易失性顺序 🎓

按 RFC 3227 规定的易失性顺序：

```
1. CPU 缓存、寄存器（毫秒级丢失）
2. 内存（断电即失）
3. 网络状态（连接、路由表）
4. 进程（运行中进程）
5. 临时文件（/tmp、swap）
6. 磁盘（持久化文件）
7. 远程日志（已传输到日志服务）
```

**云上调整**：
- 容器易失性比 VM 更高（Pod 销毁即丢，需先 snapshot）。
- EBS 卷可 detach 后挂到取证实例。
- 内存 dump 需在 EC2 仍在运行时进行（或用 EC2Rescue）。

### 4.2 STS 调用链还原

```
function TRACE_STS_CHAIN(target_event):
    # 给定一个 CloudTrail 事件，追溯原始调用者
    chain = []
    current = target_event
    
    while current.userIdentity.sessionContext:
        issuer_arn = current.userIdentity.sessionContext.sessionIssuer.arn
        # 查找对应的 AssumeRole 事件
        assume_event = CloudTrail.query(
            eventName="AssumeRole",
            requestParameters_roleArn=issuer_arn,
            eventTime_near=current.eventTime
        )
        chain.append({
            "assume_event": assume_event,
            "source_ip": assume_event.sourceIPAddress,
            "user_agent": assume_event.userAgent
        })
        current = assume_event
    
    # 链头是 Root/User/Role
    return chain
    # 复杂度：O(d) 其中 d 是 STS 嵌套深度
```

### 4.4 UEBA 异常检测

```
function UEBA_BASELINE(user_id, lookback_days=30):
    # 学习用户行为基线
    events = CloudTrail.query(userId=user_id, last=lookback_days)
    
    baseline = {
        "ip_set": set(e.sourceIPAddress for e in events),
        "hour_histogram": histogram(e.eventTime.hour for e in events),
        "api_histogram": histogram(e.eventName for e in events),
        "geo_set": geoip(e.sourceIPAddress for e in events),
        "user_agent_set": set(e.userAgent for e in events)
    }
    
    return baseline

function UEBA_DETECT(user_id, current_event):
    baseline = UEBA_BASELINE(user_id)
    score = 0
    
    if current_event.sourceIPAddress not in baseline.ip_set:
        score += 30
    if geoip(current_event.sourceIPAddress).country not in baseline.geo_set:
        score += 40
    if current_event.eventTime.hour not in baseline.hour_histogram.p90:
        score += 10
    if current_event.eventName not in baseline.api_histogram.p95:
        score += 20
    
    if score >= 70:
        emit_alert(user_id, current_event, score)
```

### 4.5 容器取证流程

```
function CONTAINER_FORENSICS(pod_name, namespace):
    # 1. 立即冻结 Pod（不删除）
    kubectl_patch_pod(pod_name, {"spec": {"terminationGracePeriodSeconds": 3600}})
    
    # 2. 节点上 exec 进容器，dump 内存（如果还活着）
    if pod_running:
        kubectl_exec(pod_name, "gcore -o /tmp/core $PID")
        kubectl_cp(pod_name, "/tmp/core", "/forensics/core")
    
    # 3. 复制容器文件系统
    container_id = docker_inspect(pod_name).containerID
    docker_cp(container_id, "/", "/forensics/fs/")
    
    # 4. Snapshot 节点 EBS（如果怀疑节点也被入侵）
    node_ebs = ec2_describe(node_id).blockDeviceMappings
    snapshot_id = ec2_create_snapshot(node_ebs.volumeId)
    
    # 5. 网络抓包（如果 Pod 还在）
    node_if = "eth0"
    kubectl_exec(node, f"tcpdump -i {node_if} -w /tmp/cap.pcap")
    
    # 6. 收集 K8s 审计日志
    audit_log = k8s_get_audit_log(filter={"user.username": "system:serviceaccount:" + namespace})
    
    # 7. Pod 销毁前留下证据，再清理
    return ForensicsBundle(snapshot_id, audit_log, core_dump, fs_copy)
```

## 六 代码/配置示例

### 6.1 教学示例：CloudTrail 实时告警 Lambda

```python
import json
import boto3

s3 = boto3.client("s3")
sns = boto3.client("sns")

SUSPICIOUS_EVENTS = {
    "DeleteTrail", "StopLogging", "UpdateTrail",
    "DeleteFlowLogs", "DeleteVpcFlowLogs",
    "DeleteSecurityGroup", "AuthorizeSecurityGroupIngress",
    "CreateAccessKey", "DeleteRolePolicy", "AttachRolePolicy",
    "PutBucketAcl", "DeleteBucketPolicy",
    "DisableKey", "ScheduleKeyDeletion",
}

def lambda_handler(event, context):
    for record in event["Records"]:
        bucket = record["s3"]["bucket"]["name"]
        key = record["s3"]["object"]["key"]
        
        obj = s3.get_object(Bucket=bucket, Key=key)
        logs = json.loads(gzip_decompress(obj["read"]()))
        
        for evt in logs.get("Records", []):
            if evt["eventName"] in SUSPICIOUS_EVENTS:
                alert = {
                    "event_time": evt["eventTime"],
                    "event_name": evt["eventName"],
                    "user": evt["userIdentity"]["arn"],
                    "source_ip": evt["sourceIPAddress"],
                    "region": evt["awsRegion"],
                }
                sns.publish(
                    TopicArn="arn:aws:sns:us-east-1:123:security-alerts",
                    Subject=f"Suspicious: {evt['eventName']}",
                    Message=json.dumps(alert, indent=2),
                )
```

### 6.2 生产级 Terraform：Organization CloudTrail + WORM + SIEM

```hcl

      "kms:GenerateDataKey",
      "kms:Decrypt",
```

### 6.6 容器取证：内存 dump + 镜像保留

```bash
#!/bin/bash
# forensics-pod.sh
# 在 Pod 销毁前采集证据

POD_NAME=$1
NAMESPACE=$2
NODE=$(kubectl get pod $POD_NAME -n $NAMESPACE -o jsonpath='{.spec.nodeName}')
CONTAINER_ID=$(kubectl get pod $POD_NAME -n $NAMESPACE -o jsonpath='{.status.containerStatuses[0].containerID}' | sed 's/containerd:\/\///')

# 1. 节点上 exec 进容器，dump 内存
ssh $NODE "crictl exec $CONTAINER_ID gcore -o /tmp/core \$(pgrep -f 'app')" || true
ssh $NODE "crictl cp $CONTAINER_ID:/tmp/core /tmp/core.$POD_NAME" || true

# 2. 复制文件系统
ssh $NODE "crictl export $CONTAINER_ID /tmp/fs.$POD_NAME.tar"
scp $NODE:/tmp/fs.$POD_NAME.tar /forensics/

# 3. Snapshot 节点 EBS
INSTANCE_ID=$(kubectl get node $NODE -o jsonpath='{.spec.providerID}' | cut -d/ -f5)
VOLUME_ID=$(aws ec2 describe-instances --instance-ids $INSTANCE_ID --query 'Reservations[0].Instances[0].BlockDeviceMappings[0].Ebs.VolumeId' --output text)
SNAPSHOT_ID=$(aws ec2 create-snapshot --volume-id $VOLUME_ID --description "forensics-$NODE-$(date +%s)" --query 'SnapshotId' --output text)

# 4. K8s 审计日志
kubectl get events -n $NAMESPACE --field-selector involvedObject.name=$POD_NAME > /forensics/events.$POD_NAME.txt
cat /var/log/kubernetes/audit/audit.log | jq "select(.user.username | contains(\"$NAMESPACE\"))" > /forensics/audit.$POD_NAME.json

# 5. 网络抓包（如 Pod 还在）
kubectl exec $POD_NAME -n $NAMESPACE -- tcpdump -i any -w /tmp/cap.pcap 30 &
sleep 30
kubectl cp $POD_NAME:/tmp/cap.pcap /forensics/cap.$POD_NAME.pcap -n $NAMESPACE

echo "Forensics bundle: /forensics/$POD_NAME"
echo "Snapshot: $SNAPSHOT_ID"
```

### 6.7 日志脱敏

```python
import re
import logging

# 脱敏规则
REDACT_PATTERNS = [
    (r'\b[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Z|a-z]{2,}\b', '[EMAIL]'),
    (r'\b\d{3}-\d{2}-\d{4}\b', '[SSN]'),
    (r'\b\d{16,19}\b', '[CARD]'),  # 信用卡
    (r'\b(?:\d{3}[-.\s]??){2}\d{4}\b', '[PHONE]'),
    (r'password["\']?\s*[:=]\s*["\']?([^"\']+)', 'password=[REDACTED]'),
    (r'Bearer\s+[\w\-\.]+', 'Bearer [REDACTED]'),
    (r'AKIA[0-9A-Z]{16}', '[AWS_KEY_ID]'),
    (r'-----BEGIN (RSA |EC )?PRIVATE KEY-----[\s\S]+?-----END (RSA |EC )?PRIVATE KEY-----', '[PRIVATE_KEY]'),
]

def redact(message: str) -> str:
    for pattern, replacement in REDACT_PATTERNS:
        message = re.sub(pattern, replacement, message, flags=re.IGNORECASE)
    return message

class RedactingFormatter(logging.Formatter):
    def format(self, record):
        original = super().format(record)
        return redact(original)

# 配置 logger
handler = logging.StreamHandler()
handler.setFormatter(RedactingFormatter('%(asctime)s %(levelname)s %(message)s'))
logger = logging.getLogger()
logger.addHandler(handler)
logger.setLevel(logging.INFO)
```

## 七 常见陷阱与最佳实践

### 7.1 陷阱表 ⚠️

| 陷阱 | 描述 | 后果 | 规避 |
|------|------|------|------|
| CloudTrail 写普通桶 | 桶无 WORM | 攻击者删日志不留痕 | Object Lock COMPLIANCE |
| 未开数据事件 | S3 GetObject 不记 | 数据外泄无法追溯 | 显式开 S3/Lambda/DynamoDB 数据事件 |
| 多账号独立 Trail | 每账号独立 | 难关联、易遗漏 | Organization Trail 集中到安全账号 |
| 日志含 PII | 应用日志直接打 password | 合规违规 + 数据泄露 | 脱敏中间件 + 结构化日志 |
| 日志保留过短 | 90 天后删 | SOX 要求 7 年 | WORM 365 天 + Glacier 长期归档 |
| Lambda 同步调 SIEM | SIEM 慢导致 Lambda 超时 | 日志丢失 | 异步 Kinesis 流式 |
| 不开 KMS 加密 | 日志明文 | 内部人员可读敏感 | KMS 加密 + 限制 KMS 解密权限 |
| UEBA 误报不调 | 直接用供应商默认 | 告警疲劳 | 业务团队参与基线调整 |
| 不收 K8s 审计日志 | kubectl 操作无记录 | 横向移动不可见 | 开启 K8s Audit Policy |
| 不收 DNS 日志 | 数据外泄走 DNS | C2 通道不可见 | Route53 Resolver Query Logs |
| 容器销毁前未取证 | Pod 消失 | 内存证据丢失 | 异常 Pod 立即冻结 + snapshot |
| Legal Hold 永久挂 | 调查结束未解除 | 桶膨胀 | 调查 SOP 含解除步骤 |

### 7.2 最佳实践

1. **Organization Trail 集中化**：所有账号审计日志写到安全账号 WORM 桶。
2. **数据事件全开**：S3/Lambda/DynamoDB 数据事件默认开启，权衡成本。
3. **WORM COMPLIANCE 365 天**：合规要求最低保留期，COMPLIANCE 模式不可绕过。
4. **KMS 加密 + Key Policy 限定**：仅 CloudTrail 服务可加密，仅安全账号可解密。
5. **OpenTelemetry 统一格式**：避免厂商锁定，Logs/Metrics/Traces 统一。
6. **Sigma 规则通用化**：跨 SIEM 平台复用检测逻辑。
7. **MITRE ATT&CK 映射**：每条检测规则标注 T 编号，便于覆盖率分析。
8. **取证链记录**：证据 hash、收集时间、收集人、存储位置全记录。
9. **日志脱敏前置**：应用层 + 网关层双重脱敏，PII/PHI/PCI 不入库。
10. **告警分级 SLA**：Critical（15 分钟响应）、High（1 小时）、Medium（24 小时）。

## 九 面试速答 ⭐

**Q1：CloudTrail 管理事件和数据事件区别？**
管理事件是控制面操作（CreateBucket、AttachRolePolicy）默认开启；数据事件是数据面操作（S3 GetObject、Lambda Invoke）默认不开，需显式开启，成本按事件数计费。

**Q2：怎么保证 CloudTrail 日志不可篡改？**
1) 写到 S3 + Object Lock COMPLIANCE 模式（到期前任何人都不能删，包括 root）；2) KMS 加密 + Key Policy 限制仅 CloudTrail 加密、安全账号解密；3) 跨账号写（安全账号桶），即使被攻击账号管理员也不能删。

**Q3：STS 调用链怎么追溯？**
CloudTrail 事件 userIdentity.sessionContext.sessionIssuer 指向上一层 assume 的 role；递归查询 AssumeRole 事件直到 Root/User。配 sourceIdentity 字段更直接。

**Q4：OpenTelemetry 三支柱是什么？**
Logs（事件流）、Metrics（数值时序）、Traces（调用链）。OTel 提供统一标准，避免厂商锁定，应用代码一次埋点，导出到任意后端（Jaeger、Prometheus、Loki）。

**Q5：容器取证流程？**
1) 立即冻结 Pod（terminationGracePeriodSeconds 拉长）；2) exec 进容器 gcore dump 内存；3) crictl export 文件系统；4) snapshot 节点 EBS；5) 收集 K8s 审计日志；6) tcpdump 网络抓包。

**Q6：CloudTrail 不开数据事件有什么风险？**
S3 GetObject 不记录，攻击者下载数据后无法从日志看出。Capital One 事件中，攻击者用 SSRF 拿到 IAM 凭证后读了 S3 数据，因为没开数据事件，最初不清楚外泄范围。

**Q7：日志脱敏怎么做？**
1) 应用层用 RedactingFormatter 拦截 password、token、PII；2) 网关层（API Gateway）响应日志脱敏；3) SIEM 摄入前再次脱敏（双重保险）；4) 关键字段（信用卡号）用 tokenization 替代。

**Q8：Legal Hold 和 Retention 区别？**
Retention 是有到期时间的 WORM（COMPLIANCE 模式到期前不可删）；Legal Hold 是无到期时间的锁定，独立于 Retention。调查期间用 Legal Hold 防止证据被删。

**Q9：UEBA 怎么避免误报？**
1) 基线学习期至少 30 天；2) 业务团队参与基线调整（已知运维操作）；3) 多维度评分（IP+时间+API+地理）而非单一维度；4) Critical 阈值高，Medium 阈值低；5) 反馈机制，误报标记后调整基线。

**Q10：跨账号 CloudTrail 怎么集中？**
1) 在安全账号建桶（WORM + KMS）；2) 桶 Policy 允许其他账号写入（s3:PutObject，条件 aws:PrincipalAccount）；3) 在 Organization 级别创建 Organization Trail，所有成员账号事件自动写入安全账号桶。

## 十 综合面试题

1. **设计题**：跨国公司有 50 个 AWS 账号、3 个 Azure 订阅、2 个 GCP 项目，如何设计统一审计？
   要点：1) 每云各自 Organization Trail / Activity Log / Audit Logs；2) 集中到 Splunk 或 Sentinel；3) Sigma 规则统一检测；4) 跨账号权限用 STS + ExternalId；5) 日志保留 7 年（SOX）+ WORM；6) 跨境日志符合数据主权。

2. **场景题**：发现某 IAM Role 的 AccessKey 在凌晨 3 点从俄罗斯 IP 调用 S3 GetObject，怎么调查？
   要点：1) 立即 disable 该 AccessKey；2) CloudTrail 查该 key 24h 内所有调用；3) 追溯 STS 链找原始泄漏源；4) 检查是否创建新用户/Role（后门）；5) 检查 S3 数据范围（哪些对象被读）；6) 评估是否报告监管（GDPR 72h 通知）。

3. **原理题**：S3 Object Lock COMPLIANCE 和 GOVERNANCE 区别？
   要点：COMPLIANCE 模式到期前 root 也不能删，强合规场景（金融、医疗）；GOVERNANCE 模式有 `s3:BypassGovernanceRetention` 权限可绕过，用于内部治理（误删保护）。COMPLIANCE 是"硬"锁，GOVERNANCE 是"软"锁。

4. **设计题**：容器化集群中，如何确保 Pod 销毁后仍能取证？
   要点：1) Falco 实时检测异常，触发 webhook 冻结 Pod；2) terminationGracePeriodSeconds 拉长（1 小时）；3) 自动化取证脚本：内存 dump、文件系统 export、EBS snapshot；4) K8s 审计日志全收；5) 网络抓包留 30 天 PCAP；6) 取证 bundle 加密存到 WORM 桶。

5. **场景题**：审计日志保留 1 年，但合规要求 7 年，怎么办？
   要点：1) S3 Lifecycle：90 天后转 Glacier Deep Archive（成本 ¥0.004/GB/月）；2) 365 天后转 Glacier Vault Lock（合规保留 7 年）；3) Athena 查询需先 restore（5-12 小时）；4) 关键事件热存储 1 年，全部冷归档 7 年。

6. **对比题**：Splunk 和 Sentinel 怎么选？
   要点：1) Splunk：自建或云，SPL 强大，生态丰富，按摄入量贵；2) Sentinel：SaaS，KQL，与 Azure 深度集成，按摄入量或容量；3) 多云/混合云 + 已有 Splunk 生态 → Splunk；4) Azure 为主 + 微软生态 → Sentinel；5) 成本敏感 + 中小规模 → Elastic Security 或 Wazuh。

7. **原理题**：MITRE ATT&CK 在审计中怎么用？
   要点：1) 每条检测规则映射 ATT&CK T 编号（如 T1078 Valid Accounts）；2) 评估检测覆盖率（哪些 T 没有规则）；3) 模拟攻击测试规则有效性（Atomic Red Team）；4) 报告给管理层用 ATT&CK 矩阵热图。

8. **场景题**：Lambda 函数日志含完整请求体（含 PII），怎么改？
   要点：1) 应用层结构化日志（JSON），PII 字段单独标 redact=true；2) RedactingFormatter 拦截 password、token、email、phone；3) API Gateway 响应日志脱敏；4) CloudWatch Logs 不存原始请求体；5) 单独把 PII 写到加密表（KMS）+ 审计表（hash 引用）。

9. **设计题**：OpenTelemetry 在 K8s 集群怎么部署？
   要点：1) DaemonSet 部署 OTel Collector（接收节点日志/指标）；2) Deployment 部署 OTel Collector（接收应用 traces）；3) 自动注入 sidecar 或 SDK 自动埋点；4) Exporter：Traces→Jaeger/Tempo，Metrics→Prometheus，Logs→Loki；5) 资源限制避免 Collector 吃资源；6) Sampling 降低成本（头部 10% + 尾部必采错误）。

10. **原理题**：取证链（Chain of Custody）怎么保证？
    要点：1) 收集时记录：时间、收集人、源（IP/实例）、hash（SHA-256）；2) 传输加密（TLS）；3) 存储到 WORM 桶 + Legal Hold；4) 每次访问记录；5) 法庭可用性：可证明证据从收集到呈堂未被篡改。

### 事故案例 🏭
- **Capital One（2019）**: 攻击者删除 CloudTrail？没删，但 CloudTrail 帮助事后追溯 9 次 KMS Decrypt 调用。启示：审计日志是事后取证核心。
- **SolarWinds（2020）**: 攻击者通过 SUNSPUR 后门操控，CloudTrail 在客户账号记录了异常 API 调用，但客户未告警。启示：检测规则覆盖率重要。
- **Uber（2022）**: 攻击者拿到 admin 后访问了内部工具，Uber 之前隐瞒 2016 年泄露被罚款。启示：审计日志被访问也要审计。
- **Codecov（2021）**: 2 个月未发现，部分原因是日志未被监控。启示：第三方 CI 日志也要监控。
- **LastPass（2022）**: 攻击者拿到 DevOps 工程师凭证后访问云存储，LastPass 4 个月才完整披露。启示：审计日志要主动分析而非被动查询。
