## 一、问题定义

### 1.1 解决什么问题

云上几乎所有事故都涉及 IAM 失效：

- 🔥 **Capital One 2019**：SSRF + 过宽 IAM 角色 → 1 亿用户泄露
- 🔥 **Tesla K8s 2018**：未授权 Dashboard → 挖矿
- 🔥 **Codecov 2021**：CI 凭证泄露 → 上游供应链
- 🔥 **SolarWinds 2020**：SAML Token 伪造 (Golden SAML)

IAM 解决三个核心问题：

1. **认证 (Authentication)** — 你是谁
2. **授权 (Authorization)** — 你能做什么
3. **审计 (Auditing)** — 你做了什么

### 1.2 与传统 AD/IAM 的差异

| 维度 | 传统 AD | 云 IAM |
|------|---------|--------|
| 边界 | 网络边界内可信 | 任何身份都需显式授权 |
| 凭证 | 密码为主 | 短期令牌 (STS) 为主 |
| 角色模型 | 域控集中式 | 多账号 + 联邦 |
| 服务身份 | 服务账号 (长期) | 工作负载身份 (短期) |
| 权限模型 | 域组 + GPO | RBAC + ABAC + 策略 |
| 跨域信任 | 林信任 | 联邦身份 + SAML/OIDC |

⚠️ **关键变化**：传统 IAM 是"内部可信"，云 IAM 是"零信任"——每次请求都验证身份和权限。

### 1.3 云厂商差异概述

| 概念 | AWS | Azure | GCP | 阿里云 | 华为云 |
|------|-----|-------|-----|--------|--------|
| 用户/角色 | IAM User/Role | Entra ID User/SP | IAM User/Service Account | RAM User/Role | IAM User/Agency |
| 临时凭证 | STS | Managed Identity | Workload Identity | STS | Agency Token |
| K8s 集成 | IRSA | AAD Pod Identity | Workload Identity | RAM for ACK | CCE Agency |
| 跨账号 | Role Assumption | AAD B2B | Workload Identity Federation | RAM Cross-Account | Agency |
| PAM 工具 | SSM Session Manager | JIT (Defender) | IAP |堡垒机| 堡垒机 |
| 权限分析 | IAM Access Analyzer | Entra PIM | IAM Recommender | RAM 配置审计 | IAM 权限分析 |

## 三、原理与机制

### 3.1 直觉：身份 = (主体, 凭证, 上下文)

每次 API 请求都携带：
1. **Who** — 主体身份（用户/角色/服务）
2. **Proof** — 凭证（密码/Token/签名）
3. **Context** — 上下文（IP/时间/设备/请求资源）

授权引擎在评估时考虑三者：
```
Allow(principal, action, resource, condition)
  ⟺ 主体匹配 ∧ 资源匹配 ∧ 动作匹配 ∧ 条件满足
```

### 3.2 形式化定义

📜 **ACL 经典模型 (Lampson, 1971)**：
$$
Auth(s, o, a) \iff (s, a) \in ACL(o)
$$
其中 $s$ = subject, $o$ = object, $a$ = action。

📜 **RBAC 标准 (NIST SP 800-162)**：
$$
U \xrightarrow{assign} R \xrightarrow{permission} P(Sess(u) = r \land (r, a, o) \in PA) \Rightarrow Auth(u, o, a)
$$

📜 **ABAC 标准 (NIST SP 800-162)**：
$$
Auth(s, o, a) \iff f(s.attr, o.attr, env.attr, action.attr) = True
$$

### 3.3 关键性质

1. **RBAC 易管理但粒度粗** — 适合稳定组织
2. **ABAC 灵活但策略复杂** — 适合动态环境
3. **PBAC = RBAC + ABAC + 工作流** — 现代云 IAM 实际是 PBAC
4. **Deny 优先于 Allow** — 显式 Deny 总是赢
5. **最小权限是过程不是状态** — 需要持续审计和收敛

### 3.4 STS 临时凭证机制

```
   客户端                STS              IAM
     │                   │                │
     │ 1. AssumeRole     │                │
     ├──────────────────►│                │
     │  (with creds)     │                │
     │                   │ 2. 评估策略     │
     │                   ├───────────────►│
     │                   │ 3. 返回 Role    │
     │                   │◄───────────────┤
     │ 4. 颁发临时凭证    │                │
     │  (access_key +    │                │
     │   secret + token) │                │
     │  + expiration     │                │
     │◄──────────────────┤                │
     │                   │                │
     │ 5. 用临时凭证调用 S3 等             │
     ├────────────────────────────────────►
```

🔥 **临时凭证的安全优势**：
- 短期 (15min - 12h)，泄露风险窗口小
- 无需分发长期密钥
- 自动轮换
- 可附加会话策略 (session policy) 进一步收紧

## 四、算法 / 流程

### 4.1 AWS IAM 策略评估算法

```
输入: Principal P, Action A, Resource R, Conditions C, 策略集 S
输出: Allow / Deny / Implicit Deny

1. S = 所有附加到 P 的策略 (identity-based + resource-based + session)
2. 收集所有匹配 (A, R) 的语句:
   for each statement s in S:
     if A ∈ s.Action AND R ∈ s.Resource:
        if s.Condition(C) == True:
           matched.add(s)

3. 决策:
   if any s in matched with Effect=Deny:
       return Deny                    # 显式 Deny 总是赢
   if any s in matched with Effect=Allow:
       return Allow
   return Implicit Deny               # 默认拒绝
```

复杂度 $O(n)$，$n$ = 策略语句数。

### 4.2 Permission Boundary + SCP 累积

```
最终决策 = Allow ∧ Boundary ∧ SCP ∧ Session Policy

其中:
- Allow: identity-based policy 显式允许
- Boundary: permissions boundary 允许 (上限)
- SCP: 组织策略允许 (上限的上限)
- Session Policy: STS 会话策略 (进一步收紧)

任一为 Deny → 最终 Deny
```

# tools/iam_least_privilege_analyzer.py
"""分析 CloudTrail 历史,推荐最小权限策略"""
import boto3
import json
from collections import defaultdict
from datetime import datetime, timedelta

cloudtrail = boto3.client('cloudtrail')
iam = boto3.client('iam')

def analyze_role_usage(role_name: str, days: int = 90) -> dict:
    """从 CloudTrail 历史推断 Role 实际使用的权限"""
    end = datetime.utcnow()
    start = end - timedelta(days=days)
    
    # 该 Role 的所有 AssumeRole + 后续 API 调用
    events = cloudtrail.lookup_events(
        LookupAttributes=[{
            'AttributeKey': 'RoleName',
            'AttributeValue': role_name
        }],
        StartTime=start,
        EndTime=end,
        MaxResults=10000
    )
    
    used_actions = defaultdict(int)
    used_resources = defaultdict(set)
    
    for ev in events.get('Events', []):
        ct = json.loads(ev.get('CloudTrailEvent', '{}'))
        if ct.get('eventName') == 'AssumeRole':
            continue  # 跳过 AssumeRole 本身
        
        action = f"{ct.get('eventSource','').replace('.amazonaws.com','')}:{ct.get('eventName')}"
        used_actions[action] += 1
        
        for resource in ct.get('resources', []):
            used_resources[action].add(resource.get('ARN', 'unknown'))
    
    # 生成推荐策略
    recommended = {
        "Version": "2012-10-17",
        "Statement": [{
            "Effect": "Allow",
            "Action": sorted(used_actions.keys()),
            "Resource": sorted({r for res_set in used_resources.values() for r in res_set})
        }]
    }
    
    return {
        "role": role_name,
        "analysis_period_days": days,
        "total_events": sum(used_actions.values()),
        "unique_actions": len(used_actions),
        "recommended_policy": recommended
    }

## 七、常见陷阱与最佳实践 ⚠️

| 陷阱 | 后果 | 对策 |
|------|------|------|
| 用 IAM User 长期 key | 凭证泄露后无法快速轮换 | 🔥 用 IAM Role + STS 短期凭证 |
| 角色 SessionDuration 过长 | 凭证泄露窗口大 | 设 1 小时上限，关键操作 15 分钟 |
| `*:*` 全权限 | 权限蔓延 + 难审计 | 用 IAM Access Analyzer 持续收敛 |
| Resource: "*" | 跨账号越权 | 显式列出资源 ARN |
| 不用 Permission Boundary | 开发者越权创建资源 | 强制 Boundary |
| 共享账号 + 多团队 | 权限混乱 + 审计断链 | 多账号 + Organizations SCP |
| 跨账号信任无 ExternalId | Confused Deputy 攻击 | 🔥 必加 ExternalId |
| EC2 实例传凭证 | 凭证泄露 | 用 Instance Profile + IRSA |
| Lambda 不用 Role | 把 key 写代码 | 用 Execution Role |
| MFA 仅控制台开启 | API 调用绕过 MFA | 强制 MFA + Condition |
| Root 账号有 access key | 全账号沦陷 | 🔥 Root 不应有 key，仅紧急用 |

### 7.1 工程重点 (🔥)

1. **角色优先** — 用户/服务都用 Role，不用 User 长期 key
2. **STS 优先** — 临时凭证 > 长期凭证
3. **Permission Boundary** — 给开发者权限套上限
4. **MFA 强制** — 控制台 + 破坏性 API 都需 MFA
5. **Cross-Account ExternalId** — 跨账号信任必加
6. **CIEM 持续分析** — IAM Access Analyzer 自动发现越权
7. **Break-Glass 审计** — 紧急角色用一次就告警

## 十、综合面试题

1. **请设计一个生产级 IAM 治理架构（多账号 + 跨账号审计）。**
   - 要点：Organizations + SCP；Security 账号 + Audit Role + ExternalId；IAM Identity Center SSO；Permission Boundary；Break-Glass + 告警；CIEM 持续审计。

2. **Capital One 事故中的 IAM 失误是什么？如何避免？**
   - 要点：EC2 Role 权限过宽（s3:GetObject *）；SSRF 让元数据服务被访问；应该限定 Resource ARN；用 IRSA 替代实例 Profile；CSPM 检测过宽角色。

3. **如何治理权限蔓延 (privilege creep)？**
   - 要点：CIEM 工具持续分析；IAM Access Analyzer；CloudTrail 历史推荐最小权限；定期重新认证 (re-certification)；JIT 替代长期授权。

4. **解释 Confused Deputy 问题及 ExternalId 解决方案。**
   - 要点：攻击者诱导第三方服务用自己的角色访问你的资源；ExternalId 是你给第三方的随机串；信任策略要求 ExternalId 匹配；攻击者无法伪造。

5. **AWS IAM Policy 评估算法的细节？**
   - 要点：收集所有匹配策略；显式 Deny 赢；无 Deny 时 Allow 赢；默认拒绝；叠加 SCP + Boundary + Session 累积收紧。

6. **K8s Pod 如何安全地获取云权限？**
   - 要点：IRSA (AWS) / Workload Identity (GCP) / AAD Pod Identity (Azure)；OIDC Token → STS AssumeRoleWithWebIdentity；不用 node 权限；按 SA 隔离。

7. **设计一个 JIT (Just-In-Time) 访问系统。**
   - 要点：用户申请 → 审批 → 自动 AssumeRole 短期凭证 → 审计 → 自动到期；用 Lambda + Step Functions 实现；用 IAM Identity Center 或 SSM Session Manager 集成。

8. **如何检测 IAM 凭证泄露？**
   - 要点：GuardDuty 凭证异常使用检测；CloudTrail 异常 IP / 异常 UserAgent；未授权地区调用；非常规时间调用；Access Key 旋转后旧 key 仍在用。

9. **多云场景下身份统一治理的挑战？**
   - 要点：策略语言不一致 (IAM vs RBAC vs IAM)；权限模型不一致；同一身份在不同云有不同权限；需要抽象层 (OPA / Terraform)；CIEM 跨云视图。

10. **零信任架构下 IAM 的角色？**
    - 要点：身份是新的边界；每次请求验证身份 + 设备 + 上下文；持续验证而非一次性；JIT + JEA；与设备姿态、网络上下文结合。
