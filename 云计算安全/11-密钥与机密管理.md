## 一 问题定义

### 1.1 业务痛点

云原生环境下密钥与机密管理面临三重困境：

1. **数量爆炸**：单个微服务集群可能涉及上百个 DB 口令、第三方 API Key、TLS 证书；多环境（dev/staging/prod）×多区域使数量再增 5-10 倍。
2. **轮转滞后**：静态机密平均年龄常 > 1 年，一旦泄露窗口期长。Capital One 2019 事件中，攻击者持有的 IAM 凭证在被发现前可用 4 个月。
3. **泄露面广**：代码库、CI 日志、容器镜像层、APM 堆栈、崩溃转储均可能携带机密。Codecov 2021 事件中，bash 上传器被植入后门 2 个月未发现，期间收集用户环境变量中的 token。

### 1.2 云厂商差异

| 维度 | AWS | Azure | GCP | 阿里云 | 华为云 |
|------|-----|-------|-----|--------|--------|
| KMS 服务 | KMS / CloudHSM | Key Vault / Managed HSM | Cloud KMS / Cloud HSM | KMS / 加密服务 HSM | KMS / DEW / CSMS |
| Secret 服务 | Secrets Manager / Parameter Store | Key Vault（机密同 KV） | Secret Manager | KMS Secrets Manager | CSMS 凭据管理 |
| 证书托管 | ACM（公有/Private CA） | App Service / Key Vault | Certificate Manager | SSL 证书服务 | SCM 证书管理 |
| BYOK | KMS Import Key Material | Key Vault Import | Cloud KMS Import | KMS Import | KMS Import |
| HYOK | CloudHSM / Outposts | Managed HSM | External Key Manager | 加密服务 HSM | 专属加密 DHSM |
| FIPS 等级 | CloudHSM L3 | Managed HSM L3 | Cloud HSM L3 | HSM L3 | DHSM L3 |

### 1.3 反模式

- ❌ 在代码仓库（含私有）硬编码 DB 口令、API Key。
- ❌ 把 KMS CMK Arn 写在代码里，但允许 `kms:Decrypt` 给所有 EC2 角色（实际等价于明文）。
- ❌ 用同一个 KMS Key 加密所有租户数据（缺乏租户隔离 DEK）。
- ❌ Secret Manager 轮转函数仅切换 DB 口令但未通知应用层重新建立连接池。
- ❌ 将 AK/SK 写入容器镜像环境变量，镜像被推到公开仓库。

## 三 原理与机制

### 3.1 密钥层级模型 🎓

**形式化定义**：

设密钥层级为三元组 $(K_r, K_{KEK}, K_{DEK})$：

- $K_r$：根密钥（Root Key），HSM 内生成，永不出 HSM。
- $K_{KEK}$：密钥加密密钥，由 $K_r$ 加密存储：$C_{KEK} = \text{Enc}(K_r, K_{KEK})$。
- $K_{DEK}$：数据加密密钥，由 $K_{KEK}$ 加密存储：$C_{DEK} = \text{Enc}(K_{KEK}, K_{DEK})$。
- 业务数据 $M$ 的密文：$C = \text{Enc}(K_{DEK}, M)$。

**解密链**：$K_r \xrightarrow{\text{HSM}} K_{KEK} \xrightarrow{\text{KMS}} K_{DEK} \xrightarrow{\text{App}} M$。

**安全属性**：
1. 应用永不接触 $K_r$ 与 $K_{KEK}$，仅持有 $K_{DEK}$（短时缓存）。
2. 撤销 $K_{KEK}$ 等价于撤销所有 $K_{DEK}$（加密粉碎）。
3. 轮转 $K_{DEK}$ 不影响 $K_{KEK}$；轮转 $K_{KEK}$ 需重加密所有 $C_{DEK}$。

### 3.2 信封加密 vs 直接加密 🎓

| 维度 | 直接加密（KMS Encrypt） | 信封加密 |
|------|------------------------|----------|
| 调用次数 | 每次加解密 1 次 KMS | 生成 DEK 1 次，后续无 KMS 调用 |
| 性能 | 受 KMS QPS 限制（默认 5500-10000/s） | 仅受本地 AES 限制（GB/s） |
| 数据传输 | 明文经过 KMS API | 明文不出客户端 |
| 适用场景 | 小数据（< 4KB） | 大数据、对象存储、DB 字段 |

**信封加密形式化**：

$$
\text{Encrypt}(M, K_{KEK}): 
\begin{cases}
K_{DEK} \leftarrow \text{KeyGen}() \\
C_1 = \text{Enc}(K_{KEK}, K_{DEK}) \\
C_2 = \text{Enc}(K_{DEK}, M) \\
\text{return } (C_1, C_2)
\end{cases}
$$

$$
\text{Decrypt}(C_1, C_2, K_{KEK}):
\begin{cases}
K_{DEK} = \text{KMS.Decrypt}(C_1) \\
M = \text{Dec}(K_{DEK}, C_2) \\
\text{return } M
\end{cases}
$$

### 3.3 KMS 调用鉴权 🎓

KMS 调用鉴权涉及双层授权：

1. **IAM 授权**：调用者身份是否被允许 `kms:Decrypt`。
2. **密钥策略（Key Policy）授权**：该 CMK 是否允许该身份调用。

**形式化**：

$$
\text{Allow}(P, K, A) = \text{IAM}_{\text{Allow}}(P, A) \wedge \text{KeyPolicy}_{\text{Allow}}(P, K, A) \wedge \neg \text{Deny}(P, K, A)
$$

其中 $P$ 为 Principal（调用者），$K$ 为 CMK，$A$ 为 Action（如 `kms:Decrypt`）。

**条件键（Condition Keys）**：
- `kms:ViaService`：限制只能由 S3、RDS 等服务调用。
- `kms:EncryptionContext:context_key`：限制加密上下文（如 `project=alpha`）。
- `kms:CallerAccount`：限制跨账号调用。

### 3.4 动态机密机制 🎓

**Vault Database Engine 工作流**：

```
1. 应用启动 → Vault Agent 请求 Database Secret
2. Vault 调用 DB 创建临时账号（GRANT SELECT ON ...）
3. Vault 返回 (username, password, lease_duration=1h)
4. 应用使用凭证建立连接池
5. lease 到期前 Vault Agent 自动 renew
6. 应用销毁时 Vault revoke → DB DROP USER
```

**对比静态机密**：

| 维度 | 静态机密 | 动态机密 |
|------|----------|----------|
| 凭证年龄 | 数月-数年 | 数分钟-数小时 |
| 撤销成本 | 改密+重启应用 | 自动到期 |
| 审计粒度 | 谁用了哪个静态凭证 | 每次签发独立凭证 |
| DB 负载 | 共用账号 | 每实例独立账号 |

### 3.5 BYOK / HYOK 区别 🎓

**BYOK（Bring Your Own Key）**：

```
本地 HSM 生成 K_material
        ↓
导入云端 KMS（CMK Origin = EXTERNAL）
        ↓
KMS 用 K_material 作为 KEK
        ↓
应用调用 KMS API 加解密
```

特点：密钥材料可在本地备份，云端删除 CMK 后无法解密；但密钥材料已离开本地 HSM。

**HYOK（Hold Your Own Key）**：

```
本地 HSM 持有 K_material
        ↓
云端 EKM（External Key Manager）配置外部 HSM 端点
        ↓
应用调用云端 KMS API → KMS 转发到 EKM → EKM 调用本地 HSM
        ↓
本地 HSM 内完成加解密，密钥永不离开 HSM
```

特点：密钥材料永不离开本地 HSM，但每次加解密增加网络延迟（10-50ms）。

## 四 算法/流程

### 4.1 KMS 加密流程（伪代码）

```
function KMS_ENCRYPT(M, CMK_ARN, ENCRYPTION_CONTEXT):
    # M 长度限制 4KB（AWS KMS / GCP KMS）
    if len(M) > 4096:
        raise Error("Use envelope encryption for large data")
    
    response = KMS_API.Encrypt(
        KeyId = CMK_ARN,
        Plaintext = M,
        EncryptionContext = ENCRYPTION_CONTEXT
    )
    return response.CiphertextBlob
    # 复杂度：O(1) 网络往返 + O(len(M)) 加密
```

### 4.2 信封加密流程

```
function ENVELOPE_ENCRYPT(M, CMK_ARN):
    # 1. 生成 DEK（明文+密文）
    dek_resp = KMS_API.GenerateDataKey(
        KeyId = CMK_ARN,
        KeySpec = "AES_256"
    )
    DEK_plain = dek_resp.Plaintext   # 32 bytes
    DEK_cipher = dek_resp.CiphertextBlob
    
    # 2. 本地用 DEK 加密业务数据
    IV = random(12)  # GCM nonce
    C, tag = AES_GCM_ENCRYPT(DEK_plain, IV, M, AAD)
    
    # 3. 立即清空明文 DEK
    secure_zero(DEK_plain)
    
    return (DEK_cipher, IV, C, tag)
    # 复杂度：O(1) KMS 调用 + O(len(M)) 本地加密
```

### 4.4 Vault Transit 加密即服务

```
# 1. 创建密钥
vault write transit/keys/order-key type=aes256-gcm96 exportable=false

# 2. 加密
plaintext = base64(b"order_id=12345")
cipher = vault write transit/encrypt/order-key plaintext=$plaintext
# → vault:v1:8SDd3WHDOYzVh... 

# 3. 解密
plaintext = vault write transit/decrypt/order-key ciphertext=$cipher

# 4. 轮转（版本化）
vault write transit/keys/order-key/rotate min_decryption_version=1
# 旧密文仍可解密，新加密用 v2

# 5. 收紧解密版本（销毁旧版本密钥材料）
vault write transit/keys/order-key min_decryption_version=2
# v1 密文不可解密
```

### 4.5 密钥轮转算法（KMS 自动轮转）

```
function KMS_ROTATE(CMK_ARN):
    # AWS KMS：每年自动生成新密钥材料，CMK ARN 不变
    # 旧密文用旧密钥材料解密（key spec 保留 backing keys 历史）
    
    BACKING_KEYS = [K_v1, K_v2, ..., K_vN]  # 按 ID 索引
    
    function ENCRYPT(M):
        K_current = BACKING_KEYS[-1]
        return Enc(K_current, M) + version_tag(N)
    
    function DECRYPT(C, version_tag):
        K = BACKING_KEYS[version_tag]
        return Dec(K, C)
    
    # 注意：删除 CMK 会删除所有 backing keys，密文不可恢复
```

## 六 代码/配置示例

### 6.1 教学示例：Python 信封加密

```python
import os
import boto3
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

class EnvelopeEncryption:
    """教学版信封加密，省略错误处理与重试"""

    def __init__(self, cmk_arn: str):
        self.kms = boto3.client("kms")
        self.cmk_arn = cmk_arn

    def encrypt(self, plaintext: bytes, context: dict) -> dict:
        # 1. 生成 DEK
        resp = self.kms.generate_data_key(
            KeyId=self.cmk_arn,
            KeySpec="AES_256",
            EncryptionContext=context,
        )
        dek_plain = resp["Plaintext"]
        dek_cipher = resp["CiphertextBlob"]

        # 2. 本地加密
        iv = os.urandom(12)
        aesgcm = AESGCM(dek_plain)
        ciphertext = aesgcm.encrypt(iv, plaintext, None)

        # 3. 立即清空明文 DEK
        del dek_plain
        del aesgcm

        return {
            "dek_cipher": dek_cipher,
            "iv": iv,
            "ciphertext": ciphertext,
            "context": context,
        }

    def decrypt(self, blob: dict) -> bytes:
        # 1. 解密 DEK
        resp = self.kms.decrypt(
            CiphertextBlob=blob["dek_cipher"],
            EncryptionContext=blob["context"],
        )
        dek_plain = resp["Plaintext"]

        # 2. 本地解密
        aesgcm = AESGCM(dek_plain)
        plaintext = aesgcm.decrypt(blob["iv"], blob["ciphertext"], None)
        del dek_plain
        del aesgcm
        return plaintext
```

### 6.6 密钥删除紧急预案（Crypto-shredding）

```python
import boto3

def crypto_shred(cmk_arn: str, reason: str):
    """紧急让所有用该 CMK 加密的数据不可恢复"""
    kms = boto3.client("kms")

    # 1. 立即禁用 CMK（停止 Decrypt 调用）
    kms.disable_key(KeyId=cmk_arn)

    # 2. 标记删除（最短 7 天等待期）
    kms.schedule_key_deletion(
        KeyId=cmk_arn,
        PendingWindowInDays=7,  # 等待期内仍可取消
    )

    # 3. CloudWatch 告警 + 通知
    cloudwatch = boto3.client("cloudwatch")
    cloudwatch.put_metric_data(
        Namespace="Security/KeyManagement",
        MetricData=[{
            "MetricName": "CryptoShredTriggered",
            "Dimensions": [{"Name": "CMK", "Value": cmk_arn}],
            "Value": 1,
            "Unit": "Count",
        }],
    )

    # 4. 触发事件告警
    sns = boto3.client("sns")
    sns.publish(
        TopicArn="arn:aws:sns:us-east-1:123456789012:security-alerts",
        Subject=f"CRYPTO-SHRED: {cmk_arn}",
        Message=f"Reason: {reason}\nKey disabled and scheduled for deletion in 7 days.",
    )
```

## 七 常见陷阱与最佳实践

### 7.1 陷阱表 ⚠️

| 陷阱 | 描述 | 后果 | 规避 |
|------|------|------|------|
| KMS Key Policy 过宽 | 给 `*` 主体 `kms:Decrypt` | 等价于明文 | 限定 Principal + EncryptionContext |
| 加密上下文缺失 | 不传 EncryptionContext | 撤销粒度粗，难定位 | 强制传 project/env/tenant |
| 单一 CMK 加密所有租户 | 跨租户共享 CMK | 一键粉碎影响所有租户 | 每租户独立 CMK 或 DEK + 上下文 |
| CMK 删除等待期 7 天 | 用最短等待期"快速删除" | 误删不可恢复 | 30 天等待期 + 多人审批 |
| 跨区域复制明文密文 | 跨区 DR 复制时把密文 + DEK 一起复制 | 等价明文 | 跨区复制仅密文，DEK 用 Multi-Region Key |
| Secrets Manager 与 DB 不同步 | 轮转 Lambda 失败但 AWSCURRENT 已切换 | 应用连不上 DB | 在 Lambda 中先 STAGING 测试再切换 |
| 应用缓存 Secret 永久 | 启动时拉一次，进程内永久缓存 | 轮转后旧凭证失效 | 缓存 TTL < 轮转周期；用 TTLCache |
| IAM Policy 写明 `kms:Decrypt` 但未限 Resource | `Resource: *` | 越权风险 | 限到具体 CMK ARN |
| 用 Parameter Store 存敏感数据 | 用 Standard（非 SecureString） | 明文可见 | SecureString + KMS CMK |
| 把 AK/SK 放镜像 ENV | 容器层可被 docker history 还原 | 镜像泄露=凭证泄露 | IRSA / Workload Identity |
| Git history 含密钥 | 已 push 的 commit 仍可被还原 | 长期暴露 | 立即 rotate + BFG 清历史 |
| Vault Root Token 不轮转 | 启动后未 revoke | Root Token 泄露=完全失守 | 初始化后立即 revoke，用 unseal key 备份 |

### 7.2 最佳实践

1. **密钥层级化**：永远用 KEK 加密 DEK，DEK 加密数据；不让 KMS 直接加密大数据。
2. **强制 EncryptionContext**：包含 project、env、tenant、purpose，便于审计与撤销。
3. **每租户独立 CMK 或独立 KEK**：避免一次删除影响所有租户。
4. **轮转自动化**：CMK 自动 1 年，Secret 自动 90 天；轮转失败有告警。
5. **缓存 TTL**：应用层缓存 Secret 不超过 5-15 分钟，CMK 解密的 DEK 不超过 1 小时。
6. **审计全开**：CloudTrail data event（KMS API 调用）、Secret Manager GetSecretValue 全部记日志。
7. **跨账号隔离**：用 Key Policy 显式允许跨账号，不依赖 IAM 信任。
8. **Crypto-shredding 演练**：定期模拟 CMK 禁用，验证业务降级与恢复。
9. **Secret 扫描三道防线**：pre-commit（开发者）、CI（卡点）、运行时（Falco 规则）。
10. **HYOK 用于强合规**：金融、医疗等数据主权场景用 EKM + 本地 HSM。

## 九 面试速答 ⭐

**Q1：KMS 和 Secret Manager 区别？**
KMS 管理加密密钥（KEK/CMK），提供 Encrypt/Decrypt API，密钥材料永不出口；Secret Manager 存储机密数据（DB 口令、API Key），通常用 KMS 加密。KMS 加密 ≤4KB 数据，Secret Manager 存储 ≤64KB。

**Q2：信封加密为什么重要？**
1) KMS QPS 限制（5500-10000/s），大数据场景瓶颈；2) 明文不出客户端，KMS 看不到业务数据；3) DEK 可在内存缓存，KMS 仅在生成/解密 DEK 时调用一次。

**Q3：BYOK 和 HYOK 区别？**
BYOK 把密钥材料导入云端 KMS，密钥材料已离开本地 HSM；HYOK 密钥永不离开本地 HSM，云端 KMS 通过 EKM 接口调用本地 HSM，每次加解密增加网络延迟。

**Q4：CMK 删除为什么要等待期？**
防止误删导致数据永久不可恢复。AWS 强制 7-30 天等待期，期间可取消删除。Crypto-shredding 利用此机制：禁用+标记删除立即让 Decrypt 失败，但保留恢复可能。

**Q5：动态机密 vs 静态机密？**
静态机密长期不变（数月-数年），泄露窗口长；动态机密（Vault Database Engine）按需签发短时凭证（1 小时 lease），到期自动 revoke，审计粒度细到每实例。

**Q6：Secret 轮转失败怎么排查？**
1) 检查 Lambda 日志（CloudWatch Logs）；2) 验证新凭证能否连接 DB（DB 用户权限、网络连通）；3) 检查 Secrets Manager 版本切换是否完成（AWSPENDING → AWSCURRENT）；4) 应用是否缓存了旧凭证（重启或缓存过期后恢复）。

**Q7：Codecov 事件对密钥管理的启示？**
Codecov bash 上传器被植入后门 2 个月，收集用户环境变量中的 CI token。启示：1) CI 环境变量不应该是长期 token，用 OIDC 替代；2) 监控 CI 出站流量异常；3) 第三方脚本要校验签名。

**Q8：跨账号 KMS 共享如何做？**
1) 在 Key Policy 中允许对方账号 Root；2) 对方账号 IAM Role 允许 `kms:Decrypt`；3) 用 `kms:EncryptionContext` 限制使用场景；4) CloudTrail 跨账号审计。

**Q9：Vault 和云 KMS 怎么选？**
多云/混合云、需要动态机密、需要强一致 → Vault；单云、静态机密、低运维 → 云 KMS。Vault 也可与云 KMS 串联：Vault 用 AWS KMS 作为 Seal。

**Q10：什么是加密粉碎（Crypto-shredding）？**
删除 KEK 即让所有用该 KEK 加密的 DEK 不可解密，进而所有密文不可恢复。用于紧急数据销毁（如租户退出、合规要求）。AWS 实现：禁用 CMK + 调度删除（7 天）。

## 十 综合面试题

1. **设计题**：跨国金融公司在 AWS、Azure、阿里云三地部署，需要统一密钥管理且满足"密钥不出境"。请设计方案。
   要点：1) 本地 HSM（如 Thales Luna）持有根密钥；2) 三地 KMS 通过 EKM 调用本地 HSM（HYOK 模式）；3) 应用层用 Vault Transit 统一 API；4) 网络延迟通过 DEK 缓存优化；5) 审计集中到 SIEM。

2. **场景题**：开发把 AWS AK/SK 提交到 GitHub 公开仓库，2 小时后被爬虫抓走。请描述响应流程。
   要点：1) 立即 disable 该 AK/SK；2) CloudTrail 查看该凭证 24h 内所有 API 调用；3) 检查是否创建新 IAM User/Role（后门）；4) 检查 EC2/S3 资源是否被滥用挖矿或外传；5) 删除凭证后 rotate 受影响 Secret；6) GitHub 历史用 BFG 清除；7) 推行 IRSA + OIDC 替代长期凭证。

3. **原理题**：为什么 KMS 不直接加密大数据？
   要点：1) KMS 是中心化服务，QPS 限制（5500-10000/s）成瓶颈；2) 大数据经过 KMS 网络往返慢；3) KMS 看到明文增加暴露面；4) 信封加密让 DEK 在客户端使用，KMS 仅生成/解密 DEK（4KB 一次）。

4. **设计题**：SaaS 多租户如何隔离密钥？
   要点：1) Tier-1：每租户独立 CMK（强隔离，CMK 数量上限）；2) Tier-2：共享 CMK + 每租户独立 DEK + EncryptionContext（tenant_id=xxx）；3) Tier-3：共享 CMK + 共享 DEK + 行级字段加密（适用低敏感）。Crypto-shredding 用 Tier-1/2 即可。

5. **场景题**：Vault 集群 3 节点 Raft，2 节点宕机，如何恢复？
   要点：1) Raft 需要 quorum（2/3），1 节点不能 unseal；2) 用 snapshot 恢复：在新节点 `vault operator raft snapshot restore`；3) 重新加入集群；4) 验证 audit log 完整性；5) 复盘：Raft 多副本跨 AZ 部署，定期 snapshot 备份到 S3（KMS 加密）。

6. **原理题**：CMK 轮转后旧密文还能解密吗？
   要点：能。AWS KMS 保留所有 backing keys（旧密钥材料），CMK ARN 不变，密文含 key version。解密时 KMS 自动用对应 backing key。删除 CMK 才会让旧密文不可恢复。

7. **对比题**：AWS KMS 和 CloudHSM 怎么选？
   要点：1) KMS：多租户共享 HSM，FIPS L2，便宜，QPS 高，BYOK 支持；2) CloudHSM：单租户专属 HSM，FIPS L3，PKCS#11 标准，合规要求高（金融、医疗）；3) KMS 用 CloudHSM 作为 backing key 实现更高合规（KMS Custom Key Store）。

8. **场景题**：Secret Manager 轮转 Lambda 失败导致 DB 口令不一致，应用连不上。
   要点：1) Lambda 在 STAGING 阶段先测试新凭证连接 DB；2) 切换 DB 口令用 `ALTER USER`，再切换 AWSCURRENT；3) 失败时 Lambda 应回滚（恢复旧口令）；4) 应用用缓存 + 重试机制容忍短时不一致；5) 监控 Lambda 失败率 > 0 立即告警。

9. **设计题**：微服务集群 200 个服务，每个服务有 DB 口令、第三方 API Key、TLS 证书，如何管理？
   要点：1) 集中化：Vault 或云 Secrets Manager；2) 工作负载身份：IRSA / SPIFFE 替代静态凭证；3) Secret CSI Driver 挂载到 Pod；4) 轮转：DB 动态机密，API Key 90 天轮转，证书 ACM 自动续期；5) 审计：每次 GetSecretValue 记日志；6) 扫描：CI 阶段 Gitleaks 防止硬编码。

10. **原理题**：什么是 KMS EncryptionContext？有什么用？
    要点：1) AAD（Additional Authenticated Data），加密时绑定上下文，解密时必须一致；2) 用途：粒度授权（IAM 限制 context）、审计（日志含 context）、撤销（删除某 context 的解密权限）；3) 注意：context 不加密，可被看到，不应放敏感数据。
