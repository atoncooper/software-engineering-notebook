# §5 - 工作负载安全

> 一句话定位：容器、K8s、Serverless 三种工作负载各有安全模型，但镜像可信 + 最小权限 + 运行时防护是共同主线。

## 一、问题定义

### 1.1 解决什么问题

云原生工作负载的核心安全挑战：

1. **镜像可信** — 镜像从哪来、有没有后门
2. **运行时权限** — 容器能做什么、能不能逃逸
3. **服务间通信** — Pod 互通是否受控
4. **配置面** — K8s RBAC/Pod Security/NetworkPolicy 是否收紧
5. **Serverless 特殊性** — 事件注入、函数权限、冷启动

🔥 **典型事故**：
- Tesla K8s 2018：未授权 Dashboard → 挖矿
- Capital One 2019：Lambda SSRF + 元数据
- Docker Hub 2019：账号被入侵，官方镜像被植入后门

### 1.2 与传统工作负载的差异

| 维度 | 传统 VM | 容器 | Serverless |
|------|---------|------|------------|
| 隔离 | hypervisor | namespace + cgroup (弱) | V8 isolate / microVM |
| 生命周期 | 月/年 | 分钟/小时 | 秒 |
| 攻击面 | 大 (含 OS) | 小 (共享 kernel) | 极小 |
| 权限模型 | VM 级 | Pod 级 + SA | 函数级 IAM Role |
| 补丁 | 慢 | 镜像重建 | CSP 负责 |
| 取证 | 全盘 | 容器 ephemeral | 极难 |

### 1.3 云厂商差异概述

| 概念 | AWS | Azure | GCP | 阿里云 | 华为云 |
|------|-----|-------|-----|--------|--------|
| 容器服务 | EKS/ECS/Fargate | AKS | GKE | ACK/ASK | CCE/CCI |
| 镜像仓库 | ECR | ACR | Artifact Registry | ACR | SWR |
| Serverless | Lambda | Functions | Cloud Functions/Run | FC | FunctionGraph |
| K8s 安全 | Security Hub + Inspector | Defender for Containers | GKE Security Posture | 容器服务安全 | HSS 容器版 |
| 镜像扫描 | Inspector | Defender | Artifact Analysis | 镜像安全扫描 | SWR 漏洞扫描 |

## 三、原理与机制

### 3.1 容器隔离机制

```
┌─────────────────────────────────┐
│  容器 (Container)               │
│  ┌───────────────────────────┐  │
│  │  namespace (隔离视图)      │  │
│  │  ├─ PID namespace         │  │
│  │  ├─ NET namespace         │  │
│  │  ├─ MNT namespace         │  │
│  │  ├─ UTS namespace         │  │
│  │  └─ IPC namespace         │  │
│  ├─ cgroup (资源限制)         │  │
│  ├─ capabilities (权限)       │  │
│  ├─ seccomp (系统调用过滤)    │  │
│  └─ SELinux/AppArmor (MAC)   │  │
│  共享 kernel                  │  │
└─────────────────────────────────┘
```

🔥 **关键弱点**：共享 kernel。kernel 漏洞 (如 Dirty COW) 可逃逸。

### 3.2 容器逃逸路径

| 路径 | 原理 | 防护 |
|------|------|------|
| 内核漏洞 | Dirty COW / OverlayFS | 及时 patch kernel |
| privileged 容器 | 容器有所有 capabilities | 永不 `--privileged` |
| 挂载 docker.sock | 容器可控制 docker daemon | 不挂载 |
| 挂载 / | 容器可读写宿主文件系统 | 不挂载 |
| capabilities 过多 | CAP_SYS_ADMIN 等于 root | 删除所有不必要 cap |
| 共享 namespace | --pid --net 共享 | 不共享 |

### 3.3 K8s RBAC 模型

```yaml
# Role (命名空间内)
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: default
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "watch", "list"]
---
# RoleBinding (绑定 Role 到用户/SA)
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods
  namespace: default
subjects:
- kind: ServiceAccount
  name: my-sa
  namespace: default
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

🔥 **RBAC 厸则**：
- 默认拒绝 (无 Role 则无权)
- 最小权限 (verbs 最小化)
- 命名空间隔离 (Role 限 namespace，ClusterRole 全局)
- 定期审计 (audit Role/ClusterRole 使用)

### 3.4 Pod Security Admission (PSA)

K8s 1.25+ 替代 PodSecurityPolicy。

```yaml
# 命名空间级 PSA 标签
apiVersion: v1
kind: Namespace
metadata:
  name: production
  labels:
    # enforce: 强制策略 (违反则拒绝)
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/enforce-version: latest
    
    # audit: 审计 (违反仅记录)
    pod-security.kubernetes.io/audit: restricted
    pod-security.kubernetes.io/audit-version: latest
    
    # warn: 警告 (违反提示用户)
    pod-security.kubernetes.io/warn: restricted
    pod-security.kubernetes.io/warn-version: latest
```

| 级别 | 限制 |
|------|------|
| privileged | 无限制 (旧 privileged 容器) |
| baseline | 防最明显提权 (不共享 host pid/net,不加 CAP_SYS_ADMIN) |
| restricted | hardening (必须 non-root,删所有 cap,seccomp Profile) |

### 3.5 Serverless 安全模型

```
事件源 → FaaS 平台 → 函数 (with role)
   │
   ├─ 事件注入: 攻击者构造恶意事件触发函数
   ├─ 函数 IAM: 函数被赋予过宽权限
   ├─ 依赖爆炸: package.json 引入数万个依赖
   └─ 冷启动: 容器复用导致数据残留
```

## 四、算法 / 流程

### 4.1 容器镜像扫描流程

```
输入: 镜像 reference (e.g., nginx:1.25)
输出: 漏洞列表 + 严重度

1. 拉取镜像 manifest
2. 逐层解压 layer
3. 识别包管理器元数据:
   ├─ /var/lib/dpkg/status (Debian)
   ├─ /lib/apk/db/installed (Alpine)
   ├─ /usr/lib/rpm (RHEL)
   ├─ pip / npm / maven 元数据
4. 对每个包查询 CVE 数据库 (NVD/OSV)
5. 输出: CVE + 包 + 严重度 + 修复版本
```

### 4.2 准入控制流程 (Kyverno)

```
kubectl apply Pod
   │
   ▼
API Server
   │
   ▼
Admission Webhook (Kyverno)
   │
   ├─ 1. verifyImages: 验证镜像签名
   ├─ 2. validate: 检查 Pod 规范 (PSA/资源/标签)
   ├─ 3. mutate: 自动注入 sidecar / 标签
   └─ 4. generate: 创建 ConfigMap/NetworkPolicy
   │
   ▼
Allow / Deny
```

### 4.3 NetworkPolicy 评估

```
输入: 流量 (src_pod, dst_pod, port, protocol)
输出: Allow / Deny

1. 找 dst_pod 命中的所有 NetworkPolicy (label selector)
2. 若无任何 policy: Allow (默认允许)
3. 若有 policy:
   for each policy:
     for each ingress rule:
       if src_pod matches AND port matches:
         return Allow
4. 所有 rule 都不匹配: Deny
```

⚠️ 默认允许是 K8s NetworkPolicy 的设计，需手动配 deny-all 才隔离。

## 六、代码 / 配置示例

### 6.1 最小可运行版（教学）：安全 Pod 配置

```yaml
# 安全 Pod 模板
apiVersion: v1
kind: Pod
metadata:
  name: secure-app
  labels:
    app: secure-app
spec:
  # 1. Service Account (最小权限)
  serviceAccountName: app-sa
  
  # 2. 安全上下文 (Pod 级)
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
    runAsGroup: 1000
    fsGroup: 1000
    seccompProfile:
      type: RuntimeDefault
  
  # 3. 自动删除完成的 Pod
  restartPolicy: Always
  
  containers:
  - name: app
    image: myapp@sha256:abc123...   # 用 digest 不用 tag
    imagePullPolicy: IfNotPresent
    
    # 4. 容器级安全上下文
    securityContext:
      runAsNonRoot: true
      runAsUser: 1000
      readOnlyRootFilesystem: true       # 根文件系统只读
      allowPrivilegeEscalation: false     # 禁止提权
      capabilities:
        drop: [ALL]                       # 删除所有 cap
        # add: [NET_BIND_SERVICE]          # 仅必要时添加
    
    # 5. 资源限制 (Guaranteed QoS)
    resources:
      requests:
        cpu: 500m
        memory: 512Mi
      limits:
        cpu: 500m
        memory: 512Mi
    
    # 6. 探针
    livenessProbe:
      httpGet: {path: /healthz, port: 8080}
      periodSeconds: 10
    readinessProbe:
      httpGet: {path: /ready, port: 8080}
      periodSeconds: 5
    
    # 7. 临时存储
    volumeMounts:
    - name: tmp
      mountPath: /tmp
    - name: cache
      mountPath: /app/cache
  
  volumes:
  - name: tmp
    emptyDir: {sizeLimit: 100Mi}
  - name: cache
    emptyDir: {sizeLimit: 500Mi}
  
  # 8. 优雅终止
  terminationGracePeriodSeconds: 60
  
  # 9. 反亲和 (跨节点)
  affinity:
    podAntiAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels:
            app: secure-app
        topologyKey: kubernetes.io/hostname
```

### 6.2 生产级版（工程）：完整 K8s 安全栈

```yaml
# ============================================
# 1. NetworkPolicy 默认拒绝
# ============================================
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: production
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  - Egress
---
# ============================================
# 2. 显式允许 frontend → backend → db
# ============================================
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-fe-to-be
  namespace: production
spec:
  podSelector:
    matchLabels:
      tier: backend
  policyTypes: [Ingress, Egress]
  ingress:
  - from:
    - podSelector:
        matchLabels: {tier: frontend}
    ports:
    - protocol: TCP
      port: 8080
  egress:
  - to:
    - podSelector:
        matchLabels: {tier: database}
    ports:
    - protocol: TCP
      port: 5432
  # 允许 DNS
  - to:
    - namespaceSelector: {}
      podSelector:
        matchLabels: {k8s-app: kube-dns}
    ports:
    - protocol: UDP
      port: 53
---
# ============================================
# 3. Kyverno 策略: 禁止特权容器
# ============================================
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: disallow-privileged-containers
spec:
  validationFailureAction: Enforce
  background: true
  rules:
  - name: privileged-containers
    match:
      any:
      - resources:
          kinds: [Pod]
    validate:
      message: "禁止使用特权容器"
      pattern:
        spec:
          containers:
          - =(securityContext):
              =(privileged): "false"
---
# ============================================
# 4. Kyverno: 禁止 latest tag
# ============================================
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: disallow-latest-tag
spec:
  validationFailureAction: Enforce
  rules:
  - name: require-image-tag-not-latest
    match:
      any:
      - resources:
          kinds: [Pod]
    validate:
      message: "镜像禁止使用 latest tag"
      pattern:
        spec:
          containers:
          - image: "!*:latest"
---
# ============================================
# 5. Kyverno: 验证镜像签名
# ============================================
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: verify-image-signatures
spec:
  validationFailureAction: Enforce
  background: false
  rules:
  - name: verify-cosign-signature
    match:
      any:
      - resources:
          kinds: [Pod]
    verifyImages:
    - imageReferences:
      - "ghcr.io/myorg/*"
      mutateDigest: true
      attestors:
      - entries:
        - keyless:
            subject: "https://github.com/myorg/*/.github/workflows/*"
            issuer: "https://token.actions.githubusercontent.com"
            rekor:
              url: https://rekor.sigstore.dev
---
# ============================================
# 6. Kyverno: 强制资源限制
# ============================================
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: require-resource-limits
spec:
  validationFailureAction: Enforce
  rules:
  - name: require-resources
    match:
      any:
      - resources:
          kinds: [Pod]
    validate:
      message: "所有容器必须设置 resources.requests 和 limits"
      pattern:
        spec:
          containers:
          - resources:
              requests:
                memory: "?*"
                cpu: "?*"
              limits:
                memory: "?*"
                cpu: "?*"
---
# ============================================
# 7. Falco 规则 (运行时检测)
# ============================================
apiVersion: falco.org/v1

metadata:
  name: detect-shell-in-container
spec:

# ============================================

  name: app-sa
  namespace: production
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: production
  name: app-read-config
rules:
- apiGroups: [""]
  resources: ["configmaps"]
  verbs: ["get", "list", "watch"]
  resourceNames: ["app-config"]   # 限定具体 ConfigMap
---

  name: app-sa-read-config
```

### 6.3 Serverless 安全 (Lambda)

```python
# lambda_secure.py - 生产级 Lambda 函数
import json
import os
import boto3
from botocore.exceptions import ClientError

# 1. 不在代码里硬编码密钥,从环境变量 (加密) 读
DB_HOST = os.environ['DB_HOST']
DB_PASSWORD = os.environ['DB_PASSWORD']  # 已被 KMS 加密
TABLE_NAME = os.environ['TABLE_NAME']

dynamodb = boto3.resource('dynamodb')
table = dynamodb.Table(TABLE_NAME)

# 2. 输入验证 (防注入)
def validate_input(event: dict) -> dict:
    """严格校验输入,防止事件注入"""
    if 'body' not in event:
        raise ValueError("Missing body")
    
    try:
        body = json.loads(event['body']) if isinstance(event['body'], str) else event['body']
    except json.JSONDecodeError:
        raise ValueError("Invalid JSON")
    
    user_id = body.get('user_id', '')
    if not user_id or not user_id.isalnum() or len(user_id) > 64:
        raise ValueError("Invalid user_id")
    
    return body

# 3. 函数级 IAM 最小权限 (从 Lambda Role 来)
# Role 策略只允许 dynamodb:GetItem on this specific table

# 4. 限制单次执行时间和内存 (Lambda 配置)
# 5. 不在 /tmp 留敏感数据 (容器复用)
TMP_FILE = '/tmp/cache.json'
def handler(event, context):
    try:
        # 6. 调用前清除 /tmp (防容器复用泄露)
        if os.path.exists(TMP_FILE):
            os.remove(TMP_FILE)
        
        body = validate_input(event)
        
        # 7. 业务逻辑
        response = table.get_item(
            Key={'user_id': body['user_id']}
        )
        
        return {
            'statusCode': 200,
            'body': json.dumps(response.get('Item', {}))
        }
    except ValueError as e:
        return {
            'statusCode': 400,
            'body': json.dumps({'error': str(e)})
        }
    except ClientError as e:
        # 8. 错误信息不泄露内部细节
        return {
            'statusCode': 500,
            'body': json.dumps({'error': 'Internal error'})
        }
```

## 七、常见陷阱与最佳实践 ⚠️

| 陷阱 | 后果 | 对策 |
|------|------|------|
| 用 latest tag | 镜像不一致 + 漂移 | 用 digest |
| 镜像含 shell | 攻击面大 | distroless / scratch |
| 以 root 运行 | 容器逃逸容易 | runAsNonRoot + runAsUser |
| privileged 容器 | 等于 root 主机 | 永不使用 |
| 不限资源 | 单 Pod 打爆节点 | resources.limits 必设 |
| 默认 NetworkPolicy 允许 | Pod 互通无隔离 | deny-all + 显式 allow |
| SA 权限过宽 | 应用被攻破后横向移动 | 最小 Role + 限定 resourceNames |
| 挂载 docker.sock | 容器可控制 daemon | 不挂载 |
| 不验证镜像签名 | 后门镜像进入集群 | Cosign + Kyverno |
| 函数 IAM 全权限 | 函数被注入后越权 | 最小 Role + 限定资源 |
| Lambda /tmp 持久数据 | 容器复用泄露 | 每次调用清 /tmp |
| 不开审计日志 | 事故无法取证 | audit log → SIEM |

### 7.1 工程重点 (🔥)

1. **distroless + non-root + readOnlyRootFilesystem** — 三件套
2. **digest 而非 tag** — 镜像不可变
3. **Cosign 签名 + Kyverno 验证** — 镜像可信
4. **NetworkPolicy 默认拒绝** — 零信任网络
5. **RBAC 最小权限 + resourceNames** — 最小化
6. **Falco 运行时检测** — 行为基线
7. **Serverless 函数 IAM 收紧** — 单函数单 Role

## 十、综合面试题

1. **设计一个生产级 K8s 安全架构（多层防御）。**
   - 要点：镜像签名 (Cosign) + 准入 (Kyverno) + NetworkPolicy 默认拒绝 + RBAC 最小 + PSA restricted + distroless + non-root + readOnlyRootFS + Falco 运行时 + audit log。

2. **容器为何不如 VM 安全？如何缓解？**
   - 要点：共享 kernel,隔离弱;缓解用 gVisor/Kata/Firecracker microVM;distroless 缩小攻击面;及时 patch;不 privileged。

3. **Tesla K8s 事故的原因及防护？**
   - 要点：Kubernetes Dashboard 未授权暴露公网;无 NetworkPolicy 限制;应用 Pod 权限过宽;应限制 Dashboard 仅内网 + RBAC + NetworkPolicy。

4. **如何防止容器逃逸？**
   - 要点：永不 privileged;删除所有 capabilities;seccomp profile;SELinux/AppArmor;及时 patch kernel;distroless;最小 SA。

5. **K8s RBAC 最佳实践？**
   - 要点：默认拒绝;Role 优先于 ClusterRole;verbs 最小化;resourceNames 限定具体资源;定期审计 RoleBinding;SA 与 Role 一一对应。

6. **NetworkPolicy 默认允许如何变为零信任？**
   - 要点：先配 `default-deny-all` (ingress + egress);再按需 allow;DNS 必须放行;CNI 必须支持 (Calico/Cilium)。

7. **Serverless 函数安全最佳实践？**
   - 要点：输入严格验证;函数 IAM 最小;不硬编码密钥;/tmp 每次清;依赖最小化 + 锁版本;冷启动数据隔离;审计 API 调用。

8. **如何检测容器内异常行为？**
   - 要点：Falco 规则 (shell 启动 / 文件读取 / 网络异常);Tetragon eBPF 实时;audit log + SIEM;基线学习。

9. **镜像供应链安全如何保障？**
   - 要点：基础镜像可信 (distroless);CI 扫描 (Trivy);签名 (Cosign);准入验证 (Kyverno);SBOM 生成;SLSA 等级。

10. **Service Mesh 提供哪些安全能力？**
    - 要点：mTLS 服务间认证;AuthorizationPolicy L7 策略;证书自动轮换;SPIFFE 身份;流量加密 + 可观测。
