## 一、问题定义

### 1.1 解决什么问题

📜 **NIST SP 800-145** 定义云计算：通过网络按需自助获取可弹性配置的共享资源池。

云计算带来三个根本变化：

1. **物理控制权丧失** — 服务器、网络、存储不再在自己的机房
2. **责任扩散** — 安全不再由一方承担，而是 CSP + 租户 + 第三方
3. **边界消失** — 传统"内网可信、外网不可信"模型失效

🔥 **核心问题**：当数据和应用跑在别人家的硬件上，谁该为安全负责？负多少？

### 1.2 与传统数据中心安全的本质差异

| 维度 | 传统数据中心 | 云计算 |
|------|--------------|--------|
| 物理安全 | 自主管控 | CSP 负责 |
| 网络边界 | 明确（防火墙内/外） | 模糊（VPC 仍可被 IAM 暴露） |
| 资产清单 | 静态、可见 | 动态、API 创建即存在 |
| 身份边界 | AD/LDAP | 多租户 + 联邦身份 |
| 补丁管理 | 自主决定 | CSP 负责 OS / 租户负责应用 |
| 取证能力 | 全盘镜像 | 仅租户视图，CSP 配合 |
| 误配置风险 | 局部影响 | 跨账号 / 公网暴露 |
| 安全工具 | 主机为主 | API + IaC + 配置面 |

⚠️ **关键转变**：云时代的安全边界从"网络"转移到"身份"（Identity is the new perimeter）。

### 1.3 云厂商差异概述

| 概念 | AWS | Azure | GCP | 阿里云 | 华为云 |
|------|-----|-------|-----|--------|--------|
| 责任模型白皮书 | AWS Shared Responsibility Model | Microsoft Shared Responsibility | Google Cloud Shared Responsibility | 阿里云责任共担模型 | 华为云责任共担 |
| 默认加密 | 部分服务 | 多数服务 | 多数服务 | 部分 | 部分 |
| 合规报告入口 | AWS Artifact | Service Trust Portal | Compliance Reports | 合规中心 | 合规中心 |

## 三、原理与机制

### 3.1 直觉：责任"分层蛋糕"

```
责任分层 (从下到上):

┌─────────────────────────────────────────┐
│  数据 & 内容 (Data)                      │  ← 始终租户负责
├─────────────────────────────────────────┤
│  身份 & 访问 (Identity & Access)         │  ← 始终租户负责
├─────────────────────────────────────────┤
│  应用 & 配置 (Application & Config)      │  ← 始终租户负责
├─────────────────────────────────────────┤
│  操作系统 (OS)                           │  ← IaaS: 租户 / PaaS·SaaS: CSP
├─────────────────────────────────────────┤
│  运行时 (Runtime: Java/Node/Python)      │  ← IaaS: 租户 / PaaS·SaaS: CSP
├─────────────────────────────────────────┤
│  虚拟化 (Hypervisor)                     │  ← 始终 CSP
├─────────────────────────────────────────┤
│  网络 (Network)                          │  ← 始终 CSP (逻辑网络租户配)
├─────────────────────────────────────────┤
│  物理 (Facilities/Hardware)              │  ← 始终 CSP
└─────────────────────────────────────────┘
```

### 3.2 形式化定义

设安全责任函数 $R(s, m)$，其中 $s \in \{CSP, Tenant, Shared\}$ 表示某层责任主体，$m \in \{IaaS, PaaS, SaaS\}$ 表示服务模型。

📜 **责任共担公理**：
$$
\forall m: R(Data, m) = Tenant, \quad R(Physical, m) = CSP
$$

$$
R(L, IaaS) \to Tenant, \quad R(L, SaaS) \to CSP, \quad R(L, PaaS) = Shared
$$

其中 $L$ 为中间层（OS / Runtime / App Config）。

### 3.3 关键性质

1. **责任不可外包** — 即使租户把运维外包给 MSP，最终法律责任仍在租户
2. **责任随服务模型变** — 越上层服务，CSP 承担越多
3. **责任 ≠ 控制** — CSP 负责但租户仍需配置（如 KMS 默认加密需租户开启）
4. **共享技术 = 共享风险** — 多租户隔离失效时所有租户受影响

## 四、算法 / 流程

### 4.1 责任归属判定流程

```
输入: 某安全事件或控制项 C
输出: 责任主体 R ∈ {CSP, Tenant, Shared}

1. 若 C 涉及物理硬件/机房/电力/网络物理层:
      返回 CSP
2. 若 C 涉及数据内容/分类/合规义务:
      返回 Tenant
3. 若 C 涉及身份/IAM 策略/密钥使用:
      返回 Tenant
4. 查服务模型 m:
   - IaaS: OS 层及以下 = CSP, OS 以上 = Tenant
   - PaaS: Runtime 层及以下 = CSP, App 配置 = Tenant
   - SaaS: App 层及以下 = CSP, 数据/身份/集成 = Tenant
5. 若步骤 4 模糊 (如网络配置):
      返回 Shared (CSP 提供能力, 租户负责配置正确)
```

### 4.2 复杂度

判定算法 $O(1)$（常数级查表），但实际争议解决 $O(n)$，n = 涉及服务数。

### 5.1 五家云厂商责任模型

| 维度 | AWS | Azure | GCP | 阿里云 | 华为云 |
|------|-----|-------|-----|--------|--------|
| 模型名称 | AWS Shared Responsibility | Microsoft Shared Responsibility | Google Cloud Shared Fate + Responsibility | 责任共担模型 | 责任共担模型 |
| 特色 | 明确"of cloud / in cloud" | "shared responsibility" 图 | 提出 "Shared Fate"（共同命运） | 与 NIST 对齐 | 与等保 2.0 对齐 |
| IaaS 边界 | Hypervisor 切 | Hypervisor 切 | Hypervisor 切 | Hypervisor 切 | Hypervisor 切 |
| 数据责任 | in cloud = 租户 | in cloud = 租户 | in cloud = 租户 | in cloud = 租户 | in cloud = 租户 |
| 容器服务 | EKS 节点 OS = 租户 | AKS 节点 OS = 租户 | GKE 节点 OS = 租户 | ACK 节点 OS = 租户 | CCE 节点 OS = 租户 |
| Serverless | Fargate 运行时 = CSP | Container Apps = CSP | Cloud Run = CSP | ASK = CSP | CCI = CSP |

🔥 **GCP "Shared Fate" 的独特观点**：CSP 不能只承担"提供工具"的责任，还要为"默认配置安全"承担共同命运。例如 GCP 默认阻断某些高危操作。

### 5.2 服务模型与责任分界实例

| 实例 | 模型 | 谁负责 OS 补丁 | 谁负责应用补丁 | 谁负责数据加密 |
|------|------|---------------|---------------|---------------|
| EC2 | IaaS | 租户 | 租户 | 租户（用 KMS） |
| RDS | PaaS | CSP | 租户（管理引擎版本） | 租户（启用 KMS） |
| Lambda | Serverless | CSP | 租户（依赖） | 租户（环境变量加密） |
| S3 | 对象存储 | CSP | N/A | 租户（SSE-SSE-KMS） |
| DynamoDB | NoSQL PaaS | CSP | N/A | 默认加密，密钥管理可选 |

## 六、代码 / 配置示例

### 6.1 最小可运行版（教学）：检测 S3 桶是否公开

```python
# detect_public_bucket.py
import boto3

s3 = boto3.client('s3')

def check_bucket_public(bucket_name):
    """检查桶是否允许公开访问"""
    try:
        acl = s3.get_bucket_acl(Bucket=bucket_name)
        for grant in acl['Grants']:
            if grant['Grantee']['Type'] == 'Group':
                uri = grant['Grantee'].get('URI', '')
                if uri == 'http://acs.amazonaws.com/groups/global/AllUsers':
                    return True, grant['Permission']
        return False, None
    except Exception as e:
        return None, str(e)

# 检查所有桶
for b in s3.list_buckets()['Buckets']:
    name = b['Name']
    is_public, perm = check_bucket_public(name)
    if is_public:
        print(f"⚠️ {name} 公开访问 ({perm})")
    else:
        print(f"✓ {name} 私有")
```

## 七、常见陷阱与最佳实践 ⚠️

| 陷阱 | 后果 | 对策 |
|------|------|------|
| 认为云默认安全 | 公网暴露的 S3 / RDS | 🔥 默认阻断公开 + Config 持续检测 |
| 用 root 账号做日常操作 | 凭证泄露后全账号沦陷 | 🔥 创建 IAM 用户 + MFA + 不用 root key |
| 责任理解错误 (以为 OS 自动补丁) | EC2 被利用 | IaaS 模型下 OS 补丁由租户负责 |
| 共享凭证代替 IAM Role | 凭证泄露 + 审计断链 | 用 STS 临时凭证 + Role chaining |
| 忽视多账号治理 | 权限蔓延 + 配置漂移 | AWS Organizations + SCP + Landing Zone |
| 用单一账号跑所有业务 | 故障半径大 + 权限混杂 | 多账号策略：log/security/workload 分离 |
| 信任 CSP 默认网络 | 0.0.0.0/0 暴露 | 默认拒绝 + 显式放行 |
| 不读 CSP 的事件通知 | 错过 CVE 通知 | 订阅 security bulletin + 自动化工单 |
| 责任甩锅给 CSP | 合规失败 + 罚款 | 明确 RACI 矩阵 + 合同条款 |

### 7.1 工程重点 (🔥)

1. **Landing Zone 优先** — 在写第一个业务之前先建多账号基线
2. **审计可追溯** — 所有 API 调用必须有 CloudTrail / Audit Log
3. **配置面不可漂移** — IaC + Config 检测 + 自动修复
4. **默认拒绝** — 网络、IAM、加密都从默认拒绝开始
5. **凭证短生命周期** — STS 临时凭证 > 长期 access key

## 十、综合面试题

1. **请解释云责任共担模型，并举例说明 IaaS / PaaS / SaaS 三种模式下分界线的差异。**
   - 答题要点：分层蛋糕图；IaaS 在 OS 处切，PaaS 在 Runtime 处切，SaaS 在 App 处切；举例 EC2 / RDS / S3。

2. **某公司在 AWS EC2 上跑应用，被攻击者通过未打补丁的 OS 漏洞入侵，谁该负责？为什么？**
   - 答题要点：IaaS 模型，OS 层由租户负责；AWS 只负责 hypervisor 以下；攻击者利用 OS 漏洞 = 租户未履行补丁责任；可借鉴 Capital One 案例区分基础设施责任与配置责任。

3. **如果使用 PaaS（如 RDS），是否就可以完全不管数据库安全？**
   - 答题要点：不能。CSP 负责 OS/引擎补丁/可用性，但租户仍需负责：数据加密、网络暴露（SG）、IAM 权限、SQL 注入防护、备份策略、合规。

4. **某团队认为"上了云就安全了"，请从责任模型角度反驳。**
   - 答题要点：云只提供能力，不提供"安全状态"；S3 默认创建时虽私有可能但策略可改公开；IAM 默认拒绝但用户可能给 * 权限；需配置面扫描 + 持续监控。

5. **比较 AWS / Azure / GCP 三家责任模型的差异。**
   - 答题要点：AWS "of/in cloud" 强调分界；Azure 类似 AWS 但更细化服务层；GCP "Shared Fate" 强调 CSP 应为默认配置承担共同责任；合规报告入口不同（Artifact / STP / Compliance Reports）。

6. **多账号架构下，如何确保所有账号都履行责任？**
   - 答题要点：AWS Organizations + SCP 强制基线；CloudFormation StackSet 跨账号部署；Security Hub 聚合；Config Aggregator 跨账号视图；GuardDuty Admin 账号委派。

7. **某金融客户问"我能否把 PCI-DSS 责任完全外包给云厂商？"**
   - 答题要点：不能。PCI-DSS 责任不可外包（PCI SSC 规定）；CSP 提供合规报告证明基础设施层控制项，但应用层、数据层、配置层仍由租户负责；需明确 RACI 矩阵。

8. **如何评估一个组织的云安全成熟度？**
   - 答题要点：CSA CMM 5 级（Initial/Defined/Managed/Quantitatively Managed/Optimizing）；评估维度：身份、网络、数据、工作负载、检测响应、合规、DevSecOps；输出成熟度雷达图。

9. **责任共担模型在多云场景下有何挑战？**
   - 答题要点：各家分界不完全一致；同一控制项在不同云的配置方式不同；权限模型不一致（IAM vs Entra ID vs Cloud IAM）；需统一的策略即代码（OPA/Cedar）+ 统一 CSPM。

10. **CSPM、CWPP、CNAPP、CIEM、KSPM 五个概念的区别和关系？**
    - 答题要点：CSPM 配置面、CWPP 运行时、CIEM 权限面、KSPM K8s 配置；CNAPP 是融合平台，包含前四者；演进趋势是 CNAPP 一体化。
