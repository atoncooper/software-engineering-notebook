## 21.4 原理与机制

### 21.4.1 答题框架(适用设计题)

🎓 **STAR-R 框架**:

```
S (Situation)  : 描述场景与约束
T (Task)       : 明确目标与威胁模型
A (Action)     : 设计方案与权衡
R (Result)     : 预期效果与监控
R (Review)     : 复盘与改进点
```

**示例应用**:

> **问题**: 设计一个跨region的灾备方案

- **S**: 业务部署在 AWS us-east-1,要求 DR 到 us-west-2
- **T**: RPO ≤ 15min,RTO ≤ 30min,成本可控
- **A**: Aurora Global Database(同步复制) + S3 CRR + Route53 健康检查 + Lambda 自动切换
- **R**: 监控复制延迟、切换耗时,季度演练
- **R**: 优化切换脚本,降低 RTO 到 10min

## 21.7 代码/配置示例

### 21.7.1 高频问题合集

#### 主题 1: 责任共担模型

**Q1 [L1]**: 云计算的责任共担模型是什么?IaaS/PaaS/SaaS 有何不同?

> 云厂商负责底层基础设施(物理机房、网络、虚拟化层)的安全,客户负责云端数据和应用的安全。IaaS 客户责任最大(含 OS 及以上),PaaS 客户负责应用和数据,SaaS 客户主要管数据和访问。AWS 的责任止于 hypervisor,Azure/GCP 类似。
> **关键要点**: 责任边界随服务模型变化;共享责任 ≠ 厂商免责;客户最易忽视 OS/应用层责任。
> **追问**: 数据库服务 RDS 谁负责打补丁?→ 厂商负责引擎补丁,客户负责参数配置与数据。

**Q2 [L2]**: 给出一个责任共担模型失效导致事故的案例。

> Capital One 2019 年事故:SSRF 漏洞 + IAM 角色过度授权,攻击者通过 WAF 服务器访问元数据服务,窃取 IAM 凭证,横向移动到 S3 拉取 1 亿用户数据。云厂商 AWS 基础设施无问题,但客户在 IAM 配置与 WAF 部署上有缺陷,责任在客户侧。最终罚款 1.9 亿美元。
> **追问**: 如何避免?→ IMDSv2 + 最小权限 IAM + 网络隔离 + GuardDuty 检测。

#### 主题 2: IAM

**Q3 [L1]**: 什么是 IAM 最小权限原则?如何落地?

> 仅授予完成任务所需的最小权限,而非"先给宽权限后续收紧"。落地方法:1) 用 IAM Access Analyzer 分析实际使用权限;2) 从空策略开始按需添加;3) 用条件键约束(IP、时间、MFA);4) 定期审计移除未用权限;5) 用 Permission Boundary 限制角色上界。
> **追问**: 如何发现过度授权?→ CloudTrail + Access Analyzer + IAM Last Accessed。

**Q4 [L2]**: 设计一个 K8s 上的服务访问 AWS S3 的安全方案。

> 推荐使用 IRSA(IAM Roles for Service Accounts):1) 创建 OIDC Provider 关联 EKS;2) 创建 IAM Role 附加最小 S3 策略;3) Role Trust Policy 限制 sub 和 aud;4) ServiceAccount 通过 annotation 绑定 Role;5) Pod 使用 SA 挂载的 token 通过 STS AssumeRoleWithWebIdentity 获取临时凭证。
> **优势**: 无需长期密钥;权限按 Pod 隔离;审计可追踪。
> **替代方案**: Pod Identity(新版)/ kiam / kube2iam。
> **追问**: 多集群如何隔离?→ 每集群独立 OIDC + Role Trust Condition 限制 aud。

**Q5 [L3]**: 如何设计一个支持百万级用户的 IAM 权限审批流?

> 1) 权限申请走 ITSM(如 ServiceNow),自动审批规则(<7 天、只读、低敏感) + 人工审批(管理员、写权限);2) 审批通过后通过 Terraform PR 修改 IAM 策略;3) CI 自动 validate 策略语法 + OPA 策略合规检查;4) Merge 后 Terraform apply;5) CloudTrail 记录变更,Security Hub 持续扫描;6) JIT(Just-In-Time)权限通过 AWS SSO 临时提升,自动过期。
> **关键设计**: 权限默认拒绝;变更走代码;监控异常使用;定期 recertify。

#### 主题 3: 网络安全

**Q6 [L1]**: VPC 的安全组与 NACL 有何区别?

> 安全组是有状态实例级防火墙,默认拒绝所有入站、允许所有出站,基于白名单;NACL 是无状态子网级防火墙,默认允许所有,基于规则序号匹配。安全组适合实例级精细控制,NACL 适合子网级粗粒度防护(如 DMZ 隔离)。生产环境两者配合使用。
> **追问**: NACL 为何无状态?→ 性能 + 简单;但需双向规则配置,易错。

**Q7 [L2]**: 设计一个面向互联网的三层 Web 应用网络架构。

> 1) 公网子网放 ALB,只开放 80/443 入站;2) 应用子网放 EC2/ECS,只允许来自 ALB 的 8080 入站;3) 数据子网放 RDS,只允许来自应用子网的 3306 入站;4) NAT Gateway 让应用子网访问互联网更新;5) VPC Endpoint 访问 S3/SSM 不走公网;6) WAF 挂 ALB 防常见攻击;7) Shield Advanced 防 DDoS;8) CloudFront 加速 + 隐藏源站。
> **追问**: 如何检测横向移动?→ VPC Flow Logs + GuardDuty + Detective。

**Q8 [L3]**: 跨账号跨 VPC 网络联通的最佳实践是什么?

> 1) 同 region 跨 VPC 用 VPC Peering(简单但难扩展);2) 多 VPC 用 Transit Gateway(中心化路由);3) 跨账号用 RAM 共享 TGW;4) 跨 region 用 TGW peering;5) 高安全场景用 PrivateLink(端点服务,不暴露路由);6) 混合云用 Direct Connect + VPN 备份;7) 全程加密(mTLS 或 MACsec);8) 路由策略用路由表 + TGW 路由域。
> **避免**: 跨账号直接 Peering 难管理;专线单点故障无备份。

#### 主题 4: 数据安全

**Q9 [L1]**: 信封加密是什么?为什么需要?

> 信封加密用数据密钥(DEK)加密数据,用主密钥(KEK)加密 DEK,加密后的 DEK 与密文一起存储。优势:1) DEK 不离开 KMS,KEK 永不出云;2) 加解密操作无需调用 KMS(只需取 DEK),性能高;3) KEK 旋转不影响历史 DEK;4) 撤销 KEK 即可使所有 DEK 不可用。
> **追问**: DEK 暴露在内存中如何防护?→ 用后即清零、内存锁 mlock、避免 swap。

**Q10 [L2]**: 设计一个跨region的加密数据同步方案。

> 1) 主region 用本地 KMS CMK 加密 DEK,DEK 加密数据存 S3;2) 用 S3 Cross-Region Replication 复制对象(含加密 DEK)到 DR region;3) DR region 用本地 KMS CMK 重新加密 DEK(S3 支持 SSE-KMS 复制时改密);4) KMS CMK 跨 region 复制用多 region key(共享密钥材料)或独立 key(更安全但需 DR 时切换);5) 权限隔离:DR region 的角色不能直接解密主 region 数据;6) 演练时验证 DR region 能解密。
> **追问**: 多 region key 风险?→ 一处泄露全局失效;独立 key 更安全但需应用感知。

**Q11 [L3]**: 如何实现"加密销毁"(Crypto-shredding)?

> 销毁数据的密钥即等价销毁数据。1) 每个数据对象用唯一 DEK 加密;2) DEK 用 KEK 加密后与数据同存;3) 销毁时调用 KMS DeleteKey(KEK),等待 7-30 天 pending window;4) 期间 KEK 不可用,密文无法解密;5) 等待期满后 KMS 永久删除 KEK,数据彻底无法恢复。适用于 GDPR"被遗忘权"。注意:KMS 删除有 pending window,紧急场景需提前规划。
> **追问**: 如何防止误删?→ 双人审批 + 删除前快照 + 跨账号备份。

#### 主题 5: 工作负载安全

**Q12 [L1]**: 容器与虚拟机的安全差异?

> 容器共享内核,隔离弱于 VM;启动快但逃逸风险高;镜像供应链是新增攻击面;运行时权限需严格限制(privileged、root)。VM 隔离强,但启动慢、资源开销大。生产推荐:敏感服务用 VM,微服务用容器,容器内用 gVisor/Kata 增强隔离。
> **追问**: Kubernetes 下如何增强隔离?→ Pod Security Admission + Kata + 网络策略 + 只读根文件系统。

**Q13 [L2]**: 容器运行时安全如何防护?

> 1) 镜像构建:用 distroless/alpine 减少攻击面,无 shell 降低 RCE 影响;2) 部署前:Trivy/Grype 扫漏洞,Cosign 验签,Kyverno/Gatekeeper 策略准入;3) 运行时:Falco/Tetragon eBPF 检测异常(如 shell 启动、文件篡改、可疑网络连接);4) 网络:Cilium 网络策略限制东西向流量;5) 权限:Pod Security Standards Restricted 模式;6) 密钥:不用 env,用 Vault / CSI Secret Store。
> **追问**: 如何检测容器逃逸?→ 监控 privileged 容器启动、/proc/1/root 异常访问、内核模块加载。

**Q14 [L3]**: 设计一个金融级 K8s 安全方案。

> 1) 多租户隔离:用 namespace + network policy + RBAC,关键服务用独立集群;2) 镜像安全:私有仓库 + Cosign 签名 + 准入控制验签 + 漏洞扫描门槛;3) 运行时:Kata Containers(VM 级隔离) + Falco + Tetragon;4) 网络:Cilium mTLS + Service Mesh(Istio)+ Egress 白名单;5) 密钥:Vault + CSI Secret Store + 动态密钥;6) 审计:Audit Log 接 SIEM + Prometheus 监控;7) 合规:CIS Kubernetes Benchmark + kube-bench;8) DR:Velero 备份 + 跨集群同步。
> **追问**: 如何处理节点被攻陷?→ Node 自动隔离 + Pod 重调度 + 取消该节点 IAM 角色 + 内存取证。

#### 主题 6: 零信任

**Q15 [L1]**: 零信任的核心原则是什么?

> 1) 永不信任,始终验证(身份 + 设备 + 上下文);2) 默认拒绝,最小权限;3) 显式授权每次访问;4) 持续监控与评估;5) 微分段隔离资源;6) 加密所有通信(不再信任内网)。NIST 800-207 定义零信任架构核心组件:PE(策略引擎)、PA(策略管理员)、PEP(策略执行点)。
> **追问**: 零信任与 VPN 区别?→ VPN 是网络层信任(进内网即信任),零信任是应用层信任(每次请求都验证)。

**Q16 [L2]**: 在 AWS 上如何落地零信任?

> 1) 身份:AWS SSO + IAM Identity Center 统一身份,MFA 强制;2) 网络:VPC Endpoint + PrivateLink 替代公网访问;3) 应用:ALB + OIDC + Cognito 验证;4) 数据:KMS + 资源策略;5) 监控:CloudTrail + GuardDuty + Access Analyzer;6) 实施 BeyondCorp 模式:IAP(Identity-Aware Proxy) 替代 VPN;7) 设备 posture:Jamf + Intune 集成,不达标设备拒绝;8) 持续评估:UEBA 行为分析动态调整信任。
> **追问**: 堡垒机是否还必要?→ 零信任下用 SSM Session Manager 替代堡垒机,无 SSH 端口暴露。

**Q17 [L3]**: 零信任的成熟度如何评估?

> 参考 CISA ZTMM 2.0:1) 传统(无零信任);2) 初始(部分身份统一);3) 进阶(身份 + 设备 + 网络分段);4) 目标(全场景零信任);5) 优化(自动化响应)。每个支柱(身份、设备、网络、应用、数据)独立评估。指标:SSO 覆盖率、MFA 覆盖率、最小权限覆盖率、网络分段比例、加密流量比例、持续验证频率。
> **追问**: 落地路径?→ 身份先行 → 设备管理 → 网络分段 → 应用改造 → 数据分级 → 自动化响应。

#### 主题 7: CSPM/CWPP/CNAPP

**Q18 [L1]**: CSPM 与 CWPP 的区别?

> CSPM(云安全态势管理)扫配置合规,如"S3 是否公开"、"安全组是否开放 0.0.0.0/0";CWPP(工作负载保护平台)保护运行时,如"容器是否被入侵"、"主机进程是否异常"。CSPM 静态、控制面、跨云;CWPP 动态、数据面、主机/容器。CNAPP 是两者融合 + CI/CD 集成。
> **追问**: 哪个更重要?→ 互补,CSPM 防配置错误(80% 事故根因),CWPP 防运行时攻击。

**Q19 [L2]**: 如何选择 CNAPP 厂商?

> 评估维度:1) 多云覆盖(AWS/Azure/GCP/阿里/华为);2) 检测规则数量与质量(CIS、等保、自定义);3) 运行时性能影响(<5% CPU);4) CI/CD 集成(IaC 扫描、镜像扫描);5) 告警噪声(误报率 <10%);6) 工作流集成(ServiceNow、Jira);7) 合规报告自动生成;8) API 与 SDK 完整度;9) 成本(按云账号 / 工作负载计费)。主流:Wiz、Palo Alto Prisma、Lacework、Aqua、Sysdig。
> **追问**: 自建 vs 商业?→ 自建适合超大规模(成本可控),商业适合中小团队(快速落地)。

#### 主题 8: DevSecOps

**Q20 [L1]**: DevSecOps 的"左移"是什么意思?

> 将安全检查从生产环境(右)前移到开发阶段(左),在 IDE、PR、CI 阶段发现漏洞,修复成本指数级降低。左移实践:1) IDE 插件(Snyk、Semgrep);2) Pre-commit hook(gitleaks 扫密钥);3) PR 扫描(SonarQube、CodeQL);4) CI 安全测试(DAST、SCA、镜像扫描);5) IaC 扫描(tfsec、Checkov);6) 准入控制(Cosign 验签)。
> **追问**: 左移能完全替代运行时安全吗?→ 不能,左移防已知,运行时防 0-day。

**Q21 [L2]**: 如何在 CI/CD 中嵌入安全门禁?

> 1) Commit 阶段:pre-commit 扫密钥 + 格式检查 + Semgrep;2) PR 阶段:CodeQL 静态分析 + Snyk SCA + tfsec IaC 扫描;3) Build 阶段:Trivy 镜像扫描 + Syft SBOM 生成 + Cosign 签名;4) Deploy 前:OPA 策略校验 + Cosign 验签 + 漏洞门禁(CRITICAL 阻断);5) Deploy 后:DAST 扫描 + 运行时监控;6) 每日:Cron 任务全量扫描 + 报告。门禁失败策略:Critical 阻断、High 警告、Medium 记录。
> **追问**: 如何避免安全门禁拖慢 CI?→ 并行执行 + 增量扫描 + 缓存。

**Q22 [L3]**: 设计一个金丝雀部署的安全验证方案。

> 1) 部署 1% 流量到新版本,运行 5 分钟;2) 监控核心指标:错误率、延迟、安全告警(Falco、WAF);3) 自动断路器:错误率 >0.5% 或 延迟 >P99 +50% 或 安全告警 ≥1 即回滚;4) 部署 10%、50%、100% 逐级验证;5) 每阶段运行自动化安全测试:漏洞扫描 + 模糊测试 + 行为基线对比;6) 回滚后保留现场用于取证;7) 全程审计:部署流水线日志 + 安全决策日志存 WORM。
> **追问**: 如何检测"慢攻击"(灰度期无异常,全量后爆发)?→ 限流 + 异常检测 + 流量镜像对比。

#### 主题 9: 密钥管理

**Q23 [L1]**: KMS 与 Secret Manager 的区别?

> KMS 管理非对称密钥(加密/解密),不存储数据,只做密钥操作;Secret Manager 存储机密信息(密码、token、证书),提供版本管理与轮换。KMS 用于加密其他密钥(信封加密),Secret Manager 用于存储应用机密。两者配合:用 KMS 加密 Secret Manager 中的 secret。
> **追问**: KMS 能存数据吗?→ 不能,只加密 ≤4KB 数据,大数据用信封加密。

**Q24 [L2]**: BYOK / HYOK / EKM 的区别?

> BYOK(Bring Your Own Key):客户提供密钥材料导入 KMS,密钥在云上使用但材料由客户控制;HYOK(Hold Your Own Key):密钥完全在客户自建 HSM,云上不持有,适用于极敏感数据;EKM(External Key Manager):AWS/GCP 服务,密钥操作需调用客户外部 HSM,云厂商无法解密。安全性:HYOK > EKM > BYOK > 云托管。代价:HYOK 性能差、可用性低。
> **追问**: BYOK 删除密钥材料后还能用吗?→ 不能,密钥状态变为 Disabled,数据无法解密。

#### 主题 10: 审计与可观测

**Q25 [L1]**: CloudTrail 记录哪些事件?

> 三类事件:1) Management Events(默认):API 调用(IAM、EC2、S3 等管理操作);2) Data Events(需手动启用):S3 GetObject、Lambda Invoke、DynamoDB 查询等数据面操作;3) Insight Events(可选):异常活动检测(如 IAM 角色被大量使用)。事件结构包含 userIdentity、sourceIPAddress、eventTime、requestParameters、responseElements。
> **追问**: CloudTrail 是实时吗?→ 不是,平均 5-15 分钟延迟,实时用 EventBridge。

**Q26 [L2]**: 如何防止 CloudTrail 被篡改?

> 1) 日志存 S3 + Object Lock COMPLIANCE 模式(连 root 都不能删);2) KMS 加密,密钥策略禁止删除;3) 日志文件完整性验证(Log File Validation,SHA-256 哈希链);4) 跨账号日志投递(目标账号无写入权限);5) CloudWatch Logs 订阅实时备份到 S3;6) 定期用 AWS Audit Manager 验证完整性;7) 关键事件 EventBridge 触发告警。
> **追问**: root 用户能删除 Object Lock 吗?→ COMPLIANCE 模式不能,GOVERNANCE 模式可以。

**Q27 [L3]**: 设计一个跨云统一审计平台。

> 1) 数据采集:AWS CloudTrail + Azure Activity Log + GCP Audit Log + 阿里 ActionTrail + 华为 CTS;2) 统一格式:转换成 OCSF(Open Cybersecurity Schema Framework);3) 数据存储:S3 数据湖 + Athena 查询 + Hot tier OpenSearch;4) 实时检测:Sigma 规则 + MITRE ATT&CK 映射;5) 可视化:Grafana / Kibana 仪表板;6) 告警:PagerDuty / Slack;7) 取证:原始日志归档 Glacier,7 年保留;8) 合规:自动化报告(等保、GDPR、SOC2)。
> **关键挑战**: 日志格式差异、跨云时区、成本控制(热温冷分层)。
> **追问**: 如何检测跨云横向移动?→ 关联同一身份的跨云活动 + IP 异常 + 时间异常。

#### 主题 11: 威胁检测与响应

**Q28 [L1]**: GuardDuty 能检测哪些威胁?

> 三类来源:1) 威胁情报(IP、域名);2) ML 异常检测(异常 API 调用、地理位置);3) 异常行为(凭证滥用、端口扫描)。典型发现:UnauthorizedAccess:EC2/CompromisedInstance、CredentialExfiltration:IAMUser、Persistence:IAMUser/Backdoor、Trojan:EC2/DriveBySourceTraffic。
> **追问**: 误报如何处理?→ Archive + 自动归档规则 + 反馈给 AWS 改进模型。

**Q29 [L2]**: 设计一个云上入侵响应 Playbook。

> 1) 检测:GuardDuty/Security Hub 触发告警;2) 分类:自动化分级(Critical 立即响应 / High 1 小时 / Medium 4 小时);3) 隔离:Lambda 自动给实例加隔离 SG + 撤销 IAM 角色 + 快照 EBS;4) 取证:内存 dump + 磁盘快照 + CloudTrail 日志导出;5) 评估:分析影响范围、数据泄露可能;6) 根除:轮换所有可能泄露的密钥、修复漏洞;7) 恢复:从干净镜像重建 + 部署;8) 复盘:48 小时内完成 RCA,改进检测规则与 Playbook。
> **追问**: 如何平衡业务连续性与隔离?→ 隔离 SG 而非关机,保留业务数据待取证。

**Q30 [L3]**: 如何用 ATT&CK 框架提升检测能力?

> 1) 映射云上攻击:ATT&CK Cloud Matrix 覆盖 Initial Access / Execution / Persistence / Privilege Escalation / Defense Evasion / Credential Access / Discovery / Lateral Movement / Collection / Exfiltration / Impact;2) 每个技术对应检测规则:如 T1078.004(Valid Accounts: Cloud)→ CloudTrail 异常登录检测;3) 优先级:覆盖高频技术(T1078、T1098、T1530);4) 紫队验证:Atomic Red Team + Stratus Red Team 模拟攻击;5) 度量:Detection Coverage Matrix 显示哪些技术已覆盖;6) 持续:每月新增 2-3 个检测规则,季度紫队演练。
> **追问**: 如何防止检测规则被绕过?→ 多层检测(签名 + 行为 + 异常)+ 规则版本化 + 攻击者视角红队。

#### 主题 12: 合规与治理

**Q31 [L1]**: GDPR 与等保 2.0 的核心差异?

> GDPR 是欧盟数据保护法,核心是个人数据保护、用户权利(访问、删除、可携)、跨境传输限制、违规罚款(最高 4% 全球营收)。等保 2.0 是中国网络安全等级保护,核心是网络安全等级(1-5 级)、技术与管理要求、测评机构测评、违规行政处罚。GDPR 关注个人权利,等保关注国家安全。
> **追问**: 跨境数据传输如何合规?→ 标准合同条款(SCC)、绑定公司规则(BCR)、中国数据出境安全评估。

**Q32 [L2]**: 如何落地 Policy-as-Code?

> 1) 策略定义:Rego(OPA)、CEL、Sentinel;2) IaC 扫描:Checkov/tfsec 在 CI 阶段扫描 Terraform;3) 准入控制:OPA Gatekeeper / Kyverno 在 K8s 准入阶段拦截;4) 云原生:AWS SCP / Azure Policy / GCP Org Policy 在云控制面拦截;5) 运行时:Config + Lambda 自动修复;6) 报告:Security Hub 统一展示。策略库开源:CIS Benchmark、FedRAMP、HIPAA。
> **追问**: 如何避免策略过多拖慢部署?→ 策略分级(强制 / 警告 / 建议)+ 例外管理 + 自动修复而非阻断。

**Q33 [L3]**: 多云合规如何统一管理?

> 1) 统一标准:用 ISO 27001 / SOC 2 作为基线,各云叠加本地合规;2) 统一采集:CloudTrail / Activity Log / Audit Log → OCSF 格式;3) 统一策略:OPA 跨云策略,各云原生策略为子集;4) 统一报告:Cloud Security Posture 工具(Wiz / Prisma);5) 数据主权:数据驻留策略,各 region 数据不互通;6) 跨境传输:统一 DLP + 加密 + 审批;7) 审计:统一审计轨迹 + 季度合规报告;8) 应急:跨云事件响应 Playbook。
> **关键挑战**: 各云服务命名差异(如 AWS SCP vs Azure Policy)、权限模型差异、合规标准差异。

#### 主题 13: 多云与混合云

**Q34 [L1]**: 多云的优势与风险?

> 优势:1) 避免厂商锁定;2) 利用各云优势服务;3) 地域覆盖;4) 谈判筹码;5) 灾备。风险:1) 复杂度上升(2-3 倍运维成本);2) 安全策略不一致;3) 跨云网络延迟与成本;4) 数据一致性挑战;5) 人才稀缺。
> **追问**: 何时该上多云?→ 业务规模足够大、合规要求、议价能力、关键服务灾备。

**Q35 [L2]**: 多云 KMS 如何设计?

> 1) 各云独立 KMS(不共享密钥材料),降低跨云依赖;2) 信封加密:应用层用统一 DEK,各云 KEK 独立加密;3) 密钥托管:Hyperledger KMS / HashiCorp Vault 跨云统一接口;4) BYOK:本地 HSM 生成密钥材料,各云导入;5) 元数据:KMS 资源映射存配置中心;6) 故障切换:DR 时切换到备用云 KMS,密文携带 DEK;7) 审计:跨云 KMS 操作日志统一聚合。
> **追问**: 全局 KEK 是否可行?→ 不建议,单点风险,性能差。

#### 主题 14: 供应链安全

**Q36 [L1]**: SBOM 是什么?为何重要?

> SBOM(Software Bill of Materials)是软件物料清单,记录组件、版本、依赖关系、来源。重要性:1) 漏洞快速定位(Log4Shell 时快速找到受影响系统);2) 许可证合规;3) 供应链攻击溯源;4) 组件生命周期管理。格式:SPDX(ISO 标准)、CycloneDX(OWASP)。
> **追问**: SBOM 包含哪些字段?→ 组件名、版本、供应商、依赖关系、哈希、许可证、PURL。

**Q37 [L2]**: 依赖混淆攻击是什么?如何防御?

> 攻击者在公共 npm/PyPI 仓库注册与内部同名的包,内部构建系统从公共仓库拉取到恶意包,导致代码执行。防御:1) 内部包名加私有前缀(@company/);2) 私有仓库优先于公共仓库(.npmrc 配置);3) 包名抢注:在公共仓库注册同名空包占位;4) Scope 严格:构建时只允许 scope 内包;5) 锁文件:package-lock.json 锁定版本与完整性;6) 漏洞扫描:Socket / Snyk 检测可疑行为。
> **追问**: 类似攻击有哪些?→ typosquatting(包名拼写攻击)、brandjacking(仿冒知名包)。

**Q38 [L3]**: SLSA 框架如何提升供应链安全?

> SLSA(Build Level 1-4)分四级:1) L1:构建有文档;2) L2:托管构建 + 审计;3) L3:构建隔离 + 不可伪造来源;4) L4:双人审核 + 可重现构建。每级要求:Source、Build、Provenance 三方面。落地:1) 用 GitHub Actions / Cloud Build 托管构建;2) 生成 provenance(SLSA Generator);3) Cosign 签名 provenance;4) Kyverno / Cosign 验签准入;5) SBOM 与 provenance 关联。xz-utils 后门正是 L3 缺失导致。
> **追问**: L4 是否过度?→ 金融/关键基础设施必需,普通业务 L3 足够。

#### 主题 15: Serverless 安全

**Q39 [L1]**: Lambda 的安全风险有哪些?

> 1) 事件注入:API Gateway / SQS / S3 事件未严格校验;2) IAM 角色过度授权:Lambda 拥有 s3:* 而非 s3:GetObject;3) 密钥泄露:环境变量存敏感信息;4) 依赖漏洞:第三方库已知漏洞;5) 冷启动信息泄露:共享执行环境残留;6) IMDS 滥用:Lambda 可访问元数据;7) 资源耗尽:递归调用或大输入导致 DoS。
> **追问**: 如何防事件注入?→ 输入校验 + Schema 验证 + 最小权限 + WAF。

**Q40 [L2]**: Lambda 冷启动如何优化?

> 1) 包大小:精简依赖(<50MB),用 Lambda Layers 共享;2) SnapStart(Java):预初始化快照,启动时间从秒级到毫秒级;3) Provisioned Concurrency:预热并发,无冷启动;4) 避免重初始化:全局变量复用初始化;5) 数据库连接:连接池 + RDS Proxy;6) 加密:避免 KMS 在冷启动调用,缓存 DEK;7) 监控:CloudWatch Insights 分析冷启动占比。
> **追问**: SnapStart 安全风险?→ 快照可能包含密钥,需在 restore 后重新加载。

#### 主题 16: AI 安全

**Q41 [L1]**: 大模型云安全的独特风险?

> 1) Prompt Injection:恶意输入操控模型;2) 训练数据投毒:训练阶段植入后门;3) 模型窃取:API 调用反推模型;4) 数据泄露:训练数据记忆并输出;5) Pickle 反序列化:加载恶意模型 RCE;6) Agent 过度授权:工具调用失控;7) 模型供应链:开源模型含后门。
> **追问**: Prompt Injection 与 SQL Injection 区别?→ SI 在数据层,PI 在语义层,PI 更难防御(自然语言无法严格分离)。

**Q42 [L2]**: RAG 系统如何安全设计?

> 1) 数据层:文档权限映射到向量库元数据,检索时过滤;2) 嵌入层:嵌入模型可信(本地或 Bedrock);3) 检索层:top-k + 权限过滤 + 跨用户隔离;4) Prompt 层:系统 prompt 与用户 prompt 隔离,标记不可信内容;5) 输出层:敏感信息脱敏 + 事实核查(grounding);6) 审计:每次调用记录用户、文档、prompt、输出;7) 监控:检测 prompt injection 模式、异常查询。
> **追问**: 如何防止向量库泄露?→ 元数据 ACL + 加密 + 独立索引 per tenant。

#### 主题 17: 灾难恢复

**Q43 [L1]**: RPO 与 RTO 的区别?

> RPO(Recovery Point Objective):可接受数据丢失量,从故障时刻往回看,如 RPO=15min 表示最多丢 15 分钟数据。RTO(Recovery Time Objective):可接受业务中断时间,从故障到恢复,如 RTO=1h 表示 1 小时内恢复。RPO 关注数据(备份频率决定),RTO 关注业务(恢复速度决定)。
> **追问**: RPO=0 如何实现?→ 同步复制(如 Aurora Global、跨 AZ 同步)。

**Q44 [L2]**: 灾备的四种模式是什么?

> 1) Backup:仅备份,无运行环境,RTO 长(小时级),成本低;2) Pilot Light:核心数据复制,服务未运行,启动后扩容,RTO 中(分钟级);3) Warm Standby:小规模运行,故障时扩容,RTO 短(分钟级);4) Active-Active:双活,流量负载均衡,RTO 极短(秒级),成本最高。选择基于 RTO/RPO 与成本权衡。
> **追问**: 银行核心系统选哪种?→ Active-Active 跨 region,甚至跨云。

**Q45 [L3]**: 勒索软件攻击下如何保护备份?

> 1) 3-2-1-1-0 规则:3 份备份、2 种介质、1 份离线、1 份不可变、0 错误验证;2) WORM 备份:S3 Object Lock COMPLIANCE 模式,连 root 都不能删;3) 跨账号备份:备份账号无写入权限,主账号被攻陷不影响;4) 跨 region 复制:防物理灾难;5) 不可变快照:AWS Backup Vault Lock;6) 验证备份:每月恢复测试,确保可用;7) 隔离:备份网络与生产网络隔离(air gap 或 logical);8) 监控:异常删除立即告警。
> **追问**: Code Spaces 事故教训?→ 备份与生产同账号,被一次性删除,公司倒闭。

### 21.7.2 综合设计题

**Q46 [L3]**: 设计一个全球 SaaS 平台的安全架构。

**业务背景**: 全球 100 万用户,1 万企业客户,要满足 GDPR、CCPA、等保 2.0。

**架构要点**:
1) 数据驻留:EU 用户数据存 EU region,US 数据存 US region,中国数据存中国 region;
2) 身份:统一 IdP(Okta),SCIM 同步,区域隔离的 IAM 角色;
3) 网络:多 region 部署 + CloudFront 加速 + WAF + Shield;
4) 加密:KMS 多 region + 信封加密 + TLS 1.3 + 字段级加密(PII);
5) 租户隔离:Row-level security + KMS per-tenant key;
6) 审计:CloudTrail 跨账号 + 统一 SIEM;
7) DR:Active-Active 跨 region,RPO=0,RTO<5min;
8) 合规:CSPM 持续扫描 + 季度审计;
9) DevSecOps:IaC + CI/CD 安全门禁 + SBOM;
10) 事件响应:7x24 SOC + Playbook 自动化。

**追问应对**:
- 如何处理跨境数据传输?→ 差分隐私 + 加密 + 审批 + SCC;
- 如何防止租户间数据泄露?→ 单租户 KMS Key + 数据库行级加密;
- 单 region 故障如何切换?→ Route53 健康检查 + Aurora Global 自动 failover。

**Q47 [L3]**: 你接到告警:某 EC2 实例正在向矿池通信,如何处置?

**即时响应(15 分钟内)**:
1) 隔离:给实例加隔离 SG(只允许 22 来自堡垒机);
2) 撤销角色:Detach IAM Role,防止横向移动;
3) 快照:EBS 快照用于取证;
4) 内存 dump(若仍在运行):用 AVML / LiME;
5) 通知:安全团队 + 业务方,评估影响。

**调查取证(1-2 小时)**:
1) 分析 CloudTrail:该实例角色最近 7 天 API 调用;
2) 分析 VPC Flow Logs:出站连接目标 IP/域名;
3) 分析进程:ps、netstat、lsof,找挖矿进程;
4) 分析持久化:cron、systemd、SSH authorized_keys;
5) 分析入侵路径:Web 应用日志、最近部署、漏洞扫描历史。

**根除与恢复(4-8 小时)**:
1) 从干净 AMI 重建实例;
2) 轮换该实例接触过的所有密钥;
3) 修复入侵路径漏洞(如升级应用、修复 SSRF);
4) 部署检测规则防类似攻击(GuardDuty + Falco);
5) 复盘:RCA 报告,改进 Playbook。

**追问**:
- 为何不直接关机?→ 关机丢内存证据,无法溯源;
- 矿池通信是否一定被入侵?→ 也可能是合法测试或员工私自部署,需确认。

**Q48 [L3]**: 如何在云上满足等保 2.0 三级要求?

**技术要求对应**:
1) 安全物理环境:云厂商负责(等保云租户责任);
2) 安全通信网络:VPC + 专线 + VPN + TLS 1.2+;
3) 安全区域边界:WAF + IDS + 边界防火墙 + DDoS 防护;
4) 安全计算环境:主机加固 + EDR + 容器安全 + 最小权限;
5) 安全管理中心:SIEM + SOC + 集中审计;
6) 安全管理制度:制度文档 + 人员 + 建设 + 运维。

**落地措施**:
1) 网络:VPC 私有子网 + Bastion + VPN,关键系统不暴露公网;
2) 主机:CIS Benchmark 加固 + AWS Inspector + 漏洞修复 SLA;
3) 身份:SSO + MFA + 最小权限 + 90 天密码轮换;
4) 数据:KMS 加密 + WORM 审计日志 + 备份 3-2-1-1-0;
5) 审计:CloudTrail + Config + 6 个月日志保留 + 不可篡改;
6) 应急:IR Playbook + 季度演练 + 备份恢复测试;
7) 测评:每年第三方测评机构测评。

**追问**: 等保与 SOC2 区别?→ 等保是法规(中国),SOC2 是审计报告(国际),两者可互补。

### 21.7.3 高级行为题

**Q49 [L3]**: 描述一次你处理过的云安全事件。

**结构化回答(STAR)**:
- **S(场景)**: 2024 年 X 月,某生产 AWS 账号 CloudTrail 异常告警,GuardDuty 检测到 IAM 用户在异常 IP 登录;
- **T(任务)**: 1 小时内确认是否入侵,2 小时内完成隔离与评估,24 小时内根除;
- **A(行动)**:
  1) 立即撤销该 IAM 用户密钥;
  2) CloudTrail 分析发现攻击者尝试访问 S3 但被 SCP 阻断;
  3) 排查发现该密钥 2 周前 commit 到 GitHub 公开仓库;
  4) 全账号密钥轮换 + GitHub 历史清理;
  5) 启用 Secret Scanning 防再发生;
- **R(结果)**: 无数据泄露,业务无影响,4 小时恢复;
- **复盘**: 引入 pre-commit gitleaks + GitHub Secret Scanning + IAM 临时凭证。

**Q50 [L3]**: 如何向非技术高管解释云安全投资价值?

**框架**:
1) **风险量化**: Capital One 罚款 1.9 亿美元、滴滴罚款 80 亿,对比安全投资(年薪百万工程师)绝对值小;
2) **业务赋能**: 合规认证(SOC2/ISO 27001)是客户准入条件,无认证丢单;
3) **效率提升**: DevSecOps 自动化降低人工运维 30%;
4) **保险**: 网络安全保险费率与安全成熟度挂钩;
5) **品牌**: 安全事件品牌损失难以量化但巨大(Uber、LastPass)。

**反例**: "花钱买工具不一定有用,但没工具一定出事;事件成本是预防成本的 10 倍。"

## 21.8 常见陷阱与最佳实践

⚠️ **答题陷阱**:

| 陷阱 | 表现 | 改进 |
|------|------|------|
| 概念混淆 | "零信任就是 VPN" | 用 NIST 800-207 定义 |
| 缺乏深度 | 只说"加密" | 说 KMS + 信封加密 + KEK/DEK |
| 忽略权衡 | "全用最安全方案" | 说成本/性能/可用性权衡 |
| 缺乏案例 | 纯理论 | 引 Capital One/SolarWinds |
| 没有故障经验 | 不知道案例 | 至少准备 5 个案例 |
| 不问澄清 | 直接长篇大论 | 先问规模/合规/已有架构 |
| 不画图 | 纯口述 | 画 ASCII 架构图 |
| 时间失控 | 一个题 30 分钟 | 1 题 10-15 分钟 |

✅ **最佳实践**:

- 先问澄清,再答;
- 结构化回答:总-分-总;
- 关键术语用英文(零信任 Zero Trust);
- 设计题画 ASCII 图;
- 案例 + 数据 + 工具名;
- 主动提权衡与限制;
- 反问环节问团队/技术栈/挑战。
