## 一、问题定义

### 1.1 解决什么问题

云原生应用面临的安全痛点：

1. **工具碎片化** — CSPM/CWPP/CIEM/KSPM 各买一个,数据不互通
2. **上下文丢失** — 配置面看不到运行时,运行时看不到权限
3. **告警疲劳** — 同一问题多个工具各报一遍
4. **优先级难定** — 缺乏全局视角
5. **响应缓慢** — 跨工具切换

🔥 **典型场景**：
- CSPM 报 "S3 公开" + CWPP 报 "容器异常访问 S3" → CNAPP 关联:此容器利用公开 S3 数据外泄
- CIEM 报 "IAM Role 过宽" + KSPM 报 "Pod 用此 Role" → CNAPP 优先级 P0

### 1.2 CNAPP 与单一工具的对比

| 维度 | 单一工具组合 | CNAPP |
|------|--------------|-------|
| 部署 | 4-5 个工具 | 1 个平台 |
| 数据孤岛 | 严重 | 统一数据模型 |
| 上下文 | 跨工具查询 | 内部关联 |
| 告警 | 重复 | 去重聚合 |
| 优先级 | 各自评分 | 综合评分 |
| 响应 | 跨工具编排 | 单一工作流 |
| 成本 | 多付费 | 单一付费 (省 30-40%) |

### 1.3 云厂商差异概述

| 概念 | AWS | Azure | GCP | 阿里云 | 华为云 |
|------|-----|-------|-----|--------|--------|
| CNAPP | Security Hub + 多服务 | Defender for Cloud | SCC Premium | 云安全中心 | SecMaster |
| 融合度 | 中 (各服务独立) | 高 (Defender 统一) | 高 (SCC) | 中 | 中 |
| 多云支持 | 仅 AWS | 多云 (Defender) | 仅 GCP | 仅阿里云 | 仅华为云 |
| 第三方 | Wiz/Prisma/Lacework | 同 | 同 | 同 | 同 |

## 三、原理与机制

### 3.1 CNAPP 数据模型

```
   ┌──────────────────────────────────────┐
   │  统一图数据库                          │
   │                                      │
   │  ┌──────┐ 信任关系 ┌──────┐           │
   │  │ IAM  │ ───────► │ S3   │           │
   │  │ Role │           │ Bucket│          │
   │  └──┬───┘           └──┬───┘          │
   │     │ 假设              │ 公开          │
   │     ▼                  ▼              │
   │  ┌──────┐           ┌──────┐          │
   │  │ Pod  │ ──运行──► │ 数据  │          │
   │  └──────┘           └──────┘          │
   │                                      │
   │  + 漏洞 + 配置 + 行为 + 数据分类       │
   └──────────────────────────────────────┘
```

### 3.2 攻击路径 (Attack Path) 分析

```
攻击者视角 (CNAPP 自动推导):

   1. S3 桶公开 (CSPM finding)
      ↓
   2. 桶内有 PII 数据 (DSPM finding)
      ↓
   3. 桶策略允许 ListBucket (CSPM)
      ↓
   4. Lambda 函数能 GetObject (CIEM)
      ↓
   5. Lambda 有公开 URL (CSPM)
      ↓
   6. Lambda 函数有 RCE 漏洞 (CWPP)
      ↓
   7. Lambda Role 可写其他桶 (CIEM)

   → 攻击路径: 公网 → Lambda RCE → 读 PII → 写其他桶
   → 爆炸半径: 全部 PII + 多桶
   → 优先级: P0 (修复 Lambda RCE + 收紧 IAM)
```

### 3.3 Toxic Combination 检测

```
单独看每个 finding 都不严重:
   - S3 公开 (Medium, 因为桶内只有非敏感数据)
   - EC2 有高危 CVE (High, 但内网)
   - IAM Role 跨账号信任 (Medium, 有 ExternalId)

组合后变 P0:
   - 攻击者通过 EC2 CVE 入侵
   - 利用 IAM Role 跨账号
   - 横向到另一账号的 S3 (公开,可下载)

CNAPP 自动发现这种组合
```

### 3.4 优先级算法

$$
Priority = f(Severity, Exposure, BlastRadius, Exploitability, BusinessImpact)
$$

| 维度 | 来源 | 权重 |
|------|------|------|
| Severity | CVSS / CIS | 30% |
| Exposure | 公网暴露 / 内网 | 25% |
| Blast Radius | 数据敏感度 + 资源数 | 20% |
| Exploitability | EPSS + KEV | 15% |
| Business Impact | 业务标签 | 10% |

## 四、算法 / 流程

### 4.1 资源图构建

```
输入: 云账号 + K8s 集群
输出: 资源关系图

1. 拉取所有资源 (云 API + K8s API)
   ├─ IAM (Users/Roles/Policies)
   ├─ 网络 (VPC/SG/NACL/Routes)
   ├─ 计算 (EC2/Pod/Lambda)
   ├─ 存储 (S3/EBS/RDS)
   └─ K8s (ServiceAccount/NetworkPolicy)

2. 构建关系:
   ├─ IAM Role → 资源 (允许动作)
   ├─ Pod → ServiceAccount → IAM Role
   ├─ Security Group → 资源
   ├─ Lambda → 触发器 → 公网 URL
   └─ S3 桶 → 公开访问

3. 标注属性:
   ├─ 漏洞 (Inspector/Trivy)
   ├─ 配置错误 (CIS)
   ├─ 数据分类 (Macie)
   └─ 暴露面 (公网/内网)
```

### 4.2 攻击路径推导

```
1. 从公网入口开始反向 BFS:
   for each public resource:
     for each vulnerable entry:
       traverse (assume role → access resource → ...)
       
2. 每条路径评分:
   length: 路径越短越危险
   severity: 终点资源敏感度
   exploitability: 中间漏洞利用难度

3. 输出 Top N 路径 + 修复建议
```

### 6.2 生产级版（工程）：CNAPP 集成架构

```yaml
# .github/workflows/cnapp-pipeline.yml
name: CNAPP Security Pipeline

on: [push, pull_request]

jobs:
  # ============================================
  # 阶段 1: IaC 扫描 (Shift Left)
  # ============================================
  iac-scan:
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v4
    
    - name: Wiz IaC Scan
      env:
        WIZ_CLIENT_ID: ${{ secrets.WIZ_CLIENT_ID }}
        WIZ_CLIENT_SECRET: ${{ secrets.WIZ_CLIENT_SECRET }}
      run: |
        # 严重问题阻断合并
        wiz iac scan \
          --path ./terraform/ \
          --output sarif \
          --policy "Production Baseline" \
          --fail-on severity=CRITICAL,HIGH
    
    - uses: github/codeql-action/upload-sarif@v3
      with:
        sarif_file: results.sarif
  
  # ============================================
  # 阶段 2: 镜像扫描 + SBOM
  # ============================================
  image-scan:
    needs: iac-scan
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v4
    
    - uses: docker/build-push-action@v5
      with:
        context: .
        tags: myapp:${{ github.sha }}
        load: true
    
    - name: Wiz Image Scan
      run: |
        wiz docker scan \
          --image myapp:${{ github.sha }} \
          --output sarif \
          --policy "Container Security" \
          --fail-on severity=CRITICAL
    
    # 上传 SBOM 到 Wiz (供运行时关联)
    - name: Generate & Upload SBOM
      run: |
        syft myapp:${{ github.sha }} -o spdx-json > sbom.spdx.json
        wiz sbom upload --path sbom.spdx.json
  
  # ============================================
  # 阶段 3: 部署到 K8s
  # ============================================
  deploy:
    needs: image-scan
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v4
    
    - name: Deploy to K8s
      run: |
        kubectl set image deployment/myapp \
          myapp=ghcr.io/myorg/myapp@${{ github.sha }}
    
    # 通知 CNAPP 工作负载变更
    - name: Notify CNAPP
      run: |
        curl -X POST https://api.wiz.io/v1/workload-events \
          -H "Authorization: Bearer ${{ secrets.WIZ_TOKEN }}" \
          -d "{
            \"workload\": \"myapp\",
            \"version\": \"${{ github.sha }}\",
            \"environment\": \"production\"
          }"
```

```python
# tools/cnapp_attack_path.py
"""从 CNAPP 拉取攻击路径并自动响应"""
import boto3
import requests
from typing import List, Dict

class CNAPPClient:
    def __init__(self, api_url: str, token: str):
        self.api = api_url
        self.headers = {"Authorization": f"Bearer {token}"}
    
    def get_attack_paths(self, severity: str = "CRITICAL") -> List[Dict]:
        """获取攻击路径"""
        r = requests.get(
            f"{self.api}/v1/attack-paths",
            headers=self.headers,
            params={"min_severity": severity}
        )
        return r.json()['attack_paths']
    
    def auto_remediate(self, path: Dict):
        """根据攻击路径自动响应"""
        # 1. 切断攻击链中最弱环节
        weakest = self._find_weakest_link(path)
        
        if weakest['type'] == 'public_resource':
            self._close_public_access(weakest['resource'])
        elif weakest['type'] == 'overly_permissive_iam':
            self._tighten_iam(weakest['role'])
        elif weakest['type'] == 'vulnerable_workload':
            self._isolate_workload(weakest['workload'])
    
    def _find_weakest_link(self, path: Dict) -> Dict:
        """找最易修复的环节 (低成本高收益)"""
        for node in path['nodes']:
            if node.get('auto_fixable'):
                return node
        return path['nodes'][-1]  # 默认终点
    
    def _close_public_access(self, resource: str):
        """关闭资源公开访问"""
        if resource.startswith('arn:aws:s3'):
            bucket = resource.split(':')[-1]
            s3 = boto3.client('s3')
            s3.put_public_access_block(
                Bucket=bucket,
                PublicAccessBlockConfiguration={
                    'BlockPublicAcls': True,
                    'BlockPublicPolicy': True,
                    'IgnorePublicAcls': True,
                    'RestrictPublicBuckets': True
                }
            )
            print(f"✓ 关闭 S3 桶公开: {bucket}")
    
    def _tighten_iam(self, role_arn: str):
        """收紧 IAM Role 权限"""
        # 推荐: 基于 CloudTrail 历史生成最小权限策略
        iam = boto3.client('iam')
        role_name = role_arn.split('/')[-1]
        
        # 拉取 CNAPP 推荐策略
        rec = requests.get(
            f"{self.api}/v1/iam-recommendations",
            headers=self.headers,
            params={'role': role_arn}
        ).json()
        
        # 创建新策略版本
        iam.put_role_policy(
            RoleName=role_name,
            PolicyName='least-privilege-recommended',
            PolicyDocument=rec['recommended_policy']
        )
        print(f"✓ 收紧 IAM Role: {role_name}")
    
    def _isolate_workload(self, workload: Dict):
        """隔离工作负载"""
        if workload['type'] == 'pod':
            # 修改 NetworkPolicy 阻断所有流量
            ...
        elif workload['type'] == 'ec2':
            # 应用隔离 SG
            ec2 = boto3.client('ec2')
            ec2.modify_instance_attribute(
                InstanceId=workload['id'],
                Groups=['sg-isolation']
            )
```

## 十、综合面试题

1. **设计一个生产级 CNAPP 架构。**
   - 要点:统一图数据库;CSPM+CWPP+CIEM+KSPM+DSPM 融合;攻击路径分析;Shift Left CI 集成;P0 自动响应;SIEM/SOAR 集成;多云视图。

2. **CNAPP 如何发现攻击路径?**
   - 要点:资源关系图;反向 BFS 从公网入口;考虑漏洞+配置+IAM+暴露面;输出最短路径 + 修复建议。

3. **解释 Toxic Combination 并举例。**
   - 要点:多个低危组合成高危;如公开 S3 + 内部 EC2 CVE + IAM 跨账号 = 全账号沦陷;CNAPP 自动发现这种组合。

4. **Agentless vs Agent 在 CNAPP 中的角色?**
   - 要点:Agentless 用于扫描 (镜像/配置/快照);Agent 用于运行时 (行为/syscall);CNAPP 应同时支持两者。

5. **如何评估 CNAPP 厂商?**
   - 要点:5 大模块 (CSPM/CWPP/CIEM/KSPM/DSPM);攻击路径准确性;多云支持;CI/CD 集成;SIEM/SOAR 集成;性价比。

6. **CNAPP 与 SIEM 的边界?**
   - 要点:CNAPP 聚焦云原生 + 配置/权限/工作负载;SIEM 全企业 + 日志聚合/分析;CNAPP finding 入 SIEM 做关联。

7. **如何处理 CNAPP 海量 finding?**
   - 要点:攻击路径优先;Toxic Combination 高亮;EPSS + 业务影响评分;自动修复减量;例外白名单审批。

8. **DSPM 如何提升 CNAPP 价值?**
   - 要点:数据分类 (PII/PHI/PCI) 标注;敏感数据驱动的优先级;数据访问路径分析;数据泄露风险评估。

9. **CNAPP 在多云场景的挑战?**
   - 要点:各家 API 不一致;策略映射复杂;权限模型差异;统一规则需抽象 (OPA);成本高。

10. **如何实现 CNAPP 的自动响应?**
    - 要点:Webhook + Lambda/Function;按 finding 类型分流 (SG 收紧/IAM 限缩/Pod 隔离);dry-run 模式;回滚机制。
