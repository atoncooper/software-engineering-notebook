## 一 问题定义

### 1.1 业务痛点

1. **依赖深**：现代应用平均依赖 500-1000 个传递依赖，单个漏洞影响整个供应链。
2. **维护者质量参差**：开源维护者多为志愿者，被收买或胁迫风险（xz-utils 事件）。
3. **构建管道高权限**：CI 凭证可访问生产环境，被攻破即失守（Codecov、CircleCI）。
4. **镜像来源不明**：Docker Hub 公开镜像可能被植入后门，拉取即风险。
5. **签名缺失**：大多数开源包无签名，篡改难被发现。

### 1.2 供应链攻击类型

| 攻击类型 | 描述 | 案例 |
|---------|------|------|
| 源代码入侵 | 攻击者直接改源码 | PHP git 服务器入侵（2021） |
| 构建管道入侵 | 攻击 CI 注入恶意代码 | SolarWinds（2020） |
| 依赖混淆 | 内部包名被外部抢注 | 2021 多家公司受影响 |
| Typosquatting | 仿冒流行包名 | npm 的 "crossenv" vs "cross-env" |
| 短包名抢注 | 维护者放弃后被人接管 | event-stream（2018） |
| 恶意 PR | 社工维护者合入恶意代码 | 多个开源项目 |
| 镜像篡改 | 注册表账号被盗改镜像 | Docker Hub（2019） |
| 凭证窃取 | CI 上传器被植入后门 | Codecov（2021） |
| 编译工具投毒 | 编译器插入后门 | xz-utils（2024） |
| 字体/CSS 投毒 | 通过第三方资源加载 | Mixpanel 仿冒（2023） |

### 1.3 反模式

- ❌ 直接从 npm/PyPI 拉包，无内部代理。
- ❌ 不锁定版本，使用 `latest` 标签。
- ❌ Dockerfile 用 `FROM python:latest`，每次构建可能不同。
- ❌ 不验证镜像签名，直接 `docker pull`。
- ❌ CI 凭证长期有效，无 OIDC。
- ❌ 不生成 SBOM，安全团队不知道用了什么。
- ❌ 不监控依赖变更，新依赖未审就合入。

## 三 原理与机制

### 3.1 SLSA 框架 🎓

**SLSA（Supply-chain Levels for Software Artifacts）** 4 级成熟度：

| 级别 | 要求 | 描述 |
|------|------|------|
| L1 | Build Provenance | 构建过程文档化（出处可追溯） |
| L2 | Hosted Build Service | 使用托管构建服务（如 GitHub Actions），有签名 provenance |
| L3 | Hardened Build Platform | 构建平台隔离（不可篡改），provenance 完整 |
| L4 | Reproducible / Two-Party Review | 可复现构建 + 两人审核 |

**SLSA Provenance 结构**：

```json
{
  "_type": "https://in-toto.io/Statement/v0.1",
  "subject": [{
    "name": "ghcr.io/my-org/app:v1.2.3",
    "digest": {"sha256": "abc123..."}
  }],
  "predicateType": "https://slsa.dev/provenance/v0.2",
  "predicate": {
    "builder": {"id": "https://github.com/actions/runner/github-hosted"},
    "buildType": "https://github.com/actions/runner/github-hosted",
    "invocation": {
      "configSource": {
        "uri": "git+https://github.com/my-org/app",
        "digest": {"sha1": "def456..."},
        "entryPoint": ".github/workflows/build.yml"
      }
    },
    "buildConfig": {...},
    "metadata": {
      "buildStartedOn": "2026-07-04T10:00:00Z",
      "buildFinishedOn": "2026-07-04T10:05:00Z",
      "completeness": {
        "parameters": true,
        "environment": true,
        "materials": true
      },
      "reproducible": false
    },
    "materials": [{
      "uri": "git+https://github.com/my-org/app",
      "digest": {"sha1": "def456..."}
    }]
  }
}
```

### 3.2 Sigstore 体系 🎓

**Sigstore 三组件**：

1. **Cosign**：签名工具，对制品（OCI 镜像、二进制）签名。
2. **Fulcio**：短期证书 CA，基于 OIDC 身份签发证书（10 分钟有效）。
3. **Rekor**：透明日志，所有签名记录到不可篡改的 Merkle 树日志。

**Keyless 签名流程**：

```
1. CI 触发构建（GitHub Actions）
2. 构建完成，生成镜像 digest
3. Cosign 向 Fulcio 提供 OIDC token（证明身份是 GitHub Actions）
4. Fulcio 签发短期证书（CN=workflow@github-actions，10 分钟有效）
5. Cosign 用证书私钥签名镜像 digest
6. Cosign 将签名 + 证书上传到 Rekor
7. Rekor 写入 Merkle 树日志，返回 EntryHash
8. Cosign 销毁私钥

验证流程：
1. 用户拉取镜像
2. cosign verify --certificate-identity=workflow@github-actions
3. 从 Rekor 查找签名 entry
4. 验证证书链 + 签名 + 镜像 digest
5. 验证通过 = 镜像确实由该 workflow 构建
```

**关键特性**：
- 短期证书（10 分钟），无长期密钥管理。
- 透明日志，所有签名公开可查，篡改即被发现。
- Keyless 模式，无需管理签名密钥。

### 3.4 依赖混淆攻击 🎓

**攻击原理**：

1. 公司内部包名 `@mycompany/internal-lib`，仅在内网 registry。
2. 攻击者侦察到内部包名（GitHub 搜索、社工）。
3. 攻击者在公开 npm 注册同名包 `@mycompany/internal-lib`，恶意代码。
4. CI 构建时，包管理器优先解析公开 registry（npm 默认），拉到恶意包。
5. 恶意代码执行，窃取 CI 凭证。

**防御**：
- 内部 registry 优先（`.npmrc` 配置）。
- 包名加前缀（`@mycompany-internal-xxx`），公开 registry 不允许同名。
- 仓库代理（Artifactory / Nexus）控制可见性。

### 3.5 xz-utils 后门分析 🎓

**事件时间线**：

```
2021: 攻击者 "Jia Tan" 加入 xz-utils 项目，逐步贡献
2022-2023: Jia Tan 成为 maintainer
2024-02: Jia Tan 在 xz 5.6.0/5.6.1 引入后门（通过 m4/build-to-host.m4 隐藏）
2024-03: 后门被 Microsoft 工程师 Andres Freund 发现（SSH 性能调试时）
2024-03-29: 演变为 CVE-2024-3094，CVSS 10.0
```

**后门机制**：
- 构建时检测 `IFUNC`（GNU 间接函数）支持。
- 在 liblzma 中嵌入恶意代码，hook 到 sshd 的 `RSA_public_decrypt`。
- 攻击者发送特定 payload 到 SSH 端口，触发 RCE。

**启示**：
- 单一维护者项目高风险（项目维护者可被收买）。
- 构建脚本审计重要（m4/build-to-host.m4 是构建时注入）。
- 性能变化可能指示后门（Freund 发现是因 SSH 性能下降 500ms）。

## 四 算法/流程

### 4.1 SBOM 生成与扫描流水线

```
function SBOM_PIPELINE(repo, ref):
    # 1. 生成 SBOM
    sbom = syft.generate(repo, format="cyclonedx-json")
    
    # 2. 漏洞扫描
    vulnerabilities = grype.scan(sbom)
    
    # 3. 许可证扫描
    licenses = syft.scan_licenses(sbom)
    license_violations = [l for l in licenses if l not in APPROVED_LICENSES]
    
    # 4. 维护者活跃度（OpenSSF Scorecard）
    scorecard = openssf.scorecard(repo)
    
    # 5. 上传到 Dependency-Track
    dtrack.upload_sbom(sbom, project=repo)
    
    # 6. 阻断决策
    critical_vulns = [v for v in vulnerabilities if v.severity == "Critical"]
    if critical_vulns and not v.fixed_in:
        return "BLOCK: unfixed critical vulnerability"
    
    if license_violations:
        return "BLOCK: license violation"
    
    if scorecard.score < 4:
        warn("Low OpenSSF score")
    
    return "PASS"
```

### 4.2 镜像签名验证流程

```
function VERIFY_IMAGE(image_ref, expected_identity):
    # 1. 获取镜像 digest
    digest = registry.get_digest(image_ref)
    
    # 2. 从 Rekor 查找签名
    signatures = cosign.lookup_signatures(digest)
    
    if not signatures:
        return "FAIL: no signature"
    
    # 3. 验证证书身份
    for sig in signatures:
        cert = sig.cert
        if not cert.matches_identity(expected_identity):
            continue
        
        # 4. 验证签名
        if not cosign.verify_signature(sig, digest):
            continue
        
        # 5. 验证 Rekor 包含
        if not rekor.contains(sig.entry_hash):
            continue
        
        # 6. 验证 provenance
        provenance = sig.attestations["provenance"]
        if provenance.builder.id == "github-actions":
            if provenance.repository == expected_identity.repository:
                return "PASS"
    
    return "FAIL: no valid signature"
```

function DEPENDENCY_CONFUSION_CHECK(package_json):

### 4.4 Reproducible Build 验证

```
function REPRODUCIBLE_BUILD_VERIFY(source_commit, build_spec):
    # 1. 第一次构建
    build1 = build(source_commit, build_spec)
    digest1 = sha256(build1.artifact)
    
    # 2. 第二次构建（不同时间、不同机器）
    build2 = build(source_commit, build_spec)
    digest2 = sha256(build2.artifact)
    
    # 3. 对比 digest
    if digest1 == digest2:
        return "REPRODUCIBLE"
    else:
        # 分析差异（时间戳、随机数、路径）
        diff = analyze_diff(build1, build2)
        return "NON-REPRODUCIBLE: " + diff
```

### 6.2 生产级 GitHub Actions：完整供应链流水线

```yaml
# .github/workflows/supply-chain.yml
name: Supply Chain Security

on:
  push:
    branches: [main]
  pull_request:

permissions:
  contents: read
  packages: write
  id-token: write  # OIDC for Cosign keyless
  security-events: write

jobs:
  # 1. SBOM 生成
  sbom:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Generate SBOM
        uses: anchore/sbom-action@v0
        with:
          format: cyclonedx-json
          output-file: sbom.cdx.json
          upload-artifact: true
          upload-sbom: true
      
      - name: Scan for vulnerabilities
        uses: anchore/scan-action@v3
        with:
          sbom: sbom.cdx.json
          fail-build: true
          severity-cutoff: high
          output-format: sarif
      
      - name: Upload to GitHub Code Scanning
        uses: github/codeql-action/upload-sarif@v3
        with:
          sarif_file: results.sarif

  # 2. 依赖混淆检测
  dep-confusion:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Check for internal packages in public registry
        run: |
          for pkg in $(jq -r '.dependencies | keys[]' package.json | grep "^@mycompany"); do
            if npm view "$pkg" version 2>/dev/null; then
              echo "::error::Internal package $pkg found in public registry!"
              exit 1
            fi
          done

  # 3. 构建镜像
  build:
    needs: [sbom, dep-confusion]
    runs-on: ubuntu-latest
    outputs:
      image-digest: ${{ steps.build.outputs.digest }}
    steps:
      - uses: actions/checkout@v4
      
      - name: Set up BuildKit
        uses: docker/setup-buildx-action@v3
      
      - name: Login to GHCR
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      
      - name: Build image
        id: build
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: ghcr.io/${{ github.repository }}:${{ github.sha }}
          labels: |
            org.opencontainers.image.source=${{ github.event.repository.html_url }}
            org.opencontainers.image.revision=${{ github.sha }}
          provenance: true
          sbom: true

  # 4. 签名镜像
  sign:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      
      - name: Install Cosign
        uses: sigstore/cosign-installer@v3
      
      - name: Keyless signing
        run: |
          cosign sign --yes \
            --certificate-identity "https://github.com/${{ github.repository }}/.github/workflows/supply-chain.yml@refs/heads/${{ github.ref_name }}" \
            --certificate-oidc-issuer "https://token.actions.githubusercontent.com" \
            ghcr.io/${{ github.repository }}@${{ needs.build.outputs.image-digest }}
      
      - name: Attest SBOM
        run: |
          cosign attest --yes \
            --predicate sbom.cdx.json \
            --type cyclonedx \
            ghcr.io/${{ github.repository }}@${{ needs.build.outputs.image-digest }}

  # 5. 部署前验证
  verify:
    needs: sign
    runs-on: ubuntu-latest
    steps:
      - name: Verify signature
        run: |
          cosign verify \
            --certificate-identity "https://github.com/${{ github.repository }}/.github/workflows/supply-chain.yml@refs/heads/${{ github.ref_name }}" \
            --certificate-oidc-issuer "https://token.actions.githubusercontent.com" \
            ghcr.io/${{ github.repository }}@${{ needs.build.outputs.image-digest }}
      
      - name: Verify SBOM attestation
        run: |
          cosign verify-attestation \
            --type cyclonedx \
            --certificate-identity "https://github.com/${{ github.repository }}/.github/workflows/supply-chain.yml@refs/heads/${{ github.ref_name }}" \
            --certificate-oidc-issuer "https://token.actions.githubusercontent.com" \
            ghcr.io/${{ github.repository }}@${{ needs.build.outputs.image-digest }}

  # 6. OpenSSF Scorecard
  scorecard:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: OpenSSF Scorecard
        uses: ossf/scorecard-action@v2
        with:
          results_file: results.sarif
          results_format: sarif
          publish_results: true
      - name: Upload to Code Scanning
        uses: github/codeql-action/upload-sarif@v3
        with:
          sarif_file: results.sarif
```

## 七 常见陷阱与最佳实践

### 7.1 陷阱表 ⚠️

| 陷阱 | 描述 | 后果 | 规避 |
|------|------|------|------|
| 用 latest 标签 | 镜像每次拉取可能不同 | 不可复现 | 锁定版本 + digest |
| 不锁依赖 | package.json 用 ^/~ | 不同构建可能不同版本 | lockfile + lockfile-only |
| 公开 registry 优先 | npm 默认公开 | 依赖混淆 | 内部 registry 优先 |
| 不验证镜像签名 | 直接 docker pull | 拉到篡改镜像 | Cosign 验证 |
| CI 凭证长期 | 长期 AK/SK | 泄露窗口长 | OIDC + 短期凭证 |
| 不生成 SBOM | 不知道用了什么 | 漏洞盲点 | 强制 SBOM 生成 |
| 不审核新依赖 | 直接合入 | 引入恶意包 | PR 模板要求审 |
| 单一维护者依赖 | 维护者可被收买 | xz-utils 模式 | 评估维护者健康度 |
| 不监控依赖变更 | 自动 PR 合入 | 恶意更新混入 | Renovate 不自动合 |
| 不审计构建脚本 | m4/build-to-host.m4 隐藏后门 | 构建时注入 | 构建脚本审计 |

### 7.2 最佳实践

1. **SBOM 强制生成**：每个制品必须附 SBOM（CycloneDX/SPDX），上传到 Dependency-Track。
2. **签名强制**：所有镜像用 Cosign Keyless 签名，部署前 Kyverno 验证。
3. **SLSA L3 目标**：托管构建服务 + 平台隔离 + 完整 provenance。
4. **内部 registry 优先**：Artifactory / Nexus 代理公开 registry，避免依赖混淆。
5. **锁文件强制**：package-lock.json / yarn.lock / poetry.lock 提交到仓库。
6. **Renovate 自动化**：自动 PR 升级依赖，安全更新优先合入。
7. **OpenSSF Scorecard**：评估开源依赖健康度，< 4 分告警。
8. **维护者审核**：新维护者加入需 2 人审，敏感操作 2FA。
9. **构建脚本审计**：CI 配置、Dockerfile、Makefile、m4 脚本定期审计。
10. **Reproducible Build**：目标可复现构建，digest 一致验证。

## 九 面试速答 ⭐

**Q1：SLSA 是什么？4 级怎么分？**
Supply-chain Levels for Software Artifacts。L1: Build Provenance 文档化；L2: Hosted Build Service 托管构建；L3: Hardened Build Platform 隔离平台；L4: Reproducible + Two-Party Review 可复现+两人审。

**Q2：Sigstore 三组件？**
Cosign（签名工具）+ Fulcio（短期证书 CA，基于 OIDC）+ Rekor（透明日志，不可篡改）。Keyless 模式无需管理签名密钥，证书 10 分钟有效。

**Q3：依赖混淆攻击？**
内部包名被外部抢注。CI 构建时公开 registry 优先，拉到恶意包。防御：内部 registry 优先（.npmrc）+ 包名加前缀 + Artifactory 代理。

**Q4：xz-utils 后门？**
2024 年 CVE-2024-3094，攻击者 Jia Tan 长期渗透 xz-utils 维护者，在 5.6.0/5.6.1 通过 m4 构建脚本注入后门，hook sshd。被 Microsoft 工程师因 SSH 性能下降 500ms 发现。启示：单一维护者项目高风险，构建脚本审计重要。

**Q5：SBOM 是什么？为什么重要？**
Software Bill of Materials，软件物料清单。完整记录所有直接 + 传递依赖。用于漏洞管理（Log4Shell 时快速定位）、合规（EO 14028 强制）、许可证审计。

**Q6：Cosign Keyless 签名流程？**
1) CI 提供 OIDC token；2) Fulcio 验证 token 签发短期证书；3) Cosign 用证书私钥签名镜像 digest；4) 签名 + 证书上传 Rekor；5) 销毁私钥。验证时从 Rekor 查找签名，验证证书链 + 签名。

**Q7：SolarWinds 攻击怎么发生的？**
2020 年攻击者入侵 SolarWinds 构建系统，在 Orion 软件更新包中植入 SUNSPUR 后门。18000 客户安装了被污染的更新。启示：构建管道高权限 + 签名验证缺失 + 透明日志缺失。

**Q8：Reproducible Build 为什么重要？**
同一源码 + 同一构建环境 = 相同二进制 digest。可验证构建过程未被篡改。SLSA L4 要求。GCC、Debian 等已支持。难点：时间戳、随机数、路径需消除。

**Q9：OpenSSF Scorecard 评估哪些维度？**
分支保护、代码审查、维护者活跃度、CI 测试、签名发布、依赖更新、模糊测试、二进制文件、安全策略、漏洞历史等。10 分制，< 4 分告警。

**Q10：Codecov 事件启示？**
2021 年 Codecov bash 上传器被植入后门 2 个月，收集 CI 环境变量 token。启示：1) 第三方脚本要校验签名 + hash；2) CI 凭证短期化（OIDC）；3) 监控 CI 出站流量。

## 十 综合面试题

1. **设计题**：金融 SaaS 公司如何实现 SLSA L3？
   要点：1) GitHub Actions 托管构建（L2）；2) Self-hosted runner 隔离（L3）；3) OIDC + 短期凭证，无长期 secret；4) 强制 SBOM 生成（Syft）；5) Cosign Keyless 签名；6) in-toto provenance 完整记录；7) Kyverno 部署前验证；8) Reproducible Build 目标。

2. **场景题**：发现某个 npm 依赖被植入恶意代码，已经上线，怎么响应？
   要点：1) 立即定位使用该包的应用（SBOM 查询）；2) 紧急回滚到上一版本；3) 检查 CI 是否泄露凭证（被植入代码可能收集 env）；4) rotate CI 凭证；5) 通知下游客户；6) 上游 npm 报告 yank；7) 复盘：依赖审核流程改进。

3. **原理题**：Cosign Keyless 和传统 KMS 签名区别？
   要点：1) Keyless：OIDC 身份 → 短期证书（10 分钟）→ 签名 → 销毁私钥；KMS：长期密钥托管在 KMS。2) Keyless 无密钥管理负担；KMS 需轮转、权限控制。3) Keyless 透明日志强制；KMS 可选。4) Keyless 适合 CI；KMS 适合生产部署。

4. **场景题**：内部包名 `@mycompany/internal-lib` 被 npm 公开抢注，CI 拉到恶意包，怎么处理？
   要点：1) 立即禁用 CI；2) 检查 CI 是否被植入后门（恶意代码可能下载更多恶意包）；3) rotate 所有 CI 凭证；4) 配置 .npmrc 内部 registry 优先；5) Artifactory 代理公开 registry；6) 公开 npm 报告抢注；7) 复盘：依赖来源验证。

5. **设计题**：开源项目如何提升供应链安全？
   要点：1) OpenSSF Scorecard 评估；2) 启用分支保护（强制 PR + 2 审）；3) Renovate 自动更新依赖；4) SBOM 生成（GitHub native）；5) Cosign 签名 release；6) Provenance 发布；7) 维护者 2FA 强制；8) SECURITY.md 公开漏洞披露流程。

6. **对比题**：SPDX 和 CycloneDX 怎么选？
   要点：1) SPDX：ISO 标准，合规/许可证为主，企业/政府；2) CycloneDX：OWASP，安全/漏洞为主，开发者；3) 工具都支持双格式（Syft/Trivy）；4) 漏洞管理选 CycloneDX（VEX 字段强）；5) 合规审计选 SPDX。

7. **场景题**：Docker Hub 公开镜像被篡改，拉到后门镜像，怎么发现？
   要点：1) 镜像签名验证（Cosign）；2) SBOM 对比（预期 vs 实际）；3) Trivy 漏洞 + 后门扫描；4) Falco 运行时检测异常行为；5) 私有 registry 代理（Artifactory）只缓存已知 digest；6) digest 锁定（K8s deployment 用 sha256 而非 tag）。

8. **原理题**：Rekor 透明日志怎么防篡改？
   要点：1) Merkle 树日志，每个 entry 包含前一个 hash；2) 任何修改破坏树结构；3) 多方监控（监视 witness），独立验证；4) 树根发布到公开位置（如区块链、GitHub）；5) 攻击者需同时改所有副本，难度极高。

9. **设计题**：K8s 集群如何强制只允许已签名镜像？
   要点：1) Kyverno verifyImages 策略；2) 限定镜像来源（ghcr.io/my-org/*）；3) 验证 Cosign 签名 + Rekor entry；4) 验证 SLSA provenance attestation；5) admission webhook 拦截未签名镜像；6) 异常告警 Security Hub。

10. **原理题**：可复现构建（Reproducible Build）为什么难？
    要点：1) 时间戳：构建时间嵌入二进制；2) 随机数：UUID、临时文件名；3) 文件路径：构建目录差异；4) 顺序：并行构建非确定；5) 编译器版本：不同版本输出不同。需用 SOURCE_DATE_EPOCH、确定性构建工具。
