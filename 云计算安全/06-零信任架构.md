## 一、问题定义

### 1.1 解决什么问题

传统"城堡式"安全模型失效：

```
传统模型:
   外网不可信 ────► 防火墙 ────► 内网全可信
                              ↑
                         一旦攻破,横向移动无阻

零信任模型:
   任何位置 ────► 持续验证 ────► 单次访问授权
   (无内网外网之分,基于身份+上下文)
```

🔥 **典型事故**：
- SolarWinds 2020：攻击者拿到内部 SAML Token 后，在"可信内网"横向移动 9 个月未被发现
- Capital One 2019：内网 EC2 通过元数据服务拿到 IAM 凭证后访问 S3
- Target 2013：HV 供应商 VPN 入侵后横向到 POS 系统

### 1.2 与传统边界的差异

| 维度 | 传统边界 | 零信任 |
|------|----------|--------|
| 信任基础 | 网络 (内/外) | 身份 + 上下文 |
| 验证频次 | 一次 (登录) | 每次请求 |
| 授权粒度 | 网段 | 应用/动作/资源 |
| 默认状态 | 内网默认允许 | 默认拒绝 |
| 网络位置 | 决定信任 | 仅是上下文之一 |
| 加密 | 边界加密 | 全程加密 (mTLS) |
| 取证 | 网络日志 | 身份 + 应用日志 |

### 1.3 云厂商差异概述

| 概念 | AWS | Azure | GCP | 阿里云 | 华为云 |
|------|-----|-------|-----|--------|--------|
| BeyondCorp 类似 | Verified Access | Entra Private Access | BeyondCorp Enterprise | 云访问安全 CASB | CloudTrust Access |
| ZTNA | Client VPN + Verified Access | Entra Global Secure Access | IAP | 云堡垒机 + CBH | CBC |
| 设备姿态 | Inspector + Jamf | Intune | Endpoint Verification | 终端管理 | MDM |
| 微分段 | SG + NetworkPolicy | NSG + Azure Firewall | VPC Service Controls | 安全组 | 安全组 |
| mTLS | App Mesh | Service Mesh | Anthos Service Mesh | ASM | CCE Service Mesh |

## 三、原理与机制

### 3.1 NIST SP 800-207 七项原则 📜

1. **所有数据源和计算服务都是资源** — 包括数据库、API、容器、SaaS
2. **所有通信都加密** — 不论网络位置
3. **资源访问授权基于会话** — 不是长期信任
4. **访问基于动态策略** — 身份 + 设备 + 上下文 + 行为
5. **资产完整性和安全状态监控** — 持续评估
6. **所有资源认证和授权动态严格** — 每次访问都验证
7. **收集尽量多信息改善安全态势** — 持续优化

### 3.2 零信任核心组件 (PE/PA/PEP)

```
   用户/设备 (Subject)
       │
       │ 1. 访问请求
       ▼
   ┌─────────┐
   │   PEP   │  ← 策略执行点 (代理/网关)
   │  (代理) │
   └────┬────┘
        │ 2. 查询策略
        ▼
   ┌─────────┐    ┌─────────┐
   │   PA    │ ◄─►│   PE    │  ← 策略管理员 / 引擎
   └────┬────┘    └────┬────┘
        │               │
        │ 4. 决策       │ 3. 输入
        ▼               ▼
   ┌─────────────────────────────┐
   │  上下文:                     │
   │  ├─ 身份 (IdP)               │
   │  ├─ 设备姿态 (MDM)           │
   │  ├─ 位置 (IP/Geo)            │
   │  ├─ 时间                     │
   │  ├─ 行为分析 (UEBA)          │
   │  └─ 威胁情报                  │
   └─────────────────────────────┘
        │
        ▼ 5. 允许/拒绝 + 短期 Token
   ┌─────────┐
   │   PEP   │
   └────┬────┘
        │ 6. 转发请求 (短 Token)
        ▼
   资源 (Application/Service)
```

### 3.3 信任算法 (Trust Algorithm)

🎓 **形式化定义**：
$$
Trust = f(Identity, Device, Context, Behavior, ThreatIntel)
$$

$$
Allow(s, r, a) \iff Trust(s, r, t) \geq Threshold(r, a)
$$

其中：
- $s$ = subject (主体)
- $r$ = resource (资源)
- $a$ = action (动作)
- $t$ = time (时间)
- $Threshold$ = 资源敏感度对应的阈值

🔥 **关键**：信任是动态的，会随上下文变化。同一用户从受管设备 + 公司网络访问 vs 个人设备 + 公共 WiFi，信任分不同。

### 3.4 SDP vs VPN

| 维度 | 传统 VPN | SDP |
|------|----------|-----|
| 暴露面 | 整个内网 | 单应用 |
| 验证 | 一次登录 | 每次请求 |
| 网络层 | L3 | L7 (应用层) |
| 客户端 | VPN client | SDP client / 浏览器 |
| 默认状态 | 连接后允许 | 默认拒绝 |
| 横向移动 | 可在内网移动 | 仅能访问授权应用 |

### 3.5 微分段

```
传统网络分段:
   VLAN 1 (办公) ────► VLAN 2 (生产)
   (网段级隔离,网段内全通)

微分段:
   ┌─────────────────────────────────┐
   │  VLAN 1 (办公)                   │
   │  ┌────────┐  ┌────────┐         │
   │  │ 员工 A  │  │ 员工 B  │  互不通信│
   │  └────────┘  └────────┘         │
   └─────────────────────────────────┘
   (基于身份/应用级隔离)
```

## 四、算法 / 流程

### 4.1 BeyondCorp 访问流程

```
1. 用户登录 (浏览器)
   ↓
2. IdP (Google) 认证 + MFA
   ↓
3. 设备证书 + 姿态检查 (公司管理 vs BYOD)
   ↓
4. Access Proxy 接收请求
   ↓
5. 信任算法评估 (身份 + 设备 + 上下文)
   ↓
6. 短期 Token (15-60 min)
   ↓
7. 转发到后端应用 (mTLS)
   ↓
8. 持续监控 (异常行为触发重新认证)
```

### 4.2 Service Mesh mTLS 模型

```
   Pod A                Pod B
     │                    │
     ▼                    ▼
   ┌─────────┐         ┌─────────┐
   │ Sidecar │ ◄─mTLS─►│ Sidecar │
   │ (Envoy) │         │ (Envoy) │
   └─────────┘         └─────────┘
     │                    │
     │ 明文                │ 明文
     ▼                    ▼
   App A                App B

证书: SPIFFE ID,自动轮换 (cert-manager)
策略: AuthorizationPolicy (L7)
```

```yaml
apiVersion: security.istio.io/v1beta1

  namespace: production

  {}   # 空 spec = 拒绝所有

apiVersion: security.istio.io/v1beta1
kind: AuthorizationPolicy
metadata:
  name: allow-frontend-to-backend
  namespace: production
spec:
  selector:
    matchLabels:
      app: backend
  action: ALLOW
  rules:
  - from:
    - source:
        principals: ["cluster.local/ns/production/sa/frontend-sa"]
    to:
    - operation:
        methods: ["GET", "POST"]
        paths: ["/api/*"]
    when:
    - key: request.headers[x-api-key]
      values: ["*"]   # 必须有 API key header
---
# ============================================
# 3. RequestAuthentication (JWT)
# ============================================
apiVersion: security.istio.io/v1beta1
kind: RequestAuthentication
metadata:
  name: jwt-auth
  namespace: production
spec:
  selector:
    matchLabels:
      app: backend
  jwtRules:
  - issuer: "https://idp.example.com"
    jwksUri: "https://idp.example.com/.well-known/jwks.json"
    forwardOriginalToken: false
    outputPayloadToHeader: "x-jwt-payload"
---
# ============================================
# 4. SPIFFE 身份 (Service Identity)
# ============================================
apiVersion: v1
kind: ServiceAccount
metadata:
  name: backend-sa
  namespace: production
  annotations:
    # SPIFFE ID 自动生成: spiffe://cluster.local/ns/production/sa/backend-sa
---
# ============================================
# 5. 持续验证: OPA 策略 (基于设备姿态)
# ============================================
apiVersion: templates.gatekeeper.sh/v1beta1
kind: ConstraintTemplate
metadata:
  name: k8srequiredeviceposture
spec:
  crd:
    spec:
      names:
        kind: K8sRequireDevicePosture
  targets:
  - target: admission.k8s.gatekeeper.sh
    rego: |
      package k8srequiredeviceposture
      
      violation[{"msg": msg}] {
        input.review.object.metadata.annotations["device-posture"] != "compliant"
        msg := "Pod must be deployed from compliant device"
      }
---
# ============================================
# 6. 持续监控: Falco 规则 (异常访问模式)
# ============================================
- rule: Unusual API Access Pattern
  desc: 检测用户突然访问平时不用的服务
  condition: >
    ka.verb in (get, list, watch) and
    ka.user.name != "" and
    not ka.user.name in (allowed_users)
  output: >
    异常 API 访问 (user=%ka.user.name
    verb=%ka.verb resource=%ka.target.resource
    source_ip=%ka.source.ip)
  priority: WARNING
  tags: [zero-trust, anomaly]
```

### 6.3 Google BeyondCorp 模型 (示意)

```python
# beyondcorp_trust_engine.py
"""BeyondCorp 信任算法示例"""

from dataclasses import dataclass
from typing import Dict, Optional
import time

@dataclass
class DevicePosture:
    managed: bool
    encrypted: bool
    patched_within_days: int
    av_running: bool
    last_scan: float

@dataclass
class UserContext:
    identity: str
    department: str
    mfa_verified: bool
    last_login: float
    risk_score: int   # 0-100

@dataclass
class AccessContext:
    ip: str
    geo: str
    time: float
    user_agent: str

class TrustEngine:
    def __init__(self):
        self.thresholds = {
            'low_sensitivity': 30,
            'medium': 50,
            'high': 70,
            'critical': 90
        }
    
    def compute_trust(self, user: UserContext, device: DevicePosture, 
                      ctx: AccessContext) -> int:
        """计算信任分 (0-100)"""
        score = 0
        
        # 1. 身份 (max 40)
        if user.identity:
            score += 10
        if user.mfa_verified:
            score += 15
        if user.department == 'engineering':
            score += 10
        if user.risk_score < 30:
            score += 5
        
        # 2. 设备姿态 (max 35)
        if device.managed:
            score += 15
        if device.encrypted:
            score += 10
        if device.patched_within_days <= 7:
            score += 5
        if device.av_running:
            score += 5
        
        # 3. 上下文 (max 25)
        if self._is_corporate_ip(ctx.ip):
            score += 10
        if self._is_working_hours(ctx.time):
            score += 5
        if ctx.geo in ['US', 'CN']:  # 预期国家
            score += 5
        if 'Chrome' in ctx.user_agent:
            score += 5
        
        return min(score, 100)
    
    def authorize(self, user, device, ctx, resource_sensitivity: str) -> bool:
        trust = self.compute_trust(user, device, ctx)
        threshold = self.thresholds[resource_sensitivity]
        
        # 持续验证: 信任分低于阈值 → 拒绝 + 触发重新认证
        if trust < threshold:
            self._trigger_reauth(user)
            return False
        
        return True
    
    def _trigger_reauth(self, user):
        """触发重新认证 + 通知"""
        print(f"User {user.identity} 信任分过低,触发重新 MFA")
    
    def _is_corporate_ip(self, ip: str) -> bool:
        return ip.startswith('10.')
    
    def _is_working_hours(self, t: float) -> bool:
        import datetime
        dt = datetime.datetime.fromtimestamp(t)
        return dt.weekday() < 5 and 9 <= dt.hour < 18
```

## 七、常见陷阱与最佳实践 ⚠️

| 陷阱 | 后果 | 对策 |
|------|------|------|
| 把零信任当产品买 | 仅装了 ZTNA 不是真零信任 | 视为架构哲学,持续迭代 |
| 一次性全切换 | 业务中断 + 用户抵触 | 渐进式 (先远程办公,再内网) |
| 仅做网络层 | 没解决身份/设备问题 | 多层并进 (身份+设备+网络+应用) |
| 信任分过于静态 | 攻击者获取高分后作恶 | 持续监控 + 异常重认证 |
| 设备姿态缺失 | 任何设备都能访问 | 强制 MDM + 姿态检查 |
| mTLS 不强制 | 明文流量可被窃听 | STRICT 模式 |
| Service Mesh 不开策略 | 任意服务可互访 | 默认 deny + 显式 allow |
| 不审计零信任决策 | 事后无法追溯 | 全部决策入 SIEM |
| 应用未改造 | 仍依赖网络位置 | 改造为基于身份 + Token |
| 旧应用兼容 | 无法用 ZTNA | 用代理 + Legacy 桥接 |

### 7.1 工程重点 (🔥)

1. **身份优先** — IdP 是零信任核心
2. **设备姿态必查** — MDM + 加密 + 补丁
3. **持续验证** — 不是一次登录,每次请求都验证
4. **mTLS 强制** — 服务间全程加密
5. **微分段** — Identity-Aware 网络分段
6. **默认拒绝** — 显式 Allow
7. **短期 Token** — 15-60 分钟过期

   - 要点:IdP + MFA;设备姿态 (MDM);访问代理 (PEP);信任算法;短期 Token;持续监控。

3. **Service Mesh 如何实现零信任?**
   - 要点:mTLS (服务身份);AuthorizationPolicy (L7 策略);默认 deny;证书自动轮换;SPIFFE 身份。

4. **零信任迁移的难点和路径?**
   - 要点:难点是应用改造、设备管理、用户体验;路径是先远程办公→内网关键应用→全应用;渐进式。

5. **SolarWinds 攻击中零信任如何防御?**
   - 要点:Golden SAML 伪造身份;零信任会持续验证设备姿态+行为;异常访问触发重认证;横向移动被微分段阻断。

6. **如何评估设备姿态?**
   - 要点:MDM/EDR;补丁状态;加密状态;AV 运行;上次扫描;合规检查 (CIS)。

7. **零信任的信任算法如何设计?**
   - 要点:多维输入 (身份+设备+上下文+行为);加权评分;动态阈值 (按资源敏感度);持续调整。

8. **微分段如何实现?**
   - 要点:Identity-Aware (SG 引用 SA);NetworkPolicy (Pod label);Service Mesh AuthorizationPolicy;基于应用而非网段。

9. **零信任在 Serverless 中的体现?**
   - 要点:FaaS 函数级 IAM Role (最小权限);每次调用独立凭证;无内网概念;事件源认证;默认就是零信任。

10. **如何检测零信任架构下的横向移动?**
    - 要点:服务间调用图 + 异常路径;UEBA 行为基线;Falco 运行时规则;持续验证中信任分骤降触发告警。
